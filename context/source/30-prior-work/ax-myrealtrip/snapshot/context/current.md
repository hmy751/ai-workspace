# current — 현재 그림

사용자의 현재 그림을 AI와 싱크하는 자리다. 지금 어디 서 있고, 무엇을 향하고, 어떤 생각 구조로 움직이는지를 AI가 매 세션 같은 그림으로 보게 한다.

> - 모든 대화와 작업을 관통하면서 계속 변한다. core가 거의 안 변하는 기준이라면, current는 계속 갱신되는 현재 위치와 방향이다.
> - current는 현재의 메모에 가깝다. core와 완벽하게 분리하려는 강박은 갖지 않는다 — 뼈대를 적다 보면 겹치기 마련이다. 겹침이 어긋남이 될 것 같을 때 정리하면 된다(원천을 정하고 가리키는 식으로).
> - 덮어쓰기 전용. 최신만 남기고 이력은 남기지 않는다(이력은 context/process/). 완결된 문서가 아니어도 된다.
> - 방향이 바뀔 때마다 갱신한다. AI가 갱신을 제안하고, 확정은 사용자가 한다.
> - 세션이 새로 시작되거나 대화가 꼬이면, AI는 과거 기록을 뒤지기 전에 이 파일부터 읽고 — 프로젝트가 뭔지, 어디까지 왔는지, 다음 할 일이 뭔지 먼저 설명한다. 사용자의 그림과 다르면 작업 전에 지도부터 고친다.
> - **이 문서의 본체는 지도 트리다.** 첫 뎁스는 큰 묶음 몇 개로 좁게, 아래로는 깊어져도 된다. 새로 알게 된 것·링크·가설은 트리의 맞는 가지에 그 자리에서 붙인다. 가지의 설명이 길어지면 트리에는 한 줄과 링크만 남기고 상세를 하단 섹션으로 뺀다.
> - 진행 표시는 커서 하나만 쓴다 — 백틱으로 감싼 `*-> 지금*`을 해당 가지의 불릿 바로 뒤에 둔다. 백틱이라 `*`가 서식으로 먹히지 않고 그대로 보이고, 리스트 개행도 안 깨진다. 단계의 게이트를 넘을 때 AI가 이동을 제안한다. 커서는 참고지 정답이 아니다 — 작업하다 보면 어긋날 수 있으니, 실제 위치가 커서의 전후 단계일 수 있다고 보고 유연하게 읽는다. 어긋나 보이면 작업 전에 커서부터 고친다. 끝난 가지는 지우지 않고, 미래 가지는 지금의 가설이라 지나며 고친다.
> - 가리킴 표기: 노드 끝에 `(→ 경로)` — context/와 .md는 생략(예: core/research), 같은 문서 안은 `(→ 아래 …)`, 두 곳이면 역할어를 붙인다 `(→ 규칙 core/research · 기록 research/)`.

## 실행 스캐폴딩 — 단계별 절차·게이트 (쓰면서 고친다)

지도의 각 가지를 실제로 굴릴 때 따르는 절차다.

- 게이트 보고는 채팅이 아니라 context/process/의 파일로 쓴다(시간순 번호-단계명). 사람은 그 파일을 읽고 게이트를 닫는다 — 기록 없이는 게이트를 넘지 않는다.
- 보고 파일의 고정 슬롯: 한 것 / 펼친 후보 / 기각한 후보와 이유 / 막힌 지점과 해결 / 검증 안 된 것. 해당 없으면 "없음"이라고 쓴다. 빠르게 읽히는 분량으로 짧게 유지한다.
- 게이트를 닫으면 커밋한다 — diff가 그 단계의 산출물과 기록을 보여주는 확인 지점이 된다.

### 룰 파악

- 과제 페이지(https://hack.primer.kr/rounds/10)를 정독하고, 제출 형식·5문항(글자수·도움말)·로그 규정·타임라인을 context/core/requirements.md와 대조해 달라진 점만 보고한다.
- 게이트: 사람이 원문을 같이 읽고 requirements.md 확정, context/sources/ 캡처 갱신.

### 리서치

- context/core/research.md의 가중치와 자료 보관 경계를 따른다. 자료 가중치는 읽기 전에 정한다. 조사 결과는 주장 단위(주장 → 근거 URL → 가중치 → 접근일)로 context/research/에 남긴다.
- 실무자 인터뷰 정리본(context/sources/)에서 회사가 직접 말한 문제의식과 방향을 근거 문장과 함께 뽑는다.
- 문제를 과장하지 않게 잡아주는 반대/보정 근거를 일부러 찾는다.
- 게이트: 뭘 찾았고 뭐가 부족한지 한 문단으로 보고 → 사람이 출처의 질(공식 채널인가)을 직접 확인.

### Problem Statement

- 문제 후보를 펼친다. 후보마다: 누가·언제·무엇에 막히는가 / 뒷받침하는 근거 문장 / 이 회사에 왜 중요한가. 아직 고르지 않는다.
- 첫 후보 구조에 고정될 위험이 크면 기존 후보판을 보지 않고 리서치 원자료와 현재 기준만으로 독립 추출한 뒤 대조한다. 새 추출에는 기존 후보와 같게·다르게 만들라는 목표를 주지 않는다.
- 관점 선택: 후보를 비교하며 누구의, 어느 순간의 문제인지 사람이 고른다.
- 크기 판단: 손실·마찰의 중요도, 반복성, 비즈니스 연결, 회사 방향 적합성, 과제 스코프 적합성을 축으로 본다. "너무 크지 않은가", "너무 작지 않은가", "기존 서비스의 작은 복제는 아닌가"도 함께. 숫자를 지어내지 않는다.
- 해커톤의 독창성·비즈니스성·데모 매력이 문제 선택을 바꿀 수 있으면, 최종 문제를 닫기 전에 근거가 성립하는 후보들의 plugin 개입 가능성을 짧게 확인한다. 본격 솔루션 설계로 넘어가거나 솔루션 매력으로 사용자 문제의 빈칸을 덮지 않는다.
- 닫기: 문항 1(누가·어떤 상황)·2(왜 이 문제)에 답이 되는지, 확신이 서는지 본다. 안 서면 리서치로 되돌아간다.

### Problem Solutioning

- 최종 문제를 닫기 전 비교에서는 성과 축을 탈락 기준이 아니라 생성 압력으로 먼저 사용한다. 문제 후보마다 같은 폭으로 솔루션을 펼치고 `개념 / Codex 개입 순간 / 입력 / 핵심 판단 / 출력 윤곽 한 줄 / 행동 변화 / 특히 노린 성과 축`을 남긴다.
- 첫 발산판을 수정하지 않고 같은 후보를 문제 직접성, 근거 연결, 행동 변화, plugin 이유, 범위·데이터·불확실성으로 다시 본다. 그 뒤 두 판을 함께 비교한다.
- 최종 문제를 닫은 뒤 살아남은 솔루션 후보를 본격 구체화한다. 이때도 바로 하나를 고르지 않고 Output-first 비교로 넘긴다.

### Output-first 비교

- 솔루션 후보를 이름과 기능 목록만으로 고르지 않는다. 각 후보마다 사용자가 무엇을 넣고 심사자가 어떤 결과를 바로 보는지, 출력 구조·판정 기준·데모 케이스(정상/예외/정보 부족)를 먼저 만든다.
- 이 단계의 출력은 비교용 초안이다. 아직 하나의 최종 출력 계약이나 goal로 고정하지 않는다.
- 실제로 유용한 결과가 나오지 않거나 정보 부족을 정직하게 처리할 수 없는 후보는 Prioritization 전에 약점이 드러나야 한다.

### Prioritization

- 실제 출력까지 확인한 후보 중 무엇을 구현할지 하나로 제한한다 — 객관적으로 가장 큰 게 아니라, 내 역량·시간 안에서 가장 잘 풀어낼 하나. AI는 내 진짜 역량 상한을 모르니 이 선택은 사람이 한다.
- 후보가 약하면 원인이 내가 앞서 건 제약일 수 있다. 스코프를 잡아주는 가드레일이 야심까지 같이 줄이고, AI는 내 제약을 그대로 반영한다. 원인을 짚고 반대 방향으로 압력을 걸어 재선정시킨다. 얼마나 키울지·무슨 축으로 재선정할지는 그때 정한다.
- 닫는 감각: 문제 근거, 실제 출력의 유용성, 구현 가능성을 함께 본다. 취향과 근거가 갈리면 근거 쪽으로.
- 선택 뒤 출력 구조·판정 기준·데모 케이스를 최종 계약으로 확정하고 지도의 goal을 만든다. 여기부터 구현 순서는 핵심 가설이 가장 빨리 검증되는 순서로 잡는다.

### 구현 루프

- context/core/loop.md의 틀 그대로: 바퀴 시작 블록 → 구현 → 판별(실입력 검증 + 리뷰어 판별) → 기준 갱신.
- 사람이 매 바퀴 확인한다. "될 때까지 알아서 진행"으로 통째로 맡기지 않는다.
