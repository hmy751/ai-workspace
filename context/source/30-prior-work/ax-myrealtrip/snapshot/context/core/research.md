# 리서치

조사를 어떻게 하는지의 규칙이다: 출처 가중치, 반복 루프, 중단 조건, 자료 보관 경계.

## 출처 가중치 (높은 순)

1. 과제 공식 자료 (과제화면 원문·공식 안내)
2. 출제 기업의 직접 발화 (공식 인터뷰 영상·공식 기술블로그·공식 문서)
   - 이 등급 안에서는 **이번 해커톤 공식 소개 영상에 나온 마이리얼트립의 직접 발화**를 최우선으로 둔다. 출제 맥락에서 회사가 직접 밝힌 문제의식·방향이므로 다른 일반 인터뷰나 공식 문서보다 과제 의도와 가깝다.
   - 그다음에 다른 공식 인터뷰, 공식 기술블로그, 공식 문서를 둔다.
3. 서비스 원문 (상품 상세·고객센터 규정 — 문제와 직접 닿을 때 강한 근거)
4. 커뮤니티·후기 (보조 근거로만 — 생생한 사례로 쓰되 문제 크기의 핵심 근거로 쓰지 않는다)

- 가중치는 자료를 읽기 전에 정한다 — 나중에 정하면 결론에 맞는 자료가 가중치를 얻는다.
- 반대/보정 근거 자리를 상설로 둔다 — 문제를 과장하지 않도록 잡아주는 자료를 일부러 찾는다.
- 모든 근거는 공개 URL로 재접근 가능해야 한다. 근거마다 접근 날짜를 남긴다.
- 로컬 정리본은 발화 탐색과 재검토의 진입점이고, 문항 2의 제출 근거로 쓰기 전에는 해당 공식 영상의 공개 URL을 연결한다.

## 루프 (조사하고 끝내지 않는다)

조사 → 정함(주장 단위로 근거 연결) → 다음 단계 넘어갈 때 "이 판단이 아직 근거 위에 서 있나" 확인 → 부족하면 재조사 → 갱신

## 반복 브라우저 조사 — 품질을 유지하며 빠르게 보기

같은 질문을 여러 상품·페이지에 반복 적용할 때 쓴다. 목적은 단순 병렬화가 아니라, **판단과 반복 추출을 분리해 품질을 유지하면서 조사 시간을 줄이는 것**이다.

### 1. 추출 전에 판단 틀을 고정한다

- main이 먼저 이번 조사로 바뀌어야 할 판단과 비교 질문을 정한다.
- 모든 URL에 공통으로 쓸 기록 칸과 판정값을 고정한다.
- 기본 기록 칸은 `확인한 사실 / 화면 위치·구역 / 판정 / 확인 불가 / 현재 접근·판매 상태`다.
- 추출 단계에서 하지 않을 판단도 적는다. 보통 원인, 문제 크기, 사업 영향, 사용자 대표성, 솔루션은 보류한다.
- 첫 소수 표본으로 기록 칸이 실제 화면에 맞는지 확인한 뒤 일괄 수집한다. 틀이 틀렸으면 표본을 늘리기 전에 고친다.

### 2. 반복 추출은 URL별로 독립 병렬화한다

- 상품·페이지 하나를 한 작업 단위로 나누고 모두 같은 기록 형식으로 수집한다.
- 이 단계의 `낮은 추론`은 모델 설정값을 뜻하지 않는다. 정해진 칸에 직접 보이는 사실과 확인 불가만 옮기고, 새로운 문제 정의나 해석을 만들지 않는다는 뜻이다.
- URL, 페이지 제목, 접근일, 현재 판매·공개·휴면·삭제 상태를 먼저 확인한다. 현재 상태가 다르면 같은 표본으로 합치지 않는다.
- 문구가 있다는 사실뿐 아니라 상단에서 보이는지, 한 구역에서 닫히는지, 여러 구역을 합쳐야 하는지, 문의가 필요한지까지 기록한다.
- 병렬 작업은 서로 독립된 URL·탭·읽기 전용 접근으로 나눈다. 같은 in-app browser 탭을 여러 작업이 동시에 클릭하게 하지 않는다.
- 로그인, 문의 전송, 옵션 확정, 장바구니, 결제처럼 외부 상태를 바꾸는 행동은 조사 범위에 명시적으로 필요하고 승인된 경우가 아니면 하지 않는다.

### 3. main이 높은 추론으로 한 번에 종합한다

- 실제 확인한 사실과 작업자의 추정을 분리하고, 수치·인용·현재 상태·충돌 문구는 main이 다시 확인한다.
- 공통 패턴뿐 아니라 간단히 해결되는 반대 사례와 이미 해결된 경로도 함께 본다.
- 휴면·삭제·구버전 표본은 현재 서비스 근거에서 제외하고, 필요하면 같은 비교축의 현재 표본으로 교체한다.
- 문의가 필요하다는 사실을 곧바로 실패로 해석하지 않는다. 문의가 정상 해결 경로인지, 문의로도 닫히지 않는지, 오판·추가 행동과 연결되는지를 따로 본다.
- 의도적으로 고른 소수 표본의 칸 개수는 발생률이나 문제 규모로 일반화하지 않는다.

### 4. 다음 일괄은 판단을 바꿀 빈칸만 다시 본다

- 첫 결과 뒤 비교 질문·표본·계획을 수정하고, 결론을 바꿀 수 있는 미확인 항목만 재조사한다.
- 첫 묶음에서는 main 확인과 독립 추출을 일부 겹쳐 틀을 보정할 수 있다. 틀이 안정된 뒤에는 전체를 중복 조사하지 않고 상태·수치·인용·충돌만 표본 검사한다.
- 새 정보가 현재 판단을 바꾸지 못하면 조사를 늘리지 않고 중단 조건을 적용한다.

이 흐름의 기본형은 다음과 같다.

> 높은 추론으로 질문·기록 칸 고정 → URL별 낮은 추론 병렬 추출 → main의 높은 추론 종합·계획 수정 → 판단을 바꿀 빈칸만 재조사

## 중단 조건

- 핵심 주장마다 강한 근거 1개 + 보조 근거 1개가 붙으면 일단 닫는다.
- 새 정보가 판단을 바꿀 것 같을 때만 다시 연다.
- 이 기준은 써보며 조정한다.

## 기록

- 조사 산출물은 context/research/에 남긴다. 주장 단위 기록(research-log): 주장 → 근거 URL → 가중치 → 접근일.

## 자료 보관 경계 — research와 sources

- 조사한 근거는 우선 전부 context/research/의 기록에 남긴다.
- 다음 중 하나에 해당하면 원문을 context/sources/에 저장하고, 기록에서 그 파일을 가리킨다:
  1. 판단이 특정 문구나 수치에 기대는 자료 — 그 문장 자체가 근거인 것
  2. 바뀌거나 사라질 수 있는 페이지 — 상품 상세, 고객센터 규정, 커뮤니티 글
  3. 구현이나 샘플 입력의 원천이 되는 자료
- 안정적인 공식 문서와 배경 참고는 URL과 접근일만 남긴다. 단 문서 버전이 판단에 영향을 주면 의존한 문장과 확인일을 함께 남긴다.
- 저장할 때는 파일명에 날짜를 붙이고, 안에 원문(또는 판단에 쓰인 부분)과 URL, 접근일을 함께 둔다.
- 문항 2의 출처는 심사 AI가 직접 여는 공개 URL이어야 한다. context/sources/ 스냅샷은 우리 검증용이지 URL을 대체하지 않는다.
