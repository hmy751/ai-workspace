# 구현 루프

spec은 무엇을 만들지 미리 정하는 앞단 장치다. 앞단만 있으면 구현 후의 고치기는 일회성 수정에 그치고, 만든 것의 품질을 끌어올리는 장치가 없다. 이 문서가 그 뒷단 장치다.

루프가 도달하려는 상태는 **사용자의 평가 기준과 에이전트의 평가 기준의 일치**다. 일치될수록 에이전트가 기준에 맞춰 스스로 확인하며 결과에 도달할 때까지 반복할 수 있고, 사람은 기준이 어긋나는 지점에서만 개입한다.

## 루프가 돌기 위한 세 조각

- **loop goal과 평가 축** — 이 바퀴가 최상위 goal의 어느 상태로 올라가는지. 없으면 판별할 대상이 없고 루프는 방향 없는 반복이 된다. 작업마다 달라지므로 미리 박지 않고 매 바퀴 새로 정한다.
- **판별자** — 작업 맥락 밖의 눈. 판별을 사람이 혼자 지면 사람이 지적한 부분만 고쳐지고, 개선의 상한이 사람의 판별 범위에 묶인다.
- **틀의 상시 유지** — 이 순서는 세션이 길어지거나 바뀌어도 유지되어야 돈다. 그래서 이 문서는 core에 있고, 매 세션 시작 시 읽힌다.

이 문서는 틀(순서와 이유)만 고정한다. 최상위 goal의 내용은 engineering에서 최신으로 유지하고, loop goal·평가 축·검증 증거는 매 바퀴 새로 채운다.

## 최상위 goal과 loop goal

- **최상위 구현 goal**은 여러 바퀴가 함께 도달할 관찰 가능한 최종 작동 상태다. 프로젝트마다 다르므로 core에 내용을 두지 않고 `context/engineering/00-top-level-goal.md`에서 최신 상태를 유지하며, `current.md`는 한 줄 요약과 링크만 가진다.
- **loop goal**은 최상위 goal에서 이번 바퀴가 새로 가능하게 만들거나 가장 먼저 검증할 한 조각이다. `context/engineering/NN-loop-NN-goal.md`에 목표·범위·평가 기준·검증 증거를 현재 구현 계약으로 쓰고, goal을 정하거나 바꾼 이유는 `context/process/`의 시간순 기록에 남긴다.
- 완료된 loop goal 문서는 어떤 계약으로 구현했는지 볼 수 있게 engineering에 번호순으로 보존한다. 다만 완료된 문장을 현재 지시로 계속 쌓지 않으며, 활성 loop는 current의 커서 하나로 가리킨다. 검증된 능력과 실제 증거는 process에 축적하고 이후에도 지켜야 할 평가 기준만 최상위 goal이나 current의 최신 기준으로 승격한다.
- 최상위 goal도 구현 증거가 전제를 뒤집으면 바꿀 수 있다. 조용히 고치지 않고 `이전 goal → 새 goal`과 계기를 process에 남긴다.

## 한 바퀴

goal 설정 → 구현 → 판별 → 기준 갱신 → 다음 바퀴 goal 설정

**goal 설정** — 이 바퀴가 끝나면 무엇이 달라져 있어야 하는지 정한다. engineering의 해당 loop goal 문서에 아래 계약을 채우고, 선택 이유·대안·기각·미검증 사항은 같은 시점의 process 기록에 남긴다.

- 루프 번호
- 목표
- 평가 기준 — 금지 조건 나열이 아니라 도달할 품질(행동 변화, 재현성, 임팩트)로
- 검증 증거 — 무엇을 확인하면 통과인지, 케이스·실행 명령 단위
- 다음 루프 조건 — 무엇이 확인되면 멈추고, 무엇이 남으면 더 도는지

**구현** — goal에 맞춰 만들고 고친다.

**판별** — 두 갈래로 본다.

- 실입력 검증: 샘플, 실제 URL, 자연어 요청 같은 실제 입력으로 실행하고, 명령과 결과를 그대로 기록한다. 이 기록이 문항 5의 재료다.
- 리뷰어 판별: 작업 맥락이 없는 새 세션/서브에이전트에 결과물만 주고 평가시킨다. 작업한 세션은 자기 결과물과 쌓인 맥락에 맞춰 평가하기 쉽다. 평가 축은 판별자가 먼저 제안하고 사용자가 고른다. 통과가 아니면 무엇이 채워지면 통과인지 조건 목록을 받는다. 결과는 빠르게 읽히는 짧은 리포트로 받는다. 기준을 승격할 때마다 투입하고, 제출 직전 한 번으로 미루지 않는다.

**기준 갱신** — 루프의 핵심 마디. 판별 결과를 두 갈래로 나눈다.

- 결과물 보정: 이번 바퀴에서 고칠 것 → 다음 구현으로.
- 기준 갱신: 그 판단을 평가 기준 자체에 반영 → 다음 판별로.

결과물 수정 지시로 끝내면 그 한 번으로 끝나지만, 기준을 고치면 다음 바퀴부터 에이전트가 같은 지점을 스스로 확인한다. 판별에 든 비용이 기준으로 남아 재사용된다.

- 기록: "이전 기준 → 갱신 기준" 쌍과 갱신 계기 한 줄을 context/process/에 남긴다.
- 반영: 현재 loop 계약은 engineering의 해당 goal 문서, 여러 loop가 공유할 기준은 최상위 goal, 현재 위치는 context/current.md에 반영한다. 최신 기준이 process의 시간순 기록에만 남으면 다음 바퀴가 옛 기준으로 돈다 — 기준을 늘 곁에 두는 이유다.

**사람의 개입** — 매 바퀴 사이에 사람이 확인하고 다음 바퀴를 정한다. 멈춰서 봐야 할 지점(기준 승격, 방향 전환)은 미리 정해 둔다. "될 때까지 알아서 진행"으로 통째로 맡기지 않는다.

## 제출 직전 마지막 바퀴

- 평가 축은 문항 1~5의 도움말을 그대로 쓴다. 도움말이 각 답변에 들어가야 할 요소를 지정하고 있다 (정리판: context/core/requirements.md).
- 작업 맥락이 없는 판별자에게 제출물만 주고 도움말 기준으로 채점시키고, 부족한 항목을 보강한다.
- 평가는 AI와 심사자가 함께 하므로, 사람이 읽었을 때 자연스러운지도 확인한다.
