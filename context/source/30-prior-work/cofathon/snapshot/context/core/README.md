# core — 프로젝트 전반의 현재 기준판

core는 현재 커서가 어느 단계에 있든 프로젝트 전체에 계속 깔려 있어야 하는 기준을 둔다. 불변 아카이브는 아니며, 실제 작업에서 여러 단계가 함께 따라야 할 기준이 달라졌다면 이유를 남기고 최신판으로 고칠 수 있다.

프로젝트의 Mission과 Campaign Goal은 core가 아니라 [goal](../goal.md)이 소유한다. `current.md`는 그 요약·링크, 실제 진행 위치, 현재 판별 질문과 단일 커서를 유지한다.

## 현재 구성

- [requirements.md](./requirements.md) — 지원·행사 전 과정에서 계속 확인해야 할 공식 요구사항과 공개되지 않은 제약
- [support-evidence-artifact.md](./support-evidence-artifact.md) — 문제 설정부터 지원 제출까지 계속 적용하는 플러그인 지원 증거물의 형태·증거 계약·열린 경계
- [candidate-exploration-judgment-order.md](./candidate-exploration-judgment-order.md) — 발산·교차 중의 주장별 근거 판단과 마지막 수렴의 후보 단위 선택·종료를 분리하는 기준
- [loop.md](./loop.md) — 활성 Goal의 다음 판별 질문·구현 loop를 고르는 바깥 반복과, 구현 결과를 사람·원근거·에이전트 평가로 대조해 기준과 다음 반복 목표를 함께 보정하는 안쪽 반복의 운용
- [dev-principles.md](./dev-principles.md) — 구현 편의보다 사람의 결과 변화와 검증 가능성을 먼저 키우고, 의미 판단·결정론적 실행·output-first·실입력 검증을 가르는 기준
- [research.md](./research.md) — 같은 질문을 여러 공개 페이지에 반복 적용할 때 main의 판단과 페이지별 사실 추출을 분리하는 조사 계약

위 목록은 현재 활성 기준 문서다. 세션 시작과 단계 전환 시 관련 문서를 실제로 읽고 적용한다. [engineering/](../engineering/README.md)은 최상위 구현 Goal과 활성 loop Goal, 구현 기록으로 가는 입구다. loop Goal은 최상위 Goal 합의 뒤 독립 계약이 필요할 때만 만든다.

필요할 것 같다는 이유로 빈 기준 파일을 미리 만들지 않는다. 특정 단계에서 생긴 판단은 해당 단계의 현재판에서 먼저 다듬고, 다른 단계에서도 계속 참조해야 한다는 사실이 확인될 때 core 승격을 검토한다.

## 읽는 경로

- Goal의 완료 상태를 정하거나, 현재 판별 질문을 고르거나, 구현 loop 안에서 평가 기준과 다음 반복 목표를 갱신하거나, 반복을 닫거나, 새 증거로 Goal을 다시 열 때 `loop.md`를 읽는다.
- 후보를 발산·교차·수렴할 때는 `candidate-exploration-judgment-order.md`를 읽고, 한 판별 실행의 실패를 후보 전체의 종료로 바꾸지 않는다.
- 문제–솔루션의 가치·출력·역할·검증 경계를 정하거나 단계가 전환될 때 `dev-principles.md`를 읽는다.
- 공식 요구를 해석하거나 제출 상태를 닫을 때 `requirements.md`를 라이브 원문과 함께 다시 본다.
- 같은 질문을 여러 공개 페이지에 반복 적용할 때만 `research.md`를 열어 판단과 사실 추출을 분리한다.
- 각 단계의 현재 사실과 판단은 core가 아니라 `research/`, `problem/`, `solution/`, `engineering/`의 현재판에서 읽는다.

## 판단 감각

좋은 예:

- 지원 문항·트랙·행사 시간·제출 제약은 리서치부터 제출 직전까지 계속 영향을 주므로 core에 둔다.
- 실제 작업에서 반복 확인된 운용 틀이 문제 선정·구현·검증 모두에 같은 방식으로 필요해지면, process에 승격 이유를 남기고 core에 최신 기준을 둔다.
- 여러 단계가 같은 Goal 아래에서 상태를 보고 다음 판별 질문과 실행을 다시 고르는 운용 틀은 core에 둔다. 실제 Goal 내용은 프로젝트별 소유 문서에 둔다.
- Mission·Campaign Goal은 [goal](../goal.md)이 소유한다. 엔지니어링은 실제 단계가 열릴 때 최상위 구현 Goal을 만들고, 독립 계약이 필요한 loop Goal만 추가하며, [engineering/](../engineering/README.md)을 현재 문제–솔루션에 맞게 갱신한다.

맞지 않는 예:

- Cofathon 자료에서 도출한 `50/40/7/3`을 반복해서 쓴다는 이유만으로 core에 둔다. 이는 현재 리서치 대상과 출처 구성이 만든 판단값이다.
- 현재 후보, 선택 직전 비교축, 프로젝트 Goal의 실제 내용을 다음 세션에도 볼 것이라는 이유만으로 core에 둔다. 이 내용은 각각 단계별 현재판, `current`, 프로젝트 Goal 문서가 소유한다.
- 바뀔 가능성이 있다는 이유만으로 core에서 뺀다. core도 바뀔 수 있으며, 핵심은 변화 가능성이 아니라 적용 범위다.

새 기준을 core에 넣기 전에 묻는다.

- 현재 커서가 다른 단계로 이동해도 이 기준을 계속 들고 있어야 하는가?
- 특정 조사·후보·구현의 현재 결론이 아니라 프로젝트 전반의 운용 기준인가?
- 단계별 `00`에 두면 다음 단계가 실제로 같은 기준을 놓치게 되는가?
- 아직 한 단계에서 시험 중인 판단을 너무 일찍 승격하는 것은 아닌가?

## 다른 문서 층과의 경계

- `current.md` — 전체 지도와 현재 위치·방향
- [goal](../goal.md) — Mission·Campaign Goal의 현재판, 상위 완료 상태와 엔지니어링 단계의 관계
- `research/00-current-synthesis.md` — Cofathon 리서치의 현재 종합과 출처 근거판
- `problem/`, `solution/`, [engineering/](../engineering/README.md) — 각 단계의 현재 산출물과 계약
- `process/` — 기준이 생기거나 바뀐 이유의 시간순 이력
- `sources/` — 다시 확인해야 할 원문과 최소 발췌

## 갱신 규칙

- 조용히 바꾸지 않는다. 바뀐 이유와 영향을 `process/`에 먼저 남긴다.
- core에는 최신 기준만 두고, 이전 기준과 변화 과정은 process에서 확인한다.
- 공식 제약이 바뀌면 원문을 먼저 다시 확인하고 관련 단계의 문서도 함께 대조한다.
- 우리의 추론을 공식 요구사항처럼 적지 않는다.
