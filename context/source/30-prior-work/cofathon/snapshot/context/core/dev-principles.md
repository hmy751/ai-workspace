# 개발·작업 원칙

상태: **현재 프로젝트 전반에 적용하는 개발·작업 기준**

한 줄 원칙: **사람의 중요한 결과를 바꾸고, 그 변화가 왜 생겼는지 다시 확인할 수 있게 만든다.**

이 문서는 특정 후보·Goal·제출 문구를 정하지 않는다. 문제를 구체화하고, 해결 범위를 정하고, 구현·검증할 때 반복해서 사용할 판단 감각만 둔다.

## 만드는 것에 대한 감각

- 기술 구성을 보여주는 전시물이 아니라 실제 workflow에서 판단·행동·산출물 중 중요한 결과를 바꾸는 것을 만든다.
- 이름, 기능 목록, host로 일찍 닫지 않는다. 기준은 `누구의 어느 순간에 무엇이 달라지는가`다.
- model·agent·MCP 수를 가치나 AI Native 역량의 대리 지표로 쓰지 않는다. 문제 해결과 검증에 필요한 구성만 쓴다.
- 산출물의 단위는 정보량이 아니라 행동 변화다. 근거와 다음 행동이 좁혀지지 않는 요약은 결과로 세지 않는다.

## 가치를 키우는 발산

- 발산은 아무 자료나 더 읽거나 기능을 늘리는 일이 아니다. 더 중요한 사람의 결과, 더 결정적인 개입 순간, 함께 있어야 가치가 생기는 조합, 기존 해결 뒤에도 남는 실패를 찾는 일이다.
- 후보 발산에서는 기존 순위나 결합 조건으로 새 가능성을 조기 종료하지 않는다. 발산·교차 중의 근거 판정과 마지막 후보 단위 수렴의 상세 순서·종료 기준은 [후보 탐색의 판단 순서](./candidate-exploration-judgment-order.md)가 소유한다.
- 구현하기 쉬운 범위로 아이디어의 가치를 먼저 줄이지 않는다. 먼저 강한 결과 변화와 증명 가능한 장면을 찾은 뒤, 그 가치를 보존하는 자연스러운 행동 단위를 정한다.
- 약해 보일 때는 기능을 옆으로 붙이기 전에 출력의 중심을 올린다. `더 많은 정보`가 아니라 `더 나은 판단·다음 행동·실제 결과`가 되는지 본다.
- 흥미롭다는 이유로 근거보다 큰 문제나 효과를 말하지 않는다. 가치의 크기와 증거 강도를 분리한다.

## 사실·가설·실행을 구분한다

- 조사 사실, 문제에 대한 추론, 해결 가설, 승인 상태, 구현 결과를 한 사실처럼 섞지 않는다.
- 문제와 솔루션은 서로 수정하며 왕복할 수 있지만, 좋은 해결 아이디어가 약한 문제 근거를 대신 승인하지 않는다.
- 단계나 분석마다 지금 결정하지 않는 것을 남긴다. 범위는 선언보다 보류 항목으로 더 잘 지켜진다.
- 새 증거가 앞선 전제를 뒤집으면 이미 지나온 판단도 다시 연다.

## 의미 판단과 반복 가능한 실행을 가른다

- AI는 맥락·관계·불확실성을 해석하고 사람이 이해할 설명과 질문을 만든다.
- 코드·규칙·테스트는 같은 입력에서 같아야 하는 중간 결과, 계산, 상태 전이, 형식 검사를 고정한다.
- 가르는 질문은 **같은 입력에서 같은 중간 결과가 나와야 하는가**다.
- 규칙으로 충분한 일을 다시 LLM 호출로 감싸거나, 결정론적 코드가 AI 판단을 어설프게 흉내 내게 하지 않는다.
- 현재 실행 주체의 AI 판단과 결정론적 실행으로 충분하면 별도 model API·LLM service·agent pipeline을 기본 구성으로 더하지 않는다. 재현성, 로그·비밀정보, 운영 범위를 넓히는 비용보다 핵심 결과 변화가 커야 도입할 수 있다.
- 현재 host 밖에서 독립 실행해야 하거나, 대량 의미 분류·검색이 핵심이거나, 규칙만으로 핵심 품질을 만들 수 없거나, 외부 실시간 데이터와 model 판단을 자동 연결해야 할 때는 별도 model 도입을 다시 검토한다. 이때도 필요한 범위와 검증 방법을 먼저 정한다.
- 사람이 최종 승인하거나 책임지는 판단을 자동화된 것처럼 숨기지 않는다.

## Output-first

- 구현 전에 대표 입력, 현재 방식, 개입 지점, 달라질 결과, 근거, 사람의 다음 행동을 먼저 그린다.
- 최종 출력과 수락 기준이 잡히기 전에 기능 목록으로 범위를 정하지 않는다.
- 핵심 가치 가설이 가장 빨리 틀렸다고 판정될 수 있는 순서로 구현한다.
- 서로 다른 행동 조건은 서로 다른 출력과 다음 행동을 가져야 한다. 예를 들어 정상 진행, 추가 질문으로 해소 가능한 불확실성, 반드시 멈춰야 하는 불확실성을 같은 요약으로 평평하게 만들지 않는다.

## 근거와 정보 부족

- 공식 요구, 공개 사실, 로컬 경험, 사용자 판단, 앞으로 검증할 가정을 구분한다.
- 검증하지 않은 수치와 단정 표현을 쓰지 않고, 의도적으로 고른 소수 사례를 발생률이나 대표성으로 일반화하지 않는다.
- 확인할 수 없는 것은 그럴듯한 이야기로 채우지 않는다. `확인됨 / 추정 / 확인 불가`를 가르고, 무엇을 확인하면 판단이 달라지는지 적는다.
- 정보 부족이나 실행 실패를 조용히 삼키지 않는다. 실패 이유와 함께 확인 질문, 대체 경로, 안전한 중단 중 지금 가능한 다음 행동을 보여준다.
- 질문으로 해소할 수 있는 불확실성과 행동을 멈춰야 하는 불확실성을 구분한다. 확인 전에는 둘을 모두 최대 경고나 임의 진행으로 평평하게 만들지 않는다.
- 반대 사례와 이미 해결된 경로를 함께 본다.
- 뺀 기능, 다루지 않은 환경, 미검증 범위와 그 리스크를 드러낸다.

## 검증과 재현

- 문서 설명과 mock만으로 작동을 증명하지 않는다. 실행이 증거다.
- 내가 만든 샘플뿐 아니라 통제 밖의 실제 입력을 최소 한 번 통과시킨다.
- 중간 판정 하나가 아니라 대표 workflow가 입력부터 사람의 다음 결과까지 도는지 본다.
- 재현은 받는 사람의 환경을 기준으로 한다. 받는 사람이 실행할 경로는 절대경로·특정 OS 전용 명령에 기대지 않고, 개발 형태의 직접 실행과 plugin을 설치한 뒤 연 새 세션 같은 최종 소비 형태의 통과를 구분한다.
- 수정 전후는 같은 시나리오·입력과 Goal의 안정된 제약에서 비교한다. 새 근거로 평가 기준을 보정했다면 보정된 기준을 이전 결과와 새 결과에 똑같이 적용하고, 현재 결과를 통과시키기 위해 기준을 낮추지 않는다.
- 작업 맥락 밖 판별이 필요할 때는 결과물과 원자료 접근점을 주고, 예상 결론은 주지 않는다. 새 세션만으로 독립성을 대신하지 않으며, 판별자가 main의 질문·평가 범위를 기각하거나 필요한 증거 범위를 다시 정할 수 있게 한다.

## skill과 plugin

- `SKILL.md`는 소개문이 아니라 AI가 실제로 따를 지시다. 발동 조건, 입력, 절차, 판단 기준, 출력, 사람 승인, 실패 대응이 이어져야 한다.
- description은 trigger다. 언제 쓰고 언제 쓰지 않는지 분명해야 한다.
- 요구항목은 `공식 필수 / 목표 달성이나 host 호환에 사실상 필요 / 선택 / 범위 밖`으로 나눈다. `사실상 필요`는 공식 요구가 아니라 현재 조건에서 도출한 판단임을 밝히고, 이유와 검증 대상을 함께 남긴다.
- MCP, app, hook은 형식에 있으므로 붙이는 것이 아니라 핵심 문제 해결에 필요할 때만 쓴다.
- 사용자가 플러그인 개념을 몰라도 설치를 전제하지 않는 첫 접촉에서 대표 요청·결과·근거 경로를 확인할 수 있어야 한다. 구체 소비 형식이 README인지 다른 공개 결과물인지는 지원 제출 단계에서 정한다.
- 형식 스펙은 구현 착수 전과 최종 소비 형태 검증 전에 공식 문서에서 다시 확인한다.

## 흔들릴 때 묻는 질문

1. 누구의 어느 순간에 어떤 결과가 달라지는가?
2. 구현 편의가 가치의 크기를 먼저 줄이고 있지 않은가?
3. 이 산출물은 정보를 늘리는가, 다음 판단과 행동을 바꾸는가?
4. 같은 입력에서 같아야 할 것과 맥락에 따라 달라질 것을 제대로 갈랐는가?
5. 근거보다 강하게 말하거나 작은 표본을 일반화하고 있지 않은가?
6. 정상·반례·실패를 통과시키며, 실패 이유와 다음 경로가 실제로 보이는가?
7. 받는 사람이 첫 접촉에서 이해하고 실제 소비 형태에서 재현할 수 있는가?
8. 외부 model이나 통합을 더한 이유가 핵심 결과 변화에 직접 필요한가?
9. 공식 필수와 사실상 필요를 섞어 말하고 있지 않은가?
