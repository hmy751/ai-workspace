## 입력 손실과 문서 작성 문제

Main의 실제 대화에는 테스트 배치·설정 선택의 이유와 비용이 있었지만, Maintainer에게 전달한 수동 요약에는 상당 부분이 선택 결과로만 남았다. 당시 대화는 Maintain 연결 전 구간이었고 자동 과거 수집 대상이 아니었다. Main은 이전 대화 전체를 검토한다고 안내한 뒤 요약을 전달했으므로, 이 결과를 자동 Maintain의 원문 처리 실패와 동일하게 평가할 수 없다.

별도로 작성 결과에서는 설정 이름과 처리 출처 설명이 두드러지고, 독자가 선택을 재검토할 이유와 조건은 짧게 압축됐다. 앞선 작성 지침은 실제 Maintainer grounding에 포함돼 있었으므로 지침 전달 누락은 아니었다. 기존 기준의 미준수와 내용 충분성 판단의 보완 필요를 함께 다뤘다.

이 판단에서 확인한 원문은 Main session `01a08ff3-0e91-7921-afe4-69f0968638ef`의 대화와 수동 전달 입력, Maintainer session `01a0902d-4f7e-7681-a9ad-288d60bb9997`의 입력·결과다. 비교의 최소 근거는 다음과 같다.

- 원래 설명은 별도 `tests/` 배치의 장점으로 제품 타입 설정과의 분리를, 비용으로 구현과 테스트의 물리적 분리를 제시했다. 수동 전달에는 별도 `tests` 아래 source 소유 구조를 따르는 배치 결과만 담겼다.
- 테스트 전용 타입 설정은 유지할 회귀 테스트의 타입까지 검사할지와 설정 관리 비용을 비교했다. 전달 요약과 기록에서는 이 이유가 “필요시”로 줄었다.
- Maintainer는 원대화 대신 요약을 받았다고 밝히고 Ticket 03·records 색인과 decision schema를 읽었다. 출처를 과장하지 않은 점과 요청한 논의 내용을 충분히 보존했는지는 별개의 판단이다.

## 분리한 책임과 보완 내용

Workspace collection README의 긴 작성 기준을 같은 경계의 `DOCUMENT-WRITING.md`로 옮겼다. README에는 Workspace 내부 관계, 기존 record의 append-only 보존과 각 관리 기준의 진입점을 남겼다. 새 문서는 Workspace 문서와 운영 지침 전반의 작성 기준이며 Spec·Ticket만의 서식이나 특정 Maintainer의 prompt 규칙으로 한정하지 않았다.

작성 기준은 문서 목적에 필요한 설명, 자료의 충분성, 선택 이유·비용·적용 조건을 보존하는 압축, 정보의 비중과 읽기 흐름, 기존 내용에 통합하는 갱신을 다룬다. 경로·설정 이름만 남은 논의와 선택 이유를 복원할 수 있는 논의를 예로 구별했다. 고정 목차나 모든 문서에서 선택지 표를 만드는 의무는 두지 않았다.

Spec·Ticket과 생성·전환 기준, Work 운영 진입점은 새 문서로 연결했다. Maintain은 이 기준을 적용하고, 허용된 자료로 요청한 기록을 완성할 수 없으면 빠진 의미와 필요한 자료를 `unresolved`에 반환하는 책임을 갖는다. Guard는 기존 부작용·형식 검사 범위를 유지한다.

사용자는 본문을 실제 입력에 넣으면 중복되는지 물었다. 지침 원본은 한 파일에만 유지하고 자동 경로가 그 파일을 읽어 주입하도록 했다. 본문을 받은 agent에게 같은 파일을 다시 읽도록 요구하지 않으며, 본문이 없는 수동 경로에서 직접 읽는다. 매 후속 응답에 계약 전체를 다시 주입하는 기존 구조는 이번에 변경하지 않았다.

글로벌 `ai-system_*` reference는 책임 경계·응집·사람용 진입·판단 배치·제거 가능성을 대조하는 읽기 전용 기준으로 사용했다. 작성 지침은 Workspace에 남고 Maintainer는 이를 소비하므로 실행 장치를 바꿔도 작성 기준을 다시 만들 필요가 없다. 글로벌 파일은 수정하지 않았다.
