# 합의: 코드 범위별 Ticket과 분석 주제의 검토 범위를 함께 관리

대상 Workspace: `002-code-readability-refactoring`
Main session: `01a08b64-7f25-7972-ac3e-496cb4af1de7`

## 사용자 정정과 채택

사용자는 다음과 같이 Ticket 경계 질문의 뜻을 정정했다.

> 아니 초기 분석보면 바텀부터 올라가잖아? 주제라고 해야하나?
> 왜물어봤냐면 경비 합계 표시 이러니까 아까 주제 단위가 아니라 주제들을 포함하는 경계단위인것 같아서 그게 티켓 경계같고

Main은 이를 분석의 개선 관점과 실제 코드 작업 범위의 관계로 다시 이해했다. 앞서 전체 후보가 모두 티켓화되었는지를 묻는 것으로 해석했던 답변은 이 질문의 뜻을 잘못 짚었다. 이어 사용자가 “그럼 궁금한게 이렇게 해나가면면 분석에서 본 주제를 다 다룰수 있는거지? 최대한?”이라고 물었고, Main은 개별 Ticket 수행과 전체 분석 주제의 검토 범위를 함께 관리하는 방식을 설명했다.

사용자는 다음과 같이 진행 방식을 채택하고 기록을 요청했다.

> 그래 좋아 그럼 이렇게 진행하는걸로 알게 기록 남기고 티켓 확인좀 하고 있을게

## 합의된 진행 방식

1. 이름·조건·기본값·변환·타입·작은 함수·책임 분리는 코드를 살펴보는 개선 관점이다. Ticket은 관련된 여러 개선 주제를 함께 다루고, 그 범위의 동작 보존과 개선 효과를 확인할 수 있는 실제 코드 작업 범위로 잡는다. 하나의 Ticket을 한 종류의 표현 개선으로 제한하지 않는다.
2. 각 Ticket 안에서 해당 코드와 관련된 바텀 요소부터 살피고, 근거가 있을 때 필요한 함수·책임 정리까지 이어간다. 모든 Ticket에서 모든 주제의 수정거리를 반드시 찾아야 하는 것은 아니다.
3. Ticket의 실제 개선 목적과 보존 계약을 수정 전에 구체화한다. 변경 전 필요한 검사를 실행하고 리팩토링한 뒤 같은 조건으로 확인하며, 코드 개선 효과도 별도로 비교한다. 새로 발견한 개선을 포함하려면 해당 범위의 보존·개선 기준을 먼저 보완한다.
4. 기존 분석과 추가 후보 목록을 Ticket에 연결해 주제별로 어느 코드 범위를 확인·개선했고 무엇이 남았는지 관리한다. 한 Ticket에서 이름이나 조건을 개선했다고 그 주제 전체의 검토가 끝났다고 하지 않는다. 검토 결과에는 개선, 유지할 이유, 버그 수정으로 분리한 부분, 보류와 미확인을 남긴다.
5. 여러 코드 범위에 걸친 중복이나 계약 문제가 드러나면 근거에 따라 관련 Ticket 경계를 조정하거나 공통 부분을 맡는 Ticket을 추가한다. 전체 분석 주제를 최대한 다루는 것을 지향하되 무조건 공통화·전면 변경하지 않는다.
6. 현재 다섯 Ticket은 실행 전 초안으로 유지한다. 사용자는 지금 Ticket을 검토하려고 한다. 이번 동의는 진행 방식에 대한 채택이며 개별 Ticket 범위·첫 대상·추천 순서의 최종 확정이나 제품 구현 착수 명령으로 확대하지 않는다.

## 현재 문서에 연결할 의미

자동 Maintain은 이 합의를 기존 Spec의 진행 방식/완료 판단과 Ticket 색인, 전체 상태에 필요한 만큼 연결한다. 같은 정의를 별도의 장기 정본으로 복제하지 않는다. 특히 현재 state의 “전체 배치를 먼저 마친 뒤 실행한다”는 흐름은 Main이 앞선 질문을 잘못 이해해 제시했던 계획이다. 이를 사용자가 요구한 필수 선행 조건으로 남기지 않는다. 채택된 방식은 범위별 Ticket을 수행하면서 전체 분석 주제의 남은 검토 범위도 함께 관리하는 것이다.

제품 수정·테스트·Verify는 실행하지 않았다. 현재 사용자는 Ticket 검토 중이고 Main은 구현을 시작하지 않는다. 본 기록은 현재 사용자 합의와 Main 해석을 보존하며 기존 비동기 Maintain의 완료를 주장하지 않는다.
