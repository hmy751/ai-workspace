### 도시 검색의 요청 조건과 결과 필터

`apps/client/src/features/trip/create-trip/geonames.api.ts:32`의 `searchCities`가 API 요청, 결과 선별, City 변환을 함께 수행한다. 허용 도시 코드 네 개가 요청의 `featureCode`(41행)와 응답 필터의 `allowedFCodes`(49행)에 반복된다. 인구가 10,000보다 큰 도시 또는 수도 코드 `PPLC`를 허용하는 조건(55행)을 독자가 직접 해석해야 한다. `useSearchCities.ts`는 이 함수를 실제 queryFn으로 사용한다.

동일한 도시 종류를 바꿀 위치가 둘이라는 구체적 부담이 있다. 그 목록을 한 곳에서 설명하고, 이름·국가 필드/도시 종류/인구 또는 수도 조건과 문자열 좌표 변환의 역할이 읽히도록 정리할 수 있다. 좌표의 parseFloat는 외부 문자열을 숫자로 바꾸므로 불필요한 변환으로 제거하지 않는다. 실패를 빈 배열로 바꾸는 catch도 재전파만 하는 catch와 다르다. Ticket 02로 제안한다.

### 인증·재시도 설명과 실제 실행 연결

`shared/services/auth/auth-interceptor.ts:180`의 sync helper 설명은 토큰 갱신도 같다고 하지만 본문은 401에서 만료 상태를 설정하고 AuthRequiredError를 던진다(187행). 이 helper는 export되지만 조사 범위에서 실제 setup 호출을 찾지 못했다. 실행 중인 sync 클라이언트는 `shared/services/sync/api.ts`에서 자체 인터셉터를 등록한다.

### 로그아웃과 계정 삭제의 비슷한 정리 단계

`shared/services/auth/logout-service.ts`에서 큐 삭제, DB reset, 인증 상태 정리, 캐시 clear가 두 번 반복된다. 그러나 로그아웃은 서버 실패 후에도 로컬 정리를 이어가고, 계정 삭제는 서버 실패 시 바깥 catch로 끝난다. `checkPendingSync`는 pending/inProgress를 hasPending에 포함하고 failed는 별도로 반환한다.

반복만 보고 하나의 옵션 많은 절차로 합치지 않는다. 동일한 로컬 정리 부분을 다룰 후속 후보이며 서버 실패 이후 실행 여부·단계 순서·부분 실패·미전송 작업 보존 조건이 확인되어야 한다. 실제 계정 삭제나 DB reset을 이번 조사에서 실행하지 않았다.

## 1차 Ticket 초안

다섯 Ticket은 각각 실제 코드 개선과 그 범위의 보존 증거를 끝내는 단위다. 번호는 제안한 읽기·실행 순서이며 강한 기술 의존성이 아니다. 첫 Ticket이 전체 Work의 완료를 대신하지 않는다. 테스트 준비를 독립적인 장기 기반 Ticket으로 앞세우지 않고, 처음 필요한 Ticket에서 변경 전 제품 코드를 검사할 최소 실행 방법을 갖추어 이후 재사용한다. 구체적인 runner는 아직 선택하지 않았다.

### Ticket 01 — 경비 합계의 강조·소수 자릿수 규칙을 읽히게 한다

**맡은 결과와 범위:** `screens/ExpensesScreen.tsx`의 통화 합계와 `shared/lib/currency.ts`의 관련 규칙. 첫 항목 강조와 자릿수 판단을 반복 해석하지 않게 한다. 날짜 그룹·폼·카드 전체나 환율 계산까지 넓히지 않는다.

**실행 맥락과 접근:** Spec 02·03·04. 기본 통화가 목록에 있으면 우선되고 없으면 다른 통화가 첫 항목이다. 그러므로 첫 항목을 `isBaseCurrency`로 명명하지 않는다. 현재 toFixed 표시와 helper의 천 단위 구분자 차이를 보존한다. 내부 함수/변수 배치는 코드를 보며 정한다.

**완료 조건과 확인 방법:** 수정 전 groupExpensesByCurrency/formatCurrencyDisplay의 실제 export와 현재 화면 통화 합계 렌더를 대상으로 필요한 검사를 먼저 실행한다. 빈 경비, 기본 통화가 있는/없는 목록, 동일 통화 합산, 동률, KRW/JPY와 EUR/USD, 0·소수·1,000 이상 금액을 다룬다. 계산 순서·정렬·표시 문자열·첫 항목 강조가 후에도 같아야 한다. 기존 화면에 자동 검사가 어려우면 고정 fixture의 전후 화면과 조건을 남기며 pure helper 검사만으로 UI 표시까지 입증하지 않는다. 개선은 강조 판단의 뜻이 정확하고 공통 자릿수 규칙을 여러 곳에서 다시 해석할 필요가 줄었는지 비교한다.

**현재 상태와 실제 결과:** 초안. 소스와 사용처 확인만 완료. 제품 코드·테스트 미수정, 실행 결과 없음. Main의 첫 작업 추천이다.

### Ticket 02 — 도시 검색의 선별 조건과 변환을 명확히 한다

**맡은 결과와 범위:** `features/trip/create-trip/geonames.api.ts`의 요청 도시 코드와 응답 선별/City 변환. query hook의 debounce·cache·에러 표시 정책은 바꾸지 않는다.

**실행 맥락과 접근:** 허용 도시 코드가 요청/필터에 반복되고 인구 기준과 수도 예외가 식 안에 묶여 있다. 기존 `searchCities`를 외부 호출 경계로 유지한 채 동일 기준과 조건의 의미를 드러낸다. 외부 응답의 문자열 좌표 변환은 필요하며 유지한다. catch의 빈 배열 반환도 이번 refactor에서 새 오류 throw로 바꾸지 않는다.

**완료 조건과 확인 방법:** 리팩토링 전 searchCities에 고정된 HTTP 응답을 공급해 실제 반환값과 요청 인자를 확인한다. 허용/비허용 코드, 이름/국가 누락, 인구 10,000과 10,001, 인구 기준 미달 수도, 응답 순서, 숫자 문자열 좌표, 요청 실패를 포함한다. 수정 뒤 같은 검사를 실행한다. 실제 GeoNames 서비스 가용성 검증으로 확대하지 않는다. 허용 코드 변경 위치가 하나로 모이고 수도 예외·필드 변환의 이유를 가까운 코드에서 읽을 수 있어야 한다. 범용 검색 엔진 도입은 완료가 아니다.

**현재 상태와 실제 결과:** 초안. 신규 확인 후보이며 외부 API 호출·제품 테스트 실행 없음. Ticket 01과 기술적 의존성은 없다.

### Ticket 03 — 저장 용량의 집계·부분 실패·표시를 명확히 한다

**맡은 결과와 범위:** `features/profile/hooks/useStorageStats.ts`와 해당 프로필 표시 연결. 같은 stats 생성 표현을 두 곳에서 맞춰야 하는 부담을 줄인다.

**실행 맥락과 접근:** 파일 읽기 전체를 감싼 실패와 개별 팩 실패의 계속 여부가 다르다. 이미 집계한 값을 보존하는 순서를 유지한다. 함수의 분리 크기는 자유지만 각 단계의 실패가 어느 결과를 남기는지 더 많은 파일을 찾아다녀야 하면 다시 판단한다.

**완료 조건과 확인 방법:** 변경 전 기존 hook을 통해 FileSystem/Mapbox 의존성을 제어하고, 빈 디렉터리·대상 확장자와 무관 파일 혼합·DB 파일 조회 중간 실패·getPacks 실패·개별 pack.status 실패 후 다음 팩 성공을 확인한다. 0/1,024/소수 단위 표시, 최종 DB/지도/합계, 관련 호출 순서를 비교한다. 후에도 동일 조건으로 같아야 한다. 실제 기기 파일 접근과 네이티브 지도 팩 확인이 없으면 그 범위는 미확인으로 남긴다. 성공/실패 표시 조립이 한 의미로 관리되고 부분 결과 보존 위치가 명확해야 한다.

**현재 상태와 실제 결과:** 초안. 신규 확인 후보. 테스트·실기기 검증은 미실행이며 필요한 hook 검사 방법은 실행 때 준비한다.

### Ticket 04 — 경비 API의 요청·검증·반환과 오류 책임을 간결하게 한다

**맡은 결과와 범위:** `entities/expense/api/expenses.ts`의 다섯 remote 함수. 재전파 catch·반복 주석/로그가 작은 본문을 가리는 부담을 줄인다. repository/router, schema 계약, 전역 fetcher의 오류 변환은 바꾸지 않는다.

**실행 맥락과 접근:** 기존 후보의 대표 단위다. 요청 검증과 응답 검증은 서로 다른 경계이므로 둘을 중복으로 삭제하지 않는다. 삭제할 출력과 남아야 할 실패 기록의 책임을 먼저 확인한다. 사용자 오류 표시·오류 종류·추가 fallback은 바꾸지 않는다.

**완료 조건과 확인 방법:** 수정 전 기존 API export를 호출하는 검사로 정상 요청·반환, 잘못된 요청은 HTTP 전에 실패, 잘못된 응답은 검증 실패, 네트워크 실패는 같은 오류 전달, 삭제 반환과 HTTP 횟수를 확인한다. 후에도 같은 검사를 사용한다. 진단 로그 정리는 변경 내역과 남은 기록 책임을 따로 설명하며 데이터/오류 계약 변경과 혼합하지 않는다. 개선은 실제 요청·검증·반환 흐름이 직접 보이고 재전파를 읽기 위한 부수 코드가 줄었는지 비교한다. 한 함수를 위해 범용 API framework를 만들지 않는다.

**현재 상태와 실제 결과:** 초안. 기존 후보의 구체적 범위를 확인했다. 실행/검증 결과 없음.

### Ticket 05 — 서버 일정 응답의 날짜 변환을 한 의미로 유지한다

**맡은 결과와 범위:** `apps/server/src/routes/schedules.ts`의 생성·목록·단건·수정 응답에서 반복되는 scheduledAt/createdAt/updatedAt/deletedAt 변환. 반복되는 동일 응답 변환을 다룬다. CRUD 쓰기 값·소유권·조회 조건·삭제 응답·activation/sync endpoint 통합은 제외한다.

**실행 맥락과 접근:** 동일한 네 날짜 변환이 50·91·147·246행 주변에 있다. DB row 타입에서 응답 값으로의 변환을 좁게 다루되 새 any/단언으로 넘기지 않는다. 기존 entity/envelope 검증과 오류 처리 분기가 다르므로 이 Ticket에서 검증을 통째로 합치거나 제거하지 않는다. 좌표 0 변환과 updateData:any는 별도의 영향 범위다.

**완료 조건과 확인 방법:** 변경 전 실제 route handler의 고정 DB 반환 fixture로 각 endpoint의 응답 JSON·status·날짜 문자열·deletedAt null/값을 확인하고 수정 후 비교한다. 오류 경로의 기존 응답/전파가 보존되어야 한다. 순수 변환 helper를 새로 만든 뒤 그 helper만 테스트한 것을 변경 전 기준 검사로 제시하지 않는다. handler 검사에서 DB를 대체했다면 실제 인증·ownership·영속 저장 보존을 검증했다고 말하지 않는다. 그 부분은 diff/사용처의 영향 확인과 구분한다. 개선은 같은 날짜 변환의 수정 위치가 줄고 호출부에서 DB row→응답 변환 역할이 읽히는지 판단한다.

**현재 상태와 실제 결과:** 초안. 반복 변환이 현재 코드에 있음을 확인했다. server 검사와 응답 검사는 미실행이다. client Ticket과 기술적 선행 관계는 없다.

## 남은 기존 후보와 후속 범위

기존 14개 후보를 아래처럼 연결하되 이것을 최종 처리 판정이나 전체 완료로 보지 않는다. 첫 다섯 Ticket은 1차 실행 후보이고 아래 범위를 조용히 누락하지 않는다.

- 이름·주석·로그·catch → Ticket 04에서 경비 API를 먼저 다룬다. auth wrapper·미사용처럼 보이는 export·날짜 설명은 별도 후속 판단이다.
- 조건식과 표시 규칙 → Ticket 01. 카테고리 색상은 사용처 차이를 확인한 추가 후보다.
- 불필요한 값 변환과 기본값 → 일정 form의 number 왕복은 후속 범위다. 도시 검색의 문자열 변환은 Ticket 02에서 보존한다. 좌표 0 문제와 섞지 않는다.
- 타입으로 이어지는 검증 결과 → Ticket 05의 좁은 DB row/응답 연결. sync as never[]와 mutation any 전반의 해결을 이 Ticket 완료로 주장하지 않는다.
- 중복 검증과 도달하지 않는 분기 → 후속. Ticket 05는 응답 변환만 맡으며 오류 계약 확인 전 검증을 지우지 않는다.
- 목록 계산/useMemo → 후속으로 일정·경비의 날짜 범위/그룹을 비교한다. UTC/local date 조건이 동작 차이로 이어지면 기대 동작을 먼저 확인한다.
- 폼 초기값/reset/값 변경 → 후속으로 한 폼의 취소·재열기·다른 항목·늦은 기본값을 구체화한다. 현재 기대 UX의 미확정을 임의로 닫지 않는다.
- picker callback 의미 → 후속으로 picker와 그 호출부를 묶는다. 선택/닫기/취소 횟수와 값 전달을 확인한다.
- 저장 성공 이후 처리 → 후속으로 하나의 저장 흐름과 캐시/이동/경로 준비까지 묶는다. 500ms 제거·오래된 좌표 변경은 동작 수정과 구분한다.
- 생성·수정 컴포넌트 반복과 차이 → 위 폼 경계 확인 후 같은 입력 의미를 다룬다. 외관·조회/오류/캐시 차이를 일괄 통일하지 않는다.
- 공통 데이터·경로·정리 구현 → 기존 route/upsert/cleanup 차이와 미전송 보존 문제에 직접 걸리는 범위만 선행 확인한다. 이번의 로그아웃/삭제 후속 후보도 같은 판단 기준을 적용한다.
- 완료 상태와 조율 책임 표현 → 활성화/동기화 상태 이름과 실제 완료 범위를 후속 구체화한다. sync 재시도 불일치는 우선 동작 확인 대상으로 유지한다.
- 설정과 실제 사용처 → policy syncStrategy의 실행 연결을 재검토할 때 미호출 sync auth helper 같은 추가 근거도 함께 보되 무조건 삭제/구현하지 않는다.
- 서버 변환·오류 처리 책임 → Ticket 05에서 일정 CRUD 응답 변환부터 시작한다. auth/places 오류와 activation/sync 변환 차이는 별도 후속 범위다.

새로 발견한 대표 여행 선택, 카테고리 표시, datetime 설명, sync 재시도/로그아웃 후보는 위 1차 범위 밖에도 남긴다. primitive나 서로 다른 mutation을 범용화할 독립 Ticket은 현재 근거로 만들지 않는다.

## Maintain에 전달할 현재 의미

이 문서는 Main의 조사 결과와 작업 분해 초안이며 기존 Spec의 새 정본이 아니다. 기존 자동 Maintain이 위 근거를 필요한 records에 보존하고, 1차 다섯 범위를 실행 전 초안 Ticket으로 만들고 색인에서 연결할 수 있다. 우선순위는 Main 추천, 테스트 방법은 계획, 제품 실행 결과는 없음으로 유지한다. 전체 후보/현재 상태에도 추가 조사와 남은 범위가 이어지게 하되 내용을 중복 복제하지 않는다. 현재 Spec의 목표·보존 기준을 변경하거나 첫 구현 대상을 사용자 확정으로 기록하지 않는다.

별도의 이전 상태 정정 근거: Main이 앞선 turn에서 자동 수집 시작 전 대화 60개를 retrospective note로 보존했다고 보고했다. 실제 저장 경로는 `evidence-collector/store/recollections/846e3c64734effd3f30168c7ca0e341939c101f93d3e8f7124ab117f5a6e4466/20260910T135903.326183Z-b0d87f1f4f7e48518611b68b3a1a5261/note.md`이며 당시 bytes/hash 일치를 확인했다. 자동 수집 당시 기록과는 구별한다. 이를 아직 원문 미보존 상태라고 단정하는 이전 state가 남아 있다면 최신 Main 보고와 대조할 수 있다. 이번 조사는 그 저장을 새로 수행하거나 재검증하지 않았다.
