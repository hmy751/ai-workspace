# 03 — 저장 용량의 집계·부분 실패·표시

## 맡은 결과와 범위

`apps/client/src/features/profile/hooks/useStorageStats.ts`와 `apps/client/src/screens/ProfileScreen.tsx`의 표시 연결을 다룬다. 성공·실패 경로의 같은 stats 생성 표현을 두 곳에서 맞춰야 하는 부담을 줄인다. 병렬 조회·새 실패 상태·새 단위 체계는 도입하지 않는다.

## 실행 맥락과 접근

[보존 계약](../spec/03-concepts-and-contracts.md)과 [품질 기준](../spec/04-quality-and-completion.md)을 적용한다. Main 조사에 따르면 파일 조회 도중 실패하면 앞서 집계한 용량을 표시하고 지도 조회까지 진행하지 않는다. 개별 지도 팩 조회 실패는 경고 후 다음 팩 조회를 계속한다. 이미 집계한 값을 보존하는 순서와 실패별 계속 여부를 유지한다.

표시 조립을 한 의미로 관리하되 부분 결과를 이해하기 위해 더 많은 파일을 따라가야 한다면 분리 방법을 다시 판단한다. [추가 조사 기록](../../../records/2026-09-11-01-additional-research.md)에 선택 이유와 확인 범위가 있다.

## 완료 조건과 확인 방법

변경 전 기존 hook을 통해 FileSystem/Mapbox 의존성을 제어한다. 빈 디렉터리, 대상 확장자와 무관 파일 혼합, DB 파일 조회 중간 실패, `getPacks` 실패, 개별 `pack.status` 실패 후 다음 팩 성공을 확인한다. 0/1,024/소수 단위 표시, 최종 DB·지도·합계와 관련 호출 순서를 변경 후 동일 조건으로 비교한다.

실제 기기 파일 접근과 네이티브 지도 팩 확인이 없으면 해당 범위를 미확인으로 남긴다. 성공·실패의 표시 조립을 함께 수정할 위치가 줄고 부분 결과 보존 위치가 명확해졌는지를 전후 코드로 확인한다.

## 현재 상태와 실제 결과

Main이 제안한 실행 전 초안이다. 코드와 표시 사용처를 조사했다고 보고했으며 제품 수정·테스트·실기기 검증은 미실행이다. 필요한 hook 검사 방법은 실행 때 준비한다. 번호는 제안 순서이며 다른 Ticket의 결과를 강한 선행 조건으로 두지 않는다.
