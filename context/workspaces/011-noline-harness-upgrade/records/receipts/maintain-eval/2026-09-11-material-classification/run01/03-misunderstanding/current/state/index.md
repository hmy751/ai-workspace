2026-09-11 사용자의 '추가로 또 조사해봐 합의한 내용 바탕으로 또 다른곳까지 있는지' 요청에 Main은 기존 후보 밖의 코드와 사용처를 추가 조사했다고 보고했다. 사용자가 '그럼 아까 주제들을 모두 포함하는 경계로 잡은거야?'라고 물은 turn `01a08de0-ce1d-7420-80c0-0e555e377266`에서 Main은 다섯 Ticket이 먼저 작업하기 좋은 일부를 자신이 선택한 것이며 전체 주제를 포괄하는 티켓 구성은 미완료라고 밝혔다. 폼 초기화·재진입, picker, 날짜 그룹, 저장 후 처리, 공통 데이터·경로·정리, 완료 상태와 설정 등은 후보로 남아 있으나 티켓 경계에 모두 배치되지는 않았다.

제품 작업의 다음 행동은 전체 후보가 어느 Ticket에 들어가는지, 무엇은 동작 확인이 먼저 필요한지, 무엇은 변경할 필요가 없는지를 근거와 함께 빠짐없이 정리한 다음 실행 순서를 정하는 것이다. 이는 이번 응답에서 Main이 밝힌 진행 방향이며 전체 배치나 개별 후보 판정이 완료됐다는 뜻은 아니다. 기존 다섯 초안은 유지하며, 경비 합계 규칙을 첫 작업으로 추천했던 순서도 사용자 확정 사항이 아니다. 실행 범위를 정하면 현재 코드·보존 계약·사전 개선 목표·변경 전후 검증 방법을 대조한다. 구체적인 runner는 미선택이며 필요한 최소 검사 실행 방법은 처음 사용하는 Ticket에서 준비해 재사용한다는 제안이다. 특정 첫 파일이나 '일정 생성부터'는 사용자 확정 사항이 아니다. 직접 걸리는 버그의 기대 동작·수정·선행 관계만 연결하며 버그 전체 해결을 기다리지는 않는다.

추가 조사 문서에서 Main은 `refactor/codebase`, HEAD `a612ba4c49b92b1193e75e1d56bdefcdcd86bbda`를 확인했고 조사 시작·마지막의 미커밋 파일은 이 state뿐이었다고 보고했다. 제품 test/spec 파일·runner 설정을 경로 검색하고 확인한 root/client/server scripts에서도 제품 test 명령을 찾지 못했다고 보고했지만 저장소 밖의 검사까지 없음을 뜻하지 않는다. 전체 파일 정독·앱·외부 API·DB 실행 결과가 아니며 과거 타입·린트 실패도 재실행하지 않았다. 이 Git·검색 상태는 Main의 조사 당시 보고이고 현재 상태의 독립 확인이 아니다.

앞선 현황 파악 당시 Main은 `refactor/codebase`, HEAD `e7c1134`, 미커밋 변경 없음이며 분석 기준 이후 제품 소스가 바뀌지 않았고 대표 후보도 남아 있다고 보고했다. 이는 당시 비교 보고이다. 타입·린트의 이전 실패와 설치 불일치는 [구성 기록](../../records/2026-09-10-01-workspace-setup.md)에 있다. 실행 시 필요한 만큼 기준선을 확인한다.

동기화 API의 최대 3회 재시도 설명과 `_retry` 조건 충돌은 Main의 정적 코드 관찰에 따른 동작 확인 후보다. 실제 요청 횟수나 런타임 결함 재현을 확인한 것으로 기록하지 않는다. 수정이 필요하면 별도 동작 수정 경계를 따른다. 기존 폼·picker·날짜 그룹·저장 후 처리와 새 대표 여행·색상·날짜 설명·로그아웃 후보는 후속 범위로 유지한다.

## 대화 반영과 자동 동작의 확인 범위

초기 구성 당시 active/default index와 session binding은 변경하지 않았다. 이후 Main은 현재 session이 `002-code-readability-refactoring` generation 1 active라고 보고했다. 앞선 점검에서는 개별 hook 7개의 승인 기록이 생긴 뒤에도 자동 Maintain 접수·처리 기록이 없고 Evidence collector가 시작되지 않았다. 초기 승인 누락만을 당시 미동작의 전체 원인으로 확정하지 않는다.

사용자의 '한번더 테스트 해볼래?' 요청에 대한 Main 보고에서는 현재 대화의 사용자 요청 1건이 Maintain에 자동 접수됐고, Evidence 서비스가 시작되어 수집 사건 1건을 `done`으로 처리했다. 해당 turn은 `01a08b95-9282-7ec0-910f-de5802a73719`다. 이는 Main이 보고한 해당 요청의 접수·수집 범위이며, 해당 응답 종료 처리의 완료는 아직 입력으로 확인되지 않았다. 별도 테스트 작업은 두 번 모두 응답·도구 기록 없이 종료돼 재검증이 불완전하다고 보고됐고, 이후 연결 해제 후 닫았다는 Main 보고가 있다. 모든 작업의 정상 동작이나 과거 미동작 원인의 해소까지 입증한 것은 아니다.

후속 Evidence 점검에서 Main은 수집이 '한번더 테스트 해볼래?' 메시지부터 시작됐으며 시작 이후 수집 사건 3개는 처리 완료됐다고 보고했다. 그보다 앞선 Spec 목표·source 배경·테스트 기준 합의 원문은 당시 Evidence에 미수집이고 전체 대화 파일 경로만 연결돼 있었다. 이 확인은 turn `01a08b98-9aad-7c83-a2f4-0685f01d1b67`에서 전달됐다. 원문은 Main 보고상 `/Users/hammyeong-yeon/.codex/sessions/2026/09/10/rollout-2026-09-10T21-56-54-01a08b64-7f25-7972-ac3e-496cb4af1de7.jsonl`에 남아 있다.

이후 turn `01a08b9b-d7b7-7900-a7b1-6e0ced3f9e4b`에서 Main은 누락 대화를 Evidence의 사후 메모로 보존하고 본문·해시를 확인했다고 보고했다. Evidence는 Git 제외 저장소에 있어 문서 커밋과 별도로 보존된다. 사후 보존 완료 보고를 반영하되, 자동 수집이 과거 구간까지 수행됐다는 뜻으로 보지 않는다.

2026-09-11 조사 초안에는 앞선 사후 보존 대상이 자동 수집 전 대화 60개이고, 저장 경로는 `evidence-collector/store/recollections/846e3c64734effd3f30168c7ca0e341939c101f93d3e8f7124ab117f5a6e4466/20260910T135903.326183Z-b0d87f1f4f7e48518611b68b3a1a5261/note.md`이며 당시 bytes/hash 일치를 확인했다는 Main 보고가 추가로 연결됐다. 경로와 보존 분량 보고를 이어받되 이번 조사나 Maintain이 사후 메모를 새로 저장·재검증한 것은 아니다. 정확한 해시값과 원문 재현 범위는 독립 확인하지 않았다. 기존 대화 파일 경로는 재접근 위치이며 그 자체가 사후 메모의 보존 증거는 아니다.

사용자는 'maintain한테 그냥 대화 다 읽고 필요한 부분 다 일단 업데이트부터 하라고 하고 확인해봐'라고 요청한 뒤 '내말은 대화 읽게 다 시킨다음에 왜 안도는지 확인하라고'라고 순서를 정정했다. 이에 기존 semantic session에 제공된 작업 대화 전체가 수동 전달되어 Spec과 필요한 현재 상태를 통합하는 판단 입력으로 사용됐다. 당시 통합안은 앞선 미적용 변경안을 대체하도록 반환됐고, 이후 Main이 문서 검증·커밋 완료를 보고했다. 수동 대화 전달, 문서 반영, Evidence 사후 보존과 자동 hook 동작은 서로 다른 확인 범위다.

자동 동작의 남은 확인과 과거 미동작 원인 조사는 Main이 별도로 맡는다. 이 운영 문제를 제품 리팩토링의 목표나 완료 기준으로 추가하지 않는다. 연결과 동작 확인의 상세 경계는 [session binding 계약](../../../../harness/maintain/SESSION-BINDING-AND-LIFECYCLE.md)을 따른다. `status.json`은 제품 Verify의 마지막 기계 결과만 소유하며 제공된 null receipt는 제품 Verify 결과가 없음을 뜻한다. 이번 문서 반영으로 변경하지 않는다.

## 원래 분석 경로의 삭제에 대비한 보존

사용자가 `.claude/sessions`의 기존 분석 경로를 나중에 삭제할 계획을 밝혀 원자료를 이 Workspace 안에 보존했다. [분석 목차](../../source/codebase-analysis/README.md)에서 전체 내용을 읽고, [source 색인](../../source/index.md)에서 원문 사본과 해시를 찾는다. 후보·검증 기준을 판단할 때 원래 경로 대신 이 보존본을 읽는다. 보존 당시 원래 파일은 삭제하지 않았으며 그 작업은 제품 구현·Ticket·activation·완료 상태를 바꾸지 않았다.

기존 상태 기록에는 원래 분석 경로를 제외한 임시 Project에서 원문 7개 일치, 읽기용 본문 일치와 local 링크·명시적 Recover 성공을 확인했다고 남아 있다. 상세 범위는 [분석 보존 검증](../../records/2026-09-10-04-analysis-preservation-validation.md)에 있다. 이는 제품 동작 검증 결과가 아니다.
