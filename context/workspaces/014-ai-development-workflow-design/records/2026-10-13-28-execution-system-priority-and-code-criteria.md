# 작업 단계의 시스템을 먼저 구체화한다

2026-10-13. 사용자와 Main이 작업을 논의·결정하는 단계와 실제 구현·검토·검증하는 단계를 구별하고, 강연에서 가져오려는 효과와 코드 기준의 근거를 확인했다. 구체 운영안이나 코드 기준을 채택한 기록은 아니다.

## 이번에 확인한 방향

사용자는 Main과 작업을 논의하여 Spec·Ticket 등을 결정하는 과정이 기존에도 어느 정도 잘 동작했다고 본다. 강연에서 가장 가져오고 싶은 것은 **결정된 작업을 좋은 코드와 확인 가능한 결과로 만드는 작업 단계의 시스템**이다. 제공하는 컨텍스트, 코드 기준, 작업 절차, 워크플로, 도구와 검증 환경의 미성숙함을 먼저 구체화한다.

설계·Spec 절차는 개선 범위에 남는다. 다만 원자료에 구체적인 선행 설계 절차가 있다는 이유만으로 이를 다음 논의의 중심이나 모든 작업의 선행 조건으로 삼지 않는다. Project 맥락과 작업 환경을 구체화하면서 필요한 보완을 연결한다. 구현 중 모듈·인터페이스·테스트 경계를 설계하고 개선하는 일은 작업 단계의 코드 품질에 포함된다. 이 단계 구분은 구현 중 발견 때문에 Main과 다시 논의할 수 없다는 고정 관문이 아니다.

사용자가 요청한 논의는 충분히 조사한 구체 사례에서 차이·이유·조건을 살펴보는 과정이다. 구체 예시를 만들었다는 이유로 바로 운영안이나 구현 범위를 확정하지 않는다. 앞선 [원자료 조사](2026-10-13-27-source-investigation-and-proposal-reset.md)는 유효한 근거로 유지하되, 그 기록 마지막의 ‘선행 설계부터 논의’는 Main의 당시 제안으로 구별한다.

## 코드 기준의 근거와 아직 필요한 정보

사용자는 기존 코드 대부분에 만족하지 않았다고 말했고, 충분한 컨텍스트를 주지 않았다는 점도 함께 언급했다. 이는 사용자 경험이며, 코드별 결함이나 불만의 원인을 이번 발화만으로 확정한 것은 아니다. 프로젝트 records에 가독성 기준이 있을 수 있다는 언급도 확인된 파일 사실로 올리지 않는다.

기존 코드에 자주 나타나는 패턴은 관찰 자료이지 곧바로 선호나 표준이 아니다. 언어·프레임워크의 제약, 과거 타협, AI가 만든 코드와 사용자가 좋아하는 선택을 구체 사례에서 구별해야 한다. 사용자에게 기준 전체를 추상적으로 먼저 정의하도록 요구하지 않는다.

토스의 유력 후보는 [Frontend Fundamentals — 변경하기 쉬운 프론트엔드 코드를 위한 지침서](https://frontend-fundamentals.com/code-quality/)다. [공식 토스 글](https://toss.tech/article/34895)이 이 프로젝트를 소개하며, [기준 본문](https://frontend-fundamentals.com/code-quality/code/)은 가독성·예측 가능성·응집도·결합도와 기준 간 충돌을 다룬다. 2026-10-13에 공식 본문에서 이름·범위만 확인했다. 사용자 지칭 여부·전체 내용의 적합성·채택은 미확인이다.

## 현재 문서와 다음 논의의 관계

Spec에는 두 단계의 관계와 작업 단계 우선순위를 반영한다. 01-01은 실행·검토·검증의 연결, 01-02는 코드 기준과 구현·수정 방법, 01-03은 동작 확인, 03은 작업 주체가 사용할 Project 맥락과 연결된다. 이 관계는 여러 Ticket을 동시에 완성하거나 순서를 고정하자는 뜻이 아니다.

다음 논의 후보는 **좋은 구현을 위해 작업자가 무엇을 알고, 어떤 코드와 기준을 참고하고, 어떤 확인 수단을 갖춰야 하는가**다. 구체 코드를 비교하면서 기준 자체를 논의하고, 그 기준을 문서·좋은 코드 예시·도구·검사·작업 절차 어디에서 받칠지 연결해 볼 수 있다. 아직 기준 묶음이나 역할별 입력 형식을 확정하지 않았다. B의 직접 수정 방향과 전체 Project·Work·기록·경험 반영 범위는 유지한다. 실제 코드·스킬·하네스 변경과 자동 Maintainer 재개는 하지 않았다.
