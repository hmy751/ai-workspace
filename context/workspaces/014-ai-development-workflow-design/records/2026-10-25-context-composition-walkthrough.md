# 04-03 — 워크플로·공통 참조·반영 스킬의 배치와 사용 장면

현재 지위: **다음 구체화의 잠정 작업안으로 합의했다.** [잠정 합의·사용자 유보·직접 발화·재개 기준](2026-10-25-context-framework-provisional-agreement.md)을 먼저 읽는다. 사용자는 USAGE와 context-update로 나뉘는 사용감에 유보를 남긴 채 이 정도 틀에서 이어가기로 했다. 아래는 당시 제시한 배치와 사용 장면이며 파일·호출 형태까지 최종 확정한 것은 아니다. 가칭 파일·스킬은 생성하지 않았고 기존 실행 본문·prototype·설정도 변경하지 않았다. 판단 근거는 [Matt·Lauren 조사와 기존/새 체계 종합](2026-10-25-context-reference-synthesis.md)에서 찾는다.

사용자 요청:

> 그럼 니가 추천하는 구성을 실제로 한번 펼쳐서 보여줘. 어떤 건 워크플로에 두고 어떤 건 공통 참조나 스킬로 두는지, 담당자들이 읽고 갱신하는 흐름이랑 별도 요청까지 연결해서. 아직 만들진 말고 책임 분리랑 유지가 어떻게 되는지 같이 보자

## 제안하는 배치

**기존 development와 영역별 내용·관리 계약을 유지하면서, 공통 읽기 방법은 일반 참조 하나로, 지정한 지속 본문을 맞추는 과업은 반영 스킬 하나로 펼쳐본다.** Work current의 일상 유지는 Main과 Work 계약에 둔다. 책임마다 스킬을 만들거나 모든 맥락 작업을 한 관리자에게 보내지 않는다.

| 형태·제안 위치 | 직접 소유하는 판단 | 실제 사용하는 사람·AI와 종료 |
| --- | --- | --- |
| 기존 `development`와 역할 상세 | 어떤 목표·역할·판본으로 일을 맡기고, 언제 추가 맥락을 연결하며, 변화가 진행 중인 작업·이전 판단과 검증에 미친 영향을 어떻게 회수할지 | Main이 전체를 조정하고 각 담당자가 맡은 수행을 한다. 문서 반영 완료와 전체 작업 완료를 구별한다. |
| 기존 대상의 `context/README.md`와 root 진입 | Personal·Project·Work의 경계, 실제 위치와 일반 진입 경로 | 개발 중 사용과 직접 요청이 같은 대상·정본을 찾는다. 실제 권위·구조가 다른 Project에 이 demo 경로를 강제하지 않는다. |
| 가칭 `context/USAGE.md` — 공통 참조 | 맡은 질문에서 관련 본문 선택, 유효한 읽기 재사용, 원문·실물 대조, 적용 조건·충돌·미확인의 구별 | Main·구현자·검토자·검증자·직접 요청 수행자가 필요할 때 읽는다. 필요한 이해가 생기면 원래 과업으로 돌아간다. 새 agent·보고서·파일 갱신은 요구하지 않는다. |
| 기존 Personal·Project의 본문과 관리 지침 | 개인 기준·제품 약속·현재 구현 사실, 각각의 변경 조건·권한·형성 근거 | 내용을 사용하는 담당자는 필요한 본문을, 의미를 고치는 담당자는 해당 관리 지침·필요한 형성 자료를 읽는다. 일상 읽기에 전체 관리 문서를 붙이지 않는다. |
| 기존 Work 계약과 current·records·output | 이번 목표·선택·상태, 그 근거와 산출물 위치, 일반 재개와 한정 위임의 차이 | Main이 직접 유지·확인한다. 기록 역할을 별도 배정했다면 그 범위에서 담당자가 수행한다. 다른 역할이 공유 current를 자유롭게 고치는 권한은 생기지 않는다. |
| 가칭 `context-update` — 기존 update 기능을 재구성할 스킬 | 지정된 Personal 또는 Project 지속 본문을 변경 요청·근거·기존 권한에 맞게 대조·반영하고, 허용된 관련 문서·진입·읽기 경로를 확인하는 수행 | Main 또는 본문 수정을 맡은 담당자가 사용한다. 반영한 내용·확인 범위·남은 결정·영향받는 소비자를 반환하면 이 과업이 끝난다. |

새 공통 참조는 일단 **대상 Project의 context 체계 안에 있는 로컬 정본**으로 제안한다. 스킬·workflow는 자기 설치 위치에서 대상 context 경로를 추정하지 않고 대상 진입점에서 찾는다. 여러 저장소의 배포·원형 관리·동기화는06에서 다룰 사항이며 이번 안에 자동 동기화나 별도 전역 관리자까지 넣지 않는다.

`SYSTEM-GUIDANCE.md`는 지침을 구성하는 사람의 기준이고, `CONTENT-POLICY.md`는 적용 대상의 본문·형성 자료 관리 기준이다. 두 문서를 평상시 맥락 사용법으로 바꾸지 않는다. 특히 Work에 새 형성 자료 구성을 적용하지 않는 현재 경계를 유지한다.

## 공통 참조를 추가하면 기존 본문에서 무엇을 옮기나

새 파일을 추가한 뒤 같은 알고리즘을 여러 곳에 그대로 남기지 않는다. 다만 각 진입점이 자기 책임을 설명할 짧은 핵심과 읽을 조건은 유지한다.

| 현재 설명 | 제안하는 정본과 이관 | 원래 위치에 남길 내용 |
| --- | --- | --- |
| development와 Project reading의 일반적인 질문별 선택·유효한 읽기 재사용·추가 탐색 | 역할과 영역을 넘어 같은 의미로 쓰이는 방법만 `USAGE`로 모은다. 실제 조항별 이관은 구현 전에 대조한다. | development에는 역할 인수·새 증거·조건 변경 때 누가 적용할지, Project reading에는 제품별 질문·주제 선택과 적용 사례를 남긴다. |
| 원문의 의미를 실제 코드·사용 조건과 대조하기 | 공통 참조는 대조할 근거와 적용·충돌·미확인을 구별하는 방법을 소유한다. | Project는 제품 약속과 현재 구현 사실의 권위·정정 기준을, Personal은 개인 기준의 적용 조건과 변경 기준을 계속 소유한다. |
| 변경 뒤 관련 자료와 읽기 경로 맞추기 | 각 영역의 관리 계약이 필요한 반영 범위·완료 기준을 소유하고 `context-update`는 그것을 수행한다. | development에는 Main이 Work·진행 중인 담당자·이전 의견과 검증 근거에 미친 영향을 처리할 책임을 남긴다. |

공통 참조는 모든 내용의 우선순위표·파일 경로 목록·문서 작성 규칙을 새로 만들지 않는다. 짧은 단순 읽기에서 이미 유효한 방법과 내용을 알고 있다면 같은 파일을 매번 재독하지 않는다. 반대로 공통 참조를 읽지 않은 담당자에게 Main이 이름만 전달하고 이해한 것으로 취급하지 않는다. 목표·질문과 실제 읽을 경로를 전달한다.

## 반영 스킬의 범위

이 스킬을 독립 과업으로 보는 이유는 **지속 본문을 실제로 맞추고 그 문서가 다시 읽히는 경로까지 확인한다는 분명한 결과**가 있기 때문이다. 개발 중 변경, 사용자의 직접 갱신 요청,05에서 채택된 개선의 문서 반영이 같은 과업을 사용할 수 있다. 같은 AI가 이어 수행할 수 있으며 별도 관리 agent를 만들지 않는다.

입력은 대상 본문·변경 요청 또는 확인된 변화·근거·허용 범위다. 구현 사실을 바로잡을지, 기존 약속을 더 명료하게 설명할지, 새로운 기준·제품 선택이 필요한지를 먼저 구별한다. 열린 선택을 대신 채택하지 않지만 이미 요청·위임·합의된 수정에 새 승인을 반복해서 요구하지도 않는다.

- **하는 일:** 해당 관리 지침을 읽고 근거를 대조한다. 허용된 본문·관련 상세·진입과 필요한 형성 자료를 맞춘다. 실제 읽기 경로에서 새 의미와 적용 조건이 드러나는지 확인하고 반영 결과와 영향 범위를 반환한다.
- **따로 남는 일:** 이번 Work 상태 유지, 개발 작업 배치와 재검증 결정, 제품 코드 수정, 경험에서 개선 수단·새 기준을 채택하는 판단, 새 Work 생성, 다른 저장소로의 배포·동기화.
- **채택과 반영의 차이:** ‘앞으로 모든 작업에서 이 기준을 쓰자’를 결정하는 일은 이 스킬의 권한이 아니다. 그 기준이 권한 있게 채택됐고 Personal에 반영하도록 요청받았다면 해당 문서 반영은 이 스킬의 정상 과업이다.
- **여러 대상:** Personal과 Project를 함께 다루라는 범위라면 각 영역의 이유·근거·권한을 따로 대조한다. 한쪽 변경 때문에 다른 쪽도 자동으로 바꾸거나 context 전체를 동기화하지 않는다.
- **작은 편집:** 뜻이 같은 오타 수정까지 별도 관리 과업으로 키우지 않는다. 의미 있는 지속 본문 반영을 맡겼을 때 같은 절차를 재사용한다.

`context-update`의 완료는 **지정한 본문과 허용된 문서 연결의 반영 완료**다. Work·진행 중 담당자·이전 확인의 영향이 남았다면 무엇이 달라졌고 누가 이어야 하는지 Main에게 반환한다. Main은 전체 작업의 연결을 닫는다. 활성 Work가 없는 직접 요청에서도 확인한 문서 범위를 말하며, 다른 모든 작업·저장소까지 정합해졌다고 보고하지 않는다.

## 개발 중 읽고 반영하는 예

아래는 경계를 보여 주는 가상 로그인 작업이다. 실제 demo를 이번 턴에 변경하거나 재검증했다는 뜻은 아니다.

1. **Main이 맡길 일을 정한다.** 요청은 ‘로그인 뒤 조회가 실패해도 인증 자체가 실패한 것처럼 안내하지 않게 고쳐라’라고 가정한다. Main은 기존 Project 계약, 관련 Personal 판단, 이번 Work 목표·제약, 대상 판본과 수정 범위를 연결한다. 관련 경로는 출발점이며 담당자의 추가 원문 탐색을 막는 허용 목록이 아니다.
2. **구현자가 직접 읽고 판단한다.** Project에서 인증 완료와 후속 조회의 약속을, Personal에서 완료 이름을 판단하는 관련 기준을, Work에서 이번 변경 범위를 읽는다. 실제 코드·사용처·실패 경계를 대조하며 새 질문이 생기면 관련 내용만 더 읽는다. 여기서는 공통 사용 방법을 적용하고 반영 스킬을 의무 호출하지 않는다.
3. **변화의 종류에 맞게 반영한다.** 이번 함수명 선택·보존 조건·미확인은 Work에 남긴다. 구현을 허용된 계약에 맞춰 고쳤고 Project의 현재 구현 설명도 달라졌다면, 해당 본문 수정까지 맡은 담당자나 Main이 `context-update`를 사용한다. 실제 코드와 제품 약속이 충돌하면 코드 상태에 맞춰 약속부터 바꾸지 않고 결함·기존 요구·새 선택을 판단한다.
4. **검토자·검증자는 자기 질문으로 원문을 읽는다.** 검토자는 결과·계약·관련 기준으로 대안을 비교한다. 검증자는 요구·최신 대상·실행 방법·실제 근거로 충족 여부를 확인한다. Main의 해석만 넘기거나 모두에게 같은 전체 current·기록을 읽히지 않는다. 기존 독립성·첫 입력·담당 재사용 조건을 유지한다.
5. **Main이 변경의 후속 영향을 잇는다.** 반영한 문서와 근거를 확인해 현재 Work 선택·상태를 맞춘다. 이미 작업 중인 담당자와 이전 의견·검증의 전제가 달라졌으면 해당 범위에 새 입력을 연결한다. 문구·경로만 바뀌었다고 모든 검사를 다시 하지는 않는다. 계약·동작·입력 조건이 달라진 경우 필요한 확인을 다시 정한다.

담당자는 읽는 중 중요한 충돌·계약 변경 필요를 발견하면 종료 보고까지 기다리지 않고 알린다. 단순 추가 읽기마다 Main 허가를 받지는 않는다. 본문 수정은 기존 배정 범위 안에서 수행하며 같은 공유 파일에 중복 수정자를 두지 않는다.

## 별도 요청은 어디로 들어오나

| 사용자 요청 | 같은 방법에 도달하는 경로 | 그 요청이 끝나는 지점 |
| --- | --- | --- |
| ‘이 작업에 필요한 맥락을 읽고 설명해줘’ | 실제 root·context 진입에서 대상과 영역을 찾고 공통 사용 방법·필요한 본문을 읽는다. | 적용할 내용·충돌·미확인을 답한다. 읽기만으로 새 Work·개발 전체 흐름·문서 갱신을 시작하지 않는다. |
| ‘확인한 변경을 Project/Personal에 반영해줘’ | 지정한 대상과 근거를 `context-update`가 해당 관리 계약으로 처리한다. | 허용된 반영·문서 연결 확인과 남은 영향·결정을 반환한다. 현재 대화의 Main이 관련 작업 연결을 담당한다. |
| ‘이번 작업의 현재 상태를 정리해줘’ | 현재 Work의 실제 상태·선택·근거를 읽고 Work 관리 계약을 수행한다. | current·필요한 records/output을 맞춘다. 이를 지속 기준의 반영 과업으로 바꾸지 않는다. |
| ‘이 경험에서 앞으로 뭘 개선할지 봐줘’ |05에서 정할 경험 개선 절차로 문제·수단·채택을 판단한다. | 선택한 결과가 문서 반영이면 위 스킬, 코드·검사·도구 변경이면 해당 수행으로 잇는다. 이후 효과 확인은05 책임이다. |
| ‘새 Work로 나눠 이어가자’ | 독립 목표·계승할 의미·대상 환경을 새 Work 생성 계약으로 처리한다. | 생성과 인수·활성화 조건을 확인한다. 기존 runtime 전제를 해결하기 전 보존 원형을 그대로 실행하지 않는다. |

개발 밖에서도 현재 요청을 받은 Main은 있다. development 전체를 실행해야만 읽기·반영 권한이 생기는 구조로 만들지 않는다. root·context 진입에는 직접 요청에서 공통 참조·해당 관리 과업으로 가는 조건을 연결하고, 스킬의 발견 설명에도 대상·종료를 드러내야 한다. 이는 제안한 실제 진입의 일부이며 아직 설정·routing을 변경하지 않았다.

## 변경·교체할 때 함께 관리할 범위

| 바뀌는 것 | 실제로 고치고 확인할 곳 | 유지할 경계 |
| --- | --- | --- |
| Project의 본문 위치·제품 조건 | Project 본문·진입·영향받은 참조와 사용 중 Work. 수정자가 문서 경로를 확인하고 Main이 작업 영향을 처리한다. | 공통 방법 안에 제품 상세나 고정 경로를 복제하지 않으면 같은 이유로 공통 참조 전체를 바꿀 필요가 없다. |
| 질문별 원문 선택 방법 | `USAGE`와 그 변경을 실제 사용하는 호출·참조 지점의 행동 | development의 역할·시점과 영역별 권위는 별도다. 선택 방법을 고치면서 권한까지 바뀌면 관련 계약도 명시적으로 재검토한다. |
| Work의 기록 구조 | Work 계약·실제 유지/재개 소비자·관련 workflow 연결 | Personal·Project의 반영 스킬에 Work 파일 구조를 넣지 않는다.02의 기록 설계가 모든 스킬 변경으로 번지지 않게 한다. |
| `context-update`를 다른 수행 수단으로 교체 | 호출자·스킬 발견/설치·실제 반영과 반환의 연결 | 내용·수정 권한·관리 기준은 해당 영역에 남아 수동 수행이나 다른 수단으로 이어갈 수 있어야 한다. |
| 경험 개선 절차를 중단·교체 | 개선 후보·채택·효과 관찰의 흐름 | 일상 읽기·Work 유지·허용된 사실 정정은 계속된다. |

모든 구성 요소를 아무 조정 없이 제거할 수 있다는 주장은 아니다. `USAGE`를 공통 방법의 정본으로 선택한다면, 파일을 없앨 때 계속 필요한 방법을 다른 정본으로 이관해야 한다. 반영 스킬도 호출자와 실제 확인을 맞추지 않고 이름만 삭제할 수는 없다. 유지할 내용 책임과 현재 실행 수단을 구별한다는 것이 이 배치의 기준이다.

기존 `read-project-context`의 일반 방법은 공통 참조, Project 특유 방법은 Project 읽기 지침으로 이관하는 후보이며 단순 삭제가 아니다. `update-project-context`는 위 반영 과업으로 재구성할 후보이고, 새 Work 생성은 별도 목적을 유지한다. 기존 명시 호출이나 설치된 소비자가 있다면06에서 실제 경로를 조사해 이관한다. 필요할 때만 기존 진입이 새 방법을 참조하는 호환 수단을 두고 절차를 두 벌 유지하지 않는다. Recover의 입력 복원과 Maintain의 자동 실행을 수동 문서 읽기·Main 유지와 같은 것으로 취급하지 않는다.

## 지금 판단할 범위

이 안은 파일명·스킬 개수를 확정한 최종 구현 명세가 아니다. 다만 책임 분리의 실제 대안으로 **일상 읽기의 공통 참조, 지속 본문 반영의 한정 스킬, Main의 Work와 작업 연결**을 구체적으로 선택해 보여 준다. 특히 반영 스킬을 지정한 Personal·Project 본문까지 공통화하는 범위와, 공통 참조로 이관할 실제 조항의 응집성을 다음 논의에서 확인한다.

기존 계약과 독립 대조에서 공통 참조 추가 시 일반 방법의 중복을 남기지 않을 것, 반영 스킬 완료 뒤 Main의 소비자 연결을 빠뜨리지 않을 것, 이미 채택된 기준의 반영은 정상 범위라는 점을 보완했다. 실행 본문·prototype·설정·source는 바꾸지 않았고 동작 시험·실제 제거 시험도 하지 않았다.

## 후속 — 디렉터리와 파일 배치

사용자가 디렉터리·파일 구성을 요청했을 때 보여 준 배치의 핵심을 보존한다. 설명 문장은 정리했으며 전체 답변의 축어 전사본은 아니다. 실제 prototype의 `development-workflow/skills/`와 `noline-demo/context/` 관계를 유지했다. `[추가 후보]`는 아직 없고, `[조정 후보]`는 추후 내용·연결을 맞출 곳이다. 잠정 합의 뒤에도 이 이름·형태는 최종 설치 명세가 아니다.

새 형성 자료는 기존 정책에 맞춰 안내·형성 맥락·기록·근거를 구별하되 실제 필요한 내용으로 구성하고 빈 틀을 미리 만들지 않는다. Work의 기존 구조에 새 `_background`를 붙이지 않는다. 실제 Project의 스킬 설치 위치, 여러 저장소의 배포·원형 관리·동기화는06에서 잇는다.
