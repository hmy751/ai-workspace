# 04-02 — 선택 판단과 조사 충분성의 보완 제안

**후속 반영 완료:** 사용자가 종합 방향의 적용·의미 확인·두 재시험을 요청해 [반영과 확인 기록](2026-10-26-ticket04-02-choice-investigation-adoption.md)으로 이어졌다. 아래 미반영·제안 표현은 채택 전의 판단 경과다.

**현재 판단:** 아래 최초 제안은 같은 날 `_background`와 원대화를 추가 대조하여 조정했다. [종합 재판단](#배경과-원대화를-함께-본-종합-재판단)을 먼저 읽는다. 사용처·대안 비교와 작업 담당의 근거 확인이라는 방향은 유지하지만, 현재 일정 화면만으로 내부 유지를 추천한 예시는 철회한다. 상세 열람 연결은 보조 수단이며 네 파일 수정 자체를 해결 단위로 확정하지 않는다.

2026-10-26. 사용자 요청: “2번이랑 4번을 기존 스킬이랑 실제 응답에 대조해서 어떻게 보완하면 좋을지 구체적으로 제안해봐”. **현재 요구를 더 강하게 반복하기보다, 판단을 가르는 자료를 고르는 방법과 해당 상세를 읽는 조건을 보완할 것을 제안한다. 실행 스킬에는 아직 반영하지 않았다.**

## 2번: 현재 위치의 설명에서 선택 판단으로 넘어갈 근거가 빠졌다

기존 본체는 이미 “요구·사용처·의미 있는 대안의 이득과 부담을 대조”하라고 한다. 작성 상세는 반환 항목의 누락 질문을 바로 복원 명령으로 바꾸지 말고 소비자가 여전히 필요한지 보라고까지 적는다. 따라서 필요한 원칙이 없었던 사례로 볼 수 없다.

실제 응답은 access가 내부에 있고 바깥에는 actions/view가 나온다는 사실을 정확히 설명했다. 그러나 결론은 다음과 같다.

> 폼의 보조 조회처럼 그 구별이 필요한 사용처까지 고려한다면 […] 제가 제안했던 계약대로 `{ query, access, actions, view }`를 반환하고 […] 열어 두는 편이 일관됩니다.

여기서는 ‘폼이 조건 구별을 필요로 한다’는 전제가 확인되지 않았고, 과거 제안과의 일관성이 현재 노출 선택의 주된 이유가 됐다. 당시 일정 화면 diff는 actions/view를 소비한다. 제공된 폼 발췌는 조회 데이터 사용을 보여 주지만 새 ReadAccess 전체를 필요로 한다는 증거는 아니다. 반환 확대 자체를 오답으로 정하지 않는다.

### 제안하는 편집

**explain 본체의 ‘선택의 적절성과 변경의 이득’ 첫 문단을 교체**한다. 권한·과거 의도·전후 비교의 기존 조건은 유지하며 첫 진입에서 작성 상세를 읽게 한다. 교체 후보:

> 선택의 적절성을 묻는다면 작성 상세의 선택 판단 절을 읽는다. 현재 요구와 실제 사용처에서 선택을 가르는 조건을 찾아, 현재안을 유지할 때와 의미 있는 대안으로 바꿀 때의 이득·부담을 대조하고 의견을 낸다. 앞선 AI 제안, 채택된 요구·계약, 현재 구현은 구별한다. 유효한 계약은 판단 기준에 포함하되 과거 제안과의 일치만으로 현재 선택을 정당화하지 않는다. 역할이 다르거나 다른 곳에서도 쓸 수 있다는 사실만으로 분리·노출의 필요를 확정하지 않는다. 당시 의도는 기록이 지지하는 범위로 말하고, 설명의 어려움이나 이의만으로 구조가 잘못됐다고 보거나 즉시 변경하지 않는다.

**작성 상세의 마지막 ‘어디 갔나/왜 없나’ 일반 예시를 구체적인 판단 대비로 교체**한다. 고정된 대안 수나 모든 호출부의 전수 조사를 요구하지 않는다. 후보:

> 반환 항목이 사라진 이유를 묻는다면 내부 존재 여부와 바깥에서 필요한지를 나누어 확인한다. 노출 필요의 근거로 든 실제 사용처에서 어떤 값을 읽고 어떤 결정을 내려야 하는지 본다. 현재 반환값으로 그 결정을 할 수 있다면 전체 내부 상태를 더 노출할 이득은 약하다. 반대로 필요한 구별이 사라졌다면 그 구별을 제공하는 방법과 부담을 비교한다. 예를 들어 조회 가능 여부와 제한 이유만 필요한 화면, 표시 정책과 실제 실행 정책을 별도로 알아야 하는 사용처는 같은 판단이 아닐 수 있다. 전체 상태 노출은 후자를 도울 수 있지만 소비자가 내부 정책을 다시 해석하고 분기하는 부담도 만든다. 확인되지 않은 다른 사용처는 가능성으로 남기고, 현재 추천과 그 추천이 달라질 조건을 밝힌다.

### 이번 답이 어떻게 달라져야 하는가

가능한 보완 답의 중심은 다음과 같다. 이것이 유일한 정답은 아니며 실제 합의된 계약의 지위도 함께 확인해야 한다.

> access는 내부에 남아 있습니다. 이번 일정 화면은 조회 가능 여부와 제한 안내를 actions/view로 받고 있으므로, 이 화면 때문에 access 전체를 추가 반환할 필요는 확인되지 않았습니다. 제공된 폼 발췌도 조회 데이터 사용을 보여 줄 뿐 표시 정책과 실제 정책을 따로 읽어야 함을 보여 주지는 않습니다. 전체를 노출하면 다른 화면이 그 정책 차이를 활용할 수 있지만, 화면마다 정책 분기를 다시 만들 가능성도 생깁니다. 현재 사용처 근거로는 내부 유지 쪽을 권합니다. 별도 정책 판단이 필요한 소비자가 확인되면 필요한 정보의 노출 범위를 다시 정해야 합니다. 앞선 반환 형태와 달라졌다는 점은 설명해야 하지만 그 사실만으로 복원을 권할 수는 없습니다.

현재안 유지 권고는 Main의 제한된 자료에 근거한 판단이다. 사용자가 명시적으로 채택한 반환 계약이 있다면 이 권고만으로 없앨 수 없다. 계약 충족 문제와 계약 재검토의 추천을 구별한다. 모든 응답을 ‘자료가 더 필요하다’로 끝내지 않고 확인한 범위의 추천은 낸다.

## 4번: 실행 불가와 지금 가능한 근거 대조가 섞였다

실제 응답은 코드·화면을 조사했고 과거 검사와 현재 미실행을 구별했다. 정상 경로와 제한·복구의 연속 관찰도 나눴다. 자료를 보지 않고 한계만 고지한 실패가 아니다.

다만 “화면 검사는 […] 다룬다”, “현재 코드와 회귀 검사상 수정됐다”는 근거에는 테스트 이름 검색이 주로 사용됐다. 테스트 본문의 설정·실제 확인 항목까지 읽은 기록은 없다. 뒤에는 기기에서 할 확인 목록이 이어졌다. 앱을 실행할 수 없어도 검사 코드가 실제로 어디까지 다루는지는 더 확인할 수 있었다.

추가 대조한 `case04-investigation/input/materials/repository/apps/client/tests/screens/create-schedule-flow.test.tsx`에는 다음이 있다.

```tsx
DatePicker: () => null,
TimePicker: () => null,
```

같은 파일의 첫 검사는 offline에서 직접 작성한 제목·장소·주소가 online 복귀 뒤 남고 저장 버튼이 하나이며 검색/저장이 저절로 실행되지 않음을 확인한다. 이 검사의 가치는 유지된다. 반면 날짜·시간 선택창을 실제로 열고 값을 바꾸는 동작은 이 검사로 확인되지 않는다. 이는 테스트가 무효라는 판단이나 실제 picker 결함을 발견했다는 뜻이 아니다. 이번 스냅샷의 다른 모든 검사에도 해당 보장이 없다고 확대하지 않는다.

### 제안하는 편집

검증 상세에는 이미 ‘어떤 경로를 실행하고 무엇을 assertion으로 보장하는지’, ‘mock이 중요한 실패를 숨기는지’, ‘한 경로가 막혀도 독립적으로 가능한 확인은 계속’이 있다. 이 내용을 explain에 다시 만들 필요는 없다.

**development 본체의 결과 반환 절 첫 문단을 교체**한다. 별도 검증을 의뢰할 때뿐 아니라 조사·보고 담당이 증거를 사용하는 순간에도 필요한 상세로 연결한다. 후보:

> 검사 통과·검토 발견 없음만으로 완료를 설명하지 않는다. Main이 직접 조사하거나 결과를 보고할 때도, 검사·기존 보고를 결론의 근거로 사용한다면 검증 상세의 ‘요구와 기본 검사에서 시작해 중요한 공백을 확인한다’를 읽어 해당 근거의 적용 범위를 대조한다. 실행이 막혔다면 ‘실제 경로와 실행 공백을 다룬다’를 읽어 지금 가능한 확인을 수행하고 남은 공백을 좁힌다. 근거가 유효하고 충분하면 재사용하며, 이 대조를 위해 전체 검사를 재실행하거나 별도 검증 역할 전체를 호출하지 않는다. 필요한 독립 검증의 조건은 앞의 전체 흐름을 따른다.

**검증 상세 도입의 독자 안내도 함께 맞춘다.** Main의 의뢰·반환·재검증 안내에 다음 범위를 연결한다.

> Main이나 조사 담당이 기존 검사를 근거로 결론을 낼 때는 아래 검사 적절성과 근거 재사용 부분을, 실행 제약을 다룰 때는 실행 공백 부분을 적용한다. 이 사용이 별도 검증을 수행했다는 뜻은 아니다.

검사 적절성의 기존 항목에는 필요하다면 “이름·통과 요약은 관련 검사를 찾는 단서이며, 결론을 지지하는 실제 확인 항목·입력·대체 구성을 대조한다”를 통합한다. 별도 체크리스트·모든 테스트 본문 열람 의무는 만들지 않는다.

development의 첫 결과에서 explain을 사용하라는 조항은 유지한다. 이번에 explain을 읽지 않았다는 것은 적용 누락의 관찰이지만, 같은 호출 문장을 더 강하게 반복하거나 모든 응답에 열람 증명을 출력하게 하는 개선은 권하지 않는다. 설명 조항을 읽었는지와 필요한 조사 행동을 했는지는 후속 확인에서도 따로 본다.

### 이번 답이 어떻게 달라져야 하는가

> 일정 생성의 기존 검사는 연결 복귀 뒤 제목·장소·주소와 단일 폼이 유지됨을 확인합니다. 다만 날짜·시간 선택창은 빈 대체 컴포넌트로 바꿔 놓았으므로, 해당 검사를 선택창 조작의 근거로 사용할 수는 없습니다. 선택창 호출부와 컴포넌트에서 값 전달·닫기 처리를 더 대조할 수 있고, 실제 열기·스크롤·키보드 동작은 기기 확인이 남습니다. 이번 환경의 실행 제약과 별개로 이 검사 범위의 한계는 파일에서 확인했습니다.

호출부·컴포넌트를 더 대조하겠다고 쓴 뒤 실제로 읽지 않고 완료 처리해서는 안 된다. 이 제안은 확인 순서와 근거 범위를 보이는 예시다. 날짜 초기값 전달이나 시간 선택 위치가 의심되더라도 해당 계약·구현과 실제 관찰 없이 제품 결함으로 확정하지 않는다.

## 권고 범위와 확인 방법

우선 편집 범위는 explain 본체·작성 상세, development 본체·검증 상세 네 파일의 해당 문단이다. shared 기준과 앞선 발화 상세는 이번 근거로 바꿀 필요를 찾지 못했다. 채택할 때 관련 형성 맥락·최소 발췌·안내와 표시 사본을 맞춘다. 전역 설치·모델 변경·새 agent·hook·별도 점검표를 추가하는 안은 아니다.

반영 뒤에는 우선 2번·4번만 같은 GPT-6-sol medium 조건에서 각 최초 1회 수행하여 기존 원응답과 대조하는 것이 적절하다. 동일 사례 재시험은 그 장면의 개선 확인이며 일반화 근거는 아니다. 평가 기준은 특정 결론이나 숨은 한 버그를 맞혔는지가 아니다.

- 2번: 실제 소비 조건으로 유지/변경을 비교했는가. 다른 조건이라면 반대 추천도 가능한가. 과거 제안만으로 결론을 닫지 않는가.
- 4번: 중요한 주장에 사용한 검사·관찰의 실제 보장 범위를 확인했는가. 가능한 추가 조사를 수행한 결과와 외부 실행이 필요한 공백이 구별되는가. 다른 중요한 공백을 충분히 조사했어도 인정한다.

1번·3번을 다시 돌리는 것은 이번 변경이 첫 전달·앞선 말 정정의 공통 수행에 실제 영향을 주었는지 보고 정한다. 이번 턴에는 제안 기록·진입점만 갱신했고 실행 스킬 수정·재시험·커밋·Ticket 마감은 하지 않았다.

## 배경과 원대화를 함께 본 종합 재판단

사용자는 배경 확인 범위를 물었고 Main은 안내·context 일부를 확인했으나 evidence와 변경 기록까지 대조하지 않았음을 밝혔다. 이어 “종합적으로 판단해봐 앞선 판단과 _backgorund랑 같이”라고 요청했다. 이 절은 해당 요청에 따른 후속 판단이다. 위 최초 제안을 모두 채택하거나 반대로 전부 무효화하지 않는다.

### 이번에 대조한 형성 근거

- explain의 [context](prototypes/development-workflow/skills/explain/_background/context.md)·[evidence](prototypes/development-workflow/skills/explain/_background/evidence.md) 전문, 통합·기존 두 본문 재검토·선별 반영·코드 표현·전체 구성·가독성·본문 정리의 현재 변경 기록을 읽었다.
- development의 [context](prototypes/development-workflow/skills/development/_background/context.md)·[evidence](prototypes/development-workflow/skills/development/_background/evidence.md), [실행 통합](prototypes/development-workflow/skills/development/_background/records/2026-10-23-execution-integration.md)과 [검증 통합](prototypes/development-workflow/skills/development/_background/records/2026-10-24-verification-integration.md)을 읽었다. 현재 review·verification·prior-explanation과 앞선 제안도 대조했다.
- 실험의 access 원대화에서 사용자가 명시한 설계 목표와 적용 범위 축소를 다시 확인했고, 보고서 원대화에서 이미 알려진 미확인과 이번 시험의 수행 제약을 대조했다.
- 모든 legacy 원본과 외부 자료 전체를 새로 조사한 것은 아니다. 위 형성 근거의 실제 선택 이유와 현재 응답을 대조하는 범위이며 새로운 일반 성능 증거는 없다.

### 배경 때문에 달라진 판단

**읽기 경로가 핵심 원인이라는 기대를 낮춘다.** 이전 비교에서 새 explain은 작성 상세를 읽었고, 후속에는 전후 코드도 읽었지만 실제 답의 구현·이유 연결은 충분히 나아지지 않았다. 상세를 읽으라는 연결을 추가하는 것은 누락 가능성을 줄이는 보조 수단이며 판단 수행의 해결 자체가 아니다. 당시와 이번 사례는 다르므로 현재 읽기 누락이 무관하다고 단정하는 것도 아니다.

**기존 구성을 존중하되 배경을 고정 규칙으로 삼지 않는다.** 사용자 원문에는 “배경에서 뜻이 그렇다고 딱 지키란 건 아니야”, “무지성으로 모두 조합해서 진리처럼” 다루지 말라는 정정이 있다. 기존 선택·근거·새 응답을 함께 판단하며, 옛 조항 전부를 복원하거나 실패마다 새 규칙·완성 답을 쌓지 않는다. 통합 후에는 관계·이유를 한 작성 상세에 둔 이유도 있으므로 선택 판단만 별도 스킬·파일로 떼지 않는다.

### 2번: 실제로 사용 중인 곳과 지원해야 할 사용 조건을 함께 본다

원대화의 사용자2471은 다음과 같다.

> 그러니까 조합도 중요하지만 폼이나 단독 쿼리데이터 등 확장성? 유연성? 이라고 해야하나? 이것도 염두하는

사용자2740은 다음과 같다.

> 잠깐 일단 다 적용하진말고 한군데 적용하고 마쳐봐

후자는 적용 범위를 줄인 지시이며 앞서 명시한 유연성 목표의 철회 근거가 아니다. **최초 제안의 ‘현재 일정 화면이 충분하니 내부 유지 권고’는 이 설계 목표까지 판단한 답으로는 부족하다.** 해당 권고 예시를 철회한다. 원응답의 전체 access 반환 권고도 폼의 실제 필요를 입증하지 못했으므로 그대로 채택하지 않는다.

판단할 것은 ‘전체 access를 내보내느냐’ 이전에, 목록·폼 보조 조회·데이터만 쓰는 소비에서 필요한 조회 상태·접근 조건·실행 기능을 각각 얻을 수 있는가다. 현재 화면뿐 아니라 사용자가 명시한 지원 조건도 비교 기준이다. 현재 소비가 없다는 이유만으로 요구된 유연성을 기각하지 않고, 막연한 확장 가능성만으로 모든 내부 정보를 공개하지도 않는다.

이번 구조에서는 actions.canRefetch가 실행 가능 여부를, view가 표시 결과를 제공하고 내부 access에는 display/actual 등의 구별이 남아 있다. 이것이 각 소비의 요구를 충족하는지와 별도 접근 정보가 필요한지를 연결해 판단해야 한다. 필요하다면 access 전체 반환과 필요한 공개 정보만 제공하는 선택을 비교할 수 있다. 특정 대안 수를 의무화하지 않고, 기존 제안의 필드 이름을 정답으로 고정하지 않는다.

**권고하는 보완 중심:** explain 선택 절의 기존 요구를 ‘이번 질문의 평가 기준을 유지한 채, 같은 사용 조건에서 선택별 결과·부담을 비교하는 수행’으로 구체화한다. 작성 상세의 기존 여행 복구 사례는 이미 실패 상황으로 책임 배치의 이유를 보여 주므로 유지한다. 마지막 반환 항목 일반 예시를 편집할 때는 다음 대비를 보인다.

1. 한 화면 적용의 충분성과 공통 구조의 지원 범위는 다를 수 있다.
2. 같은 소비 상황에서 현재 반환값으로 가능한 결정과 부족한 정보가 무엇인지 확인한다.
3. 부족한 정보를 제공하는 대안의 이득과 정책 중복·결합 부담을 대조하고 추천한다.

이는 응답 양식이나 반드시 세 단계로 출력할 요구가 아니다. 본체는 이 판단과 조건부 상세 연결을 맡고, 상세는 왜 어떤 자료를 골랐는지 보여 준다. access 전체 반환 또는 비노출을 정답 예시로 학습시키지 않는다. 앞선 AI 제안·채택된 계약·현재 사실의 구별은 여전히 유효하다.

### 4번: 추가 확인의 충분성이 중심이고 mock 확인은 그 한 사례다

배경의 원사용자789는 “추가 검토는 왜 안한거야? 정말 어렵거나 사유가 있으면 몰라도 […] 디테일하게 계속 파고들란건 아니고”라고 했다. 목적은 무한 조사나 한계 표시가 아니라 맡은 질문에 필요한 확인을 수행하는 것이다. development 배경에서도 기계 검사 유효성·검사 적절성·공백 추가 실행은 이미 구별해 합의했고, 개선 검토와 요구 충족 검증도 따로 두었다.

따라서 **4번 전체를 ‘테스트 본문을 안 읽은 문제’로 좁히지 않는다.** 중요한 결론을 현재 근거로 말할 수 있는지 보고, 결론을 바꿀 공백 중 지금 확인 가능한 것을 수행하며, 접근이 막힌 부분은 무엇이 해결되지 않았는지와 필요한 다음 실행으로 연결하는 것이 중심이다. 검사 코드 대조는 이번 환경에서 가능한 한 수행이다.

이번 원응답은 코드·이미지를 조사했고 실제 UI 미확인을 정직하게 밝혔다. 시험은 앱 조작·설치를 제외했으므로 원래 사건의 추가 실앱 확인 책임 전체를 평가한 것이 아니다. 검사 본문의 대체 구성과 실제 확인 항목을 읽지 않은 관찰은 근거 깊이의 제한된 부족을 지지하지만, 모든 조사·검증이 소극적이었다는 결론은 지지하지 않는다.

picker 미확인 자체도 원대화에 이미 있었다. 따라서 `() => null`을 찾는 것은 숨은 새 버그를 찾아낸 성과가 아니다. 기존 검사로 말할 수 있는 범위와 남은 사용자 경험을 더 정확히 연결하는 가치가 있다. 후속 시험에서도 이 설정을 반드시 찾게 하거나 이를 찾았다고 4번을 완료 처리하지 않는다.

**권고하는 보완 중심:** 작업 수행·종료 책임은 development에 유지한다. 기존 ‘한 경로가 막혀도 가능한 확인은 계속’ 조건을 설명 단계에서만 작동하는 일로 만들지 않는다. Main이 직접 조사·보고하거나 기존 결과를 재사용할 때도 필요한 검사 적절성·실행 공백 부분을 적용한다는 독자 연결은 좁게 보완할 가치가 있다. 그러나 verification의 기존 방법 전체를 본체나 explain에 복제하지 않는다. explain 호출 누락은 적용 누락으로 남기고 새로운 호출 장치로 해결하려 하지 않는다.

### 최종 권고와 남은 확인

| 최초 제안 | 종합 판단 |
| --- | --- |
| 실제 사용처·대안 비용으로 선택 판단 | 유지하되 명시된 지원 목표·아직 적용하지 않은 소비 조건도 포함한다. |
| 이번 자료로 access 내부 유지 권고 | 공통 설계의 결론으로는 철회한다. 현재 화면만의 충분성과 전체 지원 목표를 구별해 재판단한다. |
| 선택 상세를 읽는 조건 강화 | 보조 편집으로 유지한다. 수행 개선의 주된 근거로 내세우지 않는다. |
| Main·조사 담당도 검사 적절성 상세 적용 | 좁은 독자 연결로 유지한다. 별도 검증 역할 전체와 동등하게 취급하지 않는다. |
| 테스트 본문·mock 확인을 중심 보완으로 삼기 | 이번 가능한 확인의 예시로 한정한다. 중요한 결론과 필요한 추가 확인의 연결이 중심이다. |
| 네 파일을 고치고 같은 두 사례 재시험 | 파일 수를 확정하지 않는다. 채택한 행동 차이가 기존 문단·예시·연결에 반영되는지 먼저 대조한다. 재시험은 같은 장면 확인이며 일반화 입증은 아니다. |

배경을 종합한 현재 권고는 **질문의 목표를 유지하며 판단 근거를 만드는 방법을 구체화하고, 이미 있는 작업·검증 책임의 적용 범위를 좁게 연결하는 것**이다. 본체 문구 강화·파일 읽기·모델 변경만으로 해결됐다고 보지 않는다. 현재 구조를 대규모 재편하거나 새 스킬·agent·지표를 추가할 근거도 찾지 못했다. 이번에는 이 판단과 진입 기록만 갱신했으며 실행 스킬·실험 원응답은 변경하지 않았다.
