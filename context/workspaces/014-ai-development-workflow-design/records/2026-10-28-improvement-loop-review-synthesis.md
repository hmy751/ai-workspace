## 이름·기록에서 실제로 바꾼 것

사용자 원문:

> 근데 왜 learning이야? 너무 배우는거에 집중하는것 같아서 전체 성격을 고려한 네이밍은 없을까?
>
> 그래 그걸로 네이밍하고 다시 기록이나 이런거 한번 점검하고
> 검증자랑 개선리뷰 돌려봐 개선은 더 잘 하기위한 개선을 묻는 리뷰

스킬 폴더·frontmatter·표시명은 `improvement-loop`, 제목은 ‘작업 체계를 살펴 더 나은 선택을 반영한다’로 맞췄다. 실행안은 `improvement-loop.md`, 현재 티켓은 `05-improvement-loop.md`로 옮기고 현재 호출·진입·후속 연결을 갱신했다. 현재 본문·기준·구조·협업·수행 수단을 개선한다는 전체 목적을 드러낸 이름이다. 경험의 학습·축적은 계속 포함하지만 전체 목적을 대신하지 않는다.

당시 발화·초기 형성기록·고정 리뷰판의 옛 이름은 역사적 맥락으로 남겼다. 다시 접근하는 문서 링크는 현재 위치로 연결했다. 전역 스킬 설치·운영 설정·제품 코드·보존 source는 수정하지 않았다. 새 이름은 prototype의 실행 지침이며 전역 호출 활성화의 증거가 아니다.

검증 V1/P3는 `2026-10-28-ticket05-execution-prototype.md`의 현재 수행 표시명과 ‘learning-loop 본체’ 두 곳이었다. 링크는 정상이고 실행을 막지는 않았으나 두 이름이 별개 스킬로 읽힐 수 있어 improvement-loop로 수정했다. 현재 티켓의 합의 항목에 남은 당시 ‘파일/구현은 아직’도 prototype 작성·운영 미확인으로 정리했다. 과거 검사 수치를 새 판본 수치로 덮지 않고 검사 시점을 구별했다.

## 검증과 개선 리뷰의 범위

검토 시작 전에 이름 변경판의 prototype220개 파일을 [보존](reviews/improvement-loop-2026-10-28/input/prototype/README.md)하고 [SHA manifest](reviews/improvement-loop-2026-10-28/input/manifest.json)를 남겼다. 표시 사본 viewer.html은 제외했다. 두 담당자는 별도 맥락에서 시작했고 서로의 결론·Main의 예상 결론을 받지 않았다. 검토 중 실제 prototype도 고정했다. 보고서는 각 담당자가 직접 작성했으며 Main이 재서술해 원문을 바꾸지 않았다.

| 역할 | 실제 결론과 Main 판단 |
| --- | --- |
| 검증자 | 네 묶음 합의의 실행 본문·Personal 저장/재조회·대상별 반영, 후보/채택/실제 반영/효과와 원문 한계의 구별은 문서 계약 수준에서 충족. 명칭 잔여 V1만 경미한 불충족. Main은 V1을 수정하고 아래 한계를 유지한다. |
| 개선 리뷰어 | 큰 구조를 유지하되 한정 시도의 실제 소비·종료 연결을 우선 구체화하고, 동일 목적에서 개선 수단을 비교하는 사례로 보완할 것을 권고. 단순 적절성 확인과 다른 수행 개선 제안이며 Main도 두 안을 추천한다. |

검증자는 고정판·실물220개 해시, 실제 viewer 검사, 선택한 합의 원문과 사례 근거를 직접 대조했다. 개선 리뷰어는 고정판과 인터뷰·외부 보존 원문을 읽고 현행 유지와 다른 선택을 비교했다. 둘 다 원 세션 전체 훑기·실제 후속 세션 수행·운영 효과 시험을 한 것은 아니다. ‘큰 결함 없음’을 효용 입증으로 바꾸지 않는다.

## 추천 1 — 선택한 한정 시도가 실제 작업에서 읽히고 끝나게 연결

현재 본문은 한정 시도의 상황·행동·기대 변화와 관련 작업 연결을 요구한다. 그러나 일반 읽기는 채택 기준 중심이고 경험 후보 재조회는 요청 루프가 맡으므로, 다음 세션에서 선택한 시도만 회수할 위치는 수행자가 다시 판단해야 한다. 이것은 이미 발견 불가능하다는 결함 판정은 아니지만 즉시 반영과 다음 사용을 잇는 목적을 강화할 지점이다.

예를 들어 ‘다음 열린 설계 한 번에서 대안 차이를 먼저 보여주고 남은 질문을 묻자’를 선택했다면 다음과 같이 나눈다.

| 상황 | 구체 보완안 |
| --- | --- |
| 현재 대화에서 곧바로 수행 | 바로 수행한다. 보존을 위해 별도 진행 문서를 만들지 않는다. |
| 정해진 다음 작업에서 수행 | 그 작업이 원래 읽는 기존 지시·재개 본문에 시도 상황·행동·끝나는 범위와 경험 주제 연결을 둔다. 기존 Work가 있다면 current/Ticket을 쓸 수 있으나 Work 생성·등록은 필수가 아니다. |
| 어느 작업에서 실행할지 아직 없음 | 시도 의사·열린 후보는 보존하되 ‘다음 작업 연결 완료’로 표시하지 않는다. |
| 정한 시도가 끝남 | 임시 수행 연결을 더 이상 실행 지시로 읽히지 않게 갱신한다. 결과·이유는 경험 주제에 남기며 지속 채택은 별도 선택이다. |

채택 시 바꿀 곳은 [스킬의 선택 문단](prototypes/development-workflow/skills/improvement-loop/SKILL.md#함께-선택한-가능한-개선을-실제로-반영한다)과 [검토 당시 실행 사례](reviews/improvement-loop-2026-10-28/input/prototype/improvement-loop.md)다. USAGE에는 이번 작업에 이미 선택된 한정 시도의 범위도 읽는 연결만, 경험 관리에는 실제 소비 위치와 결과 연결만 둔다. 같은 규칙을 여러 곳에 전문으로 반복하지 않는다.

본문에 통합할 문안 후보:

> 한정 시도가 현재 대화에서 이어지면 바로 수행한다. 다른 시점의 특정 작업에서 수행한다면 그 작업이 실제로 읽는 기존 지시·재개 본문에 적용 상황·행동·끝나는 범위와 경험 주제를 연결한다. 소비 지점을 아직 정하지 못했다면 연결 완료로 표시하지 않는다. 시도 범위가 끝나면 임시 수행 연결을 갱신하고 결과·이유는 경험 주제에 남긴다. 이를 위해 모든 시도에 Work 생성·등록을 요구하지 않는다.

이득은 선택이 실제 행동으로 이어지고 한 번의 시도가 영구 규칙처럼 남지 않는 것이다. 비용은 필요한 경우 임시 연결을 만들고 끝낼 책임이며 상시 대장·일반 작업의 후보 전수 읽기보다 좁다. 확인은 선택된 작업의 재개에서 시도/종료 범위를 찾는 장면, 시도를 선택하지 않은 다른 작업에서 적용하지 않는 장면, 끝난 시도를 다시 실행하지 않는 장면으로 제한할 수 있다. 아직 이 행동 시험을 수행하지 않았다.

## 추천 2 — 같은 목적에서 개선 수단의 실제 차이를 보여주는 사례로 교체

현재 실행 사례는 협업 대화·문서 편집·설명 개선에 모여 있어 보존·문장 보완·유지의 예가 강하다. 범위 문구를 더 늘리기보다 실행안의 가상 중복 문서 통합 대목 일부를, 실제 준비가 필요한 ‘현재 세션 대화 전체 확인’의 대안 비교로 바꾸는 안을 추천한다. 역사적인 좋은 편집 경험은 Personal에서 그대로 보존한다.

| 같은 목적을 이루는 선택 | 실제 달라지는 행동 | 선택할 근거 |
| --- | --- | --- |
| 현행 유지 | 지침을 따라 원문을 직접 구간별로 읽는다. | 드물거나 현재 준비가 충분하면 새 도구·규칙의 비용이 더 클 수 있다. |
| 설명·예시 보완 | 혼동한 메시지 종류·시작/끝 범위를 이해하게 한다. | 이해 부족이 문제라면 직접적이다. 기계적 반복 준비 자체는 줄지 않는다. |
| 읽기 전용 추출 도구의 한정 시도 | 같은 세션 식별·발화 순서·중복 제외·원래 위치 처리를 반복 수행한다. | 실제 준비 부담·누락이 확인될 때 검토한다. host 변화·fork·압축 경계를 유지할 비용이 있다. |

현재 확인한 것은 원문 파일 식별과 구조다. 반복 비용·누락·도구 필요를 사실로 만들어내지 않는다. 이 안은 **비교 사례를 보완하자는 제안이며 추출 도구 채택·설치 제안이 아니다.** 실제 첫 사용에서 준비와 공백을 확인한 뒤 설명 문제인지 수행 수단 문제인지 판단하고 선택한 경우에만 해당 수행으로 잇는다.

필요하면 추천 문단에 ‘같은 장면에서 현행과 각 안이 무엇을 달리 하게 하는지 비교한다’는 뜻을 통합한다. 모든 후보의 표 형식이나 새 도구 후보 제출을 의무화하지 않는다. 이득은 개선을 문구 추가로 좁히지 않고 현행 유지·이해 보완·수행 수단 변경을 이유에 맞게 고르는 데 있다. 사례 일부를 교체하는 정도의 비용이며 실제 발견 품질 향상은 아직 기대다.

## 더하지 않을 것과 다음 판단

새 리뷰어를 루프의 필수 역할로 만들거나 발견·경험 조회 담당을 분리하는 안, 후보 상태 코드·점수·기한·정기 평가, 일반 작업의 모든 후보 열람은 지금 추가하지 않는다. 현재 근거로는 두 보완보다 운영 부담이 크거나 문제 자체가 확인되지 않았다. 기타-01은 계속 별도 보류다.

이번 요청의 개명·기록 점검·두 리뷰는 마쳤다. Main은 두 개선안을 추천하지만, 사용자와 고른 뒤 반영한다는 합의에 따라 실행 본문에는 아직 넣지 않았다. 다음은 두 안의 채택 범위를 정하고 선택하면 해당 본문·읽기 경로·대표 장면을 보완한 뒤 05 완료 조건을 대조하는 것이다. 실제 운영 설치·일반 효과는 별도다. 새 커밋은 만들지 않았다.
