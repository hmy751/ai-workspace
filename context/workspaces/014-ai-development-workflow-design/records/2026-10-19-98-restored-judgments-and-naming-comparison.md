# 빠진 기존 판단의 반영과 같은 코드의 이름 비교

2026-10-19. [평가97](2026-10-19-97-decision-coverage-and-body-assessment.md) 뒤 사용자 요청으로 현재 [development-workflow](prototypes/development-workflow/README.md)에 빠진 기존 판단을 반영했다. **공통 제공·사용처 선택과 계약·수명 두 주제를 일반 기준·상세 사례로 추가하고, 같은 인증 코드에 이름 유지+설명과 개명+설명을 나란히 두었다.** 기존 실행 예제의 이름과 동작은 유지한다.

## 사용자 요청과 실제 범위

> 그래 그럼 빠진 기존 판단부터 현재 프로토타입에 반영하자. 결정된 것과 유보된 건 구분하고, 이름 유지에 설명만 보완한 안과 개명한 안도 같은 코드로 나란히 보여줘. 왜 그렇게 반영했는지도 같이 설명해줘.

이 요청은97에서 확인한 미수록 판단을 현재 실물에 반영할 권한이다. 기록만 추가하는 데서 끝내지 않고 실제 Personal 본문과 읽기 경로, 이름 비교, Project·Work의 선택 설명과 viewer를 고쳤다. 특정 새 API·전역 기준·제품 설치·워크플로의 열린 운영 조건을 선택한 요청으로 확대하지 않는다. 작업 시작 HEAD는 `0aeb9e4`이며, 앞선97 평가와 재진입 안내의 미커밋 변경을 그대로 이어받았다.

일반 기준은 현재 적용할 의미·조건·판단 질문을 직접 설명한다. 상세 사례에는 최소 원문과 당시 코드·관찰, 사용자 동의·회고, Main이 구체화한 해석, 다른 선택이 가능한 조건을 함께 둔다. 기존 네 절을 같은 파일 구조로 복사하지 않고 필요한 판단의 관계로 두 주제를 구성했다. 기능 단위·내부 책임·물리적 배치와 완료·대기는 기존 이름 본문의 설명을 연결해 중복 정의를 줄였다.

## 이름 비교에서 같은 것으로 고정한 것

두 안은 현재 wrapper와 Login 소비자에서 주입용 factory만 생략한 재구성이다. A는 `loginAndRefresh`·`onCompleted`, B는 현재 이름인 `signInAndRequestRefresh`·`onSignedIn`을 쓴다. 인증 서비스 대기, 조회 비대기, 동기 요청 오류와 이후 rejection의 별도 전달, session 반환, 완료 뒤 안내·이동을 모두 같게 했다. 계약 주석도 똑같다. 초기 가정 코드에 없었던 동기 오류 분리는 현재 demo 동작으로 두 안에 공통 적용했다고 밝혔다.

| 비교 결과 | 반영 이유 |
| --- | --- |
| A도 가까운 설명을 읽으면 현재 사용에 충분하다. | 유지 안을 설명 없는 코드로 두어 개명 안을 유리하게 만들지 않는다. 확인하지 않은 내부 추적 부담도 가정하지 않는다. |
| B는 이름만 훑을 때 조회 요청과 인증 완료의 단서를 더 준다. | 이것이 이번 개명의 추가 이득이다. 실제 이해 속도가 개선됐다는 실험 결과로 주장하지 않는다. |
| 내부 두 사용처는 변경 비용을 제한한다. | 바꾸기 쉽다는 사실 자체를 개명 이유로 삼지 않는다. 현재 Spec 선택 요약과 Work의 개인 맥락 설명도 같은 의미로 고쳤다. |
| “로그인과 화면 갱신 완료”는 두 안 모두 “로그인 완료”로 정정한다. | 실제로 확인하지 않은 완료를 약속한 문구는 어느 이름에서도 고칠 대상이다. 문구 정정과 함수 개명의 효과를 섞지 않는다. |
| 조회 완료를 기다리는 동작은 추가하지 않는다. | 현재 소비자는 최신 조회 값을 바로 읽지 않는다. 실제로 필요해지면 이름 비교와 별도로 완료 계약을 판단한다. |

현재 B 선택은 유지하며 그 이유를 더 구체적으로 설명했다. 이 비교를 최초 구현자가 수행했던 비교나 사용자가 특정 함수명을 최종 수용한 사실로 쓰지 않았다. Personal은 비교 방법을, Project는 이 제품에서 구별할 완료·실패를, Work는 구체 이름과 선택 이유를 맡는다.

## 표시와 확인

같은 viewer에 ‘이름 유지·개명 비교’를 추가했다. 비교 원문 한 파일을 읽어 A·B 절만 넓은 화면에서 두 열로 배치하고, 좁은 화면에서는 순서대로 표시한다. 공통 조건과 비교 결론은 앞뒤에 유지하며 원문 보기에서는 Markdown 전체를 보여 준다. 표시용 코드 사본을 별도 정본으로 만들지 않았다.

- 별도 결정 검토자는 새 네 본문을35·37·47·48·49·50·52·53·54와 대조했다. 사용자 인용과 결정/회고/미선택 경계에서 수정이 필요한 문제를 보고하지 않았다.
- 별도 품질 검토자는 같은 코드 비교와 Personal·Project·Spec 설명을 읽었다. A/B 조건의 차이, 유지 안의 왜곡, 과거 수행·사용자 채택으로의 소급 문제를 보고하지 않았다. 이는 문서·코드 읽기이며 독립 적용 효과의 검증은 아니다.
- 두 코드 블록은 함수명·callback명 두 쌍을 대응시키면 주석까지 동일함을 확인했다. viewer 검사에도 이 비교를 추가했다. 현재 실행 소스와 테스트는 변경하지 않았고 제품 동작 검사를 다시 실행하지 않았다.
- viewer의 문서55개·소스와 테스트5개는 현재 원문·SHA와 일치했다. 내부 링크273개·참고 링크54개·앵커33개에 누락이 없고 두 비교 코드와 화면 스크립트 구문 검사를 통과했다. Workspace 전체 미커밋 변경의 Markdown29개에서 로컬 링크633곳과 끝 공백을 확인했으며 누락·공백 문제가 없었다. `git diff --check`도 통과했다. 이 변경 집합에는 앞선97 평가가 포함된다.
- 브라우저 실화면 확인은 수행하지 못했다. 로컬 HTTP 서버는 환경의 포트 바인딩 제한으로 시작하지 못했고, 브라우저 도구는 로컬 파일 프로토콜을 허용하지 않았다. 표시 사본의 원문·링크·앵커·스크립트와 두 코드의 동일성은 정적으로 확인하며, 실제 화면 배치·클릭 확인과 구별한다.

이번 변경은 같은 prototype과 Workspace의 재진입 안내에 한정했다. 원자료·과거 날짜별 기록·실제품·전역 하네스·기존 스킬은 수정하지 않았다. 커밋·운영 설치·전체 본문 수용·Ticket 완료로 처리하지 않았다. 후속은 같은 작업의 스킬 선택·구현·검토 수정·확인·반환을 구체화하며, 이번 본문에서 추가 판단 차이가 생기면 함께 다룬다.
