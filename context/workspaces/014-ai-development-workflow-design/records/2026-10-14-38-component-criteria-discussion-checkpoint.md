# Field·무한 스크롤 논의의 판단 기준과 현재 위치

2026-10-14. 사용자가 이번 대화의 기록을 요청한 시점에, 사례의 선택 이유와 일반화할 범위를 모았다. 현재 판단의 요약이며 직접 발화·코드·비교 과정은 기록 35~37이 소유한다. 글로벌 개발 규칙이나 새 컴포넌트 설계를 채택한 문서는 아니다.

사용자:

> 맞아 중요한건 상황마다 목적이나 뭐 트레이드오프를 고려해야겠지
> 그럼 이 대화에서 나온걸 기록 남길거 잘 남기자 더 나눌거 있어?

## 먼저 복원할 판단

**상황의 목적·필요와 선택의 이득·비용을 근거로 구조를 판단한다.** 공통으로 제공할 형식·동작은 필요한 만큼 묶고, 사용처마다 달라질 부분에는 그에 맞는 자유도를 둔다. 어떤 패턴이 항상 옳은지 고르거나, 근거 없이 '상황에 따라 다르다'고 결론을 미루는 기준이 아니다.

이번 사례에서는 아래 내용이 그 판단의 구체적 근거였다.

| 사례 | 확인한 사용자 의도·질문 | 이후에도 유지할 조건 |
| --- | --- | --- |
| Field | 디자인 변경에 대응할 확장성·유연성을 위해 의도적으로 합성 가능한 부품으로 나눴다. | 사용하는 곳에서 배치·조합을 바꿀 수 있는 가치를 코드량과 함께 본다. 합성은 공통 부품을 재사용하는 방식이며 미완성 공통화가 아니다. |
| Field와 React Hook Form | 전용 자동 연결안이 라이브러리에 종속되는지, 기존 Input이나 다른 입력으로 교체할 수 있는지 물었다. | UI 구성의 자유와 상태 연결의 위치는 따로 살핀다. 라이브러리 의존성의 범위·교체 계약을 평가하며, 모든 래핑이나 자동 연결을 거부한 것으로 확대하지 않는다. |
| 무한 스크롤 Container | 당시 일정 디자인 형식과 필요가 있어 컴포넌트로 제공했고, 달라질 부분은 열어 두었다. | 공통화의 필요와 예상 재사용 가치가 낮아지면 제거할 수도 있다. 고정된 재사용 횟수나 모든 화면의 동일 구조를 요구하지 않는다. |
| 무한 스크롤 Hook | 현재 Hook이 이미 별도 파일에 분리돼 있고 Container가 사용한다는 사실을 확인했다. | Hook과 Container는 서로 다른 수준의 재사용을 함께 제공할 수 있다. 둘 중 하나만 남겨야 하는 선택으로 다루지 않는다. |

Field와 Container의 선택은 양립한다. 제공하려는 역할과 필요한 변화 범위가 다르므로 묶는 범위도 다르다. 사용처의 연결 코드가 길다는 이유만으로 삭제하거나, 자유도가 더 높다는 이유만으로 모든 기본 조합을 해체하지 않는다. 반대로 기존 구조의 목적을 이해했다는 이유로 영구 보존하지도 않는다.

## 더 논의할 부분과 여기서 충분한 부분

Main의 판단으로, 이 두 사례에서 합성·공통화·Hook/Container 분리의 사용자 의도를 다시 묻는 추가 인터뷰는 지금 필요하지 않다. 현재 코드의 상세 API를 더 설계하는 일은 별도의 필요가 생길 때 선택한다. 이 판단은 코드 품질 기준 전체를 파악했다거나 01-02가 완료됐다는 뜻은 아니다.

다음 후보로는 **실패 상황의 처리와 검증을 어디에 맡길지**를 실제 코드에서 보는 논의를 제안한다. 예를 들어 기존 데이터가 있는 조회 실패의 화면 처리, 검증할 동작과 도구가 이미 보장하는 부분을 구별하는 문제가 있다. 이는 Main의 미채택 제안이며 01-02의 코드·검사 설계와 01-03의 동작 검증을 연결할 수 있다. 코드 네이밍·가독성 등 앞서 남겨 둔 기준 탐색도 아직 열려 있다. 다음 주제를 사용자 대신 확정하거나 조사를 시작하지 않는다.

전체 목표는 좋은 구현을 돕는 컨텍스트·기준·절차·도구와 기록·경험 반영을 함께 설계하는 것이다. 지금 얻은 기준을 구현자·검토자에게 어떻게 전달하고 실제로 확인할지도 후속 설계 대상으로 남는다. 선호를 모은 사실만으로 실제 실행 효과를 인정하지 않는다.
