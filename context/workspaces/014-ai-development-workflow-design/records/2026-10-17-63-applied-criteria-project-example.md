# 형식이 실제로 배치·전달·적용된 가상 프로젝트

후속 안내(2026-10-18): 이 기록은 아래 날짜의 제작 이유와 당시 형태를 보존한다. 연결된 prototype 본문은 [보완 기록66](2026-10-18-66-principles-cases-and-refinement-prototype.md)에 따라 원칙·사례·읽기 안내와 두 추가 장면이 갱신됐다. 아래9문서 설명을 현재 최종 배치나 운영 채택으로 읽지 않는다.

2026-10-17. 사용자 정정에 따라 기준 조각과 선택 비교를 설명하던 방식에서, **하나의 구체 배치를 선택해 이미 적용된 상태의 파일·메시지·결과를 보여 주는 방식**으로 바꿨다. [전체 파일](prototypes/applied-criteria-2026-10-17/README.md)과 [의뢰부터 최종 결과까지](prototypes/applied-criteria-2026-10-17/walkthrough.md)를 직접 읽을 수 있다.

> 애매해 초안이라고 대충 만들어서 정말 적용 상태라 가정하고 아웃풋을 보여줘봐 이게 어떻게 어던 형식으로 존재해서 전달되고 적용되고 하는지가 잘 안보여

## 사용자가 볼 현재 결과

가상 `shop-web`에 Project 기준·현재 HTTP 계약·개발 skill·HTTP-07 작업 Ticket·구현자 인계·검토자 결과를 실제 Markdown 파일로 작성했다. 파일에는 빈칸이나 ‘나중에 작성할 내용’ 대신 이 사례의 본문을 넣었다. 채팅으로 보내는 요청과 결과도 walkthrough에 완성된 문장으로 제시했다.

**프로젝트·역할 메시지·코드 수정·검사 통과·완료 상태는 모두 가정이다.** 실제 문서를 만들고 연결을 확인한 것과 제품에서 실제 개발·테스트를 수행한 것은 다르다. 이 폴더의 AGENTS·skill은 시연 자료이며 현재 ai-workspace나 원본 템플릿에 적용·설치하지 않았다. 소스·테스트 파일 전체는 복제하지 않고, 기준이 수정 판단으로 이어진 코드 부분을 발췌 형식으로 구성했다.

이 배치는 최종 채택 전의 **한 가지 완성된 적용 가정**이다. 범용 분류·폴더 표준을 확정한 것은 아니다. 62의 통합/분리 비교는 설계 이력으로 유지하며, 현재 사용자가 볼 대상은 이 배치와 실제 입력·출력이다.

## 기준이 실제 선택에 작용한 장면

1. 구현자는 공통 계약의 신뢰성과 HTTP 계약을 읽고, 본문 읽기·파싱 실패의 APIError 전달과 HTTP 상태 보존을 수정했다. 정상·오류 본문을 확인했다고 보고했고 느린 본문과 timer 정리는 미확인으로 인계했다.
2. 검토자는 같은 원요구와 기준, 변경과 구현자 기록을 받았다. 헤더 직후 timer를 해제해 본문 처리에 timeout이 적용되지 않는 문제와 요청 실패 때 정리 공백을 확인했다.
3. ‘제공한 수명과 실제 경로가 일치하는가’라는 기준을 10초 요청 계약에 적용해 본문 완료까지 timer를 유지하고 `finally`에서 정리했다. 관련 실패 경로를 다시 확인했다고 기록했다.
4. Main은 해당 작업 범위의 완료를 판단했고, Project의 HTTP 문서에 본문 처리까지 포함한 timeout 계약을 명확히 했다. 일반 품질 기준에는 이 버그의 수정 답안을 새 의무로 추가하지 않았다.

위 네 단계는 모두 같은 가상 사건의 구성이다. 기록 53의 수정 판단과 B 선택을 재료로 삼았으나, 실제로 관찰된 제품 결과로 승격하지 않는다.

## 이전 시안에서 달라진 점

62는 기준 본문과 전달 예시를 작성했지만 프로젝트 안의 지속 위치, 반복 절차와 작업별 입력, 구현자 제출 뒤 검토자가 실제로 바꾸는 결과가 충분히 한 장면으로 이어지지 않았다. 링크·anchor 검사와 한 독자의 의미 복원은 그 사용 장면을 대신하지 못했다.

이번에는 배치를 한 가지로 구체화하고, 일반 기준·현재 프로젝트 계약·반복 절차·이번 요구·실행 결과의 실제 파일과 문장을 모두 보여 준다. ‘미채택’이라는 설명을 이유로 결과 본문을 미완성으로 남기지 않고, 가정 범위를 바깥에서 명확히 한 뒤 그 안의 입력과 출력을 완성했다.

외부 참고 방식은 [61](2026-10-17-61-reference-comparison-for-format-design.md)의 의미 설명·조건별 질문·필요한 자료 읽기·작업 연결을 유지한다. 새 외부 조사보다 실제 배치·전달·수정·기록이 이어지는지 확인하는 것이 이번 작업의 초점이다.

## 실제로 확인한 범위

이 기록과 사례 문서 12개의 로컬 링크·anchor 80개를 확인했고 누락은 없었다. 대화에서 단계별로 읽는 화면에 넣은 프로젝트 문서 9개의 본문도 저장한 파일과 일치했다. 여섯 단계의 전환과 각 단계의 문서 선택을 브라우저에서 실행했으며, 스크립트 오류와 데스크톱·모바일 가로 넘침은 발견하지 못했다. `git diff --check`도 통과했다.

별도 독자는 시작 시점의 계약과 완료 후 문서가 섞이는 문제, 계약에서 구분한 오류 의미보다 확인 보고가 좁은 문제를 지적했다. 시작 시 계약 발췌를 분리하고, Project 계약에서 특정 수정 방법을 제거했으며, 가상 검토 결과의 본문 읽기·파싱·네트워크 실패 구분을 채웠다. 해당 독자가 이 두 수정 부분의 정합성을 다시 확인했다.

이 확인은 문서 연결·시점·가상 사건의 일관성과 화면 동작에 대한 것이다. 실제 fetcher 구현·제품 테스트·운영 적용의 증거는 아니다.
