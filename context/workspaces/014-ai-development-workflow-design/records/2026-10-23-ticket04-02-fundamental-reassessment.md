# 04-02 — 반복 개선의 정체와 두 설명 스킬의 다음 방향

**후속 논의:** 사용자가 ‘설명’ 하나를 진입점으로 하는 가능성을 열고, `_background`의 의도에 고정하지 말고 source·현재 논의를 함께 고려하라고 정정했다. 이에 Main은 아래의 두 스킬 분리 유지 권고를 [통합 구성 제안](2026-10-23-ticket04-02-explanation-skill-composition-proposal.md)으로 수정했다. 아래는 그 전의 재검토와 당시 제안을 보존한다. 반복 시험의 정체·실제 작성 방법 재구성이라는 진단은 이어가며, 최신 구성은 여전히 미채택 제안이다.

**Main 권고는 설명 복구의 현행 유지를 이번 설계 판단으로 확정하고, 브리핑은 요구 문구 보강에서 실제 설명 작성 방법의 재구성으로 전환하는 것이다.** 첫 완료 보고의 설명 책임도 함께 구체화하되, 브리핑 자동 호출만으로 조사·검토·범위 판단까지 해결하려 하지 않는다. 새로운 비교 시험보다 이 설계 선택이 먼저다.

이는 관련 기록·본문·원응답을 대조한 제안이며 사용자 채택이나 실행 본문 변경이 아니다. 현재 prototype·설명 복구·운영 설치 상태는 유지했다. 새 응답 시험, 제품 검사, 커밋은 하지 않았다. 준비된 Network A/B는 미실행 자료로 남으며 자동으로 다음 작업이 되지 않는다.

## 사용자가 다시 연 질문

사용자 원문:

> 난 지금 근본적으로  의문점이 든다해야하나? 이 두 스킬의 어던 구성이나 방법도 수정해야하나 싶기도 하고 뭔가 지금 사례들을 가지고 계속 개선 테스트 하는데 뭔가 잘 안풀려 아싸리 다른 스킬 04-01 처럼 필요 없어서 마무리 된것도 아니고 뭔가 작업도 뺑뺑돌고 그래서 니가 관련 길고이랑 문제점이랑 잘 파악해봐 그래서 어덯게 앞으로 하면 좋을지 고민해봐

직전 Main은 현황을 보고한 뒤 적용 조건부터 논의하자고 제안했다. 이번 요청은 그 다음 항목을 이어 정하라는 뜻보다, 두 스킬의 구성·방법과 지금까지의 문제 해결 방식 자체를 재검토하라는 뜻이다. Main이 왜 특정 문제를 스킬 수정으로 배정하고, 어떤 결과에서 다음 시험으로 넘어갔는지도 검토 대상이다.

[10월 21일 접근 재검토](2026-10-21-ticket04-02-approach-and-evaluation-reset.md)에도 다음 원문이 있다.

> 추가로 애초에 이 문제를 해결하기 위한 접근법이나 해결 방법 등등 이런게 잘못됐다고 봐 그러니까 지금 계속 삥삥돌잖아? 좀 제대로 확인해봐

따라서 이번 의문을 새 시점 비교 요구로 좁히지 않는다. 다만 이후 개별 보완·시험은 사용자도 직접 요청했으므로, 그 실행 자체를 무단 진행이나 정체 원인으로 단정하지 않는다.

## 기록이 지지하는 문제와 Main의 판단

### 1. 비교를 더 정확히 만드는 일과 해법을 선택하는 일이 분리됐다

초기 비교에는 이미 교정된 입력을 사용하거나, 별도 보고 지침의 효과를 스킬 시점과 혼동한 문제가 있었다. 이후에는 당시 자료 복원, 교정 제외, 판본 고정, 전문 읽기를 보완했다. 이 보완은 유효하다. [접근 재검토](2026-10-21-ticket04-02-approach-and-evaluation-reset.md)와 [시점 해석 정정](2026-10-22-ticket04-02-timing-and-skill-evaluation-clarification.md)이 경위를 보존한다.

그러나 최근의 더 엄밀한 비교에서도 결과는 주로 국소 개선 또는 우세 미확인으로 남았다. 그때마다 다음 사례·모델·문구·적용 배치로 옮겨갔지만, 어느 결과에서 무엇을 유지·변경·그만둘지는 충분히 결론 내리지 못했다. **실험 수보다 실험이 바꿀 설계 결정이 흐려진 것이 현재 정체의 한 원인이라는 것이 Main의 판단**이다. 모든 과거 실행이 무가치했다는 뜻은 아니다.

### 2. 필요한 요구가 없다는 문제와 요구가 수행되지 않는 문제를 구별해야 한다

[현재 브리핑](prototypes/development-workflow/skills/explain/_background/legacy/work-artifact-briefing/records/2026-10-23-before-explain.txt)은 시작, 실제 설명, 종료에서 역할·상태·책임과 실제 코드의 대응을 요구한다. [최신 여행 비교](experiments/artifact-explanation-trip-responsibility-2026-10-23/comparison.md)에서는 양쪽 모두 자료를 읽고 역할·흐름·이유를 설명했지만 그 대응을 함수 이름과 파일 링크 뒤에 남겼다. 통합판의 Router 책임 표현에도 부정확해질 여지가 있었다.

반면 [인증 비교](experiments/artifact-explanation-auth-depth-sol6-2026-10-22/comparison.md)에서는 코드·값·대기 전후 설명의 국소 개선이 있었다. 스킬이 무효라고 결론 내릴 근거도, 최신 문구가 안정된 해법이라고 결론 내릴 근거도 부족하다. 다만 **같은 요구를 더 자세히 쓰는 방식의 추가 이득을 당연시할 근거는 약해졌다.**

저장된 최신 여행 [공통 지시](experiments/artifact-explanation-trip-responsibility-2026-10-23/r71/input/prompt.txt)에는 답을 짧게 쓰거나 코드를 생략하라는 조건이 없다. 읽기용 출력 한도와 최종 응답 분량은 구별한다. 스킬을 먼저 읽고 60개 파일·108조각을 모두 읽은 조건은 일상 수행과 다르며 입력 부담의 영향은 미확인이다. 보존 자료만으로 당시 상위 시스템 지시 전체나 모델 내부 원인을 확정하지 않는다.

### 3. 원하는 설명의 예시는 이미 있으며, 그것을 다시 만드는 것도 반복이 될 수 있다

[Astra 개선 리뷰의 예시](2026-10-23-ticket04-02-astra-improvement-review.md#리뷰가-제안한-응답-예시의-핵심)는 생성 훅과 Repository의 실제 코드, 파리·도쿄 조건 대비, 저장 성공과 목록 갱신 성공의 차이를 함께 설명한다. 전체 완성 브리핑이나 사용자 수용 결과는 아니지만, 어떤 설명을 만들려는지 구체적으로 보여 준 자료다.

이번 설계 조사자도 처음에는 여행 설명을 새로 만들자고 권했으나 이 기존 예시를 대조한 뒤 철회했다. **기존 예시를 또 작성하는 대신, 예시에서 실제로 한 일을 수행 방법으로 옮길지 판단해야 한다.** 현재 예시는 설계·형성 자료이며 보통 실행에서 읽는 설명 방법의 자료와는 다르다. 이를 실행용으로 쓸 때도 역사적 예시의 지위와 내용은 보존하고, 같은 여행 답을 시험 입력에 준 뒤 일반 개선을 주장하지 않는다.

### 4. 설명·조사·구현 판단을 한 스킬의 개선 성과로 묶을 수 없다

보고서 사건은 필요한 관찰과 결과 종합의 부족이 함께 있었고, Network는 변경 범위의 해석과 설명이 섞였다. 충분히 설명하는 행동만으로 원래 조사나 구현 판단까지 적절해졌다고 볼 수 없다. 반대로 “다른 Ticket의 책임”이라는 이유로 첫 결과의 설명 문제를 이번 검토 밖으로 밀어낼 수도 없다.

[기존 책임 연결안](2026-10-21-ticket04-02-skill-and-workflow-change-proposal.md)은 이미 이 구별을 제안했다. 현재 필요한 것은 같은 구별을 다시 선언하는 것이 아니라, 첫 결과를 작성하는 Main이 무엇을 확인·설명하고 어떤 조건에서 브리핑 방법을 재사용할지 실제 연결안을 선택하는 것이다. 01-01·04-03의 병렬 실행 본문에는 이번 제안을 임의로 반영하지 않는다.

## 04-01에서 참고할 점

[04-01 마감](2026-10-21-ticket04-01-minimal-update-and-two-checks.md)은 두 스킬이 불필요하다는 결론이 아니다. work-discussion은 최소 보완을 채택했고 reconsider-work는 기존판을 유지했다. 앞선 16회 비교가 보편적인 정확도 우위를 입증하지 못했어도, 필요한 보완과 두 대조 조건을 정해 설계 결과를 마감했다. 운영 설치와 일반 신뢰성은 별도 후속이었다.

04-02에도 [완료 조건](../current/tickets/04-skill-improvements/04-02-artifact-explanation.md#완료-조건과-확인-방법)은 있다. 유지·보완안, 첫 보고·별도 브리핑·복구의 응답 차이, 질문 의도, 설명 부담과 사용자 판단을 다룬다. 모든 모델·장면의 이해 개선을 입증해야 설계 완료한다는 조건은 아니다. 다만 현재의 알려진 핵심 미수행을 “일반화 미확인”으로만 넘겨 완료할 수도 없다.

## Main이 권하는 구성과 방법

| 대상 | 권고 | 판단 이유·비용 |
| --- | --- | --- |
| explanation-recovery | 현행 유지로 이번 보완 판단을 정리한다 | 앞선 실제 발화의 뜻·누락·오류를 복구하는 입력과 행동이 분명하다. 브리핑과 통합하면 작은 뜻 질문까지 조사 범위가 커질 수 있다. 새로운 보완 근거가 생기면 다시 열 수 있다. |
| work-artifact-briefing | 역할·근거 경계는 유지하고 설명 작성 방법을 재구성한다 | 요구 항목이 이미 있어도 핵심 대응이 출력에서 빠진다. 같은 문구 강화보다 자료 선정과 설명 작성을 실제로 연결하는 방법을 제시할 가치가 있다. 재구성의 효과는 아직 가설이다. |
| 첫 완료 보고 | Main의 결과 작성 책임과 브리핑 방법의 사용 조건을 함께 구체화한다 | 변경의 의미·목표와 범위·핵심 근거·남은 문제는 첫 전달에서 다뤄야 한다. 매번 전체 브리핑을 호출하거나 설명 스킬에 독립 결함 발견까지 맡길 근거는 없다. |
| 준비된 Network A/B | 당장의 다음 실행에서 내려둔다 | 같은 기존판의 자연 선택/명시 적용 비교는 브리핑 작성 방법의 대안을 선택하는 시험이 아니다. 그 호출 선택이 실제 열린 결정이 될 때 재사용한다. |

브리핑의 재구성 방향은 설명에 넣을 항목을 늘리는 것보다 **독자가 지금 이해해야 할 관계를 정하고, 그 관계를 보여 주는 원자료 부분을 먼저 고른 뒤, 그 자료에 역할·조건·결과를 붙여 설명하는 것**이다. 필요한 추가 자료는 이 관계를 설명하다 발견된 공백에서 선택한다. 출력에는 설명의 중심과 근거가 함께 드러나야 하며, 전체 파일·원문을 그대로 나열하는 방식은 아니다.

- 코드라면 누가 판단하고 어떤 일을 위임하며 무엇을 반환하는지 드러나는 구현을 고른다. 저장 성공과 목록 갱신 실패를 구별하려면 그 두 처리가 갈라지는 코드와 결과를 함께 설명한다.
- 문서·보고서라면 현재 결론을 지지하거나 제한하는 실제 관찰을 골라, 원래 질문에 답하는 부분과 아직 답하지 못하는 부분을 연결한다.
- 짧은 의미 질문은 앞선 발화와 직접 답만으로 충분할 수 있다. 작은 질문까지 이 전체 구성으로 늘리지 않는다.

이 작성 방법과 필요한 짧은 예시는 실행 시 참고하는 본문·상세로 구성할 수 있다. 형성 자료는 왜 선택했는지를 계속 맡는다. 파일을 나누거나 예시를 추가하는 것 자체가 효과의 근거는 아니며, 기존 공통 기준과 사실·권한 경계를 중복 정본으로 만들지 않는다. 현재 두 스킬의 통합·폐기나 새 설명 전용 agent를 기본으로 둘 근거는 부족하다.

## 다음에 만들 결과와 닫을 조건

다음 제안 산출물은 **현재 브리핑의 재구성 본문과 실행 예시의 연결, 복구 유지 판단, 첫 완료 보고와의 사용 관계를 묶은 검토 가능한 안**이다. 새 사례 수집이나 좋은 예시의 재발견부터 시작하지 않고 위 기존 자료를 사용한다. 사용자에게 원하는 설명 기준을 추상적으로 다시 정의하라고 맡기지 않는다.

설계안을 선택한 뒤 확인은 바뀐 행동에 맞춘다. 예를 들면 원자료 선정·설명 연결이 실제로 출력에 남는지와 작은 질문이 불필요하게 무거워지지 않는지를 본다. 일반적인 기존/수정 승자 찾기보다 이번 안의 핵심 행동·사실 정확성·설명 부담을 판정한다. 실행 전에는 핵심 행동이 빠지면 재구성안 채택을 보류하고 같은 문구·같은 사례의 반복 생성을 하지 않는다는 후속 판단까지 정한다. 필요한 확인의 정확한 수·조건은 이번에 채택하지 않았다.

설계 완료는 각 스킬의 유지·변경과 연결 방법을 선택하고, 그 선택의 대표 수행과 한계를 확인해 기존 완료 조건에 대조하는 지점이다. 알려진 미수행을 숨기지 않되 실제 사용자 이해·장기 일관성·운영 효과를 모두 이 한 Ticket에서 입증하려 하지 않는다. 실사용 확인으로 넘길 부분은 구체적으로 남기며, 사용자 선택 전에 이번 권고를 완료나 새 운영 원칙으로 올리지 않는다.

## 이번 확인의 범위
