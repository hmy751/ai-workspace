# 날짜 예제의 월 입력과 구간 경계

2026-10-16. 사용자가 날짜·데이터 변환 예제를 살펴보도록 요청했다. 지정 template의 `src/utils/date.md`를 읽고 src에서 관련 식별자와 Calendar·DateRow 파일을 검색했다. 해당 Calendar·DateRow 실행 파일은 검색에서 발견되지 않았고 getCalendarDataWeeks 호출은 날짜 및 React Query Markdown 예제에서 확인했다. 구현 적용·실행 검증은 없다.

## 월 입력의 의미

루트 `/Users/hammyeong-yeon/Desktop/20_lab/template` 기준 `src/utils/date.md:120`은 다음 호출을 보여준다.

```ts
getCalendarDataWeeks({
  year: currentYear,
  monthIndex: (currentMonth - 1) as MonthIndex,
});
```

같은 문서 :83의 함수는 `new Date(year, monthIndex, 1)`로 시작한다. UI의 currentMonth는 문서상 1~12이고 함수 입력 monthIndex는 0~11이다. 이름과 명시적 -1 변환으로 표현의 차이를 드러낸다. `as MonthIndex`는 런타임 값 검증이 아니며 해당 타입 정의는 이번 src 검색에서 확인하지 못했다. 캘린더 결과의 그룹화·반환은 생략되어 있으므로 완성 함수의 계약을 검증했다고 하지 않는다.

함수가 일반적인 달력의 월을 받는 API라면 month를 1~12로 받아 함수 내부에서 -1을 할 수도 있다. 0~11로 이미 계산하는 코드에서 사용하는 함수라면 현재 monthIndex 계약도 자연스럽다. 무엇이 무조건 좋은지보다 변환 경계와 입력 의미를 사용처가 예측할 수 있는지가 판단 지점이다. 새 API를 제안·채택한 것은 아니다.

## 같은 문서의 서로 다른 끝 경계

:46은 `reservationStart <= weekEnd && reservationEnd > weekStart`, :72는 `reservationStart <= weekEnd && reservationEnd >= weekStart`다. 문서의 예제에서는 시작·종료일을 startOfDay로 정규화하고, 주의 끝은 endOfDay로 잡는다.

예약 종료일이 주 시작일과 같으면 첫 식은 제외하고 둘째 식은 포함한다. 예를 들어 10월 12일에 종료되는 예약과 10월 12일 시작 주를 비교하면 이 차이가 드러난다. 숙박에서 퇴실일을 점유하지 않는 표현이면 >, 종료일도 표시할 요구면 >=가 맞을 수 있다. 실제 제품의 표시 정책은 자료만으로 확정하지 않는다. 같은 의도를 설명하는 메모라면 일치시킬 후보지만 원본·제품 결함으로 즉시 판정하지 않는다.

## 남길 판단과 한계

숫자·날짜의 의미와 단위, 시작·끝 포함 여부는 계산의 계약이다. 라이브러리 사용이나 이름만으로 업무 의미가 자동으로 결정되지는 않는다. 책임·가독성·정확성이 같은 코드에서 연결되는 사례다. 현재 사용자의 당시 의도·보편적 명명 규칙 선택은 없다. 날짜 문자열의 시간대와 today 메모화 등 다른 메모는 발견했지만 이번 설명은 월 단위·끝 경계에 한정했다. 문서의 모든 권고를 사실로 재인용하거나 검증하지 않는다.


## 종료일 의미에 대한 확인 결과

종료일 포함 여부의 당시 의도를 물었고 사용자는 “이건 기억이 잘 나지 않네”라고 답했다. 종료일 포함·제외 모두 미확정으로 남긴다. 사용자에게 임의로 하나를 선택하게 하거나 일반적인 숙박 관행으로 당시 정책을 대신 확정하지 않는다. 비교식 차이는 코드 관찰로 유지하되 어느 쪽이 결함인지 단정하지 않는다.

이번 기준 탐색은 이 과거 정책을 복원하지 않아도 이어갈 수 있다. 실제 구현·수정이 필요할 때에는 해당 기능의 요구·표시 방식·기존 테스트에서 계약을 확인하거나 새로운 요구로 명시적으로 결정해야 한다. 여기서는 입력 단위와 경계 포함 여부를 드러내고, 경계가 같은 사례로 결과를 확인한다는 판단 재료를 남긴다. 이는 AI의 정리이며 사용자 정책 선택이 아니다. 같은 회고 질문을 반복할 필요는 없다.
