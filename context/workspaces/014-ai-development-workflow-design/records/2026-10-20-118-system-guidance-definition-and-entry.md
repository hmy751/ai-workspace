# 체계 지침의 개념 선택과 독립 본문

[117의 마무리](2026-10-20-117-content-policy-application-checkpoint.md) 이후 사용자는 Work의 기존 구성을 유지하고, DEVELOPMENT·CONTENT-POLICY처럼 원래 위치에서 진입점이자 본체였던 문서의 성격부터 구체화하자고 했다. 명명·정의·진입·분할을 논의한 뒤 **‘체계 지침’을 선택하고 CONTENT-POLICY와 별도의 문서로 작성**하도록 요청했다. 이번 시작 판본은 `114a5e9`이며 작업 트리는 깨끗했다.

## 대화에서 이어받은 판단

| 구별 | 현재 선택과 근거 |
| --- | --- |
| 내용의 성격 | 특정 영역의 구성요소와 그 작성·사용·연결·변경 방식을 다루는 체계 지침. 사용자는 개발 작업 중심의 정의를 정정했고 문서 체계도 포함하도록 했다. |
| 진입 본문의 역할 | 그 이름과 위치에서 공통 기준을 직접 설명하는 책임. 단순 링크 안내로 바꾸는 것과 필요한 상세를 분리하는 일을 구별한다. 모든 지침이 진입점이어야 한다는 합의는 없다. |
| 상세 분할 | 사용자는 `REFERENCE/composition.md`처럼 세분화할 수 있다고 명시했다. 소문자 상세도 현재 기준을 소유할 수 있다. |
| 대문자 | 대표 문서를 알아보기 위한 사용자 선호를 이번 기본 표기에 반영했다. 모든 지침의 대문자 의무·상위 권한·일괄 개명으로 확대하지 않는다. |
| 참고 예시 | 사용자가 지정한 `reference-project/context/work/workspaces/DOCUMENT-WRITING.md`는 읽기 전용 비교 예시다. 그 원본·운영 체계를 수정하거나 데모로 이식하지 않는다. |
| 이번 범위 | Work의 current·Spec·Ticket·source·output·records는 유지한다. 워크플로·스킬 구체화는 다음 Ticket이고, Personal·Project 전체의 관리 단위나 품질을 전면 재구성하는 요청도 아니다. |

‘운영 지침’, ‘컨텍스트 사용·관리 지침’, ‘작업 체계 기준’, ‘대표 기준문서’, ‘체계 진입 지침’은 검토 과정의 제안이었다. 앞의 세 가지는 범위가 좁거나 의미가 모호할 수 있었고, 대표·진입이라는 말은 내용의 성격보다 찾아오는 역할을 설명했다. 마지막에는 체계 지침이라는 이름과 구체적인 담당 범위의 설명을 함께 두기로 했다. 필요한 사용자 원문과 참고 예시의 발췌는 [새 본문 가까이 둔 근거](prototypes/development-workflow/noline-demo/context/_background/system-guidance/evidence.md)에 보존했다.

## 현재 결과와 책임

[SYSTEM-GUIDANCE.md](prototypes/development-workflow/noline-demo/context/SYSTEM-GUIDANCE.md)를 context 바로 아래 CONTENT-POLICY와 나란히 작성했다. 영문 파일명과 실제 배치는 Main의 구현 선택이며 사용자 발화 자체로 기록하지 않는다.

새 본문은 체계 지침의 구별, 진입 본문·상세 지침의 관계, 담당 책임을 드러내는 이름·첫 설명, 기존 읽기 경로와 형성 자료의 관계를 설명한다. 코드·제품 기준과 대비하고, 문서 작성 기준·혼합 README·분할 지침 같은 경계 사례도 다룬다. 과거 명명 논의를 순서대로 붙이는 대신 현재 문서를 새로 구성할 독자가 판단할 질문에 맞춰 썼다.

[CONTENT-POLICY](prototypes/development-workflow/noline-demo/context/CONTENT-POLICY.md)는 본문·형성 자료의 구성·보존·읽기·갱신을 계속 소유한다. 기존 진입 보존 설명은 새 문서의 해당 판단으로 연결하고, 개념을 두 정본에서 다시 정의하지 않도록 범위를 밝혔다. context와 prototype 입구에서도 필요한 상황에 새 본문을 찾게 했다.

새 문서의 [형성 자료](prototypes/development-workflow/noline-demo/context/_background/system-guidance/README.md)는 현재 의도·선택 이유, 명명과 진입의 판단 기록, 필요한 사용자 발화와 참고 예시를 구별한다. 014 전체 과정을 따라가지 않아도 본문의 이유를 재검토할 수 있게 선별했다. 기존 정책의 형성 자료는 이 논의로 이어지는 경로만 추가했다.

## 확인과 남은 범위

본문·연결 수정 뒤 열람 화면을 재생성했다. 문서117개·코드5개의 원문·해시 일치와 내부 링크678개·앵커201개를 확인했으며 경로·절 누락은 없었다. 대상물 밖 로컬 문서 의존도 없다. 이 결과는 표시 사본과 연결의 확인이며 브라우저 렌더링 실측이나 제품 동작 검사 결과는 아니다.

대화 대조에서는 최종 명칭·독립 문서 선택, 개발 범위 축소의 정정, 분할 허용, 대문자 선호, 참고 예시와 명시 제외를 별도로 확인했다. 실제 Work·reference-project·제품 코드·스킬은 수정하지 않았다. 기존 자료에 대한 평가나 새 문서의 작성이 전체 품질 수용·장기 유지 효과·관련 Ticket 완료를 뜻하지 않는다.

앞선 대화를 받지 않은 새 독자는 context README와 새 지침·CONTENT-POLICY에서 시작해 composition과 DEVELOPMENT를 선택해 읽었다. 형성 자료를 먼저 읽지 않고 다섯 가상 요청을 판단했다.

- 형성 자료 추가를 이유로 DOCUMENT-WRITING 본문을 전부 옮기고 옛 파일을 링크 안내로 남기는 안: 진입 본체의 책임을 잃는다고 읽었다. 실제 대상 문서와 참조를 읽지 않은 상태에서는 분할 내용을 확정하지 않았다.
- 소문자 composition: 자기 범위의 현재 기준을 소유하는 상세 체계 지침으로 읽었고, 개명이나 background 이동을 요구하지 않았다.
- 검토 절차와 코드 명명 규칙이 섞인 CONTRIBUTING: 내용별 역할을 구별하되 파일 전체 분류·분리 의무로 확대하지 않았다.
- Work의 새 background·index 구성: 현재 보류를 찾아 이번 변경의 적용 대상에서 제외했다.
- 개발 문서 한정 여부: 문서 구성·작성·갱신과 설명 충분성을 다루는 실제 예시로부터 개발 실행 절차 없이도 이 역할이 성립한다고 읽었다.

독자의 결론 일부는 다음과 같다.

> 읽은 자료는 context README, SYSTEM-GUIDANCE, CONTENT-POLICY, `REFERENCE/composition.md`, DEVELOPMENT다. 아래 판단에는 형성 자료가 필요하지 않았다.

> SYSTEM-GUIDANCE는 **체계 지침의 성격과 진입·상세의 책임, 이름·위치 판단**을 소유한다. CONTENT-POLICY는 **지속 본문과 형성 자료의 관리 단위·보존·읽기·갱신·이동 처리**를 소유한다.

이는 한 독자가 현재 본문을 읽고 가상 요청을 해석한 결과다. 실제 파일 변경 실험·장기 운용 검증은 아니며, 현재 다섯 장면에서 필수 수정으로 보고된 모호함이나 충돌은 없었다.

다음 세션은 [새 본문](prototypes/development-workflow/noline-demo/context/SYSTEM-GUIDANCE.md)을 현재 기준으로 읽고, 그 의미·구성을 바꾸려 할 때 관련 형성 자료를 고른다. Work는 당장 재편하거나 새 형성 자료를 붙일 대상으로 잡지 않는다. DEVELOPMENT의 최종 위치·운영 책임과 구체 워크플로·스킬은 후속 작업에서 이어간다. 이번 요청에는 커밋을 포함하지 않았다.
