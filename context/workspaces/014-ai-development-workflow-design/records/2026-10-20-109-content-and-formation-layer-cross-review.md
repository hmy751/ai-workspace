# 본문·사례와 형성 맥락·근거 — 독립안과 상호 검토

2026-10-20. 사용자 요청에 따라 두 리뷰어가 같은 사용자 원문·실제 문서·외부 자료에서 독립안을 작성하고, 최초안을 고정한 뒤 서로 검토했다. **큰 구성과 관리 판단은 일치했다. 남은 파일명 선택과 적용 조건은 그대로 구별하며, 이를 사용자 채택이나 실제 운영 효과의 검증으로 올리지 않는다.** 이번에는 기록과 현재 안내를 갱신했으며 prototype은 변경하지 않았다.

후속: [110의 대화 재점검](2026-10-20-110-formation-context-dialogue-review.md)에서 실제 대화의 흐름과 사용자 `index.md`·`index.cases.md` 제안을 함께 대조했다. 본문·사례, 현재 맥락·기록·근거의 책임과 읽기·갱신 조건을 이어 정리했다. 아래 독립안과 당시 파일명 제안은 그 시점의 검토로 보존한다.

## 사용자가 바로잡은 구별

본문과 사례는 현재 내용을 이해하고 적용하는 층이다. 형성 맥락과 근거는 그 내용을 이루게 한 의도·배경·목적·판단을 정확히 이해하거나 수정할 때 필요한 층이다. 사례도 필요할 때 선택해서 읽으므로, 읽는 빈도만으로 두 층을 나눌 수 없다.

가까이 두려는 이유는 중앙 records에만 남겼을 때 본문과 형성 이유의 연결이 시간이 지나며 유실되는 문제를 보완하기 위해서다. 본문을 읽는 사람이 바깥014의 전체 기록을 알아야 이해하는 구성은 유지하지 않는다. 필요한 핵심 맥락과 최소 발췌는 주제 가까이에서 읽을 수 있어야 한다.

추가 사용자 의견:

> 하나 더 그 맥락 근거 층위에 일단 내 개인적인 견해는 의도 배경 목적 정도는 웬만하면 있었으면 좋겠다는 뉘앙스도 추가로 전달해줘 정담 진리라기보다 내의견

두 리뷰어에게 이 의견을 그대로 전달하고, 세 제목이나 파일을 반드시 채우는 규칙으로 취급하지 않도록 했다. 정확한 사용자 원문과 동일하게 전달한 자료는 [공통 입력](context-layer-discussion-2026-10-20/brief.md)에 보존한다.

이 정정에 따라 [108](2026-10-20-108-topic-bundles-and-context-management-discussion.md)의 네 역할을 주제 폴더에 평평하게 모으는 Main 제안을 그대로 후속 구현 기준으로 삼지 않는다. 역할 구별을 실제 배치와 읽기 경로에도 드러내야 한다.

두 사람이 제안한 공통 구조는 다음과 같다. 파일명 대안은 미결정인 채 표시한다.

```text
noline-demo/context/
  README.md                         데모 공통 읽기·관리 원칙의 위치 후보
  personal/development/
    README.md                       개발 관점과 주제 선택
    naming-and-completion/

      cases.md                      현재 기준을 이해·적용하는 사례
      background/
        context.md 또는 README.md   형성 의도·배경·목적·선택 이유·열린 판단

```

이 구조는 비교 결과를 보여 주는 **제안**이다. 폴더명 `background`도 사용자에게 확정받은 이름이 아니다. 두 최종안은 위 맥락 파일을 각각 하나만 두며, 두 파일을 모두 만드는 절충안을 권하지 않는다.

## 상호 검토로 구체화한 내용

리뷰어 1은 리뷰어 2의 **실제 수정 제안으로 맥락의 충분성을 확인하는 방법**을 수용했다. “설명을 읽으면 두 이름 모두 쓸 수 있으니 동등하게 권하자”는 수정이 들어왔을 때, 가까운 맥락에서 코드 자체의 명료함을 지향한 이유를 찾아 무엇을 다시 비교해야 하는지 알 수 있어야 한다. 단순히 목적 항목이 채워졌는지를 확인하는 것보다 구체적이다.

리뷰어 2는 리뷰어 1의 **화면에서도 두 층을 구별해야 한다는 제안**을 수용했다. 파일을 하위 폴더로 옮겨도 열람 화면에서 네 문서를 동등한 항목으로만 표시하면 사용자가 원한 차이가 전달되지 않을 수 있다. 이 의견은 화면을 확인해 효과를 입증한 결과가 아니라 향후 반영할 구성 제안이다.

양쪽 모두 다음 내용 배치를 권했다.

- 초대 기능·오류 반환 같은 짧은 코드는 일반 기준의 뜻을 완성하므로 본문에 유지한다.
- 인증 A/B·저장 완료·문자열 `isError`는 현재 선택이 갈리는 상세 사례이므로 본문과 같은 사용 층에 둔다. 설명용 가정과 효과 미측정도 사례에서 함께 읽게 한다.
- 기존 `.context.md`의 형성 목적·방향을 가른 판단·미확정은 맥락에 유지한다. 긴 공통 읽기·갱신 표는 데모 공통 원칙으로 옮겨 줄이고 이름 기준 특유의 영향 관계만 남긴다.
- 기존 `.evidence.md`는 당시 발화·출처·최소 상황과 확인 범위를 보존한다. 현재 기준의 논증을 반복하는 해설은 맥락에서 맡는다.

의도·배경·목적을 남기는 예로 양쪽이 제시한 핵심은 “좋은 코드를 만들기 위해서” 같은 일반 문구가 아니다. 기능 요구와 함께 개인 코드 판단을 전달하려던 배경, 설명을 읽으면 사용할 수 있는 상태와 코드 자체가 의미를 드러내는 상태를 구별한 사용자 지향, 작성자가 이를 이름·타입·책임·완료 기준으로 구체화했다는 범위를 연결하는 것이다. 실제 작성 예와 어떤 정보가 부족한지는 각 최초안에서 확인한다.

## Main 판단과 남은 확인

이번 결과에서 의미 있는 개선은 파일을 하나 더 만드는 것이 아니라 **현재 적용에 필요한 내용과 형성 의도를 복원할 내용을 구별하면서 둘의 연결을 잃지 않는 것**이다. 이 방향은 사용자 정정을 충실히 설명한다. 의도·배경·목적을 가능한 한 남기되 충분성을 실제 수정 질문으로 확인하자는 보완도 타당하다.

파일명은 아직 하나로 정하지 않는다. 두 리뷰어가 서로의 이름을 받아들여 최종 권고가 교차한 사실 자체가, 역할에는 동의하면서 탐색상의 우선순위는 작고 조건적이라는 것을 보여 준다. 파일 목록과 폴더 진입 중 실제 사용 경로를 보고 정할 수 있다. 외부 권위나 다수결로 해결할 쟁점은 아니다.

구현을 이어갈 때 확인할 장면은 다음과 같다.

1. 새 소비자가 조회 결과를 필요로 한다면, 본문·사례만으로 이름 변경과 동작 변경을 구별하는가?
2. 두 이름을 동등하게 권하자는 수정 앞에서, 맥락으로부터 놓치면 안 되는 지향과 현재 비교 조건을 복원하는가? 과거 B 선택을 영구 정답으로 취급하지 않는가?
3. 사용자 의도와 작성자 구체화의 지위가 쟁점이면, 필요한 발췌에서 확인 범위와 미확인을 구별하는가?

이 장면들은 제안의 확인 기준이며 새 구조에서 실행한 검증 결과가 아니다. 기존 [107의 변경 실험](2026-10-20-107-naming-context-pilot-and-maintenance-trials.md)도 지금 제안한 새 배치의 장기 효과를 입증하지 않는다. 두 리뷰어의 일치 역시 독립 실험 두 번으로 셀 수 없다.

## 변경과 확인

최초안 두 파일은 교차 검토 전후 SHA-256이 일치했다. prototype 65개 파일의 목록·내용 해시도 이번 검토 시작 시점과 같았다. 갱신한 Workspace 진입·현재·비교 문서 8개에 포함된 로컬 링크 350개의 파일 대상이 존재했고 `git diff --check`를 통과했다. 이 확인은 링크 대상의 존재와 변경 범위에 관한 것이며 모든 절 앵커나 문서 의미의 자동 검증은 아니다.

공통 입력·최초안·상호 검토·이 비교 기록을 추가하고 Workspace의 현재 안내와108의 후속 정정 연결을 갱신했다. 이번 작업에서 제품 코드·브라우저·새 구조 사용 실험은 수행하지 않았으며 커밋은 만들지 않았다.

## 후속 논의 — 바뀐 이유와 과거 판단의 보존

사용자는 과거 기록 전체를 background에 두려는 것은 아니지만, 무엇을 피하려고 선택을 바꿨는지 남아야 현재 선택을 이해할 수 있다고 짚었다. 이후 조건이 바뀌어 과거 선택으로 복귀할 수도 있고, 실제 실패 경험 때문에 같은 선택을 피해야 할 수도 있어 별도 record가 필요한지 우려했다. 아직 구조 변경 요청이나 별도 기록 형식의 채택은 아니다.

사용자 원문 중 핵심:

> 바뀐이유가 현재 나은거랑 과거에 어떤 이것때문에 회피한거고 그게 남아야 지금의 이유를 명확히 알잖아?

> 물론 시간이 지나서 안돼서 과거의 결정을 복귀할수도 잇고 오히려 그건 안돼서 실패사례라 그걸 피해서 갈수도 있고

Main은 기존 제안을 대조했고 리뷰어1에게 이 우려의 포함 범위와 부족한 운용을 짧게 재검토하도록 했다. 최초안의 ‘변경할 때 무엇을 실제로 확인하는가’에는 중요한 방향을 뒤집으면 이전 선택·바뀐 조건·현재 판단을 짧게 남긴다고 이미 적혀 있다. 다만 현재 맥락을 고쳐 쓰면서 보존할 판단의 단위, 실패와 미채택의 구별, 반복 변경·복귀 시 별도 기록을 둘 조건은 아직 충분히 구체화하지 않았다. 아래는 후속 제안이며 두 리뷰어의 새 합의로 쓰지 않는다.

**현재 이유를 설명하는 데 필요한 과거 판단도 가까운 형성 맥락의 내용이다.** 무엇을 시도·고려했고, 당시 어떤 조건에서 어떤 이유로 바꿨으며, 그 이유가 지금도 유효한지를 함께 남긴다. 의도·배경·목적만 설명하고 중요한 전환을 최신 이유로 덮어쓰면 사용자의 유실 우려를 해소하지 못한다.

| 과거 선택의 상태 | 남길 의미 |
| --- | --- |
| 실제 시도에서 실패 | 관찰한 문제와 발생 조건, 무엇까지 확인됐는지. 모든 상황에서의 영구 금지로 일반화하지 않는다. |
| 예상 위험·비용 때문에 미채택 또는 유보 | 예상과 판단 근거, 시도하지 않았다는 사실, 다시 볼 조건. 실패로 기록하지 않는다. |
| 조건 변화로 다른 안으로 교체 | 이전 안의 이점 중 여전히 유효한 것과 바뀐 제약. 교체됐다는 이유로 이전 선택 전체가 틀렸다고 소급하지 않는다. |
| 과거 안으로 복귀 | 이전에 떠난 이유와 지금 달라진 조건, 그동안 얻은 관찰. 같은 이름의 선택으로 돌아와도 이전 판단 과정을 지우지 않는다. |

예를 들어 이름 B의 명료함과 낮은 변경 비용을 이유로 선택했다가 이후 호환 비용 때문에 A로 돌아간다고 가정하면, B의 명료함이 실패했다고 쓰면 안 된다. 명료함의 이점은 남지만 바뀐 비용 때문에 다른 절충을 택했다고 설명한다. 이는 운용을 설명하기 위한 가정이며 실제 prototype에서 일어난 변경·관찰은 아니다.

기본 제안은 짧은 전환 이유를 맥락의 해당 판단 곁에 날짜·조건과 함께 남기고, 직접 발화·관찰의 확인에 필요한 부분은 근거에서 보존하는 것이다. 현재 설명과 중요한 과거 선택을 구별해 갱신한다. 모든 편집의 날짜별 로그를 가까이 누적할 필요는 없다.

현재 설명을 다시 쓰면서 과거 판단의 정확한 내용이 사라지거나, 여러 변경·복귀를 구별해야 하거나, 판단을 지지하는 비교·검증 자료가 길어지면 별도 결정 기록으로 분리할 수 있다. 예를 들어 `background/decisions.md`나 개별 기록은 후보일 뿐 지금 생성할 기본 파일이 아니다. 분리해도 현재 맥락에는 지금의 선택을 설명하는 핵심 전환 이유와 재검토 조건을 유지한다. 결정 기록은 당시 선택·조건·이유를, evidence는 이를 확인할 발화·관찰·자료를 맡으므로 동일 내용을 형식적으로 중복하지 않는다.

현재의 추가 설계 질문은 “record를 둘 것인가” 하나보다 **어떤 과거 판단이 사라지면 현재 선택의 이해·실패 회피·대안 재검토가 어려워지는가, 그리고 그것을 갱신하면서 어떻게 보존할 것인가**다. 파일 배치와 공통 관리 원칙에 이 조건을 구체화할 필요가 있으며, 이번 후속 논의에서도 prototype은 변경하지 않았다.

## 후속 정정 — 기록 책임을 처음부터 구별하는 안

사용자는 다음과 같이 처음부터 decisions 층을 두는 편을 제안했다.

> 그냥 decisisons 층을 두는건 어때? 어차피 계속 다 읽어야 하는건 아니잖아? context에 애매하게 두다가 나중에 분리한다 보다 층을 도 분리하는게 나아보이는데?

또한 ‘분리가 필요해진 주요 결정의 기록’보다 `naming-and-completion`에 관한 기록·결정 등으로 역할을 설명하는 것이 지금 논의에 더 정확하지 않은지 물었다. 아직 실제 재배치 요청은 아니다.

Main은 실제 맥락·근거 파일을 다시 읽고 리뷰어2의 짧은 후속 의견을 받았다. 현재 설명과 당시 판단을 보존하는 기록은 갱신 성격이 다르므로, 분량이 커지는 것만을 분리 계기로 삼은 앞선 추천을 수정한다. **이번 이름 기준 묶음에서는 기록 책임을 처음부터 구별하는 안을 권한다.** 별도 보존과 매번 필독은 다른 문제다.

기록의 역할명은 **‘이름·완료 기준의 형성과 변경 기록’**이 적합하다. 이 기준의 의미를 형성하거나 바꾼 논의·제안·사용자 정정·선택·유보·변경 이유와 확인·반영 범위를 보존한다. 확정된 결정이나 실제 실패만 기록하는 것으로 좁히지 않으며, 모든 대화·편집·작업 완료 보고를 수집하는 뜻도 아니다.

구체적으로 코드 자체의 명료함에 관한 기록에서는 사용자에게 확인한 지향과 작성자가 이름·타입·책임 배치로 구체화한 시안의 범위를 구별한다. 개명 이득·비용에 관한 기록에서는 ‘함께 고칠 수 있음’을 개명 이유로 쓰던 설명을 전환 비용의 근거로 고친 내용을 보존한다. 후자는 Main의 본문 구체화이며 그 정확한 문장을 사용자에게 따로 확정받은 것으로 소급하지 않는다.

현재 제안은 background 아래에서 `context.md`가 목적·배경·현재 유효한 이유와 관계를 설명하고, 별도 기록이 당시 쟁점·조건·선택·변경과 그 지위를 보존하며, `evidence.md`가 필요한 실제 발화·관찰·출처를 제공하도록 하는 것이다. 현재 맥락에도 중요한 전환 이유의 요지는 남긴다. 기록을 추가했다는 이유로 모든 문서에 같은 내용을 복제하지 않는다.

`decisions/`는 선택과 결정 상태를 중심으로 표현할 때 적합하다. 미해결 논의·정정·제안까지 포함하는 이번 범위에는 `records/`와 위 역할 설명이 더 정확하다는 것이 Main의 현재 명칭 제안이다. 이 records는 해당 기준의 형성과 변경에 한정하며 바깥014 전체 작업 기록의 복제본이 아니다. 폴더명과 실제 구성은 아직 미채택이고 prototype 변경도 없다.
