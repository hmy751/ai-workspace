# 적용 사례와 도출 이유를 함께 본 제3자 개선 리뷰

2026-10-17. [적용 사례 63](2026-10-17-63-applied-criteria-project-example.md)과 Main이 설명한 도출 이유를 함께 검토하도록 사용자가 요청했다. 형식·분류·전달 방식의 부족한 점과 개선 방향을 판단하는 리뷰이며, 제품 동작 검증이나 현재 안의 채택 심사가 아니다.

## 사용자 요청과 검토 입력

> 그럼 이 결과물이랑 방금 설명한 이유를 같이 제3자 개선 리뷰어한테 보여주자. 우리 스펙이랑 내 생각을 고려했을 때 형식·분류·전달 방식에서 뭐가 부족하고 어떻게 개선하면 좋을지 봐달라고 해줘.

사용자가 앞서 제시한 생각은 [57](2026-10-16-57-criteria-organization-and-guiding-questions.md)에 원문으로 보존돼 있다. 구체 코드 사례를 넘어 통하는 일반 가이드·원칙, 무엇을 고민해야 하는지의 구체화, 작업자·검토자가 기준을 고려하도록 질문을 전달하는 방식이 핵심이다. 모든 질문을 사용자에게 되묻거나 같은 답안 양식을 의무화하자는 확정 요구는 아니다.

Main의 직전 설명에서 검토 대상으로 전달한 핵심 문구:

> 이번 구성의 목적은 네가 코드마다 설명해 준 판단 기준을, 다른 작업에서도 AI가 찾아 적용하고 네가 그 판단을 이해·수정할 수 있게 만드는 것이었어.

> 원칙은 무엇을 중요하게 보는지 알려 주고, 질문은 실제로 무엇을 확인할지 알려 주며, 사례는 조건에 따라 답이 달라지는 모습을 보여 주는 역할이야.

> 정확한 파일명, 파일 수, 하나의 develop skill에 두 역할을 넣는 선택은 내가 적용 모습을 구체화하려고 정한 부분이야.

직전 설명 전체도 reviewer의 대화 입력으로 전달했다. 설명은 사용자 생각을 출발점으로 삼고, Spec의 Project·작업·검토·기록·경험 반영을 연결하며, 외부 자료의 개념 설명·조건별 질문·필요시 읽기·작업 근거 연결을 참고했다는 Main의 도출 주장이다. 외부 자료가 실제 파일 배치나 효과를 입증한다는 뜻은 아니며, 그 도출 관계 자체도 이번 검토 대상이다.

원자료 진입점은 [Spec](../current/spec.md), [01-02](../current/tickets/01-development-workflow/01-02-code-design-quality.md), [사용자 생각 57](2026-10-16-57-criteria-organization-and-guiding-questions.md), [앞선 개선 조언 59](2026-10-16-59-format-design-objectives-advisor.md), [외부 비교 61](2026-10-17-61-reference-comparison-for-format-design.md), [적용 사례 전체 파일](prototypes/applied-criteria-2026-10-17/README.md)과 [walkthrough](prototypes/applied-criteria-2026-10-17/walkthrough.md)다. 59의 목적·비교 기준과 Main의 파일 분할도 정답으로 고정하지 않았다.

## 리뷰의 독립성과 작업 경계

제작에 참여하지 않은 내부 subagent에게 개선 리뷰를 맡겼다. 사용자의 발동 원문·앞선 정정·현재 산출물·직전 설명을 전달하고, 필요한 원문과 문제 정의를 reviewer가 직접 정하게 했다. 처음에는 원문 중계를 요청받았으며, 이후 읽기 전용 파일 API로 Spec·Ticket·사용자 발화와 사례 문서에 직접 접근할 수 있게 했다. 파일 수정·shell 실행·설치·추가 위임은 맡기지 않았다.

리뷰는 중요한 부족점의 실제 문구·위치, 사용자/Spec 목적과의 관계, 구체적인 개선 방향·비용과 작은 전후 예를 요청했다. 가상 프로젝트의 코드 변경·검사 통과·완료를 실제 실행 증거로 사용하지 않으며, 문서에서 판단 가능한 것과 이후 실제 사용에서 확인할 것을 구별한다.

## 개선 의견과 Main의 판단

리뷰어는 Spec, 01-02, 57·59·61·63, 적용 예시 README·walkthrough와 shop-web 문서 9개를 직접 읽었다고 보고했다. 다음은 조언을 결정별로 압축한 기록이며, 실제 사용 효과의 판정은 아니다.

핵심 의견:

> 현재 구성은 문서가 어디에 있고 구현·검토·완료로 어떻게 이어지는지는 보여 준다. 다만 사용자가 원한 ‘다른 코드에도 통하는 기준과 질문’의 형식을 결정하기에는, 질문이 판단을 바꾸는 장면과 기준의 지위를 설명하는 부분이 약하다.

### 1. 기준과 질문이 선택에 영향을 주는 장면을 보완한다

현재 walkthrough에서는 Main이 기준을 지정하고, Ticket이 본문까지 포함한 timeout을 요구하며, 구현자가 느린 본문·timer 정리를 미확인으로 인계한다. 이는 계약·인수·B의 직접 수정을 설명하는 데 적합하다. 다만 일반 기준·질문을 제거해도 같은 수정으로 이어질 가능성이 있어, 질문의 형식과 전달 방식을 비교하는 장면으로는 차이가 약하다는 의견이다. 이는 문서를 근거로 한 reviewer의 해석이며 실제 제거 비교 실험의 결과가 아니다.

현재 HTTP 요구를 일부러 모호하게 만들지 않고 사례를 유지하되, Field나 Container에서 선택이 갈리는 짧은 장면을 보완하라고 권했다. 예를 들어 ‘입력 연결 중복을 줄여 달라’는 요청에서 작업 단서로 기준을 찾고, 실제 사용처의 차이를 확인한 뒤 일체형·합성 유지·연결만 공유하는 선택을 비교하게 한다. 조건이 달라지면 판단도 달라질 수 있음을 보여 준다. Main이 요청문에 기준 이름과 답을 모두 지정하지 않아야 찾아 쓰는 부분도 드러난다.

이 제안의 비용은 작은 장면 하나이며, 새 프로젝트나 전체 작업 기록 세트를 추가하자는 뜻은 아니다.

### 2. 일반 판단·프로젝트의 현재 선택·사례의 지위를 본문에서 구별한다

직전 설명에서는 사용자 생각·Spec·외부·Main 설계를 구별했지만, quality.md만 읽으면 Field·Container 서술이 조건을 설명하는 사례인지 현재 프로젝트 구조인지 해석해야 한다. Project README에도 같은 구조가 현재 사실로 소개돼 있다. 01-02의 공통 기준·제품 규칙·사용자 선호 구별과 Spec의 이유 이해·재판단 목적에 비추어 보완할 부분이다.

모든 문장에 출처 태그를 붙이기보다 선택을 오독하기 쉬운 곳에 이유와 바뀔 조건을 짧게 쓰라고 권했다. 제안된 문구:

> 공통 단위가 보장할 동작과 사용처가 선택할 부분을 함께 판단한다.
>
> 이 프로젝트가 Field의 합성을 유지하는 이유는 화면마다 입력 배치와 구성이 달라지기 때문이다. 연결 코드가 남아 있다는 사실만으로 이 선택을 바꾸지는 않는다. 연결을 공유하더라도 필요한 배치와 입력 교체가 유지되는지 확인한다.

첫 문장은 일반 기준이며 다음 문장은 프로젝트의 선택과 이유다. 실제 구조 상세는 Project 설명이 소유하고 quality에는 판단 차이를 이해할 만큼의 대비를 남길 수 있다. 중요한 선택은 결정 근거에 연결한다. 이 문구는 가상 사례의 개선 제안이며 원본 제품의 새 정책이 아니다. 비용은 설명이 조금 늘어나는 것으로, 사용자 선호·일반 원칙·정책을 각각 별도 파일로 만들자는 권고는 아니다.

### 3. 찾아 읽는 안내의 소유 위치와 적용 조건을 정리한다

AGENTS·Project README·Work README·Ticket·skill이 같은 자료와 현재 HTTP 작업을 반복 소개한다. 가장 구체적인 상황별 읽기 안내는 develop skill에 있다. 그 조건은 ‘공통 단위의 범위를 바꿈’, ‘공개 입력·반환·오류·수명을 바꿈’에 집중돼 있어, 구조·계약을 바꿀 의도가 없는 결함 수정이나 페이지 책임·이름 이해 작업에서 진입이 상대적으로 약하다. 현재 두 기준을 전체 코드 기준의 최종 분류로 볼 수 없다는 의견이다.

한 대안으로 Project README가 상황별 기준·계약 안내 표를 소유하고, develop은 그 표를 이용한 역할별 수행·반환, AGENTS는 Project·지정 Work·역할 절차로의 진입을 맡는 구성을 제안했다. 특정 HTTP 작업 소개는 작업 요청에서 전달할 수 있다. 읽기 조건 예시는 ‘계약을 바꿀 때’에서 ‘반환·오류·실행 수명이 관련되는 변경이나 결함을 다룰 때’로 보완한다.

목적은 파일 수 감소보다 같은 읽기 조건을 고칠 곳을 분명히 하는 것이다. Project 입구의 표를 유지하는 비용이 생기므로 현재 단계에서 세밀한 분류 체계나 여러 색인을 추가할 필요는 없다고 봤다.

### 4. 현재 계약·이번 작업 범위·최종 인수 판단을 구별한다

완료 판단이 Work README·Ticket·review의 Main 수락·채팅에 반복된다. 요약 반복은 가능하지만 지속 파일 각각이 같은 상태와 상세 판단을 소유하면 정정 위치가 늘어난다. http-client.md의 ‘이번 계약이 제공하지 않는 동작’ 아래 ‘HTTP-07에 포함하지 않는다’는 문장은 제품의 현재 미지원과 이번 작업에서 건드리지 않은 범위가 섞여 있다.

Project에는 현재 지원·미지원 계약을, Ticket에는 이번 변경·보존·제외 범위와 최종 인수를, Work README에는 상태 요약과 정본 경로를, 구현·검토 기록에는 각 역할의 당시 관찰을 두는 방향을 제안했다. Project 문서를 누가 갱신하고 누가 인수하는지도 짧게 명시할 수 있다. 예컨대 수정 담당자가 관련 계약을 맞추고 Main이 Ticket에서 인수하는 안이다. 이는 아직 선택할 운영안이며 자동화나 새 역할 파일을 요구하지 않는다.

### 유지할 강점과 외부 근거의 강도

원칙·질문·조건별 사례를 가까이 두는 구성, 구현자와 검토자가 같은 요구·기준을 쓰는 방식, 질문마다 답안 제출을 강제하지 않는 선택, Field·Container를 단순 좋음/나쁨으로 나누지 않는 점은 유지할 만하다고 봤다. 일반 기준에 timer 수정 방법을 새 의무로 추가하지 않은 점도 기록과 기준 개선을 구별한 예로 평가했다.

외부에서 얻은 근거가 강한 것은 이유·조건·질문·사례의 연결과 필요한 때 읽는 방향이다. 9개 파일, 하나의 develop skill, 여러 완료 기록은 외부에서 필연적으로 나온 구성이 아니다. Main이 이를 자체 설계라고 밝힌 것은 적절하지만, 출처를 더 붙이기보다 배치가 실제로 줄이는 해석·탐색·갱신 부담을 비교하라고 권했다. reviewer는 이번에 외부 원문을 새로 조회하지 않았으며 외부 인용의 정확성 재검증을 수행한 것은 아니다.

## Main의 판단과 다음 논의

Main은 1·2를 먼저 보완할 문제로 받아들인다. 현재 HTTP 사례는 배치·인수·수정·기록을 설명하는 역할로 유지하고, 조건이 선택을 바꾸는 짧은 장면과 이유·바뀔 조건이 드러나는 기준 본문을 나란히 비교하는 것이 다음 추천이다. 사용자가 요청한 형식 판단을 돕기 위한 범위이며, 기준 전체 재작성·추가 코드 탐색·새 프로젝트 구성을 먼저 요구하지 않는다.

3에서 읽기 안내의 중복과 적용 조건은 보완할 가치가 있다. 다만 안내 표를 반드시 Project README로 옮기는 세부 배치는 reviewer의 대안으로 남긴다. 역할별 절차와 사람이 찾는 입구 사이에서 무엇을 한곳이 소유해야 하는지 판단한 뒤 정한다. 4의 현재 미지원과 작업 제외 범위는 의미를 구별해야 하며, 최종 인수 정본과 갱신 담당의 구체 선택은 01-01·02·03·04와 연결할 운영안으로 남긴다.

**이번에는 리뷰를 받고 기록했으며 적용 사례의 본문·분류·skill을 변경하지 않았다.** 사용자 채택·전체 형식 확정·제품 적용은 없고 01-02는 진행 중이다. 실제 AI가 필요한 기준을 찾는지, 질문 때문에 판단이 나아지는지, 보고 부담이 적절한지는 이후 실제 사용에서 확인할 사항이다.

## 기록 반영과 확인 범위

리뷰 기록과 Workspace 진입·현재 상태·Spec·01-02·output·records 색인에 최신 논의를 연결했다. 이번 변경 문서 8개의 로컬 링크 대상 300곳이 존재했고 `git diff --check`가 통과했다. 내부 anchor·원격 URL 전체 검사, 제품·agent 적용 실험은 수행하지 않았다. 가상 사례 파일·외부 원문·source·전역 지침·실제 제품은 변경하지 않았다.

[05](../current/tickets/05-improvement-loop.md)는 한 번의 관찰을 일반 기준의 수정으로 올릴 조건, [06](../current/tickets/06-framework-transition/README.md)은 공통 기반과 프로젝트 사이의 적응·반영, [07](../current/tickets/07-integrated-rehearsal.md)은 부분 설계의 연결과 후속 적용 확인을 맡는다. 07의 연결 관점은 지금부터 사용하지만 전체 연결 검토를 완료했다고 보지 않는다. 지금 예시 하나로 경험 반영 규칙이나 프로젝트 간 이식 방식을 확정하지 않는다.

04는 현재 가상 develop skill을 그대로 완성하는 과제가 아니라 기존 스킬의 실제 조건·입력·반환·기록을 보완하는 과제다. 04-01은 기존 요구 안의 선택과 목표·계약 재판단의 경계, 04-02는 조건과 이유가 드러나는 첫 보고·브리핑·설명 복구, 04-03은 실제 맥락 읽기·갱신·생성을 맡는다. 현재 예시는 그 접점을 드러내는 재료이며 기존 스킬 대조를 대신하지 않는다. 02의 범위도 실행 결과 보고뿐 아니라 후일 다시 볼 분석·대안·시도·검증의 보존을 포함한다.

다음에 제안할 구체 결과는 기존 사례와 파일을 사용한 **기준 본문 한 부분·선택이 갈리는 짧은 작업 장면·관련 Ticket에 남길 선택과 열린 질문**이다. Field의 입력 연결 중복처럼 둘 이상의 구조가 타당할 수 있는 장면을 골라, Main이 정답과 기준 이름을 모두 지정하지 않은 요청에서 어떤 자료를 찾고 어떤 조건을 확인해 선택하는지 보여 준다. 결과와 이유를 어디에 남길지도 같은 장면에서 연결한다. 형식을 논의하는 데 필요한 내용만 사용하며, 사례 전체 추가 조사나 또 다른 가상 프로젝트를 선행 조건으로 삼지 않는다.

이 보완에서 확인된 관계는 해당 Ticket과 Spec에 반영하고 아직 정하지 않은 파일 배치·호출·갱신 운영은 명시적으로 남긴다. 예시 하나를 완성했다는 이유로 01-02나 관련 Ticket을 완료 처리하지 않는다.
