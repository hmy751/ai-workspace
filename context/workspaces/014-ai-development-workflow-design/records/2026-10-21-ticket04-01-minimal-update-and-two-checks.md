# 04-01 work-discussion 최소 수정 반영과 두 조건 확인

2026-10-21. **사용자가 승인한 최소안을 prototype의 스킬 본문에 반영했고, 서로 다른 두 입력에서 충분성 확인과 필요한 구체화를 구별했다.** 각 입력1회, 총2회만 실행했다. 기존판 대비 우월성이나 새 Work 전체·장기 효과를 확인한 결과는 아니다.

## 승인과 적용 범위

사용자는 최소 수정안을 본 뒤 “이 최소 수정안으로 반영하고, 기존 정의가 충분한 경우랑 실제로 구체화가 필요한 경우 둘 다 제대로 판단하는지 확인”하도록 요청했다. “16개상황 확인처럼 토큰 과다 소모”는 피하도록 했다.

현재 산출물은 [prototype work-discussion 본문](prototypes/development-workflow/skills/work-discussion/SKILL.md)과 [스킬 안내](prototypes/development-workflow/skills/README.md)다. 처음 Reference에 반영했던 위치는 사용자 정정에 따라 prototype으로 옮겼고, Reference의 이번 변경은 원복했다. 함께 읽는 설명 기준도 prototype 안에 연결했다. 기존 정의·보완 후보의 대조를 구체화하고, 충분성 질문에는 충분 여부와 실제 보완을 먼저 반환하도록 했다. 겹치는 유지·변경 반환 문장을 통합하고 description을 맞췄다. 필요한 요구 발견, 사람의 선택, Spec·Ticket 연결·실행 권한·운영 책임은 유지했다. reconsider-work와 source 보존판·외부 프로젝트·전역 스킬은 변경하지 않았다.

[실제 변경분](experiments/work-discussion-minimal-2026-10-21/change.patch)과 [시험한 전체 본문](experiments/work-discussion-minimal-2026-10-21/SKILL.md)을 보존했다. 앞선 큰 보완안 전체를 채택한 것이 아니다.

## 두 번의 수행과 Main 판정

| 입력 | 실제 응답 | 판정 |
| --- | --- | --- |
| 기존 표시·동작 보존과 완료 기준이 있는 경비 합계 Ticket | “이미 실행 범위와 완료 판단을 잡을 만큼 구체적”이라고 답했다. 기존 기준을 새 보강 목록으로 만들지 않고, USD 1.005의 표시 차이를 기존 보존 검사에 연결했다. 실제 코드에서도 차이를 먼저 확인하도록 했다 | 충분성 판단과 유효한 검사 구체화를 함께 수행했다. 검사 사례를 남기는 것은 허용되는 보완이며 요구를 새로 정하지 않았다 |
| 표시 통일로 범위가 바뀌었고 최종 표시 기준은 미선택인 가상 조건 | 구분자·반올림의 선택과 추천 결과를 제시했다. 기존 합산·자릿수·정렬·강조 보존은 다시 선택하지 않았다. 선택 뒤 화면과 helper의 일치 확인을 연결했다 | 필요한 구체화를 충분하다는 말로 닫지 않았고 제안과 채택·반영을 구별했다 |

원응답: [충분한 정의](experiments/work-discussion-minimal-2026-10-21/results/run-a.md), [구체화가 필요한 정의](experiments/work-discussion-minimal-2026-10-21/results/run-b.md).

두 번째 답변의 반올림 제안은 방향 제시 수준이다. 실제 채택·구현에서는 데이터 계약에 맞는 경계값과 일반 규칙을 확정해야 한다. 이번 확인은 티켓 논의에 대한 응답이며 제품의 금액 표시 정확성을 검증한 것이 아니다.

## 확인 방식과 한계

앞선 실험의 D1·D2 입력과 공통 지침을 재사용하고 스킬만 승인된 최소안으로 바꿨다. [실행 전 계획](experiments/work-discussion-minimal-2026-10-21/protocol.md)과 [실제 지시문·입력 해시](experiments/work-discussion-minimal-2026-10-21/manifest.json)를 고정했다. 서로 이력이 없는 새 실행자2명에게 자기 입력과 본문만 제공했다. 사후 정정·기대 답·이전 응답·평가 관점은 주지 않았다. 모델·추론 설정은 Main을 상속했고, 별도 평가자를 추가하지 않고 Main이 원응답을 판정했다.

평가는 단순히 새 제품 선택을 만들지 않았는지가 아니라, 기존 내용을 불필요한 보강으로 제안했는지와 새 관찰이 실제 검사에 연결됐는지까지 보았다. 응답 분량이나 특정 제목을 성공 기준으로 삼지 않았다.

앞선 입력과 동일하게 전체 원 Spec·제품 코드·긴 작업 이력은 재현하지 않았다. 필요한 관찰을 선제공한 두 조건의 수행 확인이며, 문서를 스스로 찾아 연결하는 과정·새 작업의 전체 구체화·기존판 대비 향상·반복 안정성은 미검증이다. 지시 기반 접근 범위를 사용했고 OS 격리나 전체 접근 이력 감사를 추가하지 않았다.

최초 시험에서 입력 무변경과 시험 사본·당시 Reference 본문의 일치, 기본 frontmatter 필드와 스킬 내부 링크를 확인했다. [확인 결과](experiments/work-discussion-minimal-2026-10-21/integrity.json)에 남겼다. 제공 quick_validate는 Python의 PyYAML 미설치로 시작하지 못해 의존성 설치 없이 기본 필드·링크를 직접 확인했다. 이는 행동 확인과 별개다.

## 현재 판단과 후속

이 최소안은 사용자 승인에 따라 prototype에 반영한 현재 본문이다. 실제 Reference·Noline에 설치한 상태는 아니다. 두 조건에서는 요청한 구분을 관찰했으므로 같은 입력의 반복 실험은 추가하지 않는다. reconsider-work는 기존 본문을 유지한다. DB·인증은 이후01-01·01-02의 워크플로 논의로 유지한다. 당시에는04-01 마감 대조 전이었으며, 아래 완료 조건 대조 뒤 설계 결과를 마감했다. Workspace 전체 완료는 아니다.

후속은 기존01-01·04-03에서 호출·진행·문서 반영의 관계를 이어 보는 것이다. 실제 프로젝트 이식과 Maintain 제거 이후 책임 변경은 이번 최소 수정에 섞지 않았다.

`skill-creator`, `subagent-delegation`, `recall-document-guidance`를 적용했다. `ai-system_instruction-clarity.md: 적용`.

## 반영 위치 정정

사용자가 “reference-project 말고 context/workspaces/014-ai-development-workflow-design/records/prototypes/development-workflow 여기에 반영”하도록 정정했다. 시험 원응답·판본·당시 integrity는 과거 실행 근거로 보존한다. 현재 prototype 본문은 시험판에서 설명 기준의 상대 링크만 바뀌었고 판단 문구는 같다. Reference는 이번 본문·색인 수정분만 원복했다. 두 사례의 행동 시험은 반복하지 않았다. 시험판과 현재 본문의 차이가 설명 기준의 상대 링크뿐인지 확인했고, Reference 두 파일의 Git diff가 비어 있음을 확인했다. prototype 열람 화면을 재생성해 문서126개·코드5개, 내부 링크738개·앵커238개의 원문·연결과 누락0건을 확인했다. 기본 모듈 탐색 실패 뒤 이미 제공된 marked 경로를 지정해 생성했으며 새 패키지는 설치하지 않았다. 브라우저 렌더 실측이나 제품 검사는 수행하지 않았다.


## 완료 조건 대조와 마감

사용자가 남은 일과 완료 조건의 대조를 요청한 뒤 “워크스페이스 기록할거 하고 정리하고 커밋까지” 승인했다. **04-01은 work-discussion 최소 보완·reconsider-work 유지의 설계 결과로 완료한다.** 실제 배포나 일반적인 수행 신뢰성 확보를 완료로 합치지 않는다.

| 완료 조건 | 근거와 마감 판단 |

| 본문 보완·사용자 선택·다른 Ticket·후속 | 최소안은 사용자 채택 후 prototype에 반영했다. reconsider-work 교체의 이득은 입증되지 않아 기존 유지로 결정했다. 아래 후속 책임을 남겼다 |

공통 설명 기준의 두 사본은 색인 링크의 표시 이름 외에 같음을 확인해 `skills/shared/explanation-and-evidence-criteria.md`로 통합했다. work-discussion의 링크를 연결하고 중복 사본을 제거했다. 세 스킬의 공통 색인에는04-01의 채택 본문과04-02의 검토 초안을 구별했다. 상위04의 일괄 미수행 문구는 하위 Ticket의 상태를 읽도록 고쳤다. 동작 문구와 기존 시험 자료는 바꾸지 않아 행동 시험을 추가하지 않았다.

후속은 호출·실행 연결01-01·04-03, Maintain 제거 뒤 기록 책임02·06, 실제 이식·통합 확인06·07이다. DB·인증 사례의 구현·검토·완료 책임은01-01·01-02에서 다룬다. 이 연결은 수신 과제의 완료나 실제 인수를 뜻하지 않는다.04-02의 검토·채택은 별도 진행으로 남긴다.

마감 확인: 시험판과 현재 work-discussion 본문은 공통 기준의 상대 링크 외에 동일하다. Reference 변경은 없으며, 커밋 대상 prototype만 구성한 사본의 문서123개·내부 링크733개·앵커238개와 병행 초안을 보존한 작업 폴더의 문서125개·내부 링크738개·앵커238개를 각각 확인했다. 두 열람 화면 모두 원문·SHA가 일치하고 누락 경로·앵커는0건이다. 브라우저 실측·제품 검사는 추가하지 않았다.04-02의 미커밋 초안·기록은 이번 커밋에서 제외하고 작업 폴더에 보존한다.

Git 공백 검사는 보존한 사용자 인용·실험 요청의 공백과 저장된 patch의 문맥 줄을 지적했다. 원문 및 실험 입력 해시를 유지하기 위해 해당 보존 자료는 변경하지 않았다. 현재 운영 문서·prototype 본문의 공백 검사는 별도로 통과했다.
