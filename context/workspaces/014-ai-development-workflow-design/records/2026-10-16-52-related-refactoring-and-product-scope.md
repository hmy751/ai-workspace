# 이번 수정에 관련 구조 개선을 포함할 조건

2026-10-16. 최근 코드 기준 논의를 현재 01-02 목표에 대조한 뒤, 유지 판단에 비해 실제 수정으로 넘어가는 조건을 덜 확인했다는 Main의 평가에서 시작한 후속 비교다. 가상 사례이며 실제 중복 발견·제품 변경·실행 검증이 아니다. 사용자 응답은 상황별 검토 기준으로 보존한다.

## 질문의 배경과 비교 장면

01-02는 좋은 코드의 판단을 필요한 수정으로 연결하는 것을 맡는다. 기존 사례에서 목적에 맞는 현 구조의 유지, 공통 계약, 수명, 같은 업무 흐름, 지원 범위의 조건을 얻었다. 이번에는 현재 변경과 관련된 개선을 함께 수행할지 판단하는 장면을 구체화했다.

가정한 제품에는 PC 주문 페이지·모바일 주문 페이지·빠른 주문 모달이 있다. 세 화면 모두 현재 장바구니 전체를 주문한다는 같은 업무 흐름임이 확인됐다. 주문 요청과 orders·catalog 캐시 무효화, clearCart가 복사돼 있고 화면 이동·모달 완료 처리만 다르다. 이번 요청은 사용한 쿠폰이 목록에 남는 문제를 고치는 것이며 원인은 coupons 캐시 무효화 누락으로 확인됐다고 가정한다. 긴급 장애는 아니고 성공·실패 동작을 확인할 여유가 있다. 별도의 주문 구조 전체 리팩터링 요청은 없다.

- 비교안 A: 세 곳에 coupons 무효화를 추가하고 공통화는 후속으로 제안한다. 수정 범위는 작지만 다음 공통 변경도 여러 곳에 적용해야 한다.
- 비교안 B: 주문 요청·관련 캐시 무효화·장바구니 정리를 useCheckoutOrder 같은 단위로 묶고 화면별 완료 처리는 callback으로 남긴다. 공통 변경은 한곳에서 다루지만 세 화면의 연결과 기존 성공·실패·로딩 동작 보존도 확인해야 한다.

이 A/B는 이번 가상 리팩터링 선택지이며 앞서 선택한 개발 역할 배치 B의 새 승인이나 재선택과 혼동하지 않는다. 코드 예시는 성공 처리 설명용이며 구체 Hook API 채택이 아니다.

## 보존할 기준과 적용 범위

- 같은 업무 흐름임이 확인되고 이번 수정과 직접 관련된 개선이라면, 요청 기능을 고치면서 공통 구조도 함께 정리할 수 있다. 명시적 리팩터링 요청이 없다는 사실만으로 반드시 제안 단계에 멈출 필요는 없다는 해당 사례의 판단이다.
- 중복 횟수만으로 공통화하지 않는다. 변경 범위·비용과 기존 동작 보존을 함께 판단한다. 화면별 차이는 유지해야 한다.
- 제품의 목적·범위와 확장 필요가 구조 개선의 투자 수준에 영향을 준다. 작은 범위의 테스트·실험 제품이거나 확장이 덜 요구된다면 작은 수정으로 끝내는 선택도 가능하다. 예상 수명·재변경 가능성을 확인하는 것은 이 응답을 적용하기 위한 Main의 해석이지 사용자가 별도 기간 기준을 정한 것은 아니다.
- 작은 제품에서 정확성을 생략해도 된다는 뜻은 아니다. 이번에 달라지는 것은 공통 구조 개선의 필요와 비용 판단이다. 모든 작은 제품은 공통화하지 않는다는 규칙도 아니다.
- 이 응답은 실제 저장소 전체에 임의의 리팩터링을 수행하라는 권한으로 확대하지 않는다. 현재 대화는 개발 기준 설계이고 제품 수정은 요청하지 않았다.

최근 확보한 '목적에 맞으면 유지' 기준에 '이번 변경에 필요한 개선을 함께 수행할 수 있는 조건'을 보완한 것이다. 01-02가 완료되거나 reviewer의 전체 수정 범위가 확정된 것은 아니다. 다음 추천은 확보한 기준으로 한 사례의 유지·수정·보류와 필요한 확인을 Main이 제시해 적용 감각을 대조하는 것이다. 반복적인 추상 인터뷰를 먼저 늘릴 필요는 없다.
