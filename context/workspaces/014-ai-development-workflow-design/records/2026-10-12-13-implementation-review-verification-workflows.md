# 구현·품질 검토·실제 검증을 연결하는 워크플로 비교

> 이 문서는 당시 비교 이력이다. 이후 [기록 15](2026-10-12-15-reviewer-editing-choice-and-start.md)에서 B 방향을 선택했으며, 본문의 C 기본 추천은 현재 선택이 아니다.

2026-10-12. **미채택 설계안. 의미 있는 기능 변경의 기본 후보로 C안(구현자가 수정 책임을 유지하고 별도 검토자가 보고·재검토)을 권한다.** 작은 변경에는 A안, 계약이 분명한 품질 개선에는 B안의 검토자 직접 수정을 비교한다. 앱 실행 확인을 별도 담당자에게 맡기는 선택은 세 안과 구별해 판단한다. 역할의 효과와 운영 비용을 실제 작업에서 측정한 결과는 아니다.

사용자의 이번 요청은 다음과 같다.

> 강연 자료에 더불어서 vercel 자료도 참고로 봐줘
> 그럼 자료들이랑 기존 구성을 같이 보고 구현·품질 검토·실제 검증을 어떻게 연결할지 구체적인 워크플로 안을 비교해줘. 과거 사례는 그 안을 검토하는 데 쓰고.

이에 강연·Vercel 자료에서 후보를 만들고 현행 구성과 대조했다. 과거 사례는 후보를 시험하는 데 쓴다. [앞선 비교](2026-10-12-12-development-flow-first-comparison.md)는 작업 크기와 사람의 선택 시점에 치우쳤으므로 현재 워크플로의 중심 제안으로 삼지 않는다. 그 비교는 작업을 한 번에 어디까지 맡길지 검토할 보조 자료로 남긴다.

## 세 안의 구체적인 차이

여기서 Main은 사용자와 전체 목표를 연결하고 결과를 통합하는 책임이다. A·B에서는 Main이 구현을 직접 맡을 수 있다. 아래 역할은 비교를 위한 책임이며 새 agent 파일·고정 팀을 설치했다는 뜻이 아니다.

| 안 | 구현·검토·수정·실제 확인의 연결 | 적합한 조건 | 감수하는 비용·약점 |
| --- | --- | --- | --- |
| **A. 한 담당자가 끝까지 수행** | Main이 작업을 정의하고 구현한다. 자동 검사와 실제 사용 흐름 확인 중 결함을 고치고, 구조·요구 충족을 다시 검토해 보고한다. | 계약이 분명하고 영향이 좁은 변경. 예: 기존 오류 문구와 대응을 국소적으로 고치는 작업. | 인계 비용이 작다. 자기 설계의 전제와 검사 누락을 같은 담당자가 놓칠 수 있다. 자체 검토를 독립 검토라고 부르지 않는다. |
| **B. 별도 품질 검토자가 수정까지 수행** | 구현자가 동작하는 결과와 초기 실행 근거를 만든다. 별도 검토자는 원요구·기준·코드·증거를 대조하고, 합의된 범위 안의 품질 결함을 수정·검사한다. 구현/Main이 그 변경을 대조하고 최종 코드의 실제 흐름을 재확인한다. | 기능 구현과 구조 품질을 함께 다루는 변경. 검토자가 기존 계약을 유지하며 충분한 개선을 할 수 있는 경우. | 검토 맥락과 수정 인계가 추가된다. 검토자가 바꾼 코드는 더 이상 그 검토자의 독립 판정만으로 보증되지 않는다. 최종 재확인이 필요하다. |
| **C. 구현자가 수정하고 검토자가 재검토 — 기본 후보** | 구현자가 개발 중 검사와 실제 실행을 한다. 별도 검토자는 요구·구조·테스트·실행 근거를 읽어 보고한다. Main/구현자가 지적을 판정·수정하고 실제 흐름을 재확인한다. 검토자는 중요한 지적의 해소와 수정 영향을 다시 본다. | 기능 동작과 구조 판단이 얽혀 있고 구현자가 가진 맥락을 유지할 이점이 큰 변경. 실제 수정도 작성자와 다른 관점에서 다시 볼 필요가 있는 경우. | 쓰기 책임과 개발 맥락을 유지하며 최종 수정도 별도 검토받는다. 대신 지적을 충분히 전달하고 구현자가 다시 해석·수정하는 왕복이 생긴다. 근거가 약한 지적을 주고받기만 하면 비용이 커진다. |

C를 기본 후보로 권하는 이유는 구현자가 제품·상태·검증 맥락과 쓰기 책임을 유지하면서, 수정 결과를 별도 시각으로 다시 볼 수 있기 때문이다. 기존 Main·실행자 책임과 보고형 검토를 연결하기에도 비교적 직접적이다. 품질 지적을 사람에게 옮겨 적게 하지 않고 AI 사이에서 판단·수정·재확인하는 책임은 B와 C 모두 갖는다.

B의 고유한 예상 이점은 **문제를 조사한 검토자가 바로 고쳐 지적 전달과 코드 재탐색을 줄일 수 있다는 것**이다. 예를 들어 계약이 그대로인 중복 상태 계산이나 실제 실패를 놓치는 테스트를 충분한 근거로 고치는 경우다. 대신 쓰기 인계와 검토자 수정의 재확인 비용이 든다. C의 왕복보다 그 비용이 작을 때 B가 유리하다. 현재 자료는 어느 비용이 실제로 더 작은지 입증하지 않는다. 역할 배치의 목적은 처음 구현의 품질 책임을 늦추는 것이 아니다.

**실제 실행 확인을 별도 담당자에게 맡길지는 별도 선택이다.** 기본적으로 A/B/C 모두 구현 담당자가 앱·API 등 실제 결과를 직접 확인한다. 여러 세션·권한·공유 상태가 얽혀 있거나, 구현자의 재현만으로 중요한 반대 조건을 놓칠 우려가 크면 별도 검증자가 원요구와 실제 환경으로 확인한다. 세 안 어디에도 추가할 수 있다. 앱 환경이 없거나 관찰 수단이 부족한 문제는 담당자를 늘려도 해결되지 않는다.

## 같은 작업에서 책임이 어떻게 달라지나

**가상 요청:** “설정 화면에서 알림 수신 옵션을 바꾸고 저장할 수 있게 해줘.” Noline의 기존 사건이나 새 구현 요청이 아닌 비교용 사례다. 여기서는 사용자가 저장 버튼을 눌러 반영하고 실패하면 입력을 유지하는 제품 방향이 선택됐다고 가정한다. 먼저 B의 수정 인계를 끝까지 펼치고, C에서 달라지는 부분을 대조한다.

| 시점 | 수행 주체와 행동 | 다음으로 넘길 결과·되돌아갈 조건 |
| --- | --- | --- |
| **작업 정의·설계** | Main이 기존 제품 설정·저장 API·화면 기준·Spec/Ticket을 읽는다. 현재 값 로딩, 편집, 저장 중, 성공, 실패, 권한 없는 상태 중 실제 도달하는 경우를 고른다. 제품 선택이 열려 있으면 자동 저장과 명시적 저장 등의 차이·추천을 제시한다. 상태 소유·저장 경계·변경 영향을 설계하고 어려운 구조 선택은 구현 전에 비교한다. | 목표, 보존할 계약, 필요한 품질, 관찰할 결과, 열린 선택. 이미 유효한 합의와 위임 안의 구현 판단은 다시 승인받지 않는다. |
| **구현·개발 중 확인** | 구현자가 제품·구조 맥락과 필요한 기준을 받아 UI·저장·오류 처리를 연결한다. 기존 lint·type·관련 테스트를 사용하고 실제 화면에서 옵션 변경·저장·다시 진입을 확인한다. 실패 시 입력이 남는지도 관찰한다. | 변경판, 자동 검사 결과, 실제 실행한 상태와 못 본 상태. 구현만 마친 코드를 완성 결과로 넘기지 않는다. 앱 접근 자체가 막히면 그 공백을 드러내고 가능한 코드 검토는 계속한다. |
| **별도 품질 검토** | 검토자가 원요구·채택한 결정·필요한 Project 기준·변경 코드와 호출부·테스트·실행 근거를 직접 읽는다. 요구 충족과 구조 품질을 구별해 판정한다. 저장 순서와 실패 처리가 화면마다 흩어졌는지, 테스트가 내부 호출 모양만 반복하는지, 실행 근거가 다른 상태를 빠뜨렸는지 확인한다. | 근거 있는 지적, 유지할 선택, 추가 확인. Main의 “이 부분은 괜찮다”는 요약을 결론으로 주입하지 않으며 필요한 주변 근거에 접근할 수 있게 한다. 모든 기준 문서를 무차별로 읽히지는 않는다. |
| **품질 수정** | 검토자가 기존 계약 안에서 상태·저장 책임을 응집시키거나 누락된 실패 처리를 고친다. 관련 테스트를 수정·실행하며, assertion을 약하게 만들어 통과시키지 않는다. | 수정 diff, 지적별 처리 이유, 검사 결과와 남은 이견. 저장 방식을 자동 저장으로 바꾸거나 새 기능을 넣는 선택은 직접 품질 수정에 숨기지 않고 Main에 돌린다. 큰 구조 변경도 허용 범위와 영향 확인이 충분하지 않으면 설계 판단으로 돌린다. |
| **최종 통합·실제 재확인** | 구현/Main이 검토자의 수정과 기존 계약을 대조한다. 최종 코드로 저장·새 진입·실패 후 입력 유지처럼 수정 영향이 닿는 흐름을 다시 실행한다. 오류가 있으면 현재 수정 책임자가 고치고 관련 검사와 검토를 다시 받는다. | 이전 성공 결과를 나중 수정의 검증으로 재사용하지 않는다. 시뮬레이션 실패와 실제 네트워크·서버 실패 관찰은 구별한다. 재수정이 구조나 계약에 영향을 주면 해당 부분을 품질 검토에 다시 돌린다. |
| **결과 보고·기록** | Main이 사용자에게 무엇이 가능해졌는지, 어떤 구조 선택을 했고 왜 적절한지, 실제 확인 범위와 남은 선택을 설명한다. 채택한 결정과 현재 상태를 연결하고, 재검토할 가치가 있는 대비안·실패·검증도 보존한다. | 사람은 새로운 제품 선택, 체감 품질, 감수할 비용을 판단할 수 있다. 이미 판정 가능한 결함을 단순 지적 목록으로 떠넘기지 않는다. 질문이 오면 설명·재판단·변경 요청을 구별한다. |

**같은 작업에서 A라면** 위 책임을 Main이 모두 수행한다. 품질 점검 시 저장 결과뿐 아니라 실패 복구와 호출자 부담을 따로 보되, 독립성은 없다. **C라면** 검토자가 “실패 후 입력이 초기화된다”는 재현·관련 위치·위반한 계약과, 저장 책임이 흩어졌다는 구조 근거를 보고한다. Main/구현자가 필요한 수정과 유지할 선택을 판단하고 고친 뒤 최종 저장·실패·재진입을 다시 실행한다. 검토자는 그 지적이 해결됐는지와 변경이 만든 새 영향을 확인한다. 근거 있는 유지 판단도 허용하며, 미해결 이견을 숨기지 않는다. B와 C 모두 사람이 지적을 새 작업 지시로 다시 작성할 필요는 없다.

별도 동작 검증자를 붙였다면 최종 수정 이후 그 검증자가 새로 화면에 진입해 관련 흐름을 실행한다. 품질 검토와 병렬로 확인할 때도 코드 변경판과 테스트 상태를 맞춘다. 모든 에이전트가 같은 화면과 파일을 동시에 수정하는 운영은 하지 않는다.

실제 UI가 없는 API·배치 작업에서는 화면 대신 실제 공개 API·명령·저장 결과 등 전달하는 인터페이스를 확인한다. 새 테스트나 앱 전체 실행을 모든 문구 수정의 의무로 만들지 않는다. 변경이 영향을 주는 계약과 관찰 공백으로 확인 범위를 정한다.

## 수정·재확인·종료에서 빠지면 안 되는 연결

- **한 변경판을 대조한다.** HEAD만으로 미커밋 작업을 식별하지 못하므로 기준점과 포함한 작업 트리 변경, 검사한 상태를 함께 넘긴다. 검토 중 쓰기 담당자를 한 명으로 정하고 인계한다. 별도 담당자의 병렬 read-only 검토·실행은 같은 변경판과 분리된 테스트 상태를 확보할 때만 한다. 처음부터 새 snapshot 시스템을 만드는 요구는 아니다.
- **검토와 수정의 권한을 구별한다.** read-only 리뷰 요청이면 어떤 안에서도 수정하지 않는다. B의 직접 수정은 개발 실행을 맡긴 범위 안에서 Main이 쓰기 책임을 인계한 경우다. 검토자의 자신감만으로 제품 계약·범위·사람의 결정 권한이 넓어지지 않는다. 자동 commit·merge도 포함하지 않는다.
- **실행 결과와 기준의 충분성을 함께 본다.** 검토자는 코드뿐 아니라 테스트가 실제 실패를 검출할 수 있는지와 빠진 사용자 상태도 판단한다. 새 테스트·수정이 생기면 그 결과를 다시 얻는다. 판단 가능한 지적은 AI가 해결하고, 요구와 충돌하거나 아직 위임받지 않은 제품 선택은 근거·대안과 함께 사람에게 돌린다.
- **완료는 역할의 수가 아니라 결과로 판단한다.** 맡은 결과와 보존 계약에 대한 근거가 있고, 이를 막는 미해결이 없으며, 수정 이후 관련 확인이 유효한 상태여야 한다. 실행 불가·근거 부족이 결과 판단을 막으면 부분 완료나 미확인으로 남긴다. 사소한 새 취향을 계속 찾아 무한 재검토하지 않는다. 검토 의견이 충돌하면 원요구·제품 사실·기준·실행 증거로 쟁점을 좁혀 한 번 더 판단한다.
- **품질의 원인이 상류에 있으면 돌아간다.** 구현 후 검사 단계에서 고칠 수 없는 제품 흐름·책임 경계 문제가 나오면 설계를 재검토한다. B는 먼저 대충 만들고 마지막 검토가 모든 품질을 해결한다는 순서가 아니다.

## 후속 설계와 실제 적용 전에 남은 것

01-01은 세 안의 진행과 책임 연결을 비교했다. 01-02는 실제 코드·구조 대비에서 어떤 수정이 품질 향상인지와 B의 직접 수정 경계를, 01-03은 대상 프로젝트의 실행 경로·시나리오·관찰 한계를 더 구체화해야 한다. 두 과제의 결과가 흐름을 바꾸면 01-01도 함께 고친다. 이번 비교로 세 Ticket이 완료된 것은 아니다.

02·03에는 필요한 기록과 제품·구조 맥락을, 04에는 실제 호출·입력·결과의 연결을 넘긴다. 05에는 반복 지적·잘된 결과에서 개선 후보를 만드는 문제를, 06에는 코드·검사·가이드·도구 중 어디에 반영하고 프로젝트 간에 어떻게 전달할지의 비용을 잇는다. Vercel식 주간 수집·collector/judge나 새 전용 CLI는 채택하지 않았다.

적용 범위를 정한 뒤에는 좁은 기능 변경에서 C를 기본으로 시험하되, 계약이 같은 품질 지적을 B 방식으로 처리할 때의 차이도 비교한다. 지적 중 실제로 해결한 결함, 계약을 바꾼 수정, 빠진 실행 상태, 사람에게 다시 설명·판단을 요청한 이유, 인계·재검증 비용을 본다. 가능하면 같은 기준의 별도 사례에서 A/B/C를 비교한다. 한 번 성공한 결과만으로 항상 쓸 기본값을 고정하지 않는다. 제품의 동작 검사와 워크플로 효과 평가를 구별하고, 사람이 좋아한 결과와 특정 역할 배치의 인과 효과도 구별한다.

초안의 별도 문서 검토에서 B와 C가 수정권·별도 검증자라는 두 선택을 동시에 바꿨다는 지적을 반영했다. 수정권을 같은 조건에서 비교하고 별도 실행 확인은 별도 선택으로 정리했다. 이는 문서상 책임 연결 확인이며 실제 역할 배치의 효용 검증은 아니다.

이번에는 제공 자료와 현행 구성의 문서·선택된 실행 경로를 읽고 설계안을 작성했다. 제품 코드·스킬·하네스 변경, 앱 실행, 워크플로 실험은 수행하지 않았다.
