# 형성 맥락 논의 재점검과 본문 묶음의 구성

2026-10-20. 사용자는 주제 본문을 README보다 `index.md`로, 연결된 사례를 `index.cases.md`로 표현하는 안을 제시했다. 이어 최근 논의에 편향되지 않도록 관련 대화를 다시 읽고 충돌·유실·미반영을 점검해 종합 설명하라고 요청했다.

후속: [111](2026-10-20-111-content-policy-entry.md)에서 cases를 선택적인 본문 분할 예시로 일반화하고 공통 관리 원칙을 작성했다. [112](2026-10-20-112-formation-context-session-checkpoint.md)는 정책의 viewer 문단 제거와 세션 정리를 다룬다. 아래는 당시의 대화 재점검과 미적용 구성안이다.

**현재 권고는 주제 본문 `index.md`와 연결 사례 `index.cases.md`, 그 아래 background의 현재 맥락·형성과 변경 기록·근거를 구별하는 것이다.** 기록 책임은 처음부터 둔다. 데모 공통 관리 원칙과 선택적 읽기·변경에 따른 갱신도 구성에 포함한다. 파일 수를 줄이는 판단으로 서로 다른 책임을 다시 섞지 않는다. 이번 결과는 원문 재검토와 구성안이며 prototype 재배치 결과가 아니다.

## 확인한 원문과 점검 방식

`ai-self-check`에 따라 이전 설계를 맡지 않은 별도 auditor에게 최신 사용자 원문과 parent thread 접근점을 제공했다. auditor가 필요한 범위를 정해 최초 LLM Wiki 질문부터 최신 발화까지 직접 조회했다. Main의 원인 가설이나 예상 결론을 과제로 주지 않았다. 아래 감사 결과는 공개 대화에 관한 것이며, auditor가 prototype 파일이나 이전 실험을 새로 검증한 것은 아니다.

Main은 현재 이름 기준의 맥락·근거 파일,107의 적용 기록, 현재 상태를 함께 확인했다. 별도 explorer는 현재 viewer가 새 이름을 어떻게 처리하는지만 읽기 전용으로 확인했다. 외부 자료를 새로 조사하거나 제품·브라우저 실험을 수행하지 않았다.

## 최근 설명에서 약해졌지만 유지할 요구

다음은 모두 없어진 것으로 단정할 내용이 아니다. 일부는107의 현재 실물에 있고 최근 폴더 설명에서 덜 드러났으므로 종합안에 다시 연결한다.

- **데모 공통 관리 원칙:** 여러 본문을 다루며 이름 기준 묶음도 포함한다. 이름 기준만의 관리 안내나 Personal 전용 규칙으로 좁히지 않는다.
- **읽기·갱신 조건과 담당:** 해당 본문을 바꾸는 작업자가 관련 맥락·사례·기록의 영향을 확인한다. 파일을 가까이 두거나 링크를 검사하는 것만으로 관계 유지를 보장하지 않는다.
- **본문의 충분성:** 일상 적용에 필요한 이유·조건은 본문과 사례에서 읽을 수 있어야 한다. 모든 이유를 background로 옮기지 않는다.
- **형성 맥락의 충분성:** 의도·배경·목적을 웬만하면 남기고 싶다는 사용자 선호를 반영한다. 고정 세 제목을 채우거나 확인하지 못한 과거 의도를 만들지 않는다.
- **과거 판단의 보존:** 실제 실패, 예상 위험에 따른 미채택·유보, 조건 변화에 따른 교체, 복귀를 구별한다. 현재 설명을 고쳐도 당시 이유·조건·발화를 새 결론에 맞춰 덮어쓰지 않는다.
- **주제에 필요한 기록의 선별:** 처음부터 기록층을 둔다는 뜻은 모든 대화·편집·완료 보고를 적는다는 뜻이 아니다. 이 기준의 의미를 형성하거나 바꾼 판단과 필요한 과정을 보존한다.
- **책임과 출처의 경계:** Personal·Project·Work의 내용 소유는 유지한다. 바깥014의 작업 전체를 대상물 기록으로 복제하거나 실제 형성 논의를 예제 제품의 사건으로 소급하지 않는다.
- **외부 참고의 지위:** 외부 자료는 역할·보존·접근·갱신을 설계하는 참고다. 특정 파일명이나 폴더 구성을 외부에서 도출한 정답으로 말하지 않는다.

## 현재 제안하는 구성

아래는 제안 경로이며 실제로 옮긴 파일 목록이 아니다.

```text
noline-demo/context/
├── README.md                         구성 안내와 데모 공통 관리 원칙
├── personal/
│   ├── README.md                     개인 기준의 범위와 역할 안내
│   └── development/
│       ├── README.md                 개발 공통 관점과 주제 선택
│       └── naming-and-completion/
│           ├── index.md              현재 사용하는 이름·완료 기준
│           ├── index.cases.md        이 본문과 연결된 적용·비교 사례
│           └── background/
│               ├── context.md        형성 의도·배경·목적과 현재 이유의 관계
│               ├── records/          이 기준의 형성과 변경 기록
│               └── evidence.md       필요한 발화·관찰·출처
├── project/                          제품의 의미·계약·현재 구현
└── work/                             이번 작업의 입력·선택·진행·결과
```

`index.md`는 이 묶음의 시작 본문으로 사용한다. 문서 제목과 첫 설명에 이름·완료 기준임을 밝히고 연결 사례와 background의 읽을 조건을 안내한다. 파일 목록만 있는 색인으로 만들지 않는다. `index.cases.md`는 같은 본문에 붙는 사례라는 관계를 이름에서도 표현한다. 이 이름이 보편적으로 역할을 보장하는 것은 아니므로 실제 제목·상호 링크·화면 표시도 맞춰야 한다.

상위 README는 구성과 운영을 안내하는 역할을 유지한다. 사용자의 요청을 데모의 모든 README를 index로 바꾸는 일로 확대하지 않는다. 주제 폴더 안에 안내 전용 README를 별도로 추가할 필요도 현재 확인되지 않았다.

`records/`는 논의·정정·선택·유보를 포함하는 범위를 드러내려는 Main의 명칭 제안이다. 사용자가 제시한 `decisions/`도 가능한 이름이며, 정확한 폴더명은 확정됐다고 쓰지 않는다. 다만 기록 책임을 처음부터 구별한다는 방향을 다시 “분량이 많아지면”으로 되돌리지 않는다.

## 같은 이름 기준에서 각 자료가 실제로 담을 것

| 자료 | 코드 자체의 명료함에 관한 내용 예 |
| --- | --- |
| `index.md` | 이름·타입·책임 배치로 의미를 드러내는 현재 판단, 설명이 맡을 부분, 유지·개명·동작 수정을 가르는 조건 |
| `index.cases.md` | 같은 인증 코드에서 이름 유지와 개명의 차이, 완료 범위와 사용처, 이득·비용·가정 |
| `background/context.md` | 설명을 읽으면 사용할 수 있음과 지향할 코드 명료함을 구별하게 된 문제의식, 현재 기준의 목적과 이유, 열린 판단 |
| `background/records/`의 관련 기록 | 당시 어떤 해설이 있었고 사용자가 무엇을 정정했는지, 어떤 방향을 확인하고 무엇을 시안에 반영했는지, 남은 유보 |
| `background/evidence.md`의 관련 항목 | “근데 난 되도록 설명이 필요없는 코드가 지향되어야 할 코드라고 생각해”라는 실제 발화와 출처·당시 조건·확인 한계 |

각 문서에 같은 사건을 전부 복제하지 않는다. context는 현재 읽히는 설명을 소유하고 기록은 당시 판단의 관계를 보존하며 근거는 확인할 원자료를 제공한다. 맥락 문서를 기록의 목차만으로 만들거나, 기록마다 맥락의 전체 설명과 모든 발췌를 다시 복제하면 이 구별의 효과가 없어진다.

## 읽기와 갱신을 구성에 포함한다

| 하려는 일 | 필요한 읽기·갱신 |
| --- | --- |
| 현재 코드에 기준 적용 | 본문과 필요한 사례를 읽는다. 일반 사용에 background 전체를 필수로 만들지 않는다. |
| 기준의 의미·우선순위·조건 변경 | 관련 맥락을 읽고 필요한 기록·근거를 선택한다. 영향받는 본문·사례·현재 설명을 맞추며, 남길 판단 변화가 있으면 주제 기록에 보존한다. |
| 과거 선택의 정확한 뜻이나 복귀 판단 | 관련 기록의 당시 조건·이유와 필요한 근거를 읽는다. 실패·미채택·교체의 지위를 구별한다. |
| 같은 뜻의 표현·오탈자 수정 | 해당 내용을 고친다. 형식상 관계를 표시하려고 모든 자료의 날짜와 문장을 함께 갱신하지 않는다. |
| 새 관찰이나 상충하는 근거 | 확인한 범위와 출처를 남기고 현재 판단에 미치는 영향을 대조한다. 과거 원문을 수정하거나 최신 관찰을 자동으로 우선하지 않는다. |
| 특정 Project·Work 조건만 변경 | 해당 소유 문서를 먼저 다룬다. 개인 기준의 의미도 바뀐 것인지 별도로 판단한다. |

위 공통 원칙은 데모 context 입구에서 찾게 하고, 각 묶음에는 자신의 자료 관계와 특별한 영향 범위만 남기는 안이다. 새 workflow·스킬·자동 hook 구현은 이전에 나눈 후속 범위로 유지한다.

## 실제 상태와 이후 구현에 필요한 범위

현재 실물은107의 점 접미사 파일과 기존 사례 경로다. 주제 폴더, background 기록층, 새 파일명, 데모 공통 관리 원칙으로의 이관은 아직 적용하지 않았다.107의 복사본 변경 실험은 기존 시범 묶음에 관한 결과이며 새 구성이나 장기 유지 효과의 검증은 아니다.

viewer의 읽기 전용 확인에서는 `index.md`·`index.cases.md` 모두 `.md` 문서로 수집된다. 폴더를 열면 README/index를 자동 선택하거나 우선 정렬하는 처리는 없으며 링크는 정확한 파일 경로를 사용한다. 실제 이동 시에는 관련 본문·진입점의 링크, viewer build의 고정 문서 경로·표시명, check의 필수 관계 경로, 생성된 viewer.html을 함께 맞춰야 한다. 이번에는 이 코드를 수정·빌드·실행하지 않았다.

이 점검 결과와 현재 진입 안내만 기록했다. 변경한 안내·기록의 로컬 링크327개에서 누락 경로가 없었고 `git diff --check`를 통과했다. 논의 전 snapshot과 대조한 prototype65개 파일의 내용은 모두 같았다. 제품·prototype·source·전역 지침 변경과 추가 커밋은 없다.
