# 04-03 네 구체안의 독립 개선 리뷰와 Main 반영

2026-10-26. Main이 항목별 초안을 작성하고, 각 초안을 부모 대화 전체를 받지 않은 별도 읽기 전용 리뷰어에게 제공했다. 이 기록은 리뷰를 사용자 합의나 수행 효과로 바꾸지 않는다. 실행 스킬·설정·source는 수정하지 않았다.

## 진행 방식과 입력

사용자 요청의 핵심 원문을 보존한다.

> 다만 니가 먼저 구체화 하고 그걸 독립 리뷰 개선리뷰를 돌리는거지 같은 자료에 대해 이 결과를 보고 더 개선할 포인트를 찾아내라 라는식으로 그냥 적당히 괜찮다 말고 개선을 끌어올리는 리뷰 돌리고 그 다음 결과를 종합해서 나한테 설명하는거지

> 근데 4가지를 나눳으니 대신 초안을 각 하나 당 하고 종합하는건? 이전에 어떻게 햇는지 참고해볼래? 그러니까 검토자 담당자 구체화한 작업에서 일너식으롷 ㅐㅆ엇거든

이후 사용자는 구체화 전에 correction-scope를 리마인드했고 “그래 시작해보자”라고 지시했다. Main은 최근 파일 포장 논의에 범위를 좁히지 않고 기존 체계·새 workflow·원래 연결 목적을 함께 구체화한다. 유효한 합의는 유지하고, 바뀐 판단은 관련 항목의 행동·입력·현재 의미에 함께 반영한다.

앞선 [구현6](2026-10-23-implementation-completion-and-handoff-proposal.md), [검토7~12](2026-10-23-review-workflow-7-12-improvement-reviews.md), [실행/기록13~15](2026-10-23-runtime-integration-and-records-13-15-improvement-reviews.md)의 의미 있는 단위별 초안·개선 리뷰·종합 방식을 참고했다. 이번에는 네 항목 각각의 초안이 준비된 순서대로 독립 리뷰에 넘겼고, 다른 항목 작성과 리뷰를 겹쳐 진행했다. 네 항목을 각각 최종 확정하거나 사용자 승인을 네 번 요구하는 절차는 아니다.

각 리뷰어에게 해당 초안, 사용자 원문 발췌, 전체 네 항목의 범위, Spec·04-03·잠정 합의, 실제 prototype의 지침/내용, 기존 Noline/Reference 스킬, 고정 외부 원문 접근점을 제공했다. Main의 프레임·범위도 재판단할 수 있게 했고 다른 리뷰 결과·예상 결론·발견 수는 주지 않았다. 각 대상 초안은 그 리뷰의 최종 반환까지 수정하지 않았다. 리뷰어는 필요한 근거 범위를 직접 선택했고 Main은 반환을 대조해 실제 설계안을 수정했다.

실제 내부 작업 이름은 `context01_improvement`, `context02_improvement`, `context03_improvement`, `context04_improvement`다. 새 컨텍스트로 호출했고 모델·추론 수준은 별도 override하지 않았다. 이전 리뷰의 모델 설정을 이번 실행 설정으로 기록하지 않는다. 읽기 전용 역할 지시는 도구 권한을 기계적으로 제한했다는 뜻이 아니다.

## 항목1 — 중심 복원과 요청별 진입

대상: [시작·재개안](2026-10-26-context-01-start-resume-proposal.md).

초안은 “목표·보존 조건·현재 선택·확인 상한·남은 행동·실제 산출물을 읽는다”, “현재 선택이 여전히 맞는지 … 판단한다”고 했다. 리뷰어는 읽은 내용보다 **그 근거에서 첫 행동의 우선순위를 어떻게 복원하는지**를 구체화할 것을 제안했다.

직접 근거는 [보존 대화](../source/noline-evaluation/corpus/01a0f772-73ab-7823-b282-bddb19124b7e/messages.jsonl) `source_line:69,76`이다. Main도 두 메시지를 직접 확인했다. 담당자는 배경·잠정 상태·코드·검사 한계를 요약하고 두 버그의 기대 동작을 다음 중심으로 골랐다. 사용자는 “지금 구조랑 배경을 더 파악해봐 마지막 문제 2가지는 아직 그렇게 중요한건 아니고”라고 정정했다.

**채택:** 첫 행동을 현재 요청·선택 이유와 대조하고 중심/부수 발견을 구별하도록 바꿨다. 명확한 로그인 가정뿐 아니라 이 실제 재개 사례를 후속 판별 장면에 추가했다. 원자료 부족이나 기록 시점이 단독 원인이라고 진단하지 않는다.

둘째 제안은 일반 Work 재개·한정 질문·Work 없는 시작을 구별하는 것이다. 기존 read는 필요한 Project 질문에서 시작하고 Workspace가 필요할 때 내려가며, development도 요청된 단계에서 참여한다. **채택:** 초입에 세 시작 범위를 넣었다. 활성 Work 선택을 전체 인수 의무로 확대하지 않는다. 이 판단은 항목2의 한정 위임과 항목4의 불필요한 생성 방지에 연결했다.

## 항목2 — 실제 추가 선택·같은 담당자의 반영·반환 유효성

대상: [역할 수행안](2026-10-26-context-02-role-execution-proposal.md).

초안은 “요구가 모호하면 관련 Ticket·Spec·원문을 추가 확인”하며 가상 사례에서 필요한 세 문서를 처음부터 지정했다. 리뷰어는 요구가 명확해도 실제 사용처 차이에서 새 질문이 생기는 것을 보여 주자고 했다.

**채택:** 새 소비자의 대기 요구에서 ‘공통으로 무엇을 보장할 것인가’라는 질문을 만들고, 처음 목록 밖의 [공통 제공·사용처 선택](prototypes/development-workflow/noline-demo/context/personal/development/shared-boundaries/INDEX.md)을 주제 입구에서 추가 선택하는 장면을 넣었다. Main이 해당 본문을 직접 대조했다. 반환은 추가 파일 목록보다 선택이 달라진 이유를 남긴다.

초안의 “미확인·관련 문서 반영 필요” 반환과 뒤쪽의 “함께 배정됐다면”은 구현자가 보고하고 Main이 다시 조사하는 흐름을 기본처럼 보이게 할 수 있었다. **채택하되 조건부 배치:** Main이 초기 배정에서 구현과 함께 바뀔 현재 사실 설명·관련 입구까지 맡길지 정한다. 포함하면 같은 담당자가 항목3의 반영을 이어 한다. 작은 변경은 Main 직접 처리도 유지하고 제품 약속·Personal 채택 권한을 자동 확대하지 않는다.

리뷰어는 [execution](prototypes/development-workflow/skills/development/references/execution.md)의 공유 상태 대조와 [verification](prototypes/development-workflow/skills/development/references/verification/INDEX.md)의 최종 대상 비교를 근거로 반환의 유효성을 보완했다. **채택:** 중요한 반환/수용 시 판단을 가른 대상·요구·계약의 변화를 대조하고 현재판을 못 봤다면 해당 판본·조건의 의견으로 한정한다. 새 해시 체계·감시 장치·전체 재검토는 도입하지 않는다.

## 항목3 — 중단 후 남은 연결·약속의 지위·수행 방법의 유지

대상: [변화·기록안](2026-10-26-context-03-change-records-proposal.md).

초안은 “영향받는 작업·소비자 접근점을 반환한다”, “Work를 실제로 갱신할 담당은 Main이 연결한다”고 했다. 리뷰어는 문서 반영 후 Main 연결 전에 끊겼을 때 남은 일을 복원하는 경로가 약하다고 지적했다.

**채택:** 중요한 변화에는 기존 Ticket/state에 달라진 선택·이미 반영한 곳·남은 수행/확인·다음 행동을 남기고 결과가 돌아오면 실제 상태로 갱신한다. 별도 전달 장부는 만들지 않는다. 항목3을 일렬 순서의 마지막 기록 단계가 아니라 네 장면에서 의미 있는 변화마다 적용하는 책임으로 통합했다. 항목1·4의 재개도 이 남은 연결을 사용한다.

“이미 채택된 선택…반영”과 “새 약속과 기존 코드…어긋나는 부분을 Main이 후속에 연결”한다는 초안에 대해, 채택·적용 조건·실제 지원을 분리하는 예시가 필요하다고 했다. Main은 [인증 계약](prototypes/development-workflow/noline-demo/context/project/guidance/authentication-and-session/INDEX.md)의 소비자별 대기와 [현재 구현](prototypes/development-workflow/noline-demo/context/project/current/authentication-flow/INDEX.md)의 지원·확인 범위를 직접 대조했다.

**채택:** 기존 계약 안의 소비자별 대기라면 계약 본문을 유지하고 Work 선택·현재 구현·실제 확인을 시점별로 갱신하는 표를 추가했다. 새 약속이 즉시 유효하면 미충족을 남기고 향후 적용이면 그 조건과 현재 약속을 구별한다. 항목1의 읽기, 항목2의 검증 입력, 항목4의 완료 의미에도 이어 붙였다.

초안의 변화 표에는 스킬·공통 참조의 허용된 유지가 빠져 있었다. 기존 development의 Owner 표는 반복 절차·발동 조건·책임을 해당 스킬이 관리한다고 이미 정한다. **채택:** 허용된 절차 변경은 해당 정본 담당이 반영하고 Main이 호출자·진행 중 작업을 연결한다. 모든 수정을05의 새로운 경험 후보로 돌리지 않으며 context-update에 실행 지침 수정권을 넣지도 않는다.

## 항목4 — 기존 Work 전환·늦은 반환 귀속·같은 작업의 재개

대상: [완료·연속안](2026-10-26-context-04-completion-continuation-proposal.md).

초안은 “둘째 작업을 만들 때” 아래 생성·전환을 함께 두고 전환 요청에서 기본 선택과 현재 대화 대상을 함께 맞추도록 했다. 리뷰어는 생성 없이 기존 Work로 이동하는 경로와 runtime의 실제 적용 시점을 구체화하자고 했다. Main은 [기존 생성/전환 계약](../source/ai-workspace-baseline/reference-project/context/work/workspaces/CREATE-AND-TRANSITION.md)의 ‘현재 turn은 predecessor, 다음 prompt는 successor’와 실패 시 기존 binding 보존을 직접 대조했다.

**채택:** 생성과 기존/새 Work 전환을 별도 절로 나누고, 먼저 수동/설치 runtime을 구별한다. 요청 대상·다음 기본 선택·host 적용 시점을 각각 처리한다. 수동 demo의 명시적인 지속 전환에 한해 현재 대상과 다음 기본값을 함께 맞추는 안으로 한정했다. 설치된 대상에 수동 행동을 먼저 강제하지 않는다. 항목1도 명시 대상 선택과 지속 전환을 구별하도록 맞췄다.

초안의 “현재 Work의 넘길 상태와 새 Work의 준비”에는 진행 중 담당자의 늦은 반환 귀속이 충분히 드러나지 않았다. 기존 execution의 배정·판본과 생성 계약의 pending/late 의미를 참고해 **채택:** 기존 배정은 원래 Work·판본·권한을 유지하고 새 Work에 필요한 결과만 Main이 선택한다. 재배정이면 새 목표·권한을 직접 전달한다. 항목2의 반환에도 같은 관계를 반영했다.

Lauren [pause 원문](../source/workflow-references/pstack/repository/skills/poteto-mode/playbooks/pause-safely.md)의 모든 중첩 담당자 취소·WIP commit은 차용하지 않는다. 사용자가 요청한 전환에 필요한 결과만 확인하며 일괄 취소·새 commit·관련 없는 pending 대기는 요구하지 않는다.

셋째 제안은 새 Work 사례에 비해 약했던 같은 Work 재개를 구체화하는 것이다. **채택:**001의 메모리 예제 확인 뒤 표현 보완으로 재개하는 장면을 추가했다. 현재 대상의 관련 차이를 보고 유효한 기존 근거를 활용하며, 현재 완료 주장에 영향을 주는 결함이면 해당 상태를 다시 열되 당시 실행 기록은 보존한다. 새 마감 보고서·모든 산출물의 해시는 요구하지 않는다.

## 네 항목을 함께 맞춘 결과

각 리뷰를 해당 문서의 경고문으로만 추가하지 않았다. 중심 과제 복원은1·3·4, 질문별 선택과 문서 배정은2·3, 채택/적용/지원 구별은1·2·3·4, 전환 후 배정 귀속은1·2·4에 연결했다. 변경 결과를 뒤 단계의 최종 종합까지 방치하지 않고 관련 초안을 함께 고쳤다. 전체 판단과 남은 사용자 논의는 [통합안](2026-10-26-context-integrated-proposal.md)에서 이어간다.

## 확인의 상한

리뷰는 원자료와 설계 초안의 독립 대조다. 역할이 실제 개발 전체를 수행하거나 중단 뒤 재개·생성/활성화·교체를 성공했다는 시험은 아니다. 개선의 기대 이득과 새 비용은 후속 대표 수행에서 확인한다. 파일 수·링크 통과·리뷰어 동의만으로 효과나 사용자 수락을 선언하지 않는다.
