## 범위와 적용 방식

추가 관점을 이후 코드에만 적용하면 앞선 사례의 검토 범위가 다르게 남는다. 앞서 실제로 읽은 Dialog·Field·폼 연결·무한 스크롤과 관찰 Hook·fetcher를 다시 확인했다. 입력 교체의 맥락에서 Input·Select·MultiSelect.Trigger의 같은 prop도 함께 대조했다. 외부 원자료는 `/Users/hammyeong-yeon/Desktop/20_lab/template`이며 수정하지 않았다.

기존 목적·책임·합성 판단은 유지하고, 이름이 전달하는 의미·타입과 실제 사용·처리 순서의 읽기 부담에 관한 새 관찰만 추가한다. 명명 후보를 사용자 선호나 의무 규칙으로 올리지 않는다. 구조·동작 문제가 드러나면 스타일 변경과 구별한다.

## 확인 결과

| 대상 | 코드에서 확인한 사실 | 보완 판단 |
| --- | --- | --- |
| Dialog | controlledOpen·uncontrolledOpen·isControlled로 제어 방식이 구별된다. Confirm·Cancel은 callback과 onClick을 모두 받고 callback → 닫기 → onClick 순서로 실행한다. | 제어 상태 이름은 현재 역할을 설명한다. 두 callback의 용도·순서는 호출부에서 구현을 더 읽어야 하는 계약 부담 후보다. 이미 논의한 Confirm 제거 방향은 유지하며 새 API 설계를 다시 시작하지 않는다. |
| Field·폼 조합 | Title·Label·Description·Message·ElementsBox의 부품과 입력·규칙·문구 연결이 사용 예시에 드러난다. Message는 항상 error 색상을 쓴다. | 합성 구조는 유지할 근거가 있다. Message를 오류 전용 이름으로 표현할지는 의도에 따라 달라지는 명명 후보다. JSX가 길다는 이유로 RHF 일체형 컴포넌트로 바꾸지 않는다. |
| Input·Select·MultiSelect | Input·Select의 isError는 string, MultiSelect.Trigger의 isError는 boolean이다. Input·Select는 그 문자열을 직접 출력하지 않고 스타일 조건으로 사용하며 문구는 Field.Message가 출력한다. | 같은 이름을 통해 예상할 입력 의미가 달라지는 구체적 API 일관성 검토 지점이다. 상태만 받을지, 오류 값을 받을지 계약을 정한 뒤 이름·타입을 맞추는 안을 비교할 수 있다. is 접두사 금지 같은 스타일 규칙이나 단순 이름 교체로 결론내리지 않는다. |
| InfiniteScrollContainer·관찰 Hook | hasNextPage·isFetchingNextPage·fetchNextPage는 다음 페이지 역할을 드러낸다. 초기 로딩·오류·빈 목록을 조기 반환하고 목록·하단 표시를 이어 그린다. | 단계별 이름과 분기는 읽는 흐름에 도움이 된다. children(items)의 items는 펼친 전체 배열이며 단일 항목이 아니다. 타입·실제 사용이 이를 보여 주므로 renderItem으로 바꾸는 식의 불일치 개선은 하지 않는다. 이미 확인한 오류 표시·중복 요청 문제는 동작 문제로 별도 유지한다. |
| fetcher | handleError는 모든 분기에서 throw한다. 호출부도 throw handleError(error)로 적혀 있다. | 오류를 반환하는 함수인지 직접 던지는 함수인지 호출부와 이름만으로 바로 알기 어렵다. 오류 변환 후 반환과 내부에서 던지기 중 계약을 분명히 표현할 후보다. async handleResponse의 오류 경로 등 동작 분석과 구별하며 이번에 수정하지 않았다. |

위 판단은 Main의 보완 검토다. 확실한 코드 관찰과 변경 후보를 구별했고, 현재 구조를 유지하는 결과도 포함한다. 이번 검토로 코드 스타일 전반이나 모든 기존 파일의 품질 검사가 완료됐다고 하지 않는다.

## 다음 논의와 기존 기록의 관계

가장 구체적인 새 논의 후보는 isError의 입력 의미·타입과 호출부 표현이다. 실제 값과 문구 표시 책임을 놓고 비교한 뒤 유지·변경 이유를 남길 수 있다. 다른 명명 후보까지 한 번에 확정하도록 사용자에게 요구하지 않는다.

후속 사용자 요청:

> 그래 그럼 기록할거 하고 다음뭘 허면 좋을까?

기록할 핵심은 추가 관점을 앞선 관련 범위에도 보완 적용하고, 기존 판단을 유지할 부분과 새로 논의할 부분을 구별한다는 것이다. isError·callback·handleError의 관찰은 변경 후보이며 사용자가 특정 이름·타입 변경을 채택한 것은 아니다.

Main은 다음으로 isError 한 사례에서 현재처럼 오류 문자열을 넘기는 방식과 boolean 상태를 넘기는 방식을 실제 호출부로 짧게 비교하도록 추천한다. 스타일을 바꾸는 입력과 문구를 표시하는 입력의 역할, 이름·타입이 기대하게 하는 의미, 사용처 편의를 함께 본다. 이 비교로 얻은 조건을 정리한 뒤 계획 42의 다른 코드 영역으로 이어가며 Field 전체 API를 다시 설계하지 않는다. 이는 당시 다음 순서 제안이었다. 이후 아래 사용자 판단으로 비교를 정리했다.

## isError 비교에 대한 사용자 판단

> 음 여기서 불리언이 더 명확하긴 한데  메시지 자체가 오류룰 발생시킬 우려는 없어서 괜찮아 보여 이렇게 했어 음 뭐 크게 크리티컬해보이지는 않네

사용자는 boolean이 더 명확하다는 점은 인정하면서, 현재 맥락에서는 메시지 문자열을 전달하는 방식도 괜찮고 중요한 수정 사안은 아니라고 판단했다. 따라서 이 사례는 현재 방식을 수용할 수 있는 것으로 정리하고 boolean 변경을 필수 수정으로 올리지 않는다. 실제 문자열 처리 전체가 모든 상황에서 안전하다고 검증한 것은 아니다.

이 사례에서 남길 판단은 **더 명확한 표현을 제안할 수 있다는 것과 현재 코드를 반드시 고쳐야 한다는 것은 구별한다**는 것이다. 오류 가능성과 실제 사용 맥락을 함께 봤다는 근거로 보존하며, 모든 boolean 이름에 문자열을 허용하거나 명명 일관성을 무시하는 일반 규칙으로 확대하지 않는다. 코드 변경·새 스타일 규칙 채택은 없다.

isError의 추가 API 설계는 여기서 마치고, Main의 다음 추천은 계획 42의 fetcher 공통 요청 계약이다. 이미 읽은 코드에서 요청·응답·오류·타임아웃을 누가 맡고 호출자가 무엇을 기대할 수 있는지 보는 흐름으로 이어간다.
