# 04-02 — 보고서 외 장면 선정과 검증 가능 범위

## 현재 판단

**본문 비교의 우선 후보는 인증 interceptor 코드 따라읽기, 자연어 호출 확인의 보조 후보는 network.ts 설명이다.** 두 사건 모두 첫 답 전에 briefing 적용 선언이 있으므로 ‘당시 늦게 발동해 실패했다’는 사례로 쓰지 않는다. 이번 조사는 장면 선정이며 테스트 실행·새 입력 묶음 구성·스킬 수정·별도 행동 지침 추가는 하지 않았다. 복구 스킬 유지와 04-02 미완료는 그대로다.

사용자는 보고서 외 source에서 적용 시점과 본문 효과를 구별할 장면을 실제 대화 근거로 고르되 테스트는 시작하지 말라고 했다. 조사 모델은 사용자 지시에 따라 GPT-6-sol medium이었다. 두 조사자의 반환을 Main이 아래 메시지 원문과 대조해 인용·순서·첫 답의 실제 내용을 확인했다. 조사자의 초기 인증·일정 우선 추천은 그대로 채택하지 않았다. 사용자 스스로 역할·도식을 미리 요구한 정도, 이미 설명된 내용, 당시 코드 확보 여부를 대조한 뒤 후보를 좁혔다.

## 후속 정정 — 기존 source에는 시점 문제의 근거가 있다

사용자는 두 후보를 수용하면서 “늦게 발동한 장면이 없다고? 그럼 기존 soruce에는 있어?”라고 확인했다. 앞선 선정은 설명 요청 이후 첫 답까지의 선택·선언을 주로 확인했다. **그보다 앞선 작업 결과 전달에서 설명·검토가 충분했어야 한다는 원래 문제를 이 조사로 부정할 수 없다.** ‘선정한 두 사건에서 늦은 호출을 입증하지 못했다’와 ‘기존 source에 시점 문제의 근거가 없다’를 구별한다.

- [Noline 인터뷰](../source/noline-evaluation/reviews/interview-20261012.md)의 보고서 장면에서 사용자는 “내가 한 번 더 말해야 괜찮아진다는 게 아쉬운 거지 처음부터 그 정도로 검토하고 설명해줬으면 좋겠어”라고 말했다. Ticket03 회고에도 “무엇을 고치고 뭐 스스로 판단해 구현도 다했는데 내가 이해가 안가서 저걸 물어본것 도 있거든”, “묘하게 내가 한 번 더 물어봐야 괜찮아지는 경우가 있더라고”가 있다. 이는 실제 회고 근거이며 특정 스킬 호출 지연을 단독 원인으로 입증한 말은 아니다.
- Main이 Ticket03 원문 01a08ff3…2560–2819를 확인했다.2560은 변경 목록·검사 통과 보고,2632는 “근데 회귀 테스트 하고 코드르 바꾸면 테스트도 바뀌어 있어야 하는거 아닌가?”,2638은 외부 동작 보존과 같은 테스트 통과의 의미를 처음 상세히 설명했다.2645 이후는 개선 폭·React 구현 품질에 대한 정정이므로 설명 시점 문제와 구현 충분성 문제를 함께 구별해야 한다. 이 사건은 첫 결과 전달 이전의 설명 책임을 재검토할 추가 근거이며 새 시험 후보로 확정한 것은 아니다.
- [원래 TripProof 회고의 종합](../source/supplement/research-original/05-tripproof-harness-retro/original/insight-memo.md)은 “완료 주장은 사용자가 심문하는 순간에야 검증됐고(5), 새 개념은 부채가 쌓인 뒤에야 설명됐다(10)”고 분석했다. 이는 과거 장면을 종합한 분석 문장이다. 현재 briefing이 설치된 뒤 늦게 불린 직접 로그와 같지 않다.
- 같은 연구의 [반대 검토 P8](../source/supplement/research-original/05-tripproof-harness-retro/original/judgment/r2-adversarial-verdicts.md)은 “설명 계약이 수동 호출형이라 기본 동작이 바뀌지 않았다”는 인과를 정정했다. 상시 설명 기준이 있었고 수동 호출 뒤에도 마찰이 남았다는 반대 증거가 있다. 따라서 사후 보완이라는 현상에서 ‘호출만 앞당기면 해결’로 건너뛰지 않는다.
- [후속 인지부채 연구](../source/research-basis/09-tripproof-cognitive-debt/04-integrated-solution-candidates.md)는 사용자 요청형의 한계로 “사용자가 간극을 감지하지 못하면 호출되지 않는다”를 적고, 완료·범위 변경·인계에서 호출하는 별도 후보 C를 검토했다. 이 대안은 연구 당시 미구현·열린 설계였으며 이번에 채택한 지침이 아니다.

현재 해석: 두 선정 장면은 본문/자연어 선택을 검토할 후보로 유지한다. 예방 시점의 검증을 대신하지 않는다. 기존 source의 첫 결과 보고·새 개념 도입 전후는 별도 시점 후보로 다시 볼 근거가 있으며, 실제 책임 누락과 원인·개입 효과는 아직 구별해서 판단한다. 이번 후속에서는 테스트·스킬 수정·새 지침 추가를 하지 않았다.

## 1. 우선 후보 — 붙여넣은 인증 interceptor 코드를 이해하려는 첫 질문

원자료: [보존 대화](../source/noline-evaluation/corpus/01a0c6c9-a603-77a2-8abe-50fc7e0814b0/messages.jsonl). 아래 번호는 JSONL 물리행이 아니라 source_line 값이다.

선행 9에서 사용자는 `??=` 문법을 물었고 13에서 그 한 줄 설명을 받았다. 20에서는 `AuthRequest`, `refreshes`, 세션 확인·갱신·거부와 요청·응답 interceptor 구현을 붙였다. 메시지의 질문 원문은 다음과 같다. 전체 코드와 문법 질문은 중앙 원문에 보존돼 있다.

> 여기 동작좀 설명해줄래? 코드 동작이 어려우서

이때 스킬명·도식·역할 우선·코드 블록별 설명 요구는 없다. 다만 바로 앞 문법 질문과 붙인 코드 자체가 코드 읽기를 돕는 설명이 필요하다는 근거다. 뒤의 교정을 이 요청에 소급해서 추가하지 않는다.

AI 31의 적용 선언:

> `work-artifact-briefing` 기준으로 실제 코드와 연결 지점을 짧게 확인하겠습니다. 붙여주신 코드만으로 읽히는 흐름과 저장소에서 확인한 동작을 구분해서 설명할게요.

첫 답 48의 첫 문장:

> 이 코드는 **Axios 요청에 현재 세션의 access token을 붙이고, 필요하면 refresh token으로 갱신한 뒤 한 번 재시도하는 장치**입니다.

48 전체는 요청 전·응답 뒤·renewSession의 세 구간으로 실행을 설명하고, 세션 교체 시 결과 차단과 갱신 Promise 공유, 인증 거부와 통신 장애의 구별을 담았다. 전체 역할과 흐름이 없는 답은 아니다. 그러나 사용자가 붙인 구현의 블록을 함께 놓고 읽는 설명은 제공하지 않았다.

첫 후속 사용자 55:

> 코드랑 같이 자세히 설명해야지 맥락만 알려주는게 아니라

**추천 입력 경계:** 원문 9·13·20을 순서대로 제공하고 20에서 끝낸다. 24·31의 답변 계획, 48의 완성 답, 55의 교정 및 66의 보완 답은 입력에서 제외한다. 이후 반응은 평가 측 자료로만 둔다. 이는 실제 질문을 다시 쓰거나 의도한 답을 알려주는 구성과 다르다.

**본문에서 판별할 차이:** 같은 시점·같은 원문에서 기존판과 통합 후보를 적용해, 사용자가 붙인 실제 코드를 읽을 수 있게 연결하는지 본다. 통합 후보의 ‘실제 코드가 필요한 설명에는 관련 코드와 그 의미를 함께 둔다’는 문구가 이 장면에 직접 대응한다. 기존판에도 source·책임·대표 흐름·값과 조건이 있으므로 새 요구가 전혀 없던 것을 만들었다고 평가하지 않는다. 코드 블록 개수·답 길이가 아니라 실제 질문에 답하는 설명의 연결을 본다. 문서 결과의 원래 질문 연결·진행별 종료라는 후보의 다른 변경 효과까지 이 장면으로 판정할 수는 없다.

**자료의 충분성과 한계:** 핵심 함수 구현은 입력 20 안에 보존돼 있어 코드 내부 설명의 비교는 가능하다. Auth Store와 transport의 내부 보장, 실제 사용처·테스트 결과까지 평가하려면 당시 코드 판본이 더 필요하다. 원문 답 48의 파일 링크를 당시 구현의 보존물로 취급하지 않는다. 범위를 붙여넣은 코드로 제한하면 원래 저장소 조사 전체를 재현한 시험은 아니라는 점을 표시해야 한다. Main은 meta.json이 가리킨 원 rollout의 현재 부재도 확인했다. 공개 메시지의 선언으로 실제 SKILL.md 읽기를 입증할 수 없다.

## 2. 보조 후보 — network.ts의 자연어 흐름 질문

원자료: [보존 대화](../source/noline-evaluation/corpus/01a0ad3d-d8d0-7f33-a3fa-c9eaf01d3f30/messages.jsonl).

직전 1202는 다른 다섯 파일의 정리 결과였다. 사용자 1209는 다음처럼 별도 파일의 흐름을 물었다.

> apps/client/src/shared/store/network.ts
> 
> 이 코드 설명좀 해줘 이해가 안돼 흐름이

질문에는 파일 경로만 있고 코드 본문이나 비텍스트 첨부가 없다. AI 1212:

> `work-artifact-briefing` 스킬을 적용해 코드를 읽고, 앱 시작부터 상태 변경·화면 반영까지 실제 호출 순서로 설명하겠습니다.

첫 답 1239의 첫 문장:

> 이 파일은 **네트워크 연결을 관측해 상태를 저장하고, 화면이나 동기화 코드가 그 상태를 읽게 하는 코드**입니다.

1239는 저장 상태와 NetworkSession, init·관측·refresh·늦은 결과 방지·소비자·cleanup을 코드와 도식으로 설명했다. 첫 반응 1246:

> 여기서 세션은 앱 실행되고 네트워크 감지하는 단위인거네 물론 리프레시나 앱이 꺼지면 보통 끝날거고 새로고침같이

AI 1251의 정정:

> 다만 **`refresh()`는 session을 끝내거나 새로 만들지 않습니다.** 기존 감지를 유지하면서 현재 연결 상태를 한 번 더 확인하는 요청만 추가합니다.

**선정 이유:** 도식이나 역할을 먼저 지시하지 않은 자연어 코드 흐름 질문에 실제로 briefing을 선택한 사례다. 사용자 반응에는 session 단위의 이해와 refresh 수명 혼동이 함께 있어, 전체 성공·전체 실패 어느 쪽으로도 단순화하지 않는다. 첫 답도 역할·코드·도식·값·조건을 이미 포함했다.

**시점에 관해 확인되는 것:** 이 질문에서 스킬 선택은 첫 답 전에 나타났다. 따라서 조기 호출이 필요한 실패 예보다 ‘자연어 요청에서도 제때 선택할 수 있었는가’를 확인하는 비교 사례다. 같은 대화 920에서 다른 변경에 스킬을 직접 호출한 이력도 있다. 이를 숨기거나 이력을 지워 순수한 최초 자동 선택이라고 부르지 않는다. 실제 본문 읽기·조항 수행 시점은 공개 메시지로 확인되지 않는다. Main은 meta.json이 가리킨 원 rollout의 현재 부재도 확인했다.

**추천 입력 경계와 공백:** 사용한다면 1209에서 끊고, 원래 선행 대화와 당시 network.ts·호출부·소비자 코드를 확보해야 한다. 1239의 설명용 코드 발췌로 입력 코드를 대신하면 기존 답이 새 입력에 섞인다. 현재는 설명 방식과 사건 순서를 확인한 후보이며 실행 준비가 끝난 사례가 아니다. 1246·1251은 평가에만 쓴다.

## 시점과 본문을 다시 섞지 않기

- 이번에 확인한 우선 두 사건에는 모두 첫 답 전 적용 선언이 있다. **‘늦게 발동한 원인’은 이번 조사로 입증되지 않았다.** 적합한 반례가 없다는 이유로 강제로 늦게 읽게 하는 조건을 만들어 당시 실패 재현이라고 부르지 않는다.
- 자연어 요청에서 기존판을 스스로 선택하는지 보는 것과, 기존판을 조사 시작부터 읽게 하는 것의 차이는 실제 읽기 기록으로 확인해야 한다. 둘 다 처음부터 읽었다면 시점 대비가 성립하지 않은 것이다.
- 본문 비교는 동일 원문·동일 자료·동일 적용 시점에서 기존판/통합 후보만 바꾸는 비교다. 별도 보고 의무·새 설명 요구·후속 교정을 추가하지 않는다.

- 여기의 선정 이유·후속 교정·평가 질문을 향후 응답 생성자의 입력에 넣지 않는다. 이번 조사자는 원문 선정자였고 블라인드 응답 시험자가 아니었다.
