# 04-02 — 같은 세 장면의 기존판·수정안 응답 비교

> 2026-10-21 후속 정정: 이 비교는 이미 사용자 교정이 들어간 후속 요청 대응이다. 특히 access 평가자가 사용자 의도 근거 없이 반환 형태 복원을 충족 기준으로 삼았으므로 아래 상대평가를 실제 문제 해결·사용자 이해의 판정으로 쓰지 않는다. 최초 응답과 평가 원문은 보존한다. [접근법 재검토](2026-10-21-ticket04-02-approach-and-evaluation-reset.md)

**이번 비교에서는 수정안의 우세를 확인하지 못했다.** 일정 작성 브리핑과 access 질문은 두 익명 평가 모두 실질 동등이었다. Promise 설명 복구는 한 평가자가 수정안, 다른 평가자가 기존판을 근소하게 선호했다. 기존판도 핵심 역할·흐름·오류와 반환값의 구별을 수행했다. 결과가 같다는 사실로 스킬이 불필요하거나 수정 문구가 무효라고 결론내릴 수도 없다.

사용자 요청:

> 그럼 기존 스킬이랑 수정안으로 같은 장면에 응답해보고 실제로 뭐가 달라지는지 비교해보자. 우리가 의도한 답을 미리 알려주지 말고 검증해봐

진행 중 사용자는 “몇개 장면까지 돌릴예정이야?”라고 물었고, Main은 세 장면·판본별 한 번·총 여섯 응답, 두 명의 익명 평가로 이번 범위를 명시했다. 이 범위에서 종료했다.

## 어떻게 비교했는가

- [응답 생성 전 계획](experiments/artifact-explanation-2026-10-21/protocol.md)을 고정했다. 원문 세 장면을 질문 시점에서 잘랐고 이후 사용자 정정·AI 답·인터뷰·설계 기록·Main의 예시와 기대 답은 전달하지 않았다.
- 여섯 응답은 각각 대화 이력을 상속하지 않는 새 worker에서 작성했다. 같은 기본 모델·추론 설정을 사용했으며 실행자는 한 스킬 판본만 읽었다. 입력 대화와 공통 기준은 장면별 양쪽에 동일했다. 명시적으로 지정한 스킬의 수행 비교이며 자동 호출 판단은 검증하지 않았다.
- 입력은 당시 대화와 그 안의 코드 발췌다. 원래 제품 저장소·시뮬레이터 접근은 허용하지 않았다. 따라서 이번 결과는 같은 자료를 설명하고 판단하는 행동 비교이며, 실제 코드 조사와 추가 검증 수행의 재현은 아니다.
- 최초 응답은 수정·재시도 없이 고정하고 해시를 저장했다. [판본·원문 범위·입력 및 응답 해시](experiments/artifact-explanation-2026-10-21/manifest.json), 각 run의 prompt·SKILL·guidance·receipt를 보존했다. 공통 기준 링크만 동일한 실행 경로로 정규화했다.
- 두 평가자는 원문과 익명 A/B 응답만 받았다. 스킬·판본·개선 목표는 받지 않았고 판단 기준의 중요도를 직접 정했다. [첫 평가](experiments/artifact-explanation-2026-10-21/reviews/review-1/assessment.md)와 [역순 표시 평가](experiments/artifact-explanation-2026-10-21/reviews/review-2/assessment.md)는 독립 생성했다. [표시 순서 매핑](experiments/artifact-explanation-2026-10-21/review-mapping.json)을 보존했다.

### 일정 작성

기존판:

> 하나의 일정 초안을 둔 채 검색과 입력 폼을 오가고, 저장할 때 그 초안을 생성 요청으로 넘기는 구조입니다.

수정안:

> 검색으로 장소를 고르고, 같은 초안을 편집하다가, 필요하면 장소만 다시 고른 뒤 저장한다

둘 다 요청에 맞춰 화면 흐름을 중심으로 재구성했고 근본 역할을 흐름 안에 붙였다. 기존판은 사용자 행동·초안 변화·화면의 대응 표가 있고, 수정안은 장소 변경이 같은 검색 로직으로 돌아오는 관계와 정책 영향의 의사코드가 조금 더 명시적이다. 수정안은 저장 분기의 전제를 도표 가까이에 두었다. 어느 한쪽만 역할 우선이나 흐름 연결을 수행한 것은 아니다.

공통 한계도 있다. 실제 코드 발췌는 입력에 보존된 step 선언이고 나머지 연결은 의사코드다. 양쪽 모두 이 지위를 밝혔다. 실제 handler·props·제출 구현의 코드와 설명을 연결하는 능력까지 검증한 것은 아니다. 또한 사용자 마지막 질문 자체가 화면·로직·코드를 명시하므로 새 스킬 문구의 독립 기여를 구별하기 어렵다.

### Promise

기존판:

> 오류가 `error`라는 인자로 들어왔다고 해서 이 함수도 자동으로 오류를 던지는 건 아닙니다.

수정안:

> `error`는 이 함수가 받은 것이고, `undefined`는 이 함수가 반환한 것

두 응답 모두 catch callback의 입력과 반환을 구별하고 return undefined와 throw error, 123 반환을 비교했다. 원래 답을 길게 반복하거나 대기열 전체를 다시 설명하지 않았다.

수정안에는 원래 `() => undefined`에서 매개변수를 생략한 이유, 호출자가 실패한 P1을 처리 없이 await한 다음 줄에서 B를 등록한다면 그 줄에 도달하지 못한다는 조건이 추가됐다. 평가 1은 이 연결을 유용하게 봤고, 평가 2는 지금 질문의 전제가 이미 연결된 B이므로 새 갈림길이 설명 부담을 늘린다고 봤다. 기존판은 `P2.then(() => operationB())`가 undefined 값을 사용하지 않는다는 점을 더 직접적으로 연결했다.

두 평가자가 모두 자신의 표시 순서에서 B를 선호했으나, 두 번째는 순서가 반대여서 실제 판본 선호는 갈렸다. 평가자 차이와 표시 순서의 영향을 분리한 결과가 아니며 다수결 우세도 없다. 추가 설명이 실제 이해를 돕는지는 후속 사용자 반응이 없다.

### access

기존판:

> 현재 가능한 일을 알려 주는 `access`와, 실행을 맡는 `actions`는 역할이 다르므로 함께 둘 수 있습니다.

수정안:

> `access`는 그대로 필요한데 ... 반환 형태는 다음과 같아야 합니다.

둘 다 `query, access, actions, view` 형태를 제시하고, 설명에서 빠졌다는 사실과 실제 구현에서 빠졌는지의 미확인을 구별했다. 실제 수정·복원을 실행하거나 완료했다고 보고하지 않았다. 두 평가자는 질문을 기존 합의 누락에 대한 정정으로 해석했고 실질 동등으로 판정했다.

Main은 수정안의 더 강한 표현을 개선 근거로 채택하지 않는다. 접근 판단 자체가 필요하다는 것과 access를 외부 반환값으로 반드시 노출해야 한다는 것은 별도 판단이며, 이번 수정안 응답은 기존 소비자·대안·비용을 비교하지 않았다. 다만 이 시점의 짧은 질문은 위치 조회로도 읽히므로, 필요한 설계 비교를 하지 않았다는 이유만으로 응답 실패를 확정하지도 않는다.

원래 대화의 이후 사용자 정정2769는 “아니 무조건 하란게 아니라 판단하라고”였다. 이는 **실행자·평가자에게 제공하지 않은 후속 근거**다. 이번 응답은 실제 수정을 약속하지 않아 당시 AI 답과 같지는 않지만, 사용자가 후속에 드러낸 적절성 판단 요구까지 해결한다고 확인한 결과도 아니다. 이 구별은 익명 평가 뒤 Main의 해석이며 평가자 판단으로 소급하지 않는다.

## 보완안에 대해 지금 말할 수 있는 것

- 역할·흐름·코드 연결과 작은 설명 복구는 기존판에서도 나왔다. 이번 응답만으로 관련 문구 추가의 효과를 입증하지 못했다.
- 수정안의 추가 설명은 정보가 조금 늘어난 부분과 단정이 강해진 부분을 함께 만들었다. 자세함 자체를 개선으로 계산하지 않는다.
- 원인 단정 방지, 이전 문제·수정·현재 보고의 연속성, 요청한 질문식 학습과 전환, 접근 가능한 추가 조사의 수행은 이번 세 장면으로 충분히 시험하지 않았다. 특히 보고서 장면은 이번 범위에 없다.
- 중복 목록을 본문에 합친 문서 정리의 가치와 응답 품질 개선의 입증을 구별한다. 통합안은 프로토타입 검토안으로 유지하되 성능 개선이 검증됐다고 표기하지 않는다. 이번 비교를 이유로 스킬 문구를 추가 수정하지 않았다.

## 재현·보존과 한계

[실험 자료 안내](experiments/artifact-explanation-2026-10-21/README.md)에서 입력·판본·최초 응답·평가 원문을 찾는다. Main은 원문 질문, 여섯 응답, 두 평가를 직접 대조했고 응답 해시가 고정 이후 달라지지 않았음을 확인했다. 각 실행 receipt는 지정 자료만 읽고 제품 파일·네트워크·다른 실행을 조회하지 않았다고 보고한다. 공유 파일시스템을 기술적으로 격리한 실험은 아니다.

장면별 판본당 한 번, 총 여섯 응답이므로 반복 일관성·일반적인 우열·사용자의 실제 이해 개선·정확한 수정 조항의 단독 인과를 입증하지 않는다. 사례는 보완안을 만들 때 본 장면에서 Main이 선택했으므로 보지 않은 새 사례에 대한 검증도 아니다. 당시 정확한 모델·스킬·실행 환경을 재현한 것이 아니므로 과거 실패의 재현 실험이라고 부르지 않는다.
