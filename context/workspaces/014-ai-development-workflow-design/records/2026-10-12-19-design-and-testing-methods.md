## 1. 호출자가 알아야 하는 일을 줄이는 설계

### 자료의 뜻

codebase-design의 interface는 함수 이름과 인자뿐 아니라 호출 순서, 설정, 실패 처리와 불변 조건 등 올바른 사용에 필요한 지식 전체다. 깊은 모듈은 그 지식을 작게 유지하면서 내부에서 충분한 동작을 제공한다. 파일을 크게 만들거나 모든 책임을 한 클래스에 넣는 뜻은 아니다. 내부에서는 다른 변경 이유와 의존성에 따라 나눌 수 있다.

### 같은 기능의 대비

가상 요구는 알림 설정을 명시적으로 저장하고, 실패하면 입력을 유지하며 재시도할 수 있게 하는 것이다. 여러 화면이 같은 저장 계약을 사용한다고 가정한다.

| 구조 | 화면이 알아야 하는 것 | 판단 |
| --- | --- | --- |
| 각 화면이 저장 흐름을 구성 | 검증 → 요청 → 저장된 값 반영 → 편집 상태 정리 → 캐시 갱신, 실패 시 입력 유지 | 같은 계약을 각 화면이 다시 조립하므로 순서와 정책이 흩어질 수 있음 |
| 작은 함수들을 공통 파일로 추출 | 함수 이름은 공통이지만 호출 순서·실패 복구를 화면이 계속 조립 | 중복 코드는 줄어도 호출자가 알아야 할 부담은 남을 수 있음 |
| 설정 편집 모듈이 저장 흐름을 소유 | 화면은 입력 변경·저장을 요청하고 공개 상태로 결과를 표시 | 같은 저장 계약의 순서·상태 처리를 모듈 안에서 일관되게 다룰 수 있음 |

개념적인 인터페이스 예:

```text
editor.change({email: true})
await editor.save()
editor.state()  # draft, saved, status, error를 읽는다
```

함수 하나로 감쌌더라도 호출 전에 `prepare`, 실패 뒤 `restore`, 성공 뒤 `invalidate`를 화면이 다시 해야 한다면 숨긴 복잡함이 적다. 반대로 이 모듈이 화면별 팝업·탐색·전혀 다른 저장 정책까지 옵션으로 흡수하면 사용하는 쪽과 고치는 쪽의 부담이 커질 수 있다. 예시의 화면 표시와 탐색 결정은 화면에 남긴다.

**Locality**는 저장 계약을 바꿀 때 지식·코드·검사가 함께 모여 있어 여러 호출부를 다시 조사하지 않아도 되는 이점이다. **Leverage**는 화면과 테스트가 적은 사용법으로 충분한 동작을 얻는 이점이다.

### 기존 기준과의 관계

CODE-QUALITY의 ‘같은 책임과 변경 이유는 모으고 다른 이유는 분리’, ‘파일 수·줄 수를 분리 목표로 삼지 않는다’와 방향이 같다. 자료는 그 판단을 **호출자가 반드시 알아야 할 일을 전후로 비교하는 방법**으로 더 구체화한다. 우리 기준에는 depth라는 명시적 기준과 아래 삭제 사고실험이 없다.

삭제 테스트는 모듈을 없앴다고 상상했을 때 복잡함이 어디로 가는지 보는 것이다. 단순 전달 계층을 없애도 사용법이 그대로라면 필요성을 다시 볼 수 있다. 저장 흐름을 맡은 모듈을 없애자 각 화면이 실패·캐시 정책을 다시 구현해야 한다면 그 모듈이 유용한 책임을 맡았다는 근거다. 호환 경로를 보존하는 얇은 연결 코드는 우리 기준이 명시적으로 허용하므로 얇다는 이유만으로 삭제하지 않는다.

## 2. 같은 인터페이스에서 결과와 실패를 검사한다

### 자료의 뜻

PR 강연은 상수 값을 그대로 재확인하거나 소스 문자열의 순서를 검사하는 테스트, 실패를 모두 성공 stub으로 가리는 테스트를 문제로 든다. codebase-design은 호출자와 테스트가 같은 인터페이스를 사용하면 내부 구조 변경에 덜 묶일 수 있다고 제안한다. 내부 seam도 허용하므로 내부 테스트 전체 금지로 읽지 않는다.

### 같은 저장 기능의 대비

| 검사 | 보장하는 것과 놓치는 것 |
| --- | --- |
| 저장 헬퍼가 한 번 호출됐는지 확인 | 위임 사실은 보지만 입력 유지·저장 결과는 입증하지 못함 |
| 소스 파일에 `restoreDraft` 문자열이 있는지 확인 | 코드 모양을 보며 실제 오류 때 그 경로를 타는지는 모름 |
| 네트워크와 저장 모듈을 모두 성공 mock으로 대체 | 연결 부품을 흉내 낼 수 있으나 검사하려던 실제 저장 정책까지 빠질 수 있음 |
| 실제 편집 모듈에 실패하는 저장 의존성을 연결하고 상태 확인 | 실패 뒤 draft 유지·saved 불변·오류 표시 상태라는 계약을 확인할 수 있음 |

다음은 실행한 테스트가 아닌 설명용 의사 코드다. 기존 저장값은 `email: false`이고 실패하는 외부 저장 의존성을 주입했다고 가정한다.

```text
editor.change({email: true})
gateway.failNextSave("offline")
await editor.save()

확인: draft.email == true
확인: saved.email == false
확인: status == "error"

gateway.succeedNextSave()
await editor.save()

확인: saved.email == true
확인: status == "saved"
```

편집 모듈 내부의 함수명이나 파일 배치가 바뀌어도 같은 계약을 같은 공개 인터페이스에서 확인할 수 있다. 인터페이스 자체를 바꾸면 테스트 호출도 바꾸되, 원래 결과·실패 보장은 유지해야 한다.

네트워크 fake로 통과한 것은 **주어진 실패를 편집 모듈이 올바르게 처리한다는 근거**다. 실제 HTTP 오류 변환, 서버 저장, 화면의 오류 메시지·재진입은 해당 연결 검사와 실제 실행에서 별도로 확인할 부분이다. 이 구분은 01-03으로 연결되며, 이 테스트 하나로 앱 전체가 확인됐다고 하지 않는다.

### 기존 기준과의 관계

우리 기준도 구현 반복 검사 금지, 실패·부작용 검사, 내부 호출 assertion 변경 시 보장 유지, 실제 실행과 자동 테스트의 구별을 이미 요구한다. 자료의 추가 강점은 **호출자에게 제공하는 설계 경계와 주된 동작 테스트의 경계를 함께 잡는 방법**이다.

호출 횟수 assertion이나 상수 검사가 언제나 무의미한 것은 아니다. 예를 들어 ‘결제를 두 번 요청하지 않는다’는 외부 계약이면 호출 횟수가 의미 있다. 계약이 정한 한도를 검사하는 것과 구현에서 읽은 값을 그대로 기대값으로 복사하는 것도 다르다. 이는 자료의 경고를 적용할 때 필요한 해석이며 자료에 모든 예외가 서술돼 있다는 뜻은 아니다.

## 3. 바꿔 끼울 경계와 순수 계산을 필요한 곳에 둔다

codebase-design은 외부 의존성을 내부에서 직접 생성하기보다 전달받고, 계산은 입력을 몰래 수정하기보다 결과로 돌려주는 예를 제시한다.

```text
내부 생성: editor.save()가 매번 HttpGateway를 직접 만든다
주입: createEditor(accountId, gateway)로 만들고 editor.save()를 사용한다
```

실제 앱은 HTTP 구현을, 테스트는 실패·지연을 통제할 fake를 연결할 수 있다. 편집 상태와 저장 정책은 실제 코드를 실행하고 외부 의존성만 바꾼다. 자료에서 seam은 사용하는 쪽을 고치지 않고 동작 구현을 바꿀 수 있는 자리, adapter는 그 자리에 넣는 구체 구현이다.

우리 기준도 파일 시스템·프로세스처럼 부작용을 통제해야 하는 의존성은 필요한 경계에서 명시적으로 전달하고, 현재 필요 없는 인터페이스는 만들지 않도록 한다. 이 부분은 크게 겹친다.

자료의 ‘실제 변이가 없는 seam을 만들지 않는다’와 ‘어댑터 하나면 가상, 둘이면 실제’는 추측성 추상화를 경계하는 강한 문장이다. 이를 운영 구현이 두 개 있어야만 테스트 경계를 허용한다는 규칙으로 바로 옮길 수는 없다. 자료 자체도 의존성 주입과 테스트용 대체를 다룬다. 현재 검증에서 실제 대체 필요가 있는지로 비교할 여지가 있으며, 정확한 채택 문구는 미정이다.

계산 예에서는 `applyDiscount(cart)`가 입력을 변경하는 대신 `calculateDiscount(cart)`가 결과를 반환하면 숨은 부작용 없이 검사하기 쉽다. 그렇다고 저장 기능까지 효과 없는 함수로 만들 수는 없고, 모든 계산을 별도 공개 파일로 추출할 필요도 없다. improve-codebase-architecture는 테스트하기 쉬운 순수 함수만 떼어냈지만 실제 버그가 그 함수의 호출·조립에 남는 경우도 탐색 대상으로 든다. 모듈 내부의 계산 테스트와 외부 동작 테스트를 목적에 맞게 함께 둘 수 있다.

## 4. 개선 후보를 발견하고 비교하는 절차

improve-codebase-architecture는 사용자가 지정한 범위를 먼저 따르고, 범위가 없으면 최근 반복 변경된 곳을 탐색한다. 기존 도메인 용어와 결정 이유를 읽은 뒤, 한 개념을 이해하려고 얼마나 많은 파일을 오가는지·서로 내부를 침범하는지·검사하기 어려운 동작이 있는지를 찾는다. 전후 구조·이점·추천 강도를 보여주고 후보를 고른 뒤 더 자세한 인터페이스를 논의한다. 여러 다른 인터페이스를 비교하는 방법도 소개하지만 관련 상세 참조 파일은 제공되지 않았다.

가상 저장 기능에서는 ‘함수를 몇 개 합칠까’보다 다음 비교가 먼저다.

- 공통 저장 함수만 제공하면 각 화면에 어떤 상태 조립 책임이 남는가.
- 편집 모듈이 상태와 저장 흐름을 소유하면 호출자가 얼마나 단순해지고 내부 책임은 어떻게 나뉘는가.
- 화면마다 저장 계약이 다르면 별도 모듈 유지가 더 이해하기 쉬운가.

우리 실행 기준은 결과와 계약을 먼저 정하고 요청에 필요한 관련 흐름을 조사하라고 한다. 자료는 그 조사에서 사용할 구체적인 마찰 신호, 후보 선택과 전후 제시 방법을 더한다. ‘최근 많이 바뀐 곳부터’는 범위가 지정되지 않은 탐색 방법이며 모든 작은 변경을 리팩터링 기회로 확대하는 근거가 아니다. HTML 보고·여러 agent·용어집 파일을 우리 모든 작업의 필수 절차로 정하지 않았다.

## 5. 요구 충족과 코드 품질을 나누어 본다

code-review 자료는 Spec과 Standards를 나눠 본다. 예를 들어 입력 유지가 요구인데 실패 시 초기화하면 요구 충족 문제다. 실패 후 입력은 유지하지만 세 화면이 같은 저장 계약을 각각 조립하면 구조 개선 후보일 수 있다. 전자는 계약으로 바로 판정할 수 있고, 후자는 변경 이유와 비용·동작 차이를 살펴야 한다.

우리 실행 기준도 요구 결과·품질·보존 계약을 함께 판단하라고 한다. 차이는 제공 스킬이 두 축을 별도 agent에서 병렬로 보고하고, Fowler 코드 스멜을 항상 후보 기준에 포함하는 구체 절차까지 정한다는 점이다. 자료도 스멜을 절대 위반으로 보지 않으며 저장소 규칙과 자동 검사 역할을 우선한다.

강연은 검토자가 직접 개선하도록 권하지만 제공 code-review의 동작은 보고로 끝난다. 우리 B는 직접 수정 방향을 선택했고, 아직 상세 방법을 설계 중이다. ‘두 판단을 구별한다’는 것과 ‘항상 두 agent로 실행한다’는 것을 함께 채택하지 않는다.

## 6. 이번 코드를 다음 AI가 따라 할 패턴으로 본다

Agent 신뢰 강연은 기존 코드 패턴이 다음 작업에 확장되는 환경이므로 구조·데이터·자동 검사·지침을 함께 개선하라고 권한다. 저장 때 캐시 갱신을 자꾸 빼먹는다면 ‘잊지 말라’는 문장을 반복하는 것에 더해 저장 경로 안에서 일관되게 처리할 수 있는지 본다. 화면에서 낮은 수준의 저장 API를 우회 호출하는 것을 import 규칙으로 정확히 잡을 수 있다면 자동 검사도 후보가 된다. UI/프로세스 경계를 넘는 무거운 작업을 구조와 의존성 규칙으로 막는 것이 강연의 실제 예다.

우리 기준에도 공통 계약을 중복하지 않고 실제 차이에 맞춰 분리하며 기존 lint·검사를 사용하는 내용은 있다. 다만 ‘앞으로 AI가 복사할 환경을 개선하고 반복 실수를 어느 층에서 막을지’의 명시적 우선순위는 자료가 더 강하게 제시한다. 구조 변경·lint·스킬 각각의 적용 비용과 범위는 비교해야 하며 모든 검토에서 새 자동화를 만드는 것으로 읽지 않는다.

Vercel은 여기서 추가 구별을 준다. 기존 코드는 무엇이 존재하는지의 근거지만 그것이 옳은 이유까지 보장하지 않는다. 현재 제품 동작·채택 결정·가이드로 패턴을 판단해야 한다. 안정적으로 판별할 수 있는 것은 lint로, 제품 맥락이 필요한 판단은 사례·지침으로 다루는 제안도 있다. Dune의 주석 금지는 그 팀의 특수 선택이며 이유를 설명하는 주석을 허용·요구하는 우리 기준과 다르다.

## 논의할 차이와 상태

방향이 겹친다는 사실만으로 기존 실행이 충분했다고 평가하지 않는다. 반대로 방법 이름이 새롭다는 이유로 새 기준이 필요하다고 단정하지도 않는다. 이번에 구분한 것은 다음이다.

| 구분 | 논의할 내용 |
| --- | --- |
| 기존 기준을 더 구체적으로 적용할 수 있는 방법 | 호출자가 알아야 할 일을 전후로 비교, 삭제 사고실험, 같은 인터페이스에서 동작·실패 검사, 구조 후보의 전후 대비 |
| 채택하려면 의미와 예외를 정해야 할 강한 규칙 | 외부 인터페이스 중심 검사의 적용 범위, seam의 실제 필요, 얇은 모듈의 예외, 강제 설계 어휘·주석 금지 등 |
| 운영 배치의 선택 | 구현자와 검토자가 읽고 적용할 기준, Spec·Standards의 분리 방식, B의 수정과 기존 기준의 연결 |
| 이후 Ticket과 연결할 구체 내용 | 실제 앱 실행 수단은 01-03, 공통 기준·사례 위치는 03, 사람에게 보여줄 설명은 04-02, 경험에서 코드·검사·스킬 개선을 선택하는 방법은 05 |

첫 논의 대상으로는 **호출자 부담과 변경의 응집을 실제 전후에서 비교하는 방법**, **그 인터페이스의 결과·실패를 보는 테스트 방법**이 서로 연결되어 있다. 일괄 채택 대신 이 둘의 적용 예와 불필요한 추상화가 되는 반례부터 판단할 수 있다. B 방향 이외의 새 기준은 선택하지 않았다. 실제 코드 조사·수정·테스트 실행·워크플로 효과 검증은 수행하지 않았다.
