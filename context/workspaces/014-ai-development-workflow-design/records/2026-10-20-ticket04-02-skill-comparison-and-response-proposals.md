# 04-02 — 기존 설명 스킬의 유지·보완과 응답 대비안

2026-10-20 재대조 반영. **두 스킬의 역할과 호출 경계는 유지하되, 코드의 근본 역할을 먼저 이해시키고 실제 코드·화면·흐름에 연결하는 기준을 구체화한다.** 보고서는 이전 문제·이후 수정·이번 확인·다음 판단을 이어 주고, 설명 중 제기된 설계 의문은 타당성까지 검토한다. 첫 보고의 충분함은 작업 수행 책임에 연결한다.

이 문서는 사용자 요청에 따라 만든 **검토용 설계안**이다. 기존 스킬·글로벌 지침·제품 코드에는 적용하지 않았다. 응답 예시는 Main이 보존된 장면을 바탕으로 새로 작성한 것이며 당시 응답이나 실제 실행 결과가 아니다. 사용자 채택, 실제 스킬 수행과 이해 개선 효과는 남아 있다.

요청 원문:

> 그럼 04-02 진행해보자. 방금 본 장면들이랑 기존 스킬을 대조해서 뭘 유지하고 어떻게 보완하면 좋을지 실제 응답 예시랑 같이 제안해봐

04-01은 다른 세션에서 진행 중이다. 여기서는 설명 중 필요한 판단과 재판단으로 이어지는 조건을 제안하며, 그 스킬의 최종 동작·기록 운영을 대신 확정하지 않는다.

## 대화를 다시 읽고 바꾼 판단

사용자는 첫 제안의 2번에 대해 “동작만 설명하지말고 먼저 코드의 근본 역할을 설명하라고 한” 발화를 찾아 비교하도록 했고, 이어 다음과 같이 요청했다.

> 그럼 04-02다시 대화 들 보면서 판단해보자 이렇게 오해한게 잇을수 잇잔아

첫 제안의 네 장면 앞뒤를 다시 읽고, 보존 corpus에서 근본 역할·멘탈모델·구체적 코드·이해 어려움에 관한 사용자 발화를 찾아 일정 작성·여행 목록·시간 선택창·질문식 학습 장면을 추가 대조했다. 사용자 발화, 당시 AI의 해석, 현재 Main의 해석을 구별했다. 전체64세션을 모든 주장에 대해 검증한 것은 아니다.

또 첫 제안의 “사용자를 시험하지 않는다”는 표현은 너무 넓었다. 네트워크 대화2716에서 사용자는 “질문을 통해서 내 이해를 끌어줘 소크라테스식으로”라고 직접 요청했다. 기존 recovery처럼 **이해 확인 시험을 기본 종료 조건으로 강제하지 않는다**는 경계가 맞다. 요청한 질문식 학습은 수행하고,2831처럼 구체적 코드 설명을 요구하면 그 방식으로 전환한다.

이 정정은 현재 제안 본문과 예시에 반영했다. 과거 AI 응답의 자기평가를 사용자 의도나 실제 효과의 근거로 승격하지 않으며, 아래 예시를 새로 썼다는 사실로 개선 성공을 확정하지 않는다.

## 무엇을 유지하고 어디를 보완할 것인가

기준판은 [Noline briefing](../source/noline-baseline/.claude/skills/work-artifact-briefing/SKILL.md), [Noline recovery](../source/noline-baseline/.claude/skills/explanation-recovery/SKILL.md), [공통 설명·근거 기준](../source/noline-baseline/context/project/guidance/explanation-and-evidence-criteria.md)이다. 앞선 대조에서 두 SKILL.md는 각각 Reference 기준판과 동일했다. 설치 경로의 차이를 설명 행동의 차이로 읽지 않는다. 이 기준판이 각 과거 응답 때 실제 읽힌 정확한 판본이었다고 단정하지 않는다.

| 현행 요구와 책임 | 장면에서 드러난 차이 | 제안 |
| --- | --- | --- |
| briefing은 작업물 원자료를 조사하고, recovery는 앞선 실제 발화의 뜻과 빠진 연결을 복구한다. | 보고서에는 설명 누락과 추가 조사 부족이 함께 있었고, Promise 질문은 대화 안에서 점차 혼동을 좁혔다. | **유지.** 요청의 주목적을 따라 수행한다. 설명을 하다가 사실 확인이 필요해져도 두 스킬을 항상 순서대로 호출하지 않는다. |
| briefing은 중요한 이름의 역할을 설명하고 호출 순서만 나열하지 않는다. | 인증 첫 설명에도 역할은 있었다. 사용자는 여러 장면에서 근본 역할·멘탈모델을 먼저 잡고 구체적 코드와 흐름으로 설명하도록 요청했다. | **구체화.** 전체에서 무엇을 맡고 왜 필요한지 먼저 설명한다. 구현 종류의 분류만으로 대신하지 않고 역할이 실제 코드·화면·데이터 관계에서 어떻게 구현되는지 잇는다. |
| briefing은 관련 source·사용처·실행 근거를 필요한 만큼 조사하고 미확인을 밝힌다. | 보고서에서는 접근 가능한 후속 확인도 미확인으로 남겨 다음 판단이 막혔다. | **조사 조건 보완.** 현재 답을 바꾸는 미확인인지 판단하고, 기존 권한과 범위 안에서 가능한 확인을 수행한다. 보고서 작성 업무의 검사 수행을 설명 스킬에 모두 넘기지 않는다. |
| briefing은 구조 선택의 이득·제약을 설명하고 당시 의도와 현재 해석을 구별한다. | access 질문 뒤 수정부터 약속했고, 정정 후에야 사용 조건과 비용을 설명했다. 추천 방향 자체는 같았다. | **질문 대응 구체화.** 변경 사실, 확인 가능한 선택 이유, 현재 적절성의 판단을 구별한다. 질문을 변경 권한으로 바꾸지 않으며, 이유 설명을 금지하거나 판단을 회피하지도 않는다. |
| recovery는 직접 답과 가장 가까운 누락부터 복구하고, 틀린 주장은 정정한다. | Promise 장면은 질문에 따라 표현을 바꾸었고 두 갈래 설명이 도움됐다는 회고가 있다. 인증 비교에서는 첫 응답을 부정확하게 축약한 주장 자체를 고쳐야 했다. | **유지·구체화.** 사용자의 이해·미이해 발화를 다음 답의 범위에 사용한다. 혼동 원인은 가설로 두고 반복 질문만으로 실패를 단정하지 않는다. 이해 시험은 강제하지 않되 요청한 질문식 학습은 지원한다. |
| 고정 목차·구조도·전체 조사·이해 확인 질문을 강제하지 않는다. | 역할과 동작을 합친 인증 설명은 길어지며 주제 구분이 약해졌다. | **유지·표현 보완.** 조사 항목과 출력 구성을 구별한다. 내용을 연결하는 일과 독립 주제를 구분하는 일을 함께 한다. |
| 설명은 read-only가 기본이며 정정은 Main에 반환하고 기록은 상위 계약을 따른다. | 기준판은 Maintain 인계를 명시하지만 014는 수동 관리 중이다. | **반환 책임 유지, 운영 연결은 후속 대조.** 자동 Maintainer를 되살리거나 설명 스킬이 문서 갱신을 중복 소유하지 않는다. 실제 이식 시 02·04-03·06에서 상위 기록 책임과 문구를 맞춘다. |

현행 요구가 이미 있다는 사실은 수행이 충분했다는 뜻도, 문구 보완이 무의미하다는 뜻도 아니다. 아래는 기존 요구를 실제로 구별해 적용하도록 만드는 제안이다. 어느 문장 때문에 당시 실패했는지의 단독 인과는 확인하지 못했다.

## 보고서: 무엇을 검사했고 그 결과로 무엇이 달라졌는가

[원문](../source/noline-evaluation/corpus/01a1052a-4e61-7072-9b81-ff44449e5b85/messages.jsonl)의 `source_line` 603에서 사용자는 기존 홈 보고서와 같은 방식으로 나머지 네 보고서를 요청했다. 779의 첫 완료 답은 “4개 보고서를 각각 만들고” 확인 결과·미확인·다음 작업을 담았다고 보고했다. 이 항목들이 있다는 사실만으로 사용자의 질문에 답한 것은 아니었다.

789의 사용자 원문:

> 보고서들이 뭘 됐고 뭐가 안돼서 뭘 하란건지 잘모르겠어
> 끄리고 기존 보고서랑 맥락이 안이어지는것 같아 새 보고서가 그래서 왜 이걸 검사했는지도 모르겠고 등
> 그리고 추가 검토는 왜 안한거야? 정말 어렵거나 사유가 있으면 몰라도 그렇다고 기존 범위를 너무 벗어나서 디테일하게 계속 파고들란건 아니고

836·1100에서 AI는 정상 화면 수집에 치우쳤고, 폼에서 Debug 화면으로 이동하기 어려운 제약이 다른 확인까지 중단할 이유는 아니었다고 설명했다. 후속 답은 목록 복귀, 날짜 저장값, 선택창을 추가 확인했다고 보고하며 수정 필요 여부를 다시 나눴다. 1119에서 사용자는 “보고서가 뭔가 덜 부족하긴한데 일단 비활성 홈 문제 해결부터 하자”라고 했다. [인터뷰](../source/reading/noline-evaluation/reviews/interview-20261012.md)의 부분 개선·만족 유보와 함께 읽는다.

> **확인 범위**
>
> - 이번 확인으로 제품 코드를 수정하지는 않았습니다.
> - 실제 통신 단절 중 저장까지 확인한 결과는 아닙니다.
> - 기존 보류 항목은 그대로 남아 있습니다. 위 결과만으로 Ticket 전체를 완료 처리하지 않습니다.

이 예시는209·221의 과거 문제·이후 수정 보고와1100의 추가 확인 보고를 연결한 짧은 도입부다. 실제 보고서라면 해당 화면의 이전 문제와 현재 장면, 어떤 코드·검사가 그 차이를 지지하는지를 본문에서 보여 줘야 한다. 이 표만으로 네 HTML 보고서의 충분함을 대신하지 않는다. 보존되지 않은 보고서 본문·화면 링크·검증 결과를 새로 만들지 않는다.

**확인하지 못했다면:** “날짜 차이의 원인을 아직 모른다”에서 멈추거나 추정 원인을 확정하지 않는다. 현재 판단을 가르는 것이 저장값인지 표시 기준인지 밝히고, 허용된 범위에서 그 둘을 대조한다. 기기 접근 등이 막혔다면 무엇까지 확인했고 어떤 결론을 아직 낼 수 없는지 남긴다. 이 제한이 무관한 목록 확인까지 중단할 이유가 되지는 않는다. 사람의 새로운 제품 선택이 필요하면 그 선택의 차이를 설명한다.

**스킬과 작업 흐름의 관계:** 최초 검토·보고 작성은 원래 맡은 작업의 책임이다. 기존 보고서를 이해시켜 달라는 요청이면 briefing이 질문·기준·근거·남은 판단을 조사한다. 앞선 “확인됐다”의 뜻을 묻는다면 recovery로 그 말의 범위를 복구한다. 사용자가 추가 검토도 요청했다면 해당 검토 업무를 함께 수행하되, 설명 요청만으로 새 전체 검사를 착수하지 않는다.

## 코드 브리핑: 근본 역할을 먼저 잡고 실제 코드와 흐름으로 잇기

최초 [브리핑 원문](../source/noline-evaluation/corpus/01a0c3ac-f144-7251-805b-2e582aed07c6/messages.jsonl) 1546에는 이미 상태·역할·이유·실패 조건·근거가 있었다. Store가 “세션을 받아들일 조건, 저장, 상태 반영”을 함께 맡고, 이 배치가 기술적으로 유일한 방법은 아니라고 설명했다.

[후속 원문](../source/noline-evaluation/corpus/01a0c7bd-f413-7551-836d-3203775e7c38/messages.jsonl) 50의 요청:

> 코드 주체 자체에 대한 근본적인 역할 정의 뭐 이런게 나와야 되지 앟ㅎ을까 싶어 설명중간에 그런게 잘 녹아야 동작을 봐도 아 이런거구나 하고 그러는데

AI가 이전 설명을 동작만의 설명으로 축약하자 사용자는80에서 다시 대조하도록 했다.96에서 AI는 그 주장을 정정했지만, “구조 먼저라는 고정 순서도 과했다”는 자기 해석까지 덧붙였다. 사용자가 역할 우선 요구를 거부한 근거로 쓰지 않는다. 역할·동작을 합친125 뒤에는132에서 “이번 설며은 너무 서술적이야 문단이나 구분도 안되고”라는 정정이 있었다. 최종149의 구성 변화는 확인되지만 이해 개선 효과는 확정하지 않는다.

[일정 작성 원문](../source/noline-evaluation/corpus/01a0f20d-50a5-78e2-a665-e2c59c34987e/messages.jsonl)2461·2499는 역할 우선과 구체적 흐름을 함께 요구한다. [여행 목록 원문](../source/noline-evaluation/corpus/01a1052a-4e61-7072-9b81-ff44449e5b85/messages.jsonl)3962에서도 “앞선 설명은 설명만 잇으니까 좀 어렵네 멘탈모델 도식화 구체적 코드도 고려하고”라고 했다. 따라서 구체적 코드는 한 줄을 별도로 물을 때만 추가하는 장식이 아니다. 전체 브리핑에서도 역할·연결을 이해하는 데 필요한 부분을 선별해 보여 줄 수 있어야 한다.

### 응답 예시 — 일정 작성 구조의 근본 역할과 실제 연결

**예시 전제:** 당시2492·2504의 코드 발췌를 바탕으로 다시 쓴 부분 브리핑이다. 현재 제품 코드를 실행·확인한 답이 아니다.

> **핵심: 검색이 막혀도 작성 중인 일정은 유지됩니다.**
>
> 먼저 두 가지를 구별하면 됩니다.
>
> | 구분 | 의미 | 네트워크가 끊기면 |
> | --- | --- | --- |
> | 작성 중인 내용 | 제목·날짜·선택 장소 등 사용자가 만들고 있는 일정 | 유지 |
> | 기능의 사용 가능 여부 | 지금 검색하거나 저장할 수 있는 조건 | 해당 기능의 조건에 따라 제한 |
>
> **각 코드의 근본 역할**
>
> | 코드 | 맡는 역할 |
> | --- | --- |
> | `useCreateScheduleForm` | 작성 중인 일정을 유지하고, 입력 변화가 다른 값에 미치는 영향을 관리 |
> | 화면의 `step`과 연결 함수 | 같은 초안을 사용하면서 검색·입력 중 어떤 단계를 보여 줄지 결정 |
> | 검색 정책과 검색 코드 | 현재 검색·선택이 가능한지 판단하고 검색을 수행 |
>
> **장소를 선택하면**
>
> 당시 코드의 핵심 세 줄입니다. 키보드를 닫는 호출은 생략했습니다.
>
> ```tsx
> if (!search.canSelect()) return; // 지금 선택할 수 있는가
> draft.selectLocation(place);    // 작성 내용에 장소 반영
> setStep('form');                // 같은 초안의 입력 화면 표시
> ```
>
> 직접 수정한 제목을 보존할지는 **초안**이 결정하고, 입력 화면으로 이동할지는 **화면**이 결정합니다. 초안은 검색·입력 영역보다 오래 유지되는 화면 쪽에 있어 두 영역을 오가도 같은 내용을 씁니다. 네트워크 변화만으로 작성 내용이나 화면 단계를 초기화하지 않습니다.

역할을 먼저 이해시키는 것과 역할별 큰 표를 먼저 채우는 것은 다르다. 이 예시는 작성 내용과 기능 가용성이라는 핵심 구분에서 시작해, 필요한 코드가 등장하는 자리에서 역할과 연결을 보여 준다. 설명해야 할 대상이 이미 공유됐다면 같은 도입을 반복하지 않는다.

### 응답 예시 — 인증 만료 시의 관계를 묻는 브리핑

**예시 전제:** 보존된 당시 코드 설명을 사용한 부분 브리핑이다. 현재 Noline 코드나 인증 구조 전체를 검증한 답이 아니다.

> **핵심: 서버 인증이 만료돼도 같은 계정의 활성 여행은 계속 사용할 수 있어야 합니다.**
>
> 따라서 **현재 사용할 계정**과 **서버 요청을 시도할 인증 상태**를 구별합니다.
>
> **각 코드가 맡는 역할**
>
> | 코드 | 이 구조에서 맡는 일 |
> | --- | --- |
> | Auth Store | 앱이 사용할 계정과 인증 상태를 관리하고 화면·서비스가 같은 세션 판단을 사용하게 함 |
> | 인증 interceptor | 현재 세션의 인증 수단으로 서버 요청을 처리하고 인증 거절을 Store에 전달 |
> | `local-access` | 현재 계정·활성 여행 조건을 로컬 접근에 적용할 SQL 조건과 검증 함수 제공 |
> | Local 구현 | 해당 조건을 실제 데이터 조회·변경에 적용 |
>
> **A 계정의 토큰 갱신까지 거절되면**
>
> 1. interceptor가 인증 거절을 Store에 전달합니다.
> 2. Store는 계정 ID를 유지하고 인증 상태를 `reauth-required`로 바꿉니다.
> 3. 이후 로컬 접근은 유지된 계정과 활성 여행 조건을 사용하고, 보호된 서버 요청은 차단됩니다.
>
> | 대상 | 이 상태에서의 결과 |
> | --- | --- |
> | A의 활성 여행 로컬 작업 | 계정·활성 여행 조건을 충족하면 계속 가능 |
> | 보호된 서버 요청 | 서버 호출 전에 인증 조건으로 차단 |
>
> `local-access`가 계정 ID를 읽는 이유는 **SQL의 소유자 조건에 필요하기 때문**입니다. 별도의 인증 상태를 관리하는 것은 아닙니다. 서버 권한의 최종 판정은 서버가 맡으며, 위 역할 설명만으로 현재 파일 분리까지 최선이라고 판단할 수는 없습니다.

이 표는 “객체·함수 모음”이라는 구현 형태보다 전체에서 맡는 역할을 설명한다. 문단은 그 역할이 한 사건에서 어떻게 사용되는지 잇는다. 이는 관계를 묻는 부분 답변이며, 전체 코드 브리핑 요청에는 위 일정 예시처럼 필요한 구현도 연결한다. 이미 역할을 공유한 뒤 특정 한 줄을 묻는 경우에는 표와 전체 사건을 반복하지 않는다. 설명이 붙는다는 이유로 더 명료한 코드로 바꿀 여지를 닫지 않으며, 구조 품질 판단은01-02와 연결한다.

## access 질문: 변경 사실과 현재 판단을 구별하기

[원문](../source/noline-evaluation/corpus/01a0ec21-e59e-7370-8432-8434271aa669/messages.jsonl) 2757에서 사용자는 “근데 access 는 어디간거야?”라고 물었다. 2762는 훅 내부로 옮겼다는 답 뒤에 곧바로 “아래처럼 유지하겠습니다”라고 변경을 약속했다. 2769의 정정은 “아니 무조건 하란게 아니라 판단하라고”였다.

2774도 access 반환을 추천했지만 현재 화면과 다른 소비자의 조건, 다시 조합할 때 표시 규칙이 흩어질 비용을 설명했다. 추천 결론의 반전보다 판단 근거의 추가가 차이였다.2740에서 사용자는 우선 한 곳만 적용하라고 했으므로, 여러 소비자를 고려하는 설계와 이번 적용 범위도 구별해야 한다. 당시 의도와 현재 구조의 이득을 구별하며, 질문을 받았다는 사실만으로 변경을 실행하지 않는다.

### 응답 예시 — 위치 질문에 판단 요청의 맥락이 있는 경우

> **`access`는 훅 내부로 옮겼습니다. 앞서 논의한 소비자 범위를 유지한다면 다시 반환하는 편을 권합니다.**
>
> **현재 무엇이 바뀌었나**
>
> - 접근 조건은 훅 내부에서 사용합니다.
> - 화면에는 재조회 가능 여부만 `actions.canRefetch`로 제공합니다.
>
> **어떤 조건에서 필요한가**
>
> | 사용 조건 | 판단 | 이유 |
> | --- | --- | --- |
> | 현재 일정 목록처럼 표시 결과와 재조회만 필요 | 현재 구성도 충분 | `view`와 `canRefetch`로 처리 가능 |
> | 앞서 논의한 폼처럼 데이터를 직접 사용하고 접근 이유도 필요 | `access` 반환 권장 | 화면용 `view`를 해석하지 않고 조건·이유를 사용 가능 |
>
> **추천하는 구성**
>
> ```ts
> const { query, access, actions, view } = useSchedulesRead(tripId);
> ```
>
> | 반환값 | 맡는 역할 |
> | --- | --- |
> | `query` | 데이터와 조회 상태 |
> | `access` | 표시·조회 허용 여부와 제한 이유 |
> | `actions` | 조건을 확인하고 재조회 실행 |
> | `view` | 일반 화면에서 바로 사용할 표시 결과 |
>
> **비용과 적용 범위**
>
> - 화면마다 `query`와 `access`를 다시 조합하면 표시 규칙이 흩어질 수 있습니다. 일반 화면은 `view`를 쓰고 필요한 소비자만 직접 조합하도록 합니다.
> - 이 안에서는 `actions.canRefetch`를 없애되 `actions.refetch` 내부의 조건 확인은 유지합니다.
> - 적용은 요청한 일정 목록 한 곳에서 먼저 비교하는 범위입니다.

이 답은 당시 변경 이유를 새로 지어내지 않고 확인된 변경과 현재 추천을 설명한다. “앞으로 그런 소비자가 생길 수 있다”는 가능성만으로 현재 반환값을 늘리는 일반 규칙도 아니다. 여기서는 앞서 논의한 소비자 범위가 판단 조건이다.

| 같은 대상에 대한 다른 요청 | 수행할 대응 |
| --- | --- |
| “access가 정의된 파일 위치만 알려줘.” | 위치를 확인해 바로 답한다. 설계 비교·전체 briefing은 불필요하다. |
| “왜 내부로 옮겼어? 지금도 적절해?” | 보존된 이유와 현재 사용 조건을 대조해 판단한다. 이유를 찾지 못했다면 당시 의도는 미확인이라고 말한다. |
| “직접 쓰는 소비자는 이제 없어. 그래도 반환해야 해?” | 바뀐 조건으로 기존 선택을 다시 본다. 영향받는 결과와 후속 행동까지 달라지면 04-01의 재판단 책임에 연결한다. |
| “access를 다시 반환하도록 수정해줘.” | 명시된 변경 범위에서 구현·호출부·검증을 확인한다. 설명 스킬만 수행하고 멈추거나 의례적으로 다시 허락을 묻지 않는다. |

짧은 질문만으로 항상 전체 설계 재판단을 시작하지 않는다. 반대로 앞선 선택과 다른 소비자까지 묻는 맥락인데 단순 위치 답만 주는 것도 충분하지 않다.

### 역할을 설명해도 설계 적절성의 답이 남는 경우

여행 목록3962의 재브리핑 요청 뒤3977은 역할·코드·도식을 제시했다. 그런데4068에서 사용자는 “왜 그렇게 로직이 복잡해졌는지”, “왜 캔슬을하지? 안전한가?”를 물었다.4088의 응답은 목록 조회에 기기 사본 갱신을 함께 맡긴 선택, 덮어쓰면 안 되는 로컬 변경, 취소하는 조회와 이미 성공한 저장의 차이, 대안·비용을 설명했다.

이어4095·4127에서 사용자는 여행 목록만 기존 시스템과 다르게 조건을 조합하는 점을 물었고 수정을 요청했다.4120에서 AI는 기존 정책·조회 계약과 맞지 않는 조건 계산·캐시 분리 및 검증 누락을 보고했다. 이는 당시 AI의 코드 대조 보고이며 이번 검토가 제품 결함을 새로 재현한 것은 아니다.

이 장면에서 유지할 점은 “이 코드는 무엇을 보호한다”와 “이 책임을 여기 두는 것이 현재 시스템에 적절하다”를 구별하는 것이다. 이해 질문에 적절성·복잡성·안전성의 의문이 포함되면 해당 근거와 대안을 조사해 답한다. 설명 가능한 구조를 정당한 구조로 가정하거나, 설명 스킬이라는 이유로 판단을 다른 Ticket에 넘기고 답을 끝내지 않는다. 실제 수정과 더 넓은 품질 기준은 원래 요청·01-01·01-02·04-01의 책임과 연결한다.

## 설명 복구: 이미 이해한 부분을 유지하며 남은 차이를 좁히기

[Promise 원문](../source/noline-evaluation/corpus/01a0b4fc-3afa-7462-ae9e-6052b5a9e3c0/messages.jsonl)3504에서 사용자는 A·B 등록 연결은 이해하지만 오류 이후가 덜 이해된다고 했다.3509는 P1과 P2의 다른 결과를 설명했고,3528의 질문 뒤3533은 async/await과 반환·재던지기 비교를 제시했다.3545는 두 갈래로 표현했고,3576의 추가 질문 뒤3581은 빈 함수의 암묵적 반환을 설명했다. [인터뷰](../source/reading/noline-evaluation/reviews/interview-20261012.md)는 두 갈래 설명이 도움됐고 혼동을 더 빨리 짚을 여지도 있었다고 보았지만, 전체 성공·실패 평가는 유보했다.

### 응답 예시 — 3528의 남은 혼동에 답하기

> **P1은 실패한 채로 남고, catch 콜백이 정상 반환해서 별도의 P2가 성공합니다.**
>
> P2 뒤에 다음 작업이 연결된다는 부분은 이해됐다고 했으니, 오류를 받은 뒤 두 Promise의 결과가 어떻게 달라지는지 보겠습니다.
>
> **코드에서 두 대상을 구분하면**
>
> ```ts
> const result = pendingWrites.then(() => operation()); // P1
> pendingWrites = result.catch(() => undefined);        // P2
> return result;                                       // 호출자에게는 P1
> ```
>
> | Promise | 누가 사용하는가 | 작업이 실패했을 때 |
> | --- | --- | --- |
> | P1: `result` | 현재 작업의 호출자 | 실패 유지. 기다리는 호출자는 오류를 받음 |
> | P2: 새 `pendingWrites` | 다음 작업 | catch의 정상 반환으로 성공. 다음 작업을 시작할 수 있음 |
>
> **P2가 성공하는 기준은 catch 콜백의 종료 방식입니다.**
>
> | catch 콜백의 동작 | P2의 결과 |
> | --- | --- |
> | `return undefined` | 성공 |
> | 아무것도 반환하지 않고 정상 종료 | 암묵적으로 `undefined`를 반환하므로 성공 |
> | 오류를 다시 던지거나 실패한 Promise를 반환 | 실패 |
>
> `undefined`가 오류를 없애는 특별한 값은 아닙니다. 여기서 “오류가 나도 이어진다”는 말은 **다음 작업이 사용하는 P2의 흐름**을 뜻합니다. 현재 작업의 호출자에게 오류가 전달되지 않는다는 뜻은 아닙니다.

예시 코드는 당시3487·3521의 핵심 세 줄에 P1/P2 대응을 붙였다. 뒤의3576에서 명확해진 `undefined`·빈 함수 구분을 앞선 질문에 넣어 본 설계 예시이므로,3528에서 그 혼동까지 확정적으로 알 수 있었다고 주장하지 않는다. 당시3533도 정상 반환과 재던지기 차이를 설명했다. 이 새 답이 더 빠른 이해를 만들지는 미확인이다.

**앞선 주장이 틀렸다면:** 인증 장면의 “이전 설명에는 동작만 있었다”를 다시 설명해 정당화하지 않는다. “앞선 설명에도 Store의 수락 조건·저장·상태 반영 역할이 있었다. 역할이 없었다는 비교는 틀렸다. 다만 사용자는 근본 역할을 이해한 상태로 동작을 읽을 수 있게 설명해 달라고 요청했다”처럼 확인된 사실과 요구를 먼저 복구한다. 부족 원인의 세부 해석을 다시 사용자 의도로 확정하지 않는다.

## 실제 본문을 고친다면 넣을 문구와 위치

아래 문구는 **기존 본문의 지정 위치를 교체하는 후보**다. 사용자 요청에 따라 교체 범위와 실제 넣을 문장을 구체화했다. 표시한 곳 외의 호출 조건·조사 절차·근거 구분·수정 권한·종료 조건은 유지한다. 사례는 이 문서에서 후보를 판단하는 데 사용하며 SKILL.md에 모두 넣지는 않는다. 실제 스킬 파일에는 적용하지 않았다. 후속 읽기 구성 정정에서는 위 응답 예시들을 핵심 답·역할·비교·코드·확인 범위가 구별되도록 다시 썼다. 기존의 주제 구분·관계에 맞는 형식 선택 기준을 적용한 것이며, 모든 응답에 표나 같은 목차를 의무화하는 규칙을 추가하지 않았다.

### work-artifact-briefing — 조사 기준을 구체화

`대상에 맞춰 조사한다 / 문서·분석·review 결과`의 기존 세 항목을 다음 네 항목으로 교체한다.

> - 어떤 질문과 기준을 대상으로 만든 산출물인지 확인한다. 이전 작업을 이어받았다면 기존 문제·이후 수정과 이번 확인의 관계를 대조한다.
> - 직접 확인한 finding, 작성자의 해석, 아직 확인하지 않은 범위와 후속 판단을 구분한다. 현재 코드·검사·설정이 답을 바꾸면 실제 담당 구현까지 확인한다.
> - 현재 답이나 다음 판단을 바꾸는 미확인이 있고 기존 권한·범위 안에서 확인할 수 있으면 관련 근거를 더 조사한다. 확인할 수 없으면 이유와 결론의 제한을 밝힌다. 설명 요청만으로 새 제품 검사나 전체 review를 맡지는 않는다.
> - 결과가 원래 질문에 어떤 답을 주며 무엇을 유지·변경·유보하게 하는지 설명한다. 조사한 항목을 그대로 나열하는 것으로 결과 설명을 대신하지 않는다.

### work-artifact-briefing — 역할과 결과를 연결하는 출력 기준

`실제 결과`의 첫 문단을 다음 세 문단으로 교체한다. 바로 뒤의 대표 장면·설명용 값·근거 지위·중요 조건 비교 문단은 유지한다.

> 결론과 작업물의 전체 역할을 먼저 보여 준다. 코드 구조·변경을 설명할 때는 전체를 이해할 핵심 구분과 중요한 코드의 근본 역할을 먼저 잡는다. 그 코드가 전체에서 무엇을 맡고 왜 필요한지 설명한 뒤 실제 동작으로 잇는다. 객체·함수 같은 구현 형태나 메서드의 동작 목록만으로 역할 설명을 대신하지 않는다. 이미 공유한 역할을 반복하거나 모든 파일의 책임 표를 먼저 만들지는 않는다.
>
> 역할과 연결을 이해하는 데 필요한 실제 코드 부분을 골라 조건·값·호출이 어떤 책임을 구현하는지 보여 준다. 화면·로직의 흐름을 묻는다면 대표 장면에서 그 코드들이 어떻게 연결되는지 함께 설명한다. 구체적 코드나 도식을 요청했다면 추상 설명·역할 표만으로 대신하지 않는다. 도식의 관계와 근거는 아래 구조 표현 기준을 따른다.
>
> 중요한 이름은 처음 쓰는 자리에서 실제 데이터나 책임에 연결하고, 기존 file·symbol과 정확한 위치를 남긴다. 중요한 주장에는 확인한 근거를 가까이 두며 필요한 상세를 펼친다. 내용의 연결을 유지하면서 독립적으로 찾아야 할 주제·조건은 문단·표·목록 등으로 구분한다.

`실제 결과`의 “다음 변경이나 선택을 위한 브리핑이면”으로 시작하는 문단을 다음 두 문단으로 교체한다.

> 다음 변경·선택을 위한 브리핑이거나 기존 선택의 이유·복잡성·적절성을 묻는 질문이면, 실제 변경 사실과 확인 가능한 당시 이유, 현재 조건에서의 판단을 구별해 답한다. 질문에 필요한 기존 계약·소비자·대안·비용을 대조해 무엇을 유지하거나 바꿀지 추천한다. 당시 이유는 보존된 근거로 확인할 수 있을 때만 말하고 현재 해석과 구분한다. 역할을 설명할 수 있다는 이유로 현재 구조를 정당화하지 않는다.
>
> 질문만으로 수정·복원을 약속하지 않는다. 명시된 변경 요청이나 기존 실행 권한이 있으면 그 범위에 따라 이어간다. 모든 구조의 장단점·선택 이력을 기본 조사하거나 일반 동작 설명을 전체 architecture review로 확대하지 않는다.

### explanation-recovery — 남은 혼동을 다음 설명의 입력으로 사용

`무엇이 끊겼는지 찾는다`의 “다음 중 실제 원인을 고른다.”를 다음 문단으로 교체한다. 기존 원인 후보 목록과 필요할 때만 질문하는 조건은 유지한다.

> 실제 발화에서 사용자가 이해했다고 밝힌 부분과 아직 묻는 부분을 구별하고, 다음 목록에서 끊긴 연결의 후보를 찾는다. 추가 질문만으로 앞선 설명의 실패나 사용자의 혼동 원인을 확정하지 않는다. 앞선 AI의 자기해석도 사용자 발화와 대조하며, 불확실한 원인을 확인된 사실처럼 말하지 않는다.

`작은 복구에서 시작한다`의3번을 다음 항목으로 교체한다. 나머지 번호와 뒤의 오류·정정 문단은 유지한다.

> 3. 사용자가 이미 이해한 표현과 현재 유효한 Project 용어에서 시작하고, 아직 묻는 차이에 다음 답의 범위를 맞춘다. 같은 표현으로 연결되지 않으면 실제 코드·값·대상 간 대응이나 필요한 사례로 표현을 바꾼다. 앞선 답에서 이미 바꾼 설명과 새로 드러난 질문도 확인한다.

`하지 않을 것`의 Quiz 항목은 다음으로 교체한다.

> - Quiz, 자기 말로 다시 말하기나 형식적 승인을 기본 종료 조건으로 요구하지 않는다. 사용자가 질문식 학습을 요청하면 그 방식으로 돕되, 이후 직접 설명·코드·다른 방식으로 전환하라는 요청을 따른다.

직접 답·대화 우선·조건부 source 확인·원뜻과 타당성 구별·부작용 경계·종료 조건은 유지한다. “이해했다”는 사용자 발화는 그 시점의 다음 답을 조정하는 입력이지 영구 이해 상태가 아니다.

### 첫 보고 — 01-01에 전달할 기준 후보

> 맡은 작업을 보고할 때는 만든 파일이나 수행 목록만으로 결과를 대신하지 않는다. 원래 요구에 대해 무엇이 달라졌고 어떤 확인이 그 결론을 지지하는지, 남은 일이 결론이나 다음 행동을 어떻게 제한하는지 설명한다. 필요한 확인을 할 수 있는데도 미확인이라고 적는 것으로 수행을 끝내지 않는다. 확인을 넓힐지는 현재 판단에 미치는 영향과 맡은 범위·실행 가능성으로 정한다.

이것을 두 설명 스킬의 공통 자동 호출 조건으로 추가하지 않는다. 작업 수행·검토·최종 보고의 실제 인수 관계는 01-01이 소유하고, 04-02는 이 기준이 어떤 설명으로 드러날지와 스킬이 필요한 조건을 제시한다.

## 선택의 비용, 다른 안, 확인할 것

**권하는 안은 기존 본문 일부의 구체화와 선택적으로 읽는 대비 사례다.** 본문을 그대로 두고 사례만 붙이면 공통 행동을 사례에서 매번 추론해야 한다. 반대로 본문을 전면 재작성하거나 고정 보고 서식으로 만들면 이미 있는 사실성·권한·종료 경계를 잃거나 단순 질문까지 무거워질 수 있다. 현재 근거로는 스킬 합치기·새 자동 호출·별도 이해 기록을 추가할 이점이 충분하지 않다.

| 조건 | 이 안의 행동과 비용 |
| --- | --- |
| 역할·조건을 공유한 뒤 한 값·위치를 묻는다 | 직접 답한다. 전체 브리핑·다이어그램·history 조사는 생략한다. |
| 전체 구조를 처음 이해하려 한다 | 핵심 구분과 근본 역할을 먼저 잡고 필요한 코드·대표 흐름을 연결한다. 초기 설명량은 늘 수 있지만 동일한 역할 정의를 여러 절에 반복하지 않는다. |
| 다음 행동을 바꿀 미확인이 있다 | 관련 근거를 더 확인한다. 조사 비용이 늘 수 있으며, 새 범위·권한·접근 제약은 해당 결론 가까이 드러낸다. |
| 중요한 조건은 모두 확인했지만 취향·제품 선택이 남았다 | 끝없는 조사로 사람의 선택을 대신하지 않고 대안과 추천을 제시한다. |
| 질문이 설명·이의 제기·수정 요청을 함께 담는다 | 필요한 설명과 정정은 답하고, 명시된 변경은 원래 작업 범위에서 수행한다. 해석에 따라 행동이 달라지는 불명확성만 확인한다. |

다음 확인은 문구 선호보다 실제 출력 차이를 본다. 원자료와 요청을 같은 범위로 준 뒤 현행안과 보완안이 만든 응답에서 질문의 답, 근거 상한, 역할·동작 연결, 필요한 후속 행동과 비적용 조건을 대조한다. 실제 사용자에게는 이해가 쉬운지와 설명량·구조가 적절한지를 구체 응답으로 판단받는다. 후속 질문 횟수·침묵·커밋 요청만으로 성공을 판정하지 않는다.

이 문서에서는 과거 원문 대조와 응답·본문 문구의 설계, 사용자 정정에 따른 재대조까지 수행했다. 새 스킬을 통한 별도 실행 비교, 제품 동작 검증, 실제 사용자 수용·효과 확인은 수행하지 않았다.04-02는 **원문 재대조를 반영한 보완안 검토 중**이며 완료로 닫지 않는다.

### 작성 뒤 대조

첫 제안 당시 별도 검토자가 사실 지위·역할·조사와 수정 권한·요구 충족을 대조했다. 최초 인증 예시의 “로컬 접근 함수는 … A의 데이터를 조회”가 `local-access`의 조건 생성과 Local 구현의 실제 조회를 섞는다는 지적을 받아 수정했다. 당시 검토자는 그 밖의 실질 수정 사항을 보고하지 않았지만, 이후 사용자 지적으로 역할 우선의 누락과 이번 재대조 사항을 확인했다. 첫 검토를 현재 보완안의 독립 검증이나 해석 완전성의 증거로 쓰지 않는다. 이번 재대조는 Main이 수행했다.

Main은 제안·04-02·output의 로컬 링크 대상과 변경 문서의 공백 오류를 확인했다. 이는 문서 연결과 원자료 대조의 결과이며 제품 코드 검증·보완 스킬의 실행 비교·사용자 이해 효과를 대신하지 않는다. 이 대조 결과로 설계안의 채택이나 Ticket 완료를 확정하지 않았다.
