# 알림 설정 사례 — Project·작업 정의와 구현·검토 인수 예시

2026-10-13. 사용자는 다음과 같이 요청했다.

> 그럼 두 번째 안으로 가정하고, 알림 설정 사례에서 구현자랑 검토자한테 실제로 뭘 넘기는지 보여줘. Project에 둘 내용이랑 그 작업의 Spec·Ticket에 둘 내용도 같이 구분해줘.

이번 사례에서는 **상세 품질 기준을 검토자에게 집중하는 안**을 가정한다. 전체 시스템에 대한 최종 채택이 아니다. 아래 Spec·Ticket은 014 자체의 작업 정의가 아니라 **가상 개발 Project 안에서 알림 설정을 개발하는 Work의 예시**다. 실제 기능 개발이나 검증은 수행하지 않았다.

## 예시를 성립시키는 가정

가상 제품에는 로그인한 사용자가 자신의 ‘댓글 알림 받기’ 값을 조회·저장하는 서버 기능이 이미 있고, 화면에는 조회만 연결돼 있다고 가정한다. 이번 작업은 화면에서 값을 바꾸고 저장하는 흐름을 완성하는 것이다. 실제 알림 발송 기능은 변경하지 않는다.

또한 테스트 앱 실행·테스트 사용자 로그인·서버 저장 거절 재현 방법이 개발 환경에 있다고 가정한다. 실제 프로젝트에서 이런 수단이 없으면 Main과 실행자가 필요한 준비를 확인해 작업 범위에 반영해야 한다. 존재하지 않는 수단을 있다고 보고 인수하거나 완료 처리하지 않는다. 실제 파일 경로·명령·커밋 값은 이 예시에서 만들지 않았다.

## Project가 계속 소유할 내용

다음은 파일 이름이 아니라 내용의 소유 위치다. 기존 canonical에 해당 내용이 있으면 그곳을 사용한다. 이 한 작업에 쓸 내용만 보여주는 것이며 Project context의 전체 범위를 제한하지 않는다.

| 내용 | 이 사례의 본문 예시 | 기본 소비자 |
| --- | --- | --- |
| 제품 의미 | ‘댓글 알림 받기’는 로그인한 사용자 계정의 설정이다. 이 값은 해당 사용자의 댓글 알림 수신 여부를 나타내며, 다른 사용자의 설정은 바꾸지 않는다. | Main·구현자·검토자 |
| 현재 구조와 계약 | 설정 조회·저장은 기존 서버 기능을 사용한다. 현재 화면은 조회 결과를 표시한다. 사용자 식별·권한 확인과 기존 요청·응답 형식은 관련 코드/API 계약에서 확인한다. | 구현자·검토자 |
| 개발·실제 확인 방법 | 테스트 앱을 실행하고 테스트 사용자로 로그인한 뒤 ‘설정 → 알림’으로 진입한다. 저장을 서버가 거절하는 상태의 재현·해제 방법, 관련 자동 검사 실행 방법을 제공한다. 실제 가이드에는 확인된 명령과 준비 조건이 들어가야 한다. | 구현자·검토자 |
| 상세 품질 판단 | 저장 처리를 위해 화면이 알아야 할 순서·오류·설정이 과도한가? 모듈을 나눴을 때 호출자의 부담이 실제로 줄었는가? 테스트가 저장 결과를 확인하는가, 내부 함수 호출 순서만 확인하는가? | 이 안에서는 검토자가 기본으로 읽는다. 필요한 구현자의 참조를 금지하지 않는다. |

품질 판단의 소유자가 이미 별도 공통 기준이라면 Project에는 적용 관계와 필요한 차이만 둔다. 같은 기준을 Project·Spec·Ticket·스킬에 각각 복제하지 않는다. ‘상세 기준을 기본 입력으로 넣지 않는다’는 것은 구현자가 나쁜 코드를 작성해도 된다는 뜻이 아니다. 필수 계약·타입·자동 검사와 관련 코드의 의미는 구현 때부터 사용한다.

## 이 개발 작업의 Spec 예시

**목표:** 사용자가 댓글 알림 설정을 직접 바꾸고 저장할 수 있다.

**원하는 동작:**

1. 알림 화면에서 현재 저장값을 확인하고 값을 바꿀 수 있다.
2. 저장 성공을 확인한 뒤 완료를 표시한다. 화면을 닫고 다시 열면 저장한 값이 보인다.
3. 서버가 저장을 명시적으로 거절하면 이전 서버 저장값은 유지한다. 화면에는 사용자가 바꾼 값과 오류를 남겨 재시도할 수 있게 한다.

**범위:** 명시적인 저장 조작으로 처리한다. 자동 저장, 알림 발송 방식, 기존 저장 형식과 권한 체계는 변경하지 않는다.

**완료 근거:** 위 세 동작을 자동 검사와 실제 앱에서 확인하고, 검사한 변경 상태·환경·결과·확인하지 못한 부분을 구별한다. 화면 테스트에서 저장 응답을 대체했다면 실제 서버 저장까지 확인한 근거로 쓰지 않는다.

**남겨 둔 선택:** 통신 중단으로 저장 성공 여부를 알 수 없는 경우는 ‘서버가 거절한 경우’와 다르다. 기존 제품 정책을 먼저 확인하고, 없다면 Main이 제품 동작을 정리한다. 내부 함수·모듈의 이름과 분할은 구현·검토 중 발전시킬 수 있다.

제품의 공통 의미와 API 계약은 Project를 참조한다. 이번 결과와 제외 범위는 이 Spec이 소유한다. 나중에 해당 동작이 실제 제품 상태가 되면 필요한 공통 설명을 Project에서 갱신하고, Work에는 선택 경위와 검증 근거를 남긴다.

## 이 개발 작업의 Ticket 예시

**맡은 결과:** 알림 설정의 편집·저장·실패 후 재시도를 기존 서버 기능과 연결하고, 검토·수정·실제 확인까지 마친 결과를 Main에게 반환한다.

**입력:** 위 Spec의 동작·제외 범위·완료 근거, Project의 제품 의미·설정 계약·실행 가이드, 실제 작업 위치와 비교 기준 커밋.

**진행:** 구현자가 기능과 동작 검사를 만들고 초기 확인을 한다. 같은 Ticket의 결과를 검토자가 인수해 품질 검토·직접 수정·최종 실제 확인을 한다. Main은 남은 제품 선택과 완료 여부를 판단한다. 구현과 검토를 위해 별도 Ticket 두 개를 만드는 것을 전제하지 않는다.

**기록:** 현재 맡은 주체와 단계, 변경 위치, 초기·최종 확인 근거, 남은 문제를 연결한다. Spec의 요구를 통째로 반복하거나 검토자의 상세 기준을 여기 복제하지 않는다. 이 작은 작업에서 Spec·Ticket을 별도 파일로 둘지는 아직 정하지 않았으며, 여기서는 내용의 역할을 나눠 보여준다.

## Main이 구현자에게 넘길 요청문

아래 ‘Spec’, ‘Ticket’, ‘Project’ 참조는 위 예시의 해당 본문을 가리킨다. 실제 위임 시 Main은 확인한 파일 경로와 작업 위치·비교 기준을 넣는다. 링크만 주고 필요한 내용이 비어 있는 상태로 넘기지는 않는다.

> 이 Ticket의 알림 설정 편집·저장 기능을 구현해 주세요.
>
> 먼저 작업 Spec의 목표·동작·제외 범위와 Project의 알림 의미, 기존 설정 계약, 실행 가이드를 확인하세요. 로그인한 사용자의 기존 저장 기능을 사용하고, 저장 형식과 권한 체계는 유지하세요.
>
> 화면에서 값을 바꿔 저장하고, 성공 후 재진입하면 저장값이 보이게 하세요. 서버가 저장을 거절하면 입력값과 오류를 남겨 다시 시도할 수 있게 하세요. 이 동작들을 확인하는 자동 검사를 추가하거나 보완하고 초기 실행 확인도 하세요. 내부 구조는 관련 코드를 확인해 판단하세요.
>
> 기존 계약만으로 요구를 충족할 수 없거나, 통신 중단 때의 제품 동작이 정해져 있지 않다면 발견한 사실·영향·추천을 Main에게 돌려주세요. 단순한 내부 함수 분할은 직접 판단해 진행할 수 있습니다.
>
> 반환할 것은 변경된 코드와 검사, 주요 구현 판단, 실행한 확인의 명령·환경·결과와 미확인 항목입니다. 검토자가 같은 작업 상태를 식별할 수 있도록 기준 대비 변경 범위와 미커밋 변경도 명시하세요. 실행하지 않은 확인을 완료로 쓰지 마세요.

여기에 깊은 모듈의 전체 설명과 품질 체크리스트를 기본 입력으로 추가하지 않는다. 구현자의 반환은 초기 구현 결과이며 Ticket 전체의 최종 완료와 구별한다.

## 검토자에게 넘길 요청문

검토자는 **같은 Spec·Ticket과 Project 맥락**, **실제 초기 구현의 변경 상태**, **초기 확인 근거·남은 문제**, **상세 품질 기준**을 받는다. 구현자의 설명은 탐색을 돕는 입력이며 실제 코드와 결과의 검증을 대신하지 않는다. 초기 확인 결과는 아직 없으므로 이 문서에 통과한 것처럼 채우지 않았다.

> 이 Ticket의 초기 구현을 검토하고 필요한 품질 수정을 직접 해 주세요. 수정 후 최종 실제 확인까지 맡습니다.
>
> 먼저 Spec의 요구와 Project의 설정 계약을 기준으로 코드를 확인하세요. 구현자가 제출한 검사 결과도 읽되, 요구 충족과 테스트의 충분함은 직접 판단하세요. Project에서 연결한 상세 품질 기준을 이번 변경에 적용하세요.
>
> 특히 화면이 검증·저장·오류 변환의 세부 순서를 모두 알아야 하는지, 책임을 모았을 때 호출자의 부담이 줄어드는지 살펴보세요. 테스트가 결과를 확인하는지, 구현 내부의 함수 호출만 확인하는지도 보세요. 문제를 발견하면 맡은 결과와 관련된 코드·테스트를 직접 개선하세요. 함수나 파일을 나누는 것 자체를 목표로 삼지는 마세요.
>
> 기존 제품 동작·권한·저장 계약을 유지하는 내부 구조 변경은 직접 할 수 있습니다. 저장 형식 변경, 자동 저장 도입, 오류 때 입력값을 버리는 동작처럼 합의된 결과·범위가 달라지는 변경은 Main에게 근거와 대안을 돌려주세요.
>
> 수정한 최종 상태에서 관련 자동 검사를 다시 실행하고, 실제 앱에서 저장 성공·서버 거절·재시도·재진입을 확인하세요. 확인 수단이 없거나 실제 서버까지 확인하지 못했다면 그 한계를 남기고 Main에게 반환하세요.
>
> 반환할 것은 개선된 코드·검사, 중요한 변경 이유, 최종 상태에 대응하는 실제 확인 근거와 남은 판단입니다. 지적 목록만 반환하는 것으로 맡은 검토를 끝내지 마세요.

## 검토에서 실제로 구조가 달라진다면

가령 초기 구현의 화면 코드가 입력 검증·저장 요청·서버 오류 변환을 모두 조합한다고 가정하자. 검토자는 저장 처리를 맡는 모듈에 그 책임을 모아 화면은 입력과 결과 표시를 맡도록 바꿀 수 있다. 이것이 항상 좋은 구조라는 결론은 아니며, 실제로 호출자가 알아야 할 순서·오류 처리가 줄고 테스트가 관찰할 동작이 분명해질 때의 예다.

- Spec의 저장 동작이 그대로라면 Spec을 코드 구조 설명으로 다시 쓰지 않는다.
- Ticket에는 최종 변경·확인 위치와 현재 결과를 연결한다. 구조를 택한 이유·비교했던 대안·시도는 후일 검토 가치에 따라 Work 기록에 남긴다.
- Project의 현재 구조 안내가 낡았다면 Main이 해당 공통 설명의 갱신을 챙긴다. 검토자의 추천을 곧바로 모든 개발에 적용할 새 품질 기준으로 만들지는 않는다.
- Main은 검토자가 반환한 근거와 미확인을 보고 완료 여부 및 사람에게 필요한 선택을 정리한다. Main이 같은 실제 검증을 반드시 다시 수행하는 절차를 추가하지 않는다.

## 이번 예시에서 구체화된 관계와 한계

Project는 공통 제품 의미·현재 계약·찾고 실행하는 방법을 제공한다. 작업 Spec은 이번 변화의 결과·범위·완료 근거를, Ticket은 그 결과를 수행하는 입력·담당·진행·증거 연결을 맡는다. 역할별 요청문은 그 내용을 복제하는 새 정본이 아니라 이번 담당의 행동과 반환을 지시한다.

이 예시는 01-01의 인수·수정 책임, 01-02의 상세 기준 소비, 01-03의 실제 확인 수단, 02의 기록 역할, 03의 공통 맥락을 같은 작업에 대입한 것이다. 실제 Project 본문과 도구의 충분함을 검증하거나 각 Ticket을 완료한 것은 아니다. 문서 파일 배치·스킬 형식·도구 구현·상세 기준의 최종 채택은 계속 설계할 대상이다.
