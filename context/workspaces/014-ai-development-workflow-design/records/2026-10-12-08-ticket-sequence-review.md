# Ticket의 순서·크기·구체성 검토

이 문서는 당시 검토 제안을 보존한다. 과제 표기는 현재 상위 Ticket 번호로 정리했으며 제안의 채택 강도는 바꾸지 않았다. 이후 실제 분할은 [분할 기록](2026-10-12-09-ticket-split.md)에 있다.

2026-10-12 사용자 요청: “그럼 티켓의 순서와 조금 더 구체화? 뭐라해야지 적절한지? 그리고 더 필요하거나 아니면 수정할게 있는지 좀 볼까?”

**판단: 일곱 영역은 유지할 가치가 있지만, 실제 논의를 시작하려면 큰 Ticket을 나누고 처음 보여 줄 결과를 정하는 편이 좋다.** 특히 01·04는 이미 여러 독립적인 판단을 담고 있어 추가 분해를 나중까지 미룰 이유가 적다. 새 대주제를 늘리기보다 각 결과의 구체성과 연결을 먼저 보완한다.

아래는 Main의 검토 제안이다. 사용자와 논의할 순서·분할이며 채택된 작업 순서나 개발 운영 방식이 아니다. 이번에는 Ticket 본문의 범위·완료 조건을 바꾸거나 설계안을 실행하지 않았다. 앞선 검토가 원문과의 정합성과 범위 보존을 봤다면, 이번에는 실제 설계 대화를 진행할 수 있는 크기와 결과를 봤다.

## 제안하는 논의 순서

한 Ticket을 완결해야 다음 Ticket을 시작하는 순서가 아니다. 표의 순서는 각 결과를 먼저 구체화할 때의 추천이며, 앞선 가정이 바뀌면 관련 결과도 보완한다.

| 먼저 다룰 순서 | 기존 Ticket과 범위 | 처음 보여 줄 결과와 다음 판단 |
| --- | --- | --- |
| 1 | 01의 대표 작업 진행 초안. 관련 04 스킬과 07 사례를 함께 확인 | 개발 장면 하나에서 목표·조사·설계·검토·사람의 판단·보고·기록이 어떻게 이어지는지 펼친다. 각 부분에서 필요한 맥락과 아직 선택하지 않은 방법이 드러나면 02·03로 이어갈 수 있다. |
| 2 | 02 기록·재개·Maintain | 실제 기록의 현재 내용과 보완 예시를 비교한다. 재개에 쓸 내용과 후일 돌아볼 내용을 각각 고르고, 보존·열람·적용 중 무엇을 보완하는지 판단한다. |
| 3 | 03 Project context | 제품 설명, 현재 구조, 변경 가이드처럼 역할이 다른 문서의 본문 예시와 사용 장면을 만든다. 필요한 내용·읽기·갱신의 관계를 비교한다. |
| 4 | 01의 설계 품질·검증 방법을 따로 구체화하고 진행안 보완 | 코드 설계의 대비안, 실제 동작을 확인할 근거와 도구 선택을 각각 검토한다. 구현·검토·수정·첫 보고의 연결을 다시 맞춘다. |
| 5 | 04 기존 스킬의 구체 보완과 연결 정리 | 앞의 논의에서 다룬 관련 스킬을 모아 유지·구체화·통합·제외의 이유와 본문·동작 예시를 비교한다. 스킬 전체를 이때 처음 읽는다는 뜻은 아니다. |
| 6 | 05 경험 반영 루프 | 반복 교정 하나와 필요한 사람의 질문 같은 대비 사례에서, 기록→문제 해석→유지/보완 후보→필요한 사람 판단→다음 관찰을 보여 준다. |
| 7 | 06의 변경 배치·전환안과 07의 전체 연결·적용 계획 | 관련 설계 결과를 어느 공통 기준·프로젝트 내용·스킬·도구에 반영할지 정리하고, 연결 검토를 거쳐 우선 적용 후보와 확인할 효과를 제안한다. |

**기존 02 우선 후보를 조정하는 이유:** 기록 사례부터 시작하기 쉽다는 장점은 여전히 있다. 그러나 지금은 전체 체계를 설계하려는 요청이므로, 먼저 실제 개발 작업에서 필요한 정보와 판단을 드러내면 기록·Project를 그 사용 목적과 함께 논의할 수 있다. 01 전체를 먼저 완성하자는 제안은 아니다. 문서 설계만 먼저 고정하는 부담과, 모든 개발 방법을 먼저 확정하는 부담을 함께 줄이려는 선택이다.

04의 현행 스킬 대조, 06의 기존 결합 확인, 07의 부분 연결 검토는 처음부터 필요한 만큼 사용한다. 05에서 다룰 개선 경험도 각 부분에서 후보로 남길 수 있다. 이들을 표의 후반까지 전부 미루면 앞선 설계가 기존 구성과 어긋날 수 있다. 반대로 모든 관련 작업을 동시에 열어 놓을 필요도 없다.

## 01·04는 검토할 결과를 나눈다

기존 Ticket 번호는 유지하고 다음을 하위 결과 후보로 제안한다. 새 파일을 몇 개 만들지는 이 분할을 논의한 뒤 정해도 된다. 결과 분할을 별도 agent 수나 고정 호출 순서로 해석하지 않는다.

| Ticket | 따로 검토할 결과 | 다른 결과와의 경계 |
| --- | --- | --- |
| 01 | **작업 진행과 사람의 판단**: 목표·Spec·Ticket에서 조사·설계·구현·검토·수정·첫 보고로 이어지는 안 | 필요한 품질·검증 결과를 연결하고, 누가 어떤 근거로 진행·재검토·보류하는지 다룬다. 처음에는 전체 연결 초안을 만들고 아래 두 결과로 보완한다. |
| 01 | **코드·설계 품질을 다루는 방법**: 책임·인터페이스·변경 부담을 실제 전후 또는 대비안으로 판단 | 단순히 reviewer를 추가하는 것으로 완료하지 않는다. 호출자가 알아야 할 지식·순서·오류 부담, 변경이 흩어지는 정도와 사용자에게 필요한 이해를 비교한다. |
| 01 | **동작 검증과 도구 선택**: 사용자 장면에서 필요한 증거, 자동 검사와 실제 앱 관찰의 역할 | 테스트가 실제 요구와 실패를 검출하는지, 앱 제어·Feature Map·기존 실행 도구·Verify가 무엇을 제공하는지 비교한다. 새 CLI 구현을 미리 결과로 정하지 않는다. |
| 04 | **작업 정의·재판단**: work-discussion, reconsider-work | 01이 일반 작업 방법을 맡고, 이 결과는 실제 스킬의 발동 조건·입력·행동·결과·기록 연결을 맡는다. 같은 사례와 근거를 다시 수집하지 않는다. |
| 04 | **작업물 이해·브리핑·설명 복구**: work-artifact-briefing, explanation-recovery | 첫 보고의 책임과 요청에 따른 추가 설명을 구별한다. 질문에 설명할 때, 기존 선택을 재검토할 때, 실제로 바꿀 때의 차이를 보여 준다. |
| 04 | **맥락 읽기·갱신·Workspace 생성**: read/update-project-context, create-context-workspace | 02·03의 내용·관리 설계와 06의 전환에 붙여 보완한다. 문서의 정본 책임을 스킬에 복제하지 않는다. |

04는 공통 책임 대조를 일찍 하고, 해당 주제를 논의할 때 구체안을 함께 만든 뒤 전체 연결을 확인하는 편을 추천한다. 현행 스킬 이름마다 하나의 Ticket을 만들면 기존 분할을 고정하고 중복을 늘릴 수 있다.

02·03·05·06·07은 지금 추가 분리가 반드시 필요하다는 근거가 부족하다. 다만 02에서는 **충분히 보존했는가**와 **읽고 적절히 사용했는가**를 각각 확인해야 한다. 03는 전면 문서 개편이 아니라 역할이 다른 본문과 소비 장면부터, 05는 경험 후보 하나를 끝까지 따라가는 예시부터 만들면 논의할 크기를 제한할 수 있다. 크기를 제한한다는 이유로 해당 Ticket의 전체 범위를 축소하지 않는다.

## 더 분명하게 만들 것

다음은 완전히 없던 주제를 추가하는 제안이 아니다. 현재 Spec과 Ticket에 대부분 들어 있지만, 실제 비교 결과에서 드러나도록 보완할 항목이다.

- **사람의 판단과 AI 검토의 종료:** 중요한 제품 선택·학습 질문·기대 기준의 반복 교정을 구별한다. AI가 스스로 더 확인할 때, 판단 가능한 결과를 제시할 때, 사람의 선택이나 추가 관찰이 필요한 때를 사례로 비교한다. 모든 사람 개입의 제거 또는 무한 검토를 목표로 만들지 않는다. 01의 진행안이 연결을, 04가 구체 대응을, 05가 기준 발전을 맡을 수 있다.
- **실제 선택을 바꾸는 결과물:** 각 부분에서 현재 방식, 구체적인 보완 예시, 달라지는 행동과 비용, 남은 선택을 보여 준다. 파일 목록이나 원칙 목록이 늘어난 것만으로 충분하다고 하지 않는다. 설계 품질의 경우 실제 코드·구조의 대비가 필요하고, 설명의 경우 같은 결과를 어떻게 이해·판단할 수 있게 할지 비교한다.
- **작은 작업에서의 비용:** 작은 변경에서도 전체 문서 읽기·별도 리뷰·인터뷰·기록·회고가 모두 필수가 되는지 살핀다. 모델·맥락·도구·사람의 읽기 부담을 함께 비교하되 측정하지 않은 절감 수치를 만들지 않는다. 새 장치보다 기존 내용·검사·도구의 연결 보완이 충분한지도 확인한다.
- **다른 Ticket에 미치는 선택:** 예를 들어 reviewer에게 읽힐 품질 기준을 바꾸면 03의 문서, 04의 읽기, 06의 배치가 함께 영향을 받는다. 각 결과에 그 영향과 미정을 표시하고, 07에서 함께 대조한다. 별도 관리 시스템이나 중복 상태표를 만들 필요는 없다.

지금은 첫 결과·의존 관계·논의할 차이를 구체화한다. 최종 agent 수, 모든 호출 문구, 전체 문서 목차, 상세 도구 명령, 모든 후속 Ticket의 세부 절차까지 고정하면 아직 보지 않은 설계를 선결할 위험이 있다.

## 첫 논의에서 보여 줄 구체적인 예

후보는 Noline의 **여행 조회·네트워크 복구에서 구조와 동작을 함께 검토했던 작업 일부**다. [철회·후속 구현 비교](../source/reading/noline-evaluation/reviews/withdrawal-followup-comparison.md)에 실제 선택과 구현 차이가 보존돼 있다. 가독성이라는 Spec 명칭만으로 동작 개선 전체를 무단 확대라고 판단하지 않아야 한다는 사실도 이 사례에 포함된다. 철회 이유의 단일 원인은 여전히 확정하지 않는다.

이 사례에서 처음 만들 결과는 다음 관계가 보이는 짧은 진행 초안이다.

1. 원하는 결과와 유지할 동작, 아직 정하지 않은 선택은 무엇인가.
2. 어떤 Project·Work 맥락과 실제 근거를 읽어야 조사·설계를 할 수 있는가.
3. AI가 스스로 판단할 부분과 사용자에게 결과·대안을 제시할 지점은 어디인가.
4. 설계 품질·검사·앱 동작을 무엇으로 확인하고, 첫 보고와 기록에는 무엇을 연결할 것인가.

처음부터 최종 운영안을 선택하기보다, 이 결과를 보고 02·03과 01의 세부 설계에서 풀 질문이 구체적이면 다음 논의로 이어갈 수 있다. 복잡한 과거 장면 하나가 모든 작업의 표준이 되지 않도록, 작은 변경의 비교 장면도 필요할 때 가정임을 밝히고 대조한다. 이 예시는 첫 논의 후보이며 이미 사용자가 선택한 장면은 아니다.

- 별도 검토에서도 01·04의 크기와 첫 결과 구체화 필요성을 확인했다. 05에 기존 장치 확인을 더하자는 의견은 현행 본문에도 이미 들어 있어, 새 의무를 중복 추가하기보다 실제 후보 비교에서 확인하는 것으로 판단했다.

검토 범위는 현재 초안과 선택한 보존 근거다. 전체 corpus를 재수집하거나 제품을 실행하지 않았다. 이 순서가 실제 논의 시간이나 개발 품질을 개선했다는 효과는 아직 확인하지 않았다. 실제 구현 계획으로 옮길 때에는 보존 기준판과 현행 적용 대상의 차이를 다시 확인해야 한다.
