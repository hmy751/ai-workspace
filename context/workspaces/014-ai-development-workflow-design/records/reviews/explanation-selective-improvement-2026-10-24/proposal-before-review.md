# 04-02 — 근거를 선별한 설명 수행 개선안

상태: Main의 리뷰 전 제안. 실행 스킬은 수정하지 않았다. 독립 개선 리뷰에서 목적·선택·방법 자체를 바꿀 수 있으며, 아래 구성과 사례를 정답으로 제공하는 문서가 아니다.

## 이번에 해결할 일

사용자 요청:

> 좋아 한번만더 고민해봐 통합 하라고 하면 또 무지성으로 모두 조합해서 진리처럼 다뤄서 다 반영할까 우려되니까 다시 종합해서 고민하고 해봐 그리고 그 다음 제3 개선 리뷰어한테 물어봐 니가 생각한게 괜찮은지 반드시 개선하려고 하는 목적으로 돌려 단순히 적당하다 이런 검증하는거 말고

직전 정정:

> 어쨋든 이 스킬의 본래 목적과 그리고 noline에서 개선하려고 햇떤 장면과 그런 것들을 종합해서 구체적으로 판단해줘야 내가 와닿을 것 같은데? 레퍼도 중요하고 기존 논의나 생각등 우리가 나누면서 내가 느꼇던 지점도 중요하고 그런 통합적인 판단이 안 보여

스킬의 목적은 사용자가 실제 대상의 뜻·동작·구조·선택을 이해하고 자기 질문과 판단을 이어가도록 돕는 것이다. 불필요하게 설명 방식을 재지시해야 하는 부담을 줄이려 한다. 모든 재질문을 없애거나, 모든 답에 코드·도식·설계 평가·완료 판단을 넣는 목표는 아니다.

현재 `explain`에는 이 목적과 실제 구현 대응·전후 비교·앞선 말 대조·목적별 충분성이 이미 있다. 사례를 다시 발견하거나 같은 요구를 더 강하게 적는 것만으로 개선했다고 말할 수 없다. [기존 수행 본문](prototypes/development-workflow/skills/explain/SKILL.md), [작성 상세](prototypes/development-workflow/skills/explain/references/constructing-explanations.md), [앞선 발화 상세](prototypes/development-workflow/skills/explain/references/prior-explanation.md)를 대체 대상으로 삼되 기존 의미를 전부 옮기는 목표도 두지 않는다.

## 어떤 근거를 무엇에 쓰는가

| 근거 | 이번 선택에 사용하는 부분 | 그 근거로 확정하지 않는 것 |
| --- | --- | --- |
| 사용자의 현재 요청·정정 | 실제 경험과 목적을 함께 판단하고, 무차별 편입·반복 소폭 수정·승인용 리뷰를 피할 것 | 모든 과거 요구의 상시 필수화, 새 실행 파일의 즉시 채택 |
| Noline 직접 대화 | 특정 설명이 부족했던 위치, 사용자가 요구한 깊이와 이유, 설명 뒤의 반응 | 후속 요청을 모든 첫 답의 의무로 소급하거나 모든 질문을 실패로 계산하기 |
| 사용자 인터뷰 | 재설명 부담·학습 경험·판단 요구의 체감 | 기억이 불확실한 사건의 원인 확정, 개별 스킬의 인과 효과 |
| 기존 스킬의 배경 | 원래 해결하려던 문제와 경계의 이유 | 옛 분리·목차·분량을 그대로 복구할 의무 |
| 보존 응답 비교 | 읽기와 실제 출력의 차이, 구체적으로 부족하거나 나았던 부분 | 모델·문구·통합 자체의 단일 원인, 보편적 우열 |
| Matt·pstack·Vercel | 공통 수행과 상세의 배치, 작업이 요구할 결과, 판단·자동 검사의 경계에 관한 대안 | 다른 호스트의 호출 보장, 저자 방식의 우월성, 우리 목적의 대체 |

자료의 양을 합치는 대신 서로의 적용 범위를 제한하는 데 사용한다. 판단의 출처와 범위는 [직전 통합 판단](2026-10-24-ticket04-02-skill-routing-source-research.md#사용자-정정-뒤의-통합-판단)에 있다.

## Main이 선택한 방향과 채택하지 않은 대안

**권고: 하나의 설명 입구를 유지하고, 지금 질문을 푸는 관계를 실제 대상과 함께 완성하는 일을 본체의 중심으로 재작성한다.** 읽기·조사와 응답 작성을 연결하되, 선택 이유·추가 검토·첫 결과 전달은 현재 질문과 작업의 요구에 따라 사용한다. 파일 수나 이름은 이번 개선의 근거가 아니다.

| 대안 | Main 판단 |
| --- | --- |
| 코드 읽기·구조·선택·검증·복구를 모두 답의 필수 내용으로 합친다 | 채택하지 않는다. 인증의 문법 도움, 여행의 설계 판단, 보고서의 추가 확인은 같은 과제가 아니다. |
| development의 완료 보고 요구만 강화한다 | 보고서·첫 전달에는 필요하지만 직접 코드 질문과 학습을 다루지 못하므로 주된 개선으로 삼지 않는다. |
| 사례별 독립 스킬이나 상시 설명 agent를 만든다 | 현재 근거로는 채택하지 않는다. 한 대화에서 여러 설명이 이어지며 별도 실행의 이득을 확인하지 못했다. |
| 옛 두 스킬로 돌아가거나 새 스킬을 제거한다 | 현재 비교로는 결정하지 않는다. 통합 효과는 미확인이나 분리 자체가 낫다는 근거도 없다. 계속 유지할 가치 역시 향후 기본 응답과의 대조 대상이다. |
| 설명할 실제 관계를 먼저 완성하고 필요한 깊이·보조 자료를 붙인다 | 현재 권고다. 기존 조항이 이미 이를 요구한다는 점 때문에 아래 구체 수행이 기존과 실질적으로 다른지 독립 개선 리뷰가 필요하다. |

## 본체에서 바꾸려는 수행

아래는 교체할 본문의 의미를 구체화한 초안이다. 완성된 SKILL 전체나 자동 적용된 규칙이 아니다.

> 현재 질문과 가까운 대화에서 무엇을 이해하려는지 정한다. 사용자가 이미 이해했다고 밝힌 것은 이어받는다. 직접 코드를 붙이고 동작이 어렵다고 했다면 그 코드를 읽을 수 있게 설명하고, 구조나 선택을 묻는다면 그 역할과 선택을 판단할 수 있게 설명한다. 사용자의 지식을 고정 등급으로 추정하거나 혼동 원인을 먼저 진단해 달라고 요구하지 않는다.
>
> 답의 핵심을 실제로 설명할 부분부터 만든다. 질문을 푸는 코드·값·관찰·앞선 문장을 골라 그 부분을 응답에 놓고, 거기서 어떤 처리나 관계가 결론을 만드는지 가까이에서 풀어 쓴다. 코드라면 필요한 대목의 실제 표현과 의미를 대응시킨다. 전체를 묻는 경우에는 무엇을 맡는 구조인지 먼저 잡고 대표 상황에서 핵심 부분이 어떻게 협력하는지 따라간다. 설명의 중심이 된 관계를 읽고 따라갈 수 있게 만든 뒤, 다른 변경과 확인 내역은 그 답에 필요한 비중으로 붙인다.
>
> 질문이 선택의 적절성을 포함하면 요구·사용처·이득과 부담을 대조해 의견을 낸다. 당시 의도와 현재 효과의 추론은 구별한다. 설명하다 답을 바꿀 사실의 공백을 발견하면 기존 권한 안에서 필요한 확인을 하거나 작업 담당자에게 되돌린다. 이해가 어렵다는 말만으로 현재 구조가 잘못됐다고 판단하거나 즉시 구현을 바꾸지 않는다.
>
> 응답에 실제 대상과 결론 사이의 필요한 연결이 있는지 확인한다. 이름·역할의 요약만 있고 독자가 핵심을 소스에서 다시 조립해야 한다면 그 부분을 보완한다. 작은 뜻 질문은 짧게 끝낼 수 있고 학습 질문은 이어질 수 있다. 사용자의 이해·동의는 설명을 제공했다는 사실만으로 확정하지 않는다.

실질 변경 후보는 마지막에 요구를 추가하는 것이 아니라, 본체에 흩어진 자료 선택·구현 대응·형태·첫 결과 전달 절을 위 수행에 맞춰 재배치하고 중복을 걷어내는 것이다. 현재 완료 보고에서 다시 ‘코드 설명 목적이면’이라고 선택해야 하는 구조를 그대로 두지 않는다. 다만 이런 재배치만으로 실제 응답이 나아진다고 확정할 수는 없다.

## 상세가 실제로 도와야 할 두 설명

작성 상세를 늘리기보다 현재 설명 예시의 판별력을 높인다. 아래는 Main이 원문에서 도출한 구성 제안이며 독립 생성 응답이 아니다. 사례 이름을 일반 실행 규칙에 넣지 않는다.

**인증: 실제 코드의 값과 기다림을 읽게 한다.** [입력](../source/artifact-explanation-scenes/02-auth-interceptor/input/conversation.txt)에서 문법 질문 뒤 전체 코드가 어렵다는 요청이 있었다. 첫 답의 세션 확인·토큰 갱신 요약만으로 코드 읽기를 돕지는 못했다. 설명은 한 요청이 가진 세션 값이 `await` 전후에 어떻게 쓰이는지 같은 요청의 상황으로 보여 줄 수 있다. 기다리는 중 로그아웃·계정 변경이 생기면 뒤의 검사에서 왜 중단하는지 해당 코드에 대응한다. 그 뒤 다른 분기가 질문에 필요하면 펼친다. 목적은 모든 줄 해설이 아니라 실제 표현이 하는 일을 따라 읽게 하는 것이다.

**여행: 책임 이름과 실제 위임을 연결해 판단하게 한다.** [이전 논의](../source/artifact-explanation-scenes/05-trip-list-briefing/input/conversation.txt)에서 사용자는 여행 자체의 특수성은 이해했지만 책임 분리가 적절한지 물었다. 설명은 파리의 로컬 값과 도쿄의 서버 값이 목록 하나에 필요한 이유를 잡고, Repository가 실제 작업을 제공하며 Router가 조건으로 선택하는 대목을 붙여 각 코드의 역할을 보인다. 저장과 목록 준비의 책임이 갈리는 설명도 같은 사용 장면에서 이어갈 수 있다. 그 사실만으로 현재 추상화가 최선이라고 결론 내리지 않고 현재 사용처와 변경 부담에 비춰 판단한다.

두 설명은 고정 모드나 필수 목차가 아니다. 한 질문에 필요하면 함께 쓴다. 상세의 가치는 단지 좋은 예시를 보여 주는 데 있지 않고, 어떤 관계가 필요한지 판단하고 왜 그 부분을 골랐는지를 복원할 수 있는 데 있다. 현재 작성 상세에도 이 취지가 있고 여행 예시도 있으므로, 다른 예시를 추가하기만 하는 방안은 충분하지 않다.

## 함께 보존할 경계와 바꾸지 않을 범위

- Promise의 다음 질문은 이전 답의 반복 실패일 수도 있고 정상적인 학습일 수도 있다. [인터뷰](../source/noline-evaluation/reviews/interview-20261012.md)가 둘을 함께 인정했으므로 재질문 수를 성공 기준으로 삼지 않는다. 앞선 발화 상세는 실제로 이해한 부분과 남은 연결을 구별하고, P1/P2처럼 관계가 달라 보이는 표현으로 전환할 때 사용한다.
- access 질문은 [실제 대화](../source/noline-evaluation/corpus/01a0ec21-e59e-7370-8432-8434271aa669/messages.jsonl)처럼 뜻과 선택 판단을 포함할 수 있다. 이유를 설명할 권한과 코드를 수정할 권한을 구별한다. 전체 설계 감사나 사용자 비위 맞추기 모두 기본 동작으로 두지 않는다.
- [보고서](../source/artifact-explanation-scenes/01-report-delivery/evaluation/conversation.txt)의 원래 문제·관찰·결론 연결은 development가 전달할 결과에 포함한다. 답에 필요한 실제 확인이 부족하면 그 작업을 수행해야 한다. 설명 스킬이 독립 검증·모든 추가 조사·전체 작업 완료를 소유하게 하지 않는다.
-06은 첫 전달을 보는 사례로 유지한다. 뒤의 철회를 첫 답의 정답으로 삼거나 품질 목표를 동작 변경 전면 금지로 바꾸지 않는다.
- background는 중요한 선택 이유와 불확실성을 보존한다. 모든 사례와 외부 규칙을 일상 본문에 넣지 않는다. 기존 공통 근거 기준을 다시 복제하지 않는다.

## 이번 리뷰가 바꿀 수 있는 것

리뷰어는 제안의 문제 정의·우선순위·본문 방식·상세 구성·개입 크기 모두를 바꿀 수 있다. 지금의 문장 재배치가 다시 소폭 수정에 그치는지, 설명의 개선을 실제 작업 품질의 개선과 혼동하는지, 다른 방식이 더 낫다면 무엇인지 원자료와 함께 판단해 달라. 단일 입구 유지나 두 상세 유지도 검토 대상이다.

반환에서는 가장 가치 있는 개선을 구체적으로 보여 주면 된다. 제안 문단의 대체 예시나 특정 원문에서 현재 방식과 달라질 수행이 있으면 좋다. 좋은 점의 나열·합격 판정·모든 기준의 전수 편입은 목표가 아니다. 다만 개선점을 억지로 만들어 개수를 채우지는 않는다. Main은 근거와 적용 범위를 대조해 의견을 채택·보류·기각한다.

새 시험은 이번 요청의 후속 자동 작업으로 두지 않는다. 수정안의 구체적 차이와 기존 실패 답에 대한 판단을 먼저 정하고, 효과를 확인할 필요가 생겼을 때 무스킬 기준선·사례 일반화·자연 호출을 각각 무엇을 판단할 시험인지 구별한다.
