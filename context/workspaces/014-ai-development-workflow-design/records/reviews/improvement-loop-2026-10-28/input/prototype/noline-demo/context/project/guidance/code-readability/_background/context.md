# 인증의 실제 결과에 맞게 이름과 안내를 판단하는 이유

이 문서는 [인증 표현 가이드](../INDEX.md)의 형성 맥락이다. 일반적인 이름 선호와 제품의 구체적인 완료·실패 의미가 어떤 관계로 남았는지 설명한다.

## 제품이 보장하는 결과를 알아야 표현을 판단할 수 있다

이 가이드는 이름을 길게 만들거나 특정 접두사를 표준화하려고 만들어진 것이 아니다. 보존된 Noline 표현 기준은 일부 저장 action과 로그인 전체 절차, 조회 요청과 조회 완료를 다른 책임으로 다뤘다. 현재 가이드는 그 [제품 표현 기준](evidence.md#이름과-완료-범위의-제품-기준)을 인증 예제에 적용해, 호출자가 다음에 할 수 있는 행동을 잘못 예상하지 않도록 구체화했다.

Store의 부분 처리를 전체 로그인 서비스처럼 읽거나 조회 요청 뒤 callback을 화면 준비 완료로 읽으면, 이름의 문제가 동작·오류 안내의 오해로 이어진다. 그래서 현재 본문에는 Store·서비스·wrapper의 책임, Login·Reauth의 다음 행동, 표현이 담을 수 있는 결과를 직접 설명한다. 제품 계약을 이해하기 위해 Personal 원문부터 읽어야 하는 관계는 두지 않았다. 세 영역의 공통 책임은 [context 형성 자료](../../../../_background/README.md)에서 확인할 수 있다.

## 이름 개선이 필요한 장면과 동작 변경이 필요한 장면

이번 초기 입력에는 인증 완료 뒤 조회를 기다리지 않으면서 화면 갱신까지 끝났다고 읽히는 문구가 있었다. 그러나 두 소비자는 완료 callback에서 최신 조회 값을 직접 사용하지 않는다고 가정했다. 이 조건에서는 표현을 실제 보장에 맞추는 것과 새 조회 대기를 도입하는 것이 같은 수정이 아니다. 실제로 최신 결과가 필요하면 동작·완료 계약을 다시 판단해야 한다.

기존 제품 기준도 `await`를 보기 좋은 순서 때문에 추가하지 말고 뒤 작업의 선행 조건에 따라 사용하도록 설명했다. [정확한 원문](evidence.md#비동기-표현의-제품-기준)이 그 근거다. 후속 조회 오류를 로그인 실패로 안내한다면 문구만 고칠지 오류 전달 경로까지 고칠지는 실제 분류 책임에 달려 있다. 현재 가이드는 이를 판단하게 하며, 상세 인증 계약을 독립적으로 다시 정의하지 않는다.

## 현재 선택한 이름은 제품 전체의 의무가 아니다

처음 시안에서는 Project 가이드가 최종 이름을 미리 제공해 일반 기준을 사용한 선택인지 보기 어려웠다. 이후 역할·계약·판단 조건은 guidance에, 선택한 함수명·구현·지원 범위는 current에 두도록 구별했다. [당시 기록](records/2026-10-19-product-expression-boundary.md)은 이 배치가 독립 적용 실험의 성공을 뜻하지 않는다는 한계도 남긴다.

개인 기준에 ‘가능한 한 코드 자체가 명료해야 한다’는 지향을 보완하면서 Project까지 일반 우선순위·A/B 비교 방법·이번 개명 비용 판단을 넣은 적이 있다. 이후 [개인 기준 소유 정정](../../../../personal/development/naming-and-completion/_background/records/2026-10-19-personal-ownership.md)에 따라 이 일반 판단은 Personal과 Work에 남기고, Project에는 인증 결과·실패 의미·소비자 요구에 필요한 설명을 유지했다.

비슷한 설명이 있다는 이유로 모두 제거한 것은 아니다. Project의 지속 규약이나 자기 계약을 설명할 필요가 바뀌면 다시 갱신할 수 있다. 현재 구현의 이름은 [인증 흐름](../../../current/authentication-flow/INDEX.md), 이번 선택의 대안과 비용은 [Work 이름 비교](../../../../work/workspaces/001-login-completion-names/records/2026-10-19-06-naming-alternatives.md)가 소유한다.
