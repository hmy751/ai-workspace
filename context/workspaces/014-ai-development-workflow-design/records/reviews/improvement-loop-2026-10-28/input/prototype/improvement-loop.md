# 작업 체계 개선 루프의 실행 구체안

**사용자가 요청하면 지금 대화하는 Main이 대화 전체와 관련 내용을 살피고, 추천을 함께 고른 뒤 가능한 개선을 실제 반영한다.** 경험과 열린 후보는 Personal에서 다시 찾는다. 합의한 네 묶음을 실행 지침·실제 저장 위치·기존 반영 경로로 펼친 프로토타입이다.

## 어떤 파일이 무엇을 맡나

| 책임 | 실제 파일과 연결 |
| --- | --- |
| 사용자 요청을 받아 검토·선택·반영·종료 | [improvement-loop/SKILL.md](skills/improvement-loop/SKILL.md). 현재 Main이 사용한다. 별도 agent나 새 세션은 만들지 않는다. |
| 압축 전 대화까지 확인 | [대화 원문 확인](skills/improvement-loop/references/conversation.md). 현재 문맥·같은 세션 원문·복구 불가 구간을 구별한다. |
| 이전 변경의 실제 도움·부담 판단 | [효과 판단](skills/improvement-loop/references/effects.md). 다음 관련 루프에서 필요할 때 읽는다. |
| Personal의 기준과 경험 경계 | [Personal](noline-demo/context/personal/README.md). 기존 개발 기준과 경험·해석·후보를 구별한다. |
| 경험과 열린 후보를 다시 찾기 | [길잡이](noline-demo/context/personal/experience/README.md). 세 실제 근거 기반 주제와 아직 묶지 않은 질문을 담았다. |
| 보존·갱신·채택 후 연결 | [경험 관리](noline-demo/context/personal/experience/MAINTENANCE.md). 정본·근거·상태 구별을 유지한다. |
| 실제 대상의 반영 | [context-update](skills/context-update/SKILL.md)는 Personal·Project 본문, [development](skills/development/SKILL.md)는 필요한 개발 수행·확인과 기존 작업 기록을 잇는다. 스킬·도구는 각 대상의 계약을 따른다. |

파일명·세 주제 배치는 이번 요청에 따른 구체화 선택이다. Personal 전체를 이 주제들로 분류한 것이 아니다. 일반 기준은 기존 개발 본문에 있고 경험은 `personal/experience/`에 있다. 아직 묶지 않은 짧은 기록은 길잡이 안에 두며 양이 늘 때만 나눈다.

## 실제 한 번의 흐름

| 시점 | Main이 하는 일 | 사용자에게 보이거나 남는 결과 |
| --- | --- | --- |
| “이번 대화 돌아보자” | 이번 세션 처음부터 요청 시점까지 훑는다. 요약뿐인 구간은 원문을 찾는다. | 검토 범위와 중요한 입력 공백. |
| 대화에서 중요한 발견이 드러남 | Personal 길잡이·미분류 기록을 훑고 관련 주제와 현재 대상 본문 전체·실제 결과·내용 지침을 대조한다. | 관찰과 해석, 좋은 사례·새 방식·내용/수행 개선의 후보. |
| 선택에 충분한 근거를 확보 | 구체 이득·근거·부담·대안·실제 반영 대상을 연결해 추천한다. | 추천과 이유 먼저, 다른 후보·유지 판단·공백도 확인 가능. |
| 사용자가 고름 | 선택한 범위를 실제 대상에 반영하고 직접 확인한다. 한정 시도라면 그 범위를 연결한다. | 실제 변경과 확인, 아직 남은 실행을 구별. |
| 이번 반영을 마침 | 경험 주제의 이해·후보·선택과 길잡이를 맞춘다. Work 기록은 기존 작업 방식에 따른다. | 반영·보류·유지/접기와 이유. 새 Work 등록 절차 없음. |
| 다음 관련 루프를 요청 | 현재 대화와 Personal 길잡이에서 관련 경험을 다시 찾고 실제 사용·도움·부담을 대조한다. | 유지·수정·조건 축소·철회 또는 필요한 한정 비교를 다시 선택. |

네 합의 묶음은 위 실행의 네 고정 단계나 네 담당자가 아니다. 사용자와 선택하기 전에는 새 기준을 실제 적용하지 않으며, 이미 허용된 일상 갱신에는 루프를 기다리는 관문을 만들지 않는다.

## 사례: 지금 보존한 경험에서 다음 선택까지

### 여러 자료가 좋지만 무엇을 가져올지 고르기 어렵다

[설계 논의 주제](noline-demo/context/personal/experience/topics/design-conversation.md)에 실제 사용자 발화와 당시 진행을 보존했다. 현재 해석은 ‘자료를 더 모으는 것만으로 선택이 쉬워지지 않으며, 대안의 실제 차이와 남은 질문을 연결할 필요가 있다’는 것이다. ‘비교 후 질문하기’는 열린 후보이고 매번 도식·인터뷰를 요구하는 기준은 아니다.

다음 실제 대화에서도 여러 대안 사이에서 선택이 어려웠다면 Main은 대화 전체를 훑고 길잡이에서 이 주제를 다시 찾는다. 단순히 ‘인터뷰’라는 단어를 찾는 것이 아니라 선택 기준이 불분명했던 조건을 연결한다. 새 대화의 실제 비교·질문·사용자 선택과 기존 work-discussion 전체를 대조해 이미 충분한지, 읽지 않았는지, 새로운 행동 조건이 필요한지 판단한다.

여기서 가능한 추천은 특정 열린 설계에만 한정 시도하기, 기존 스킬의 조건을 보완하기, 경험만 보존하기다. 기존 스킬로 충분한데 인터뷰 단계만 늘리는 안은 제외할 수 있다. 제안할 때 실제 바꿀 문장이나 수행 장면을 보여준다.

**사용자가 한정 시도를 선택한다면** 해당 작업에서 언제 어떤 비교와 질문을 할지 연결하고 주제에 시도 범위·기대 변화·실제 반영 대상을 남긴다. **현재 기준의 보완을 선택한다면** 해당 스킬을 실제 수정·확인하고 주제의 열린 후보를 반영 결과로 바꾼다. 일반 기준 전문을 경험 주제에 복제하지 않는다. 아무것도 선택하지 않거나 미결 이유가 같으면 후보를 그대로 유지하고 다음번에 자동 재권고하지 않는다.

이 후반의 선택·반영은 실행 경로 설명이며 지금 실제로 work-discussion을 바꾸거나 그 후보를 채택한 것은 아니다.

### 좋은 편집을 경험으로 남긴 뒤 관련 본문 전체를 본다

[문서 품질 주제](noline-demo/context/personal/experience/topics/document-quality.md)는 첫 11편 편집의 긍정 반응과 조건·순서·예외를 보존한 방식을 담는다. 다음 문서 반영에서는 새 정보 한 줄만 넣지 않고 해당 주제 전체와 내용 지침을 대조한다. 같은 설명이 이미 충분하면 무수정 유지, 부족한 적용 조건이 확인되면 기존 본문 통합, 다른 문서에서도 유용한 판단이면 Personal 사례 보완을 추천할 수 있다.

가령 실제 대상에서 같은 의미가 두 곳에 중복돼 독자를 혼동시킨 것이 확인되고 사용자가 통합을 선택했다면, context-update로 실제 본문과 들어오는 참조를 함께 고친다. 읽는 입구에서 조건·예외가 복원되는지 확인한 뒤 반영 결과를 잇는다. 이 가정은 현재 demo에 그 결함이 발견됐다는 주장이 아니다. 모든 문서를 표로 바꾸는 기준은 이 좋은 경험에서 나오지 않는다.

### 이전 보완을 썼는데 이득이 애매하다

[설명 방식의 효과 주제](noline-demo/context/personal/experience/topics/explanation-effects.md)에 보존한 비교에서는 일부 근거가 좋아졌지만 전체 이득이 제한적이었고, 문구를 더하지 않고 현행을 유지한 판단이 있었다. 이것을 이번 루프 스킬의 사용 효과로 옮기지 않는다.

다음 관련 사용에서는 먼저 이전 변경의 목적과 실제 사용을 대조한다. 읽지 않은 장면이면 접근·적용 문제를, 사용했지만 효과가 불분명하면 조건과 부담을 살핀다. 작은 이득이 있어도 불필요한 절차가 커졌다면 범위 축소·간소화를 권할 수 있다. 비교로 결정을 바꿀 수 있을 때만 관련 요청에 한정해 비교한다. 전체 대화를 다시 돌리거나 만족도 질문을 매번 하지 않는다.

## 입력·권한·정본의 경계

- 대화는 현재 문맥과 같은 세션의 실제 원문을 사용한다. 로컬 Codex에서 식별자·파일·메시지 구조까지 확인한 접근 예가 있다. 특정 host의 경로·형식을 모든 환경에 가정하지 않으며 원문 부재를 고지하는 것만으로 전체 검토를 완료하지 않는다.
- Personal의 경험은 판단 재료다. 새로운 일반 기준을 채택하는 권한은 사용자에게 있고, 실제 반영은 선택된 범위의 Main 또는 담당자가 맡는다. AI가 기록했다는 이유로 기준이 되지 않는다.
- 제품 의미·코드·검사·스킬·현재 작업의 정본은 기존 대상이 계속 맡는다. 모든 후보를 Personal로 복사하거나 모든 실행을 Work에 등록하지 않는다.
- 일반 작업의 내용 충분성·기계 검사·역할 배치는 기존 계약을 사용한다. 새 범용 개선 리뷰어·스케줄·hook·후보 상태 머신을 추가하지 않았다.
- 실행 지침은 모델이 따를 계약이다. 읽음·준수·효과를 자동으로 보장하는 runtime은 아니다. 스킬을 바꿔도 Personal의 관리 계약·경험·채택 기준은 유지할 수 있다.

## 무엇이 만들어졌고 무엇이 남았나

이번에는 실행 본문, 원문·효과 상세, Personal 실물과 근거 예시, root/context/USAGE/development/context-update의 읽기·반영 연결을 작성했다. 실물의 내용·링크·표시 사본과 대표 조건을 Main이 확인한다. 형성 이유·사용자 발화·외부 참고의 선별은 [가까운 형성 자료](skills/improvement-loop/_background/README.md)에 보존했다.

실제 host 설치·호출 시험, 여러 저장소 Personal 위치와 배포·동기화, 다음 실제 사용 효과는 별도다. 새 파일명을 만든 사실을 운영 채택이나 05 전체 마감으로 표시하지 않는다. 일반 자동 반영 범위, 후보의 점수·반복 횟수·고정 분류·평가 양식은 여전히 열린 선택이며 기본 의무로 채우지 않는다.

다음에는 이 실행안의 실제 읽기·판단을 점검하고 필요한 보완을 고른다. 운영 전환에서는 루프와 동반 자료·Personal 진입·원문 접근을 연결하고, 적용 관찰에서는 실제 요청부터 후보 저장·재조회·선택·반영·사용까지의 확인 범위를 정한다. 설계 설명·Main의 제한된 실물 점검·독립 수행 시험·장기 효과를 서로 구별한다.
