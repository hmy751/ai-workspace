# 인증 완료·실패와 후속 조회의 계약

로그인·재인증의 저장 순서, 성공·실패 전달, 후속 조회와 완료 알림을 바꿀 때 읽는다. **새 인증은 기기 저장 뒤 공개하고, 인증 적용과 후속 조회의 결과를 구별한다.** 같은 계정의 로컬 작업을 보존하는 제품 의미는 [기기 세션](../../common/device-session/INDEX.md)에 있다.

아래 기기 저장·상태 공개의 경계는 Noline 보존 문서에서 가져왔다. Query 요청 wrapper와 callback의 구체 동작은 현재 demo의 선택이다. 실제 구현의 충족 범위는 [인증 흐름 현황](../../current/authentication-flow/INDEX.md)에서 대조한다.

## 인증을 적용하는 책임과 조율하는 책임

Auth Store는 기존 계정과 로컬 DB·queue의 귀속을 확인하고, 세션을 기기에 저장한 뒤 공개 인증 상태를 바꾸는 책임을 갖는다. 전체 세션 변경 서비스는 진행 중인 sync·cleanup·접수된 DB 작업의 종료와 본작업을 조율한다. Store action만 호출했다고 전체 조율을 거친 것으로 취급하지 않는다.

이 demo의 Store는 계정 ID와 메모리 여행 목록의 귀속만 검사하고, 서비스는 주입받은 `waitForActiveWork`를 기다린다. 실제 DB·queue 검사와 진행 작업 종료 장치는 연결하지 않았다.

## 사건별로 보존할 결과와 다음 행동

| 발생한 일 | 인증과 데이터 상태 | 호출자에게 전달할 결과 | 다음 행동의 범위 |
| --- | --- | --- | --- |
| 인증 응답·귀속 확인·선행 대기 중 실패 | 새 인증을 공개하지 않는다. 기존 상태·데이터를 유지한다. | 로그인/재인증 절차의 실패. 인증 완료 callback은 호출하지 않는다. | 실패 단계의 원인을 처리한다. 귀속 불명 데이터를 자동 정리하지 않는다. |
| 기기 저장 진행 중 | 새 인증은 아직 공개되지 않는다. | 인증 완료를 알리지 않는다. | 저장 결과를 기다린다. |
| 기기 저장 실패 | 기존 공개 인증 상태·로컬 데이터를 유지한다. | 저장 실패. 인증 완료 callback은 호출하지 않는다. | 저장 경계를 복구하거나 재시도를 판단한다. |
| 기기 저장과 공개 상태 반영 완료 | 새 인증이 적용되고 같은 계정의 로컬 데이터는 유지된다. | 인증 적용 성공 | 인증이 필요한 다음 작업을 시작할 수 있다. 조회·화면 준비 완료는 별도로 판단한다. |
| 그 뒤 조회 요청 시작 실패 또는 비동기 조회 실패 | 이미 적용한 인증을 유지한다. | 후속 조회 실패 | 조회 복구를 판단한다. 실패 자체를 인증 저장 실패로 바꾸지 않는다. |

후속 조회 실패만으로 앞선 인증 저장을 실패로 바꾸지는 않는다. 다만 요청에서 현재 인증 수단의 거부가 별도로 확정되면 새 인증 사건으로 처리해 보호된 요청을 막아야 한다. 이 demo는 거부 판정·요청 차단·재인증 전환을 구현하지 않았다.

기기 저장 어댑터가 일부만 저장한 뒤 실패할 때의 원자성·복구, 동시 세션 변경, callback 자체가 던지는 오류는 현재 예제의 보장 밖이다. 이 표의 보존 계약을 실제 어댑터로 옮길 때에는 그 조건을 별도로 설계하고 확인해야 한다.

## 조회를 기다릴지는 다음 화면의 요구로 정한다

조회 실패가 인증을 되돌리지 않는다는 것과 조회를 기다리지 않는다는 것은 별개의 선택이다.

| 다음 행동의 요구 | 가능한 대기 방식 | 완료와 실패를 표현할 방법 |
| --- | --- | --- |
| 인증 복구 뒤 이동·닫기를 시작할 수 있고, 도착 화면의 조회는 별도로 처리한다. | 인증 적용 뒤 조회를 요청하고 결과를 기다리지 않을 수 있다. 현재 demo가 선택한 방식이다. | 인증 완료를 알리고 조회 실패를 별도로 전달한다. 화면 준비까지 끝났다고 말하지 않는다. |
| 다음 단계가 최신 조회 결과를 즉시 사용해야 한다. | 인증 적용 뒤 필요한 조회까지 기다린다. 이 경로는 현재 demo에 구현하지 않았다. | 인증 적용 완료와 조회 대기를 구별한다. 조회 실패에도 인증이 남는다는 사실을 함께 전달한다. |

최신 결과를 필요로 하는 소비자만 기다릴지, 여러 소비자가 공유할 작업의 완료 계약을 바꿀지도 구별한다. 일부 소비자만의 요구라면 기존 인증 완료 경계를 유지하고 해당 소비자의 후속 흐름에서 조회를 기다릴 수 있다. 공통 반환 시점을 바꾸는 선택이라면 기존 Login·Reauth의 loading 의미와 이동·닫기 시점, 실패 안내에 미치는 영향을 함께 검토한다. 함수명에 `Ready`를 붙이거나 `await`를 추가하는 것만으로 화면의 요구가 정해지지는 않는다.

## 인증 완료와 후속 조회 전달의 약속

이 demo에서 인증 서비스와 후속 조회를 연결하는 진입점은 다음 순서를 지킨다.

1. 인증 서비스가 저장과 공개 상태 반영을 마칠 때까지 기다린다.
2. Query 갱신을 요청한다. 요청 함수가 즉시 던지는 오류와 반환 Promise의 rejection은 후속 조회 오류 callback으로 전달한다.
3. Query 완료를 기다리지 않고 인증 완료 callback을 호출한 뒤 세션을 반환한다.

따라서 성공은 **인증 적용과 조회 요청 시도, 인증 완료 callback 호출까지**를 뜻한다. 요청 자체가 시작되지 못했어도 후속 오류를 전달한 뒤 인증 완료는 알린다. 두 callback은 오류를 다시 던지지 않고 정상 반환하는 계약이다.

비대기와 두 callback은 이 demo가 선택한 계약이다. 특히 요청 자체의 동기 오류까지 후속 오류로 보내는 처리는 실행 예제를 만들며 추가한 선택으로, 초기 가정 코드가 이미 보장했다고 소급하지 않는다.

이 계약을 바꿀 때에는 저장 전 공개가 없는지, 저장 실패 때 기존 결과가 남는지, 조회 대기·실패가 완료 알림에 어떤 영향을 주는지 확인한다. 소비자의 이동 함수 호출과 실제 화면 전환 완료도 구별한다. 현재 선택한 함수명·구현 코드·검사 위치는 [인증 흐름 현황](../../current/authentication-flow/INDEX.md)에 있다.

본문의 범위와 형성 의도·변경 근거를 읽을 경로는 [구성 안내](README.md)에 있다.
