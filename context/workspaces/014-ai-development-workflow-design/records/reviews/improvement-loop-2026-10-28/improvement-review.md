# Improvement Loop 실행안의 개선 리뷰

2026-10-28. **현행 구조는 유지하고, 선택한 한정 시도의 실제 소비 경로를 먼저 구체화하는 편이 좋다. 그다음에는 기존 설명 사례 하나를 서로 다른 개선 수단의 실제 차이를 보여주는 사례로 바꾸기를 권한다.** 기준·상태·평가 항목을 더 늘리는 안보다 이 두 보완이 실행안의 다음 판단을 직접 개선할 가능성이 크다.

검토 대상은 [고정판 manifest](input/manifest.json)의 `input/prototype/`이다. 중심 판본은 `skills/improvement-loop/SKILL.md`의 SHA-256 `8bcf39883b6103c8433aa2d749cf9edba9b3bb4aa6c86c46f9cfa8eeae5ec92c`다. 현재 작업 중인 prototype이나 다른 리뷰어의 판단은 입력으로 사용하지 않았다. 이 보고서는 합의 적절성의 합격 판정이 아니라, 현재안을 유지하는 선택과 더 나은 실제 수행 대안을 비교한 제안이다. 실제 루프 실행·사용자 효과 시험은 하지 않았다.

## 먼저 보완할 것 — 선택한 한정 시도가 일반 작업에서 쓰이고 끝나는 경로

현행은 한정 시도를 일반 기준과 구별하고 상황·행동·기대 변화·다시 볼 계기를 남긴다. [실행 본문 47행](input/prototype/skills/improvement-loop/SKILL.md#함께-선택한-가능한-개선을-실제로-반영한다)과 [실행 사례](input/prototype/improvement-loop.md#여러-자료가-좋지만-무엇을-가져올지-고르기-어렵다)는 해당 작업에 연결하라고 한다. 그런데 [공통 읽기](input/prototype/noline-demo/context/USAGE.md), [Personal 입구](input/prototype/noline-demo/context/personal/README.md), [경험 관리](input/prototype/noline-demo/context/personal/experience/MAINTENANCE.md)를 따라가면 일반 작업은 채택 기준을 읽고, 경험·후보의 재조회는 사용자 요청 루프가 맡는다. **‘선택한 한정 시도’를 다음 일반 작업에서 발견하는 연결은 가능한 구현 판단으로 남아 있다.** 발견 불가능하다는 판정은 아니지만, 이 실행안이 가장 도움을 줘야 할 재개 장면에서 담당자가 다시 설계해야 한다.

실제 대입할 장면은 현재 `design-conversation` 주제의 후보다. 사용자가 ‘다음 열린 설계 한 번에서는 대안 차이를 먼저 보여주고 남는 질문을 묻자’를 선택했다고 가정한다. 같은 Main이 바로 그 설계를 이어가면 추가 파일 없이 수행할 수 있다. 그러나 다음 세션에서 일반 설계 작업으로 재개하면 경험 길잡이를 읽어야 할 이유가 없을 수 있다. 후속 루프에서야 ‘사용 장면 없음’을 발견하면 기록은 이어지지만 선택했던 개선은 사용되지 않는다. 반대로 경험 전체를 매번 읽게 하면 사용자와 합의한 부담 경계가 무너진다.

비교한 대안은 다음과 같다.

| 선택 | 실제 장면의 차이 | 판단 |
| --- | --- | --- |
| 현행 유지 | 숙련된 Main이 해당 작업에 적절히 연결하면 충분하다. 재개 시에는 ‘연결’의 뜻을 다시 판단한다. | 같은 대화 안에서 끝나는 시도에는 충분하다. |
| 모든 일반 작업에서 경험·열린 후보 읽기 | 시도를 찾을 가능성은 높지만 미선택 후보와 역사적 경험까지 매번 들여오고, 후보가 지시처럼 작동하기 쉽다. | 권하지 않는다. |
| 선택된 시도만 해당 작업의 기존 진입에 연결 | 일반 작업은 선택한 범위만 회수하고, 경험 주제는 근거·결과를 계속 소유한다. | 재개를 넘는 시도에 추천한다. |

구체 변경은 별도 시도 대장이나 Work 등록 단계를 만드는 것이 아니다. `SKILL.md`의 한정 시도 문단과 실행안의 현재 예시를 다음 차이가 드러나게 고친다.

- 현재 대화에서 즉시 수행할 시도는 바로 실행한다. 보존을 위한 별도 진행 문서를 만들지 않는다.
- 다른 시점의 특정 작업에서 수행할 시도는 그 작업이 실제로 읽는 기존 지시·재개 본문에 상황, 할 행동, 끝나는 범위와 경험 주제 연결을 둔다. Work를 이미 쓰는 작업이면 기존 current/Ticket이 가능하지만, 모든 시도에 Work 생성을 요구하지 않는다.
- 아직 수행할 작업·소비 지점을 정하지 못했다면 경험에 시도 의사를 남길 수 있다. 다만 ‘다음 작업에 연결됨’으로 완료 처리하지 않는다. 이후 루프에서 다시 고를 후보와 이미 실행할 준비가 된 시도를 구별한다.
- 정한 한 번 또는 조건 범위가 끝났으면 임시 수행 연결은 더 이상 실행 지시로 남지 않게 하고, 결과·이유는 기존 경험 주제에 보존한다. 지속 채택은 별도 사용자 선택이다.

`USAGE.md`의 이번 목표·선택 읽기 설명에는 ‘이번 작업에 이미 선택된 한정 시도가 있으면 그 범위도 함께 읽는다’ 정도의 의미만 연결하면 된다. 매번 시도가 있는지 전역 검색하는 새 절차는 필요 없다. 경험 관리 문서는 시도 범위와 실제 소비 위치를 연결한다는 정도로 맞춘다. 실제 보완 시에는 같은 규칙을 세 문서에 반복 설명하지 않고 실행 지침과 저장 계약의 책임을 나눈다.

확인할 효과는 두 조건을 대입하면 된다. 하나는 선택한 시도가 연결된 작업을 재개했을 때 일반 읽기만으로 그 시도와 종료 범위를 복원하는지, 다른 하나는 비슷하지만 시도를 선택하지 않은 작업에서 열린 후보를 실행하지 않는지다. 이후 완료한 작업에서 같은 임시 지시가 다시 적용되지 않는지도 확인한다. 이 확인은 읽기·실행 연결의 개선이며, 시도 자체가 유용했다는 효과 입증과는 다르다.

근거는 사용자의 ‘억지로 Work층에 남기는 것처럼 하지 않아도 된다’는 정정과 다음 작업의 실제 사용 관찰 합의, 전체 구체안의 ‘선택한 시도의 다음 수행 연결’이다. 사용자는 시도마다 별도 기록을 만들라고 하지 않았다. 따라서 연결 방식은 실제 수행을 넘길 필요가 있는 경우에만 좁게 쓰는 것이 맞다. 이 제안의 부담은 임시 연결을 끝낼 책임이 하나 생긴다는 점이다. 그 책임 없이 ‘다음 작업에서 시도’를 약속하는 것보다 작고 명시적인 부담이라고 판단한다.

## 다음 보완 — 사례를 개선 수단의 실제 차이를 고르는 연습으로 바꾸기

현행 `SKILL.md`는 내용·접근·적용·도구·배치를 모두 살피고 새 방식도 발견하도록 한다. 이 범위를 더 추가할 필요는 없다. 다만 현재 [실행안의 세 사례](input/prototype/improvement-loop.md#사례-지금-보존한-경험에서-다음-선택까지)는 설계 대화, 문서 편집, 설명 효과에 모여 있고, 실행은 주로 문장 보완·경험 보존·현행 유지로 설명된다. 도구·검사·환경을 바꿀 수 있다는 문구에 비해, **같은 장면에서 무엇을 바꾸면 사람과 AI의 행동이 달라지는지를 비교하는 예시는 약하다.** 이 차이는 이름을 `improvement-loop`로 바꾼 이유와도 연결된다.

권고는 사례나 검토 항목을 계속 더하는 방식이 아니다. 문서 품질 주제의 실제 긍정 경험과 근거는 그대로 두고, 실행안의 ‘중복 문서를 통합한다’는 가정 사례 일부를 **현재 프로토타입 자체에 있는 수행 능력 선택**으로 교체하면 된다. 적합한 소재는 [대화 원문 확인](input/prototype/skills/improvement-loop/references/conversation.md)이다. 현재 파일 식별과 메시지 구조는 확인했지만 전체 추출·접근의 수행은 아직 미확인이고, exporter를 설치하지 않았다는 경계가 분명하다.

예시는 다음과 같은 비교가 될 수 있다. 이는 이 보고서에서 exporter를 만들거나 채택하자는 제안이 아니다.

| 같은 목표: 같은 세션의 전체 발화 범위를 빠뜨리지 않고 훑기 | 바뀌는 실제 행동과 이득 | 부담·선택을 가르는 근거 |
| --- | --- | --- |
| 현행 원문 지침을 따라 필요한 때 직접 읽기 | 새 도구 없이 host 구조를 확인하고 연속 구간을 읽는다. | 드문 호출과 짧은 원문에는 충분할 수 있다. |
| 설명·예시를 보완하기 | 시작·종료 경계나 메시지 종류를 헷갈렸던 부분을 바로 이해한다. | 문제 원인이 이해 부족이면 유효하다. 반복 추출 작업 자체는 줄지 않는다. |
| 같은 세션을 읽는 작은 읽기 전용 추출 도구를 한정 시도하기 | 세션 일치·발화 순서·중복 제외·원래 위치를 되풀이해 처리하는 준비를 줄일 수 있다. | 실제 반복 준비 비용이나 누락이 확인될 때 가치가 커진다. host 형식 변화와 fork/압축 경계를 유지해야 하며, 추출 성공이 전체 의미 검토를 대신하지 않는다. |

이 사례를 끝까지 쓰려면 ‘지금은 구조만 확인했으므로 반복 비용을 사실로 만들지 않는다. 실제 첫 사용에서 준비 과정과 누락을 확인하고, 명확한 이해 문제면 설명을 고치며, 반복 기계 처리가 핵심일 때 도구 시도를 추천할 수 있다’까지 보여준다. 사용자가 선택한 경우에만 해당 수행 계약으로 반영하고, 원문 읽기·후보 판단은 여전히 Main이 맡는다. 일반 설치나 자동 수집을 기본값으로 만들지 않는다.

외부 원형과의 비교도 이 선택을 뒷받침한다. 이번에 직접 읽은 [Matt retro 보존판](../../../source/workflow-references/matt-pocock/repository/skills/engineering/retro/SKILL.md)은 기존 검사 연결·탐색·도구 비용·접근 능력을 실제 변경 후보로 다룬다. 다만 기계적 문제는 무조건 검사로 만들라는 원형의 강한 기본값까지 가져올 이유는 없다. [workflow-from-chats 보존판](../../../source/workflow-reference-supplements/2026-10-27-learning-perspectives/repository/plugins/cursor-team-kit/skills/workflow-from-chats/SKILL.md)은 재사용 지침을 추출해 스킬·규칙·문서·산출물 없음을 고르는 데 초점이 있다. 이 루프는 그보다 넓은 수행 수단을 선택하려 하므로, 결과 형식의 목록보다 동일한 목적에서 어떤 행위를 바꾸는지 보여주는 편이 적절하다. 외부 최신판이나 효과를 확인한 주장은 아니다.

`SKILL.md`의 추천 문단은 이미 충분한 요소를 담고 있으므로 길게 확장하지 않아도 된다. 필요하다면 ‘상충하는 안은 같은 장면에서 현행과 각각 무엇을 달리 하게 되는지 비교한다’는 뜻만 통합한다. 예시의 비교 내용을 모든 후보의 고정 양식으로 승격하지 않는다.

확인할 효과는 이후 실행안 독자가 ‘지침 보완이 기본 해법’이라고 생각하지 않고, 위 장면에서 현행 유지·이해 보완·수행 수단 변경을 서로 다른 이유로 선택할 수 있는지다. 새로운 도구 후보를 반드시 내야 성공한 것은 아니다. 동일 목표에서 현행이 더 낫다는 이유도 구체적으로 설명되면 목적에 맞다. 이 보완은 예시의 범위 편향을 줄일 것으로 기대하지만 실제 발견 품질 향상은 아직 가설이다.

## 바꾸지 않는 편이 나은 대안들

대화 발견과 과거 경험 검토를 별도 담당자로 분리하거나, 과거 후보를 보기 전 독립 초안을 반드시 만드는 방식도 검토했다. 현재는 대화 전체를 먼저 훑고 길잡이·관련 상세를 읽으며 반례를 대조하는 흐름이 있다. 이 단계에서 별도 발견 목록·담당자를 의무화할 만큼 실제 과거 후보 편향이 입증되지 않았다. 현재 Main이 맥락을 이어 반영하려는 합의를 유지하는 편이 낫다.

Personal을 경험 저장소와 후보 대기열로 다시 나누거나, 상태 코드·점수·기한·주기적 효과 확인을 추가하는 방식도 권하지 않는다. 현재 세 주제에서는 경험·현재 해석·열린 후보·실제 반영을 함께 읽는 이득이 크고, 사용자는 그 방향을 수용했다. 일반 작업의 후보 전수 읽기나 상시 추적 없이도 위의 선택된 시도 연결은 보완할 수 있다.

지금 모든 장면을 실제 실행하는 대규모 평가나 전체 대화 재생도 권하지 않는다. 우선 첫 번째 제안의 재개·비적용·종료 조건, 두 번째 제안의 동일 장면 대안 선택을 좁게 확인하면 이 변경을 판단하는 데 직접 필요한 근거를 얻는다. 그 확인이 통과해도 운영 설치·장기 효과·05 전체 마감을 의미하지 않는다.

## 근거 범위와 Main이 결정할 것

직접 읽은 핵심 입력은 고정판 실행 본문·대화/효과 상세·세 경험 주제와 관리·일반 소비 문서, [사용자 인터뷰](../../2026-10-27-ticket05-interview.md)의 관련 직접 발화, [전체 구체안](../../2026-10-27-ticket05-integrated-proposal.md), [05 티켓](../../../current/tickets/05-improvement-loop.md), [넓은 외부 조사](../../2026-10-27-ticket05-broader-reference-investigation.md), 위 외부 보존 원문 두 개다. 원 세션 전체 발화와 외부 자료 전체를 재검증하지 않았으며, 이 리뷰가 전체 세션 훑기의 실제 수행 근거는 아니다.

Main에는 첫 번째를 실행 연결의 구체화로 우선 채택할지, 두 번째를 기존 사례 교체로 채택할지 판단하기를 권한다. 첫 번째도 Work 등록 의무로 구현하면 권고 취지를 벗어나며, 두 번째도 원문 추출 도구의 실제 채택으로 읽으면 범위를 넘는다. 이 보고서는 파일 구조 재설계·새 역할 생성·도구 설치를 승인하거나 수행하지 않았다.
