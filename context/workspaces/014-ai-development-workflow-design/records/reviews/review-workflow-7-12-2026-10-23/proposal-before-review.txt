# 7~12번 — 검토 입력부터 수정·검증 인계까지의 연결안

**현재 지위: 두 묶음 개선 리뷰에 제공할 Main의 초안.** 사용자는7~12번을 연결된 전체안으로 먼저 구체화하고,7~8번과9~12번 개선 리뷰를 받은 뒤7번부터 함께 논의하도록 요청했다.1~5번 합의와 [6번 통합안](2026-10-23-implementation-completion-and-handoff-proposal.md)을 이어받지만, 이 문서의 운영 선택은 아직 사용자 확정이나 실행 스킬 반영이 아니다.

목표는 관련 기준으로 만든 첫 결과를 다른 주체가 다시 판단해 **더 좋은 선택을 발견하고, Main의 선택이 실제 수정과 확인까지 이어지게 하는 것**이다. 요구·계약 위반을 찾는 일과 결함 없는 결과를 더 낫게 만드는 일 모두 포함한다. 검토 지적·대안·수정의 개수를 성공 조건으로 삼지 않는다. Personal은 개인의 판단 기준·이유·조건, Project는 제품 계약·지속 규약·현재 사실, Work는 이번 목표·선택·진행·결과를 계속 소유한다.

## 7. 검토자가 처음 받을 맥락과 자료

### 무엇을 판단하러 왔는지와 무엇을 볼지를 함께 준다

Main은 짧은 과제 설명에 이번 목표·대상·범위·보존 조건·수행 권한을 담고, 실제 원문 위치와 읽을 이유를 연결한다. 검토자는 관련 원문과 실제 결과를 읽어 판단한다. 링크만 전달했다는 사실을 충분한 입력이나 실제 열람으로 취급하지 않는다. 읽을 수 없는 자료는 중요한 내용·조건·출처·미확인 범위를 전달하거나 접근 문제를 드러낸다.

| 처음부터 파악할 의미 | 전달할 자료와 사용 목적 |
| --- | --- |
| 검토 목적·역할 | 현재 [검토 상세](prototypes/development-workflow/skills/development/references/review.md)의 공유 목적·검토자 부분. 요구·기준의 실제 적용과 더 나은 선택을 재판단하며, 발견 없음은 전체 검증 완료가 아님을 공유한다. |
| 이번 목표·범위·보존 조건 | 관련 Spec/Ticket·현재 유효한 사용자 결정·원요구. 변경하지 말아야 할 결과와 재판단 가능한 현재 선택을 구별한다. 서로 충돌하는 원문이나 미결정은 숨기지 않는다. |
| 관련 판단 기준·제품 조건 | 해당 Personal 기준의 의미·이유·적용 조건과 Project의 제품 계약·개발 가이드. Main이 적용했다고 보고한 기준뿐 아니라 이번 요구·변경에서 관련성이 드러나는 기준도 고른다. |
| 실제 결과와 영향 범위 | 비교 기준·현재 코드/문서·미커밋 변경 포함 여부·관련 사용처·검사 접근점. diff는 변화의 진입점이며 판단 대상을 바뀐 줄에 가두지 않는다. |
| 확인한 것과 남은 조건 |6번 인계의 검사 결과·확인 대상·미확인·알려진 문제·중요한 가정. 결과와 근거의 판본이 맞는지 알 수 있게 한다. |
| 현재 선택과 판단을 가른 이유 | 구현자의 중요한 선택·대안·적용 이유와 근거 위치. 제품 계약·실제 사실과 구별해 검토할 주장으로 제공한다. 기존 선택 자체를 유지해야 할 조건으로 올리지 않는다. |

관련 Personal을 기본적으로 숨기거나 Main이 다시 쓴 검토용 원칙집만 주는 안은 택하지 않는다. 실제 관련 본문을 선택하고, 긴 자료의 일부를 지정할 때는 필요한 조건·예외를 함께 포함하며 원문 전체 접근점을 남긴다. 짧고 모두 관련된 Spec이면 전체를 읽고, 큰 Spec이면 이번 범위와 연결 계약을 우선 읽는다.

### 사례·형성 자료·작성자의 이유를 어떻게 다룰까

현재 사용에 필요한 기준 설명·사례와 기준이 만들어진 형성 자료는 역할이 다르다. 요구의 구체 사례·실패 재현·필수 제약·알려진 위험은 첫 입력에 포함한다. 기준을 이해하는 데 필요한 사례도 포함할 수 있다. 같은 대상의 이전 A/B 비교·작성자의 선호 결론·긴 시행착오·모든 `_background`는 기본 입력 전체에 붙이지 않고, 해석·비교·이유 확인에 필요할 때 읽게 한다.

구현자의 이유는 숨기지 않는다. 첫 설명에서 목표·계약·실제 결과와 작성자의 해석을 구별하고, 검토자가 원요구·코드·사용처와 직접 대조하게 한다. 설명을 항상 늦게 공개하거나 단계별로 차단하는 절차는 기본으로 두지 않는다. 의미 있는 제한·환경·트레이드오프를 모른 채 같은 대안을 반복하는 비용도 있기 때문이다.

현재 문서·코드에도 이전 선택이 들어 있으므로 ‘사례 파일을 제외했으니 편향 없는 검토’라고 주장하지 않는다. 독립 재판단을 돕는 핵심은 원자료 접근과 목표/선택의 구별, Main의 선별과 초기 해법도 다시 볼 권한이다. 대화 상속·자동 지침의 실제 전달 방식은13번에서 확인한다.

Personal의 같은 인증 A/B 사례와 상세 형성 자료는 의미나 기존 선택의 근거가 쟁점이 될 때 내려간다. Project·Personal의 README는 선택 경로로 제공하지만 모든 관리 정책을 함께 읽게 하지 않는다. 현재 Spec에 이름 선택이 있다는 이유로 해당 문장을 지우지 않고 ‘현재 해법’으로 대조한다.

짧은 검토 과제의 예는 다음과 같다. 실제 호출 프롬프트의 고정 양식은 아니다.

> 이 인증 완료 예제가 호출자에게 맡긴 일과 끝난 일을 충분히 드러내는지, 같은 목표·보존 계약에서 의미 있게 더 나은 선택이 있는지 검토해 달라. 관련 기준의 적용과 현재 이름·책임 배치 모두 재판단할 수 있다. 저장 전 인증 공개 금지와 후속 조회 실패 분리 등 요구는 원문과 대조하라. 현재 코드·두 소비자·검사와 선택 이유를 함께 제공한다. 이번 배정은 읽기·분석과 허용된 검사, 의견 반환이며 파일 수정은 맡기지 않는다. 발견·대안은 근거와 이득·비용을 연결하고, 조사에서 새로 생긴 중요한 질문도 반환하라.

## 8. 질문에 따라 자료를 더 찾고 Main에 반환한다

Main의 첫 묶음은 출발점이다. 검토자는 현재 판단을 바꿀 질문이 생기면 관련 정본·실제 호출자·피호출자·검사·원문으로 탐색을 넓힌다. 허용된 작업 범위의 추가 읽기마다 승인을 요구하지 않는다. 이미 충분한 근거가 있으면 같은 문서를 재독하거나 전체 context로 펼치지 않는다.

| 새 질문 | 추가 탐색과 판단 |
| --- | --- |
| 이름 문제인가, 실제 완료 시점의 문제인가 | 요구·Project 완료 계약과 호출자가 다음에 하는 일을 함께 본다. 구현자의 이름 설명만으로 판단을 닫지 않는다. |
| 공통 함수로 모으면 더 나은가 | 실제 사용처의 공통 조건·서로 다른 다음 행동과 관련 Personal 기준을 본다. 같은 코드 모양만으로 공통화하지 않는다. |
| 기존 가정이 실제 사용처에서도 성립하는가 | 입력·상태·호출 순서와 검사의 대체 의존성을 따라 확인한다. 필요하면 허용된 재현을 수행하고 관찰·추론을 구별한다. |
| 이전 선택 이유가 불명확하거나 현재 조건과 다르다 | 해당 Work 기록·기준의 형성 자료에서 필요한 이유와 당시 조건을 찾는다. 과거 선택은 재판단할 근거이지 자동 제약이 아니다. |

탐색은 모든 파일을 보았을 때가 아니라, 중요한 의견을 뒷받침할 조건·실제 경로·비교 이득과 비용을 설명할 수 있고 남는 불확실성을 구별할 수 있을 때 멈춘다. 추가 자료가 선택을 바꿀 가능성과 비용을 비교한다. 아직 확인 못 한 사실은 단정하지 않고, 가정에 따라 달라지는 추천을 할 수 있다.

원자료 접근 불가, 요구·계약 충돌, 작업 밖 제품 선택·권한 필요, 주요 주장에 결정적인 정보 공백은 Main에 반환한다. “판단 불가”만 쓰지 않고 풀려는 질문·확인한 것·부족한 것·결정에 미치는 영향·가능한 다음 행동을 연결한다. 해결 가능한 사실 문제를 바로 사용자 선호 질문으로 넘기지 않는다. 읽기 범위를 넓혔다는 이유로 수정 범위도 자동 확대하지 않는다.

## 9. 검토 권한과 의견 반환

**기본 추천은 읽기·분석·허용된 검사·보고다.** 자료를 읽을 권한, 테스트를 실행할 권한, 파일·외부 상태를 바꿀 권한을 구별한다. 검토 과제에서 허용된 로컬 검사·격리된 실험으로 의견을 확인할 수 있다. 검사에 필요한 임시 파일·캐시·실행 상태와 제품 결과·정본을 바꾸는 권한은 구별하고, 실제 허용 범위를 과제에 맞춘다. 제품 파일·정본 수정, 데이터 변경, 외부 호출이나 설치가 필요한 행동은 기존 사용자 권한과 Main의 배정에 따른다. 역할 이름에서 새 권한을 추론하지 않는다.

의견은 실제 문제가 있는지뿐 아니라 더 좋은 선택이 있는지도 다룬다. 중요한 의견에는 대상·조건·관찰/추론·근거·왜 중요한지·대안의 이득과 비용·남은 가정을 연결한다. 모든 의견에 대안을 의무로 붙이지 않으며, 결함·개선·확인 공백을 같은 심각도로 취급하지 않는다. 강한 단정이 판단을 돕지 않는다면 조건부 추천으로 반환한다.

발견이 없거나 현재안 유지가 좋다면 무엇을 비교했고 판단을 가른 이유와 확인 한계를 짧게 밝힌다. 모든 읽기 목록·체크리스트 답안을 제출하지 않는다. 후속 수정 권한을 함께 부여하는 선택은 가능하지만, 그 경우 분석 결과와 실제 변경·확인을 구별해 반환하고11번의 작성 책임을 함께 맞춘다.

기본을 이렇게 추천하는 이유는 검토자가 현재안·Main의 선택을 평가하는 순간과 그 의견을 채택하는 순간을 구별하기 위해서다. 사소한 명백한 수정까지 긴 승인 절차로 만들지는 않으며 Main은 기존 위임 안에서 즉시 판단·배정할 수 있다. 검토자 직접 수정이 유리한 경우의 비용·조건은 사용자와9·11번을 함께 논의한다.

## 10. 언제 어떤 범위로 검토를 호출할까

6번 수준의 첫 결과를 만든 뒤 별도 관점이 선택을 개선할 가치가 있는 개발 작업에 검토를 붙인다. 목표는 사용자에게 전달하기 전에 실제 결과·설계·기준 적용을 더 좋게 만드는 것이다. 매 커밋·모든 파일·모든 응답을 호출 단위로 삼지 않는다.

| 상황 | 추천하는 호출 |
| --- | --- |
| 새로운 동작, 여러 사용처, 상태·실패·계약 변화, 의미 있는 구조·표현 선택 | 첫 완성 뒤 관련 결과와 영향 범위를 함께 검토한다. 파일 수보다 판단의 내용과 파급을 본다. |
| 큰 구현 전에 선택 비용이 커지거나 구현 중 반복 마찰이 생김 | 의문인 설계·사용 장면을 좁혀 중간 의견을 받는다. 부분 구현과 미결정을 밝혀 완성 결과 검토와 구별한다. |
| 요구와 수정이 국소적이고 관련 판단이 결정적 검사로 충분히 확인됨 | 별도 검토를 생략하거나 짧게 줄일 수 있다. Main이 범위·기계 검사 밖 판단의 유무를 보고 정한다. 단순히 변경이 작거나 이미 테스트가 통과했다는 이유로 생략하지 않는다. |
| 여러 독립 결과가 병렬 진행됨 | 결과 단위로 검토를 나눌 수 있으나 공유 계약·통합 영향의 담당을 Main이 남긴다. 부분 검토를 합한 것만으로 전체 정합성을 확인했다고 보지 않는다. |

검토자가 보는 코드가 계속 바뀌면 Main은 기준 상태와 이후 변경을 식별해 의견의 유효 범위를 맞춘다. 모든 작업을 멈추는 고정 관문으로 만들 필요는 없지만, 다른 판본에 대한 의견을 현재 결과에 그대로 적용하지 않는다.

## 11. Main의 선택을 실제 수정과 확인으로 잇는다

Main은5번 합의대로 관찰·문제의 타당성과 해결안의 채택을 구별한다. 연결된 의견을 함께 보고 채택·조정·현행 유지·필요한 확인·후속 분리를 결정한다. 알려진 필수 미충족은 후속 분리라는 이름만으로 완료 처리하지 않는다.

기본 수정 담당은 원 구현자로 추천한다. 구현 맥락과6번의 자기 확인 책임을 이어받아 수정할 수 있기 때문이다. Main이 직접 구현했으면 Main이 수정할 수 있고, 원 구현자가 없거나 특정 전문성이 필요하면 다른 담당자에게 결과·결정·근거를 넘긴다. 같은 구현자를 이어 쓰든 새 담당자를 쓰든 최신 결과·변경된 지시·채택 이유를 맞춰 주며, 이전 대화 기억만으로 수정 과제를 대신하지 않는다. 검토자에게 수정까지 맡길 경우에도 별도 배정으로 드러내고 같은 부분을 동시에 고치지 않는다.

수정 요청에는 채택한 문제와 해결 방향, 보존 조건, 영향을 받는 요구·검사, 남은 선택을 연결한다. 리뷰어의 모든 문장을 지시로 복사하지 않는다. 수정자는 지시의 전제가 실제 결과와 맞지 않거나 새 충돌이 드러나면 근거와 대안을 Main에 반환하고, 기존 위임 안에서 풀 수 있는 세부 선택은 스스로 처리한다.

수정 뒤에는 무엇을 바꿨고 어떤 의견을 어떻게 해소했는지, 영향받는 확인 결과와 남은 문제를 반환한다. Main은 실제 변경과 근거를 대조해12번 재검토·검증으로 연결한다. 의견 수신·채택·수정 완료·확인 완료는 각각 구별한다.

## 12. 재검토·검토 종료·검증 인계

수정으로 새 판단이나 의미 있는 파급이 생기면 해당 질문을 다시 검토한다. 이미 유효한 전체 검토를 무조건 반복하지 않고 바뀐 부분과 연결 영향을 선택한다.

| 수정·잔여 상태 | 다음 확인 |
| --- | --- |
| 채택한 뜻이 분명하고 국소 수정과 직접 검사로 해소를 확인할 수 있음 | Main이 변경·근거를 확인하고 검증에 연결한다. 같은 의견을 다시 얻기 위한 검토를 반복하지 않는다. |
| 책임·계약·사용처·기준 적용이 달라졌거나 새 절충이 생김 | 영향을 받는 질문을 재검토한다. 기존 검토자를 이어 쓰면 앞선 우려·변경을 함께 주고, 새 관점이 필요하면 역할을 다시 배정한다. |
| 사실·요구 충돌이 남아 선택을 못 함 | 필요한 확인·권한 있는 선택으로 돌린다. 같은 입력으로 검토자 수나 반복 횟수만 늘려 해결된 것으로 보지 않는다. |

검토를 닫으려면 중요한 의견의 처리 이유가 정리되고, 채택한 수정이 실제 반영됐으며, 설계 판단에 영향을 주는 미해결이 해소되거나 무엇이 남았는지 책임과 다음 행동이 드러나야 한다. 검토자의 동의나 지적0개를 종료의 필수 조건으로 만들지 않는다. 유효한 개선은 비용·범위 때문에 후속으로 둘 수 있으나 필수 요구 미충족은 해결 또는 권한 있는 범위 재판단이 필요하다.

검증자에게는 최신 대상·판본, 요구·보존 계약·중요한 사용 조건, 수정으로 달라진 것과 영향 범위, 기존 확인의 근거·한계·남은 확인을 전달한다. 검토 의견의 다수결이나 구현자의 ‘완료’ 주장은 요구 충족의 근거를 대신하지 않는다. 검증자는 기존 검사의 결과뿐 아니라 그 검사가 요구를 뒷받침하는지 보고 필요한 직접 확인을 수행한다. 세부 검증 도구·시나리오는 [01-03](../current/tickets/01-development-workflow/01-03-behavior-verification.md)에서 구체화한다.

검토에서 설계 판단을 닫은 것과 최종 결과를 충분히 검증한 것은 다르다. 검증 실패가 국소 구현 문제라면 수정·해당 확인으로, 계약·설계 전제의 문제라면 관련 검토 질문으로 돌아간다. Main은 그 결과와 확인 한계를 종합해 완료 여부를 판단하고 사용자 선택·수락이 필요한 부분을 구별한다. 전체 완료 전에 필요한 확인이 남았다면 그 상태를 그대로 전달한다.

## 작성·리뷰·사용자 논의의 상태

이 초안을7~8번,9~12번 두 묶음의 개선 리뷰어에게 전체안·목표·기존 구조·원자료 접근점과 함께 전달한다. 리뷰어는 담당 묶음을 중심으로 더 좋은 행동·결과를 만들 제안을 하며 연결 문제도 지적할 수 있다. Main이 두 의견의 충돌·비용·영향을 종합한 뒤 사용자와7번부터 논의한다. 각 리뷰의 추천과 Main의 채택은 사용자 확정·실행 본문 적용·효과 입증과 구별한다.
