# 검증안 1~6 개선 리뷰 — 기대 결과와 증거 선택을 실제 행동으로 잇기

2026-10-24. [공통 의뢰](README.md)와 [리뷰 전 전체안](proposal-before-review.txt) 전체를 읽고 목적·시작·입력·방법·기계 검사·독립 근거를 중심으로 검토했다. 사용자 목표와 확정된 development 구조를 유지하면서 더 나은 결과를 만들 선택을 제안한다. 적합성 승인이나 제품 실행 검증은 아니다. 아래의 위험은 문서 해석과 설계 대조에서 찾은 것이며, 이 운영안을 실행해 재현한 실패가 아니다.

**가장 큰 개선은 검증자에게 검사 목록을 더 주는 것이 아니라, 독립적인 기대 결과를 먼저 세우고 현재 결론을 바꿀 미확인부터 해소하게 하는 것이다.** 여기에 구현 초기에 필요한 관찰 준비와 마지막에 확인할 개선 결과의 범위를 연결하면, 기존 역할을 늘리지 않고도 늦은 재작업과 형식적인 완료를 줄일 수 있다.

## 1. 요구에서 기대 결과를 세우는 판단을 작성자 증거의 평가보다 앞에 둔다

초안 3은 최신 요구·계약·기존 확인을 함께 제공하고, 4는 관찰될 동작을 잡으며, 5는 독립 기대값을 요구한다. 방향은 맞다. 다만 실제 시작 행동에서는 작성자가 만든 테스트와 완료 설명을 읽은 뒤 그 목록의 충분성만 판단해도 이 문장을 따랐다고 느끼기 쉽다. **검증자가 직접 정할 것은 추가 테스트 하나뿐 아니라, 무엇을 성공과 실패로 구별해야 하는지다.** Main의 확인 주장은 출발점이며 전체 요구의 경계와 같다고 가정하지 않아야 한다.

구체 장면은 인증이다. 작성자가 “조회 실패에도 로그인은 성공한다”와 통과 로그를 주면, 검증자는 실패 후 signed-in이 남는지만 확인하기 쉽다. 그러나 [제품 계약](../../prototypes/development-workflow/noline-demo/context/project/guidance/authentication-and-session/INDEX.md)은 저장 중 새 인증 비공개, 저장 실패 때 이전 데이터 보존, 후속 조회 실패와 인증 실패의 분리, 다음 소비자의 최신 결과 필요 여부를 각각 구별한다. 특히 “조회 실패가 인증을 되돌리지 않는다”에서 “모든 소비자는 조회를 기다릴 필요가 없다”는 결론은 나오지 않는다. [현재 Work의 가정](../../prototypes/development-workflow/noline-demo/context/work/workspaces/001-login-completion-names/current/memory/spec/05-constraints-design-assumptions.md)도 그 차이를 명시한다.

[독립 검토 기준](/Users/hammyeong-yeon/.claude/references/independent-review.md)은 verifier의 근거 탐색과 판정을 독립시킨다. [Matt tests](../../../source/workflow-references/matt-pocock/repository/skills/engineering/tdd/tests.md)는 구현과 같은 계산을 반복하는 기대값을 피한다. 이 두 원칙을 연결하면 입력을 숨기는 방법보다 **요구에서 기대를 만드는 일과 작성자 설명을 평가하는 일을 분리하는 방법**이 적절하다. Personal·Project를 공유한다는 기존 합의와도 양립한다.

검증안 3~4의 첫 행동을 다음처럼 구체화할 것을 권한다.

> 검증자는 원요구·유효한 정정·제품 계약과 사용처에서 이번 결과의 중요한 성공·실패를 구별할 관찰을 먼저 정한다. 그 뒤 작성자의 주장·테스트·기존 근거가 이를 어디까지 확인하는지 대조한다. 작성자가 제시한 주장 밖에도 이번 요구에 필요한 결과가 빠졌으면 확인 범위에 연결한다. 계약 자체의 충돌은 Main에 반환하고, 이미 정해진 계약의 구체적인 확인 방법은 검증자가 선택한다.

이것은 파일 열람의 엄격한 순서를 통제하거나 기대값 문서를 새로 제출시키자는 제안이 아니다. 실제 자료를 읽다 기대를 수정할 수 있고 그 이유를 남기면 된다. 짧은 작업은 머릿속 대조로 충분하다. 이득은 작성자와 같은 가정을 반복할 가능성을 줄이는 것이고, 비용은 중요한 약속을 한 번 독립적으로 구성하는 시간이다. 모든 요구를 별도 명세로 다시 쓰거나 Main의 과제를 임의 확장하는 데 쓰면 이득이 사라진다.

## 2. 검사 종류보다 ‘어떤 미확인을 어떤 관찰로 가를지’를 방법 선택의 중심에 둔다

초안 4의 작업 유형 표와 5의 검사 설명은 후보를 찾는 데 유용하다. 6의 “작은 수정은 … 큰 통합은 …”은 보조 설명으로는 맞지만, 확인 깊이를 정하는 핵심 기준으로는 약하다. 한 줄의 저장 순서 변경이 큰 결과를 낼 수 있고, 넓은 이름 변경은 기존 근거와 직접 대조로 닫힐 수 있다. 사용자에게 필요한 것은 테스트 기법의 목록보다 **지금 불확실한 약속을 무엇으로 가장 잘 구별할 수 있는가**다.

[pstack 형식 검증 원문](../../../source/workflow-references/pstack/repository/skills/create-formal-verification-skill/SKILL.md)은 검사하기 쉬운 대상을 고르기보다 깨졌을 때 사용자 피해가 크고 테스트가 잘 닿지 않는 약속을 고른다. 도구도 질문을 가장 낮은 비용으로 해결하는 것으로 정한다. [책임 배치 기준](/Users/hammyeong-yeon/.claude/references/ai-system_behavior-responsibility-allocation.md)은 실패 영향뿐 아니라 탐지·복구 가능성을 함께 본다. [Matt mocking](../../../source/workflow-references/matt-pocock/repository/skills/engineering/tdd/mocking.md)의 경계 대체도 이 관점에서 선택해야 한다.

아래는 같은 인증 주제라도 방법이 달라지는 설계 비교다. 현재 demo에 새 요구나 도구를 추가하라는 뜻이 아니다.

| 남은 질문 | 먼저 고를 방법과 구별할 결과 | 비용과 확인 한계 |
| --- | --- | --- |
| 저장 완료 전에 성공을 알리는가, 조회 완료를 불필요하게 기다리는가 | 기존 공개 진입을 호출하고 저장·조회 Promise를 각각 멈추는 검사. 각 시점의 공개 상태·반환·소비자 행동을 본다. | 현재 demo의 [검사](../../prototypes/development-workflow/noline-demo/examples/authentication/tests/authentication.test.mjs)가 이미 이런 방법을 사용한다. 같은 의미를 새 테스트로 복제할 필요가 없다. 실제 저장소 원자성은 확인하지 않는다. |
| 실제 저장 어댑터가 부분 쓰기 후 실패해도 이전 데이터를 보존하는가 | 실제 어댑터의 실패 지점을 통제하고 다시 읽거나 재진입해 보존을 확인한다. | demo의 성공/실패 어댑터 가정만으로는 답할 수 없다. 실제 대상·격리·복구 준비가 필요하다. 브라우저 정상 경로를 여러 번 실행하는 것보다 이 경계의 관찰이 중요하다. |
| 로그인·로그아웃이 겹치는 여러 순서에서 계정 귀속이 유지되는가 | 실제 요구에 포함되면 좁은 순서 재현부터 시작하고, 순서 수 때문에 공백이 남으면 상태 기반 생성 검사나 작은 모델 검사를 비교한다. | 현재 demo의 범위 밖이다. 모델이 한 단계로 취급한 동작이 실제 코드에서도 그렇게 묶이는지 별도 확인해야 한다. 모델 도입이 실제 어댑터 검사를 대체하지 않는다. |
| AI 스킬 수정이 처음 보는 요청에서도 기준을 찾아 적용하는가 | 형식 검사와 별개로, 결과를 미리 보여주지 않은 관련 새 사례에서 실제 수행·결과를 관찰한다. 수정 효과가 주장이라면 이전판과의 차이를 비교한다. | [Vercel의 eval 설명](../../../source/lectures/vercel-product-design%20%281%29.md)은 정답 편집을 숨긴 사례와 스킬 없는 조건을 사용하고 규칙 충족과 기존 결과 유사성을 따로 본다. 한 번의 성공을 일반 효과로 확대할 수 없으며, 모든 코드 변경에 이 평가를 붙이지 않는다. |

검증안 4의 방법 선택과 6의 깊이 선택을 잇는 본문으로 다음을 권한다.

> 현재 요구 충족 판단을 가장 크게 바꿀 미확인을 먼저 찾고, 이를 구별할 관찰을 고른다. 우선순위는 변경량보다 사용자 결과에 미치는 영향, 기존 근거의 공백, 실패를 발견·복구할 수 있는 정도로 정한다. 기존 근거가 해당 질문에 답하면 재사용하고, 답하지 못하는 경계만 더 확인한다. 실행 결과가 새 의문을 만들면 방법을 바꾸며, 같은 근거를 늘리는 것만으로 확신을 높이려 하지 않는다.

검사가 결함을 놓칠 가능성이 구체적으로 의심될 때에는 “실패할 수 있는가”도 그 질문에 포함한다. 예컨대 저장 전 상태 공개가 금지라면 해당 순서를 좁게 깨뜨렸을 때 기존 검사가 잡는지 보는 대조는 가치가 있다. 모든 검사를 변형해 보는 절차로 만들 필요는 없다.

이 개선의 이득은 쉬운 검사만 많이 실행하거나 비싼 전체 실행을 습관적으로 반복하는 일을 줄이는 것이다. 비용은 검사 선택 이유를 중요한 공백에 대해 짧게 설명해야 한다는 점이다. 실패 영향 점수표나 위험 등급별 의무 검사 묶음으로 만들지 않는 편이 좋다. 사용자와는 기법 이름별 채택 여부보다 위와 같이 **조건이 바뀌면 어떤 관찰로 바뀌는지**를 먼저 논의할 수 있다.

## 3. 최종 검증은 최신 결과를 대상으로 하되, 관찰 가능한지의 확인은 구현에 늦지 않게 연결한다

초안 2는 외부 실행 경로나 데이터 접근을 초기에 확인한다. 이를 **접근 가능 여부에서 필요한 실패·보존 조건을 관찰할 수 있는지까지** 확장하면 마지막 단계의 재작업을 줄일 수 있다. API에 접속할 수 있어도 저장 중간 실패를 만들 수 없거나, 재시작 뒤의 상태를 읽을 수 없다면 중요한 계약의 확인 가능성은 아직 모르는 상태다.

현재 demo는 저장 실패 때 이전 값을 유지하는 어댑터와 정상 반환하는 callback을 가정한다. 이는 예시 범위에서는 적절하게 드러난 한계다. 이 코드를 실제 제품에 연결하는 가상 장면에서는, 구현·개선 검토가 끝난 뒤 실제 어댑터가 그 가정을 충족하지 않는다는 사실을 발견하면 검증 문제가 설계 재작업으로 커진다. 이 예시는 현재 demo의 결함 판정이 아니라 **향후 통합 때 달라지는 조건**이다.

[development 구현자 계약](../../prototypes/development-workflow/skills/development/SKILL.md)은 실제 사용 경로까지 완성하고 요구에서 자기 확인을 도출하도록 이미 요구한다. [pstack refactoring](../../../source/workflow-references/pstack/repository/skills/poteto-mode/playbooks/refactoring.md)은 구조를 옮기기 전 보존 동작의 기준선을 확보하고, [pstack bug-fix](../../../source/workflow-references/pstack/repository/skills/poteto-mode/playbooks/bug-fix.md)는 원래 표면의 재현을 수정에 앞서 둔다. [Vercel lint 절](../../../source/lectures/vercel-product-design%20%281%29.md)도 값싼 피드백을 작업 중에 받는 이득을 설명한다. 이 부분을 마지막 검증자만의 일로 새로 만들 이유가 없다.

검증안 2에 다음을 연결할 것을 권한다.

> 중요한 약속의 확인에 특수 데이터·실패 주입·전후 기준선·실제 어댑터 관찰이 필요하면 Main과 구현자는 구현 중에 그 확인 가능성을 확보한다. 가능 여부가 설계 선택을 바꾼다면 가장 작은 재현이나 관찰부터 수행한다. 이 준비 결과는 최종 검증의 입력이며 독립 판정을 대신하지 않는다. 별도 검증자는 최신 결과에서 준비된 방법의 적절성과 실제 근거를 다시 판단한다.

최종 검증자를 일찍 호출해 전체 설계를 승인받거나, 모든 작업에 사전 검증 계획서를 만드는 방식은 권하지 않는다. 자료로 풀 수 없는 중요한 방법 선택에만 좁은 도움을 구할 수 있다. 확정된 구현·개선 검토 뒤의 별도 검증 경계는 유지한다. 이득은 수정이 비싸지기 전에 관찰 공백을 발견하는 것이고, 비용은 해당 작업에 필요한 작은 실험·실행 준비다. 권한 밖 실제 환경 조작은 이 문구로 승인되지 않는다.

## 4. 동작 보존과 함께 ‘이번에 약속한 개선이 실제 반영됐는가’를 확인할 연결을 남긴다

초안 1은 설계 대안 탐색을 앞선 개선 검토의 중심으로 두며, 대표 리팩터링 장면은 읽기 쉬움 개선의 근거를 이어받고 전체 대안 비교를 반복하지 않는다고 설명한다. 이 경계는 유지할 만하다. 그러나 **동작이 같다는 근거와 이번 변경의 목적을 달성했다는 근거는 다르다.** 리팩터링·이름·문서가 작업의 핵심인 경우 최종 검증을 동작 보존만으로 읽으면, 수정 과정에서 의도한 개선이 사라져도 통과할 수 있다.

현재 [Work의 품질·완료 기준](../../prototypes/development-workflow/noline-demo/context/work/workspaces/001-login-completion-names/current/memory/spec/04-quality-and-completion.md)은 “호출부에서 인증 적용과 조회 완료의 차이를 이해할 수 있고” 두 소비자가 필요한 결과만 안내해야 한다고 말한다. 함수명 문자열과 테스트 통과만 확인해서는 이 요구의 근거가 완성되지 않는다. 반대로 모든 이름 후보를 다시 탐색해 최선임을 증명할 필요도 없다. 최종 코드·호출부·설명에서 인증 완료와 화면 준비의 구별이 실제로 유지됐는지, 필요한 설명을 찾을 수 있는지의 좁은 확인은 가능하다. 새로운 사용자가 항상 더 잘 이해한다는 효과까지 말하려면 별도 관찰이 필요하다.

[확정 development](../../prototypes/development-workflow/skills/development/SKILL.md)는 수정자가 “해결한 문제와 개선 이득”을 반환하고 Main이 “실제 수정 결과·확인, 얻은 이득과 새 부담”을 본다고 정한다. 이 책임을 검증자에게 전부 옮기자는 제안은 아니다. **이미 채택한 개선과 최신 결과 사이에서 누가 무엇을 확인했는지 인계가 이어져야 한다.** [pstack refactoring](../../../source/workflow-references/pstack/repository/skills/poteto-mode/playbooks/refactoring.md)도 동작 보존 증명과 변경을 유지할 가치의 확인을 별개로 둔다. 그 자료의 강한 구조 처방이나 자동 되돌리기 규칙은 가져올 필요가 없다.

검증안 1과 3의 범위를 다음처럼 보완할 수 있다.

> 이번 요구나 채택한 수정에 동작 외의 명시된 결과가 포함되면, 그 결과가 최신 산출물에 반영됐는지도 확인 대상에 연결한다. 더 나은 대안을 전부 다시 탐색하지 않고, Main이 확인한 개선 근거를 재사용하거나 남은 확인을 좁혀 맡는다. 구조·이름·설명에서 직접 확인한 반영과, 실제 사용자의 이해·유지 효과에 대한 추정을 구별한다.

이득은 “회귀 없음”을 “이 작업의 목적 달성”으로 잘못 올리는 일을 줄이는 것이다. 비용은 요구에 포함된 비기능 결과를 어떤 근거로 확인할지 한 번 구체화하는 정도다. 주관적 취향을 새 통과 기준으로 만들거나, 구현·개선 검토가 끝난 뒤 또 다른 전면 설계 심사로 키우면 안 된다.

## 유지할 선택

- 개선 검토와 별도 검증을 구별하고, 검증자는 자기 제품 수정 없이 기대 결과·관찰·판정을 반환하는 방향을 유지한다. 세션이 새롭다는 사실만으로 독립성이 완성됐다고 보지 않는 설명도 유지한다.
- 기계 검사를 적극 사용하되 assertion·실행 경계·mock의 한계를 읽는 선택은 핵심이다. Matt 원문의 내부 대체·DB 직접 관찰 경고를 무조건적인 금지로 옮기지 않은 점도 유지한다. 인증에서는 공개 시점과 저장 부작용 자체가 계약일 수 있다.
- 기존 근거 재사용은 유지한다. [pstack shipping](../../../source/workflow-references/pstack/repository/skills/poteto-mode/playbooks/shipping.md)의 매 PR 실제 실행 규칙보다 이 작업 체계에 유연하다. 동일 명령을 다시 실행했다는 사실보다 근거의 유효성과 충분성을 따로 판단하는 편이 중요하다.
- 실제 앱 실행은 증거 수집 방법이고, [Verify](../../../../../../reference-project/context/work/harness/verify/README.md)는 고정 명령·snapshot·receipt를 남기는 실행기라는 구별을 유지한다. 검증자 역할을 새 전역 agent나 Verify schema로 먼저 고정할 필요가 없다.

## Main과 사용자에게 남길 논의

위 제안 중 먼저 논의할 것은 두 가지다. 첫째, 검증자가 Main의 전달 주장에 빠진 이번 요구도 복원해 기대 결과를 구성한다는 책임을 어디까지 명시할지다. 추천은 원요구·유효 계약 안에서 적극적으로 복원하되, 계약 변경은 Main·사용자의 선택으로 남기는 것이다. 둘째, 이름·구조·문서 개선이 작업 목적일 때 Main의 최종 확인과 검증자의 좁은 확인을 어떻게 나눌지다. 추천은 Main의 선택 책임을 유지하면서 최신 결과의 반영 여부와 근거 공백은 검증 인계에 드러내는 것이다.

기법 선택은 사용자에게 TDD·속성 검사·형식 검증 중 하나를 보편 기본값으로 고르게 하기보다, 2절의 구체 장면처럼 이득·비용이 달라지는 조건으로 논의하는 편이 낫다. 별도 검증자의 기본 호출 범위와 단순 변경 축소는 현재 제안대로 논의 가능한 선택이지만, 이 리뷰가 실제 비용·효과를 입증한 것은 아니다.

본문을 수정할 때에는 새 주의문을 맨 뒤에 누적하기보다 3~4의 시작 행동, 4~6의 선택 기준, 2의 조기 준비, 1·3의 확인 범위를 각각 교체·통합하는 편이 좋다. 역할·단계·필수 보고 항목의 수를 늘릴 필요는 없다.

## 읽은 근거와 한계

전체를 읽은 핵심 대상은 공통 의뢰와 `proposal-before-review.txt`, 확정 development·review·execution, 2026-10-24 전체 틀 기록, 01-03, 독립 검토·책임 배치 기준, Matt TDD·tests·mocking, pstack shipping·feature·bug-fix·refactoring·create-verification·create-formal-verification이다. Spec은 문제·목표·대표 사례·전체 구상·현재 초점 부분을, 04-03은 현재 상태·책임·완료 조건을 중심으로 읽었다. 강연은 Matt의 자동 검사와 거짓 확신, Lauren의 검증 단계·실제 제어·Feature Map, Vercel 글은 lint·eval 관련 절을 직접 읽었다.

demo는 진입 지침, context·Project·Personal README, 인증 계약, Work의 동작·품질·가정, 인증 서비스 코드와 해당 테스트 전체를 읽었다. Verify는 현재 README의 소유 계약과 한계를 읽었다. 원문에 대한 판단과 이 문서의 추천은 구별했으며, 외부 자료의 모든 처방을 공통 규칙으로 채택하지 않았다.

상대 리뷰 파일은 읽지 않았다. 실제 Noline, UI·기기·DB 연결, 현재 운영 도구, 이번 검증자 실행 효과는 확인하지 않았다. 제품 코드·테스트를 실행하거나 수정하지 않았고, 검토 보고 파일 하나만 작성했다. 본문 예시는 확인 방법을 비교하기 위한 가상 적용이며 새로운 테스트 결과가 아니다.
