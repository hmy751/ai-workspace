# 검증안 7~12 개선 리뷰

2026-10-24. [고정 초안](proposal-before-review.txt) 전체를 읽고 실제 실행·권한·반환·수정·종료·기록 연결을 중심으로 비교했다. 적합성 승인이나 제품 실행 검증이 아니다. 아래 제안은 채택 전이며, 다른 리뷰어의 보고는 읽지 않았다.

**가장 큰 개선은 실패 장면을 계약 위반과 구별하는 대표 예시, 검증을 막는 실행 공백을 실제로 해결하는 담당 연결, 독립 재현을 수정 뒤에도 유지하는 흐름이다.** 역할이나 검사 종류를 더 늘리기보다 현재 안의 세 연결을 강화하는 편이 사용자 목표에 직접 도움이 된다.

## 1. 오류가 발생한 장면에서도 요구를 충족할 수 있음을 실제 판정과 수정 배정에 반영한다

초안의 첫 대표 장면은 “인증 뒤 목록 조회가 실패한다. 구현자 테스트는 모두 통과했다”이며, “mock이 조회 실패를 숨기면 독립 사례를 만들고 구현자에게 수정·회귀 검사를 맡긴다”고 이어진다. 이 예시는 본문의 요구 중심 판단보다 실패를 곧바로 수정으로 연결하는 힘이 강하다.

실제 [demo 인증 계약](../../prototypes/development-workflow/noline-demo/context/project/guidance/authentication-and-session/INDEX.md)은 후속 조회가 동기·비동기로 실패해도 이미 적용한 인증을 유지하고 조회 오류를 별도로 전달하도록 정한다. 조회가 끝나기 전에 이동·닫기를 시작하는 선택도 현재 소비자의 계약이다. [검사 코드](../../prototypes/development-workflow/noline-demo/examples/authentication/tests/authentication.test.mjs)는 이 오류 분리를 이미 명시적으로 검사한다. 코드와 보존된 [실행 기록](../../prototypes/development-workflow/noline-demo/context/work/workspaces/001-login-completion-names/records/2026-10-19-03-execution.md)을 읽은 사실이며, 이번에 다시 실행한 결과는 아니다.

따라서 이 장면에서 검증자가 더 잘해야 할 일은 조회 오류 제거가 아니라 **실패 조건에서 약속한 상태·전달·다음 행동이 유지되는지** 판단하는 것이다. 검사에 오류 사례가 빠져 있어도 독립 확인에서 동작이 맞으면 검사 공백을 보완할지 정하면 된다. 제품 수정이 자동으로 따라오지는 않는다. 반대로 후속 조회 실패를 로그인 실패로 전파하거나 인증을 지웠다면 계약 위반이다. 인증 수단의 거부가 별도로 확정된 경우는 같은 계약에서도 다른 처리이며, 현재 demo는 이를 구현하지 않았다.

이는 새 원칙을 얹자는 제안이 아니다. [development의 구현자·수정 계약](../../prototypes/development-workflow/skills/development/SKILL.md)이 요구하는 제품 계약 적용과 “관찰의 타당성/해결책 분리”를 검증안의 실제 예시까지 일치시키자는 것이다. Matt의 [tests](../../../source/workflow-references/matt-pocock/repository/skills/engineering/tdd/tests.md)는 사용자·호출자가 기대하는 관찰 가능한 결과를 기준으로 삼는다. pstack의 [bug-fix](../../../source/workflow-references/pstack/repository/skills/poteto-mode/playbooks/bug-fix.md)도 실행 근거에 맞는 수정만 요구한다. 오류가 관찰됐다는 이유만으로 모든 경로를 성공하게 만드는 처방은 이 근거들에서 나오지 않는다.

**본문 수정 제안:** 검증안9의 문제 분류를 늘리기보다, 판정과 수정 사이를 다음처럼 설명한다.

> 정상 경로와 실패 경로 모두 요구·계약에서 기대한 결과로 판정한다. 오류가 관찰돼도 약속한 상태 보존과 오류 전달·후속 행동이 맞으면 그 실패 처리 요구에는 충족 근거가 된다. 검사 공백과 제품 결함을 구별하고, 제품 수정은 어긋난 약속을 특정한 뒤 배정한다.

첫 대표 장면은 “조회가 실패했는데 인증까지 실패 처리된다”처럼 구체적인 계약 위반 가정으로 바꾸거나, “조회는 실패하지만 인증 유지·별도 오류 전달이 맞으면 해당 요구를 충족한다”는 유지 분기를 함께 보여 주는 편이 좋다. 현재 demo에서 실제 버그를 발견했다는 표현은 쓰지 않는다.

**이득과 비용:** 오류를 없애려다가 의도한 비대기 흐름이나 인증 보존을 망가뜨리는 수정을 줄이고, 맥락을 읽는 이유를 실제 행동으로 보여 준다. 비용은 예상 오류 상태를 계약에서 해석하는 일이다. 모든 오류를 정상이라고 합리화하지 않도록 그 주장을 지지하는 계약과 이번 사용자의 결과를 함께 읽어야 한다. 계약이 최신 화면 데이터까지 요구한다면 인증만 성공했다는 근거로 닫을 수 없다.

## 2. 실행 공백의 첫 해결과 반복 실행 자산에 대한 투자를 구별한다

검증안2는 접근 문제를 초기에 드러내도록 하고, 7은 “공백이 반복되면 … 보완할 후보로 돌린다”, 10은 “환경 공백은 실행 준비·접근 해결”로 잇는다. 방향은 맞지만 **이번 요구를 확인하는 데 꼭 필요한 첫 실행 경로를 누가 완성하는지**가 일반적인 후속 후보와 함께 남는다. 첫 실행부터 막히는 중요 경로는 반복 여부를 기다릴 일이 아니다.

예를 들어 기능 코드는 완성됐지만 테스트 계정으로 접근하는 방법이나 초기 데이터 준비가 없어 실제 저장·재진입을 확인하지 못하는 장면을 생각할 수 있다. 검증자가 매번 임시 해결책을 만들거나 “실행 환경 미확인”을 반환하는 것으로 끝내면 Main과 사용자가 그 공백을 반복해서 메운다. 이것은 앱 제어 도구를 일괄 새로 설치해야 한다는 뜻도 아니다. 현재 demo에는 이미 [실행 명령과 범위](../../prototypes/development-workflow/noline-demo/README.md)가 있어 새 CLI를 만들 이유가 없다. 실제 Noline의 현재 실행 가능성은 이 리뷰 범위에서 알 수 없다.

[Lauren 강연의 Practical verification skills](../../../source/lectures/03_Agent_신뢰_강연_전체번역.md)는 매 세션 다른 스크립트를 만드는 부담을 줄이기 위해 실행 수단에 투자하고, 기능에 접근하는 방법을 함께 제공한 이유를 설명한다. [create-verification-skill](../../../source/workflow-references/pstack/repository/skills/create-verification-skill/SKILL.md)의 1·2·4절은 기존 실행 수단을 먼저 찾되, usable 상태까지의 준비·실제 조작·관찰·정리를 한 번 직접 수행해야 절차를 전달할 수 있다고 한다. 초안은 새 도구의 일괄 도입을 잘 줄였지만, 이 자료의 적극적인 실행 기반 개선까지 “반복되면 후보”로 약화시킬 필요는 없다.

**본문 수정 제안:** 검증안7의 마지막 운영 문단을 다음 의미로 보완한다.

> 이번 요구의 중요한 결과를 관찰할 경로가 없으면 Main이 그 공백의 해결 담당과 필요한 범위를 정한다. 기존 권한 안의 로컬 준비·임시 계측은 검증자가 수행할 수 있고, 제품·지속 테스트·실행 도구의 변경이 필요하면 해당 담당에게 배정한다. 이번 확인을 막는 준비와 반복 사용을 위한 도구 투자를 구별한다. 새로 만들거나 고친 실행 절차는 실제로 사용해 확인한 범위와 함께 기존 Project 실행 안내 또는 로컬 도구의 Owner에 남긴다.

권한 연결에는 한 가지 구체화가 유용하다. `test mode`나 `dry-run`이라는 이름만으로 공유 데이터·발송·비용이 차단됐다고 보지 않고, 그 경계를 중요한 확인에 사용할 때 실제 격리 설정이나 도구가 제공하는 제약을 확인한다. 이는 pstack의 Evidence 절과 [판단·보장·권한 배치](/Users/hammyeong-yeon/.claude/references/ai-system_behavior-responsibility-allocation.md)의 실제 집행 구별에 근거한다. 모든 검사 앞에 새 승인 절차를 붙일 필요는 없다.

**이득과 비용:** 첫 적용에서도 사용자 요구를 확인할 수 있는 상태를 만들며, 뒤의 담당자가 같은 준비를 다시 발명하는 비용을 줄인다. 비용은 이번 작업에 필요한 작은 실행 보완이다. 미래 사용을 추측해 범용 CLI·기능 목록 전체·새 상태 체계를 만드는 데 확대하면 오용이다. 권한 밖 계정·외부 실행은 여전히 필요한 선택만 사용자에게 연결하며, 이번 설계 요청이 그 실행을 승인한 것은 아니다.

배치는 기존 선택을 유지할 수 있다. 일반 역할은 development, 검증자의 조작·관찰 선택은 verification reference, 실제 명령과 준비는 기존 Project 실행 안내·로컬 도구, 이번 관찰과 한계는 Work에 둔다. Feature Map이라는 별도 제품 정본을 만들 필요는 없다.

## 3. 독립 재현을 수정 전후에 이어 쓰고, 작은 재현의 통과를 원래 사용자 경로의 해결과 구별한다

검증안8은 임시 probe를 허용하고, 10은 실패 재현·기대 결과를 수정자에게 전달하며 후속 재현을 요구한다. 이를 조금 더 구체화하면 독립성이 사람을 새로 부르는 비용을 넘어 실제 수정 품질로 이어진다. **검증자가 만든 재현의 실행 가능한 형태와 기대 결과를 보존하고 수정 전후에 이어 쓰는 것**을 기본 선택으로 권한다.

예를 들어 검증자가 실제 저장 후 재진입 실패를 발견하고 원인을 좁히기 위한 작은 재현도 만들었다고 하자. 수정자가 설명만 전달받아 자기 방식의 새 테스트를 만들면 재현 조건이나 기대값이 달라질 수 있다. 또 작은 재현은 통과해도 실제 진입점의 설정·저장 연결·재시작에서 실패가 남을 수 있다. 초안은 기준 약화를 금지하고 영향받은 계약을 다시 확인하도록 하지만, 무엇을 그대로 이어 받아 무엇을 다시 봐야 하는지 실제 장면으로 드러내는 편이 더 강하다.

pstack [bug-fix](../../../source/workflow-references/pstack/repository/skills/poteto-mode/playbooks/bug-fix.md)의 4절은 원래 surface의 재현으로 돌아가라고 하고, 5절은 저렴한 로컬 테스트가 있을 때 실패 재현을 수정과 구별해 남긴다. [shipping](../../../source/workflow-references/pstack/repository/skills/poteto-mode/playbooks/shipping.md)은 코드 작성에 참여하지 않은 검증자가 사용자 경로를 확인하며 판본 변화 뒤 근거가 여전히 맞는지 본다. 이 자료에서 가져올 핵심은 고정 commit 순서나 매번 전체 재실행이 아니라 **원래 관찰·수정·최신 사용자 결과가 연결되는 증거**다.

**본문 수정 제안:** 검증안10의 인계·재검증 문단에 다음 의미를 통합한다.

> 유용한 독립 재현은 수정자가 다시 실행할 수 있는 코드·명령·입력 또는 조작 기록과 기대 결과로 넘긴다. 수정 전에 관찰한 실패와 수정 뒤 결과를 같은 조건으로 비교하며, 재현이나 기대값을 바꿨으면 무엇이 왜 달라졌는지 밝힌다. 좁힌 재현이 원래 실패를 관찰한 경계를 대신하지 못하면 수정 뒤 그 원래 경로도 확인한다. 영향받지 않은 근거는 재사용한다.

지속 테스트 작성 권한을 검증자에게 항상 추가할 필요는 없다. 검증자는 재현과 독립 기대 결과를 소유하고, Main이 지정한 수정·테스트 담당자가 기존 테스트 체계에 반영하면 된다. 검증자가 테스트 작성을 별도로 맡아도 제품을 고치지 않았다면 제품 작성자의 자기 확인과는 다르다. 핵심은 그 테스트가 요구에서 나온 기대를 유지하는지이며, “검사 파일을 썼으니 검증 독립성 상실”로 자동 분류할 이유는 없다.

검증안12의 기록 연결도 이 지점만 구체화하면 충분하다. Main은 종료·중단 전에 이후 판단에 필요한 재현과 실패/수정 후 관찰을 Work의 기존 records나 지속 테스트에 남기고, 임시 환경 정리가 유일한 근거를 지우지 않게 한다. 한 번의 probe를 모두 영구 테스트로 만들거나 모든 로그를 보존하지 않는다. 재실행 비용과 다시 틀렸을 때의 영향을 보고 보존 형태를 고른다. 기존 [Verify](../../../../../../reference-project/context/work/harness/verify/README.md)가 필요하지 않은 경우에도 이 근거 연결은 가능하다.

**이득과 비용:** 수정자가 검사 기준을 다시 해석하는 왕복을 줄이고, 검증자가 지적한 실패가 사라졌다는 사실을 더 분명히 남긴다. 다른 사용자 경로가 남았는데 작은 테스트만 통과한 상태로 끝나는 일을 줄인다. 비용은 재현 조건·기대 결과를 재사용 가능한 형태로 남기고 필요한 원래 경로를 다시 보는 일이다. 비싼 외부 실패를 재현하기 위해 무작정 반복하거나, 불안정한 현상을 재현 가능하다고 꾸미거나, 모든 수정에 새 회귀 테스트·전체 앱 실행을 강제하면 오용이다.

## 유지할 선택과 사용자 논의점

유지할 선택은 별도 검증자의 근거 판정과 Main의 전체 상태 판단 분리, 제품 수정의 별도 배정, 허용된 로컬 확인의 능동 수행, 중요 미확인을 통과에 묻지 않는 반환이다. 기존 근거를 유지하면서 영향받는 범위를 재확인하고, verification 상세를 development 내부 reference로 두는 배치도 그대로 쓸 수 있다. Verify와 의미적 검증의 구별, Main의 지침 기반 Owner 갱신, 자동 Maintain 미연결 역시 바꿀 이유를 찾지 못했다.

사용자와 논의할 가치가 큰 선택은 **중요한 실행 경로의 공백을 이번 개발 결과의 일부로 해결할지, 별도 기반 투자로 나눌지의 기준**이다. 이번 요구를 확인하는 데 반드시 필요한 준비는 이번 범위에서 담당을 연결하고, 반복 비용을 줄일 범용화는 이득·유지 비용에 따라 별도로 고르는 안을 추천한다. 실제로 새 외부 환경·계정·장기 운영 도구가 필요할 때만 그 구체 선택을 올리면 된다.

독립 재현의 보존·지속 테스트 반영 주체도 논의할 수 있다. 기본 추천은 현행 수정자 배정을 유지하고 검증자의 재현을 재사용하는 방식이다. 역할 분리를 이유로 동일한 테스트를 두 담당자가 다시 쓰게 할 필요는 없다. 이 리뷰만으로 새 권한이나 실행 절차를 확정하지 않는다.

## 직접 읽은 범위와 한계

- 공통 의뢰 README·초안 전체, root 지침·CODE-QUALITY, Spec의 목표·대표 사례·현재 구상과 작업 우선순위, 전체 작업 틀 기록, 01-03, 04-03을 읽었다. 긴 Spec의 날짜별 과거 경과 전체를 정독한 것은 아니다.
- 확정 실행 본문인 development·review·execution을 읽었다. demo와 Project·Personal 진입점, demo 적용 지침·context 관계, 인증 계약, Work의 동작 사례·완료 기준, 보존된 실행 기록, 인증 검사 코드의 관련 구간을 대조했다.

- 독립 검토 및 판단·보장·권한 배치 reference, 문서 작성 기준 상기 skill과 지침 명확성·사람용 구조 reference, 기존 Verify README, Noline 보존 스킬 색인의 관련 실행 안내를 확인했다.
