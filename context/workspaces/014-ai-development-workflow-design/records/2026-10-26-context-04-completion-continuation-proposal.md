# 04-03 구체안 4 — 완료·설명·다음 재개를 연결한다

2026-10-26. 항목별 독립 개선 리뷰 뒤 기존 합의·현재 prototype·원형·외부 고정판과의 전체 대조를 반영한 설계안. [리뷰와 채택 근거](2026-10-26-context-improvement-reviews.md)를 보존했다. 이번 수정은 설계 문서의 종합이며 새 Workspace·생성 지침·실행 스킬은 만들지 않았고 기본 선택·host binding도 변경하지 않았다.

**Main이 최신 결과의 완료 범위를 판단하고 설명·기록한 뒤, 같은 목표는 같은 Work에서 이어간다.** 요청된 독립 목표로 분리할 때는 필요한 현재 의미를 새 Work에 직접 남긴다. 생성과 지금 그 작업으로 넘어가는 일, 다음 일반 재개의 기본 선택, host의 실제 세션 연결을 구별하며 이전 Work의 미완료를 완료로 바꾸지 않는다.

## 마무리할 때 남길 것

Main은 [development](prototypes/development-workflow/skills/development/SKILL.md)의 전체 완료 기준으로 최신 요구·결과·확인·중요한 공백을 판단한다. 검토 의견 제출·검증 반환·문서 저장과 전체 완료는 다르다. 사용자 수락이나 배포가 필요한 범위이면 그 상태도 구별하되 매번 별도 승인 단계를 추가하지 않는다.

development는 이미 첫 결과를 전달할 때 [explain](prototypes/development-workflow/skills/explain/SKILL.md)을 사용하도록 연결한다. Main이 원래 목표에 무엇이 답해졌는지, 실제 변경·중요한 선택·확인·남은 공백이 결론을 어떻게 지지하는지 설명한다. 설명 방법은 explain, 결과·상태 판단과 지속 기록은 해당 작업 담당·Owner의 책임으로 유지한다. 이 안에서 새 설명 단계를 만들거나 그 책임을 context 스킬로 옮기지 않는다.

Work에는 현재 결과와 선택 이유·확인 상한·미해결의 의미와 다음 행동을 남긴다. 상세 비교·시도·실패·정확한 원문은 필요한 만큼 records/source에서 찾고, output은 선택한 실제 산출물을 가리킨다. 인계를 위한 새로운 종합 보고서나 동일 내용의 복제본을 기본 생성하지 않는다.

다음 세션은 [항목1](2026-10-26-context-01-start-resume-proposal.md)의 경로로 현재 목표와 첫 행동의 이유를 복원할 수 있어야 한다. 마지막에 발견한 구체적인 결함이 곧 다음 중심 과제가 되는 것은 아니다. 이번 세부안은 완료 후 새 사실이 나왔을 때 당시 확인의 유효 범위와 현재 남은 일을 구별하도록 구체화한다. 후속 문제의 발견이 당시 모든 근거를 지우는 것도, 과거 완료 표기가 새 문제를 해소하는 것도 아니다.

예를 들어 현재 [001 state](prototypes/development-workflow/noline-demo/context/work/workspaces/001-login-completion-names/current/state/index.md)는 메모리 예제 검사와 실제 저장소 미확인을 구별한다. 이 결과의 표현을 보완하라는 요청이면 같은 Work에서 당시 확인 대상과 현재 산출물의 관련 차이, 이름 기준과 사용처를 읽는다. 동작이 그대로이고 원본 근거가 유효하면 기존 동작 확인을 활용한다. 현재 완료 주장에 영향을 주는 결함이 드러나면 해당 Ticket·현재 상태를 다시 열고 당시 실행 기록은 보존한다. 문서에 새 약속을 적었다거나 새 Work를 만들었다는 이유로 현재 구현 지원이나 남은 확인을 완료 처리하지 않는다.

## 같은 작업을 마치고 다시 이어가는 장면

[항목2](2026-10-26-context-02-role-execution-proposal.md)·[항목3](2026-10-26-context-03-change-records-proposal.md)의 ‘새 화면이 로그인 뒤 최신 여행 목록을 필요로 한다’는 가상 요구를 이어 대입한다. 아래는 설계 장면이며 실제 구현·검증 결과가 아니다.

1. 담당자가 구현·배정된 사실 문서와 확인 결과를 반환한다. Main은 새 소비자의 요구와 기존 소비자의 보존 동작을 최신 대상에서 어디까지 확인했는지 판단한다. 확인이 남았다면 문서 저장을 전체 완료로 취하지 않고 담당과 다음 행동을 연결한다.
2. 사용자에게는 새 소비자에서 무엇이 달라졌는지, 공통 인증 완료 경계를 유지한 이유, 확인한 범위와 미확인을 첫 결과부터 설명한다. 기존 development→explain 연결을 사용하며 설명만으로 확인 공백을 메우지 않는다.
3. Main은 current·해당 Ticket에 현재 선택·결과·남은 일을, records에 필요한 직접 근거를 남기고 output에서 실제 결과를 찾게 한다. 원문·코드·과거 확인을 복제한 별도 인계 보고서를 기본 생성하지 않는다.
4. 같은 목표의 다음 세션은 README·memory/Spec/Ticket·state·output과 관련 최신 원문에서 현재 범위·선택 이유·미확인·첫 행동을 복원한다. 끝난 작업은 유효 범위에서 이어받고, 남은 소비자 확인이나 새로 드러난 조건부터 수행한다. 독립 목표를 분리하라는 요청이 있을 때만 아래 생성·전환 관계로 넘어간다.

## 기존 Work에서 이어갈지 분리할지

| 상황 | 제안하는 처리 |
| --- | --- |
| 새 세션에서 같은 목표 재개, 작은 후속 수정, 현재 요구의 미확인 해소 | 기존 Work를 이어간다. 세션 교체·컨텍스트 길이만으로 새 Work를 만들지 않는다. |
| 현재 목표의 범위/접근이 바뀌지만 같은 결과를 추적해야 함 | Main이 기존 요청·합의와 변화 이유를 대조해 current·Spec/Ticket을 맞춘다. 단순한 기술 선택은 위임 범위에서 처리한다. |
| 독립 목표·완료 장면·진행 책임을 따로 관리할 필요가 있고 사용자가 분리를 요청 | 새 Work 생성 계약을 수행한다. 요청한 분리가 충분히 명확하면 중복 확인 없이 진행한다. Main이 분리가 유익하다고 보더라도 요청 없이 자동 생성하지 않는다. |
| 활성 Work 없이 한정된 읽기·설명·검토·작은 개발 요청 | 필요한 대상 지침과 원문으로 수행한다. Work 생성 자체를 선행 조건으로 강제하지 않는다. 지속 작업으로 분리할 필요가 생기면 의미와 비용을 설명해 연결한다. |

이는 기존 ‘새 독립 Work는 요청됐을 때’라는 조건을 유지한 설계다. 첫 Work와 추가 Work의 **의미 구성**은 공통으로 쓸 수 있으나, Harness 최초 설치는 별도 이식 과업이다. 첫 Work가 없다는 이유로 Harness를 설치하거나 기존 context를 정형화하지 않는다.

## 새 Work에 무엇을 넘기나

가상 요청은 ‘실제 기기 저장소 연결을 별도 Work로 만들자’다. 현재 로그인 예제는 메모리 기반 확인까지만 있다. successor의 current에는 다음과 같은 현재 의미를 직접 쓴다.

> 목표는 실제 저장소에서 인증 정보 저장·상태 공개·실패 복구 경계를 연결하고 확인하는 것이다. 저장 완료 전 인증 성공을 공개하지 않고 같은 계정의 로컬 작업을 보존한다. 이전 Work의 메모리 예제는 이 순서의 참고 구현이지만 실제 저장소의 부분 실패·복구를 확인한 근거가 아니다. 첫 판단은 실제 어댑터의 쓰기·실패·복구 의미를 제품 계약과 대조해 적용 범위와 검사 조건을 정하는 것이다.

실제 생성을 요청받으면 이 예시를 복사하는 대신 그 요청과 대상 근거로 작성한다. 해당 Personal·Project 본문의 현재 접근점과 왜 필요한지, 실제 결과 위치·확인 범위, 권한 있는 결정·열린 판단을 연결한다. 이전 Work의 전체 대화·이름 A/B 비교를 기본 입력으로 옮기지 않는다. 당시 선택을 다시 판단해야 하는 부분만 exact record/source로 단방향 참조한다.

source에는 원자료와 provenance를 두고 현재 해석은 current에 쓴다. output에는 실제로 선택한 산출물만 연결한다. 생성 시점에 결과가 없으면 완료 산출물처럼 채우지 않는다. 이전 원본을 복사해 receipt·pass·완료 상태를 물려주지 않는다. 여러 Work에서 쓰게 됐다는 이유만으로 Project 공통 기준으로 승격하지 않는다.

## 이어받은 생성·전환 안을 실제 입구에 연결한다

수동 demo의 현재 [Work 목록](prototypes/development-workflow/noline-demo/context/work/workspaces/README.md)은001만 안내한다. 아래는 앞선 생성 큰그림을 이 입구에 적용한 안이다. 둘째 작업을 만들 때에는 다음 연결이 필요하다.

1. Work의 생성·전환 계약에서 목적·필수 의미·내용 구성·기존 원본 보호·인수 조건을 정의한다. 기존 Work 구성 안의 가칭 `work/workspaces/CREATE-AND-TRANSITION.md`를 후보로 삼는다. 컬렉션 README가 관계와 진입을 연결하고 전체 상세를 root에 복제하지 않는다.
2. 새 경로의 기존 파일·이름 충돌·사용자 변경을 확인하고 새 goal의 README·current·필요한 source/output/records를 구성한다. 기존 Work는 필요한 현재 관계만 맞추며 역사적 기록을 새 결론으로 덮지 않는다.
3. 새 진입점만으로 목표·보존 조건·현재 근거·중심 과제·첫 행동과 필수 원문을 복원해 본다. 중요한 인계라면 생성자의 설명을 받지 않은 별도 읽기 주체로 확인한다. 작은 생성은 Main의 직접 대조로 줄일 수 있으며 이를 독립 인수 시험이라 부르지 않는다. 누락이면 successor의 의미·선택을 보완한다. 이전 Work 전체를 추가해 통과시키지 않는다.
4. 생성만 요청했다면 목록에 존재와 준비 상태를 연결하되 기본 선택·현재 세션 연결은 유지한다. 전환까지 요청했다면 아래 Work 전환 계약을 이어 적용한다. 이미 존재하는 Work로 이동할 때에는 생성 단계를 수행하지 않는다.

## 기존 또는 새 Work로 전환한다

이번 세부 보완안은 기존 전환·결과 귀속 책임을 수동 demo의 요청·기본 선택·진행 중 담당자에 대입한다. 생성·활성화를 구별하는 기존 계약을 유지하면서 수동 demo와 실제 설치 대상에서 무엇을 바꿀지 구체화한다.

먼저 대상이 수동 demo인지 설치된 runtime인지 확인한다. 이번 요청의 대상·다음 일반 재개의 기본 선택·실제 전환 적용 시점을 각각 대상 계약으로 정한다. 수동 전환을 먼저 수행한 뒤 설치된 runtime에 덧씌우지 않는다.

| 요청과 대상 | 연결할 행동 |
| --- | --- |
| 기존 Work의 특정 일을 명시 | 이번 요청은 지정 Work에서 수행한다. 다음 일반 재개의 기본값 변경이나 host activation을 자동 수행하지 않는다. |
| 수동 demo에서 ‘그 Work로 넘어가자’ | 현재 넘길 의미와 대상 준비를 확인한 뒤, 이번 대화의 수행 대상과 다음 일반 재개의 기본 선택을 함께 맞추는 안을 권고한다. 일반 재개는 root·context·Work가 목록의 선택 한곳을 따르게 한다.001은 이름 있는 예제 링크로만 남긴다. |
| 설치된 runtime을 쓰는 대상의 전환 설계 | 현존 binding·활성화 계약에서 전환 시점과 자동 Maintain 의존을 확인한다.06에서 자동 Maintain 의존을 제거·대체한 뒤 사용할 전환 절차와 연결한다. 현재 turn을 이전 Work로 마감하고 다음 prompt부터 적용하는 계약을 유지한다면 그 시점을 지키며, 기본 index 변경을 실제 세션 전환의 대용으로 쓰지 않는다. |

전환 전에 Main은 진행 중 담당자·미반영 반환 중 다음 작업에 영향을 주는 것만 확인한다. 계속 수행할 일과 늦게 도착하는 결과는 **원래 맡긴 Work·판본·권한**에 귀속된다. 기본 선택이 바뀌었다는 이유로 기존 담당자의 쓰기 대상이나 반환 위치를 바꾸지 않는다. 새 Work에서 쓸 의미만 판단 후 선택해 반영하고 재배정이 필요하면 바뀐 목표·권한을 직접 전달한다. 모든 담당자를 취소하거나 관련 없는 결과를 기다리는 규칙은 추가하지 않는다. 중요한 미완료 연결은 항목3의 current 갱신으로 남긴다.

명시 대상 재개와 미지정 기본 재개가 각각 올바른 Work에 도달하는지 확인한다. 생성되지 않은 새 목표를 명시했을 때의 구성은 위 생성 계약을, 이미 있는 대상의 현재 의미 복원은 항목1을 사용한다. 별도 전환 스킬은 제안하지 않는다.

수동 목록 변경은 실제 host activation이 아니다. 설치된 Harness가 있는 대상의 identity·Recover·Verify·Maintain/binding 계약은 현존 의존을 파악할 입력이다. 설치돼 있다는 이유로 기존 자동 Maintain 활성화를 새 흐름에 연결하지 않는다. 자동 Maintain을 재개하지 않는 방향으로06에서 의존의 제거·대체와 호환되는 전환 절차를 정한다. 수동 demo에 없는 기계 파일을 추가해 기존 스킬을 작동시킨 것처럼 만들지 않는다. 실제 전환 확인에서는 유지된 대상·준비된 successor·막힌 host 연결을 구별하고 상태가 확인되지 않았는데 완료라고 하지 않는다.

## 기존 create에서 이어받을 책임과 대상 차이

[기존 create-context-workspace](../source/ai-workspace-baseline/reference-project/.agents/skills/create-context-workspace/SKILL.md)는 설치된 Harness와 두 번째 이후 Workspace, 세 물리 layer, machine identity·Recover·Verify·Maintain activation을 전제한다. 이 조건을 현재 demo에 그대로 적용하면 새 Work 의미를 만드는 일과 runtime 설치가 섞인다.

| 기존 책임 | 유지·보완 제안 |
| --- | --- |
| 새 목표·범위와 필요한 의미 선별, predecessor 원본 보호, 단방향 참조 | 유지. Personal 선택도 새 목표에 맞게 연결하고 최신 원문/당시 근거를 구별한다. |
| 생성·전환 canonical 참조 | 유지. 내용 구조·인수 의미는 Work가 소유하고 skill은 수행과 반환을 맡는다. |
| Git 최상위·고정 상대 경로, 물리 layer 부재를 설치 실패로 취급 | 실제 대상 root와 context 계약으로 바꾼다. target에 필요한 정본 공백은 알리되 demo 구조 차이를 repair로 오인하지 않는다. |
| machine shape 생성·bounded Recover·Verify·Maintain 활성화 | 현존 결합의 조사 입력으로 구별한다. 자동 Maintain은 재개하지 않고 의존을 제거·대체하는 방향으로06에 연결한다. Recover·Verify·identity/binding의 유지·단순화와 필요한 실행은 그 의존 분석으로 정하며 없는 runtime의 모조 명령·JSON은 만들지 않는다. 수동 읽기 대조와 실제 Recover 성공을 구별한다. |
| 생성과 활성화의 구별 | 유지하며 현재 요청 대상·다음 기본 선택·host binding의 결과를 분리해 반환한다. |

**생성은 별도 과업으로 유지할 이유가 있다.** 독립된 요청·쓰기 범위·인수 결과가 있고 일상 읽기·본문 반영과 종료가 다르다. 기존 이름을 유지해 재구성할지 실제 배포에서 다른 진입을 둘지는06의 소비자 조사에 따라 정할 수 있다. 지금 새 관리 스킬로 전체 context 수명을 묶지 않는다.

## 이번에 정할 관계와 후속 책임

04-03은 읽기·선택·반영·완료 뒤 재개·요청된 생성의 입력/결과와 실제 진입 연결을 구체화한다.02는 Work 구조·기록 시점·완료 후 보존의 전체 운영안을,06은 기존 설치·bridge·Harness 의존과 대상별 전환/복구를,07은 전체 적용과 관찰을 맡는다. Main의 현재 기록 책임은 이미 있으며02가 끝날 때까지 유보하지 않는다. 필요한 의미 계약은 여기서 제안하되 이를 이유로02·06 완료를 선행 요구하거나 해당 Ticket들을 완료 처리하지 않는다.

기존 Harness의 Recover는 읽기 전용 재진입 packet, Maintain은 허용된 Owner의 의미 갱신, Verify는 상태 전환·인계에 필요한 지속 제품 증거를 맡았다는 [기존 책임 계약](../source/ai-workspace-baseline/reference-project/context/work/harness/README.md)을 조사 입력으로 사용한다. 이 의미 구별을 보존하되 자동 Maintain을 재개하지 않고 장치를 걷어내며 기록 원칙을 남기는06의 방향을 따른다. 현재의 기록 수행은 Main이 맡는다. 수동 읽기·Main 갱신·직접 검사를 각각 옛 runtime의 실행 성공으로 표현하지 않는다. 현재 demo에는 자동 Maintain·session activation이 연결돼 있지 않으며, 나머지 실행 수단의 유지·단순화와 전환은06에서 의존·권한·호환 조건으로 구체화한다.

외부의 pause/pickup·recall은 이어갈 정보를 반환하는 참고 사례이고 우리의 새 Work 생성·원본 보존·host 전환 전체를 대신하지 않는다. [고정판 조사](2026-10-25-context-reference-synthesis.md)와 기존 생성 계약을 함께 사용한다.

후속 적용에서 확인할 것은 같은 목표 재개에서 불필요한 생성이 없는지, 새 Work에서 이전 대화를 몰라도 중심과 첫 행동을 복원하는지, 생성만/명시 대상/전환 요청에서 선택 상태가 맞는지, 실제 runtime이 있는 대상과 없는 대상의 결과를 구별하는지다. 이번 설계 대조는 생성·활성화 성공이나 전체 운영 효과를 입증하지 않는다.
