# Dialog 논의에서 남긴 코드 기준 후보와 다음 사례

2026-10-13. 01-02의 사용자 코드 기준 탐색 기록이다. Confirm의 비동기 API 비교를 마치고, 이 사례의 잠정 선택과 다른 코드에도 적용할 판단 후보를 구별해 남긴다. 템플릿·제품 코드와 실제 개발 지침을 변경한 기록은 아니다.

> 지금대화들에서 남길만한걸 생각해보자 다시

Main은 아래 네 가지를 기준 후보로 정리했고, 사용자는 “그래 이정도 남기고 그 다음 뭐지?”라고 기록을 요청했다. 네 항목의 보존에 동의한 것이며, 상황과 무관한 의무 규칙이나 스킬 구현을 채택한 것은 아니다. 특히 사용처 부담은 계속 평가할 질문으로 남긴다.

Confirm은 일단 Radix 공식 비동기 예제처럼 작업 완료와 닫기를 사용처에서 연결하고, 별도 Confirm을 제거하는 방향으로 정리했다. 라이브러리를 실제로 도입하거나 템플릿 코드를 수정하지 않았다. 일반 Button과 제어된 Dialog를 사용하는 것이 본래부터 나쁜 것은 아니다. 앞서 지적된 문제는 Confirm의 목적을 검토하지 않고 즉시 닫기용으로 축소한 판단이었다. [당시 목적 정정과 실제 코드](2026-10-13-32-template-code-and-usage-discovery.md)

## 다른 사례에도 가져갈 기준 후보

### 목적을 이해한 뒤 유지·변경·제거를 판단한다

기존 구조가 제공하려던 역할과 편의를 먼저 파악한다. 대안이 그 역할을 유지하는지, 다른 곳으로 옮기는지, 의도적으로 없애는지 확인한다. 목적을 이해한 결과라면 기존 추상화를 제거할 수 있다.

이 사례에서 Confirm은 원하는 callback을 실행한 뒤 닫는 편의를 의도했다. 비동기 문제가 생겼다는 이유만으로 즉시 닫기 전용으로 재정의하고 예외를 밖으로 옮기는 설명은 그 목적과 Cancel의 관계를 놓쳤다. 이후 사용처가 완료와 닫기를 연결하는 방향을 선택하면서 그 편의를 내려놓는다는 점을 함께 확인했다. 기존 구조 보존 의무와 모든 사용처 제어의 금지로 해석하지 않는다.

### 이미 도구에 맡긴 책임을 분리 판단의 출발점으로 삼는다

현재 사용하는 라이브러리와 기존 모듈의 실제 역할을 고려한다. 이미 맡겨진 책임을 불필요하게 다시 구현하지 않으며, 추가로 감쌀 때는 그 단위가 제공하는 역할이나 편의를 분명히 한다.

React Query가 요청·진행·오류를 맡거나 React Hook Form이 입력 상태·검증을 맡는 상황에 따라 기능 Hook과 UI의 경계가 달라질 수 있다. 여러 작업의 조율이 한 기능의 책임이라면 기존 도구까지 포함해 감쌀 수도 있다. 라이브러리 사용·래핑 금지나 특정 도구의 일괄 도입을 뜻하지 않는다. [앞선 기능 Hook 논의](2026-10-13-31-criteria-roles-and-responsibility-interview.md)

### 공통화의 편의와 사용처 부담을 함께 평가한다

공통화로 줄어드는 코드와 함께, 사용처가 알아야 할 계약과 추가 연결 코드를 본다. 일반적인 오류 처리나 기존 도구의 사용 방식과 충돌하는지도 확인한다.

이 평가 질문을 만든 사용자 발화:

> 근데 이렇게 하면 쓰는 쪽에서 실패를 다시 던져야 한다는 걸 알아야 하잖아? 다시 고민해봐야 할것 같은데?

> 근데 이것도 결국 쓰는 쪽에서 결과를 반환해야 하는 건 같잖아? 이 정도는 사용처가 맡는 게 자연스러운 책임인지, 아니면 더 나은 방식이 있는지 다른 안이랑 구체적으로 비교해보자.

Promise 기반 Confirm에서는 오류를 표시한 뒤에도 reject를 유지해야 닫히지 않는다. 별도 결과값 방식에서는 사용처가 결과를 변환해 반환해야 한다. 직접 닫는 방식은 이 반환 계약을 없애는 대신 사용처가 성공과 닫기를 연결한다. 어느 방식도 부담이 사라지는 것은 아니다. 사용처가 자연스럽게 맡을 책임인지, 공통 API를 맞추기 위한 추가 작업인지 비교한다. 오류 재전파·결과 반환 자체가 나쁘다는 규칙으로 정하지 않는다. 이 항목은 확정된 취향보다 이번 대화에서 얻은 평가 질문이다.

### 공통 컴포넌트의 역할과 구현 수단을 구별한다

외부 라이브러리는 공통 컴포넌트를 구현하는 선택지다. 사용할지, 감쌀지, 직접 구현할지는 필요한 역할과 개발 비용을 보고 판단한다.

사용자가 Radix를 감싼 이유는 개발 리소스를 줄이고 사용처에 프로젝트 공통 Dialog를 제공하기 위해서였다. 네이밍에는 공통 컴포넌트와 라이브러리 이름의 충돌을 구별하려는 맥락이 있었다. 사용처가 내부 구현 수단을 알 필요 없게 하려는 의도와, 모든 라이브러리를 반드시 감싸야 한다는 규칙은 다르다. 직접 구현이 더 적합하면 그렇게 할 수 있다.

## 판단에 사용한 외부 사례

2026-10-13 공식 문서와 공개 구현을 확인했다. 아래는 당시 API 비교의 최소 근거이며 우리 코드 기준의 자동 채택 근거는 아니다. 대화에서 작성한 삭제·프로필 저장 코드는 설명용 변형으로 실행하지 않았다.

공개 master 구현과 문서는 변경될 수 있다. 이 기록은 위 확인일의 계약을 남긴 것이며 설치 버전에서 동작을 검증했다는 뜻은 아니다. Promise 결과 타입이나 전용 어댑터, Mantine식 옵션을 우리 API로 채택하지 않았다.

## 논의의 위치와 다음 후보

현재는 01-02에서 사용자의 코드 판단 기준을 실제 사례로 탐색하는 단계다. Confirm의 API 설계가 독립 목표가 되면서 책임 분리라는 논점이 흐려졌고, 위 기준 후보로 다시 연결했다. 상세 비동기 버튼 API를 계속 설계하기보다 다음 실제 사례에 이 관점을 대입한다.

Main의 다음 제안은 같은 `20_lab/template`의 `src/component/FormSection/Field/index.tsx`와 `src/component/FormSection/index.stories.tsx`를 함께 보는 것이다. 확인된 코드에는 Field의 UI 구성과 React Hook Form의 register·Controller 사용 예시가 있다. 입력 상태·검증·오류 표시를 각각 어디에 두었는지, 공통 Field가 라이브러리를 직접 알 때와 사용처가 연결할 때 어떤 차이가 있는지를 구체 코드로 비교할 수 있다. 순서는 아직 제안이며 해당 구성을 사용자 선호로 확정한 것이 아니다.

그 뒤 후보는 React Query·관찰 Hook·무한 스크롤 컴포넌트의 책임 배치다. 과제물·회사 코드는 계속 후속 참고 후보로 남기고 지금 조사 범위를 넓히지 않는다. 코드 기준 탐색이 끝난 것도 아니며, 전체 작업 체계의 컨텍스트·브레이크·검토·검증·기록 설계 범위는 유지한다.
