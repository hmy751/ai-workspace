# 기준을 찾아 읽고 구현·검토에 전달하는 형식 시안

> 후속: 사용자는 이 시안만으로는 실제 존재·전달·적용이 보이지 않는다고 정정했다. 현재 보여 줄 결과는 [적용 사례 63](2026-10-17-63-applied-criteria-project-example.md)이다. 아래 내용과 검사는 이전 시안의 이력으로 보존한다.

2026-10-17. **같은 내용의 연결본과 통합본, 작업자·검토자 요청문, 판단 뒤 남길 내용까지 작성했다.** 현재 추천은 사람과 함께 처음 내용을 검토할 때 통합본을 먼저 보고, 실제 작업 전달은 ‘작업 중점·보존 계약 + 기준 원본 링크’를 사용하는 것이다. 파일을 나눌지는 여러 작업에서 기준을 다르게 골라 읽을 필요와 관리 비용을 보고 정한다. 최종 형식·운영 채택은 아니다.

**바로 보기:** [B — 한 문서에서 읽는 시안](prototypes/criteria-format-2026-10-17/combined.md) · [A — 작업 상황에서 찾아가는 시안](prototypes/criteria-format-2026-10-17/start.md) · [작업자·검토자 전달문](prototypes/criteria-format-2026-10-17/fetcher-task.md)

## 이번 시안이 보여 주려는 것

사용자:

> 그럼 그렇게 시안 만들어서 보여줘. 실제로 어떻게 찾아 읽고 작업자나 검토자한테 전달되는지, 선택이 갈리는 부분은 대안도 같이 비교해줘.

잠정 목표는 작업자·검토자가 필요한 기준을 찾아 상황에 맞게 판단하고, 사용자가 그 이유를 이해해 기준과 결과를 고칠 수 있게 하는 것이다. 비교 기준은 찾기, 조건에 맞는 판단, 사람의 이해·수정, 사용·유지 비용이다. [개선 조언 59](2026-10-16-59-format-design-objectives-advisor.md), [외부 비교 61](2026-10-17-61-reference-comparison-for-format-design.md), [Spec](../current/spec.md)을 실제 시안으로 연결했다.

이번에 넣은 내용은 기준 두 개와 Field·Container·fetcher 사례다. 다른 기준이 필요 없다는 뜻은 아니다. UI에서 조건에 따라 다른 구조가 타당해지는 모습과 API에서 수정·보류·재확인으로 이어지는 모습을 보기 위해 골랐다. 제품 코드·원본 템플릿은 수정하지 않았고, 실제 역할 요청 전송이나 동작 검증을 수행한 것도 아니다.

## 시안 A — 작업 상황에서 필요한 기준으로 찾아간다

[작업 입구](prototypes/criteria-format-2026-10-17/start.md)는 사용자가 쓰는 작업 표현을 기준으로 연결한다. 기준은 하나의 본문에 주제별로 설명하고, 작업 전달문은 이번 목표·보존 계약·중점과 그 본문을 연결한다. 현재 파일 분리는 비교를 보여 주기 위한 것으로 최종 Project 배치가 아니다.

| 들어온 작업 | 실제로 열어 볼 곳 | 읽은 뒤 판단할 것 |
| --- | --- | --- |
| 이메일 입력의 설명·오류 배치를 바꾼다 | [입구의 폼 변경 안내](prototypes/criteria-format-2026-10-17/start.md#choose)에서 [공통 부품과 사용처의 선택](prototypes/criteria-format-2026-10-17/principles.md#shared-choice)으로 이동 | Field의 의도적 합성을 유지하면서 사용처 조합으로 해결되는지. 연결 공유와 합성 유지가 양립할 여지도 본다. |
| 같은 표시 정책의 목록을 추가하거나 기존 Container를 없애려 한다 | 같은 입구에서 [Field·Container 대비](prototypes/criteria-format-2026-10-17/principles.md#component-cases)와 바로 위 원칙을 읽는다 | 실제로 공유하는 정책과 필요한 자유도를 기준으로 판단한다. Hook·Container 중 하나를 보편적 정답으로 고르지 않는다. |
| 공통 fetcher의 오류 계약을 정비한다 | [작업자 요청](prototypes/criteria-format-2026-10-17/fetcher-task.md#implementer)에서 [공통 계약](prototypes/criteria-format-2026-10-17/principles.md#trusted-contract)으로 이동 | 호출·정상 반환을 보존하고 의미가 깨지는 오류 경로를 수정하며 별도 확장을 구별한다. |
| 위 구현 결과를 검토하고 필요한 품질 수정을 한다 | [검토자 요청](prototypes/criteria-format-2026-10-17/fetcher-task.md#reviewer), 같은 작업 계약·기준, 실제 작업에서는 diff와 실행 결과 | 구현자의 주장을 다시 대조하고 범위 안의 문제를 직접 수정·재확인한다. |

전체 흐름을 처음 보는 사람은 이 표에서 각 경로를 따라갈 수 있다. 실제 작업 요청에는 필요한 링크와 읽는 이유를 직접 넣었으므로, 매번 입구 표를 거쳐야만 하는 절차는 아니다.

## 시안 B — 기준과 사례, 전달 모습을 한 문서에서 읽는다

[통합본](prototypes/criteria-format-2026-10-17/combined.md)에 A의 작업 안내·기준 두 개·요청문·판단 예시를 같은 내용으로 넣었다. 상단 목차로 필요한 절에 바로 갈 수도 있고, 전체를 읽으며 원칙과 사례·역할의 연결을 이해할 수도 있다. B를 비교하기 위해 불필요한 내용을 더 넣거나 목차를 없애지 않았다.

두 안의 차이는 기준 내용이나 판단 철학이 아니라 **정보를 찾고 함께 읽는 단위**다. A의 기준 두 개도 한 본문에 있으므로 ‘기준 하나당 파일 하나’가 전제되어 있지 않다.

## 선택이 갈리는 부분

### 통합해서 읽을까, 필요한 내용을 나눠 읽을까

| 비교 | A: 작업 입구 + 연결된 기준·작업 예시 | B: 하나의 문서 + 목차 |
| --- | --- | --- |
| 처음 전체를 이해하기 | 입구·본문·작업 예시의 관계를 따라가야 한다 | 원칙·조건·예시·전달을 한곳에서 비교하기 쉽다 |
| 특정 작업에 필요한 정보 | 작업 요청에서 관련 기준으로 바로 이동할 수 있다 | 목차나 구간 읽기로 선별할 수 있다. 문서 전체를 제공하면 무관한 내용도 들어간다 |
| 놓치기 쉬운 것 | ‘폼 연결 변경’을 ‘사용처의 선택권’과 연결하지 못하면 관련 기준을 안 읽을 수 있다 | 문서가 길어지면 예외·다른 기준을 지나치거나 전체 읽기 비용이 커질 수 있다 |
| 수정·관리 | 공통 본문은 재사용하지만 읽는 안내·링크도 맞춰야 한다 | 한곳에서 바꾸기 쉽지만 주제·작업 예시가 늘면 탐색과 편집 부담이 커진다 |
| 잘 맞는 조건 | 여러 작업이 서로 다른 기준 조합을 반복 사용하고 분리 효과가 있을 때 | 기준이 적고 함께 읽는 내용이 많거나 사람이 전체를 검토할 때 |

**현재 추천:** 이번처럼 기준 두 개를 처음 함께 검토할 때는 B가 더 단순하다. 실제 개발에서 다른 기준 조합을 선택할 필요가 커지면 A의 읽기 안내와 분리 구조를 사용한다. 문서가 길다는 이유만으로 분리하거나, 파일이 적다는 이유로 통합을 최종 선택하지 않는다. 실제 읽기·관리에서 차이가 나는지 확인한다.

### 작업 요청에는 어느 정도를 넣을까

같은 fetcher 작업에서의 실제 표현 차이다.

| 대안 | 전달되는 문장 예 | 이득과 비용 |
| --- | --- | --- |
| 링크만 | “오류 계약을 정비해 줘. [공통 계약 기준](prototypes/criteria-format-2026-10-17/principles.md#trusted-contract)을 참고해 줘.” | 복제가 적고 원본 갱신이 이어진다. 이번 보존 계약과 중점을 작업자가 별도로 복원해야 한다. |
| 선별 본문 복사 | “공통 모듈의 오류 형태와 의미를 사용처가 믿고 쓸 수 있게 해야 한다. 내부 실패가 다른 의미로 전달되거나 이미 얻은 정보가 사라지는지 확인해 줘.”라고 기준을 복사해 붙인다 | 필요한 설명이 눈앞에 있다. 발췌에서 조건을 빠뜨리거나 원본 변경과 어긋날 수 있고, 이것만으로 이번 작업 범위가 정해지지는 않는다. |
| 작업 중점·보존 계약 + 원본 링크 | “기존 호출·정상 반환·10초 timeout과 화면 정책 분리를 유지하면서 오류 경로를 정비해 줘. HTTP 실패 본문도 깨졌을 때 상태가 남는지와 timeout 수명을 확인하고, [공통 계약 기준](prototypes/criteria-format-2026-10-17/principles.md#trusted-contract)을 읽어 줘.” | 이번 판단 지점과 읽는 이유가 보인다. Main의 중점 선정 비용이 있고, 목록 밖 문제도 살필 책임을 남겨야 한다. |

**현재 추천은 세 번째다.** 전체 기준을 매번 복사하지 않으면서 이번 작업의 중요한 계약을 직접 전달한다. 다른 환경에서 원본에 접근할 수 없을 때는 필요한 조건을 포함한 본문과 출처·판본을 함께 전달하는 방식이 더 적합할 수 있다. 접근할 수 없는 링크만 주고 전달을 끝내지 않는다.

### 모든 기준을 같은 목차와 질문 개수로 쓸까

이번 기준 두 개는 의미·적용 상황·판단 질문·사례를 갖추었지만 이를 의무 칸으로 확정하지 않았다. 두 본문 모두 질문 세 개를 쓴 것은 이번 내용을 설명하기에 충분해서이며 개수 규칙이 아니다.

고정 양식은 누락을 확인하고 비교하기 쉽다. 반면 짧은 기준까지 불필요한 사례·예외·보고 항목을 채우게 할 수 있다. 자유 서술은 의미에 맞게 쓰기 좋지만 적용 조건을 빠뜨리거나 찾는 방식이 들쭉날쭉해질 수 있다. 현재는 **무엇을 중시하는지·언제 달라지는지·무엇을 확인할지가 드러나야 한다는 공통 요구**를 두고, 질문·대비표·문단의 구성은 기준에 맞게 바꾸는 편을 권한다.

### 질문의 답을 전부 출력할까

질문별 답안을 고정하면 고려한 흔적은 보기 쉽지만, 말로 답한 것이 코드 판단과 실제 수정에 반영됐다는 보장은 없다. 이번 시안은 중요한 선택 이유·실제 변경·확인 근거·미확인을 남기도록 했다. 질문별 답안은 특정 기준의 적용을 집중 점검해야 할 때 비교할 수 있으며 모든 작업의 기본 보고로 정하지 않는다.

## 작업과 검토가 끝난 뒤 무엇이 남는가

[fetcher 판단 예시](prototypes/criteria-format-2026-10-17/fetcher-task.md#decision-example)는 ‘유지·수정 후보·보류’와 그 이유, 확인할 경로를 연결한다. 전부 미실행 예시로 표시했다. 실제 보고라면 코드 변경·확인 방법과 결과가 있어야 하며, 샘플만 보고 완료로 바꾸지 않는다.

[사용자가 판단을 바꿀 때의 예시](prototypes/criteria-format-2026-10-17/fetcher-task.md#record-use)에서는 이번 작업 범위, Project 공통 계약, 일반 기준 중 어디를 수정할지 구별한다. 작업 결과를 남기는 것과 그 경험을 새 공통 규칙으로 채택하는 것은 다른 판단이다. 이 연결은 03의 Project 맥락·01-01/04의 실행·01-03의 확인·02/05의 기록과 개선을 살피기 위한 것이며 전체 역할·자동화를 확정하지 않는다.

## 현재 판단과 확인 범위

형식 시안과 연결된 요청문은 작성했다. 먼저 통합본으로 의미 관계를 검토하고, 작업자에게는 해당 작업의 계약·중점과 기준 링크를 주는 방향을 추천한다. 실제로 어느 형태가 더 잘 읽히는지, 코드 품질이나 수정 비용에 어떤 차이를 만드는지는 아직 확인하지 않았다.

다음 대화에서는 이 시안에서 찾기 어려운 기준, 과하거나 부족한 설명, 작업자·검토자에게 넘기는 정보의 차이를 직접 가리켜 고칠 수 있다. 시안 제작을 전체 형식 채택이나 01-02 완료로 기록하지 않는다.

### 이번에 확인한 범위

이전 대화를 받지 않은 내부 reader에게 A의 `start.md`와 이메일 배치 변경·fetcher 검토라는 작업 두 개를 주었다. reader는 `start.md`, `principles.md`, `fetcher-task.md`만 열고, 각 작업의 기준과 조건·보고 범위를 찾았다. Field의 합성 의도와 폼 연결의 별개 판단, fetcher의 호출·정상 반환·timeout·화면 정책 보존, 검토자의 직접 수정·재확인 및 계약 변경 반환을 복원했다고 보고했다. 실제 제품의 디자인·API·checkout·diff·실행 결과가 별도로 필요하다는 점도 구별했다.

이 결과는 한 독자가 연결본에서 필요한 의미를 찾았다는 문서 수준의 관찰이다. B와의 성능 비교, 실제 코드 변경·테스트, 여러 작업에서의 적용 효과를 증명하지 않는다.

변경·신규 Markdown 19개에서 로컬 링크 402개와 시안 anchor 39개를 검사해 누락이 없었다. 연결본 세 문서의 본문과 통합본이 링크 변환을 제외하고 일치함을 확인했고 `git diff --check`를 통과했다. 원격 URL 전체 검사나 제품 테스트는 수행하지 않았다.
