# fetcher 유지·수정·보류 판단 연습

2026-10-16. 사용자가 확보한 기준을 실제 사례에 적용하고 추가 질문이 있는지 확인하도록 요청했다. 현재 template `src/api/fetcher.ts`를 다시 읽고, '공통 오류 처리를 사용처가 신뢰할 수 있게 정비하는 작업'을 가정해 리뷰 판단을 제시한다. 목적·규모·계약·수정 범위 기준의 적용 예이며 제품 코드 변경 권한으로 해석하지 않는다. 사용자 채택 전 Main의 판단안이다.

## 보존할 계약과 유지 판단

get/post/put/delete 호출 방식, 정상 응답의 JSON·문자열 본문 반환, 기본 URL·헤더·10초 timeout은 유지한다. 상품 가공·페이지 정책·토스트·화면 이동은 사용처에 둔다. 현재 크기에서 하나의 fetcher와 APIError로 공통 요청을 제공하는 구조는 이 목표에 충분하며 inter-persona의 전체 오류 서비스나 다수 오류 클래스를 가져오지 않는다. 신뢰할 오류 계약과 구조의 복잡성을 구별한다.

## 현재 목표와 직접 관련된 수정 판단

- 비동기 본문 읽기·파싱 실패도 일관된 오류 계약을 거쳐 전달하도록 한다. 현재 return handleResponse(response)의 rejection은 지역 catch를 통과하지 않을 수 있다.
- 파싱 오류를 단순히 네트워크 오류로 바꾸지 않도록 요청 실패·응답 읽기·JSON 파싱의 경계를 구별한다. return await 한 줄만 바꾸는 수정으로 충분하다고 보지 않는다. 본문 읽기 중 timeout은 파싱 실패로 잘못 덮지 않아야 한다.
- HTTP 실패 응답의 본문 파싱마저 실패할 때 이미 받은 HTTP 상태를 보존한다. 예를 들어 500과 깨진 JSON을 받았다면 원래 상태와 읽기 실패 근거를 잃지 않게 한다. 실패 본문이 null 등 예상 객체 형태가 아니어도 message·code 접근이 새 오류를 만들지 않도록 한다.
- timeout timer의 수명을 요청·본문 처리의 종료까지 연결하고, 완료·실패 때 정리한다. fetch에서 헤더를 받은 직후 조기 해제하지 않도록 한다. 사용자 취소 signal의 지원 계약 확장은 이번 판단의 필수 구현안으로 섞지 않는다.

수정 후보는 단순 명명 취향이나 미래 범용화가 아니라 선택한 오류 처리 목표에 직접 연결된다. 모든 기능 작업마다 이 주변 오류 경로를 고치라는 규칙은 아니다.

## 보류와 지원 범위

자동 재시도·인증 이동·공통 토스트, 모든 응답의 스키마 검증, 오류 클래스 대규모 분리와 파일 재배치는 요구가 확인되지 않아 보류한다. 입력 signal이 내부 controller에 덮이는 현재 제한은 기존 관찰로 남기며, 호출자 취소를 이번 목표에 포함하는 실제 요구가 생기면 별도 계약 판단이 필요하다. 미지원과 정확성 결함을 같은 것으로 취급하지 않는다.

## 수정한다면 확인할 동작

정상 JSON·문자열 반환, 정상적으로 읽힌 HTTP 오류의 status·code 보존, 200 응답의 깨진 JSON이 네트워크 실패와 구별되는지, 500의 깨진 JSON에서도 HTTP 상태가 남는지, 본문 읽기 중 시간 초과의 의미, 완료·실패 뒤 timer 정리를 확인할 계획이다. 전부 실행 전이며 테스트 통과나 실제 수정 결과는 없다.

## 추가 사용자 질문과 다음 단계

현재 대화의 리뷰 판단안을 만드는 데 필수인 추가 질문은 없다. 제품 목적·직접 관련성·변경 범위·동작 유지에 관한 답을 이미 받은 상태다. 사용자에게 파싱 코드 이름이나 예외 클래스 수 같은 일상 구현 결정을 떠넘기지 않는다. 제시한 유지·수정·보류 판단이 기대와 다르면 그 차이를 후속 사례로 보정할 수 있다.

추가 미확정 제품 요구가 없는 이번 분석 단계에서는 질문을 만들어 늘리지 않는다. 실제 배포 프로젝트에 적용할 때의 요청 범위·호환성·오류 표시 정책은 그 프로젝트 근거로 확인해야 한다. 01-02 완료나 reviewer의 전체 실행 권한을 확정한 것이 아니다.
