# 04-02 — 유지할 기준, 스킬 보완, 첫 보고 실행 연결의 구체안

[새 source와 형성 배경의 재판단](2026-10-21-ticket04-02-source-and-background-reassessment.md)을 토대로 제시한 논의안이다. 비교 기준은 보존된 Noline 기존판이며 현재 prototype의 보류 후보가 아니다. 실제 SKILL.md·공통 실행 기준·DEVELOPMENT를 변경하거나 새 응답 시험을 수행하지 않았다.

## 유지할 것

| 대상 | 유지할 내용 | 이유 |
| --- | --- | --- |
| briefing 목적·실제 결과 | 전체 역할·대표 흐름부터 설명하고 중요한 이름을 데이터·책임과 연결. 필요할 때 값·조건 대비와 최소 구조 표현 | 원래 연구와 기존 본문에 이미 있다. 역할 항목·도식 의무를 더 넣는 방식으로 반복하지 않는다 |

이번 사건에 대한 권고는 recovery 본문 유지다. 이전 보류 후보의 사용자 이해 추정 방지·표현 전환·질문식 학습 관련 문구 전체를 이번 결론으로 채택하지 않는다. 다른 장면에서의 보완 필요성은 그 장면의 원문·기준·효과를 따로 대조할 문제다.

## briefing에서 구체화할 두 위치

새 책임을 추가하기보다 기존 요구가 현재 답에서 무엇으로 드러나야 하는지 명확히 하는 후보이다. 문구 차이의 효과는 아직 확인하지 않았다.

### 문서·분석·review 결과의 조사 항목 교체

기존:

> 어떤 질문과 기준을 대상으로 만든 산출물인지 먼저 확인한다.
>
> 직접 확인한 finding과 작성자의 해석, 아직 확인하지 않은 범위와 후속 판단을 구분한다.
>
> 문서가 가리키는 live code·test·configuration이 중요하면 현재 Owner까지 내려가 대조한다.

교체안:

> 어떤 질문과 기준에 답하려던 산출물인지 확인하고, 현재 설명할 결과가 그 질문의 어느 부분에 답하는지 연결한다. 이전 문제를 다시 확인한 자료라면 당시 문제·그 뒤 변경·이번 확인의 관계가 현재 결론을 바꾸는 부분을 함께 설명한다.
>
> 직접 확인한 finding과 작성자의 해석, 아직 확인하지 않은 범위를 구분한다. 확보한 근거가 현재 질문에 답하지 못하면 그 간극을 밝히고, 답에 필요한 사실은 허용된 범위에서 더 확인한다. 새 진단·review나 실행이 필요하면 현재 설명으로 확인한 범위와 이어서 수행할 일을 구별한다.
>
> 문서가 가리키는 live code·test·configuration이 중요하면 현재 Owner까지 내려가 대조한다.

첫 문단은 ‘질문을 확인했다’에서 그 질문과 현재 결과의 관계까지 이어 준다. 둘째 문단은 미확인을 분류하는 데서 멈추지 않고 현재 답을 만드는 데 필요한 사실을 다룬다. 모든 과거 이력이나 실패 경로를 조사하라는 뜻은 아니다. 새 검토 작업의 충분성 판단 전체는 아래 실행 흐름이 맡는다.

### 끝낼 때 첫 문단 교체

기존:

> 대상의 역할, 실제 변경이나 연결, 중요한 근거 한계와 미확정이 보이면 현재 브리핑을 끝낸다. 추가 세부는 현재 질문에 필요하거나 사용자가 요청한 부분부터 펼친다. 기준 source·runtime·artifact가 바뀌면 결론도 달라질 수 있을 때만 재확인 조건을 남긴다.

교체안:

> 현재 질문에 답하면서 대상의 역할, 실제 변경이나 연결, 결론을 바꾸는 근거 한계와 미확정을 보여 줬으면 현재 브리핑을 끝낸다. 진행·남은 일이나 다음 선택을 묻는 경우에는 무엇이 해결·미해결·판단 대기인지와 그것이 다음 행동에 갖는 의미까지 연결한다. 구조 이해가 목적이면 그 이해에 필요한 답으로 마친다. 추가 세부는 현재 질문에 필요한 부분부터 펼치며, 기준 source·runtime·artifact가 바뀌면 결론도 달라질 수 있을 때만 재확인 조건을 남긴다.

기존 역할·연결·근거 항목은 유지하되 항목의 존재를 질문에 답한 것으로 대신하지 않게 한다. 모든 설명에 다음 행동을 요구하지 않는다. 반복된 결과 항목 목록과 종료 문장의 편집 정리는 전체 본문 통합 때 판단하며 별도 새 체크리스트를 붙이지 않는다.

## 작업 흐름에서 연결할 책임

연결 위치는 현재 DEVELOPMENT의 결과 통합·보고 부분에 대응한다. 문서의 최종 위치·실행 스킬 배치는01-01·04-03과 맞춰야 하며 병렬 작업의 현재 본문은 이 제안으로 수정하지 않는다. 별도 reviewer·agent를 추가해야 하는 안이 아니다. 아래는 조사·검토 결과로 현재 상태나 다음 행동을 판단해 보고하는 작업에 대한 제안이다.

| 시점 | main 또는 맡은 실행자가 할 일 | 보고서 사건에 적용하면 |
| --- | --- | --- |
| 조사·위임 시작 | 원래 목적에서 이번 확인이 답해야 할 질문과 필요한 조건을 잡아 전달. 수집·해석의 담당을 분명히 함 | 비활성 여행의 제한·복귀 질문에는 같은 비활성 여행에서 전환 전후의 관찰이 필요. 단순 화면 목록으로 축소하지 않음 |
| 수집 결과가 도착 | 결과를 질문과 조건에 대조. 무관한 정상 관찰과 필요한 관찰을 구별 | 활성 정상 화면은 대조군으로 쓸 수 있어도 비활성 제한 확인 완료로 인정하지 않음 |
| 중요한 간극이 남음 | 결론에 미치는 영향·허용 범위·비용·제약으로 추가 확인 또는 제한된 종료를 판단 | 열린 폼의 Debug 이동 제약을 목록 복귀·저장 날짜값 확인까지 멈추는 이유로 쓰지 않음 |
| 첫 결과 전달 전 | 원래 질문에 대한 현재 답·근거·미해결·그에 따른 행동을 종합. 담당한 검토가 끝났는지 판단 | ‘캡처와 네 HTML 완성’과 ‘남은 문제의 판단 완료’를 구별. 추가 검토가 필요하면 조사 상태로 보고 |

흐름 본문의 통합 문구 후보:

> Main은 작업을 시작하고 결과를 받는 과정에서, 이번 판단이 답해야 할 질문과 확보한 근거를 대조한다. 위임할 때는 필요한 대상·조건과 수집·해석의 담당을 전달하고, 반환된 자료가 그 질문에 답하는지 확인한다. 중요한 간극이 남으면 결론에 미치는 영향, 허용 범위와 확인 비용·제약을 따져 필요한 확인을 이어가거나 현재 결론의 범위를 제한한다. 미확인 표시는 조사 종료의 이유를 대신하지 않는다.
>
> 첫 결과를 전달할 때는 원래 문제와 이번 결과를 연결해 현재 답·근거·남은 문제와 그에 따른 행동을 종합한다. 실제로 마친 조사·수정·확인과 남은 작업을 구별하며, 자료 수집이나 보고서 파일 생성만으로 맡은 검토가 끝났다고 보고하지 않는다. 이 설명은 사용자 재질문을 기다리지 않고 작업 결과의 일부로 수행한다.

자동 재시도 횟수나 전수 확인을 강제하지 않는다. 제약 때문에 결론을 제한해 보고하는 것도 가능한 종료다. 새 제품 선택이나 권한 밖의 조작이 필요한 일은 그 사실을 드러내되, 이미 맡은 범위의 추가 확인을 형식적 승인 요청으로 멈추지 않는다.

## 기존 스킬·공통 기준과의 실제 연결 후보

첫 보고 전체를 recovery로 처리하지 않는다. 이미 존재하는 결과를 더 깊이 이해하려는 요청에는 briefing을, 특정 앞선 응답의 뜻·논리를 복구하려는 요청에는 recovery를 유지한다.

작업 절차가 위 첫 결과보고를 직접 수행하면서 근거 구별과 설명 깊이를 재사용하려면, 공통 기준의 consumer를 명시해야 한다. 현재 shared의 ‘세 스킬에서만 사용한다’는 계약을 그대로 둔 채 작업 절차가 사용한다고 적으면 연결이 맞지 않는다. 권고 후보는 작업 결과보고를 소비자로 추가하고 실행 기준을 한 곳에서 유지하는 것이다. 이것은 독립적인 적용 범위 변경이며 이번에 실제 반영하지 않았다.

공통 기준의 ‘적용과 수명’ 첫 문단 교체 후보:

> 이 문서는 `work-discussion`, `explanation-recovery`, `work-artifact-briefing`이 적용되거나, 작업 수행 절차가 조사·검토·구현의 첫 결과를 설명하는 기준으로 명시해 사용할 때 적용한다. Skill별 호출과 행동은 각 SKILL.md가, 조사·구현·검토의 수행과 종료는 해당 작업 절차가 소유한다. 이 문서가 일반 대화와 모든 응답의 자동 적용 workflow가 되지는 않는다.

같이 맞출 곳은 shared의 consumer·수명 설명, skills 안내, 실제 작업 절차의 사용 시점과 읽기 링크다. 현재 공통 기준에는 ‘세 consumer가 모두 없어지면’이라는 조건도 있어 추가 소비자를 포함하도록 바꿔야 한다. 기준의 부작용 제한은 설명 요청만으로 권한이 생기지 않는다는 뜻을 유지하며, 원래 맡은 조사·구현·보고 권한을 취소하는 것으로 해석하지 않는다. 실제 절차가 정해지기 전에 가상의 실행 정본·스킬을 만들지는 않는다.

## 같은 사건에서 달라져야 할 실제 행동과 전달

아래는 과거에 실제로 실행한 결과가 아니라 후보의 행동 차이를 설명하는 예시다.

수집이 활성 여행 화면만 돌려준 시점:

> 활성 여행에서 내용이 유지되는 것은 확인했지만, 이번 질문인 비활성 여행의 제한·복귀에는 아직 답하지 못합니다. 목록에서 같은 비활성 여행의 제한 전후를 확인할 수 있는지 추가로 보겠습니다. 홈 재현에 필요한 상태 변경은 별도 제약으로 남깁니다.

원래 흐름에서 달라져야 하는 핵심은 이 말을 더 일찍 쓰는 것보다 실제 추가 확인을 지시·수행하고 그 결과를 판단에 사용하는 일이다.

확인이 제한된 채 첫 보고를 마치는 경우:

> 이번 보고서로 확인된 것은 활성 여행에서 연결이 바뀌어도 기존 내용이 유지된다는 점입니다. 비활성 여행에서 제한을 해제한 뒤 내용이 돌아오는지는 아직 확인하지 못해, 목록 복귀가 해결됐다고 결론 내릴 수 없습니다. 날짜 차이는 화면에서 재현됐지만 저장값과 시간대의 대조가 남아 있어 원인 확인 단계입니다. 이 확인을 마쳐야 수정 대상과 종료 가능한 항목을 나눌 수 있습니다.

이는 추가 확인이 가능한데도 이 문구로 종료해도 된다는 예시가 아니다. 앞의 범위·비용·제약 판단에 따라 제한된 종료가 타당할 때의 전달이다. 날짜 원인을 확인해도 어떤 날짜 의미로 바꿀지라는 제품 결정이 자동으로 끝나는 것은 아니다.

## 검증할 주장

후속 확인은 이 보완안이 효과를 냈다고 미리 전제하지 않는다. 같은 최초 요청과 당시 유효한 원자료에서 기존 조건·제안 조건을 비교할 때, 질문에 맞는 관찰을 요청하고 부족한 반환을 대조하며 필요한 추가 확인 또는 근거 있는 제한을 판단했는지 확인해야 한다. briefing 문구만 바꾼 조건과 실행 흐름을 연결한 조건을 한꺼번에 바꿔 효과를 귀속하지 않는다. 원래 자료 공백을 해설이나 기대 답으로 대신하지 않으며 실제 사용자 이해와 실행 과정의 개선은 구별한다.
