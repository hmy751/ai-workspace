## 책임과 사용 조건

일반 호출부는 무엇을 언제 알릴지와 원하는 표시 시간을 전달한다. 배열 갱신·ID 생성·타이머 정리 방법은 몰라도 된다. Toast를 배치하는 앱 통합부는 표시 컴포넌트가 공유 상태를 읽고 자동 제거 타이머도 소유한다는 사용 조건을 알아야 한다.

현재 duration은 addToast 시각부터 계산하는 데이터 만료 시간이 아니라 ToastItem effect가 시작된 뒤 자동 제거까지의 시간이다. Toast가 없으면 데이터는 추가돼도 표시·타이머는 시작하지 않는다. 만료 전 Toast가 unmount되면 타이머는 취소되지만 store의 항목은 삭제되지 않는다. 다시 mount되면 남은 항목마다 새 duration으로 타이머를 시작한다. 여러 Toast를 배치하면 같은 배열의 항목을 각각 표시하고 타이머도 각각 만든다. 이는 실제 앱에서 발생했다는 보고가 아니라 코드로 도출한 수명 조건이다.

Toast를 앱 공통 위치에 하나 두고 안정적으로 유지한다면 현재 분리는 단순하고 자연스럽다. 표시 컴포넌트가 사라져도 요청 시점부터 만료되어야 하는 요구가 있다면 상태 수명과 타이머 책임을 함께 재검토할 이유가 생긴다. 타이머를 무조건 store로 옮겨야 한다는 결론은 아니다.

이전 fetcher의 공개 계약·사용처 부담 기준을 상태의 수명에 적용한 관찰이다. Toast를 이 방식으로 만든 당시 사용자 의도와 다른 수명 정책의 선호는 아직 확인하지 않았다. 다음 대화는 이 실제 구조와 사용 조건에 대한 판단에서 이어가며, 다른 영역 탐색 충분성이나 01-02 완료로 해석하지 않는다.


## 후속 비교: ToastItem과 store의 타이머 소유

사용자는 같은 addToast 호출을 기준으로 두 방식의 코드·적합한 상황·사용처 지식 차이를 요청했다. 실제 template는 유지하고, store 대안은 대화의 설명용 코드로 제시했다. 대안은 기존 ToastData·ToastState·randomId를 사용하고 create 콜백 안의 Map에 ID별 timer를 보관한다. addToast가 기본 5000ms의 타이머와 항목을 만들고 removeToast가 timer 취소·Map 제거·목록 삭제를 함께 수행한다. ToastItem에서는 effect를 제거하고 기존 표시 JSX를 유지한다. 구현 적용·컴파일·실행 검증은 하지 않았다.

- 현재 방식: ToastItem effect 시작부터 duration 뒤 제거. unmount 시 타이머 취소, 데이터 유지, remount 시 새 duration. 렌더링된 항목의 표시 수명을 기준으로 할 때 적합하다. 숨겨진 탭까지 포함한 실제 가시 시간을 측정하거나 남은 시간을 보존하는 구현은 아니다.
- store 대안: addToast 호출부터 duration 뒤 제거를 예약한다. 같은 앱 실행 안에서 화면이 unmount되어도 유지되고, 표시되지 않은 항목도 만료된다. 화면과 독립된 일시 알림 데이터 수명이 필요할 때 적합하다. 브라우저 전체 종료를 넘는 영속 만료를 제공하는 것은 아니다.
- 일반 호출 API는 동일하지만 duration의 의미가 바뀐다. 단순한 코드 이동이 아니라 동작 계약 변경이다.
- 화면 통합부는 두 방식 모두 Toast 표시 위치를 마련해야 한다. 현재 방식에서는 그 컴포넌트의 수명이 만료에 영향을 주며, 대안에서는 표시 컴포넌트 없이도 만료된다. 여러 Toast가 같은 배열을 중복 표시하는 문제는 store 타이머로 해결되지 않는다.
- store 대안은 수동 제거와 자동 만료의 정리를 함께 소유해야 한다. 앱별 전체 초기화·store 폐기 요구가 생기면 그 경로의 timer 정리도 필요하다. 현재 비교에서 추가 API 설계나 구현을 하지 않는다.

적합성은 화면에서 표시되는 시간과 추가 이후 데이터 만료 중 무엇을 원하는지로 판단한다. 사용자의 선택은 아직 없으며 store 이동을 필수 개선으로 기록하지 않는다.
