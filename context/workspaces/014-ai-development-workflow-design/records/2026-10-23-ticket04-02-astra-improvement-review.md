# 04-02 — 목표에 맞춘 브리핑 개선 리뷰

**권고는 현재 방향을 유지하면서, 사용자가 구별하려는 책임을 설명의 중심으로 잡고 실제 코드·조건·결과를 그 관계에 연결하는 것이다.** 실제 코드 제시의 적용 조건만 넓히는 데서 끝내지 않고, 현재 구조의 이유를 설명하는 조건과 핵심·상세의 비중도 기존 본문에 통합할 것을 추천한다. 이번에는 개선 방향을 제안했으며 스킬 본문 수정·새 응답 시험·운영 설치·커밋은 하지 않았다.

후속: 사용자 요청으로 이 방향을 본문·background에 반영하고 [직전 채택판과 비교](experiments/artifact-explanation-trip-responsibility-2026-10-23/comparison.md)했다. 양쪽 모두 실제 코드 없이 답해 의도한 핵심 개선은 나타나지 않았다. 아래는 반영 전 개선 리뷰와 판단의 기록이며 실제 시험 결과와 구별한다.

## 요청과 리뷰의 역할

여행 저장·목록 갱신의 [두 판본 비교](experiments/artifact-explanation-trip-list-body-2026-10-23/comparison.md) 뒤 사용자는 “그럼 보완이 나을까?”라고 물었다. Main은 전체 역할·구조 이해에도 실제 코드가 필요할 수 있으므로 코드 제시 조건과 종료 판단을 보완하자고 답했다. 이어 사용자는 다음을 요청했다.

> 지금 상황에 개선리뷰어 물업하 검증 말고 개선할게 뭐인지 목표에 맞게 더 개선하는 아스트라 하이로

GPT-6-astra, high, 새 컨텍스트의 내부 리뷰어 `briefing_improvement_astra`에 목표에 맞는 개선 조언을 맡겼다. 현재안의 통과/실패 판정이나 새로운 응답 시험이 아니다. Main의 직전 원인 가설·수정안을 제시하지 않고 원자료, 현재 본문, 형성 의도와 두 응답을 제공했다. 범위는 읽기·판단으로 한정했고 수정·시험·다른 agent 호출은 맡기지 않았다.

개선 판단에는 실제 후속 교정도 자료로 제공했다. 이는 교정을 제외했던 응답 생성 실험과 다른 목적이며, 후속 교정이 원래 시험 입력에 있었다고 해석하지 않는다. 리뷰어는 원문·본문에서 필요한 근거를 선택하고 Main의 방향을 바꿀 수 있었다. 해당 역할 운용에는 `subagent-delegation`과 독립 판별자 기준을 적용했다.

## 직접 대조한 목표와 근거

원래 [형성 맥락](prototypes/development-workflow/skills/explain/_background/legacy/work-artifact-briefing/context.md)은 사용자가 작업물의 역할·실제 연결·근거의 범위를 이해해 자기 질문과 판단을 만들게 하는 것을 목표로 둔다. 역할 설명, 대표 흐름, 실제 코드·값 연결은 새로 발견한 요구가 아니다.

[선행 대화](../source/artifact-explanation-scenes/05-trip-list-briefing/input/conversation.txt)에서 사용자는 전체 브리핑 전에 이미 책임 배치를 물었다.

> 여행 자체가 다른 성격이라 그런건 이해가 된느데 아직 그래도 책임 분리와 이런 구조가 잘 반영이된 선택인가? 싶어 다시 검토해줘

이 발화는 source_line=3484다. 앞선 구현 재검토 요청의 목적을 마지막 “전체 작업 설명해봐 어떤건지”(3905)가 이어받는다. 마지막 문장만 보고 일반적인 작업 개요로 좁히기보다, 무엇이 달라졌고 그 책임이 실제 어디에 놓였는지를 함께 설명할 맥락이 있었다.

[첫 브리핑 뒤 원문](../source/artifact-explanation-scenes/05-trip-list-briefing/evaluation/conversation.txt)의3962는 다음과 같다.

> 근데 앞선 설명은 설명만 잇으니까 좀 어렵네 멘탈모델 도식화 구체적 코드도 고려하고 코드는 순수 동작 보다도 각 코드가 맡는 핵심적 역할 고려해서 잘 설명해줘 다시 브리핑 해봐

이번 [기존판 응답](experiments/artifact-explanation-trip-list-body-2026-10-23/r35/output/response.md)과 [현재판 응답](experiments/artifact-explanation-trip-list-body-2026-10-23/r82/output/response.md)은 저장 위치 불일치, 목록 조회로 옮긴 책임, 로컬 변경 보존, 검사 한계를 설명했다. 역할·사실·근거 설명이 전혀 없었다고 평가하지 않는다. 다만 많은 구성요소와 조건이 문장으로 이어지고 실제 코드가 제시되지 않아, 사용자가 책임 배치를 구현에 대응하는 부담이 남았다.

## 리뷰어의 개선 우선순위와 Main 판단

리뷰어의 핵심 표현:

> 내용은 들어 있지만, 사용자가 코드의 책임 관계를 다시 조립해야 하는 부담이 남아 있습니다.

| 개선 우선순위 | 유지할 것 | 기존 본문에 통합할 변경 | Main 판단 |
| --- | --- | --- | --- |
| 이해해야 할 구별을 먼저 잡기 | 현재 질문과 선행 대화에서 설명 목적·깊이를 정한다 | 시작1번에서 역할·상태·책임의 어떤 차이를 이해하려는지 잡는다. 전체 구조 이해와 실제 코드 사용을 양자택일로 두지 않는다. 종료에서도 그 차이가 사례의 결과에 연결됐는지 본다 | 권고에 반영. 직전 제안의 코드 제시 조건보다 앞에서 설명의 초점을 잡는다 |
| 책임 경계가 드러나는 코드를 고르기 | 역할 우선, 대표 흐름, 실제 코드·값·실행 연결 | 중요한 판단을 어디서 하고, 무엇을 다른 코드에 맡기며, 어떤 결과를 반환하는지 드러나는 부분을 고른다. 문법 상세는 필요한 때 추가한다 | 권고에 반영. 기존 실제 코드 요구에 선정 기준을 통합하며 별도 중복 규칙을 붙이지 않는다 |
| 현재 구조의 이유·효과도 설명하기 | 당시 이유와 현재 도출 효과를 구별한다. 전체 설계 review로 확대하지 않는다 | 현재의 “다음 변경이나 선택을 위한 설명일 때”를, 현재 구조가 왜 그렇게 나뉘었는지 이해하는 데 필요한 조건까지 포괄하도록 정리한다 | 권고에 반영. 모든 구조의 장단점 의무가 아니라, 사용자의 구조 이해 질문에 필요한 효과·제약을 설명한다 |
| 중심 관계와 보강 정보의 비중 나누기 | 전체 역할에서 대표 흐름·세부로 내려간다. 필요한 사실과 한계는 보존한다 | 가장 중요한 관계와 한 사례를 먼저 연결하고, 그 뒤 다른 분기·검사 세부를 보강한다. 관계를 반복해서 문장으로 되짚게 되면 표·도식 등의 표현을 실제로 선택한다 | 권고에 반영. 정보량 축소나 고정 목차·도식 개수로 해결하지 않는다 |

리뷰어는 위 내용을 세 우선순위로 묶었고, 이 표는 Main이 현재 구조의 이유·효과에 관한 적용 조건을 따로 드러낸 것이다. 제안의 출처와 Main의 재구성을 구별한다.

**Main의 직전 제안에서 보완된 부분:** “전체 작업 설명에서도 실제 코드를 보여 줄 조건”은 유지하되, 설명의 중심을 먼저 정하고 그 질문에 맞춰 구현과 조건을 묶는 방향으로 넓힌다. 가독성 요구가 이미 있다는 이유만으로 실제 구성의 부족을 두고 넘어가지 않는다. 기존 요구를 반복하는 대신 목적 판별·세부 선정·이득과 제약의 적용 조건·종료를 연결한다.

## 리뷰가 제안한 응답 예시의 핵심

다음은 리뷰어 예시 중 저장과 목록 갱신의 관계를 보여 주는 부분을 Main이 발췌·재구성한 것이다. 새로운 시험 응답이나 사용자 수용 결과가 아니다. 실제 코드는 당시 복원 자료와 대조했다.

이번 변경의 핵심은 **여행을 저장하는 일과 화면에 보여 줄 목록을 준비하는 일을 나눈 것**이다. 파리가 활성 여행이고 새 도쿄가 비활성 여행이라는 설명용 상황에서는, 기기 DB에 둘 다 보여도 둘의 수정 경로까지 같아지는 것은 아니다.

| 대상 | 변경을 확정하는 곳 | 목록 조회에서 하는 일 |
| --- | --- | --- |
| 활성 파리 | 기기 DB와 서버 전송 대기열 | 기기의 값을 보존 |
| 새 비활성 도쿄 | 서버 | 서버 값을 기기의 목록용 사본에 반영 |

생성 훅의 다음 부분은 저장과 재조회 요청의 경계를 보여 준다.

```ts
return useMutation({
  mutationFn: (data: CreateTripRequest) => TripRepository.create(data),
  onSuccess: () => cancelAndInvalidateQueries(queryClient, { queryKey: tripQueryKeys.all() }),
  // 오류 처리 생략
});
```

`mutationFn`은 도쿄를 만드는 일을 맡는다. `onSuccess`는 성공 뒤 여행 목록을 다시 읽으라고 요청한다. 이 자리에서 도쿄의 목록용 사본을 직접 쓰거나 파리의 보존 여부를 판단하지 않는다. 원문은 [생성 훅](../source/artifact-explanation-scenes/05-trip-list-briefing/historical-materials/files/apps/client/src/entities/trip/data/useCreateTrip.ts)이다.

서버에서 목록을 읽는 경로에서는 다음 코드가 서버 목록과 보존할 로컬 데이터를 연결한다.

```ts
const response = await TripApi.fetchAllTrips();
const result = await TripLocal.refreshTripListLocal(response.data, sessionId, signal);
return { trips: result.trips, source: result.hasLocalTrips ? 'mixed' : 'remote' };
```

이 코드의 “조회”는 단순히 DB에서 읽는 것에 그치지 않는다. **화면에 줄 목록을 준비하면서 목록용 사본도 갱신한다.** Repository가 두 작업을 연결하고, 로컬 저장 코드는 어떤 행을 보존·반영할지 처리한다. 활성 여행과 미전송 변경이 남은 여행은 서버 결과로 덮어쓰지 않는다. 원문은 [Repository](../source/artifact-explanation-scenes/05-trip-list-briefing/historical-materials/files/apps/client/src/entities/trip/repository/trip-repository.ts)와 [로컬 반영 코드](../source/artifact-explanation-scenes/05-trip-list-briefing/historical-materials/files/apps/client/src/entities/trip/lib/trip-local.ts)다.

처음 수정안에서는 생성·수정·삭제가 각각 목록 사본도 고쳤다. 그 반영에 실패해도 당시의 목록 새로고침은 로컬만 읽어 복구하지 못했다. 목록을 준비하는 규칙을 조회에 두면 생성 직후뿐 아니라 이후 재조회에서도 같은 규칙을 사용한다. 이는 선행 원문3521의 재검토 이유와 연결된다.

**저장 성공과 목록 갱신 성공도 별개다.** [갱신 함수](../source/artifact-explanation-scenes/05-trip-list-briefing/historical-materials/files/apps/client/src/shared/lib/query-refresh.ts)는 이전 조회 취소를 기다린 뒤 새 조회를 요청하고, 새 조회 완료는 기다리지 않는다. 따라서 목록 재조회 실패를 이미 끝난 서버 저장의 실패와 혼동하면 안 된다.

이 예시가 만들려는 이해는 “저장은 됐는데 목록이 오래됐으면 어느 책임을 봐야 하는가”, “로컬 사본이 있다고 왜 로컬 수정이 가능한 것은 아닌가”를 구별하는 것이다. 코드 개수·도식 유무 자체가 성공 기준은 아니다.

## 확인 범위와 다음 판단

리뷰어는 현재·기존 스킬, 형성 자료 세 파일, 최근 입력·평가 대화 전문, 두 시험 응답, 구성 정책·공통 기준, 당시 Repository·Router·생성/조회 훅·로컬 저장·갱신 함수를 읽었다고 보고했다. Main은 현재 본문·현재판 응답과 선행3484·후속3962를 직접 다시 읽고, 예시의 생성 훅·Repository·갱신 함수 및 로컬 보존 코드에 대조했다.

후속 교정과 원래 목적은 개선 방향의 근거다. 특정 문장이 모델 출력의 원인이라는 증거, 새로운 문구의 안정된 효과, 실제 사용자 이해의 확인은 아니다. 반대로 이 인과가 미확정이라는 이유로 현재 근거에 따른 개선 제안을 미룰 필요도 없다.

다음 권고는 위 판단을 현재 본문의 해당 위치에 통합한 수정안을 만드는 것이다. 사용자에게 방향을 제시한 상태이며 새 본문은 아직 작성·채택하지 않았다. 설명 복구 스킬, 호출 시점, 별도 workflow 지침, 운영 설치는 이번 개선 조언으로 변경되지 않는다. 가까운 `_background`의 현재 선택도 아직 바꾸지 않았으며, 실제 의미 변경 때 이번 근거와 선택을 선별해 반영한다.
