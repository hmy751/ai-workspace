## 적용할 기준과 남은 선택

[잠정 합의](2026-10-25-context-framework-provisional-agreement.md), [배치안](2026-10-25-context-composition-walkthrough.md), [전체 책임 재대조](2026-10-26-context-whole-scope-reconciliation.md), [통합안](2026-10-26-context-integrated-proposal.md)과 네 상세안, 현재 development·context 관리 계약을 다시 읽었다. Matt·Lauren의 [고정판 종합](2026-10-25-context-reference-synthesis.md)을 사용하고 관련 Domain Docs·Skill mechanics·maintain-verification-skill 보존 원문을 재확인했다. 최신 외부판이나 운영 효과를 새로 조사한 것은 아니다.

- 담당자는 Main이 준 목표·범위·판본·접근점에서 출발해 필요한 원문을 직접 읽고, 새 질문에 따라 추가 탐색한다. Main의 요약이나 current가 원문을 대신하지 않는다.
- 현재 Work에는 이번 적용 의미·선택·상태·다음 행동을 남긴다. 상세 근거·대안·중요한 제안과 처리 이유는 기존 records, 실제 결과는 output으로 연결한다.
- 구현자는 맡은 결과와 자기 확인을 완성하고 지속 본문에 반영할 변화가 있으면 근거로 제안한다. 현재 Main이 전체 맥락을 검토하고 실제로 반영한다. 별도로 맡긴 문서 갱신은 그 권한을 따르며 새 상설 관리자를 만들지 않는다.
- Project 갱신 전에 그 변화가 계속 관리할 제품·구조·계약·제약·선택 이유인지 선별한다. 이번 구현·검사 진행은 Work가 맡는다. 공유 이해에 필요한 현재 지원 사실까지 일괄 제외하지 않는다.
- 일상 유지와 이미 정한 의미의 반영은 개발 중 수행한다. 대화 기준의 명시적 개선 단계는05에서 구체화하며, 채택 뒤에는 같은 반영 방법을 쓸 수 있다.
- USAGE 공통 참조와 context-update 스킬은 잠정 작업안이다. 분리된 형태의 사용감·정확한 이름에는 유보가 남아 있다. 이번 적용 계획은 그 안을 실제 본문으로 펼쳐 확인하는 권고이며, 사용자가 둘 중 하나를 선택하거나 입력을 다시 작성해야 하는 절차를 만들지 않는다.

## 네 항목이 한 작업에서 이어지는 모습

가상 요구는 기존 예제의 ‘새 화면이 로그인 뒤 최신 여행 목록을 받은 다음 진행한다’다. 실제 제품 변경이나 확인 결과가 아니다.

1. **시작·재개:** Main이 이번 요청, Work의 선택·이유·실제 결과를 복원한다. 이번 새 소비자 요구에 필요한 Personal·Project 원문을 고른다. 기존 비대기 선택을 새 소비자의 정답으로 옮기거나 충분한 정의를 다시 인터뷰하지 않는다.
2. **인수·수행:** 구현자는 배정된 범위·판본과 원문을 직접 대조하고 필요한 질문을 추가로 탐색한다. 구현과 자기 확인을 끝내며 지속 설명을 바꿀 필요가 있으면 그 의미·범위·근거를 기존 반환에 붙인다. 중요한 충돌은 완료 보고 전에 알린다.
3. **변화·반영:** Main이 그 제안을 원요구·계약·다른 사용처에 대조한다. 기존 계약 안의 소비자별 적용이면 이번 선택·진행은 Work에 남기며 Project 변경 없이 끝날 수 있다. 공통 약속·구조·지원 제약이 실제 바뀌면 해당 본문을 한정 반영하고 관련 담당자·이전 의견과 검사에 미친 영향을 잇는다. 변경된 문서도 기존 개선 검토·요구 검증에서 평가할 결과다. 이 연결은 수행 중 반복된다.
4. **완료·연속:** Main이 최신 결과와 근거로 이번 완료 범위를 정하고 기존 explain으로 설명한다. 관련 current·Ticket·output과 남은 행동을 맞춘다. 같은 목표의 다음 대화는1번에서 이어가며, 독립 목표 분리가 요청되면 필요한 의미를 새 Work에 구성하고 생성·전환 결과를 구별한다.

직접 요청도 같은 방법을 쓴다. ‘읽고 설명’은 공통 읽기에서 답으로 끝나고, ‘current에 정리’는 Main의 Work 유지까지, ‘Project에 반영’은 해당 반영 과업까지 수행한다. 활성 Work나 개발 전체 수행을 강제하지 않는다. 이후05의 루프는 남은 후보뿐 아니라 이미 반영한 선택·근거·결과도 사용하며, 채택 결과가 문서일 때 같은 반영 과업으로 연결한다.

## 적용 전 대조에서 확인한 실제 정리 지점

후속 합의를 유지한 채 옛 문장을 정리할 부분을 찾았다. 새 정책 선택이 필요하다는 뜻이 아니다.

- [2번 예시](2026-10-26-context-02-role-execution-proposal.md)의 새 사용처·미구현 설명 정정을 당연한 Project 갱신처럼 잇는 문장은 [3번의 내용 선별](2026-10-26-context-03-change-records-proposal.md)과 맞춰야 한다. 데모에 있다는 사실이 올바른 소유 위치의 근거는 아니다.
- 2번의 ‘기존 배정의 수정 권한 유지’ 문장은 [4번](2026-10-26-context-04-completion-continuation-proposal.md)의 ‘늦은 결과는 원 Work·당시 판본에 귀속, 계속 수정은 최신 배정·공유 상태를 따름’으로 맞춰야 한다.
- 현재 development의 ‘현재 코드·사용처·지원 연결 사실 → Project’ 행에도 지속할 공통 맥락의 선별을 넣어야 한다. 형성 자료 읽기는 기준 재검토뿐 아니라 더 정확한 이해의 조건도 드러내야 한다.
- 현재 root/context의001 직접 선택은 두 번째 Work의 생성·전환 흐름을 적용할 때 목록의 선택 한곳을 따르게 맞춘다. 수동 선택 변경과 실제 host activation은 다르다.

이번에는 이 차이와 적용 위치를 확인·기록했으며 해당 설계 본문이나 실행 지침을 아직 수정하지 않았다. 과거 조사·리뷰 기록은 당시 판정으로 보존하고, 현행 설계 본문과 실행 지침을 최신 관계로 맞추는 것이 다음 적용의 일부다.

## 적용 순서와 끝났다고 볼 범위

1. 위 차이를 최신 합의로 맞추고, 공통 방법의 정본과 기존 위치에 남길 핵심을 실제 조항 단위로 정한다. 이름만 새로 붙이거나 양쪽에 전문을 남기지 않는다.
2. 공통 읽기·지정 반영·생성 수행과 Work 계약을 작성하고, development·역할 상세·root/context·목록에서 실제로 사용되도록 한 묶음으로 연결한다. 기능을 추가하는 동안 이미 정한 역할·권한·내용 경계를 유지한다.
3. 대표 요청에서 직접 읽기·반환·기록·재개가 이어지는지 확인한다. 의미 있는 연결 변경은 기존 역할 계약에 따라 별도 대조를 사용한다. 설명만 요청/같은 Work 재개, 구현자의 제안이 Project 편집 불필요로 끝나는 경우, 실제 지속 내용 변경, 반영 중 중단·재개, 생성만/전환 요청의 차이를 우선 본다. 없는 구현·host의 성공을 가정하지 않는다.
4. 링크·조항 중복·기존 호출·형성 자료·표시 사본을 확인하고04-03의 기존 완료 조건에 대조한다. 확인한 대표 수행과 미확인 운영 효과를 구별해 현재 상태와 후속을 정리한다.

이는 프로토타입의 실제 사용 연결을 완성할 범위다.02의 기록 운영 전체,05의 대화 기준 루프,06의 배포·기존 자동 장치 의존 제거·host 전환,07의 전체 적용·관찰은 각 책임으로 이어간다. 그 전체를 먼저 완성해야 프로토타입에 연결할 수 있다는 뜻도, 이번 통합으로 그 책임까지 완료된다는 뜻도 아니다.

이번 조사에서는 Main이 논의·설계·현재 본문을 읽었고 별도 읽기 전용 담당자가 프로토타입의 실제 조항·부재 파일·책임 중복을 대조했다. 새 독립 개선 리뷰나 사용 시험을 수행한 것으로 기록하지 않는다. 기록·현재 진입의 갱신 외 프로토타입·source·설정은 변경하지 않았다.
