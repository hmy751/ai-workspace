**한 번의 독립 개선 리뷰를 마쳤다. Main은 통합 진입점을 유지하되, 작성 과정 예시를 중심으로 상세를 재구성하고 첫 결과 전달과의 연결을 구체화하는 의견을 현재 제안에 반영한다.** 이는 Main의 제안 보완이며 사용자 채택·스킬 구현·설치·수행 효과 확인이 아니다.

## 1. 요구를 다시 쓰기보다 작성 과정을 보여 준다

리뷰 원문:

> 이전 본문에 방법이 전혀 없었던 것이 아니라, 그 방법을 실제 답으로 만드는 데 실패한 관찰입니다.

> 따라서 새로 추가할 가치가 가장 큰 것은 짧은 **작성 과정 예시**입니다. 좋은 완성 답만 보여 주기보다 무엇을 고르고 어떻게 설명으로 바꿨는지 보여 주는 것입니다.

리뷰어는 [기존 브리핑](prototypes/development-workflow/skills/explain/_background/legacy/work-artifact-briefing/records/2026-10-23-before-explain.txt), [최신 여행 원응답](experiments/artifact-explanation-trip-responsibility-2026-10-23/r71/output/response.md), 당시 `useCreateTrip.ts`와 `trip-repository.ts`를 대조했다. 기존 본문에도 실제 코드를 고르고 의미와 대응시키라는 방법이 있다. 원응답은 역할·이유·사례를 설명했지만 실제 코드 대응은 함수명과 링크에 남겼다.

**Main 반영:** 새 안의 차별점을 ‘이전에는 방법이 없었다’고 설명하지 않는다. 본체에 관계를 정하고 해당 부분을 골라 설명하는 공통 수행을 남기고, 상세에는 설명할 관계·고른 원자료·왜 그 부분인지·실제 짧은 설명을 연결한 작성 과정 예시를 둔다. 이 네 요소를 매 사용자 답의 고정 목차로 만들지는 않는다.

여행 예시는 생성 요청과 성공 후 갱신 요청을 하는 훅, 서버 조회 결과를 로컬 목록에 반영하는 부분을 함께 고르는 이유를 보여 준다. 기존 리뷰의 완성 예시를 새로 발견한 성과로 세거나 전체 브리핑을 복제하지 않는다. 정확한 예시 유지 비용과 특정 사례 편향이 있으며 수행 개선은 아직 가설이다.

## 2. 함께 수행하는 설명 방법을 함께 둔다

리뷰 원문:

> `relationships`와 `reasons-and-evidence`는 현재 설명만으로는 수행 경계가 충분히 다르지 않습니다.

> 파일 두 개가 옳다는 주장이 아니라, 현재 제안에서는 세 번째 독립 경계를 정당화하는 내용이 아직 약하다는 판단입니다.

리뷰어는 현재 구성, 공통 기준, 두 스킬의 형성 자료와 development의 검토 상세를 대조했다. 구조·동작과 이유·근거의 상세는 질문·자료 선정·조건 비교가 겹친다. 앞선 발화 대조에는 그때의 뜻과 지금의 타당성을 분리하고 과거 말을 바꿔 쓰지 않는 별도 수행이 있다. development의 검토 상세는 별도 역할·반환·선택 책임이 있어 분리 근거가 더 분명하다.

**Main 반영:** 초기 상세 후보를 `constructing-explanations.md`와 `prior-explanation.md`로 조정한다. 전자는 원자료와 관계·조건·이유를 연결하는 작성 방법과 예시를 필요한 절로 묶고, 후자는 실제 앞선 발화 대조를 맡는다. 본체는 기본 설명을 직접 수행하며 상세 안내만 남기지 않는다. 전자가 장문 일반 지침 모음이 되지 않도록 공통 기준을 복제하지 않고, 별도 자료·수행 책임이 생겼을 때만 다시 분리한다. 원문 대조를 별도로 남기는 이유는 현재 행동의 차이이며 과거 두 스킬 분리의 의무가 아니다.

## 3. 첫 결과를 만들 때 설명의 공백을 판단한다

리뷰 원문:

> 설명이 성립하지 않는 공백을 결과를 내기 전에 발견하고, 표현을 보완할지 사실을 더 확인할지 작업 담당자가 판단하게 하는 것입니다.

제안된 연결 문안:

> 작업 결과를 전달할 때는 원래 질문에 무엇이 답해졌는지 먼저 구성한다. 그 답을 이해하려면 변경의 관계나 선택 이유를 따라가야 하는 경우 설명 방법을 사용한다. 필요한 연결을 만들 수 없는 이유가 사실 부족이면, 기존 작업 권한 안에서 더 확인하거나 확인할 수 없는 이유와 그 영향을 밝힌다.

리뷰어는 [보고서 후속 대화](../source/artifact-explanation-scenes/01-report-delivery/evaluation/conversation.txt)와 [사용자 인터뷰](../source/noline-evaluation/reviews/interview-20261012.md)를 근거로 들었다. Main도 source_line 789의 사용자 지적, 836의 문제 연결·추가 확인, 864·928의 날짜 원인 확인과 결론 변화, 1100의 최종 보고를 대조했다. 리뷰 반환의 `788 부근`은 정확한 사용자 발화 위치 `789`로 기록한다. 당시 AI가 추가 관찰과 결론 변화를 보고한 대화 근거이며 현재 제품 재실행을 한 것은 아니다.

**Main 조건부 반영:** 이 취지를 통합안의 호출자와 설명 스킬의 연결 계약으로 구체화한다. 작업 주체는 원래 질문에 대한 답을 만들 책임과 필요한 추가 확인의 판단을 맡고, 설명 스킬은 관계·근거를 이해할 수 있게 구성하는 방법을 맡는다. 설명을 위해 모든 작업을 다시 검사하거나 항상 전체 브리핑을 생성하지 않는다. 사실 공백은 현재 답을 바꾸는 범위에서 다룬다. 병렬 진행 중인 development 실행 본문이나 자동 호출 설정은 이번에 수정하지 않는다.

## 유지·변경·확인 범위

유지할 것은 하나의 설명 진입점, 본체의 실질적 수행, 대상·시점을 배타적 모드로 고정하지 않는 판단, 원래 발화의 뜻과 현재 타당성의 구별이다. 수정할 것은 상세의 초기 경계, 작성 과정 예시의 역할, 첫 결과 전달과의 구체 연결이다.

Main은 이번 리뷰로 구성 제안만 보완한다. 사용자의 채택과 실제 본문 작성은 남아 있다. 새 설명 응답을 생성하지 않았고, 파일 수·리뷰 의견·과거 장면 대조를 수행 개선의 증거로 세지 않는다. 기존 Network A/B도 계속 미실행이다.
