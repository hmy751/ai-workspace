## 지금 이어갈 위치

**다음에는 코드 기준을 구체 사례로 논의한다. 전체 설계 대상은 좋은 코드를 반복해서 만들도록 받쳐 주는 작업 단계의 시스템이다.** 여기에는 기준의 내용뿐 아니라 어떤 컨텍스트를 제공하고 찾게 할지, 어떤 절차로 구현·수정할지, 자동 검사·AI 검토·사람 검토와 실제 실행 확인을 어떻게 연결할지, 경험을 무엇에 반영할지도 포함한다.

Main과 사용자 사이의 요구·작업 정의와 Spec·Ticket 결정 단계는 이 작업 단계와 구별한다. 사용자는 전자가 기존에도 어느 정도 작동한다고 보며, 강연에서 특히 영감을 받은 부분은 후자의 미성숙한 환경을 보완하는 일이었다. 선행 설계 절차의 도입을 다음 논의의 중심에 놓았던 것은 Main의 제안이다. 구현 중 모듈·인터페이스·테스트 경계를 설계하는 일은 코드 품질 문제로 계속 다룬다. Project 맥락과 실행 환경을 구체화하며 앞단에 필요한 보완도 연결한다. [직접 근거와 자세한 설명 — 기록 28](2026-10-13-28-execution-system-priority-and-code-criteria.md)

## 기록 28 뒤의 중요한 대화

Main은 기록 28을 작성한 뒤, ‘코드 기준의 내용’과 ‘그 기준이 실제 작업에 쓰이는 방법’을 함께 보자고 제안했다. 같은 동작의 코드 대비, AI가 참고할 기준·좋은 코드·프로젝트 맥락, 기준에 못 미친 결과를 개선하는 방법을 논의 후보로 들었다. 이는 Main의 다음 논의 제안이며 새 운영 계약이 아니다. 또한 토스 자료가 Frontend Fundamentals인지와 코드 스타일을 살필 프로젝트를 물었다. 아직 그 둘에 대한 구체 답은 받지 않았다.

## Matt의 ‘브레이크’에서 직접 확인한 것

[제공된 강연 전체번역](../source/lectures/01_PR_병목_강연_전체번역.md#L19)의 **02:18~04:39**에서 Brake는 세 층을 가리킨다. 자동 검사(lint·test·type checking 등), AI 자동 검토, 사람의 PR 검토다. 강연은 품질이 낮은 코드가 다음 AI 작업의 환경이 되어 더 나쁜 코드를 낳는 문제를 설명하고, 앞의 확인들이 사람 검토의 부담을 줄이도록 연결한다.

**04:39~08:15**에는 자동 검사 통과가 충분한 증거가 아닌 이유와 구현을 반복하거나 과도한 mock으로 실제 문제를 숨기는 테스트가 나온다. **11:20~16:17**에는 별도 검토 context에서 상세 코드 기준을 적용하고 직접 수정하라는 권고가 있다. **16:17~22:24**에는 사람이 변경의 영향과 가역성, 코드가 만들어진 시스템을 보고 경험에서 검사·기준·탐색·도구 개선을 제안하는 관계가 이어진다.

따라서 코드 기준의 내용과 그것을 검사·검토·수정에 연결하는 절차는 구별되지만 함께 설계할 대상이다. 다만 강연의 Brake라는 말 자체를 Project context·기록·워크플로 전체의 공식 명칭으로 확대하지 않는다. 강연의 권고와 현재 공개 `code-review`의 보고서 반환 계약 차이, 실제 인수·재검사·종료 책임의 공백은 [Matt 조사](2026-10-13-24-matt-source-investigation.md)에 남아 있다. 이 차이를 이번 발화로 해결했다고 보지 않는다.

## 유지할 선택과 아직 열린 것

- **유지:** B의 검토자 직접 수정 방향. Main과 작업을 결정하는 단계와 실행 단계를 구별하며, 현재는 실행을 받쳐 주는 시스템을 우선 구체화한다. Project·Work·기록·스킬·경험 반영의 전체 목표도 유지한다.
- **당장 논의할 것:** 구체 코드 대비와 자료를 통해 좋은 코드를 판단하는 기준의 의미·조건·충돌을 살핀다. 기준을 실제 컨텍스트·코드 예시·절차·검사에 어떻게 연결할지도 필요한 만큼 함께 본다. 논의 순서를 모든 자료 조사나 전체 체계 완성의 선행 조건으로 만들지 않는다.
- **미정:** 세부 코드 기준, 역할별 입력과 읽을 범위, 검토자의 상세 수정 권한, 최종 실제 검증의 주체·독립성, 검사·도구·브레이크의 구성과 적용 조건, 기준과 경험의 갱신 방법. 특정 폴더나 새 자동화의 도입은 결정하지 않았다.
- **필요한 추가 정보:** 토스 자료의 정확한 지칭과 개인 코드 스타일을 살필 프로젝트·부분. 기존 코드에서 발견한 패턴은 선호의 증거로 자동 채택하지 않는다. 기존 records의 가독성 기준은 필요한 원문을 확인한 뒤 사용한다.
- **논의 태도:** 원자료의 방법, Main의 해석·제안, 사용자의 선택을 구별한다. 예시를 구체적으로 만들었다는 이유로 바로 채택·구현으로 넘어가지 않는다. 사용자 재질문을 모두 실패로, 침묵이나 가정 요청을 만족·승인으로 취급하지 않는다.

01-02는 기준의 구체 내용과 구현·수정 방법, 01-01은 절차와 판단 책임, 01-03은 자동 검사·실제 확인과 도구, 03은 공통 맥락, 04는 이를 사용하는 스킬과 연결된다. 05·06의 경험 반영과 공통 방식 개선, 02의 기록 구성도 전체 범위에 남는다. 이는 Ticket별 내용을 한꺼번에 확정하거나 다시 분할한 것이 아니다.

## 대화를 남기는 범위에 대한 정정

Main이 최근 대화 보존 요청을 현재 채팅 전체 저장으로 넓혀 원문 사본·JSONL·manifest 세 파일을 만들었고, 사용자는 다음과 같이 정정했다.

> 잠깐 근데 대화를 다 무조건 저장하란건 아닌데 저장하려고 하는건 아니지?

이번에 Main이 새로 만든 전체 대화 사본 세 파일은 되돌렸다. 기존 source의 원문 사본은 변경하지 않았다. 이번 요청은 **마지막 기록 이후 의미 있는 논의·정정·미결정을 자세히 남기고, 나중에 해석을 재검토하는 데 필요한 발화를 선택해서 보존**하는 범위로 처리한다. 모든 사용자·AI 발화, 진행 보고, 도구 출력의 일괄 저장을 기본으로 삼지 않는다. 원문이 이미 보존된 기록 22~28은 연결하고, 이번 기록에 필요한 새 발화만 덧붙였다.

이번 변경은 설계 문서와 진입점의 보완이다. 실제 코드·스킬·하네스 변경, 자동 Maintainer 재개, 새 운영안 채택, Git 커밋은 하지 않았다.
