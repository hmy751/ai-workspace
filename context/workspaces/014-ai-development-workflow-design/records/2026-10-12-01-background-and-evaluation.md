# 평가에서 전체 설계로 넘어온 배경

이 문서는 기존 평가의 근거와 한계를 현재 설계 논의에 연결한다. 새로운 전체 대화 분석이나 Noline 제품 재검증을 수행한 기록은 아니다. 근거 원문과 원래 평가 문서는 [source 안내](../source/README.md)에서 찾는다.

## 연구·이식·평가의 관계

07 연구는 목표를 문서에 저장하고 읽는 것만으로 그 목표가 실제 선택·완료 판단에 쓰이지는 않는다는 문제를 다뤘다. Work의 Spec은 결과와 공통 기준을, Ticket은 확인 가능한 실행 결과를 맡도록 구체화했고, 작업 논의와 재판단을 연결했다. 평가 질문도 판단 연속성 하나가 아니라 개발 결과, 코드 품질과 후속 변경, 사람이 이해·판단하며 결과까지 가는 부담을 포함했다.

09 연구는 사람이 필요한 이해와 판단을 유지하고, 나중에 다시 복구해야 하는 부담을 줄이려 했다. 작업물 브리핑과 앞선 설명 복구는 이 목적의 수단이다. 설명을 제공한 사실로 사람의 내적 이해를 판정하거나, 이해 지원을 제품·코드의 최종 적합성 판정으로 확대하지 않았다. 그림도 설명의 수단이며 효과가 자동으로 보장되는 장치는 아니었다.

Noline에는 이 연구와 ai-workspace의 기반을 단계적으로 이식했다. 평가의 제품 기준점은 `4fb309d2ba50afaca44019879d7161964b9b2328`이다. 설치된 규정과 실제 호출·적용·효과는 구분해야 하고, 나중에 도입한 기준을 초기 개발에 소급하지 않는다. [설계·설치 근거 사본](../source/noline-evaluation/reviews/noline-design-basis.md)

## 사용자의 회고가 바꾼 해석

| 장면 | 확인된 경험과 남은 판단 |
| --- | --- |
| 기록과 Ticket으로 재개 | 전체적으로 재설명할 일이 줄고 이전보다 편해졌다. 일부 중심 교정은 답답했지만 보통 한두 번으로 바로잡았고 큰 부담은 아니었다. |
| DB Promise 설명 | 두 갈래로 나눈 설명은 도움이 됐다. 필요한 학습과 AI가 혼동 지점을 더 빨리 짚을 여지가 함께 있어 전체 성공·실패로 닫지 않았다. |
| 첫 결과·보고의 충분함 | 한 번 더 요구하면 나아지는 점이 아쉬웠다. 재작성은 “좀 나아졌다” 정도였고 기준이 불명확해 넘어간 부분도 있었다. |
| Project 문서 | 문서의 부족, 나중으로 미룸, 관리 부담 중 무엇이 컸는지는 기억이 불확실하다. 문서에 따라 핵심·사례·절차의 필요가 다르며 짧음만으로 품질을 판단하지 않는다. |
| 네트워크 개선 철회 | 가독성 작업이었지만 사용자는 필요한 동작 개선도 의도적으로 받아들였다. 나중에 유사 기능을 구현했으므로 당시 철회를 범위 위반이나 구현 거부로 단정할 수 없다. |
| access 질문 | 마지막 설명은 도움이 됐다. 질문하자 바로 바꾸려는 대응은 아쉬웠고, 기존 선택을 판단하고 이유를 설명하기를 원했다. |
| DB·인증 실패 동작 논의 | 중요한 선택이라 질문할 만했고, 이해를 위해 이어 물은 과정도 나쁜 과정으로 평가하지 않았다. |
| Ticket 06 종료 | 기록상 종료 처리는 확인되지만 만족도·중단 동기는 불확실하다. “급하게 마무리” 정정은 현재 인터뷰 질문 수에 관한 말이었다. |

이 해석의 직접 근거는 [인터뷰](../source/noline-evaluation/reviews/interview-20261012.md)와 [현재 채팅의 사용자 발화·AI 응답](../source/discussion/conversation.md)이다. 원래 개발 장면은 [scene evidence](../source/noline-evaluation/scene-evidence.md), 세션별 원문은 보존된 `source/noline-evaluation/corpus/<session>/messages.jsonl`에 있다. JSONL의 `source_line`은 추출 파일의 행번호가 아니라 원본 rollout의 행번호다.

## 보류했다가 실제로 비교한 세 가지

**철회한 기능과 나중 구현:** 네트워크 실패 뒤 기존 화면을 다시 쓰게 하는 흐름, 폼 상태 보존, 중복 동기화 처리, 대상 여행으로의 이동은 이후 일부가 다른 구조와 단계로 구현됐다. 예전에는 refetch 성공을 기다리는 안이 있었고 이후에는 기존 캐시를 먼저 보여 주며 갱신 실패를 따로 다뤘다. 유사 기능이 채택됐다는 사실은 예전 구현이 동일하거나 적절했다는 증명이 아니다. 당시 철회의 주된 동기는 계속 미확정이다. [후속 비교](../source/noline-evaluation/reviews/withdrawal-followup-comparison.md)

**글로벌 문서 기준과 Project 문서:** 9월 14일 개선은 9월 30일 `recall-document-guidance` 도입 전의 사건이다. 10월 1일에는 실제 스킬 호출·기준 열람·문서 편집·첫 11편에 대한 “훨씬 나아졌다”는 평가가 연결된다. 다만 결과는 별도 worktree의 미커밋 편집이며 평가한 main과 다르다. 이후 8편까지 같은 평가를 확대하지 않는다. 통화 문서는 38행에서 52행으로 늘면서 조건·역할이 분명해졌으므로 짧아진 문서만 개선인 것은 아니다. 스킬 단독 인과와 장기 효과는 미확인이다. [후속 비교](../source/noline-evaluation/reviews/document-guidance-followup.md)

**기록 시점과 재개:** 어긋난 사례도 핵심 발췌가 기록에 남았고 새 세션이 읽었다. 그러나 첫 다음 행동이 구조·배경의 검토보다 두 버그 중심으로 제안됐다. 성공 비교도 긴 작업과 정정 뒤 수동 기록이었으며, 다음 세션이 선택창 작업과 그 이유를 복구했다. 따라서 늦게 기록한 것이 손실 원인이라고 확정할 수 없고, 내용 보존·열람·현재 행동에 적용을 구분해야 한다. 이 관찰을 Maintain 전체 목적을 재개 정보로 한정할 근거로 사용하지 않는다. [후속 비교](../source/noline-evaluation/reviews/record-timing-followup.md)

## 왜 코드 개선 한 과제가 아니라 전체 밑그림인가

AI는 인터뷰 반영 뒤 실제 코드 흐름의 품질 개선을 우선하는 방향을 제안했다. 사용자는 그보다 큰 밑그림을 먼저 논의하고 싶다고 정정했다. 기록 원칙·보완 시점, Project 구성, 기존 스킬, ai-workspace 자체, 개발 에이전트와 방법·워크플로는 서로 영향을 주므로 각 내용을 더 구체적으로 보고 설계하려는 것이다.

좋은 개발 자체가 추가 질문을 줄일 것이라는 생각은 후속 설계의 출발점으로 다루되, 과거 질문의 원인을 증명하는 과제로 되돌리지 않는다. 또한 사람의 개입을 전부 제거하려는 목표로 바꾸지 않는다. 필요한 이해·제품 선택과 이미 기대한 기준을 다시 적용시키는 교정은 구별할 필요가 있다.

기존 `improvement-directions.md`에는 당시 코드 품질 우선 제안이 그대로 남아 있다. 평가 과정의 역사적 제안이며 현재 작업 순서를 정하는 문서가 아니다. 현재 요청과 제안의 지위는 [current/memory](../current/memory.md)와 [정정 기록](2026-10-12-03-proposals-and-corrections.md)을 따른다.
