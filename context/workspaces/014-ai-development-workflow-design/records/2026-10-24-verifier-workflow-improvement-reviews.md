# 검증자 두 묶음 개선 리뷰와 Main 종합

후속 사용자 논의에서 역할 겹침을 재검토했고, **목적·책임·테스트 작성/지속 반영·기본 수정 및 재검증 방향과 시작 시점·첫 입력, 검사 방법·충분성과 실행 공백·결과 반환·종료 기준을 확정했다.** [합의 원문과 남은 범위](2026-10-24-verifier-workflow-proposal.md#후속-확정--역할테스트-작성수정과-재검증의-기본-흐름)를 따른다. 아래 리뷰 채택 표는 당시 종합이며, 개선 반영 전체를 검증자의 일반 책임으로 확장한 부분은 기존 Main·수정 담당 흐름에 유지하는 합의로 대체한다.이후 후속 재검증·실행 연결까지 확정해12개 설계 합의를 마쳤다. 실제 실행 본문 적용과 대표 작업 확인은 다음이다.

검사 방법·충분성의 후속 합의는 사용자 지적 뒤 Main이 원자료를 다시 대조해 기계 검사 활용·수행 단계·지속 반영을 보완한 결과다. [확정 내용](2026-10-24-verifier-workflow-proposal.md#후속-확정--검사-방법과-충분성)을 따른다. 아래 두 리뷰 당시 입력·반환과 구별하며 새 독립 리뷰를 실행한 것으로 기록하지 않는다.

2026-10-24. **목표·기존 구조·보존 레퍼런스를 대조한 검증안1~12번을 작성하고, 두 개선 리뷰의 보완을 [추천안](2026-10-24-verifier-workflow-proposal.md)에 통합했다.** 다음은 사용자와 검증안1번의 목적·책임부터 논의하는 것이다. 설계 합의·development 실행 본문 적용·실제 제품 동작 확인은 아직 하지 않았다.

이번 요청은 이전 구현·개선 검토자 때와 같은 구체화·개선 리뷰였다. 원문은 [입력 안내](reviews/verifier-workflow-2026-10-24/README.md)에 보존했다. 리뷰는 적당함이나 준수 여부를 승인하는 검증이 아니라, 사용자가 원하는 좋은 구현·확인 가능한 결과·이해와 다음 판단을 더 잘 만들 방법을 찾는 역할이었다.

## 비교에 사용한 목표·기존 구조·레퍼런스

Main은 현재 Spec·관련 Ticket·기존 development와 실행 배치, 전역 독립 검토·판단/보장/권한 배치 기준을 읽었다. 두 읽기 전용 조사는 기존 확정 계약과 레퍼런스의 구체적인 채택·조정·보류를 나눠 확인했다. 기존 구조 조사는 GPT-6.1-sol medium, 여러 레퍼런스의 열린 비교는 GPT-6.1-sol high를 사용했다.

조사에서 이어받은 핵심 사실은 다음과 같다.

- 구현·개선 검토와 별도 검증의 구별, 최신 요구·판본·변경·근거·공백 인계, 원 구현자 수정 기본값은 이미 합의돼 있다. 이를 이번에 다시 미정으로 만들지 않았다.
- 기존 Verify는 고정 명령·snapshot·receipt를 소유하며 의미적 충분성·전체 완료·사용자 수락을 결정하지 않는다. 직접 검사와 지속 근거 보존을 구별한다.
- pstack shipping에는 코드 작성에 참여하지 않은 검증자의 실제 사용자 경로 확인과 판본 변화 후 판정 유효성 확인이 있다. 이를 우리 Main·내부 담당 구조에 적용하되 cloud·PR·자동 merge 절차까지 가져오지 않았다.
- Matt의 공개 인터페이스 중심 검사와 pstack의 저장·외부 부작용 관찰은 일괄 채택하면 충돌할 수 있다. 주된 사용자·호출 경로를 확인하고, 부작용 자체가 계약이면 저장·파일·로그도 함께 관찰하는 것으로 조정했다.
- Lauren의 실행 수단·Feature Map, pstack의 verification/formal verification 생성 스킬, Vercel의 기계 규칙·맥락 판단·eval을 비교했다. 새 CLI·기능 문서 전체·형식 검증을 모든 작업의 선행 조건으로 만들지 않았다.
- 보존 Noline 스킬 색인의 `start-app`은 본문이 없어 현행 실행 가능성을 확인할 수 없다. UI 없는 메모리 demo의 검사 가능성을 실제 Noline 기기·DB·화면 지원으로 올리지 않았다.

주요 원문과 우리 구조에 맞춘 선택은 추천안의 레퍼런스 표에서 찾는다. 공개 자료의 최신판을 검색한 것이 아니라 기존 보존판을 분석했다.

## 두 개선 리뷰의 입력과 결과

GPT-6-astra high의 새 컨텍스트 두 개에 동일한 [리뷰 전 초안](reviews/verifier-workflow-2026-10-24/proposal-before-review.txt)을 제공했다. 이전 개선 리뷰와 같은 배치이며 모델 효과를 비교한 실험은 아니다. 부모 대화 전체와 서로의 리뷰는 주지 않았다. 원래 목표·사용자 발화·확정 구조·원자료 접근점을 함께 제공했고 Main의 문제 구분과 추천도 검토 대상으로 뒀다.

- [검증안1~6 리뷰 전체](reviews/verifier-workflow-2026-10-24/review-1-6.md): 기대 결과·방법 선택·독립성·초기 관찰 준비·약속한 개선 반영을 살폈다.
- [검증안7~12 리뷰 전체](reviews/verifier-workflow-2026-10-24/review-7-12.md): 실제 실행·판정과 수정·공백 해결·독립 재현의 인계를 살폈다.

두 리뷰어는 전체 초안을 읽고 관련 Spec·현재 실행 본문·demo 계약·코드/검사·직접 레퍼런스를 선택해 대조했다. 긴 과거 이력을 전부 읽었다고 주장하지 않았고, 실제 읽은 범위와 미확인은 각 보고서 끝에 남겼다. 제품 실행·원본 수정·운영 설치는 하지 않았다. 보고서 파일만 각자 작성했다.

첫 리뷰의 핵심 원문:

> 가장 큰 개선은 검증자에게 검사 목록을 더 주는 것이 아니라, 독립적인 기대 결과를 먼저 세우고 현재 결론을 바꿀 미확인부터 해소하게 하는 것이다.

둘째 리뷰의 핵심 원문:

> 오류가 나도 약속한 상태 보존과 오류 전달·후속 행동이 맞으면 그 실패 처리 요구에는 충족 근거가 된다. 검사 공백과 제품 결함을 구별하고, 제품 수정은 어긋난 약속을 특정한 뒤 배정한다.

특히 오류 예시는 Main 초안의 실질적 보완이다. 원래 문장은 조회 실패를 숨긴 mock을 발견하면 곧바로 제품 수정으로 이어질 여지가 있었다. 실제 demo 계약은 후속 조회가 실패해도 인증을 유지하고 조회 오류를 별도로 전달하는 동작을 허용한다. Main도 해당 계약을 직접 읽고 리뷰의 지적을 채택했다. **demo에서 새 버그를 발견했다는 보고가 아니라 논의안의 잘못된 수정 유도를 바로잡은 것**이다.

두 리뷰의 조기 준비 제안은 함께 통합했다. 이번 약속을 확인하는 데 필요한 관찰은 처음부터 해결할 책임이 있고, 모든 미래 작업을 위한 도구 투자는 별도 판단이다. 이 둘을 나누면 “도구를 과하게 만들지 말자”는 취지를 “중요한 확인 공백도 일단 남기자”로 축소하지 않는다.

검증자의 기본 권한은 허용된 검사·조작·임시 재현까지로 유지한다. 영구 테스트는 원 구현자나 지정 담당이 검증자의 재현을 이어받아 반영하는 추천을 유지하되, 별도 배정으로 검증자가 검사 파일을 작성했다는 사실 자체를 제품 작성자와의 독립성 상실로 보지 않도록 보완했다. 제품을 직접 수정했다면 그 결과의 자기 확인과 독립 확인을 구별한다.

## 다음 사용자 논의와 확인 상한

먼저 검증안1의 목적·책임을 논의한다. 핵심은 검증자가 단순 실행 담당을 넘어 요구에서 기대 결과를 만들고, 검사 충분성과 실제 결과를 독립적으로 판단한다는 것이다. 구현·개선 검토의 선택 책임과 Main의 최종 상태 판단은 유지한다. 이후 호출 범위·맥락 입력, 기계 검사와 실제 실행·형식 검증의 선택, 임시 재현과 지속 테스트의 배정, 수정·재검증·종료를 같은 구체안으로 이어갈 수 있다.

이번 자료에는 실제 역할 운영·제품 실행·수행 효과의 증거가 없다. 대표 장면은 설계 대조다. 두 리뷰어의 제안을 통합한 사실을 사용자 채택이나 전체01-03 완료로 올리지 않는다. 합의 뒤에는 기존 development 본체·verification 상세·execution의 필요한 연결을 반영하고, 실제 대상의 도구 가용성과 별도 설치·전체 연결 범위는 관련 Ticket에서 이어간다.

리뷰 입력의 원본 초안과 주요 파일 판본, 반환 원문을 보존했다. 주요 기존 입력14개는 기록한 Git 판본에서 같은 해시로 복원 가능함을 확인했다. 링크·문서 공백 확인은 기록의 연결 확인이며 운영 품질 검증이 아니다.

정리 확인: 관련 문서13개의 로컬 링크 대상617개를 확인해 누락0, 문서 후행 공백0, Git diff 공백 오류0이었다. 리뷰 전 초안의 해시 일치와 추천안12개 항목을 확인했다. 실제 development·review·execution·explain 본문과 제품 코드는 수정하지 않았다. 이번 구체안·리뷰·재진입 기록은 사용자 논의를 위한 미커밋 변경으로 남겼다.
