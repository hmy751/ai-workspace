# 04-03 구체안 2 — 담당자가 원문을 읽고 판단을 돌려준다

2026-10-26. 항목별 독립 개선 리뷰 뒤 기존 합의·실행 본문·맥락 구조를 다시 대조해 종합한 설계안이다. 사용자가 요청한 재종합이며 세부 추가안 전체의 확정은 아니다. [앞선 리뷰와 반영 근거](2026-10-26-context-improvement-reviews.md)를 보존했고 실제 역할 지침·호출 설정을 변경하지 않았다.

**Main은 목표·보존 조건·대상과 관련 접근점을 전달하고, 담당자는 그 원문을 자기 질문으로 읽어 결과를 만든다.** current는 이번 선택을 이해하는 입력이다. 구현자의 선택 이유와 Main의 해석도 검토 가능한 주장으로 두며, 원문 직접 읽기나 별도 판단을 대신하지 않는다.

현재 [development](prototypes/development-workflow/skills/development/SKILL.md), [execution](prototypes/development-workflow/skills/development/references/execution.md), [review](prototypes/development-workflow/skills/development/references/review.md), [verification](prototypes/development-workflow/skills/development/references/verification.md)에 이 역할 분담이 있다. [항목1](2026-10-26-context-01-start-resume-proposal.md)의 공통 방법을 역할별로 어떻게 사용하고 무엇을 넘기는지 구체화한다. 모델·세션·검토 호출 기준을 새로 정하지 않는다.

## 기존 책임과 이번 추가안

| 지위 | 이번 안에서 사용하는 내용 |
| --- | --- |
| 이미 합의·실행 prototype 반영 | 관련 기준 공유와 원문 직접 읽기, 질문에 따른 추가 탐색, Main의 종합·수정 배정, 개선 검토와 별도 요구 검증. 첫 검토·검증의 세션 조건, 수정 담당 기본값·재사용은 기존 execution·review·verification을 따른다. |
| 10월25일 잠정 배치 | [잠정 합의](2026-10-25-context-framework-provisional-agreement.md)의 공통 읽기 방법과 한정된 지속 본문 반영 과업을 개발 중 같은 수행자가 사용하는 구성. USAGE·context-update라는 형태·호출은 아직 최종 확정하지 않았다. |
| 이번 구체화의 조건부 추가안 | 구현과 함께 달라질 현재 사실 설명·읽기 경로를 초기 수정 범위에 포함할지 Main이 정한다. 포함하면 같은 구현자가 반영까지 이어 하되 Work 유지·전체 영향 연결과 실제 반영 확인은 Main이 책임진다. |
| 기존 계약을 연결한 보완 | 새 소비자 요구가 처음 목록 밖의 기준 선택으로 이어지는 예와, 중요한 반환·수용 때 대상·요구·계약의 현재 유효성을 대조하는 지점을 명시한다. 후자는 기존 execution의 공유 상태 대조와 verification의 최종 대상 비교를 잇는다. |

역할별 원문 읽기와 동적 선택이 없어서 새로 만드는 안은 아니다. 이번 추가안을 실행 본문에 적용한 상태나 재조사 비용 감소를 확인한 결과로 해석하지 않는다.

## 입력을 전달하는 단위

Main은 다음 판단에 필요한 만큼 요청문과 정확한 접근점을 제공한다. 새 전달 서식이나 별도 packet 파일은 만들지 않는다.

- **해야 할 결과와 지킬 것:** 사용자 요구·유효한 정정·범위·보존 계약. 문제 정의 자체가 검토 대상이면 발단 원문도 제공한다.
- **실제 대상:** Project/Work·산출물 위치, 확인할 판본과 미커밋 범위·병행 작업, 수정 가능한 대상.
- **출발할 맥락:** 관련 Personal·Project·Work 본문과 왜 관련됐는지. 이번 선택·가정과 확정 계약은 구별한다. 접근점은 탐색 출발점이며 읽기 허용 목록이 아니다.
- **기존 근거와 공백:** 실제 확인 원본·조건·재현 경로, 아직 확인하지 못한 것, 허용된 실행과 외부 접근 범위.

새 약속이 채택됐어도 지금 적용되는 조건과 현재 구현의 지원 범위를 구별해 전달한다. 검증자는 그 요구의 적용 조건으로 기대 결과를 만들며 ‘새 문서가 있으니 구현됐다’는 전제를 받지 않는다.

담당자는 적용 지침을 확인하고 맡은 범위부터 읽는다. 일반 재개처럼 Work 전체를 자동 인수하지 않는다. 요구가 명확해도 실제 사용처·실패·상태·설계 비교에서 답이 필요한 질문이 생기면 해당 본문과 실물을 추가 선택한다. 요구 자체가 불분명하면 관련 Ticket·Spec·원문을 확인한다. 작업을 바꿀 미확인이 남으면 Main에게 구체적으로 반환한다. 자동 주입된 지침·부모 대화·도구 권한도 실제 입력이므로 짧은 요청문만 보고 독립성을 주장하지 않는다.

**이번 조건부 추가안:** Main은 구현과 함께 달라질 가능성이 높은 **현재 구현 설명과 관련 읽기 경로**를 초기 수정 범위에 포함할지 정한다. 포함했다면 방금 실물을 확인한 구현자가 항목3의 반영까지 이어 맡는다. 현 development의 Main 직접 갱신 기본값에서 실제 작성 범위를 명시적으로 배정하는 구체화이며, Main의 Work 유지·전체 영향 연결·실제 반영 확인 책임은 유지한다. 작은 변경은 Main이 직접 처리해도 된다. 수행 중 새 Owner가 발견되면 필요한 범위만 연결하며, Personal 기준·새 제품 약속의 결정권까지 함께 부여한 것으로 보지 않는다. 재조사 왕복 감소는 기대 이득으로 남긴다.

## 역할마다 달라지는 읽기와 반환

| 역할 | 원문으로 하는 판단 | 자연스러운 반환 |
| --- | --- | --- |
| 구현자 | 요구와 제품 계약을 실제 호출자·실패·상태·수명에 적용하고 관련 Personal 기준으로 설계 선택을 비교한다. 범위 안의 결과를 완성하고 자기 확인한다. 위 추가안으로 사실 문서까지 함께 배정했다면 그 반영도 수행한다. | 실제 코드·배정된 문서 변경과 자기 확인, 선택을 가른 근거와 적용 조건, 미확인·범위 밖 반영 필요. 읽은 모든 파일의 목록은 불필요하다. |
| 개선 검토자 | 같은 요구·기준·결과를 직접 대조하고 다른 선택의 이득·비용을 판단한다. 처음 자료 선택·Main의 해법과 기준 적용도 다시 볼 수 있다. | 유지/변경 의견과 직접 근거, 대안의 비용·불리한 조건, 판단에 중요한 공백. 정본 수정은 별도 배정이 있을 때만 한다. |
| 검증자 | 요구·제품 약속·실제 사용 조건에서 기대 결과를 구성하고 최신 대상·기존 검사의 적절성·중요한 미확인을 확인한다. | 요구별 충족/불충족 근거·미확인, 재현·입력·조건과 유효한 대상. 구현자가 선택한 기대값을 그대로 정답으로 받지 않는다. |
| Main | 각 반환의 근거·현재 유효성과 조합을 판단하고 선택·변경·사용자 판단·재검증을 연결한다. | 전체 결과와 이유, 남은 결정·다음 수행. Work를 유지하고 지속 본문 반영이 필요하면 항목3으로 잇는다. |

같은 Personal 기준을 공유해도 같은 결론을 요구하지 않는다. 검토 독립성을 위해 필요한 기준이나 예외를 숨기지 않는다. 구현자는 결과를 완성하고 검토자는 더 나은 선택을 비교하며 검증자는 실제 요구 충족을 확인한다. 같은 문제의 발견은 어느 역할에서든 가능하다.

사례·형성 자료는 각 본문의 읽기 조건에 따라 선택한다. 형성 의도나 이전 선택 이유를 알아야 현재 내용을 더 정확히 이해할 수 있으면 해당 자료로 내려가되, 현재 적용에 필요한 조건을 모두 과거 기록에서 다시 조립하게 하지 않는다. 작업 정의가 불충분하거나 방법의 전제가 흔들린 경우에는 [항목1의 기존 작업 판단 연결](2026-10-26-context-01-start-resume-proposal.md#읽기-뒤에는-기존-작업-판단으로-돌아간다)로 Main에게 반환한다. 공통 읽기와 역할 표가 work-discussion의 명시 호출이나 reconsider-work의 조건을 대체하지 않는다.

## 새 질문으로 읽기 범위가 바뀌는 장면

현재 demo의 로그인 완료는 후속 조회 완료를 포함하지 않는다. ‘새 화면이 로그인 직후 최신 여행 목록을 필요로 한다’는 **가상 후속 요구**를 사용한다. 실제 제품 변경·실행 증거가 아니다.

1. Main은 새 화면의 요구와 기존 인증 보존 조건을 준다. ‘기존처럼 비대기면 충분하다’는 답을 먼저 넣지 않는다. 구현자는 [인증 계약](prototypes/development-workflow/noline-demo/context/project/guidance/authentication-and-session/INDEX.md), [현재 인증 흐름](prototypes/development-workflow/noline-demo/context/project/current/authentication-flow/INDEX.md), [이름·완료 기준](prototypes/development-workflow/noline-demo/context/personal/development/naming-and-completion/INDEX.md)과 실제 소비자를 읽는다.
2. 기존 이름 문제에서 소비자의 대기·실패 처리 문제로 질문이 바뀐다. 구현자는 두 기존 소비자와 새 소비자의 후속 행동이 다름을 보고 ‘어디까지 함께 보장할 것인가’를 묻는다. 처음 지정된 이름 기준에 머물지 않고 [Personal 주제 입구](prototypes/development-workflow/noline-demo/context/personal/development/README.md)를 통해 [공통 제공과 사용처 선택](prototypes/development-workflow/noline-demo/context/personal/development/shared-boundaries/INDEX.md)을 추가 선택한다. 같은 API 호출과 같은 업무 흐름을 구별하는 기준으로, 새 소비자에서 조회를 기다리는 안과 공통 완료 범위를 바꾸는 안의 부담을 비교한다. 실패가 인증을 취소하지 않는다는 약속은 기다림 여부와 별도다. 반환에는 추가 열람 목록보다 그 근거가 선택을 어떻게 바꿨는지를 남긴다.
3. 기존 계약 안의 기술 선택이면 위임 범위에서 수행한다. 새 제품 약속이나 범위 변경이 필요하면 Main에게 해당 충돌과 선택지를 일찍 알린다. 추가 읽기마다 허락받거나 결과 반환까지 중요한 충돌을 숨기지 않는다. 막히지 않은 부분은 계속한다.
4. 개선 검토자는 원요구·변경 결과와 관련 계약에서 출발해 구현자의 안을 재평가한다. 예컨대 공통 함수가 필요 없는 소비자까지 조회를 기다리게 만드는지, 별도 소비자 흐름이 중복과 오류 처리를 늘리는지 비교한다.
5. 검증자는 ‘새 화면은 필요한 최신 결과 뒤 진행하는가’, ‘조회 실패가 인증을 취소하지 않는가’, ‘기존 소비자의 보존 동작은 지켜지는가’를 요구에서 도출해 실제 범위에 맞게 확인한다. 어떤 결과를 확인해야 하는지는 구체 요구에 달리며 이 세 문장을 모든 작업의 고정 검사로 만들지 않는다.

판단이 바뀐 근거·현재 조건·결정 필요가 반환되면 Main은 현재 Work와 관련 담당자에 연결한다. 일반 방법을 읽었다는 보고보다 실제 선택에 무엇이 달라졌는지를 남긴다.

## 이미 작업 중인 담당자에게 변경이 생기면

담당자는 새로운 원문을 읽는 것과 진행 중인 과업의 계약을 바꾸는 것을 구별한다. 대상 파일·요구·계약이 변해 현재 판정에 영향을 주면 바뀐 범위를 알리고 영향받는 판단을 새 입력에 맞춘다. 자기 인수 이후의 변화와 무관한 판단은 그대로 활용할 수 있다.

Main은 항목3에서 변화의 의미를 판단해 해당 담당자에게 변경 내용·이유·최신 접근점·무효가 된 가정·필요한 후속을 연결한다. 이전 보고가 새 판본에도 유효한지는 실제 영향으로 판단한다. 세션 재사용이나 새 담당자 배정은 기존 execution 계약을 따른다. 문구·경로 변경만으로 모든 리뷰·검증을 재실행하지 않는다.

중요한 반환이나 Main의 결과 수용 시점에는 판단을 가른 대상·요구·계약이 인수 당시와 달라졌는지 기존 변경 근거로 대조한다. 차이가 있으면 영향받은 결론만 갱신하고, 현재판까지 확인하지 못했다면 어느 판본·조건에 대한 의견인지 한정한다. 같은 경로라는 이유로 같은 입력이라 보지 않는다. 기존 execution의 공유 상태 대조와 verification의 최종 대상 비교를 잇는 것이며 전체 해시·읽기 로그·감시 장치를 새로 만들지 않는다.

공유 current의 유지·내용 판단·실제 반영 확인은 Main이 책임진다. 별도 기록 수행을 명시적으로 배정하더라도 구현·검토·검증 역할이라는 이유로 모든 context를 고칠 수는 없다. 위 조건부 추가안에서 구현과 현재 사실 설명이 함께 배정됐다면 같은 담당자가 항목3의 한정된 반영을 이어 할 수 있으며, 그 배정만으로 Work current 수정까지 포함하지 않는다. 추가 관리 agent가 필수는 아니다.

Main의 현재 Work가 전환돼도 기존 배정의 대상·판본·수정 권한은 유지된다. 늦은 결과는 원래 Work의 결과로 반환하고, 새 Work에도 필요한 의미는 Main이 선택해 연결한다. 대상 자체를 바꿔 맡기는 경우에만 새 목표·권한을 명시한다.

| --- | --- |
| development | Main의 초기 연결·중요한 변화 회수·전체 판단 책임 |
| execution | 실제 입력·판본·권한·병행 작업·세션 상속/재사용 |
| review / verification | 각 역할의 질문·독립 판단·반환·후속 조건 |
| 공통 사용 방법 | 본문 선택·재사용·원문 대조. 각 역할 상세에 같은 절차를 반복하지 않음 |
| 각 context와 Work | 원문 내용·권위와 이번 선택/상태. 역할 지침에 제품별 내용 복사하지 않음 |

독립 검토만 요청받은 경우에도 이 경로를 사용한다. 구현·새 Work·개발 전체 절차를 자동 시작하지 않는다. 원자료 접근 실패가 있으면 관련 판단의 한계를 반환하며, 자료량 문제·잘못된 전제·권한 문제를 모두 ‘맥락 부족’으로 묶어 전체 자료를 더 읽히지 않는다.

Lauren의 원칙 leaf 직접 읽기와 parent/leaf 수행·반환 분담, Matt의 Project 본문 소비 경로는 [고정판 조사](2026-10-25-context-reference-synthesis.md)의 참고점이다. 외부의 고정 모델·모든 role의 mode 전체 읽기·기본 다중 agent는 가져오지 않는다. 후속 적용에서는 한정 위임자가 전체 Work를 읽지 않아도 중요한 계약·예외를 적용하는지, 새 소비자 질문을 스스로 찾아 판단하는지, 변경 뒤 필요한 의견·확인만 갱신하는지를 살핀다. 링크나 역할 이름이 있다는 사실만으로 이 수행을 확인했다고 하지 않는다.
