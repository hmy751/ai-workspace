## 보완된 경계

처음 확인한 03 묶음은 895에서 시작해, 원래 세션에서 사용자가 1209 전에 본 설명을 일부 빠뜨렸다. 원 corpus의 `source_line` 9는 Ticket 06 현황 파악을 요청하고, 96은 Network Store의 `unknown`·구독/정리/재확인·private closure를 설명한다. 255는 `network.ts`의 session 소유, 요청 identity, 관측 version 검사가 서로 다른 문제를 보호한다고 보고한다. Main이 **9~844의 34개 발화를 `03-network-flow/prior-context/`에 추가**했고, 이 파일은 원 corpus 물리 1~34행과 바이트 일치한다. 갱신된 03 README·상위 README·구성 기록도 선행 맥락과 짧은 input 사용의 제한을 밝힌다. 따라서 원문 입력 경계의 이 결함은 해소됐다. 여전히 당시 실제 코드 판본은 확보되지 않았으며, 1239의 평가 답을 원본 코드로 대체해서는 안 된다.

## 자료 공백과 시험 범위에 대한 판정

- **02:** 사용자20에 interceptor 코드가 들어 있다. 코드 내부의 문법·블록·순서·역할을 함께 설명하는 본문 비교는 성립할 수 있다. Store/transport 내부와 실제 API·sync 사용처는 없다는 README·manifest·구성 기록의 제한이 맞다. 사용자9의 `??=` 한 줄 질문은 자동 스킬 적용 후보로 올리지 않았고, 55의 “코드랑 같이 자세히”를 입력에 소급하지 않았다. 31은 선언 증거일 뿐 실제 SKILL.md 읽기 기록이 아니다.
- **03:** 920 직접 스킬 호출과 963 설명이 input에 남아 있고, 선행 9~844도 prior-context에 보존됐다. 따라서 1209에서 자연어 질문에 다시 선택하는 수행은 볼 수 있어도 순수한 최초 자동 선택은 볼 수 없다는 기록의 제한이 맞다. 사용자1209에는 파일 경로만 있어 당시 `network.ts`·호출부·미커밋 상태가 필요한데 확보되지 않았다. 1239의 코드 발췌를 입력 자료로 승격하지 않는다고 명시한 것도 적절하다. 1246은 세션·refresh 관계를 확인하는 질문으로 읽히며, 후속 질문의 존재만으로 첫 답 전체를 실패라고 판정하지 않은 기록이 적절하다.
- **04:** 사용자2456은 설명 요청이 아니라 코드 변경 지시다. 기준판 description이 구현 주목적 요청을 자동 적용에서 제외하므로, 첫 전달의 명시적 briefing 적용 시험은 기존 위반 재현이 아니라 호출 배치 개입이라는 기록이 맞다. `prior-context` 9~1542와 input 1549~2456은 원 세션의 2456까지 연속이고, 짧은 input만 쓰면 Ticket·Spec·코드 보강이 필요하다는 경고가 맞다. 2456 직전 working tree 및 2560 직전 실제 diff·검증 출력이 없는 상태에서는 코드 정확도와 변경 품질을 비교할 수 없다. 2645는 설명 부족 외에 구현 폭에 대한 반응도 포함하므로 설명 시험 성공/실패로 환산하면 안 된다는 기록도 맞다.
- **04의 비텍스트 공백:** input의 사용자 `source_line` 1720·1933·2089는 `nontext_types=["input_image"]`이고 text에는 스크린샷 경로·placeholder만 남았다. 이미지 픽셀은 이 묶음에 없다. 이는 TypeScript/에디터 오류 대응의 당시 맥락을 완전히 재현할 수 없다는 제한이다. Main이 04 README와 구성 기록에 이 공백을 명시한 것을 확인했다. 첫 제품 코드 변경 보고의 핵심 코드·diff 공백과 구별한다.

구성 기록의 “핵심 두 축을 비교할 수 있다”는 문장은 후보 범위를 갖췄다는 뜻으로 읽을 때 이후의 자료 제한·미실행 표시와 양립한다. 실제 비교를 즉시 실행할 준비가 됐거나 시점/본문 효과가 입증됐다는 뜻으로 읽지 않도록 현재의 제한 문구를 유지해야 한다. 이 검토에서 세 묶음의 원문 배열 오류나 미래 교정의 JSONL input 혼입은 발견하지 못했다.
