# 동적 맥락 선택과 별도 관점 검토의 의도

2026-10-21. 사용자가 앞선 자료 비교 뒤 자신의 구상과 질문에 대한 답을 설명했다. **Personal을 구현의 바탕으로 쓰고, 별도 역할이 현재 결과와 다른 선택지를 검토하며, Main이 유지·적용·사용자 논의 여부를 판단하는 방향**이다. 작업 결과와 요구사항을 다시 보며 필요한 맥락을 선택하는 동적 라우팅도 함께 구체화한다. 역할별 정확한 입력·수정 권한·검증 배치·호출 방식은 레퍼런스와 더 비교할 항목이다.

## 원문과 이 기록을 읽는 방법

사용자의 후속 보존 요청에 따라 [대화 원문](../source/discussion/2026-10-21-workflow-routing-review/conversation.md)을 source에 별도 구성했다. S1은 러프한 구상, S2는 Main의 이해와 세 질문, S3은 사용자의 답변과 동적 라우팅 구상, S4는 Main의 이해 응답, S5는 보존 요청이다. 원래 오탈자·표현·문단을 유지한 사용자 발화 3개와 AI 응답 2개이며, [출처와 hash](../source/discussion/2026-10-21-workflow-routing-review/manifest.json)로 원본 로그의 위치를 찾을 수 있다.

이 기록은 그 대화를 해석해 이후 판단에 필요한 뜻과 열린 항목을 정리한다. 직접 발화는 source, 외부 방식의 실제 근거는 보존한 레퍼런스, Main의 연결 제안은 이 기록에서 구별한다. S4 뒤 사용자의 기록 요청을 모든 제안·상세 운영의 승인으로 해석하지 않는다.

| 구분 | 현재 보존할 내용 |
| --- | --- |
| 사용자가 밝힌 목적·방향 | 의미 있는 검증, Personal을 바탕으로 요구와 맞고 이해하기 쉬운 구현, 별도 관점에서 현재 결과와 다른 선택지 비교, Main의 유지·적용 판단과 필요한 사용자 논의, 결과에 따른 맥락 재선택, 초기 테스트 보완, 자신의 context 구성 반영, 후속 레퍼런스 비교 |
| 사용자가 제시한 입력 후보 | 검토자에게 원칙을 주고 기존 해법 사례는 제외하는 안. 부족하면 기준·방법을 더 구성하는 데 열어 두었다. |
| Main의 연결 제안 | Main이 초기 맥락을 전달하고 실행 담당자도 새 질문에 따라 원문을 더 찾는 방식, 관찰과 trade-off를 통해 원칙을 적용하는 방법, 명확한 검사와 맥락 판단을 연결하는 방식 |
| 구체화가 필요한 것 | 검토자에게 줄 원칙·사례의 실제 범위, 역할별 추가 자료 접근과 라우팅 책임, Main 판단 후 수정 담당·시점, 기계 검사·테스트 보완·최종 확인의 담당과 충분성, 구체 스킬 구성 |

## 사용자 설명에서 보존할 뜻

앞선 러프한 구상에서 사용자는 검증을 ‘대충 무의미하게’ 하지 않고 잘하는 것이 중요하다고 했고, CLI·ESLint·테스트에도 기준이 필요하다고 봤다. 구현 워커는 Personal뿐 아니라 Spec·Ticket과 Project도 읽어야 정확하다고 설명했다. 초기 테스트가 완벽하지 않으므로 후속 보완도 필요하며, 외부 방식과 다른 자신의 context 구성도 고려하자고 했다.

후속 설명:

> 라우팅은 좀 더 동적으로도 할수 잇나? 구현 하고 구현 결과물과 다시 요구사항이나 보고 적절한 컨텍스트를 다시 보고 하면서? vercel 내용을 그런 뉘앙스로 이해했거든

> personal을 한건 개인적 기준이 있어야 코드가 나와 어느정도 싱크가 맞아서 내가 미리 구체화한 기준을 작성하니까 이해도 쉽기도 하고 내 요구에 맞게 될거라 생각했어

> 그래야 내 기존 선호 또는 지식과 더 나은 선택지를 봐야 정말 적절한 선택을 할 수 잇다 생각해서 매번 끌어올리려는건 아니고 굳이 그럴 필요는 없지 그래서 검토자가 내놓은걸 main 이 한번더 판단하게 하고 싶었어

> 딱히 뭐 거기서 거기면 그냥 내걸로 하고 뭐 느레이드오프나 좋은기준을보고 개선할필요가 있거나 애매하면 나랑 얘기할수도 잇는거고

수정 책임에 대해서는 “main이 판단하고 하면 되겠지?”라고 했고, 레퍼런스를 보며 상세를 더 구체화하자고 했다. 검토 기준은 우선 자신의 원칙을 주고 사례를 제외하는 생각을 설명했으며, 그것이 부족하면 적절한 판단 기준과 방법을 구성하는 데 열어 두었다. 모든 품질 관점의 우선순위를 지금 정한 것은 아니다.

## 현재 이해와 앞선 제안의 조정

Personal은 사용자의 사고방식·선호와 맞는 코드를 만들고 결과를 이해하기 쉽게 하는 출발점이다. 상황에 따라 더 나은 선택이 있을 수 있으므로, 별도 검토 역할은 현재 결과의 적절성과 대안을 근거로 비교한다. 검토를 매번 개선안을 만들어 내거나 기존 선호를 뒤집는 과제로 만들지 않는다. 실질적인 차이가 작으면 기존 기준을 유지하고, 가치 있는 차이나 판단하기 어려운 trade-off가 있으면 Main이 적용 또는 사용자와의 논의를 선택한다.

[앞선 Main 비교안](2026-10-21-implementation-review-reference-comparison.md)의 ‘두 단계가 같은 품질 기준을 사용한다’와 ‘검토자가 범위 안 수정을 바로 마친다’는 내용을 이 설명의 확정 구현으로 이어 쓰지 않는다. **검토의 입력과 관점을 달리하고, 검토 결과의 적용 판단을 Main이 맡는 관계**를 먼저 구체화한다. 과거 B의 직접 수정 선택은 [당시 기록15](2026-10-12-15-reviewer-editing-choice-and-start.md)에 보존하되, 그것만으로 현재 수정 담당·시점을 결정하지 않는다. Main이 채택한 뒤 검토자에게 수정을 맡길 수도 있으며, 그 방식과 명백한 결함 처리의 위임 범위는 열려 있다.

검토자에게 Personal 전체를 감출지, 관련 원칙만 줄지, 어떤 원칙은 공유하고 어떤 사례를 제외할지는 상세 입력 설계다. 사용자가 든 ‘원칙은 주고 사례는 제외’는 우선 비교할 후보다. Spec·Ticket의 요구와 Project의 사실·계약, 검토 대상 코드·실행 결과를 이해할 정보는 함께 고려해야 한다. 개인 기준의 과거 해법 사례를 제한한다는 생각을 요구사항의 사례·재현 조건·실제 증거까지 숨기는 규칙으로 확대하지 않는다.

원칙의 이름만 나열해 ‘적절히 판단하라’고 하는 대신, 어떤 관찰로 원칙을 적용하고 무엇과 충돌할 때 선택이 달라지는지 설명하는 방법을 비교한다. 유지안도 대안과 같은 조건에서 비교할 수 있어야 한다. 기준의 개수·문구·우선순위는 아직 선택하지 않았다.

## 동적 라우팅과 Vercel 원문의 관계

[Vercel 보존 글](<../source/lectures/vercel-product-design (1).md>)은 작업과 대상에 맞춰 정본을 선택하고(64~70행), 구현뿐 아니라 전체 검토에서도 관련 제품 판단·품질 기준을 읽으며(151·157~166행), 실제 소스와 렌더링 결과를 대조한다(120·172~180행). 따라서 기준 선택을 구현 전 한 번에 고정하지 않고 검토 대상에 맞춰 수행한다는 사용자의 이해는 원문의 방향과 맞는다.

다만 ‘구현 결과와 요구사항을 다시 대조해 맥락을 재선택하는 반복 절차’ 전체를 원문에 명시된 알고리즘으로 소개할 근거는 없다. 그것은 원문의 조건별 선택을 우리 작업 흐름에 구체화할 제안이다. 주간 collector/judge의 기준 갱신(335~351행), skill 효과 eval(325~333행), 한 작업 안에서 필요한 기준을 다시 읽는 동작은 구별한다.

연결 후보는 Main이 초기 목표·관련 맥락을 전달하고, 구현과 검토 중 새로 드러난 질문·변경 결과·검사 실패·미확인을 바탕으로 담당자가 필요한 정본을 추가로 고르는 방식이다. Main은 기준 사이 충돌과 적용 여부를 종합한다. 예를 들어 이름을 다루다가 상태의 시작·종료 의미가 쟁점이 되면 해당 Project 계약과 그 판단에 필요한 원칙을 다시 찾는다. 검토자에게 제공할 Personal의 범위는 위 입력 설계와 함께 맞춘다. 전체 context를 매번 재독하거나 자료를 새로 읽었다는 이유로 요구와 계약까지 바꾸는 절차는 아니다.

## 의미 있는 검증을 연결할 때 볼 것

기계적 검사에는 무엇을 잡아야 하는지 명확한 기준이 필요하다. 반복해서 판별할 수 있는 규칙은 lint·type·자동 테스트 등에, 실제 사용 결과는 해당 실행·관찰 경로에 연결하는 방법을 비교한다. 맥락에 따른 구조 선택은 근거와 trade-off를 판단할 역할에 남긴다. 이것은 앞으로의 책임 배치 후보이며 특정 검사 도구나 담당을 정한 것은 아니다.

테스트가 있다는 사실과 충분한 검증을 구별한다. 요구·보존 계약에서 기대 결과를 가져왔는지, 이번 변경이 드러낸 경로를 실제로 다루는지, 빠진 조건이나 구현과 같은 가정을 반복한 검사는 없는지 다시 판단할 수 있어야 한다. 구현·검토·Main 중 누가 어떤 보완과 최종 확인을 맡을지는 자료와 대표 작업을 대조해 정한다.

## 다음 구체화와 기록의 지위

다음에는 사용자 설명을 기준으로 Matt의 구현·검토·테스트 경계, pstack의 lead 판단·전문 검토·실행 확인, Vercel의 조건별 기준 선택·제품 판단을 비교한다. 우리 Personal·Project·Work 구성에서 각 역할의 입력, 관점의 독립성, 추가 자료 선택, 제안의 비교·채택, 실제 수정·재확인 책임을 구체화한다.

이 기록은 사용자의 의도와 열린 선택을 보존한다. 앞선 DB·인증 사례는 필요할 때 비교할 자료이며 다음 실험이나 유일한 설계 입력으로 선택된 것은 아니다. 실행 스킬·DEVELOPMENT 본문·제품 코드는 변경하지 않았다. 현재 Spec·Ticket·상태와 산출물 안내에는 후속 방향과 기존 시안의 차이를 연결했다.
