# Development의 실행 상세와 계층 확장

2026-10-26. 기존 맥락 연결 적용을 `191e2d86`(`맥락 읽기와 반영 흐름을 프로토타입에 연결`)로 먼저 커밋했다. 이후 사용자 요청에 따라 구조 판단을 기록하고 구현 수행·검증 근거 상세를 prototype에 적용했다. **두 상세의 구성·소비 경로 연결·독립 검토 보완과 정적 확인을 완료했다.** 실제 역할의 반복 사용 효과와는 구별한다.

## 사용자 의도와 앞선 구조 판단

사용자는 현재 트리를 보고 필요한 확장을 억제하지 않아도 된다고 말했다.

> 원래 트리는 엄청 많지 않았나? 그걸 따르란건 아닌데 보니까 적절한것만 넣으려고 하다보니까 뭔가 계층을 안늘리나 싶어서 확장할건 해도 된다 생각하거든? 일단 반영하진말고 생각좀 해봐

읽기 전용으로 현재 본문·정책과 [10월23일 구조 구상](2026-10-23-development-skill-structure-proposal.md)을 다시 대조했다. 당시 사용자의 의도는 ‘한 스킬 안에 내용이 쌓이고 필요한 상세가 계층적으로 성장하는 것’이었다. [최초 적용](2026-10-23-development-skill-prototype-adoption.md)은 구현·검증 세부가 미정이라 빈 파일을 만들지 않았고, 이후 구현 책임은 본체에 구체화됐다. 처음의 유보가 계층 확장 금지는 아니며 현재 내용·독자·수정 이유에서 다시 판단할 수 있다.

새 읽기 전용 검토자도 원래 사용자 발화와 현재 실물·과거 구상을 독립적으로 대조했다. 구현 상세를 우선 권고하고, Main·조사 담당도 사용하는 검사 근거 판단을 새 분리 후보로 보았다. review의 검토자 수행/Main 판단은 독자가 다르지만 현행 절별 연결도 기능하고 있어 우선순위를 낮게 보았다. 이는 구조 판단이며 분할 후 사용성 향상을 시험한 결과가 아니다.

Main은 구현 상세와 여러 담당자가 재사용하는 검증 근거부터 구조를 다시 보는 안을 설명했다. 사용자는 그 뒤 적용을 요청했다.

> 일단 커밋하고 기록할거 하고 반영해보자

파일·줄·계층 수를 줄이는 것을 목표로 하지 않는다. 각 책임이 필요한 설명·절차·대비 사례를 충분히 담고, 실제 읽기·수정·재사용의 차이가 배치에 드러나게 한다. 현재 실행할 상세를 `_background`로 밀어 넣어 본체만 줄이지 않으며, 상세 분리를 새 스킬·새 담당자·의무 단계의 추가로 취급하지 않는다.

검토자/Main 상세의 추가 분할은 이번에 하지 않는다. 다른 두 후보와 동일한 파일 모양을 만드는 것이 목적이 아니며 현재 읽기 경로로 역할을 구별할 수 있다. USAGE·context-update·생성 스킬과 Personal·Project·Work의 소유도 유지한다. 이 판단은 그 구조를 영구 고정하는 규칙이 아니다.

## 확인할 범위

기준판191e2d86과 책임·조건·권한·종료를 대조하고, 실제 호출자가 필요한 상세로 연결되는지 확인한다. 본체의 공통 설명이 사라지거나 같은 알고리즘을 두 곳에 중복 관리하지 않는지도 본다. 별도 검토자는 의미 보존과 분할의 실제 이득·새 부담을 확인한다. 열람 화면을 재생성해 원문·링크·앵커를 대조하며, 제품 동작을 바꾸지 않은 문서 구성을 위해 인증 검사를 반복하지 않는다.

## 실제 반영과 검토 결과

구현 수행과 검사 근거 상세를 작성하고 본체·검증 수행·스킬 안내·prototype 진입·walkthrough·열람 화면을 연결했다. 구현 상세는 기존 합의의 초기화 부담과 저장 지연 사례로 설계·자기 확인의 적용을 설명한다. 검사 근거 상세는 메모리 순서 검사의 유효 범위와 실제 저장소 주장, 어댑터 변경 뒤 유지할 근거와 새 확인을 구별한다. 특정 예제의 제품 요구를 다른 작업의 의무로 일반화하지 않았다.

새 독립 검토자는 기준판191e2d86·기존 합의·실제 diff와 새 본문을 대조했다. 역할·권한·종료 조건의 실질적 유실을 찾지 못했고, 본체가 전체 흐름·핵심 책임·완료·Owner 연결을 유지한다고 반환했다. 새 상세가 읽기와 이후 보완의 독립 단위가 되는지, review의 현행 절 구별을 유지해도 되는지도 검토했다.

중요한 개선은 근거 유효성 판단의 전문 중복1건이었다. 검토자의 핵심 반환:

> 근거 유효성 판단의 수정 위치를 한곳으로 모으는 편이 좋습니다.
> 향후 재사용 조건을 보완하면 조사 담당과 검증자가 서로 다른 규칙을 읽을 가능성이 있습니다. 실제 실패가 관찰된 것은 아닙니다.

Main은 이를 채택해 verification의 재검증 절에는 Main·검증자가 그 판단을 적용한다는 책임을 남기고, 판본·검사·설정·데이터·의존 조건과 영향 범위 판단은 evidence의 실제 절로 연결했다. 조건을 없애거나 예외를 새로 만든 변경이 아니다. 수정 뒤 Main이 두 본문과 실제 링크를 직접 대조했다.

| 대표 요청 | 독립 검토자가 복원한 읽기 경로와 책임 |
| --- | --- |
| 후속 구현 수정 | 본체 → implementation의 후속 수정 → 필요한 execution·검사 근거. 재현·독립 기대값을 이은 자기 확인과 최신 판본 인계가 이어지고 재검증 배정·전체 완료는 Main에 남는다. |
| 기존 검사 pass로 보고서를 판단 | 본체의 결과 반환 → verification/evidence. 실제 입력·실행·assertion·대체 경계와 현재판 유효성을 대조하며 독립 검증 역할을 새로 시작하지 않는다. |
| 최신 결과의 별도 검증 | 본체 → verification의 시작·입력 → 근거 상세 → 실행 공백·반환·재검증·충분성. 독립 첫 배치·제품 수정 권한 분리·요구별 판정·Main 완료 판단을 유지한다. |

이 확인은 지침의 의미와 읽기 경로 대조다. 제품 실행이나 세 역할의 실제 개발 수행, 분할 뒤의 반복 사용성·속도·비용 효과는 시험하지 않았다. 원래 source·제품 코드·검사·실제 운영 설정은 바꾸지 않았다. 실제 파일·정적 확인 결과는 아래에 남긴다.

## 후속 정정 — 검증 단위를 INDEX와 상세로 함께 배치

사용자는 “나눈건 좋은데 구성이 이상한데 ? 왜 저렇게 떨어져 있어?”라고 지적했다. Main은 기존 파일 경로를 유지한 채 상세만 하위 폴더로 보낸 배치가 검증 단위를 흩어 놓았음을 확인했다. 뷰어의 폴더 우선 정렬도 두 위치가 떨어져 보이게 했다. 사용자는 “index는 어때?”라고 제안하고 설명 뒤 “그래 해보자”로 적용을 요청했다.

검증 본체는 [verification/INDEX.md](prototypes/development-workflow/skills/development/references/verification/INDEX.md), 근거 판단 상세는 같은 폴더의 [evidence.md](prototypes/development-workflow/skills/development/references/verification/evidence.md)에 둔다. INDEX는 기존 검증 수행 본문을 그대로 맡고 development의 전체 조율과 evidence의 직접 읽기 관계를 유지한다. 원래 본문을 링크 목적지 외에는 바꾸지 않고 이동했으며, 들어오는 안내·본문 내 상대 경로·표시 사본을 함께 갱신했다. 과거 기록의 현재 산출물 링크는 새 위치로 연결하되 당시 경로에 대한 서술과 보존 원문·실험 입력은 유지했다.

이번 변경은 검증 단위의 묶음과 진입 경로 정리다. 다른 주제를 일괄 분할하거나 검증 절차를 추가한 변경은 아니다. 확인 결과는 아래에 남겼고, 이 이동을 마친 시점에는 앞선 상세 확장과 함께 미커밋으로 두었다.
