# 04-03 — 네 구체안의 재종합과 실제 작업 흐름

2026-10-26 후속 재종합. **기존 합의·잠정 구성·추가 세부안을 구별해 네 구체안을 다시 연결했다.** 사용자가 요청한 것은 전체 안의 기존 책임 중복과 보완을 종합하는 일이었다. create의 과거 선택 복원이나 합의 목록만으로 대신하지 않는다. [전체 대조와 정정 근거](2026-10-26-context-whole-scope-reconciliation.md)에 요청 원문·판정·이번 수정 범위를 남겼다.

이 문서는 사용자와 검토할 **설계안**이다. 최초 재종합 뒤 [1번의 개선 리뷰와 적용 설명](2026-10-26-context-01-goal-improvement-review.md)을 거쳐 development의 재개 문장과 1번 사례·후속 확인 방법을 한정 보완했다. 후속 2번에서는 [직접 수정안의 리뷰와 사용자 후속 논의](2026-10-26-context-update-responsibility-improvement-review.md)를 거쳐 **담당자가 근거와 함께 반영을 제안하고 현재 Main이 검토 후 반영하는 방향**으로 2번·3번과 이 흐름을 구체화했다. 이번에는 설계 문서만 바꿨다. 세부 선택의 일괄 합의나 USAGE/context-update·생성 계약·설정·설치 승인은 아니며, 별도04-02의 실행 변경도 그 작업과 구별한다.

## 한 작업에서 실제로 어떻게 이어지는가

아래는 현재 로그인 예제에 **‘새 화면은 로그인 뒤 최신 여행 목록을 받은 다음 진행해야 한다’**는 가상 요구를 대입한 설계 장면이다. 현재 예제는 인증 정보 저장·상태 적용을 기다리지만 후속 조회 완료는 기다리지 않으며, 메모리 기반 확인과 실제 저장소의 미확인을 구별한다. 새 요구·코드 변경·역할 수행·검사 성공이 실제로 있었던 것은 아니다.

### 1. Main이 이번 요청과 기존 선택을 연결한다

Main은 기존 Work의 목표·선택·확인 범위와 실제 산출물을 복원한다. ‘기존 두 소비자에서는 비대기 선택이 맞았다’는 과거 결과를 ‘새 소비자도 비대기면 된다’로 옮기지 않는다. 이번 중심은 새 소비자가 기다려야 할 결과와 기존 인증 약속을 함께 지키는 것이다.

Work에는 이번 판단을 이어갈 의미가 남고, Personal의 이름·완료 기준과 Project의 인증 계약은 원문으로 찾는다. 정의가 충분하면 바로 수행한다. 목표를 처음부터 재인터뷰하거나 work-discussion을 자동 호출하지 않는다. 기존 접근의 전제가 실제로 흔들리면 Main이 관련 재판단 책임으로 처리한다. 공통 읽기 방법은 필요한 이해와 공백을 제공한다.

### 2. 구현자가 자기 질문으로 읽고 선택한다

Main은 요구·보존 조건·대상 판본·수정 범위와 최초 접근점을 전달한다. 구현자는 인증 계약, 현재 흐름, 이름·완료 기준을 실제 소비자와 대조한다. 공통 반환까지 바꿀지 의문이 생기면 Personal의 공통 제공·사용처 선택 기준을 추가로 읽는다. 초기 목록은 탐색을 막는 허용 목록이 아니다.

기존 계약 안에서 새 소비자만 필요한 조회를 기다릴 수 있다면 기술 선택을 비교한다. 공통 제품 약속 자체를 바꿔야 한다면 그 선택과 영향을 Main에게 돌려준다. 이미 충분한 근거를 다시 전부 읽거나 추가 탐색마다 허가를 받지 않는다.

구현자는 맡은 결과를 완성하고 자기 확인을 반환하며, 지속 설명이 달라져야 한다면 이미 확보한 근거로 제안한다. 예컨대 새 화면의 대기 동작과 기존 소비자의 보존 조건, 실제 확인 범위를 연결하고 Project current와 계약 본문에 함께 있는 미구현 설명의 정정을 제안한다. 파일 종류로 제안 범위를 자르거나 전체 맥락을 다시 조사해 완성 문안을 만드는 과업으로 확대하지 않는다. 중요한 충돌은 완료 보고 전에 알린다.

### 3. 달라진 의미를 알맞은 곳에 반영하며 수행을 잇는다

Main은 제안·실제 변경·확인 근거를 원요구와 유효한 계약·다른 소비자에 대조한다. ‘새 소비자만 조회를 기다린다’를 모든 로그인의 공통 보장으로 일반화하지 않는다. Work의 Ticket/current에 선택·이유·남은 확인을 남기고, 실제 지원이 확인되면 Project current와 계약 본문에 함께 적힌 현황을 맞춘다. 기존 공통 약속으로 설명되는 선택이면 그 뜻을 유지하며 미래 약속의 채택을 현재 지원으로 기록하지 않는다.

Main은 잠정 반영 과업의 방법을 사용해 해당 관리 지침으로 근거를 대조하고 허용된 본문·읽기 경로를 맞춘다. 검토와 반영마다 새 주체나 별도 호출을 만들지 않는다. 진행 중 담당자와 이전 의견·검사가 새 조건에도 유효한지도 연결한다. 제안을 받았다는 사실, 반영을 결정한 것, 실제 수정·확인과 전체 완료는 서로 다르다.

검토 전에 멈췄다면 중요한 제안과 근거·남은 판단을, 반영 후 멈췄다면 실제 반영과 남은 확인을 기존 Ticket/current에서 복원할 수 있게 한다. 중요한 제안·조정·미채택의 이유와 당시 조건은 후일 판단에도 쓸 수 있도록 records 등에 보존한다. 새 전달 장부나 모든 읽기의 영구 로그는 필요하지 않다. 재개는 자료가 남아 있는 담당자를 무조건 다시 호출하지 않고 이 근거와 현재 상태로 이어간다.

### 4. 기존 개선 검토·수정·검증을 거쳐 결과를 설명한다

개선 검토자는 원래 요구·관련 기준·실제 결과에서 소비자별 처리와 공통 처리의 이득·비용을 별도로 판단한다. 관련 Project 설명도 변경 결과에 포함하며 구현자 또는 Main이 쓴 새 문장을 자동으로 정답으로 받지 않는다. Main이 채택한 수정은 기존 수정 담당 흐름으로 연결한다. 검증자는 유효한 요구·계약·사용 조건에서 기대 결과를 도출하고 최신 대상의 근거를 확인한다. 이전 두 소비자의 검사가 여전히 유효하면 그 범위는 재사용하고 새 소비자 때문에 달라진 확인을 구별한다.

Main이 전체 상태를 판단하고 explain으로 요청에 답한 결과·이유·확인 상한을 설명한다. 설명을 위해 중요한 근거가 더 필요하면 기존 development 책임으로 확인한다. 문서의 반영 완료, 검증자의 반환, 전체 완료와 사용자 수락은 같은 상태가 아니다.

Work에는 현재 결과·남은 일·다음 행동, records에는 재판단에 필요한 비교와 근거, output에는 실제 결과 위치가 남는다. 같은 목표의 후속은 여기서 이어간다. 독립 목표의 분리가 요청되면 기존 생성·계승 방향에 따라 필요한 의미만 옮긴다. 이 전환 뒤에도 기존 담당자의 늦은 반환은 원래 Work·판본·권한에 귀속된다.

**이 흐름의 반복점:** 읽기·적용·변화 반영은 검토·검증 중에도 다시 일어난다. 3번을 마지막 문서 정리 단계로 미루거나, 네 항목 전체를 매 요청마다 실행하지 않는다.

이후05의 경험 개선에서는 위 제안·판단·실제 반영과 결과를 필요한 만큼 선택해 사용한다. 미반영 후보만 모으는 대기열로 한정하지 않고, 이미 반영한 선택의 효과나 유지할 이유도 볼 수 있다. 당시 근거가 유효하면 같은 설명을 다시 받지 않으며, 공백·충돌·후속 변경이 있으면 해당 부분만 추가 확인한다. 새로운 개선을 채택한 뒤 본문을 바꿀 때도 같은 반영 방법을 사용한다. 이것으로05의 발동 시점·담당이나02의 전체 기록 구조를 확정하지 않는다.

## 기존 수단에서 무엇을 유지하고 무엇을 공통화하나

| 대상 | 유지·보완·이관 판단 |
| --- | --- |
| development와 execution/review/verification | 전체 수행·시점·역할·권한·판본·판정은 유지한다. 공통 선택 방법의 전문을 나눌 때도 본체가 맡는 핵심 관계와 읽을 조건은 남긴다. |
| work-discussion / reconsider-work | 작업 정의와 전제 재판단이라는 다른 결과를 유지한다. 관련 맥락을 읽는다는 이유로 read에 통합하지 않는다. 직접 호출·실제 설치/호환 조건도 유지한다. |
| explain | 기존 첫 결과 설명 연결을 사용한다. 내용 수집·개발 완료·기록 권한을 explain에 넘기거나 4번에 별도 설명 체계를 만들지 않는다. |
| 기존 read-project-context | 이미 반복 선택·재사용·실물 대조·원래 과업 복귀를 맡았다. 일반 방법은 공통 참조로, 제품 특유 탐색과 권위는 Project에 남기는 잠정 이관안을 구체화한다. 기존 이름 유지나 별도 호출을 의무화하지 않는다. |
| 기존 update-project-context | 근거·보존 의미·허용 반영·소비 경로 확인·영향 반환을 보존한다. 대상 관리 계약에 따라 Personal에도 적용할 수 있는 한정 수행으로 펼친다. 영역별 관리 규칙을 복제하지 않는다. |
| Work 관리와 생성·전환 | 현재 상태·계승 의미의 정본은 Work에 남는다. 생성 방향은 이전 안을 이어 구체화하며 일상 읽기·본문 반영에 흡수하지 않는다. 실제 runtime의 설치·발견·전환은 대상 계약과06에서 잇는다. |

공통화할 실제 방법은 **질문별 본문 선택, 유효한 읽기 재사용, 원문·실물 대조, 적용 조건·충돌·미확인 구별, 원래 과업 복귀**다. 목표·제품 약속·개인 기준·이번 작업의 우선순위·검증 기대값까지 공통 참조가 결정하지 않는다.

본문의 이유·예외는 그 내용을 소유한 영역에서 읽는다. 형성 자료의 읽기·수정 원칙은 CONTENT-POLICY를 따른다. Work 재개 순서·파일 구성을 공통 참조에 복제하지 않는다. 실행 본문화 때에는 공통 조항을 기존 위치에 그대로 둔 채 파일만 더하지 않고, 각 입구에 남길 핵심과 상세로 옮길 방법을 실제 조항으로 대조해야 한다.

## 개발 밖의 요청도 같은 방법을 쓴다

| 요청 | 진입과 결과 |
| --- | --- |
| 관련 맥락을 읽고 설명해 달라 | 대상 root/context에서 관련 본문을 선택·대조하고 적용 의미·이유·공백을 답한다. 전체 개발·새 Work·문서 수정은 자동 추가하지 않는다. |
| 읽어서 이번 current에 정리해 달라 | 같은 읽기 후 Main이 Work 계약으로 이번 적용·선택·상태를 맞춘다. 원문 전문을 복사하지 않는다. |
| 확인한 변화를 Personal/Project에 반영해 달라 | 같은 한정 반영 과업이 해당 관리 기준으로 처리한다. 활성 Work가 없어도 가능하며 확인한 범위와 남은 영향을 반환한다. |
| 이번 경험에서 방식을 개선할지 보자 |05의 문제·대안·채택·효과 판단으로 연결한다. 채택 결과가 문서라면 반영 과업을 사용할 수 있다. 일상 사실 정정을 그 판단까지 미루지 않는다. |

USAGE와 context-update는 사용자가 매번 둘 중 하나를 골라야 하는 두 관문이 아니다. 같은 수행자가 유효한 근거를 이어 사용해 허용된 반영까지 수행할 수 있다. 실제로 중복 읽기·입력 재작성·불필요한 호출이 생긴다면 파일·호출 묶음을 조정할 근거다. 현재는 사용감이 확인된 결과가 아니라 검토할 흐름이다.

## 유지·교체와 후속 과제

- 읽기 방법을 바꾸면 공통 방법의 정본과 실제 읽을 조건·소비 연결을 맞춘다. 제품 내용과 Work 구조까지 같은 이유로 다시 정의하지 않는다.
- 반영 수단을 바꾸면 호출·반환·확인을 맞춘다. 각 영역의 권한·관리 기준은 남으므로 수동 수행이나 다른 수단으로 이어갈 수 있다.
- Work 구성 변경은02에서 기록·재개·생성 소비자와 함께 다룬다. 현재 Main의 갱신 책임은 이미 정해져 있으므로02의 전체 완료를 기다리지 않는다. Work에 새 형성 자료 구성을 적용하는 보류도 유지한다.
- 05는 경험에서 개선 수단을 채택하고 효과·수정·철회를 판단한다. 코드·검사·도구도 가능한 반영 대상이며 context-update만으로 이 루프를 대체하지 않는다.
- 06은 실제 설치·bridge·기존 장치 의존·배포·전환·복구를,07은 전체 적용과 관찰을 잇는다. 자동 Maintain을 재개하지 않는 사용자 방향과 Main의 현재 갱신 책임을 유지한다. 필요한 접점은 지금 다루되 이 설계로 후속 전체 완료를 선언하지 않는다.

Matt·Lauren·Vercel의 [기존 고정판 조사](2026-10-25-context-reference-synthesis.md)는 일상 문서 사용과 능동적 과업, 상위 흐름과 한정 수행·수정 권한의 구별을 뒷받침한다. 우리 관련 기준 공유·역할 배치·내용 소유를 대체하거나 USAGE+스킬이라는 정확한 형태의 우월성을 입증하지 않는다. 새 웹 조사나 외부 운영 효과 확인은 이번에 하지 않았다.

## 현재 남은 판단

현재 논의할 것은 위 실제 흐름에서 **요청별 진입·원문 선택이 충분한지, 제안의 근거·범위와 Main의 검토·반영 연결이 적절한지, 반영 후 남은 연결을 복원할 수 있는지, 공통 참조와 반영 과업의 형태가 자연스러운지**다. 기존 합의를 설명 없이 다시 열거나 이름·파일 수부터 고르게 하지 않는다. 구체 세부의 사용자 수용·실행 반영·효과 확인은 각각 별도로 남긴다.

최신 수정과 문서 확인 결과는 [제안·검토 후 반영 구체화](2026-10-26-context-proposal-review-apply-design.md)에 남긴다. 앞선 [전체 대조](2026-10-26-context-whole-scope-reconciliation.md)와 [초기 항목별 리뷰](2026-10-26-context-improvement-reviews.md)는 당시 근거로 보존하며 이번 후속과 혼동하지 않는다.
