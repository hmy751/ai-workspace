## 본체에서 교체할 수행

목적·권한·근거 책임을 유지하면서, 현재의 범위 판단과 핵심 설명 구성 앞부분을 아래 책임으로 다시 묶는다. 고정 답변 목차나 출력해야 할 작성 계획을 만들지 않는다.

### 1. 질문에 답하려면 무엇을 연결해야 하는지 정한다

교체 문구 후보:

> 현재 질문에서 사용자가 이해하거나 판단하려는 것을 실제 대상에 연결한다. 여러 부분이 함께 작동하는 대상을 설명할 때는 결과를 만드는 부분들이 무엇을 주고받고, 어떤 사건이나 조건에서 연결되는지 확인한다. 그 연결을 이해하는 데 필요한 구별을 먼저 잡고, 이를 따라 설명 순서와 코드 발췌를 고른다. 전체 역할을 한 문장 소개한 뒤 파일 순서대로 해설하는 것으로 이 구성을 대신하지 않는다. 단순한 표현이나 이미 공유된 연결의 한 대목을 묻는다면 해당 대목에서 바로 답한다.

이는 ‘핵심을 찾으라’는 문장만 추가하는 안이 아니다. 다음 상세에서 같은 자료를 함수 목록으로 조직했을 때와 사건·주고받는 값·공유 작업의 관계로 조직했을 때 무엇을 골라야 하는지 실제로 보여 준다. 구조 질문에만 이 방법을 제한하지 않되, 모든 흐름 질문을 구조의 적절성 평가로 확대하지 않는다.

### 2. 대상의 실제 작동 방식과 읽는 순서를 연결한다

현재 전체 범위·대표 경로 문단을 다음 의미로 교체한다.

> 대표 사건을 따라갈 때, 그 순간 실행되는 처리와 나중에 실행할 작업의 등록, 계속되는 관측과 선택적으로 시작되는 작업을 구별한다. 서로 독립적으로 들어오거나 겹칠 수 있는 경로를 하나의 필수 순서로 설명하지 않는다. 해당 관계가 답의 이해를 좌우하면 작은 도식·호출부·등록부를 먼저 연결하고, 같은 이름과 값을 유지해 필요한 코드로 내려간다. 실제로 단순한 순차 처리라면 그 순서를 그대로 설명하면 된다.

위 구별은 모든 답의 새 체크리스트가 아니다. callback을 등록한 코드와 실행 시점, 공유 Promise, Store 상태와 관측 수명처럼 실제 대상에서 구별하지 않으면 동작을 다르게 이해하게 되는 관계에 적용한다. 세부 표·도식을 항상 출력하라는 요구로 만들지 않는다.

### 3. 부분 해설은 전체에서 맡는 역할을 해결한다

현재 코드 발췌 기준·인접 배치·중심/보조 비중은 유지하되, 이미 반복되는 역할·관계 요구를 여기에 합친다.

> 각 부분의 해설은 앞에서 잡은 연결 중 무엇을 설명하는지 드러내고, 실제 구현이 그 역할을 어떻게 수행하는지 잇는다. 조건은 조건문 뜻뿐 아니라 그 조건이 달라질 때 해당 연결이나 결과가 어떻게 달라지는지 설명한다. 동작을 이해시키는 기능상의 이유와 현재 배치가 더 적절하다는 평가를 구별한다. 적절성 판단이 요청되면 그때 요구·사용처·대안의 이득과 부담을 대조한다.

국소 해설에 다시 전체 역할 요약·전후 비교·대안 검토를 모두 붙이지 않는다. 작성자의 과거 의도를 코드의 현재 효과에서 지어내지 않는다. 코드의 표현을 읽기 위해 필요한 문법 도움도 이 연결 가까이 둔다.

### 4. 마무리를 설명 목적에 맞춰 바꾼다

현재 마무리의 ‘핵심 조건과 후속 동작’만으로 전체 설명을 충분하다고 보지 않는다.

- 전체 코드·흐름: 설명 안에서 주요 사건이 어디로 들어와 어떤 부분과 상태를 거쳐 결과가 되는지, 독립 경로·공유 작업이 어떻게 연결되는지 찾을 수 있는가.
- 국소 표현: 해당 표현·값·조건이 지금 묻는 결과로 이어지는가. 전체 재설명은 필요하지 않다.
- 선택·결과 판단: 사용자가 묻는 선택에 직접 답했고, 그 판단을 바꾸는 근거·조건을 설명했는가.
- 앞선 말: 원뜻과 지금 유지·정정하는 주장, 달라지는 결론을 구별했는가.

이는 AI가 작성한 답의 점검 기준이며 사용자에게 시험·재진술을 요구하는 절차가 아니다. 기존 옛 브리핑의 목적별 충분성을 지금 본체의 공통 수행과 맞추되 옛 표를 그대로 붙이지 않는다.

## 상세의 구체 재편

파일은 현재 두 개를 유지한다. 작성 상세 안에서 다음 책임 순서로 재구성한다.

1. **여러 부분을 하나의 설명으로 구성하기:** 기존 인증 전체 안내를 실제 완성 가능한 구성 예시로 교체한다. 전체 사건·연결과 발췌 선택의 이유를 함께 보여 준다.
2. **이미 잡은 연결의 특정 대목 풀기:** 현재 인증 catch와 A/B 세션 대비는 위 전체 설명의 후속으로 옮긴다. 동기화의 두 호출·공유 Promise 예시는 국소 연결 보완으로 유지하되 첫 예시와 겹치는 일반 당위는 제거한다.
3. **선택과 변경을 판단하기:** 여행의 역할·위임 설명과 복구 경로의 적절성 비교를 유지한다. 기능상 이유와 선택 판단의 차이를 여기서 보여 준다.
4. **작업 결과를 원래 질문으로 돌려주기:** 보고서의 목표·관찰·결론 연결을 유지한다. 코드 사례의 작성 방식이 코드 없는 설명에도 전부 적용되는 것처럼 만들지 않는다.

### 인증의 전체 예시가 보여 줄 내용

원자료는 [당시 관측 코드](../source/artifact-explanation-scenes/02-auth-interceptor/historical-materials/observed/auth-interceptor-observed-20260922-0155Z.ts)다. 스킬 실행에서 현재 제품 구현인 것처럼 취급하지 않고 형성 예시의 판본·생략 범위를 표시한다.

처음 잡을 이해는 ‘요청에 토큰을 붙인다’만이 아니다. **요청이 속한 로그인 세션을 유지하면서, 필요한 토큰 갱신은 같은 세션의 요청들이 공유하고,401 뒤에는 한 번 재시도한다**는 연결이다. `setupAuthInterceptors`는 이 과정을 한 번에 끝까지 실행하는 함수가 아니라 Axios가 이후 요청·응답 때 호출할 처리를 등록한다.

| 설명에서 풀 연결 | 선택할 실제 코드 | 다음 설명과의 연결 |
| --- | --- | --- |
| 설정 시 등록과 실제 요청 실행 | `client.interceptors.request.use`, `response.use`의 등록부 | 아래 요청·응답 처리는 API 요청 때 호출된다는 것을 먼저 구별한다. |
| 한 요청이 속한 세션과 토큰 부착 | `config.sessionId ??= ...`, 세션 검사, `Authorization`, `return config` | 요청의 세션은 await 뒤에도 같은 작업의 기준이며 현재 Store는 바뀔 수 있다. |
| 두 곳에서 같은 갱신 작업 사용 | access token 부재 경로와401 경로의 `renewSession` 호출, `refreshes.get/set` | 요청 전 갱신과 응답 뒤 갱신이 별개의 알고리즘이 아니며 같은 세션의 진행 중 Promise를 공유한다. |
| 갱신 뒤 재시도와 중단 | `authRetried`, 갱신 후 세션 검사, `client(request)` | 갱신 성공 후 원 요청이 다시 client를 거치며 재차401이면 재인증으로 끝난다. |
| 기다리는 사이 세션이 달라지는 경우 | 기존 catch와 A/B 세션 대비 | 이미 본 전체 중 왜 이 위치의 세션 검사가 필요한지 후속으로 확대한다. |

표를 실행 답에 그대로 출력하는 형식으로 고정하지 않는다. 실제 상세에는 위 연결을 따라 짧은 설명과 정확한 코드 발췌를 구성한다. 모든 함수의 완전한 코드와 모든 오류 분기를 복사하는 것이 목적은 아니다. 단순히 이 표를 추가하고 기존 catch 해설을 그대로 병렬 배치하면 전체 예시가 완성됐다고 보지 않는다.

## 03에서 실제로 달라져야 할 답의 구성

03-C의 내용 자체를 틀렸다고 하거나 실패 정답으로 만들지 않는다. 사용자가 코드의 흐름을 이해하고 싶어 했으므로 동작 해설은 유효하다. 다만 `init → listener → refresh → cleanup`은 큰 수명 순서로는 유용해도 실제 관측이 계속되며 refresh가 겹칠 수 있는 관계를 주된 구성으로 보여 주지는 않는다.

후속 설명은 예를 들어 다음 관계에서 시작할 수 있다.

> init은 관측을 열어 두는 일입니다. 이후 기본 경로는 listener가 계속 보내는 값을 반영하는 것이고, refresh는 필요할 때 추가 관측을 요청하는 경로입니다. 둘은 기다리는 동안 겹칠 수 있고 결과는 applyObservation에서 실제 상태로 바뀝니다. 그래서 늦은 refresh 결과를 받아도 되는지 별도로 검사합니다. cleanup은 그 관측 수명을 끝냅니다.

그다음 listener 등록부와 refresh의 요청·accept가 각각 `applyObservation`에 연결되는 실제 코드, session 수명의 시작·종료를 먼저 보여 준다. 네 상태의 구별은 이 연결에서 실제 관측·확인 안내·디버그 표시가 무엇을 바꾸는지를 설명하는 자리에서 유지한다. `resolveNetworkStatus`의 boolean 판정부터 모든 함수를 차례대로 설명하는 구성에 새 역할 문단만 얹지 않는다.

이 network 문단은 현재 제안의 차이를 설명하는 Main 예시다. 독립 시험 결과가 아니며 이 문단을 실행 상세의 정답으로 복사하지 않는다. 이후03을 다시 생성해도 이미 반복 분석한 사례이므로 일반화 검증으로 삼지 않는다.

## 04와 과잉 적용 방지

04는 ‘테스트도 수정돼야 하는가’라는 판단 질문이다. ‘테스트를 다시 실행해야 한다’로 답을 옮기지 않고 동작 보존 리팩터링에서 기대값을 유지하는 이유를 직접 말하면 된다. 코드 동반·전체 구조 도식·등록/실행 구별을 여기까지 의무화하지 않는다. 앞선 발화 상세에는 이미 직접 질문·타당성 대조 기준이 있으므로04용 예외를 새로 덧붙이지 않는다.

## 수정과 확인을 진행할 기준

승인 이후 실행 변경을 한다면 본체의 구성·종료와 상세의 전체 예시를 한 묶음으로 바꾼다. 먼저 새 예시가 실제 원자료와 일치하고 전체 연결을 보여 주는지, 작은 질문·판단 질문·보고서·복구의 범위를 유지하는지 대조한다. ‘역할·관계’ 단어가 늘었는지, 코드 블록이 생겼는지로 완료하지 않는다. 본체의 수행과 상세의 실제 예시가 맞지 않으면 응답 생성 전에 고친다.

그 뒤 실제 효과 시험이 필요할 때는 설계 예시에 넣지 않은 상황으로 이 동작이 전이되는지를 본다. 표본·생성 변동과 사용자 판단의 한계는 유지한다. 이번 단계에서는03·04를 자동 재생성하지 않고, 실행 문구·예시·마무리 기준이 하나의 설명 방법으로 이어지는 구체안을 검토한다. 새 리뷰·모델 변경·스킬 분리·전역 설치를 해결책으로 자동 추가하지 않는다.

_background에는 원래 목적이 바뀐 것이 아니라 전체 구성 수행과 예시의 대응을 보완하는 이유, 직전 Main 진단의 부족, 재시험 사례의 노출 한계를 남긴다. 배경의 기록을 실행 시 전부 읽게 하지 않는다.
