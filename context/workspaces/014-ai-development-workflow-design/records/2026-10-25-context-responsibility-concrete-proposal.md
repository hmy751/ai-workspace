# 04-03 — 공통 맥락 절차의 구체 책임안

현재 추천은 후속 [Matt·Lauren 원문 조사와 종합](2026-10-25-context-reference-synthesis.md)에서 읽는다. 아래 하나의 context 스킬 안은 미채택 비교 후보로 남긴다. 이 안도 Owner·경험 개선의 경계를 구별했으며, 후속 조정은 일상 맥락 사용의 기본 진입을 새 스킬로 전제할지에 관한 것이다.

**사용자에게 보여 주기 위한 설계 후보다.** 하나의 맥락 스킬과 그 연결을 구체적으로 제안하며, 채택·실행 스킬 작성·설치는 하지 않았다. [앞선 구성 비교와 사용자 후속](2026-10-25-context-responsibility-and-skill-architecture.md)의 개발 중 사용 우선·직접 요청 병행을 입력으로 받는다.

후속 논의에서는 변화 반영과 경험 개선의 관계, 여러 영역에 걸친 스킬의 유지·교체 가능성을 구체화했다. 마지막 절의 일상 갱신·개선 채택·허용된 반영 구별과 세 변경 사례를 함께 읽는다. 하나의 스킬이라는 구성을 확정한 것은 아니다.

## 요청과 설계 기준

사용자는 앞선 추상 설명을 충분히 이해하지 못했다고 했고, 이어 다음을 요청했다.

> 좀 실제 어떻게 구분된느지 정확히 보고 싶어 니가 구상한걸
> 책임 분리 신경써서 한 번 보여줘봐

Main·담당자는 실행 주체이고, development·맥락 스킬은 그들이 사용하는 지침이며, Personal·Project·Work는 내용과 관리 기준을 소유하는 단위다. 이 셋을 같은 종류의 담당자로 그리지 않는다. 일반 수행과 내용 소유의 현재 관계는 [development](prototypes/development-workflow/skills/development/SKILL.md), [Work 지침](prototypes/development-workflow/noline-demo/context/work/AGENTS.md), [Personal](prototypes/development-workflow/noline-demo/context/personal/README.md), [Project 관리](prototypes/development-workflow/noline-demo/context/project/MAINTENANCE.md)에 있다.

## 문서별로 소유할 것

아래 `skills/context/SKILL.md`는 아직 없는 후보 위치이며 이름은 가칭이다. 실제 대상 root는 수행 입력과 root 진입점에서 찾고 스킬의 설치 위치로 추정하지 않는다.

| 문서·단위 | 이곳이 소유하는 내용 | 다른 정본과 연결하는 방법 |
| --- | --- | --- |
| `skills/development/SKILL.md`와 역할 상세 | 목표·범위, 작업 배정·수정권, 구현·검토·검증의 인수/반환, 변경 영향과 전체 완료. 맥락이 필요한 작업 장면과 수행 책임도 연결한다. | 담당자가 맡은 질문과 관련 원문을 직접 확인하고, 결과를 Main에게 반환하도록 연결한다. 선택·갱신의 공통 실행 방법은 맥락 스킬을 사용한다. |
| 가칭 `skills/context/SKILL.md` | 맡은 질문에 필요한 원문 선택·이해·실제 적용, 새로운 의미의 지속 범위·권위·근거 대조, 허용된 반영과 영향 확인의 재사용 절차. | 아래 context 진입·관리 기준을 읽고 적용한다. 작업 배정·역할 변경·새 제품 약속·개인 기준 채택 권한을 자체로 만들지 않는다. |
| Personal 본문과 관리 기준 | 개인 판단의 의미·조건·이유, 필요한 본문과 사례의 읽기 경로, 기준을 바꾸는 조건. | 이번 사용 조건과 선택은 Work에 남긴다. 개인 기준의 의미가 바뀔 때 해당 관리·선택 권한을 따른다. |
| Project 본문과 관리 기준 | 제품 약속·개발 규약·현재 구현 사실, 주제별 진입, 사실 정정과 새로운 제품 결정의 구별. | 이번 작업은 실제 계약과 구현을 대조한다. 새로운 제품 선택은 정해진 결정권으로 연결한다. |
| Work 본문과 관리 기준 | 이번 목표·제약·선택·상태와 근거, current·records·output의 역할과 유지 책임. | Main이 필요한 적용 의미를 남기고 원문을 연결한다. 내용 정본을 Work에 재정의하지 않는다. 상세 기록 구조는02에서 이어 정한다. |

공통 맥락 스킬은 여러 층에 쓰일 수 있는 실행 방법을 소유한다. 무엇이 특정 Project의 제품 계약인지, 어떤 상태를 Work current로 유지하는지까지 자기 안에서 별도 정의하지 않는다. development에는 맥락 책임의 수행 연결을 남기고, 같은 선택·갱신 알고리즘을 다시 복제하지 않는다.

## 가칭 맥락 스킬의 실제 실행 범위

스킬 하나 안에 아래 두 수행을 둔다. 별도 agent나 별도 스킬 두 개를 뜻하지 않으며, 짧고 충분하면 하나의 본문으로 시작한다.

| 수행 | 들어오는 정보 | 수행과 반환 | 문서 수정 |
| --- | --- | --- | --- |
| 필요한 맥락을 선택해 적용 | 맡은 목표·질문·대상·역할·판본, 관련 현재 상태와 이미 확보한 유효한 자료 | 실제 root와 정본의 읽기 경로에서 관련 계약·조건을 선택한다. 필요한 코드·근거를 대조해 이번 적용, 충돌, 열린 판단을 구별한다. 이미 읽은 유효한 내용은 재사용한다. | 읽었다는 사실만으로 문서를 고치지 않는다. 지속할 적용 의미나 변경 필요가 생기면 반영 수행에 연결한다. |
| 달라진 의미를 반영 | 확인된 사실·선택·변경 요청, 직접 근거, 기존 정본, 맡은 수정 범위 | 어느 의미가 달라졌는지와 지속 범위·권위를 해당 관리 기준으로 판단한다. 허용된 본문과 영향받은 진입·현재 상태를 맞추고 실제 반영 및 남은 판단을 반환한다. | 실행자의 기존 역할·배정·사용자 요청이 허용하는 범위만 수정한다. 범위를 넘는 변경 필요는 Main 또는 해당 결정권자에게 연결한다. |

이 입력과 반환은 별도 양식이나 매 호출 보고서를 의무화하지 않는다. 같은 Main의 수행 안에서 이어질 수 있고, 위임된 담당자는 Main이 다음 판단을 할 만큼 중요한 근거와 변화만 반환한다. 읽기 질문은 담당자가 계속 새로 만들 수 있으며 추가 읽기마다 Main의 허가를 기다리지 않는다.

스킬의 적용 조건은 필요한 맥락이 부족하거나, 현재 이해가 새 질문·근거와 맞지 않거나, 지속할 의미가 바뀌었거나, 사용자가 읽기·정리·반영을 직접 요청한 경우다. development는 역할 인수·수행 중 새 질문·결과 반환과 변경 처리에서 이 책임을 수행하도록 연결한다. 고정 시점마다 전부 재독·갱신하는 단계는 아니다.

## 실행 주체의 판단권과 수정권

| 주체 | 직접 판단하고 수행할 것 | 수정과 반환의 경계 |
| --- | --- | --- |
| Main | 목표·범위와 담당자 입력을 연결하고, 반환된 사실·선택·충돌을 전체 작업에 대조한다. 지속 범위·Owner와 기존 권한에 따라 반영하고, 바뀐 입력·기존 검증 근거의 영향을 연결한다. | Work current의 반영·확인을 기본으로 맡는다. 다른 문서의 수정 배정은 대상과 범위를 명시한다. 새로운 제품 약속·개인 기준은 해당 선택 권한을 따른다. |
| 구현·개선 검토·검증 담당자 | 자기 질문으로 필요한 current·원문·실제 근거를 읽고 판단한다. 중요한 적용 이유, 새 사실·충돌·변경 필요를 근거와 함께 반환한다. | 자기 역할과 명시 배정의 수정 범위를 따른다. 맥락 스킬을 썼다는 이유로 Work나 Project의 수정권을 얻지 않는다. 검증자의 제품 코드 수정 금지 등 기존 역할 계약도 유지한다. |
| 사용자·해당 결정권자 | 기존 위임을 넘어선 새로운 제품 약속이나 개인 기준 선택을 판단한다. | 이미 맡긴 범위의 사실 정정·기록마다 새 승인을 요구하는 구조는 아니다. |

Main이 직접 구현할 때는 같은 주체가 읽기·적용·유지를 이어 한다. 역할을 나눴을 때도 하나의 사실마다 별도 agent를 호출하지 않는다. 담당자의 독립 판단을 Main의 요약으로 대신하지 않으며, Work의 채택된 요구·조건과 Main의 미채택 제안을 구별해 전달한다.

## 로그인 이름 작업에 대입한 모습

다음은 현재 demo에 있는 책임 관계를 사용한 설명용 장면이다. 이번에 새 역할 수행이나 제품 검증을 실행한 증거는 아니다. 실제 Work의 [Project 선택](prototypes/development-workflow/noline-demo/context/work/workspaces/001-login-completion-names/current/memory/project-context.md)과 [Personal 선택](prototypes/development-workflow/noline-demo/context/work/workspaces/001-login-completion-names/current/memory/personal-context.md)에도 현재 선택·적용 이유와 원문 접근점이 이미 있다.

| 장면 | 실행 주체와 사용하는 지침 | 실제 읽기·판단·기록 |
| --- | --- | --- |
| 완료 callback의 이름을 정리하는 작업을 시작한다 | Main이 development로 범위·보존 조건을 잡고 맥락 스킬의 선택·적용을 사용한다. | Project의 저장·인증 상태 적용과 이후 조회의 계약, Personal의 완료 이름 기준을 선택한다. Work에는 이번 이름 변경의 목표와 동작 보존 조건·선택 이유를 남긴다. |
| 구현 담당자가 맡은 이름과 사용처를 대조한다 | 담당자가 역할 지침과 맥락 스킬의 선택·적용을 사용한다. | 관련 current에서 이번 범위를 읽고 계약·코드·소비자를 직접 확인한다. 필요한 추가 읽기를 수행하고 변경·근거·공백을 반환한다. |
| 검토나 검증에서 새로운 조건을 발견한다 | 담당자가 추가 읽기·대조를 수행하고 Main에게 중요한 차이를 반환한다. | 이번 선택으로 설명되지 않는 소비자 요구가 있다면 기존 범위·계약과의 충돌을 밝힌다. Project 계약을 임의로 바꿔 문제를 없애지 않는다. |
| 반환된 결과를 현재 작업에 반영한다 | Main이 development의 전체 판단과 맥락 스킬의 반영 수행을 사용한다. | current의 선택·상태와 필요한 records를 맞춘다. 제품 의미·사실이 실제로 달라졌다면 해당 Project 본문도 맞춘다. 변화가 없는 Personal·Project를 매번 갱신하지 않는다. |

이 장면에서 Work에 남길 적용 의미의 예시는 “이번 완료 표현은 저장과 인증 상태 적용을 가리키며, 이후 조회 완료를 약속하지 않는다. 이번 이름 변경은 동작을 보존한다. 판단 근거는 관련 제품 계약과 실제 사용처에 있다”이다. 이는 이번 작업의 의미와 적용 범위를 설명하는 예시이며, 현재 코드에 없는 변경이나 새로운 확인을 기록했다는 뜻이 아니다.

Project는 인증 완료·실패에 관한 제품 약속을, Personal은 완료 이름을 판단하는 조건을 계속 소유한다. Work는 그 기준을 이번 작업에 어떻게 적용했는지 소유한다. 원문이 달라져 이번 선택에 영향을 주면 Work도 다시 판단한다.

## 직접 요청과 후속 작업

‘이 맥락 읽어줘’는 같은 스킬의 선택·이해 부분에 직접 들어간다. ‘이번 결정 반영해줘’는 허용된 반영 부분을 사용한다. 개발 전체나 새 Work를 강제로 시작하지 않으며, 읽기만 요청한 것을 지속 문서 수정으로 확대하지 않는다.

02는 Work에 남길 내용과 수명·재개 방식,05는 경험에서 어떤 개선을 선택하고 효과를 볼지,06은 실제 배치·Recover·Verify·전환,07은 대표 작업의 연결과 부담을 소유한다. 경험 개선은 이 공통 절차로 원문을 읽고 채택된 맥락 변경을 반영할 수 있다. 새 Work 생성은 목표·선별 인수·진입을 만드는 별도 과업이며, 두 과업 전체를 이 맥락 스킬에 합치지 않는다.

## 이번 제안의 확인 범위

기존 development·Work 지침·Personal·Project 관리 기준·실제 선택 문서를 대조했다. 별도 읽기 전용 검토에서 행위자와 절차를 구별할 것, 직접 읽기를 자유로운 정본 수정권으로 넓히지 말 것, 이번 적용과 지속 기준 채택을 구별할 것을 확인하고 위 경계에 반영했다. 현재 역할 권한과 내용 정본을 유지하는 배치 추천이며, 실행 스킬·runtime·설치와 수행 효과는 미확인이다.

## 후속 — 경험 개선과의 관계 및 유지·교체 가능성

사용자 원문:

> 니가 말한 context 스킬에 변화반영도 말한거 보니 루프에서 반영하는그런걸 말하는건가?
> 음 전반적으로 니가 새로 만든다는건 좋아보이긴 한데 여러 영역에 만약 걸치면 이게 어떻게 유지되려나? 이런생각도들고 책임을 어떻게 잘 분리해서 블록처럼 서로 뗏다 붙엿다 잘 가능한 어떤 그런 좋은 고나리가 되려나 싶기도 하고

사용자는 새 구성에 가능성을 보면서도 영역을 가로지르는 책임의 유지·교체 가능성을 질문했다. 이를 하나의 맥락 스킬 채택이나 새 관리 장치의 구현 승인으로 해석하지 않는다.

### 일상 갱신·개선 판단·반영의 관계

| 구분 | 목적과 책임 | 맥락 절차와의 연결 |
| --- | --- | --- |
| 일상적인 맥락 유지 | 현재 사실·작업 선택·진행·미확인을 실제 결과에 맞춘다. 기존 Work 유지와 관련 내용 Owner의 책임이다. | Main과 허용된 담당자가 근거·권위·지속 범위를 판단하고 필요한 문서를 반영한다. 경험 개선을 매번 거치지 않는다. |
| 경험을 통한 개선 | 실제 경험에서 무엇을 왜 바꿀지, 다른 대안과 비용, 채택과 효과 관찰을 판단한다.05의 책임이다. | 필요한 맥락을 읽고 채택한 변경 중 문서 반영을 공통 절차로 수행할 수 있다. 코드·검사·도구 변경은 해당 실행 책임으로 연결한다. |
| 허용된 변화의 반영 | 근거·현재 정본·수정 권한을 대조하고, 바뀐 의미와 영향받은 경로를 맞춘다. | 일상 유지와 경험 개선 모두 사용할 수 있다. 미채택 후보는 후보로 보존하며 현재 규칙으로 반영하지 않는다. 반영 중 근거 부족이나 충돌이 발견되면 그 쟁점을 결정한 주체에게 반환한다. |

반영 수행에도 선별·권위·충돌·영향 판단이 있다. 이미 결정됐다는 이유로 기계적으로 쓰는 절차가 아니며, 새로운 개선 전략이나 제품 약속을 스스로 채택하는 절차도 아니다. 단순 사실 정정을 하기 위해 별도 개선 과업이나 새로운 승인 단계를 만들지 않는다.

### 지속 책임과 교체 가능한 실행 방법

각 context는 자기 의미·읽기 경로·관리 규칙의 정본을 유지한다. Main의 Work 유지와 전체 영향 연결, 역할별 읽기·판단·수정 범위도 맥락 스킬의 존재 여부와 무관하게 남는다. 스킬은 이 책임을 수행하는 공통 방법을 제공하며 특정 Project의 계약이나 Work의 내부 배치를 독점하지 않는다.

여러 영역을 쓰는 것과 여러 영역의 규칙을 한 스킬이 소유하는 것은 다르다. 공통 스킬에는 현재 질문에서 필요한 원문을 찾고 근거·권위를 대조하며 허용된 반영을 확인하는 방법을 둔다. 어느 Project의 어떤 계약을 채택할지, Work의 파일을 어떻게 구성할지, Personal 기준을 언제 바꿀지는 해당 정본과 선택 권한을 따른다.

연결할 때 필요한 정보는 맡은 목적·대상, 보존 조건·수정 범위, 관련 근거와 현재 선택이다. 반환은 적용·수정한 의미와 확인 범위, 미해결 충돌, 다른 작업에 영향을 주는 변화다. 이는 관계를 명확히 하기 위한 설명이며, 별도 JSON·고정 양식·매 호출 문서 생성을 요구하지 않는다. 한 주체의 수행 안에서 이어질 수도 있다.

각 영역의 반영 결과를 전체 작업과 맞추는 책임은 Main에 남는다. Project 본문만 반영되고 영향받은 Work가 아직 바뀌지 않았다면 그 상태를 구별해 이어 처리한다. 모든 영역의 갱신이 끝났다고 한꺼번에 간주하지 않는다.

이 사례는 설계상의 교체 가능성 대조이며 실제 파일 이동·스킬 제거·runtime 교체를 실행한 시험은 아니다. 한 곳을 바꿀 때 연관 변경이 전혀 없다는 약속도 아니다. 실제로 공유하는 의미나 권한 계약이 바뀌면 소비자도 조정해야 하며, 내부 구현만 바뀌는 일을 불필요하게 전파하지 않는지가 기준이다.

영역마다 새 스킬·adapter·담당자를 두거나 고정 입출력 형식을 도입해야 이 분리가 성립하는 것은 아니다. 기존 정본과 진입 관계를 우선 사용하고, 같은 내용을 반복 수정하게 하는 실제 차이가 드러날 때만 별도 책임이나 연결을 구성한다.
