### 기본 검사와 추가 확인의 관계

Project가 제공하는 필수 검사·변경 영향에 따른 검사 범위·실행 도구를 먼저 활용한다. 검증자가 매번 검사 체계를 처음부터 고르는 구조로 두지 않는다. 기계 검사는 정적 검사뿐 아니라 자동 단위·통합·실제 앱 E2E도 포함한다. 명확하고 반복 가능한 조건은 안정적인 도구로 확인하고, 기대값과 검사 범위의 적절성은 검증자가 판단한다.

검증자 안에서는 **필요한 기계 검사의 실행·유효성 확인, 그 검사가 원하는 결과를 확인하는지 판단, 중요한 잔여 공백의 추가 실행**을 구별한다. 현재 판본·환경·기대 결과에 유효한 원본 근거는 재사용한다. 명령 성공만으로 실제 검사가 실행됐다고 보지 않으며, 전체 테스트 전수 재실행이나 자동 E2E가 충분히 확인한 경로의 수동 반복을 의무로 만들지 않는다. 조건부 특수 검사는4~6번의 요구·공백에 따른 선택을 따른다.

### 충분성과 지속 반영

**필요한 기본 검사 결과가 유효하고, 중요한 요구·실패·보존 조건을 실제로 확인하며, 결론을 뒤집을 중요한 공백이 남지 않았을 때 검증을 마친다.** 필수 실제 경로를 확인하지 못했다면 자동 검사 통과로 그 요구를 충족 처리하지 않는다. 새 검사로 중요한 미확인을 구별할 수 있으면 실행하고, 같은 사실만 반복하며 새 변화·실패·의문이 없으면 종료한다. 테스트 수나 커버리지 비율만으로 충분성을 결정하지 않는다.

새로 발견한 문제는 다음에도 기계적으로 확인할 수 있는지 판단한다. 재발 가능한 동작 오류는 회귀 테스트, 안정적으로 판별할 규칙은 타입·lint·schema, 반복해서 새로 구성하는 앱 실행·조작은 기존 도구 보완에 연결한다. 맥락에 따른 선택은 해당 지침과 판단 역할에 둔다. 제품·지속 테스트·도구의 반영은 원 구현자나 Main이 지정한 담당이 검증자의 재현·입력·기대값을 이어받아 수행한다. 모든 임시 probe의 영구화나 새 도구 도입을 요구하지 않는다.

### 실행 공백의 처리

어떤 요구를 확인할 수 없고 무엇을 준비하면 확인 가능한지 좁힌다. 검증자는 기존 실행 명령 확인·허용된 로컬 데이터 준비·임시 관찰 코드 등 기존 권한 안의 준비를 직접 수행한다. 제품·지속 테스트·실행 도구 변경은 Main이 원 구현자나 해당 담당에게 배정하고 재현·필요 조건을 넘긴다. 계정 접근·외부 권한·사용자 선택이 필요하면 Main이 필요한 정확한 행동·결정만 연결한다. 요구가 모호하거나 자료가 충돌하면 원문과 계약을 먼저 대조한다.

이번 요구에 반드시 필요한 첫 실행 준비는 이번 작업에서 해결 담당과 범위를 연결한다. 반복될 때까지 미루지 않으며, 향후 여러 작업의 반복 비용을 줄일 범용 도구 투자는 필요성과 비용을 따로 판단한다. 한 경로가 막혀도 독립적으로 확인 가능한 나머지는 계속한다. 대체 환경·mock을 쓰면 확인 범위와 남은 실제 경계를 구별한다.

### 결과와 다음 행동의 연결

요구별로 **충족 근거 있음 / 불충족 근거 있음 / 미확인**을 반환한다. 어떤 대상·판본·조건을 확인했는지, 기대와 실제 결과, 근거·한계·다음 행동을 연결하되 고정된 긴 보고서는 요구하지 않는다. 원인이나 해결책이 확정되지 않았어도 관찰한 실패를 반환하고 추정과 사실을 구별한다.

제품 계약 위반은 제품 수정, 검사·기대값 결함은 검사 보완, 실행 공백은 준비 해결, 요구의 모호함은 기준 확인으로 잇는다. 오류 발생 자체를 제품 결함으로 판정하지 않고 실패 조건에서 약속한 상태 보존·오류 전달·후속 행동을 대조한다. 기존 실패도 이번 요구를 막거나 영향이 커졌다면 처리하며 무조건 제외하지 않는다. 요구와 무관한 개선 아이디어는 별도 의견으로 남긴다.

### 검증 반환과 전체 완료의 구별

검증자는 필요한 확인을 마쳤을 때뿐 아니라, 수정할 문제를 확인했거나 필요한 준비·결정이 남아 더 확인할 수 없을 때도 결과를 반환한다. 중요한 실패는 모든 검사를 마칠 때까지 보고를 미루지 않으며, 독립적으로 가능한 확인은 계속한다. 수정·준비로 넘긴 반환은 전체 요구 충족이나 완료가 아니다.

Main은 충분한 근거가 있는 현재 범위의 완료, 결함의 수정·재검증, 핵심 미확인의 준비·사용자 결정을 구별해 연결한다. 질문을 보냈다는 사실로 미확인이 해소되지 않으며 범위 축소·유보가 실제로 정해지기 전에는 기존 요구가 유지된다. 불안정한 실행은 한 번 성공할 때까지 반복해 통과시키지 않고 조건을 좁히거나 다른 관찰 방법을 찾는다. 중요한 불확실성은 그대로 남긴다.

개발 완료·검증 결과·실제 설치 및 배포·사람의 수락은 확인된 범위대로 구별한다. 모든 작업 끝에 별도 사용자 승인 단계를 추가하지 않는다. 검증자는 근거와 한정된 판정을, Main은 해결 담당·남은 선택·전체 완료 상태를 책임진다.

[Lauren 강연](../source/lectures/03_Agent_신뢰_강연_전체번역.md)과 [pstack 실행 도구 생성](../source/workflow-references/pstack/repository/skills/create-verification-skill/SKILL.md)의 실제 사용 가능 상태·조작·관찰, [feature](../source/workflow-references/pstack/repository/skills/poteto-mode/playbooks/feature.md)의 불명확한 결과·잘못된 확인 경로를 통과로 보지 않는 기준을 우리 책임 배치에 종합했다. 기존 리뷰와 보존 자료의 재대조이며 새 독립 리뷰·제품 실행 검증은 아니다.

### 재검증의 범위와 근거 유효성

수정자는 원래 재현·입력·독립 기대 결과를 이어받아 수정하고 자기 확인한다. 검증자는 같은 조건에서 원래 실패가 해결됐는지 확인하고, 좁은 재현이 원래 사용자·호출 경계를 대신하지 못하면 그 경로도 확인한다. 수정에 영향받은 정상 동작·실패 처리·상태 보존을 함께 본다. 재현이나 기대값을 바꾸면 근거와 이유를 밝히며, 현재 출력에 맞추는 것으로 해결을 대신하지 않는다.

Main과 검증자는 마지막 확인 대상과 현재 대상을 대조한다. 제품 코드뿐 아니라 테스트·설정·데이터·의존 조건의 변경도 근거 유효성에 영향을 줄 수 있다. 여전히 유효한 근거는 유지하고 영향받은 부분을 다시 확인한다. 영향이 불분명하면 그 불확실성을 해소할 만큼 범위를 넓힌다. 새 커밋마다 전체 폐기하거나 같은 기능이라는 이유로 이전 통과를 자동 유지하지 않는다.

### 담당자 재사용과 개선 검토로 돌아가는 조건

좁은 후속 재검증은 기존 검증자가 이어가는 것을 기본으로 한다. 최신 대상·변경·수정자의 확인·바뀐 가정·무효가 된 근거를 갱신해 전달한다. 요구·계약·주요 책임 변경, 충분한 입력에서도 반복되는 잘못된 전제, 다른 전문성의 필요, 검증자의 제품 수정 참여로 별도 확인이 필요한 경우에는 Main이 담당·범위를 다시 배정한다. 단순 입력 누락·접근 실패는 입력과 접근부터 해결한다.

개선 검토로 돌아가는 조건은 별도로 판단한다. 국소 결함은 수정·재검증으로 잇고, 책임 배치·공개 계약·사용 방식·중요한 절충이 바뀌면 관련 설계 질문을 다시 개선 검토한다. 매번 전체 리뷰나 같은 리뷰어의 재승인을 의무화하지 않는다.

### Verify와 기록의 연결

반복 개발 확인은 직접 검사 명령을 사용한다. 지속 증거가 필요한 인계·상태 전환에서 실제 설치·호환된 Verify를 선택적으로 사용한다. Verify의 명령 실행·snapshot·receipt는 검증자의 의미 판단과 Main의 완료 결정을 대신하지 않으며 모든 검증의 선행 조건이 아니다.

Main은 기존 지침에 따라 기록을 관리한다. 유용한 재현·수정 전후 관찰을 Work 기록이나 지속 테스트에 남기고, 실행 방법이 달라지면 해당 Project 안내·도구를 갱신한다. 임시 환경 정리가 유일한 근거를 지우지 않게 한다. 자동 Maintain은 미연결로 유지하며 explain은 결과 설명 방법을 맡는다.

## 전체 관계와 세 가지 확인

구현자는 맥락을 적용해 구현하고 자기 확인을 마친다. 개선 검토자는 더 나은 선택을 탐색하며 Main이 채택·수정을 연결한다. 그 최신 결과를 별도 검증자가 확인하고, 문제가 있으면 Main과 수정 담당자가 해결한다. 검증 결과를 받은 Main은 전체 완료 상태와 사용자에게 필요한 설명·결정을 정한다.

| 구별할 것 | 맡기는 일 | 이것만으로 말할 수 없는 것 |
| --- | --- | --- |
| 기계적 검사 | lint·타입·schema·자동 테스트 등 명시된 규칙과 기대 결과를 반복 판별 | 검사할 규칙이 충분한지, 기대값 자체가 맞는지, 실제 사용 전체가 되는지 |
| 검증자의 판단 | 요구·제품 계약에서 필요한 증거를 고르고 기존 검사와 실제 결과를 대조 | 보지 못한 환경의 실제 성공, 사람의 주관적 수락 |
| 사람의 판단 | 목표·약속 변경, 중요한 절충, 사람에게 남은 수락과 기존 권한 밖 선택 | 실행하지 않은 동작의 성공을 대신 증명하는 것 |

실제 앱 실행은 이 셋과 경쟁하는 별도 계층이 아니라 **증거를 얻는 방법**이다. 자동 E2E도 실제 앱을 실행할 수 있고, 검증자도 도구로 앱을 조작할 수 있다. 테스트·eval은 관찰 근거이며 실행 중 권한·데이터 제약을 강제하는 장치와는 다르다. 기존 `Verify`는 명령 실행과 근거 보존을 맡는 도구이지 이 검증자 역할의 다른 이름이 아니다.

## 검증안1. 목적과 책임

검증자는 **현재 결과가 이번 요구·보존 계약을 충족하는지, 그 결론을 말할 근거가 충분한지** 판단한다. 원요구·제품 계약·사용 조건을 직접 읽고, 작성자가 무엇을 의도했는지와 실제로 무엇이 일어나는지를 구별한다. 발견이 없다는 보고나 검사 통과 개수를 완료 근거로 대신하지 않는다.

성능·접근성·권한·데이터 보존·실패 동작도 이번 요구나 영향받는 제품 약속이면 확인 대상이다. 설계와 코드의 질에서 더 나은 대안을 계속 탐색하는 일은 앞선 개선 검토의 중심이다. 검증 중 드러난 구조 문제는 보고할 수 있지만 모든 설계 비교를 다시 시작하지 않는다. 같은 문제를 여러 역할이 발견하는 것은 허용한다.

코드·설계·테스트의 더 나은 선택은 개선 검토자가 평가하고, 채택한 개선의 수정·반영·이득 확인은 기존 Main·수정 담당 흐름이 책임진다. 이를 검증자의 일반적인 재심사 과제로 넘기지 않는다. 검증자는 최종 결과의 요구·계약 충족과 이를 뒷받침하는 검사·실행 근거를 중심으로 판단한다. API 변경의 호출부 누락이나 이름이 뜻하는 완료 시점과 실제 반환의 불일치처럼 검증 중 드러난 구체적인 요구 위반은 반환할 수 있다. 구조·이름의 더 나은 대안 전체를 다시 평가하는 책임과 구별한다.

기대 결과가 모호하거나 현재 Spec의 해석과 원문이 충돌하면 문제를 드러내고 Main에 돌려준다. 검증자가 통과시키기 위해 목표·계약을 낮추거나, 임의로 새 요구를 추가하지 않는다. 명확한 요구를 읽고 구체적인 기대 결과를 정하는 일까지 사용자에게 넘기지는 않는다.

## 검증안2. 시작 시점과 담당자

별도 검증은 구현·개선 검토의 중요한 의견을 처리한 **최신 결과**를 대상으로 한다. 큰 작업에서 독립적으로 확인 가능한 완성 단위는 먼저 검증할 수 있으며 전체 통합 검증과 구별한다. 구현 중에는 구현자가 계속 자기 확인하며 마지막 검증까지 알려진 결함을 미루지 않는다. 중요한 외부 실행 경로나 데이터가 없으면 그 접근 문제는 초기에 확인해 마지막까지 숨기지 않는다.

특수 데이터·실패 주입·전후 기준선·실제 어댑터 관찰이 중요한 약속의 확인에 필요하면 Main과 구현자는 구현 중에 확인 가능성을 확보한다. 접근할 수 있다는 사실만으로 필요한 실패·보존 조건까지 관찰할 수 있다고 가정하지 않는다. 이 가능성이 설계 선택을 바꾸면 작은 재현·관찰부터 수행한다. 준비된 방법과 근거는 최종 검증의 입력이며 별도 판정을 대신하지 않는다. 모든 작업에 사전 계획서나 검증자 사전 승인을 추가하는 것은 아니다.

제품 동작·계약·통합에 판단이 개입된 개발 결과에는 별도 검증자 한 명을 기본으로 둔다. 오탈자·내용을 바꾸지 않는 형식 정리 등 해당 범위가 결정적 검사·직접 대조로 충분하면 Main의 확인으로 줄일 수 있다. 축소한 확인을 별도 독립 검증을 수행한 것처럼 부르지 않는다. 코드 변경량이나 Main의 확신만으로 생략하지 않는다.

첫 검증자는 해당 구현·수정을 작성하지 않은 새 컨텍스트에서 시작하고, 개선 검토자의 세션과 구별한다. 앞선 의사결정 대화 전체는 기본 상속하지 않는다. [실행 배치](prototypes/development-workflow/skills/development/references/execution.md)의 내부 담당 시작값 GPT-6.1-sol medium과 실제 도구·입력 확인을 이어받는다. 전문성이 다른 독립 범위가 있을 때만 추가 배정을 고려하며, 어려운 판단을 단순 검사 실행과 같은 이유로 낮은 역량에 맡기지 않는다.

## 검증안3. 첫 입력과 추가 맥락

Main은 확인할 대상과 주장, 최신 요구·계약·사용 조건, 변경 범위와 기준 판본·미커밋 변경, 실제 자료 접근점, 기존 확인 근거와 공백, 실행 환경·권한을 연결한다. 채택한 변경이 동작·계약·사용 조건을 바꿨다면 그 최신 의미와 기존 확인 근거를 이어 준다. 개선 의견 전체의 재승인을 요청하지 않는다. 작성자의 “완료”는 검증할 주장으로 제공하고 예상 판정은 주지 않는다. 원문·실물 대신 요약만 주지 않는다.

관련 root·로컬 지침과 Project·Work 계약은 직접 읽게 한다. Personal의 관련 판단 기준도 접근·적용할 수 있지만 Personal 전체를 매번 읽는 고정 절차나 새로운 검증 규칙집으로 만들지 않는다. 실제 결과가 지켜야 할 선택과 검토 과정의 개인 선호를 구별한다. 원요구의 해석이 쟁점이면 최소 원문과 이후 유효한 정정을 함께 본다.

검증자는 필요한 원자료·호출부·실행 근거를 스스로 더 찾아볼 수 있다. 자료 접근 실패, 충돌하는 약속, 맡은 결과를 넘어서는 범위 변경은 근거와 영향을 Main에 반환한다. 읽을 범위를 넓힐 수 있다는 사실이 수정·외부 실행의 권한까지 넓히지는 않는다. 일반 Workspace 전체 인수 대신 맡은 검증의 목표·계약에서 출발한다.

## 검증안4. 요구에서 확인 장면과 방법을 고른다

원요구·유효한 정정·제품 계약과 사용처에서 이번 결과의 중요한 성공·실패를 구별할 관찰을 먼저 정하고, 작성자의 주장·테스트·기존 근거가 이를 어디까지 확인하는지 대조한다. 작성자가 제시한 주장에 빠졌어도 이번 요구에 필요한 결과는 확인 범위에 연결한다. 엄격한 파일 열람 순서나 기대값 명세서를 추가하는 요구는 아니며, 자료를 더 읽고 기대 결과를 고칠 수 있다.

정상 성공만이 아니라 이번 변경이 건드린 실패·경계·상태 전이와 소비자를 함께 본다. 현재 요구 충족 판단을 크게 바꿀 미확인을 먼저 찾고, 이를 구별할 관찰을 고른다. 우선순위는 변경량보다 사용자 결과의 영향, 기존 근거의 공백, 실패를 발견·복구할 수 있는 정도로 정한다. 모든 가능한 예외의 전수 검사나 위험 점수표는 요구하지 않는다.

| 작업과 주장 | 우선 확인할 근거 | 더 확인해야 하는 조건 |
| --- | --- | --- |
| 버그 수정 | 원래 재현 조건과 수정 뒤 결과, 가능하면 같은 조건의 수정 전 실패 | 원인을 가정한 재현만 있거나 주변 실패·회복 경로가 바뀜 |
| 기능 구현·통합 | 실제 호출자·사용자 진입에서 행동과 결과, 필요한 저장·외부 효과 | 함수 단위는 성공하지만 사용 경로·설정·권한·실제 의존 연결은 미관찰 |
| 동작 보존 리팩터링 | 보존할 공개 계약, 중요한 기존 사례의 전후 결과·부작용 | 책임·상태 수명·호출 순서·공통 기반이 바뀌어 기존 검사로 영향이 덮이지 않음 |
| 규칙·형식·타입 변경 | 해당 규칙의 검사와 변경 의미의 직접 대조 | 실행 때의 값·환경·사용 의미까지 달라짐 |

성능 요구는 실제로 약속한 조건에서 측정하고, 성능 수치를 맞췄다는 이유로 기능·품질까지 통과시키지 않는다. 문서·설명·스킬 같은 AI 산출물은 링크·형식 검사와 의미 대조, 필요하면 대표 요청의 실제 수행을 구별한다. 원문 접근·호출 성공·한 번의 응답으로 일반적 효과를 증명하지 않는다.

## 검증안5. 기계적 검사를 충분히 활용하고 그 검사를 읽는다

위 합의의 수행 흐름에 따라 기본 검사는 구현 중부터 활용한다. Project의 필수 검사와 변경 영향별 검사 범위를 바탕으로, 검증자는 실행·유효성 확인과 검사 적절성·추가 확인을 구별한다. 도구가 이미 확실히 판별한 사항의 중복 자연어 검토를 줄이고, 새로 발견한 문제는 기존 테스트·규칙 검사·실행 도구에 지속 반영할지 담당자와 연결한다.

대상의 기존 lint·타입·단위·통합·E2E 등에서 요구와 변경 영향을 확인할 수단을 먼저 고른다. 명확하고 반복 가능한 조건을 자연어 재판단으로만 남기지 않는다. 어떤 검사가 실제로 해당 코드·경로를 실행하고 무엇을 assertion으로 보장하는지 확인한다. 실행 명령이 성공해도 테스트가 선택되지 않았거나 관련 경로를 우회했다면 해당 동작의 근거로 쓰지 않는다.

테스트의 기대값은 요구·계약·독립 사례에서 가져와야 한다. 구현의 상수·알고리즘을 그대로 다시 계산하는 검사, 내부 배치만 보는 검사, mock 때문에 중요한 실패가 사라지는 검사는 근거 상한을 낮춘다. 가능하면 실제 공개 인터페이스와 소비자가 보는 결과로 확인한다. 저장·외부 부작용 자체가 계약이면 DB·파일·로그 등의 관찰을 보조 근거로 함께 사용한다.

검사가 실제 결함을 잡는지 의심되면 원래 재현·적절한 실패 사례·좁은 대조 실험으로 구별한다. 모든 테스트에 mutation test를 붙이거나 모든 변경을 TDD로 다시 만드는 것은 기본이 아니다. 불변식·많은 입력 조합이 핵심인 구체 과제라면 속성 기반 검사나 모델 대조를 후보로 볼 수 있지만 새로운 도구부터 도입하지 않는다. 형식 검증은 명확한 필요와 유지 역량이 있는 별도 선택으로 남긴다.

형식 검증은 동시성·재시도처럼 테스트가 놓치기 쉬운 순서나 입력을, 명시한 모델·범위·가정 안에서 확인하는 방법이다. 적용한다면 모델과 실제 코드의 대응, 깨진 변형에서 실패하는지, 확인한 한계와 유지 비용을 함께 본다. 작은 모델이 통과해도 실제 앱 전체의 성공으로 올리지 않는다. 이 방법은 매 작업에 붙이는 네 번째 담당자가 아니라 특정 약속을 확인할 도구 선택이다.

## 검증안6. 기존 근거 재사용과 독립 확인의 깊이

작성자가 실행한 검사도 원본 결과·대상·방법·조건을 확인할 수 있고 현재 판본에 유효하면 재사용한다. 독립성의 중심은 같은 명령을 새 사람이 다시 실행하는 횟수가 아니라 **요구와 실제 근거의 관계를 별도로 판단하는 것**이다.

재실행·추가 확인은 판본이나 실행 산출물이 바뀜, 조건·데이터·의존성이 다름, 원본 증거가 없음, 중요한 실패를 검사하지 못함, 결과가 불안정함 등의 이유에서 고른다. 설명·로그의 주장만 있고 실제 행동 근거가 없으면 중요한 경로를 직접 확인한다. 실행한 대상과 검토 중인 파일이 다른 경우도 확인한다.

기존 근거를 읽은 부분, 검증자가 직접 재실행한 부분, 새 독립 사례로 확인한 부분, 확인하지 못한 부분을 구별한다. 관찰 없는 추론을 실험 결과처럼 보고하지 않는다. 한 줄의 저장 순서 변경도 중요한 보존 조건을 바꿀 수 있고, 넓은 이름 변경은 기존 근거와 직접 대조로 닫힐 수 있다. 현재 질문에 답하는 근거는 재사용하고 답하지 못하는 경계를 더 확인한다. 새 의문이 생기면 방법을 바꾸며 같은 근거를 늘리는 것으로만 확신을 높이지 않는다. 전체 재실행·고정 표본 개수·매번 해시 체계 구축을 의무화하지 않는다.

### 합의한 검사 충분성 기준

필요한 기본 검사 결과가 유효하고, 현재 결과의 중요한 요구·보존 조건과 이번 변경이 영향 주는 경로에 적합한 근거가 있고, 그 근거가 현재 대상·환경·기대 결과에 유효하며, 결론을 뒤집을 중요한 실패·모순·미확인이 남지 않았는지를 본다. 정상 결과만이 아니라 관련된 실패 처리·상태 전이·부작용을 포함하되 작업 범위를 넘어선 모든 가능성의 확인을 요구하지 않는다.

다음 검사가 아직 남은 중요한 질문을 구별할 수 있으면 수행하고, 같은 사실을 반복 확인할 뿐이며 새 변화·실패·의문이 없으면 검사를 끝낸다. 테스트 수·커버리지 비율·고정 반복 횟수를 충분성의 단독 기준으로 삼지 않는다. 필수 실제 경로를 확인하지 못했다면 테스트가 통과해도 그 요구는 미확인이다. 대상 밖 한계와 핵심 요구의 공백을 구별해 반환하며, 전체 완료 상태는 Main이 판단한다.

기존 근거의 재사용은 파일 이름이나 성공 요약만으로 정하지 않는다. 실제 대상 판본, 검사 코드·설정·데이터·의존 조건, 기대 결과와 관찰 범위가 현재 질문에도 유효한지 본다. 직접 재실행·새 독립 사례·기존 근거 대조를 구별해 반환한다. 조건부로 재사용한다는 선택은 별도 검증자의 요구 해석·근거 판단을 생략하는 뜻이 아니다.

## 검증안7. 실제 실행과 도구·환경

실행이 필요한 주장은 실행 가능한 경로를 찾는다. 대상의 기존 안내와 도구로 시작해, 올바른 판본과 인스턴스·사용 가능한 초기 상태·인증·데이터를 확인하고 실제 진입점에서 조작한다. 그 행동과 결과, 계약상 필요한 부작용을 연결해 관찰한다. 화면 한 장·프로세스 응답·내부 setter로 만든 상태만으로 실제 사용 성공을 주장하지 않는다.

앱이면 UI·API·기기 경로 중 이번 사용자가 통과하는 경계, 라이브러리면 공개 API, CLI면 실제 명령과 출력·파일 효과를 고른다. 모든 과제에 브라우저나 전체 앱 실행을 붙이지 않는다. mock·test mode·대체 환경을 썼으면 생략한 실제 경계와 그로 인해 남는 확인을 밝힌다. 실패하면 제품 결함인지 실행 준비·도구 문제인지 근거로 구별한다.

반복 사용에 필요한 정보는 무엇을 실행하고, 어떻게 준비 완료를 알며, 기능에 어떻게 접근하고 조작하고, 무엇을 관찰하고, 어떤 임시 자원을 정리하는지다. 기존 Project 문서·테스트·앱 제어 도구가 이를 제공하면 재사용한다. Feature Map은 기능·접근 경로·조작·관찰 결과를 찾게 하는 역할로 참고하며 별도 파일 묶음을 의무로 만들지 않는다.

이번 요구의 중요한 결과를 관찰할 경로가 없으면 첫 발견부터 Main이 해결 담당과 필요한 범위를 정한다. 허용된 로컬 준비·임시 계측은 검증자가 수행할 수 있고, 제품·지속 테스트·실행 도구 변경은 지정 담당자가 맡는다. 이번 확인을 막는 준비와 반복 비용을 줄이기 위한 도구 투자를 구별한다. 반복 사용의 이득이 있으면 로컬 스킬·helper·기능 접근 안내를 보완하되, 첫 필수 확인을 반복 실패가 생길 때까지 미루지 않는다. 새로 고친 실행 절차는 실제 사용해 확인한 범위와 함께 기존 Project 안내나 로컬 도구의 Owner에 남긴다. 한 경로가 막혀도 독립적으로 확인 가능한 나머지는 계속한다. 확인할 수 없는 요구와 필요한 준비·접근·결정을 구체적으로 반환한다.

현재 demo는 UI 없는 메모리 기반 Node 예시다. 보존 Noline 색인에 `start-app`이 있지만 본문·현행 실행은 확인하지 못했다. 따라서 실제 Noline을 실행할 수 있다고 가정하지 않고, 적용 시 대상의 기존 실행 수단부터 확인한다. 이번 설계가 새로운 CLI 설치나 운영 앱 조작의 승인은 아니다.

## 검증안8. 검증자가 실행·작성할 수 있는 범위

기본 권한은 대상 읽기, 허용된 검사·앱 조작, 격리된 임시 재현·검증 코드 작성, 근거 반환까지다. 읽기 전용 보고 역할과 도구 실행 가능 범위를 구별한다. 임시 probe는 동작을 관찰할 용도이며 제품 정본이나 통과 기준을 바꾸는 우회로가 아니다.

제품 코드·지속 테스트·계약의 정본 수정은 Main이 별도 담당과 범위를 정한다. 영구 회귀 검사가 필요하면 검증자가 독립적인 실패 사례·기대 결과를 정의해 넘기고 원 구현자나 지정 담당자가 제품 수정과 테스트 통합을 맡는다. 검증자가 지속 테스트 작성을 별도로 맡을 수 있으며 검사 파일을 썼다는 사실만으로 제품 작성자와의 독립성이 사라지는 것은 아니다. 제품을 직접 고쳤다면 자기 확인과 별도 판정의 범위를 밝히고 자신이 고친 결과를 독립 확인했다고 부르지 않는다.

기존 권한 안의 되돌릴 수 있는 로컬 확인은 계속 진행한다. 실제 외부 효과, 공유 데이터·인스턴스, 비용·발송·삭제 등은 대상 지침과 이미 받은 권한을 따른다. 안전한 방법이 없고 승인이 필요한 정확한 행동만 Main이 사용자에게 연결한다. 모든 앱 실행을 새 승인 단계로 만들지 않는다. 격리 공간·프로세스는 자신이 만든 범위만 정리하고 필요한 증거는 유지한다.

중요한 실행에서 `test mode`·`dry-run`의 이름만으로 부작용이 차단됐다고 가정하지 않는다. 그 경계에 의존한다면 실제 설정·도구가 격리하는 범위를 확인한다. 실행 권한이나 실제 집행을 지침 문구만으로 보장했다고 표현하지 않는다.

## 검증안9. 반환은 판정과 다음 행동을 연결한다

확인한 주장별로 **충족 근거 있음 / 불충족 근거 있음 / 미확인**을 구별하고, 현재 결론과 실제 대상·방법·관찰·제한을 연결한다. 기계 판정 schema나 긴 보고 양식이 아니라 Main이 다음 행동을 정할 정보다.

문제가 있으면 기대와 실제 결과, 재현 조건·근거, 사용자 결과에 미치는 영향, 다음에 확인하거나 고칠 지점을 반환한다. 제품 결함, 검사·기대값의 결함, 실행·접근 공백, 요구의 모호함, 기존부터 있던 실패를 구별한다. 원인·해결책이 불명확해도 관찰된 실패 자체는 보고할 수 있으며, 제안 원인과 확인 사실을 섞지 않는다.

정상 경로와 실패 경로 모두 요구·계약에서 기대한 결과로 판정한다. 오류가 나도 약속한 상태 보존·오류 전달·후속 행동이 맞으면 해당 실패 처리 요구에는 충족 근거가 된다. 검사 공백과 제품 결함을 구별하고, 제품 수정은 어긋난 약속을 특정한 뒤 배정한다. 현재 요구가 최신 조회 결과까지 필요하다면 인증만 성공했다는 근거로 전체를 닫지 않는다.

중요한 미확인이 남으면 “통과+참고”로 묻지 않는다. 반대로 요구와 무관한 개선 아이디어 때문에 동작 검증 전체를 실패로 만들지도 않는다. 기존 실패는 근거와 이번 영향으로 구별하며 무조건 제외하지 않는다. 검증자는 해당 범위의 결론을 반환하고 Main이 전체 작업 상태를 정한다.

## 검증안10. 수정과 재검증

Main은 실패 관찰의 타당성과 해결책을 구별해 판단한다. 제품 결함은 원 구현자 기본 수정, 검사 결함은 적절한 기대값·검사 보완, 환경 공백은 실행 준비·접근 해결, 모호한 약속은 필요한 원자료·사용자 결정으로 잇는다. 같은 문제의 수정자가 겹치지 않게 한다.

수정자는 최신 과제·실패 재현·독립 기대 결과·보존 조건·기존 증거에서 무효가 된 부분을 받아 고치고 자기 확인한다. 실패 assertion을 삭제하거나 기대값을 현재 출력에 맞춰 통과시키는 것으로 계약을 바꾸지 않는다. 실제로 기존 기대값이 틀렸다면 그 기준의 근거를 먼저 바로잡는다.

유용한 독립 재현은 다시 실행할 수 있는 코드·명령·입력 또는 조작 기록과 기대 결과로 넘긴다. 수정 전 관찰한 실패와 수정 뒤 결과를 같은 조건으로 비교하며, 재현이나 기대값을 바꿨으면 무엇이 왜 달라졌는지 밝힌다. 좁힌 재현이 원래 실패를 관찰한 경계를 대신하지 못하면 수정 뒤 원래 사용자·호출 경로도 확인한다. 같은 검사를 두 담당자가 새로 작성하거나 영향 없는 근거까지 다시 실행할 필요는 없다.

좁은 후속 재현과 영향받은 보존 계약의 재검증은 기존 검증자가 이어가는 것을 기본으로 한다. 최신 대상·변경·수정자의 확인·바뀐 가정·무효가 된 근거를 전달한다. 제품 코드 외에 테스트·설정·데이터·의존 조건 변화도 살피고 영향이 불분명하면 확인 범위를 넓힌다. 목적·계약·주요 책임이 바뀌거나 같은 잘못된 판단이 반복되면 Main이 재판단·담당 교체·필요한 개선 검토를 선택한다. 중요한 설계 변경에 해당할 때만 앞선 개선 검토로 돌아가며 작은 버그 수정마다 두 단계를 처음부터 반복하지 않는다. 수정 전 판정의 유효 범위를 갱신하고 영향받지 않은 근거는 유지한다.

## 검증안11. 검증 반환과 전체 완료를 구별한다

검증자는 필요한 확인을 마쳤거나, 수정할 문제를 확인했거나, 필요한 준비·결정 때문에 더 확인할 수 없을 때 근거와 한정된 판정을 반환한다. 중요한 실패는 모든 검사를 마칠 때까지 보고를 미루지 않는다. 수정·준비로 넘긴 반환은 전체 요구 충족이나 작업 완료가 아니며, 독립적으로 가능한 확인은 계속한다.

Main은 현재 대상의 요구·보존 계약에 필요한 근거가 있고 중요한 실패·미확인이 해소되면 해당 범위의 완료를 판단한다. 결함이 남으면 수정·재검증을 연결한다. 핵심 요구가 미확인이면 확인된 부분과 막힌 부분·재개 조건을 구별하고 필요한 준비·사용자 결정을 연결한다. 질문을 보냈다는 사실로 미확인이 해소되지는 않는다. 범위 축소·유보를 제안할 수 있지만 실제 선택이 정해지기 전 기존 요구는 유지된다.

실행 불가나 불안정한 실패는 한 번 성공할 때까지 무작정 반복해 통과시키지 않는다. 누락된 전제·실패 조건·다른 관찰 방법·담당 재배치를 찾고 허용된 방법으로 사실을 확인할 수 있으면 계속한다. 실제 사용자 선택이나 접근이 필요한 지점만 묻고, 중요한 불확실성은 그대로 반환한다.

Main은 사용자가 요청한 결과, 중요한 변경과 판단, 확인한 범위, 남은 선택을 설명한다. 개발 완료, 별도 검증의 결론, 설치·배포, 사람의 수락을 실제 확인한 범위대로 구별한다. 검증을 수행했다는 사실로 제품 완성·운영 수락을 주장하지 않고, 별도 사람 승인 회의를 모든 작업의 끝에 추가하지 않는다.

## 검증안12. development·Project·기존 Verify·기록의 배치

공통 역할·수정·완료·Main의 기록 책임은 기존 [development 본체](prototypes/development-workflow/skills/development/SKILL.md)에 두고, 합의한 검증자의 수행 상세는 같은 스킬 내부의 `references/verification.md`로 연결하기로 합의했다. 이 파일의 실제 생성·연결은 다음 실행 통합 작업이다. Main은 의뢰·반환·재검증 판단에 필요한 부분을, 검증자는 수행 상세와 대상 원문을 읽도록 연결한다. 모델·세션·실제 도구 설정은 기존 `execution.md`를 따른다. 전역 verifier agent나 새 시스템을 먼저 설치하지 않는다.

제품의 약속은 Project common/guidance, 현재 실행·지원 사실은 Project current와 실제 코드·검사 안내, 이번 확인·한계·다음 행동은 Work가 소유한다. 반복 실행 절차가 실제로 필요한 부분만 로컬 스킬·도구에 둔다. Feature Map이라는 이름의 별도 정본에 제품 의미를 다시 쓰지 않는다.

[기존 Verify](../../../../reference-project/context/work/harness/verify/README.md)는 고정 명령 실행·snapshot·receipt를 기록하며 의미적 충분성·완료·acceptance를 결정하지 않는다. 반복 개발 확인은 직접 검사로 수행하고, 인계·상태 전환에서 지속 증거가 필요할 때만 실제 설치·호환된 Verify를 사용한다. 이 Workspace에 자동으로 연결하지 않으며 실제 결합은06의 대상별 판단을 따른다.

Main은15번 합의대로 적용 지침을 읽고 Ticket·current·records·Project의 해당 Owner를 갱신한다.04-03의 읽기·재판단·갱신 스킬은 실제 설치·호환 조건에 맞춰 연결하며 없으면 Main이 직접 수행한다. 자동 Maintain은 연결하지 않는다.04-02 explain은 설명 방법을 맡고 완료 근거 판정을 대신하지 않는다.

종료·중단 때 이후 판단에 필요한 재현과 실패·수정 후 관찰은 기존 Work records나 지속 테스트에 남긴다. 임시 환경 정리가 유일한 근거를 없애지 않게 하고, 다시 실행할 비용·재발 영향을 보고 보존 형태를 고른다. 모든 probe의 영구 테스트화나 전 로그 보존을 요구하지 않는다. Verify를 사용하지 않았어도 이 근거 연결은 필요하다.

같은 인증 작업도 남은 질문에 따라 확인 방법이 달라진다. 저장이 끝나기 전 성공을 알리는지라면 공개 진입과 저장 Promise의 시점을 통제하는 기존 검사부터 본다. 실제 저장 어댑터가 부분 실패 후 이전 값을 지키는지라면 실제 어댑터의 실패 지점·재읽기를 확인해야 한다. 여러 로그인·로그아웃 순서의 귀속 보존이 실제 요구라면 좁은 순서 재현에서 시작하고 남는 공백에 따라 생성 검사·모델 검사를 비교할 수 있다. 뒤의 두 조건은 현재 demo의 범위 밖이며 이번에 추가한 요구나 실행 결과가 아니다.

예를 들어 필요한 조회 오류 전달이 누락됐다는 가상 결함을 발견했다면, 검증자가 재현·기대 결과를 넘기고 Main이 원 구현자에게 수정을 배정한다. 수정자는 같은 재현을 사용해 고치고 자기 확인하며, 검증자는 오류 전달과 인증 보존을 다시 본다. 실제 앱의 저장·재진입에서 발견한 문제라면 작은 함수 재현의 통과 외에 그 원래 경로도 확인한다. 이 흐름은 검증 역할을 늘리기보다 같은 근거를 수정 전후에 이어 쓰는 안이다.

## 후속 논의 — 품질 개선 책임과 테스트 작성·반영을 구별한다

리뷰 후 사용자는 “약속한 반영은 뭔가 검토자와 겹쳐서 헤깔리네 틀렸다라기보다”라며 레퍼런스의 역할 구분을 물었고, 이미 합의한 개선 검토자가 코드·설계를 평가하므로 자연스럽게 구분할 수 있는지 확인했다. Main은 Lauren의 동작 검증과 코드 품질 구별, pstack 개발 담당자의 검토·검증 책임과 shipping의 별도 검증, Matt code-review의 Standards·Spec 두 축을 원문에서 다시 대조했다.

Main의 후속 추천은 **개선 선택·반영·이득 확인은 기존 구현·개선 검토·Main 흐름에 유지하고, 검증자는 최종 결과의 요구·계약 충족과 테스트·실행 근거의 충분성에 집중**하는 것이다. 검증안1·3과 리팩터링 예시를 이 방향으로 정리했다. 리뷰가 제안한 “약속한 개선 반영”을 검증자의 일반 책임으로 넓힌 부분은 이 추천으로 대체한다. 관련 사실을 발견하거나 한정된 확인을 맡는 것까지 금지하는 구분은 아니다. 아직12개 항목 전체의 사용자 합의나 실행 본문 적용이 아니다.

사용자가 “그럼 어떻게 구체화하면 좋을까? 물어볼거 있음 물어보고”라고 하자 Main은 검증자가 지속 테스트도 직접 추가·보완하는 선택을 우선 추천하며 물었다. 사용자는 “흠 고민되네 추천안도 괜찮아 보이고 레퍼는 어덯게 했어?”라고 답했다. **선택 승인이 아니라 레퍼런스 비교 요청**으로 보존한다.

- [pstack autopilot-full](../source/workflow-references/pstack/repository/skills/poteto-mode/playbooks/autopilot-full.md)은 검증 발견을 실패 테스트와 함께 Owner에게 넘기고, 브랜치의 작성자를 하나로 유지한다. 큰 PR 운영 절차이므로 구조 전체를 우리에게 적용하지는 않는다. 발견·재현과 정본 수정의 책임을 나누는 근거로 참고한다.
- [cursor-team-kit control-cli](../source/workflow-references/cursor-team-kit/repository/skills/control-cli/SKILL.md)는 필요할 때 임시 조작·재현 스크립트를 만들되, 재사용 테스트 추가 요청이 없다면 임시로 유지하도록 명시한다. 이는 CLI 검증 도구의 범위이며 모든 검증자의 테스트 편집을 금지하는 보편 규칙은 아니다.

따라서 현재 추천은 검증자가 **검사 실행·테스트 타당성 판단·실행 가능한 추가 재현/검사 작성**까지 능동적으로 맡고, 제품 코드와 지속 테스트 체계의 통합·기존 기대값 변경은 Main이 정한 수정 담당이 맡는 것이다. 검증자가 만든 코드·입력·기대값을 그대로 이어받아 같은 테스트를 새로 쓰는 왕복을 줄인다. 별도 배정으로 테스트 파일만 검증자가 담당하는 선택은 열어 두며 매번 사용자 승인을 요구하지 않는다. 테스트를 쓸 수 있는가와 저장소의 지속 테스트를 누가 변경하는가를 한 선택지로 묶었던 앞선 질문을 이렇게 구체화한다. 이 시점에는 권한 배치가 미확정이었다. 이후 사용자가 이 방향의 확정·기록을 요청했으며 현재 합의 범위는 위 「후속 확정」에 따른다.
