# 작업물 이해 브리핑

이미 존재하는 작업물이 전체에서 무슨 역할을 하고, 실제로 어떻게 연결되며, 무엇까지 확인됐는지 사용자가 다음 질문이나 지시를 만들 수 있는 형태로 설명한다. File 목록, diff 통계와 test 숫자를 다시 읽어 주는 보고가 아니다.

이 skill은 최근 code 변경, 현재 codebase의 구조와 동작, 특정 commit·시점의 역사 상태, 문서·분석·review 결과와 code 외 산출물을 모두 직접 다룬다.

## 시작

1. 실제 적용 프로젝트의 root AI 지침(예: `AGENTS.md`, `CLAUDE.md`)과 그 지침이 안내하는 관련 맥락 위치를 확인하고, 필요한 기존 문서와 공통 [`설명과 근거 기준`](../../../context/project/guidance/explanation-and-evidence-criteria.md)을 읽는다.
2. 설명 대상과 사용 목적을 잡는다. 사용자가 이미 대상·시점·질문을 밝혔다면 되묻지 않는다.
3. 답을 바꿀 때만 기준 상태를 고정한다. 현재 대상이면 branch·HEAD·working tree와 관련 runtime configuration을, 과거 대상이면 commit·날짜·artifact 생성 시점과 당시 원자료를 확인한다.
4. Local instruction과 관련 Project canonical을 읽고, 사용자의 질문에 필요한 source·entry·consumer·configuration·wiring·test만 직접 조사한다. 실제 동작이 중요하면 허용된 범위에서 trace·log·runtime observation도 확인한다.

현재성을 확인하지 못했으면 현재라고 단정하지 않고 브리핑의 효력 범위를 밝힌다.

Work의 목표·진행과 작업물의 관계를 설명할 때는 root AI 지침이 안내하는 관련 Spec·Ticket을 읽는다. Spec에서 Work가 이루려는 결과·공통 기준을, Ticket에서 맡은 결과·범위, 실행 맥락·접근, 완료 조건·확인 방법과 보고된 진행·실제 결과를 확인한다. 확인할 계획과 실제 확인한 결과를 구별한다. 질문에 필요한 항목과 Ticket을 골라 실제 코드·산출물·검증 결과에 연결하며, 전체 Spec이나 모든 Ticket을 기본 입력으로 삼지 않는다. Spec의 존재나 Ticket의 완료 표시만으로 실제 수행·검증 또는 전체 목표 충족을 인정하지 않는다. 코드 개선에서는 기존 동작이 보존됐다는 근거와 책임·중복·변경 부담이 개선됐다는 근거를 구별한다.

## 대상에 맞춰 조사한다

### 방금 또는 특정 변경

- 사용자가 정한 base가 있으면 그 기준을 사용한다.
- 기준이 없으면 current working tree, staged change와 관련 commit history를 확인해 비교 기준을 명시한다.
- Diff만 읽지 않고 변경 후 source와 실제 consumer·호출 경로를 확인한다.
- 무엇이 전후로 달라졌고 그 변화가 전체 역할·대표 흐름·상태·외부 effect에 어떤 차이를 만드는지 연결한다.

### 현재 구조와 동작

- 사용자 입력이나 대표 사건이 들어오는 entry point에서 결과·외부 effect까지 따라간다.
- 각 component의 책임, 경계, 호출·소비 관계와 정확한 file·symbol·사용 위치를 연결한다.
- Interface나 type의 존재와 실제 runtime provider·configuration·wiring을 같은 상태로 취급하지 않는다.

### 과거 코드나 작업물

- 당시 commit, 보존 문서, 대화·review·artifact 가운데 질문에 필요한 원자료에 시점을 고정한다.
- 당시 보고, source로 확인한 사실과 현재의 해석을 구분한다.
- 과거 상태를 현재 working tree에도 그대로 유효하다고 확대하지 않는다.

### 문서·분석·review 결과

- 어떤 질문과 기준을 대상으로 만든 산출물인지 확인한다. 이전 문제에 대한 후속 결과라면 당시 문제, 그 뒤의 수정과 이번 확인의 관계를 함께 조사한다.
- 직접 확인한 finding과 작성자의 해석, 아직 확인하지 않은 범위와 후속 판단을 구분한다. 문서가 가리키는 live code·test·configuration이 답을 바꾸면 현재 Owner까지 내려가 대조한다.
- 중요한 미확정 가운데 허용된 범위에서 확인할 수 있는 것은 더 조사한다. 확인하지 못하면 이유와 그 때문에 제한되는 결론을 밝힌다. 설명 요청만으로 새 제품 작업이나 전체 review를 시작하지 않는다.
- 원래 질문에 답하고, 이번 결과가 무엇을 유지·변경·보류할 판단으로 이어지는지 설명한다. 조사한 항목을 나열하는 것으로 대신하지 않는다.

## 실제 결과

결론과 작업물의 전체 역할을 먼저 보여 준다. 코드 구조·변경을 설명할 때는 전체를 이해할 핵심 구분과 중요한 코드의 근본 역할을 먼저 잡는다. 그 코드가 전체에서 무엇을 맡고 왜 필요한지 설명한 뒤 실제 동작으로 잇는다. 객체·함수 같은 구현 형태나 메서드의 동작 목록만으로 역할 설명을 대신하지 않는다. 이미 공유한 역할을 반복하거나 모든 파일의 책임 표를 먼저 만들지는 않는다.

역할과 연결을 이해하는 데 필요한 실제 코드 부분을 골라 조건·값·호출이 어떤 책임을 구현하는지 보여 준다. 화면·로직의 흐름을 묻는다면 대표 장면에서 그 코드들이 어떻게 연결되는지 함께 설명한다. 구체적 코드나 도식을 요청했다면 추상 설명·역할 표만으로 대신하지 않는다.

중요한 이름은 처음 쓰는 자리에서 사용자가 하려는 일, 실제 데이터나 책임에 연결하고, 기존 file·symbol과 정확한 위치를 남긴다. 중요한 주장에는 확인한 근거를 가까이 두며 필요한 상세를 펼친다. 내용의 연결을 유지하면서 독립적으로 찾아야 할 주제·조건은 문단·표·목록 등으로 구분한다.

추상적인 설명만으로 동작이나 근거 한계의 의미를 놓치기 쉬우면, 대표 입력·사용 장면의 입력·중간 값·결과 중 필요한 값을 연결해 무엇이 왜 달라지는지 보여 준다. 실제 확인한 값을 쓰거나 설명용 값임을 밝히며, source에서 재구성한 동작·관찰한 실행·아직 제안한 동작의 지위를 유지한다. 대표 흐름만으로 결과를 오해하기 쉬울 때는 결과가 달라지는 중요한 조건을 함께 비교한다. 모든 브리핑에 사례를 추가하거나 모든 실패 경로를 펼치지는 않는다.

다음 변경·선택을 위한 브리핑이거나 기존 선택의 이유·복잡성·적절성을 묻는 질문이면, 실제 변경 사실과 확인 가능한 당시 이유, 현재 조건에서의 판단을 구별해 답한다. 질문에 필요한 기존 계약·소비자·대안·비용을 대조해 무엇을 유지하거나 바꿀지 추천한다. 당시 이유는 보존된 근거로 확인할 수 있을 때만 말하고 현재 해석과 구분한다. 역할을 설명할 수 있다는 이유로 현재 구조를 정당화하지 않는다.

질문만으로 수정·복원을 약속하지 않는다. 명시된 변경 요청이나 기존 실행 권한이 있으면 그 범위에 따라 이어간다. 모든 구조의 장단점·선택 이력을 기본 조사하거나 일반 동작 설명을 전체 architecture review로 확대하지 않는다.

직접 호출에서는 `작업물 이해 브리핑 — <대상>` 제목을 기본으로 쓰고, 자연어 상황에서 자동 선택된 짧은 답에는 제목을 생략할 수 있다. 고정 목차나 줄 수 제한은 없다. 질문에 필요한 관계와 조건에 맞춰 구성한다.

### 관계를 구조로 보여 줄 때

결론과 전체 역할을 말한 뒤, 사용자가 도식을 요청했거나 관계·분기·상태 변화를 구조로 보는 것이 이해에 도움이 되면 현재 질문에 필요한 가장 작은 부분 구조를 보여 준다. 실행·상태 변화에는 flow, 책임·소유·의존에는 tree나 map, 전후 차이나 정확한 대응에는 delta 표현이나 table을 고려할 수 있지만 고정 mapping은 아니다. 별도 도식 요청이 없고 문장이나 짧은 목록이 더 명확하면 구조를 만들지 않는다.

- 한 구조에는 실행 순서, dependency, 역사, 근거 강도 가운데 현재 질문의 중심 관계 하나를 우선한다.
- Node뿐 아니라 화살표·묶음·방향도 호출·시간·데이터 이동·소유·의존에 관한 주장으로 본다. 현재 질문의 source·configuration·runtime observation·당시 artifact·design·review evidence가 뒷받침하는 관계만 표시하고, AI가 설명을 위해 도출한 grouping은 설명용임을 밝히며 확인된 구조처럼 제시하지 않는다.
- 관계가 무엇으로 확인됐는지 또는 AI가 도출한 것인지, 경로가 기본·opt-in·disabled·stub 중 어떤 활성·완성 상태인지가 결론을 바꿀 때만 각각 구분한다. 미확인은 근거 한계로 둔다.
- Source·configuration만으로 재구성한 흐름은 그 범위와 live trace가 아니라는 점을 항상 밝힌다. `관찰된 실제 실행`은 trace·log·runtime observation이 있을 때만 사용하고, 서로 다른 근거가 한 흐름에 섞이면 edge나 구간별로 구분한다.
- 대표 경로나 질문 관련 부분만 보였다면 전체 architecture처럼 보이지 않게 생략 범위를 밝힌다. 중요한 부분은 exact source·사용 위치와 필요한 실행 근거로 내려간다.

## 근거와 판정 경계

- 설계 의도, current source, runtime observation, test·compiler·rule과 AI 해석이 답하는 질문을 섞지 않는다. Stub·mock·hard-coded·미연결·미구현·미확인이 결론을 제한하면 그 상태와 영향을 드러낸다.
- 직접 확인한 불일치와 그 때문에 제한되는 설명 범위는 숨기지 않는다.
- 변경의 영향을 설명하기 위해 필요한 source·history·test를 이 skill 안에서 더 조사한다.
- 요구 위반, 위험 수용과 최종 acceptance를 설명 속에 몰래 확정하지 않는다. 사용자가 그 판정까지 요청했다면 확인 근거와 열린 선택을 보여 주고 판정 책임을 명시한다.

## 끝낼 때

대상의 역할, 실제 변경이나 연결, 중요한 근거 한계와 미확정이 다른 skill 없이 따라갈 수 있게 보이면 현재 브리핑을 끝낸다. 온전한 설명을 위해 모든 file·symbol을 나열하거나 history·configuration·test를 매번 전부 조사할 필요는 없다. 추가 세부는 현재 질문에 필요하거나 사용자가 요청한 부분부터 펼친다. 기준 source·runtime·artifact가 바뀌면 결론도 달라질 수 있을 때만 재확인 조건을 남긴다.

이 skill의 기본 행동은 read-only 조사와 설명이다. 설명 요청만으로 code, 문서, review 결과나 Workspace 상태를 직접 수정하는 작업으로 확대하지 않는다.

설명 중 확인한 차이·정정과 근거 한계는 Main의 최종 응답에 드러낸다. 서브로 설명을 수행했다면 그 내용을 Main에게 반환한다. Spec·Ticket과 관련 Workspace 문서 갱신은 root AI 지침이 안내하는 상위 운영 계약에 따라 Maintain에 맡겨 중복 수정을 피하고, 다음 실행이 문서에 의존할 때 필요한 실제 반영을 확인한다. 설명을 제공한 사실만으로 새 요구나 작업 완료를 확정하지 않는다.
```

# 설명 복구본

어려운 응답을 짧거나 쉬운 말로 바꾸는 데서 멈추지 않는다. 사용자가 어디서 이해의 연결을 잃었는지 찾아, 이미 공유한 맥락에서 원래 뜻까지 다시 이어 준다. 뜻을 묻는 것과 주장에 이의를 제기하는 것을 구별하고, 한 질문에 둘 다 있으면 함께 답한다. 작업 중·작업 후 대화뿐 아니라 일반 대화의 AI 응답에도 사용할 수 있다.

## 시작

1. 사용자가 가리킨 실제 응답과 바로 앞의 필요한 대화를 확인한다. 막힌 문장이 명확하면 같은 질문을 다시 시키지 않는다.
2. 대화만으로 뜻을 복구할 수 있으면 repository나 긴 reference를 먼저 읽지 않고 바로 답한다.
3. Project 사실·근거 범위·오래된 용어의 현재성이 설명의 뜻을 바꿀 때만 실제 적용 프로젝트의 root AI 지침(예: `AGENTS.md`, `CLAUDE.md`)과 그 지침이 안내하는 관련 맥락 위치를 찾아 필요한 canonical·source와 공통 [`설명과 근거 기준`](../../../context/project/guidance/explanation-and-evidence-criteria.md)을 확인한다.

복구 대상은 **그 단어가 일반적으로 가질 수 있는 뜻이나 codebase 안의 같은 이름이 아니라, 사용자가 가리킨 실제 응답에서의 뜻**이다. 앞선 응답이 code component를 가리키지 않았다면 같은 이름의 symbol을 찾아 그 뜻으로 바꾸지 않는다. 필요한 앞선 문장이 현재 context에 없고 가능한 뜻에 따라 답이 달라지면, 어느 문장을 가리키는지 한 번만 묻거나 가장 가능성 높은 해석임을 명시한다.

Work에 관한 말의 범위나 근거를 확인해야 한다면 root AI 지침이 안내하는 관련 Spec·Ticket을 읽는다. Spec의 목표·범위·기준과 Ticket에 정의된 실행·보고된 진행을 질문에 필요한 만큼 확인하며, 모든 Spec·Ticket을 기본 입력으로 삼지 않는다. 현재 문서의 내용으로 과거 발화의 원래 뜻을 바꾸지 않는다. “완료됐다”는 말이 문제라면 기록된 완료 범위와 실제 산출물·검증으로 확인한 범위, Spec의 전체 목표를 구별해 설명한다.

## 무엇이 끊겼는지 찾는다

실제 발화에서 사용자가 이해했다고 밝힌 부분과 아직 묻는 부분을 구별하고, 다음 목록에서 끊긴 연결의 후보를 찾는다. 추가 질문만으로 앞선 설명의 실패나 사용자의 혼동 원인을 확정하지 않는다. 앞선 AI의 자기해석도 사용자 발화와 대조하며, 불확실한 원인을 확인된 사실처럼 말하지 않는다.

- 처음 나온 용어의 뜻과 실제 가리키는 대상이 빠졌다.
- `이것`, `그 결과`, `현재 상태`처럼 지시 대상이 불분명하다.
- 전제나 중간 인과를 생략해 결론이 갑자기 나왔다.
- 여러 의미를 한 문장에 과도하게 압축했다.
- 확인한 사실, AI 해석, 추천과 사람의 판단이 섞였다.
- 표현이 아니라 답을 만들 사실 자체가 부족하다.
- 사실은 충분하지만 앞선 주장에 모순이나 잘못된 추론이 있다.

막힘 후보가 여러 개라 복구 방향이 실제로 달라질 때만 짧은 질문 하나를 한다. 그 외에는 가장 가까운 끊김을 잡고 바로 답한다.

## 작은 복구에서 시작한다

1. 사용자가 묻는 말의 직접 답을 먼저 준다.
2. 그 답만으로 연결이 복구되지 않으면 마지막 공유 지점에서 빠진 전제나 중간 이유까지 잇는다.
3. 사용자가 이미 이해한 표현과 현재 유효한 Project 용어에서 시작하고, 아직 묻는 차이에 다음 답의 범위를 맞춘다. 같은 표현으로 연결되지 않으면 실제 코드·값·대상 간 대응이나 필요한 사례로 표현을 바꾼다. 앞선 답에서 이미 바꾼 설명과 새로 드러난 질문도 확인한다. 친숙하더라도 현재 사실과 충돌하는 용어는 그대로 반복하지 않는다.
4. 새 용어는 동의어만 붙이지 말고 실제 대상·역할·현재 대화에서의 의미를 함께 설명한다. 새 비유·분류 체계·더 많은 이름으로 막힘을 덮지 않는다.
5. 사실·AI 해석·미확정·사람 판단을 섞어 더 강한 결론으로 오해할 때만 그 차이를 드러낸다.
6. 사실 부족이나 의심되는 사실 오류가 현재 답을 바꿀 수 있을 때만, 대화로 확인할 수 없는 부분을 관련 source에서 조사하고 확인한 범위와 미확인을 말한다.

원래 뜻을 복원하는 일과 그 주장이 현재도 타당하다고 인정하는 일을 구별한다. 읽은 대화나 근거에서 실제 오류·모순·잘못된 추론이 보이면 문제가 된 주장이나 연결을 구체적으로 짚고, 무엇을 유지·정정·철회하거나 아직 판단하지 못하는지 밝힌다. 재설명하면서 결론이나 제안의 의미가 달라지면 그 차이를 드러내고, 바뀐 뜻을 원래부터 했던 말처럼 쓰지 않는다. 원인은 확인한 발화·사실·추론에서 설명하며 AI의 숨은 의도를 만들어내지 않는다.

직접 답, 끊겼던 연결과 결론을 바꾸는 조건이 보이면 더 넓은 배경까지 펼치지 않는다. 짧게 설명하려고 원뜻의 조건과 한계를 빼지 않는다. 사용자가 전체 흐름·영향이나 더 깊은 이유를 요청하거나 생략된 전제가 여러 단계일 때만 범위를 넓힌다.

실제 응답에서는 `설명 복구본` 제목을 생략할 수 있다. 고정 목차보다 끊긴 연결을 자연스럽게 잇는 것이 우선이다. 독립적으로 비교해야 할 대상·조건은 문단·표·목록·코드 등으로 구분하되, 짧은 답을 전체 브리핑 형식으로 늘리지 않는다.

## 끝낼 때

원래 응답의 직접 뜻과 가장 가까운 누락, 결론을 바꿀 조건이 있다면 그 조건까지 답했으면 현재 복구를 끝낸다. 이의 제기나 정정이 있었다면 그에 대한 답과 유지·정정·유보한 부분도 보여야 한다. 제목, 전체 근거 분류, repository 조사, 이해 확인 질문을 기본으로 붙이지 않는다. 사용자의 내부 이해를 추측해 완료 판정으로 저장하지 않는다.

Quiz, 자기 말로 다시 말하기나 형식적 승인을 기본 종료 조건으로 요구하지 않는다. 사용자가 질문식 학습을 요청하면 그 방식으로 돕되, 이후 직접 설명·코드·다른 방식으로 전환하라는 요청을 따른다.

설명에 필요한 정정을 과거 전체 감사·구현·문서 수정·작업 범위 재합의로 자동 확대하지 않는다. 별도의 변경 요청이나 기존 실행 권한이 있으면 그 범위에 따라 이어간다.

Spec·Ticket과 관련 Workspace 문서에 반영할 차이·정정이 확인됐다면, Main은 확인한 내용·근거·미확인을 최종 응답에 드러낸다. 서브로 설명을 수행했다면 그 내용을 Main에게 반환한다. 문서 갱신은 root AI 지침이 안내하는 상위 운영 계약에 따라 Maintain에 맡겨 중복 수정을 피하고, 다음 실행이 문서에 의존할 때 필요한 실제 반영을 확인한다. 설명을 복구한 사실만으로 새 요구나 작업 완료를 확정하지 않는다.
```

## 확인 범위와 다음 판단

기준판과 문단별로 대조해 기존 호출 범위·대상별 조사·근거·권한·종료·기록 연결을 보존하고 중복 목록을 통합했다. 실제 운영 파일과 읽기 전용 source는 변경하지 않았다. 별도 실행 비교나 사용자 이해 개선 효과는 확인하지 않았으며, 이번 전체 문구의 채택·수정과 실제 적용은 다음 판단으로 남는다.

## 프로토타입 파일 배치

사용자 요청으로 [development-workflow의 skills](prototypes/development-workflow/skills/README.md)에 두 SKILL.md와 필요한 공통 설명 기준을 배치했다. 두 스킬은 위 통합안과 본문 의미가 같고 공통 기준 링크만 새 배치에 맞췄다. 공통 기준은 Noline 기준판에서 가져와 내용은 보존하고 안내 링크만 이 폴더의 consumer 안내로 연결했다. 프로토타입에 수정안을 만든 것이며 실제 제품·전역 스킬 설치나 효과 확인은 아니다. 상세 변경점은 해당 안내의 기존판·수정안 비교표에서 확인한다.

배치 확인: 두 파일이 제시한 전체 초안과 공통 기준 링크 외에는 동일함을 대조했고 두 스킬의 형식 검사를 통과했다. 프로토타입 열람 화면을 재생성하고 원문·링크·앵커 검사를 통과했다. 브라우저 실측이나 스킬 행동 효과 검증은 하지 않았다.
