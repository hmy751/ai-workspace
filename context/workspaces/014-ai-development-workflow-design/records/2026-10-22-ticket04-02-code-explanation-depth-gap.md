# 코드와 함께 설명하지 않은 결과 — 기존판·통합 후보 문구 대조

사용자는6.0 luna·sol에서도 수정판이 코드와 함께 자세히 설명하지 않은 이유를 기존 스킬과 대조하되, 바로 고치지 말고 부족한 지점을 먼저 보여 달라고 요청했다. 이번 작업은 문구·출력·형성 의도 대조이며 새 스킬 수정이나 응답 시험은 하지 않는다.

**주된 문구 공백은 역할·흐름을 설명하는 것과 사용자가 코드를 직접 따라 읽도록 돕는 것을 충분히 구별하지 못한 점이다.** 코드·값을 설명하라는 요구가 전혀 없는 것은 아니다. 이미 있는 요구가 이번 출력에 충분히 반영되지 않은 사실과, 그 적용 판단을 구체화하지 못한 문구를 구별한다. 모델 내부의 정확한 실패 원인을 이번 결과만으로 확정하지 않는다.

## 대조한 판본과 근거

시험 입력에 실제 사용한 [기존판](experiments/artifact-explanation-auth-body-2026-10-22/r31/input/skill/SKILL.md), [통합 후보](experiments/artifact-explanation-auth-body-2026-10-22/r74/input/skill/SKILL.md), [공통 설명 기준](experiments/artifact-explanation-auth-body-2026-10-22/r31/input/shared/explanation-and-evidence-criteria.md)을 기준으로 삼았다. 별도의 보류 prototype 본문과 혼동하지 않는다.

인증 원문은9의 문법 질문,13의 답,20의 코드 전체와 “여기 동작좀 설명해줄래? 코드 동작이 어려우서”다.55의 “코드랑 같이 자세히 설명해야지 맥락만 알려주는게 아니라”와73의 후속 질문은 사후 평가 근거이며 생성자에게 전달하지 않았다.6.0 sol의 [기존판](experiments/artifact-explanation-auth-sol6-body-2026-10-22/r36/output/response.md)과 [수정판](experiments/artifact-explanation-auth-sol6-body-2026-10-22/r91/output/response.md)은 코드 블록 없이 주요 동작을 요약했다. 앞선6.1-sol은 같은 입력으로 자세히 설명했으므로 본문이 상세 설명을 금지하거나 원천적으로 불가능하게 만든다고 해석하지 않는다.

## 부족한 지점

### 1. 설명 목적을 잡지만, 코드 읽기의 어려움을 설명 깊이로 연결하는 판단은 약하다

- 기존15: “설명 대상과 사용 목적을 잡는다.”
- 후보16: “설명할 대상·시점과 사용자가 이해하려는 내용을 확인한다.”

상위 목적은 타당하다. 하지만 시스템의 역할·연결을 알고 싶은 요청과 특정 코드의 표현·분기·대기를 따라 읽고 싶은 요청에 대해 무엇이 달라져야 하는지는 구체화하지 않았다. 이번 입력에는 문법 질문과 코드 전체, 동작이 어렵다는 발화가 함께 있었다. 이를 상세 설명의 신호로 해석할 근거가 있었지만 두6.0 출력은 일반 흐름 소개 수준으로 마쳤다. “자세히”라는 명시적 교정이 있어야만 상세 설명이 허용된다는 규칙은 없다.

### 2. 조사한 코드와 응답에서 읽을 코드를 구별하지 못한다

- 기존35·후보44: component의 책임·경계·호출·소비 관계를 정확한file·symbol·사용 위치와 연결한다.
- 후보88: “실제 코드가 필요한 설명에는 관련 코드와 그 의미를 함께 둔다.”

후보에는 실제 코드 제시 요구가 추가되어 있다. 이를 없는 요구로 취급해 다시 덧붙이면 중복이다. 다만 “실제 코드가 필요한” 조건을 판단하는 근거와 “함께 둔다”의 수행 깊이가 분명하지 않다. 이 문장은 형식 선택 절에 있어 목록·표·짧은 문단의 선택과 같은 수준으로 읽힐 여지도 있다. 이것이 모델의 실제 선택 원인이었다는 증거는 없다.

수정판 출력은파일·줄 위치를 반복해 근거 연결을 수행했지만, renewSession의 실제 분기나 반환을 코드와 대조하며 읽게 하지는 않았다. 위치를 제시해 주장을 검증 가능하게 하는 책임과, 그 자리의 코드를 사용자가 읽도록 설명하는 책임은 다르다. 코드 블록 개수를 요구할 문제가 아니라 현재 질문에 필요한 코드·값·의미의 대응이 빠진 문제다.

### 3. 값과 조건 설명은 이미 있으나, 충분성 판단에 맡겨져 있다

- 기존54: “추상적인 설명만으로 동작이나 근거 한계의 의미를 놓치기 쉬우면” 입력·중간 값·결과와 중요한 조건을 연결한다.
- 후보71~75: “추상 설명만으로 차이가 드러나지 않을 때” 대표 장면의 입력·중간 값·결과를 연결하고 중요한 조건의 결과 차이를 비교한다.

값·조건을 추가하라는 요구 자체는 기존판에도 있었다. 이번 수정판의 “요청A와B가 같은 갱신을 기다린다”는 사례는 기존Promise를 가져오고 반환하는 실제 분기, 호출자가await하는 위치, 완료·실패가 어떻게 이어지는지까지 연결하지 않았다. 또한 세션 변경의 일반 이유는 설명하지만 refresh 실패catch 안에서 왜 먼저 검사해야 하는지의 경로는 펼치지 않았다.

모델이 일반 원리를 말한 것으로 충분하다고 판단하면 이 조건부 보강을 건너뛸 수 있는 구조다. 모든 값·실패 분기를 의무화할 근거는 없으며, 이미 있는 값 연결 요구의 적용 여부와 충분성을 현재 질문에 맞춰 판단하는 부분이 약하다는 분석이다.

### 4. 종료 기준이 역할·연결 소개만으로도 충족되기 쉽다

- 기존89: “대상의 역할, 실제 변경이나 연결, 중요한 근거 한계와 미확정이 보이면 현재 브리핑을 끝낸다.”
- 후보115: “현재 질문에 답했고” 역할·연결·근거 한계가 드러나면 끝낸다.
- 후보119: 구조와 동작 이해는 “그 역할과 연결을 이해하는 데 필요한 답으로 마친다.”

후보의 질문 충족 조건은 옳지만 실제로 무엇을 확인하면 질문에 답한 것인지는 추상적이다. 이번 응답에는 역할·대표 흐름·근거 한계가 모두 있어, 이 항목들만 보면 종료할 수 있다. 코드를 읽기 어렵다는 질문에서는 중요한 분기와 값의 흐름을 사용자가 본 코드에 대응해 볼 수 있게 설명했는지가 별도로 남는다. 사용자 이해를 AI가 확정하거나 퀴즈를 요구하자는 뜻은 아니다.

## 구체적으로 남은 설명의 간극

수정판은 “둘은 같은 갱신을 기다리고, 완료되면 Map 항목을 지웁니다”라고 설명한다. 역할 요약으로는 맞다. 다만 다음 코드와 연결이 드러나지 않는다.

```ts
const existing = refreshes.get(sessionId);
if (existing) {
  return existing;
}
```

여기서 existing은 진행 중 Promise이고, 그것을 return하므로 다음 호출도 같은 완료를 기다리며, 호출부의 await renewSession에서 진행이 멈춘다는 대응을 응답에서 따라 읽게 하지 않았다. “같은 Promise 공유”라는 이름을 알려 준 것과 코드를 읽는 방법을 설명한 것을 구별할 필요가 있다. 이 부분은 새 수정안이나 정답 응답이 아니라 기존 출력과 원 코드의 간극을 특정하는 예다.

## 유지할 요구와 성급히 원인으로 삼지 않을 것

- 역할을 먼저 설명하고 대표 흐름에서 세부로 내려가는 기준은 유지할 가치가 있다. 곧바로 모든 줄을 해설하는 방식으로 바꿀 근거는 없다.
- 실제 코드·값·조건·근거 한계 요구는 이미 있다. 이들을 새 요구처럼 중복 추가하지 않는다.
- 모든symbol·분기·history를 조사하지 않는 제한은 과잉 조사를 막는 기준이다. 현재 질문에 필요한 핵심 코드를 생략하라는 뜻으로 읽지 않는다.
- 공통 기준은 “목표는 설명을 무조건 짧게 만드는 것이 아니다”라고 명시한다. 후보도 분량을 줄이기 위해 중요한 전제·값·한계를 삭제하지 말라고 한다. 짧게 답하라는 명시 규칙 때문에 실패했다고 단정할 수 없다.
- 현재 공통 상위 지침·모델의 응답 성향·단일 표본 변동 영향은 배제하지 못한다. 이번 대조는 문구의 약한 연결과 실제 미수행을 지적하며 인과를 확정하지 않는다.

## 이번 후보가 바꾼 범위와 판단

후보의 실질 보강은 문서·분석 결과를 질문·이전 문제와 연결하는 부분, 목적별 종료, 읽기 쉬운 형식에 집중했다. “현재 구조와 동작”의 조사 항목은 기존판과 거의 같고, 코드 읽기의 깊이를 보완하는 부분은 형식 절의 조건부 한 문장 정도다. 따라서 인증 코드의 세부 해설에서 큰 차이가 생길 것이라고 기대할 근거는 약했다. 이것은 보고서 결과 연결 보강까지 무효라는 판단이 아니다.

보완이 필요하다면 검토할 위치는 시작의 목적 판별, 실제 코드와 의미를 함께 두는 조건, 값·분기를 펼칠 충분성 판단, 목적별 종료의 연결이다. 현 단계에서는 수정 문구를 작성하거나 판본을 교체하지 않았다. 실행 요구가 이미 있는데 지켜지지 않은 부분을 구별하면서 최소 변경 여부를 판단해야 한다.
