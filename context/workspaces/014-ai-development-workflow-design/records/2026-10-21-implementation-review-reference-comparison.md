# 구현과 검토·수정 단계의 자료 비교

**후속 설명 반영:** 아래는 사용자의 러프한 구상과 답변을 듣기 전 Main의 비교·권고다. 현재 논의는 [동적 맥락 선택과 별도 관점 검토의 의도](2026-10-21-dynamic-context-and-review-intent.md)에서 이어간다. Personal을 구현의 바탕으로 삼고 별도 역할의 검토 결과를 Main이 비교·판단하는 관계를 우선 구체화하며, 아래의 같은 기준 전달·검토자 선행 수정안을 그대로 확정하지 않는다. 자료별 사실 비교는 참고 근거로 유지한다.

2026-10-21. 수집 커밋 `232200d`의 Matt·pstack 원문과 기존 Vercel 글을 현재 [DEVELOPMENT](prototypes/development-workflow/noline-demo/context/work/DEVELOPMENT.md)에 대조했다. **구현은 목표·구조·동작의 첫 완성을 맡고, 검토 및 수정은 원요구와 실제 결과를 다시 대조해 부족한 부분을 직접 고치는 두 단계**를 권고한다. 아래는 논의를 위한 제안이다. B의 검토자 직접 수정 방향은 기존 선택이며, 이번 상세 책임·종료·스킬 배치를 새로 채택한 것은 아니다.

## 이번 질문과 기존 출발점

사용자 요청:

> 그래 그럼 모은 자료들 보면서 구현이랑 검토 및 수정 단계를 어떻게 가져갈지 비교해보자 각 자료에서 참고할 부분이랑 우리 워크플로에 어떻게 연결하면 좋을지 일단 생각해봐

[B 선택15](2026-10-12-15-reviewer-editing-choice-and-start.md)는 실행할 작업이 충분히 정의된 뒤 구현자가 인수하고, 검토자가 필요한 품질 수정을 직접 수행하는 방향이다. [우선순위28](2026-10-13-28-execution-system-priority-and-code-criteria.md)은 결정된 작업을 좋은 코드와 확인 가능한 결과로 만드는 작업 단계의 시스템을 먼저 다루도록 한다. 구현 중 필요한 조사·설계도 이 범위에 포함된다.

현재 DEVELOPMENT에는 Personal·Project·Work 입력 선택, 계약 충돌의 반환, B의 직접 수정, Main의 통합, 결과를 해당 내용 책임에 돌리는 절차가 있다. 이번 비교가 보탤 것은 **각 단계에서 실제로 할 일, 인수할 변경과 근거, 수정 뒤 확인, 충분히 마친 상태의 판단**이다.

## 권고하는 두 단계

### 구현: 목표와 기준을 실제 변경으로 완성한다

인수할 것은 이번에 얻을 결과, 보존할 동작·제약, 현재 코드와 관련 맥락, 기존 선택과 아직 열린 설계다. 구조 개선이 목적이면 ‘동작을 유지한다’와 함께 어떤 이해·변경 부담을 줄일지도 이어받는다. 별도 표를 항상 작성하기보다 기존 Ticket·대화·문서에서 이 내용이 충분한지 판단한다.

구현자는 원자료와 호출부를 읽고 필요한 내부 설계를 구체화한다. Main이 고른 자료는 출발점이며, 작업 중 새 주제가 드러나면 구현자가 해당 본문·근거를 더 찾는다. 특정 기준의 예시 모양을 정답으로 복사하지 않고 이번 목적·사용처·비용에 대입한다. 일반 사용에는 기준 본문을 읽고, 기준의 의미를 바꾸거나 형성 이유를 재판단할 때 가까운 형성 자료를 선택한다.

작게 구현하고 확인하는 Matt의 방식을 기본 참고로 삼는다. 버그는 가능한 재현에서 시작하고, 구조 개선은 지킬 동작을 먼저 확인하며, 기능은 실제 이용 경로에서 관찰할 결과를 잡는다. 테스트 순서·도구는 작업에 맞춰 고른다. 제품의 결과와 구조 개선을 함께 충족하려는 첫 완성을 구현자에게 요구하는 편이 좋다. 구현자가 이미 확인한 범위 안 결함을 검토자에게 떠넘기는 것을 정상 인계로 만들 이유는 없다. 외부 접근 부재처럼 해소하지 못한 확인은 한계와 영향을 밝힌다.

검토에 넘길 때에는 원요구와 실제 변경 대상, 선택을 가른 이유, 수행한 확인과 남은 미확인을 연결한다. 검토할 기준점·현재 파일 상태·미커밋 변경 포함 여부를 식별하고 동일 부분의 수정 담당을 넘긴다. 모든 작업에서 새 인계 파일이나 커밋을 요구하는 안은 아니다.

### 검토 및 수정: 원요구에서 다시 판단하고 수정 결과까지 확인한다

검토자는 구현 결과를 인수해 다음을 함께 판단한다.

| 판단 | 확인할 내용 |
| --- | --- |
| 이번 목표와 계약을 충족했는가 | 요구 누락·부분 충족·새로 생긴 동작, 보존할 결과와 현재 코드·실행의 관계 |
| 이 코드의 구조와 표현이 적절한가 | 책임·이름·상태·호출 관계, 호출자가 알아야 하는 사실, 함께 바뀌는 위치와 실제 읽는 부담 |
| 확인 근거가 해당 결과를 뒷받침하는가 | 어떤 경로·상태를 실제 관찰했는지, 테스트의 기대값과 대체 의존성, 검사로 확인하지 못한 것 |

검토자는 구현자의 설명을 참고하면서 원요구·정본·현재 변경과 직접 대조한다. 관련 호출부나 원문을 더 볼 수 있어야 한다. Main이 결함의 이름이나 기대 결론을 미리 지정해 검토의 판단을 대신하지 않는다. 큰 변경에서 관점을 나눠 검토할 수 있지만 같은 코드에 대한 수정은 한 담당자가 통합한다.

범위 안의 결함·이름·중복·구조 문제는 검토자가 근거를 판단해 직접 고친다. 구조 개선의 허용 범위를 수정 줄 수나 파일 수로만 제한하지 않는다. 이번 목표와 보존 계약에 필요한 변경인지, 이득이 비용에 비해 타당한지가 기준이다. 반면 사용자의 목표·제품 결과·합의된 범위를 바꾸는 선택은 Main에게 근거와 대안을 돌린다. Main이 위임된 범위에서 판단하고 새로운 사람의 선택이 필요한 부분을 사용자와 논의한다.

수정 후에는 수정자가 영향받은 확인을 다시 수행한다. 버그는 원래 재현, 구조 개선은 동작 보존과 구조 목표, 기능은 달라진 사용자 결과를 확인한다. 구현자의 수정 전 통과를 최종 코드의 통과로 재사용하지 않는다. 중요한 발견은 어느 요구·기준과 어긋났고 무엇을 고쳤으며 어떤 근거로 마쳤는지 연결해 반환한다.

종료는 원래 목표와 범위 안의 중요한 문제를 처리하고, 최종 변경에 필요한 확인과 남은 한계를 설명할 수 있는 상태로 잡는 편이 좋다. 검토를 반복해 지적 수를 0으로 만드는 것을 목적에 두지 않는다. 선택적인 개선 후보는 효과·비용과 함께 남길 수 있다. Main은 목표·결과·검토 후 확인을 종합해 완료·부분 완료·남은 판단을 결정한다.

## 확인 책임과 실행 환경

두 단계 모두 자신의 변경을 확인하고, 검토·수정 담당자가 최종 변경에 필요한 확인을 이어서 맡는 안을 우선 추천한다. Main은 반환된 주장과 직접 근거를 대조한다. 이를 수정과 독립된 검증이라고 부르지 않는다.

별도 검증자를 항상 세 번째 단계로 붙일지는 현재 근거로 정하지 않는다. 예를 들어 검토자의 수정으로 원래 검사하지 않았던 제품 동작이 바뀌거나, 같은 설계 가정을 구현·검토·테스트가 공유하는 중요한 공백이 드러나면 그 계약과 근거를 다른 관점에서 확인하게 할 수 있다. 우선 부족한 관찰·검사를 구체화해야 하며, 실행 환경이 없는데 agent 수만 늘려도 실제 검증은 생기지 않는다. 이 조건과 비용은01-03에서 대표 사례로 더 대조한다.

pstack이 보태는 중요한 부분은 **실제로 확인할 수 있는 프로젝트 환경**이다. 실행 전제, 시작·준비 상태, 사용자 경로의 조작 방법, 관찰할 결과, 정리를 다음 담당자가 재현할 수 있어야 한다. 기존 검사·도구·프로젝트 가이드를 먼저 사용하고 반복해서 필요한 경로를 유지한다. 검증 skill을 작성했다는 사실과 실제 실행 성공을 구별한다.

## 기존 사례에서 펼쳐 볼 차이

[DB·인증 사례 분석](2026-10-20-ticket04-01-db-auth-comparison.md)에서는 준비 완료의 의미를 여러 곳에서 따로 해석하는 부담을 이미 알고 있었지만, 첫 결과가 실패 동작과 테스트 중심으로 마무리됐다. 후속에서는 중복을 줄인 실제 개선이 있었고, ‘Root 한곳’이라는 방법만으로 구조가 충분하다고 본 판단은 다시 교정됐다.

이 사례에 제안을 적용한다면 구현자는 DB·인증 실패 동작을 보존·개선하는 것과 함께, 완료 판단·재시도·후속 작업의 책임을 실제 코드에 연결해 첫 결과를 만든다. 검토자는 테스트 통과를 확인한 뒤에도 그 관계가 호출자에게 일관되게 드러나는지 대조하고, 범위 안 구조·표현을 직접 개선한다. 수정한 결과에서는 원래 동작과 구조 목표를 다시 확인한다. application 분리나 특정 폴더 구성을 정답으로 미리 주지 않는다.

이는 당시 실패를 재현하거나 개선 효과를 입증한 실행이 아닌 **다음 논의를 위한 적용 가정**이다. 당시 선택·판본·보존 자료의 한계는 원 분석에 남아 있다. 다음에는 이 사례에서 구현자가 완성해 넘길 결과와 검토자가 추가로 판단·수정할 일을 나란히 펼쳐, 두 단계의 품질 책임과 인계가 충분한지 비교하는 것이 유용하다.
