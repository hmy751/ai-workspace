직접 대조한 원문은 보존된 [Noline 코드 표현 가이드](../source/supplement/worktree-project-context/context/project/guidance/code-readability.md)와 [리팩터링 가이드](../source/supplement/worktree-project-context/context/project/guidance/behavior-preserving-refactoring.md), [78의 범위 비교](2026-10-18-78-code-guides-comparison-and-applicability.md), 현재 Personal의 공통·공통화·계약/수명·이름/완료 본문과 형성 자료다.78에는 사용자가 중괄호를 제품과 무관한 기준의 예로 든 직접 발화가 있다. 보존 가이드가 이전 사용자 합의의 통합본임은 그 가이드의 설명이며, 이번에 당시 대화 전문을 새로 검증한 것은 아니다.

이번 턴 시작 HEAD는 `a26d2f95`다. 다른 세션의 [Reference 첫 적용 기록](2026-10-29-ticket06-01-reference-partial-application.md)과 `e38ce52b`를 확인했다. ## Personal에 둘 코드 표현 본문 후보

다음 본문은 검토용이다. 실행 정본 경로로 생성하지 않았으며 기준의 자동 활성화를 뜻하지 않는다.

### 코드의 흐름과 필요한 설명·진단을 드러낸다

새 코드를 쓰거나 맡은 범위의 기존 코드를 고칠 때, 읽는 사람이 처리 목적과 다음 흐름을 따라가고 필요한 이유·실패 정보를 찾을 수 있게 구성한다. 이름·타입·책임·제어 흐름으로 의도와 동작을 드러내는 것을 우선하며, 설명은 코드로 드러내기 어려운 내용을 보완한다. 현재 프로젝트의 언어·표현 규약과 도구 설정을 함께 적용한다. 충돌하는 기준은 차이와 영향을 확인해 이번 작업의 권한 안에서 선택한다.

**처리 목적이 보이게 문장을 묶는다.** JS/TS의 조건문·반복문처럼 블록 생략이 가능한 제어문에도 중괄호를 쓴다. 짧은 guard도 같은 방식으로 표현한다. 같은 조건을 준비하거나 하나의 결과를 만드는 코드는 가까이 두고, 입력 준비·실행 조건 판단·외부 작업·결과 반영처럼 목적이 바뀌는 곳은 빈 줄로 구별한다. 모든 `await`·`return` 앞뒤를 자동으로 띄우지는 않는다. 들여쓰기·따옴표 등 기계적 형식은 프로젝트의 formatter를 따른다.

형식을 정리하면서 조기 반환을 새로 추가하면 뒤의 실행이 달라질 수 있다. 중괄호·개행 편집과 조건·순서 변경을 구별하고, 동작이 바뀌는 부분은 해당 요구와 보존 조건으로 판단한다.

**전체 동작과 필요한 상세를 연결한다.** 호출자가 맡기는 동작의 흐름을 먼저 이해하고, 필요한 세부로 내려가도록 배치한다. 세부를 확인하려고 여러 파일을 반복해서 오가거나 호출 순서를 다시 조립해야 한다면 관련 코드의 배치·이름·책임을 함께 살핀다. 함수 순서만으로 해결할 수 있는 것과 책임 자체가 섞인 문제를 구별한다. 보기 좋은 순서를 만들기 위해 새 helper나 파일을 늘리지 않는다. 언어·프레임워크의 선언·초기화 조건도 보존한다.

**주석은 이유와 필요한 탐색을 돕는다.** 인접 코드를 그대로 다시 읽어 주는 주석은 줄인다. 코드에서 드러내기 어려운 선택 이유·외부 제약·비자명한 계약은 유지한다. 관련 처리 구간을 빠르게 찾는 짧은 안내도 필요하면 둘 수 있다. 다만 모든 줄을 단계별로 해설하거나, 불명확한 코드의 역할을 주석만으로 계속 설명하는 상태는 개선할 여지가 있는지 본다. 긴 장식 구분선은 간소화하되 요약·예시·단계 번호라는 형식만으로 제거하지 않는다. 주석이 실제보다 큰 최신성·완료를 약속하면 표현과 실제 계약을 대조한다.

**실패 처리와 진단 정보를 따로 판단한다.** 실패를 복구·전파·사용자 안내 중 어떻게 처리할지 정한 뒤, 그 처리로는 남지 않는 진단 정보가 필요한지 본다. 같은 오류를 여러 층에서 반복 출력한다면 하나로 모았을 때 필요한 사건·실패 단계·작업 맥락을 보존할 수 있는지 비교한다. 반환·예외 전달과 로그 기록은 서로의 대체물이 아니다. 복구에 성공했더라도 반복 원인을 살펴야 한다면 기록이 필요할 수 있고, 예외를 전파한다고 모든 층에 로그가 필요한 것은 아니다.

실제 로그의 수집 방법·필수 정보·민감 정보 보호는 Project 계약을 따른다. console 전면 금지, 새 logger 도입, 매 catch의 로그 추가를 이 기준만으로 요구하지 않는다. 로그 문구도 실제로 관찰한 사건·값·완료 범위를 표현한다.

이름·타입·완료 범위를 선택할 때는 기존 이름·완료 본문을, 오류 의미·자원 수명과 실패 전달은 계약·수명 본문을 함께 사용한다. 이번 변경의 수행·동작 확인은 기존 개발 흐름에서 맡으며, 이 본문을 읽었다는 이유로 관련 없는 기존 코드 전체를 정리하지 않는다.

Main의 문서상 적용 대조다. 실제 코드 변경·실행·새 독자 수행에서 확인한 결과는 아니다.

## 배치와 대안의 비교

**추천은 Personal 개발 아래 `code-expression` 주제를 추가하는 것**이다. 현재 이름·완료는 역할·타입·완료와 유지/개명/동작 수정의 판단을 맡고 있어, 개행·주석·진단까지 모두 넣으면 그 질문의 범위가 커진다. 새 주제는 읽기 흐름과 보조 정보의 판단을 맡고 필요한 이름·계약 본문에 연결한다. 제목은 ‘코드 표현과 진단’으로 제안한다. 이름·폴더는 아직 선택되지 않았다.

- 이름·완료 본문에 전부 합치면 진입 수는 줄지만 완료 계약을 찾는 독자가 개행·로그까지 함께 읽게 된다. 두 주제가 실제로 늘 함께 소비된다면 통합도 가능하나 현재 질문의 차이에서는 분리를 추천한다.
- 세부를 모두 Project에 남기면 현재 대상에서만 사용하는 규칙은 잘 유지할 수 있다. 다만 사용자가 제품과 무관한 개인 기준도 구별하려던 목적과, 여러 작업에서 같은 판단을 관리하려는 Personal의 역할을 충분히 살리지 못한다.
- 별도 표현 스킬은 추천하지 않는다. 이미 구현·검토가 관련 Personal을 읽고 판단하므로 새 호출·반환 절차가 필요하다는 근거가 없다.

채택 후에는 주제 README·현재 본문·필요한 형성 자료를 구성하고 기존 개발 README에 질문별 진입을 추가한다. 공통 본문의 ‘포맷·주석·로그 세부는 Project’ 문장은 개인의 표현 판단과 대상 Project의 실제 규약·도구 계약을 구별하도록 바꾼다. 이름·완료의 코드 명료함 지향은 유지하고 주석 상세는 새 주제로 연결한다. 서로 다른 의미의 상수, catch·void의 한정 보완은 해당 기존 주제에서 소유한다. 이것은 반영 위치 제안이며 해당 파일을 이번에 생성·이동한 것은 아니다.

Project의 인증·통화·DB·native 등 제품 내용은 독립된 계약으로 유지한다. 기존 Noline 가이드를 실제로 재편하려면 적용 세션이 현행 내용과 사용자 변경, 현재 참조를 대조해야 하며 보존 사본의 구성만으로 삭제·이동을 결정하지 않는다. 이번 논의가 첫 Reference 적용을 되돌리거나02의 기록·Maintain 선택을 변경하지 않는다.
