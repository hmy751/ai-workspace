## 회사 프로젝트를 살필 때의 범위 제안

Main의 제안이며 아직 회사 코드 조사를 실행하지 않았다. 처음부터 저장소 전체나 사용자의 모든 커밋을 정독할 필요는 없다. 작성자·기간·기능 영역의 이력을 먼저 확인하고, 의미 있는 대표 변경 몇 개를 골라 작성 당시 diff와 주변 코드를 함께 읽는다. 단순 포맷·자동 생성·기계적 변경을 선호 근거로 삼지 않는다. 여러 작성자 ID, squash·공동 작업, 이후 다른 사람의 수정 때문에 작성자 정보만으로 실제 기여나 선택 이유를 확정할 수 없다는 점도 확인한다.

결과는 ‘관찰된 선택과 근거’, ‘사용자의 선택인지 팀 관례인지 불분명한 부분’, ‘사용자가 지금도 유지하고 싶은지 논의할 대비’로 제시할 수 있다. 대표 변경에서 얻은 후보를 다른 작업에서도 확인하되, 빈도만으로 규칙으로 만들지 않는다. 부족한 사례가 드러날 때 조사 범위를 넓힌다.

다음에 필요한 정보는 회사 프로젝트의 로컬 경로와 그 저장소에서 사용한 Git 이름·이메일 또는 대표 커밋이다. 사용자가 기억하는 기능·작업 시기도 범위를 좁히는 단서가 된다. 정확한 코드 기준 전체를 사용자에게 먼저 정의하도록 요구하지 않는다. 이 방식은 개인 코드 기준 논의의 근거를 찾는 제안이며, 컨텍스트·브레이크·워크플로 등 전체 작업 시스템의 범위를 줄이지 않는다.
