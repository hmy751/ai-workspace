# 04-02 — ‘설명’ 하나를 진입점으로 삼는 구성 제안

**후속 적용:** 사용자 요청으로 이 리뷰 반영 구성을 [explain prototype](prototypes/development-workflow/skills/explain/SKILL.md)에 구현하고 기존 두 실행 경로를 정리했다. [생성 중 정정·적용·확인](2026-10-23-ticket04-02-explain-prototype-adoption.md)을 읽는다. 아래 미채택·미구현 표기는 제안 당시 상태이며 최신 상태가 아니다. 운영 설치·실제 수행 효과와 prototype 생성은 구별한다.

**Main은 별도 브리핑·복구 스킬을 전제로 한 보완에서, 하나의 설명 스킬이 공통 작성 방법을 소유하는 구성으로 전환할 것을 권한다.** 내부는 기존 두 스킬이나 코드·문서 같은 대상별 메뉴로 나누기보다, 현재 질문을 설명할 때 실제로 필요한 방법을 함께 사용하도록 구성한다. 이름은 가칭 `explain`이며 본문·상세의 정확한 분량과 명칭은 아직 확정하지 않았다.

이는 사용자 구상을 source·기존 본문·형성 자료와 대조해 구체화한 **논의용 제안**이다. 통합 채택·prototype 교체·운영 설치·새 응답 시험은 하지 않았다. [앞선 근본 재검토](2026-10-23-ticket04-02-fundamental-reassessment.md)의 ‘복구 유지·브리핑 재구성’은 당시 권고이며, 두 스킬을 따로 유지해야 한다는 결론은 이번 제안으로 수정한다. 요구 문구 추가와 비교 시험의 반복을 멈추고 작성 방법을 바꿔야 한다는 판단은 이어간다.

후속 사용자 요청에 따라 [독립 개선 리뷰 한 번과 Main 판단](2026-10-23-ticket04-02-composition-improvement-review.md)을 거쳐 아래 제안을 보완했다. 관계·이유·근거의 작성 상세를 함께 두고, 앞선 발화 대조를 별도로 둔다. 기존 본문에도 작성 방법은 있었으므로 새 안의 차이는 방법의 최초 도입이 아니라, 자료 선정 이유부터 실제 짧은 설명까지 보여 주는 작성 과정 예시와 첫 결과 전달의 연결을 구체화하는 데 둔다. 사용자 채택·수행 효과 확인은 아니다.

## 사용자가 연 구성 가능성과 근거의 지위

사용자 원문 발췌:

> 내가 생각한건 아티팩트 브리핑을 떠나서 그냥 설명으로 하나 하고 거기서 뭐 좀 나눠지던가 왜냐면 설명 리커버리도 있고 하니까
> 러프하게 생각하면 이렇고 딱잘라 이런것보다 어떻게 생각해?

> 근데 중요한건 배경에서 뜼이 그렇다고 딱 지키란건 아니야 지금 source들과 우리 논의들도 같이 고려해봐야 하는거 알지?

사용자는 통합을 확정하거나 기존 두 스킬을 하위 메뉴로 그대로 옮기라고 지시한 것이 아니다. 이 구상이 적절한지 함께 판단하자는 요청이다. Main은 두 스킬의 `_background`를 직접 읽었다. [브리핑 형성 자료](prototypes/development-workflow/skills/explain/_background/legacy/work-artifact-briefing/README.md)는 산출물의 부분 설명이 제품 목표·실제 수행과 연결되지 않던 문제를, [복구 형성 자료](prototypes/development-workflow/skills/explain/_background/legacy/explanation-recovery/README.md)는 앞선 발화의 뜻과 오류·이의를 다루던 선택을 보여 준다. 이 자료는 당시 분리 이유를 설명하지만 현재 분리를 유지해야 함을 증명하지 않는다.

작은 질문의 부담을 줄일 필요도 현재 질문과 근거로 다시 판단한다. 짧은 표현 질문이어도 뜻이 실제 설계·사실에 걸려 있으면 확인 범위가 커질 수 있고, 작업물 전체 설명이어도 질문에 필요한 관계가 단순하면 짧게 끝날 수 있다. ‘복구는 작게, 브리핑은 크게’라는 고정 분류를 새 구성의 전제로 삼지 않는다.

아래는 보존된 장면에 대한 설계 대조다. 새 스킬로 응답을 실행하거나 통합 효과를 확인한 결과가 아니다.

공통점은 **지금 이해할 질문을 잡고, 답을 성립시키는 관계와 근거를 골라, 독자가 그 관계를 직접 따라갈 수 있게 설명하는 일**이다. 달라지는 것은 근거와 보여 주는 방법이다. 발화·코드·관찰·조건 비교가 한 설명 안에서 함께 필요할 수 있다.

이 장면들은 통합 구상과 양립하고, 기존 두 진입점에 고정될 이유를 약하게 한다. 다만 ‘분리 때문에 실패했다’는 인과나 ‘통합하면 더 잘 설명한다’는 효과까지 입증하지는 않는다. [사용자 인터뷰](../source/noline-evaluation/reviews/interview-20261012.md)의 “처음부터 그 정도로 검토하고 설명”, “왜 그렇게 했는지 판단해서 설명”을 목적에 두고, 새 질문을 탐색한 것까지 실패로 세지 않는다.

## 공통 본문은 실제 설명 방법을 소유한다

적용 대상은 특정 작업물에 한정하지 않는다. 개념·코드·문서·작업 결과·앞선 발화의 뜻, 관계, 동작, 선택 이유를 사용자가 이해하려는 요청을 다룬다. 설명을 실제로 작성하는 시점의 사용 조건이며, 현황 파악이나 결과 전달이라는 표현만으로 항상 전체 설명 절차를 추가하지 않는다. 첫 보고에서 재사용할 관계는 아래처럼 작업 흐름과 연결한다.

다음 문단들은 본문에 둘 핵심 실행 내용의 초안이다. 고정된 출력 목차나 모든 답에 차례로 수행할 절차가 아니다.

**현재 질문에서 무엇을 알면 답이 되는지 잡는다.** 사용자가 가리킨 대상과 앞선 대화에서 이미 공유한 내용을 확인해 설명의 중심을 정한다. 뜻을 묻는지, 과정이 연결되지 않는지, 선택 이유나 앞선 주장이 맞는지 묻는지를 현재 말과 맥락으로 판단한다. 이를 배타적인 질문 유형으로 분류하거나 사용자에게 혼란의 원인을 먼저 진단해 달라고 요구하지 않는다. 판단을 바꾸는 모호함만 확인한다.

**답과 그 답을 이해하는 데 필요한 연결을 함께 만든다.** 직접 답을 먼저 제시하고, 그 답이 왜 그런 뜻인지 또는 어떻게 성립하는지 따라갈 수 있게 필요한 관계를 펼친다. 이름을 풀어 쓰는 데 그치지 않고, 예를 들어 무엇을 맡는 부분인지와 실제로 하는 일이 어떻게 이어지는지 설명한다. 답의 근거가 비어 있으면 허용된 범위에서 필요한 부분을 확인한다. 이미 충분한 사실·맥락으로 답할 수 있다면 별도 조사부터 시작하지 않는다.

**중요한 주장을 실제 대상 가까이에서 설명한다.** 코드의 역할을 이해해야 한다면 그 역할을 드러내는 코드를 골라 처리·조건·결과와 연결한다. 보고서의 의미라면 결론 옆에 그 결론을 지지하는 관찰과 한계를 붙인다. 개념이라면 관계가 드러나는 구체 상황을 쓸 수 있다. 함수 이름·링크·추상적 역할표만 주고 핵심 대응을 독자에게 맡기지 않는다. 전체 코드를 옮기거나 모든 근거를 나열할 의무도 없다.

**이해를 가르는 차이가 있으면 그 차이를 보여 준다.** 같은 상황에서 값이나 조건이 달라질 때 어떤 결과가 달라지는지, 두 선택이 어느 요구를 다르게 충족하는지를 비교한다. 문장만으로 관계를 따라가기 어렵다면 코드 발췌·표·그림을 선택해 설명과 붙인다. 표현 수단 자체를 필수 요소로 세지 않는다. 구조를 이해하는 것이 현재 목적이면 다음 행동을 억지로 붙이지 않는다.

**앞선 설명을 묻거나 이의를 제기하면 실제 발화에 돌아간다.** 그때 말한 뜻과 지금 확인한 타당성을 구별한다. 이미 설명한 것·빠진 연결·틀린 주장을 대조하고, 틀린 것은 정정하면서 현재 설명을 이어간다. 이전 답을 더 나쁘게 단순화해 새 답의 장점을 만들거나, 새로운 설명으로 원래 말의 뜻을 바꾸지 않는다. 사용자의 질문이 새 관심사인지 실제 교정인지는 대화로 판단한다.

현재 질문의 답과 이해에 필요한 관계가 드러나고, 답의 의미를 바꾸는 미확정이 보이면 응답을 마친다. 이해 여부의 형식적 승인이나 재진술 시험을 기본으로 요구하지 않는다. 사실과 해석, 설명·추천과 실제 수정·채택의 경계는 기존 [공통 기준](prototypes/development-workflow/skills/shared/explanation-and-evidence-criteria.md)을 사용하고 본문에 장문으로 복제하지 않는다.

## 본체와 수행 상세를 계층으로 구성한다

후속 사용자 원문:

> 그럼 만들기전에 어던식으로 구성할건지 좀 더 설명해줘봐 그러니까 상황마다 조합인가? 유형? 아니면 기존 두개 처럼 시점도 나뉘는건가?
> 또 context/workspaces/014-ai-development-workflow-design/records/prototypes/development-workflow/skills/development 이것처럼 안에 좀 계층적으로 나눌거 잇음 나누던가 해서 잘 본체랑해서 구성해놓으면 좋을 것 같아

Main은 [development 본체](prototypes/development-workflow/skills/development/SKILL.md)와 [검토 상세](prototypes/development-workflow/skills/development/references/review.md)를 직접 대조했다. 가져올 구성은 본체가 공통 수행을 소유하고, 상세가 특정 수행의 조건·판단·행동을 깊게 맡는 관계다. 개발 역할·단계 자체를 설명에 옮기지는 않는다. 앞선 ‘실행 예시 한 파일’ 권고를 아래 수행 상세 후보로 구체화한다. 예시는 각 방법 가까이에 두며 예시 모음만으로 실행 상세를 대신하지 않는다. 아직 실제 스킬 파일은 만들지 않았다.

**권고는 공통 본체와 필요에 따라 함께 사용하는 수행 상세다.** 설명 대상의 유형은 무엇을 읽을지의 단서이고, 시점은 이전 대화·기존 결과와 어떤 관계에 있는지 판단할 조건이다. 이 둘을 각각 독립적인 모드나 파일 계층으로 늘리지 않는다. 상세 선택은 단순히 모델이 어렵다고 느끼는 때가 아니라 현재 질문에서 아래 수행이 필요한지로 판단하며, 읽은 상세를 사용자 답의 고정 목차로 출력하지 않는다.

이 두 상세는 배타적인 유형이 아니다. 예를 들어 “아까 저장하면 목록도 갱신된다고 했는데 저장 성공과 조회 성공은 같은 거야?”에는 이전 발화 대조와 실제 동작의 연결이 함께 필요할 수 있다. “왜 그렇게 나눴어?”가 이어지면 선택 이유의 설명도 같은 작성 상세에서 이어간다. 본체는 현재 질문에 필요한 부분을 골라 하나의 답으로 통합하며 두 상세를 매번 순서대로 실행하지 않는다. 최초 세 상세안은 [리뷰 직전 사본](reviews/explanation-composition-2026-10-23/proposal-before-review.txt)에 보존했다. 관계와 이유·근거를 나누면 현재 수행이 겹친다는 리뷰를 반영한 조정이며, 실제로 별도 자료·수행 책임이 생기면 그때 분리한다. 두 파일이라는 수 자체는 목표가 아니다.

첫 설명·작업 결과 전달·후속 질문이라는 시점은 본체에서 다룬다. 첫 설명에서는 필요한 공통 전제와 관계를 처음 구성하고, 결과 전달에서는 원래 목표·이전 상태와 무엇이 달라졌는지 잇는다. 후속에서는 이미 공유한 내용에 이어 새 질문인지 앞선 설명의 보완·정정인지 판단한다. 상세를 쓰는 시점을 응답 마무리로 고정하지 않는다. 설명이 필요한 것이 분명해지면 근거를 고르고 읽는 과정부터 방법을 적용한다. 특정 시점에서 항상 전체 브리핑을 실행하거나 후속마다 복구로 바꾸는 규칙은 두지 않는다.

예시는 원하는 답 전체를 외우게 하기보다 작성 중 달라져야 할 행동을 보여 줘야 한다. [이미 있는 여행 예시](2026-10-23-ticket04-02-astra-improvement-review.md#리뷰가-제안한-응답-예시의-핵심)에서 가져올 것은 ‘저장과 조회 역할을 설명하라’는 문장 추가가 아니다. `TripRepository.create(data)`와 성공 후 갱신 요청을 하는 부분을 함께 고르고, 조회와 로컬 반영을 하는 구현을 이어서 보여 줌으로써 **저장 성공과 목록 갱신 성공이 서로 다른 결과라는 설명을 코드에 대응시키는 방법**이다. 파리·도쿄 조건 대비는 그 차이가 실제 상황에서 무엇을 뜻하는지 보여 주는 방법이다. 기존 예시 전문을 다시 작성해 새 성과로 세지 않는다.

작성 과정 예시에서는 무엇을 설명하려는지, 어떤 부분을 골랐는지, 왜 그 부분이 필요한지, 실제 짧은 설명이 어떻게 나오는지를 연결한다. 여행이라면 `create`만 보여서는 목록 변화가 설명되지 않으므로 생성 훅의 갱신 요청과 조회 쪽 반영을 함께 고르는 이유를 보여 준다. 이 구성은 실행 방법을 가르치는 예시이며 모든 사용자 답의 필수 목차가 아니다. 본체에도 이 수행의 핵심은 남기고, 실제 자료 선택과 짧은 출력이 이어지는 상세를 보조로 쓴다.

복구 예시도 ‘더 쉽게 설명하라’ 대신 실제 이전 문장과 현재 자기평가를 대조하는 동작을 보여 준다. 보고서 예시는 관찰을 나열한 답과 그 관찰이 원래 문제에 무엇을 답하는지 연결한 답의 차이를 보여 준다. 이 방법들은 코드·문서·앞선말의 독립 경로가 아니며 한 질문에서 조합할 수 있다.

## 다른 책임과 연결하고 기존 것을 정리하는 방법

첫 완료 보고에서는 작업 주체가 수행·미수행·검증 결과를 파악한 책임을 계속 가진다. 그 결과가 사용자의 원래 목표에서 무엇을 뜻하는지 설명할 때 공통 방법을 재사용한다. 설명 중 답을 바꾸는 사실 공백이 드러나면 확인 범위를 판단하고, 전체 구현·조사·acceptance를 이 스킬의 성공으로 합치지 않는다. 01-01·04-03에서 진행 중인 작업 흐름에 자동 호출을 임의로 삽입하지 않는다.

호출자와의 연결은 다음 취지로 구체화한다. **작업 결과를 전달할 때 원래 질문에 무엇이 답해졌는지 먼저 구성한다. 그 답을 이해하려면 변경의 관계나 선택 이유를 따라가야 하는 경우 설명 방법을 사용한다. 필요한 연결을 만들 수 없는 이유가 사실 부족이면 작업 주체가 기존 권한 안에서 추가 확인할지 판단하고, 확인할 수 없다면 이유와 답에 미치는 영향을 밝힌다.** 항상 전체 브리핑이나 재검사를 요구하지 않으며, 추가 확인은 현재 답을 바꾸는 공백에 맞춘다. 설명을 완성된 조사 결과의 마지막 문장 다듬기로만 두지 않기 위한 관계다. 이번에는 설계 제안에만 반영하고 development 실행 본문은 수정하지 않는다.

통합을 채택한다면 두 기존 진입점의 현재 사용 관계를 하나로 옮긴다. 기존 두 스킬과 새 스킬을 셋 다 같은 설명 책임의 독립 정본으로 운영하는 구성을 목표로 하지 않는다. 다만 과거 비교 입력·원응답·형성 기록은 당시 판본을 그대로 보존한다. 특히 현재 `explanation-recovery/SKILL.md`는 보류한 수정안이므로, 그 파일을 이미 채택된 운영 기준처럼 그대로 흡수하지 않는다.

공통 기준은 `work-discussion`도 사용한다. 통합 때문에 그 기준까지 새 설명 스킬 안으로 옮기거나 중복하지 않고, 채택 시 실제 consumer 안내만 함께 맞춘다. 현재는 이 연결·설치·기존 파일 삭제를 실행하지 않았다.

## 이번 논의의 다음 결과

지금 결정할 것은 **이 공통 작성 방법이 원하는 설명의 일을 충분히 맡는지와, 어떤 상세가 실제 수행을 바꾸는지**다. 이름 변경·폴더 통합만으로 마감하거나 같은 요구 문장을 더 강하게 쓴 뒤 다시 승자를 찾는 비교로 돌아가지 않는다. Main의 추천은 이 방법을 중심으로 통합 본문을 구체화하는 것이다.

후속 확인이 필요하면 채택하려는 행동과 실제 열린 결정을 연결한다. 예컨대 하나의 설명 요청에서 역할·코드·조건의 대응을 만들 수 있는지, 앞선말을 묻는 짧은 질문에서 필요한 원문을 정확히 다루는지가 확인 대상이다. 이 기록의 source 대조는 그 수행 증거가 아니며, 파일 분할·기준 읽기·요소 포함·사용자 이해도 서로 다른 증거다. 준비된 Network A/B는 이 구성 결정을 직접 가르는 시험이 아니므로 계속 미실행 자료로 둔다. 효과가 없을 때는 알려진 미수행을 근거로 선택을 다시 판단하고, 자동으로 같은 사례 재생성이나 추가 문구 보강을 시작하지 않는다.

## 구성 판단에 적용한 작성 기준

`skill-creator`의 기본 역량 가정·실질적인 공통 본문·필요한 상세만 분리하는 기준과, prototype의 [스킬 본문 관리 정책](prototypes/development-workflow/skills/SKILLS-CONTENT-POLICY.md)을 적용했다. 공통 본문을 파일 안내로 비우지 않고, 알려진 문제에서 실제로 달라질 작성 행동에 집중했다. instruction clarity·context ownership·responsibility cohesion reference는 목적·조건·행동의 관계와 본문·상세·형성 자료의 책임을 정리하는 데 사용했다. 이 기준들은 구성의 근거이며 통합의 수행 효과를 증명하지 않는다.
