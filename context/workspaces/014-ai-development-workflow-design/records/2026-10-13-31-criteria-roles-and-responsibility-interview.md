# 코드 기준의 역할 구분과 책임 분리 인터뷰

2026-10-13. 코드 기준을 구체화하는 대화에서 얻은 사용자 선호와 적용 조건을 남긴다. 역할별 분류, 구현 패턴, 분리 판단을 공통 기준으로 채택한 기록은 아니다.

**현재 중요한 보완:** 사용자는 길이 중심의 정리가 실제 개발에서 독립된 페이지·컴포넌트를 한 파일에 모으게 할까 우려했다. Dialog를 함께 보는 이유는 합성형 컴포넌트의 구성과 부품을 한곳에서 파악하기 편해서다. 역할·책임 경계·패턴을 먼저 이해하고, 짧다는 이유만으로 분리할 단위를 합치지 않아야 한다. 아래 ‘역할과 패턴에 관한 후속 정정’에 직접 발화를 남긴다.

후속 코드 비교에서는 기능 흐름을 Hook으로 묶으면서 내부 검증·결과 처리를 함수로 나누는 구성을 좋게 보았다. 기존 React Query·React Hook Form 등에 이미 맡긴 책임도 분리 판단에 포함해야 한다고 보완했다. 아래 요약은 논의 중인 선호이며, 예시의 상태 구조·파일 배치·특정 라이브러리 도입을 확정한 원칙이 아니다.

## 현재까지 드러난 선호와 열린 조건

| 선호 | 함께 남길 조건과 한계 |
| --- | --- |
| 책임을 명확히 나누고, 같은 책임을 이해하는 데 필요한 맥락을 모은다. | 파일·함수 수를 늘리는 것 자체를 선호한다는 뜻은 아니다. 페이지의 다른 역할과 해당 기능의 비중에 따라 경계가 달라진다. |
| 독립된 페이지·기능 컴포넌트는 역할과 패턴에 맞게 나눈다. | 길이가 짧다는 이유만으로 한곳에 합치지 않는다. 작은 기능을 페이지에 둘 여지는 있으며 크기 기준은 미정이다. |
| 합성형 Dialog의 관련 부품은 함께 파악하기 좋은 구성을 선호한다. | 모든 UI 부품을 한 파일에 모으는 규칙은 아니다. 합성형의 구성 자유와 부품 관계를 보는 편의가 이유다. |
| 재사용성을 고려할 수 있는 의미 있는 단위로 나눈다. | 실제 사용처가 두 곳 이상이어야 한다거나, 재사용만이 분리 이유라는 조건은 확인되지 않았다. |
| 서로 의존하는 작업 흐름은 기능 Hook으로 묶을 수 있고, 내부 책임은 함수 등으로 더 나눌 수 있다. | 다중 초대·부분 실패·수정 후 재전송 사례에서 납득한 구성이다. 모든 기능에 같은 Hook·함수 묶음을 요구하지 않는다. |
| 기존 도구·라이브러리에 이미 맡긴 책임을 분리 판단에 포함한다. | React Query·React Hook Form은 사용자가 든 예다. 실제 프로젝트의 사용 방식·책임 범위를 확인해야 하며 설치나 일괄 도입을 선택한 것은 아니다. |

기능의 외부 사용 단위, 내부 함수의 책임, 파일 배치는 서로 관련되지만 같은 결정이 아니다. 이번 예시의 네이밍·코드 스타일과 세부 API 모양은 사용자가 나중에 논의할 것으로 구별했다. 위 선호를 구현자의 의무 규칙으로 채택하는 작업은 아직 하지 않았다.

## 자료와 기준의 역할을 구별한 논의

사용자는 Airbnb 코드스타일도 떠오른다고 했지만, 떠오른 것을 전부 조사·적용하라는 지시는 아니라고 명시했다. 템플릿에는 UI 컴포넌트 패턴이 있고 React 내용도 있을 수 있는 한편, 토스는 코드를 보는 관점에 가깝게 느껴진다며 이런 차이를 논의하자고 요청했다.

Main은 품질을 판단하는 관점, 작성 규약, 설계·구현 패턴, 동작상 제약·계약을 구별하는 안을 제시했다. React·TypeScript·UI는 적용 분야이며, 한 분야에 여러 역할의 내용이 포함될 수 있다고 설명했다. 이 구분은 논의용이며 파일·스킬·공통 템플릿의 구성을 결정한 것은 아니다.

템플릿에 대해 사용자는 다음과 같이 말했다.

> 전 후자다 작성하고 싶고 근데 절대 원칙으로 두면 고정이 될 것 같아서 이런건 좀 여지를 둬도 되겠다 뭐 그렇게 생각하고 있어
> 그럼 그전에 기준부터 좀 나눠볼까? 니 말대로 좀 영역이 다른것 같긴하네

여기서 분명히 확인한 것은 그런 방식으로 작성하고 싶은 의향과, 절대 원칙으로 고정하지 않고 여지를 남기고 싶은 방향이다. 참고만 하는 자료 또는 항상 적용할 규칙 중 하나로 일괄 확정하지 않는다.

## 실제 사례의 질문과 Main의 비교안

Main은 [토스의 구현 상세 추상화 예제](https://frontend-fundamentals.com/code-quality/code/examples/login-start-page.html)의 FriendInvitation을 사용했다. 2026-10-13에 공식 본문을 확인했다. 원문은 페이지 안의 동의창과 전송 처리를 InviteButton에 모아 페이지가 한 번에 읽을 맥락을 줄이고, 버튼과 클릭 처리를 가까이 두는 방식이다.

Main은 별도로 동의창의 상세를 `askInvitationConsent`에 분리하되, 동의 후 전송하는 순서를 페이지의 `handleInvite`에 남기는 설명용 변형을 ‘중간 형태’라고 불렀다. 이는 Main의 비교 예시다. 사용자가 의미를 확인해 동의창 상세·전송·순서를 누가 맡는지 설명했다. 코드 구현이나 실행 검증은 하지 않았다.

질문은 페이지에 어느 정도의 정보를 남기고 싶은지, 다른 컴포넌트로 이동해 상세를 읽는 것을 어떻게 느끼는지였다.

현재 확인한 선호는 책임 분리를 명확히 하고 같은 책임의 맥락을 모으는 것이다. 합성형 UI는 구성의 자유를 유지하면서 각 부분의 로직을 맡은 범위에 집중시킬 수 있다는 점을 좋아한다. 이를 짧은 함수·많은 파일·한 패턴의 일괄 적용 선호로 바꾸지 않는다.

페이지에 다른 책임이 얼마나 있는지, 초대 흐름이 페이지의 주된 역할인지에 따라 동의와 전송의 위치를 판단한다. 컴포넌트 이동도 상황에 따라 다르다. 한곳에서 충분히 표현할 수 있다면 그것도 좋고, 확장이 예상되면 나누는 방향을 생각하지만 그 조건과 정도는 아직 미정이다.

## 파일 분리 수준을 비교한 후속 답

Main은 같은 파일 안에 페이지와 InviteButton을 각각 정의하는 방식과 별도 파일로 나누는 방식을 비교했다. 사용자:

> 지금 같은 경우는 애초에 거의 페이지 정도면 커질게 예상되고 그래서 나누는게 나아보여

이 사례에서 사용자는 페이지 자체의 성장을 예상하는 점을 파일 분리의 근거로 보았다. 구체적인 확장 일정이 이미 확정되어 있어야만 분리한다는 뜻으로 좁히지 않는다.

이후 Main은 한 Dialog를 구성하는 짧은 Content·Title·Description 등도 각각 파일로 나눌지 물었다. 사용자:

> 그런건 예를 들어 정말 짧을것 같다 앞으로도 그정도면 둬도 되는데 벌써 나눠지는게 맞지 않나? 아니다 이정도면 뭐 안나눠져도 좋은것 같긴해 내 실제 파일도 함께되어 있을거야 이정도는 하나가 더 나아보여

사용자는 분리도 생각해 본 뒤, 이 정도로 짧고 앞으로도 짧을 것으로 보는 부품들은 한 파일에 두는 편을 좋게 보았다. 본인의 실제 파일도 함께 있을 것이라는 언급은 모든 실무 코드를 직접 확인한 사실로 기록하지 않는다. 지정된 code-template의 예제에는 실제로 관련 부품들이 함께 정의되어 있다.

| 비교 장면 | 당시 답과 Main의 해석 |
| --- | --- |
| 페이지와 초대 기능 | 페이지가 커질 것으로 예상하므로 초대 기능을 별도 파일로 분리하는 쪽 |
| 한 Dialog의 짧은 구성 부품 | 같은 UI를 구성하며 앞으로도 짧을 것으로 보는 경우 함께 두는 쪽 |

당시 Main은 책임의 관계와 예상되는 크기·변경을 함께 판단한다고 해석했다. 그러나 설명이 길이와 성장성에 치우쳐 Dialog를 함께 보는 패턴의 이유와 일반 컴포넌트의 경계를 충분히 드러내지 못했다. 이를 아래 사용자 정정으로 보완한다.

## 역할과 패턴에 관한 후속 정정

사용자:

> 근데 또 짧다 길다만 보면 애매한게 페이지나 컴포넌트는 보통 나뉘잖아? 프리젠테이션 패턴도 있고 막 그런 뭐랄까 그냥 솔직히 딱봐도 나눠질 파일인데 실제 개발할때 또 단순히 길이 짧다 하고 다 모아놓을까봐 좀 우려되기도 하네
> Dialog는 합성형이고 하나에서 보고 부품들 파악하고 보통 그러기도 하니까 그게 편했고

사용자가 우려한 것은 길이 기준의 애매함뿐 아니라, AI가 이미 역할·패턴상 구별할 페이지·컴포넌트까지 ‘짧다’는 이유로 합치는 적용이다. Dialog는 하나의 합성형 UI를 구성하는 부품들을 함께 파악하는 편의가 중요한 이유다. 짧게 유지될 것이라는 앞선 답은 이 역할과 패턴 맥락 안에서 읽는다.

현재 해석은 독립된 책임 단위의 경계와, 한 단위를 구성하는 관련 부품의 모음을 구별해야 한다는 것이다. 실제 프로젝트의 구성 관습과 기술별 패턴도 확인할 판단 재료이며, 길이·예상 성장만으로 대신하지 않는다. 사용자가 프리젠테이션 패턴을 예로 든 것을 모든 프로젝트에서 특정 패턴을 의무 적용하라는 선택으로 올리지 않는다.

기준을 구체화할 때에는 역할·책임·패턴에 따라 무엇을 한 단위로 볼지 먼저 드러내고, 그 단위 안에서 구성 부품을 함께 둘지 또는 세부 구현을 더 나눌지 논의한다. 이는 길이나 파일 수의 고정 규칙을 만든 것이 아니다.

## 기능 내부의 로직 단위와 재사용에 관한 답

Main은 초대 기능 파일 하나에 입력 상태·검증·요청·오류 처리·UI를 함께 두는 안과, 로직 전체를 `useMemberInvitation`으로 옮기는 안을 비교했다. 사용자는 먼저 ‘이정도는 당연히 두개 나누는게 낫지’라고 답했으나 곧 다음과 같이 덧붙였다.

> 아니다 기능ㅇ이 너무작으면 페이지 안에 해도 될 것 같기도 하고

Main은 펼침·접힘 같은 표시 동작과, 이름 수정처럼 입력·검증·저장 요청이 있는 기능을 비교해 ‘작다’고 떠올린 장면을 물었다. 사용자의 답:

> 일단 재사용성이 있는 단위 정도로 나눌 것 같아 어느정도 그런걸 고려해서 단위를 나누지 막 한번에 훅으로 다 넣진 않을 것 같아
> 유효성 검사도 뭔가 넣는게 그러니까 그런 단위가 맞다 생각이 들면 넣고 뭐 러프하게는 그렇게 떠오르네

중요한 것은 두 파일 중 하나를 고르는 것보다, 재사용을 고려할 수 있고 그 책임에 적합한 단위를 찾는다는 점이다. 유효성 검사를 무조건 UI에 남기거나 Hook에 넣는 것으로 결정하지 않았으며, 어느 단위의 일부로 보는 것이 적절한지 판단한다. ‘실제 호출부가 두 곳 이상이어야 분리’나 ‘재사용이 없으면 분리하지 않는다’는 조건도 발화에서 확인되지 않았다.

Main이 제시한 ‘컴포넌트 안에 모두 두기 / 화면을 제외한 로직 전체를 Hook으로 옮기기’는 선택지를 충분히 펼치지 못한 비교였다. 다음 예제에서는 순수 함수, API 함수, 상태와 동작을 맡는 Hook, 기능 UI 등 적합할 수 있는 단위를 실제 책임과 사용 장면에 맞춰 비교한다. 나눈 파일을 새로 채우는 방식이나 모든 예제에서 이 단위들을 전부 만들도록 하는 방식으로 고정하지 않는다.

## 기존 도구의 책임과 기능 Hook 내부 분리

Main이 요청·진행 상태를 맡는 새 Hook을 분리 후보로 제시하자 사용자는 기존 도구의 책임이 빠졌다고 정정했다. 필요한 원문 발췌:

> 리액트 쿼리 훅이 있으면 데이터는 거기에 맡기고 왜냐면 그 책임 포인트가 있으니 근데 정말 복잡한 로직경우 쿼리 훅까지 포함해서 하는경우도 있고

> 너가 계속 질문이 너무 러프하게 생각을 하는 경향이 있어보여 상황마다 되게 다르잖아?

이어 Main은 기존 이메일 형식 검사와 React Query mutation Hook이 있다는 가정 아래 코드로 비교했다. 다음은 Main이 만든 설명용 사례이며 토스·사용자 프로젝트에서 확인한 구현이 아니다.

1. 회사 이메일만 허용하는 가입과 외부 이메일도 허용하는 초대: 공통 형식 검사와 기능별 정책을 구별했다.
2. 여러 이메일 초대: 기능 Hook이 입력 목록의 검증 결과·성공·실패·재전송 대상을 관리하고, 기존 mutation Hook이 요청과 진행 상태를 맡는 구성을 보였다.
3. 실패한 이메일을 그 자리에서 수정: 이메일과 별개의 행 식별자를 두고, 미완료 항목의 수정값·재검증·전송 결과를 연결했다. 성공 항목 제외, 전송 중 수정 금지, 중복 처리 등은 설명을 위한 Main의 가정이며 사용자 제품 정책으로 채택하지 않았다.
4. Hook 내부 분리: `prepareSubmission`이 검증과 전송 대상을 계산하고, `applyInvitationResults`·`applyRequestFailure`가 새 목록을 만들며, 기능 Hook은 상태와 실행 순서를 연결하는 구성을 보였다. 결과 처리 함수들은 같은 파일에 두는 예시였고 실제 파일이나 테스트는 만들지 않았다.

사용자는 다중 초대 사례에서는 기능 Hook으로 묶는 것을 이해한다고 했고, 이어 내부 책임 분리를 짚었다.

> 기능 훅으로 묶는 거랑 그 안에서 책임을 더 나누는 건 또 다른 얘기 같은데 그 부분도 같은 예시로 보자.

내부 함수 분리 예시를 본 뒤 사용자:

> 그래 이런 식으로 기능 훅으로 묶으면서 안에서도 책임을 나누는 건 괜찮아 보여. 지금까지 얘기한 내 선호를 한번 정리해보자. 아직 확정된 원칙은 아니고 상황에 따라 달라지는 부분도 같이 남겨줘.

> 그리고 하나 더 만약 여기 React hook form 이 있었다면 또 달라졌을거야 아마 그런게 생각나네 이미 있는 툴 라이브러리나 리액트 쿼리 등을 활용하고 이미 책임을 맡겼다면 그게 고려 기준에 들어가야 하는것 같아 코드를 분리하고 할때도

현재 해석은 기능을 한 사용 단위로 제공하면서 내부의 의미 있는 책임을 나누는 구성이 양립한다는 것이다. 기능 Hook을 만들기로 했다는 이유로 검증·변환 구현을 모두 그 본문에 넣거나, 반대로 내부 함수를 뺐다는 이유로 기능 흐름을 폼에 흩뜨리는 것으로 읽지 않는다.

기존 도구의 존재뿐 아니라 실제로 맡긴 책임을 먼저 확인해야 한다. 예를 들어 폼 도구가 입력값·입력 오류를 이미 소유하는 상황이면, 앞 예시의 Hook이 같은 값을 별도 상태로 보관하는 구성을 그대로 적용할 근거가 없다. 어떤 상태를 폼 도구에 두고 어떤 기능 흐름을 별도로 묶을지는 구체 구성에 따라 다시 비교할 대상이다. 이는 Main의 설명을 보완하는 판단이며 React Hook Form 버전·API를 조사하거나 실제 프로젝트 사용을 확인한 결과가 아니다.

## 다음에 더 확인할 판단

### code-template에서 더 논의할 부분과 조사 순서의 재검토

선호 요약 뒤 사용자가 다음 논의를 물었을 때 Main은 과제물에서 폼·검증·요청이 연결된 기능 하나를 골라 실제 도구와 주변 코드에서 선호를 확인하고, 이어 재사용·추상화의 경계를 보자고 제안했다. 사용자는 다음과 같이 물었다.

> 그럼 code-template에서 나올건 다 봤다고 생각하는거야?

Main은 파일을 읽은 것과 그 자료에서 사용자 선호를 충분히 논의한 것은 다르며, 과제물로 넘어가자는 제안이 성급했다고 정정했다. 현재 code-template에서 대화로 주로 확인한 것은 Dialog의 합성형 UI와 파일 배치에 대한 선호다. 템플릿에서 얻을 내용을 모두 살폈다고 결론 내리지 않는다.

다음 후보로 Main이 제안한 것은 기존 Radix 기반 Dialog와 사용하는 모양을 함께 놓고 다음을 비교하는 것이다.

- 라이브러리 위의 래퍼가 스타일·사용 방식·구성에서 추가로 맡는 책임.
- `Dialog.Content`·`Dialog.Trigger` 등을 조합하는 호출부의 선택권과 알아야 할 내용.
- 기존 라이브러리 props의 노출 범위와 직접 만든 컴포넌트의 타입·인터페이스 경계.

앞서 논의한 ‘부품을 어디에 둘까’에서 ‘기존 라이브러리 위에 어떤 책임과 인터페이스를 만들까’로 질문을 넓히는 제안이다. Matt의 깊은 모듈과 합성형 UI를 같은 실제 코드에서 비교하는 것도 후보이며, 둘을 같은 방식으로 적용하기로 한 것은 아니다. 함수·타입 등 다른 템플릿 메모도 남아 있고, 모두 소진해야 다른 자료로 넘어간다는 순서도 정하지 않았다.

사용자는 이후 먼저 미기록 대화를 확인·보존하고 커밋하라고 요청했다. 위 Dialog 비교는 다음 논의 후보로 남으며 아직 추가 조사·코드 비교를 수행하지 않았다. 과제물·회사 자료도 계속 미조사 상태다.

### 열린 판단

- 페이지·독립된 기능 컴포넌트·합성형 UI 부품 등 실제 역할과 패턴에서 어떤 단위를 분리하고 함께 파악하는가. 주변 책임과 프로젝트 구성 관습을 제공하고 판단한다.
- 나눌 때 공개 인터페이스·책임 소유·파일 배치를 어디까지 바꿀 것인가. 책임 분리와 파일 분할을 같은 것으로 전제하지 않는다.
- 이름·근접 배치·호출 방식 등 나뉜 코드에서도 맥락을 이해하기 쉬운 구체적인 모양.
- 재사용할 단위의 의미와 그 안에 둘 검증·상태·요청의 관계. 표현상 닮은 코드와 같은 책임을 재사용하는 경우를 실제 사례로 구별할 수 있다.
- 기존 폼·요청 도구에 실제로 맡긴 상태·검증·진행 책임을 확인한 뒤, 기능 Hook이 추가로 소유할 상태와 연결 동작을 비교한다. 도구를 적용하기 전 예시의 경계를 그대로 고정하지 않는다.

현재는 인터뷰로 선호와 적용 조건을 이해하는 단계다. ‘확장 가능성이 조금이라도 있으면 반드시 분리’나 특정 UI 패턴의 의무 적용을 채택하지 않았다. 전체 작업 단계의 시스템·컨텍스트·브레이크·워크플로 범위도 유지한다.
