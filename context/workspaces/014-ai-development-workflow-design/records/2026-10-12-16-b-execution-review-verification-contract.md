# B의 구현 인수·품질 수정·최종 실제 검증 초안

> 후속 논의에서 최종 실제 확인도 검토자가 이어가는 안으로 제안을 바꿨다. 아래 구현자 최종 확인 배치는 당시 제안이며 변경 이유는 [기록 17](2026-10-12-17-workflow-basis-and-connected-design.md)에 있다.

2026-10-12. **B 방향은 선택됐고, 이 문서의 상세 책임 배치는 검토할 제안이다.** 구현자에게는 결과·계약·품질 관심·맥락·확인 경로를 넘긴다. 검토자는 그 기준으로 직접 품질 개선과 검사를 수행한다. 마지막 실제 검증의 기본 수행자는 구현자, 완료 판단과 결과 통합의 책임자는 Main으로 제안한다. 구현자를 다시 모든 품질 수정의 담당자로 돌리는 C 방식은 아니다.

사용자 요청:

> 그럼 B 기준으로 구현자한테 뭘 넘기고 검토자는 어떤 기준으로 어디까지 수정하는지, 마지막 실제 검증은 누가 하는지 좀 더 구체화해보자

## 하나의 작업이 흐르는 방식

1. Main이 실행할 Ticket의 결과·계약·범위와 필요한 맥락을 구현자에게 넘긴다.
2. 구현자가 조사·세부 설계·구현을 수행하고 자동 검사와 초기 실제 동작 확인을 한다.
3. 검토자가 원요구·기준·변경판·실행 근거를 읽고 품질을 판단하며 필요한 수정을 직접 한다. 수정에 필요한 검사도 수행한다.
4. 구현자가 검토자의 수정이 반영된 최종 코드로 실제 사용 흐름을 확인한다. 실패하면 근거를 검토자에게 돌려 수정·재확인한다.
5. Main이 요구 충족·품질 개선·동작 근거·미해결을 종합하고 완료 범위와 다음 행동을 판단한다.

Main이 구현을 직접 맡으면 1·2·4·5를 같은 주체가 수행한다. 역할마다 별도 agent를 만드는 것이 아니다. 구현자는 자신의 초기 설계를 알고 있으므로 마지막 확인을 완전한 새 관점의 독립 검증이라고 부르지 않는다. 검토자의 수정과 다른 주체의 동작 확인을 연결하는 기본 배치다.

## 구현자에게 넘길 내용

기존 Ticket의 결과·실행 맥락·완료 조건을 활용한다. 아래 내용을 새 문서나 필수 양식으로 중복 작성하지 않는다. 알고 있는 사실과 미확인은 구별하고, 구현자가 조사할 코드 사실을 Main이 사전에 모두 채우려 하지 않는다.

| 필요한 내용 | 알림 설정 저장이라는 가상 작업의 예 |
| --- | --- |
| **만들 결과와 맡은 범위** | 설정을 바꾸고 저장하면 다시 진입해도 값이 유지된다. 이번 작업은 해당 설정의 조회·편집·저장·실패 복구를 연결한다. |
| **보존·제외 계약과 선택 이유** | 저장 버튼을 눌러 반영한다. 실패하면 작성 중 입력을 유지한다. 다른 계정에 응답이 섞이지 않는다. 자동 저장·알림 발송 정책 개편은 이번 범위에 없다. |
| **이번 결과의 품질과 판단 기준** | 조회된 값과 편집 중 값의 책임을 구분한다. 여러 화면에 저장 순서·오류 처리가 반복된다면 맡은 범위에서 적절히 모은다. 기존 root/local 기준을 따른다. 파일 수나 줄 수를 줄이는 것 자체는 목표가 아니다. |
| **읽을 원자료와 수정 출발점** | 해당 Spec·Ticket, 채택한 결정, 관련 Project 제품·구조·guidance, 현재 코드·호출부·테스트의 진입점을 연결한다. 파일 목록은 출발점이며 결과에 필요한 관련 연결은 조사한다. |
| **완료를 볼 장면과 실행 경로** | 저장 후 재진입, 저장 실패 후 입력 유지·재시도, 저장 중 계정 전환을 확인한다. 기존 개발 실행·검사 명령과 테스트 환경 안내를 찾게 한다. 환경이나 경로가 미확인이면 구현자가 먼저 확인하고 가능한 범위를 밝힌다. |

모든 작업에 위 상태를 그대로 넣지 않는다. 실제 요청과 시스템에서 도달할 수 있는 상태를 고른다. Vercel의 상태별 제품 판단을 활용하되 제품의 미정 정책을 AI가 예시로 확정하지 않는다.

**인수 지시 예시:**

> 이 Ticket의 알림 설정 저장을 완성한다. 저장 버튼 방식과 실패 시 입력 유지, 계정별 응답 분리를 지킨다. 관련 제품·구조 기준과 현재 저장 경로를 읽고 내부 설계는 발전시켜도 된다. UI부터 저장 결과까지 연결하고 자동 검사와 실제 저장·재진입·실패 흐름을 확인한다. 이후 별도 검토자가 품질 수정을 맡으므로, 변경판·구현 선택·실행 근거·남은 문제를 넘긴다. 제품 계약이나 제외 범위를 바꿔야 하면 근거와 대안을 Main에 돌린다.

별도 검토가 있다는 이유로 구현자가 품질을 무시하거나 이미 발견한 결함을 방치하지 않는다. 결과를 만들 책임과 확인은 구현자에게도 있다. 반대로 내부 파일·함수·구조를 Main이 모두 확정해 넘기지도 않는다.

### 구현자가 검토자에게 넘기는 결과

검토자가 받는 것은 동작하는 변경과 확인 근거다. 정상 경로조차 구현되지 않았다면 ‘구현 완료’가 아니라 현재 막힘과 필요한 검토를 구별해 넘긴다. 환경 때문에 실제 실행이 막혔다면 코드 검토는 진행할 수 있지만 실제 확인 완료로 표시하지 않는다.

- 기준점과 이번 변경이 포함된 코드 상태. 미커밋·신규 파일이 있으면 함께 식별하며 HEAD만 넘기지 않는다.
- 구현한 결과와 중요한 구조 선택·그 이유. 원요구·Spec·선택 기록에 직접 접근할 수 있게 한다.
- 실행한 검사·사용 장면, 결과와 환경, 아직 확인하지 못한 부분 및 알려진 문제.

긴 자기평가 보고서는 필요하지 않다. 검토자가 “다 맞게 구현했다”는 설명을 그대로 결론으로 받지 않도록 코드·원자료·실행 근거를 직접 읽게 한다. 쓰기를 검토자에게 넘긴 동안 구현자는 같은 변경을 동시에 고치지 않는다.

## 검토자는 무엇을 기준으로 수정하나

검토자의 목적은 **맡은 결과의 충분함과 개발 품질을 개선한 코드**를 넘기는 것이다. 다음은 검토 관점이며 각각 별도 agent나 순차 승인을 요구하지 않는다.

| 검토 관점 | 실제 판단 질문과 수정 예 |
| --- | --- |
| **요구·제품 동작** | 저장 실패 뒤 입력이 사라지는가? 기존 코드가 그렇게 동작해도 합의한 입력 유지와 어긋나면 고친다. 요청하지 않은 자동 저장을 추가했다면 계약에 맞게 바로잡는다. |
| **구조·인터페이스** | 화면마다 요청·갱신·오류 처리 순서를 알아야 하는가? 관련 책임을 모아 호출자가 알아야 할 순서와 실패 처리를 줄일 수 있는가? 추상화의 설정·예외가 더 복잡해지면 분리하지 않는다. |
| **검사의 질** | 저장 함수를 호출했다는 확인만 있고 실제 실패 후 입력 보존은 확인하지 않는가? 과도한 mock으로 실패를 숨기거나 내부 코드 모양만 검사한다면 결과·계약을 보는 검사로 고친다. |
| **실제 화면·결과와 근거** | 성공 화면만 있고 저장 중·실패·재진입이 누락됐는가? 제품 결정과 시각·조작 품질은 관련 실행 근거로 대조하고, 근거가 없으면 실제 확인하거나 미확인으로 남긴다. |

root/local 의무 기준은 모두 지키고, 추가로 필요한 상세 품질 기준은 검토자가 집중해서 사용한다. 모든 규칙을 처음부터 구현자에게 쏟아붓거나, 필요한 제품·구조 맥락까지 reviewer 전용으로 숨기는 양쪽을 피한다.

### 어디까지 직접 바꿀 수 있나

**직접 수정할 수 있는 범위:** 맡은 결과·품질을 충족하기 위한 내부 구조·호출부·오류 처리·테스트와 직접 연결되는 안내다. 여러 파일의 책임을 재배치하거나 인터페이스를 바꾸더라도 보존할 공개 계약과 맡은 범위를 지킬 수 있으면 검토자가 수행할 수 있다. 파일 개수나 단순/복잡이라는 이름으로 B를 국소 수정에 가두지 않는다. 이미 승인된 공개 계약 변경을 맡았다면 그 범위 안에서 구현할 수 있다.

가상 작업에서는 공통 저장 기능과 세 화면의 사용 방식을 함께 정리하고, 실패 때 입력을 지우던 결함과 검사 누락을 고칠 수 있다. 목표는 기존 코드 동작을 모두 보존하는 것이 아니라 **합의한 결과와 보존 계약**을 충족하는 것이다.

**Main으로 돌아갈 조건:** 근거를 더 읽고도 원하는 제품 동작이 미정이거나 충돌하는 경우, 사용자에게 약속한 범위·공개 계약·명시적 제외를 바꿔야 하는 경우, 작업 전체나 다른 Ticket의 책임·완료 기준을 바꾸는 경우다. 기존 저장 버튼을 자동 저장으로 바꾸거나 이 작업을 위해 공통 저장 정책 자체를 재설계해야 한다면 차이·영향·대안을 전달한다. Main은 이미 받은 권한으로 판단 가능한 것은 처리하고 사람의 선택이 필요한 것만 논의한다.

단지 같은 파일에서 발견했다는 이유로 무관한 개선을 편입하지 않는다. 하지만 맡은 결과가 불충분해지는 문제를 후속으로 넘겨 완료 기준을 낮추지도 않는다. 품질 수정마다 Main의 사전 승인을 받는 구조로 B를 다시 리포트 제출 절차로 만들지 않는다.

### 검토자가 반환하는 것

수정된 코드, 무엇을 왜 바꿨는지, 수정 후 실행한 검사·장면, 남은 판단과 확인 범위를 짧게 반환한다. 실제 발견이 없거나 바꾸지 않는 편이 낫다면 그 판단도 유효하다. 지적 개수나 diff를 만들기 위한 수정은 하지 않는다. 새 공통 기준·스킬·lint 정책의 채택을 품질 수정에 숨기지 않고 개선 후보로 분리한다.

## 마지막 실제 검증은 누가, 무엇을 확인하나

**기본 수행자는 원 구현자, 검증 범위의 충분함과 완료 판단 책임은 Main**으로 제안한다. Main이 구현을 직접 했으면 Main이 실행 확인도 맡는다. 검토자는 자신이 바꾼 부분에 필요한 자동 검사와 동작 확인을 먼저 마쳐야 하며, 마지막 검증 담당자에게 전부 미루지 않는다.

이 배치는 구현자가 확보한 앱 실행·데이터 준비·재현 맥락을 활용하고, 수정 당사자와 다른 주체가 최종 사용자 결과를 보는 데 이점이 있다. 구현자의 초기 판단에 종속될 수 있다는 한계도 있다. 공통 상태·권한·여러 세션의 결과를 새 관점에서 확인할 구체적 필요가 있으면 Main이 별도 검증자에게 맡긴다. 처음부터 항상 네 번째 역할을 추가하지 않는다.

최종 확인자는 검토자의 수정판과 관련 영향을 확인한 뒤 **동일한 최종 코드·실행 설정**으로 테스트 환경에서 다음을 수행한다. 이전 코드의 통과 결과로 대체하지 않는다.

| 가상 작업의 확인 장면 | 확인하려는 결과와 증거 |
| --- | --- |
| 값을 바꾸고 저장한 뒤 새로 진입 | 화면 내부 값만 바뀐 것이 아니라 저장된 값을 새로 읽어 같은 결과를 제공하는지 본다. |
| 저장 실패 후 재시도 | 실제 오류 경로에서 입력·선택이 유지되고 다시 저장할 수 있는지 본다. 실패 주입을 사용했다면 실제 서버 장애 관찰과 구별한다. |
| 저장 중 계정 전환 | 앞 계정의 늦은 결과가 새 계정의 표시·상태에 반영되지 않는지 본다. |
| 검토자가 바꾼 공통 경로의 소비처 | 대표 화면 외에 같은 저장 기능을 쓰는 화면도 계약을 지키는지 영향 범위에 맞춰 본다. |

초기 구현 확인을 무조건 전부 반복하지 않고, 최종 결과의 핵심 흐름과 수정이 영향을 준 경로를 다시 확인한다. 실행 결과에는 변경판·환경·조건·관찰 결과·미확인을 남긴다. 화면 캡처만으로 저장·데이터 무결성을, 자동 테스트만으로 화면의 실제 조작 품질을 입증하지 않는다. UI 없는 작업은 공개 API·명령·저장 결과 등 전달하는 인터페이스에서 같은 관계를 확인한다.

### 실패하거나 도구가 없을 때

최종 검증 담당자는 재현 조건·기대 결과·관찰 결과·근거를 돌려주며 같은 코드를 임의로 병행 수정하지 않는다. **품질 수정 단계의 쓰기 책임은 검토자에게 유지**해 수정·검사를 수행하고, 최종 확인자가 실패 장면과 관련 회귀를 다시 확인한다. 원 구현의 결함인지 검토자 수정의 결함인지 따져 책임을 미루지 않는다. 전체 구현을 다시 해야 할 정도로 맡을 결과가 바뀌면 Main이 재분해하고 명시적으로 인계한다.

앱·계정·데이터 등 실행 환경이 없으면 구현자가 가능한 경로를 확인하고 Main에 정확한 공백을 알린다. 코드 검토·자동 검사는 계속할 수 있지만 필요한 실제 확인을 통과로 바꾸지 않는다. 대체 근거가 충분한지, 별도 환경 준비나 사람의 실행이 필요한지는 Main이 결과의 성격에 따라 판단한다. 사람만 가능한 확인이 있다면 그 구체적인 동작과 이유를 남긴다.

검증 성공 후 코드를 다시 수정했다면 영향받는 근거를 갱신한다. 충분한 결과를 얻었으면 취향이나 새 개선거리를 찾아 무한 반복하지 않는다.

## Main이 최종적으로 받는 결과와 남은 설계

Main은 원요구와 결과를 대조하고, 검토자의 품질 개선 이유와 최종 실행 근거가 같은 변경판에 적용되는지, 목표를 막는 미해결이 남았는지 판단한다. 이미 수행된 전체 코딩·품질 검토를 다시 복제하기보다 계약의 변경·이견·관찰 공백에 집중한다. 사용자 보고는 결과·중요한 구조 선택·확인 근거·남은 판단으로 구성한다.

Spec·Ticket·state에는 선택과 실제 결과를, 재검토할 가치가 있는 대안·실패·검증은 records에 연결한다. 코드나 사용자 설명만으로 드러나지 않는 공통 제품·구조 지식은 Project Owner의 갱신 대상으로 판단한다. 이번 초안을 새 문서 양식이나 자동 Maintain으로 설치하지 않는다.

01-01은 위 연결을, 01-02는 실제 구조 대비와 수정 기준을, 01-03은 실제 대상의 실행 도구·시나리오·증거를 더 구체화해야 한다. B 방향 선택과 이번 세부 제안, 실제 적용 효과를 구별한다. 현행 제품 실행 명령을 확인하거나 앱을 실행한 결과는 아직 없다.
