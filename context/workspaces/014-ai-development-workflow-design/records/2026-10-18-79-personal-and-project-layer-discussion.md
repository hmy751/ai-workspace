# 개인 기준과 Project를 별도 층으로 둘지에 관한 논의

2026-10-18.78의 비교 뒤 사용자는 Main의 “무엇을 다루는가와 어디까지 적용하는가를 함께 본다”는 설명이 무슨 뜻인지 물었다. 이어 다음 생각에 대한 의견을 요청했다.

> 그래서 아예 project와 개인 기준의 층을 나눠야 되나? 라는 생각도 들어 여기에 대해서도 니 생각을 말해줘

이번 결과는 설명과 Main의 분리 추천이다. 사용자가 분리안을 채택하거나 실제 파일·전역 지침·읽기 장치를 변경하도록 요청한 것은 아니다.

## 앞선 설명을 실제 의미로 풀기

개인 기준 안에도 표현 규칙과 설계 판단이 있고, Project 기준 안에도 표현 규칙과 설계 판단이 있다는 뜻이었다.

- 중괄호를 항상 쓰는 개인 기준은 표현을 다룬다.
- 공통화할 때 사용처의 선택권·변경 비용을 보는 개인 기준은 설계를 다룬다.
- Noline의 통화 표시 관례는 그 제품의 표현을 다루며, 공유 schema·route·serializer의 책임 배치는 그 프로젝트의 설계를 다룬다.

따라서 개인 기준을 표현 취향에만 한정하거나 모든 설계 판단을 Project 고유 내용으로 묶지 않는다. 앞선 두 구분은 새로운 복잡한 분류 체계를 의무화하려는 말이 아니었다.

## Main의 의견: 우선 코드 기준에서 두 층의 책임을 분리하는 편이 좋다

**개인 기준은 프로젝트가 바뀌어도 가져갈 개발 기준을 소유하고, Project는 해당 제품·구현·팀에서 정한 구체적인 의미와 계약을 소유하는 방향을 추천한다.** 관련 작업에서는 두 내용을 연결해서 사용한다.

| 책임 | 넣을 내용의 예 | 유지할 이유 |
| --- | --- | --- |
| 개인 기준 | 중괄호·빈 줄 같은 표현 선택, 목적·사용처·변경 비용에 따른 공통화, 책임·계약·수명·이름에 관한 판단 | 프로젝트마다 같은 기준을 다시 작성하거나 서로 다른 사본으로 유지하는 부담을 줄이고, 사용자가 발전시킨 판단을 다른 프로젝트에도 이어 쓸 수 있음 |
| Project | 제품 정책·데이터 의미, 현재 구조와 실제 지원, 해당 API·저장·인증 계약, 채택한 코드·도구 규칙과 프로젝트별 적용 조건 | 제품·팀의 선택과 실제 구현을 그 프로젝트의 근거로 관리하고, 개인의 일반 판단이 구체 계약을 대신하지 않게 함 |

이 분리는01-02의 기준 본문을 모두 Project 안에 두는 배치가 확정이 아님을 보여 준다.01-02에서 얻은 기준 중 상당 부분은 개인 기준 후보로 다루고, Noline 가이드에 들어 있는 개인 공통 내용과 대조할 수 있다. 그러나 세 가이드 전체를 통째로 한쪽에 옮기지는 않는다. 리팩터링의 일반적인 작업 방법과 Noline의 구체적인 검사·사례도 역할이 다르다.

## 함께 사용할 때의 관계

예를 들어 “이름이 실제 역할을 드러내야 한다”는 개인 기준을 Noline 경비 화면에 적용할 때는, Project의 “화면 첫 통화 그룹과 여행 기본 통화는 다를 수 있다”는 의미가 필요하다. 개인 기준만으로 제품 값을 추정하지 않고, Project만 읽고 일반 코드 판단을 매번 새로 만들지도 않는다.

개인 기준은 별도 원문으로 관리하고 Project는 필요한 적용 관계와 구체 조건·예외를 설명하는 구성을 추천한다. 동일 본문을 매 Project에 복제하는 배치는 우선 추천하지 않는다. 다만 실제 읽기 접근성과 공유·이식 조건을 보지 않은 채 링크만으로 충분하다고 확정하지도 않는다.

개인 층을 분리한다는 사실이 모든 기준을 모든 작업의 기본 입력에 싣거나 항상 Project보다 우선한다는 뜻은 아니다. 예컨대 팀이 명시적으로 채택한 표현 규칙과 개인 선호가 다르면 해당 프로젝트의 합의를 우선하는 방향을 추천한다. 일반 품질 기준을 구체화한 프로젝트 선택인지 실제로 충돌하는지부터 구별하며, 개인 기준을 바꾸었다고 기존 프로젝트 코드 전체가 자동 수정되는 구조도 전제하지 않는다. 이는 Main의 운영 방향 의견이며 세부 우선순위 계약의 채택은 아니다.
