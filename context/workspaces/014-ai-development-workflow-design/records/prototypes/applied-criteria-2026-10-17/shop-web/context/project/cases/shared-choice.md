# 구체 판단 사례 — Field와 Container의 선택이 달랐던 조건

이 문서는 [공통 제공 범위와 사용처 선택 원칙](../quality.md#shared-choice)을 이해하고 다시 판단할 때 읽는다. **Field는 합성형, Container는 일체형이라는 분류를 외우는 문서가 아니다.** 두 사례에서 무엇을 공통으로 제공하려 했고 무엇을 달리할 필요가 있었는지 비교한다. 원칙의 현재 지위는 quality.md가 소유하며, 이곳은 당시 조건·판단·한계와 근거를 소유한다.

<a id="field"></a>

## Field — 구성 자유를 위해 의도적으로 나눈 사례

**관찰과 의도.** 2026-10-13에 읽은 template의 Field는 제목·입력 배치·라벨·설명·메시지를 조합하는 부품을 제공했다. 사용 예에서는 이름의 단일 입력과 이메일의 입력·선택창 조합이 있었고, 사용처가 React Hook Form과 오류 표시를 연결했다. 사용자는 다음과 같이 설명했다.

> 난 의도적으로 나눴어 그래야 확장성 유연성이 생긴다 보거든 디자인 변경이 있을때 저렇게 하나에 다 두면 어려울거라 봤어 위에 처럼 했어 그래서

**그때의 판단과 정정.** 연결 코드가 남아 있다는 사실을 공통화가 덜 끝난 상태로 읽어서는 안 된다. 배치·복수 입력·부품을 사용처에서 바꿀 수 있는 것이 당시 선택의 목적이었다. Main이 처음 제시한 ‘직접 연결 또는 배치까지 묶은 RHFTextField’ 두 안만으로 선택을 제한한 설명도 보완됐다. 화면 합성을 유지하면서 폼 연결만 공유할 수 있기 때문이다.

**현재 작업에서 다시 물을 것.** 줄이려는 반복이 같은 연결 책임인가, 화면별로 달라야 하는 구성인가? 연결을 공유해도 기존 Input과 다른 입력의 값·이벤트·ref·오류 계약을 유지할 수 있는가? 구성 자유를 실제로 쓰는 사용처가 있는가?

**열린 선택.** 특정 RHF 연결 API·Context 도입은 채택하지 않았다. 모든 래핑을 금지하거나 모든 연결을 직접 작성하기로 한 것도 아니다. 현재 작업의 사용처가 같은 형식·정책을 계속 공유한다는 근거가 있다면 그 범위의 편의 컴포넌트를 다시 검토할 수 있다. 필요가 약하면 연결 추상화 자체를 추가하지 않을 수도 있다.

[당시 코드 발췌·사용자 원문·Main의 해석과 정정](../../../../../../2026-10-13-35-field-composition-and-design-flexibility.md). 현재 구현을 고칠 때는 이 과거 기록과 별도로 대상 코드·호출부를 확인한다.

<a id="container"></a>

## Container — 공통 형식 자체에 가치가 있었던 사례

**관찰과 의도.** 2026-10-14에 다시 읽은 template에서는 감지 Hook이 이미 분리돼 있었고, Container가 이를 사용하며 데이터 펼치기·상태별 분기·하단 배치를 제공했다. 목록 내부 구성은 사용처에 열려 있었다. 사용자는 당시 일정한 디자인 형식과 필요가 있어 Container를 만들었고, 불필요해지거나 재사용 가치가 낮아지면 없앨 수 있다고 설명했다.

**그때의 판단.** Hook과 Container는 감지 재사용과 공통 화면 조합을 함께 제공할 수 있다. 자유도를 높인다는 이유만으로 Container를 제거하거나, 반복을 줄인다는 이유만으로 모든 표시 정책을 안에 넣는 결론은 나오지 않는다.

**선택이 바뀌는 조건.** 기존 목록을 오류 뒤에도 유지해야 하는 화면은 당시 Container의 기본 오류 분기와 요구가 달랐다. 그때에는 공통 계약을 바꿀 가치와 Hook을 직접 조합할 비용을 비교한다. 이 예는 새 요구를 가정한 대비이며 실제 제품 변경 결과가 아니다. 여러 사용처가 같은 새 정책을 필요로 한다면 공통 단위를 보완하는 쪽이 적합할 수도 있다.

[당시 대비 코드·사용자 설명·Hook 분리 확인](../../../../../../2026-10-14-37-infinite-scroll-container-and-hook-comparison.md). Container를 제거하는 일반 규칙이나 고정 재사용 횟수는 정하지 않았다.

## 두 사례를 다른 작업에 사용하는 방법

| 현재 확인한 조건 | 검토할 선택 | 이 사례만으로 정할 수 없는 것 |
| --- | --- | --- |
| 배치·입력 구성이 다르지만 같은 폼 연결이 반복됨 | 합성을 유지하고 같은 연결만 공유 | 연결 API, 입력별 변환, 실제 비용과 검증 결과 |
| 표시 형식·정책을 함께 제공할 필요가 확인됨 | 해당 범위의 공통 편의를 유지·보완 | 모든 화면에 같은 형식을 강제할지 여부 |
| 사용처 정책이 공통 기본값과 달라짐 | 계약 보완과 직접 조합을 비교 | 차이를 공통 옵션으로 받을 가치가 있는지 |

이 표는 조건별 후보이며 자동 판정표가 아니다. 현재 요구·코드·사용처를 대조해 선택하고, 과거와 다른 결론이면 무엇이 달라졌는지 남긴다. 새 사례가 기존 원칙의 설명을 바꿀 필요를 드러내면 해당 작업에서 후보와 근거를 기록하고 quality.md의 범위·문구도 다시 판단한다. 사례 하나의 결과를 바로 일반 규칙으로 올리지 않는다.

형식·분류를 다시 설계하는 담당자는 [후속 Ticket 재구체화 장면](../../../../refinement-walkthrough.md)에서 이번 과정의 어떤 근거를 다시 읽고 어디를 수정하는지 확인한다. 일반 구현 작업마다 전체 설계 기록을 읽도록 요구하지 않는다.
