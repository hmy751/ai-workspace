> 가상 적용 프로젝트의 문서 — 실제 프로젝트 지침이 아님.

# 개발 품질 판단

공통을 짧게 두고 이름·가독성을 독립 절로 찾는 **형식은 사용자 요청으로 이 시안에 반영했다.** 본문의 판단 방향은 사용자와 코드 사례를 논의하며 정리한 기준 후보이며, 모든 제품의 의무 규칙으로 채택한 것은 아니다. 사례는 특정 조건의 선택 이유를, 기능 문서의 현재 제품 계약은 이 시안에서 보존해야 할 약속을 담는다.

<a id="applying-principles"></a>

## 공통 — 현재 목적과 동작에서 시작한다

제품 목적과 이번 목표, 보존할 동작을 확인한다. 원칙·사례와 코드 모양이 다르다는 사실은 살펴볼 단서다. 현재 사용처·읽기와 변경 부담·비용으로 유지·수정·보류를 판단하고, 관련 구조 개선도 기대하는 이득과 동작 보존을 함께 본다. 이 적용 방식은 기준을 채택한 뒤에도 같다.

이름·타입·호출 흐름에서 책임과 결과를 예상할 수 있는지도 살핀다. [Project 읽기 안내](README.md#reading-route)에서 판단에 필요한 상세를 고른다. 원칙의 구별만으로 선택이 분명하지 않으면 연결된 사례로 내려간다. 질문마다 답안을 만들지 않고, 판단을 가른 이유와 확인·미확인을 작업 결과에 남긴다.

<a id="shared-choice"></a>

## 공통으로 제공할 것과 사용처에 남길 선택

공통 단위는 목적상 함께 제공할 형식과 동작을 맡고, 사용처마다 달라질 부분에는 필요한 선택권을 둔다. 반복을 줄이는 편의와 함께, 변경할 때 사용처가 알아야 할 계약과 공통 코드를 수정해야 하는 범위를 살핀다.

컴포넌트·Hook·업무 흐름을 공통화하거나 나누는 작업, 기존 공통 단위에 옵션을 더하는 작업, 사용처의 연결을 공통 코드 안으로 옮기는 작업에서 이 기준을 적용한다. 현재 구조가 목적에 맞으면 유지할 수 있고, 공통으로 제공할 필요가 사라지면 줄이거나 제거할 수도 있다.

### 무엇을 보고 판단하는가

- 함께 유지해야 할 형식·동작은 무엇이며, 현재 공통 단위는 어떤 편의를 제공하는가?
- 사용처마다 바뀔 배치·부품·정책은 무엇인가? 필요한 변경을 사용처에서 표현할 수 있는가, 공통 코드에 새 옵션과 분기를 추가해야 하는가?
- 연결을 줄이면 사용처에 필요한 제어와 이해할 계약은 어떻게 달라지는가? 책임 위치도 바뀐다면 [책임 배치](#responsibility)를 함께 본다.

같은 API를 호출한다는 이유만으로 서로 다른 업무 흐름을 묶지 않는다. 같은 업무 흐름이 확인되고 이번 수정과 직접 관련된다면 관련 구조 개선을 함께 할 수 있다. 이때 화면별 차이, 변경 비용과 기존 동작 보존을 확인한다. 작은 실험 범위이거나 확장이 적은 제품에서는 구조 개선보다 작은 수정이 적합할 수 있으며, 정확성에 필요한 수정은 별도로 판단한다.

### 원칙만으로 선택이 분명하지 않을 때

화면의 합성 방식과 폼 상태 연결 위치는 별개의 선택이다. 구성 자유를 유지하면서 반복 연결만 공유할 수 있다. 반대로 같은 형식·정책을 함께 제공할 필요가 있으면 이를 묶은 편의도 유효하다. 이 차이가 이번 판단의 쟁점이면 [Field·Container 사례](cases/shared-choice.md)를 읽는다. 여기에는 당시 목적, 사용자 정정, 다른 선택이 가능한 조건과 미정인 API가 있다.

업무 흐름을 묶을 경계가 불분명하면 [장바구니 주문과 바로 구매의 대비](cases/order-flow.md)를 읽는다. 같은 API인지와 같은 업무 흐름인지를 구별하고, 조건이 현재 사용처와 맞는지 확인한다.

이 원칙은 [Field의 사용자 의도와 Main의 일반화](../../../../../2026-10-13-35-field-composition-and-design-flexibility.md), [Container의 필요와 제거 조건](../../../../../2026-10-14-37-infinite-scroll-container-and-hook-comparison.md)을 함께 보고 정리했다. ‘합성형이 언제나 좋다’는 결론은 이 근거에서 나오지 않는다. 상세 원문은 기준의 뜻·적용 범위를 다시 정할 때 읽는다.

<a id="responsibility"></a>

## 책임을 어디에 둘 것인가

함수·컴포넌트·업무 흐름을 옮기거나 나눌 때, 맡는 일과 변경 이유를 확인한다. 하나의 책임 안에서도 읽기나 검증을 위해 함수가 나뉠 수 있고, 역할이 나뉘어도 가까이 읽는 전용 부품은 함께 놓을 수 있다. 함수 수·파일 수가 책임의 수를 정하지 않는다.

- 현재 단위가 조율할 일과 사용처가 선택할 일은 무엇인가?
- 기존 도구가 맡은 상태·검증·전송을 다시 소유하게 되는가, 필요한 업무 순서를 연결하는가?
- 옮긴 뒤 전체 흐름과 변경할 위치를 더 쉽게 찾을 수 있는가? 제거하거나 바꿀 때 다른 책임까지 함께 바뀌는가?

주문 흐름이 요청·캐시 갱신·장바구니 정리를 조율할 수 있어도, 화면 이동 정책까지 HTTP 전송 계층의 책임이 되는 것은 아니다. 공유할 범위는 [공통 편의·사용처 선택](#shared-choice), 이동으로 바뀔 동작은 [동작 계약·수명](#public-contract)에서 판단한다. 라이브러리 도입·래핑·제거 자체를 목표로 삼지 않는다.

이 구별의 근거는 [책임 단위·함수·물리적 배치31](../../../../../2026-10-13-31-criteria-roles-and-responsibility-interview.md)과 [목적·기존 도구 책임33](../../../../../2026-10-13-33-component-purpose-and-library-responsibility.md)이다. 상세 원문은 기준의 뜻과 적용 범위를 다시 정할 때 읽는다.

<a id="public-contract"></a>

## 공통 계약을 믿고 사용할 수 있게 한다

공통 모듈이 제공한다고 한 형태와 의미는 실제 성공·실패 경로에서도 유지되어야 한다. 사용처가 자신의 역할에 필요한 공개 계약을 아는 것은 자연스럽다. 다만 내부 처리 순서나 숨은 예외까지 알아야 올바르게 사용할 수 있다면, 사용처에 설명을 더하기 전에 계약과 구현을 함께 검토한다.

입력·반환·오류 의미를 바꾸거나, 상태·타이머·이벤트의 책임 위치를 옮길 때 적용한다. 공개 계약을 바꿀 의도가 없어도 실제 구현이 그 계약을 지키는지 검토할 때 사용한다. 호출 모양이 같아도 동작이 같다고 단정하지 않는다.

### 무엇을 보고 판단하는가

- 사용처가 기대하는 결과·오류·처리 수명은 무엇이며, 실제 경로에서도 그 의미가 유지되는가?
- 내부 실패가 다른 의미로 전달되거나, 이미 얻은 정보가 사라지는 경로가 있는가? 사용처가 이를 우회하려고 내부 구현을 알아야 하는가?
- 이번 목표에 필요한 수정과 새 요구가 있어야 할 확장을 구별했는가? 유지·수정·보류 판단을 확인할 동작은 무엇인가?

오류를 공통으로 제공한다면 같은 형태라는 것과 같은 의미로 사용할 수 있다는 것을 함께 확인한다. 응답을 읽지 못한 오류를 네트워크 연결 실패처럼 전달하거나, HTTP 실패 상태를 본문 해석 실패 때문에 잃는다면 사용처는 공통 계약을 신뢰하기 어렵다. 오류 클래스나 계층을 늘리는 것 자체가 해결은 아니다.

시간과 자원 정리는 수명을 소유한 책임에서 확인한다. 작업이 실제로 끝나는 시점과 관련 자원이 해제되는 시점이 맞는지, 실패하거나 중단된 경로에서도 정리되는지 살핀다. 어느 시점을 시작·완료로 보는지는 해당 기능의 계약에 따라 판단한다.

비동기 처리를 옮길 때는 호출 순서와 완료 순서를 구별한다. 캐시 갱신을 호출한 뒤 다음 처리를 하는 것과 갱신 완료까지 기다리는 것은 다른 약속이다. 기다림을 추가하면 화면 완료·로딩의 경계도 달라지는지 확인한다. [현재 주문 계약](order-workflow.md)의 대기 방식은 그 제품의 값이며 모든 작업의 일반 규칙이 아니다.

HTTP 클라이언트의 현재 구체 계약은 [http-client.md](http-client.md)를 따른다. 그 계약에 도달한 유지·수정·보류 판단과 검사 결과는 [HTTP-07 기록](../workspaces/http-error-contract/README.md)에 있다. 이 사례의 수정 목록을 모든 기능 작업에 일률적으로 적용하지 않는다.

이 방향에는 공통 오류의 형태·의미를 믿고 사용할 수 있어야 한다는 [사용자 동의와 비교 47](../../../../../2026-10-16-47-fetcher-error-contract-comparison.md)이 있다. 시간의 시작점에 따라 책임이 달라진다는 [Toast 사례 48](../../../../../2026-10-16-48-toast-state-and-timer-responsibilities.md)도 조건을 보충한다. 이 원칙에 대한 동의와 특정 오류 서비스·타이머 배치의 채택은 구별한다.

<a id="naming-readability"></a>

## 이름·가독성 — 정한 의미를 읽을 수 있게 한다

이름·타입·조건식·호출부를 만들거나, 읽기 어려운 이유를 검토할 때 적용한다. 사용처가 실제 역할·입출력·실패·완료 범위를 예상할 수 있는지 본다. 책임이나 동작 자체가 미정이면 [책임 배치](#responsibility) 또는 [동작 계약](#public-contract)에서 먼저 의미를 정한다.

- 이름과 타입이 실제 의미를 전달하는가? 읽는 사람이 구현 안쪽을 추측해야 하는 부분은 무엇인가?
- 표현만으로 충분한가, 짧은 설명이나 단위·경계의 표시가 함께 필요한가?
- 더 명확한 표현으로 줄일 오독·탐색 부담이 수정 비용에 비해 유효한가?

같은 장바구니 주문 구현에서 `useOrder`와 `useCartCheckout`은 역할을 얼마나 드러내는지 비교할 수 있는 후보 이름이다. 완료 callback도 주문 생성과 캐시 갱신 완료 중 무엇을 뜻하는지 설명해야 한다. 이름만 고쳐 실제 대기 동작의 문제를 해결했다고 판단하지 않는다. [주문 사례](cases/order-flow.md)에서 조건과 예시의 한계를 확인할 수 있다.

더 명확한 표현이 있다는 사실만으로 기존 이름을 모두 바꾸지 않는다. [isError 판단45](../../../../../2026-10-16-45-naming-readability-supplement.md)는 boolean이 더 분명하다는 선호와 당시 수정 필요성을 구별했다. 정해진 명명 규칙·줄 수·모든 상태의 boolean화를 이 사례에서 도출하지 않는다.
