# shop-web Project

shop-web은 상품을 살펴보고 장바구니에서 주문하는 소규모 상점의 React·TypeScript 웹 UI다. 화면마다 필요한 표현과 완료 처리를 유지하면서, 반복되는 UI 부품과 HTTP 요청 기반을 공유한다. 현재 규모에서 필요한 역할을 분명히 하고, 실제 요구가 생기는 범위를 기준으로 확장한다.

## 제품과 공통 코드의 경계

화면은 어떤 상품을 조회하고 가공할지, 어떤 안내를 표시할지, 성공 뒤 어디로 이동할지를 정한다. 공통 HTTP 클라이언트는 전송·응답 해석·오류 전달과 timeout을 맡는다. 요청 도구를 사용한다는 이유로 화면 정책까지 공통 클라이언트에 넣지 않는다.

UI 공통화는 제품의 디자인과 필요한 변화 범위를 따른다. Field는 제목·입력·설명·오류를 사용처에서 합성할 수 있게 제공한다. 무한 스크롤 Container는 여러 목록에서 공유할 표시 형식을 제공하고, 감지 Hook은 별도 책임으로 사용한다. 이 차이를 판단하는 기준은 아래 품질 문서에 있다.

이 문서의 제품 설명과 현재 구조는 가상 shop-web의 전제다. 과거 template 사례에서 사용자의 관점을 가져왔지만, 그 사례가 shop-web의 실제 상태를 증명하지는 않는다.

## 작업 단서로 필요한 자료를 고른다

지정 작업의 목표와 관련 기능의 현재 계약을 코드·호출부와 대조하고, [공통 적용 관점](quality.md#applying-principles)을 읽는다. 아래 표는 작업 중 생긴 판단에 맞춰 상세를 찾는 안내다. 같은 문서 안에 있다는 이유로 모든 상세와 사례를 순서대로 읽지는 않는다. 사례는 원칙의 구별만으로 현재 선택이 불분명할 때 읽고, 그 조건과 현재 사용처를 대조한다.

| 작업에서 마주친 판단 | 읽을 자료와 쓰임 |
| --- | --- |
| 반복을 줄이거나 공통 단위의 범위·사용처 제어를 정함 | [공통 편의·사용처 선택](quality.md#shared-choice). 화면 구성은 연결된 Field·Container 사례, 업무 흐름은 주문 대비 사례로 내려간다. |

| 입력·반환·오류·시간·완료 의미를 바꾸거나 기존 동작을 검토함 | [동작 계약·수명](quality.md#public-contract). 호출 모양이 같아도 완료·실패 의미가 같은지 확인한다. |

| 맡은 구현·검토 역할의 읽기·수정·검증·반환 절차 | [develop skill](../../.agents/skills/develop/SKILL.md) |

Project 문서는 여러 작업에서 계속 사용하는 제품 맥락과 현재 계약을 소유한다. 개별 작업의 목표, 변경 과정, 검사 결과와 미확인 사항은 해당 Workspace가 소유한다. 현재 계약을 수정한 작업자는 관련 문서를 함께 맞추며, 한 번의 수정 결과를 품질 기준의 새 의무로 자동 추가하지 않는다.

일반 원칙의 판단 방향, 구체 사례의 조건·근거, 현재 제품 계약을 구별한다. 사례를 읽었다는 사실만으로 현행 계약을 바꾸지 않는다. 기준의 범위·지위나 제품 계약을 바꿔야 한다면 작업 책임자가 선택할 근거와 영향을 반환하고, 채택된 현재 의미를 해당 정본에 반영한다. 누가 어느 범위의 채택을 결정하는지는 실제 적용 대상의 권한과 함께 정할 사항이다.
