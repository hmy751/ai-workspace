# 구체 판단 사례 — 같은 API와 같은 주문 흐름

[공통 제공 범위](../quality.md#shared-choice)의 구별만으로 장바구니 정리까지 묶을지 분명하지 않을 때 읽는다. 같은 API를 사용하는 두 화면과 같은 업무 흐름을 사용하는 여러 화면은 공유할 범위가 다를 수 있다. 이 문서는 그 조건 차이를 설명하며 현재 작업의 공유안을 대신 결정하지 않는다.

## 조건이 달라 결론도 달라질 수 있다

| 당시 장면 | 함께 보아야 할 조건 | 그때 검토한 공유 범위 |
| --- | --- | --- |
| 주문 기록49의 장바구니 주문과 바로 구매 | 주문 생성 API는 같아도 바로 구매는 장바구니를 정리하는 흐름이 아니다. | 요청·공통 캐시 무효화와 장바구니 업무 흐름을 구별한다. 같은 API라는 이유로 장바구니 정리와 화면 완료를 모두 묶지 않는다. |
| 관련 개선 기록52의 PC·모바일 주문 페이지와 빠른 주문 모달 | 세 화면 모두 현재 장바구니 전체를 주문하며 요청·관련 무효화·정리가 반복된다. 화면별 완료 표현은 다르다. coupons 무효화 누락을 함께 고쳐야 한다는 가정이다. | 이번 수정과 직접 관련된 공통화의 이득·비용·동작 보존을 함께 판단할 수 있다. 화면별 완료 선택은 구별한다. |

52의 사용자 판단은 관련 구조 개선을 이번 작업에서 고려할 수 있다는 뜻이다. 제품 전체 리팩터링이나 특정 Hook API를 채택한 것은 아니다. 같은 정책의 변경 위치·실수·탐색 부담을 줄일 이득과 추가 계약·연결·확인 비용을 비교해야 한다. 반복 횟수나 공유 가능성만으로 공통 단위를 만들지는 않는다.

## 현재 작업에 대입할 때

현재 사용처가 무엇을 주문하고 어떤 상태를 정리하는지 먼저 확인한다. ‘빠른 주문’이라는 이름만으로49의 바로 구매로 분류하지 않는다. 현재 제품이 작은 실험 범위이거나 실제로 같은 변경 책임을 묶을 이득이 약하다면, 각 화면을 직접 고치는 안도 비교할 수 있다.

공유 범위를 정했더라도 호출과 완료 의미는 별도로 확인한다.49의 예제는 orders·catalog 무효화를 호출한 뒤 완료를 기다리지 않고 장바구니 정리·이동을 이어 간다.52의 세 화면도 비대기라고 둔 것은 [주문 장면71](../../../../../../2026-10-18-71-order-reading-and-criteria-boundaries.md)의 추가 가정이다. 공통화하면서 대기를 새로 넣어도 된다는 근거가 아니다. 현재 값은 [주문 동작 문서](../order-workflow.md), 일반 구별은 [공개 계약](../quality.md#public-contract)이 소유한다.

## 판단의 근거를 다시 확인할 때

- [주문 기록49](../../../../../../2026-10-16-49-order-mutation-workflow-boundaries.md): 당시 코드 발췌, 서로 다른 주문 흐름의 대비, 요청과 업무 흐름의 경계.
- [관련 개선 기록52](../../../../../../2026-10-16-52-related-refactoring-and-product-scope.md): 세 화면이 같은 장바구니 흐름이라는 가정과 관련 구조 개선에 대한 사용자 판단, 비용·보존 조건.
- [주문 읽기 장면71](../../../../../../2026-10-18-71-order-reading-and-criteria-boundaries.md): 두 기록을 구별해 사용한 이유, 이번 시안에 추가한 비대기 가정, 표현과 동작 판단의 차이.

위 요약으로 조건 차이가 충분하면 매 작업마다 긴 원문을 모두 읽을 필요는 없다. 사용자 의도나 기준의 의미가 쟁점이면 해당 원문으로 내려간다. 문서 배치·읽기 경로를03에서 다시 판단할 때는 [후속 설계 장면](../../../../refinement-walkthrough.md)에서 이번 형식 선택의 이유도 함께 찾는다.
