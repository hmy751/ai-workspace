# 입력 연결을 줄이라는 요청에서 기준을 찾아 판단하는 장면

**형식과 판단 과정을 보여 주는 가상 장면이다.** 아래 의뢰·화면 관찰·코드 변경·검사 결과·역할 메시지는 새로 구성한 가정이다. 실제 사용자 발화와 당시 코드 관찰은 [Field 기록 35](../../2026-10-13-35-field-composition-and-design-flexibility.md)와 [Container 기록 37](../../2026-10-14-37-infinite-scroll-container-and-hook-comparison.md)에 있으며, 이 장면의 화면·결함을 그 기록에서 발견했다는 뜻이 아니다. 실제 제품 코드·테스트는 만들거나 실행하지 않았다.

비용을 비교하기 위한 추가 가정은 **반복이 기존 폼 도구의 짧은 값·오류 조회에 그치고, 함께 바꿔야 할 별도 정책이나 반복 때문에 생긴 실수·탐색 부담은 확인되지 않았다**는 것이다. 실제 코드에서 새로 확인한 사실이나 사용자 요구가 아니다. 이 조건에서는 공유 가능성만으로 공유를 선택한 최초 판단을 검토에서 되돌리는 모습을 보인다.

기존 [HTTP 장면](walkthrough.md)이 계약을 인수하고 검토자가 직접 수정하는 흐름을 보여 준다면, 여기서는 **기준을 찾고 조건을 확인하면서 여러 선택 중 하나를 고르는 모습**을 보인다. FIELD-01 Workspace와 요구 문서가 있는 것으로 가정하며, 읽을 초기 내용을 아래 발췌로 채웠다. **Field용 Workspace·Ticket·기록 파일 세트는 실제로 생성하지 않았다.** 본문의 발췌는 문서 읽기 장면을 보여 주는 자료이며 운영에서 Workspace를 생략하는 예외가 아니다. 실제 저장 위치·역할 호출 방식은 후속 Ticket에서 구체화할 대상이다.

## 1. Main은 요청과 범위를 전달한다

Main → 구현자:

> FIELD-01을 맡아 줘. 주문 입력 화면과 배송 정보 화면에 반복되는 입력 연결을 줄여 줘. 현재 보이는 구성, 입력 동작, 검증과 오류 안내는 유지해 줘.
>
> shop-web의 `AGENTS.md`에서 시작하고 구현 역할로 진행해 줘. 사용하는 곳을 확인해서 어느 부분을 함께 관리할지 판단해 줘. 변경 이유와 확인 결과를 검토자가 이어받을 수 있게 남겨 줘. 기존 화면 동작을 바꾸는 제품 선택이 필요하면 그 차이를 Main에 알려 줘.

이 의뢰에는 기준 이름, ‘합성형을 유지하라’는 해답, 특정 폼 연결 API가 없다. 보존할 결과와 맡은 역할만 전달한다. 지정 작업에서 읽는 초기 문서 내용은 다음과 같이 가정한다. 실제 저장하지 않은 파일에 링크하지 않는다.

**가정한 FIELD-01 Workspace README의 초기 발췌:**

> 주문 입력·배송 정보 화면의 입력 연결 중복을 줄이는 작업이다. 현재는 구현 전이며 구현자가 맡는다. 목표·범위·완료 조건은 이 Workspace의 Ticket에 있고, 초기 내용은 바로 아래와 같다. 구현·검토 기록은 각 역할의 변경 이유와 확인 결과를 소유한다.

**가정한 FIELD-01 Ticket의 초기 발췌:**

> **목표:** 두 화면의 입력 연결에서 같은 의미로 반복되는 부분을 찾아 관리 부담을 줄인다. 줄일 부분과 그대로 둘 부분은 현재 사용처를 보고 판단한다.
>
> **보존할 결과:** 현재 화면 구성, 입력값 처리, 검증 동작과 사용자에게 보이는 오류 안내를 유지한다.
>
> **범위:** 두 화면과 직접 관련된 연결을 다룬다. 디자인 통일·다른 폼 도구 도입·아직 없는 입력 지원은 이번 요구에 포함하지 않는다. 기존 제품 동작을 바꿀 필요가 생기면 차이와 영향을 Main에 돌린다.
>
> **완료 판단에 필요한 것:** 변경한 연결과 남긴 차이의 이유를 설명하고, 두 화면에서 영향받은 입력·검증·표시가 유지되는지 확인한다. 확인 결과와 미확인을 구별해 남기며, 구현 보고만으로 검토까지 완료 처리하지 않는다.

## 2. 구현자가 작업 단서로 읽을 기준을 고른다

구현자는 [AGENTS](shop-web/AGENTS.md)에서 [Project 안내](shop-web/context/project/README.md)와 지정된 FIELD-01 Workspace로 진입한다. 이 장면에서는 **위 README 초기 발췌를 읽고 그 안내로 Ticket 초기 발췌를 읽은 뒤**, [구현 역할](shop-web/.agents/skills/develop/SKILL.md#implement)을 확인한다. ‘입력 연결을 줄인다’는 요청이 공통 단위의 범위와 사용처 선택에 영향을 줄 수 있어 Project 안내에서 [일반 판단 기준](shop-web/context/project/quality.md#shared-choice)을 골라 읽는다.

그 기준은 답을 미리 정하지 않는다. 구현자는 ‘같이 제공할 편의가 무엇인가’, ‘사용처마다 달라지는 구성은 무엇인가’, ‘연결을 옮기면 어떤 제어가 바뀌는가’를 현재 사용처에서 확인할 질문으로 삼는다. 이어 [Field·Container 판단 사례](shop-web/context/project/cases/shared-choice.md)에서 서로 다른 선택이 나온 조건과 아직 결정하지 않은 것을 읽는다.

여기서 자료의 역할을 구별한다.

| 읽은 것 | 이 작업에서 사용하는 방식 |
| --- | --- |
| 일반 원칙·질문 | 사용자와 코드 사례를 논의하며 정리한 판단 후보다. 공통 편의와 사용처 선택을 함께 살필 관점으로 사용한다. ‘항상 나눠라’라는 보편 규칙으로 읽지 않는다. |
| Field 사례 | 디자인 변경의 자유를 위해 의도적으로 나눴다는 사용자 설명이 있다. 연결 코드만 보고 미완성 공통화라고 해석했던 방향을 경계한다. 현재 화면에도 같은 필요가 있는지는 다시 확인한다. |
| Container 사례 | 공유할 디자인 형식과 필요가 있을 때 공통 조합을 제공할 수 있다는 대비다. Field의 결론을 모든 공통 UI에 확대하지 않는다. |
| 이번 의뢰 | 기존 화면·입력·검증·오류 안내를 보존해야 한다는 이 작업의 요구다. 판단 후보와 달리, 바꾸려면 Main과 제품 선택을 다시 해야 한다. |

사례 요약으로 판단 조건을 이해할 수 있으면 과거 대화 전체를 읽지 않는다. ‘Field는 추상화가 덜 되어 연결이 남았다’는 해석이 다시 제기된다면, 사례에서 연결한 [35의 사용자 설명과 당시 해석 보정](../../2026-10-13-35-field-composition-and-design-flexibility.md)을 열어 이유를 확인한다. 기록 접근은 결론을 바꿀 의문이 생겼을 때의 재접근이다.

## 3. 현재 사용처와 대안의 비용을 비교한다

이 장면에서는 구현자가 다음을 관찰했다고 **가정한다**.

- 주문 입력 화면은 입력 하나와 설명을 배치한다. 배송 정보 화면은 입력과 선택 부품을 함께 놓고, 안내의 위치도 다르다.
- 두 화면은 같은 폼 도구에서 값과 오류 상태를 읽는 연결을 반복한다. 각 입력이 내보내는 이벤트를 값으로 바꾸는 방법과 오류 안내 문구에는 차이가 있다.
- 두 화면의 배치를 하나의 공통 형태로 맞춰야 한다는 제품 요구는 없다. 줄이려는 반복은 화면 전체보다 연결의 일부에서 확인된다.

아래 표는 최초 구현과 뒤의 검토에서 비교하는 같은 대안이다. 이 장면에서 폼 상태 관리는 이미 도구가 맡고 있다. 같은 도구를 호출하는 코드와, 우리 프로젝트가 함께 관리해야 할 정책·변경 책임은 구별한다.

| 대안 | 지금 조건에서의 이득과 비용 | 다른 선택이 될 조건 |
| --- | --- | --- |
| 배치·입력·폼 연결을 하나의 공통 필드로 묶는다 | 호출부를 짧게 만들 수 있지만 두 화면의 구성·안내 차이를 옵션과 분기로 다시 표현해야 한다. 현재 함께 관리할 화면 정책이 없어 이번 변경 비용을 정당화하기 어렵다. | 같은 디자인과 입력 계약을 함께 유지하는 것이 제품 요구이고, 필요한 차이를 그 계약 안에서 표현할 수 있을 때 다시 비교한다. |
| 각 화면의 연결을 그대로 둔다 | 짧은 도구 호출의 반복은 남는다. 대신 입력별 값 변환과 안내를 그 사용처에서 바로 읽을 수 있고, 별도 연결층의 계약을 배우고 유지할 비용이 없다. 현재 근거에서는 이 안이 적합하다. | 반복의 길이·실수·탐색 부담이나 여러 위치를 함께 바꿔야 하는 책임이 실제로 확인되면 공유의 이득을 다시 비교한다. |
| 화면 합성은 유지하고 동일한 폼 상태 연결만 공유한다 | 일부 호출을 감출 수 있다. 그러나 입력별 연결은 여전히 남고, 도구가 제공하는 조회 위에 별도 입력·반환 계약과 확인할 위치가 추가된다. 현재는 줄어드는 관리 부담보다 이 비용이 작다는 근거가 부족하다. | 공통 정책을 한곳에서 바꾸는 이득, 반복된 연결에서의 실수 감소, 읽고 찾는 부담 감소가 추가 계약의 비용보다 클 때 선택할 수 있다. |

최초 구현자는 화면 합성과 연결을 나누는 데에는 성공했지만, ‘공유할 수 있다’를 충분한 이득으로 보고 세 번째 안을 선택했다고 가정한다. 뒤의 검토자는 위 비용까지 대조해 두 번째 안으로 되돌린다. 일반 질문을 읽었다는 사실만으로 좋은 선택이 보장되지는 않는다. 공통 정책이 반드시 있어야 공유할 수 있다는 규칙도 아니다. 단순 연결이어도 줄이는 실수나 읽기 부담이 충분하다면 공유할 이유가 된다.

구체적인 Context·Hook·연결 컴포넌트 API는 이 예시로 채택하지 않는다. 구현 예에서 말하는 ‘연결 공유’는 같은 상태를 읽고 전달하는 책임 범위를 뜻하며, 최종 API는 실제 코드·사용처·확인 비용을 보고 정해야 한다.

## 4. 구현자는 최초 변경과 판단을 반환한다

구현자 → Main의 가상 전달:

> 두 화면의 배치와 입력 구성을 유지하고, 같은 폼 상태를 읽고 전달하는 연결을 함께 관리하도록 바꿨어. 서로 다른 입력 이벤트를 값으로 맞추는 부분은 각 사용처에 남겼어.
>
> 화면까지 묶으면 현재 차이를 공통 옵션으로 다시 넣어야 해서 선택하지 않았어. 같은 조회를 함께 관리할 수 있다는 이유로 연결만 공유했어. 다만 이 추가 연결층이 짧은 도구 호출보다 관리하기 쉬운지, 함께 바꿀 정책이나 줄어드는 실수가 있는지는 근거를 확보하지 못했어.
>
> 정상 입력과 기본 오류 표시를 기존 결과와 비교했다고 기록했어. 구현에서 바뀐 연결과 두 사용처를 함께 검토해 줘. 검토가 인수한 뒤에는 같은 부분을 동시에 수정하지 않을게.

이것은 최종 권고가 아니라 비용 비교가 부족했던 최초 판단이다. 공유 가능한 부분을 찾은 것과 그 부분을 공유할 이득을 확인한 것을 구별해 검토자에게 전달한다. 위 검사·변경도 가정이며 실제 통과 근거가 아니다.

## 5. B 검토자는 같은 요구와 현재 변경을 직접 대조한다

Main → 검토자의 가상 의뢰:

> 두 입력 화면의 연결 중복을 줄인 변경을 검토하고, 같은 요청 범위 안의 품질 문제는 직접 수정해 줘. 원요청과 구현 전달을 함께 보고, 실제 사용처의 기존 동작과 변경을 대조해 줘. 새 제품 정책이 필요하면 선택과 영향을 Main에 돌려줘.

검토자는 [검토 역할](shop-web/.agents/skills/develop/SKILL.md#review)에서 시작해 관련 기준을 선택한다. 구현자가 고른 구조를 정답으로 두지 않고 두 사용처를 대조한다. 이때 공유된 연결이 기본 오류 문구까지 선택하면서, 배송 화면이 원래 제공하던 오류 안내를 덮는 문제를 발견했다고 **가정한다**. 구현자는 이 결함을 미리 알려 주지 않았다.

검토자는 ‘연결 공유’라는 이름만으로 그 안의 책임이 적절하다고 판단하지 않는다. 오류 문구가 바뀐 문제와 함께, 그 부분을 제외하면 공유층이 짧은 도구 호출을 한 번 더 감싸고 입력별 연결은 그대로 남는다는 비용을 대조한다. 이 장면에서는 새로운 연결층을 제거하고 사용처의 기존 연결·안내를 복원하도록 직접 수정한다. 기존 안내 보존은 원요청에 있고 최초 공유 구조 자체는 요구가 아니다. 오류 안내를 새 디자인으로 통일하는 결정이라면 Main에 돌려야 한다.

검토자 → Main의 가상 반환:

> 연결부가 공통 오류 문구까지 고르면서 배송 화면의 기존 안내가 바뀌는 부분을 발견했어. 문구 선택을 밖으로 돌린다고 해도, 남는 공유층은 짧은 도구 조회를 감추고 입력별 연결은 그대로 요구해. 현재 자료에서는 그 추가 계약과 확인 위치를 유지할 만큼의 관리 이득이 확인되지 않았어.
>
> 이번에 추가한 연결층을 걷어 내고 사용처의 기존 연결·문구 선택을 복원했어. 수정 뒤 정상 입력과 기본 오류뿐 아니라 두 화면의 서로 다른 안내, 입력 부품별 값 연결, 기존 배치를 대조했고 이 장면의 보존 요구와 일치한다고 판단했어.
>
> 결과적으로 코드 중복은 줄지 않았고 이번 변경도 남기지 않았어. 보존 요구를 지킨 것과 반복 감소 목표를 달성한 것은 구별해야 해. 공유로 줄일 실제 부담의 근거가 부족하므로, 현행 유지 판단과 미충족 목표를 함께 반환할게. 같은 정책을 여러 곳에서 바꾸는 일이나 연결 실수·탐색 부담이 확인되면 다시 비교할 수 있어.

여기서 직접 수정은 **이번 화면별 안내의 차이, 기존 결과 보존 요구와 추가 연결층의 비용**에 따른다. 항상 오류 문구를 밖에 두거나 짧은 반복을 유지하라는 일반 법칙이 아니다. 다른 폼 도구나 아직 쓰지 않는 입력 부품의 교체 가능성까지 확인한 것도 아니다.

## 6. 결과를 남길 때 원칙·사례·관찰을 섞지 않는다

이 장면에서 남길 결과의 모양은 다음과 같다. 아래는 이 문서 안의 가상 결과 메모이며 별도 작업 파일을 만들었다는 뜻이 아니다.

> **이번 선택과 상태:** 최초 공유 변경은 검토에서 제거하고 두 화면의 기존 연결과 안내를 유지했다. 기존 동작 보존은 확인한 것으로 가정하지만 반복 감소 목표는 미충족이며 Main의 다음 판단으로 돌렸다.
>
> **선택 이유:** 배치·입력 계약·안내가 다르며, 공통으로 남는 부분은 기존 도구의 짧은 조회다. 호출을 감추는 것 외에 줄어드는 실수·탐색·변경 부담은 확인하지 못했다. 사용처별 연결이 남는 상태에서 추가 계약과 확인 위치를 유지할 이득이 부족하다.
>
> **다시 볼 조건:** 연결의 반복이 길어지거나 실수·탐색 부담을 만들 때, 같은 정책의 변경이 여러 사용처에 함께 필요할 때, 제품이 공통 디자인·안내를 채택할 때 공유의 이득과 비용을 다시 비교한다. 새 정책의 존재만을 공유의 필수조건으로 삼지는 않는다.
>
> **근거와 한계:** 일반 기준과 Field·Container 사례를 판단 관점으로 사용했다. 이번 관찰·수정·검사는 가상이며, 실제 적용 효과를 확인하지 않았다. Field의 사용자 의도와 당시 선택의 근거는 사례에서 원기록으로 재접근할 수 있다.

[일반 원칙](shop-web/context/project/quality.md#shared-choice)은 판단 관점으로, [구체 사례](shop-web/context/project/cases/shared-choice.md)는 조건·사용자 설명·미정인 선택을 이해하는 자료로 남는다. 이번 가상 선택을 거기에 ‘정답 사례’나 새 의무로 추가하지 않는다. 이후 기준·사례의 배치와 전달 방식을 판단할 때는 [64의 문제 제기](../../2026-10-17-64-applied-format-improvement-review.md)와 [65의 과정 재사용 요구](../../2026-10-18-65-criteria-status-and-cross-ticket-refinement.md)를 함께 보아, 왜 이 장면을 추가했는지와 아직 확인하지 않은 효과를 복원한다.

공유의 가능성과 이득을 다시 구별하게 된 이유는 [67의 비용 근거 재검토](../../2026-10-18-67-refined-prototype-improvement-review.md)에 있다. 이전 시안의 공유 결론도 이 근거에 따라 수정할 수 있으며, 결론을 바꾼 것 자체를 좋은 재판단의 증거로 삼지 않는다.

이 과정과 근거를 후속 Ticket이 다시 읽고 현재 시안의 판단을 바꾸는 형태는 [후속 설계에서 다시 구체화하는 장면](refinement-walkthrough.md)에서 이어 본다.
