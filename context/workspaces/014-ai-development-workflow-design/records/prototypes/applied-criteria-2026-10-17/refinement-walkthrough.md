# 03에서 이번 선택의 이유와 실제 사용 조건을 다시 대조한다

현재 시안은 사용자 요청에 따라 **짧은 공통 부분과 이름·가독성의 독립 절**을 반영했다. 일반 원칙·사례·현재 제품 계약은 역할을 구별하고, 상세 기준은 quality 한 파일의 절로, 조건별 사례는 별도 파일로 두었다. [반영 요청과 판단 기록72](../../2026-10-18-72-short-common-and-detail-prototype.md)에서 이번 선택의 범위와 이유를 읽는다.

아래는 03이 실제 Project와 기존 스킬에 대입할 때 사용할 재판단 요청과 반환 예시다. **03을 수행했거나 실제 읽기 효과를 확인한 결과는 아니다.** 새 조건을 확인한 결과에 따라 현재 구성을 유지하는 것도 유효한 결론이다.

## 후속 담당자가 받는 요청

> 현재 시안의 Project 입구·짧은 공통 기준·상세 절·조건별 사례·현재 계약을 실제 대상 Project와 기존 읽기 스킬에 대입해 줘. 주문 작업자의 장면에서 왜 이 배치를 선택했는지도 함께 봐줘.
>
> 공통을 짧게 둬도 필요한 관점을 알아차릴 수 있는지, 이름·가독성 절이 실제로 독립적인 판단에 쓰이는지, 상세와 사례를 같은 파일에서 읽는 편이 나은지 살펴줘. 이름·문서 수·읽기 순서는 실제 조건에 따라 다시 판단할 수 있어.
>
> 추천만 반환하지 말고 선택한 본문과 읽기 안내를 채워줘. 바꾼다면 무엇을 어느 정본에 반영할지, 유지한다면 어떤 근거로 충분한지 설명해줘. 이번 사용자 선택과 과거 판단 과정은 덮어쓰지 말고 새 조건과 구별해 남겨줘.

실제 대상의 문서와 스킬을 먼저 확인한다. 이 시안의 develop이 기존 read-project-context 등을 대체한다고 전제하지 않는다. [03의 범위](../../../current/tickets/03-project-context.md)와 [04-03의 실제 읽기·갱신 행동](../../../current/tickets/04-skill-improvements/04-03-context-skills.md)을 함께 맞춘다.

## 무엇을 왜 다시 판단하는가

현재 절 링크는 필요한 내용의 위치를 찾게 한다. 이것만으로 AI가 해당 절만 입력받거나 읽는 양이 줄었다고 보장하지 않는다. 실제 읽기 스킬이 전체 파일을 읽는지, 필요한 절을 선택할 수 있는지도03·04-03에서 확인하고 파일 분리의 이득·비용에 반영한다.

| 현재 선택 | 이 선택을 한 이유 | 03에서 다시 볼 조건과 가능한 반영 |
| --- | --- | --- |
| 공통은 적용 관점·읽기 단서까지 | 모든 작업에 주문·캐시·합성 사례를 먼저 읽히지 않으면서 목적·동작·비용·표현의 관점은 놓치지 않게 하려 했다. | 기준 제목을 미리 주지 않은 실제 요청에서도 필요한 상세를 찾고 적용하는지 본다. 빠진 관점은 공통이나 읽기 단서에 보완하고, 읽어도 쓰지 않는 설명은 상세로 옮긴다. 짧은 길이 자체를 성공으로 보지 않는다. |
| 이름·가독성은 같은 문서의 짧은 독립 절 | 책임·동작을 정한 뒤에도 표현의 정확성과 수정 필요성 판단이 남았다. 모든 주제에 같은 설명을 반복하지 않고 찾을 자리를 두려 했다. | 이름만 검토하는 작업과 기능 변경에서 실제로 별도 판단이 남는지 본다. 계속 계약 설명만 반복한다면 본문을 합칠 수 있지만, 표현 관점과 찾아갈 경로가 사라지지 않게 한다. 새 독립 파일은 사용·관리 조건이 뒷받침할 때 비교한다. |
| 상세 기준은 quality 한 파일의 절 | 읽기 입구를 하나로 두고 관련 절로 이동할 수 있다. 현재 시안만으로 파일 네 개의 필요성은 확인되지 않았다. | 실제 분량·함께 읽는 범위·갱신 주체가 다르면 분리를 비교한다. 같은 질문을 여러 절에서 다시 해결해야 하면 경계와 연결을 먼저 고친다. |
| 사례는 별도 파일, 원칙에서 조건부 연결 | 일반 기준과 특정 조건의 선택 이유를 구별하고 필요한 대비만 찾아가게 했다. | 같은 담당자가 늘 함께 읽고 고치는 짧은 사례라면 같은 문서의 구별된 절로 합칠 수 있다. 사례가 길거나 사용 시점이 다르면 분리를 유지한다. 과거의 선택이 현재 작업의 답을 대신하지 않게 한다. |
| 주문의 현재 동작과 이번 수정 요구는 기능 문서·Ticket에서 각각 소유 | ‘갱신 완료를 기다리지 않음’은 제품의 값이고, 쿠폰 누락 수정은 이번 목표다. 일반 기준이나 사례와 섞이면 동작 변경을 놓칠 수 있다. | 실제 정본 위치와 현재 코드의 일치, 작업 이후 갱신 담당을 확인한다. 쿠폰 수정을 마친 뒤 현재 계약은 실제 결과에 맞추고 당시 누락과 변경 이유는 Work 기록에 남긴다. |
| 읽기 안내는 Project README, 절차는 기존 스킬과 연결 | AGENTS·skill·Ticket마다 같은 분류 표를 복제하지 않으려 했다. | 실제 host와 스킬이 이 입구를 발견하는지, 겹치는 안내가 생기는지 확인한다. 안내 위치가 달라지면 같은 기준으로 가는 연결과 갱신 책임도 함께 바꾼다. |

## 실제 조건에 따라 반환이 달라지는 예

**함께 읽고 관리한다는 근거가 생긴 경우의 가상 반환:**

> 작은 Project에서 UI 공유 원칙과 짧은 Field·Container 사례를 같은 담당자가 함께 읽고 고친다는 조건을 확인했다고 가정하면, 사례를 quality의 별도 절로 옮기는 안을 제안할 수 있습니다. 일반 원칙과 사례의 지위는 유지하고, Project 입구와 관련 원칙의 사례 링크를 같은 문서의 사례 절로 바꿉니다. 주문 대비는 사용 시점이 달라 별도로 유지할 수 있습니다.
>
> 이름·가독성은 계약을 정한 뒤 표현을 고르는 판단이 남으므로 짧은 독립 절을 유지합니다. 파일을 하나로 합쳤다는 사실로 관점이나 지위까지 합치지는 않습니다. 실제 조건과 선택 이유는 새 기록에, 현재 본문과 경로는 Project 정본에 반영합니다.

이 예시의 ‘함께 읽고 관리함’은 새 설계 가정이다. 앞선66의 후속 장면도 ‘기준 두 개·항상 함께 읽기·같은 관리주체’를 가정해 사례 통합을 제안했다. 이제 시안은 네 상세 절과 주문 장면을 포함하므로, 그 가정을 현재 사용 사실로 이어받지 않는다. 확인한 사용 조건이 다르거나 통합의 이점이 없다면 **현재 분리를 유지하고 이유를 반환**한다.

통합을 선택할 때는 원칙의 사례 링크, Project 읽기 안내, 영향을 받는 작업 장면과 기존 스킬의 참조를 함께 맞춘다. 과거 기록의 원문과 당시 선택은 유지한다. 현재 시안에 위 통합안을 추가 적용한 것은 아니다.
