# 주문 작업에서 공통 관점·상세 기준·사례를 찾아가는 장면

**문서는 실제로 열어 볼 수 있지만 제품·작업은 가상이다.** 이 장면은 작업 전달과 구현 전 판단까지만 보여 준다. shop-web의 주문 코드·테스트는 없으며 수정·검사·검토가 끝난 결과를 만들지 않았다.

사용자는 이번 시안에서 공통 부분을 짧게 두고 이름·가독성을 별도 절로 두는 방향을 선택했다. 아래는 그 형식을 적용한 것이다. 상세 기준 전체의 채택이나 실제 읽기 효과의 입증을 뜻하지 않는다. 최초 구별과 가정은 [주문 장면71](../../2026-10-18-71-order-reading-and-criteria-boundaries.md)에 있다.

## 1. 같은 작업 경로와 역할을 전달한다

Main → 작업자의 가상 입력:

> shop-web의 `context/workspaces/order-coupon-refresh/` 작업을 develop의 구현 역할로 진행해 줘. 세 장바구니 주문 화면에서 사용한 쿠폰이 목록에 계속 남는 문제를 고쳐 줘. 기존 주문·장바구니 처리와 화면별 완료 방식은 보존해 줘.
>
> 이번 수정에 직접 관련된 반복은 함께 정리할 이득과 비용도 판단해 줘. 지정 작업의 요구와 현재 주문 설명을 코드·호출부와 대조하고, 무엇을 바꿀지와 유지할 동작, 추가 결정이 필요한 부분을 설명해 줘.

작업자는 [develop의 같은 작업 계약](shop-web/.agents/skills/develop/SKILL.md), [작업 README](shop-web/context/workspaces/order-coupon-refresh/README.md), [Ticket](shop-web/context/workspaces/order-coupon-refresh/ticket.md)에서 맡은 역할과 목표·범위를 찾는다. 별도의 ‘작업자용 요구’를 만들어 같은 목표를 다시 관리하지 않는다. 코드·호출부를 읽는 단계는 실제 적용에서 수행할 일이며 이 시안에서는 기록71의 가정과 일치한다고 놓았다.

## 2. 짧은 공통 관점과 현재 제품 계약으로 시작한다

[Project 읽기 안내](shop-web/context/project/README.md#reading-route)는 작업에서 생긴 의문을 어디에 연결할지 알려 준다. 작업자는 그곳에서 [공통 적용 관점](shop-web/context/project/quality.md#applying-principles)과 [현재 주문 동작](shop-web/context/project/order-workflow.md)을 찾는다.

공통 부분은 목적·현재 계약·사용처·비용으로 판단하고 이름·타입·호출 흐름의 의미도 살피도록 짧게 환기한다. ‘세 화면은 같은 장바구니 전체 주문이다’, ‘캐시 무효화 완료는 기다리지 않는다’는 값은 현재 주문 문서에 있다. 제품 값과 일반 관점을 같은 규칙으로 합치지 않는다.

읽기 안내는 Project README 한곳에서 관리한다. 아래 표는 그 안내를 이번 주문에서 사용한 결과이며, 모든 작업의 추가 읽기 목록이 아니다.

사례의 짧은 대비로 조건 차이를 이해하면 그 안의 긴 원문까지 모두 읽을 필요는 없다. 사용자 의도나 기준의 의미가 쟁점일 때 원자료로 더 내려간다. 이번 공유 판단 때문에 Field·Container·Toast의 전체 원문을 기본 입력으로 추가하지 않는다.

## 4. 이름·가독성은 의미를 정한 뒤에도 남는 판단을 맡는다

새 공통 단위가 장바구니 주문을 조율한다고 정했다면, 가칭 `useOrder`와 `useCartCheckout` 중 사용처가 범위를 더 쉽게 예상할 표현을 비교할 수 있다. 이름 하나에 모든 후속 처리를 넣기보다는 캐시·장바구니의 세부 약속을 짧은 설명과 타입에서 찾게 한다.

완료 callback도 가칭 `onCompleted`와, 주문 생성 성공 시 호출되고 캐시 재조회 완료는 보장하지 않는다고 설명한 `onCreated`를 비교할 수 있다. 이 이름들은 이번 표현 비교용 후보이며 특정 Hook·callback API를 채택하지 않았다.

여기서 재조회 완료까지 기다리도록 구현을 바꾸는 것은 이름 문제가 아니다. [공개 계약](shop-web/context/project/quality.md#public-contract)으로 돌아가 동작 변경의 요구와 영향을 판단해야 한다. 더 명확한 이름이 보인다는 이유로 기존 전체 이름을 바꾸지도 않는다. 이번에는 새 단위의 이름을 정하는 비용과 기존 API를 일괄 바꾸는 비용이 다르다.

## 5. 선택 이유와 아직 하지 않은 일을 함께 돌려준다

작업자 → Main의 가상 구현 전 반환:

> 세 장바구니 주문 화면의 coupons 무효화 누락을 수정할 계획이야. 같은 주문·정리 정책을 함께 관리하면 이번 수정의 변경 위치를 줄일 수 있어서 공통 흐름으로 묶는 안을 제안해. 세 화면을 새 단위에 연결하고 성공·실패·로딩을 다시 확인할 비용도 있어.
>
> 화면별 이동·모달 완료 선택은 사용처에 남길게. 무효화를 호출한 뒤 다음 처리로 가던 비대기 흐름도 보존할 거야. 새 단위는 장바구니 주문이라는 범위가 이름과 짧은 설명에 드러나게 할 계획이야.
>
> 쿠폰 호출 추가와 실제 목록 반영, 장바구니 정리, 각 화면 완료와 기존 실패·로딩을 확인해야 해. 아직 구현·검사를 수행하지 않았고 구체 Hook API도 정하지 않았어.

이 제안은 이번 조건에서의 선택이다. 작은 실험 제품이거나 같은 변경 책임을 묶을 이득이 확인되지 않으면 세 곳을 직접 고치는 안도 비교한다. 공통화 여부와 쿠폰 문제 해결 여부는 별도로 판단한다.

이후 검토를 맡긴다면 Main은 같은 `order-coupon-refresh/` 경로, develop의 [검토 역할](shop-web/.agents/skills/develop/SKILL.md#review), 실제 변경 범위와 구현 기록을 함께 전달한다. 검토자는 같은 Ticket·관련 기준·코드와 결과를 대조하며 구현자의 공유안을 정답으로 전제하지 않는다. 이 장면에는 아직 그 구현·검토 기록이나 완료 결과가 없다.

## 6. 형식 선택의 이유를03으로 넘긴다

이번에는 하나의 quality 문서 안에서 짧은 공통 부분과 필요한 상세 절을 찾아가고, 주문의 조건 대비는 별도 사례로 내려가게 했다. 이름·가독성은 표현만의 판단을 찾을 수 있도록 독립 절을 두었다. 이것을 파일 수·읽는 순서·영구 분류의 정답으로 고정하지 않는다.

03에서 실제 Project 규모와 기존 읽기 방식에 대입해 무엇을 유지·합치거나 나눌지, 어떤 이유와 원문을 다시 참고할지는 [후속 설계 장면](refinement-walkthrough.md)이 소유한다. 결과물뿐 아니라 공통을 짧게 둔 이유, 표현 관점을 놓치지 않으려는 이유, 사례가 현재 동작을 대신하지 않도록 한 구별도 함께 넘긴다.
