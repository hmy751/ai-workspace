# 기준과 작업 예시를 한 문서에서 읽기

형식 시안 B다. A의 작업 안내·기준 두 개·fetcher 전달과 판단 예시를 같은 순서와 같은 본문으로 모았다. 이 파일은 비교를 위한 생성 사본이며 따로 유지할 정본이 아니다. 시안 비교 기간에는 연결본을 고치면 이 통합본에도 반영한다. 실제 채택 때 두 사본을 함께 관리하자는 제안이 아니다.

**시연 상태:** 일반 원칙·질문은 후보이며, 아래 작업자·검토자 요청은 전달 형태의 예시다. 제품 코드 수정이나 실제 작업자 전송, 테스트 실행은 없다. fetcher 사례는 과거 관찰을 작업 상황으로 가정한 것이고 현재 소스 상태를 확인한 결과가 아니다. 실제 실행에는 대상 checkout·변경·실행 근거가 연결되어야 한다.

## 지금 어떤 판단이 필요한가

| 지금 작업에서 보이는 상황 | 읽을 기준과 이유 |
| --- | --- |
| 폼의 배치·입력 부품·연결 방식을 바꾸거나, 공통 UI에 옵션을 추가하려 한다 | [공통으로 제공할 것과 사용처에 남길 선택](#shared-choice). 반복을 줄이는 편의와 사용처의 제어 중 무엇이 바뀌는지 본다. |
| 여러 목록 화면에서 같은 상태 표시를 쓰거나 기존 Container를 없애려 한다 | [같은 기준의 Field·Container 대비](#component-cases). 기존 공통 형식의 가치와 새로운 화면 요구가 맞는지 비교한다. 바로 위 원칙·질문도 함께 읽는다. |
| 공통 API·결과·오류·자원 정리의 의미를 사용처가 믿고 써야 한다 | [공통 계약을 믿고 사용할 수 있게 한다](#trusted-contract). 실패 경로에서도 공개한 의미와 이미 얻은 정보가 유지되는지 본다. |
| fetcher의 오류 계약을 정비하는 작업을 시작하거나 검토한다 | [작업자에게 전달되는 요청](#implementer) 또는 [검토자에게 전달되는 요청](#reviewer). 이 작업의 보존 계약과 판단 중점을 기준에 연결한 예시다. |

작업에 해당하는 행이 여러 개면 관련 기준을 함께 읽는다. 제목이 익숙하지 않으면 [기준 두 개의 본문](#shared-choice)에서 적용 상황을 확인한다. 이 시안에 없는 제품·기술 판단은 현재 작업의 요구와 프로젝트 자료에서 확인할 부분이며, 두 기준으로 모든 품질 문제를 다룬다고 가정하지 않는다.

<a id="classification"></a>
## 분류와 작업 안내의 관계

기준은 **무엇을 판단하는가**에 따라 이름 붙였다. ‘공통으로 제공할 것과 사용처의 선택’, ‘공개 계약의 신뢰성’이 이번 두 주제다. UI·API라는 파일 종류나 구현·리뷰라는 단계가 기준 자체의 분류는 아니다. 같은 기준을 다른 코드와 역할에서 함께 사용할 수 있다.

위 표는 작업자가 쓰는 말에서 그 기준으로 찾아가는 안내다. 폼 연결과 Container 검토는 다른 작업이지만 같은 기준을 읽는다. 오류 계약을 고치다 책임 이동까지 필요해지면 두 기준을 같이 읽을 수 있다. 한 문서 안의 제목 링크만으로 충분한 경우에는 기준마다 파일을 나눌 필요가 없다.

프로젝트의 확인된 동작·제품 요구·이미 선택된 계약은 적용 조건이다. 일반 기준과 맞지 않아 보이면 그 조건과 변경 영향을 먼저 살피고, 합의된 제품 계약을 바꿔야 하는 선택은 작업 범위를 다시 판단한다. 일반 원칙만으로 제품 정책을 새로 정하지 않는다.

<a id="role-use"></a>
## 읽은 내용을 작업에서 사용하는 방법

구현자는 이번 변경에 관련된 질문을 코드·요구·사용처에 대입한다. 검토자는 같은 기준과 작업 계약을 사용해 구현자의 결론·변경·확인 근거를 다시 대조하고 필요한 품질 수정을 수행한다. 질문을 모두 사용자에게 되묻거나, 답변마다 전부 출력할 필요는 없다.

결과에는 선택을 바꾼 근거, 실제로 바꾼 것, 확인한 것과 남은 불확실성을 남긴다. 구체 전달문과 완료를 가장하지 않은 판단 예시는 [fetcher 작업 예시](#implementer)에 있다.

<a id="shared-choice"></a>
## 공통으로 제공할 것과 사용처에 남길 선택

**적용할 때:** 공통화·분리·제거를 검토하거나, 현재 공통 부품이 새로운 사용처의 요구에도 맞는지 판단할 때.

공통 단위는 목적상 함께 제공할 형식과 동작을 맡고, 사용처마다 달라져야 하는 부분에는 필요한 선택권을 둔다. 반복을 줄이는 편의와 함께, 변경할 때 사용처가 알아야 할 계약과 공통 코드를 수정해야 하는 범위를 살핀다. 연결 코드가 있다는 사실만으로 합치거나, 자유도를 늘린다는 이유만으로 기존 공통 형식을 해체하지 않는다.

현재 작업에서 확인할 질문:

- 함께 유지해야 할 형식·동작은 무엇이며, 현재 공통 단위가 어떤 편의를 제공하는가?
- 사용처마다 바뀔 배치·부품·정책은 무엇이며, 필요한 변경을 어디에서 할 수 있는가?
- 연결 코드를 줄이거나 책임을 옮기면 기존 도구의 책임과 사용처의 제어가 어떻게 달라지는가?

질문은 작업의 실제 요구와 사용 코드를 확인하기 위한 것이다. 가상의 모든 확장에 대비하는 구조를 만들라는 요구는 아니다.

<a id="component-cases"></a>
### 같은 기준이 다른 선택으로 이어지는 사례

| 사례와 조건 | 그 조건에서의 판단 | 판단이 달라질 때 |
| --- | --- | --- |
| Field: 배치·설명·오류 위치·복수 입력을 디자인 변경에 맞춰 조합하려고 부품을 의도적으로 나눴다 | 사용처가 부품을 조합할 수 있는 구조를 유지한다. 연결 코드의 줄 수만으로 일체형 입력을 개선이라고 보지 않는다. | 반복되는 연결을 줄이면서도 합성·입력 교체가 가능한 대안이 있다면 따로 비교할 수 있다. 모든 래핑이나 공유 연결의 금지는 아니다. |
| InfiniteScrollContainer: 당시 공통으로 제공할 디자인 형식과 상태 표시가 필요했다. 감지 Hook은 이미 분리되어 있다 | 같은 표시 정책을 쓰는 화면에는 Container의 편의가 유효하다. Hook과 Container가 서로 다른 책임을 맡으며 공존할 수 있다. | 이미 읽은 목록을 유지하며 추가 조회 오류를 표시하는 등 기존 정책과 다른 요구가 생기면, 공통 정책 확장과 Hook 직접 조합을 비교한다. |

화면의 합성 방식과 폼 상태·오류를 어디서 연결하는지는 별개의 선택이다. 합성형 API를 유지하면서 연결을 공유할 수도 있다. 특정 새 연결 API의 채택은 이 기준으로 정해지지 않는다.

### 작업 요청에 실리는 모습

설명용 작업 요청:

> 이메일 입력 영역의 설명·오류 표시 위치를 새 디자인에 맞게 바꿔 줘. 기존 Field 부품과 입력 교체 가능성, 폼 도구의 상태·검증 의미를 유지해 줘. 위 ‘공통으로 제공할 것과 사용처에 남길 선택’을 읽고, 사용처의 조합으로 해결되는지 먼저 확인해 줘. 공통 연결을 바꾸는 편이 낫다면 보존되는 자유도와 변경 영향을 근거로 설명해 줘.

같은 기준을 읽고 Container를 사용하는 작업이라면 요청의 중점이 달라진다.

> 기존 목록과 같은 상태 표시 정책을 쓰는 상품 목록을 추가해 줘. 현재 Container가 제공하는 공통 형식과 필요한 화면별 선택을 확인해 줘. 공통화나 분리 자체를 목표로 삼기보다 이번 요구를 충족하는 범위를 판단해 줘.

두 요청에서 읽는 기준은 같다. 첫 요청은 배치·교체 자유도 보존을, 두 번째는 실제로 공유하는 형식과 화면별 선택을 확인하게 한다. 사용자의 모든 코드에 같은 구조를 적용하는 요청이 아니다.

**이 본문의 근거와 지위:** Field의 의도적 합성과 Container의 당시 필요는 사용자 설명이다. 질문과 일반화 문장은 이를 전달하기 위한 Main의 후보 표현이다. [Field 원문 35](../../2026-10-13-35-field-composition-and-design-flexibility.md), [Container 원문 37](../../2026-10-14-37-infinite-scroll-container-and-hook-comparison.md). 과거 의도를 다시 확인할 때 이 기록을 읽으며, 보통 작업마다 전체 대화를 읽게 하지는 않는다.

<a id="trusted-contract"></a>
## 공통 계약을 믿고 사용할 수 있게 한다

**적용할 때:** 공통 모듈의 입력·결과·오류·자원 수명을 추가하거나 바꾸고, 사용처가 그 의미에 의존할 때.

공통 모듈이 제공한다고 한 형태와 의미를 사용처가 믿고 쓸 수 있는지 확인한다. 사용처가 자신의 역할에 필요한 공개 계약을 아는 것은 자연스럽다. 내부 처리 순서나 숨은 예외까지 알아야 올바르게 사용할 수 있다면 계약과 구현을 함께 검토한다. 오류 종류나 구조를 늘리는 것 자체가 개선은 아니다.

현재 작업에서 확인할 질문:

- 사용처가 기대하는 결과·오류·처리 수명은 무엇이며, 실제 경로에서도 그 의미가 유지되는가?
- 내부 실패가 다른 의미로 전달되거나, 이미 얻은 정보가 사라지는 경로가 있는가?
- 이번 목표에 필요한 수정과 별도 요구가 있어야 할 확장을 구별했는가?

### fetcher에 적용하면

공통 오류 처리를 신뢰할 수 있게 정비하는 작업에서는 작은 공통 요청 구조와 기존 호출·정상 반환 계약을 유지할 수 있다. 본문 읽기·파싱 실패가 다른 오류로 바뀌는지, HTTP 상태가 사라지는지, timeout이 본문 처리까지 이어지고 정리되는지는 목표와 직접 관련된 확인 대상이다.

자동 재시도·인증 이동·공통 토스트·모든 응답의 스키마 검증·대규모 오류 클래스 분리는 별도 필요를 확인할 확장이다. 단순히 오류와 관련 있다는 이유로 이번 작업에 포함하지 않는다. 다른 작업에서는 목표와 기존 계약에 따라 이 범위가 달라진다.

이 질문의 답을 말로만 남기지 않고, 이번에 바뀌는 실패 경로와 보존할 경로를 실제로 확인할 항목으로 연결한다. 구현·검토 요청에 어떻게 실리는지는 [fetcher 작업 예시](#implementer)에서 읽는다.

**이 본문의 근거와 지위:** 사용자는 공통 오류 계약을 믿고 사용할 수 있어야 한다는 기준과 [리뷰 판단 연습 53](../../2026-10-16-53-fetcher-review-decision-rehearsal.md)의 판단 수준을 수용했다. 그 연습의 세부 구현·실행 효과가 승인되거나 검증된 것은 아니다. [종합 54](../../2026-10-16-54-code-quality-criteria-and-remaining-work.md)는 다른 사례와의 관계를 확인할 때 읽는다.

<a id="implementer"></a>
## 작업자가 받는 요청

> **할 일:** 공통 fetcher에서 사용처가 오류의 형태와 의미를 믿고 처리할 수 있도록 오류 경로를 정비해 줘. 먼저 현재 fetcher와 대표 호출부를 읽고, 아래 보존 계약과 맞는지 확인해 줘.
>
> **보존할 계약:** get/post/put/delete 호출 방식, 정상 JSON·문자열 반환, 기본 URL·헤더·10초 timeout을 유지해 줘. 상품 가공·토스트·화면 이동 같은 화면 정책은 사용처에 둬.
>
> **읽을 기준과 중점:** [공통 계약을 믿고 사용할 수 있게 한다](#trusted-contract)를 읽어 줘. 본문 읽기·파싱 실패가 공통 오류 계약을 거치는지, HTTP 실패의 본문도 깨졌을 때 이미 받은 상태가 남는지, timeout이 본문 처리를 포함하고 완료·실패 때 정리되는지 살펴봐. 실패 원인의 구별을 특정 오류 클래스 개수로 제한하지는 않아.
>
> **변경 범위:** 이 목표에 직접 필요한 수정과 확인을 해 줘. 자동 재시도·인증 이동·공통 토스트·호출자 취소 지원 확대는 이번 목표에 포함하지 않았어. 기존 계약을 바꿔야 해결되는 문제가 보이면 근거와 영향을 먼저 알려 줘. 예상과 다른 책임 이동이 필요하면 [공통 단위와 사용처의 선택](#shared-choice)도 함께 대조해 줘.
>
> **검토자에게 남길 것:** 중요한 변경과 이유, 바꾸지 않은 것 중 판단이 필요한 부분, 실제 확인한 동작·방법·결과, 미확인과 막힌 점을 전달해 줘. 기준의 질문 전체를 답안으로 반복하기보다 변경·판단·확인 근거가 이어지게 써 줘.

이 요청문에는 기준 본문 전체 대신 **작업 목표·보존 계약·이번 중점과 원본 링크**가 들어간다. 보존 계약은 작업자가 반드시 알아야 하므로 링크 뒤에만 두지 않는다. 중점이 모든 결함의 목록인 것은 아니며 현재 코드와 요구를 확인할 책임은 남는다.

<a id="reviewer"></a>
## 검토자가 받는 요청

아래 요청은 구현이 끝난 뒤 같은 작업 정의와 실제 변경·실행 근거를 함께 전달하는 형태다. 이 시안에는 실제 diff나 테스트 결과가 없다.

> **역할:** 이 작업의 오류 계약을 기준으로 변경을 검토하고, 목표·보존 계약 안의 품질 문제는 직접 수정해 줘. 구현자의 설명은 검토할 주장으로 보고 코드·호출부·실행 근거와 대조해 줘.
>
> **작업 맥락:** 바로 위 작업자 요청의 목표·보존 계약·변경 범위를 함께 전달한다. 실제 작업에서는 구현자의 변경 diff, 변경 이유, 실행 명령과 결과, 미확인 항목도 여기에 연결한다.
>
> **읽을 기준:** [공통 계약을 믿고 사용할 수 있게 한다](#trusted-contract). 본문 실패가 전달되는 의미, HTTP 상태 보존, timeout의 범위와 정리를 살펴봐. 정상 동작과 화면 정책 분리가 유지되는지도 확인해 줘. 구조를 옮겼다면 [공통 단위와 사용처의 선택](#shared-choice)도 대조해 줘.
>
> **수정과 확인:** 근거가 확인된 품질 문제는 범위 안에서 수정하고 관련 경로를 다시 확인해 줘. 오류 전달을 한곳으로 모았다는 사실만으로 완료로 판단하지 말고, 200의 깨진 JSON·500의 깨진 JSON·본문 읽기 중 timeout처럼 의미가 갈리는 경우를 확인해 줘. 보존 계약 변경이나 새 기능 선택이 필요하면 이유·대안과 함께 Main에 돌려줘.
>
> **반환:** 유지할 판단, 실제 수정, 보류한 확장과 이유, 확인 방법·결과·남은 한계를 설명해 줘. 수행하지 못한 검사는 미실행으로 남겨 줘. 구현자가 보고한 확인과 검토자가 직접 한 확인을 구별해 줘.

검토자에게 ‘원하는 결론’을 미리 주입하기보다 같은 계약과 기준, 실제 변경을 준다. 직접 수정과 관련 재확인은 이 시안의 연결 제안이며, 모든 최종 acceptance를 검토자가 단독으로 소유한다고 정한 것은 아니다.

<a id="decision-example"></a>
## 읽은 기준이 판단과 확인으로 이어지는 예

다음은 기록 53의 판단을 결과 형식에 넣은 **미실행 예시**다. 실제 작업자의 제출물·검토자의 발견·수정 결과가 아니다.

| 판단 | 기준을 적용한 이유 | 수정한다면 확인할 것 | 현재 증거 상태 |
| --- | --- | --- | --- |
| 호출 방식·정상 반환·작은 공통 구조 유지 | 신뢰할 계약이 목표이며 구조를 크게 만드는 것은 목표가 아니다 | 정상 JSON·문자열 반환, 기존 호출과 화면 정책 분리 | 과거 판단 예시. 이번 시안에서 실행 안 함 |
| 본문 읽기·파싱 실패 처리 보완 | 사용처가 내부 rejection 경로를 알아야 오류 의미를 해석하는 부담을 줄인다 | 200 응답의 깨진 JSON이 네트워크 실패와 구별되는지, 본문 중 timeout 의미를 덮지 않는지 | 수정 후보. 미구현·미실행 |
| HTTP 상태 보존 보완 | 실패 본문이 깨져도 이미 받은 HTTP 상태는 유효한 정보다 | 500+깨진 JSON에서 상태와 읽기 실패 근거가 남는지, null 등 본문 형태도 안전하게 처리되는지 | 수정 후보. 미구현·미실행 |
| timer 수명·정리 보완 | timeout 계약은 헤더 수신 뒤의 본문 처리에도 관계한다 | 본문 읽기 중 timeout, 완료·실패 뒤 정리 | 수정 후보. 미구현·미실행 |
| 재시도·인증 이동·공통 토스트 확대 보류 | 사용처 정책과 새로운 요구를 공통 오류 정비에 섞지 않는다 | 별도 요구가 생기면 계약과 책임을 다시 비교 | 보류 판단 예시 |

실제 보고에서는 이 표를 모두 채우는 대신, 중요한 판단을 짧은 문장으로 전달할 수도 있다. 예를 들어 “호출·정상 반환은 유지하고 HTTP 상태가 사라지는 오류 경로를 보완했다”라고 말하려면 실제 변경과 해당 확인 결과가 있어야 한다. 이 시안의 ‘수정 후보’를 ‘수정 완료’로 복사하지 않는다.

<a id="record-use"></a>
## 사용자가 판단을 바꾸려 할 때

- “이번 작업에서는 인증 이동도 필요하다”는 요청이면 작업 목표·범위와 제품 정책을 다시 판단한다. 공통 기준 자체가 곧바로 틀린 것은 아니다.
- “우리 프로젝트의 공통 fetcher가 화면 정책도 맡기로 했다”는 확인된 선택이면 Project의 계약 설명과 해당 작업 입력을 바꾼다. 다른 프로젝트까지 자동으로 같은 규칙으로 만들지 않는다.
- “이 질문은 계속 엉뚱한 판단을 유도한다”는 관찰이 쌓이면 [기준 본문](#trusted-contract)의 설명·조건·질문을 보완하고 근거 사례를 남긴다.

이번 작업의 실제 결과와 미확인은 작업 기록에, 여러 작업이 공유할 확정 계약은 Project 설명에 연결하는 안이다. 보존할 원문·대안은 상세 기록에 둘 수 있다. 한 번의 적용 결과를 자동으로 공통 원칙으로 승격하거나 새 갱신 자동화를 설치하는 제안은 아니다.
