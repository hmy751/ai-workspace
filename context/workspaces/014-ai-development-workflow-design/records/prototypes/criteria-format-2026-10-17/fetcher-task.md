# fetcher 작업에서 기준을 전달하고 사용하는 모습

**시연 상태:** 기록 53의 ‘공통 오류 계약 정비’ 작업을 가정한 전달문이다. 아래 요청문은 향후 작업에 전달될 형태를 보여 주며 지금 다른 작업자에게 전송하거나 제품 코드를 수정하지 않았다. 당시 코드 관찰을 현재 코드의 상태로 단정하지 않는다. [기준 찾기](start.md) · [전체 시안 비교](../../2026-10-17-62-criteria-format-prototype.md)

실제 작업으로 사용할 때는 대상 checkout·변경 범위·현재 코드·실행 환경이 연결되어야 한다. 여기서는 역사적 사례의 `src/api/fetcher.ts`와 호출부를 대상으로 삼았다고 가정하며, 실제 경로·diff·실행 결과를 꾸며 넣지 않는다. ‘검토자가 품질 수정까지 한다’는 B 방향만 기존 선택이고, 세부 요청문은 이번 시안이다.

<a id="implementer"></a>
## 작업자가 받는 요청

> **할 일:** 공통 fetcher에서 사용처가 오류의 형태와 의미를 믿고 처리할 수 있도록 오류 경로를 정비해 줘. 먼저 현재 fetcher와 대표 호출부를 읽고, 아래 보존 계약과 맞는지 확인해 줘.
>
> **보존할 계약:** get/post/put/delete 호출 방식, 정상 JSON·문자열 반환, 기본 URL·헤더·10초 timeout을 유지해 줘. 상품 가공·토스트·화면 이동 같은 화면 정책은 사용처에 둬.
>
> **읽을 기준과 중점:** [공통 계약을 믿고 사용할 수 있게 한다](principles.md#trusted-contract)를 읽어 줘. 본문 읽기·파싱 실패가 공통 오류 계약을 거치는지, HTTP 실패의 본문도 깨졌을 때 이미 받은 상태가 남는지, timeout이 본문 처리를 포함하고 완료·실패 때 정리되는지 살펴봐. 실패 원인의 구별을 특정 오류 클래스 개수로 제한하지는 않아.
>
> **변경 범위:** 이 목표에 직접 필요한 수정과 확인을 해 줘. 자동 재시도·인증 이동·공통 토스트·호출자 취소 지원 확대는 이번 목표에 포함하지 않았어. 기존 계약을 바꿔야 해결되는 문제가 보이면 근거와 영향을 먼저 알려 줘. 예상과 다른 책임 이동이 필요하면 [공통 단위와 사용처의 선택](principles.md#shared-choice)도 함께 대조해 줘.
>
> **검토자에게 남길 것:** 중요한 변경과 이유, 바꾸지 않은 것 중 판단이 필요한 부분, 실제 확인한 동작·방법·결과, 미확인과 막힌 점을 전달해 줘. 기준의 질문 전체를 답안으로 반복하기보다 변경·판단·확인 근거가 이어지게 써 줘.

이 요청문에는 기준 본문 전체 대신 **작업 목표·보존 계약·이번 중점과 원본 링크**가 들어간다. 보존 계약은 작업자가 반드시 알아야 하므로 링크 뒤에만 두지 않는다. 중점이 모든 결함의 목록인 것은 아니며 현재 코드와 요구를 확인할 책임은 남는다.

<a id="reviewer"></a>
## 검토자가 받는 요청

아래 요청은 구현이 끝난 뒤 같은 작업 정의와 실제 변경·실행 근거를 함께 전달하는 형태다. 이 시안에는 실제 diff나 테스트 결과가 없다.

> **역할:** 이 작업의 오류 계약을 기준으로 변경을 검토하고, 목표·보존 계약 안의 품질 문제는 직접 수정해 줘. 구현자의 설명은 검토할 주장으로 보고 코드·호출부·실행 근거와 대조해 줘.
>
> **작업 맥락:** 바로 위 작업자 요청의 목표·보존 계약·변경 범위를 함께 전달한다. 실제 작업에서는 구현자의 변경 diff, 변경 이유, 실행 명령과 결과, 미확인 항목도 여기에 연결한다.
>
> **읽을 기준:** [공통 계약을 믿고 사용할 수 있게 한다](principles.md#trusted-contract). 본문 실패가 전달되는 의미, HTTP 상태 보존, timeout의 범위와 정리를 살펴봐. 정상 동작과 화면 정책 분리가 유지되는지도 확인해 줘. 구조를 옮겼다면 [공통 단위와 사용처의 선택](principles.md#shared-choice)도 대조해 줘.
>
> **수정과 확인:** 근거가 확인된 품질 문제는 범위 안에서 수정하고 관련 경로를 다시 확인해 줘. 오류 전달을 한곳으로 모았다는 사실만으로 완료로 판단하지 말고, 200의 깨진 JSON·500의 깨진 JSON·본문 읽기 중 timeout처럼 의미가 갈리는 경우를 확인해 줘. 보존 계약 변경이나 새 기능 선택이 필요하면 이유·대안과 함께 Main에 돌려줘.
>
> **반환:** 유지할 판단, 실제 수정, 보류한 확장과 이유, 확인 방법·결과·남은 한계를 설명해 줘. 수행하지 못한 검사는 미실행으로 남겨 줘. 구현자가 보고한 확인과 검토자가 직접 한 확인을 구별해 줘.

검토자에게 ‘원하는 결론’을 미리 주입하기보다 같은 계약과 기준, 실제 변경을 준다. 직접 수정과 관련 재확인은 이 시안의 연결 제안이며, 모든 최종 acceptance를 검토자가 단독으로 소유한다고 정한 것은 아니다.

<a id="decision-example"></a>
## 읽은 기준이 판단과 확인으로 이어지는 예

다음은 기록 53의 판단을 결과 형식에 넣은 **미실행 예시**다. 실제 작업자의 제출물·검토자의 발견·수정 결과가 아니다.

| 판단 | 기준을 적용한 이유 | 수정한다면 확인할 것 | 현재 증거 상태 |
| --- | --- | --- | --- |
| 호출 방식·정상 반환·작은 공통 구조 유지 | 신뢰할 계약이 목표이며 구조를 크게 만드는 것은 목표가 아니다 | 정상 JSON·문자열 반환, 기존 호출과 화면 정책 분리 | 과거 판단 예시. 이번 시안에서 실행 안 함 |
| 본문 읽기·파싱 실패 처리 보완 | 사용처가 내부 rejection 경로를 알아야 오류 의미를 해석하는 부담을 줄인다 | 200 응답의 깨진 JSON이 네트워크 실패와 구별되는지, 본문 중 timeout 의미를 덮지 않는지 | 수정 후보. 미구현·미실행 |
| HTTP 상태 보존 보완 | 실패 본문이 깨져도 이미 받은 HTTP 상태는 유효한 정보다 | 500+깨진 JSON에서 상태와 읽기 실패 근거가 남는지, null 등 본문 형태도 안전하게 처리되는지 | 수정 후보. 미구현·미실행 |
| timer 수명·정리 보완 | timeout 계약은 헤더 수신 뒤의 본문 처리에도 관계한다 | 본문 읽기 중 timeout, 완료·실패 뒤 정리 | 수정 후보. 미구현·미실행 |
| 재시도·인증 이동·공통 토스트 확대 보류 | 사용처 정책과 새로운 요구를 공통 오류 정비에 섞지 않는다 | 별도 요구가 생기면 계약과 책임을 다시 비교 | 보류 판단 예시 |

실제 보고에서는 이 표를 모두 채우는 대신, 중요한 판단을 짧은 문장으로 전달할 수도 있다. 예를 들어 “호출·정상 반환은 유지하고 HTTP 상태가 사라지는 오류 경로를 보완했다”라고 말하려면 실제 변경과 해당 확인 결과가 있어야 한다. 이 시안의 ‘수정 후보’를 ‘수정 완료’로 복사하지 않는다.

<a id="record-use"></a>
## 사용자가 판단을 바꾸려 할 때

- “이번 작업에서는 인증 이동도 필요하다”는 요청이면 작업 목표·범위와 제품 정책을 다시 판단한다. 공통 기준 자체가 곧바로 틀린 것은 아니다.
- “우리 프로젝트의 공통 fetcher가 화면 정책도 맡기로 했다”는 확인된 선택이면 Project의 계약 설명과 해당 작업 입력을 바꾼다. 다른 프로젝트까지 자동으로 같은 규칙으로 만들지 않는다.
- “이 질문은 계속 엉뚱한 판단을 유도한다”는 관찰이 쌓이면 [기준 본문](principles.md#trusted-contract)의 설명·조건·질문을 보완하고 근거 사례를 남긴다.

이번 작업의 실제 결과와 미확인은 작업 기록에, 여러 작업이 공유할 확정 계약은 Project 설명에 연결하는 안이다. 보존할 원문·대안은 상세 기록에 둘 수 있다. 한 번의 적용 결과를 자동으로 공통 원칙으로 승격하거나 새 갱신 자동화를 설치하는 제안은 아니다.
