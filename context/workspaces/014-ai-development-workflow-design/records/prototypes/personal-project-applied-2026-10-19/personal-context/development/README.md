# 개발 판단 — 짧은 공통 기준과 필요한 상세

코드를 만들거나 고칠 때는 지금 해결할 문제와 실제 사용처를 먼저 확인한다. 읽고 바꾸는 사람이 역할과 동작을 이해할 수 있게 하되, 추상화·분리·개명 자체를 개선의 목표로 삼지 않는다. 제안한 변경이 줄이는 부담과 새로 만드는 제약·호환 비용을 함께 본다.

**기준을 채택한 뒤에도 현재 목적·사용처·비용에 따라 적용한다.** 원칙이나 사례와 코드 모양이 다르다는 사실은 살펴볼 단서이며, 그 차이만으로 수정하지 않는다. 현재 조건에서 줄일 부담과 보존할 동작을 보고 유지·수정·보류를 판단한다. 기준이 전제한 조건이 달라졌다면 적용 범위와 이유도 다시 검토한다.

현재 동작에 근거가 있다는 것과 앞으로도 유지해야 한다는 것은 다르다. 요구와 계약에 맞는 동작은 보존하고, 어긋난 부분은 표현 문제인지 구현 문제인지 확인한다. 중요한 선택은 무엇을 근거로 골랐는지 설명하고, 확인하지 않은 결과를 보장했다고 말하지 않는다.

이 공통 부분은 모든 상세를 매번 읽게 하는 체크리스트가 아니다. 이번 작업의 쟁점에 해당하는 기준을 골라 읽고 실제 코드·계약과 대조한다. 원칙만으로 선택이 불분명하면 해당 상세에 연결된 사례에서 선택을 가른 조건을 확인한다. 기준의 뜻이나 적용 범위를 다시 정할 때는 원래 대화까지 내려간다.

| 판단할 내용 | 상세 본문과 읽는 조건 |
| --- | --- |
| 이름에서 맡은 일과 보장 범위를 이해할 수 있는가 | [이름·책임·완료 범위](naming-and-completion.md). 함수·상태·반환값·완료 알림을 만들거나, 그 표현 때문에 동작을 잘못 예상하는 부분을 고칠 때 읽는다. |

현재 시안에는 위 주제만 작성했다. 본문은 기존 판단 방향을 Main이 재서술한 시안이며, 사용자 선택과 새 구체화의 지위는 [Personal 입구](../README.md#이-시안에서-선택한-것과-검토할-것)에서 구별한다. 설계·검증 등 다른 주제의 전체 기준이나 파일 구성을 확정한 것은 아니다.

조건에 따른 적용의 원래 이유는 [사용자 요청과 보완68](../../../../2026-10-18-68-principle-application-and-choice-basis.md), 그때 실제로 쓴 문장은 [01 공통 본문](../../../applied-criteria-2026-10-17/shop-web/context/project/quality.md#applying-principles)에서 찾는다. 이름·책임·완료 판단의 대화·사례와 이번에 추가한 설명은 [상세의 근거 안내](naming-and-completion.md#원래-대화와-사례를-다시-읽을-때)에서 고른다. 일반 적용마다 이 기록 전체를 읽는 절차는 아니다.
