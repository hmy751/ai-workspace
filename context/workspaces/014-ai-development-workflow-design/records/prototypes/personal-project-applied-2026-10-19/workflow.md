# 개인 기준과 Project 계약을 작업에서 연결하는 방식

> 이 문서는 지금 Main이 맡을 실행 연결을 구체화한 시안이다. 새 skill이나 전역 지침으로 설치한 것이 아니며 실제 운영 절차로 채택한 결과도 아니다. 사용자는 개인 기준의 운영 위치를 `ai-workspace/context/personal/`로 선택했다. 실제 파일은 옮기지 않았으며 아래 경로는 이 시안 안에서 실제로 열 수 있는 예시 배치다.

개인 기준과 Project 계약은 서로의 본문을 알아야 성립하는 관계가 아니다. **Main이 이번 요청의 성격에 맞춰 두 입력을 가져오고, 이번 Work의 목표와 실제 코드에 대입해 구현·검토를 연결한다.** 개인 기준은 판단 관점을, Project는 제품의 의미·개발 계약·현재 사실을 제공한다. 이 문서는 그 내용을 다시 정의하지 않고 선택·비교·전달·갱신을 누가 언제 맡는지 설명한다.

## 요청에서 필요한 입력을 고른다

Main은 맡은 작업의 목표·보존할 동작·미정인 선택을 파악하고 [Work 입구](noline-demo/context/work/workspaces/login-completion-names/README.md)에서 이번 범위를 고정한다. 그 뒤 필요한 판단을 기준으로 아래 입력을 고른다. 모든 요청에서 모든 문서를 순서대로 읽는 절차가 아니다.

| 필요한 입력 | Main이 고르는 경로와 가져올 내용 |
| --- | --- |
| 개인의 개발 판단 | [Personal 입구](personal-context/README.md)에서 개발 작업임을 보고 [짧은 개발 공통](personal-context/development/README.md)과 관련 주제를 고른다. 이름·완료 표현이 쟁점이면 [상세 기준](personal-context/development/naming-and-completion.md)의 뜻·질문·조건별 판단을 가져온다. 관련 없는 개인 주제는 붙이지 않는다. |
| 대상 Project의 의미와 계약 | 대상의 [진입 지침](noline-demo/AGENTS.md)과 [Project 안내](noline-demo/context/project/README.md)에서 현재 질문에 필요한 제품·개발 계약을 고른다. 인증의 이름이라면 인증 계약과 표현 가이드를 읽고 해당 코드·호출부를 대조한다. 개인 기준이 없어도 이 경로에서 Project의 약속을 이해할 수 있어야 한다. |
| 이번 Work의 요구·상태·결과 | Work의 Ticket과 현재 상태에서 목표·보존 범위·미충족을 읽는다. 이어 하는 작업이면 필요한 구현·검토 기록을 고른다. 과거 선택이 현재 요구인지 이력인지 구별한다. |

이미 읽은 내용으로 판단할 수 있으면 같은 원문을 재독하는 절차를 반복하지 않는다. 새로운 사람·AI에게 넘길 때에는 그가 앞선 대화를 알 것이라고 가정하지 않고 직접 읽을 경로와 선택 이유를 함께 준다. 기준이 필요한데 접근할 수 없다면 무엇이 빠졌는지 알리고, 원문을 읽은 것으로 보고하지 않는다.

실제 제품 작업에서는 코드·호출부·검사 근거가 관찰 입력이다. 이 시안은 제품 코드가 없으므로 [시작 입력](scenario-input.md)의 명시적 가정과 발췌가 그 역할을 대신한다. 작업 후 Project 현황을 과거 입력으로 사용하지 않는다.

## 구현 전에 Main과 구현자가 비교하는 것

Main은 무엇이 이번 요구이고 무엇이 제품 계약인지, 어떤 개인 기준을 왜 함께 볼지 구현자에게 전달한다. 함수명을 미리 정답으로 주는 대신 판단할 책임과 보존 범위를 준다. 구현자는 원자료와 실제 사용처를 읽고 가능한 선택의 이득·비용을 비교한다. Main의 요약만 읽어 원문을 대체하거나 개인 기준의 예시 이름을 의무로 복사하지 않는다.

이번 이름 작업에서는 Project 계약이 ‘인증 적용과 조회 요청까지’라는 완료 범위를 제한한다. 개인 기준은 그 의미를 이름·타입·가까운 설명 중 무엇으로 전달할지, 기존 표현을 유지할 이점과 개명 비용을 어떻게 비교할지 돕는다. 내부 사용처가 두 곳이라는 사실은 이번 작업의 입력이며 일반 기준이나 Project의 영구적인 명명 정책이 아니다.

구현자는 표현 보완만으로 충분한지, 동작이나 약속 자체를 고쳐야 하는지 구별한다. 관련 질문은 살필 사실을 찾는 데 사용한다. 모든 질문의 답안 목록을 출력하지 않고, 선택을 가른 근거와 유지할 동작, 확인할 범위·미확정을 작업 결과로 돌려준다.

## 입력이 어긋나거나 충돌할 때

개인 기준이 Project 계약보다 자동으로 우선하지 않는다. 반대로 현재 구현이 존재한다는 사실만으로 Project의 의도나 좋은 구조를 확정하지도 않는다.

| 발견한 차이 | 판단과 반환 |
| --- | --- |
| 개인 예시와 Project의 현재 구조가 다름 | 목적·사용처·비용을 대조한다. 다른 모양만으로 고치지 않으며 현행 유지도 가능하다. |
| 코드가 Project의 명시된 완료·실패 계약을 못 지킴 | 이름을 좁혀 차이를 감추지 않는다. 어느 약속이 어긋나는지 밝히고, 이번 범위 안의 결함 수정인지 계약 재판단이 필요한지 Main과 구별한다. |
| 개인 선호를 적용하면 제품 약속·팀 합의·공개 호환성이 바뀜 | 구현자는 필요한 변화와 영향을 Main에게 돌린다. Main은 원요구와 권한 안에서 판단하고, 새 제품·팀 선택이 필요하면 해당 결정권자에게 확인한다. 기존 계약을 묵시적으로 덮어쓰지 않는다. |
| 문서와 코드가 다르지만 어느 쪽이 유효한지 불명확함 | 관찰과 약속을 구별하고 관련 근거·담당자를 확인한다. 추정으로 이름과 문서를 함께 고쳐 일치시켰다고 처리하지 않는다. |

원래 목표와 보존 계약 안의 표현·품질 수정마다 별도 승인 단계를 추가하는 것은 아니다. 어느 선택이 기존 범위에서 가능한지와 새로운 결정을 필요로 하는지가 판단 대상이다.

## 구현 인계와 검토 인계

구현자가 변경과 확인·미확인을 [구현 기록](noline-demo/context/work/workspaces/login-completion-names/records/implementation.md)에 남기면 Main이 검토자에게 원요구, 선택한 개인 기준, 관련 Project 계약, 시작 입력·현재 변경, 구현자의 인계를 전달한다. 기준·계약 원문 경로는 보존하고, 구현자의 선택 이유와 미확인은 원문과 별도로 표시한다.

검토자는 같은 요구와 입력에서 변경을 직접 대조한다. Main은 찾아야 할 결함이나 기대 결론을 미리 주입하지 않는다. 검토자는 범위 안의 품질 문제를 직접 고치고 관련 확인을 수행하며, 새로운 제품 약속이나 범위 재판단이 필요하면 Main에게 돌린다. 인계 뒤 구현자와 검토자가 같은 부분을 동시에 수정하지 않도록 Main이 담당을 맞춘다.

검토자는 자신의 발견·직접 수정·확인과 남은 한계를 [검토 기록](noline-demo/context/work/workspaces/login-completion-names/records/review.md)에 남긴다. Main은 원목표·보존 요구·미충족·증거 상한을 보고 이번 작업의 상태를 판단한다. 직접 수정한 검토자의 보고를 별도 독립 검증의 결과로 바꾸지 않는다. 실제 검사하지 않은 내용은 계획·예상으로 구별한다.

## 결과를 해당 책임으로 돌려준다

| 결과의 성격 | 갱신할 곳과 판단 |
| --- | --- |
| 여러 Project에서도 쓸 개인 판단의 의미·조건이 바뀜 | 개인 기준의 소유자가 근거와 적용 범위를 보고 Personal 본문을 보완할지 판단한다. 한 번 개명했다는 이유로 새 필수 어휘를 추가하지 않는다. |
| 대상 제품의 의미·약속·개발 계약이 바뀜 | 해당 Project의 권한 있는 선택에 따라 common 또는 guidance를 맞춘다. 개인 원문을 알아야만 이해할 수 있는 문서로 만들지 않는다. |
| 현재 함수·사용처·지원 연결이 바뀜 | 변경 담당자가 확인한 범위와 함께 Project current를 맞추고 Main이 작업 인계에서 확인한다. 과거 상태는 이번 Work의 입력·기록에 남긴다. |
| 이번 선택·대안·수정·검사·미충족 | Work의 기록과 현재 상태에 남긴다. 기준이나 제품 계약의 정본으로 중복 관리하지 않는다. |
| 입력을 찾지 못하거나 전달·인수·갱신이 빠짐 | 이번 Work에 경위와 영향을 남기고 이 실행 연결을 보완할 필요를 Main이 판단한다. 곧바로 새 skill이나 역할을 만들지 않는다. |

이 시안에서 선택한 문서와 메시지의 적용 모습은 [walkthrough](walkthrough.md)에 있다. Personal·Project·Work의 연결을 실제 코드 작업에서 검증한 결과는 아니며, 이 절차를 기존 skill에 반영할지와 설치·권한·최종 검증 방식은 열린 결정이다.
