# 검토 인계: 남은 완료 문구를 직접 수정

> 가상 검토 장면의 기록이다. 아래 발견·수정은 제시된 코드 발췌에 대한 설명이며 제품 소스 변경이나 실제 검사 결과가 아니다. 확인 계획과 예상 판정은 실행 증거로 취급하지 않는다.

**이 장면에서는 완료 문구를 고친 뒤 이름·표현 정리의 범위를 충족한다고 판단한다.** 실제 제품 적용을 승인하는 결론은 아니다. 별도의 최종 독립 검증자가 변경을 확인한 것도 아니다.

## 구현자의 결론과 별개로 대조한 것

[Ticket](../current/ticket.md)은 식별자뿐 아니라 소비자의 완료 표현까지 실제 보장과 맞추라고 요구한다. [구현 인계](implementation.md)는 두 식별자·가까운 설명·사용처를 변경했으나 표시 문구 대조를 남겼다. Main에게 받은 [개인 개발 공통](../../../../../../personal-context/development/README.md)·[이름 상세](../../../../../../personal-context/development/naming-and-completion.md)와, 독립된 Project의 [인증·세션 계약](../../../../project/guidance/authentication-and-session.md)·[표현 가이드](../../../../project/guidance/code-readability.md), 변경 전후와 두 소비자를 함께 대조한다.

개명은 Project가 정한 답이 아니라 이번 Work의 선택이다. 초기 이름에 설명을 보완하는 안도 가능하지만, 현재의 과도한 완료 표현과 두 내부 사용처의 제한된 변경 비용을 보면 개명과 짧은 계약 설명을 함께 쓰는 이득이 있다고 판단한다. 실제 공개 사용처가 발견되면 이 비용 판단은 다시 해야 한다. 제품 계약은 완료 의미를 정하고 개인 기준은 표현 수단과 변경 필요성을 비교하는 역할을 한다.

wrapper의 새 이름은 인증 적용 이후 조회 갱신을 요청한다는 책임을 드러낸다. 그러나 LoginScreen의 `로그인과 화면 갱신 완료`는 callback 시점에 재조회와 렌더까지 끝났다고 읽힌다. 이 장면에서는 Query를 기다리지 않으므로 표현이 실제 보장보다 넓다.

## 기존 계약 안에서 직접 고친 부분

```diff
 onSignedIn: () => {
-  showStatus("로그인과 화면 갱신 완료");
+  showStatus("로그인 완료");
   navigateAfterSignIn();
 },
```

문구는 사용자에게 필요한 로그인 성공만 알린다. 인증 적용·조회 요청의 세부 경계는 개발자용 이름·타입·설명이 맡으며 화면에 내부 구현 단계를 나열하지 않는다. Query에 `await`를 추가해 기존 문구를 사실로 만들려고 하지 않았다. 화면 이동을 wrapper로 옮기거나 재조회 실패를 로그인 실패로 합치지도 않았다. ReauthDialog는 표시 문구가 없는 사용처이므로 새 callback 이름과 기존 닫기 책임을 유지한다.

이 수정은 원래 요청에 포함된 완료 표현을 바로잡는 범위다. 반대로 실제 요청이 ‘화면 데이터가 준비될 때까지 이동하지 않기’라면 후속 대기·실패·화면 계약을 바꾸는 요구이므로 Main에게 돌려준다. 실제 서비스가 가정한 범위보다 일찍 해소되거나 외부 공개 소비자가 발견되어도 현재 개명 결론을 그대로 승인할 수 없다.

## 실제 적용 때 실행할 확인과 예상 판정

아래는 아직 실행하지 않은 계획이다. 표의 예상은 가상 계약을 보존했다면 관찰해야 할 결과이며, 통과 보고가 아니다.

| 확인 장면·방법 | 예상 판정 |
| --- | --- |
| 서비스와 Query의 완료를 따로 제어해 호출 순서를 관찰한다 | 서비스가 해소되기 전에는 Query 요청과 `onSignedIn`이 없다. 해소 뒤 Query를 요청하고 재조회 완료를 기다리지 않은 채 callback을 호출한다. |
| Query를 미해소 상태로 유지한다 | 사용자 문구는 `로그인 완료`로 성공한 로그인만 알린다. 화면 갱신·렌더 완료를 주장하지 않으며 내부 조회 단계도 나열하지 않는다. |
| 서비스가 실패하도록 한다 | 기존 인증 실패가 전달된다. Query 요청과 `onSignedIn`이 실행되지 않는다. 실제 실패 후 상태·저장 보존은 서비스의 별도 계약과 검사 근거로 확인한다. |
| 인증 적용 후 Query를 reject한다 | `onRefreshError`가 실패를 받는다. 후속 실패 때문에 이미 적용한 인증을 인증 실패로 다시 분류하거나 되돌리지 않는다. |
| 두 소비자의 callback 동작을 대조한다 | LoginScreen은 기존 이동, ReauthDialog는 기존 닫기 동작을 유지한다. wrapper가 화면 정책을 가져가지 않는다. |
| 변경된 식별자와 사용처·타입 연결을 검색·검사한다 | 두 소비자가 새 이름을 사용하며 이 장면의 내부 사용처 전제가 맞는다. 숨은 외부 사용처가 있으면 호환성 판단을 다시 한다. |

현 시안에서 가능한 문서상 대조는 전후 발췌의 호출·대기·오류 담당이 같고, 완료 문구만 좁혀졌다는 것이다. 실제 테스트 실행, OAuth·기기 저장, 서버 토큰 처리, 화면 렌더와 사용자 수용 확인은 수행하지 않았다.

## Main에 돌려주는 결과와 기록 위치

이번 장면은 가정한 계약 안에서 이름·완료 표현을 정리한 것으로 마친다. [현재 상태](../current/state.md)에 시안 범위와 실제 적용 전 확인을 남긴다. Personal 기준과 독립된 Project의 표현·인증 계약·제품 의미는 바꾸지 않는다. [Project 현황](../../../../project/current/authentication-flow.md)은 가상 작업 후 이름·callback·사용처에 맞춰 갱신하고, [시작 입력](../../../../../../scenario-input.md)의 과거 상태를 덮어쓰지 않는다. 실제 Noline의 문서나 코드를 갱신했다는 의미는 아니다.

개인 기준을 썼다는 사실만으로 모든 Project에 이 이름을 설치하지 않는다. 검토자가 직접 수정한 기록을 별도 독립 검증의 결과로 바꾸지도 않는다. 한 가상 장면의 일관성과 실제 AI의 기준 발견·판단 효과는 별도 확인 대상이다.
