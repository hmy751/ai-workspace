# 로그인 완료와 후속 조회의 개발 계약

> 가상 Project의 계약이다. 기기 저장·상태 적용과 실패 경계는 Noline 보존 문서에 근거하고, 아래의 비대기 wrapper·callback 선택은 이번 예시에서 추가한 가정이다.

로그인·재인증의 순서나 성공·실패 전달, 후속 조회 갱신과 완료 알림을 바꿀 때 읽는다. 로그인은 서버 응답을 받은 것만으로 완료되지 않는다.

## 계정 확인·기기 저장·상태 적용을 마쳐야 인증 완료다

기존 계정과 DB·queue의 귀속을 확인한 뒤 세션을 기기에 저장하고, 저장 성공 뒤 새 토큰과 `signed-in` 상태를 공개한다. 저장에 실패하면 이전 인증 상태와 로컬 데이터를 보존한다. 저장 성공 전에 로그인 완료 callback을 호출하지 않는다.

Auth Store는 이 검사·저장·상태 적용을 맡고, 전체 세션 변경 서비스는 진행 중인 sync·cleanup·접수된 DB 작업의 종료와 본작업을 조율한다. 새 로그인 진입점이 Store action만 호출해 이 전체 절차를 대신하지 않게 한다. 같은 계정의 데이터를 유지하는 이유는 [제품 의미](../common/device-session.md)에 있다.

## 인증 완료 이후 조회는 별도의 성공·실패를 갖는다

저장·상태 적용 뒤 Query 갱신이 실패해도 인증 복구는 완료된 상태다. 이 실패를 인증 저장 실패로 다시 분류하거나 완료된 인증을 되돌리지 않는다. 후속 갱신의 실패를 누가 처리하는지 호출 경계에서 드러낸다.

**이 예시의 동작 선택:** 전체 로그인 서비스가 끝난 뒤 wrapper가 Query 무효화를 요청하고, 재조회 완료를 기다리지 않고 인증 완료 callback을 부른다. Query 실패는 별도 `onRefreshError` callback으로 전달하며 이 callback은 실패를 처리하고 다시 던지지 않는다고 가정한다. 인증 실패는 로그인 호출의 실패로 전달한다. callback 이후 화면 이동·모달 닫기는 각 화면이 결정한다.

따라서 wrapper의 성공은 인증 적용과 조회 갱신 요청까지를 뜻한다. 재조회 결과·화면 이동·렌더링 완료를 보장하지 않는다. 관련 이름·설명도 이 의미를 따른다. ‘갱신 완료까지 기다리기’를 요구한다면 이 계약과 화면의 대기·실패 처리를 함께 재판단한다.

## 바꾼 경계에 맞춰 확인한다

저장 실패 때 기존 상태·데이터가 남고 완료 callback은 호출되지 않는지, 갱신이 계속 진행 중이어도 인증 완료를 전달하는지, 후속 실패가 인증 실패로 바뀌지 않는지 본다. 실제 확인은 변경된 코드·호출부와 제어 가능한 비동기 경계에서 수행한다. 이름만 바꿨다는 이유로 호출부와 완료 의미의 대조를 생략하지 않는다.

현재 함수와 두 사용처는 [현재 연결](../current/authentication-flow.md)에서 찾는다. 이 시안의 검사 항목은 실제 제품 테스트 통과 결과가 아니다.
