# 인증 코드의 이름과 완료 표현

이 가이드는 인증·세션 함수, callback, 로그와 사용자 안내를 만들거나 고칠 때 적용한다. **표현을 읽은 호출자가 인증 적용, 조회 요청, 조회 결과, 화면 준비를 혼동하지 않게 한다.** 각 표현이 보장할 수 있는 결과와 소비자가 이어서 할 수 있는 행동을 설명한다. 제품의 순서·실패 계약은 [인증·세션 계약](../authentication-and-session/INDEX.md)이 소유한다.

## Store action과 기능 진입점의 이름

| 코드가 맡는 일 | 이름·가까운 계약에서 드러낼 범위 | 포함시키면 안 되는 약속 |
| --- | --- | --- |
| Store의 귀속 확인·기기 저장·공개 상태 적용 | 인증을 적용하는 부분 책임 | 진행 중인 sync·cleanup·DB 작업의 전체 종료 조율 |
| 인증 응답 획득·주어진 대기 경계·Store 적용 | 전체 인증 절차를 조율하는 기능 | 최신 Query 결과와 화면 준비 |
| 인증 서비스 실행·후속 조회 요청 시도·인증 완료 통지 | 인증 적용과 조회 요청 시도까지 끝낸 결과 | 조회 성공 또는 화면 렌더링 완료 |

서비스가 전체 인증 절차를 조율한다면 기능 전체를 뜻하는 이름을 쓸 수 있다. 그 내부의 저장·검사 함수를 나눴다는 이유로 서비스 이름까지 모든 단계의 목록으로 만들 필요는 없다. 반대로 Store의 부분 action을 로그인 진입점으로 공개하려면 빠진 조율 책임을 먼저 확인해야 한다. 현재 선택한 이름과 실제 연결은 [인증 흐름 현황](../../current/authentication-flow/INDEX.md)에서 대조한다.

**판단 질문:** 현재 호출부가 저장 action을 직접 부르고 있는가, 전체 조율이 필요한 작업을 맡기고 있는가? 이름을 바꾸는 것과 올바른 진입점을 선택하는 것은 별도의 수정일 수 있다.

## 완료 callback 뒤의 실제 행동을 읽는다

이 demo의 Login은 인증 완료 뒤 이동을, Reauth는 닫기를 시작하는 소비자다. 완료 callback에서 최신 Query 결과를 직접 사용하지 않는 조건을 두었다. 이 조건이 실제 도착 화면 전체의 준비 완료를 보장하지는 않는다.

완료 표현을 고를 때는 인증 저장·공개가 끝났는지, 조회 요청을 시도했는지, 조회 결과까지 받았는지를 나눠 본다. 이 demo는 조회 요청이 즉시 실패하거나 나중에 실패해도 후속 오류를 별도로 전달하고 인증 완료 통지는 진행한다. 두 callback은 정상 반환하는 계약이다. 성공 알림만으로 최신 여행 데이터나 화면 렌더링까지 준비됐다고 표현해서는 안 된다. 이 경계를 생략하지 않은 실제 코드는 [현재 반환·오류 경계](../../current/authentication-flow/INDEX.md#반환과-오류-전달의-현재-구현)에 있다.

최신 결과가 필요한 소비자가 생기면, 그 소비자에서 조회 완료를 기다릴지 공통 작업의 완료 계약을 바꿀지 [대기 조건](../authentication-and-session/INDEX.md#조회를-기다릴지는-다음-화면의-요구로-정한다)에서 비교한다. 일부 소비자만 필요한 대기라면 기존 인증 완료 경계를 유지할 수 있다. 공통 반환 시점을 바꾼다면 현재 Login·Reauth의 대기 표시, 이동·닫기 시점, 실패 처리까지 함께 확인한다.

| 표현하려는 결과 | 사용할 수 있는 조건 | 이 demo에서 확인할 차이 |
| --- | --- | --- |
| 인증 적용 완료 | 기기 저장과 공개 상태 반영을 마쳤다. | 이동·닫기를 시작할 수 있다는 것과 화면 준비 완료를 구별한다. |
| 최신 데이터·화면 준비 완료 | 필요한 조회·처리와 준비의 범위를 정하고 실제로 마쳤다. | 비대기 인증 완료만으로는 이 결과를 보장하지 않는다. |
| 후속 조회 실패 | 인증 적용 뒤 별도 조회가 실패했다. | 인증 저장 실패와 구별해 알린다. |

이 표는 접두사 목록이 아니다. 이름·반환형·가까운 설명을 함께 읽고 실제 후속 행동을 판단한다. 사용자가 보는 문구에는 재인증 또는 조회 재시도처럼 사용자가 이해해야 할 결과를 담고 내부 함수 이름을 나열하지 않는다.

## 표현을 고칠지 동작을 고칠지

현재 Login·Reauth는 인증 적용 뒤 이동·닫기를 시작하며, 완료 callback에서 최신 Query 결과를 읽지 않는다. 따라서 조회가 끝나기 전에 callback이 실행된다는 사실만으로 대기 동작을 추가하지 않는다. 먼저 **인증만 필요한 소비자에게 조회·화면 준비까지 약속한 표현이 있는지**, 또는 **실제로 최신 결과가 필요한 소비자에게 이 완료 경계를 쓰고 있는지**를 구별한다.

| 살펴본 조건 | 이 Project에서의 판단 | 수정 뒤에도 구별할 것 |
| --- | --- | --- |
| 반환·callback이 보장하는 상태나 후속 오류의 전달 경로가 불명확하다. | 인증 저장·공개, 조회 요청·결과 각각의 실제 경계와 호출부에 알려진 계약이 일치하는지 확인하고 빠진 약속을 명확히 한다. | 인증 적용 뒤 이동·닫기를 시작하는 것과 조회·화면 준비 완료는 다르다. |
| 이름이나 완료 알림이 조회 결과까지 준비됐다고 읽히지만, 소비자는 인증 적용만 필요하다. | 표현이 약속하는 결과를 실제 인증 적용·조회 요청 범위에 맞춘다. | 이름·문구 개선을 이유로 새 조회 대기를 넣거나 기존 이동·닫기 시점을 바꾸지 않는다. |
| 소비자가 완료 직후 최신 여행 데이터를 읽어야 한다. | 그 소비자에서 필요한 조회를 기다리거나 공통 완료 계약을 바꿀지 판단한다. 현재 demo에는 이 요구의 경로가 구현돼 있지 않다. | 조회 대기 실패와 이미 끝난 인증 적용을 구별한다. 공통 경계를 바꾸면 기존 두 소비자의 대기·이동·닫기 영향도 확인한다. |
| 인증 적용 뒤 후속 조회만 실패했는데 “로그인 실패”로 표시한다. | 실패한 단계를 조회로 바로잡아 전달한다. 처리 경로가 두 실패를 합치고 있다면 문구뿐 아니라 오류 전달도 고친다. | 일반 조회 실패만으로 인증이나 같은 계정의 로컬 데이터를 되돌리지 않는다. 별도 인증 거부 판정은 [인증 계약](../authentication-and-session/INDEX.md#사건별로-보존할-결과와-다음-행동)의 경계를 따른다. |

가까운 계약에는 “인증을 적용한 뒤 후속 조회를 요청하지만 그 결과를 기다리지 않는다. 완료 callback은 인증 적용을 알리며, 조회 요청·결과의 실패는 별도로 전달한다”처럼 **호출자가 다음 행동을 고를 수 있는 범위**를 쓴다. 이는 현재 demo의 계약을 표현하는 예이며, 모든 인증 함수에 붙이는 공통 문구가 아니다. 정확한 순서·예외는 [인증 완료와 후속 조회 전달의 약속](../authentication-and-session/INDEX.md#인증-완료와-후속-조회-전달의-약속)이 소유한다.

현재 사용하는 함수명·callback과 소비자의 연결은 [현재 구현](../../current/authentication-flow/INDEX.md)에서 확인한다. 공개 호출부가 추가되거나 완료 범위를 바꿀 때에는 그 사용처가 기대하는 결과와 호환성 영향도 함께 확인한다.

예를 들어 현재 callback 뒤 Login의 이동이 시작돼도 조회 완료를 뜻하지는 않는다. ‘로그인 완료’는 인증 적용 범위를 표현하지만 ‘최신 여행 준비 완료’는 현재 보장을 넘는다. 최신 값을 사용하지 않는 이 소비자에는 표현을 고치기 위해 새 대기를 추가할 이유가 없으며, 소비자가 최신 결과를 필요로 하게 되면 대기 조건을 다시 판단한다.

본문의 범위와 형성 의도·변경 근거를 읽을 경로는 [구성 안내](README.md)에 있다.
