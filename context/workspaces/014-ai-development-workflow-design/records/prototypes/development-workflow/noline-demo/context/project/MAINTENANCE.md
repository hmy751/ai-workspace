# Project context 관리

제품 의미·계약·현재 구현에 계속 영향을 주는 변화가 확인됐거나 사용자가 내용의 복원·재구성을 요청했을 때 적용한다. 실제 본문의 변경 담당자가 [구성 기준](REFERENCE/composition.md)과 해당 근거·코드·검사를 대조해 갱신한다.

기존 요구를 명확하게 설명하는 작업, 구현 사실을 바로잡는 작업, 새로운 제품 약속을 결정하는 작업을 구별한다. 새 제품 선택이나 상충하는 권위 사이의 결정은 사용자 또는 해당 결정권자에게 확인한다. 코드가 현재 그렇다는 사실만으로 계약을 바꾸지 않는다.

의미가 달라진 본문부터 맞추고 그 변화 때문에 설명이나 읽기 경로가 달라지는 문서를 이어 맞춘다. 해당 layer README, Project 진입, 관련 Work의 Project 선택과 output이 현재 Owner를 가리키는지 확인한다. 같은 상세 정책을 여러 곳에서 각각 고쳐야 한다면 책임을 다시 나눈다.

갱신 뒤 대표 작업 하나에서 Project 입구로 들어가 본문만으로 제품 의미와 적용 조건을 설명할 수 있는지 읽어 본다. 그 뒤 실제 구현과 확인 범위를 대조한다. 링크 검사·파일 수·자동 테스트가 내용 충분성을 대신하지 않는다.

한 작업의 시도·대안·실행 수치는 Work records에 남긴다. 새로운 본문을 만들 가치가 있는지와 기록할 가치가 있는지는 구별한다. 과거 source·기록을 새 결론에 맞춰 덮어쓰지 않는다. 이 demo의 관리는 직접 수행하며 자동 Maintain이 Project를 갱신했다고 가정하지 않는다.
