# Project context 관리

제품 이해·여러 작업의 개발과 판단에 필요한 의미·구조·계약·제약·선택 이유가 달라졌거나 사용자가 그 내용의 복원·재구성을 요청했을 때 적용한다. 현재 구현·지원 사실도 이 공통 맥락을 설명할 필요가 있을 때 포함한다. 구현이 바뀌었다는 이유만으로 Project 갱신을 전제하지 않으며 이번 구현 여부·검사 진행·실행 상세는 Work에서 관리한다.

이 문서는 Project에 남길 내용·변경 권한·반영 완료 기준을 소유한다. 실제 변경 담당자는 [구성 기준](REFERENCE/composition.md)과 해당 근거를 적용하고, 지정 본문을 맞추는 공통 수행은 [context-update](../../../skills/context-update/SKILL.md)를 사용한다. 주제의 본문과 형성 자료를 구성·수정할 때는 [공통 관리 원칙](../CONTENT-POLICY.md)을 따른다. 이들 절차가 제품 내용의 권위를 대신하지 않는다.

기존 요구를 명확하게 설명하는 작업, 지속할 현재 사실을 바로잡는 작업, 새로운 제품 약속을 결정하는 작업을 구별한다. 새 제품 선택이나 상충하는 권위 사이에서 현재 권한으로 해결할 수 없는 결정은 사용자 또는 해당 결정권자에게 확인한다. 이미 권한 있게 정한 변경의 반영에 승인을 반복하지 않으며 코드가 현재 그렇다는 사실만으로 계약을 바꾸지 않는다. 개발 중 누가 제안·검토·반영할지는 [development](../../../skills/development/SKILL.md)가 정한다.

프로젝트에서 계속 적용할 코드 품질 기준도 적용 범위와 이유를 분명히 해 guidance에 둘 수 있다. 다른 본문의 기준을 이번 작업에 사용했다는 사실만으로 Project의 공통 규약이 되지는 않는다. 이 프로젝트가 지속해서 지킬 규약으로 정했거나 기존 계약을 이해하는 데 필요한 설명일 때 반영한다. 필요한 설명이 다른 문서와 일부 겹치는 것은 허용하되, 갱신 여부는 이 Project의 의미·규약·현재 사실이 달라졌는지로 판단한다.

의미가 달라진 본문부터 맞추고 그 변화 때문에 낡은 사실·조건·이유를 전달하게 되는 설명과 읽기 경로를 함께 맞춘다. 해당 layer README, Project 진입, 관련 Work의 Project 선택과 output이 현재 Owner를 가리키는지 확인한다. Work의 실제 갱신은 Main 또는 그 책임을 맡은 담당자가 이어 수행하며, Project 반영 권한을 Work의 무제한 수정권으로 넓히지 않는다. 같은 상세 정책을 여러 곳에서 각각 고쳐야 한다면 책임을 다시 나눈다.

갱신 뒤 대표 질문에서 Project 입구와 영향받은 기존 참조로 들어가 본문만으로 제품 의미·적용 조건·현재 지원의 한계를 설명할 수 있는지 읽어 본다. 실제 구현과 확인 범위를 대조하며, 필요한 설명·근거·경로가 남았다면 그 부분은 반영 미완료다. 링크 검사·파일 수·자동 테스트가 내용 충분성을 대신하지 않는다. 문서 반영을 마친 것과 제품이 요구를 충족한 것, Work 전체 완료는 구별한다.

한 작업의 시도·대안·실행 수치는 Work records에 남긴다. 새로운 본문을 만들 가치가 있는지와 기록할 가치가 있는지는 구별한다. 과거 source·기록을 새 결론에 맞춰 덮어쓰지 않는다. 이 demo의 관리는 직접 수행하며 자동 Maintain이 Project를 갱신했다고 가정하지 않는다.

이 관리 계약과 읽기·구성 기준을 형성한 근거가 필요하면 [REFERENCE의 형성 자료 안내](REFERENCE/_background/README.md)에서 관련 질문을 고른다.
