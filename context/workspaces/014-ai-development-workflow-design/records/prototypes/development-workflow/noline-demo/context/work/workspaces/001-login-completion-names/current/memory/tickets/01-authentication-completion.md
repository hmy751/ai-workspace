# 01 — 인증 완료를 실제 코드와 사용처에서 맞춘다

## 맡은 결과와 범위

기존 설명 시안의 `loginAndRefresh`·`onCompleted`는 무엇이 끝났는지 넓게 읽힐 수 있었다. 그 가상 시작 장면을 참고해, 이번에는 인증 저장·상태 적용과 조회 요청·완료를 구별하는 새 실행 코드를 작성한다. 이전 제품 코드를 개명했다는 작업으로 기록하지 않는다.

범위는 메모리 기반 Store, 인증 서비스·wrapper, Login·Reauth 소비자 함수와 동작 검사다. Project에는 제품 의미·개발 계약·현재 연결을 각각 두고, 이번 입력 선택·대안·실행 결과는 Work가 소유한다.

## 완료 조건과 확인 방법

완료하려면 다음을 실제로 확인한다.

- 저장이 끝나기 전 새 인증 상태와 완료 알림이 공개되지 않는다.
- 저장 실패 때 이전 인증 상태·로컬 데이터가 남고 조회·완료 알림은 시작하지 않는다.
- 저장·상태 적용 뒤 조회 갱신을 요청하고 조회 완료를 기다리지 않고 인증 완료를 알린다.
- 후속 조회 실패는 완료된 인증을 되돌리지 않으며 별도로 전달된다.
- 두 소비자가 인증 완료만 안내하고 각자의 이동·닫기를 요청한다.

실제 Noline의 서버·저장소·Query·UI 통합, 전체 DB·queue 조율, 기준 설치·기존 파일 이동·본문 전체 채택은 범위 밖이다. 새 문장·구현 선택이 사용자 확정 기준으로 기록되지 않았는지도 확인한다.

## 실행 맥락과 접근

Work의 [Spec](../index.md), [선택한 Project](../project-context.md)와 [개인 기준](../personal-context.md), [초기 입력](../../../source/scenario-input.md)을 함께 사용한다. 내부 소비자 두 곳에서 이름·설명 보완과 조회 대기 동작 변경의 이득·비용을 대조한다. 이름이 바뀐 사실과 동작 계약이 충분한지는 각각 확인한다.

## 현재 상태와 실제 결과

예제 코드와 소비자 작성, 직접 동작 검사7개 및 정상·실패 실행을 마쳤다. 실제 수행 범위는 [실행 기록](../../../records/2026-10-19-03-execution.md)에 있다. 이후 구조 정정으로 context 배치와 Work의 Spec·Ticket·상태·입력·결과 관계를 보완했다. 이름의 이해 효과와 실제 Noline 통합, 사용자 수락은 아직 확인하지 않았다.
