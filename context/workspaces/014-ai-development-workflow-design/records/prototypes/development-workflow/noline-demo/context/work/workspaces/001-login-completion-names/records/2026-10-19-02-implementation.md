# 새 실행 예시를 작성한 판단

2026-10-19, 설명용 조건을 바탕으로 이 Work 아래에서 새 코드와 본문을 작성했다. 그 조건은 [시작 입력](../source/scenario-input.md)에 보존한다. 이전 설명에서 가정했던 구현자·검토자의 활동을 이번 작업의 실제 수행 이력으로 복사하지 않았다. 아래는 당시 작성 판단이며, 이후 같은 코드로 대조한 선택 이유는 [이름 비교](2026-10-19-06-naming-alternatives.md)에 있다.

## 무엇을 유지하고 무엇을 새로 골랐는가

저장 뒤 상태 공개, 저장 실패 시 이전 상태·데이터 보존, 인증 이후 조회 실패의 분리를 제품 계약으로 사용했다. 현재 약속은 [Project 인증 가이드](../../../../project/guidance/authentication-and-session/INDEX.md)에서 읽는다. 이 예시에서는 메모리 저장 어댑터와 단순 여행 목록으로 제한해 실행한다. 실제 DB·queue 귀속 검사와 세션 변경 조율을 구현한 것으로 승격하지 않는다.

기존 시안의 두 내부 사용처·비대기 Query·별도 후속 실패 callback은 설명용 가정이었다. 이번 실행 예시도 그 조건을 선택했다. 코드 모듈 구성, 메모리 어댑터, 테스트, Query 요청의 동기 오류도 후속 오류로 보내는 처리는 이번 작성자가 추가한 구현 선택이다. 사용자와 확정한 개인 기준의 문장이나 실제품 요구로 기록하지 않는다.

| 이번 조건에서 비교한 선택 | 채택 여부와 이유 |
| --- | --- |
| 기존 넓은 이름을 유지하고 가까운 설명 보완 | 가능하지만 이번 새 예시는 내부 소비자가 두 개라 호환성 비용이 작고 호출부 자체에서 범위를 드러내기 쉽다. |
| `signInAndRequestRefresh`·`onSignedIn`으로 표현하고 계약 보완 | 이번 코드에 선택했다. Query 결과를 기다리지 않는다는 사실을 이름·설명·소비자 동작에서 함께 확인할 수 있다. |
| Query 결과까지 기다린 뒤 완료 전달 | 이번 요구가 인증 복구 완료이며 후속 조회 실패를 분리하므로 선택하지 않았다. 조회 결과가 필요한 요구라면 다시 검토한다. |

이 표는 실제 기존 제품의 변경 비용을 측정한 결과가 아니다. 이전 시안의 내부 사용처 조건을 새 예시에 대입한 설계 판단이다. 코드가 새로 생겼으므로 기존 제품 API의 호환성을 보존했다고 주장하지 않는다.

## 실제 작성한 책임

Store는 계정·예시 여행 데이터의 귀속을 확인하고 저장 성공 뒤 상태를 적용한다. 서비스는 인증 응답과 주어진 진행 작업 종료 대기를 거쳐 Store를 호출한다. wrapper는 후속 조회를 시작하고 결과를 기다리지 않고 인증 완료를 전달한다. Login과 Reauth는 각각 안내·이동 또는 안내·닫기를 요청한다.

Login 안내는 처음부터 ‘로그인 완료’로 작성했다. 기존 시안의 ‘검토자가 남은 화면 갱신 완료 문구를 찾아 수정했다’는 장면을 이번 실제 수정 이력으로 만들지 않았다. 현재 완료 의미와 코드·소비자의 관계는 Project current에서 찾는다.

전체 기준 채택·운영 위치 설치·실제품 변경은 수행하지 않았다. 이번 예시는 기준 본문과 제품 계약을 한 작업에서 선택하고 실제 결과에 대조하는 적용 모습을 제공한다. 독립 검토 여부와 테스트 결과는 실제 수행한 범위대로 별도 기록한다.
