# 이름에서 맡은 일과 끝난 일을 알 수 있게 한다

함수·Hook·상태·반환값·완료 알림을 설계하거나, 기존 표현 때문에 사용처가 동작을 잘못 예상할 때 읽는다. **호출자가 이름·타입·가까운 계약을 읽고 무엇을 맡겨도 되는지, 성공 뒤 무엇을 해도 되는지 판단할 수 있게 한다.** 내부의 모든 단계를 이름에 나열하는 것이 목적은 아니다.

이 문서는 여러 작업에 적용할 판단과 핵심 조건을 설명한다. 특정 상황의 관찰·선택·한계는 [이름·완료 판단 사례](cases/naming-and-completion.md)에 따로 둔다. 기준만으로 선택이 분명하지 않을 때 해당 사례를 고른다. 짧은 코드 대비는 의미를 설명하기 위한 예시이며 특정 이름이나 구현을 의무로 정하지 않는다.

일반 기준과 상세 사례의 파일 분리는 사용자가 이번 시안에 반영하도록 선택했다. 현재 기준의 정확한 문장·설명 예시 전체를 채택한 것은 아니다. 사용자 판단과 Main의 구체화, 원문 발췌는 [작성 근거](../../../../authoring-basis.md)에서 확인한다.

## 이름을 정하기 전에 사용 단위와 내부 책임을 구별한다

외부에서 하나의 기능으로 사용하는 것과 내부의 책임을 나누는 것은 함께 성립한다. 하나의 제출 흐름을 제공하면서 내부의 대상 계산·요청·결과 반영을 나눌 수 있다. 외부 이름은 사용자가 맡기는 기능을, 내부 이름은 각 부분이 수행하는 일을 설명한다.

이때 세 결정을 구별한다.

| 결정 | 판단할 내용 | 그 결정만으로 정해지지 않는 것 |
| --- | --- | --- |
| 외부 사용 단위 | 호출자가 어떤 일을 한 번에 맡겨야 하는가. 어디까지 조율해야 그 일을 했다고 말할 수 있는가. | 내부를 한 함수에 모두 쓸지 여부 |
| 내부 책임 | 입력 검증·전송 대상 계산·요청·결과 해석 중 서로 다른 지식과 변경 이유를 가진 부분이 무엇인가. | 각 부분을 별도 파일로 만들지 여부 |
| 파일 배치 | 함께 읽고 바꿀 내용, 독립적으로 사용할 내용, 프로젝트의 구성 관습은 무엇인가. | 파일이 짧다는 이유로 독립 역할을 합칠지 여부 |

**판단 질문 — 호출자가 직접 알아야 할 것이 무엇인가?** 호출자가 매번 검증·요청·결과 반영의 내부 순서를 조립한다면, 기능을 제공하는 단위가 그 순서를 맡는 편이 나은지 본다. 반대로 요청 대상이나 후속 처리가 사용처마다 실제로 달라진다면 그 선택을 호출자에게 남길 수 있다. 내부 구현을 숨기는 것과 사용처가 가진 선택권을 없애는 것을 구별한다.

이미 폼 도구가 입력값·검증 오류를 관리하거나 요청 도구가 pending·error를 소유한다면, 새 기능 단위에 같은 상태를 다시 만들기 전에 **그 상태가 다른 의미를 갖는지** 확인한다. 요청 하나의 진행 상태로 표현되지 않는 항목별 결과는 별도의 기능 상태일 수 있다. 이름과 책임은 기존 도구에 실제로 맡긴 범위까지 포함해 정한다.

기능 단위와 내부 분리가 함께 성립하는 모습을 더 확인하려면 [초대 흐름의 판단 사례](cases/naming-and-completion.md#기능-hook과-내부-책임을-함께-나눈-초대-사례)를 읽는다. 그 코드는 당시 논의한 가상 사례의 재구성이며 현재 작업의 상태 구조를 정하는 답이 아니다.

## 이름·타입·가까운 계약이 같은 역할을 설명하게 한다

이름은 빠르게 역할을 찾게 하고, 타입은 받을 값과 돌려줄 값을 정하며, 가까운 계약은 순서·실패·예외처럼 타입에 드러나지 않는 약속을 설명한다. 셋을 읽고도 올바른 호출 방법을 알기 위해 내부 분기를 매번 따라가야 한다면 설명할 경계가 빠진 것이다.

**판단 질문 — 이 입력은 상태인가, 값인가, 문구인가?** 같은 이름이 이 의미를 오가면 호출자는 사용처마다 다른 전제를 배워야 한다. 특히 표시 여부를 정하는 값과 실제 출력할 메시지를 구별한다.

새로운 API에서는 의도한 값의 종류가 이름·타입·가까운 설명에 드러나도록 한다. 기존 API에서는 실제 혼동·오사용·변경 범위에 비춰 개선 이득을 판단한다. 더 명확한 표현이 있다는 사실만으로 기존 사용처를 모두 바꾸지는 않는다. 더 명확한 표현을 인정하면서 현재 계약을 유지한 조건이 필요하면 [문자열 isError 판단 사례](cases/naming-and-completion.md#문자열-iserror를-유지한-판단)를 읽는다.

반환과 예외에서도 같은 질문을 적용한다. `handleError`라는 이름만으로는 오류를 변환해 돌려주는지, 직접 던지는지 구별하기 어렵다. 실제 코드가 어느 일을 하는지 먼저 확인하고 그 결과를 호출 형태에도 드러낸다.

```ts
// 변환한 오류를 반환하는 계약
function toRequestError(cause: unknown): RequestError { /* 변환 */ }
throw toRequestError(cause);

// 이 함수 안에서 던지는 계약을 선택한 경우
function throwRequestError(cause: unknown): never { /* throw */ }
throwRequestError(cause);
```

위 두 형태는 역할을 설명하는 대안이다. 실제 변환 구현을 생략한 개략 코드이며 새 공통 오류 API를 선택한 것은 아니다. 선택 후에는 호출자가 오류의 형태·의미를 신뢰할 수 있어야 한다. 응답 해석 실패를 네트워크 실패라고 부르는 것처럼 의미를 잘못 분류한 문제는 이름만 명확하게 해도 해결되지 않는다.

타입만으로 사용 의도가 분명해 보여도 실행 우선순위가 숨을 수 있다. 옵션이 전체 처리를 제어하는지, 앞선 처리기가 없을 때만 적용되는지 구별한다. 공통 처리와 로컬 선택의 우선순위·우회 방법은 제품의 계약이며 단어만 바꿔 해결하지 않는다. 실제 관찰과 가능한 오독의 차이는 [silent 옵션의 우선순위 사례](cases/naming-and-completion.md#silent-옵션과-등록-처리기의-우선순위)에서 확인한다.

## 완료 표현은 호출자의 다음 행동과 맞춘다

**판단 질문 — 이 함수가 성공하거나 callback이 불린 직후, 호출자는 어떤 행동을 안전하게 할 수 있는가?** 이름보다 먼저 반환·알림 시점과 그 다음 사용처를 함께 읽는다.

| 성공 시점에 끝난 일 | 아직 말할 수 없는 결과 | 확인할 사용처 |
| --- | --- | --- |
| 작업을 큐에 접수함 | 실행·저장까지 완료됨 | 접수 직후 결과 파일이나 갱신된 데이터를 읽는가 |
| 저장을 마침 | 후속 조회·화면 반영까지 완료됨 | 성공 알림 뒤 최신 조회 결과가 반드시 필요한가 |
| 조회 결과를 받음 | 화면 전환·렌더링까지 완료됨 | callback이 화면에서 무엇을 사용할 수 있다고 약속하는가 |

모든 함수명에 이 단계들을 이어 붙일 필요는 없다. 핵심 결과는 이름과 반환형에서 알 수 있게 하고, 중요한 비대기·실패 조건을 그 함수의 계약 가까이에 둔다. `requestRefresh`와 `refreshAndRead`는 요청과 조회 결과 반환을 대비하는 설명용 이름이며 고정 접두사 규칙이 아니다.

**실패의 범위와 기다릴 범위도 따로 판단한다.** 저장 후 조회가 실패해도 저장은 완료됐을 수 있다. 이때 호출자가 최신 데이터를 필요로 하면 조회를 기다리면서 저장 성공과 조회 실패를 따로 전달할 수 있다. 조회 실패가 저장을 취소하지 않는다는 이유만으로 비대기를 선택하지 않는다. 대기 여부는 다음 행동에 필요한 결과로 정한다.

오류나 성공 문구는 이 완료 경계와 함께 읽는다. 일부 단계가 실패했을 때 이미 끝난 일을 전체 실패처럼 알리면 사용자가 불필요하게 재시도할 수 있다. 반대로 남은 작업이 있는데 전부 끝났다고 알리면 아직 준비되지 않은 결과를 사용하게 된다.

## 유지·개명·계약 보완·동작 수정을 고른다

선택을 가르는 것은 표현의 취향과 함께 **현재 요구, 공개한 약속, 확인한 구현, 사용처의 기대**다.

| 확인한 차이 | 판단과 조치 |
| --- | --- |
| 역할과 동작은 일치하며 이름도 해당 맥락에서 충분하다. 더 선명한 대안은 있지만 실제 이득이 작다. | 현재 이름을 유지할 수 있다. 새로운 이름이 더 마음에 든다는 사실만으로 관련 사용처를 모두 바꾸지 않는다. |
| 동작은 요구를 지키지만 이름 때문에 호출자가 더 큰 결과를 기대한다. | 이름·타입·가까운 계약을 함께 고른다. 내부 사용처를 함께 고칠 수 있으면 개명하고, 공개 호환성이 있으면 기존 이름의 설명 보완과 새 진입점·전환 비용을 비교한다. |
| 공개한 완료 약속을 구현이 지키지 못한다. | 약속을 지키도록 구현을 고친다. 이름만 좁혀 기존 호출자의 요구를 없애지 않는다. |
| 무엇을 완료로 볼지 요구와 사용처에서 합의되지 않았다. | 필요한 결과와 실패 때 유지할 결과를 먼저 정한다. 이름을 고르며 제품 동작을 묵시적으로 결정하지 않는다. |

검토에서는 판단을 바꾼 코드·사용처와 이유, 바꿀 행동과 보존할 약속을 제시한다. “이름이 추상적이다”만으로는 그 관계를 알 수 없다. 내부 함수·공개 API·파일 저장에서 선택이 달라지는 조건은 [유지·개명·동작 수정의 설명용 사례](cases/naming-and-completion.md#유지개명동작-수정이-달라지는-설명용-사례)에서 비교한다.

이 기준을 채택한 뒤에도 같은 방식으로 판단한다. 조건이 달라져 유지가 타당해지거나, 새 사용처 때문에 이전 설명으로 부족해질 수 있다. 질문은 선택을 가를 근거를 찾는 데 쓰고, 매번 모든 질문의 답안 목록을 출력하는 의무로 만들지 않는다.
