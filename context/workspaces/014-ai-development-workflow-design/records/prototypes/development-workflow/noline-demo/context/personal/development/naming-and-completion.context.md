# 이름 기준의 형성 맥락

[이름·책임·완료 기준](naming-and-completion.md)을 만든 목적과 선택 이유, 아직 열어 둔 판단을 설명한다. 현재 적용할 기준은 그 본문이 소유한다. 여기의 설명은 본문을 이해하고 수정할 때 쓰며, 당시 발화·관찰은 [근거 발췌](naming-and-completion.evidence.md)에서 구별해 읽는다.

이 맥락은 **개인 개발 기준을 만드는 과정의 실제 논의**를 재구성했다. 인증 예제의 제품 사건이나 팀 합의로 소급한 기록은 아니다.

## 무엇을 만들려 했나

개발 작업에서 원하는 구현이 나오려면 기능 요구뿐 아니라, 구현자가 무엇을 좋은 코드로 판단하는지도 전달되어야 한다. 이 기준은 그 필요에서 출발했다. 이름 규칙 목록을 만드는 것보다, 코드를 읽는 사람이 맡겨진 역할과 완료 범위를 알아내는 부담을 줄이고 다음 행동을 올바르게 고르게 하는 데 목적이 있다. [출발 배경의 근거](naming-and-completion.evidence.md#목적)

따라서 이름만 따로 평가하지 않고 타입·책임 배치·반환 시점·사용처를 함께 다룬다. 이름은 좋아졌지만 호출자가 필요한 결과를 얻지 못한다면 목적을 달성한 것이 아니다. 반대로 동작이 맞더라도 매번 설명을 찾아야 역할을 구별할 수 있다면 개선할 여지가 있다.

## 현재 방향을 만든 판단

### 사용할 수 있는 수준과 지향하는 명료함을 구별했다

인증 코드의 이름 유지 안과 개명 안을 같은 동작·같은 설명으로 비교하면서, 앞선 해설은 두 안 모두 설명을 읽으면 사용할 수 있다는 점을 강조했다. 사용자는 “되도록 설명이 필요없는 코드”를 지향한다고 밝혔다. 이 말은 본문의 우선순위를 분명하게 했다. 설명으로 사용법을 전달하는 데서 멈추지 않고 코드가 직접 의미를 드러낼 방법을 먼저 검토한다. [당시 발화와 해석 범위](naming-and-completion.evidence.md#코드가-드러내는-의미)

그렇다고 필요한 설명까지 없애는 방향으로 정리하지 않았다. 선택 이유나 외부 제약은 이름에 넣기 어려울 수 있다. 현재 본문이 코드의 명료함과 설명의 역할을 함께 다루는 것은 이 때문이다. 이 구체적인 설명 방식은 발화를 바탕으로 작성자가 풀어 쓴 것이며, 모든 문구를 사용자가 직접 정한 것은 아니다.

### 바꿀 수 있다는 사실과 바꿔서 얻는 이득을 나눴다

인증 예제에서는 내부 사용처 두 곳을 함께 수정할 수 있었다. 이 조건은 개명 비용을 낮추지만, 그 자체가 개명의 이유는 아니다. 이름을 바꿔 호출자가 덜 추론하게 되는 의미가 무엇인지 별도로 설명해야 했다. 이 구별을 반영하면서 실제 오류가 발생하지 않았어도 읽기·변경 부담을 줄이는 개선은 검토하되, 더 선명한 이름이 떠오른다는 이유만으로 기존 API를 모두 바꾸지는 않도록 정리했다. [보완 당시의 판단 근거](naming-and-completion.evidence.md#개선의-이득과-비용)

본문에서 유지·설명 보완·개명·동작 수정을 나란히 다루는 이유도 같다. 이들은 품질의 고정 순위가 아니라 서로 다른 문제에 대응하는 조치다. 특히 필요한 결과가 빠진 상황을 이름만 좁혀 해결했다고 판단하면, 호출자가 기대하는 약속을 잃는다.

### 조건에 따른 적용과 기준 자체의 변경을 구별했다

논의 중 ‘나중에 기준을 다듬을 수 있다’는 뜻과 ‘채택한 기준도 현재 목적·사용 조건에 대입한다’는 뜻을 구별했다. 사용자가 이해하고 반영을 요청한 것은 후자의 의미도 포함한다. 조건에 따라 유지나 보류를 고르는 것이 단지 초안이라서 허용되는 것은 아니다. [이 구별을 확인한 대화](naming-and-completion.evidence.md#조건별-적용)

개인 기준을 Project 가이드까지 반영한 뒤에는 관리 책임도 다시 정리했다. 여러 제품에 가져갈 판단은 Personal이 관리하고, 이번 적용은 Work가, 제품의 지속 계약은 Project가 관리한다. 이는 설명을 서로 완전히 분리하자는 뜻이 아니다. 개인 선호의 변경이 제품의 약속 변경으로 자동 전파되지 않게 하려는 선택이다. [관리 기본값을 정리한 대화](naming-and-completion.evidence.md#개인-기준의-소유)

## 반영한 방향과 아직 열려 있는 것

**사용자에게 확인한 방향**은 코드 자체의 명료함을 지향하는 것, 채택한 기준도 조건에 대입해 적용하는 것, 개인 기준과 제품 계약의 관리 책임을 구별하는 것이다. 본문은 이 방향을 현재 판단에 사용할 수 있도록 구체화한 시안이다. 문장·표·사례 전체의 충분성까지 최종 수용된 것은 아니다.

[인증 비교 사례](cases/naming-and-completion.md#같은-동작에서-이름-유지와-개명-비교)의 `signInAndRequestRefresh`·`onSignedIn`은 그 예제 조건에서 선택한 표현이다. 일반 명명 규칙이나 가능한 최선의 이름으로 확정한 결과가 아니다. 같은 코드 비교는 표현 차이를 설명하지만, 실제 이해 속도나 장기간의 유지 비용이 개선됐다는 측정 근거는 아직 없다.

이 기준을 더 구체화할 때는 실제 사용처에서 어떤 추론이 줄었는지, 설명에 남겨야 할 계약은 무엇인지로 판단할 수 있다. 새 사례가 기존 방향과 어긋나면 아래 방식으로 근거와 해석을 구별해 재검토한다.

## 언제 무엇을 읽나

| 하려는 일 | 읽을 범위 |
| --- | --- |
| 현재 코드에 기준을 적용한다. | [본문](naming-and-completion.md)을 읽는다. 선택이 갈리는 이유가 더 필요하면 [사례](cases/naming-and-completion.md)를 고른다. 형성 과정을 매번 읽을 필요는 없다. |
| 기준의 의미·우선순위·적용 조건을 바꾸거나, 문장만으로 의도를 확신하기 어렵다. | 본문과 이 맥락을 함께 읽는다. 여기서 설명한 목적·판단·열린 부분 중 무엇이 달라지는지 확인한다. |
| 사용자 동의의 범위, 이전 판단의 정확한 뜻, 새 근거와의 충돌을 판단한다. | 해당 설명에 연결된 [근거 발췌](naming-and-completion.evidence.md)를 읽는다. 발화와 작성자의 해석을 구별한다. |

## 변경할 때 관계를 유지하는 방법

개인 기준의 의미와 채택에 관한 책임은 기준의 소유자인 사용자에게 있다. 현재 작업자는 요청받은 범위에서 본문과 관련 맥락을 함께 관리한다. 이 문서가 새 선호를 임의로 채택할 권한을 주는 것은 아니며, 승인된 수정이나 표현 정리에 매번 별도 승인을 요구하는 것도 아니다.

| 실제로 달라진 것 | 갱신할 내용과 유지할 경계 |
| --- | --- |
| 개인 기준의 의미·우선순위·적용 조건 | 본문을 고치고, 이 맥락의 현재 설명·열린 판단 중 영향받는 부분을 같은 작업에서 고친다. 새 선택의 이유와 근거를 연결한다. 사례가 여전히 같은 판단을 보여 주는지 확인하고 필요한 부분만 수정한다. |
| 뜻이 같은 문장 다듬기·오탈자 | 해당 문장만 고친다. 관계를 확인했다는 표시를 위해 맥락·근거의 날짜나 문구를 함께 바꾸지 않는다. |
| 기존 판단과 충돌하는 새 관찰·발화 | 근거에 출처·시점·조건·확인 한계를 추가하고, 여기에서 기존 판단에 미치는 영향과 남은 질문을 설명한다. 새 관찰만으로 기존 사용자 방향을 뒤집거나, 과거 발화를 새 결론에 맞춰 다시 쓰지 않는다. 명시적인 방향 변경이면 그 요청을 근거로 현행 본문도 갱신한다. |
| 특정 제품의 요구·이번 사용처·변경 비용 | 해당 Project 또는 Work의 판단을 갱신한다. 개인 기준 자체가 달라졌는지 별도로 판단하며, 개인 기준의 변경만으로 Project의 계약을 함께 바꾸지 않는다. |
| 파일 이동·이름 변경 | 들어오는 링크·본문 사이의 연결과 열람 화면을 갱신한다. 위치 변경을 기준의 새로운 합의로 기록하지 않는다. |

근거의 당시 원문은 보존한다. 잘못 옮긴 발췌를 발견하면 원자료와 대조해 정정하고, 어떤 전사 오류를 고쳤는지 옆에 남긴다. 새 해석은 맥락에, 새 근거는 출처를 구별한 별도 항목에 쓴다. 맥락은 현재 이해에 맞게 다시 구성할 수 있으며 전체 대화나 매번의 편집 이력을 누적할 필요는 없다.

마무리할 때는 **본문이 지금 권하는 행동과 맥락이 설명하는 이유·범위가 맞는지**, 연결한 근거가 그 설명을 실제로 뒷받침하는지 확인한다. 서로 어긋나면 수정 시각이 최신인 쪽을 무조건 정답으로 삼지 말고, 현재 요청·근거·권한으로 해결할 수 있는 차이인지 판단한다. 해결할 수 없는 차이는 이 맥락의 열린 판단에 구체적으로 남긴다. 기준을 사용 중인 Work의 선택에도 영향이 있는지 살핀다.

링크와 [열람 화면 생성 검사](../../../../viewer/README.md)는 경로·누락·표시 원문 일치를 확인한다. 본문만 바뀌었다는 사실은 맥락이 낡았다는 증거가 아니며, 검사 통과도 의미의 일치를 보장하지 않는다. 이 묶음은 작업자가 읽고 갱신하는 방식으로 운영하며 자동 감지나 저장소 간 동기화를 전제하지 않는다.
