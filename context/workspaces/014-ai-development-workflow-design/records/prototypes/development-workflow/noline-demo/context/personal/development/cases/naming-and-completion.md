# 이름·책임·완료 범위의 판단 사례

이 문서는 [일반 기준](../naming-and-completion.md)을 특정 조건에 적용했을 때 무엇을 보고 선택했는지 설명한다. 일반 기준이 현재 판단을 소유하고, 이곳은 사례의 상황·당시 선택·한계와 다시 볼 조건을 소유한다. 현재 작업의 코드·요구 확인을 대신하지 않는다.

초대는 사용자와 논의한 가상 사례의 재구성, isError와 silent는 당시 실제 코드의 관찰, 마지막 세 대비는 Main이 만든 설명용 상황이다. 사용자 발화·관찰과 새 해석을 각 사례에서 구별한다. 아래 이름·코드·유지 결론을 모든 작업의 규칙으로 올리지 않는다. 원문 발췌와 외부 자료를 참고한 범위는 [작성 근거](../../../../../authoring-basis.md)에서 더 확인할 수 있다.

## 기능 Hook과 내부 책임을 함께 나눈 초대 사례

**논의한 상황.** 여러 이메일의 입력 검증·전송 대상 계산·초대 요청·항목별 결과 반영을 하나의 기능으로 제공하는 가상 예를 비교했다. 사용자는 기능 Hook으로 묶는 것과 그 안에서 책임을 나누는 것이 다른 선택이라고 짚었고, 두 선택을 함께 하는 구성을 괜찮게 보았다. 이는 사용자 제품의 실제 구현을 확인한 사례가 아니다.

**당시 판단.** 호출자는 초대 기능을 맡기고, 기능 내부에서는 검증·요청·결과 처리를 나눌 수 있다. 사용자는 이를 확정된 원칙으로 고정하지 말고 상황에 따라 달라지는 부분을 함께 남기라고 했다. React Hook Form·React Query처럼 이미 책임을 맡은 도구가 있다면 분리 판단에 포함해야 한다는 의견도 덧붙였다.

다음 코드는 앞선 본문 개선에서 그 구별을 보이려고 재구성한 설명용 코드다. 원래 코드의 정확한 발췌나 채택한 API가 아니다.

```ts
// 기능을 사용하는 쪽은 초대의 내부 처리 순서를 조립하지 않는다.
const invitation = useMemberInvitation();
await invitation.submit();

// useMemberInvitation 내부의 submit을 단순화한 예
async function submit() {
  const prepared = prepareSubmission(rows);
  setRows(prepared.rows);
  if (prepared.targets.length === 0) return;

  const results = await invitationMutation.mutateAsync(prepared.targets);
  setRows(current => applyInvitationResults(current, results));
}
```

`submit`은 제출 흐름을 조율하고, `prepareSubmission`은 검증 결과·전송 대상을 계산하며, `applyInvitationResults`는 응답을 목록에 반영한다. 오류 처리·재전송 정책은 생략했으므로 실제 변경에서는 그 정책까지 확인해야 한다.

**적용 한계와 다시 볼 조건.** 폼 도구가 입력·검증 오류를 관리한다면 `rows`를 그대로 별도 상태로 추가할 이유는 없다. 요청 도구의 pending·error와 항목별 성공·실패가 같은 정보인지도 구별한다. 위 이름·상태 구조·Hook 사용·파일 분리를 의무로 정한 것은 아니다. 사용처마다 대상 선택이나 후속 처리가 달라지는 경우 무엇을 공통 기능에 맡길지는 다시 판단한다. 이 구체적인 재검토 설명은 당시 도구 책임 관점을 현재 본문에 적용한 Main의 설명이다.

[당시 사용자 발화·가상 코드·도구 책임 논의](../../../../../../../2026-10-13-31-criteria-roles-and-responsibility-interview.md)에서 상황을 더 확인한다. 당시 논의가 특정 명명 규칙을 직접 채택한 것으로 읽히지 않게 한다.

## 문자열 isError를 유지한 판단

**관찰한 상황.** 당시 Input·Select는 문자열 `isError`를 받아 오류 스타일의 조건으로 사용했고, 문구 출력은 `Field.Message`가 맡았다. 같은 계열의 MultiSelect.Trigger는 boolean을 받았다.

아래 JSX는 그 관계를 보여 주려고 재구성한 대비다. 사용자가 작성한 원본의 정확한 발췌나 채택한 새 API가 아니다.

```tsx
// 당시 사례의 의미: 문자열의 유무로 오류 스타일을 정한다.
<Input isError={errorMessage} />
<Field.Message>{errorMessage}</Field.Message>

// 오류 상태만 받도록 계약을 바꾼다면 가능한 표현
<Input isError={Boolean(errorMessage)} />
<Field.Message>{errorMessage}</Field.Message>
```

**당시 사용자 판단.** boolean이 더 명확하다는 점은 인정하면서도, 당시 사용에서 문자열 전달을 중요한 수정 사안으로 보지 않았다. 따라서 boolean 변경을 필수 수정으로 올리지 않았다. 더 명확한 표현을 제안할 수 있다는 것과 현재 코드를 반드시 고쳐야 한다는 것은 구별한다.

**이 판단의 한계.** 모든 `is` 이름에 문자열을 허용한 결정이나 모든 사용처의 안전성을 검증한 결과가 아니다. 현재 방식을 유지할 수 있다는 사례 판단이며 새로운 코드의 입력 의미를 모호하게 정할 근거도 아니다.

**다시 볼 조건 — 이번 설명안.** 새 사용처가 문자열을 출력할 내용으로 기대하거나 컴포넌트마다 다른 입력 의미가 실제 오사용을 만든다면 계약을 다시 비교한다. 이름·타입 변경으로 줄일 혼동과 기존 호출부를 바꾸는 비용을 함께 확인한다. 이 조건의 정확한 문구는 이번 구체화이며 당시 사용자가 채택한 API 규칙이 아니다.

[Input·Select 관찰과 사용자 판단 원문](../../../../../../../2026-10-16-45-naming-readability-supplement.md#iserror-비교에-대한-사용자-판단)을 함께 보존한다.

## silent 옵션과 등록 처리기의 우선순위

**관찰한 상황.** 오류 처리 비교에서 ErrorBoundary는 `errorService.handle(error, { type: 'silent', context: ... })`를 호출했다. 등록된 AuthError·NetworkError 처리기는 silent 분기보다 먼저 실행되므로 토스트나 이동이 발생할 수 있었다. 우회 인자는 있었지만 이 호출에서는 전달하지 않았다. 당시 코드를 읽은 분석이며 이번에 제품을 새로 실행해 재현한 결과는 아니다.

**관찰에서 얻은 해석.** 호출부의 `silent`만 보면 모든 표시를 막는 옵션으로 오해할 수 있다. 이는 가능한 오독에 대한 Main의 해석이며 당시 호출자의 내적 의도를 확인한 발화가 아니다. 실제 구현은 등록 처리기가 없을 때의 대체 동작에 해당 옵션을 사용했다. 이름·타입만으로 처리 우선순위가 충분히 드러나는지 확인할 사례다.

**사용자 동의와 미정.** 사용자가 동의한 것은 공통 오류의 형태와 의미를 사용처가 신뢰할 수 있어야 한다는 관점이다. 등록 처리기보다 로컬 옵션을 항상 우선하기로 결정한 것은 아니다. 공통 정책·로컬 선택의 우선순위와 예외 범위는 제품의 계약에 맞춰 정할 후보로 남겼다.

**다시 볼 조건 — 설명안.** 표시 억제나 오류 처리의 우회가 실제 요구라면, 어느 처리까지 억제해야 하는지와 등록 처리기·fallback의 순서를 함께 확인한다. 이름만 바꾸거나 모든 공통 처리를 우회하는 것으로 답을 고정하지 않는다.

[실제 호출·등록 처리기 순서·사용자 동의](../../../../../../../2026-10-16-47-fetcher-error-contract-comparison.md)를 다시 읽을 수 있다. 반환/throw의 표현 문제는 [일반 기준의 짧은 대비](../naming-and-completion.md#이름타입가까운-계약이-같은-역할을-설명하게-한다)와 연결되지만 같은 API 설계 결정은 아니다.

## 유지·개명·동작 수정이 달라지는 설명용 사례

아래 상황은 기존 비용·계약 관점을 설명하려고 Main이 구성한 대비다. 실제 제품 사건이나 사용자가 이미 채택한 해결책이 아니다. 기존 본문의 유지·개명·동작 수정 구별과 파일 저장 예시를 상세 사례로 보존한다.

| 가정한 조건 | 가능한 선택과 이유 | 다시 볼 변화 |
| --- | --- | --- |
| 내부 함수가 요청 접수까지만 보장하지만 이름 때문에 소비자가 후속 처리도 끝났다고 기대한다. 사용처가 적고 함께 수정할 수 있다. | 요청 범위가 드러나는 이름과 가까운 계약 설명을 함께 고를 수 있다. 실제 오독과 변경 비용을 비교하고 동작은 보존한다. | 외부 공개, 사용처 증가, 필요한 완료 결과의 변화 |
| 공개 API의 짧은 이름은 널리 쓰이고 반환형·문서로 접수와 완료를 구별할 수 있다. | 이름 유지와 설명 보완을 비교할 수 있다. 오사용이 이어지면 새 진입점과 전환 비용도 검토한다. 호환성이 있다는 이유만으로 오해를 방치하지 않는다. | 설명으로 해결되지 않는 오사용, API 전환 시점 |
| 파일 저장 완료를 약속한 함수가 쓰기를 시작하자마자 성공을 반환한다. 호출자는 성공 뒤 파일을 읽는다. | 약속을 지키도록 구현과 확인을 고친다. 이름을 저장 요청으로 좁혀 기존 요구를 없애지 않는다. | 호출자가 접수만 필요하도록 요구가 바뀌는 경우 |

마지막 상황의 검토 지적은 “`await save()` 직후 파일을 읽지만 `save`는 쓰기를 시작한 뒤 반환한다. 저장 완료 약속을 지키도록 반환 시점을 바꾸고 그 호출을 확인한다”처럼 쓸 수 있다. 이는 지적의 근거와 조치를 보여 주는 새 설명이며 실제 검사 결과가 아니다.

세 대안을 모든 코드에서 매번 작성하는 양식으로 삼지 않는다. [일반 기준의 적용 판단](../naming-and-completion.md#유지개명계약-보완동작-수정을-고른다)으로 돌아가 현재 요구·계약·사용처를 대조한다. 호출과 완료 의미를 따로 살피던 선행 시안은 [01의 주문 사례](../../../../../../applied-criteria-2026-10-17/shop-web/context/project/cases/order-flow.md)에 있고, 당시 의미와 이번 설명의 관계는 [작성 근거](../../../../../authoring-basis.md#완료실패대기의-구체화)에서 확인한다.
