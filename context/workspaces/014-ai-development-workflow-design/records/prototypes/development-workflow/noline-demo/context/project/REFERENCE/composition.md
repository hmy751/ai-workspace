# 내용 구성과 분리

다음 관련 작업자가 반복해서 물을 질문을 기준으로 본문을 구성한다. 조사 파일·Ticket·회의 순서를 그대로 목차로 옮기지 않는다. 내용의 책임과 함께 읽을 이유가 달라질 때 나누며, 파일 수 자체를 목표로 하지 않는다.

제품과 데이터의 의미·제약은 common, 여러 구현 경로의 현재 연결과 지원 범위는 current, 관련 작업의 계약·판단·검증은 guidance가 맡는다. 기술적이거나 여러 곳에 쓰인다는 이유만으로 모두 common에 넣지 않는다. 한 주제에 반드시 세 문서를 만드는 규칙도 없다.

자기 범위의 의미·이유·조건은 본문만으로 이해할 수 있어야 한다. 다른 Owner의 전제를 짧게 설명할 수 있지만 상세 기준은 복제하지 않는다. 코드가 쉽게 알려 주는 목록과 일회성 검사 수치를 별도 현황으로 반복하기보다 다음 판단을 바꾸는 관계와 확인 한계를 설명한다.

근거가 지지하는 범위보다 넓게 주장하지 않는다. 이 demo의 메모리 예제 검사를 실제 Noline의 DB·UI·queue 증거로 올리지 않는다. 새로운 제품 요구, 구현 관찰, 작성자의 예시는 각각의 지위를 밝힌다. 선택·시행착오의 상세는 Work records에 두고 필요한 때 연결한다.
