# Personal context — 개인이 여러 작업에 가져가는 판단

이 단위는 개인이 여러 Project에서 사용할 판단 기준과 그 이유·적용 조건을 소유한다. 어떤 제품의 요구, 팀이 함께 지킬 개발 계약, 현재 구현 상태, 한 작업의 진행은 여기서 정하지 않는다.

현재 작성한 주제는 [개발 판단](development/README.md)이며, 짧은 공통 기준과 이름·책임·완료 범위의 상세 본문을 제공한다. 개인 기준 전체가 완성됐다는 뜻은 아니다. 다른 주제가 필요해지면 같은 책임 안에서 추가하고, 서로 다른 내용을 하나의 긴 본문으로 합치지 않는다.

## 이 시안에서 선택한 것과 검토할 것

사용자는 01에서 일반 원칙과 구체 사례를 구별하고 조건에 따라 판단하는 방향, 짧은 공통과 이름·가독성의 독립 절을 시안에 반영하도록 선택했다. [68의 적용 보완](../../../../../2026-10-18-68-principle-application-and-choice-basis.md)과 [72의 구성 선택](../../../../../2026-10-18-72-short-common-and-detail-prototype.md)이 그 근거다. [73의 전체 수용 유보](../../../../../2026-10-18-73-prototype-reservations-and-ticket03.md)는 유지한다.

이번에는 [사용자 요청87](../../../../../2026-10-19-87-conditional-application-and-provenance.md)에 따라 채택 뒤에도 조건으로 적용한다는 설명과 원래 대화·사례로 가는 경로를 보완했다. 이 보완 요청을 기존 시안 전체의 채택으로 읽지 않는다.

현재 설명 문장과 질문의 정확한 표현, 두 파일의 구성, `requestRefresh`·`refreshAndRead` 예시와 내부 함수·공개 API·파일 저장의 세 대비는 **Main이 추가 작성한 검토안**이다. 기존 논의를 이어 쓴 부분과 새 설명의 차이는 [이름 상세의 근거 안내](development/naming-and-completion.md#원래-대화와-사례를-다시-읽을-때)에서 찾는다. 예시의 이름과 선택을 사용자가 이미 결정한 공통 규칙으로 적용하지 않는다.

## 내용과 읽는 조건

개발 작업의 목적과 변경 비용을 함께 판단할 때는 개발 판단의 공통 부분을 읽는다. 함수·상태·반환값·완료 알림이 무엇을 약속하는지 쟁점이면 그 안의 이름·완료 범위 본문을 고른다. 이 입구는 개인 기준 안에서 필요한 내용을 찾게 하며, 특정 Project의 채택 목록이나 문서 위치를 관리하지 않는다.

실제 작업에 개인 기준을 가져갈 주체는 해당 작업의 요청과 대상 맥락을 함께 확인해야 한다. 이 문서가 제품의 요구나 팀의 합의를 대신 결정하지 않는다.

## 갱신하는 경우

기존 기준으로 설명하지 못하는 조건이 드러나거나 개인의 판단이 바뀌면, 기준의 의미·이유·적용 조건을 다시 검토한다. 당시 문제와 비교한 선택을 확인할 수 있는 근거를 보존하고, 변화가 필요한 본문을 고친다. 한 작업에서 골랐던 함수명이나 해결책을 곧바로 개인 공통 의무로 추가하지 않는다.

이 프로토타입의 개인 기준은 `noline-demo/context/personal/`에 있으며, 같은 context 아래의 Project·Work와 나란히 둔다. 사용자는 개인 기준을 글로벌로 분리하지 않고 로컬 context 안에서 관리·축적·수정하려는 뜻이라고 정정했다. 별도 ai-workspace 모형을 개인 기준의 필수 호스트로 두지 않는다. 여러 프로젝트에서 같은 개인 기준을 배포·동기화하는 방법과 실제 skill 연결은 아직 정하지 않았다. 이 위치 선택은 본문 전체의 최종 채택과 다르다.
