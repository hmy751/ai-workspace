# 인증 표현 가이드의 근거

[표현 가이드](../INDEX.md)와 [형성 맥락](context.md)을 확인할 제품 원문·작성 기록의 최소 발췌다. 개인 기준의 소유 정정은 이미 있는 자료에 연결하며 같은 원문을 복제하지 않는다.

## 제품 자료의 지위

제품 원문 식별 경로는 `context/workspaces/014-ai-development-workflow-design/source/supplement/worktree-project-context/context/project/guidance/code-readability.md`이다. 해당 보존 관찰판은 Workspace의 사용자 합의를 확인해 2026-09-25에 통합했다고 밝힌다. 이 발췌는 현재 데모 작성에 참고한 제품 가이드의 증거이며 원합의 전체를 이번에 직접 회수한 것은 아니다. 관찰판의 역사 시점·실제 구현 확인 한계는 [공통 근거 안내](../../../common/device-session/_background/evidence.md#자료의-지위와-범위)를 따른다.

## 이름과 완료 범위의 제품 기준

제품 문서의 「이름은 실제 책임과 완료 범위를 표현한다」에서 발췌했다.

> 상태나 함수의 이름이 실제 보장보다 큰 뜻을 갖지 않게 한다. 네트워크의 실제 관측과 Debug 표시 상태, 일부 저장 action과 로그인 전체 절차, 조회 갱신 요청과 조회 완료는 서로 다른 책임이다.

> 인증 정보를 저장·적용하는 action은 계정 전환의 전체 중단·검사·정리 절차를 완료한 것처럼 이름 붙이지 않는다.

> 캐시 무효화를 요청했으면 화면 데이터 갱신이 끝났다고 표현하지 않는다.

부분 책임과 전체 절차, 요청과 결과를 이름에서 혼동시키지 않는 기준이다. 현재 선택한 `signInAndRequestRefresh`나 `onSignedIn`이라는 이름을 원제품에서 채택했다는 증거는 아니다.

## 비동기 표현의 제품 기준

같은 제품 문서의 「비동기 표현은 순서와 실패 책임을 따른다」에서 발췌했다.

> `await`는 뒤 작업의 선행 조건인지를 보고 사용한다. 보기 좋게 순서를 맞추려고 추가하면 동시 실행과 완료 시점이 달라질 수 있다. 기다리지 않는 작업에도 누가 실패를 처리하는지, 호출자의 완료가 어디까지인지는 분명해야 한다.

> 인증 완료 뒤 캐시 갱신 실패를 인증 저장 실패로 되돌리지 않는 것처럼 서로 다른 완료 경계는 이름·반환·`catch` 범위에서도 유지한다.

이는 이름 개선만으로 대기를 추가하지 않으며 실패·완료 계약을 함께 읽을 근거다. 실제 로그인 경로의 Query 대기 여부는 이 일반 문장만으로 확정하지 않는다.

## 판단 조건과 현재 이름을 나눈 작성 논의

출처 식별 경로: `context/workspaces/014-ai-development-workflow-design/records/2026-10-19-92-principles-cases-and-agreement-reconciliation.md`, 「실제 본문에서 바로잡은 관계」. 2026-10-19 데모의 본문 배치를 수정한 기록이다.

> Project 가이드에서 최종 함수명과 코드 발췌를 current로 옮기면서도 제품 계약의 순서·실패·대기·소비자 조건은 가이드에서 직접 이해할 수 있게 남겼다.

같은 표에서 확인 범위를 다음과 같이 제한했다.

> 원래 전달문 그대로의 복원이나 새 작업자의 독립 적용 실험이라고 주장하지 않는다. 재실험의 입력 판본 고정·전달 방식은 미정이다.

따라서 이 구별은 당시 작성자의 본문 수정과 한계이며 새로운 작업자가 기준을 찾아 같은 이름을 골랐다는 실험 증거가 아니다.

## 개인 기준 변경과 Project 갱신

2026-10-19 관리 책임 정정의 사용자 발화·Main 정리·회수 한계는 [개인 기준 소유 발췌](../../../../personal/development/naming-and-completion/_background/evidence.md#개인-기준의-소유), 당시 선택의 경위는 [소유 책임 기록](../../../../personal/development/naming-and-completion/_background/records/2026-10-19-personal-ownership.md)에 보존돼 있다.

이 가이드에서 일반적인 코드 개선 우선순위·동일 주석 A/B 비교 방법·이번 개명 비용 판단을 덜어낸 사실은 `context/workspaces/014-ai-development-workflow-design/records/2026-10-19-102-personal-project-update-ownership.md`의 「실제 문서 조정」과 대조했다. 현재 인증 결과·실패 의미·소비자 요구의 설명은 유지했다. 이 출처 식별은 추가 확인 경로이며 위 내부 발췌·기록 없이 바깥 작업 전체를 읽도록 요구하지 않는다.
