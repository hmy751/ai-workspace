# 개발 판단 — 공통 관점과 주제별 기준

코드를 만들거나 고칠 때는 **누가 무엇을 맡기고, 무엇을 알아야 하며, 어떤 결과를 믿고 다음 행동을 하는지**를 본다. 같은 책임을 이해하는 데 필요한 맥락은 모으고, 서로 다른 지식·변경 이유를 가진 책임은 구별한다. 실제로 줄어드는 호출·읽기·변경 부담과 새로 생기는 연결·호환 비용으로 판단한다.

기존 도구에 맡긴 책임도 출발점에 포함한다. 폼이 입력을, 요청 도구가 진행 상태를 이미 관리하는 경우라면 새 기능 단위가 추가로 소유할 일이 무엇인지 확인한다. 기능을 한 단위로 제공하는 것, 내부 책임을 나누는 것, 파일을 나누는 것은 각각 판단한다.

**기준은 채택한 뒤에도 현재 조건에 적용해 판단한다.** 요구·사용처·비용을 대조해 유지·수정·보류를 고른다. 현재 코드가 기준의 예시와 다른 모양이라는 사실만으로 수정하지 않으며, 실제 버그가 없어도 읽기·변경 부담을 줄이는 구조 개선은 검토할 수 있다.

| 지금 판단할 일 | 읽을 본문 | 읽고 판단할 차이 |
| --- | --- | --- |
| 함수·Hook이 맡은 일, 상태·오류의 의미, 반환·완료 알림 | [이름·책임·완료 범위](naming-and-completion.md) | 사용 단위와 내부 책임, 이름·타입·계약의 일치, 대기·실패의 범위, 유지와 수정의 이유 |
| 위 기준만으로 현재 선택이 불분명하거나 과거 선택의 조건을 다시 살필 때 | [이름·완료 판단 사례](cases/naming-and-completion.md) | 초대의 가상 비교, 실제 isError·silent 관찰, Main의 설명용 대비를 구별하고 현재 조건과 비교 |

현재 상세 본문은 이 한 주제다. 일반 기준과 상세 사례는 별도 파일로 두되 기준을 이해하는 데 필요한 조건과 짧은 대비는 기준 가까이에 남긴다. 상세 사례는 필요한 항목을 골라 읽고, 사례의 답을 현재 작업의 답으로 복사하지 않는다. 책임 설계·검증·가독성 전체를 이 한 주제로 대신하지 않는다. 필요한 주제가 늘면 그 주제의 판단을 독립적으로 설명한다. 작성 지위와 관리 범위는 [Personal 안내](../README.md#이-시안에서-선택한-것과-검토할-것)에서 확인한다.
