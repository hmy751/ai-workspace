# 이번 작업에서 고른 입력

이 문서는 Work가 실제 사용한 입력과 이유를 남긴다. Project 문서가 외부 기준을 상시 알고 관리하도록 만드는 채택 목록은 아니다. 입력의 선택·대조·전달 절차는 이 프로토타입의 [개발 workflow](../../../DEVELOPMENT.md)가 맡는다.

| 고른 입력 | 이번에 필요한 이유 | 읽는 범위 |
| --- | --- | --- |
| [개인 개발 공통](../../../../personal/development/index.md) | 기준과 모양이 다르다는 이유만으로 바꾸지 않고 목적·사용처·비용을 먼저 판단한다. | 현재 작업의 조건부 적용 설명 |
| [개인 이름·책임·완료 상세](../../../../personal/development/naming-and-completion/index.md) | 표현 정리, 설명 보완, 구현의 보장 부족을 구별한다. | 책임·완료 범위와 대안 비교. 그 안의 Main 새 질문·사례를 확정 기준으로 올리지 않는다. |
| [기기 세션의 제품 의미](../../../../project/common/device-session/index.md) | 같은 계정의 로컬 작업을 보존하는 이유를 확인한다. | 재인증과 조회 결과의 차이 |
| [인증·세션 계약](../../../../project/guidance/authentication-and-session/index.md) | 저장·상태 공개 순서와 실패 후 보존할 결과를 정한다. | 이번 wrapper가 건드리는 완료·후속 실패 경계 |
| [인증 가독성](../../../../project/guidance/code-readability/index.md) | 함수·callback·안내를 소비자가 필요로 하는 결과와 대조한다. | 이름을 고정 답으로 삼지 않는 적용 기준 |
| [시작 장면](../source/scenario-input.md) | 모호한 이름·소비자 가정을 확인한다. | 이 Work에 보존한 가상의 시작 입력이며 실제 제품 코드·이전 테스트 결과가 아니다. |

기준을 채택한 뒤에도 작업마다 조건에 따라 적용한다는 뜻을 이번 장면에서 사용했다. 내부 사용처 두 개이고 호환 API가 없다는 예시 조건에서는 개명으로 완료 범위를 알리기 쉽다. 공개 API였다면 이름 유지와 계약 보완이 타당할 수 있고, 조회 결과까지 약속한 기능이었다면 구현 변경이 필요하다. 이번 코드 선택이 그 대안들을 없애지 않는다.

이번 선택에서는 Personal 본문에 이미 붙은 원래 대화·사례 경로 전체를 새로 읽는 절차를 실행하지 않았다. 기준의 뜻·채택 범위를 다시 판단할 때 해당 상세의 선택 조건으로 돌아간다. 원문을 읽지 않았는데 재검토했다고 기록하지 않는다.
