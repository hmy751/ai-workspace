# 이번 작업이 선택한 개인 기준

기준은 같은 프로젝트의 [context/personal](../../../../../personal/README.md)에 있다. Work가 필요한 주제를 선택하며 Project 본문은 개인 기준의 위치나 채택 목록을 관리하지 않는다.

[짧은 개발 공통](../../../../../personal/development/README.md)의 목적·사용처·비용에 따른 적용을 사용한다. 이름과 완료가 쟁점이므로 [이름·책임·완료 범위](../../../../../personal/development/naming-and-completion.md)를 추가로 읽는다. 그 본문의 질문·예시를 기계적으로 복사하지 않고 유지+설명, 개명+설명, 동작 변경의 차이를 이번 계약에 대입한다.

두 내부 소비자라는 조건에서는 개명 비용이 작지만 공개 API라면 이름 유지와 계약 보완이 타당할 수 있다. 조회 결과를 약속하는 요구였다면 이름을 좁히는 대신 구현을 바꿔야 할 수 있다. 이번 코드 선택으로 다른 조건의 판단을 없애지 않는다.

일반 기준만으로 판단 차이가 드러나지 않을 때 [상세 사례](../../../../../personal/development/cases/naming-and-completion.md)의 해당 절을 고른다. 전체 기능과 내부 책임의 관계는 초대 사례, 더 명확한 이름과 변경 필요의 차이는 isError 사례, 숨은 우선순위는 silent 사례에서 살핀다. 이번 로그인 작업이 이 사례 모두를 필수 입력으로 삼는 것은 아니다.

Personal의 형식·조건별 적용에 관한 사용자 선택과 Main이 새로 쓴 문장·사례의 지위를 유지한다. 뜻이나 채택 범위를 다시 검토할 때 사례에 보존한 관찰·당시 판단과 원기록으로 돌아간다. 선택 절차는 [개발 절차](../../../../DEVELOPMENT.md), 최초 선택 이력은 [기록](../../records/2026-10-19-01-input-selection.md)에 있다. 현재 연결된 본문은 이후 보완된 판본이며 최초 입력의 고정 사본이 아니다.
