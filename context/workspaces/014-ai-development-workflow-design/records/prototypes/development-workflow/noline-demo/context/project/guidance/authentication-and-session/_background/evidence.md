# 인증 계약의 제품 근거와 작성 선택

[인증 계약 본문](../INDEX.md)과 [형성 맥락](context.md)을 확인할 최소 발췌다. 공통 제품 의미는 [기기 세션 근거](../../../common/device-session/_background/evidence.md)가 소유하며 여기에는 저장·공개·조율과 대기 선택에 필요한 부분을 둔다.

## 제품 자료의 지위

제품 원문 식별 경로는 `context/workspaces/014-ai-development-workflow-design/source/supplement/worktree-project-context/context/project/guidance/authentication-and-session.md`이다. 해당 보존 관찰판은 2026-09-25에 코드와 책임·회귀 근거를 대조했다고 기록한다. 정확한 역사판과 현재 실제 구현에 대한 한계는 [공통 자료의 범위](../../../common/device-session/_background/evidence.md#자료의-지위와-범위)와 같다. 2026-10-20에 보존 파일을 읽었으며 실제 제품 코드를 다시 실행하지 않았다.

## Store와 전체 서비스

제품 문서의 「상태 판단, DB 사실, 전체 절차를 구별한다」에서 발췌했다.

> 인증 상태에 근거한 판단은 Auth Store, 실제 데이터 소속과 SQL 접근 조건은 DB 접근 모듈, 로그인·로그아웃·탈퇴 전체의 조율은 서비스가 맡는다.

> **새 진입점도 전체 세션 변경 서비스를 사용한다.** 화면마다 저장소 검사와 종료 순서를 조립하거나 Store action만으로 전체 절차를 대신하지 않는다.

이는 책임과 진입점의 구별이다. 특정 이름·class·factory·facade를 의무화하거나 데모의 주입된 대기가 실제 종료 조율임을 증명하는 근거가 아니다.

## 로그인 완료와 저장 실패

제품 문서의 「로그인은 검사·저장·공개까지 같은 순서로 끝낸다」에서 발췌했다.

> **로그인 완료는 기기 저장과 상태 적용까지 성공한 시점이다.** 서버 로그인 성공 후에는 다음 순서를 지킨다.
>
> 1. 기존 계정과 DB·queue 귀속을 확인한다. 다른 계정은 명시적 로그아웃 뒤 로그인해야 한다.
> 2. 검사한 세션을 기기에 저장한다.
> 3. 저장이 성공하면 새 토큰과 `signed-in` 상태를 공개한다.

> **기기 저장 실패:** 이전 인증 상태와 로컬 데이터를 보존한다. 이 실패만을 위한 새 전역 인증 상태를 늘리지 않는다.

원문은 더 넓은 동시 실행·새 토큰 폐기 계약도 다루지만 이 데모는 그 전체를 구현하지 않았다. 이후 Query 실패에도 이미 끝난 인증을 유지한다는 공통 발췌는 [기기 세션 근거](../../../common/device-session/_background/evidence.md#같은-계정의-재로그인)에 있다.

## 인증 거부는 별도 사건

제품 문서의 「인증 거부는 저장을 기다리지 않고 요청부터 막는다」에서 발췌했다.

> **인증 거부가 확정되면 메모리를 `reauth-required`로 바꾸고 세션 세대를 변경해 보호된 요청을 차단한다.** 기기 저장이 지연·실패해도 거부된 인증으로 요청을 계속하지 않기 위해서다. 로그인 성공의 '저장 후 공개' 순서를 여기에 적용하지 않는다.

이는 일반 조회 실패와 확정된 인증 거부를 구별할 근거다. 현재 데모의 거부 판정·요청 차단·재인증 전환 구현은 없다.

## 제품 계약과 데모 선택을 구별한 작성 논의

출처 식별 경로: `context/workspaces/014-ai-development-workflow-design/records/2026-10-19-91-prototype-body-quality-review.md`, 「주요 권고와 Main의 판단」. 2026-10-19의 본문 개선 기록이며 제품 사건이 아니다.

> 특히 “조회 실패가 인증을 되돌리지 않음”과 “조회 완료를 기다리지 않음”은 별도 선택이라는 구별을 반영했다.

같은 기록의 「확인과 남은 판단」은 후속 보완을 다음과 같이 남겼다.

> 최신 데이터가 필요한 소비자가 생겨도 공통 wrapper의 반환 시점을 바로 바꾸지 않는다. 해당 소비자가 기다릴지 공통 계약을 바꿀지, 기존 Login·Reauth에 미치는 영향을 대조하도록 설명했다.

이는 Main이 수용해 본문에 반영한 설명이며, 정확한 문장 전체의 사용자 최종 수용이나 대안 구현을 실행한 결과는 아니다.

## 대기 이유를 바로잡은 작성 논의

출처 식별 경로: `context/workspaces/014-ai-development-workflow-design/records/2026-10-19-92-principles-cases-and-agreement-reconciliation.md`, 「실제 본문에서 바로잡은 관계」. 2026-10-19 작성 대조에서 확인한 정정이다.

> 현재 Project 가이드는 대기와 실패를 구별했으나 Work의 비대기 이유에는 “기다리면 실패 관계가 달라짐”이 남아 있었다.

같은 표는 현재 선택의 이유를 다음과 같이 설명했다.

> 기존 완료·이동·닫기 시점 보존과 두 callback의 최신 값 미사용을 비대기 이유로 설명한다. 기다려도 실패 분리는 가능하다.

새 대기 기능을 구현한 기록은 아니다. 당시 작성 기록은 보존하고 현재 선택의 설명을 바로잡았다.

## 실행 예제가 추가한 선택

데모 안의 [시작 입력](../../../../work/workspaces/001-login-completion-names/source/scenario-input.md)은 두 callback이 정상 반환하며 Query 실패를 Promise rejection으로 받는다고 가정했다. [구현 기록의 선택 설명](../../../../work/workspaces/001-login-completion-names/records/2026-10-19-02-implementation.md#무엇을-유지하고-무엇을-새로-골랐는가)은 메모리 어댑터·코드 구성·테스트·동기 요청 오류 처리까지 작성자가 추가했다고 명시한다.

이 두 문서가 원래 입력과 실제 작성의 근거를 이미 보존하므로 본문 전체나 발췌를 다시 복제하지 않는다. 현재 실행의 확인 항목과 미확인은 [Work 실행 기록](../../../../work/workspaces/001-login-completion-names/records/2026-10-19-03-execution.md)이 소유한다.
