# 로그인 완료 표현 작업을 이어가기

이 Work는 인증 저장·상태 적용과 조회 갱신 완료를 구별해, 호출부가 이름과 안내에서 과도한 완료를 기대하지 않게 하는 실행 예제다. 현재는 작성된 결과와 context 적용 구성을 검토하는 단계이며, 실제 Noline 통합과 사용자 수락은 확인하지 않았다.

## 일반 재개에서 먼저 읽는다

| 자료와 범위 | 읽을 이유 |
| --- | --- |
| [문제·목표·범위](current/memory/spec/01-problem-goal-scope.md) | 실제품 개명 작업이 아닌 새 메모리 예제라는 범위, 이름 유지·설명 보완도 가능한 선택이라는 조건을 복원한다. |
| [현재 상태](current/state/index.md) 전체 | 현재 완료 경계와 확인·미확인, 이번 요청에 따라 이어갈 판단을 확인한다. |
| [현재 산출물](output/index.md) | 실제 코드·검사와 현재 선택·대안의 위치를 찾는다. 연결된 모든 본문을 기본 입력으로 읽지는 않는다. |

현재 선택은 `signInAndRequestRefresh`와 `onSignedIn`이다. 인증 저장·상태 적용 뒤 조회를 요청하지만 결과는 기다리지 않는다. 이름 자체보다 이 완료 경계를 지키는 것이 중요하다. 선택과 미확인의 상세는 위 current가 소유하며, 과거 검사 통과를 현재 수정이나 실제품 통합의 근거로 자동 이어받지 않는다.

## 이번 요청에 맞춰 추가로 읽는다

| 다루는 질문·수행 | 자료와 필요한 범위 |
| --- | --- |
| 인증 동작·소비자를 수정하거나 검증한다 | [인증 완료 Ticket](current/memory/tickets/01-authentication-completion.md)의 범위·완료 조건·실행 맥락과 [Spec 색인](current/memory/index.md)의 관련 동작·계약·제약을 읽는다. [Project 선택](current/memory/project-context.md)에서 해당 완료·실패 계약과 현재 구현을 찾는다. 실제 코드는 output의 연결을 사용한다. |
| 이름을 유지할지 바꿀지 다시 판단한다 | [선택한 개인 기준](current/memory/personal-context.md)과 [같은 코드의 유지·개명 비교](records/2026-10-19-06-naming-alternatives.md)를 읽는다. 내부 두 소비자라는 변경 비용과 설명 의존을 줄이는 이득을 함께 본다. 개명 자체를 목표나 모든 작업의 규칙으로 올리지 않는다. |
| 조회 완료까지 기다리거나 실제 저장소를 붙이려 한다 | state의 `이어갈 때`와 [Project 선택](current/memory/project-context.md)에서 완료·실패·상태 보존 계약을 먼저 읽는다. 표현 수정과 동작 요구 변경을 구별하고 새 조건에 필요한 검증을 정한다. |
| 기존 검사 결과를 재사용하거나 확인 한계를 따진다 | [실행 기록](records/2026-10-19-03-execution.md)과 output의 동작 검사를 현재 대상·조건과 대조한다. 필요하면 [demo 실행 안내](../../../../README.md#직접-실행한다)로 직접 확인한다. |
| 가상 시작 장면과 현재 결과가 어떻게 달라졌는지 재검토한다 | [초기 입력](source/scenario-input.md)과 [입력 선택 기록](records/2026-10-19-01-input-selection.md)을 읽는다. 최초 설명 시안과 이후 새 실행 예제를 같은 판본으로 읽지 않는다. |

현재 요청이 위 조건에 없거나 중요한 의미가 빠졌으면 관련 본문·원문으로 더 확인한다. 판단을 이어갈 수 있으면 그 과업으로 돌아가며, 다른 Ticket·기록·Personal 주제 전체를 기본 읽기로 추가하지 않는다.
