# 이름에서 맡은 일과 끝난 일을 알 수 있게 한다

함수·Hook·상태·반환값·완료 알림을 설계하거나, 기존 표현 때문에 사용처가 동작을 잘못 예상할 때 적용한다. **가능한 한 이름·타입·책임 배치·제어 흐름만으로 맡은 일과 끝난 일을 이해할 수 있게 한다.** 설명을 읽으면 사용할 수 있는 수준에서 멈추지 않고, 설명에 맡긴 의미를 코드가 직접 드러낼 수 있는지 먼저 본다. 내부의 모든 단계를 긴 이름에 나열하는 것이 목적은 아니다.

필요한 동작을 이미 제공한다면 유지·설명 보완·개명의 이득과 비용을 비교한다. 필요한 결과를 제공하지 않는다면 동작을 고친다. 이 구별이 어려울 때는 [같은 인증 코드의 두 표현과 저장 완료 사례](index.cases.md)를 함께 본다.

기준의 의미·조건을 바꾸거나 형성 의도를 확인할 때는 [형성 자료 안내](background/README.md)에서 관련 맥락·기록·근거를 고른다. 이 묶음의 구성은 [주제 안내](README.md), 함께 갱신할 범위는 [공통 관리 원칙](../../../CONTENT-POLICY.md#필요한-범위만-읽고-함께-갱신한다)에서 찾는다.

## 이름을 정하기 전에 사용 단위와 내부 책임을 구별한다

외부에서 하나의 기능으로 사용하는 것과 내부 책임을 나누는 것은 함께 성립한다. 외부 이름은 호출자가 맡기는 기능을, 내부 이름은 각 부분이 수행하는 일을 설명한다. 내부 책임을 나눴다는 이유만으로 호출자에게 그 순서를 다시 조립하게 하거나, 모든 부분을 별도 파일로 만들 필요는 없다.

다음은 여러 이메일을 검증하고 초대 결과를 반영하는 설명용 예시다. 오류 처리와 재전송 정책은 생략했다.

```ts
// 사용처는 초대 기능을 맡긴다.
const invitation = useMemberInvitation();
await invitation.submit();

// 기능 내부에서는 대상 계산·요청·결과 반영을 구별한다.
async function submit() {
  const prepared = prepareSubmission(rows);
  setRows(prepared.rows);
  if (prepared.targets.length === 0) return;

  const results = await invitationMutation.mutateAsync(prepared.targets);
  setRows(current => applyInvitationResults(current, results));
}
```

호출자가 초대 전체를 맡기므로 `submit`이 그 순서를 조율한다. 대상 계산이나 후속 처리가 사용처마다 달라진다면 그 선택까지 기능 안에 고정하지 않는다. 같은 원칙에서 입력 검증을 `prepareSubmission`에 직접 구현할지 기존 폼 도구에 맡길지도 달라진다.

이미 폼 도구가 입력값·검증 오류를, 요청 도구가 pending·error를 소유한다면 같은 상태를 다시 만들기 전에 의미를 확인한다. 요청 하나의 진행 상태와 이메일별 초대 결과처럼 서로 다른 정보는 별도 상태일 수 있다. 기능 단위, 내부 책임, 파일 배치는 각각 판단하되 실제로 맡긴 역할이 이름과 구성에서 이어지게 한다.

## 이름·타입·가까운 계약이 같은 역할을 설명하게 한다

이름은 역할을, 타입은 받을 값과 돌려줄 값을, 함수의 책임과 흐름은 처리 관계를 드러낸다. 주석으로 역할이나 완료 시점을 반복해서 설명해야 한다면 이름·타입·구성을 더 명료하게 만들 여지가 있는지 먼저 확인한다. 설명은 그렇게 정리한 뒤에도 코드만으로 드러내기 어려운 선택 이유·외부 제약·비자명한 실패 조건을 보완한다. 주석을 없애기 위해 필요한 계약을 감추거나 모든 정보를 이름에 몰아넣지는 않는다.

입력에서는 상태인지, 처리할 값인지, 출력할 문구인지를 구별한다. 새로운 API에는 의도한 값의 종류가 드러나게 하고, 기존 API는 더 선명한 표현의 이득과 실제 사용을 함께 본다. 오류가 발생해야만 개선할 수 있는 것은 아니지만, 표현을 더 명확하게 만들 수 있다는 사실이 곧 필수 수정을 뜻하지도 않는다. [문자열 `isError` 사례](index.cases.md#문자열-iserror를-유지한-판단)는 이 차이를 짧게 보여 준다.

반환과 예외도 호출자가 구별할 수 있어야 한다. `handleError`가 오류를 변환해 돌려주는지, 직접 던지는지에 따라 호출 형태가 달라진다. 아래는 구현을 생략한 두 계약의 표현이다.

```ts
// 변환한 오류를 반환한다.
function toRequestError(cause: unknown): RequestError { /* 변환 */ }
throw toRequestError(cause);

// 함수 안에서 오류를 던진다.
function throwRequestError(cause: unknown): never { /* throw */ }
throwRequestError(cause);
```

이름과 호출 형태가 분명해도 오류의 의미가 틀렸다면 해결된 것이 아니다. 예를 들어 응답 해석 실패를 네트워크 실패로 분류하면 호출자는 잘못된 대응을 고를 수 있다. 옵션도 이름만 볼 것이 아니라 어느 처리에 적용되는지 확인한다. 등록 처리기와 로컬 옵션의 적용 범위는 [silent의 처리 순서 사례](../contracts-and-lifetime/index.cases.md#등록-처리기와-silent의-적용-순서)에서 다룬다.

## 완료 표현은 호출자의 다음 행동과 맞춘다

**함수가 성공하거나 callback이 불린 직후, 호출자는 어떤 행동을 해도 되는가?** 반환·알림 시점에 끝난 일과 소비자가 이어서 하는 행동을 함께 읽는다.

| 성공 시점에 끝난 일 | 그것만으로 보장되지 않는 결과 | 확인할 다음 행동 |
| --- | --- | --- |
| 작업을 큐에 접수함 | 실행·저장 완료 | 접수 직후 결과 파일을 읽는가 |
| 저장을 마침 | 후속 조회 완료 | 성공 알림 뒤 최신 조회 결과를 읽는가 |
| 조회 결과를 받음 | 화면 전환·렌더링 완료 | callback을 화면 준비 완료 알림으로 쓰는가 |

핵심 결과는 이름과 반환형에서 알 수 있게 하고, 중요한 비대기·실패 조건은 가까운 계약에 둔다. `requestRefresh`와 `refreshAndRead`는 요청과 조회 결과 반환을 구별하는 예시이지 고정 접두사 규칙이 아니다.

**실패 범위와 기다릴 범위는 별도로 판단한다.** 저장 후 조회가 실패해도 저장은 완료됐을 수 있다. 호출자가 최신 데이터를 필요로 한다면 조회를 기다리면서 저장 성공과 조회 실패를 따로 전달할 수 있다. 조회 실패가 저장을 취소하지 않는다는 이유로 비대기를 선택하지 않는다. 대기 여부는 다음 행동에 필요한 결과로 정한다.

성공·실패 문구도 같은 경계를 따른다. 후속 조회 실패를 전체 저장 실패로 알리면 이미 저장한 내용을 다시 제출하게 할 수 있다. 반대로 조회가 진행 중인데 화면 갱신까지 끝났다고 알리면 아직 준비되지 않은 결과를 사용하게 할 수 있다.

## 유지·설명 보완·개명·동작 수정을 고른다

먼저 요구와 공개한 계약에서 필요한 결과를 확인하고, 실제 반환·알림 시점의 상태 및 사용처와 대조한다. 현재 구현은 동작의 근거이며 그 동작이 옳다는 근거까지 되지는 않는다. 사용처가 이미 약속된 결과를 쓰는지, 이름에서 더 큰 결과를 추론한 것인지도 구별한다.

| 확인한 조건 | 선택과 이유 |
| --- | --- |
| 필요한 동작을 제공하고, 이름·타입·구성에서 역할과 주요 완료 범위가 드러난다. | **유지.** 더 길거나 세분된 표현이 실제 이해를 더 돕지 않는다면 현재 코드를 유지한다. |
| 코드가 역할을 드러내지만, 선택 이유·외부 제약·비자명한 실패 조건을 알아야 사용하거나 변경할 수 있다. | **설명 보완.** 코드에 담기 어려운 근거와 계약을 찾기 쉬운 위치에 쓴다. 이미 성립하는 약속을 설명하며 기존 약속을 축소하지 않는다. |
| 가까운 설명을 읽어야 역할이나 완료 범위를 구별하며, 그 의미를 코드로 더 잘 드러낼 수 있다. | **개명·타입·책임 배치 개선.** 설명 의존을 줄이는 이득을 우선 검토한다. 공개 호환성이나 변경 위험이 크면 이름을 유지하고 설명으로 보완할 수 있지만, 그 선택은 남는 읽기 부담과 비용을 감안한 절충이다. |
| 필요한 결과나 공개한 완료 약속을 구현이 제공하지 않는다. | **동작 수정.** 반환 시점·실패 전달·호출 연결 중 부족한 결과를 만드는 부분을 고친다. 이름을 좁혀 기존 소비자의 요구를 없애지 않는다. |
| 요구·문서·사용처가 서로 다른 결과를 기대한다. | **충돌을 먼저 밝힌다.** 기존 약속의 누락인지 새 요구인지 확인한다. 잘못된 진입점을 호출했다면 적절한 진입점으로 연결할 수 있으며, 곧바로 피호출 함수의 책임을 넓히지 않는다. |

이 선택들은 서로 배타적이지 않다. 동작을 고치면서 이름을 바꿀 수 있고, 이름을 유지하면서 설명을 보완할 수도 있다. 이름과 설명이 서로 다른 결과를 약속한다면 주석만 추가해 덮지 않는다.

개명을 비교할 때는 **같은 동작·같은 소비자에 같은 수준의 설명**을 둔다. 개명 안에만 자세한 주석을 달면 이름과 설명의 효과가 섞인다. 그 상태에서 설명을 보지 않고 코드로 이해할 수 있는 범위와 바꿔야 할 참조를 비교한다. 두 안을 모두 올바르게 사용할 수 있어도 지향할 명료함이 같은 것은 아니다. 비교를 위해 같은 주석을 둔 것은 실제 코드에 그 주석을 모두 남기라는 규칙이 아니다. [인증 코드 A/B](index.cases.md#같은-동작에서-이름-유지와-개명-비교)는 이 차이를 보여 준다.

검토 의견에는 무엇을 다시 알아내야 하는지 또는 어떤 결과가 부족한지, 선택한 조치가 줄일 부담과 보존할 동작을 연결해 쓴다. 실제 발생한 오류와 예상되는 혼동을 구별하고, 필요한 호출·반환·사용처만 확인한다. 모든 질문의 답이나 전수 조사 결과를 매번 출력할 필요는 없다. 새 소비자·공개 호환 요구 등 조건이 달라지면 이전의 유지나 개명 선택도 다시 판단한다.
