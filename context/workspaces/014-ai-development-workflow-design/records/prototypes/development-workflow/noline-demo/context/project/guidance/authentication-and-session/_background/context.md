# 인증 적용과 후속 조회의 경계를 남긴 이유

이 문서는 [인증 계약 본문](../INDEX.md)의 형성 맥락이다. 보존된 제품 계약과 이번 실행 예제의 선택을 구별해, 현재 순서·실패·대기를 바꿀 때 무엇을 다시 판단해야 하는지 설명한다.

## 저장 성공을 공개하는 책임과 전체 작업을 조율하는 책임

로그인 응답을 받았다는 사실만으로 새 인증을 공개하면 기기 저장이 실패한 인증을 완료로 알릴 수 있다. 보존된 제품 기준은 귀속 확인, 기기 저장, 상태 공개의 순서를 정했고 저장 실패 때 이전 상태·데이터를 보존하게 했다. 이 [직접 근거](evidence.md#로그인-완료와-저장-실패)를 현재 계약의 사건별 표로 풀어, 실패 지점마다 남는 결과와 다음 행동을 볼 수 있게 했다.

같은 자료는 Auth Store의 상태 판단·저장과 서비스의 전체 로그인 조율을 구별한다. 저장 action을 안전하게 호출했다는 사실만으로 진행 중 sync·cleanup·DB 작업을 조율했다고 볼 수 없기 때문이다. [책임 구별의 발췌](evidence.md#store와-전체-서비스)는 이 경계를 지지한다. 데모는 단순 계정·여행 목록 확인과 주입한 대기 함수로 관계를 표현하므로, 실제 제품의 DB·queue 조사와 작업 종료 장치를 구현한 것으로 해석하지 않는다.

## 조회 실패의 분리와 비대기는 서로 다른 선택

인증 저장 뒤 Query가 실패해도 앞서 끝난 인증 저장을 실패로 다시 분류하지 않는다는 것은 제품 원자료의 계약이다. 반면 이번 예제가 Query 결과를 기다리지 않고 인증 완료를 알리는 것은 두 소비자가 최신 결과를 직접 사용하지 않는다는 조건에서 선택한 동작이다. 기다리면서도 인증 성공과 조회 실패를 따로 전달하는 구현은 가능하다.

처음 Work의 작성 이유에는 인증 복구 요구와 후속 실패 분리를 비대기 선택의 이유로 함께 적었다. 이후 본문 대조에서 그 설명만으로 대기 여부가 결정되지는 않는다는 점을 바로잡았다. 현재 설명은 기존 완료·이동·닫기 시점의 보존과 소비자의 최신 값 미사용을 비대기 이유로 삼는다. 당시 설명과 정정은 [기록](records/2026-10-19-waiting-and-failure-boundaries.md), 정확한 작성 근거는 [발췌](evidence.md#대기-이유를-바로잡은-작성-논의)에 있다.

## 소비자의 요구가 달라질 때 다시 판단할 것

최신 여행 결과를 바로 읽어야 하는 소비자가 생기면 해당 소비자의 후속 단계에서 기다리는 방식과 공통 완료 계약을 바꾸는 방식을 비교한다. 공통 wrapper의 반환을 늦추면 기존 Login·Reauth의 loading·이동·닫기·실패 안내도 바뀌므로 이름이나 `await`만 고쳐서는 선택이 끝나지 않는다.

Query 요청 함수의 즉시 오류를 별도 후속 오류로 처리하는 코드와 두 callback의 정상 반환 전제는 데모에 추가한 선택이다. 실제 저장 어댑터의 부분 실패, 동시 세션 변경, callback 자체의 예외는 그 선택만으로 보장하지 못한다. [현재 흐름의 범위](../../../current/authentication-flow/INDEX.md)를 함께 대조해야 한다.

일반 조회 실패와 확정된 인증 거부도 다른 사건이다. 보존 제품 기준에는 거부를 확인하면 저장을 기다리지 않고 보호 요청부터 막는 예외가 있으며, [그 근거](evidence.md#인증-거부는-별도-사건)를 남겼다. 데모는 이 경로를 구현하지 않았다. 이 구별을 설명한 사실이 새로운 제품 거부 정책이나 실제 차단 기능을 채택했다는 뜻은 아니다.
