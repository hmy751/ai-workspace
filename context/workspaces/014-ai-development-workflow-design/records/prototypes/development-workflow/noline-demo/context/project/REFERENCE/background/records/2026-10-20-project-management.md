# 읽기·구성·갱신을 한 관리 단위에서 찾도록 구성

[Project 관리 본문](../../../MAINTENANCE.md)의 형성과 2026-10-20 구성 선택을 기록한다. 과거의 제품 선택을 새로 확정한 기록이 아니다. 기존 운영 문장·정정 기록은 [근거](../evidence.md)에 있다.

이 기록의 management 배치는 같은 날 사용자 정정으로 원복했다. 앞부분은 당시 선택의 이유이며 현재 배치는 마지막 원복 절에서 확인한다.

기존 데모는 실제 Noline의 Project 책임을 대조한 2026-10-19 수정에서 README·MAINTENANCE·REFERENCE와 common/current/guidance/decisions를 채웠다. 전제가 된 문제는 기존 배치가 파일·동작 검사를 통과했어도 실제 계층과 역할을 충분히 반영하지 못했다는 것이었다.

이번에는 지속 절차에도 본문과 형성 자료의 관리 원칙을 적용했다. 기존 MAINTENANCE의 현재 갱신 판단을 시작 본문으로, REFERENCE의 읽기·구성은 분할 본문으로 이동했다. 서로 다른 제품 계약을 합친 것이 아니라 같은 Project 본문 관리의 행동 세 가지를 가까이 찾게 한 선택이다. 읽기만 하는 작업이 갱신 절차까지 기본 입력으로 받지 않도록 각 진입은 유지했다.

기존 MAINTENANCE 이름과 REFERENCE 안내는 연결 문서로 남겼다. 이는 기존 진입과 재접근을 위한 것이며 두 곳의 정본을 만들지 않는다. 내용의 권한·수행 주체·자동화 유무는 바꾸지 않았다. 필요한 제품 선택만 결정권자에게 확인한다는 경계와, 기존 범위 안 설명 보완에 새 일괄 승인 절차를 만들지 않는 조건도 유지했다.

관리 방법 자체가 달라지면 이 단위에서 해당 본문과 현재 맥락을 함께 판단한다. 제품의 의미·계약·구현만 바뀌었다면 해당 제품 본문이 먼저이며 관리 문서를 형식적으로 갱신할 이유는 없다.

## 같은 날의 사용자 정정과 원복

위 management 배치는 당시 작성자의 구성 선택이며 현재 배치가 아니다. 사용자는 일반 본문 적용과 기존 진입·운영 문서의 재배치를 구별하고, DEVELOPMENT·Spec/Ticket 같은 기존 진입은 원복한 뒤 논의하자고 요청했다. 같은 성격의 Project MAINTENANCE·REFERENCE도 기존 이름·위치·본문 책임으로 복구했다.

현재 읽기·구성 기준은 REFERENCE의 원래 파일들이, 갱신 계약은 MAINTENANCE.md가 소유한다. 수집한 형성 근거는 이 보조 폴더로 옮겨 보존했고 management 본문·안내 중복은 제거했다. 기존 진입의 재구성과 전체 개발 workflow 구체화는 보류한다. 위 과거 선택 이유를 새 구조의 채택 근거로 재사용하지 않는다.
