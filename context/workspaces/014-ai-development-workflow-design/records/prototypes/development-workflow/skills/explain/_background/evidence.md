# 통합 선택과 작성 예시의 근거

아래는 현재 구성의 이유를 재검토하는 데 필요한 발췌다. 사용자 발화, 기존 수행 관찰, Main·리뷰어의 설계 판단을 구별한다. 파일 식별자의 `Workspace014`는 `context/workspaces/014-ai-development-workflow-design/`를 뜻한다. 바깥 기록을 읽지 않아도 핵심 판단은 이 발췌로 확인할 수 있으며 식별자는 추가 재접근용이다.

## 사용자 목적과 구성 선택 — 2026-10-23 현재 대화

반복 개선에 대한 의문:

> 뭔가 지금 사례들을 가지고 계속 개선 테스트 하는데 뭔가 잘 안풀려
> 뭔가 작업도 뺑뺑돌고 그래서 니가 관련 길고이랑 문제점이랑 잘 파악해봐 그래서 어덯게 앞으로 하면 좋을지 고민해봐

통합의 가능성을 연 발화:

> 내가 생각한건 아티팩트 브리핑을 떠나서 그냥 설명으로 하나 하고 거기서 뭐 좀 나눠지던가 왜냐면 설명 리커버리도 있고 하니까

배경의 지위:

> 근데 중요한건 배경에서 뜼이 그렇다고 딱 지키란건 아니야 지금 source들과 우리 논의들도 같이 고려해봐야 하는거 알지?

리뷰와 생성 요청:

> 하기전에 리뷰 한번만 돌려보자 목표랑 지금 상황이나 맥락등을 고려해서 여기서 더 개선한다면

> 좋아 그럼 리뷰 반영한 구성으로 스킬 만들어봐 본체랑 상세, _background까지 잘 구성하고 기존 두 스킬이랑 연결도 정리해줘

생성 중 책임과 분량에 관한 확인·정정:

> 근데 이거 기존에 두 스킬 제거하는걸 감안해서 만든거야? 예상보다 간략한것 같아서

> 근데 또 무지성으로 빠짐없이 채우란건 아니고 감안을 했냐이거지

Main은 기존 두 실행 스킬을 없애도 새 구성으로 설명할 수 있어야 한다는 전제를 확인했다. ‘모든 조항을 빠짐없이 대체한다’는 자신의 반응은 과도했음을 정정했다. 필요한 행동은 현재 목적과 source로 판단하며 원래 목차를 복원하거나 분량을 늘리는 요구로 취하지 않는다.

## 실제 사용의 평가

Workspace014 `source/noline-evaluation/reviews/interview-20261012.md`의 사용자 회고 발췌:

> 내가 한 번 더 말해야 괜찮아진다는 게 아쉬운 거지 처음부터 그 정도로 검토하고 설명해줬으면 좋겠어

> 마지막에 도움은 됐던것 같아 근데 내가 물어보면 바로 바꾸려는 게 문제지 내 말에 무조건 맞추지 말고 왜 그렇게 했는지 판단해서 설명해줬으면 좋겠어

Promise 질문에 대해서는 다음 평가도 있다.

> 둘 다였던 것 같아 내가 이해하려고 파고든 것도 맞고, AI가 내가 어디서 헷갈리는지 좀 더 빨리 짚어줬으면 좋았을 것 같아. 두 갈래로 나눠서 설명한 부분은 도움이 됐고

이는 사용자 회고이며 개별 스킬의 인과 효과를 측정한 결과가 아니다. 모든 후속 질문을 실패로 세거나 질문을 바로 수정 지시로 바꾸지 않은 이유다.

## 기존 방법과 관찰한 미수행

통합 직전 브리핑 본문에는 다음이 이미 있었다.

> 책임의 관계가 중요하면 어디서 판단하고, 어떤 일을 다른 코드에 맡기며, 무엇을 반환하거나 외부에 반영하는지가 드러나는 부분을 고른다. 파일 위치·함수 이름을 알려 주거나 동작을 요약하는 것만으로 이 대응을 대신하지 않는다.

[직전 본문 사본](legacy/work-artifact-briefing/records/2026-10-23-before-explain.txt)의 SHA-256은 `a8af2ca17805e6b7610202da0321ec5ccc83572555de6c8724e57d31ee0f7f97`이다. 복구의 [보류 후보 사본](legacy/explanation-recovery/records/2026-10-23-before-explain.txt)은 `c0d0a791bce4cc2468915f3c38e5bce128cb9a396d26c86c684a3078b01bfb1d`이다. 복구 후보를 기존에 채택된 운영 기준으로 해석하지 않는다.

Workspace014 `records/experiments/artifact-explanation-trip-responsibility-2026-10-23/comparison.md`의 핵심 관찰은 양쪽 응답 모두 실제 코드 발췌 없이 표·문장·링크를 사용했다는 것이다. GPT-6-sol medium 각1회, 같은 자료·적용 시점의 비교였다. 정확한 미수행 원인이나 실제 사용자 이해 효과까지 입증하지 않았다. 코드 블록 개수 자체가 성공 기준이라는 뜻도 아니다.

독립 개선 리뷰 반환 발췌:

> 좋은 완성 답만 보여 주기보다 무엇을 고르고 어떻게 설명으로 바꿨는지 보여 주는 것입니다.

## 통합 뒤 비교와 재검토 요청 — 2026-10-24

6.0-sol medium 비교의 사용자 반응:

> 둘 다 비슷한 것 같은데 어느 게 새 스킬이야? 니가 보기엔 실제로 나아진 게 있는지, 우리가 개선하려던 부분 기준으로 판단해봐

6.1-sol high 비교의 사용자 반응:

> 이번엔 B가 더 나은 것 같은데 어느 게 새 스킬이야? 이전 6.0 결과랑 같이 보면 우리가 개선하려던 부분에서 어떻게 판단해야 할 것 같아?

6.0에서는 A가 기존, B가 explain이고6.1에서는 A가 explain, B가 기존이었다. 같은 설정 안에서 동일 자료·적용 시점으로 각1회 최초 응답을 생성했다. 새 스킬은 두 실행 모두 작성 상세를 읽었지만 전후 코드를 직접 대조하지 않았다.6.1 기존판은 Provider와 ExpenseRepository의 전후를 읽고 실제 코드와 변경 이유를 응답에 대응시켰다. 두 모델 설정을 바꾸면서 effort도 함께 바뀌었고 조건당1회이므로 일반적 성능·인과·사용자 이해를 확정하지 않는다.

원자료 식별자: Workspace014 `records/experiments/explain-network-first-delivery-2026-10-23-retry/` 및 `records/experiments/explain-network-first-delivery-61high-2026-10-23/`의 `comparison.md`, `answer-A.md`, `answer-B.md`, `results.json`과 읽기 기록. 초기 잘린 출력의 무효 시험은 별도 폴더에 있으며 위 두 비교와 합치지 않는다.

사용자는 먼저 “바로 수정하지 말고 어떻게 보완하면 좋을지 먼저 얘기하자”라고 요청했다. Main이 네 약화 지점을 설명한 뒤 다음과 같이 요청했다.

> 이 방향으로 수정뿐만 아니라 기존 스킬 다시 꼼꼼히봐서 더 검토해봐

이 요청으로 추가 검토와 수정을 수행했다. [반영 기록](records/2026-10-24-explanation-revision.md)은 문구 대조·Main 판단·수정과 효과 미확인을 구별한다. 새 응답 생성이나 운영 설치를 수행한 기록은 아니다.

## 수정 후 비교와 평가 — 2026-10-24

수정판과 기존판을 같은6.0-sol high·원자료·첫 보고 시점으로 각1회 비교했다. A는 기존 브리핑, B는 수정 explain이다. B는 작성 상세와 Provider·Router의 before/after를 읽었고, A는 before/ 코드를 직접 읽지 않았다. 양쪽 모두 현재 동작·검사 중심으로 답했으며, B의 전후 자료 선택이 실제 처리·의미의 응답 대응까지 충분히 이어지지는 않았다. 사용자 체감과 Main의 이 판단은 구별한다.

원자료 식별자: Workspace014 `records/experiments/explain-network-first-delivery-60high-revised-2026-10-24/`의 `conditions.json`, `comparison.md`, 두 최초 응답과 각 실행의 `output/read-events.jsonl`. 이전6.1 high의 기존판이 구현·이유 연결에서 더 분명했지만 같은6.1 high의 수정 전 explain은 약했다. 조건당1회이고 수정 전후 explain의 실행 설정도 달라 모델·추론 수준·문구 수정·생성 편차의 인과 효과는 분리하지 못한다. 이 관찰 뒤 실행 지침을 추가 수정하거나 새 시험을 반복하지 않았다.

## 실행 상세 예시의 출처와 한계

### 여행 코드의 작성 과정

[작성 상세](../references/constructing-explanations.md)의 세 발췌는 Workspace014 `source/artifact-explanation-scenes/05-trip-list-briefing/historical-materials/files/apps/client/src/` 아래 보존 파일에서 가져왔다.

- `entities/trip/data/useCreateTrip.ts`: `mutationFn`은 생성 요청, `onSuccess`는 갱신 helper 호출이다.
- `shared/lib/query-refresh.ts`: 이전 조회 취소는 await하고 새 조회 완료는 기다리지 않는다. 새 조회 오류는 별도로 기록한다.
- `entities/trip/repository/trip-repository.ts`: 목록 조회의 서버 경로에서 서버 결과를 받아 로컬 목록에 반영하고 결과를 반환한다.

코드 발췌는 원문과 대조했고 중간 생략·서로 다른 함수의 일부임을 상세에 밝혔다. 예시 설명은 이 코드의 관계를 설명하기 위해 새로 작성한 문장이다. 전체 제품 실행·모든 실패 조건·사용자 이해를 확인한 결과가 아니다. 기존 응답 예시가 있던 `records/2026-10-23-ticket04-02-astra-improvement-review.md`도 자료 선정 방식의 참고로 사용했으며, 이를 새 독립 시험으로 세지 않는다.

### 앞선 발화의 뜻과 타당성

[앞선 발화 상세](../references/prior-explanation.md)의 evidence/verdict 대화 두 개는 이전 복구 [형성 맥락](legacy/explanation-recovery/context.md)에 보존된 설명용 예시를 재구성했다. 실제 사용자 대화·새 비교 응답이 아니다. 동의어만으로 끝내지 않는 것과, 잘못된 추론을 정정하면서 원래 없던 뜻을 소급해 넣지 않는 행동을 보여 주기 위해 골랐다.
