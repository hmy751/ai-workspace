# Development — 맥락을 판단과 결과로 연결한다

요구에 맞고 사용자가 이해하고 유지할 수 있는 개발 결과를 만든다. 관련 기준으로 첫 결과를 만들고, 의미 있는 다른 선택을 독립적으로 살피며, 필요한 수정과 확인을 실제 결과·사용자 판단·다음 작업으로 잇는다.

Main은 현재 사용자와 대화하는 전체 작업 담당자다. 별도 lead를 하나 더 만드는 역할이 아니다. 이 본문은 Main의 공통 수행 계약을, [검토 상세](references/review.md)는 검토자와 Main이 각자 맡을 판단을 설명한다. 구현·검증의 공통 책임은 아래에 있으며 상세한 인계·호출·수정·종료 방식은 이 prototype에서 계속 구체화한다. 고정된 에이전트 수·모델·실행 순서를 정한 스킬은 아니다.

## 이번 요청에서 시작한다

사용자가 원하는 결과, 유지할 목표·제약·계약, 현재까지 만들어진 결과와 미정을 구별한다. 이어 하는 작업이면 대상의 진입 지침에서 지정한 Workspace와 Spec/Ticket·현재 상태·산출물을 읽는다. 과거 기록의 다음 행동을 현재 지시로 취하지 않는다.

요청한 일에 맞춰 참여한다. 구현 요청에서는 설계와 자기 확인을 포함한 결과를 만들고, 검토 요청에서는 기존 결과의 판단 근거를 반환한다. 재개 요청에서는 남은 일부터 이어간다. 어떤 경우에도 스킬을 읽었다는 이유로 이미 끝난 단계를 다시 수행하거나 요청받지 않은 수정을 시작하지 않는다.

목표를 정하는 데 실제로 필요한 선택이 남았다면 [작업 논의](../work-discussion/SKILL.md)를 사용한다. 충분한 작업 정의를 매번 다시 쓰지 않는다. 무엇을 만들지의 선택과 어떻게 구현할지의 기술 선택을 구별하며, 기존 위임 안의 판단은 Main이 맡는다.

## 맥락의 소유와 현재 적용을 구별한다

대상 Project의 진입점에서 아래 정본을 찾는다. 이 스킬의 위치를 제품 코드나 Workspace의 위치로 가정하지 않는다. 이 prototype의 실제 맥락은 [demo context](../../noline-demo/context/README.md)에 있으며, 아래 관계는 특정 로그인 작업에 한정되지 않는다.

| 입력 | 소유하는 의미 | 이번 작업에서 사용하는 방법 |
| --- | --- | --- |
| Personal | 여러 작업에 가져오는 개인의 판단 기준과 이유·적용 조건 | 현재 설계·접근법·표현·선택에 관련된 기준을 고른다. 현재 본문이 개발 예제 중심이라고 Personal 전체를 코드 품질 규칙으로 한정하지 않는다. |
| Project | 제품의 의미·약속, 지속할 개발 규약, 현재 구현에 관한 사실 | 이번 결과가 지킬 계약과 실제 사용 환경을 확인한다. 계약과 현재 구현이 일치한다고 가정하지 않는다. |
| Work | 이번 목표·제약·선택·진행·입력·결과·기록 | Spec/Ticket과 현재 상태에서 작업 범위를 복원하고, 선택과 확인 결과를 이어간다. |
| 실제 산출물·실행 근거 | 현재 존재하는 코드·문서·동작과 확인한 사실 | 문서의 약속·작성자의 설명과 대조한다. 존재하는 구현은 증거이며 자동으로 올바른 선례가 되지는 않는다. |

Personal의 판단 내용을 검토용 기준집으로 다시 쓰거나, Project가 개인 기준의 채택·갱신을 관리하게 하지 않는다. 자료의 이름·보관 위치만으로 우선순위를 정하지 않고, 어떤 목표·약속·선택·관찰을 담는지 판단한다.

관련 기준의 본문과 적용 조건을 먼저 읽고, 선택 차이를 이해하는 데 필요하면 사례로 내려간다. 형성 이유나 기준의 의미를 재검토해야 할 때 해당 본문의 형성 자료를 찾는다. 모든 사례·이력을 기본 입력으로 붙이지 않는다. 접근하지 못한 원문은 읽은 것으로 보고하지 않는다.

## 작업 중 판단이 바뀌는 곳에서 맥락을 다시 고른다

처음 선택한 자료로 끝내지 않는다. 구현 결과, 검토 의견, 검사 실패나 새 사용처가 현재 설명으로 풀리지 않는 질문을 만들면 그 질문에 필요한 원문·관련 산출물을 추가로 확인한다. 예를 들어 표현을 검토하다 완료 시점이 쟁점이 되면 해당 제품 계약과 실제 호출 흐름을 함께 본다.

이미 확보한 내용으로 판단할 수 있으면 같은 자료를 반복해서 읽지 않는다. 추가 자료가 생겼다는 이유만으로 원래 목표를 넓히지도 않는다. 문서와 실제 결과가 다르면 어느 것이 약속이고 어느 것이 관찰인지, 무엇이 미확인인지 구별한다. 기준의 적용 조건이나 현재 설계는 재판단할 수 있지만 목표·명시적 제약·보존 계약을 임의로 바꿀 수는 없다.

Main은 담당자에게 이번 목적·맡길 일·보존 조건과 필요한 정본의 접근점을 전달한다. 관련 기준을 공유하되 Main의 요약이나 기존 선택 이유가 원자료와 별도 판단을 대신하지 않게 한다. 구체적인 초기 입력 묶음과 추가 탐색·반환 방식은 맡긴 일에 맞춰 명시하며 이 본문이 고정된 전달 양식을 요구하지는 않는다.

## 역할을 연결하고 전체 결과를 책임진다

| 역할 | 맡을 판단과 반환 |
| --- | --- |
| 구현자 | 요구·관련 기준·사용 조건에 맞는 구체 설계와 구현을 수행하고 자기 변경을 확인한다. 검토자가 품질을 만들어 줄 것을 전제로 미완성 선택을 넘기지 않는다. 중요한 선택, 실제 변경과 확인·미확인을 Main이 판단할 수 있게 반환한다. |
| 검토자 | 현재 결과와 기준의 적용을 별도로 재판단하고 의미 있는 대안을 비교한다. 필요한 정확성·요구 적합성·테스트 공백도 볼 수 있다. 범위와 근거 있는 의견을 반환하며 발견 없음으로 전체 검증을 대신하지 않는다. 수행할 때 [검토 상세](references/review.md)의 공유 목적과 검토자 부분을 읽는다. |
| 검증자 | 수정된 결과가 요구·계약을 충족하는지와 확인 근거가 충분한지를 판단한다. 확인 대상·판본·방법·미확인을 구별해 반환한다. 모든 설계 대안을 다시 평가하거나 사용자의 주관적 수락을 대신하는 역할은 아니다. |
| Main | 전체 목표·설계 정합성, 담당 범위·수정 권한, 의견의 종합·선택·사용자 연결, 수정 후 확인과 최종 상태 판단을 책임진다. 자신의 초기 설계도 검토 대상으로 둔다. |

같은 문제를 여러 역할이 발견할 수 있다. 역할의 구별은 발견 가능한 문제를 독점하는 구분이 아니다. 책임을 나눴다고 매번 네 에이전트를 호출하거나, 검토 후 수정 담당을 특정 역할로 고정하지 않는다. Main은 이번 배정과 허용된 변경 범위를 드러내며 배정되지 않은 수정 권한을 역할 이름에서 추론하지 않는다.

검토를 맡기거나 의견을 판단할 때 Main도 [검토 상세의 Main 판단](references/review.md#main은-의견을-선택과-다음-행동으로-잇는다)을 적용한다. 채택한 의견은 실제 수정과 필요한 확인으로 연결한다. 검토자 직접 수정·구현자 수정 중 무엇을 택할지, 언제 다시 검토할지는 이 공통 책임만으로 고정되지 않는다.

## 확인한 결과와 사용자가 판단할 내용을 돌려준다

확인은 실제 변경과 약속에 맞춰 수행한다. 반복 판별 가능한 규칙은 대상의 lint·type·테스트 같은 검사로 확인하고, 그 결과가 보장하지 않는 사용 조건·통합 동작·실제 대상은 별도 근거로 구별한다. 초기 테스트가 있다는 사실만으로 충분하다고 보지 않으며 새로 드러난 경로와 가정에 맞춰 보완 필요를 판단한다. 검사 성공·검토 발견 없음·요구 충족·사용자 수락을 같은 완료로 취급하지 않는다.

사용자에게는 요청한 결과를 먼저 보여 주고, 중요한 선택·의미 있는 대안·확인 범위·남은 결정을 결과와 연결해 설명한다. 담당자의 보고를 그대로 모아 반환하는 것으로 Main의 판단을 대신하지 않는다. 결과를 내기 전에 원래 질문에 무엇이 답해졌는지 구성하고, 그 답을 이해하려면 역할·변경의 관계나 선택 이유를 따라가야 할 경우 [explain](../explain/SKILL.md)의 설명 방법을 사용한다. 필요한 연결을 만들 수 없는 이유가 사실 부족이면 Main이 기존 작업 권한 안에서 더 확인할지 판단하고, 확인할 수 없다면 이유와 답에 미치는 영향을 밝힌다. 항상 전체 브리핑이나 재검사를 시작하는 규칙은 아니다. 설명 방법은 explain이 소유하며 개발 결과·확인·전체 상태 판단은 이 스킬의 책임으로 남는다.

## 달라진 의미를 해당 Owner에 남긴다

| 달라진 것 | 연결할 곳 |
| --- | --- |
| 이번 선택·대안·수정·검사·미충족 | Work의 기록과 Spec/Ticket·state·output 중 실제로 의미가 바뀐 곳 |
| 제품의 지속 약속·개발 규약 | 권한 있는 선택에 따라 해당 Project 본문 |
| 현재 코드·사용처·지원 연결에 관한 사실 | 확인 범위와 함께 Project의 현재 구현 설명 |
| 여러 작업에 가져갈 개인 기준의 의미·조건 | Personal의 기존 갱신 방식과 선택 권한에 따라 해당 본문 |

이번 작업에 적용한 좋은 대안을 지속 기준으로 자동 승격하지 않는다. 기준 변경과 이번 적용 결과는 관련되지만 같은 결정은 아니다. 원자료·과거 선택을 새 결론으로 덮어쓰지 않고, 해당 Owner의 관리 규칙을 따른다. 이 스킬이 Work의 파일 구조나 제품별 관리 계약을 다시 정의하지는 않는다.

이 본문은 현재 prototype의 공통 계약이다. 상세 인계·호출·수정·재검토·종료 및 실행 환경 배치는 후속 설계에 남아 있다. 목적·범위·책임을 수정하거나 이전 선택을 재검토할 때는 [형성 자료](_background/README.md)를 읽는다. 일상 적용에 필요한 기준과 조건은 이 본문과 검토 상세에서 찾는다.
