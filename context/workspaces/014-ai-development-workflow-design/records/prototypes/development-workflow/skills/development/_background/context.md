# 왜 개발 절차를 하나의 스킬로 구성했는가

사용자는 자신의 기준을 이해한 첫 구현을 얻고, 별도의 검토를 통해 기존 선호·지식이 놓친 의미 있는 다른 선택도 비교하고 싶어 했다. 매번 더 큰 개선이나 다른 결론을 요구하는 것이 아니라 현재안 유지와 변경을 실제 차이로 판단하려는 목적이다. Main이 그 결과를 종합하며, 사용자와 중요한 대안·절충을 이해하는 대화도 작업의 일부다.

처음에는 검토자에게 Personal을 덜 주는 안을 논의했다. 그러나 기준을 읽지 않으면 조건·비용·사용자 이해를 놓칠 수 있고, 정보를 줄인 것만으로 독립성이 생기지 않는다. 관련 기준을 공유하되 현재 선택과 적용 조건을 다시 판단하는 방향을 선택했다. 따라서 검토자는 기준 준수만 확인하는 역할이 아니며 Main의 초기 선택도 다시 볼 수 있다.

## 판단 내용과 수행 방법을 나눈 이유

Personal은 여러 작업에 가져갈 개인의 판단 기준·이유·조건을 소유한다. 현재 예제가 개발·코드 중심이어도 그 상위 역할을 코드 품질로 한정하지 않는다. development는 현재 개발 작업에 필요한 개인 기준과 Project·Work 맥락을 함께 사용한다. 제품의 약속·현재 사실, 이번 목표·선택은 서로 다른 Owner를 유지한다.

검토용으로 좋은 코드 원칙을 다시 만들면 Personal과 의미·예외를 이중 관리하게 된다. 반대로 링크만 제공하면 어떻게 독립적으로 판단할지 사라진다. 현재 구성은 기준의 의미는 기존 Owner에 두고, 검토에서는 적용 재판단·대안 비교·주장별 근거·강도와 Main 연결을 설명한다. 짧은 적용 예시는 가능하지만 두 번째 원칙집이 되지 않게 한다.

새 관점은 이번 판단에 쓸 수 있고, 지속 Personal 기준으로 채택할지는 별도 판단이다. 이를 ‘부족함을 입증한 뒤에만 사용’하는 방식으로 만들지는 않았다. 현재 근거로 효과·비용·적용 조건을 판단할 수 있으면 선택하고, 실제 수정 결과가 요구를 충족하는지는 따로 확인한다.

## 진입점과 상세를 함께 옮긴 이유

기존 DEVELOPMENT는 Work 안에서 공통 절차와 로그인 데모의 적용을 함께 설명했다. 사용자는 절차를 development 전용 스킬로 만들고 관련 상세가 함께 쌓이는 구성을 원했으며 진입점의 이전도 제안했다. 현재 [SKILL.md](../SKILL.md)는 Main이 이번 요청을 끝까지 연결하는 본문이고 [review.md](../references/review.md)는 공유 목적과 검토자·Main의 판단을 구별한 상세다.

계층은 읽는 목적과 변경 책임에 맞춰 만든다. 현재는 공통 본문과 검토 상세만 작성했고 구현·검증의 빈 상세 파일은 만들지 않았다. 필요한 내용이 커지면 나눌 수 있지만 폴더 깊이나 스킬 수 자체가 목표는 아니다. 검토자가 Main의 전체 배정·완료 책임까지 받는 것도 아니다.

로그인 작업의 계약·코드·선택은 기존 Work와 [적용 장면](../../../walkthrough.md)에 남는다. 스킬을 교체하더라도 Personal·Project·Work의 지속 의미와 결과가 유지되도록 그 정본을 흡수하지 않는다. 기존 DEVELOPMENT 원문은 [보존판](evidence/development-before-skill.txt)으로 남겼으며 현재 실행 진입점으로 사용하지 않는다.

## 현재 구체화한 것과 이어서 정할 것

검토의 목적, 보존 조건·재판단 범위, 역할별 공통 책임, 검토 방식·강도, Main의 선택과 사용자 참여는 본문에 반영했다. Main은 초기 맥락 선택뿐 아니라 작업 중 재탐색·의견 종합·수정 후 확인·결과 전달과 Owner별 갱신까지 연결한다. 이를 고정된 순서나 매번 같은 역할 수로 바꾸지 않는다.

구현 완성·인계, 검토 입력·추가 탐색·권한·호출, 수정·재검토·종료, 실행 배치와 기록 책임은 후속 합의에 따라 본문·검토 상세·실행 배치에 반영했다. 일반 재개와 범위를 정한 위임은 실제 root·Work 지침에서도 구별했다. 맥락 스킬은 대상에 설치되고 계약이 맞을 때 연결하며, 그렇지 않으면 Main이 실제 관리 지침으로 수행한다. 보존 원형의 존재를 설치로 취급하지 않는다. [통합 기록](records/2026-10-23-execution-integration.md)에 선택과 한계를 남겼다.

이번 초안은 실행 지침의 구성과 내용 적용이다. 실제 여러 작업에서의 효과나 자동 호출·운영 설치까지 확인한 것은 아니다. 이 경계 때문에 초안 작성을 미루거나 이미 합의한 판단을 다시 후보로 되돌리지는 않는다. 근거와 전환 과정은 [발췌](evidence.md)와 [기록](records/2026-10-23-development-skill.md)에서 찾는다.

## 첫 결과의 설명 연결 — 2026-10-24

explain 재구체화에서 첫 결과를 구성할 때 목표·실제 변경·확인을 결론으로 잇도록 호출을 명시했다. 기존의 ‘관계나 이유 설명이 필요하면’이라는 연결은 이미 맡은 결과 설명을 나중의 별도 코드 설명으로 미룰 여지를 남겼다. 개발 결과의 책임은 그대로 두고 설명 수행만 explain에 맡겼다. 설명 자료가 있어도 답이 요약에 머문 관찰이 있으므로 호출 명시만으로 효과를 보장하지 않는다. 단순 결과는 그 크기에 맞게 전달하며 별도 agent나 전체 브리핑을 의무화하지 않았다. [선별·채택의 근거](../../explain/_background/records/2026-10-24-selective-improvement-adoption.md)에서 사용자 요청과 범위·확인 한계를 이어 본다.
