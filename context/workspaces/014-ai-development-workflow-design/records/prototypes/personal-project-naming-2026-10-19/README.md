## 배치 방향과 이번 파일의 관계

- 개인 본문은 향후 ai-workspace의 `context/personal/development/`에서 소유할 주제다. `naming-and-completion.md`는 파일명 후보이며 아직 그 경로를 생성하지 않았다.
- Project 적용 본문은 해당 Project의 `context/project/guidance/`가 맡는다. 기존 가독성 가이드의 절로 둘지, 독립 주제로 둘지는 이번 내용의 충분성과 읽는 상황을 보고 정한다. 이번 파일 분리가 운영 파일 세 개를 의무화하지 않는다.
- 읽기 안내는 해당 Project의 `context/project/README.md` 주제별 진입에 연결할 내용이다. 제품 의미·개발 계약의 본문을 여기에 모으지 않는다.

비교 파일끼리의 상대 링크는 이 시안에서 읽기를 확인하기 위한 것이다. 중앙 Personal context를 실제 Project에서 찾는 설치·배포·갱신 경로는 아직 구성하지 않았다. 보존 원문의 코드 링크도 실제 제품 저장소에 접근했다는 뜻이 아니다.

## 본문을 평가할 장면

‘로그인 후 갱신 helper의 이름이 화면까지 모두 갱신됐다는 뜻으로 읽힌다’는 작업에서 [읽기 안내](reading-guide.md)를 따라 [Project 가이드](project-guidance.md)를 읽는다. 인증 완료와 캐시 무효화 요청이 다른 의미라는 점은 이 가이드에서 이해할 수 있어야 한다. 기존 계약의 이유나 실제 보호 범위가 필요할 때만 연결 원문으로 내려간다.

실제 함수가 요청만 하는지 재조회도 기다리는지는 코드를 확인해야 한다. 요청만 하는 것이 확인되고 요구에도 맞으면 이름·설명을 좁힐 수 있다. 호출자가 재조회 완료를 전제로 후속 작업을 한다면 이름만 고칠 일이 아니라 완료 계약과 구현의 불일치를 다룬다. 이 두 판단이 본문에서 갈리는지를 비교한다.

본문이 충분한지 확인할 핵심은 개인 기준을 다시 쓰지 않고도 Project 적용을 이해할 수 있는지, Noline의 구체 계약을 개인 원칙으로 올리지 않았는지, 인증과 무관한 작업에 인증 문서를 강제하지 않는지다. 작성 근거·사용자 요청·확인 범위는 [기록82](../../2026-10-19-82-naming-responsibility-completion-draft.md)에 남긴다.
