# Noline의 인증 저장·세션 전환·화면 갱신을 구별한다

> Project guidance의 본문 시안. 보존된 Noline worktree 관찰판의 계약을 사용해 작성했다. 현재 제품 코드의 재확인이나 원본 가이드의 대체·통합은 아니다.

Noline의 인증 관련 함수·상태·완료 callback·오류 표현을 만들거나 수정할 때 읽는다. [개인 기준 시안](personal-criterion.md)의 ‘이름이 실제 책임과 완료 범위를 드러내게 한다’를 이 작업 범위에 적용하는 안이다. 기존 코드 전체를 일괄 개명하는 범위는 포함하지 않는다.

## 이 Project에서 구별해야 하는 책임

Noline의 로그인은 서버 응답 성공만으로 끝나지 않는다. 기존 계정과 DB·queue의 귀속을 검사하고, 기기에 세션을 저장한 뒤 새 토큰과 `signed-in` 상태를 공개한다. **기기 저장과 상태 적용까지 성공해야 로그인 완료로 다룬다.** 저장에 실패했다면 이전 인증 상태와 로컬 데이터를 보존한다. 이 순서와 실패 계약의 본문은 [기존 인증 가이드](../../../source/supplement/worktree-project-context/context/project/guidance/authentication-and-session.md#로그인은-검사저장공개까지-같은-순서로-끝낸다)가 소유한다.

그 과정에서 Auth Store가 맡는 계정 검사·저장·상태 적용과, 서비스가 맡는 전체 세션 변경 절차는 범위가 다르다. 전체 절차에는 진행 중인 sync·cleanup·접수된 DB 작업의 종료를 기다리는 조율이 있다. Store action의 이름이나 설명만으로 이 조율까지 끝난 것으로 읽히게 하지 않는다. 새 로그인 진입점은 Store action만 호출해 전체 절차를 대신하지 않고 기존 세션 변경 서비스를 사용한다. 현재 연결과 보호 범위는 [세션 현황](../../../source/supplement/worktree-project-context/context/project/current/session-and-local-data.md#인증-저장과-사용자-절차는-다른-범위를-조율한다)에서 확인한다.

## 인증 완료와 화면 갱신 완료를 이름에서 섞지 않는다

| 표현할 결과 | 이름·반환·callback에서 지킬 범위 |
| --- | --- |
| 인증 저장·상태 적용 완료 | 새 인증을 적용했다는 의미다. 전체 세션 변경 조율이나 모든 화면 데이터 갱신까지 보장하는 이름으로 확장하지 않는다. |
| 캐시 무효화 요청 | 기존 조회 데이터를 다시 확인하도록 갱신을 요청한 단계다. 재조회 결과가 도착하거나 화면 반영이 끝났다고 표현하지 않는다. |
| 특정 데이터의 재조회 완료 | 어떤 데이터가 준비됐는지 한정한다. 그 결과만으로 화면 이동·렌더링까지 완료됐다고 표현하지 않는다. |

예를 들어 캐시 무효화 요청만 하는 helper라면 `requestSessionQueryRefresh`처럼 요청 책임이 보이는 이름을 검토할 수 있다. 이는 설명용 후보 이름이며 실제 함수명이나 개명 지시가 아니다. 실제로 어떤 범위까지 기다리는 함수인지는 반환·호출부와 함께 확인해 이름을 정한다.

## 후속 갱신 실패가 이미 끝난 인증의 의미를 바꾸지 않게 한다

저장·상태 적용 뒤 Query 갱신이 실패해도 인증 복구는 이미 완료됐다. 그 실패를 인증 저장 실패로 다시 분류하거나 완료된 인증을 되돌리지 않는다. 저장 실패를 다루는 `catch`와 후속 갱신 실패의 처리 범위, 오류 이름·로그·사용자 안내가 이 구별을 유지하는지 확인한다. 구체적인 복구·알림 방식은 변경 대상 경로의 계약을 보고 정한다.

이 구별만으로 후속 갱신을 항상 기다리거나 항상 기다리지 않는다고 정하지 않는다. 로그인 경로에서 Promise가 언제 끝나고 후속 실패가 어디로 전달되는지는 보존 문서만으로 확인되지 않았다. `await`·`void`·callback을 바꾸는 작업에서는 실제 코드와 호출자의 선행 조건을 확인한다. 대기 순서가 달라지면 이름 정리를 넘어선 동작 변경으로 함께 검토한다.

변경을 확인할 때는 실제로 바꾼 경계에 맞춰 본다. 저장 실패를 바꿨다면 기존 상태·데이터의 보존을, 후속 갱신을 바꿨다면 인증 완료와 갱신 실패의 분리를, 완료 알림을 바꿨다면 호출자가 믿는 시점과 실제 완료 조건을 대조한다. 확인한 결과와 미확인 범위는 이번 Work 기록에 남긴다.
