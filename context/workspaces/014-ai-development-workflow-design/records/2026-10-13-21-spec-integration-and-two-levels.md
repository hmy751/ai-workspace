# 전체 잠정안의 Spec 반영과 두 층의 구별

2026-10-13. 기록 20에서 전체안 중심의 논의를 제안한 뒤 사용자가 실제 Spec 보완과 ‘Spec·Ticket’이 가리키는 대상을 확인했다.

## 직접 요청

> 잠깐 일단 출발점에서 spec에 목표 범위 주의할 점이 잘보이고 하면서 현재 구상하는 체계의 모습 이런게 흩어져있다고 했잖아? 그 이후 잠정안 하나를 중심에 놓자고 말했는데 잠정안 자체는 이해돼 근데 spec을 보완하려는 건 언급이 없는데 보완 안해도 될까? 왜냐면 세션이 계속 달라질거고 하니까 그리고 하나 더 Spec 과 Ticket도 이방식에 맞게 써야 한다는건 지금 스펙 티켓을 말하는거야? 아님 우리가 개선하려는 어떤 시스템 관점으로 스펙 티켓을 언급한거야?

## 판단과 실제 보완

Main은 보완이 필요하다고 판단했다. 앞선 응답에서 Spec의 역할을 제안했지만 실제 문서 반영까지 연결하지 않아, 다음 세션이 현재 구상을 여러 기록에서 다시 조립해야 하는 공백이 남았다. 채택 전에라도 현재 잠정안과 미결정을 그 지위를 밝혀 Spec에 모을 수 있다.

- [Spec](../current/spec.md) 3절에 전체 잠정안, 전체 형태를 바꿀 주요 미결정, 부분 논의를 전체안에 반영하는 방법을 보완했다. 기존 목표·범위·제약과 B 선택을 유지했다.
- ‘Spec·Ticket을 이렇게 사용하자’는 설명은 우선 **014의 설계 작업을 진행하는 문서**를 가리킨다. **개선할 시스템에서 개발 작업에 사용할 Spec·Ticket의 내용·구성·운영**은 별도 설계 대상이다. 014에서 사용한 방식이 곧 공통 표준의 채택은 아니다.
- README·current 색인·Ticket 색인·state·output의 안내를 실제 Spec으로 연결했다. README에 남아 있던 ‘01-02가 바로 다음 순서’라는 안내도 현재 전체안에서 필요한 질문을 고르는 방향으로 갱신했다.

사용자가 잠정안을 이해했다고 한 것을 전체안 채택으로 해석하지 않는다. Ticket 번호·분할·완료 상태는 바꾸지 않았으며, 실제 스킬·하네스·제품 코드를 변경하거나 자동 Maintainer를 재개하지 않았다. 이번에는 문서만 보완했고 새 커밋은 만들지 않았다.

다음 설계 논의는 Spec의 전체 잠정안에서 시작한다. 구체 사례로 부분 선택을 논의하고, 선택이나 가정이 달라지면 현재 전체안에 미치는 영향을 같은 Spec에 반영한다. 세부 분석·대안·당시 판단은 Ticket과 records에서 보존한다.
