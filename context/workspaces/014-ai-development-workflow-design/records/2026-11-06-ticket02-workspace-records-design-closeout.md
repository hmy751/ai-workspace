# Workspace 구조와 기록 중복 범위 결정

2026-11-06. 사용자는 Noline의 도시 검색과 Ticket 06 마감 기록을 비교한 뒤 “기존 구조 유지하는 걸로 하고”라고 결정했다. Reference의 Workspace 구성을 유지하고 작업마다 필요한 문서와 설명의 깊이를 고른다. Ticket 02가 맡은 운영안 설계는 마감한다. 02에서 진행하기로 한 실제 실행 환경의 통합 확인은 후속으로 남긴다.

## 도시 검색을 다시 맡는다면

9월 11일 마감 커밋 `33348de4`에서 도시 검색 Ticket만 읽어도 요청·응답이 공유하게 된 도시 코드, 수도 예외, 인구 10,000과 10,001의 경계, 동작 보존을 확인한 방법, 실제 서비스·앱 화면의 미확인과 사용자 수락을 찾을 수 있다. 반면 임시 검사만 둔 이유는 대화에 있었다. [마감 당시 Ticket](../source/noline-evaluation/documents/blobs/0f6f53ebe5494f9f2f524129b943eaa2d2c893ff.md) · [검사 방식을 고른 대화 8행](../source/noline-evaluation/corpus/01a08f9d-59f5-7763-b0ba-5ec65fea88eb/messages.jsonl#L8)

이 사례라면 Ticket의 검증 결과에 “당시 client에는 테스트 체계가 없어, 새 의존성을 추가하지 않고 고정 응답으로 수정 전후를 비교했다”는 이유를 한 줄 보탠다. 이 판단만을 위한 별도 record를 만들 실익은 작다. state에는 “도시 검색은 기존 동작 보존과 검증 한계를 확인하고 사용자가 수락했다. 03~05는 미착수이며 순서는 열려 있다”면 다음 작업을 고를 수 있다. 필터별 검사 결과는 해당 Ticket에서 다시 본다. 이는 문안 비교이며 당시 Noline 기록은 보존한다. [당시 state](../source/noline-evaluation/documents/blobs/ca0eaa4f25b92a5cbbfe9bcf5b6876fe58362a6a.md)

## Ticket 06을 닫은 뒤 다시 묻는다면

10월 6일 마감 커밋 `4fb309d2`의 state는 06의 합의 범위 완료와 다음 기본 후보 07을 잇는다. Reload 직후 네트워크 오류는 재발하면 조사하며 07의 선행 조건으로 정한 적이 없다는 설명은 다음 세션의 순서를 바꿀 수 있어 여기에 남길 가치가 있다. 반면 picker 구현 상세와 테스트 수치는 Ticket·검증 기록에서 읽을 수 있다. [당시 state](../source/noline-evaluation/documents/blobs/894f9bf4017ab3975fc4007102f9d4675a9974be.md)

Ticket에는 완료 범위와 함께 ① 경비 삭제 안내·상세 재시도처럼 알고 보류한 결함, ② 폼 수명·기간 밖 일정처럼 후속 Ticket이 맡은 일, ③ Android·새 휠의 23:59·실제 단절처럼 직접 확인하지 않은 조건, ④ Reload 오류처럼 관찰했지만 원인을 모르는 현상을 짧게 구별한다. 종료 record에는 원래 UX 보고서와 후속 결과를 어떻게 대조했는지, 사용자가 네 범주의 설명을 듣고 “그래 일단 마무리 하자 기록할거 하고 커밋해”라고 한 맥락을 보존한다. 나중에 왜 닫았는지 물을 때 이 근거가 있어야 마감 승인을 모든 조건의 검증으로 오해하지 않는다. [Ticket의 종료 판정](../source/noline-evaluation/documents/blobs/8f825aa3db085cfd8349bc1aca979602c0abc485.md#L226) · [당시 종료 record](../source/noline-evaluation/documents/blobs/2a1774d0466d9fc301a4b22e6f65c107fde83338.md)

## 어디까지 겹쳐 남기는가

| 독자가 내려야 할 판단 | 직접 쓸 곳과 허용할 중복 |
| --- | --- |
| 다음에 어디서 시작하며 무엇을 기다려야 하는가 | **state**에 전체 현재 위치, 다음 행동과 그 순서를 바꾸는 이유를 쓴다. 완료·보류 사실은 Ticket과 겹칠 수 있다. 검사 내역 전체는 Ticket이나 record로 연결한다. |
| 이 작업이 바꾼 것과 다시 믿어도 되는 범위는 어디까지인가 | **Ticket**에 해당 범위·짧은 선택 이유·결과·검증 한계를 둔다. 여러 실행이 함께 따를 목표·계약·가정 자체가 달라지면 **Spec**도 고친다. 개별 수락마다 Spec에 결과를 옮기지 않는다. |
| 왜 대안을 접었거나 미확인을 남기고 닫았는가 | **records**에 당시 비교, 철회·보류 이유, 판단에 필요한 최소 원문과 근거를 둔다. 결론·당시 상태는 맥락을 이해할 만큼 겹쳐 쓴다. 현재 선택이 바뀌면 current를 갱신하고 과거 기록은 당시 근거로 유지한다. |
| 어떤 자료를 언제 찾아야 하는가 | **README·recover·색인**에는 진입 경로와 읽을 조건을, **output**에는 선택된 산출물 위치를 둔다. 원자료는 **source**에서 보존한다. 판단에 꼭 필요한 뜻은 각 본문에도 남겨 링크를 따라가야만 첫 행동을 정하는 비용을 줄인다. |

짧은 작업에서 state와 Ticket을 합치면 다음 행동을 고르려는 독자가 끝난 작업의 검사 세부까지 읽게 된다. 반대로 모든 선택을 별도 record로 분리하면 짧은 이유 하나를 찾는 데도 문서를 넘겨야 한다. 여러 세션에 걸친 작업은 Ticket에 전체 과정을 누적하면 현재 판정과 당시의 미확인이 섞이기 쉽다. 두 사례와 [방향 정정 비교](2026-11-06-ticket02-record-work-next-action-check.md)를 종합해 **위치는 유지하고, 해당 문서만 읽었을 때 판단이 달라지는 뜻만 반복한다**는 안을 선택했다.
