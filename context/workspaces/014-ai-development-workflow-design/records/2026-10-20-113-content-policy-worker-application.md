# 관리 정책만 전달한 데모 문서 적용과 검증

사용자는 정책문서와 필요한 지시만 워커에게 전달해 데모 본문을 수정하고, 어떻게 해석하며 어떤 결과가 나오는지 확인하라고 요청했다. 이번 작업은 앞선 논의가 없는 작업자가 정책과 현재 실물을 읽어 적용하는 한 번의 실행이다. 반복 실행의 안정성이나 장기 유지 효과를 확인한 것은 아니다.

시작 판본은 `dded9f339f1596a183fbdb3e13e5d04f1be03093`이며 작업 트리는 깨끗했다. 대상은 [development-workflow](prototypes/development-workflow/README.md), 공통 정책은 [CONTENT-POLICY.md](prototypes/development-workflow/noline-demo/context/CONTENT-POLICY.md)다.

## 워커에게 전달한 범위

앞선 대화를 상속하지 않은 새 worker에게 저장소·대상 경로와 정책 진입점을 주었다. 전달한 작업 요구는 다음과 같다.

> 정책을 읽고 현재 데모 본문과 주변 자료를 정책에 맞게 수정해줘. 어떤 주제와 연결 문서에 적용할지 현재 실물에서 판단하되, 기존 내용의 의미·지위를 보존하고 읽고 사용할 수 있는 결과를 만들어줘. 정책을 어떻게 해석해 어느 범위에 적용할지, 불명확한 점은 무엇인지 수정 전에 main에게 짧게 메시지를 보내고 이어서 작업해줘. 별도 승인을 기다릴 필요는 없어.

수정 소유 범위는 prototype의 `noline-demo/context` 본문·관련 자료와 변경에 직접 연결된 Markdown 진입 문서다. 정책·viewer·제품 코드·다른 prototype·014 current 및 외부 records는 수정에서 제외했다. 앞선 대화나 014 작업 이력을 추가 입력으로 삼지 않고 정책과 현재 데모에서 찾아 읽게 했다. 로컬 지침 준수, 다른 작업자의 변경 보존, 커밋 금지도 전달했다.

결과에는 실제로 읽은 주요 자료, 해석과 적용·비적용 이유, 변경과 확인·미확인, 정책만으로 어려웠던 판단을 요청했다. Main이 폴더 구조나 과거 합의 요약을 별도로 설명하지 않았다. 이후에는 수정 전 해석·진행 상황의 보고와 역할 분담을 안내했다. 문서 작성 후반에는 첫 독자가 본문·사례만 읽어 판단했다는 결과를 워커에게 짧게 전달했으며, 문서 의미에 관한 추가 수정 지시는 주지 않았다. 독립 검증에서 발견한 링크 수정 요청은 아래에 따로 남겼다.

## 수정 전 워커의 해석

다음은 변경 전에 받은 응답이다.

> 정책은 공통 관리 원칙을 CONTENT-POLICY 한곳에 두고, 실제 주제의 본문·분할 본문과 형성 자료를 분리하라는 것으로 읽었습니다. 현재 데모에서 분명한 주제 묶음은 Personal/development의 세 기준과 대응 사례이며, 이름·완료 주제만 형성 맥락·근거가 이미 있습니다. 세 주제를 각각 README + index + index.cases로 묶고, 이름 주제의 context/evidence를 background로 옮기며 기존 맥락에 섞인 과거 정정·선택은 근거 범위 안에서 records로 분리할 예정입니다. 다른 두 주제는 확인 가능한 형성 자료가 없어 빈 background를 만들지 않겠습니다. Project·Work는 기존 책임 체계와 실행 이력을 유지하고 직접 연결 링크·관리 진입만 맞춥니다. 불명확한 점은 정책의 적용 대상이 모든 단일 Project 본문까지 구조 전환하라는 뜻인지인데, 일괄 재배치를 금지한 문장과 현재 실물을 근거로 이번에는 Personal의 명확한 주제 묶음에 적용합니다.

이 해석을 받은 뒤 Main이 구조를 다시 지정하거나 답을 교정하지 않고 작업을 이어가게 했다. 확인할 대상은 이 첫 해석과 실제 결과가 같은지, 현재 적용과 형성 과정의 읽기 경로가 구별되는지, 원문의 의미·지위가 보존되는지다.

## 결과와 확인

워커는 다음을 실제 수정했다.

- Personal의 공통 제공·계약과 수명·이름과 완료 세 주제를 각각 `README.md`, `index.md`, `index.cases.md`로 묶었다. 세 사례 파일은 원래 있던 본문을 옮긴 것이며 cases를 모든 주제의 필수 파일로 새로 채운 것이 아니다.
- 이름 주제에 `background/README.md`, `context.md`, `evidence.md`와 형성 기록 세 개를 두었다. 기록은 조건별 적용, 명료함과 개명, Personal·Project 갱신 책임을 다룬다. 기존 데모가 보존한 맥락·근거에서 재구성했고 당시 원기록이나 새로운 독립 증거로 가장하지 않았다.
- 다른 두 주제에는 확인해 보존한 형성 자료가 없다는 상태를 안내하고 빈 background를 만들지 않았다. 이는 해당 주제가 형성 과정 없이 생겼다는 뜻이 아니라 이번에 제공된 실물의 보존 범위다.
- 개발 상위 README가 소유하던 공통 판단을 `development/index.md`에 보존하고 README를 주제 선택·관리 안내로 나눴다. 이는 워커가 정책과 실물을 대조하며 추가로 내린 배치 판단이다.
- Context·Personal·Work·prototype 진입과 연결을 맞췄다. Project에는 구성·관리 지침에서 공통 정책을 읽는 연결과 적용 관계만 추가했으며 제품 계약·현황·품질 판단을 Personal에 맞춰 바꾸지 않았다.

Main은 여섯 기준·사례의 이전 판본과 이동 후 본문을 대조했다. 사례 세 개는 링크 외 내용이 같고, 일반 기준 세 개는 읽기·관리 안내만 바뀌었다. 코드 블록 23개는 같으며 근거 발췌의 인용·비교표도 보존했다. 첫 워커 적용에서는 정책·제품 코드·Work 원자료를 바꾸지 않았다. 이후 사용자 요청으로 정책을 보완한 내용은 아래에서 구별한다.

### 처음 읽는 소비자의 두 상황

작성 워커와 별개인 새 독자에게 이전 대화·워커 보고·기대 답을 주지 않았다. 이름 주제 README와 질문만 주고 필요한 prototype 내부 자료를 고르게 했다.

첫 질문은 현재 인증 코드의 이름 유지·개명을 어떻게 판단하며, 다른 Project의 기존 공개 API에 그 선택을 그대로 적용해도 되는지였다. 독자는 **README → index → index.cases 세 파일**을 읽었다. 형성 자료는 현재 기준 적용에 필요하지 않아 읽지 않았다고 보고했다. 현재 조건에서는 B의 명료함을 권하되 공개 호환성·소비자의 다음 행동·전환 비용을 다시 판단하고, 필요한 결과가 없다면 이름만 좁히지 말고 동작을 고쳐야 한다고 설명했다.

이어 같은 독자에게 다음 **확인용 가정**을 주었다.

> 기존 이름에 익숙한 동료 두 명이 B보다 A를 더 빨리 이해했다고 말했다. 비교에 걸린 시간, 사전 설명, 실제 사용 과제는 기록하지 않았다.

이 자료를 근거로 “설명이 충분하면 기존 이름을 우선”하도록 기준을 바꾸자는 제안을 판단하게 했다. 독자는 background 안내에서 현재 맥락, 명료함·조건별 적용 기록, 근거를 고르고 공통 정책과 적용 중인 Work·관련 Project 계약을 추가로 확인했다. 기존 사용자 지향과 B의 속도 개선을 측정하지 않았다는 한계를 구별하고, 해당 관찰을 추가 검토할 단서로 보되 일반 기준이나 제품 계약을 곧바로 바꾸지 않았다. 과거 발췌 보존, 실제 관찰이라면 조건·한계를 새 근거와 기록으로 남길 수 있음, 이번 입력은 가정이므로 실제 제품 관찰로 쓰면 안 됨도 구별했다.

이 두 번째 확인은 **읽기·갱신 범위의 판단**이며 파일 편집 실험은 아니다. 확인용 관찰을 데모의 evidence·Work 상태에 넣지 않았다.

### 독립 대조에서 찾은 누락과 보완

별도 검증자에게 정책, 현재 prototype, 수정 전 Git 판본과 검증할 주장만 주었다. 워커 보고나 Main의 예상 결론은 주지 않았다.

첫 검토에서 `Work/records/2026-10-19-01-input-selection.md`의 ‘개인 개발 공통’ 링크가 공통 판단을 옮긴 `development/index.md` 대신 `development/README.md`를 가리키는 문제를 찾았다. 파일은 존재하므로 경로 검사를 통과하지만, 설명이 인용한 내용을 직접 열지 못하는 문제다. Main은 이를 워커에게 돌려보내 해당 링크와 같은 이동의 관련 연결을 확인하도록 했다.

최종 검토에서는 의미·합의 지위·근거의 훼손이나 불필요한 범위 확대를 발견하지 못했다고 보고했다. 독립 검증자는 이전 판본과 현재 내용, 기록의 재구성 범위, 현재 사용과 변경의 읽기 경로를 대조했으며 원래 대화의 완전성·사용 효과·반복 재현까지 확인한 것으로 보고하지 않았다.

워커는 누락된 링크를 `development/index.md`로 바꾸고 README로 들어오는 다른 연결 여섯 개를 확인했다. 나머지는 주제 선택·구성 안내 목적이어서 유지했다. Main도 수정한 링크와 대상 본문의 조건별 적용 설명을 직접 대조했다. 독립 검증자의 최종 보고는 수정 후 재검사 전이므로, 이 마지막 수정 확인은 Main의 검사로 구별한다.

### Main이 맡은 표시·기록 연결

Main은 viewer의 본문·사례·형성 자료 경로와 이름을 새 구조에 맞추고 표시 사본을 재생성했다. 기존 필수 연결 검사를 두 README와 본문·사례·맥락·근거의 연결 12개로 맞췄다. 이 검사는 의미 판단을 대신하지 않는다.

바깥014의 과거 기록 13개에서는 이동한 현재 실물로 들어오는 링크 34개만 갱신했다. 기록95의 이미 사라진 사례 절 앵커는 현재 사례 파일로 연결하도록 정리했다. 당시 설명·발췌·판정은 바꾸지 않았으며 현재 경로를 연결했다는 사실이 과거 판본을 복원했다는 뜻은 아니다.

표시 검사에서 문서64개·코드5개 원문 일치, A/B 코드의 이름 두 쌍 외 동일성, 내부 링크와 앵커, prototype 내부 경계, 화면 스크립트 문법을 확인했다. 브라우저 표시·제품 동작 검사는 이번에 실행하지 않았다.

## 후속 정책 보완 — 링크가 맡은 읽기 목적을 보존한다

사용자는 큰 구성과 새 독자의 읽기를 긍정하고, README를 그대로 써도 괜찮을 수 있지만 본문을 index로 옮겼다면 그 본문을 참조하는 링크도 옮기는 것이 맞다고 판단했다. 같은 일이 반복되지 않도록 관리 정책에 사례를 반영하되 단순히 규칙을 덧붙이지 말고 기존 본문을 고려해 보완하도록 요청했다.

Main은 [정책](prototypes/development-workflow/noline-demo/context/CONTENT-POLICY.md)의 기존 구성·읽기·갱신·완료 확인을 함께 다듬었다.

- 주제보다 상위의 README에는 공통 판단·설명을 함께 둘 수 있고, 분리는 실제 읽기·관리 필요로 판단하도록 명시했다. 개별 주제 README와 index의 역할 구분은 유지했다.
- 링크는 주변 설명이 요구하는 읽기 목적과 실제 내용으로 정한다. README의 공통 기준을 별도 본문으로 옮겼을 때 기준 적용 링크는 새 본문으로 옮기되, 주제 선택 링크는 README에 남기는 대비를 읽기 안내 안에 넣었다.
- 파일 경로가 남아 있어도 역할·내용이 달라진 경우를 갱신 조건에 포함했다. 변경한 문서뿐 아니라 그 내용을 참조하던 경로에서 출발해 요청한 내용을 목적지에서 읽을 수 있는지 확인한다.

이 보완을 현재 Work의 연결에 대입했다. 입력 선택 기록의 ‘개인 개발 공통’은 index의 조건별 적용 본문으로, DEVELOPMENT의 ‘개발 판단 안내’는 주제를 고르는 README로 이어져 각각의 목적과 맞는다. 이는 기존 사례의 대조이며 새 워커 실행이나 반복 신뢰성 검증은 아니다. 작업 이력 자체를 정책 안에 복제하거나 모든 README 분리·모든 링크의 일괄 교체·저장소 전체의 전수검사를 요구하지 않았다.

앞선 검증자에게 수정한 정책을 다시 읽게 해 주제·상위 README의 구별과 확인 범위가 유지됐다는 의견을 받았다. 표시 사본도 재생성해 문서64개·코드5개 원문 일치, 링크·앵커 오류 없음과 필수 연결12개를 확인했고 `git diff --check`를 통과했다. 이 도구 검사와 정책 문장의 의미 검토는 구별한다.

## 이번 결과로 판단할 수 있는 범위

정책과 기존 데모만으로 본문·사례와 형성 자료, 두 README·현재 맥락·과거 기록·원문의 역할을 구별해 실제 결과를 만들었다. 별도 독자도 현재 적용과 의미 재검토에서 읽을 범위를 달리 선택했다. 다만 작업자 한 명의 적용과 독자 한 명의 두 상황이며 장기 유지·반복 수행의 보장은 아니다.

워커는 모든 단일 Project 문서를 언제 주제 묶음으로 전환할지가 정책만으로 명확하지 않다고 보고했다. 이번에는 기존 본문·사례 관계가 분명한 Personal 세 주제를 선택하고 Project·Work 전체의 재배치를 피했다. 현재 적용 결과가 적절한지와 향후 다른 형태의 문서에 같은 구조가 필요한지는 구별한다. 이번 모호함을 이유로 모든 문서의 파일 구성을 의무화하거나 정책에 예외를 덧붙이지 않았다.

기준·사례 전체의 사용자 수용, 실제 Noline 설치, workflow·skill 구체화와 관련 Ticket 완료는 이번 결과에서 도출하지 않는다.

## 기록과 커밋 범위

사용자는 적용·검증과 후속 정책 보완을 Workspace에 기록하고 커밋하도록 요청했다. 이 변경 묶음에는 세 주제의 재배치·이름 background·공통 정책 보완, 관련 진입·참조 경로와 열람 화면, current·output·기록 안내를 포함한다. 기존 바깥 기록은 이동한 실물을 가리키는 링크만 맞췄고 과거 판단은 보존했다. 제품 코드·원자료·다른 prototype·전역 하네스는 커밋 대상 변경에 포함되지 않는다.

다음 세션은 current/state에서 현재 범위와 남은 판단을 확인하고, 실제 구성·읽기를 볼 때 주제 README와 공통 정책을 읽는다. 첫 워커에 전달한 정책 판본과 후속 보완 판본을 구별하고, 이번 긍정을 모든 본문·개발 워크플로의 최종 수용으로 확대하지 않는다.
