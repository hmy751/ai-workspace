2026-10-19. **형식·책임의 선택은 상당 부분 반영됐지만, 내용은 이름·책임·완료 한 주제로 좁아지면서 앞서 확보한 판단의 폭과 연결이 약해졌다.** 한 주제 안에서도 개명과 유지의 조건은 자세해졌으나, 실제 코드에서 그 조건을 어떻게 판별하는지 보여 주는 비교는 부족하다. 워크플로는 역할과 반환 책임을 설명하는 단계이며 기존 스킬을 통한 한 작업의 진행까지 구체화하지 않았다.

## 현재 본문 자체의 품질

### 조건은 설명했지만 실제로 조건을 판별하는 비교가 약하다

상세 사례의 내부 함수는 “이름은 후속 처리까지 끝낸 듯 보이고”, “매번 함수 내부와 완료 경로를 함께 읽어야 한다”를 가정한다. 공개 API는 “이름·반환형·가까운 문서에서 이 관계를 이해할 수 있다고 가정한다”에서 시작한다. 그래서 개명과 유지가 왜 달라지는지는 설명되지만, 실제 코드에서 어느 쪽인지 판단하는 데 필요한 관찰은 이미 가정 안에서 해결돼 있다.

반면 파일 저장 사례는 `await save()` 직후 파일을 읽는데 쓰기가 끝나지 않았다는 소비자 행동과 반환 시점을 보여 준다. 이 경우 이름을 좁혀도 요구가 충족되지 않는 이유가 직접 드러난다.

**새 품질 권고:** 내부/공개 같은 다른 조건의 사례를 더 늘리기보다, 같은 계약·같은 호출부에서 기존 이름+가까운 설명과 개명+설명을 나란히 보여 준다. 무엇은 호출부에서 알 수 있고 무엇은 여전히 내부를 따라가야 하는지, 변경 비용을 감수할 만큼 읽기 부담이 줄어드는지 비교한다. 이는 이번 평가의 제안이며 이미 합의한 작성 형식이 아니다.

### Project의 계약 설명과 실제 표현 선택 사이를 더 연결해야 한다

[초기 입력](prototypes/development-workflow/noline-demo/context/work/workspaces/001-login-completion-names/source/scenario-input.md)은 가상 코드의 `loginAndRefresh`가 인증을 기다리고 조회를 시작한 뒤 재조회 완료는 기다리지 않는다고 설정했다. `onCompleted`의 LoginScreen 표현은 “로그인과 화면 갱신 완료”였고, ReauthDialog는 모달을 닫았다. [실제 작성 기록](prototypes/development-workflow/noline-demo/context/work/workspaces/001-login-completion-names/records/2026-10-19-02-implementation.md)의 새 demo는 `signInAndRequestRefresh`·`onSignedIn`과 “로그인 완료”를 골랐다. 이것은 실제 Noline의 전후 변경 이력이 아니다.

| 같은 입력에서 비교할 부분 | 현재 판단으로 알 수 있는 것 | 더 구체적으로 비교할 것 |
| --- | --- | --- |
| “로그인과 화면 갱신 완료” → “로그인 완료” | 조회·렌더 완료를 확인하지 않으므로 초기 문구는 계약보다 큰 완료를 표현한다. 현재 표현을 좁힌 이유가 분명하다. | 사용자 문구 수정과 함수 개명을 같은 강도의 필수 조치로 묶지 않는다. |
| `loginAndRefresh`·`onCompleted` 유지 + 완료 범위 설명 | 현재 일반 기준도 가능한 선택으로 인정한다. | 호출부 가까이에 어떤 설명이 있으면 충분하며, 이때도 함수 선택·후속 코드에서 어떤 부담이 남는지 실제 짧은 코드로 보여 준다. |
| `signInAndRequestRefresh`·`onSignedIn` + 계약 설명 | 현재 선택이다. 이름에서 조회 요청과 인증 완료를 구별하려는 이유가 작성 기록에 있다. | 기존 이름+설명보다 무엇을 덜 추적하게 되는지, 긴 이름에도 여전히 설명이 필요한 부분은 무엇인지 같은 호출부에서 비교한다. |
| 조회 완료까지 기다림 | 현재 두 소비자는 최신 조회 값을 소비하지 않으므로 새 대기를 요구하지 않는다. 실패 분리와 대기는 별개라는 정정도 반영됐다. | 최신 조회 값을 실제로 쓰는 요구가 생겼을 때 소비자 대기와 공통 계약 변경을 구별한다. 현재 이름 문제의 자동 해법으로 대기를 추가하지 않는다. |

[현재 Work의 선택 요약](prototypes/development-workflow/noline-demo/context/work/workspaces/001-login-completion-names/current/memory/spec/05-constraints-design-assumptions.md)은 “두 소비자는 내부 코드이고 공개 API 호환 비용이 없다는 조건에서” 개명을 선택했다고 먼저 설명한다.95의 일반 기준은 이 사실을 비용 조건으로만 다룬다. 앞선 작성 기록에 호출부에서 범위를 드러내려는 이유가 있으므로 이유가 전혀 없거나 자동 개명을 명령한다고 판정할 수는 없다. 다만 현재 선택 요약에도 **이 사례에서 얻는 구체 이득과 설명 보완만으로 충분한 대안과의 차이**가 더 필요하다.

### B 방향을 수행 장면으로 이어 쓰는 구체화가 남아 있다

현재 DEVELOPMENT.md는 입력 선택, 구현자 전달, 검토자의 직접 수정, 새 제품 판단의 반환, 결과 갱신 책임을 설명한다. 그러나 연결한 검토 기록은 직접 수정하지 않은 실제 이력이다. 역할 문장의 존재와 B를 한 작업에서 끝까지 수행한 사실은 다르다.

93이 요청한 구체화는 기존 스킬의 어느 조건·입력·행동을 쓰며 Main이 무엇을 판단하는지, 새 작업자가 무엇을 직접 읽는지, 검토 수정 뒤 무엇을 다시 확인하며 원래 목표가 남으면 어떻게 반환하는지를 한 작업으로 연결하는 것이다. 이를 위해 모든 본문이나02를 먼저 완료할 필요는 없다. 정확한 스킬 배치·검토 예외·최종 확인 담당은 아직 열린 선택이므로 이 평가에서 정하지 않았다.

## 다음 구체화 제안

Main은 이름·완료 문구만 계속 늘리기보다 **기존 판단의 사용 범위를 복원하면서, 같은 작업의 실제 선택을 더 선명하게 비교하는 것**을 추천한다.

1. 위 내용 대조에서 빠진 공통화·부품 교체·수명·관련 개선의 판단을 현재 입구에서 남은 내용으로 찾을 수 있게 한다. 그 뒤 독립 본문이 필요한 의미와 기존 이름·완료 본문에 이미 충분히 있는 의미를 가른다. 이전 네 절의 파일 구조나 모든 문장을 그대로 복사하는 제안은 아니다.
2. 현재 인증 작업에서 문구 수정, 이름 유지+설명, 개명+설명을 같은 코드 조건으로 비교한다. 이 비교로 일반 기준의 판별 힘과 Project 가이드의 표현 구체성을 함께 보완한다.
3. 같은 작업에 기존 스킬의 실제 입력·행동을 대입해 Main·구현·검토 수정·확인·반환을 연결한다. B의 직접 수정 방향을 유지하면서 미정 운영 조건은 선택이 필요한 지점에서 비교한다.

이 순서는 이번 평가에 따른 제안이다. 새 티켓 생성, 기존 티켓의 완료, 이전 기준 전체 채택, prototype 본문 수정은 수행하지 않았다.

## 확인한 사실과 한계

- 평가 시작 Git HEAD는 `0aeb9e4`이고 작업 트리는 깨끗했다. 현재 본문을 이전 기록의 리뷰 결론만으로 평가하지 않고 실제 파일과 대조했다.
- 별도 컨텍스트 두 검토자는 각각 결정 반영과 본문 품질을 조사했다. Main은 결과를 원문 발췌·실제 본문과 함께 판단했다. 이 문서는 Main의 종합 평가이며 사용자 수용이나 독립 적용 실험의 성공 보고가 아니다.
- 후반57~96의 연속 대화 원문 전체가 source/discussion에 보존된 것은 확인하지 못했다. 해당 기록에 보존된 사용자 발췌·전후 설명과 당시/현재 실물의 대조가 근거다. 특히81의 Main 제안 전체 원문 부재는84가 이미 밝힌 한계다. 전체 대화 전수 복원이나 모든 과거 결정의 완전성을 주장하지 않는다.
- 이번에는 이 평가와 Workspace의 재진입 안내만 갱신했다. 기존 prototype·원자료·과거 날짜별 기록·스킬·제품 코드·전역 하네스는 변경하지 않았다. 제품 테스트나 이전 예제 테스트는 다시 실행하지 않았다.
- 작성 후 결정 반영 담당자가 이 기록을 다시 대조했고, 수정이 필요한 지위 과장·원문 오독·현재 본문과의 불일치를 보고하지 않았다. 변경 Markdown6개의 로컬 링크330곳에 누락이 없었고 `git diff --check`를 통과했다. 변경은 미커밋 상태다.
