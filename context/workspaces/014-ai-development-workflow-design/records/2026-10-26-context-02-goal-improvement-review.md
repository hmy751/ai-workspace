# 04-03 2번 담당자 수행의 구체화와 독립 개선 리뷰

이 기록은 직접 수정안의 당시 리뷰다. 최신 방향은 [담당자의 제안과 Main의 검토·반영 구체화](2026-10-26-context-proposal-review-apply-design.md)를 따른다.

당시 결과: 구현과 해당 사실 설명을 같은 담당자에게 함께 배정할 조건, 원문 선택·반영·반환·Main 회수, 채택할 때 맞출 지침 위치를 2번 상세안에 구체화했다. 새 독립 리뷰의 개선점 하나를 원자료와 대조해 당시 설계안에 반영했다. **문서 종류보다 이번 변경으로 달라지는 사실·약속의 의미로 범위를 정한다**는 보완은 현재 방향에서도 유지한다. 이 리뷰에서 실행 지침·스킬·제품·설정은 변경하지 않았다.

## 사용자 요청과 Main 초안

직전 대화에서는 Main의 목표·조건·원문 접근점 전달, 담당자의 직접 읽기·추가 탐색은 기존 합의이며 추가 논의 중심은 구현과 함께 달라지는 현재 구현 설명·읽기 경로를 어느 범위로 맡길 것인지 설명했다. 사용자는 다음을 요청했다.

> “일단 먼저 구체화 하고 이것도 앞선 것처럼 개선 리뷰어 돌려보자”

Main은 기존 2번을 구체화한 뒤 새 컨텍스트의 reviewer `context02_goal_improvement`에게 넘겼다. 검토 입력의 SHA-256은 `78008296fa94be4069b056f91a8cc4c38cbbdc0f1d5104deea62dbe7b5032923`이며, 출발안은 commit `088c6525`의 같은 파일이다. 초기 네 안의 리뷰와 이번 후속 리뷰를 구별한다.

초안에서는 다음을 구체화했다.

- 기존 구현자의 설명 작성과 이번 Project 사실 본문 배정을 구별하고, 구현자가 근거를 확인하는 자리에서 같이 맡길 때와 Main이 직접 정리하거나 여러 결과를 모아야 할 때를 나눴다.
- 읽기 범위와 수정 권한, 이미 결정된 약속의 반영과 새 약속 선택을 구별했다. 새 Owner·범위 밖 변경은 Main에게 연결하며 이미 맡은 범위에서 승인을 반복하지 않는다.
- 가상 로그인 후속 요구에 실제 배정 내용, 필요한 원문·추가 탐색, 코드·본문·근거의 반환, Main의 실제 반영 확인과 기존 검토·검증을 연결했다.
- development·execution·Work 안내 중 실제 채택 시 맞출 자리와 그대로 사용할 Project 관리 기준을 표시했다. 새 문서 담당 역할이나 필수 전달 양식을 만들지 않았다.

기존 계약의 좁은 사실 대조는 별도 조사 담당이 수행했다. [development](prototypes/development-workflow/skills/development/SKILL.md)의 구현 완성·배정 권한·Owner 갱신, [execution](prototypes/development-workflow/skills/development/references/execution.md)의 입력·판본·병행 작업, [Project MAINTENANCE](prototypes/development-workflow/noline-demo/context/project/MAINTENANCE.md)의 실제 변경 담당자와 근거 대조, [CONTENT-POLICY](prototypes/development-workflow/noline-demo/context/CONTENT-POLICY.md)의 변경 작업자·읽기 경로·편집과 선택 권한 구별이 근거다. development와 [Work AGENTS](prototypes/development-workflow/noline-demo/context/work/AGENTS.md)·[Work README](prototypes/development-workflow/noline-demo/context/work/README.md)의 Main 직접 갱신 문장도 함께 맞춰야 한다. 이 사실 조사와 독립 개선 리뷰는 다른 수행이다.

## 독립 리뷰의 입력과 범위

reviewer에게 최신 요청과 관련 사용자 원문, 2번 초안, 전체 목표·04-03·잠정 합의·구성 논의·1/3/4번과 통합안, 실제 development·역할 상세·영역 관리 본문·로그인 코드/검사, 보존된 read/update, 고정판 Matt·Lauren·Vercel 조사와 원문 접근점을 제공했다. 추가 원자료가 필요하면 스스로 선택할 수 있게 했다. Main의 사실 조사 결론이나 예상 지적을 별도 정답으로 전달하지 않았다.

단순 승인 대신 목표에 기여하는 개선·대안의 실제 행동 차이와 비용을 찾되, 발견을 위해 새 역할·절차를 늘리지 않도록 했다. 읽기 전용 설계 리뷰이며 파일 수정·제품 실행·실험·설치·커밋을 맡기지 않았다. 외부 자료의 최신성 재조사가 아니라 기존 고정판과 현재 체계에 대한 검토다.

## 개선점 — 계약의 뜻 보존과 파일 무수정을 구별한다

리뷰 당시 배정 예제는 다음 범위를 포함했다.

> “이번 범위에는 소비자와 필요한 호출부·검사, Project의 현재 인증 흐름 설명을 포함합니다.”

2번의 반영 예제에는 “인증 계약의 뜻도 그대로 둔다”고 적혀 있었으나, 연결된 3번 표는 다음과 같이 설명했다.

> “기존 계약으로 설명되는 선택이면 본문을 유지한다.”

reviewer는 실제 [인증 계약](prototypes/development-workflow/noline-demo/context/project/guidance/authentication-and-session/INDEX.md)의 ‘조회를 기다릴지는 다음 화면의 요구로 정한다’ 표에서 다음 문장을 찾았다.

> “인증 적용 뒤 필요한 조회까지 기다린다. 이 경로는 현재 demo에 구현하지 않았다.”

약속을 설명하는 문서에도 현재 지원 사실이 함께 있다. 가상 후속 요구를 실제로 구현했다면 약속의 뜻은 유지하면서 미구현이라는 설명은 바뀌어야 한다. current의 사실만 고치고 guidance 전체를 그대로 두면 설명이 엇갈릴 수 있다. **실제 실행에서 이미 발생한 실패가 아니라 초안의 사례에서 드러난 해석 위험**이다.

Main은 위 계약 원문과 2번의 배정·반영 문장, 3번 표를 직접 대조했다. Project 관리 본문의 ‘의미가 달라진 본문부터 맞추고 관련 설명을 이어 맞춘다’는 기준에도 맞으므로 이 개선을 설계안에 채택했다.

반영한 범위는 다음과 같다.

- **2번:** 초기 배정을 이번 구현으로 달라지는 인증의 현재 사실과 직접 관련 설명으로 정한다. current와 guidance를 파일 종류로 나누어 수정 여부를 고정하지 않는다. 예제에는 guidance의 미구현 문구도 실제 구현·확인 뒤 그 범위에서 맞추도록 명시했다.
- **3번과 통합안:** 기존 계약의 뜻·보존 조건을 유지하는 것과 그 본문 속 낡은 현황을 정정하는 것을 구별했다. 범위 밖 Owner·새 약속은 기존대로 반환한다.
- **후속 확인:** 기존 대비 장면에 같은 현재 사실이 서로 다른 종류의 본문에 들어 있는 경우를 포함한다. 전체 문서 재검사나 새 시험을 일상 작업의 필수 절차로 만들지 않는다.

가상 요구를 구현한 것은 아니므로 실제 demo의 미구현 설명은 그대로다. 초기 쓰기 범위를 명료하게 하는 안이며, 관련 문서를 읽었다는 이유만으로 무제한 수정권을 주지 않는다.

## 유지할 부분과 확인 상한

reviewer는 조건부 동시 배정, Main의 실제 반영 확인과 별도 검증의 구별, 기존 역할 재사용, 재조사 비용 감소를 기대 이득으로만 두는 점을 유지하도록 권했다. 새로운 역할이나 별도 문서 검증자를 추가할 근거는 찾지 못했다.

reviewer는 전달한 초안 해시의 일치, 현재 실행 지침·본문 관리 계약·관련 설계안·인증 코드 연결을 읽어 대조했다고 보고했다. 파일 수정·제품 실행·실제 위임 효과 확인은 하지 않았다. Main의 직접 재확인은 위 핵심 문장·원문과 연결된 설계안의 변경 범위다. 이번 작업은 세부 일괄 채택·실행 지침 반영·설치의 승인이 아니다.

다음 사용자 논의에서는 같은 담당자에게 맡길 범위와 비용, Main의 회수 책임이 실제 흐름에서 적절한지 본다. 코드 구현·정본 반영·Work 유지가 어느 위치에서 이어지는지 설명하고, 이후 채택할 범위만 실제 지침에 반영한다.

## 보완 뒤 좁은 재확인

같은 reviewer에게 최초 지적의 해소와 과도한 수정 권한 확대 여부만 반환받았다. 2번의 의미·Owner 배정과 범위 밖 반환, guidance의 미구현 사실을 실제 구현·확인 뒤 맞추는 예제, 3번과 통합안의 연결에서 해당 해석 위험이 설계 문장 수준으로 해소됐다고 확인했다. 전체 재리뷰나 실제 수행 효과 검증은 아니며, Main이 이 결과를 2번 전체의 사용자 승인으로 사용하지 않는다.

Main은 변경한 설계·리뷰·현재 진입 문서8개의 로컬 링크523개와 공백을 확인했다. 오류는 없고 runtime·source·스킬 설치 경로 변경도 없다. 실제 수행 시험과 운영 효과는 이번 확인에 포함하지 않았다.
