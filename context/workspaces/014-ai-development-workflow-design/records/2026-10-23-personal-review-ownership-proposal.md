# Personal과 검토 워크플로의 소유·입출력 관계 — 4번 구체화 제안

**현재 결론 — 4번 설계 마무리.** 책임 구분·외부 내용 배치·독립 리뷰를 거친 뒤 사용자는 과도한 보류를 지적했다. 현재 근거로 유용한 내용을 선택해 구체화하며, Personal의 A는 기존 계약·실패 판단에 통합하고 B는 조건부 상태·전이 판단으로 반영하는 방향을 받아들였다. 검토 수행·강도·외부 관점 활용도 함께 정리했다. [마지막 확정 절](#후속-확정--과도한-보류를-바로잡고4번을-마무리한다)이 현재 선택이다. 아래 최초 제안과 리뷰 직후의 A·B 보류는 형성 이력이며 최신 결론이 아니다. 정확한 본문 편집·실행 연결은 남아 있고, 다음은5번 Main 판단이다.

2026-10-23. **Personal은 여러 작업에서 사용할 개발 판단의 내용·이유·적용 조건을, 검토 워크플로는 별도 검토를 수행하고 결과를 Main의 판단에 연결하는 계약을 소유하는 안**을 제안한다. 책임을 먼저 구체화한 뒤 기존·외부 내용을 배치한다. 아래는 Main의 추천이며 새 운영 계약이나 Personal 보완을 승인·적용한 기록이 아니다.

## 사용자가 정한 진행 범위

사용자는 앞선 [실제 본문 대조와 보완 후보](2026-10-22-review-criteria-coverage-and-placement.md) 뒤 “그냥 보완 보단 책임 분리를 먼저 생각하는게 어때?”라고 했다. 이어 “Personal이랑 검토 워크플로가 각각 뭘 소유하고 서로 뭘 받아 쓰는지부터 구체화해보자 기존 구조랑 레퍼런스도 같이 비교해서 뒤에 티켓도 겹치지만 일단 4번 지금 논의에서 할수 잇는 만큼은 구체화”하도록 요청했다.

따라서 앞선 후보A·B의 문구를 먼저 채택하지 않는다. 비교에서 확인한 본문의 충분성·부분 공백은 근거로 유지하고, 실제 추가·이동·삭제는 이번 책임 구분을 통해 다시 판단한다. 1~3번 합의와4번의 독립 판단·강도·중복 관리 원칙은 유지한다. 5번 Main 판단안은 제안 상태다.

## 두 책임이 소유하는 것

| 구분 | Personal의 개발 판단 | 검토 워크플로 |
| --- | --- | --- |
| 직접 답하는 질문 | 어떤 구현 선택이 어떤 조건에서 왜 적절한가? | 별도 검토자가 무엇을 어떤 근거로 재판단하고 Main에 어떻게 연결하는가? |
| 소유 내용 | 판단 관점, 이유, 적용 조건·예외·절충, 판단을 구별하는 사례 | 역할 목적·경계, 기준 사용·독립 재판단·대안 탐색 과제, 탐색 강도, 근거·불확실성 반환, Main과의 연결 |
| 주된 사용자 | 구현자·검토자·Main 모두. 별도 리뷰가 없어도 개발 판단에 쓴다. | Main과 검토자. 다른 실행자의 인계·수정·검증과 연결한다. |
| 이 책임에서 정하지 않는 것 | 특정 Project의 계약·현재 사실, 이번 Ticket의 결정, reviewer 호출·모델·권한·보고 양식 | 좋은 코드에 관한 별도 상시 원칙집, 제품 계약의 재정의, 이미 채택된 기준을 복제한 별도 정본 |
| 수정 이유 | 지속해서 사용할 개발 판단의 의미·조건이 달라졌거나 충분하지 않다. | 기준을 잘못 전달·소비하거나, 별도 판단이 작동하지 않거나, 인계·권한·반환이 빠진다. |

이 구별은 ‘개인 취향 대 객관적 원칙’, ‘추상 대 구체’, ‘짧은 글 대 긴 글’이 아니다. Personal에도 정확성·계약·수명이 있고 검토 워크플로에도 충분한 수행 설명이 필요하다. 어떤 결정을 바꾸는 문장인지로 소유를 판단한다.

검토 워크플로는 전체 개발 워크플로 안의 책임이다. Main의 초기 배정·사용자 논의·최종 완료, 구현자의 자기 확인, 검증자의 실제 충족 판정까지 reviewer의 한 지침에 몰아넣지 않는다. 이번4번은 그중 기준 소비·독립 재판단·탐색 강도와 내용 소유의 관계를 구체화한다.

## 무엇을 받아 쓰고 무엇을 돌려주는가

1. **Personal이 제공하는 것:** 이번 판단에 관련된 원칙의 내용·취지·조건과 원문 위치. 일반 본문만으로 판단 차이가 불명확할 때 필요한 사례·형성 이유를 찾을 수 있어야 한다. 모든 본문·사례를 항상 전달한다는 뜻은 아니다. 정확한 묶음·선택 주체·조회 절차는7·8번에서 정한다.
2. **워크플로가 다른 곳에서 받는 것:** Project의 제품 의미·계약·개발 규약·현재 사실, Spec/Ticket의 목표·범위·완료 조건, 실제 코드·사용처·검사 근거. Personal이 이 입력들을 대신하거나 한 줄의 문서 서열로 모든 충돌을 해결하지 않는다.2번의 내용 성격 구별을 적용한다.
3. **검토자가 수행하는 것:** 기준과 실제 조건을 대조하고 현재 선택·적용을 독립적으로 재판단한다. Main이나 구현자의 선택이라는 사실만으로 받아들이지 않는다. 주요 대안을 살피되 발견·변경을 강제하지 않고 관련성·영향·불확실성에 따라 더 확인한다.
4. **Main에게 반환하는 것:** 확인된 문제·비교 대안·적용 조건의 의문, 판단 근거·효과·비용·불확실성. 사용한 기준과 실제 판단 사이의 관계를 찾을 수 있게 한다. 이는 의미상 필요한 결과이며 모든 의견에 동일한 필드·전체 추론·재인용을 요구하는 출력 양식은 아니다.
5. **Personal로 돌아갈 수 있는 것:** 이번 선택을 넘어 기준의 의미·조건을 다시 볼 근거. 우선 Work의 판단·갱신 후보로 다루며 검토자가 원칙을 자동 수정하거나 한 사례를 공통 규칙으로 승격하지 않는다. 지속 개인 기준인지, 제품 계약인지, 이번 작업의 선택인지는 Main과 해당 내용의 권한 있는 판단으로 구별한다. 구체 갱신은15번이다.

즉 Personal이 일상적으로 검토 결과를 매번 받아야 기준이 성립하는 구조는 아니다. 검토는 Personal과 독립된 Project/Work 입력을 사용하며, 기준 갱신이 필요한 경우에만 근거를 되돌려준다. 자동 양방향 동기화나 새 데이터 형식을 제안하지 않는다.

## 경계가 헷갈리는 문장을 구별하는 예

| 문장이 바꾸는 판단 | 소유 제안 |
| --- | --- |
| 함께 바뀌는 업무 규칙을 어디에 모으고 사용처마다 다른 정책을 어떻게 남길까 | Personal 또는 제품별 개발 가이드의 개발 판단 |
| Main이 선택한 공통 구조도 다른 구성과 비교해 보라 | 검토 수행 계약 |
| 호출자가 다음 행동에 필요한 결과를 기준으로 완료 의미를 정한다 | Personal의 일반 판단. 해당 제품에서 무엇까지 완료인지의 실제 약속은 Project/Spec |
| 현재 코드의 완료 시점과 계약·사용처가 맞는지 확인하고 불일치 근거를 반환한다 | 검토 수행. 관련 계약의 정의를 다시 복제하지 않는다. |
| 어떤 상태 표현이 모순을 줄이면서 이해·변경 비용을 감당할 수 있는가 | 앞선 후보B가 다룰 수 있는 개발 판단. 책임 확인만으로 채택하지 않는다. |
| 현재 상태 표현을 그대로 승인하지 말고 의미 있는 다른 선택이 있는지 살핀다 | 검토 수행 계약 |

Personal 공통 본문에도 “검토 결과는 ‘공통화가 부족하다’ … 에서 끝내지 않는다”는 문장이 있다. 그 핵심은 기준을 적용할 때 무엇이 실질적인 판단 근거인지를 설명하는 것이므로, ‘검토’라는 단어만으로 옮길 필요는 없다. 다만 역할별 반환 시점·상태·필수 필드·Main 처리까지 정의하면 workflow 책임이다. 짧은 목적 설명·적용 예시를 허용하되 같은 의미·조건·예외를 독립 정본으로 이중 관리하지 않는다.

외부 관점에는 두 경로가 있다. 독립 재판단·실행 경로 확인 같은 수행 요구는 workflow 후보가 되고, 개발 판단의 내용은 기존 Personal/Project에 있는지 확인해 필요할 때만 보완을 제안한다. 아직 채택하지 않은 관점도 실제 조건에 근거한 의견으로 제시할 수 있으며, 그 사실만으로 ‘우리 기준 위반’이라고 부르지는 않는다.

## 지금4번에서 결정할 수 있는 것과 후속

지금 제안하는 합의 범위는 **두 책임의 소유 질문·내용, Project/Work와 구별되는 입력, 검토 결과와 기준 갱신 후보의 관계, 외부 관점을 배치하는 원칙**이다. 책임을 먼저 정하자는 사용자 방향은 수용했지만 이 상세안 자체는 아직 추천이다.

- **01-02:** 앞선 후보A·B를 위 책임에 배치한 뒤 개발 판단의 실질 공백이 남는지, 추가·통합이 필요한지 결정한다. 보완을 기정사실로 두지 않는다.
- **5·9번:** 의견을 Main이 어떻게 처리하고 어떤 의미·근거를 반환할지 구체화한다. 지금 입출력 설명을 고정 양식으로 확대하지 않는다.
- **7·8번:** 실제로 주고받을 기준 본문·조건·원문 경로와 추가 탐색을 정한다.
- **14번·04-03:** 위 수행 계약을 기존 DEVELOPMENT/스킬/agent 중 어디에서 구현할지, 소비·갱신 연결을 어떻게 맞출지 정한다. 책임 구별만으로 새 파일·폴더·agent를 만들지 않는다.
- **15번:** 반복할 개인 기준·Project 규약·이번 작업 선택의 채택·갱신 권한과 기록을 잇는다.

실제 Personal·Project·DEVELOPMENT·스킬·04-02는 변경하지 않았다. 비교 기록과 재진입 안내만 갱신했으며 독립 리뷰나 실행 시험을 추가하지 않았다.

## 후속 — 책임 구분에 따른 외부 내용의 구체 배치

사용자는 “이 책임 구분으로 아까 가져오려던 레퍼런스 내용이랑 Personal에 둘 것과 검토 워크플로에서 정할 것을 구체적으로 나눠줘”라고 요청했다. 따라서 위 책임 구분을 이번 분류의 기준으로 사용한다. 아래 배치·문구·후속 처리는 Main의 제안이며, Personal 보완 후보 채택이나 실행 본문 적용까지 승인된 것으로 보지 않는다. 앞선 원문 대조와 내용 충분성 판단은 [coverage 기록](2026-10-22-review-criteria-coverage-and-placement.md)을 근거로 한다.

### Personal이 소유할 개발 판단

| 참고하려던 내용 | Personal이 소유할 의미·조건 | 현재 처리 제안 |

## 후속 — 독립 개선 리뷰와 Main의 추천 조정

사용자는 “그럼 개선 리뷰어 불러서 지금 상황 한번 물어보자 왜냐면 그냥 니가 단순 종합했을수도 잇고 뭐 어쨋든 이상황 전달해서 한번 물어보자”라고 요청했다. 앞서 지정한 Astra high로 새 독립 리뷰어를 호출했다. 사용자 발동 원문·가까운 정정·검토 대상과 원자료 접근점을 제공하고 Main의 문제 정의·분류도 기각할 수 있게 했다. 읽기 전용으로 수행했으며 실제 검토 workflow의 효과 시험은 아니다.

리뷰어는 현재 제안·coverage 기록, 실제 Personal·DEVELOPMENT·관련 Project·체계 지침, Matt·Lauren·Vercel의 관련 원문, 후속 Ticket과 최근 사용자 발화를 확인했다. 책임 구분이 실제 구조와 맞고 외부의 강한 처방을 사용자 목표에 맞게 조정했으므로 단순 종합에 그치지는 않는다고 평가했다. 다만 다음 세 가지를 제안했다.

1. **외부 관점의 활용과 지속 채택을 구별한다.** Personal에 없어도 이번 검토의 문제 발견·대안 탐색 단서로 쓸 수 있다. 반복 사용만으로 개인 기준이 되지는 않는다. 새 지식 저장층이 필요한 것은 아니며 기존 제안에 있는 이 관계를 배치와 실제 판단에 적용해야 한다.
2. **후보A·B의 지위를 구별한다.** A의 계약 수정 대 필요한 실패 대응은 기존 계약·수명 본문으로 상당 부분 판단 가능하다. 재시도·fallback을 명시하지 않았다는 이유만으로 실질 공백이라고 보기는 어렵다. A는 우선 기존 기준을 구체 상황에 적용하는 외부 단서로 사용하고 실제 설명 공백이 있을 때 보완을 판단한다. B의 허용 상태·전이 표현은 상대적으로 새로운 관점이지만 필수 추가는 아니다. 여러 작업에서 사용할 개인 기준으로 채택할지 별도로 판단한다. 두 관점 모두 채택 전에 이번 검토에서 사용할 수 있다.
3. **Main이 결함 없는 개선을 판단할 연결을 정한다.** Lauren의 code-quality는 적극적 구조 개선을 요구하지만 Lead 기준은 단순한 다른 접근 선호를 현재안의 구체 문제 없이 채택하지 않게 한다. 후자를 과도하게 일반화하면 사용자가 원한 대안 비교까지 사라질 수 있다. 5번에서는 계약 위반의 발생 근거와 개선안의 비교 이득·전환 비용을 구별하고, ‘현재도 동작함’이나 ‘Personal과 일치함’만으로 기각하지 않게 연결할 것을 권했다.

Main은 [Personal 공통](prototypes/development-workflow/noline-demo/context/personal/development/INDEX.md), [계약과 수명](prototypes/development-workflow/noline-demo/context/personal/development/contracts-and-lifetime/INDEX.md), [Lauren Lead 원문](../source/workflow-references/pstack/repository/skills/interrogate/references/lead-judgment.md)을 직접 대조했다. 기존 기준이 버그 없는 개선을 허용하고 계약 위반·표현 문제·제품 충돌을 이미 구별한다는 근거를 확인했다. Lauren 원문이 모든 결함 없는 개선을 금지한다는 해석은 하지 않는다. 문제는 그 필터를 우리 목적에 어떻게 적용하는가다.

**Main의 조정된 추천:** 책임 구분과 독립 재판단은 유지한다. A·B를 같은 수준의 Personal 부족분처럼 다루지 않고, A는 기존 기준의 적용·설명 공백 확인, B는 지속 판단으로의 채택 여부로 구별한다. 외부 단서 활용은 Personal 채택과 별개로 허용하고,5번에서 개선안의 실제 이득·비용을 판단하는 연결을 구체화한다. 추가 분류표·새 기준집·Personal 확장부터 진행하지 않는다.

다음 설계에서 짧게 대조할 수 있는 장면은 재시도/복구와 계약의 관계, 상태 표현과 반복 방어의 비교, 동작·기준 충족 상태에서의 명료함 개선이다. 이는 먼저 실험을 돌리자는 요구가 아니라 검토자 반환과 Main 판단의 관계를 구체화할 예시다. 모두 의무 시나리오나 새 완료 조건으로 확정하지 않는다.

리뷰와 Main의 판단은 사용자에게 제안하는 근거이며 새 사용자 합의가 아니다. Personal·Project·실행 지침·04-02는 변경하지 않았고4번 전체 완료나5번 확정으로 올리지 않았다. 실제 코드 검토 실행, workflow 효과, Noline 전체의 기준 충분성은 확인하지 않았다.

## 후속 확정 — 과도한 보류를 바로잡고4번을 마무리한다

### 사용자가 바로잡은 판단과 대화 흐름

독립 리뷰 뒤 Main은 책임 구분을 유지하면서 A는 공백이 드러날 때 보완하고 B는 지속 채택 후보로 남기는 추천을 전달했다. 사용자는 다음과 같이 지적했다.

> 흠 근데 너무 보수적인것 같다 뭔가 굳이 검증까지 해야하나? 왜냐면 불필요하다 느낌이 아니라 애매해서 검증부터 하자고 하는것 같아서 방금 의견은 어덯게 생각해? 다 가져오자는 아니지만 그렇다고 이렇게는 또 아닌것 같고

리뷰어는 별도 실행 실험을 선행하자고 요구한 것은 아니었다. 그러나 Main이 ‘실제 공백이 드러나면 보완’과 ‘후보 유지’를 다음 행동으로 강조하면서, 지금 자료·기존 구조로 판단할 수 있는 내용까지 보류하는 방향이 됐다. 사용자의 정정은 외부 내용을 전부 채택하거나 근거 확인을 생략하라는 뜻이 아니다. **중복 관리 우려를 새 내용의 채택에 앞서 부족함이나 효과를 반드시 입증해야 한다는 조건으로 확대하지 말라**는 판단으로 반영했다.

Main은 이 점을 인정하고, 기존 내용과 겹치는지 확인한 뒤에도 채택·통합·제외를 지금 결정할 수 있다고 설명했다. 판단 질문을 ‘기존에 없다는 것을 증명했나’에서 ‘어떤 판단을 더 좋게 만들고, 기존 내용과 어떻게 연결되며, 어떤 오용을 피해야 하나’로 바로잡았다. A는 기존 기준의 적용을 선명하게 하는 통합, B는 기존 책임·타입 판단을 보완하는 조건부 기준 채택을 추천했다.

사용자는 “좋아 그럼 이렇게 정하면 될까? 더 논의할건?”이라고 물었다. Main은 아래 다섯 방향으로4번을 마무리할 수 있으며, 정확한 문구·입력·권한·반환 등은 후속 구체화라고 설명했다. 이어 사용자는 “그래 앞선 논의들보고 기록 잘 작어놔줘”라고 요청했다. 이 순서에 따라 **4번의 설계 방향은 확정하고, 본문 적용·실행 세부·효과 확인은 별도 상태로 기록한다.** 앞선59개 원문 묶음 이후의 발화이며, 이 절에는 현재 대화의 핵심 원문과 Main 응답의 요지를 보존했다. 전체 대화를 새 원문 묶음으로 보존했다고 주장하지 않는다.

### 확정한 내용

| 결정 | 내용과 적용 경계 |
| --- | --- |
| Personal의 소유 | 지속해서 사용할 개발 판단의 의미·이유·조건·절충을 소유한다. 기존 명료함·책임·공통화·도구·완료·실패·수명 기준은 함께 소비하며 검토용 정본으로 복제하지 않는다. |
| A의 반영 방향 | 증상 대응과 원인·계약 수정, 필요한 복구의 구별을 기존 계약·실패 판단에 통합한다. 새 독립 원칙집을 만들거나 재시도·fallback을 일괄 금지하지 않는다. 기존 내용과 겹친다는 것은 통합 방식의 근거이며 채택 보류의 자동 사유가 아니다. |
| B의 반영 방향 | 상태·전이 표현으로 모순된 조합과 반복 방어를 줄일 수 있는지, 새 구조의 이해·변경 비용과 비교하는 조건부 기준으로 반영한다. 상태 머신·특정 타입·표현 기법을 의무화하지 않는다. |
| 검토 workflow의 소유 | 관련 기준을 소비해 주요 선택을 독립 재판단하고, 의미 있는 대안을 탐색하며, 필요한 실제 경로·사용처·근거를 확인해 Main 판단에 연결한다. 링크 안내만으로 수행 계약을 대체하지 않는다. |
| 강도와 성공 | 관련성·영향·불확실성에 맞춰 깊이를 조절한다. 발견 수·대안 수·변경을 강제하지 않고 현재안 유지도 허용한다. 결함이 없어도 개선안을 제시할 수 있다. |
| 외부 관점의 활용 | Personal에 등록되지 않은 관점도 이번 문제·대안의 판단 재료로 쓸 수 있다. 이번 활용과 지속 기준 채택은 구별한다. 외부 권고라는 이유만으로 기존 기준 위반이나 필수 변경으로 올리지 않는다. |
| 채택과 확인의 관계 | 현재 확보한 근거로 채택·통합·제외를 판단한다. 불확실하다는 이유만으로 계속 후보로 남기거나 별도 효과 검증을 모든 원칙 채택의 선행 조건으로 두지 않는다. 채택 뒤 실제 사용에서 조정할 수 있다. 실제 동작·요구 충족 검증 책임을 없앤 합의는 아니다. |

외부의 고정 행 수, 중복이면 공통화하는 자동 처방, 극적인 단순화 압박, 모든 UI 관점 일괄 적용은 그대로 채택하지 않는다. 목적·조건에 맞는 내용만 선별한다. 제품 보장은 Project/Spec, 테스트·증거 충분성은01-03, 이번 채택·기각·사용자 논의는 Main/Work 책임이라는 기존 구분도 유지한다.

### 남은 구체화와 다음 행동

- **01-02:** A·B는 이제 채택할지 처음부터 다시 묻는 후보가 아니라, 위 방향에 따라 기존 Personal에 정확한 문구·조건·연결을 반영할 후속이다. 기존 본문과 통합하며 필요할 때 대비 설명을 사용한다. 새 근거로 재판단할 수 있지만 별도 선행 실험을 자동 조건으로 만들지 않는다.
- **5번:** Main의 채택·기각·보류·사용자 논의 기준을 구체화한다. 계약 위반은 어긋난 약속과 발생 근거로, 개선안은 같은 목표·조건의 비교 이득과 비용으로 본다는 연결에서 시작한다. 상세 판단 절차는 아직 미정이다.
- **7·8·9번:** 처음 주는 기준·자료, 작업 중 추가 탐색과 맥락 요청, 반환 내용·권한을 정한다. 이번 합의를 모든 자료 완독이나 고정 출력 양식으로 확대하지 않는다.
- **6·10~15번 및01-03·04-03:** 자기 확인·호출·수정·재검토·검증 인계·모델·실행 배치·기록 갱신을 남은 항목에 맞춰 구체화한다. 이번4번 완료는 해당 항목이나 Ticket 전체의 완료가 아니다.

이번 요청에서는 합의와 형성 경과, current·Ticket·색인을 기록했다. 실제 Personal·Project·DEVELOPMENT·스킬·코드는 편집하지 않았다. 04-02의 작업은 건드리지 않았고 새 실험이나 커밋은 하지 않았다.
