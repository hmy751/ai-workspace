# 원칙·사례를 구별하고 후속 판단으로 이어지는 시안을 보완한다

2026-10-18. [직전 기록 65](2026-10-18-65-criteria-status-and-cross-ticket-refinement.md) 이후의 대화와 실제 시안 변경을 보존한다. 사용자가 요청한 시안 보완은 수행하되, 가상 제품의 코드·검사·후속 Ticket 실행을 실제 수행 결과로 올리지 않는다.

## 직전 기록 이후의 대화

65에는 후속 Ticket이 결과뿐 아니라 이번 과정도 고려해야 한다는 사용자 원문과 같은 reviewer의 추가 조언까지 보존돼 있다. 그 뒤 Main은 이전 리뷰가 역할 관계는 고려했지만 과정의 재사용·재구체화·현재 안으로 되돌리는 경로는 부족했다고 설명했다. Main 자신의 직전 제안도 책임 배분 중심이었다고 인정했다. 다음에는 기준·사례·지위를 구별한 본문, 조건별 선택 장면, 후속 재검토와 반영 경로를 함께 만들자고 권고했다. 이 문단은 직전 답변의 요지이며 원문 인용이 아니다.

이번 사용자 요청 원문:

> 그럼 직전 기록 이후 대화 내용 잘 남기고
>
> 그럼 그 방향으로 지금 시안을 보완해줘. 일반 원칙과 구체 판단 사례가 어떻게 구분되고, 이후 티켓에서 이번 과정과 근거를 어떻게 다시 참고하는지 실제 형태로 보여줘.

이는 위 방향으로 **시안을 실제 보완하라는 요청**이다. 특정 파일 분할의 최종 채택, 제품 적용, 실제 skill 설치, 관련 Ticket 전체 완료와는 구별한다.

## 어떤 이유로 이렇게 바꿨나

**원칙과 사례의 역할을 분명히 했다.** 이전 quality에는 일반 문장과 Field·Container 설명이 이어졌지만, 과거 사례인지 현재 제품의 사실인지, 사용자에게서 확인한 의도와 Main이 일반화한 후보가 무엇인지 약했다. 예전 본문의 “Field는 제목·입력·설명·오류의 배치와 복수 입력 구성을 사용처에서 바꿀 수 있도록 부품을 제공한다”는 설명은 현재도 참고하지만, 이제는 사례에서 관찰 시점·대상·의도·열린 선택을 함께 읽는다. 현재 shop-web 구조는 Project 설명의 가정으로 구별한다.

원칙 본문은 여러 상황에서 재사용할 판단을, 사례는 그 판단의 조건과 근거를 소유한다. 지위는 별개의 구별이다. 지금의 기준 후보를 보편적 진리로 올리지 않으며, 이미 요구인 제품 계약도 후보와 같은 참고 의견으로 낮추지 않는다. 사례의 수나 사용 빈도가 늘었다는 이유만으로 자동 채택하지 않는다.

**사례의 상세는 따로 두고 핵심 조건은 원칙 가까이에 남겼다.** Field의 해석 정정과 Container의 다른 선택 조건은 후속 02·03에서도 독립적으로 다시 읽을 재료여서 한 사례 파일로 묶었다. 원칙 본문에는 화면 합성과 상태 연결은 별개의 선택이며 같은 형식·정책을 함께 제공할 수도 있다는 핵심 대비를 남겼다. 상세를 보지 않으면 원칙 자체가 오독되는 구조를 피하려는 선택이다. 원칙 하나당 파일·사례 하나당 파일을 만드는 규칙은 아니다.

**읽기 안내의 반복을 줄였다.** 이전에는 AGENTS의 직접 기준 링크, Project의 자료 표, develop의 조건 표에 안내가 겹쳤다. 이번에는 Project가 작업 단서별 안내를 소유하고 진입 지침과 역할 절차가 참조하게 했다. “계약을 바꿈”이라는 조건도 “계약을 지키는지 검토함”까지 보완했다. 이는 [64의 지적](2026-10-17-64-applied-format-improvement-review.md)을 시안에 대입한 선택이며 실제 발견율·읽기 비용이 개선됐다는 측정은 아니다.

**후속 Ticket이 다시 선택하는 장면을 붙였다.** “03과 연결”이라는 이름만 남기면 어떤 판단에 무엇을 가져갈지 알 수 없다. 03이 원칙과 사례를 어느 정도 가까이 둘지 결정할 때, [35의 의도적 분리와 이분법 정정](2026-10-13-35-field-composition-and-design-flexibility.md), [37의 공통 형식 필요](2026-10-14-37-infinite-scroll-container-and-hook-comparison.md), [57의 일반 가이드·질문 의도](2026-10-16-57-criteria-organization-and-guiding-questions.md), [61의 외부 자료 선택 이유](2026-10-17-61-reference-comparison-for-format-design.md), [62](2026-10-17-62-criteria-format-prototype.md)에서 [63](2026-10-17-63-applied-criteria-project-example.md)으로 바뀐 이유 중 필요한 근거를 선택한다. 그 결과가 기존 원칙의 설명량·사례 연결·읽기 입구를 바꿀 수 있음을 실제 반환문으로 보여 준다.

후속 장면의 첫 작성은 핵심 대비를 원칙 가까이 두는 안이어서 이번 현재 시안의 선택과 충분히 달라지지 않았다. Main은 후속 재판단이 실제로 다른 선택을 만드는 모습이 필요하다고 보았다. 최종 장면에는 ‘작은 Project의 두 기준을 UI 작업에서 짧은 사례와 함께 읽고 같은 담당자가 관리한다’는 새 조건을 가정했다. 그 조건과 기존 과정 근거를 함께 보아 **한 문서의 일반 원칙·조건별 사례 절로 합치는 후속안**을 반환하게 했다. 지금 별도 파일로 구별한 안을 정답으로 고정하지 않는 모습을 보여 주려는 보완이며, 해당 사용 빈도·비용을 측정하거나 통합을 채택한 것은 아니다.

외부 자료는 기존 비교61을 사용했다. Matt의 원칙·질문·사례 표현, writing-for-agents의 자료 정체성과 읽는 조건, Vercel의 기준·근거·작업 연결, pstack의 적용 조건·이유·질문, Anthropic의 필요한 구체성과 반복 점검은 형식 판단의 재료다. 이번 파일명·분리·역할 흐름은 이 자료들의 공통 정답이 아니라 사용자 요청·Spec·리뷰와 조합한 Main의 시안이다. 새 외부 조사나 특정 자료의 현행 판본 확인은 수행하지 않았다.

## 후속 Ticket이 받는 현재 결과와 바꿀 수 있는 것

01-02에는 보완 본문·선택 장면을 현재 비교 대상으로 연결한다. 03·02·01-01·04-03·01-03·07에는 각 판단을 시작할 때 이 시안과 필요한 과정 근거로 진입하도록 연결한다. 후속 Ticket의 전체 수행을 완료한 것은 아니다.

후속 담당자는 파일을 그대로 이식할 의무가 없다. 실제 읽기 비용과 제품 맥락, 역할·도구·기록 조건을 보고 원칙의 추상도, 사례 요약, 파일 분할, 전달량까지 다시 판단할 수 있다. 변경된 현재 의미는 그 내용의 정본에, 전체 관계 변화는 Spec에, 바뀐 이유와 버린 대안은 작업 기록에 남긴다. 35·37의 발화나 62·63의 당시 제안을 새 결론으로 고치지 않는다.

**계속 열려 있는 선택:** 이 정도 상세를 같은 파일에 둘지, 기준이 늘면 어떻게 찾게 할지, 실제 기존 skill에 어떻게 연결할지, 누가 어느 범위에서 기준을 채택할지, 기록 갱신과 효과 확인을 어떻게 운영할지. 다음 논의에서는 이번 실물에서 불편하거나 오독할 지점을 집어 조정하고 관련 Ticket의 조건이 드러나면 함께 수정한다. 지금 다시 전체 원칙을 완성하거나 원본 template 수정을 시작할 필요는 없다.

## 보존과 확인 범위

63~65는 당시 산출물·리뷰·제안의 이력으로 유지한다. 63이 연결한 prototype 경로의 본문은 이번에 보완됐으므로 그 기록에 후속 변경 안내를 붙이고, 변경 전 핵심 표현과 이번 이유는 위에 보존했다. 과거9파일 배치를 이미 채택한 운영안으로 읽지 않는다.

이번 실제 수행은 문서·전달 예시 작성과 연결 확인이다. 예시 안의 제품 변경·검사 통과·후속03의 반환은 가정이며 실제 수행 이력과 섞지 않는다. 구체 확인 결과는 아래에 덧붙인다.

별도 읽기 검토자는 현재 시안과35·37·57·61·65, Spec·관련 Ticket을 직접 대조했다. 원칙 후보와 제품 계약, 실제 이력과 가상 결과, FIELD-01 초기 입력과 역할 절차, 후속 재판단의 근거·반영 위치가 구별됨을 확인했다. 작성 중의 current 문구와 실제 보완 상태가 어긋난 지적은 갱신 후 재확인했고, 남아 있던 01-01의 ‘현재 가상 사례’는 ‘앞선 HTTP-07 사례’로 좁혀 최신 Field 장면과 구별했다. 이는 문서 의미 확인이며 실제 작업자의 사용 성공 검증이 아니다.
