## 13. 누가 어떤 실행과 맥락으로 일하는가 — 확정

### 역할 수와 모델의 기본값

Main은 사용자와 대화하는 현재 세션이다. 별도 Lead를 만들거나 Main의 모델을 이 설계가 바꾸지 않는다. 구현은 Main이 직접 하거나 범위가 분명한 구현 서브에게 맡긴다. 별도 개선 검토가 필요한지는 확정10번의 선택 성격·영향으로 판단하고, 필요한 경우 **검토자 한 명**을 기본으로 둔다. 이후 요구·계약 충족을 판단하는 검증자는 구현 중 개선 검토자와 구별한다. 네 역할을 항상 네 동시 실행으로 만들지는 않는다.

서브의 확정한 초기 기본 설정은 **GPT-6.1-sol / medium**이다. 이는 사용자의 “프론티어 모델보다 한단계 낮은걸로… 미디엄 정도”라는 선호를 현재 제공되는 일반 작업 모델에 대응시킨 Main의 제안이다. 공식 등급표에서 정확히 한 단계 아래임을 입증한 주장이나 모델별 품질 실험 결과는 아니다. 구현·개선 검토·검증 모두 이 출발점을 쓰되, 판단 난도가 커지면 같은 모델의 effort를 높이거나 Main이 직접 맡고 필요하면 더 강한 모델을 고른다. 중요한 계약 충돌·여러 책임을 가로지르는 설계·같은 전제의 반복 실패는 재배치 근거다. 단순 자료 수집이 아니라는 이유만으로 매번 가장 높은 설정을 쓰지도 않는다. 자료 누락·접근 제한·낡은 전제가 원인이면 그 입력을 먼저 보완한다. 필요한 근거가 있는데 비교·종합이 부족하면 판단 배치를 바꾸고, 단지 탐색량이 많다면 범위 분할·effort를 조정한다. 모델 교체로 입력 문제를 감추지 않는다.

고정적으로 두 번째 리뷰어를 더하지 않는다. 서로 다른 전문 판단이 필요하거나 한 사람이 다루기 어려운 범위를 나눌 실익이 있을 때 추가한다. 같은 자료로 같은 질문을 반복한 동의를 독립 근거 수로 세지 않는다. 병렬 작성은 겹치지 않는 책임·파일 또는 격리된 작업 공간이 필요하며 통합 계약은 Main이 확인한다. 단일 작업은 같은 checkout에서 순차 작성하는 것으로 충분할 수 있다.

이번13~15번 **설계 개선 리뷰**는 앞선7~12번과 같은 GPT-6-astra high 두 명을 사용한다. 향후 개발 운영의 서브 기본값과 이번 설계를 끌어올리는 검토 배치는 별개다.

### 새 대화와 기존 담당자를 선택하는 기준

| 상황 | 기본 선택과 이유 |
| --- | --- |
|첫 개선 검토|새 서브, 부모 대화 전체 미상속. 목표·현재 계약·결과와 필요한 원자료를 직접 받으며 Main의 긴 사고 과정을 기본 주입하지 않는다.|

|채택 의견의 수정|11번에 따라 원 구현자가 기본이다. 해당 대화를 재사용할 수 있으면 최신 결과·변경 지시·채택 이유를 갱신해 이어간다. 부재·복구 비용·반복 전제 문제로 바꾸면 같은 역할을 새 실행자가 인수한다.|

새 대화 자체가 편향 제거를 보장하지 않는다. 기준 문서·현재 구현에도 이전 선택이 있다. 관련 Personal을 감추지 않고, 목표·계약·관찰·작성자의 해석을 구별하며 Main의 질문·자료 선택도 재판단할 수 있게 하는7~8번을 유지한다. 기존 담당자에게도 “아까 것 고쳐”만 보내지 않는다. 이전 전달 이후 목표·계약·대상·권한이 달라졌다면 무엇이 바뀌었고 이전 판단·검사 근거 중 무엇을 그대로 사용할 수 없는지 함께 전달한다. 담당자는 영향받는 근거를 다시 읽고 확인한다. 재사용과 새 담당자 인수 모두에 적용하며, 별도 무효화 장부나 모든 자료의 재독을 요구하지 않는다.

### 짧은 의뢰문 뒤에 실제로 무엇이 전달되는가

Main은 현재 tool의 모델·effort·대화 상속 옵션과 적용되는 root/local 지침을 확인하고 의도한 역할을 실행할 수 있는 방식으로 호출한다. **현재 이 세션의 도구에서는** `fork_turns: none`일 때 모델·effort를 명시할 수 있고, 전체 상속은 부모 설정을 이어받는다. 이는 현재 도구의 계약이며 모든 Codex·Claude 실행에 공통인 필드로 적지 않는다. 모델·옵션이 지원되지 않으면 동일 설정으로 실행했다고 보고하지 않고 가능한 대안과 바뀐 조건을 드러낸다.

실제 입력은 의뢰문만이 아니다. 자동 제공되는 지침·역할 설정·스킬 안내, 선택한 대화 이력, 서브가 읽는 본문과 도구 결과를 함께 고려한다. 새 대화에 root 지침까지 없다고 가정하지 않는다. Main이 볼 수 없는 내부 주입이나 정확한 토큰 수를 추측해 보고하지 않으며, 설치·최초 적용 시에는 실제 노출된 지침과 읽기 흔적으로 예상과 차이를 확인한다. 일상 위임마다 입력량 측정표를 만들 필요는 없다. 이때 자료 열람·호출 성공뿐 아니라 관련 기준을 실제 사용처에 적용했는지, 의미 있는 유지·개선 판단을 제공했는지, Main이 같은 조사를 다시 해야 했는지도 대표 작업에서 살핀다. 성능 실험을 별도 선행 사업으로 만들지 않고 실제 작업에서 판단을 바꾼 부족을 기존 기록에 남긴다.

관련 문서는 Main이 **왜 읽는지와 실제 위치**를 함께 주고 수행자가 직접 읽는다. 여러 파일에 흩어진 요약으로 정본을 다시 만들지 않는다. 대화에만 있는 최신 결정이나 문구 자체가 판단 근거인 정정은 최소 원문·앞뒤 의미를 의뢰에 담고,15번에 따라 지속할 내용은 기존 Owner에도 연결한다. 직접 접근할 수 없는 자료는 필요한 원문을 중계하고 그 한계를 밝힌다.

### 실제 의뢰문의 구성 예

아래는 현재 로그인 데모에 넣을 내용을 보여주는 예다. 제품 작업을 지금 배정하거나 데모의 과거 상태를 최신 결과라고 선언하는 지시가 아니다. 실제 호출에서는 경로·판본·권한·근거를 현재값으로 채운다.

> 역할은 구현 단계의 독립 개선 검토다. 로그인 성공과 후속 화면 준비를 사용자가 이해하고 호출자가 정확히 다룰 수 있는 결과를 목표로, 현재 선택과 더 나은 선택을 실제 사용·변경 부담으로 비교하라. Main이 붙인 질문과 선택 이유도 검토할 수 있다.
>
> 먼저 해당 Project root 지침과 development 검토 상세를 적용한다. Work의 Spec·현재 Ticket에서 이번 요구·보존 조건을, Personal의 이름·완료 본문에서 판단 기준의 의미·조건을, Project 인증 계약에서 성공·실패·완료 약속을 읽는다. 아래 연결에서 시작하고 필요하면 관련 본문·원문·사용처를 더 찾아라.
>
> 대상은 Main이 명시한 판본의 실제 구현과 관련 호출자다. diff의 기준과 미커밋 변경 포함 여부, 구현자가 확인한 검사·미확인, 현재 선택 이유와 비교한 대안을 함께 받는다. 선택 이유는 검토할 주장이다. 구현자가 권한 있는 계약으로 제시한 조건도 출처와 대조한다.
>
> 읽기·분석·이번 범위에 허용된 검사와 보고를 맡는다. 제품·정본 수정은 배정하지 않는다. 의견에는 실제 조건·근거·이득·비용·판단을 바꿀 미확인을 연결하고, 유지가 더 낫다면 이유를 설명하라. 접근할 수 없거나 Main의 선택이 필요한 부분은 필요한 원문·판단·다음 행동을 구체화해 반환하라.

실제 연결할 데모 본문은 [Work memory](prototypes/development-workflow/noline-demo/context/work/workspaces/001-login-completion-names/current/memory/index.md), [Ticket](prototypes/development-workflow/noline-demo/context/work/workspaces/001-login-completion-names/current/memory/tickets/01-authentication-completion.md), [Personal 이름·완료](prototypes/development-workflow/noline-demo/context/personal/development/naming-and-completion/INDEX.md), [Project 진입](prototypes/development-workflow/noline-demo/context/project/README.md), [결과 진입](prototypes/development-workflow/noline-demo/context/work/workspaces/001-login-completion-names/output/index.md)에서 찾는다. 경로를 아는 것과 본문을 이해·적용한 것은 다르다. 반환은 실제 조건·사용처·판단 근거로 그것을 보여야 하며, 매번 읽은 파일 목록을 전수 보고하도록 만들지는 않는다.

구현자의 입력에는 쓰기 책임과 완료 조건을 더하고6번의 자기 설계 판단·검사·인계를 요구한다. 수정자는 채택한 문제·방향·기대 이득·보존 조건·남은 선택을 받는다. 검증자는 최신 결과에 대한 요구·주장과 근거 접근점을 받으며 “리뷰가 끝났으니 통과할 것” 같은 예상 판정을 받지 않는다. 동일 brief를 모든 역할에 복사하지 않는다.

검토 대상이 바뀔 수 있으면 작업 범위의 파일·판본을 고정하거나 변경분을 구별한다. commit되지 않은 결과도 검토할 수 있어야 하므로 HEAD만으로 판본을 대표하지 않는다. 다른 작업의 편집을 임의로 되돌리거나 전 작업을 정지시키지 않는다. 읽기 중심 역할을 지시한 것과 별도 read-only sandbox가 강제되는 것은 다르며 실제 권한은 실행 환경을 따른다.

## 14. 기존 지침과 스킬을 어떻게 연결하는가 — 확정

### 흐름은 development, 내용은 기존 Owner가 소유한다

현재 실행 prototype은 [development](prototypes/development-workflow/skills/development/SKILL.md), [work-discussion](prototypes/development-workflow/skills/work-discussion/SKILL.md), [explain](prototypes/development-workflow/skills/explain/SKILL.md)이다. 아래 맥락 스킬들은 [기존 Noline 보존판](../source/noline-baseline/.claude/skills/)에 있으며 현재 prototype에 모두 설치돼 있다고 가정하지 않는다. 현행 explain 통합을 반영하고 이전 브리핑·복구 스킬을 새 active 경로로 다시 연결하지 않는다.

| 판단이 생기는 조건 | 연결할 기능과 경계 |
| --- | --- |
|일반 작업 시작·재개|대상 root의 재진입 안내로 현재 Workspace·목표·상태·결과를 복구하고 development가 이번 요청에 맞는 남은 일을 잇는다.|
|검토 등 한정 위임|적용 지침과 맡은 일에 필요한 목표·계약·결과를 읽는다. 독립 Workspace 주인이 된 것처럼 모든 current·역사·Ticket을 다시 펼치거나 active 상태를 바꾸지 않는다. 상위 지침의 필수 읽기를 의뢰문으로 생략시키지는 않는다.|
|관련 Project 본문이 아직 선택되지 않았거나 새 질문을 다루기 어려움|read-project-context가 기존 읽기 기준에 따라 본문을 고르고 이해·적용한다. 이미 유효한 이해가 충분한 단순 수정마다 다시 호출하지 않는다. 읽기는 갱신 권한을 만들지 않는다.|
|무엇을 만들지의 선택·완료 장면이 불충분함|Main이 일반 작업 대화에서 필요한 선택을 구체화한다. work-discussion은 사용자의 명시 호출 조건을 유지하며 자동 발동하지 않는다. 기술적인 세부 구현 판단마다 사용자 논의를 다시 열지 않는다.|
|결과·새 조건이 원래 방법의 전제를 흔듦|reconsider-work로 목표·선택 이유·실제 결과·의존 작업을 대조한다. 국소 구현 오류는 수정·검사로 처리하고 매 검토 의견을 상위 재설계로 확대하지 않는다.|
|결과·개념·코드의 관계와 이유를 설명할 필요|explain을 사용한다. 무엇을 확인하고 어떤 결과를 선택할지는 Main이 맡으며 설명 스킬이 전체 개발 책임을 대신하지 않는다.|
|제품의 지속 의미·계약·현재 사실이 달라짐|update-project-context를 해당 Project 관리 계약과 연결한다. 이번 Ticket의 변경·개인 기준 사용만으로 Project 공통 규약을 만들지 않는다.|
|독립한 새 작업 공간의 생성·전환이 요청됨|create-context-workspace를 대상의 실제 구조·운영 계약에 맞춰 사용한다. 서브 호출·단계 전환·작은 수정마다 Workspace를 만들지 않는다.|

### 실행 본문에 반영할 구체 범위

한정 위임의 진입 범위는 의뢰문만으로 만들지 않는다. 대상 root·Work 진입 지침에서 일반 재개와 한정 위임의 조건을 함께 맞춘다. 현재 [demo root](prototypes/development-workflow/noline-demo/AGENTS.md)·[Work 지침](prototypes/development-workflow/noline-demo/context/work/AGENTS.md)은 일반 Workspace 복구를 안내하므로 후속 적용 때 이 구분을 반영할 대상이다. 적용 전에는 기존 필수 지침을 따르며 입력이 이미 한정됐다고 주장하지 않는다. 한정 위임에서도 적용 지침·목표·보존 계약·관련 결과는 읽고 필요한 근거를 스스로 확장할 수 있어야 한다.

development 공통 본문에는6번의 맥락 이해·적용·첫 완성·자기 확인·인계와11~12번의 수정·종료·검증 연결을 통합한다. 현재 “수정 담당은 아직 미정”인 설명은 원 구현자 기본과 조건부 재배정으로 고친다. 기존 `references/review.md`에는7~10번의 입력·탐색·권한·호출과 재검토 관계를 반영한다.13번의 도구별 설정은 반복 변경될 값이므로 별도 실행 상세가 필요하면 development 내부에 두고 공통 본문에서 호출 조건으로 연결한다. 파일명을 먼저 늘리거나 전역 reviewer agent를 새로 설치하지 않는다.

Personal·Project·Work의 기준 내용과 관리 계약은 해당 Owner에 남긴다. 호출 스킬은 적용할 조건과 수행 관계를 소유한다. 역할을 지시하는 prompt만 따로 늘려 같은 요구를 여러 곳에서 고치게 만들지 않는다. 여러 workflow에서 안정적으로 반복되는 독립 역할이 확인될 때 별도 agent 승격을 검토한다.

현재 work-discussion의 [직접 호출 경계와 형성 이유](prototypes/development-workflow/skills/work-discussion/_background/context.md)를 유지한다. development의 자동 연결처럼 읽히는 문장은 그 호출 조건에 맞춰 고친다. 호출 방식 자체를 바꾸려면 별도 의미 변경으로 비교해야 하며 이번 추천에 자동 호출 채택을 숨겨 넣지 않는다. 현재 work-discussion의 결과 효력·기록 문장에도 Maintain 전제가 있으므로 실제 작성자를 지정하는 운영 계약과 맞춘다.

기존 read-project-context는 질문에 따른 선택·유효한 맥락 재사용·읽기와 쓰기 구별을 유지할 수 있다. reconsider-work의 판단 방법도 유지하되, Main 반환 이후 기록을 자동 Maintain에 연결하는 운영 문장은 대상 환경과 맞춰야 한다. update-project-context의 오래된 경로·layer 이름과 create-context-workspace의 Recover·Verify·활성화 명령은 현재 대상의 실제 계약을 확인하고 이식한다. 보존판의 명령을 이번014에 바로 실행하지 않는다.

현재014는 자동 Maintain이 비활성이며 demo도 수동 관리다. 따라서 이 환경의 실행 연결은 Main의 직접 반영을 사용한다. 자동 Maintain이 실제 연결된 다른 환경에서는 그 계약에 따라 한 작성자에게 맡기되 전달·접수·실제 반영을 구별한다. 이 차이를 이유로 현재 Maintain을 재설치하거나 Work 구조·machine 계약을 새로 만들지 않는다.

후속 적용 확인은 단순 호출·파일 존재 검사에 그치지 않는다. 일반 재개, 한정 검토, 단순 수정, 목표 전제 변경, 제품 계약 갱신의 대표 장면에서 필요한 본문을 선택하고 원래 과제로 돌아오는지 본다. 같은 실제 결과를 일반 재개와 한정 검토에 각각 주었을 때 필요한 계약·사용처에 도달하면서 역할 밖의 진행·갱신 책임을 떠맡지 않는지도 본다. 이전 브리핑 경로·중복 작성·없는 Maintain 의존이 남지 않았는지도 확인한다. 이 문서 작성으로 해당 수행을 이미 확인했다고 기록하지 않는다.

## 15. 판단을 어디에 누가 남기는가 — 확정

### Main이 선택과 실제 결과를 연결한다

검토자는 의견·직접 근거·확인 한계·열린 질문을 반환한다. 구현자·수정자·검증자도 실제 작업과 근거를 Main에 돌려준다. Main은 중요한 의견의 채택·보류·기각 이유, 실제 변경과 확인, 기대 이득·새 부담과 남은 책임을 대조한다. 서브가 반환했다고 문서가 갱신됐거나 제안이 채택됐다고 취급하지 않는다.

기록은 의미 있는 선택·예상과 다른 결과·인계에 필요한 근거가 생길 때 남긴다. 모든 작은 의견·명령·턴을 영구 장부로 만들지는 않는다. 상태를 구별할 필요가 있을 때 기존 Ticket·record에서 “의견만 있음 / 채택 / 수정 반영 / 확인 결과”를 문장으로 드러낸다. 새 machine 상태나 별도 승인 단계를 만들지 않는다.

| 달라진 의미 | 실제 반영 Owner와 담당 |
| --- | --- |
|이번 범위의 설계·선택·진행·확인·남은 일|해당 Ticket. Main이 종합하고 이 환경에서는 직접 반영한다. 상세 비교·검사 근거는 필요한 record에 둔다.|
|작업 전체의 목표·공통 요구·제약·핵심 가정|Spec 및 의존 Ticket. 중요한 목표·제약 변경은 기존 권한 있는 선택에 근거한다. 단순 구현 선택을 모두 Spec으로 올리지 않는다.|
|다음 실행자가 알아야 할 현재 상태·행동|Workspace current/state와 필요한 memory. 과거의 모든 승인 경과를 현재 지시처럼 늘어놓기보다 지금 유효한 의미를 먼저 둔다.|
|현재 선택된 결과와 실제 위치|output/index. 실제 결과를 가리키고 설계·적용·확인·수락의 상태를 구별한다. 결과물을 복제하지 않는다.|
|제품에서 계속 유효한 계약·규약·현재 구현 사실|Project의 기존 본문과 관리 계약. Main 또는 배정된 갱신 담당자가 직접 근거와 권한을 확인해 반영한다. 현재 구현만으로 새 제품 약속을 정하지 않는다.|
|여러 작업에 가져갈 개인 기준의 의미·적용 조건|Personal의 기존 본문·형성 자료·갱신 기준. 이번 대안 채택과 지속 개인 기준 변경은 별도 판단이다. 개인 기준의 소유와 기존 위임을 따르고 매번 새 승인 의무를 추가하지 않는다.|
|절차·역할·읽기 조건 자체의 수정|해당 skill 본문·실행 상세·형성 자료 및 실제 호출자. 제품 사례를 일반 절차의 고정값으로 올리지 않는다.|

중요한 선택이 바뀌면 current와 Ticket의 해당 현재 문장을 새 의미로 고친다. 대체된 다음 행동·미정·승인 상태는 필요한 record에 보존하고 현재 본문에 같은 무게로 누적하지 않는다. 현재 목표에서 왜 이 일을 다음에 하는지, 남아 있어도 지금 중심이 아닌 것은 무엇인지 이해할 수 있게 쓴다. 작업 중심·책임·중요 전제가 바뀐 대표 재개 장면에서는 이 관계를 복원할 수 있는지 확인한다. 매 갱신의 독립 리뷰나 새 시험을 의무화하지 않는다.

같은 내용을 여러 Owner에 통째로 복사하지 않는다. 예를 들어 로그인 완료 표현만 바꾸고 실제 약속은 같으면 코드·해당 Ticket·필요한 현재 구현 설명을 맞춘다. 외부 호출자에게 약속하는 완료 시점까지 바꾸기로 했다면 Project 계약과 관련 Spec·Ticket·검증 조건까지 다시 맞춰야 한다. 검토자가 제안한 표현이 좋았다는 사실만으로 Personal의 일반 규칙이 바뀌지는 않는다. 일반 기준의 적용 조건을 보완할 근거가 드러났다면 별도로 판단한다.

### 실제 갱신과 다음 실행의 입력을 맞춘다

목표·계약·기준의 적용 조건이 바뀌면 Main은 그 의미를 이미 사용하는 담당자·기존 결과·확인 근거에서 영향을 받는 부분을 찾는다. 정본 수정과 함께 관련 실행자에게 바뀐 뜻과 필요한 재판단 범위를 전달한다. 이전 검사의 실행 사실은 남기되 새 계약을 입증하는지 구별하고, 반환된 의견도 변경 후 조건에 그대로 유효한지 본다. 단순 표현 수정이나 무관한 실행까지 모두 중단·재검토하지 않는다.13번의 최신 입력 전달과12번의 재검토 판단을 여기서 연결한다.

현재 설계에서는 Main이 기록·정본 갱신을 맡으며 자동 Maintain은 연결하지 않는다. Main은 대상 root 지침과 Work·Project·Personal의 진입·관리 계약을 확인해 각 구성과 소유 범위·갱신 방법을 이해하고 따른다. 관련 내용이 이미 유효하게 확보돼 있으면 불필요하게 전부 재독하지 않는다. 추후 Main의 수행을 스킬로 보완할 가능성은 메모로 남기며, 스킬의 생성·구성·시점이나 Maintain 연결은 아직 결정하지 않았다. 이미 자동 Maintain이 있는 다른 환경의 계약은 그 환경을 다룰 때 별도로 확인할 사항이며 현재의 후속 연결 계획으로 취급하지 않는다. Main은 서브 대화가 자동 전달된다고 가정하지 않고 채택 의미·근거·미확인과 접근점을 연결한다. 다음 담당자·새 세션이 문서를 입력으로 사용하기 전 필요한 변경이 실제 반영됐는지 확인한다. 비동기 접수·파일 쓰기 요청만으로 준비 완료를 선언하지 않는다.

반영이 막히면 대화에서 확인한 최신 결정을 현재 과제에 명시해 독립적으로 가능한 일은 이어가되, 파일이 아직 과거 상태임을 밝히고 갱신 책임·대상을 남긴다. 같은 파일에 다른 작성자가 작업 중이면 범위를 조정하고 최신 변경을 읽어 합친다. 이미 적용된 사용자 변경이나 다른 작업을 이전 내용으로 덮어쓰지 않는다.

문구·순서·뉘앙스가 판단 근거이면 필요한 원문 발췌나 판본을 record에 보존한다. 안정된 배경 자료는 링크로 충분할 수 있다. 긴 근거는 한곳에 보존하고 현재 문서는 유효한 선택·이유·남은 행동을 직접 설명한다. source의 과거 원문을 새 결론으로 고치지 않는다. 문서 반영 확인은 역할 수행 효과·전체 요구 충족·사용자 수락과 구별한다.

## 후속 확정 — 13번 실행 구성·실제 맥락 전달

사용자는 개선 리뷰·레퍼런스를 반영한13번의 모델·역할 배치, 대화 상속/재사용, 실제 원자료 읽기와 변경된 전제·근거의 전달을 설명받고 다음과 같이 요청했다.

> 좋아 그럼 13번도 이렇게 확정하고 적을 거 정리해줘. 그다음 14번도 개선 리뷰랑 레퍼런스 반영한 최종안으로 설명해봐

**13번을 확정·마무리한다.** Main은 현재 대화이며 서브는 GPT-6.1-sol medium을 초기 기본값으로 둔다. 개선 검토자는 필요한 경우 한 명부터 시작하고, 추가 전문 판단·독립 범위의 실익이 있을 때 늘린다. 구현·개선 검토·검증의 역할을 구별하되 항상 네 명을 동시에 실행하지 않는다. 입력 누락·접근 제한·낡은 전제와 탐색 물량·판단 역량의 부족을 구별해 입력 보완·범위 분할·effort 조정·담당자 재배치를 선택한다.

첫 개선 검토는 새 대화에 부모 이력 전체를 상속하지 않는 것을 기본으로 한다. 관련 Personal·Project·요구·실제 결과·확인 근거는 직접 읽게 하며 기존 선택 이유도 검토할 주장으로 전달한다. 원 구현자 수정과 필요할 때의 기존 검토자 재사용을 유지하고, 새로운 관점·전문성·반복되는 전제 문제에 따라 새 담당자로 바꿀 수 있다. 최종 요구·계약 검증은 별도 판단으로 연결한다.

재사용·새 인수 모두 최신 지시뿐 아니라 바뀐 목표·계약·대상·권한과 그대로 사용할 수 없는 이전 판단·검사 근거를 함께 전달한다. 영향받는 자료와 근거만 다시 확인한다. 짧은 의뢰문 외에 자동 지침·실제 읽는 본문도 입력에 포함되므로 한정 위임의 상위 진입 조건까지 맞춘다. 구체적인 지침·스킬 편집 관계는14번에서 이어 논의한다.

이번 선택은 사용자 모델 선호와1~12번 합의, Matt의 정본·판본 연결, pstack의 역할별 배치·최신 과제 전달, Vercel의 질문별 자료 선택, 독립 검토 기준을 비교한 안에 두 개선 리뷰의 보완을 종합한 것이다. 고정 두 리뷰어·매 수정 새 대화·전체 입력 장부를 가져오지 않았다. 모델 등급의 정확한 차이·실제 수행 효과를 입증한 것으로 취급하지 않는다.

**현재1~13번 설계 확정,14~15번은 추천안이다.** 이번에는 승인 근거·현재 상태·다음 행동을 갱신했으며 실행 스킬·모델 설정 적용이나 새 실험·커밋은 수행하지 않았다. 다음은14번 기존 지침·스킬 연결의 설명과 사용자 논의다.


## 후속 확정 — 14번 기존 지침·스킬 연결

사용자는 개선 리뷰·레퍼런스를 반영한14번의 책임 배치와 조건별 연결, 실제 호출·기록 담당의 충돌 보완을 설명받고 다음과 같이 요청했다.

> 좋아 그럼 14번도 이렇게 확정하고 적을 거 정리해줘. 그다음 15번도 개선 리뷰랑 레퍼런스 반영한 최종안으로 설명해봐

**14번을 확정·마무리한다.** development가 전체 개발 흐름과 담당자·맥락·결과의 연결을 조율하고, Personal·Project·Work의 기준 내용과 관리 계약은 기존 Owner가 소유한다. 관련 기능을 질문과 적용 조건에 따라 선택하고 원래 과제로 돌아오며, 모든 스킬을 고정 순서로 호출하지 않는다.

read-project-context는 필요한 본문 선택·이해·적용을, reconsider-work는 결과가 원래 방법·가정을 흔들 때의 재판단을 연결한다. work-discussion은 사용자의 직접 호출 조건을 유지하고 일반적인 목표·완료 선택의 구체화는 Main이 맡는다. explain은 현재 통합된 설명 진입점으로 사용한다. update-project-context는 지속할 제품 의미·계약·현재 사실이 달라진 경우, create-context-workspace는 독립 작업 공간의 생성·전환이 요청된 경우에 대상의 실제 계약에 맞춰 연결한다.

한정 위임과 일반 작업 재개는 의뢰문뿐 아니라 root·Work 진입 지침에서도 구별한다. 필요한 목표·계약·결과와 적용 지침을 읽고 추가 탐색할 수 있게 하되, 한정 담당자가 Workspace 전체 진행·갱신을 떠맡게 하지 않는다. 기존 필수 지침을 무시하는 예외를 만들지 않는다.

개선 리뷰에서 확인한 work-discussion의 직접 호출 조건과 development 호출 문장의 충돌, active work-discussion·보존 reconsider-work의 Maintain 전제를 후속 편집 범위에 포함한다. 현재014·demo는 Main이 직접 문서를 반영하며, 자동 Maintain이 연결된 환경은 그 운영 계약을 따른다. 전달·접수와 실제 반영을 구별하고 중복 작성을 피한다. 이 결정이 현재 Maintain 재설치를 뜻하지 않는다.

이 선택은 Matt의 정본 접근, Vercel의 조건별 자료 선택, pstack의 작업별 기능 연결과 shared 독립 역할 배치를 실제 스킬·형성 이유와 대조한 안이다. 외부의 고정 호출·전역 역할 구성을 그대로 가져오지 않았고, 기존 직접 호출 의도를 자동 호출로 바꾸지 않았다. 후속 적용에서는 development 공통·검토 상세와 실제 호출자·진입 지침·환경 의존 기록 문장을 함께 맞추고 대표 장면에서 역할 범위·자료 선택·원래 과제 복귀·실제 반영을 확인한다.

**현재1~14번 설계 확정,15번은 추천안이다.** 이번 요청은 승인 근거·현재 상태 정리와15번 설명이며 실제 스킬·root 지침·설정 편집, 새 실험·커밋은 하지 않았다. 다음은15번의 판단 기록과 정본 갱신 책임을 논의한다.


## 후속 확정 — 15번 기록·정본 갱신과 Maintain 관련 메모

사용자는15번 설명 뒤 기록 책임과 추후 보완 방향을 다음과 같이 확인했다.

> 음 근데 maintain 얘기했었는데 연결은 안하고 추후 스킬로 보완할까 생ㄱ가인데 어쨋든 main이 맡는거니까 딱히 방향성이 내가 생각한거랑 달라보이진 않아서 괜찮아 보여 그래도 뭐 지침이나 이런건 따를거고 그래야 work project등의 구성을 알고 할테니까 일단 메모정도 하고 맞다면 15번도 합의하고 기록하자

Main은 현재 책임이 Main에게 있다는 점에서 방향이 같다고 확인했다. Main이 직접 갱신한다는 것은 구성·관리 규칙을 임의로 정한다는 뜻이 아니다. 대상의 root 지침과 Work·Project·Personal의 진입·관리 계약을 이해하고 소유 범위·기록 위치·갱신 방법을 따른다.

**15번을 합의·마무리한다.** Main이 의견 수신·채택·수정·확인을 구별하고, 중요한 선택의 이유·실제 결과·기대 이득·미확인과 남은 책임을 종합한다. 이번 선택·진행은 Ticket, 공통 요구·가정은 Spec, 유효한 상태·다음 행동은 current, 상세 근거는 records, 선택한 결과의 위치는 output, 지속 제품 의미와 개인 기준은 각각 Project·Personal의 해당 Owner에 연결한다. 단순 적용이나 좋은 대안 채택을 지속 기준 변경으로 자동 승격하지 않는다.

의미 변화가 이미 실행 중인 담당자·반환된 의견·기존 확인 근거에 미치는 영향도 연결한다. 영향 없는 결과는 유지한다. current에는 최신 판단과 다음 행동의 이유를 직접 쓰고 대체된 상태·승인 경과는 필요한 기록으로 보존한다. 기록의 존재·열람·갱신 접수와 실제 반영·적절한 재개·요구 충족을 구별한다.

**Maintain 메모:** 현재 자동 Maintain은 연결하지 않는다. Main의 기록 수행을 추후 스킬로 보완할 가능성을 열어 두되, 이는 아이디어 메모이며 스킬 신설·구체 설계·구현 시점의 확정이나 지금 착수 지시가 아니다. 과거 보존판의 Maintain 전제와 다른 환경의 자동 작성 사례를 현재 연결 계획으로 가져오지 않는다. Main의 책임과 대상의 지침·관리 계약을 따르는 방향은 그대로 유지한다.

**1~15번 설계 합의를 완료했다.** 후속은 실제 development·검토 상세·진입 지침·관련 맥락 스킬과 합의의 차이를 맞춰 실행 본문으로 통합하고 필요한 적용 확인을 하는 일이다.01-02 기준 본문과01-03 구체 검증 수단은 각 Ticket에 남아 있다. 이번에는 기록·현재 상태만 갱신했으며 실행 스킬·설정·Maintain 연결·새 스킬·실험·커밋은 수행하지 않았다. 전체Ticket·Workspace 완료를 뜻하지 않는다.
