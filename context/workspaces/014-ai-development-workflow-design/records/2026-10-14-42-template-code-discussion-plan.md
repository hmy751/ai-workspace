### 2. 공통 요청: 호출자가 무엇을 믿고 사용할 수 있는가

**볼 코드:** [fetcher.ts](/Users/hammyeong-yeon/Desktop/20_lab/template/src/api/fetcher.ts)와 [실제 조회 사용처](/Users/hammyeong-yeon/Desktop/20_lab/template/src/component/InfiniteScrollContainer/index.stories.tsx).

**남길 결과:** 공통 요청 계층이 보장하는 것과 호출자가 처리할 것, 자동화의 편의를 얻기 위한 계약 비용, 수정이 필요하다면 구체 근거와 보존할 동작. 오류 버튼의 구성 논의로 옮기지 않는다.

### 4. 이벤트·계산 Hook: 외부 환경과의 연결이 정확하고 이해하기 쉬운가

**따라갈 장면:** 열림·닫힘·제거, 스크롤·크기 변경, 대상 요소 중 일부가 아직 없는 경우.

**남길 결과:** 외부 환경을 다루는 Hook의 동작 계약, 분리·유지 이유, 놓치면 실제 동작이 달라지는 조건. Hook으로 분리됐다는 사실만으로 좋은 구조라고 판단하지 않는다.

**남길 결과:** 계산 함수의 계약·경계값과 이를 읽고 바꾸기 좋은 표현. 여기서 명명·타입·가독성을 구체 코드와 함께 논의할 수 있다.

## 진행 순서와 한 사례의 끝

추천 순서는 **store → fetcher → 요청 이후 업무 흐름 → 이벤트 Hook → 날짜·데이터 변환**이다. 첫 둘은 실제 구현과 호출부가 연결돼 있어 우선 보고, 뒤의 순서는 새로 드러나는 판단 차이에 맞춰 바꿀 수 있다.

각 영역에서는 먼저 현재 호출·구현의 흐름과 실제 계약을 설명한다. 한두 개의 구체 장면에서 유지할 부분·문제 후보·열린 의도를 구별하고, 대안이 판단에 필요할 때만 대비 코드를 만든다. 사용자에게는 코드로 알 수 없는 목적이나 실제 결론을 바꾸는 조건을 묻는다. 한 번에 모든 질문에 답하도록 요구하지 않는다.

그 사례가 알려준 판단·적용 조건·남은 불확실성이 정리되고 세부 설계를 더 해도 새 판단을 얻기 어렵다면 다음으로 넘어간다. 전체 충분성은 다른 영역에서 중요한 판단 차이가 남았는지 근거를 두고 평가한다. 단순히 파일을 읽었거나 표의 다섯 영역을 순회했다는 이유로 완료하지 않는다.

당장 반복할 필요가 낮은 것은 이미 다룬 컴포넌트 합성의 세부 API, 생성된 문서 표시 스크립트, 이번 판단에 직접 영향을 주지 않는 빌드 설정 전체다. 설정은 검증 실행 경로를 볼 때 선택한다. 다른 Desktop 저장소로 범위를 넓히지 않는다.

## 01-02의 산출물로 이어지는 것

각 사례에서 근거가 있는 판단 기준과 조건을 남기고, 실제로 어떤 검토 지적을 유지·수정·보류할지 연결한다. 공통 품질 판단, 이 프로젝트의 조건, 사용자의 선호를 구별한다. 향후 구현자·검토자가 쓸 방식과 직접 수정·재확인 범위는 기존 01-01·01-03 및 Project·스킬 설계에 연결한다.

이 계획을 작성하면서 템플릿의 파일과 호출부를 읽었으며 설치·실행·수정은 하지 않았다. 코드 자체의 결함 판정이나 테스트 통과를 주장하지 않는다. Workspace 문서만 갱신하고 커밋은 만들지 않았다.
