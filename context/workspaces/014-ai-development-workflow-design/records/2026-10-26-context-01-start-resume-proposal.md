# 04-03 구체안 1 — 시작·재개에서 맥락을 적용한다

2026-10-26. 항목별 독립 개선 리뷰 뒤 기존 합의·실행 본문·맥락 구조를 다시 대조해 종합한 설계안이다. 후속 [1번 개선 리뷰와 적용 논의](2026-10-26-context-01-goal-improvement-review.md)를 거쳐, 재개에서 이번 요청의 결과를 구별하는 문장을 development에 반영하고 아래 실제 사례·후속 확인 방법을 보완했다. 이 한정 반영을 세부안 전체의 확정이나 공통 참조·새 스킬의 생성으로 확대하지 않는다. [앞선 리뷰와 반영 근거](2026-10-26-context-improvement-reviews.md)도 유지한다.

**Main은 현재 Work에서 이번 목표·선택·남은 일을 복원하고, 그 판단에 필요한 Personal·Project 원문을 실제 결과와 대조한다.** current는 다음 행동에 필요한 이번 적용 의미를 보존한다. 원문을 전부 옮기는 공간도, 원문 링크만 모으는 공간도 아니다.

지금 root의 일반 읽기 경로는 development를 거치며 기본 예시001도 직접 가리킨다. [첫 연결안](2026-10-24-ticket04-03-context-connection-proposal.md)을 이어, root에서 요청 종류와 대상의 실제 context 입구를 연결하고 개발 수행은 development로, 읽기만 요청하면 공통 사용 방법으로 들어가게 하는 안이다. 읽기 원리나 직접 요청의 수행 능력을 새로 만드는 것이 아니다. 기본 Workspace 선택의 중복은 항목4에서 함께 보완한다.

## 요청에 맞는 시작 범위를 고른다

| 요청 | 시작 범위 |
| --- | --- |
| 기존 Work를 이어 수행 | Work 관리 계약으로 중심·선택·현재 근거를 복원한 뒤 필요한 원문을 선택한다. 아래 일반 재개 흐름을 적용한다. |
| 특정 계약·선택의 설명이나 한정된 수행 | 질문에 해당하는 본문·실물에서 시작하고 판단에 필요한 Work 부분만 추가한다. 활성 Work가 있다고 전체 인수로 확대하지 않는다. |
| 기존 Work가 없는 개발 시작 | 대상 Project·Personal·실물에서 필요한 근거를 확보해 요청한 결과를 만든다. 별도 Work 생성·선택이 필요해지면 항목4의 계약으로 연결한다. |

미지정 시 기본 Work를 고르는 것과 그 Work 전체를 인수하는 것은 다르다. 일반 재개·한정 수행·새 목표는 본문 선택·대조 방법을 공유하며 각자 필요한 범위를 갖는다.

기존 Work를 명시해 읽거나 수행하는 요청도 기본 선택·host 세션 연결을 자동 변경하지 않는다. 지속 전환까지 요청되면 항목4의 준비·대상별 적용 시점을 따른다. 같은 세션의 현재 turn과 다음 prompt를 구별하는 runtime 계약이 있으면 그 계약이 실제 전환 시점을 정한다.

## Main의 실제 재개

1. **대상과 요청을 잡는다.** 사용자 지정 Project·Work가 우선이다. 미지정이면 대상 root·context·Work 목록의 현재 선택을 따른다. 스킬 설치 위치나 Git 최상위를 곧바로 대상 Project로 간주하지 않는다. nested demo와 실제 Project의 차이가 결과를 바꾸는데 근거로 고를 수 없을 때만 사용자에게 확인한다.
2. **현재 일을 복원한다.** 해당 Work의 README, current 진입·memory·state, output에서 목표·보존 조건·현재 선택·확인 상한·남은 행동·실제 산출물을 읽는다. 이번 질문에 필요한 Spec/Ticket으로 내려간다. 과거 기록의 ‘다음 단계’는 현재 지시가 아니다.
3. **이번 판단에 필요한 본문을 선택한다.** Work에 이미 남은 Personal·Project 선택과 이유를 출발점으로 사용하고, 현재 요청·변경된 사용처·검사 실패가 만든 질문을 더한다. 관련 영역 입구에서 일반 기준·제품 약속·현재 구현 설명을 골라 실제 결과와 대조한다. 사례는 적용 차이를 이해하는 데 필요할 때 읽는다. 형성 자료는 형성 의도와 선택 이유를 확인해 내용을 더 정확히 이해하거나 의미·조건·권위를 수정·재검토할 때 선택한다. [CONTENT-POLICY](prototypes/development-workflow/noline-demo/context/CONTENT-POLICY.md)의 이 조건을 유지하며, 일상 적용에 필요한 이유·조건·예외는 현재 본문에서 찾는다.
4. **이번 요청의 결과와 첫 행동을 연결한다.** 현재 선택이 여전히 맞는지, 새 질문이 해결됐는지, 결정권이나 원자료가 필요한 공백이 무엇인지 판단한다. 현황·배경 이해를 요청했다면 현재 선택의 이유·상태·남은 판단을 복원해 설명하고, 실행까지 맡겼다면 해당 작업을 이어간다. 남은 문제 중 이번 중심과 부수 발견·후속 후보를 구별하고 첫 행동을 현재 요청과 선택 이유에 연결한다. state의 다음 행동이나 구체적인 결함 목록도 이 관계를 확인해 사용한다. 확인 가능한 작업은 계속하고 중요한 미확인은 해당 판단 가까이 둔다. 읽은 파일 수가 인수 완료의 기준은 아니다.

같은 실행 주체가 충분히 읽었고 관련 변경 신호가 없다면 본문을 다시 전부 읽지 않는다. 새 세션·새 담당자는 원문 접근과 이해를 확보해야 하며 다른 담당자가 읽었다는 사실만으로 생략하지 않는다. 과거 판단을 평가할 때에는 당시 입력을, 지금 이어갈 때에는 현재 적용할 본문과 실제 결과를 사용한다. 전체 파일 해시나 읽기 로그는 기본 요구로 추가하지 않는다.

현재 정본에서도 채택된 선택·실제 적용 조건·현재 구현 지원은 구별한다. 항목3의 반영이 도중에 끊겼다면 current에 남은 적용·확인을 이어가고, 최신 문서에 적혔다는 이유로 구현까지 끝났다고 간주하지 않는다.

## 읽기 뒤에는 기존 작업 판단으로 돌아간다

목표나 완료 장면이 불충분하면 Main이 기존 대화·Spec/Ticket·실물을 대조해 필요한 선택을 구체화한다. [work-discussion](prototypes/development-workflow/skills/work-discussion/SKILL.md)은 사용자가 직접 호출할 때만 적용하고, 일반 목표 구체화를 이유로 자동 호출하지 않는다. 기존 정의가 충분하면 새 이해안이나 인터뷰를 다시 만들지 않는다. 공통 읽기 방법은 이 판단에 필요한 의미·충돌·공백을 제공하고, 목표 정의의 책임은 Main·development와 해당 스킬에 남는다.

결과·새 조건·누적 부담이 원래 방법의 전제를 흔들면 Main이 목표·선택 이유·실제 결과·관련 작업을 다시 대조한다. [기존 reconsider-work](../source/noline-baseline/.claude/skills/reconsider-work/SKILL.md)의 판단 방법은 유지하되, 대상에 실제 설치돼 있고 현재 계약과 맞을 때 연결한다. 없거나 보존판의 Maintain 전제가 현재와 다르면 [development의 관련 맥락 연결](prototypes/development-workflow/skills/development/SKILL.md#관련-맥락-작업을-필요한-때-연결한다)에 따라 Main이 직접 수행한다. 국소 결함은 맡은 수정·검사로 이어가며 매 읽기·Ticket 종료를 전체 Work 재판단으로 만들지 않는다. 이는 기존 책임을 연결안에 드러낸 것으로, 공통 읽기가 작업 정의·재판단을 흡수하는 변경이 아니다.

## 실제 예제에 대입한다

기존 [로그인 Work](prototypes/development-workflow/noline-demo/context/work/workspaces/001-login-completion-names/README.md)를 재개한다. [state](prototypes/development-workflow/noline-demo/context/work/workspaces/001-login-completion-names/current/state/index.md)는 현재 이름이 `signInAndRequestRefresh`/`onSignedIn`이고, 저장·인증 상태 적용은 기다리며 후속 조회는 기다리지 않는다고 설명한다. 확인 범위는 메모리 예제다.

| 이번 요청 | 필요한 읽기와 판단 | current에 남길 의미 |
| --- | --- | --- |
| 기존 이름 선택의 이유를 설명 | [Personal 선택](prototypes/development-workflow/noline-demo/context/work/workspaces/001-login-completion-names/current/memory/personal-context.md), 관련 이름 기준, 실제 두 소비자와 비교 기록. 완료 의미를 코드에서 드러내는 이득과 변경 비용을 확인 | 새 선택이 없다면 재개했다는 기록을 추가하지 않는다. 답변이 요청의 결과다. |
| 새 화면이 로그인 뒤 최신 여행 목록을 바로 사용 | [Project 선택](prototypes/development-workflow/noline-demo/context/work/workspaces/001-login-completion-names/current/memory/project-context.md)에서 인증 계약·현재 흐름, 새 소비자 요구·사용처를 확인. 실패가 인증을 취소하지 않는다는 조건과 조회를 기다리는 조건을 분리 | ‘새 소비자는 조회 완료가 필요하다. 기존 비대기 결정을 그대로 가져올 수 없다. 소비자에서 기다릴지 공통 완료 약속을 바꿀지는 영향 비교가 필요하다’처럼 이번 적용과 열린 선택을 남긴다. 이 요구는 설계를 설명하는 가정이다. |
| 실제 저장소 연결을 재개 | 메모리 예제의 결과·한계와 Project 저장·상태 공개 계약, 대상 어댑터 실물·환경을 확인 | 예제 검사를 실제 DB·부분 실패·복구 확인으로 확대하지 않고 실제 작업의 미확인과 첫 행동을 남긴다. 독립 Work 분리는 항목4의 조건으로 판단한다. |

위의 갱신은 목표나 선택·상태가 실제로 바뀔 때 Main이 Work 계약으로 수행한다. 읽는 행위 자체에 저장을 묶지 않는다. 대안·사용자 선택·중요한 실패·정확한 원문이 후일 재판단에 필요하면 records에 보존하고 current에는 지금 적용할 의미와 근거 접근점을 둔다.

명확한 예제만으로 재개를 평가하지 않는다. [실제 보존 대화](../source/noline-evaluation/corpus/01a0f772-73ab-7823-b282-bddb19124b7e/messages.jsonl)의 첫 요청(`source_line:12`)은 “여기 작업 이어갈거야 최근 기록 한거 보고 현황 파악하자”였다. 담당자는 배경·잠정 상태·코드·확인 한계를 설명하고도 두 버그의 기대 동작을 다음 중심으로 골랐다(`source_line:69`). 사용자는 “지금 구조랑 배경을 더 파악해봐 마지막 문제 2가지는 아직 그렇게 중요한건 아니고”라고 정정했다(`source_line:76`). [당시 기록](../source/noline-evaluation/documents/blobs/d32b272583a04197bfdb15146e5c2122667885a3.md)에는 폼 소유 위치의 대안이 현재 배치보다 낫다는 근거를 확보하지 못했고, 앞선 구조 검토의 결론이 실제 확인 범위보다 넓었다는 판단도 있었다.

이 요청을 처리할 때 Main은 development에 따라 현황·배경 이해를 이번 결과로 잡는다. Work 지침으로 현재 구현·잠정 선택·미해결 문제를 복원한 뒤, 공통 읽기 방법으로 작성 상태를 보존해야 하는 이유와 검색·폼·제출의 현재 책임, 배치 대안과 판단 한계를 관련 기록·실물에서 대조한다. 그 관계와 미확인을 설명하고 두 버그는 남은 문제로 유지한다. 같은 상태에서 사용자가 ‘두 버그부터 고치자’고 요청했다면 해당 수정에 필요한 계약·코드를 중심으로 읽고 구현을 이어간다. 두 요청을 처리하기 위해 새 역할이나 필수 이해 보고서를 만들지 않는다.

이 장면은 기록이 없었던 사례가 아니다. 첫 요청과 당시 근거로 현재 질문의 중심을 판단하며 후속 정정은 실제 의도를 확인하는 근거다. 모든 재개에서 구조 분석을 먼저 해야 한다거나 이 문구만으로 재발을 막는다는 결론으로 확대하지 않는다.

## 공통 방법과 영역별 지침의 배치

가칭 `context/USAGE.md`에는 **질문에서 시작해 본문을 선택하고, 기존 읽기의 유효성을 판단하고, 원문·실물을 대조한 뒤 적용·충돌·미확인을 구별해 원래 과업으로 복귀하는 방법**을 둔다. 대상 경로·권위·Work 구조는 각 입구에서 찾는다. 공통 방법은 모든 영역의 우선순위를 새로 정하지 않는다.

| 현행 조항 | 구체화 후 소유 위치 | 원래 위치에 남길 것 |
| --- | --- | --- |
| read와 development의 질문별 선택·재사용·추가 탐색 | 공통 사용 방법 | development에는 수행 중 어느 조건에서 적용하는지, 기존 read 진입이 필요하면 같은 방법으로 안내하는 연결 |
| Project reading의 주제 선택·계약/현재 구현 대조 | Project의 제품별 탐색은 [reading](prototypes/development-workflow/noline-demo/context/project/REFERENCE/reading.md), 일반 대조 방법은 공통 사용 방법 | 인증·세션 등 실제 제품 질문과 권위 관계 |
| Personal의 일반 기준·사례·형성 자료 선택 | [Personal](prototypes/development-workflow/noline-demo/context/personal/README.md)과 해당 본문 | 개인 판단의 범위·제품 약속과의 관계·의미 변경 권한 |
| Work 복원 순서와 현재 적용 의미 | Work 계약과 해당 current | 이번 선택·이유·상태. 공통 참조에 current 파일 목록을 중복 정의하지 않음 |
| 목표의 충분성·현재 방법의 전제 판단 | Main·development와 실제 조건에 맞는 work-discussion/reconsider-work | 작업 정의·재판단의 발동 조건·선택·후속 행동. 공통 읽기는 필요한 근거를 제공하고 원래 판단으로 복귀함 |

최종 이관에서는 공통 조항을 원래 본문에 그대로 두고 새 파일만 더하지 않는다. 원래 입구에는 역할·읽을 조건과 짧은 핵심만 남긴다. 기존 명시 read 호출을 보존할 필요는06에서 실제 사용처를 보고 정하며, 호환 진입이 필요해도 읽기 절차를 두 벌 관리하지 않는다.

## 별도 요청과 종료

‘이 작업 맥락을 읽어 설명해줘’는 같은 대상 선택·원문 대조를 수행하고 적용할 내용·이유·공백을 답하면 끝난다. 활성 Work가 없어도 관련 Personal·Project를 읽을 수 있다. ‘읽어서 이번 current에 필요한 내용을 정리해줘’라면 명시된 Work 갱신까지 Main이 맡는다. 독립 요청을 위해 development 전체나 새 Work를 시작할 필요는 없다.

읽는 중 지속 본문의 오류를 발견하면 변경 필요와 근거를 항목3에 연결한다. 읽기 전용 요청은 쓰기 권한을 추가하지 않지만, 이미 수정까지 맡은 개발 작업에서는 같은 수행자가 허용된 반영을 이어갈 수 있다. 이때 다시 모든 원문을 읽는 새 과업으로 초기화하지 않는다.

## 외부 근거와 확인할 것

[Matt·Lauren 조사](2026-10-25-context-reference-synthesis.md)의 passive glossary 사용과 능동적 domain-modeling 구별, 원칙 leaf 직접 읽기를 차용한다. 개인 기준을 검토자에게만 주거나 mode 전체를 모든 역할에 읽히는 정책은 가져오지 않는다. 외부 원문은 방식의 근거이며 이 연결의 효과를 증명하지 않는다.

후속 적용에서는 같은 Work 재개·질문 변경·읽기만 요청에 더해 위 실제 재개 장면을 사용한다. 수행자에게는 당시 첫 요청과 당시 자료를 주고, 이후 사용자 정정은 평가 근거로 구별한다. 같은 자료에서 ‘두 버그부터 고치자’는 요청도 대조해 요청에 맞춰 읽기·수행이 달라지는지 확인한다. 필요한 계약과 확인 한계를 실제 판단에 사용하고, 중심을 부수 발견으로 바꾸지 않으며 불필요한 갱신을 시작하지 않는지 본다. 이는 후속 수행 확인 방법이며 매 재개에 적용할 절차가 아니다. 이번 문서는 그 실행 결과가 아니다.
