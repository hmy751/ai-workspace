# 04-01 작업 구체화·재판단 자체의 실패 사례 재선별

2026-10-20. **경비 합계 Ticket의 중복 보강 제안과 복구 토스트의 필요성 재판단 누락을 04-01의 다음 비교 후보로 골랐다.** 두 장면 모두 구현 전에 스킬 적용이 명시돼 있고, 작업 정의·다음 행동을 정하는 응답 자체에서 부족함을 확인할 수 있다. 기존 스킬에 관련 기준이 이미 있으므로 새 의무가 없어서 실패했다고 단정하지 않는다. 아래 보완은 수행 방식의 후보이며 본문 변경·효과 확인은 아직 하지 않았다.

## 사용자 결정과 조사 경계

사용자는 앞선 DB·인증 구조 개선 사례를 두고, 기준이 있는데 수행하지 않은 문제를 사례 추가로 해결할 수 있는지와 work-discussion의 책임인지 질문했다. Main은 사례 추가를 바로 보완 방향으로 연결한 판단을 수정했다. 사용자는 이어 다음과 같이 정했다.

> 그럼 이 사례는 나중 워크플로 정할 때 정해야하는걸로 하자  
> 04-01에서 실제로 보완할 문제가 있는 사례를 source에서 다시 찾아봐. 작업 구체화나 재판단 자체가 잘 안 된 경우로

[DB·인증 대조](2026-10-20-ticket04-01-db-auth-comparison.md)의 `source_line` 80~1067은 이후01-01·01-02에서 구현·검토·완료 책임을 논의할 근거로 넘긴다. 그 사례를04-01의 스킬 사례 추가 근거로 계속 사용하지 않는다.

이번 조사는 보존 source의 개발 원문·문서 판본·스킬과 기존 연구·평가를 대조했다. 두 조사 담당은 각각 작업 구체화와 재판단 후보를 읽었고, Main은 아래 채택 후보의 원문과 보존 문서를 직접 확인했다. 외부 Noline·TripProof 저장소, 원본 rollout, 제품 실행에는 접근하지 않았다. JSONL의 물리행과 `source_line`은 구별한다.

## 1. 이미 구체적인 경비 합계 Ticket을 새로 보강할 것처럼 답했다

원문: [01a08e27 세션](../source/noline-evaluation/corpus/01a08e27-753f-76f0-95fa-32e1c324561f/messages.jsonl), 물리행4~10 / `source_line` 67~132.

AI는 기존 Spec과 코드를 대조했다며 첫 항목 강조, 통화별 자릿수, 전후 검증과 제외 범위를 설명했다(67). 사용자가 `$work-discussion`으로 “더 구체화 할거 있나? 티켓에 대해?”라고 물었다(74). AI는 추가 사용자 선택은 없다면서도 Ticket에 보강할 네 가지를 제시했다(105).

- 구조 개선의 판단 기준
- 정렬·빈 목록의 기대 결과
- 반올림 차이 보존
- 동작 검증과 가독성 판단을 각각 남기기

사용자는 “이게 상위에 없어?”라고 되물었다(120). AI는 다음과 같이 정정했다(125).

> 대부분은 이미 상위 Spec에 있습니다. 내가 방금 티켓에 보강할 내용처럼 길게 제시한 건 중복이었습니다.

실제 새 관찰은 `1.005`를 표시할 때 화면과 helper의 반올림 결과가 다르다는 경계값이었다. AI는 현재 Ticket이 이미 실행할 만큼 구체적이고, 이 경계값만 검사 사례로 보완하면 충분하다고 수정했다. 다음 사용자 발화는 작업 시작이었다(132).

### 무엇을 직접 확인했나

[실행 전 Ticket 보존판](../source/noline-evaluation/documents/blobs/d5ed37a2cc24b3b91496699e88a408662cf8fb08.md)의 5·9·13·15행에는 이미 개선 범위, 강조의 정확한 의미, 기존 표시 차이 보존, 빈 목록·동률·통화별 검사, helper와 화면 검증 구별, 구조 개선의 별도 비교가 있다. 따라서 사용자 정정과 AI의 인정뿐 아니라 기존 문서 내용도 중복 보강이라는 판단을 뒷받침한다. 다만 이 문서가 응답 순간 실제 읽힌 출력과 바이트 단위로 같은지는 입증하지 않았다.

실패는 새로운 제품 선택을 강요하거나 실제 Ticket을 중복 수정한 것이 아니다. **기존 정의의 충분성을 묻는 요청에, 기존 요구를 새 보강사항으로 제안한 것**이다. 실제 반올림 차이 발견은 유효한 조사 성과이며 첫 응답 전체가 무가치한 것은 아니다.

### 기존 스킬과 보완 후보

[work-discussion 기준판](../source/noline-baseline/.claude/skills/work-discussion/SKILL.md)의 29·31행은 이미 정한 선택을 다시 열지 않고 충분하면 바로 마무리하도록 한다. 39·47·69행은 기존 계약의 적용, 공통 내용의 중복 방지, 유지·새 구체화·변경의 구별을 요구한다. 따라서 관련 원칙 부재보다 실제 적용 부족이 먼저 확인된다.

보완할 후보는 “중복하지 말라”는 규칙이나 사례를 하나 더 넣는 것보다, **기존 Spec·Ticket의 추가 구체화 요청에서는 충분성 판단을 먼저 반환하고 새로 필요한 차이만 이해안에 담는 것**이다. 이 장면에서는 “기존 정의로 실행 가능하고, 반올림 경계값 하나만 검사에 추가하면 된다”가 적절한 결과다.

충분성을 판단하기 위해 필요한 조사와 요구 발견은 계속한다. 기존 문서가 있다는 이유로 구체화를 생략하거나, 모든 제안마다 대조표·문서 재작성을 의무화하지 않는다. 새 Work를 정의하는 요청과 기존 정의의 부족분을 묻는 요청에서 응답 방식이 달라지는지 비교할 필요가 있다.

## 2. 복구 토스트를 재판단하면서도 구현 자체는 전제로 남겼다

원문: [01a0ed7a 세션](../source/noline-evaluation/corpus/01a0ed7a-8db9-7883-a1fe-34e4390535ec/messages.jsonl), 물리행105~116 / `source_line` 2492~2586.

원래 알림의 목적은 **연결이 끊겨 비활성 여행의 내용이 제한됐다가 다시 볼 수 있게 된 사실을 알리는 것**이었다. [9월16일 결정](../source/noline-evaluation/documents/blobs/9778a2de53e037ccb5a10c534bc0b8d231b5f2ef.md)의 11~19행에 제한·복구 상황과 조회 성공 뒤 토스트가 연결돼 있다.

이후 [9월29일 정책 변경](../source/noline-evaluation/documents/blobs/c16641b7c97a6c711687b44748be1c13a1d09b7f.md)에서는 연결이 돌아오면 기존 내용을 즉시 표시하고 재조회는 Query에 맡겼다. 알림이 붙을 사건의 의미가 달라졌고, 알림 의미는 열린 판단으로 남았다.

AI는 다음 작업을 연결 복구 알림의 구체화·구현으로 제안했다(2492). 사용자는 기존 정책과 시스템의 각 역할을 고려해 불필요한 복잡함을 없앨 수 있는지 검토하라고 했다(2499). AI는 `reconsider-work`를 적용했지만(2502), 결론은 작은 표시 컴포넌트로 알림을 구현하자는 것이었다(2542). 연결 관측·조회·동기화 책임을 다시 만들지 않는 구체 개선은 있었으나, 알림 자체의 필요성은 판단하지 않았다.

사용자가 “근데 애초에 이 기능의 배경이 뭐지?”라고 물은 뒤에야(2549), AI는 앱 전체의 연결 알림은 원래 목적보다 넓었다고 인정하고 다음 판단으로 돌아갔다(2560).

> “제한 안내가 사라지고 내용이 다시 나타나는 것만으로 충분한가, 추가 알림이 있어야 사용자가 복귀를 알아차리는가”

후속 논의에서 헤더의 연결 상태와 내용 복구가 이미 변화를 전달하고, 조회 실패는 기존 오류 처리가 맡는다는 점을 대조했다. AI는 토스트를 지금 추가하지 않고 종합 UX 확인에서 필요성이 드러나면 재검토하자고 권했고(2573), 사용자가 채택했다(2580). [9월30일 결정](../source/noline-evaluation/documents/blobs/78ef239a447b076218d56f6c4216dae01bfbb1c6.md)도 구현 완료와 현재 미추가 결정을 구별한다.

### 판정과 반대 근거

**재판단을 “현재 할 일을 어떻게 작게 구현할까”에 한정하고, 변화한 조건에서 그 일이 여전히 필요한지까지 보지 못한 사례**다. 구현 후 품질 문제가 아니라 구현 전 작업의 존재·범위·필요성을 정하는 문제이므로04-01에 직접 해당한다.

9월29일 기록에도 토스트가 후속 할 일로 남아 있었다. 기존 합의를 임의로 취소하지 않은 것 자체는 실패가 아니다. 2542의 중복 책임 제거와 제안·채택 구별도 유효했다. 부족했던 것은 정책이 달라졌다는 근거와 재검토 요청을 받고도 원래 목적에 대한 추가 기여를 판단하지 않은 부분이다. 최종 미추가 선택은 확인되지만 실제 UX 검증이나 토스트가 보편적으로 불필요하다는 결론은 아니다.

### 기존 스킬과 보완 후보

[reconsider-work 기준판](../source/noline-baseline/.claude/skills/reconsider-work/SKILL.md)의 10행은 처음 이 일을 고른 목적을, 45행은 현재 작업 목록 자체를 원래 요청과 대조하도록 한다. 49·53행도 보존할 결과와 내부 선택을 구별하고 남는 부담으로 방법을 판단하도록 한다. 이 장면 역시 기존 기준의 미수행이 먼저다.

보완 후보는 **변경된 조건이 예정 작업의 목적을 흔들 때, 구현 방법을 추천하기 전에 그 작업이 현재 목적에 더하는 결과가 무엇인지 판단하는 것**이다. 이미 다른 결과가 목적을 충족한다면 유지·수정뿐 아니라 미추가·보류도 추천할 수 있고, 무엇을 보존하며 어떤 관찰에서 다시 열지는 설명해야 한다.

모든 Ticket마다 필요성을 다시 심사하는 절차나 무조건 기능을 줄이는 기준으로 만들지 않는다. 이미 합의된 제품 결과를 구현자가 임의로 버릴 권한도 부여하지 않는다. 이 사례에서는 원래 보호할 복구 경험을 유지하면서 수단인 알림의 필요성을 사용자와 다시 정했다.

## 보조 사례와 이번에 중심에서 뺀 자료

- 같은 DB·인증 세션의 **별도 후반 정책 논의**(물리행139~147 / `source_line` 2114~2214)에서는 사용자가 인증의 역할·기준·부작용을 물었는데 AI가 비교 예시인 unknown과의 차이에 좁혀 쓰기 차단안을 먼저 제안했다. 사용자 정정 뒤 인증·계정·로컬 이용의 역할로 문제를 다시 잡았다. 명시적 reconsider 적용이 있으나, 첫 구조 개선 사례와 사건을 합치지 않는다. 재판단 대상을 오독한 보조 근거로만 남긴다.
- 기록을 읽고도 두 버그부터 처리하려 한 재개는 작업 초점의 문제지만, 특정 스킬의 수행과 맥락 재개 책임을 가르기 어렵다.
- 승인·철회 사례는 사용자가 동작 개선을 알고 승인한 근거와 이후 일부 재채택이 있다. 철회만으로 작업 구체화 실패를 확정하지 않는다.
- TripProof의 library chat 범위 축소는 구현 전 핵심 결과를 미룬 사례지만, 현행 두 스킬의 형성 배경이며 핵심 수행을 뒤로 미루지 말라는 요구가 이미 반영돼 있다. 현행 스킬의 새로운 공백 증거로 소급하지 않는다.

## 현재 결론과 다음 검토

04-01에서 직접 다룰 실패 장면 두 개는 찾았다. 다만 **적합한 실패 사례를 찾은 것과 스킬 문구를 바꾸면 해결된다는 것은 별도 판단**이다. 새 원칙보다 기존 정의의 충분성 판정과 예정 작업의 필요성 재판정을 실제 시작·반환 동작에 연결하는 보완을 비교할 수 있다.

다음 논의에서는 두 요청에서 현행 스킬이 만드는 응답과 보완안의 응답을 비교하고, 새 Work의 적극적 구체화나 정당한 기존 합의 유지까지 약화시키지 않는지 함께 본다. 두 실패 장면에만 맞춘 정답 응답을 만들거나 사례 수를 늘리는 것으로 효과를 판정하지 않는다. 실제 스킬·글로벌 지침·제품 코드·운영 흐름은 이번 조사에서 수정하지 않았다.
