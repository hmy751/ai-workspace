# 01-02의 남은 결정과 후속 Ticket의 구체화 범위

2026-10-18. [시안 보완68](2026-10-18-68-principle-application-and-choice-basis.md)까지의 결과를 [01-02](../current/tickets/01-development-workflow/01-02-code-design-quality.md)·[전체 Spec](../current/spec.md)·후속 Ticket의 책임과 대조했다. 아래 진행 순서는 Main의 추천이며, 사용자 채택이나 Ticket 완료 선언이 아니다. 최신 적용 시안은68이 연결한 본문을 그대로 유지한다.

## 사용자 요청

> 그럼 지금까지 한 걸 종합하면 01-02에서 더 정해야 할 건 뭐고, 이후 티켓에서 이어서 구체화할 건 뭐야? 다음에 어떻게 진행하면 좋을지 정리해줘.

사용자는 앞서 내용의 대량 작성보다 형식·분류·전달을 먼저 논의하고, 자신의 생각·전체 Spec·외부 자료·구체 사례를 함께 고려하도록 요청했다. 이후 Ticket이 이번 결과뿐 아니라 판단 과정과 근거도 다시 써야 한다는 [65의 방향](2026-10-18-65-criteria-status-and-cross-ticket-refinement.md)을 유지한다. 후속 작업을 지금 정한 문서를 그대로 옮기는 일로 축소하지 않는다.

## 지금까지 확보한 것

- [기준 종합54](2026-10-16-54-code-quality-criteria-and-remaining-work.md)에 목적·책임·공통화·도구·계약·상태 수명·업무 흐름·이름과 경계·관련 개선의 판단 재료가 있다. 직접 사용자 동의·회고·Main의 해석은 동일한 강도의 규칙이 아니다.
- 일반 원칙·구체 사례·현재 제품 계약을 구별하고, 원칙은 채택 이후에도 현재 목적과 조건으로 적용한다는 방향을 시안 본문에 반영했다. 질문은 판단의 관점이며 모든 답을 보고하거나 사용자에게 다시 묻는 의무 양식이 아니다.
- [현재 시안](prototypes/applied-criteria-2026-10-17/README.md)은 대표 원칙 두 개와 HTTP·Field·후속 설계 장면으로 찾아 읽기·판단·직접 수정·반환·과정 재사용을 보여 준다. 앞서 모은 기준 전체의 구성과 실제 운영을 확정한 것은 아니다. 다른 기준의 일부 의미가 두 원칙 안에 포함돼 있지만 전체 수록·분류가 결정됐다고 보지는 않는다.
- 검토자가 필요한 품질 수정을 직접 하는 B 방향은 선택됐다. 가상 develop의 상세 절차·파일 분리·최종 검증 책임·실제 효과는 미확정이다.

## 01-02에서 더 정할 것

### 처음 사용할 기준의 범위와 논리적 구성

54의 재료 중 무엇을 여러 작업에서 공통으로 묻고, 무엇을 특정 작업에서 찾아 읽으며, 무엇을 구체 사례·조건·미정으로 남길지 정해야 한다. 아홉 개 판단축을 아홉 개 문서로 만들거나 모든 문장을 의무 기준으로 올리는 것은 아니다. 일반 원칙과 사례를 구별한다는 사용자 방향은 유지하고, 각각을 이해·적용하는 데 필요한 설명과 연결을 정한다.

현재 시안의 원칙·조건·질문·사례·근거 관계를 전체 재료에 대입해 빠진 의미와 중복을 확인한다. 원칙마다 같은 목차를 채우게 할지는 별도 선택이며, 지금은 필요한 정보 관계가 먼저다. 파일 위치·분할·읽기 절차의 상세는03·04-03의 실제 조건과 함께 구체화한다. 네이밍 전체 규칙이나 기억나지 않는 날짜 정책을 먼저 완성해야 하는 것은 아니다.

### 품질 판단이 유지·수정·보류로 이어지는 최소 근거

무엇이 문제인지, 어떤 목적·계약·읽기·변경 부담과 관련되는지, 유지할 동작과 기대하는 개선은 무엇인지가 판단에서 드러나야 한다. 원칙과 코드 모양이 다르다는 사실만으로 수정을 지시하지 않으며, 구조 품질을 계약 버그 수정으로만 제한하지 않는다.

HTTP 장면의 계약 정비와 Field 장면의 공유층 제거·목표 미충족 반환을 바탕으로, 어느 정도의 근거가 지적·수정 판단에 충분한지와 무엇이 추가 판단 후보인지 구체화한다. 형식은 매번 모든 칸을 채우는 보고서로 고정하지 않는다. 판단에 필요한 내용은01-02가 맡고, 누가 언제 인수·수정·반환하고 종료하는지는01-01, 수정 뒤 무엇으로 확인하는지는01-03과 함께 정한다.

### 설계가 준비됐다고 볼 근거와 적용 뒤 관찰할 것

대표 대비안이 실제 목적·사용처·계약에 근거하고, 기존 기준의 부족인지 이미 있는 기준을 적용하지 못한 문제인지, 코드·도구·검사 지원이 필요한 문제인지 구별해야 한다. 지금 시안의 글과 연결을 확인한 것은 실제 작업자가 잘 판단한다는 증거가 아니다.

설계 단계에서는 기준의 첫 범위·표현, 유지·수정·보류의 이유, 다른 책임으로 넘길 판단과 필요한 증거가 검토 가능해야 한다. 실제 적용 단계에서는 필요한 기준을 찾았는지, 사례의 답을 복사하지 않고 조건을 비교했는지, 변경 부담과 동작 보존을 확인했는지, 기준·기록이 불필요한 부담을 늘렸는지 관찰하도록 계획한다. 실제 적용 대상·실행 수단·책임은01-03·07 및 관련 Ticket과 맞춘다.

이는 기존01-02 완료 조건을 없애거나 더하는 선언이 아니다. 현재 Spec이 구별하는 ‘검토 가능한 설계’, ‘선택’, ‘실제 적용’, ‘효과 확인’을 진행 판단에도 적용하자는 추천이다. 다른 Ticket 전체를 완료할 때까지01-02에 모든 운영 설계를 쌓아 두거나, 시안이 있다는 이유만으로 지금 완료 처리하지 않는다.

## Main의 다음 진행 추천

**바로 다음에는 기존 기준 전체의 ‘구성·분류안’을 비교하는 것이 좋다.** 본문을 모두 길게 쓰기보다54의 각 판단축을 공통으로 읽을 부분·상황별로 찾을 부분·사례로 어떻게 구성할지, 왜 그렇게 두는지, 지금 두 대표 원칙으로 설명되지 않는 부분이 무엇인지 한눈에 보이게 한다. 후보·채택 여부나 미정은 이 구성과 별도의 정보로 표시한다. 이는 논리적 분류안이며 확정 폴더나 전부 별도 문서로 만들자는 제안이 아니다. 앞선 형식 우선 요청을 유지하면서 현재 시안을 전체01-02 범위에 대입하는 다음 결과다.

그 비교를 바탕으로 처음 사용할 범위와 표현 관계를 정하고, **03·04-03에서 기존 Project 구성과 실제 읽기·갱신 스킬에 대입**한다. 지금 시안의 가상 develop이 현행 스킬 대조를 대신하지 않는다. 필요한02의 기록 경계와01-01의 인수·반환도 같은 작업 장면에서 함께 맞춘다.

이어서 **01-01·01-03에서 같은 기준을 사용한 구현·검토·직접 수정·재확인·종료를 구체화**한다. 바뀐 조건은01-02로 돌린다. 04의 관련 스킬 대조, 06의 기존 결합 확인, 07의 부분 연결 확인은 필요해지는 지점에 함께 수행하며 번호순 완료를 강제하지 않는다.

새로운 형식 리뷰를 반복하는 일이나 모든 템플릿 파일·사용자 취향을 다시 조사하는 일을 자동 다음 단계로 두지 않는다. 지금 확보한 재료를 연결하다 실제 판단 차이나 누락이 드러난 부분에서 추가 사례·외부 근거를 찾는다. 이 추천의 채택·구성안 작성·관련 Ticket 실제 수행은 이번 정리만으로 완료된 것이 아니다.

## 확인 범위

Main은 전체 Spec의 범위·연결·완료 구별,01-02의 현재 기준과 남은 일·완료 조건,54·68과 현재 진입 문서를 대조했다. 별도 읽기 담당자는 후속 Ticket의 소유 결과·입력·반환 조건을 추출했다. 이 기록은 문서에 있는 범위와 Main의 진행 추천을 구별한 종합이다. 외부 자료를 새로 검증하거나 prototype·실제 제품·스킬을 변경하지 않았다.

이 기록과 재진입 문서9개에서 로컬 링크 대상373곳의 존재와 행끝 공백을 확인했고 누락·공백 오류는 없었다. `git diff --check`가 통과했다. 내부 이동 위치·원격 URL·브라우저·제품 동작은 이번에 다시 검사하지 않았다.
