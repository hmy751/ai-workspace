# 04-02 — 근거를 선별한 설명 수행 개선안

**후속 적용:** 사용자가 이 판단을 바탕으로 스킬 구체화·반영을 요청해 [실행 본문·연결·형성 자료에 반영](2026-10-24-ticket04-02-selective-improvement-adoption.md)했다. 아래는 채택 전 제안과 개선 리뷰 당시의 상태·판단을 보존한다.

상태: Main의 재검토 뒤 독립 개선 리뷰1회를 받아 보완한 제안. 실행 스킬은 수정하지 않았다. [리뷰 전 사본](reviews/explanation-selective-improvement-2026-10-24/proposal-before-review.md)과 [리뷰 반환 전문](reviews/explanation-selective-improvement-2026-10-24/reviewer-response.md)을 보존했다. 반환의 제안 행 번호는 리뷰 전 사본 기준이다.

**최종 권고는 질문의 범위를 지키면서, 그 답에서 독자가 직접 보충해야 했던 연결을 실제 코드·값·상황으로 풀어 쓰게 하는 것이다.** 모든 사례를 필수 항목으로 합치지 않는다. 이번에 바꾼 중심은 설명의 기준을 더 추가하는 것이 아니라, 전체 코드 요청을 대표 한 대목으로 좁힌 점과 역할 설명으로 선택 판단을 대신한 점이다. 본체의 중복 요구를 이 수행에 맞춰 정리하고, 상세는 이미 나온 부족한 문단을 어떻게 보완하는지 보여 주는 방향으로 권고한다.

## 이번에 해결할 일

사용자 요청:

> 좋아 한번만더 고민해봐 통합 하라고 하면 또 무지성으로 모두 조합해서 진리처럼 다뤄서 다 반영할까 우려되니까 다시 종합해서 고민하고 해봐 그리고 그 다음 제3 개선 리뷰어한테 물어봐 니가 생각한게 괜찮은지 반드시 개선하려고 하는 목적으로 돌려 단순히 적당하다 이런 검증하는거 말고

직전 정정:

> 어쨋든 이 스킬의 본래 목적과 그리고 noline에서 개선하려고 햇떤 장면과 그런 것들을 종합해서 구체적으로 판단해줘야 내가 와닿을 것 같은데? 레퍼도 중요하고 기존 논의나 생각등 우리가 나누면서 내가 느꼇던 지점도 중요하고 그런 통합적인 판단이 안 보여

스킬의 목적은 사용자가 실제 대상의 뜻·동작·구조·선택을 이해하고 자기 질문과 판단을 이어가도록 돕는 것이다. 불필요하게 설명 방식을 재지시해야 하는 부담을 줄이려 한다. 모든 재질문을 없애거나, 모든 답에 코드·도식·설계 평가·완료 판단을 넣는 목표는 아니다.

현재 `explain`에는 이 목적과 실제 구현 대응·전후 비교·앞선 말 대조·목적별 충분성이 이미 있다. 사례를 다시 발견하거나 같은 요구를 더 강하게 적는 것만으로 개선했다고 말할 수 없다. [기존 수행 본문](prototypes/development-workflow/skills/explain/SKILL.md), [작성 상세](prototypes/development-workflow/skills/explain/references/constructing-explanations.md), [앞선 발화 상세](prototypes/development-workflow/skills/explain/references/prior-explanation.md)를 대체 대상으로 삼되 기존 의미를 전부 옮기는 목표도 두지 않는다.

## Main이 선택한 방향과 채택하지 않은 대안

**권고: 하나의 설명 입구를 유지하고, 지금 질문을 푸는 관계를 실제 대상과 함께 완성하는 일을 본체의 중심으로 재작성한다.** 읽기·조사와 응답 작성을 연결하되, 선택 이유·추가 검토·첫 결과 전달은 현재 질문과 작업의 요구에 따라 사용한다. 파일 수나 이름은 이번 개선의 근거가 아니다.

| 대안 | Main 판단 |
| --- | --- |
| 코드 읽기·구조·선택·검증·복구를 모두 답의 필수 내용으로 합친다 | 채택하지 않는다. 인증의 문법 도움, 여행의 설계 판단, 보고서의 추가 확인은 같은 과제가 아니다. |
| development의 완료 보고 요구만 강화한다 | 보고서·첫 전달에는 필요하지만 직접 코드 질문과 학습을 다루지 못하므로 주된 개선으로 삼지 않는다. |
| 사례별 독립 스킬이나 상시 설명 agent를 만든다 | 현재 근거로는 채택하지 않는다. 한 대화에서 여러 설명이 이어지며 별도 실행의 이득을 확인하지 못했다. |
| 옛 두 스킬로 돌아가거나 새 스킬을 제거한다 | 현재 비교로는 결정하지 않는다. 통합 효과는 미확인이나 분리 자체가 낫다는 근거도 없다. 계속 유지할 가치 역시 향후 기본 응답과의 대조 대상이다. |
| 설명할 실제 관계를 먼저 완성하고 필요한 깊이·보조 자료를 붙인다 | 현재 권고다. 기존 조항이 이미 이를 요구한다는 점 때문에 아래 구체 수행이 기존과 실질적으로 다른지 독립 개선 리뷰가 필요하다. |

## 본체에서 바꾸려는 수행

아래는 교체할 본문의 의미를 구체화한 초안이다. 완성된 SKILL 전체나 자동 적용된 규칙이 아니다.

> 현재 질문과 가까운 대화에서 무엇을 어느 범위까지 이해하려는지 정한다. 사용자가 이미 이해했다고 밝힌 것은 이어받는다. 전체 코드를 이해하려는 요청에는 주요 처리들이 어떻게 이어지는지 보여 주고, 특정 대목의 질문에는 그 연결을 풀어 쓴다. 대표 상황은 전체 요청을 따라가기 위한 출발점으로 사용한다. 구조나 선택을 묻는다면 그 역할을 설명하고, 적절성 판단을 요구한 경우 그 선택이 어떤 문제를 해결하며 어떤 부담을 남기는지 대조한다. 사용자의 지식을 고정 등급으로 추정하거나 혼동 원인을 먼저 진단해 달라고 요구하지 않는다.
>
> 답의 핵심 주장에 쓰인 코드·값·관찰·앞선 문장을 고르고, 그것이 왜 그 결과나 판단으로 이어지는지 실제 대상과 함께 풀어 쓴다. 코드라면 필요한 대목의 실제 표현과 의미를 대응시킨다. 전체 구조는 무엇을 맡는지 먼저 잡고 주요 부분의 협력을 따라간다. 초안의 중요한 문장에서 독자가 스스로 보충해야 하는 처리·조건·이유가 남아 있다면 그 연결을 보완한다. 사실이 부족하면 필요한 확인으로 돌아간다. 다른 변경과 확인 내역은 그 답에 필요한 비중으로 붙인다.
>
> 질문이 선택의 적절성을 포함하면 요구·사용처·이득과 부담을 대조해 의견을 낸다. 당시 의도와 현재 효과의 추론은 구별한다. 설명하다 답을 바꿀 사실의 공백을 발견하면 기존 권한 안에서 필요한 확인을 하거나 작업 담당자에게 되돌린다. 이해가 어렵다는 말만으로 현재 구조가 잘못됐다고 판단하거나 즉시 구현을 바꾸지 않는다.
>
> 응답에 실제 대상과 결론 사이의 필요한 연결이 있는지 확인한다. 이름·역할의 요약만 있고 독자가 핵심을 소스에서 다시 조립해야 한다면 그 부분을 보완한다. 작은 뜻 질문은 짧게 끝낼 수 있고 학습 질문은 이어질 수 있다. 사용자의 이해·동의는 설명을 제공했다는 사실만으로 확정하지 않는다.

실질 변경 후보는 마지막에 요구를 추가하는 것이 아니라, 본체에 흩어진 자료 선택·구현 대응·형태·첫 결과 전달 절을 위 수행에 맞춰 재배치하고 중복을 걷어내는 것이다. 현재 완료 보고에서 다시 ‘코드 설명 목적이면’이라고 선택해야 하는 구조를 그대로 두지 않는다. 다만 이런 재배치만으로 실제 응답이 나아진다고 확정할 수는 없다.

## 상세가 실제로 도와야 할 두 설명

작성 상세를 늘리기보다 현재 설명 예시의 판별력을 높인다. 아래는 Main이 원문에서 도출한 구성 제안이며 독립 생성 응답이 아니다. 사례 이름을 일반 실행 규칙에 넣지 않는다.

**인증: 전체 코드 요청과 특정 대목의 후속을 구별한다.** [입력](../source/artifact-explanation-scenes/02-auth-interceptor/input/conversation.txt)에서 문법 질문 뒤 전체 코드가 어렵다는 요청이 있었다. 전체 설명에서는 요청에 세션·토큰을 붙이는 부분, 응답과401 재시도를 처리하는 부분, 여러 요청이 갱신 작업을 공유하는 부분이 어떻게 연결되는지 보여 준다. `await` 전후 세션 확인 한 대목만 잘 설명해도 전체 요청에 답한 것은 아니다. 주요 연결을 설명하면서 해석이 필요한 코드 표현을 그 자리에서 푼다.

그 뒤 사용자가 실패 처리의 특정 대목을 다시 물었을 때에는 [이미 코드와 순서를 설명한 답](../source/artifact-explanation-scenes/02-auth-interceptor/evaluation/conversation.txt)이 있었다. 추가 가치는 같은 설명을 반복하는 것이 아니라, 요청이 보관한 세션 값과 현재 Store의 세션 값이 다를 수 있음을 보여 주는 데 있다. 예를 들어 A 세션에서 시작한 작업은 계속 A를 갖고 있지만 기다리는 동안 Store가 B로 바뀌면 `assertCurrentSession(A)`에서 멈춘다. 따라서 A의 요청 실패를 B의 자격 증명 거부로 처리하지 않는다. 이는 가능한 설명 상황이며 사용자의 내적 혼동 원인을 확정한 진단이 아니다.

**여행: 역할 설명과 선택 판단에 맞는 근거를 따로 고른다.** [이전 논의](../source/artifact-explanation-scenes/05-trip-list-briefing/input/conversation.txt)3484는 책임 분리가 적절한지 “다시 검토해줘”라는 요청이었다. 당시 검토3512·3521에서 문제 삼은 것은 서버 저장 뒤 로컬 사본 반영이 실패해도 목록 새로고침이 서버 결과를 가져오지 못하는 구조였다. 이 판단을 설명하려면 같은 실패 상황에서 기존 배치와 제안 배치를 비교해야 한다. 생성 코드가 사본을 고치고 조회는 로컬만 읽는 배치에서는 새로고침이 빠진 항목을 복구하지 못한다. 조회가 서버 결과와 사본을 맞추는 일을 맡으면 이후 조회가 그 일을 다시 수행할 수 있다. 실제 생성·조회 코드에 이 차이를 대응시켜야 책임을 옮길 이유가 읽힌다. 이것은 당시 검토 논리를 재구성한 예시이며 현재 제품 재검증이 아니다.

반면 [나중의 브리핑 요청3962](../source/artifact-explanation-scenes/05-trip-list-briefing/evaluation/conversation.txt)는 역할·도식·구체 코드를 요구했다. 여기에는 Repository가 실제 작업을 제공하고 Router가 조건으로 선택하는 위임 코드가 유용하다. 리뷰 전 제안은 이 예시를 앞선 적절성 질문의 대표 답으로 사용했다. 그 자리를 교체하되, 역할 설명 자체를 제거하거나 검토 요청의 실행 책임을 모두 explain으로 옮기지는 않는다.

두 설명은 고정 모드나 필수 목차가 아니다. 한 질문에 필요하면 함께 쓴다. 상세의 가치는 단지 좋은 예시를 보여 주는 데 있지 않고, 어떤 관계가 필요한지 판단하고 왜 그 부분을 골랐는지를 복원할 수 있는 데 있다. 현재 작성 상세에도 이 취지가 있고 여행 예시도 있으므로, 다른 예시를 추가하기만 하는 방안은 충분하지 않다.
