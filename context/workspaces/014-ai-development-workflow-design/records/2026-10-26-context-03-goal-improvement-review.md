# 04-03 항목3 — 실제 반영 범위·종료 조건의 구체화와 개선 리뷰

2026-10-26. 사용자 요청에 따라 앞선 합의·기존 관리 계약·외부 고정판을 대조하고, Main이 [3번 초안](2026-10-26-context-03-change-records-proposal.md)을 구체화한 뒤 독립 개선 리뷰를 받았다. **초안·리뷰·두 보완의 반영을 마쳤으며 다음은 사용자와 이 구체안을 논의하는 일이다.** 실제 스킬·공통 참조·runtime·제품·원자료는 수정하지 않았다.

## 요청과 이번에 다룰 결과

직전 Main은 다음을 3번으로 설명했다. 받아들인 의미를 본문·관련 설명·읽기 경로에 어디까지 반영하는지, Work와 진행 중 담당자에게 무엇을 잇는지, 문서 수정과 제품 확인·전체 완료를 어떻게 구별하는지 살피는 단계다.

사용자 원문:

> 이것도 앞선것처럼 단게 걸쳐서 해봐 외부 나 논의 다 고려해서 구체화 하고 리뷰까지 받고 등등

앞선 사용자 요구의 기준도 유지한다. 네 항목별 Main 초안·독립 개선·Main 보완 뒤 종합하며, 기존 스킬의 유지나 신설 자체를 목표로 삼지 않는다. 최근 제안 하나에 한정하지 않고 기존 시스템·합의·외부 근거를 함께 대조한다. [전체 범위 정정](2026-10-26-context-whole-scope-reconciliation.md), [잠정 합의와 사용감 유보](2026-10-25-context-framework-provisional-agreement.md), [직전 제안·검토·반영 구체화](2026-10-26-context-proposal-review-apply-design.md)를 입력으로 사용했다.

## 사전 대조에서 실제로 달라진 것

앞선 합의를 읽던 조사 담당에게 이번 범위의 기존 계약과 사용자 정정을 읽기 전용으로 대조하도록 했다. 별도 연구 담당은 아래 외부 원자료를 확인했다. 이 둘은 초안 이전의 조사이며 초안에 대한 독립 개선 리뷰로 세지 않는다.

- [기존 update 원형](../source/ai-workspace-baseline/reference-project/.agents/skills/update-project-context/SKILL.md)은 이미 보존 의미·직접 근거·실제 소비 경로·문서 반영과 제품 acceptance의 구별을 갖고 있었다. 이번 설계의 새 발명으로 설명하지 않고 Personal·Project 공통 수행과 Main 반환에 연결했다.
- [Project MAINTENANCE](prototypes/development-workflow/noline-demo/context/project/MAINTENANCE.md)는 관련 Work의 선택·output 경로 확인과 대표 작업으로 읽는 대조를 요구한다. 이를 반영 과업의 무제한 Work 수정권으로 확대하지 않고 Main의 후속으로 연결했다.
- [CONTENT-POLICY](prototypes/development-workflow/noline-demo/context/CONTENT-POLICY.md)의 갱신 범위와 완료 조건을 적용했다. 의미 변화에 필요한 형성 맥락은 함께 맞추며 중요한 자료 접근 공백은 해당 부분 미완료다. 오탈자에 모든 background 갱신을 붙이거나 Work에 새 background 구조를 만들지 않는다.
- 구체적인 기존판 차이도 있었다. update 원형은 이전 Owner의 호환 경로 역할을 허용하지만 현재 demo 정책은 승인된 일반 본문 이동 때 새 위치를 직접 연결하고 옛 안내 파일을 정리한다. 공통 수행이 과거 원형을 고정 규칙으로 복사하지 않고 대상의 현행 관리 계약을 따르도록 했다.

## Main 초안에서 펼친 실제 판단

[항목3](2026-10-26-context-03-change-records-proposal.md)에 변경 종류별 반영 범위, 내용·관계·실제 읽기·반환의 종료 판단, 부분 미완료와 편집 없는 종료를 구체화했다. 같은 소비자별 조회 예제에서 실제 guidance/current의 어떤 설명이 달라지는지, 유지할 계약과 남은 요구 검증이 무엇인지 보여 준다. 별도 요청·루프 채택·제품 불일치에서도 같은 방법의 입력과 반환을 비교했다. 가상 예시이며 제품 파일을 그 가정으로 고치지 않았다.

[통합안](2026-10-26-context-integrated-proposal.md)에는 같은 범위·종료 구별만 연결했다. 첫 초안 이후 개선 리뷰의 원문 판단·채택 여부와 실제 수정은 아래에 이어 기록한다.

## 확인과 다음 논의

Main은 두 리뷰 지적을 기존 계약에 대조한 뒤 항목3과 통합안에서 반영 범위·종료·후속 흐름을 다시 읽었다. 개발 중 제안, Work 없는 직접 요청, 루프에서 채택한 문서 변경, 계약과 다른 실제 동작, 일부 근거 공백, 검증 전후 상태를 설계 수준에서 대입했다. 실제 담당자가 스킬로 수행하거나 제품을 변경·검사한 실험은 아니다.

다음은 사용자와 이번 구체안의 실제 흐름을 논의하는 일이다. 추가로 합의해야 진행할 수 있는 새 역할·권한 결정은 발견하지 못했다. 3번을 정리한 뒤4번의 완료·연속 세부를 순차 검토한다. 실행 반영과04-03 전체 완료,05의 담당·시점·02의 전체 기록 구조·06의 설치·07의 효과 관찰은 이번 수행으로 확정하지 않는다.

문서 확인: 변경9개는 모두014의 설계·리뷰 기록·재진입 Markdown이다. 로컬 링크660개와 절 연결12개에서 누락이 없었고 `git diff --check`를 통과했다. 실제 스킬·제품·source·설정은 바뀌지 않았다. 제품 테스트·새 역할 수행 시험은 이 설계 문서 작업의 확인으로 대신 실행하지 않았다.

## 사용자 후속 — Project 내용 선별과 대화 기준 루프

사용자는 데모의 미구현 문구가 실제 존재하는지보다 그런 구현 사항을 Project가 지속 관리하는 것이 적합한지 물었다.

> 왜냐면 project의 핵심이 그런 구현 사항까지 있어야 하는건가? 그게 있는게 좀 안 맞아보여서 그랬어 demo는 그냥 막 만들다보니 뭐 그렇게 적혀잇는것 같긴한데

Main은 데모에 있다는 사실을 적합성의 근거로 쓴 설명을 바로잡았다. 기존 설계에는 제품·구조·지원 현실도 있지만, 모든 구현 여부·검사 진행을 Project에 남기라는 뜻은 아니다. 이번 수행 상태는 Work, 제품을 이해하고 여러 작업에서 판단할 공통 의미·구조·계약·제약은 Project로 먼저 선별한다. 구현 관련 내용 전체를 금지하는 새 규칙이나03 전체 설계의 폐기로 확대하지 않는다. 항목3의 내용 선별과 대표 설명을 이 기준에 맞춰 보완하며 앞선 리뷰는 보완 전 판본에 대한 판단으로 보존한다.

이어 사용자가 루프 연결을 명시했다.

> 그래 그건 뭐 다시 잡으면 되고 3번 구체화에서 말하고 싶은건 나중 루프에서도 이걸 상기해야하는 것 같아 단계를 아예 만들거거든 뭐 스킬을 통하거나 해서 매 작업마다는 아니고 대화 기준으로 할것 같아 이건 또 구체화 해야되는거고

명시적인 루프 단계를 설계한다는 방향과, 매 작업보다 대화 기준으로 보는 구상을05의 입력에 반영했다. 스킬·담당·호출 방식·대화 경계·발동 시점은 아직 구체화하지 않았다. 루프에서 채택한 변경도3번의 내용 선별·영역별 반영·실제 확인·후속 연결을 사용하며 이미 확보한 제안·근거·반영 결과를 재사용한다. 기존 일상 유지가 이 단계를 기다리거나 매 작업의 필수 회고가 되는 것은 아니다. 현재3번을 이어가기 위해 추가 답이 필수인 질문은 없으며 운영 세부 질문은05에서 실제 흐름과 함께 다룬다.
