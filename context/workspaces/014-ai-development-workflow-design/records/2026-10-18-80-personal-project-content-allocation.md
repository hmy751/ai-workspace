# 개인 기준·Project의 실제 내용 배치와 디렉터리 제안

후속 상태: 이 기록의 루트 `personal/development/` 위치 추천과 도출 근거는 [구조 정정과 방향 선택81](2026-10-19-81-personal-context-direction-and-next-step.md)에서 대체됐다. 현재 방향은 `context/personal/development/`이며 아래는 당시 제안과 내용 분류 근거다.

2026-10-18. 세 가이드의 내용을 항목별로 나누고 연결을 구체화했다. **개인 기준의 제안 위치는 ai-workspace 루트의 `personal/development/`다.** 여러 프로젝트가 참조할 개인 기준을 한곳에서 관리하고, 각 Project는 제품·구현·팀의 구체 계약을 관리하는 안이다. 분류와 위치는 검토할 제안이며 원문 이동·통합, 새 개인 기준 디렉터리 생성, 스킬·전역 지침 변경은 하지 않았다.

## 요청과 분류 기준

> 기존 리팩터링·코드 가독성 가이드랑 01-02 기준을 개인 기준으로 둘 것과 Project에 남길 것으로 실제 내용 기준으로 나눠봐. 아직 파일은 옮기거나 합치지 말고, 둘이 어떻게 연결되는지도 같이 보여줘.
> 근데 개인 기준은 디렉토리 명을 뭐라할거고 어디 층에 둘거야?

아래 개인 기준은 **그쪽에서 관리할 후보**라는 뜻이다. Noline에서의 기존 채택이나01-02에서 선택한 형식과, 모든 프로젝트의 개인 기준으로 채택하는 것은 별개다. 개인 기준은 표현 선호·설계 판단·개발 방법을 포함하지만 각각의 역할을 유지한다. 실제 작업의 요구·진행·선택·검사 결과는 기존 Work 기록에 남으며 개인 또는 Project 두 곳에 억지로 넣지 않는다.

원문은 [관찰판 리팩터링](../source/supplement/worktree-project-context/context/project/guidance/behavior-preserving-refactoring.md), [관찰판 코드 가독성](../source/supplement/worktree-project-context/context/project/guidance/code-readability.md), [01-02 quality](prototypes/applied-criteria-2026-10-17/shop-web/context/project/quality.md)다. 첫 두 문서는 별도 Noline worktree 보존판이며,01-02와 연결된 shop-web 문서는 가상 적용 시안이다. 기준판과 관찰판의 차이·각 채택 지위는 [78](2026-10-18-78-code-guides-comparison-and-applicability.md)에 있다.

개인 기준에도 [Field·Container](prototypes/applied-criteria-2026-10-17/shop-web/context/project/cases/shared-choice.md)와 [주문 흐름](prototypes/applied-criteria-2026-10-17/shop-web/context/project/cases/order-flow.md) 같은 조건 대비 사례를 둘 수 있다. 판단을 바꾸는 목적·사용처 조건·선택 이유를 남기고, 실제 관찰과 가상 조건을 구별한다. 실제 Project의 현재 API·지원·완료 계약과 전체 작업 이력까지 개인 기준이 소유하지 않는다.

## 두 내용이 연결되는 모습

### Noline 경비 표시를 정리하는 예

| 읽는 내용 | 이번 판단에 제공하는 것 |
| --- | --- |
| 개인 기준의 이름·책임 판단 | 이름이 실제 의미를 나타내는지, 같은 조건을 여러 곳에서 다시 해석하는지 본다. |
| [Project 통화 본문](../source/supplement/worktree-project-context/context/project/common/currency.md) | 화면 첫 그룹과 baseCurrency가 다를 수 있음. 기본 통화가 없는 경우 주 통화 라벨의 의미는 열린 선택. 현재 표시 자릿수와 저장·반올림 계약도 별개. |
| 개인 기준의 리팩터링 방법 | 동작 보존과 이해 부담 감소를 따로 확인하며 미정 제품 선택을 조용히 결정하지 않는다. |
| Project의 실제 코드·검사 안내와 이번 Work | 현재 강조·라벨 조건·소비부를 확인하고, 허용된 변경·검사·미확인을 작업에 남긴다. |

이 조건에서 첫 그룹을 기본 통화처럼 이름 붙이지 않는 판단이 나온다. 일반 원칙을 통화 본문에 다시 복제할 필요는 없지만, 처음 읽는 사람이 이 제품의 값과 이름의 관계를 이해할 만큼은 그 자리에서 설명한다. “연결”을 제품 본문에서 설명을 모두 빼고 링크만 남기는 방식으로 구현하지 않는다.

### 가상 HTTP 시안의 timeout 예

개인 기준은 “약속한 작업 수명과 자원 정리가 맞는지 확인한다”를 맡고, [가상 Project의 HTTP 계약](prototypes/applied-criteria-2026-10-17/shop-web/context/project/http-client.md)은 “요청 시작부터 응답 본문 처리 종료까지10초”를 맡는다. 그러면 헤더 수신 직후 timer를 해제하면 계약이 깨진다는 판단이 가능하다.10초라는 값은 개인의 기본값이 되지 않으며 이 예는 Noline의 현재 HTTP 계약도 아니다.

실제 읽기 경로의 제안은 **Project 입구가 해당 주제의 제품·구현 본문과 필요한 개인 기준을 함께 안내하는 것**이다. 개인 기준은 일반 판단을, Project 본문은 해당 조건·적용·차이를 설명한다. 관련 없는 개인 기준 전체를 모든 작업에 읽히지 않는다. 개인 원본에 접근할 수 없는 실행 환경에는 선택한 적용본의 출처·버전을 밝혀 전달하는 방법이 필요하며, 그 방식은 실제 읽기·이식 설계에서 확인한다.

## 디렉터리 이름과 놓을 층

**이름은 `personal/`, 현재 코드·개발 기준의 위치는 `/Users/hammyeong-yeon/Desktop/ai-workspace/personal/development/`를 추천한다.** 아래는 아직 생성하지 않은 제안 구조다.

```text
/Users/hammyeong-yeon/Desktop/ai-workspace/
├── personal/
│   ├── README.md
│   └── development/       # 개인의 표현·설계·리팩터링 판단 본문
├── reference-project/     # 실행 가능한 기준 Project
└── context/
    └── workspaces/014-ai-development-workflow-design/
                           # 이번 분류·선택·설계 과정의 기록
```

각 실제 제품의 `context/project/`는 계속 그 제품의 맥락을 맡는다. 개인 기준은 Project보다 적용 범위가 넓은 별도 층이며, 더 강한 지시 우선순위라는 뜻은 아니다. `personal/README.md`는 개인 기준의 범위·소유자·내용별 진입·갱신 원칙을 설명하고, `development/`는 개발 기준의 실제 본문과 필요한 사례를 소유하는 구성을 제안한다. 표현·설계·리팩터링을 한 본문으로 합칠지는 이번에 정하지 않았다.

현재 [context의 계약](../../../README.md)은 Workspace의 current·output·records와 원자료를 소유한다. 개인 기준은 이 설계 작업이 끝난 뒤 여러 프로젝트에서 계속 사용할 별도 산출물이므로 루트에 두는 편을 추천한다. [root의 구성](../../../../README.md)과 Workspace output에서 실제 정본으로 안내할 수 있다. `context/personal/`도 계약을 확장하면 가능하지만 작업 기록과 실제 개인 기준의 책임을 다시 추가로 설명해야 한다.

Reference는 실행 가능한 기준 Project이며 실제 개인 기준 전체의 정본으로 정해진 곳이 아니다. 각 제품에 별도의 개인 원본을 만들어 서로 다르게 관리하기보다 중앙 정본과 프로젝트별 적용을 구별한다. 다른 환경으로 전달할 때의 적용본은 개인 원본과 독립된 두 번째 정본으로 취급하지 않는다.

아직 `personal/`은 없고 이번에 만들지 않았다. 실제 루트 진입점 갱신·소유 관계 연결·접근/전달 방식·전역 routing 변경은 이번 제안을 채택해 구현할 때 [06](../current/tickets/06-framework-transition/README.md)·[04-03](../current/tickets/04-skill-improvements/04-03-context-skills.md)과 구체화한다. 경로를 제안하는 일을 후속 Ticket까지 미루지는 않는다.

## 확인 범위와 남은 판단

Main과 분담 조사자가 세 가이드 전체 절,01-02의 연결 사례·HTTP·주문 계약, root·context·Reference의 현재 역할을 대조했다. 내용 배치 후보와 실제 적용·채택은 구별했고 제품 실행은 하지 않았다. 문서 이동·통합·삭제, 새 개인 기준 본문 작성·설치, 전역 하네스 변경도 없다.

다음에 판단할 것은 개인 기준 후보에서 실제 채택할 항목, 기존 기준 간 중복의 소유 위치, Project별 적용·예외를 표시할 방법이다. 이번 분류를 보고 그 내용을 정한 뒤에 실제 파일 구성·읽기·갱신을 만들 수 있다.01-02 전체 완료·03 최종 구성·06 전환 계획 완료로 올리지 않는다.
