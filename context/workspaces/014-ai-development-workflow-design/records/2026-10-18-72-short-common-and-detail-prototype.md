# 짧은 공통·이름과 가독성 절을 기존 시안에 반영

2026-10-18. 사용자 요청에 따라 [기존 시안](prototypes/applied-criteria-2026-10-17/README.md)에 **짧은 공통과 이름·가독성의 독립 절**을 반영했다. [주문 작업 장면](prototypes/applied-criteria-2026-10-17/order-walkthrough.md)에서 실제 문서 링크로 필요한 상세·사례를 찾으며, [03의 재판단](prototypes/applied-criteria-2026-10-17/refinement-walkthrough.md)에는 이번 이유와 다시 볼 조건을 남겼다.

## 사용자 선택과 이번 범위

사용자 원문:

> 그럼 공통은 짧게 두고 이름·가독성은 별도 절로 두는 방향으로 기존 시안에도 반영해줘. 필요한 상세 기준이나 사례를 어떻게 찾아가는지 실제 문서로 보여주고, 03에서 다시 판단할 부분과 이유도 같이 남겨줘.

직전71까지는 이 구성이 Main의 추천이었고 prototype은68 상태였다. 이번 요청은 해당 방향을 **시안에 반영하라는 선택**이다. 이를 계속 미채택으로 기록하지 않는다. 일반 코드 기준의 모든 문장을 전체 제품의 의무로 채택하거나, 현재 파일 수·네 주제·실제 스킬 설치를 최종 확정한 요청으로 확대하지 않는다.

문서와 단계별 읽기 화면을 수정했다. shop-web은 가상이며 실제 제품 코드·테스트는 없다. 주문은 구현 전 요구·판단 상태, HTTP는 앞서 완성된 가상 실행 결과를 보여 주는 장면으로 구별한다. 01-02와03은 완료 처리하지 않았다.

## 이 형식에 도달한 근거

[구성안70](2026-10-18-70-criteria-organization-proposal.md)은 아홉 판단축과 정보의 역할을 연결했고, [대입71](2026-10-18-71-order-reading-and-criteria-boundaries.md)은 공통에 무엇을 남길지와 표현만의 판단이 남는지를 주문에서 비교했다. 이번에는 해당 추천을 실제 문서와 연결에 옮겼다.

71에서 구별한 근거도 보존한다. [주문49](2026-10-16-49-order-mutation-workflow-boundaries.md)의 같은 API·다른 흐름과 [관련 개선52](2026-10-16-52-related-refactoring-and-product-scope.md)의 같은 장바구니 흐름은 다른 조건이다. 세 화면의 비대기는71의 추가 가정이다. [표현45](2026-10-16-45-naming-readability-supplement.md)는 더 명확함과 반드시 수정할 필요를 구별한다.

[외부 비교61](2026-10-17-61-reference-comparison-for-format-design.md)의 의미·조건을 가까이 두기, 상황과 질문으로 구별하기, 필요한 자료를 선택해 읽기라는 참고를 이어 쓴다. 네 주제나 독립 이름 절이 외부 자료의 정답이라는 주장은 아니다. 이번 변경에서는 외부 자료를 새로 조회하지 않았다.

## 03에 남긴 재판단과 반영 방식

03은 공통이 충분히 짧은지라는 길이 평가만 하지 않는다. 실제 작업자가 관점을 알아차리고 필요한 상세를 찾아 적용하는지 본다. 이름·가독성 절의 독립 판단이 남는지, 상세·사례의 분량·소비·관리 조건이 분리 또는 통합을 지지하는지, 현재 계약과 Work 요구가 각 정본에서 실제 코드와 맞는지 확인한다. 기존 스킬의 입구·읽기·갱신 책임은04-03과 함께 대조한다.

같은 파일의 절 링크는 찾을 위치를 제공한 것이며, 실제 AI 입력량을 줄였다는 근거가 아니다. 기존 스킬이 파일 전체 또는 선택한 절을 읽는 방식도 후속에서 확인하고, 그 조건으로 파일 분리를 다시 판단한다.

앞선66의 후속 장면은 다음 가정에서 사례 통합을 제안했다.

> 작은 Project에 일반 기준이 두 개뿐이고, UI 공통화 작업에서는 원칙과 Field·Container의 짧은 대비를 항상 함께 읽으며, 같은 담당자가 함께 관리할 예정이라고 가정해 보자.

당시 결론은 ‘quality 한 파일 안에서 일반 원칙과 조건별 판단 사례를 절로 구별하는 안’이었다. 이는 실제 사용을 관찰한 결과가 아니었다. 현재 시안은 상세 네 절과 주문 장면을 포함하므로 이 가정을 그대로 현재 사실로 이어받지 않는다. 새 후속 문서는 통합·분리·현재 유지의 조건을 드러내며 과거의 통합 제안을 정해진 후속 결론으로 강제하지 않는다.

후속에서 바꾸면 Project 본문·읽기 안내·관련 스킬 참조와 작업 장면을 함께 맞추고,01-02에 기준 의미나 분류가 달라진 근거를 돌려준다. 현재 형식만 옮겨 놓지 않고 선택 이유·사용자 정정·새 조건을 조합한다. 이번 사용자 선택과 과거 원문은 기록으로 유지한다.

## 확인 범위

주문 문서 작성은 범위가 정해진 담당자에게 맡겼고 Main이 기준·진입·후속 연결과 통합을 맡았다. 문서·링크·화면 확인 결과는 아래에 기록한다. 실제 제품 적용·테스트·장기 읽기 효과를 확인한 것은 아니다.

- 별도 읽기 담당자가 사용자 요청·기존 근거와 현재 시안을 대조했다. 주문49의 공유 범위를 ‘공통 요청 상태’로 옮긴 한 문장을 ‘공통 캐시 무효화’로 고쳤고, 조건부 읽기·형식 선택·가상 상태·후속 재판단에서 다른 실질 누락이나 모순은 보고하지 않았다.
- 현재 진입·후속 문서, prototype과 이 기록을 합한 Markdown30개에서 로컬 링크612개·절 앵커50개를 확인했다. 대상·앵커 누락과 줄 끝 공백이 없었고 `git diff --check`도 통과했다.
- 단계 보기에는 최신 문서20개를 반영하고 본문 안의 문서·절 연결을 따라 이동할 수 있게 했다. 임시 브라우저에서 주문·공통·읽기 안내·이름 절·주문 사례·03·반영 이유로의 이동과 폭320~1024 범위의 가로 넘침을 확인했고 실행 오류는 없었다. 이는 문서 보기의 동작 확인이며 AI의 실제 기준 발견·적용 효과나 제품 테스트가 아니다.
