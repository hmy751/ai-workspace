## 마지막 정정과 실제 수정

사용자는 관리 원칙의 마지막 문단을 인용하며 “viewer는 뭐하러 둔거야?”라고 물었다. 그 문단은 열람 도구의 정적 검사와 의미 판단의 차이를 설명하려고 넣었지만, 특정 표시 도구의 운영을 본문 관리 원칙에 끌어들였다. 질문에 답한 시점에는 파일을 수정하지 않았으며, 다음 요청에서 수정·기록·커밋이 명시됐다.

> 그래 수정하고 그럼 일단 현재까지 대화 바탕으로 작업한거 랑 워크스페이스에 기록 남길거 잘 남겨두고 커밋하자

[CONTENT-POLICY.md](prototypes/development-workflow/noline-demo/context/CONTENT-POLICY.md)의 viewer 링크와 마지막 문단 전체를 제거했다. 바로 앞 문단의 본문·맥락·근거를 대조하는 기준은 유지했다. 도구별 검사 범위는 기존 viewer 안내가 소유하고, viewer 자체를 삭제하거나 제품 동작을 바꾸지는 않았다.

## 이번 대화에서 남길 판단

- 본문에 설명을 더하는 일과, 본문을 형성한 의도·배경·목적·판단을 가까이 보존하는 일은 각각 필요하다. 중앙 작업 기록에만 의존해 형성 맥락을 다시 복원하게 하지 않는다.
- 현재 읽고 쓰는 본문과 형성 자료의 역할을 구별한다. 상세·절차·사례처럼 나누어 둔 본문도 같은 사용 층에 속한다. `index.cases.md`는 `index.<내용 이름>.md` 배치의 한 예이며 필수 파일이 아니다.
- 주제 폴더의 시작 본문은 `index.md`로 두는 방향을 원칙에 구체화했다. 상위 README의 구성·운영 안내 역할과 구별한다.
- background의 현재 맥락, 해당 주제의 형성과 변경 기록, 필요한 근거는 처음부터 책임을 구별한다. 역할 분리와 매번 읽는 양을 혼동하지 않는다. 원칙의 `records/`는 확정 결정뿐 아니라 선택·정정·유보를 담으려는 구체화이며, 과거의 decisions 명칭 논의는 그대로 보존한다.
- 의도·배경·목적은 가능한 한 남기고 싶다는 사용자 선호다. 고정된 세 제목이나 빈 파일을 채우는 규칙으로 바꾸지 않는다.
- 현재 맥락은 읽히는 설명으로 갱신하고, 당시 선택과 원문은 당시 조건과 지위를 보존한다. 실제 실패·예상 위험에 따른 미채택·조건 변화에 따른 교체를 구별해야 재검토나 복귀를 판단할 수 있다.
- 본문을 바꾸는 작업자가 관련 자료의 영향을 확인한다. 일반 사용·의미 변경·표현 수정·새 근거·이동에 필요한 읽기와 갱신은 다르다. 폴더·링크·자동 검사만으로 의미의 유지가 보장되지는 않는다.
- Personal·Project·Work의 내용 소유와 바깥014의 작업 기록 경계는 유지한다. 주제에 필요한 형성 맥락을 선별해 가까이 두되 작업 전체를 복제하거나 실제 작성 논의를 예제 제품의 사건으로 바꾸지 않는다.
- 외부 자료는 설계 참고다. 이 파일명과 구성이 특정 인물이나 외부 표준이 정한 정답인 것은 아니다. 정확한 문장과 배치는 사용자 방향을 Main이 구체화한 것으로 구별한다.

현재 안내의 당시 상태와 최신 상태도 대조했다.109 당시의 기록 명칭 제안·공통 원칙 미반영을 현재 상태로 오독하지 않도록 시점을 명시하고,110에서111·112로 이어지는 후속 안내를 추가했다. 변경한 Markdown의 로컬 링크530개를 확인했다. 실제 연결의 누락은 없었고, 두 독립안의 인용된 문서 예시에 있는 아직 만들지 않은 경로6개는 제안 원형으로 보존했다.
