# 재개 안내와 직접 검증 흐름을 프로토타입에 적용

2026-11-04. 사용자는 Verify 아카이빙 방향을 선택하고 Recover의 재개 역할을 별도 안내 파일과 공통 기준으로 전환하기로 했다. 파일명·형식·배치·관리 책임을 구체화한 뒤 “그래 그럼 그 안으로 프로토타입부터 적용해봐”라고 요청했다. 이번에는 prototype에 적용했으며 Reference 실행기와 기존 증거의 실제 아카이빙은 후속이다.

## 선택한 의미와 원문

사용자는 단순히 Harness 없이 실행할 수 있는지가 아니라 없앨 때 생기는 빈틈을 고려하라고 정정했다. 이어 재개에서 읽을 양과 의미의 연속성을 함께 요구했다.

> “워크스페이스 다 읽으면 당연히 좋긴하지 근데 양이 엄청 많아질수 있잖아? 중요한건 그것같아 다른 대화세션으로 넘어가도 흐름이나 뉘앙스나 이런게 잘 유지되는 기준”

별도 recover류 파일을 선호했지만 JSON을 고정하지 않았고, 공통 구성 기준은 진입 지침·스킬 등의 위치를 비교하자고 했다. 공통 지침과02 안내 예시를 대조한 뒤, Workspace 루트 `recover.md`, Work 진입 지침의 공통 기준, 기존 current의 내용 소유, 생성 담당과 record-work의 갱신 역할을 적용안으로 선택했다.

검증은 development와 중복되는 새 책임을 만들지 않았다. [Verify 기능 비교](2026-11-04-verify-removal-tool-comparison.md)에서 직접 검사·Git/해시·결과 저장으로 가능한 부분과 자동 증거 묶음·자식 프로세스 종료 보장의 차이를 확인한 뒤 아카이빙 방향을 정했다. 도구의 대기 시간을 강제 종료 시간으로 간주하거나 기존 기계 보장이 전부 같다고 주장하지 않는다.

원문 접근점은 현재 대화 `01a185c9-de03-7111-8615-110dd6ca1122`의 [로컬 원문](/Users/hammyeong-yeon/.codex/sessions/2026/10/29/rollout-2026-10-29T12-52-41-01a185c9-de03-7111-8615-110dd6ca1122.jsonl)이다. 재개 요구 L1791·L1813·L1826, 초안 평가 L1899, Verify 비교·아카이빙 선택 L1923·L2019, 적용 승인 L2033을 연결한다. 최소 직접 발화와 현재 선택 이유는 prototype의 [재개 형성 기록](prototypes/development-workflow/skills/record-work/_background/records/2026-11-04-recovery-guide.md)에도 보존해 바깥 원문 없이 읽을 수 있게 했다.

## 확인한 범위

- 열람 화면을 재생성했다. 문서245개·코드5개, 내부 링크1409개·앵커326개에서 누락0개이며 원문/SHA·클라이언트 문법 확인을 통과했다. 브라우저 배치·클릭 시험은 하지 않았다.
- 수정한 스킬의 필수 YAML 값을 Ruby 파서로 확인했다. 공식 quick_validate는 기존 환경의 PyYAML 부재로 실행할 수 없어 의존성을 새로 설치하지 않았다.
- 이번 변경 직전과 비교해 Reference의 조사한411개 파일은 동일했고, prototype의 예제 코드·원자료·과거 작업 기록15개 파일도 동일했다. 이는 이전 미커밋 변경을 되돌렸다는 뜻이 아니라 이번 적용 전 상태를 보존했다는 뜻이다.
- 부모 대화·예상 결론을 주지 않은 새 독자 둘에게 일반 재개와 이름 비교의 한정 요청을 각각 맡겼다. 둘 다 현재 완료 경계·유지 대안·선택 이유와 실제품 통합/수락의 미확인을 복원했다. 일반 독자는27개 자료를 읽었고 한정 독자는 일반 재개용 state/output 전체·무관한 과거 기록으로 확장하지 않았다. 각 독자는 읽은 파일 전체를 확인했으며, 절 단위 선택의 효율이나 읽기량 감소를 입증한 실험은 아니다.
- 독자들은 코드·문서 수정이나 검사 재실행 없이 읽기만 수행했다. 당시7개 제품 검사 통과를 이번 새 실행 결과로 보고하지 않았다. 반환과 핵심 진입 입력은 [읽기 확인 자료](experiments/recovery-guide-2026-11-04/README.md)에 보존했다.

새 Workspace 생성 수행, record-work가 실제 방향 변경을 받아 recover를 갱신하는 수행, 중단 복구와 장기 사용 비용은 이번 읽기 확인에 포함하지 않았다. 별도 읽기 두 사례의 성공을 모든 재개·기록 수행의 보장으로 확대하지 않는다.

## 남은 적용과02 범위

후속은 Reference의 재개·생성·이식·CLI·기계 상태 소비를 새 계약에 맞추고, Verify와 관련 실행 의존성을 복원 가능한 위치에 아카이빙하는 일이다. 기존 검증 증거는 원래 Work의 근거로 접근할 수 있게 유지해야 한다. 이번 변경은 Reference/Noline 적용이나 전체02 완료가 아니다.

02의 후일 과정 보존·문서 중복·Workspace 구성과 운영 비교는 남아 있다. 앞선 [문서별 중복 비교안](2026-10-30-ticket02-document-duplication-comparison.md)은 참고한 미채택 비교안이며 이번 적용으로 모든 문서 재배치안을 채택한 것은 아니다. Commit·push는 하지 않았다.
