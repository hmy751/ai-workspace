# 01-02에서 알게 된 것과 남은 작업

2026-10-14. 실제 코드 사례를 더 살피기 전에, 01-02의 목적과 현재까지 얻은 판단 기준·남은 일을 대조한다. 아래 충분성 평가는 Main의 판단이며 사용자 acceptance나 Ticket 완료 선언이 아니다.

**후속 보정:** 사용자가 컴포넌트 밖 코드의 추가 논의 필요성을 물었다. 다른 코드 영역의 대표성을 확인하지 않은 충분성·순서 판단은 [기록 41](2026-10-14-41-template-coverage-and-next-code-areas.md)에서 보정했다. 아래 확보한 기준과 남은 검토·수정 작업은 유지하며, 추가 탐색보다 초안을 먼저 만들자는 권장은 현재 다음 행동으로 사용하지 않는다.

## 이번 정리의 계기

사용자는 실패 처리와 검증으로 논의를 이어가는 데 동의했고, 기존 목록 유지·하단 오류·재시도 상황의 코드 비교를 요청했다. 이후 다음과 같이 논의 목적과 이해 흐름을 확인했다.

> 잠깐 근데 이 질문들은 왜 한거지? 기록 이후에?

> 실패 상황까지는 그렇다 치고 근데 갑자기 버튼 얘기가 나와서 중간에 좀 나도 이해가 잘 안돼서

> 그럼 지금까지 나온 걸 기준으로 01-02에서 뭘 알게 됐고 뭐가 아직 부족한지 정리해보자. 더 얘기할 게 필요한지도 보고.

Main은 실패 시 보장과 검사 기준을 알아보려던 대화가 버튼·슬롯 API의 상세 설계로 옮겨 갔고, 그 비교가 01-02에 더하는 판단을 설명하지 못했다고 답했다. 실패 처리 조사 자체를 거부한 발화로 읽지 않는다. 기록 39의 코드 관찰은 유지하되 버튼 설계는 현재 이어갈 작업에서 내린다.

실패 처리에서는 fetcher·React Query·Container·관찰 Hook의 현재 역할, 입력 규칙과 RHF·UI의 책임, 입력 검증과 개발 테스트의 차이를 확인했다. 이는 [39](2026-10-14-39-failure-handling-and-verification-code.md)의 코드 관찰이다. 테스트 부재 관찰이나 설명용 재시도 코드로부터 사용자의 선호·필수 검사 수준을 추출하지 않는다.

## 더 대화할 필요에 대한 판단

현재는 새로운 컴포넌트를 더 골라 사용자 취향을 묻거나 버튼 API를 완성할 필요가 없다. Main이 이미 있는 재료로 **판단 기준·적용 조건·유지/수정/보류 근거를 담은 작업용 초안**을 먼저 만들고, 기존 사례 하나에 적용한 결과를 함께 검토하는 순서를 추천한다. 그 과정에서 실제로 결론을 바꾸는 미결정만 사용자에게 묻는다.

예를 들어 Field를 보고 '연결 코드가 반복되므로 하나의 RHF 입력으로 합친다'고 바로 결론내리지 않고, 현재 합성의 목적·구체적 변경 요구·의존성 범위를 검토해 유지할 수 있어야 한다. 반면 검증 안내와 실제 규칙의 불일치처럼 요구 확인이 필요한 관찰은 구분해 제시해야 한다. 이것은 다음 초안이 유용한지 확인하는 예이며, 템플릿 코드 수정이나 특정 테스트 의무의 승인으로 쓰지 않는다.

01-02는 **핵심 구조 기준의 탐색 재료를 확보했고 검토·수정 방법으로 구체화할 일이 남은 상태**다. 사용자 취향을 더 말해 줘야만 진행할 수 있는 상태도, 전체 완료도 아니다. 다음 작업의 권장 순서이지 새 스킬·하네스 구현의 채택은 아니다.

## 반영과 확인 범위

현재 Ticket·state·진입 문서에 같은 상태를 반영한다. 기존 관찰·사용자 선택·미실행 제안은 해당 기록에 남긴다. 문서만 수정하며 실제 템플릿·제품·글로벌 지침·스킬·자동 Maintainer는 변경하지 않는다. 실행 테스트나 커밋은 만들지 않았다. 링크·공백 검사 결과는 state에서 찾는다.
