# 전체 설계와 Spec·Ticket의 사용 방향 재검토

2026-10-13. 사용자는 개별 자료 대조보다 전체 방향과 Spec·Ticket을 어떻게 사용해 작업을 모을지 폭넓게 고민해 달라고 요청했다. 이 기록의 운영상 제안과 전체 설계 가설은 논의용이며 아직 채택하지 않았다. 기존 B 선택과 01-02 자료 탐색의 유효한 내용은 유지한다.

## 직접 요청과 정정

앞서 사용자:

> 니설명이 뭔가 이해가 팍 안돼 그리고 글로벌에 코드 퀄리티는 신경쓰지마 짜치니까

AI는 코드 퀄리티 문서를 이번 설계 논의의 비교 기준에서 빼겠다고 응답했다. 기록 19의 CODE-QUALITY 대조는 당시 분석으로 남기며, 기존 문서가 이미 요구한다는 사실로 앞으로의 설계 선택을 제한하지 않는다. 실제 코드 작업의 적용 지침을 수정하거나 삭제한 것은 아니다.

이후 사용자:

AI가 개별 자료 대조부터 시작하려 하자 사용자:

> 지금 대조보다 방향성과 스펙 티켓 등 뭔가 어떻게 해결할지 등 좀 더 폭넓게 도 생각하고 고민해봐줘

Feature Map과 라우팅, Matt와 Lauren은 겹침·충돌 가능성을 설명한 예다. 대체 가능성이나 실제 충돌을 확인받은 결론으로 기록하지 않는다. 사용자의 고유 코드 기준 전체도 아직 파악했다고 보지 않는다.

## 현재 문서와 진행에서 확인한 것

Main은 현행 Spec·design-map·Ticket 색인·07, 분해 당시 기록 05·09를 확인했다. Spec에는 넓은 목표·기준·제약·B 선택이 있고 Ticket에는 부분별 결과와 연결이 있다. 그러나 지금 만들려는 전체 체계의 구체적인 잠정안과 각 논의가 그 안을 어떻게 바꾸는지는 충분히 모여 있지 않다. design-map도 영역과 Ticket의 연결 중심이며, 현재 설계안 자체를 보여주지 않는다.

`ai-self-check`의 별도 읽기 전용 점검에서도 Main이 분류 위치를 통합 방법 대신 설명했고, 01-02 탐색이 전체 설계에 주는 영향을 보이지 않았다는 판단을 받았다. 01-02 진행은 사용자도 선택한 것이므로 이를 전부 잘못된 선택으로 되돌리지 않는다. 개별 자료의 설명을 더 늘리거나 모든 Ticket을 한꺼번에 상세화하는 대신, 현재 전체안과 그것을 바꾸는 결정을 중심에 놓는다.

## 전체 설계의 중심으로 삼을 제안

산출물은 한 개발 작업의 역할 순서만이 아니라 **Project의 지속적인 개발 환경과 그 위에서 작업·판단·기록·개선을 이어가는 체계**다. 다음은 그 안을 논의하기 위한 잠정 구성이다. 새 폴더·역할·스킬을 이 개수대로 만든다는 뜻은 아니다.

- **Project에서 계속 갖추는 것:** 제품 의미와 선택 이유, 개발자가 따를 코드 패턴·기준, 검사와 실행·관찰 수단, 필요한 내용을 찾는 경로. 문서로만 해결하거나 모든 자료를 기본 입력으로 넣는 것을 전제하지 않는다.
- **한 작업을 수행하는 방식:** Main이 사용자와 결과·범위를 구체화하고, 필요한 공통 맥락과 작업 상태를 선택해 구현·검토에 연결한다. B의 검토자는 직접 개선하고 실제 확인을 이어갈 수 있다. 결과·기준이 충돌하면 필요한 선택과 이유를 드러내며, 사용자는 개선된 결과와 판단에 필요한 근거를 받는다.
- **작업 중·이후에 남기는 것:** 현재 선택·미완료·근거를 이어가는 Work 맥락과, 나중에 재검토할 분석·대안·시도·결과를 목적에 맞게 남긴다. 제품·구조의 공통 사실과 선택은 Project의 적절한 위치로 연결한다. 구체 파일 구성과 갱신 책임은 여전히 설계할 대상이다.
- **경험으로 개발 환경을 바꾸는 방식:** 잘된 결과와 반복 마찰에서 개선 후보를 찾고, 코드 구조·검사·도구·기준·스킬 중 어디에 반영할지 판단한다. 프로젝트 경험을 ai-workspace로 가져오고 다시 적용하는 비용도 본다. 기록 갱신과 새 기준 채택을 같은 행동으로 자동화하지 않는다.

예를 들어 ‘검토자가 제품 의도·관련 코드·실제 확인 경로를 스스로 찾아 개선할 수 있는가’를 하나의 설계 질문으로 잡을 수 있다. 여기에 어떤 내용이 필요하고 어디에서 소유하며 어떻게 선택해서 읽고 실행할지를 먼저 구체화한 뒤, Feature Map·Vercel 라우팅·기존 Project 구성의 제안을 판단한다. 각 자료의 파일 이름을 먼저 채택해 같은 정보를 중복 관리할 필요는 없다. 반대로 관계를 모른 채 특정 방법이 다른 방법을 대체한다고 단정하지 않는다.

## Spec과 Ticket을 사용할 방법 제안

Spec은 기존 목표·제약을 유지하면서 **현재 전체 설계안, 그 안에서 이미 선택한 것과 가정하는 것, 전체를 바꿀 중요한 미결정**이 보이게 보완할 수 있다. 새 통합 장부를 추가하기보다 기존 Spec을 중심으로 삼는 안이다. 이번에는 Spec 구조를 실제로 재작성하지 않았다.

Ticket은 이 전체안의 미결 문제를 조사·비교·구체화하는 상세 작업으로 사용한다. 논의에서 선택이 생기면 어느 전체 설계 가정이 달라지는지 함께 설명하고 Spec에 반영한다. 세부 분석과 대안은 Ticket·records에 남긴다. 번호순으로 각 Ticket을 완료한 뒤 마지막에 조립하는 방식이나, 단지 서로 링크됐으니 통합됐다는 판정을 피한다.

지금 Ticket을 전부 합치거나 새로 번호 매기는 것은 제안하지 않는다. 전체안이 보인 뒤 중복된 결정을 여러 Ticket이 따로 소유한다면 그 범위를 조정한다. 07의 통합 확인도 마지막에만 생기는 일이 아니라, 부분 선택이 전체안에서 성립하는지 수시로 살피는 데 연결한다.

## 다음에 무엇을 진행할지

현재 전체 설계의 잠정안을 사용자에게 먼저 보여주고, 무엇이 선택됐고 무엇이 아직 여러 형태가 가능한지 같은 자리에서 설명하는 것이 Main의 제안이다. 그다음 전체 형태에 영향을 주는 질문부터 관련 Ticket을 선택해 구체화한다. 01-02의 깊은 모듈 설명을 자동으로 더 이어가거나 Feature Map 비교부터 시작하는 것으로 고정하지 않는다.

자료는 설계의 근거와 후보이며 채택 권위 자체가 아니다. 사용자 기준은 구체 사례와 선택에서 드러내며, 아직 표현되지 않은 내용을 AI가 대신 확정하지 않는다. 기존 제안은 ‘미채택’이라는 표시만 남기지 말고 현재 전체안에 어떤 의미가 있고 무엇을 판단해야 하는지도 보이게 할 필요가 있다. B 선택, 자동 Maintainer 중단, Project·Work·기록·경험 반영을 포함한 전체 범위는 유지한다. 실제 스킬·하네스·제품 변경이나 새 커밋은 수행하지 않았다.
