# DB·인증 사례의 스킬 요구와 실제 대응 비교

후속 결정: 사용자는 이 구조 개선 사례를 **이후 워크플로 설계에서 다루기로 했다.** 아래의 사례 추가 제안은 채택안이 아니며, 실제 수행 부족을 스킬 사례 보완으로 곧바로 연결한 판단은 수정했다.01-01·01-02에서 구현·검토·완료 책임을 다룰 근거로 보존한다.04-01의 다음 사례와 결정 원문은 [재선별 기록](2026-10-20-ticket04-01-definition-reconsideration-cases.md)에 있다.

2026-10-20. **이 사례에서 먼저 확인되는 문제는 필요한 기준이 없었던 것보다, 이미 알고 있던 구조 개선 목표를 작업 이해안·구현 결과·완료 판단까지 충분히 이어가지 못한 것이다.** 제품 동작 선택과 재판단에는 실제 효용도 있었다. 두 스킬을 전면 재작성하거나 모든 구현 뒤 자동 호출할 근거로 삼지 않는다.

현재 결과는 04-01의 첫 사례 대조와 보완 방향 후보다. 아래 보완 대응은 현재 분석에서 만든 예이며 당시 발화가 아니다. 스킬 본문·제품 코드·운영 설정은 변경하지 않았고, 후보의 수행 효과를 실험하지 않았다.

## 요청과 확인 범위

사용자 요청:

> DB·인증 사례부터 기존 스킬이 요구한 거랑 실제 대응을 비교해보자. 스킬 자체를 보완할 문제인지, 이미 있는 기준을 제대로 수행하지 못한 건지도 같이 봐봐

앞선 [source 확인](2026-10-20-ticket04-01-source-review.md)에서 고른 같은 개발 세션의 작업 정의·첫 구현·재판단·후속 정정과 리뷰 수용을 읽었다. 중심 범위는 아래 개발 원문의 `source_line` 80~1067이다. 그 뒤 별도 인증 정책 논의까지 같은 실패로 합치지 않는다.

- [개발 원문](../source/noline-evaluation/corpus/01a0b2ee-2d11-7b33-ba80-2ceeb380a0ae/messages.jsonl): 사용자의 요청·선택과 AI의 공개 보고. `source_line`은 JSONL 물리행과 다르다.
- [work-discussion 보존 기준판](../source/noline-baseline/.claude/skills/work-discussion/SKILL.md), [reconsider-work 보존 기준판](../source/noline-baseline/.claude/skills/reconsider-work/SKILL.md).
- [사용자 인터뷰](../source/noline-evaluation/reviews/interview-20261012.md), [설치·사용 조사](../source/noline-evaluation/reviews/noline-context-usage.md), [문서 판본 색인](../source/noline-evaluation/document-index.md).

제품 코드를 새로 실행하거나 당시 미커밋 코드 전체를 복원하지 않았다. 코드의 구체 결함·테스트 수·리뷰 결과는 당시 AI의 보고로 구별한다. 사용자 정정과 AI의 자기 설명만으로 기술 해법의 객관적 우열이나 장기 만족을 확정하지 않는다.

## 당시 스킬과 비교할 수 있는 정도

문서 색인은 두 스킬 모두 최초 `aa2314cd`부터 마지막 보존 `4fb309d2`까지 내용 판본이 하나라고 기록한다. work-discussion의 [보존 blob](../source/noline-evaluation/documents/blobs/ff2ba390217e8823810cb85422b42d030460b993.md)과 reconsider-work의 [보존 blob](../source/noline-evaluation/documents/blobs/fb435f71745693bd75433beeef2cc9199f129b22.md)은 현재 source 기준판과 각각 바이트가 같고 Git blob hash도 일치했다.

따라서 단순히 나중에 강화된 스킬을 과거에 소급하는 비교로 보기는 어렵다. 당시 대화에는 work-discussion 직접 호출(109)·적용 선언(113), reconsider-work 적용 선언(432)이 있고, 기존 사용 조사도 각각의 실제 본문 열람을 확인했다. 다만 해당 세션의 도구 출력 본문은 source에 보존되지 않아, 읽은 순간의 임시 미커밋 변형까지 배제하는 바이트 단위 증명은 하지 못했다.

Spec·Ticket은 여러 판본이 있다. 이번 범위에서 정확한 시점별 문서 묶음 전체를 재구성하지 않았다. 구조 목표는 당시 AI가 구현 전부터 언급한 80, 사용자의 427, 재판단 응답 432·443 등 같은 세션의 직접 근거로 확인한다. 문서 갱신 계약의 수행 여부는 이 자료만으로 확정하지 않는다.

배치에 관한 보조 근거로, [앞선 파일별 검토 기록](../source/noline-evaluation/documents/blobs/734dec78c4f447aead7b514d297b6b661cfdd30d.md)은 사용자의 “그럼 그냥 layout에 두자 그냥” 선택과 내부 유지를 보존한다. [후속 기록](../source/noline-evaluation/documents/blobs/21b8d833cc2fc4bdcb0976af03306ca33dd3cbfa.md)은 그 당시 선택과 이후 application 분리를 구별한다. [품질 Spec의 짧은 보존판](../source/noline-evaluation/documents/blobs/7b6b1cdf557cce744d7567e2b751e9c6a4dc507b.md)에도 실제 코드 개선과 동작 보존의 근거가 모두 필요하다는 기준이 있다. 이를 각 발화 순간의 전체 문서판을 복원한 증명으로 확대하지 않는다.

## 기존 기준을 더 잘 수행했다면 달랐을 대응

아래는 당시 코드의 정답 설계가 아니라, 기존 스킬 요구를 충족하도록 현재 분석에서 구성한 대응 예다. 새 질문이나 문서를 반드시 추가하는 안은 아니다.

**work-discussion의 최종 이해안에서:** 제품 선택을 정리한 뒤 이번 구조 개선과 확인할 관계를 연결할 수 있었다.

> DB 실패에는 안내·재시도를 추가하고, 인증 정보 없음·읽기 실패는 기존 로그인 이동을 유지한다. 함께 해결할 구조 문제는 준비 완료의 뜻과 판정을 여러 소비자가 따로 해석하는 부담이다. 구현에서는 준비 순서·완료 판정·하위 화면의 책임을 명확히 하고, 동작 시나리오 검사와 별도로 그 관계가 변경 전보다 어디에서 더 분명하게 읽히는지 확인한다. layout 내부 배치는 현재 출발점으로 유지하되, 이 배치가 구조 목표와 충돌하는 근거가 나오면 기존 선택 이유와 함께 다시 판단한다.

여기서 구현 전 모든 모듈을 설계할 필요는 없다. “어떤 파일로 나눌까요?”를 사용자에게 묻는 대신, 이미 확인한 문제와 AI가 입증할 개선 효과를 이어 주는 것이 차이다. 기존 Spec 전체를 매번 복사할 필요도 없다.

**reconsider-work의 첫 후속을 평가할 때:** 중복 제거와 실행 연결의 이득을 인정하되, 모았다는 사실이 책임 분리까지 증명하지 않음을 확인할 수 있었다.

> 중복 준비 상태와 간접 재시도는 정리됐다. 이것으로 앱 준비·화면 선택·로그인 후 작업의 관계까지 충분히 정리됐는지는 별도로 본다. 각 작업의 시작·끝·재시도와 상태 소유를 따라가, 함께 바뀌는 책임과 서로 다른 수명 때문에 나눌 책임을 비교한다. 현재 배치를 유지할 이유와 다른 배치로 바꿀 때의 비용을 함께 제시하고, 확인하지 못한 부분은 구조 개선 완료로 보고하지 않는다.

이 예는 매 작업의 전체 수명 분석이나 특정 세 구성요소 분리를 의무화하지 않는다. 이 장면에서 “초기화”라는 이름과 한곳 배치만으로 설명하지 못했던 관계를 구체적으로 대조하는 방법이다.

## 스킬 보완과 실행 방식 보완을 나누는 판단

**유지할 것:** 직접 호출에 따른 work-discussion의 선택 구체화, 코드로 답할 사실을 AI가 조사하는 책임, reconsider-work의 근거 있는 조건부 발동, 기능·구조와 구현 부족·가정 부족의 구별. 이 사례는 이 요구를 삭제하거나 새로운 의무로 대체할 근거가 아니다.

**04-01의 보완 후보:** 기존 문구를 더 강하게 반복하기보다 위와 같은 짧은 대비 사례로 실제 결과의 차이를 보이는 안이다. work-discussion에서는 새 제품 선택을 마친 뒤에도 기존 구조 목표가 이번 결과·확인에 이어지는 모습을, reconsider-work에서는 특정 방법으로 일부 개선한 것과 원래 목표를 충분히 달성한 것의 차이를 보여 준다. 현재 조항으로 수행 가능한 행동이므로 새 책임을 만드는 안이 아니라 적용의 구체성을 높이는 후보다. 스킬에 넣을지 관련 개발 기준·예시로 연결할지는 아직 정하지 않았다.

**01-01·01-02와 함께 다룰 것:** 구현자가 선택한 기준을 실제 코드에 적용하고, 보고 전에 결과·구조·검증을 대조하는 책임이다. 사용자가 구조 문제를 지적한 뒤 reconsider-work를 호출한 장면만 개선해서는 첫 결과의 부족을 모두 해결할 수 없다. 그렇다고 매 Ticket 종료에 두 스킬이나 독립 reviewer를 의무 호출할 근거도 없다. 이번 사용자 요청으로 붙인 독립 리뷰의 기여와 보편적 역할 배치의 효과는 다르다.

**06과 남겨 둔 것:** 보존 스킬의 Main·Maintain 인계 계약을 현재 운영에 맞추는 일. 이번 구조 문제의 원인이 문서 갱신 실패였다고 확인하지 않았으므로 인계 계약 수정만으로 이 사례가 해결된다고 주장하지 않는다.

다음에는 위 대비가 기존 본문만으로도 충분히 수행되는지, 예시 보완이 실제 선택·반환에 차이를 만드는지 좁은 장면에서 확인할 수 있다. 재실험이 모든 문구 변경의 의무라는 뜻은 아니며, 실제 효과 주장을 하려면 필요한 후속 근거라는 의미다. 사용자에게 이미 답한 선택을 다시 묻거나 최초 사례의 기술 모양을 새 표준으로 만들지 않는다.

## 확인과 한계

Main은 범위 내 개발 발화와 스킬 본문, 판본 색인·blob을 직접 대조했다. 별도 읽기 전용 조사자는 판본·계약 근거를, 앞선 대화와 Main 가설을 받지 않은 검토자는 요구·실제 대응의 충족과 부족을 대조했다. 제품 선택 과정의 효용, 첫 재판단의 구체 개선, 후속 충분성 판단의 한계를 구별해 위 판정에 반영했다.

이 기록은 당시 AI의 공개 행동과 근거 제시를 평가한다. 스킬의 모든 문장에 대한 실행 준수, 당시 코드의 객관적 최종 품질, 문서 갱신 완결, 특정 스킬의 인과 효과나 실제 사용자 부담 감소를 모두 증명한 결과는 아니다.
