# 6번 — 맥락 이해·적용부터 구현 완성·인계까지

**현재 지위: 사용자 요청에 따라 맥락 이해·적용과 개선 리뷰의 두 보완을 반영한6번 통합안.** 구현자가 필요한 맥락을 찾아 이해·적용하고, 맡은 결과의 설계·구현·자기 확인을 마친 뒤 Main이 재판단할 근거와 함께 넘기는 범위를 정리했다. 이번 반영은 설계안의 통합이며 development 실행 스킬 반영·운영 설치·수행 효과 확인과는 구별한다.

현재안은 아래 본문에서 읽는다. [개선 리뷰와 당시 Main 추천](#후속-개선-리뷰와-main-종합), [맥락 범위 확인과 통합 요청](#맥락-범위-확인과-통합-반영)은 형성 경과이며 당시 미반영 상태를 현재 상태로 취하지 않는다.

구현자의 책임은 **맥락 이해·적용, 구체 설계·구현, 자기 확인, 결과·근거 인계**까지다. 후속 검토가 있다는 이유로 첫 구현의 품질을 낮추지 않는다. 동시에 모든 대안의 열등함이나 모든 외부 환경의 동작까지 입증해야 검토할 수 있다고 요구하지 않는다.

## 기존 합의와6번의 범위

[3번 역할 합의](2026-10-22-shared-criteria-and-independent-review-decision.md#후속-확정--3번-역할별-책임-경계-마무리)는 이미 구현자의 구체 설계·구현·필요한 테스트·자기 확인 책임을 확정했다. 검토자는 그 결과와 기준 적용을 독립적으로 재판단하고, 검증자는 수정까지 반영된 결과의 요구 충족과 증거 충분성을 확인한다. Main은 전체 정합성·중요한 절충·종합·완료 판단을 맡는다.

[현재 development](prototypes/development-workflow/skills/development/SKILL.md)는 이 공통 책임을 반영했다. [적용 기록](2026-10-23-development-skill-prototype-adoption.md#다음-작업)이 남긴 6번은 자기 확인과 주요 선택·미확인의 반환 수준이다. 책임 자체를 다시 미정으로 열거나 모든 작업에 별도 구현자·검토자·검증자를 호출하는 안을 새로 정하는 항목이 아니다.

## 필요한 맥락을 이해하고 이번 결과에 적용한다

대상의 진입 지침과 Main의 배정에서 이번 목표·범위·보존 조건을 확인한다. 관련 Personal의 판단 기준·이유·적용 조건, Project의 제품 계약·개발 지침·현재 사실, Work의 Spec·Ticket·현재 선택을 실제 코드·사용처·실행 근거와 함께 읽는다. 외부 참고 자료는 현재 질문을 풀거나 대안을 비교하는 데 필요할 때 사용한다. Main이 전달한 자료는 출발점이며, 문서의 위치나 이름만으로 모든 내용을 같은 성격의 의무·사실로 취급하지 않는다.

읽은 내용을 이번 조건에서 어떻게 적용할지 판단한다. 약속·기준·현재 관찰·미확인 가정을 구별하고, 문서와 구현이 다르면 그 차이가 이번 결과에 무엇을 요구하는지 확인한다. 구현 중 새 사용처·실패·설계 질문이 드러나면 필요한 본문과 원자료를 다시 선택한다. 이미 유효한 근거는 사용하며 관련 없는 전체 자료나 모든 형성 이력을 반복해서 읽지 않는다. 추가 확인으로 풀 수 있는 사실은 직접 살피고, 목표·보존 계약이나 배정 권한을 바꿔야 하는 선택은 이유와 영향을 Main에 연결한다.

충분성은 자료를 읽었다는 보고가 아니라 **적용한 요구·기준·조건이 설계·구현·확인에 이어졌는지**로 판단한다. 관련 기준의 내용 정본은 Personal·Project·Work가 유지한다. 여기서는 그 내용을 복제하지 않고 구현자가 선택·이해·적용할 행동을 정한다. 세부 자료 전달 묶음과 동적 탐색 운영은 후속 항목에서 이어간다.

## 검토에 넘기기 전에 구현자가 끝낼 일

| 책임 | 결과에서 확인할 내용 |
| --- | --- |
| 맡은 요구를 실제 사용 경로까지 완성한다 | 이번 결과가 사용하는 호출부·설정·연결과 필요한 설명까지 맞춘다. 함수나 파일만 만들고 실제 사용처 연결을 남기지 않는다. 의도적으로 일부 단위를 맡았다면 그 단위의 경계와 남은 통합을 밝힌다. |
| 자기 설계와 코드의 적절성을 판단한다 | 관련 기준을 현재 조건에 적용하고 이름·책임·상태·흐름이 맡은 역할을 드러내는지 본다. 이번 요구와 실제 사용처에서 중요한 사용·변경 장면을 코드에 대입해, 호출자나 유지보수자가 알아야 할 순서·상태·변경 위치와 남는 부담을 살핀다. 선택을 가른 이유와 절충을 설명한다. |
| 변경 목적에 맞는 직접 확인을 한다 | 기능은 요구한 사용 경로·중요한 실패 조건, 버그는 원래 실패 조건에서의 수정 전후, 리팩터링은 보존 계약과 줄이려던 부담을 확인한다. 중요한 기대 결과는 요구·보존 계약·확인된 사례에서 가져오고, 검사가 구현의 계산이나 가정을 그대로 반복하는지 살핀다. 검사 통과가 입증하지 않는 부분도 구별한다. |
| 스스로 발견한 문제를 처리한다 | 맡은 범위와 권한 안에서 고칠 수 있는 누락·결함은 수정하고 영향받는 확인을 다시 한다. 범위·계약·권한을 바꾸어야 하거나 접근할 수 없는 조건이 있으면 문제와 영향을 Main에 반환한다. ‘검토자가 고칠 것’이라는 이유로 남기지 않는다. |

이 판단은 결과를 인계할 때 충분성을 살피는 기준이며 반드시 마지막에 한 번 더 수행하는 별도 전체 검토 절차는 아니다. 구현하면서 확보한 유효한 판단·검사 근거를 사용한다. 이후 변경이 그 근거를 무효화했다면 해당 부분을 다시 확인한다.

구조 개선이 작업 목표에 포함됐다면 동작 보존과 함께 어떤 이해·변경 부담이 줄었는지 실제 코드에서 판단한다. 예를 들어 ‘초기화를 한곳에 모았다’고 설명하는 데서 멈추지 않고, 재시도 때 호출자가 여전히 내부 상태를 조합하거나 순서를 알아야 하는지 따라간다. 이번 요구·실제 사용처·이미 드러난 부담에 관련된 장면을 선택하고, 읽기만으로 판단할 수 있으면 변경 실험까지 요구하지 않는다. 모든 대안 조사·별도 설계서·가상의 미래 기능 탐색이나 요청 밖 개선을 완성 조건으로 추가하지 않는다.

자기 확인의 깊이는 실제 변화와 영향에 맞춘다. 예를 들어 제품 계약이 ‘세션 저장 완료 뒤 다음 화면 진입’이라면 구현의 성공 반환값만 검사하기보다 저장 지연·실패에서 화면이 열리지 않는지를 확인한다. 기대 결과가 모호하면 구현에 맞춰 임의로 정답을 만들지 않고 필요한 판단을 Main에 연결한다. 모든 테스트에 출처표·별도 절차를 요구하지 않으며, 이 예시는 실제 제품 검증 결과가 아닌 판단 방법의 설명이다.

## 무엇이 남아 있어도 넘길 수 있는가

| 현재 상태 | Main에 반환할 의미 |
| --- | --- |
| 맡은 결과와 필요한 자기 확인을 마쳤고, 현재 근거에서 선택이 적절하다고 판단함 | 검토할 수 있는 구현 결과를 전달한다. 더 나은 선택이 있을 가능성 자체는 인계를 막지 않는다. |
| 외부 접근·환경 제약 때문에 일부 중요한 확인을 할 수 없음 | 구현 결과와 확인 한계를 함께 전달한다. 무엇을 시도했고 어떤 주장을 확인하지 못했는지, 남은 확인이 무엇인지 밝힌다. Main은 가능한 검토를 진행할 수 있지만 미확인을 요구 충족으로 처리하지 않는다. |
| 알고 있는 필수 요구 미충족이나 설계·계약 충돌이 남아 있음 | 완료 인계가 아닌 진행 중 문제 반환으로 알린다. 구현자가 해결할 수 있으면 계속 처리하고, 배정 밖 결정은 선택지·추천·영향을 Main에 연결한다. |

구현 도중 중요한 설계 질문이나 막힘이 생기면 완성할 때까지 숨기지 않는다. 중간 조언·부분 검토를 요청할 수 있으며 무엇이 이미 구현됐고 무엇이 아직 열린 질문인지 구별한다. 구체적인 검토 호출 시점·범위는 후속10번에서 정한다.

외부 확인의 부재와 필수 기능의 미구현은 다르다. 예를 들어 로그인 실패 처리가 요구에 있는데 구현하지 않았다면 처리해야 할 미완성이다. 실패 처리와 로컬 확인은 끝났으나 실제 인증 서버에 접근할 수 없다면 통합 동작의 확인 한계다. 어느 경우에도 ‘테스트 통과’ 한마디로 전체 완료를 표현하지 않는다. 이 예시는 구별을 위한 가정이며 실제 제품 검증 결과가 아니다.

## Main이 재구성하지 않고 판단할 수 있게 인계한다

반환에는 다음 의미가 찾아질 만큼의 설명과 실제 자료 접근점을 둔다. 모든 작은 작업에 다섯 제목을 채우거나 새 인계 파일을 만드는 형식은 제안하지 않는다.

| 인계할 의미 | Main이 알 수 있어야 할 것 |
| --- | --- |
| 결과와 범위 | 무엇을 요구받았고 현재 무엇이 달라졌는지, 맡은 결과 중 남은 것은 무엇인지 |
| 실제 대상 | 코드·diff·문서의 위치와 검토할 변경 상태. 기준점과 미커밋 변경 포함 여부 등 현재 작업에 필요한 식별 정보 |
| 중요한 선택 | 현재 방식을 택한 이유·적용한 요구와 기준·보존한 조건·중요한 절충. 판단을 가른 자료의 접근점과 적용 이유를 연결하고, 중요한 가정이나 실제로 비교한 대안이 있으면 함께 설명 |
| 확인 근거 | 무엇을 어떤 조건·방법으로 확인했고 어떤 결과가 나왔는지. 기대 결과를 뒷받침하는 근거 중 판단에 중요한 것, 필요한 재확인 경로와 그 검사가 보장하지 않는 부분 |
| 미해결과 다음 판단 | 알려진 문제·미확인·권한 밖 결정을 구별하고, 각각의 영향과 필요한 다음 행동·추천 |

예를 들어 ‘인증 파일 수정, 테스트 통과’는 결과와 확인 범위를 알기 어렵다. ‘세션 저장이 끝난 뒤 로그인 성공을 반환하도록 바꿨다. 호출부의 성공 처리를 이 시점에 맞췄고 저장 실패 시 성공 화면으로 가지 않는 것을 로컬 검사로 확인했다. 실제 인증 서버 연결은 접근 제한으로 미확인이다’처럼 동작·선택·근거·한계를 연결하고 해당 코드와 검사 위치를 붙이면 Main이 다음 판단을 할 수 있다. 이것 역시 설명용 가정이다.

요구와 기준은 기존 정본을 가리키고 이번 적용·결과를 설명한다. 모든 읽기 목록·기준별 준수표를 작성하거나 인계문 안에 Personal·Project 본문과 작업 과정을 다시 복제하지 않는다. 구현자의 이유는 검토자가 대조할 주장이지 동의해야 할 결론이 아니다. 구현자의 자가 평가를 검토 범위의 상한으로 삼지도 않는다.

Main은 실제 대상과 근거가 맞는지, 알려진 미충족이 숨겨지지 않았는지 보고 다음 검토·추가 구현·확인을 연결한다. 모든 구현 검사를 그대로 반복하는 새 승인 단계는 두지 않는다. Main이 직접 구현한 경우에도 같은 정보를 현재 결과와 기록에서 찾아 검토에 연결할 수 있으면 되며 자신에게 별도 인계 보고를 쓰게 하지 않는다.

- [10월21일 구현·검토 비교](2026-10-21-implementation-review-reference-comparison.md#구현-목표와-기준을-실제-변경으로-완성한다)는 첫 완성·알고 있는 결함 처리·변경 상태와 근거 인계를 제안했다. 이번에는 그 구현 책임을 현재1~5번 합의에 맞춰 구체화하며, 당시 검토자의 직접 수정 제안까지 함께 채택하지 않는다.
- 보존한 pstack의 [bug-fix](../source/workflow-references/pstack/repository/skills/poteto-mode/playbooks/bug-fix.md)·[refactoring](../source/workflow-references/pstack/repository/skills/poteto-mode/playbooks/refactoring.md)는 작업 목적에 맞는 실제 확인과 결과 설명을 참고할 근거다. 강한 도구·반복·커밋 절차나 호환 코드 금지까지 공통 의무로 가져오지 않는다.
- Matt의 [implement](../source/workflow-references/matt-pocock/repository/skills/engineering/implement/SKILL.md)는 구현 중 검사와 이후 검토를 연결한다. 전체 테스트·커밋을 매번 강제하는 절차로 옮기지 않고, [앞선 대조](2026-10-21-implementation-review-reference-comparison.md)에서 확인한 미커밋 변경 식별의 필요를 인계에 반영한다.

위 외부 근거는 Workspace에 이미 보존한 판본을 사용했다. 최신 공개판 조사나 실제 역할 수행 실험은 아니다. 읽기 전용 subagent가 기존 합의·원자료·사례를 조사했고 Main이 제안을 종합했다. 이 조사를 제안의 독립 승인이나 실행 효과 검증으로 부르지 않는다.

6번에서 구체화한 것은 **맥락 이해·적용을 포함한 첫 완성의 충분성, 남은 문제·미확인의 구별, 간결하지만 재판단 가능한 인계**다. 검토자에게 실제로 무엇을 첫 입력으로 줄지와 이유의 제시 방식은7번, 추가 탐색·반환은8번, 수정 권한·왕복은9·11번, 호출은10번, 재검토·검증 연결은12번에서 이어간다. 원래15항목의 번호와 책임을 유지한다.

현재 실행 정본은1~5번을 반영한 development SKILL.md·review.md다. 이번6번 통합안은 실행 스킬·설정·제품 코드·공유 기준의 변경이나01-01·04-03 전체 완료를 뜻하지 않는다.

## 후속 개선 리뷰와 Main 종합

이 절은 통합 전의 리뷰·추천 경과다. 현재 적용 문구는 위 본문과 아래 통합 기록을 따른다.

사용자 요청 원문:

> 6번 안도 리뷰어한테 우리 목표랑 기존 구조, 레퍼런스 주고 개선할 부분 있는지 물어보자 개선 리뷰어야 검증이 아니라 적당한지 보는게 아니라 끌어올릴 포인트가 더 있나

새 내부 리뷰어 `item6_improvement_review`에 GPT-6-astra high로 맡겼다. 이전 대화 전체를 상속하지 않고 위 요청·6번 제안 원문·전체 목표·역할과 내용 소유 구조, current·기존 합의·실제 prototype·사용자 원문·Matt/pstack/Vercel 보존판·DB 인증 사례의 접근점을 전달했다. 제안의 적합성 통과 판정 대신 결과의 질을 높일 기회를 찾고, 실제 행동의 차이·근거·비용·통합 위치를 반환하도록 했다. 읽기·보고 전용이며 파일 수정·새 수행 실험은 하지 않았다.

### 리뷰에서 얻은 두 보완

리뷰어의 첫 제안 원문:

> 설계의 적절성을 설명하는 데서 한 걸음 더 나아가, 실제 사용자가 감당할 일을 통해 자기 선택을 시험한다.

> 새로 얻는 것은 구조 개선 목표의 추가가 아니라, ‘좋아졌다’는 자기 설명을 실제 소비·변경 부담과 대조하는 행동이다.

구현자가 현재 요구·실제 사용처에서 중요한 사용 또는 변경 장면을 골라 실제 코드에 대입하자는 제안이다. DB·인증 예에서는 ‘초기화 책임을 Root에 모았다’는 설명에서 멈추지 않고, 재시도 때 호출자가 어떤 상태를 초기화해야 하는지, 로그인 뒤 작업이 하나 추가되면 어디를 바꿔야 하는지를 따라간다. 내부 순서나 상태 조합을 호출자가 다시 해석해야 한다면 그 부담을 줄일 수 있는지 자기 설계를 다시 본다.

근거는 [DB·인증 대조](2026-10-20-ticket04-01-db-auth-comparison.md#요구실제-대응판정), [Matt의 인터페이스 정의](../source/workflow-references/matt-pocock/repository/skills/engineering/codebase-design/SKILL.md), [pstack architect의 사용 중심 설계](../source/workflow-references/pstack/repository/skills/architect/SKILL.md)다. Main은 Matt가 타입뿐 아니라 사용자가 알아야 할 순서·실패·설정을 인터페이스로 다루고, pstack이 호출자 사용을 먼저 작성하도록 한 원문을 대조했다. 이 자료의 모든 용어나 설계 절차를 함께 채택하는 제안은 아니다.

리뷰어의 둘째 제안 원문:

> 자기 확인에 ‘테스트가 잘못된 구현과 의견이 달라질 수 있는가’를 포함한다.

> 단순히 실패 사례 하나를 추가하는 차이가 아니라 판정의 근거를 구현 밖에서 가져오는 차이다.

중요한 기대 결과를 요구·보존 계약·확인된 사례에서 가져오고, 검사가 구현의 오해를 그대로 반복하는지 살피자는 제안이다. 예를 들어 구현이 로그인 성공을 너무 일찍 반환하고 검사도 그 반환값만 보면 둘이 함께 통과할 수 있다. 계약이 ‘세션 저장 완료 뒤 다음 화면 진입’이라면 저장 지연·실패에서 다음 화면이 열리지 않는지를 확인한다. 이 예는 설명용 가정이며 실제 인증 코드 실행 결과가 아니다.

근거는 [사용자의 의미 있는 검사·초기 테스트 보완 관심](../source/discussion/2026-10-21-workflow-routing-review/conversation.md#s1--사용자)과 [Matt TDD의 Anti-patterns](../source/workflow-references/matt-pocock/repository/skills/engineering/tdd/SKILL.md#anti-patterns)다. Main은 같은 계산으로 기대값을 재생성하는 검사의 문제와 독립된 기대 결과를 요구하는 원문을 확인했다. 모든 테스트가 같은 문제를 가진다는 판정이나 TDD 전체의 도입 제안은 아니다.

### Main의 추천과 통합 위치

**두 보완 모두 기존6번 안에 통합할 가치가 있다고 판단한다.** 첫째는 이름·책임을 확인하고 이유를 설명하는 기존 책임에 실제 사용·변경 부담을 대조하는 방법을 보탠다. 둘째는 검사 대상과 미확인 범위의 구별에 더해 판정 근거가 구현과 함께 잘못될 가능성을 줄인다. 새 책임·서식·승인 단계를 늘리는 방식보다 기존 행동을 구체화하는 편이 낫다.

| 보완 | 통합할 곳과 제안 문구 | 적용 조건과 비용 조절 |
| --- | --- | --- |
| 사용·변경 장면에서 자기 설계를 판단 | ‘자기 설계와 코드의 적절성’ 행과 구조 개선 설명에 통합. “이번 요구와 실제 사용처에서 중요한 사용·변경 장면을 결과에 대입해, 호출자나 유지보수자가 알아야 할 순서·상태·변경 위치와 남는 부담을 살핀다.” | 미래 기능을 무한히 가정하거나 매번 변경 실험을 하지 않는다. 읽기로 판단할 수 있으면 그 근거를 사용한다. 좋은 구조의 내용 정본은 관련 Personal·Project가 계속 소유한다. |
| 기대 결과의 독립성으로 자기 확인 보강 | ‘변경 목적에 맞는 직접 확인’ 행에 통합. “중요한 기대 결과는 요구·보존 계약·확인된 사례에서 가져오고, 검사가 구현의 계산이나 가정을 그대로 반복하는지 살핀다.” | 모든 검사에 출처표·별도 테스트 절차를 강제하지 않는다. 계약이 모호하면 임의로 정답을 확정하지 않고 Main에 필요한 판단을 연결한다. 인계에는 선택·확인의 신뢰도에 영향을 주는 근거를 남긴다. |

리뷰어는 기존 미완성·외부 확인 한계·알고 있는 결함 처리·대상 상태 인계를 다시 늘릴 필요는 작다고 보았다. Main도 이번 보완을 그 목록의 확장으로 처리하지 않는다.7번 입력 묶음이나9~12번 권한·호출·수정·종료의 선택은 그대로 남아 있다.

이 리뷰를 받았을 당시에는 Main 추천만 남겼고 본문 통합은 하지 않았다. 이후 사용자와 맥락 범위를 확인하고 아래 요청에 따라6번 안에 통합했다. 리뷰의 존재 자체를 통과 인증이나 수행 효과 검증으로 취급하지 않는다.

## 맥락 범위 확인과 통합 반영

사용자가 책임의 의미를 확인했다.

> 좋아 근데 책임이라고 해야하나? 컨텍스트나 자료 지침등의 그런것도 고려한거지?

Main은 리뷰 입력에도 Personal·Project·Work, 현재 development 지침과 사용자 원문·외부 레퍼런스가 들어갔지만 앞선 설명이 코드와 테스트에 치우쳐 그 연결을 충분히 드러내지 못했다고 답했다. 책임은 필요한 맥락을 찾아 이해하고 이번 작업에 적용해 결과를 만들고 확인하는 범위까지이며, 자료의 열람과 실제 적용을 구별한다고 설명했다.

이후 사용자가 통합을 요청했다.

> 좋아 그럼 맥락 이해·적용까지 포함해서 리뷰 보완 두 개랑 같이 6번 안에 반영하고 정리해줘

이 요청에 따라 현재6번 본문의 책임 범위에 맥락 이해·선택·적용·필요시 재탐색을 명시했다. 실제 사용·변경 장면을 통한 자기 설계 판단과 구현과 독립된 기대 결과에 의한 자기 확인은 기존 두 책임에 통합했다. 인계에도 판단을 가른 자료·적용 이유와 중요한 기대 결과의 근거를 연결하되 전 자료 목록이나 고정 서식을 만들지 않았다.

이 절의 발화와 앞선 리뷰 원문 발췌는 형성 근거로 보존한다. current·관련 Ticket·산출물 진입에서 통합안과 실행 스킬의 반영 상태를 구별했다. 문서의 연결·내용을 대조한 작업이며 실제 구현자 수행이나 효과를 새로 시험한 것은 아니다.
