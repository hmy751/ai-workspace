# 구성 개선 1차안 — 주제 안에서 기준·사례와 형성 맥락·근거를 구별한다

2026-10-20. 공통 brief와 지정된 실제 문서, 아래에 밝힌 외부 1차 자료를 읽고 독립적으로 작성했다. 다른 리뷰어의 안, Main의 108안, 이전 리뷰 보고서는 읽지 않았다. 이 문서는 제안이며 prototype에 적용한 결과가 아니다. 1차안을 고정하고 이후 교차 검토는 별도로 남긴다.

**권장안은 이름 기준을 하나의 주제 폴더로 묶고, 기준 본문과 사례를 그 폴더의 직접 구성요소로, 형성 맥락과 근거를 그 안의 `background/`에 두는 것이다.** 현재 적용에 필요한 이유와 조건은 본문에 충분히 남긴다. 기준이 어떤 문제에서 생겼고 왜 이 방향을 택했는지, 무엇까지 확인됐는지 재검토하는 설명은 `background/README.md`가 맡는다. 당시 발화는 같은 폴더의 `evidence.md`에서 확인한다.

## 사용자 의도를 어떻게 읽었는가

사용자는 사례를 현재 기준을 이해하고 적용하는 자료로 본다. 맥락·근거는 그 기준을 형성한 의도와 판단을 복원하여 수정하거나 더 정확히 이해할 때 쓰려 한다. 따라서 “항상 읽는다/가끔 읽는다”라는 빈도만으로 나누면 부족하다. 사례도 필요할 때 골라 읽지만 본문과 함께 현재 판단을 전달한다. 형성 맥락은 자주 읽게 되더라도 기준의 성립 과정과 해석 근거를 다루는 역할을 유지한다.

가까이 두려는 이유도 구분의 일부다. 중앙 기록에 원문이 남아 있어도, 본문에서 출발한 사람이 그 존재와 연결을 잃으면 수정 판단에 쓰이지 못한다. 그러므로 가까이 둔다는 것은 폴더 거리를 줄이는 데 더해 **본문에서 이유를 찾는 경로가 보이고, 중앙 기록을 열지 않아도 중요한 형성 맥락과 최소 원문을 읽을 수 있는 상태**여야 한다. 이것이 이번 제안의 판단이다.

“의도·배경·목적은 웬만하면 있었으면 좋겠다”는 선호에는 동의한다. 세 제목을 채우는 방식보다는, 이후 수정자가 원래 풀려던 문제와 지향한 결과를 재구성할 수 있는 짧은 설명을 기본으로 남기는 편이 적합하다. 의도와 목적이 같은 내용이면 합치고, 알려지지 않은 배경은 그럴듯하게 보충하지 않는다.

## 실제 배치와 읽는 방식

아래 경로는 `noline-demo/context/personal/development/`를 기준으로 한 **제안 경로**다.

```text
README.md
naming-and-completion/
  README.md
  cases.md
  background/
    README.md
    evidence.md
```

| 위치 | 맡는 내용 | 이름 기준에서 옮겨 올 내용 |
| --- | --- | --- |
| `development/README.md` | 개발 공통 관점과 주제 선택 | 현재 공통 판단과 세 주제 안내를 유지한다. 이름 주제의 새 본문으로 연결한다. |
| `naming-and-completion/README.md` | 주제 입구이면서 현재 사용하는 기준 본문 | 현재 `naming-and-completion.md`의 기준과 짧은 예시. 별도의 목차 전용 입구는 만들지 않는다. |
| `naming-and-completion/cases.md` | 현재 판단을 이해·적용하는 상세 사례 | 현재 `cases/naming-and-completion.md`의 인증 A/B, 저장 완료, 문자열 `isError` 사례. |
| `naming-and-completion/background/README.md` | 형성 목적·주요 선택 이유·확인 범위·재검토할 지점 | 현재 `.context.md`에서 이름 기준의 형성에 관한 내용. |
| `naming-and-completion/background/evidence.md` | 형성 설명에 실제로 쓰는 발췌와 출처 | 현재 `.evidence.md`의 필요한 원문과 최소 해설. |

현재 이름 기준은 독립 기준 본문 하나, 상세 사례 하나, 형성 맥락과 발췌 각각 하나를 이미 갖고 있다. 이 정도면 주제 폴더가 실제 묶음을 표현한다. `README.md`를 다시 링크 모음으로 만들면 기준에 도달하는 단계만 늘어나므로 본문이 직접 입구를 맡는다. `background/`도 별도 색인을 추가하지 않고 그 README가 형성 설명을 직접 맡는다.

한 묶음에 관련 본문이 여러 개 필요해지면 같은 폴더 바로 아래에 이름이 분명한 본문을 추가한다. 사례가 길어져 특정 사례를 따로 다룰 이유가 생기면 그때 `cases/`로 나눈다. 현재 세 사례는 한 파일에서 비교하는 이점이 있으므로 처음부터 사례별 파일로 쪼개지 않는다.

기준 본문의 상단에는 다음 정도의 안내를 둔다.

> 이름·타입·책임 배치·완료 시점으로 호출자가 맡기는 일과 다음에 해도 되는 행동을 판단한다. 아래 기준과 필요한 사례를 함께 사용한다.
>
> [판단 사례](cases.md) · [기준의 형성 맥락·근거](background/README.md)
>
> 의미를 고치거나 이 기준이 겨냥한 문제를 더 정확히 확인할 때는 형성 맥락을 읽는다.

이후 기존의 실제 기준이 곧바로 이어진다. 일반 적용자는 필요한 절과 사례에서 판단을 끝낼 수 있다. 수정자는 배경으로 한 단계 들어가 이유와 열린 판단을 읽고, 정확한 발화나 합의 범위가 쟁점일 때 그 설명에 연결된 근거 항목을 확인한다. 이 경로는 순차 필독 목록이 아니다. 이미 의도가 불분명하다면 일반 적용 중에도 배경을 읽는다.

본문·사례와 배경은 같은 주제의 일부다. `background/`를 “믿지 않아도 되는 자료”나 “현재 의미와 관계없는 옛 기록”으로 표시하지 않는다. 화면에서도 `기준·사례`와 `형성 맥락·근거`라는 역할 이름으로 구별하는 편이 좋다. 단순히 네 파일을 같은 비중의 탭으로 보여 주면 파일을 옮긴 효과가 줄어든다.

## 현재 문서에서 유지·이동·축소할 것

현재 `.context.md`가 다루는 개인 기준과 Project 계약의 소유 구별은 두 부분으로 나눈다. 현재 소유 정책은 Personal·Project·Work의 입구 및 공통 관리 안내에서 찾게 하고, 왜 그런 경계를 재확인했는지는 배경에 짧게 남긴다. 과거 오류의 상세를 매번 현재 본문에 재현할 필요는 없다.

### 형성 설명의 실제 문단 예

다음은 이름 기준의 `background/README.md` 시작 부분에 둘 수 있는 문장이다. 현재 근거 파일이 보존한 범위에서 재구성한 제안이며 새 사용자 합의가 아니다.

> 이 기준은 개발 작업에 기능 요구뿐 아니라 원하는 코드 판단을 전달하려는 논의 속에서 구체화됐다. 이름 유지와 개명 안을 비교할 때, 설명을 읽으면 둘 다 사용할 수 있다는 평가만으로는 사용자가 지향한 “되도록 설명이 필요없는 코드”를 충분히 설명하지 못했다. 그래서 현재 기준은 호출자가 역할과 완료 범위를 코드에서 알아내도록 하는 방향을 먼저 살피며, 개명이 줄이는 읽기 부담과 실제 전환 비용을 함께 판단한다. [당시 사용자 발화와 기록의 범위](evidence.md#코드가-드러내는-의미)
>
> 이 지향은 필요한 주석을 모두 없애거나 이미 약속한 결과를 이름만 좁혀 제거하자는 뜻으로 확인된 것이 아니다. 현재 본문은 코드로 드러낼 의미와 설명에 남길 이유·제약을 구별하도록 작성자가 구체화한 시안이다. 문장·사례·이름 각각의 최종 채택과 실제 이해 속도 개선은 별도로 확인할 부분이다.

첫 문단은 배경·의도·목적을 연결해서 설명한다. 두 번째는 해석의 범위와 남은 판단을 보여 준다. 이 정도로 시작한 뒤 현재 선택을 가른 쟁점 두세 개를 구체화하면 된다. 앞선 전체 개발 워크플로 발화 하나만으로 이름 기준의 모든 목적을 사용자가 직접 정했다고 소급하지 않는다.

예를 들어 개명 판단은 다음처럼 “어떻게 고칠 때 다시 볼 것인가”까지 연결할 수 있다.

> 내부 두 소비자를 함께 바꿀 수 있다는 조건은 개명 비용을 낮춘다. 이름이 개선되는 이유는 인증 완료와 조회 요청을 더 직접적으로 구별하게 하는 데 있다. 따라서 소비자 수가 늘면 비용 판단을 다시 해야 하고, 조회 결과가 필요한 새 소비자가 생기면 명명 비교에 앞서 완료 계약을 다시 확인해야 한다. 이 사례의 이름을 개인의 고정 명명 규칙으로 만들 근거는 아직 없다.

이는 본문의 선택 기준을 모두 반복하는 문단이 아니다. 현재 예시가 어떤 전제 위에서 만들어졌고 어떤 변화가 재판단을 요구하는지 보존한다.

### 근거 항목의 실제 모양 예

현재 근거는 원대화 전체를 직접 보존한 파일이 아니라, 이전 작업 기록에서 다시 고른 발췌다. 이번 리뷰에서 원기록까지 대조하지 않았으므로 그 구별을 유지한다.

> **코드가 드러내는 의미**
>
> 출처: 2026-10-19 「코드 자체의 명료함을 우선하는 판단 보완」에 보존된 사용자 발화. 인증 코드의 이름 유지안과 개명안을 비교하던 대화에서 나온 말이다.
>
> “근데 난 되도록 설명이 필요없는 코드가 지향되어야 할 코드라고 생각해”
>
> 이 발췌가 직접 확인하는 것은 코드 자체의 명료함을 지향한다는 점이다. 모든 주석 제거·특정 함수명 채택·실제 효과 측정을 확인하는 발화는 아니다. 현재 해석은 [형성 맥락](README.md)에서 읽는다.

발췌 원문, 발화 주체, 날짜·문서 제목, 발화에 필요한 직전 맥락, 확인 범위가 있으면 중앙 기록이 없어도 핵심 판단을 재검토할 수 있다. 원자료 경로·commit·anchor를 확보할 수 있으면 재접근 정보도 더한다. 다만 이번 검토에서 회수하지 않은 원대화의 위치나 내용을 만들어 넣지 않는다. 외부 저장소로 묶음을 옮길 때 원자료 링크가 끊겨도 발췌와 출처 지위는 남아야 한다.

## 의도·배경·목적을 얼마나 남길 것인가

기본값은 **각 지속 기준 묶음에 형성 설명을 남기는 것**이다. 특히 이 이름 기준처럼 서로 가능한 안 중 하나를 택했고, 사용자 정정이 방향을 바꿨으며, 해석 범위를 잃기 쉬운 경우에는 생략하지 않는 편이 좋다.

충분한지는 항목 수가 아니라 다음 세 질문으로 판단한다.

- 이 기준으로 줄이려던 실제 어려움과 지향한 결과를 설명할 수 있는가?
- 현재 표현만 보면 비슷하게 타당해 보이는 다른 선택을 왜 덜 택했는지, 무엇을 감수했는지 알 수 있는가?
- 무엇이 달라지면 기준을 다시 볼지, 그때 확인할 근거가 무엇인지 찾을 수 있는가?

모든 주제에 세 답이 길게 필요하지는 않다. 배경이 본문 목적과 같고 별도 선택이 없으면 짧은 단락과 근거 연결로 충분하다. 배경을 아직 모르면 확인하지 못한 부분만 표시하며, 비어 있는 목적·의도·배경 제목이나 임의의 채움 문장을 만들지 않는다. 근거 파일도 보존할 구체적인 원문·관찰이 있을 때 만든다.

선별할 것은 현재 의미를 재검토하는 데 필요한 결정적 계기, 선택 이유, 제약, 미확정이다. 단순 편집 순서·반복된 AI 답변·모든 조사 링크·오탈자 수정은 붙이지 않는다. 동시에 깔끔한 최종 이유만 남기려고 실제 충돌이나 미확인을 삭제해서도 안 된다.

## 데모 공통 관리와 각 묶음의 책임

지금은 새 관리 체계를 크게 만들지 않고, `noline-demo/context/README.md`에 **본문 묶음의 읽기·관리** 절을 짧게 추가하는 것을 권한다. 적용 범위는 demo 안에서 계속 사용하는 기준·설명 묶음이며 Personal·Project·Work의 내용 소유를 바꾸지 않는다. 일회성 기록, raw source, 실행 결과마다 같은 폴더를 만들라는 규칙은 아니다.

공통 절은 다음 관계를 소유한다.

1. 현재 사용하는 본문과 사례를 함께 찾게 하고, 형성 맥락·근거는 같은 묶음 안에서 역할을 구별한다.
2. 현재 적용에 필요한 조건과 이유는 본문에서 충분히 설명한다. 형성 맥락에는 의도·배경·목적과 중요한 선택 이유를 가능한 한 남긴다.
3. 의미·우선순위·적용 조건을 바꿀 때는 관련 형성 맥락을 읽고 현재 설명과 사례의 관계를 맞춘다. 뜻이 같은 표현 수정에는 형식적인 동반 갱신을 요구하지 않는다.
4. 현재 해석과 과거 원문을 구별하고, 새 판단을 이유로 과거 발췌를 다시 쓰지 않는다. 발췌 오류는 원자료와 대조해 정정한 사실을 남긴다.
5. 각 묶음은 자기 입구에서 무엇을 포함하는지와 읽는 경로를 설명한다. 의미의 소유와 결정권은 Personal·Project·Work의 기존 책임을 따른다.

각 묶음 입구는 이 정책 전체를 복사하지 않는다. 이름 기준이라면 기준 본문·사례·배경의 연결을 제공하고, 배경 끝에 다음 한 문단을 둔다.

> 이름 기준의 의미를 고치면 이 형성 설명의 선택 이유와 미확정, 사례의 권고가 함께 유효한지 확인한다. 인증 사례의 적용 결과가 달라졌다면 해당 Work도 대조한다. 개인 기준의 변경만으로 Project의 완료 계약을 바꾸지는 않는다. 공통 읽기·갱신 원칙은 context 입구에서 찾는다.

Work의 `DEVELOPMENT.md`에는 개인 기준을 선택하는 기존 경로를 새 주제 본문으로 맞추고, 기준 자체를 수정할 때 배경을 확인한다는 연결만 둔다. Project의 `MAINTENANCE.md`는 제품 계약 변경에 관한 자기 책임을 유지한다. 이름 기준의 형성 설명을 Project 계약의 숨은 필수 입력으로 만들지 않는다.

이 공통 정책은 다른 주제에도 적용하되 동일한 파일 수를 의무화하지 않는다. 형성 맥락이 두세 문장이고 자료가 적은 묶음은 본문 끝의 구별된 절로 시작할 수 있다. 다만 이름 기준처럼 이미 상세 사례와 여러 근거 항목이 있는 묶음은 위 폴더 분리가 더 명료하다.

### 변경할 때 무엇을 실제로 확인하는가

작업자는 바꾼 주장과 직접 연결된 사례·형성 이유·근거를 함께 본다. 새 의미가 기존 이유를 더 잘 표현한 것인지, 목적이나 조건 자체가 바뀐 것인지 설명할 수 있어야 한다. 후자라면 바뀐 이유와 그 근거를 배경에 반영한다. 반대 근거가 남아 있으면 양쪽과 미해결 차이를 보존하며 최신 파일을 자동 승자로 취급하지 않는다.

원문은 유지하고 현재 해석은 고쳐 쓴다. 중요한 방향을 뒤집었다면 배경에 이전 선택·바뀐 조건·현재 판단을 짧게 남기고 상세 과정은 기존 기록으로 연결할 수 있다. 매번 별도 ADR이나 로그를 만들 필요는 없다. 원기록 전체를 묶음으로 복제하는 것도 피한다.

마무리 확인은 대표적인 두 읽기에서 한다. 적용자는 이름 기준과 사례만으로 “새 소비자가 조회 결과를 필요로 한다면 이름만 바꿔도 되는가”를 판단할 수 있어야 한다. 수정자는 배경에서 “왜 사용 가능함과 지향한 명료함을 구별했는가”를 찾아 근거 발췌의 확인 범위와 대조할 수 있어야 한다. 이 확인은 제안의 수용 기준이며, 이번에 새 구조로 실행한 검증 결과는 아니다.

경로를 옮길 때는 상위 링크·절 링크·열람 화면을 함께 고친다. 링크 검사 통과와 의미의 일치는 별개다. 문서 수정 시각만으로 낡음을 판정하는 장치나 자동 동기화는 이번 제안에 필요하지 않다.

## 감수하는 비용과 다른 선택이 나은 조건

주제 폴더를 만들면 파일 경로와 기존 링크가 바뀌고, 짧은 주제에도 적용하면 폴더 수가 부담이 된다. 그 비용을 감수하는 이유는 현재 네 파일이 이미 한 주제의 지속 단위를 이루고 있고, 사용자가 이들의 관계를 파일 배치에서도 드러내길 원하기 때문이다. 기존 링크 호환성이 매우 중요하고 탐색 화면이 역할을 분명히 나눠 준다면 접미사 파일을 유지하는 선택도 가능하다.

`background/`는 자칫 읽지 않아도 되는 부록처럼 보일 수 있다. 이를 막으려고 매번 필독으로 만들면 사용자의 의도와 어긋난다. 수정·해석이 필요한 조건을 본문 입구에 쓰고, 배경 첫 문단부터 해당 기준의 실제 목적을 설명하는 쪽을 택한다. 이 방식이 실제로 발견되는지는 새 독자의 읽기로 확인해야 한다.

한 원문이 여러 기준에 쓰이면 가까운 발췌가 중복될 수 있다. 먼저 각 묶음의 주장을 뒷받침하는 최소 구간만 남긴다. 같은 긴 발췌가 여러 묶음에서 반복되어 정정 누락이 생길 정도가 되면, Personal 안의 공통 원자료 한곳을 정본으로 두고 각 묶음에는 필요한 짧은 발췌·출처·해석 연결을 남기는 편이 낫다. 처음부터 모든 원문을 중앙화하는 것은 이번 사용자의 유실 우려를 다시 만든다.

공통 정책을 context README에 두는 선택도 규모에 따른 절충이다. 정책이 길어져 주제 선택을 가리기 시작하면 별도 관리 문서로 분리하고 입구에서 연결할 수 있다. 지금은 이름 전용의 긴 운영 설명을 여러 위치에 반복하는 일을 먼저 줄이는 것이 낫다.

## 교차 검토에서 논의할 쟁점

| 쟁점 | 이 안의 선택 | 다른 안과 비교할 핵심 조건 |
| --- | --- | --- |
| 구별을 어디에서 드러낼 것인가 | 주제 폴더 안에서 `background/`를 한 단계 내림 | 접미사만으로도 사용자·AI가 역할을 안정적으로 구별하는지, 화면에서만 구별하면 파일 사용 시 유실되는지 |
| 별도 입구 파일이 필요한가 | 기준 README가 본문과 입구를 겸함 | 여러 본문을 가진 묶음에서 안내가 본문을 가리기 시작하는 시점 |
| 형성 설명을 어디까지 기본으로 둘 것인가 | 지속 기준에는 짧게라도 남기는 기본값, 파일·목차는 규모에 맞춤 | 얇은 주제에도 별도 배경 파일을 두는 이점이 유지 비용보다 큰지 |
| 근거 옆 해석을 얼마나 허용할 것인가 | 발화 식별과 확인 범위만 남기고 현재 해석은 배경에 집중 | 원문만 떼면 오독할 위험과 설명 중복의 비용 사이에서 필요한 최소 맥락 |
| 공통 정책의 소유 위치 | demo context 입구의 짧은 절 | Personal 외 Project·Work에도 같은 원칙을 적용할 때 별도 관리 문서가 실제로 필요한지 |
| 가까운 보존과 중앙 정본의 관계 | 핵심 발췌는 묶음에 남김 | 여러 묶음의 원문 정정 비용이 커졌을 때 공통 source를 도입할 조건 |

지금 구성을 제안하는 데 반드시 추가 사용자 답변이 필요한 부분은 없다. `background`라는 영문 이름은 의미를 설명하기 위한 선택이고 취향에 따라 바꿀 수 있다. 실제 파일 이동을 확정하기 전에는 다른 독립안과 위 쟁점을 비교하는 것이 적절하다. 모든 문서의 물리적 이동이나 일괄 템플릿화를 사용자 요구로 이미 확정하지는 않았다.
