# 독립안 2의 교차 검토 — 핵심 구성은 같으며 발견 경로와 보존 기본값을 보완한다

2026-10-20. 고정된 `proposal-one.md`를 읽고 공통 brief, 앞서 직접 읽은 실제 문서·외부 자료와 대조했다. `proposal-two.md`와 prototype은 수정하지 않았다. 아래는 교차 검토 후의 권장안이며 구현·운영 검증 결과가 아니다.

**두 안은 실질적으로 같은 구성이다.** 주제 폴더에 기준 본문과 사례를 두고, `background/` 아래에 형성 설명과 근거를 구별한다. 현재 판단에 필요한 이유·조건은 본문에 남기고, 의도와 과거 발화를 정확히 확인할 때 형성 자료를 읽는다. 공통 관리 원칙은 데모 context 입구에 짧게 둔다. 서로 다른 철학이나 큰 대안처럼 비교할 이유가 없다.

교차 검토 뒤에는 상대안의 `background/README.md`를 받아들이고, 형성 설명을 남기는 기본값을 내 최초안보다 명시적으로 표현하겠다. 그 밖의 핵심 배치·선별·갱신 판단은 유지한다.

## 상대안의 가장 강한 점

상대안은 **형성 자료를 분리하면서도 본문을 빈약하게 만들지 않는 기준**을 구체적으로 설명한다. 초대 기능 예시와 오류 반환·throw 예시는 해당 절을 이해시키므로 본문에 남기고, 인증 A/B·저장·`isError`는 선택이 갈리는 상세 사례로 둔다. “이유·예시가 포함됐다”는 형식만으로 배경이나 사례 파일로 일괄 이동하지 않는다. 현재 실제 문서의 내용과 맞는 판단이다.

또한 근접 보존의 의미를 잘 짚었다. 상대안의 “중앙 기록을 열지 않아도 중요한 형성 맥락과 최소 원문을 읽을 수 있는 상태”는 사용자 요구를 폴더 이동 이상으로 해석한다. 본문에서 연결을 발견할 수 있어야 하고, 그 연결을 따라갔을 때 이미 잃어버린 원대화 전체를 찾아야만 이유를 이해하는 상태여서는 안 된다.

화면에서도 `기준·사례`와 `형성 맥락·근거`를 구별하자는 제안은 내 안보다 분명하다. 네 파일을 계속 같은 비중으로 표시한다면 파일을 한 단계 옮겨도 사용자가 느끼는 층위는 달라지지 않을 수 있다. 실제 열람 화면을 고칠 때 이 원칙을 포함하는 것이 좋다. 다만 현재 화면에서 자동으로 그렇게 보인다고 확인한 것은 아니다.

마지막으로 “각 지속 기준 묶음에 형성 설명을 남기는 기본값”을 분명히 하면서 작은 묶음은 짧은 단락으로 시작하고, 자료가 없으면 파일을 채우지 않도록 했다. 사용자 선호를 적극적으로 받아들이되 목차 의무로 만들지 않는 설명이다.

## 같은 판단과 실제 차이

| 항목 | 두 안의 관계 | 교차 검토 판단 |
| --- | --- | --- |
| 기준·사례와 형성 맥락·근거의 층위 | 같다. 읽는 빈도보다 쓰임으로 나눈다. | 그대로 유지한다. 사례도 선택해서 읽는다고 형성 자료와 같은 역할이 되지는 않는다. |
| 주제 폴더와 본문 README | 같다. 별도의 목차 전용 관문을 만들지 않는다. | 그대로 유지한다. |
| 형성 설명의 파일명 | 상대는 `background/README.md`, 나는 `background/context.md`였다. | 작은 발견 경로의 차이다. 내용 책임은 같다. 상대안의 README를 수용한다. |
| 의도·배경·목적의 보존 | 모두 적극 보존하고 고정 세 제목·빈 파일 채우기는 요구하지 않는다. 상대가 기본값을 더 직접적으로 썼다. | 정책의 대립은 아니다. 내 안의 기본값을 더 명시적으로 보완한다. |
| 공통 정책의 위치와 범위 | 같다. 데모 context 입구에 짧게 두고 기존 Personal·Project·Work 소유를 유지한다. | 그대로 유지한다. |
| 근거 옆에 둘 해설 | 같다. 발화 식별·필요한 당시 조건·확인 범위는 남기고 현재 논증은 형성 설명에 모은다. | ‘원문만 남긴다’로 단순화하지 않는다. |
| 공통 원자료로 모을 시점 | 모두 반복되는 긴 원문과 정정 비용이 커질 때 공통 보존을 고려한다. | 차이보다 조건의 표현이 다르다. 실제 정정 누락이 발생하기 전에도 비용이 예상되면 판단할 수 있다. |
| 화면의 역할 표시 | 상대가 더 명시적으로 제안했다. 내 안도 읽기 층 구별과 화면 갱신을 요구했다. | 상대의 구체화를 받아들인다. 별도 파일 정책과 충돌하지 않는다. |

파일명을 제외하면 서로 양립할 수 없는 선택은 찾지 못했다. 형성 설명의 기본값과 화면 표시는 상대안을 통해 내 안의 표현을 더 명확하게 할 부분이다. 이를 합의를 위한 절충으로 설명할 필요는 없다.

## 실제 적용·수정 장면에서의 이득과 부담

**새 소비자가 최신 조회 결과를 즉시 필요로 하는 장면.** 두 안 모두 기준 본문과 인증·저장 사례만으로 현재 동작이 충분한지 판단하게 한다. 형성 맥락을 읽어야만 “이름을 바꿔도 필요한 결과가 생기지 않는다”는 답을 알 수 있게 만들지 않는다. 같은 결과에 같은 읽기 부담이므로 이 장면에서는 우열이 없다.

**“설명을 읽으면 A와 B 모두 쓸 수 있으니 동등하게 권하자”는 수정 제안.** 두 안 모두 형성 설명에서 사용 가능함과 지향한 코드 명료함을 구별한 이유를 찾고, 해당 발췌에서 사용자의 지향과 작성자의 구체화를 구별하게 한다. 여기서 보존할 것은 특정 B 이름의 영구적 우위가 아니라 무엇을 비교해야 하는지다. 두 안 모두 이 점을 충족한다. 실제 이해 속도 개선을 측정했다고 해석할 근거도 둘 다 없다.

**처음 보는 사람이 `background/` 폴더로 직접 들어오는 장면.** 상대안의 README는 그 폴더에서 먼저 읽을 설명을 표시한다. 별도 색인을 추가하지 않으므로 파일 수와 내용 중복도 늘지 않는다. 내 안의 `context.md`는 파일명에서 내용을 직접 식별하는 장점이 있지만, 주제 경로와 문서 제목이 이미 역할을 설명하므로 여기서는 README를 택하겠다. 이것은 관례에 기대는 작은 탐색상 이득이며 현재 열람 도구에서 효과를 검증한 결과는 아니다.

**형성 자료가 적은 새 기준을 추가하는 장면.** 상대안은 짧게라도 형성 설명을 남기는 기본값이 명시되어 있어 사용자 선호가 다음 주제에서 빠질 가능성을 줄인다. 다만 이를 “모든 기존 문서에 배경 파일을 소급 생성하라”로 읽으면 부담이 커진다. 지속해서 사용할 기준 묶음을 새로 구성하거나 의미를 크게 고칠 때, 알려진 문제·지향·선택 이유를 필요한 만큼 남긴다는 범위로 적용하겠다. 현재 작성자가 가진 의도는 현재 작성 의도로 설명할 수 있지만, 기록이 없는 과거 작성 의도를 복원한 것처럼 쓰지는 않는다.

**오탈자 또는 같은 뜻의 문장 수정.** 두 안 모두 해당 부분만 고치며 관련 파일의 날짜를 형식적으로 갱신하지 않는다. 과거 발췌 자체의 전사 오류라면 원자료와 대조하고 정정 사실을 남긴다는 별도 조건도 같다. 지속 관리 부담의 차이는 없다.

**같은 긴 사용자 발화가 여러 주제의 형성을 설명하는 장면.** 두 안 모두 핵심 발췌를 가까이 남기고 원문 전체의 복제는 피한다. 문서마다 같은 긴 발췌를 따로 정정해야 한다면 공통 원자료 한곳과 주제별 연결을 고려한다. 어느 안도 중앙 기록만 남기자는 주장이 아니며, 반드시 여러 복사본에서 정정이 실패한 뒤에야 공통화하라는 규칙으로 읽을 필요는 없다.

## 수용·보완·유지·유보

수용하는 것은 `background/README.md`와 화면의 역할 구별이다. README가 형성 설명 본문을 직접 맡도록 하면 새 관문이 생기지 않는다. 화면에는 ‘기준·사례’와 ‘형성 맥락·근거’를 표시하되 형성 자료를 중요하지 않은 옛 기록으로 표현하지 않는다.

보완하는 것은 보존 기본값의 명시다. 데모에서 지속해서 사용할 기준·설명 묶음을 구성하거나 의미를 바꿀 때는 의도·배경·목적을 가능한 한 남긴다. 알려진 내용과 현재 판단에 맞는 분량으로 쓰며 제목 수·파일 수를 강제하지 않는다. 본문에서 이미 목적이 충분히 드러나고 별도 형성 계기가 없다면 짧은 설명으로도 충분하다.

유지하는 것은 본문 자체의 충분성, 사례의 현재 사용 가치, 최소 발췌의 근접 보존, 원문과 해석의 구별, 의미 변경에 따른 선별 갱신이다. 구체적인 사용자 발화의 지위는 현재 근거 파일이 보존한 범위까지만 인정한다. 이번 두 리뷰가 원대화 전체를 새로 검증한 것은 아니다.

유보하는 것은 전 주제의 일괄 이동과 공통 source 구성이다. 공통 관리 원칙은 데모의 여러 본문에 적용할 수 있지만, 실제 파일 배치는 각 묶음의 자료와 규모를 보고 정한다. 단순한 기준까지 동일한 네 파일로 만드는 것은 두 안 모두 권하지 않는다. 이 유보는 새로운 사용자 승인 절차를 제안한다는 뜻이 아니다.

## 교차 검토 후 권하는 최종 배치

현재 이름 기준에는 다음 배치를 권한다. 최초안의 `background/context.md`를 `background/README.md`로 바꾼다는 것이 파일 구조상의 유일한 수정이다.

```text
noline-demo/context/
  README.md                    데모 공통 읽기·관리 원칙의 짧은 절
  personal/development/
    README.md                  개발 공통 관점과 주제 선택
    naming-and-completion/
      README.md                현재 기준 본문이면서 묶음 입구
      cases.md                 인증 A/B·저장 완료·오류 입력 사례
      background/
        README.md              의도·배경·목적, 선택 이유, 열린 판단
        evidence.md            필요한 당시 발췌·출처·확인 범위
```

주제 README에는 적용에 필요한 목적·조건과 기준을 직접 쓰고, 사례와 형성 설명으로 가는 짧은 연결을 둔다. `background/README.md`에는 기준이 어떤 필요에서 만들어졌고 무엇을 구별하려 했는지, 현재 선택에 남은 한계와 재검토 조건을 쓴다. 원문 확인이 필요한 문장에서 `evidence.md`의 해당 항목으로 연결한다. 현재 `.context.md`의 일반 읽기 표와 긴 관리 표는 공통 절로 줄이고, 이름 기준 특유의 갱신 범위만 남긴다.

새 공통 절의 핵심은 다음 정도다.

> 지속해서 사용할 기준·설명 묶음에는 적용할 본문과 사례를 함께 찾게 하고, 그 형성 의도와 판단 근거를 가까이 보존한다. 의도·배경·목적은 가능한 한 남기되 현재 알려진 내용에 맞게 서술하고, 자료가 없는 형식 항목을 채우지 않는다. 현재 적용에 필요한 이유와 조건은 본문 자체에서 설명한다.
>
> 의미·우선순위·적용 조건을 바꾸면 관련 형성 설명과 사례를 함께 살핀다. 과거 발췌는 새 결론에 맞춰 다시 쓰지 않고 현재 해석을 갱신한다. 같은 뜻의 표현 수정에는 형식적인 동반 갱신을 요구하지 않는다. 각 묶음은 필요한 읽기 경로를 보여 주며, 내용의 소유와 결정권은 기존 Personal·Project·Work 경계를 따른다.

이름 기준처럼 이미 자료가 충분한 묶음은 위와 같이 분리한다. 작은 묶음은 본문 끝의 구별된 짧은 형성 설명으로 시작할 수 있다. 실제 적용 후에는 기준·사례만 읽는 사람의 판단과 형성 의도를 확인하는 사람의 판단을 각각 확인한다. 이때 같은 사람이 여러 파일을 열었는지보다 필요한 답과 근거의 한계를 올바르게 찾았는지가 중요하다.

## 외부 근거와 남은 확인

외부 자료에 관한 상대안의 설명은 앞서 직접 읽은 자료와 부합한다. 특히 [Ryan Lopopolo 자료집의 docs 원칙](https://github.com/lopopolo/harness-engineering/blob/226c8d35fb6ea3ed55467753dba6dea2b5fd5778/docs/AGENTS.md)은 주제 README가 주장을 전개하고 사례가 내용을 발전시키는 구성을 설명한다. 이것은 별도 색인 없이 본문이 입구를 맡는 선택에 참고가 된다. 다만 우리의 `background/README.md`라는 배치를 직접 권고하거나 검증한 자료는 아니다.

[pstack의 rationale-template](https://github.com/cursor/plugins/blob/ddf824aff1e55ba14bd666b30bce3fc69962abe6/pstack/skills/architect/references/rationale-template.md)은 문제·사용·선택·대안·비용 등을 다루는 설계 산출물 양식이다. [epistemics](https://github.com/cursor/plugins/blob/ddf824aff1e55ba14bd666b30bce3fc69962abe6/pstack/skills/why/references/epistemics.md)는 과거 의도에 대한 진술과 추론을 구별한다. 이 자료들에서 사용자의 세 단어를 고정 목차로 삼거나 모든 기준에 별도 근거 파일을 만들 의무를 도출할 수는 없다.

[Gwern의 사이트 설계](https://gwern.net/design)는 필요한 깊이까지 읽도록 하는 표시와 접근 방식을, [Michael Nygard의 결정 기록](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)은 후속 작업자가 이유를 모른 채 결정을 유지하거나 뒤집지 않도록 맥락을 보존하는 방식을 설명한다. 가까운 발견 경로와 이유 보존의 동기를 참고할 수 있지만 Markdown 폴더 이동의 효과까지 뒷받침하지는 않는다.

두 리뷰어가 같은 결론에 도달했다는 사실은 이 입력에서 같은 구성이 설득력 있다는 비교 결과다. 실제 사용자의 발견 속도, AI의 오독 감소, 장기 갱신 비용을 입증한 독립 실험 두 번으로 셀 수 없다.

남는 확인은 큰 철학적 대립이 아니라 적용의 충분성이다. 형성 설명을 다음 기준에서도 필요한 만큼 남길 수 있는지, 화면과 파일 경로에서 두 쓰임이 실제로 구별되는지, 원자료가 없는 상황에서도 최소 발췌로 중요한 해석을 다시 판단할 수 있는지를 보아야 한다. 현재 제안을 정하기 위해 추가로 사용자에게 물어야만 하는 쟁점은 없다.
