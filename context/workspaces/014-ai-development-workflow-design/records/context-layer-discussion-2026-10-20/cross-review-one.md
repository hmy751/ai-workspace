# 독립안 1의 교차 검토 — 핵심은 같으며 적용 경계를 더 분명히 한다

2026-10-20. 고정한 [최초안 1](proposal-one.md)과 [상대 최초안 2](proposal-two.md)를 비교했다. 공통 brief의 사용자 원문과 앞서 직접 읽은 실제 문서·외부 자료를 판단 근거로 삼았다. prototype과 최초안은 수정하지 않았다.

**두 안은 사실상 같은 구성안을 독립적으로 제안했다.** 주제를 하나로 묶고 기준 본문과 사례를 직접 배치하며, 형성 맥락과 근거는 가까운 `background/` 아래에서 구별한다. 주제 README가 본문을 직접 맡고, 데모 공통 관리는 context 입구의 짧은 절이 맡는다는 판단도 같다. 이를 대립하는 두 설계로 보여 주면 실제 차이보다 논쟁이 커진다.

검토 후에도 이 구조를 권한다. 배경 설명 파일명은 상대안의 `context.md`를 채택하되, 이 선택은 구조 변경이나 검증된 우열이 아니다. 더 중요한 보완은 형성 설명의 충분성을 실제 수정 제안에 대입해 확인하고, 본문이 여러 개가 될 때 입구를 어떻게 바꿀지 명시하는 것이다.

## 상대안의 가장 강한 점

상대안은 **형성 맥락이 실제로 수정 판단을 바꾸는지를 구체적인 질문으로 보여 준다.** “설명을 읽으면 두 이름 모두 쓸 수 있으니 동등하게 권하자”는 제안이 왔을 때, 가까운 형성 설명에서 사용자가 지향한 코드 자체의 명료함을 되찾아 무엇을 다시 비교해야 하는지 판단할 수 있어야 한다는 예가 특히 좋다.

이 예는 의도·배경·목적을 남겨야 한다는 선호를 단순한 문서 충실도 문제가 아니라 다음 수정의 판단 문제로 만든다. 제 최초안의 “문제·결과·대안·재검토 조건을 복원할 수 있는가”보다 이 실제 이름 기준에서 무엇이 충분한지 한 번에 드러낸다. 이를 최종 확인 장면으로 수용한다.

상대안은 현재 기준 본문에 필요한 이유를 남기는 경계도 구체적으로 설명한다. “조회 실패가 저장을 취소하지 않는다는 이유로 비대기를 선택하지 않는다”는 문장은 현재 적용 판단이므로 본문에 남겨야 한다. 이름 유지와 개명에 같은 설명을 붙여 비교하게 된 형성 이유는 배경에서 다룬다. 같은 주제를 다루는 문장이 양쪽에 있다는 사실만으로 중복이라고 판정하지 않는 점이 설득력 있다.

또한 지금은 주된 기준 하나이므로 README가 본문을 맡되, 동등한 본문이 여러 개 생기고 시작 질문이 갈리면 짧은 입구를 따로 둘 수 있다는 확장 조건이 분명하다. 제 최초안도 여러 본문을 허용하지만, 언제 README의 역할을 바꿀지가 상대안에서 더 직접적으로 드러난다.

## 같은 판단과 실제 차이

| 비교할 점 | 판단 | 차이가 실제 행동을 바꾸는가 |
| --- | --- | --- |
| 사례의 지위 | 두 안 모두 현재 기준을 이해하고 적용하는 본문으로 본다. | 차이 없음. 사례를 가끔 읽는다는 사실로 형성 자료와 같은 층으로 보내지 않는다. |
| 주제 폴더·`background/` 배치 | 같다. | 차이 없음. |
| 주제 README의 역할 | 현재는 실제 기준 본문을 겸한다. | 차이 없음. 별도 파일 목록만 있는 관문을 만들지 않는다. |
| 배경 설명 파일명 | 제 안은 `background/README.md`, 상대안은 `background/context.md`다. | 거의 표현·탐색 차이다. 두 안 모두 파일 두 개로 같은 내용 책임을 나눈다. |
| 의도·배경·목적 | 두 안 모두 가능한 한 남기고, 고정 세 제목이나 채움 문장을 요구하지 않는다. | 차이 없음. 제 안의 “기본값”이라는 표현이 상대안보다 강해 보이지만, 상대안도 공통 정책과 작성 예에 적극 반영한다. |
| 본문과 배경의 이유 설명 | 두 안 모두 적용에 필요한 이유는 본문에, 형성 선택과 해석 범위는 배경에 둔다. | 차이 없음. 상대안의 실제 문장 예가 이 경계를 더 잘 보여 준다. |
| 근거 해설의 양 | 최소 당시 맥락·출처·발췌·확인 한계는 근거에, 현재 해석의 전체 논증은 배경에 둔다. | 차이 없음. 원문 곁 해설을 전부 삭제하자는 안은 둘 다 아니다. |
| 공통 관리 위치·원문 보존 | context 입구의 짧은 절, 핵심 발췌의 근접 보존, 필요해지면 공통 원자료를 둔다. | 차이 없음. 처음부터 일괄 중앙화하거나 모든 원문을 복제하지 않는다. |
| 형성 설명의 확인 방법 | 제 안은 복원 질문과 적용·수정 두 읽기를 제시하고, 상대안은 실제 수정 제안을 추가한다. | 양립하는 보완이다. 상대안의 질문이 사용자 지향을 잃는 구체적인 수정을 찾아내기 쉽다. |

이번 비교에서 결론이 갈리는 실질적인 구조 쟁점은 발견하지 못했다. 남은 문제는 공동으로 택한 구조가 실제 읽기·수정에서 작동하는지와, 규모가 커질 때 어느 시점에 나눌지다. 두 리뷰어가 같은 안을 냈다는 사실은 독립적인 의견의 일치이며 운영 효과의 검증은 아니다.

## 실제 장면에서 비교한 이득과 부담

### 새 소비자가 조회 결과를 필요로 하는 경우

두 안 모두 기준 본문과 인증·저장 사례에서 판단해야 한다. 현재 예제의 인증 완료와 조회 완료가 다르고, 새 소비자의 다음 행동에 필요한 결과가 바뀌었으므로 이름만 고쳐 해결할 수 없다는 것을 읽을 수 있어야 한다. 형성 과정을 먼저 읽을 필요는 없다.

이 장면에서는 두 안의 경로와 부담이 같다. 인증 사례의 두 내부 소비자라는 가정과 실제 효과를 측정하지 않았다는 한계를 배경으로 치워 버리지 않는다는 점이 핵심이다. `background/README.md`냐 `context.md`냐는 이 판단에 영향을 주지 않는다.

### “두 이름 모두 사용 가능하니 동등하게 권하자”는 수정이 제안된 경우

두 안 모두 본문에서 배경으로 들어가 사용자 발화와 작성자의 구체화를 구별할 수 있다. 상대안의 확인 질문을 적용하면 수정자가 “사용 가능함”과 “지향하는 명료함”을 비교하는 일을 빠뜨렸는지 바로 살필 수 있다.

다만 과거 발화가 현재 대안의 우열을 영구 고정하지는 않는다. 지금의 이름과 타입·사용처가 실제로 어떤 의미를 드러내는지, 공개 호환 비용이 달라졌는지도 다시 봐야 한다. 배경은 비교에서 놓칠 기준을 되살리고, 새로운 비교의 결론은 현재 조건으로 판단한다. 이 구별은 두 안 모두 더 명시해도 좋다.

### 의미가 같은 문장을 다듬는 경우

두 안 모두 해당 본문만 고칠 수 있다. 배경이나 근거의 날짜를 맞추기 위해 함께 수정하거나, 변경이 생겼다는 이유로 형성 원자료를 전부 재독하지 않는다. 반면 “설명 의존을 줄인다”를 “설명만 충분하면 된다”로 바꾼다면 의미가 달라지는 수정이므로 같은 처리로 볼 수 없다.

유지 비용은 구조보다 이런 변경 성격의 구별에 달렸다. 두 안 사이의 차이는 없으며, 짧은 공통 관리 절이 이를 충분히 전달해야 한다.

### 동일한 사용자 발화를 여러 기준이 사용하게 된 경우

두 안 모두 각 묶음에 필요한 짧은 발췌와 그 연결 이유를 유지한다. 긴 원문을 여러 번 옮기는 부담이 커지면 Personal 공통 원자료 한곳을 둘 수 있다. 이름 묶음만 읽어도 그 발화가 이 기준에 왜 필요한지는 알아야 한다.

여기서 중앙 원자료로 옮겼다는 이유로 가까운 의미까지 링크 하나로 축소하면 사용자의 원래 우려가 다시 생긴다. 반대로 긴 원문 전체를 매번 복제하면 정정 시 어긋날 수 있다. 두 안은 같은 절충을 택했고, 실제 중복과 정정 부담이 생기기 전에 관리 장치를 추가할 이유는 없다.

### 한 묶음에 동등한 본문이 여러 개 생긴 경우

현재는 기준 본문 하나와 사례 하나이므로 두 안 모두 README에 본문을 둔다. 이후 서로 다른 시작 질문을 가진 본문들이 같은 묶음에 들어오면 README는 짧은 범위·읽기 안내를 맡고 본문을 별도 파일로 나누는 것이 적합하다. 상대안의 이 전환 조건을 수용한다.

파일이 늘었다는 사실만으로 입구를 분리하지는 않는다. 사례나 근거가 늘어났어도 중심 기준은 하나일 수 있다. 동등한 본문이 실제로 생겼고, 하나의 본문을 입구로 두는 것이 다른 본문을 찾기 어렵게 하는지가 기준이다.

## 수용·수정·유지·유보할 판단

| 처리 | 판단과 이유 |
| --- | --- |
| 수용 | 상대안의 실제 수정 제안 질문을 형성 설명의 충분성 확인에 사용한다. 의도를 적어 두었는지보다 그 의도로 다시 판단할 수 있는지를 확인하기 좋다. |
| 수용 | 동등한 본문과 시작 질문이 여러 개가 될 때 README를 안내로 전환한다는 조건을 명시한다. 현재 이름 기준에는 적용하지 않는다. |
| 작은 수정 | 배경 설명 파일명은 `background/context.md`로 고른다. 상위 `background/`가 자료층을, `context.md`와 `evidence.md`가 각각 설명과 근거를 드러낸다. 별도 README는 추가하지 않는다. |
| 유지 | 주제 단위 묶음, 기준 README·사례의 직접 배치, 가까운 형성 맥락·발췌, context 입구의 공통 정책을 유지한다. 양쪽 근거가 같고 현재 실제 문서에 맞는다. |
| 유지·명료화 | 의도·배경·목적을 가능한 한 남기는 기본값을 유지하되, 제목·파일·역사적 이유를 만들어 채우지 않는다. 현재 적용에 필요한 이유는 본문에 남긴다. |
| 유보 | 다른 모든 본문에 폴더 구조를 일괄 적용하거나 공통 원자료 저장소를 지금 만드는 일은 유보한다. 동일한 역할 구별은 적용하되 실제 내용과 중복 부담을 보고 물리적 배치를 정한다. |
| 유보 | 새 배치가 장기 유실이나 AI 오독을 줄였다는 결론은 유보한다. 독립안의 일치와 링크 검사만으로 입증되지 않는다. |

파일명 수정에는 작은 양보가 있다. `background/README.md`는 폴더를 열었을 때 설명이 자동으로 보이는 열람 환경에서 유리하다. `context.md`는 파일 목록에서 설명과 근거를 구별하기 쉽다. 현재 제안에서는 주제 본문이 배경 설명으로 직접 연결하므로 후자를 택한다. 실제 사용이 폴더 자동 미리보기에 주로 의존한다면 README도 동등하게 타당하며, 이 이름을 채택의 핵심 쟁점으로 만들 필요는 없다.

## 검토 후 권하는 최종 배치

현재 이름 기준에는 다음을 권한다. 경로는 prototype의 `noline-demo/context/personal/development/` 아래를 뜻하는 제안이다.

```text
README.md
naming-and-completion/
  README.md                 현재 기준 본문과 묶음의 입구
  cases.md                  인증 A/B·저장 완료·오류 입력 사례
  background/
    context.md              형성 의도·배경·목적, 선택 이유, 현재 해석과 미확정
    evidence.md             필요한 당시 발췌·출처·조건·확인 한계
```

본문 입구는 현재 적용 대상을 설명한 뒤 사례와 형성 맥락을 짧게 연결한다. 정확한 발화·합의 범위가 쟁점일 때는 형성 맥락의 해당 설명에서 근거 항목으로 연결한다. 근거에 곧바로 들어갈 수 없게 제한할 이유는 없지만, 일반 읽기 안내에서 세부 자료 링크를 모두 동등하게 나열할 필요도 없다.

데모 `context/README.md`의 공통 정책에는 다음 뜻을 포함한다.

> 지속해서 사용하는 기준·계약과 사례는 현재 판단을 충분히 설명한다. 그 내용을 정확히 이해하거나 고칠 때 필요한 형성 맥락·근거는 해당 주제 가까이에 두고 읽을 조건을 알린다. 의도·배경·목적은 가능한 한 남기되, 같은 뜻을 세 제목으로 반복하거나 확인하지 못한 이유를 채워 넣지 않는다.
>
> 의미·우선순위·적용 조건을 바꾸면 영향받는 본문·사례·형성 설명을 함께 살핀다. 과거 원문과 현재 해석은 구별하고, 정확한 문구가 판단을 가르는 경우에는 필요한 발췌를 가까이 보존한다. 의미가 같은 표현 수정에는 형식적인 동반 갱신을 요구하지 않는다.

각 묶음은 자기 범위·자료 관계·특수한 영향 범위만 안내한다. Personal의 개인 기준을 고친 사실만으로 Project 계약을 바꾸지 않는다. Work는 이번 적용과 결과를 관리한다. 현재 `.context.md`에 집중된 긴 공통 운영 표는 축소·이동하되, 이 이름 기준이 왜 형성됐는지와 무엇이 미확정인지는 배경에 남긴다.

최소 확인 장면은 세 가지다. 일반 적용자는 조회 결과를 필요로 하는 새 소비자 문제를 본문·사례에서 판단한다. 수정자는 두 이름을 동등하게 권하자는 제안에서 어떤 품질 기준을 다시 비교해야 하는지 배경에서 찾는다. 발화의 권한이 쟁점이면 근거 파일에서 직접 확인한 사용자 지향과 작성자가 구체화한 문장·사례를 구별한다. 세 장면을 실제 새 독자에게 적용하기 전까지는 구성 제안이다.

## 외부 근거와 우리의 추론을 구별한다

이번 교차 검토에서는 외부 자료를 새로 추가하거나 다른 판본으로 교체하지 않았다. 최초안에서 직접 읽은 지정 commit과 공개 본문의 관계를 그대로 사용했다.

Ryan Lopopolo의 [자료집 구조](https://github.com/lopopolo/harness-engineering/blob/226c8d35fb6ea3ed55467753dba6dea2b5fd5778/ARCHITECTURE.md)와 [docs 작성 원칙](https://github.com/lopopolo/harness-engineering/blob/226c8d35fb6ea3ed55467753dba6dea2b5fd5778/docs/AGENTS.md)은 주제의 주장·사례·적용을 발전시키는 내용과 원자료 보존의 책임을 구별하고, 필요한 만큼 읽도록 안내한다. 이 자료에서 사례가 선택적으로 읽힌다는 사실은 사례와 원자료가 같은 의미층이라는 뜻이 아니다. 주제 README를 본문으로 쓰는 참고는 되지만, 우리 `background/` 배치의 성능을 입증하지는 않는다.

pstack의 [epistemics](https://github.com/cursor/plugins/blob/ddf824aff1e55ba14bd666b30bce3fc69962abe6/pstack/skills/why/references/epistemics.md)는 과거 의도에 대한 직접 진술과 추론·미확인을 구별한다. 이를 근거로 사용자 발화와 Main의 구체화를 나눈다. `context.md`와 `evidence.md`를 별도 파일로 만드는 것은 그 구별을 현재 자료의 양과 갱신 방식에 적용한 우리 선택이다. 두 파일 분리를 해당 자료가 직접 명령한 것은 아니다.

Gwern의 [현재 설계](https://gwern.net/design)는 상세를 필요한 수준에서 펼쳐 읽게 하고 지나치게 작은 페이지로 쪼갠 탐색의 부담도 다룬다. 이 때문에 가까운 접근과 불필요한 관문을 함께 고려할 수 있다. Markdown 디렉터리를 한 단계 내리는 것만으로 웹의 상세 열람 경험이나 장기 보존 효과가 생기는 것은 아니다.

두 안은 외부 자료로 사용자 의도를 대체하지 않고, 실제 문서에 맞는 배치를 추론했다는 점에서도 일치한다. 남은 판단은 두 의견 중 하나를 선택하는 경쟁이 아니라, 같은 제안을 적용했을 때 읽기와 수정이 실제로 충분한지 확인하는 일이다.
