[책임 인터뷰31](2026-10-13-31-criteria-roles-and-responsibility-interview.md)에서 사용자는 기능 Hook과 그 내부 분리를 같은 예시로 비교한 뒤 말했다.

또한 기존 도구의 책임을 추가했다.

> 이미 있는 툴 라이브러리나 리액트 쿼리 등을 활용하고 이미 책임을 맡겼다면 그게 고려 기준에 들어가야 하는것 같아 코드를 분리하고 할때도

당시 사례에서는 기능 Hook이 초대 흐름을 연결하고, 검증·전송 대상 계산과 결과 반영은 내부 함수로 구별했다. 당시에도 모든 기능에 Hook·별도 파일을 요구하거나 구체 이름을 채택하지 않았다. 이 부분은 **책임을 이해하는 선행 구별**이며 명명 규칙을 직접 확정한 발화가 아니다.

91에서 이름 본문의 외부 단위·내부 책임·파일 배치 표와 `useMemberInvitation` 코드를 이 구별을 설명하려고 새로 구성했다. 현재 표는 일반 기준에, 코드는 상세 사례에 있다. 기존 문장의 “전체 업무의 이름과 내부 책임 분리가 충돌하는지”는 제거했다. 원래 논의에서 두 선택은 양립하며, 충돌을 전제할 근거가 없었다. 코드의 구체 변수·API·상태 처리는 설명용이고 사용자 제품 구현을 복사한 것이 아니다.

## isError — 더 명확한 표현과 수정 필요의 구별

[실제 이름·가독성 대조45](2026-10-16-45-naming-readability-supplement.md)에서는 Input·Select가 문자열 `isError`를 스타일 조건으로 쓰고, Field.Message가 문구를 출력하는 관계를 확인했다. 사용자는 이렇게 판단했다.

> 음 여기서 불리언이 더 명확하긴 한데  메시지 자체가 오류룰 발생시킬 우려는 없어서 괜찮아 보여 이렇게 했어 음 뭐 크게 크리티컬해보이지는 않네

이는 당시 사용에서 boolean 변경을 필수 수정으로 올리지 않은 **사례 판단**이다. 모든 `is` 이름에 문자열을 허용하거나 모든 사용처가 안전하다고 보장한 것은 아니다.

상세 사례의 두 JSX 호출은 그 의미를 보이기 위한 재구성이다. 사용자가 쓴 원본 코드의 정확한 발췌가 아니며, `Boolean`으로 변환하는 예시를 채택한 API로 올리지 않는다. 원기록의 사실과 사용자의 판단은 사례 본문에도 직접 설명해, 링크 없이 차이를 이해할 수 있게 했다.

## 유지·설명 보완·개명·동작 수정의 이번 구체화

[68](2026-10-18-68-principle-application-and-choice-basis.md#원칙은-현재-목적과-조건에-대입한다)에서 반영한 조건별 적용은 현재 목적·사용처·변경 비용과 읽기·변경 부담을 함께 본다. 이를 이름 판단에 대입해 다음을 보완했다.

- 기존의 “내부 사용처를 함께 고칠 수 있으면 개명”은 자동 결론처럼 읽힐 수 있어, 함께 고칠 수 있다는 것은 전환 비용의 조건으로 고쳤다. 실제 읽기 부담과 기대 개선도 판단에 포함한다.
- 이미 성립하는 비대기·실패 범위를 설명하는 일과 새 완료 보장을 만드는 일을 나눴다. 일반 기준의 절 제목도 “계약 보완” 대신 “설명 보완”으로 바꿨다.
- 사용처의 기대가 기존 요구인지, 이름에서 추론한 것인지, 잘못된 진입점을 사용한 것인지에 따라 조치가 달라짐을 설명했다. 이 구체적인 분류·문장은 Main의 설명안이다.
- 상세 사례의 내부 함수·공개 API·파일 저장 대비를 유지하면서 접수 식별자와 별도 결과 조회 등 판단 조건을 보탰다. 추가 조건과 검토 의견 문장은 설명용 가정이며 당시 실제 코드의 관찰이나 사용자 결정이 아니다.

유지·설명 보완·개명·동작 수정은 새 고정 절차나 배타적 네 분류로 채택한 것이 아니다. 이름을 유지하며 설명을 보완하거나 동작과 표현을 함께 고칠 수 있다. 이번 보완 요청도 정확한 문장·사례 전체의 최종 수용을 뜻하지 않는다.

Project 가이드에는 현재 demo의 인증 적용·후속 조회·이동과 닫기 조건을 독립적으로 풀었다. 특정 개인 기준을 참조해야 해석되는 구조를 추가하지 않았다. 선택한 함수명은 계속 Project current와 Work에 두고, 제품 동작·초기 입력·기존 작업 기록은 바꾸지 않았다. 외부 자료를 새로 조사하거나 외부 저자가 이번 선택 표와 문장을 직접 권고했다고 주장하지 않는다.

## 오류 계약 — 이름·타입 바깥의 순서와 우선순위

[오류 계약47](2026-10-16-47-fetcher-error-contract-comparison.md)에서 사용자:

> 그런거 좋은 기준 또는 생각으로 보여 누가 무엇을 알고 몰라야 하는 그런 기준과 책임을 잘 고려하는것이라고 해야하나?

> 맞아 오류를 공통으로 처리한다면 사용처에서 그 형태와 의미를 믿고 쓸 수 있어야겠네.

이 동의는 공통 오류의 형태와 의미를 신뢰할 수 있어야 한다는 판단이다. 구체 오류 클래스 체계나 공통 처리 우선순위 API를 채택한 것은 아니다.

당시 `handleError`가 직접 throw하는데 호출부도 `throw handleError(error)`로 쓰인 관찰은45에 있다. 이번의 `toRequestError`·`throwRequestError` 코드는 반환과 throw의 차이를 설명하는 새 대안이며 실제 API 변경이 아니다.

47의 별도 사례에서는 `silent` 옵션보다 등록 처리기가 먼저 실행되어 토스트·이동이 발생할 수 있었다. 이 관찰은 이름·타입이 있어도 올바른 사용에 필요한 우선순위가 숨을 수 있음을 설명한다. 당시 코드 읽기 분석이며 이번 턴에 제품을 재현한 결과는 아니다. 호출자가 silent만으로 공통 처리를 건너뛸 것이라 오해할 수 있다는 설명은 Main의 해석이며, 실제 호출자의 의도 관찰과 구별한다.

## 완료·실패·대기의 구체화

01의 [주문 사례](prototypes/applied-criteria-2026-10-17/shop-web/context/project/cases/order-flow.md)는 공유 범위와 호출·완료 의미를 따로 살피는 시안이었다. 이번의 요청 접수·저장·조회·화면 준비 표와 파일 저장 예시는 그 관점을 새로 구체화한 설명이다. 새 일반 규칙이나 실제 제품 사건을 추가로 발견했다는 뜻은 아니다.

Project의 기기 저장·상태 공개·같은 계정 데이터 보존은 기존 Noline 근거에서 이어받았고, 비대기 Query wrapper와 두 callback은 현재 demo의 선택이다. 출발 자료와 판본은 [구조 정정89](2026-10-19-89-local-context-structure-correction.md)에 있다. 이번에는 그 동작을 바꾸지 않고 다음 두 판단을 구별해 썼다.

- 일반 조회 실패를 앞서 완료한 인증 저장 실패로 소급하지 않는다. 이후 인증 거부가 별도로 확인되면 새 사건으로 처리한다.
- 조회를 기다릴지는 다음 행동이 최신 결과를 필요로 하는지로 정한다. 일부 소비자의 요구와 공통 완료 계약 변경을 구별한다.

인증 거부와 저장 실패의 구별은 [Noline 관찰판의 인증 계약](../source/supplement/worktree-project-context/context/project/guidance/authentication-and-session.md)에 있다. Main은 후속 개선 리뷰에서 이 범위를 지적받고 원문을 직접 대조했다. demo에 그 거부 처리나 새 상태를 구현한 것은 아니다.

대기 경로와 소비자별 책임 비교는 추가 조건이며 현재 구현된 기능이 아니다. 이름·표현을 다듬는 중 제품 계약을 조용히 변경하지 않도록 이 차이를 본문에 표시했다.

2026-10-19, 기존 설명 시안을 옮기지 않고 이 Work 아래에서 새 코드와 본문을 작성했다. 기존 [시작 입력](prototypes/personal-project-applied-2026-10-19/scenario-input.md)과 [가상 적용 장면](prototypes/personal-project-applied-2026-10-19/walkthrough.md)은 설계 입력이다. 그 문서에서 구현자·검토자가 발견하고 수정했다고 서술한 활동을 이번 작업의 실제 이력으로 복사하지 않았다.

## 무엇을 유지하고 무엇을 새로 골랐는가

저장 뒤 상태 공개, 저장 실패 시 이전 상태·데이터 보존, 인증 이후 조회 실패의 분리는 [보존된 Noline 인증 가이드](../source/supplement/worktree-project-context/context/project/guidance/authentication-and-session.md)가 지지하는 제품 계약이다. 이 예시에서는 메모리 저장 어댑터와 단순 여행 목록으로 제한해 실행한다. 실제 DB·queue 귀속 검사와 세션 변경 조율을 구현한 것으로 승격하지 않는다.

기존 시안의 두 내부 사용처·비대기 Query·별도 후속 실패 callback은 설명용 가정이었다. 이번 실행 예시도 그 조건을 선택했다. 코드 모듈 구성, 메모리 어댑터, 테스트, Query 요청의 동기 오류도 후속 오류로 보내는 처리는 이번 작성자가 추가한 구현 선택이다. 사용자와 확정한 개인 기준의 문장이나 실제품 요구로 기록하지 않는다.

| 이번 조건에서 비교한 선택 | 채택 여부와 이유 |
| --- | --- |
| 기존 넓은 이름을 유지하고 가까운 설명 보완 | 가능하지만 이번 새 예시는 내부 소비자가 두 개라 호환성 비용이 작고 호출부 자체에서 범위를 드러내기 쉽다. |
| `signInAndRequestRefresh`·`onSignedIn`으로 표현하고 계약 보완 | 이번 코드에 선택했다. Query 결과를 기다리지 않는다는 사실을 이름·설명·소비자 동작에서 함께 확인할 수 있다. |
| Query 결과까지 기다린 뒤 완료 전달 | 이번 요구가 인증 복구 완료이며 후속 조회 실패를 분리하므로 선택하지 않았다. 조회 결과가 필요한 요구라면 다시 검토한다. |

이 표는 실제 기존 제품의 변경 비용을 측정한 결과가 아니다. 이전 시안의 내부 사용처 조건을 새 예시에 대입한 설계 판단이다. 코드가 새로 생겼으므로 기존 제품 API의 호환성을 보존했다고 주장하지 않는다.

## 실제 작성한 책임

Store는 계정·예시 여행 데이터의 귀속을 확인하고 저장 성공 뒤 상태를 적용한다. 서비스는 인증 응답과 주어진 진행 작업 종료 대기를 거쳐 Store를 호출한다. wrapper는 후속 조회를 시작하고 결과를 기다리지 않고 인증 완료를 전달한다. Login과 Reauth는 각각 안내·이동 또는 안내·닫기를 요청한다.

Login 안내는 처음부터 ‘로그인 완료’로 작성했다. 기존 시안의 ‘검토자가 남은 화면 갱신 완료 문구를 찾아 수정했다’는 장면을 이번 실제 수정 이력으로 만들지 않았다. 현재 완료 의미와 코드·소비자의 관계는 Project current에서 찾는다.

전체 기준 채택·운영 위치 설치·실제품 변경은 수행하지 않았다. 이번 예시는 기준 본문과 제품 계약을 한 작업에서 선택하고 실제 결과에 대조하는 적용 모습을 제공한다. 독립 검토 여부와 테스트 결과는 실제 수행한 범위대로 별도 기록한다.
