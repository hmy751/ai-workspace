# 04-02 — 네 문제에 맞는 사례와 확인 방법

2026-10-26. **저장 용량 첫 보고, access 선택 질문, 인증 자기평가, 보고서 작성 중 추가 조사**를 추천한다. 현재판이 맡은 일을 수행하는지 먼저 확인하고, 구체적인 실패가 발견되면 그 원인에 맞춰 보완한다. 과거판과 다시 비교해 작은 우열을 만드는 일을 기본으로 두지 않는다.

사용자 요청:

> 그럼 해결과제를 위한 적저한 사례를 찾아서 어떠헥 할지 고민해봐

이 문서는 원문·기존 시험·당시 자료의 확보 가능성을 조사한 **Main의 진행 제안**이다. 사례별 응답 생성, 스킬 수정, 제품 실행·설치, Ticket 완료는 하지 않았다. 기존 실행판 `b6195d4`와 [네 문제의 범위](2026-10-26-ticket04-02-four-problems-and-comparison-checkpoint.md)는 유지한다. 이전 저장 용량의 두 조건 비교는 미실행안으로 보존하며, 이번에는 단일 현재판 수행을 먼저 권한다. 사용자에게 새 방법을 승인받았다는 뜻은 아니다.

## 어떤 사례를 왜 고르는가

## 첫 전달 — 저장 용량 변경 보고

[원자료04](../source/artifact-explanation-scenes/04-storage-stats-delivery/README.md)의 마지막 요청2456은 “그래 이제 코드 변경해봐”다. 원래 목표는 성공·실패 경로에서 표시용 결과를 따로 조립해 함께 수정해야 하는 부담을 줄이는 것이었다. 실제 첫 보고2560은 `createStorageStats` 통합·`finally` 갱신·기존 동작·검사 결과를 열거했다.

여기서는 **무엇을 덜 함께 수정하게 됐고, 일부 처리가 실패했을 때 얻은 결과와 중단/계속 정책은 왜 유지되는지**를 첫 보고에서 이해할 수 있어야 한다. 뒤의2632 테스트 질문과2645 “코드 개찔끔이네”에는 검사 근거와 구현 깊이에 관한 판단도 있다. 이를 전부 설명 실패로 세거나 첫 보고에 미래 질문의 답까지 넣게 하지 않는다.

추천 방법:

- 구현·검사를 마쳤고 첫 보고는 아직 작성하지 않은 상태에서 시작한다. 현재 development를 진입점으로 사용하고 explain 연결은 실제 수행에 맡긴다.
- 선행9~1542와1549~2456 원문, 당시 Ticket·관련 Spec, 수정 전후 hook·최초 diff·변경 전 테스트·검사 원출력2513/2523을 제공한다. 당시 대화123발화는 길지만 임의 요약으로 바꾸지 않는다. 줄인다면 원래 요구·선택·제약의 누락을 별도로 확인한다.
- 첫 보고2560, 이후 질문·추가 개선, `later-reference`, 과거 응답·평가·형성 자료는 생성 입력에서 뺀다. 결과는 고정하고 제품 수정·새 검사 실행은 이 조건에 넣지 않는다.
- 파일 읽기와 답의 충분성을 나누어 본다. 줄인 수정 부담·보존한 정책·검사와 미확인 범위가 근거에 맞게 연결됐는지 판단한다. 정해 둔 표현·목차의 일치를 점수로 삼지 않는다.

[이전 자연 선택/명시 적용 비교](experiments/artifact-explanation-storage-placement-fullread-2026-10-22/comparison.md)의 두 답도 핵심을 설명했다. 현재 연결의 추가 이득을 입증하는 비교가 꼭 필요한 상황은 아니다. **현재판 한 번의 수행이 충분하면 해당 장면을 마치고**, 부족하면 자료 선택·사실 해석·설명 구성 중 실제 끊긴 위치를 확인한다.

Network 첫 완료 보고06은 범위 확대·철회와 설명 부족이 섞이고 변경 파일도 많다. 이미 여러 본문 비교를 했으므로 이번 첫 확인보다 작업 범위 판단까지 다룰 후속 사례로 남긴다.

## 선택 판단 — access를 어디에 둘 것인가

[원문](../source/noline-evaluation/corpus/01a0ec21-e59e-7370-8432-8434271aa669/messages.jsonl)의2757 질문은 “근데 access 는 어디간거야?”다.2762는 역할 차이를 설명한 뒤 “아래처럼 유지하겠습니다”라고 선택을 확정했고,2769에서 사용자는 “아니 무조건 하란게 아니라 판단하라고”라고 정정했다.

접근 가능 조건이 필요하다는 사실과 그것을 조합 훅 밖으로 반드시 반환해야 한다는 결론은 다르다. 화면에서 `view/actions`로 충분한지, 폼이나 데이터만 쓰는 소비자가 별도 조건을 필요로 하는지, 외부에서 정책을 다시 조립하는 부담이 있는지를 보고 판단해야 한다. 앞서 구현 권한이 있었으므로 ‘질문이면 어떤 변경도 하면 안 된다’를 정답으로 만들지 않는다.

**이번에 당시 코드 확보 경로를 찾았다.** [source 메타데이터](../source/noline-evaluation/corpus/01a0ec21-e59e-7370-8432-8434271aa669/meta.json)가 가리킨 원본 `.jsonl.zst`를 확인했고, 해제한 SHA-256이 기록의 `9f6df322184a78c975c2ff733cd383b1f4604a6e6a11b44a99b216949617037d`와 일치했다. 다른 세션이나 Noline 저장소는 열지 않았다. 선정한 도구 원문10개와 행별 해시를 [근거 사본](receipts/case-selection/access-source-evidence-2026-10-26.json)에 보존했다. 당시 명령은 자료이며 실행하지 않았다.

|2714·2715 | 조합 훅·view·`actions.canRefetch`·내부 정책 확인과 소비부 변경. 이후 축소 전 상태다. |

다음 준비는2267~2757 연속 대화와 **질문 직전까지 수정이 적용된 관련 파일**을 조립하고 원자료와 대조하는 것이다. 아직 조립본·최종 해시·전체 앱 실행 환경을 만들지는 않았다.2762 이후의 설명으로 코드 빈틈을 메울 필요는 없어졌다.

준비 후 현재 explain으로 한 번 판단하게 한다. 생성 입력에서2762 이후 정정·수락, 인터뷰, 과거 시험 답·평가를 제외한다. 유지·노출·조건부 노출 중 어느 결론이든 실제 요구·소비자·비용에 근거하면 가능하다. 역할표나 ‘없애기로 한 적 없다’만으로 복원을 확정하거나 코드 확인 없이 ‘설명에서만 빠졌다’고 단정하면 판단이 부족하다.

[옛 평가](experiments/artifact-explanation-2026-10-21/reviews/review-1/assessment.md)는 이 질문을 누락 정정으로 규정하고 네 반환값을 제시하는 것을 충족으로 보았다. 이 기준은2769의 실제 사용자 의도와 맞지 않는다. 이번에는 옛 답을 정답으로 삼지 않는다. 여행3484의 책임 배치 질문도 좋지만, 현재 코드 묶음은3905의 수정 후 판본이다. 더 이른 판본 확보 비용이 크므로 access 다음의 깊은 보조 사례로 남긴다.

## 앞선 말의 보완·정정 — 인증 설명의 자기평가

사용자50은 “코드 주체 자체에 대한 근본적인 역할 정의”가 설명 중간에 녹아야 한다고 했다. AI55는 앞선 설명이 메서드 호출은 보여줬지만 주체의 역할을 먼저 세우지 못했다고 일반화했다. 사용자80은 “이전설명이 정말 동작 포인트만 있던걸까?”라고 그 자기평가를 다시 물었다.

[기존 입력 전문](experiments/artifact-explanation-intent-2026-10-21/inputs/recovery/conversation.md)은 최초 설명1546, 사용자50, AI55, 사용자80의 네 발화를 포함한다. 최초 설명에는 AppInitialization·Store·local-account·저장 큐·세션 절차의 역할 설명이 이미 있었다. 더 긴 인증 해설을 쓰는 것보다 **있던 설명을 인정하고 실제로 부족했던 연결을 구별하는가**를 보기 좋다.

이 입력에 현재 explain을 적용하는 작은 회귀 확인을 권한다.80 이후 실제 정정·사용자132·옛 응답·평가·형성 자료는 제외한다. 당시 스킬 링크는 역사적 참조이고 현재 실행판과 구별한다. 제품 코드를 복원할 필요는 없으며, 원문 밖 제품 사실까지 새로 확정하지 않는다.

과거 말에 대한 주장을 원문으로 뒷받침하는지, 실제 오류·연결 부족·표현 선호를 구별하는지, 유지·보완·철회의 이유가 있는지 본다. 사용자가 이의를 제기했다는 이유만으로 전면 철회하거나 새 해설을 원래 의도로 소급하지 않아야 한다. [과거 두 답](experiments/artifact-explanation-intent-2026-10-21/recovery-full-comparison.md)도 이 점을 다뤘으므로 새로운 일반화 사례나 새 판본의 우세를 입증하는 시험으로 부르지 않는다.

UTC는 원래 약속·앱 동작·새 날짜 정책이 섞이고 당시 코드 공백이 있다. Promise는 학습 질문의 성격도 강하다. 앞선 말 왜곡을 좁혀 확인하는 첫 사례로는 인증이 낫다.

## 실제 확인으로 돌아가기 — 보고서의 검증 범위 대조

[보고서 사건01](../source/artifact-explanation-scenes/01-report-delivery/README.md)의789에서 사용자는 “추가 검토는 왜 안한거야? 정말 어렵거나 사유가 있으면 몰라도”라고 지적했다.221에는 작성 흐름·picker·키보드 경험의 확인 부족이 이미 원래 범위로 남아 있었다.836은 열린 폼에서 Debug로 이동하기 어려운 제약을 다른 확인의 중단 이유까지 넓혔다고 설명했다.

이 사건은 ‘미확인’ 표시를 잘하는 것과 **허용 범위에서 더 확인해 판단을 바꾸는 것**의 차이를 보기 좋다. 답만 다시 작성하게 하면 네 번째 문제를 확인할 수 없다.

DB·시뮬레이터 상태가 없으므로 전체 재연은 추천하지 않는다. 대신 **619까지 요청과 첫 보고 전 관찰을 인수한 뒤, 보고서를 마치기 전에 자료로 더 확인할 수 있는 중요한 공백을 판단하는 제한된 조사**를 제안한다.619 이후 수집된 관찰도 제공하므로619 시점부터의 역사 재연이라고 부르지 않는다. 네 보고서 전체 대신 종합 UX의 조사 범위를 떼어 낸 시험이라는 변경도 명시한다.

평가자가 볼 수 있는 구체 근거는 다음과 같다. 이는 생성자에게 주는 조사 지시나 유일한 정답 목록이 아니다.

- 원본 archive의 `apps/client/tests/screens/create-schedule-flow.test.tsx:30`은 `DatePicker: () => null`,31은 `TimePicker: () => null`로 선택창을 대체한다. 기존 폼 검사 통과가 선택창의 동작까지 입증하지 않는다는 사실을 직접 확인할 수 있다.
- `CreateScheduleScreen.tsx:98`의 날짜 선택창 호출에는 현재 날짜값 전달이 없다. 시간 선택창에는107에서 `initialTime`을 전달한다. 이 차이는 관련 컴포넌트를 더 살펴볼 구체 근거이며, 한 호출부만으로 실제 화면 결함을 확정하지 않는다.
- `TimePicker.tsx:36` 이후는 선택 상태와 목록의 표시 위치를 구별해 살펴볼 대상이다. 실제 기기에서의 위치·터치 경험은 코드 읽기만으로 확인됐다고 말할 수 없다.
- [당시 관찰703](../source/artifact-explanation-scenes/01-report-delivery/historical-materials/pre-779-observations/readings/703.txt)은 정상 홈 복귀·폼 기본 화면을 관찰했지만 실제 단절·refresh 호출·열린 초안의 제한 왕복은 확인하지 못했다고 적는다. 관찰자가 남긴 한계를 실제 요구·검사와 대조해야 한다.

현재 Main도 [보존 archive](../source/artifact-explanation-scenes/01-report-delivery/repository/noline-0b3b167.tar.gz)에서 위 코드·검사를 직접 읽었다. 이는 사례의 타당성 조사이며 새 agent 수행 시험이나 제품 동작 검증이 아니다.

생성자에게는 원래 요청·관련 Ticket·관찰·당시 저장소를 주고, 위 파일명·mock 결론·사후 발견은 주지 않는다. 실제 자료를 찾아 주장을 확인하거나 좁히고, 남은 공백의 영향과 다음 확인을 연결하는지 본다. 다른 중요한 공백을 타당하게 조사해도 된다. 모든 파일을 다시 읽거나 숨겨 둔 한 결함을 맞히게 하지 않는다.

코드·기존 검사 열람은 가능한 행동이다. 실제 테스트 실행을 관찰하려면 그 환경이 동작하는지 준비 단계에서 먼저 확인해야 한다. DB·시뮬레이터가 필요한 검증은 현재 환경에서 완료할 수 없으므로 필요한 관찰·담당·접근을 구체화하는 수준이다. 이 제한 수행으로 **추가 조사 책임**을 볼 수 있지만, 제품 수정→재검증 왕복이나 실제 화면 수락까지 확인한 것으로 확대하지 않는다. 그 나머지는 실행 환경을 갖춘 후속 작업에서 이어 확인한다.

## 이어갈 작업과 결과에 따른 처리

첫 전달부터 보자는 앞선 방향을 유지해 **저장 용량 입력을 준비하고 현재판 최초 수행 한 번**을 다음 실행 후보로 삼는다. access는 찾은 원문에서 질문 직전 판본을 조립하는 것이 다음 준비이고, 인증은 짧은 회귀 확인으로 둔다. 보고서 사건은 관찰 인수 시점·열람 범위·실행 가능 도구를 고정한 뒤 추가 조사 수행을 별도로 본다. 이 네 가지를 한꺼번에 응답 생성 묶음으로 실행할 필요는 없다.

실행한다면 먼저 원 응답·행동 근거를 보존하고, 사람이 읽는 답의 충분성과 실제 조사·판단의 충분성을 나누어 평가한다. 원래 요청과 주요 보존 조건을 충족하면 해당 장면을 마친다. 표현 취향·작은 우열만으로 재생성하지 않는다. 부족하면 실제 실패 주장과 관련 원자료를 짚고 다음 중 필요한 책임만 보완한다.

- 자료가 없거나 판본이 잘못됐으면 입력을 바로잡는다. 미래 해결 코드를 대신 넣지 않는다.
- 확인할 자료가 있는데 찾지 않거나 잘못 읽었으면 자료 선택·조사 수행을 본다.
- 사실은 맞지만 목표·이유·선택에 대한 답이 빠지면 explain의 적용·설명 구성을 본다.
- 실제 구현·검사가 부족하면 development와 담당자의 확인·수정으로 돌아간다. 설명 문구만 늘리지 않는다.

여러 사례의 평균 점수나 모델 간 우열은 이번 목적이 아니다. 먼저 현재판의 어떤 책임이 충족·미충족인지 보며, 구체 수정의 효과를 확인해야 할 때 이전 조건과의 비교를 추가한다. 사용자 이해·지속 사용 효과, 운영 설치, Ticket 전체 마감은 각각 남은 근거에 맞춰 판단한다.
