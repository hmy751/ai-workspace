## 제안을 받아 현재 권한과 전체 맥락에서 판단한다

입력은 담당자가 작업하며 확보한 변화·이유·범위·근거다. 제안을 받았다고 반영을 확정하지 않고, 반대로 모두 다시 조사하거나 원 구현자에게 같은 설명을 반복 요청하지 않는다. Main은 현재 요청·유효한 계약과 결정, 관련 사용처·병행 작업에서 그 주장이 맞는 범위를 확인한다. 기존 근거를 그대로 쓸 수 있으면 사용하고, 공백·충돌·후속 변경이 있는 부분만 추가 확인한다. 파일 목록이나 작성자의 자신감으로 충분성을 판정하지 않는다.

제안이 없다는 사실로 지속 본문에 영향이 없다고 확정하지 않는다. Main은 기존 결과 종합에서 직접 확인한 중요한 변화도 반영에 연결한다. 담당자의 제안을 빠뜨리지 않게 받는 것과 Main의 기존 결과·영향 판단은 함께 유지하며, 이를 Project 문서 전수 검사로 늘리지 않는다.

확인된 사실 정정과 이미 권한 있게 정한 의미의 반영은 현재 권한으로 처리한다. 제안의 일반화 범위가 지나치면 좁혀 반영하고, 문서를 바꿀 필요가 없으면 이유를 남길 가치가 있는 만큼 설명한다. 새 제품 약속이나 지속 기준의 채택이 필요하면 기존 선택 권한으로 연결하며, 단순 반영 검토를05의 새 개선 채택으로 확대하지 않는다. 작성자의 표현을 그대로 승인하는 행위가 아니라 의미·근거·Owner에 맞춘 판단이다.

현재는 Main이 검토와 실제 반영을 이어 맡는다. 명시적으로 배정된 문서 갱신 담당이 있다면 정해진 의미·권한·근거를 이어 수행할 수 있으나, 기본 구현·검토·검증 역할에서 자동으로 그 권한을 얻지는 않는다. 독립적인 새 context 검토자나 매 제안의 사용자 승인을 추가하지 않는다. Main이 직접 구현했거나 사용자가 반영을 직접 요청했다면 인위적으로 제안자를 따로 만들지 않고 같은 대조를 수행한다. 이것을 독립 검토라고 부르지는 않는다.

검토 뒤 실제 본문과 읽기 경로를 맞추는 수행은 아래 공통 방법을 사용한다. 한 Main이 근거 대조·판단·반영을 이어 할 수 있으며 별도 문서 두 개나 호출 두 번을 필수로 만들지 않는다. 경험에서 무엇을 채택할지의 판단과 실제 반영은 구별하되, 반영 방법 자체도 의미·근거·권한을 판단하는 수행이지 단순 복사가 아니다.

## 변화의 내용으로 반영 위치를 정한다

먼저 **그 변화가 해당 영역에서 계속 관리할 내용을 바꾸는지** 판단한다. 구현이 바뀌었거나 검사를 마쳤다는 사실만으로 Project 갱신이 필요한 것은 아니다. Project에는 제품 이해·여러 작업의 개발과 판단에 필요한 의미·구조·계약·제약·선택 이유를 남긴다. 현재 지원 사실도 그 공통 맥락을 설명할 필요가 있을 때 포함한다. 이번 구현 여부·검증 진행·실행 상세는 Work에서 관리하며, 코드·검사의 내용을 문서로 계속 복제하지 않는다. 데모에 문장이 있다는 사실은 그 문장의 적절한 소유 위치를 입증하지 않는다.

사용자 유보는 USAGE 참조와 context-update 스킬이 나뉘는 사용감에 있다. 이 안은 담당자의 제안에 연결된 근거와 Main이 이미 유효하게 읽은 맥락을 사용해 검토·허용된 반영을 이어가는 흐름이다. 스킬을 사용한다고 다시 전체 맥락을 읽거나 새 담당자를 만들지 않는다. 읽기·제안과 실제 반영의 권한·끝나는 조건은 구별한다.

개발자는 계약과 실제 결과가 다를 때 ‘최신 코드가 이렇다’는 이유로 약속을 바꾸지 않는다. 결함인지, 현재 사실 설명의 오류인지, 새 제품 선택이 필요한지 구별한다. 이미 위임·채택된 선택에는 승인을 반복해서 요구하지 않는다. 아직 없는 권한이 실제로 필요한 결정만 사용자나 해당 결정권자에게 연결한다.

이번 세부안에서는 약속의 **채택·적용 조건·현재 구현 지원**을 나누어 전달하고 기록하도록 구체화한다. 즉시 유효해진 약속을 구현이 못 지키면 그 불충족을 남긴다. 향후 조건에서 적용하기로 한 결정은 그 조건과 현재 약속을 함께 설명한다. 어떤 경우든 최신 문서라는 이유로 미구현 약속을 현재 동작의 보장으로 쓰지 않는다.

## 지정된 지속 본문을 맞추는 과업

가칭 context-update의 결과는 **지정한 Personal·Project 본문과 허용된 문서 연결의 반영**이다. 지속할 의미·현재 사실의 변화가 확인됐거나 해당 본문의 반영·복원·승인된 이동을 요청받았을 때, 대상·변화·근거·허용 범위를 입력으로 삼는다. 작업 중 사용과 직접 요청에서 같은 수행·종료를 사용한다. Work 상태만 정리하는 요청이나 읽기만 필요한 장면에는 이 과업을 추가하지 않는다.

항목2의 담당자는 제안과 근거를 반환하고 현재 Main이 검토 후 아래 반영을 수행한다. 제안이 불필요한 전체 정비를 뜻하지 않으며, 반영 담당이 된 사실만으로 새 제품 약속이나 Personal 기준의 채택권이 생기지 않는다. 이미 명시적으로 배정한 한정 문서 갱신은 그 계약을 따른다. 추후 별도 담당을 정하더라도 이 방법이 담당자 선정 규칙을 다시 소유하지는 않는다.

1. 대상 입구에서 내용 Owner·관리 지침을 찾고 요청·변화·근거·수정 범위를 확인한다. 이미 확보한 유효한 근거는 재사용한다. 관련 사용자 변경·병행 수정도 대조한다.
2. 보존할 뜻, 바뀐 사실과 확인 범위, 채택된 의미와 열린 선택, 영향받는 입구·사용자를 구별한다. 작업 중 판단이면 충분하며 별도 영구 체크리스트는 만들지 않는다.
3. 본문과 그 의미 변화 때문에 필요한 상세·읽기 경로를 맞춘다. Personal·Project의 형성 자료는 [CONTENT-POLICY](prototypes/development-workflow/noline-demo/context/CONTENT-POLICY.md)를 적용한다. Work에 새 형성 자료 구조를 추가하지 않는다.
4. 해당 영역 입구와 영향받은 기존 진입에서 읽어 제품/기준의 의미·적용 조건을 복원할 수 있는지 확인하고 직접 근거와 대조한다. 링크 검사만으로 끝내지 않는다.
5. 실제 반영·확인 범위, 미반영/열린 선택, 달라진 의미와 영향받는 작업·소비자 접근점을 반환한다. 전체 저장소·모든 과거 Work가 정합해졌다고 주장하지 않는다.

### 무엇을 함께 고칠지는 바뀐 의미로 정한다

첫 범위는 Main이 검토한 변화와 대상 본문이다. 실제 본문을 읽어 새로 드러난 의존 설명·입구까지 대조하되, 링크가 있다는 이유만으로 모든 문서를 갱신하지 않는다. 다른 곳을 그대로 두면 독자가 **어떤 오래된 사실·조건·이유로 판단하게 되는가**를 기준으로 포함한다. 동일 범위의 필요한 정정은 이어 수행하고, 새로운 약속·Owner 이동·권한 밖 변경은 그 판단을 분리해 Main에게 돌려준다. 기존 사용자·병행 변경은 현재판에서 합치며 제안 당시 문장을 그대로 덮어쓰지 않는다.

| 구현 지원 사실이 달라짐 | 그 사실을 소유한 Project current와 다른 계약·가이드에 함께 적힌 같은 현황. 근거가 확인한 조건과 한계도 맞춘다. | 지속 약속·선택 이유가 그대로라면 그것을 새 합의로 다시 쓰지 않는다. |
| 의미·적용 조건·우선순위가 달라짐 | 해당 본문과 필요한 상세·사례, 현재 선택을 설명하는 관련 형성 맥락. 중요한 전환 이유·최소 근거는 해당 관리 계약으로 보존한다. | 관계없는 주제와 당시 선택을 보존한 원문·과거 기록. 새 결론으로 과거를 고쳐 쓰지 않는다. |

| 뜻이 같은 표현·오탈자만 달라짐 | 해당 표현과 그 정정으로 실제 의미가 달라지는 연결만 확인한다. | 모든 background·날짜·진행 중 작업을 형식상 다시 갱신하지 않는다. |

이 표는 [CONTENT-POLICY의 읽기·갱신 기준](prototypes/development-workflow/noline-demo/context/CONTENT-POLICY.md#필요한-범위만-읽고-함께-갱신한다)을 이번 수행에 대입한 예시다. 정책 전문을 반영 스킬에 복제하지 않는다. 기존 update 원형의 호환 경로 처리는 대상 계약에 따라 달라진다. 현재 demo에서 승인된 일반 본문 이동은 참조를 새 본문으로 직접 맞추고 옛 안내용 파일을 정리하며, 도구가 실제로 요구하는 진입 파일의 역할은 별도로 보존한다. 이동 자체가 요청되지 않았는데 갱신을 이유로 구조를 재편하지 않는다.

필요한 형성 맥락이 비어 있다면 접근 가능한 작성 근거를 확인한다. 찾지 못한 의도를 만들어 넣거나 ‘자료 없음’ 안내만으로 채우지 않는다. 이번 수정에 필요한 부분을 복원하지 못하면 그 부분은 미완료다. 뜻이 같은 정정에 관계없는 과거 전체를 재조사하는 조건으로 확대하지 않는다.

본문이 실제 코드와 맞는지만으로 적절성을 확정하지 않는다. 새 설명의 주장 범위와 적용 조건도 유효한 요구·계약·결정 근거에 맞아야 한다. 필요한 기존 개선 검토·검증에는 변경된 본문도 결과로 연결하고, 새로 쓴 문장만을 검증 기준으로 제공하지 않는다. 문서 반영이 원래 요구의 독립 검증을 대신하거나 모든 정정에 새 검토자를 요구하는 것은 아니다.

[기존 update](../source/ai-workspace-baseline/reference-project/.agents/skills/update-project-context/SKILL.md)의 근거 대조·보존 의미·누락 복원·승인된 Owner 이동·실제 소비 경로 확인은 유지한다. Project 고정 경로와 Project 전용 조건은 대상 관리 계약에서 찾도록 바꾸고 Personal도 자기 권위로 처리한다. Work current·제품 코드·machine 상태·새 Work 생성·다른 저장소 동기화는 이 과업의 쓰기 범위에 포함하지 않는다. 별도 위임받은 다른 책임으로 이어 할 수는 있다.

Project의 [MAINTENANCE](prototypes/development-workflow/noline-demo/context/project/MAINTENANCE.md)가 ‘관련 Work 선택과 output 확인’을 요구하는 부분은 삭제할 내용이 아니다. 본문 수정 담당자는 영향과 경로를 확인해 돌려주고, Work를 실제로 갱신할 담당은 Main이 연결한다. 확인 책임과 수정 권한을 구별해 빈틈이나 무제한 수정권을 만들지 않는다.

### 한정 반영은 무엇을 확인하면 끝나는가

**요청된 의미를 근거가 지지하는 범위에서 본문에 반영하고, 영향받은 읽기 경로에서도 그 의미와 한계를 복원할 수 있을 때 문서 반영을 마친다.** 시작할 때 잡은 범위와 실제 발견한 영향을 대조한다. 반영하지 않은 내용이 있다면 원래 범위 밖인지, 판단해 제외한 것인지, 필요한데 아직 못 한 것인지 구별한다. 필요한 수정을 남겨 두고 ‘범위 밖’으로 이름만 바꾸어 완료하지 않는다.

- **내용:** 보존할 의미와 채택된 변경이 반영됐고 현재 사실·약속·미확인이 구별된다. 새 문장은 유효한 요구·결정·직접 근거와 대조한다.
- **필요한 관계:** 영향받은 상세·형성 자료·현재 안내가 같은 적용 범위와 이유를 설명한다. 과거 원자료는 보존하고 해당 내용의 현행 정본을 찾을 수 있다.
- **실제 읽기:** 대상 영역의 입구와 영향받은 기존 참조에서 대표 질문으로 읽어, 링크 주변에서 약속한 내용과 조건을 목적지에서 찾고 설명할 수 있다. 링크 존재 검사만으로 대신하지 않는다.
- **반환:** 실제 수정·확인, 미반영 이유, 영향을 받는 작업과 남은 행동을 현재 Main이 이어 판단할 수 있다. 같은 Main이 수행하면 기존 결과 설명·Work 갱신으로 연결하며 별도 완료 보고서를 만들지 않는다.

이 조건은 기존 관리 계약과 [update 원형](../source/ai-workspace-baseline/reference-project/.agents/skills/update-project-context/SKILL.md)의 의미 보존·실제 소비 경로 확인을 연결한 것이다. 매 편집의 독립 reviewer나 제품 재시험을 의무화하지 않는다. 뜻이 같은 정정은 작은 대조로 끝내고, 의미가 달라져 기존 검토·검증의 기준에 영향을 주면 Main이 그 수행을 이어 연결한다.

**문서 반영의 완료와 그 문장이 설명하는 제품의 충족은 별개다.** ‘구현은 추가됐고 요구 검증은 남았다’는 문서는 근거가 맞으면 반영을 마칠 수 있다. 제품이 요구를 만족한다는 주장은 그 확인 전까지 하지 않는다. 필수 설명·형성 근거·읽기 경로가 남았다면 문서 반영 자체가 부분 미완료다. 권한 밖의 진행 중 Work 수정이나 코드·검사는 반영 과업이 완료했다고 대신 주장하지 않고 Main에게 돌려준다. Main은 그 후속이 이번 전체 완료에 필요한지 기존 development 기준으로 판단한다.

제안이 현행 본문에 이미 반영되어 있거나 적용되지 않는 경우에는 대조 결과와 필요한 이유를 반환하고 편집 없이 끝낼 수 있다. 새 결정이나 근거가 부족해 일부를 못 고칠 때는 독립적으로 확정할 수 있는 부분은 반영하고, 남은 판단·책임·다음 행동을 함께 남긴다. ‘반환했다’는 사실만으로 미완료 부분이 해결된 것은 아니다.

## Main이 진행 중인 작업을 잇는다

현재 의미에 영향이 있으면 문서 반영이 모두 끝날 때까지 기다리지 않고 해당 담당자에게 먼저 알린다. Main은 현재 적용할 결정·근거·최신 대상과 필요한 후속을 전달한다. 아직 정본에 반영되지 않았다면 어느 본문이 과거 상태인지와 갱신 담당·남은 일도 함께 밝혀, 원문을 직접 읽는 담당자가 현재 결정과 낡은 설명을 구별하게 한다. 현재 전제에 의존한 작업만 멈추거나 다시 맞추고 무관한 수행은 계속한다. 이 임시 안내는 정본 갱신을 대신하지 않으며, 그 문서를 다음 실행의 입력으로 넘기기 전에 필요한 변경의 실제 반영을 확인한다.

중단 뒤에도 기존 책임이 이어지도록 이번 안은 다음 연결을 구체화한다. 연결이 끝나기 전에 중단될 수 있다면 기존 Ticket·state 중 적절한 곳에 달라진 선택, 이미 반영한 곳, 아직 맞추지 않은 수행·확인, 다음 행동을 남긴다. 결과가 돌아오면 실제 반영·확인으로 현재 내용을 갱신한다. 전달 장부나 필수 상태값을 만들지 않고, 이어받을 영향이 없는 문구 수정에서는 생략한다. 항목3은 역할 수행 뒤 마지막에 한 번 지나는 단계가 아니라 시작·수행·완료 사이의 의미 있는 변화마다 쓰는 연결 책임이다.

| 변화 예 | 기존 의견·확인의 처리 |
| --- | --- |
| 문구나 경로만 바뀌고 뜻·대상이 같음 | 새 접근점을 연결한다. 의미가 같다는 대조로 충분하면 제품 검사를 다시 하지 않는다. |
| 새 소비자가 조회 완료를 요구함 | 기존 두 소비자의 비대기 검사는 그 범위에서 보존한다. 새 소비자의 기대 결과·설계 의견·관련 검사를 추가/수정한다. 이전 ‘전체 충분’ 판단은 새 범위에 그대로 쓰지 않는다. |
| 공통 완료 약속을 변경함 | 영향을 받는 요구·사용처·진행 중 구현/검토/검증을 찾아 새 계약으로 맞춘다. 다른 코드·설정·검사 조건도 바뀌면 관련 근거 유효성을 다시 판단한다. |
| 기준 적용이 잘못됐다는 개선 의견을 채택함 | 문제와 선택을 바꾼 이유를 기록하고 실제 수정·이득·확인을 연결한다. 새 판단에 의존하는 다른 항목도 함께 맞추며 경고문만 덧붙이지 않는다. |

담당자의 반환은 그가 실제로 사용한 조건·판본에 대한 근거다. 새 입력이 전달됐다는 사실만으로 반영 완료로 보지 않고 반환된 대상·판단이 변경을 포함하는지 확인한다. 잘못된 전제가 남으면 입력을 고치거나 관련 질문을 다시 배정한다. 새 broadcast 시스템·전역 소비자 registry·모든 agent의 승인 응답은 만들지 않는다. 현재 배정과 실제 참조에서 확인 가능한 영향 범위로 처리하고, 확인 못한 소비 범위는 구별한다.

후속 구현·검증 결과도 지속 본문의 기존 주장·미확인을 바꾸는 입력이다. Project에 남긴 지원 범위·확인 한계가 달라졌다면 해당 본문을 같은 반영 방법으로 다시 맞춘다. 매 검사 진행·수치까지 Project에 누적하지 않고, 다음 관련 작업의 판단을 바꾸는 관계만 남기며 상세 실행은 Work 근거에 둔다. 문서 반영 뒤 검증을 별도로 잇는다는 이유로, 검증이 끝나도 이전 미확인 문장을 그대로 두지는 않는다.

Main의 Work 기록은 중요한 결정·의미 변경·실행 결과·막힘·인계처럼 다음 수행이나 후일 재판단에 필요한 시점에 남긴다. 매 도구 실행·모든 발화에 기록하지 않는다. current의 낡은 다음 행동은 교체하고, 상세 대안·실패·정확한 문구가 판단 근거면 records에 최소 원문과 위치를 보존한다. source는 새 결론으로 덮어쓰지 않는다.

## 제안과 처리 근거를 이후에도 사용할 수 있게 남긴다

별도 제안함·승인 장부·필수 상태값을 만들지 않고 기존 Work의 Ticket·records·current를 사용한다. 당장의 다음 행동뿐 아니라 후일 선택을 다시 판단할 가치가 있는 제안도 보존할 수 있다. 제안의 근거와 당시 조건, Main의 판단 이유, 실제 반영 위치·확인 범위를 서로 찾을 수 있게 연결한다. 모든 작은 의견이나 반복된 제안을 복제해 누적하지 않는다.

| 남길 의미 | 기존 위치와 읽을 때의 구별 |
| --- | --- |
| 이번 일을 계속하는 데 필요한 미처리 제안·남은 검토·반영·확인 | 해당 Ticket이나 current의 남은 행동에 둔다. 수신·채택·파일 수정·확인을 하나의 ‘완료’로 쓰지 않는다. |
| 중요한 제안의 이유·근거·대안과 반영/조정/미채택의 판단 | 기존 작업 기록 또는 records에 필요한 만큼 둔다. 즉시 쓸 일이 없더라도 후일 재검토 가치가 있으면 남긴다. |
| 현재 유효한 선택·실제 결과·다음 행동 | current를 최신 의미로 맞춘다. 제안 전체와 과거 승인 경과를 상시 입력으로 누적하지 않는다. |
| 이후 경험 개선에서 볼 자료 | 위 제안·판단·실제 반영과 결과의 접근점을05에서 선택할 수 있게 남긴다. 제안이 존재한다는 이유로 새 기준 채택이나 효과를 확인한 것으로 쓰지 않는다. |

구현자가 종료된 뒤에도 이 자료로 검토를 이어갈 수 있다. 당시 근거가 현재도 유효하면 원 구현자에게 다시 물을 필요가 없다. 중요한 누락·충돌·대상 변경이 있으면 필요한 원문·실물을 확인하고, 기존 자료로 해결되지 않는 부분에 한해 추가 질문이나 조사를 연결한다. 모든 과거 제안의 재승인·전면 재검증은 하지 않는다.

개발 중 필요한 사실·이미 정한 의미는 그때 검토해 반영한다. 루프에서는 미반영 후보뿐 아니라 이미 반영한 선택과 그 결과도 재검토 자료가 될 수 있다. 새 개선을 채택했다면 같은 본문 반영 방법 또는 해당 코드·도구 수행을 사용한다.05의 주기·담당·독립 검토 구성과02의 전체 기록 구조는 이 연결만으로 확정하지 않는다.

사용자는 후속에서 루프를 명시적 단계로 만들며 매 작업보다 대화를 기준으로 하는 방향을 제시했다. 해당 단계의 구체화 때도 위 내용 선별·영역별 책임·반영과 확인의 구별을 적용한다. 스킬을 사용할지, 어느 대화 경계에서 누가 시작할지는 [05](../current/tickets/05-improvement-loop.md)에서 정한다. 현재 일상 갱신 흐름을 매 작업의 회고 호출로 바꾸거나 루프가 모든 본문을 재갱신하도록 하지 않는다.

이 표는 쓸 문장을 이해하기 위한 설계 예시다. 실제 요청·수정·실행은 없었고 prototype의 현재 문서를 이 가정으로 바꾸지 않았다. 중심 과제가 달라졌다면 부수 발견과의 우선순위도 함께 맞춰 다음 재개가 예전 다음 행동을 따르지 않게 한다.

이 예의 첫 결과는 ‘기존 Project 계약으로 설명 가능한 소비자별 적용이므로 이번 선택·구현·검사 상태는 Work에 남긴다’일 수 있다. Project 갱신 여부를 먼저 판단해야 본문 반영 과업의 필요와 범위도 정해진다. 여러 작업에서 필요한 구조·지원 제약이 실제 달라졌다면 그 설명을 별도로 선별하며, 코드 변경 목록과 검증 진행을 통째로 옮기지 않는다.

반대로 제품의 지속 약속을 바꾸기로 정한 경우라면, 반영 결과에는 달라진 계약·적용 조건과 그 이유, 함께 맞춘 설명·읽기 경로, 구현이 아직 그 약속을 충족하지 못하는 중요한 제약이 드러나야 한다. Main은 이번 Work의 구현·검증과 진행 중 담당자의 입력을 이어 맞춘다. 구현 지원의 한계를 밝히는 일과 이번 작업의 진행을 Project에 누적하는 일을 구별한다.

## 개발 밖 요청과 관리 비용

‘이 문서에 확인한 사실을 반영해줘’는 활성 Work 없이도 가능한 과업이다. 현재 요청의 Main이 반영 결과와 확인한 영향·남은 결정을 설명한다. 영향받는 진행 중 작업이 확인되면 해당 관리 권한 안에서 연결하고, 접근·권한 밖의 작업까지 완료했다고 보고하지 않는다. ‘작업 상태만 정리해줘’는 Work 계약으로 끝낸다. 뜻이 같은 오탈자 편집을 전체 반영 과업으로 키우지 않는다.

잠정 배치에서 USAGE는 읽기 방법, context-update는 지정 본문 반영, development는 시점과 결과 연결, 각 Owner는 내용·권위를 소유한다. 실행 본문으로 옮길 때는 기존 update의 공통 수행을 재구성하고 각 영역의 관리 계약·CONTENT-POLICY는 참조한다. 같은 규약 전문을 스킬에 다시 정의하거나 Work 파일 구조를 옮기지 않는다. 따라서 반영 스킬을 교체해도 관리 기준과 허용된 수동 반영은 남는다. 읽는 도중 반영이 필요한 상황에서 입력을 중복 수집하거나 사용자가 파일 형태를 골라야 한다면 포장을 재검토할 근거가 된다. 현재안의 책임 구분을 유지하되 사용감이 검증됐다고 단정하지 않는다.

‘이 확인 내용을 반영해줘’처럼 사용자가 이미 한정 반영을 요청했으면 별도 구현자 제안·새 사용자 승인을 만들지 않는다. 현재 Main이 대상 관리 계약으로 근거·범위를 대조해 반영한다. ‘읽고 설명해줘’는 읽기·설명으로 끝내고, ‘이번 상태를 정리해줘’는 Work 유지로 처리한다. 반복해서 쓰는 방법과 독립 요청을 같은 경로로 연결하되 모든 요청이 제안·갱신·루프를 통과하지는 않는다.

| 시작 장면 | 같은 방법이 맡는 일과 끝난 뒤의 연결 |
| --- | --- |
| 개발 중 구현자의 반영 제안 | Main이 근거·의미·권한을 검토하고 필요한 지속 본문과 읽기 경로를 맞춘다. 결과를 이번 Work와 진행 중 수행에 연결한다. |
| Work 없이 ‘이 사실을 Project에 반영해줘’ 요청 | 요청과 근거를 직접 입력으로 삼아 해당 본문·연결을 확인한다. 결과·한계를 사용자에게 설명하고, 실제 영향받는 Work가 있을 때만 그 유지 책임을 연결한다. 기록 보존은 대상 관리 계약을 따르며 새 Work 생성을 전제하지 않는다. |
| 이후 루프에서 Personal 기준의 변경을 채택함 | 채택 의미·적용 조건·근거·허용 범위를 입력으로 해당 본문·필요한 형성 자료·읽기 경로를 맞춘다. 적용 중인 Work 영향을 반환하고 실제 경험에서의 효과는05의 후속으로 남긴다. 채택 대상이 코드·스킬·도구라면 그 대상의 수행으로 보내며 이 방법의 쓰기 범위를 넓히지 않는다. |
| 계약과 다른 동작을 발견함 | 실제 관찰과 유효한 약속을 구별해 기록·반환한다. 단순 사실 오류는 바로잡되 결함을 정당화하도록 약속을 바꾸지 않는다. 필요한 코드 수정·제품 선택은 Main이 해당 책임으로 연결한다. |

Matt의 resolved glossary 즉시 반영과 별도 retro, Lauren의 한정된 유지 권한·reflect 채택과 반영 구별을 [고정판 조사](2026-10-25-context-reference-synthesis.md)에서 차용했다. 저자의 자동 commit·외부 tracker 발행·고정 반복 조건은 가져오지 않는다. 후속 확인은 읽기만 요청의 무수정, 사실 반영과 제품 선택의 구별, 변경 후 진행 중 담당자·이전 근거의 실제 갱신, 반영 수단이 없어도 가능한 수동 유지다. 자동 Maintain을 재개하지 않는 사용자 방향에 따라 기존 장치의 의존 정리와 실제 host 관찰은06·07에서 다룬다.
