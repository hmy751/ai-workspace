# Spec·Ticket으로 설계 결과를 나눈 첫 초안

## 사용자 요청과 판단

Workspace를 만든 뒤 사용자는 다음과 같이 물었다.

> 근데 여기 보니까 spec ticket 구조는 아니던데 어떤 방식이 더 나아보여? 하나하나 나누려면 스펙 티켓이 더 좋아보이긴한데 순수 개발작업은 아니라서 맞나? 싶기도 하네

AI는 전체 목적과 부분별 결과·진행을 이어갈 필요가 크므로 Spec·Ticket이 적합하다고 판단했다. 기존 기준은 작업의 결과·공통 기준·열린 가정을 다룰 수 있지만 구체 예시는 개발 중심이다. 조사·설계·문서 Ticket의 운영 효과가 이미 검증됐다고 확인한 것은 아니다. 이번 작업에 적용할 결과와 완료 근거를 구체화해야 한다.

사용자는 이어서 요청했다.

> 그래 그럼 그렇게 나눠보고 티켓도 한 번 일단 나눠봐 보면서 또 논의하게

이는 Spec·Ticket을 사용해 **초안을 만들고 보며 논의할 권한**이다. AI가 고른 일곱 분할과 각각의 운영 방안까지 채택한 것으로 해석하지 않는다. 정확한 세 발화는 [분해 요청 원문](../source/discussion/spec-ticket-conversation.md)에 보존했다. 사용자 발화는 원본 2987·3042행이며 추출 범위와 hash는 [manifest](../source/spec-ticket-discussion-manifest.json)에 있다.

## 이번에 선택한 문서 관계

전체 목표·공통 기준·현재 가정을 [Spec 한 편](../current/spec.md)에 모았다. Reference가 쓰는 다섯 관점을 한 문서의 다섯 절로 적용했다. 루트 Workspace의 수동 운영을 유지하며 `current/memory.md`는 평가 배경, `state.md`는 전체 진행, `tickets/`는 부분별 결과·진행을 맡는다. 자동 Maintain과 JSON 상태 계약을 설치하거나 Reference의 공통 기준을 변경하지 않았다.

기존 memory의 사용자 방향과 미정은 Spec의 대표 사례·제약에 이어 주고, 배경과 회고의 의미는 memory에 남겼다. design-map은 열린 관점과 Ticket의 관계를 보여 주도록 갱신했다. Spec·Ticket·색인·원문·기록은 각자 소유하는 내용을 연결하며 같은 목표나 상태를 별도 정본으로 복제하지 않는다.

## 왜 이 결과들로 나눴나

이번 일곱 Ticket은 주제 이름을 그대로 파일로 옮기기보다 논의 뒤 검토할 결과를 기준으로 만들었다.

- 기록의 보존 목적과 갱신 시점·재개를 별개로 먼저 확정하면 기록 내용과 운영이 어긋날 수 있어 **기록·Maintain 과제**에서 실제 예시와 운영안을 함께 다룬다.
- Project의 본문·읽기·관리 책임은 개발 주체의 입력을 구체화하는 결과가 필요하므로 **Project context 과제**로 둔다. 개발 방법을 그 문서 구조에서 일방적으로 도출하지 않도록 **개발 작업 방식**과 상호 대조한다.
- 개발의 수행·검토·검증·보고는 실제 결과를 만들고 확인하는 방법을 맡으므로 **개발 작업 방식**에 연결했다. 코드 품질·도구·사람 선택도 포함한다. 세부 방법이 커지면 추가 분해할 수 있다.
- 기존 스킬의 실제 조항·호출·결과를 대조하는 **기존 스킬 보완 과제**를 두어 새 워크플로 설명만으로 스킬 보완을 대신하지 않는다. 일곱 스킬을 한꺼번에 재작성하겠다는 약속은 아니다.
- 기록한 내용을 보존·갱신하는 일과 경험에서 작업 방식을 개선하는 판단이 같지 않으므로 **경험 반영 과제**를 구별했다. 모호한 기준을 구체 사례로 발전시키는 사람의 참여와 후속 효과 확인도 여기서 다룬다.
- **기반 전환 과제**는 설계의 실제 반영 위치, 공통 기반과 대상의 차이, Maintainer 장치를 걷어낸 뒤 이어질 책임을 맡는다. 장치 제거만 따로 처리해 책임이 빠지지 않게 한다.
- **전체 연결 과제**는 부분 설계를 대표 작업의 흐름에 연결해 대조하고 후속 적용안을 만드는 결과다. 각 Ticket의 검토를 마지막으로 미루기 위한 단계는 아니다.

현재 Spec·Ticket 자체의 운영을 논의하는 작업과 앞으로 개발자가 Spec·Ticket을 어떻게 사용하는지 설계하는 대상은 구별한다. 후자는 개발 방식의 목표 분해·실행, 스킬 보완의 work-discussion·reconsider-work, 기반 전환의 공통 기준 반영에 연결했다.

사람의 참여는 경험 반영에만 있는 기능이 아니라 Spec의 공통 기준이다. 개발과 보고에서 중요한 선택·학습 질문·반복 교정을 구별하는 책임은 개발 방식·스킬 보완에도 있다. 당시에는 기록을 먼저 논의할 후보로 제안했지만 채택된 순서는 없었다. 기록을 논의할 때에도 실제 개발 장면을 참고해 전체를 기록 관점으로 좁히지 않는다는 기준을 남겼다.

## 초안의 한계와 다음 확인

개발 작업 방식과 기존 스킬 보완은 범위가 넓다. 실제 내용을 비교할 때 별도의 결과·근거·검토가 필요한 부분은 추가 Ticket으로 나누거나 인접 Ticket과 조정한다. 전체를 새로 잘게 쪼개는 것보다 충분한 결과를 만들 수 있는지를 기준으로 삼는다.

모든 Ticket은 현재 설계 작업 미착수다. 분해 문서가 만들어진 것, 자료를 이미 읽은 것, 설계안을 충분히 제시한 것, 채택·구현·효과 확인은 서로 다르다. 이번 완료 대상은 사용자가 검토할 Spec과 Ticket 초안이며, 다음에는 이 분해와 먼저 다룰 부분을 보며 논의한다.

## 확인

작성 전 별도 검토자가 현재 요청과 기존 기록을 읽고 누락되기 쉬운 결과·공통 요구·상호 의존 관계를 확인했다. 기록 목적의 폭, Project 소비자, 실제 스킬 대조, 코드의 역할, 장치 제거 뒤 책임, 경험 반영을 분해에 연결했다.

작성 뒤 같은 검토자에게 README·Spec·Ticket 색인과 일곱 본문, memory·state·design-map·output의 의미·범위·관계를 대조하게 했다. 초안과 채택·구현·효과의 지위 구별, 빠지거나 중복된 책임, 순서·범위의 과도한 고정, 사용자의 검토와 새 세션 재진입을 살폈다. 실질적인 문제는 발견하지 못했고, 모든 부분을 실제로 실행하거나 효과를 검증한 결과는 아니라고 구분했다.

Main은 작성·갱신 문서 23편의 링크 201개와 대화 원문 anchor 16개를 확인했고 누락을 발견하지 못했다. 새 대화 발췌의 hash와 크기를 확인했으며 `git diff --check` 및 작성 문서의 끝 공백 검사도 통과했다. 제품·글로벌 스킬·하네스 실행 파일은 변경하지 않았고, 이번 확인은 문서의 접근 경로와 초안 의미에 한정된다.
