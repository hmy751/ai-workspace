# 전체 잠정안에서 먼저 구체화할 결정과 그 영향

2026-10-13. 문서 정리 커밋 `5950cf9` 직후 작업 트리가 clean임을 확인하고 논의를 이어갔다. 이 기록은 다음 결정의 **비교안과 Main의 추천**이며 사용자 채택이나 실제 실행 결과가 아니다.

## 사용자 요청과 비교 범위

> 먼저 커밋해줘
> 그럼 이제 Spec에 모은 전체 잠정안을 기준으로 이어가보자. 지금 뭘 먼저 결정해야 하고, 그 선택에 따라 전체 체계랑 관련 티켓이 어떻게 달라지는지 구체적인 예시로 보여줘.

이미 선택한 B의 검토자 직접 수정, Main의 작업 정의·결과 통합은 유지한다. 첫 질문으로 **구현 전에 무엇을 갖춰 주며 어떤 상세 판단은 검토에 집중할지**를 제안한다. 구체적으로 이번에는 깊은 모듈·테스트 설계 같은 상세 품질 기준을 구현자와 검토자 모두 기본으로 읽게 하는 안과 검토자에게 집중하는 안을 비교한다. 이는 일반적인 ‘맥락은 적을수록 좋다’의 선택이 아니다.

이 질문을 먼저 고른 이유는 B에서 검토자가 직접 수정한다는 방향은 있지만, 어떤 판단을 구현에서 기대하고 어떤 판단을 검토에서 보강하는지가 덜 구체적이기 때문이다. 이를 정하면 Project가 제공할 내용, 작업별 Spec·Ticket의 깊이, 스킬의 읽기 경로와 검토 결과가 남길 기록을 같은 사례로 설계할 수 있다. 전체 기록 구성이나 모든 스킬을 먼저 확정할 필요는 없다.

## 같은 가상 작업에 두 안을 적용한다

가상 요청은 ‘알림 설정을 바꾸고 저장할 수 있게 해 달라’이다. 아래 동작은 비교를 위해 가정한 요구이며 실제 Noline 요구가 아니다.

- 저장 성공을 확인한 뒤 완료를 알리고, 화면을 다시 열면 저장한 값이 보인다.
- 서버가 저장을 거절하면 이전 저장값은 유지되고, 화면의 입력값과 오류가 보여 다시 시도할 수 있다.
- 자동 저장·계정 간 동기화·저장 형식 변경은 이번 결과에 포함하지 않는다.
- 성공·저장 거절·재진입을 확인할 테스트와 실제 실행 경로가 필요하다. 구체 명령·실패 재현 수단의 존재는 아직 가정하지 않는다.

두 안 모두 구현자에게 이 결과와 제약, 관련 제품 맥락, 기존 저장 코드와 검사·실행 경로를 전달한다. 공통 계약·필수 제약을 검토 때 처음 알려 주는 안은 비교 대상이 아니다. 검토자는 두 안 모두 직접 수정하고 수정 후 검사·실제 확인을 할 수 있다. UI 단위 검사만으로 실제 저장·재진입까지 확인했다고 보지는 않는다.

| 비교 | 구현자와 검토자가 상세 기준을 함께 사용 | 상세 기준을 검토자에게 집중 |
| --- | --- | --- |
| 구현 시작 | 동작 요구와 함께 깊은 모듈·호출자 부담·테스트 경계의 상세 기준을 읽고 설계에 적용한다. | 동작 요구·필수 계약·관련 코드·검사 수단을 사용한다. 상세 품질 체크리스트 전체를 기본 입력으로 추가하지 않는다. |
| 첫 구현 | 호출자가 검증·저장·오류 변환 순서를 일일이 알지 않도록 처음부터 구조를 설계한다. | 기능을 구현하고 의미 있는 동작 검사를 만든다. 설계를 포기하는 것은 아니지만, 구조의 충분한 개선을 다음 검토에서도 맡는다. |
| 검토자가 하는 일 | 같은 기준으로 판단을 다시 살피고 직접 개선한다. 구현자가 이미 기준을 읽었어도 별도 판단의 필요가 사라지지는 않는다. | 상세 기준을 적용해 UI에 흩어진 저장 처리 책임을 적절한 모듈로 모으고, 구현 내부 호출 순서만 확인하는 검사를 동작 중심으로 고친다. |
| 기대 이점 | 초기 설계에 기준을 반영해 큰 재작업을 줄일 수 있다. | 구현자의 탐색·디버깅 부담과 세밀한 품질 판단을 나눌 수 있다. |
| 비용·약점 | 구현자가 읽고 적용할 내용이 늘고 검토와 판단이 겹칠 수 있다. | 검토 시 수정량이 커질 수 있고, 초기에 필요한 구조 제약을 뒤늦게 알면 재작업이 크다. |

이는 예측되는 차이이며 어느 안의 실제 성능이 더 좋았다는 비교 결과가 아니다. 모듈 추출이나 특정 함수명 자체를 좋은 설계의 증거로 삼지 않는다. 호출자가 알아야 할 순서·오류·설정이 줄었는지, 변경과 검사가 적절한 곳에 모이는지를 비교한다.

## Main의 추천과 예외

현재 추천은 **상세 품질 판단은 검토자에게 집중하되, 제품 맥락·필수 계약·실행 수단은 처음부터 갖춰 주는 안**이다. 이미 선택한 B를 활용하고 Matt가 제안한 판단 부담의 분리를 구체적으로 검토할 수 있기 때문이다. 구현자는 기존의 좋은 코드 패턴과 검사에서 도움을 받고, 검토자는 그 패턴 자체가 이번 요구에 적절한지도 판단한다.

권한·데이터 형식·외부 공개 계약·다른 작업과 공유하는 인터페이스처럼 뒤늦게 바꾸기 어려운 결정은 구현 전에 다룬다. 위 사례에서 단순한 내부 함수 정리는 검토자가 직접 할 수 있지만 저장 형식을 바꾸거나 실패 시 사용자 입력을 버리는 동작으로 바꾸는 것은 Main의 재판단으로 돌아간다. ‘내부 설계는 언제나 사전 논의 불필요’라는 규칙은 제안하지 않는다.

| 설계할 부분 | 상세 기준을 함께 사용하면 | 검토자에게 집중하면 | 현재 014의 담당 |
| --- | --- | --- | --- |
| 작업 정의와 실행 | 작업별 결과·제약에 더해 구현 단계에 적용할 설계 기준을 선택해 연결한다. | 작업별 결과·제약·검증 장면과 관련 공통 맥락을 연결하고, 구현 후 검토에서 정교화할 설계 판단을 구별한다. | 01-01의 인수·수정 범위, 04-01의 작업 정의·재판단 행동 |
| 품질 기준과 스킬 | 구현과 검토 두 시점에서 쓸 구체 사례·기준과 읽기 범위를 설계한다. | 구현자가 처음부터 알아야 할 제약과 검토자가 집중해 판단할 기준을 구별한다. 검토는 지적 보고에 그치지 않고 수정·재확인까지 잇는다. | 01-02가 기준의 내용·적용 조건을 주도하고 관련 스킬 과제로 전달 |
| Project 공통 맥락 | 구현자와 검토자가 필요한 설계 기준·이유·사례를 찾는 경로를 갖춘다. | 공통 제품·구조·실행 맥락과 검토용 상세 기준을 필요에 따라 찾도록 한다. 문서·폴더를 반드시 별도로 만든다는 뜻은 아니다. | 03, 구체 읽기·갱신 행동은 04-03 |
| 실제 검증 | 양쪽 모두 저장 성공·거절·재진입을 확인할 수 있어야 한다. | 동일하다. 검토자에게 최종 확인을 맡기려면 그 주체도 앱 실행·상태 재현·관찰 수단을 쓸 수 있어야 한다. | 01-03. 검토자가 바뀌어도 필요한 결과 근거 자체는 줄어들지 않는다. |
| 기록과 경험 반영 | 초기 설계 이유와 검토에서 달라진 판단을 연결해 보존한다. | 검토에서 실제 구조가 달라질 수 있으므로 최종 선택·근거와 다시 볼 대안·시도를 남긴다. 반복 수정이 보이면 코드·검사·지침 중 어디를 개선할지 별도로 판단한다. | 기록의 구성·갱신은 02, 새 기준 채택은 05, 프로젝트 간 전달·재적용은 06 |

관련 Ticket을 모두 착수·완료로 바꾸는 것은 아니다. 01-02에서 이번 기준 배치의 사례를 비교하고 01-01의 인수·수정 범위에 연결한다. 03과 01-03에서는 그 사례를 성립시키는 공통 맥락·실행 수단을 필요한 만큼 구체화한다. 07의 전체 연결 검토는 이 선택이 다른 책임과 충돌하는지 보는 데 사용한다.

예를 들어 검토 중 ‘저장 실패 때 입력이 사라지는 문제’를 수정했다고 하자. 수정 근거와 확인 결과는 해당 Work에 남긴다. 그 한 번의 수정만으로 모든 프로젝트에 새 스킬을 설치하지 않는다. 반복될 가능성과 영향이 크다면 기존 저장 모듈의 오류 처리나 회귀 검사로 막는 안, 제품별 개발 기준에 남기는 안을 비교한다. 이런 경험을 ai-workspace 공통 방식에 올릴지와 다른 프로젝트에 다시 반영할지는 비용까지 보고 별도 판단한다.

## 자료에서 가져온 것과 우리 판단

- [Matt의 PR 병목 강연](../source/lectures/01_PR_병목_강연_전체번역.md) 5장은 상세 coding standards를 reviewer에게 집중하고 reviewer가 직접 변경하도록 권한다. 현재 추천은 이 부담 배치를 참조한다. 우리 환경에서의 효과가 확인된 것은 아니다.
- [Lauren의 Agent 신뢰 강연](../source/lectures/03_Agent_신뢰_강연_전체번역.md) 4~5장·10장은 실행·관찰 능력, 좋은 코드 패턴과 구조·자동 검사의 역할을 강조한다. reviewer용 기준을 정비하는 것만으로 개발 환경 설계를 끝내지 않는 근거다. 모든 Project에 전용 CLI·Feature Map·새 framework를 만들자는 채택은 아니다.
- [Vercel 제공 자료](<../source/lectures/vercel-product-design (1).md>)의 routing은 작업과 대상에 맞는 canonical 내용을 선택하고, 제품 맥락과 실제 화면을 확인하게 한다. 구현 단계에서도 상세 UI 기준을 읽게 하므로 Matt의 ‘standards는 reviewer만’과 적용 범위가 완전히 같지는 않다. 어떤 기준을 언제 적용할지는 우리 설계에서 판단해야 한다.
- Feature Map은 기능 의미·도달 방법, routing은 필요한 근거를 찾는 방식에 관한 예를 제공한다. 실제 내용의 중복과 대체 가능성은 사용할 장면과 기존 Project 내용을 보고 판단한다. 파일 이름을 먼저 채택하거나 둘의 병존을 의무화하지 않는다.

다음 구체화에서는 이 가상 작업의 구현 인수 내용·검토 입력·실제 검증 근거를 짧은 본문으로 작성해 비교할 수 있다. 그 결과를 통해 어떤 내용을 Project가 소유하고 어떤 내용을 Work에 남길지 정한 다음, 기록 구성과 스킬의 실제 형태를 판단한다. 이 순서는 현재 Main의 제안이며 사용자의 선택에 따라 바꾼다.
