# 04-01 기존 스킬·보완안의 사후 정정 없는 실행 비교

2026-10-20. **보완안은 충분한 Ticket의 재서술을 줄였지만, 두 스킬의 판단 정확도를 개선했다고 입증하지는 못했다.** 두 사례와 각각의 반대 조건에서 기존판·보완판을 각2회, 총16회 실행했다. 버전을 가린 독립 검토도16개 모두 현재 요청에 답하기에 충분하다고 판단했다. 실제 Reference와 제품은 변경하지 않았다.

사용자 요청:

> 그럼 기존 스킬이랑 보완안으로 실제 비교해보자. 사후 정정이나 정답은 주지 말고, 두 사례랑 반대 조건에서도 판단이 제대로 달라지는지 확인해봐

## 결과와 해석

| 조건 | 기존 스킬2회 | 보완 스킬2회 | 확인한 차이 |
| --- | --- | --- | --- |

표의2회는 각 조합에서 독립 실행한 수이며 통계적 성공률이 아니다. 개별 응답과 입력은 [실험 자료](experiments/work-decision-skills-2026-10-20/README.md)에서 조건별로 연결한다.

### 작업 구체화에서 달라진 것

기존판 [run-11](experiments/work-decision-skills-2026-10-20/results/run-11.md)은 “조금 더 구체화할 부분은 있습니다”라며 세 묶음의 보강을 제시했다. 동시에 “이미 정한 요구라서 새 선택 없이 완료 조건에 구체화”한다고 밝혔고, 추가 제품 선택이 없다고 답했다. [run-15](experiments/work-decision-skills-2026-10-20/results/run-15.md)도 기존 관찰의 기대값과 개선 기준을 더 명시하자는 응답이었다.

보완판 [run-14](experiments/work-decision-skills-2026-10-20/results/run-14.md)는 “지금 티켓은 구현에 들어갈 만큼 구체적”이라고 판단한 뒤 새 반올림 경계만 검사에 연결했다. [run-05](experiments/work-decision-skills-2026-10-20/results/run-05.md)도 같은 방향이었다. 충분성 판단과 실제 추가분을 먼저 반환하게 한 문구의 의도에 맞는 차이다.

그러나 이를 기존판의 오답을 고쳤다고 계산하면 안 된다. 독립 검토자는 기존판의 구체적 기대값도 입력에 근거한 타당한 제안이며, 문서 추가를 착수의 차단 조건으로 만들지 않았다고 보았다. Main도 이 판정을 수용한다. **확인한 효과는 반복 명시를 줄인 것이고, 요구 해석의 정확도 향상은 아니다.** 문서 편집이나 후속 구현을 실행한 시험이 아니므로 실제 유지 비용이 줄었다는 것까지 확인하지 않았다.

반대 조건에서는 두 판본 모두 기준을 선택해야 한다고 판단했다. 일반 반올림 규칙은 기존판 run-07이 “정확히 절반이면 절댓값이 커지는 쪽”으로 가장 명확히 제안했다. 보완판 run-01은 대표 값 `1.005 → 1.01`에 집중했다. 채택 시 이를 일반 규칙과 연결해야 하므로 짧은 응답을 무조건 개선으로 볼 수 없다.

### 복구 알림에서 달라지지 않은 것

기존판 [run-16](experiments/work-decision-skills-2026-10-20/results/run-16.md)도 첫 문장에서 “기존 화면 표시로 복귀를 충분히 알 수 있는지 먼저 확인”하자고 했다. [run-06](experiments/work-decision-skills-2026-10-20/results/run-06.md)은 작은 안내의 역할부터 설명했지만, 뒤에서는 구현 전에 UX를 확인하고 부족할 때만 안내를 추가하자고 연결했다.

보완판 run-03·run-09 역시 필요성 확인을 앞당겼다. 두 판본 모두 기존 정책의 선택을 임의로 폐기하지 않았고, 알림을 위해 강제 조회·화면 대기·동기화 조율을 추가하지 않았다. **보완판이 처음으로 필요성 재판단을 수행했다는 결론은 성립하지 않는다.**

반대 조건에서도 네 응답 모두 현재 표시의 인지 부족을 인정하고 해결 방식을 검토했다. 기존판 run-12가 토스트를 우선 검증한 것은 가능한 순서다. 화면을 잠시 보지 않는 실패 조건에서 토스트도 놓칠 수 있음을 더 선명하게 다룰 수 있지만, 토스트의 효과를 검증 완료로 간주하지는 않았다.

보완판에도 작은 누락은 있었다. run-13은 실제 Ticket의 “알림 의미·시점 결정 및 구현”을 “토스트 구현”으로 좁게 재서술했고, run-09는 초기 확인 제외·반복 알림 방지 조건을 응답에 다시 적지 않았다. 독립 검토는 모두 추천을 무효화할 오류는 아니라고 봤다. 어느 판본도 후속 구현용 지침으로 그대로 복사하면 충분하다는 판정은 아니다.

## 실행과 독립 검토 방법

실행 전에 [계획](experiments/work-decision-skills-2026-10-20/protocol.md), 판본, 입력과 해시를 고정했다. 기존판은 현재 Reference 두 스킬의 전체 본문이다. 보완판은 [앞선 제안](2026-10-20-ticket04-01-skill-behavior-proposal.md)의 시작·판단·반환 문구를 적용한 전체 사본이다. 제안 기록에 있던 기대 응답·사례 해설·검증표는 실행자에게 주지 않았다.

- 각 실행은 대화 이력이 없는 새 subagent였다. 같은 Main 모델·추론 설정을 상속하고 실행 순서는 고정 seed로 섞었다. 각 실행자는 자기 입력과 한 판본만 받았다. 판본 이름·다른 응답·평가 기준·사후 사용자 정정은 제공하지 않았다.
- 작업 구체화에는 원요청·실행 전 Ticket·공통 품질 일부·중립적인 Work 안내와 당시 계산·표시의 사실 보고를 제공했다. 복구 알림에는 원요청·이전 및 후속 정책 발췌·현 상태와 조사 사실을 제공했다. 실제 source의 경로·구간과 재구성 방법은 실행 전 계획에 남겼다.
- 복구 알림 요청에는 시험 대상인 reconsider-work를 명시했다. 실제 사건의 자동 선택 여부를 시험한 것은 아니다. 두 판본 모두 같은 호출·같은 자료를 받았다.
- 반대 조건은 표시 통일 요청, 복귀 인지 실패 관찰을 각각 만든 가상 변형이다. 필요한 선택·관찰을 명시한 좁은 조건 분기 시험이며, 숨은 요구를 스스로 발견하는 시험은 아니다.
- 응답 회수 후 계열별 별도 검토자2명에게 버전을 숨기고 같은 입력과 섞은 응답을 제공했다. 현재 요구·근거·미확정·추천의 유효성을 평가하도록 했으며, 정답 기능이나 기대 승자를 주지 않았다. 응답의 원자료 링크만 검토 사본으로 바꿨다.
- [구체화 검토](experiments/work-decision-skills-2026-10-20/reviews/definition.md)와 [재판단 검토](experiments/work-decision-skills-2026-10-20/reviews/reconsideration.md)는 각각8개를 모두 충분으로 판정했다. Main이 버전 매핑을 열어 원응답과 대조했다. ‘충분’은 이번 요청에 대한 판단 제안이 타당하다는 뜻이다.

## 해석의 한계와 후속 판단

이 시험에는 제품 코드 전체나 원래 긴 작업 대화가 없었다. 당시 조사에서 얻었다고 보고된 사실을 Main이 선별해 먼저 제공했다. 특히 작업 구체화의 전체 원 Spec은 재현하지 않고 실행 전 Ticket과 공통 품질·현재 관찰로 구성했다. **따라서 원래 실패의 재현시험이 아니라, 필요한 사실을 받은 뒤 판단하는 판본 비교다.** 기존판이 이미 잘 작동한 이유를 스킬, 짧고 정리된 입력, 모델, 당시 대화 부담 중 하나로 단정할 수 없다.

각 조합의 반복은2회이며 사례도 두 계열뿐이다. 신규 Work를 처음 만드는 장면, 명시적으로 필수인 특정 수단, 긴 대화에서 문서를 찾아 대조하는 동작, 실제 문서 수정과 구현까지 검증하지 않았다. 범위 밖 접근은 지시로 제한했고 OS 격리나 전체 도구 접근 감사를 추가하지 않았다. 해시 확인은 입력의 무변경 증거이지 열람 경계의 증명은 아니다.

이 결과에서의 권고는 다음과 같다.

- **work-discussion:** 충분성 확인 요청의 반환을 좁히는 안은 유지할 후보이다. 이번 근거의 효과 명칭은 중복 구체화 제안 감소로 제한한다. 전체 작업 정의 능력이 좋아졌다는 근거로 채택하지 않는다.
- **reconsider-work:** 이번 비교만으로 본문 교체 필요성은 뒷받침되지 않았다. 기존판도 목적·현재 기여·관찰 필요성을 재판단했으므로 보완안은 미채택으로 둔다.
- **후속 원인 확인:** 사후 정정 전에 필요한 기존 기준·정책 변화를 실제로 찾고 연결하는 과정에서 어디가 빠졌는지 원문으로 좁히는 것이 더 유용하다. 이번 입력에 자료를 선별해 제공한 효과와 스킬 자체의 효과를 분리해야 한다. 여기서 또 기준·사례를 늘리거나 곧바로 별도 검증 장치를 도입하지 않는다.

위 권고는 Main의 시험 결과 해석이며 사용자의 채택 결정이 아니다. 실제 스킬 변경은 하지 않았다. DB·인증 사례는 앞선 사용자 결정대로 이후01-01·01-02에서 다룬다.04-01 전체의 완료나 다른 병렬 Ticket의 상태 변경으로 올리지 않는다.

## 보존과 확인

16개 원응답, 네 조건의 입력, 네 전체 스킬 판본, 변경분, 실행 지시문·해시, 두 독립 검토와 버전 매핑을 [실험 폴더](experiments/work-decision-skills-2026-10-20/README.md)에 보존했다. 실행 입력은 모두 고정 해시와 일치하며 실제 Reference 두 스킬은 실험의 기존판·보존 Noline판과 바이트가 같다. 확인 결과는 [integrity.json](experiments/work-decision-skills-2026-10-20/integrity.json)에 남긴다.

`skill-creator`의 실행 비교, `subagent-delegation`의 독립 입력·역할 분리, `recall-document-guidance`의 현재 상태·근거 보존을 적용했다. 제품·운영·전역 스킬 파일은 변경하지 않았다.
