# 판단의 이유·조건을 본문 가까이에 두는 조사와 구성안

**현재 지위 — 2026-10-20 정정:** 사용자가 원한 것은 본문을 형성한 의도·배경·판단과 필요한 과정·원문을 본문 옆 별도 자료로 두는 것이다. 아래의 본문 설명·형식과 주제별 본문·사례 배치 중심 제안은 이를 충족하지 못해 현재 추천에서 제외했다. 외부 자료 조사 사실과 당시 제안은 보존하며, 현재 구체화는 [105](2026-10-20-105-adjacent-formation-context.md)에서 이어간다.

2026-10-19. 세션 정리103과 커밋864d953 뒤 사용자는 다음 Ticket으로 넘어가기 전에 Karpathy의 LLM Wiki, Matt의 지침, Desktop/dev-wiki를 참고해 현재 데모의 본문과 주변 맥락을 어떻게 구성할지 조사·논의하자고 요청했다. **이 기록은 자료 조사와 Main의 적용 제안이다. 데모 변경·새 구조 채택·스킬 구현은 아직 하지 않았다.**

후속으로 사용자가 구성·형식을 더 구체화하자고 요청해 [구체 구성안](#후속-구체화-파일-배치와-본문-형식)에 파일 배치, 같은 내용의 두 형식, 사례·상세 근거의 작성 형태와 연결 예를 추가했다. 아래 첫 조사의 제안과 후속 구체안을 구별한다.

## 세 자료가 각각 말하는 것

### Karpathy: 대화에서 얻은 이해가 현재 본문에 축적되게 한다

Andrej Karpathy의 [LLM Wiki 공식 원문](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)은 새 자료와 질문에서 얻은 내용을 기존 개념·종합 설명에 통합하고 모순을 드러내는 패턴이다. 원자료, 유지되는 위키, 운영 지침을 구별하며 내용 탐색과 시간순 이력도 나눈다. 핵심 표현은 “The knowledge is compiled once and then kept current”다. 출처: The core idea, Architecture, Operations, Indexing and logging. 2026-10-19에 공식 Gist 본문을 확인했고 Raw 링크가 가리킨 revision은 ac46de1ad27f92b28ac95459c782c07f6b8c964a다.

이번에 가져올 의미는 논의 결과를 기록에만 쌓지 않고 현재 설명을 실제로 갱신하는 것이다. ‘모든 지침 옆에 의도를 적는다’는 구체 배치는 원문의 직접 요구로 확인되지 않는다. 상세 구조는 목적에 맞게 선택하도록 열어 둔다.

### Matt: 한 판단에 필요한 의미를 함께 읽게 한다

Matt Pocock의 [writing-for-agents 고정 원문](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/skills/productivity/writing-for-agents/SKILL.md#L29)은 Co-location을 “Keep a concept's definition, rules, and caveats under one heading rather than scattered”라고 설명한다. 모든 사용 경로에 필요한 내용과 일부 경로에서만 필요한 상세를 구별하고, 후자는 자료의 역할과 읽을 조건을 가진 연결로 둔다. Pruning에서는 코드·설정을 조회해도 알 수 없는 선택 이유 등을 보존할 대상으로 든다. 2026-10-19에 공식 main과 위 고정판의 관련 문장을 대조했다.

이는 사용자가 기억한 ‘가까이 두기’와 직접 대응한다. 같은 의미를 여러 곳에서 별도로 관리하는 것과는 다르다. [기존 비교61](2026-10-17-61-reference-comparison-for-format-design.md)에서도 이 원칙을 다뤘다. 코드의 변경·검증 범위를 모으는 locality와는 관련되지만 같은 주장은 아니다.

### dev-wiki: 본문과 관련 자료를 같은 주제 안에서 관리한다

실제 [README의 자료 관계](/Users/hammyeong-yeon/Desktop/dev-wiki/README.md)는 주제별 묶음 안에서 현재 설명인 main과 출처·대화 기록·이력인 support를 구별한다. [초기 결정 기록](/Users/hammyeong-yeon/Desktop/dev-wiki/meta/2026-10-12-dev-wiki.md)에는 사용자의 “react-query 면 그 폴더 안에 다 있어야” 한다는 직접 요구가 있다. 이 폴더 구성은 사용자 목적에 맞춘 선택이다.

두 문장이 이번 검토에 특히 직접적이다.

- [README](/Users/hammyeong-yeon/Desktop/dev-wiki/README.md): “각 본문은 보조 자료를 모두 읽지 않아도 설명을 이해할 수 있어야 한다.”
- [현재 지침](/Users/hammyeong-yeon/Desktop/dev-wiki/CLAUDE.md): “사례나 연습 기록의 저장과 링크 추가만으로 본문 갱신을 대신하지 않는다.”

[React Query 본문](/Users/hammyeong-yeon/Desktop/dev-wiki/topics/react-query/main/content.md)은 화면에서 쓰는 쿼리·기본 설정이라는 조건과 이전 값이 잠시 보이는 이유를 본문에 설명한다. [주변 기술 근거](/Users/hammyeong-yeon/Desktop/dev-wiki/topics/react-query/support/sources.md)는 더 상세한 적용 조건과 확인 출처를 맡는다. 본문이 이유를 설명하는 것과 상세 근거를 다시 확인하는 깊이가 다르다.

사용자가 소화한 이해만 본문에 편입하는 학습 기준, main/support라는 고정 배치, 면접 자료 분리는 이 저장소의 목적에 따른 선택이다. 개발 행동 지침에 자동으로 가져오지 않는다. 실제 콘텐츠가 적으므로 장기 운영 효과의 입증 사례로도 취급하지 않는다. [Karpathy 참고 메모](/Users/hammyeong-yeon/Desktop/dev-wiki/meta/karpathy-llm-wiki.md)는 AI가 작성한 해석이며 원문 사본은 아니다.

## 적용 제안: 현재 의미는 본문에, 상세 근거는 관련 절에서

**본문은 무엇을 할지와 함께, 지금 그 판단이 성립하는 이유·조건을 설명한다.** 논의가 있었다는 사실보다 그 논의로 명료해진 현재 의미를 문서의 독자와 역할에 맞게 쓴다. 아래는 Main의 제안이며 아직 새 운영 규칙으로 채택한 것은 아니다.

1. 해당 판단을 적용하는 데 필요한 목적·이유·조건·중요한 예외는 같은 절에서 읽게 한다. 문서 첫머리에 모든 배경을 몰거나, 필요한 전제를 여러 링크에서 조립하게 하지 않는다. 이미 충분하면 늘리지 않는다.
2. 상세 사례나 대안 비교가 있어야 판단 차이가 이해될 때만 같은 책임 범위의 자료로 연결한다. 연결 문구는 무엇을, 어느 상황에서 보아야 하는지 설명한다. 모든 문서에 별도 rationale 파일·support 폴더·동일한 목차를 만들지는 않는다.
3. 어떤 선택이 현재 유효한 이유와 그 선택이 생긴 대화 경위를 구별한다. 현재 이유는 본문이, 원문·당시 대안·변경 이력은 해당 기록이 맡는다. 전제가 바뀌면 현재 설명을 고치고 과거 기록은 당시 근거로 보존한다.
4. 내용 책임을 유지한다. 개인의 일반 판단 이유는 Personal, 제품이 계속 지킬 약속의 이유는 Project, 이번 적용 조건·대안·선택은 Work, 입력 선택·역할 연결·갱신 절차의 이유는 DEVELOPMENT에 둔다. 서로의 전제를 이해하기 위한 짧은 설명과 상세 기준의 중복 관리는 구별한다.
5. 자료를 추가했을 때는 본문의 어떤 의미가 달라졌는지 대조한다. 새 조건·정정·선택 이유가 생겼다면 그 본문을 갱신하고 실제로 영향을 받는 판단과 안내를 이어 맞춘다. 같은 적용이 반복됐다는 이유만으로 본문을 늘리거나 모든 관련 파일을 동기화하지 않는다.

이 구상은 [102의 갱신 책임](2026-10-19-102-personal-project-update-ownership.md)을 유지한다. 가까이 둔다는 것은 관련 자료의 현재 의미를 같은 문맥에서 이해하게 하는 것이며, 개인 기준의 상세를 Project에 복제하는 근거가 되지 않는다.

### 한 절에 적용한다면

DEVELOPMENT의 갱신 표 앞에 둘 수 있는 설명 초안이다. 기존102의 관리 기본값을 독자가 이해할 이유로 다시 서술한 Main의 문장이며, 사용자 직접 인용이나 실제 반영 결과는 아니다.

> 개인 기준을 이번 작업에 적용하는 것과 프로젝트 전체가 계속 지킬 약속으로 정하는 것은 다른 선택이다. 개인의 선호가 바뀌었을 때 제품 계약까지 함께 바뀐 것으로 읽히지 않도록, 달라진 판단을 소유한 본문부터 갱신한다. 이번 적용의 이유와 비용은 Work에 남기고, Project가 지속 규약으로 채택했거나 제품 계약·구현 사실이 달라진 부분은 Project에 반영한다. 각 문서가 자기 의미를 설명하는 데 필요한 짧은 설명은 함께 둘 수 있다.

여기에 바로 아래의 기존 갱신 표와 필요시 [walkthrough의 적용 장면](prototypes/development-workflow/walkthrough.md#다음-변경은-달라진-내용을-소유한-곳에-남긴다)을 이어 읽게 하는 방식이다. 기존 본문과 중복되는 문장은 추가가 아니라 교체·통합으로 처리해야 한다. 목적·규칙·예외라는 고정 항목을 모든 절에 채우려는 예시는 아니다.

### 014 기록과 대상물의 경계

014의 과거 논의는 작성자가 정확한 의미를 복원할 근거다. 그 과정에서 얻은 현재 이유와 조건은 데모 안에서 자립적으로 설명할 수 있다. 데모 독자에게 바깥014 기록을 필수로 읽게 하거나, 작성자의 대화를 데모 안에서 벌어진 제품 결정으로 바꾸지는 않는다.

예를 들어 코드 자체의 명료함을 지향하는 이유는 Personal에 설명하고, 이 문장을 만들게 된 실제 사용자 정정은014 기록101에 보존한다. 인증 개명의 이번 비용·대안은 데모 Work의 현재 설계와 A/B 기록이 맡는다. 이 둘은 보존하려는 사건과 독자가 다르다. 새 구상을 과거의 ‘작성 근거를 데모 안에 다시 넣기’로 환원하지 않는다.

## 다음 논의에서 판단할 것

전체 문서를 일괄 개편하기 전에, 위 갱신 절처럼 이유 보완의 값이 있는 한 부분을 실제 전후 문장으로 비교하는 것이 Main의 추천이다. 아직 적용 순서나 대표 장면을 사용자와 확정하지 않았다.

읽는 사람이014 대화 없이 해당 절에서 목적과 조건을 설명하고, 새 상황에서 유지·수정 판단을 할 수 있는지 본다. 예컨대 개인 선호만 달라진 경우와 Project의 공개 완료 계약이 달라진 경우를 구별할 수 있어야 한다. 현재 채택·가정·유보를 구분하고, 상세 근거를 읽어야 할 때 그 위치와 이유를 찾을 수 있는지도 확인한다. 링크 검사와 글의 길이만으로 이 효과를 판단하지 않는다.

## 조사·변경 범위

Main은 공식 Karpathy·Matt 원문, 현재 데모의 관련 본문과97~103 중 필요한 기록을 확인했다. 두 읽기 전용 조사자가 dev-wiki의 실제 구성과 Matt 관련 원자료를 나눠 확인했고, Main이 핵심 문장과 대표 파일을 대조해 종합했다. dev-wiki 외의 다른 Desktop 저장소로 범위를 넓히지 않았다.

이번에는 이 조사 기록과014의 현재 진입 안내만 갱신한다. Personal·Project·Work 본문, viewer, 코드, source, 운영 스킬과 전역 지침은 그대로다. 데모 개선·새 작업자의 실제 수행 효과·전체 수용·Ticket 완료·추가 커밋은 이 조사의 결과가 아니다.

## 후속 구체화: 파일 배치와 본문 형식

사용자 요청:

> 근데 좀 더 구체적으로 구성이나 형식을 정하고 싶어

아래는 선택할 수 있도록 구체화한 Main의 추천안이다. 앞선 의미 설명만으로 실제 작성 형태가 정해진 것처럼 취급하지 않는다. **파일 배치와 문서 안의 쓰는 형식을 각각 정한다.** 현재 데모를 이 구조로 이동하거나 고친 상태는 아니다.

### 파일은 내용 책임을 유지하면서 필요한 주제만 묶는다

Personal의 세 주제는 각각 일반 본문과 상세 사례가 한 쌍이다. 이 둘은 같은 판단을 배우고 적용할 때 함께 찾으므로 주제 폴더로 묶는 안을 추천한다. README가 해당 주제의 실제 본문을 맡고, 사례는 바로 옆 cases.md에서 읽는다. 별도의 목차 전용 README와 본문 파일을 둘 다 만들지는 않는다.

Personal 개발 기준 폴더 안의 제안 배치다. 실제 경로를 변경한 목록이 아니다.

```text
development/
├── README.md                       공통 관점과 주제 선택
├── naming-and-completion/
│   ├── README.md                    이름·책임·완료의 현재 기준과 이유·조건
│   └── cases.md                     같은 코드 비교·저장 완료·isError 사례
├── contracts-and-lifetime/
│   ├── README.md                    오류·계약·수명의 현재 판단
│   └── cases.md                     fetcher·Toast·이벤트의 조건별 판단
└── shared-boundaries/
    ├── README.md                    공통 책임과 사용처 선택의 현재 판단
    └── cases.md                     Field·Container·주문 사례
```

현재 이름 주제의 [일반 본문](prototypes/development-workflow/noline-demo/context/personal/development/naming-and-completion/INDEX.md)과 [상세 사례](prototypes/development-workflow/noline-demo/context/personal/development/naming-and-completion/INDEX.cases.md)를 같은 주제 아래 모으는 차이다. 내용의 책임은 Personal로 같다. 현 배치를 유지하면 이동 비용은 없고, 주제 묶음으로 바꾸면 같은 이름의 파일을 두 위치에서 찾아 짝짓는 부담이 줄어든다. 이 제안은 후자의 이득을 선택한 것이다.

이 데모에서 자료 역할이 다른 곳에는 같은 폴더 모양을 강제하지 않는다.

| 대상 | 추천 배치 | 이유 |
| --- | --- | --- |
| Personal의 일반 기준·상세 사례 | 위 주제 폴더 안 본문과 cases | 같은 판단에 대한 일반 설명과 구체 대비를 함께 읽고 갱신한다. |
| Project의 common·guidance·current | 현재 역할별 위치 유지 | 제품 의미, 지속 계약, 현재 구현은 서로 다른 이유로 바뀐다. 현재 구현을 계약의 부록처럼 배치하지 않는다. 관련 계약 절에서 필요한 제품 목적을 짧게 설명하고 정본으로 연결한다. |
| Project의 중요한 제품 선택 | 기존 decisions 사용 | 제품 공통 선택의 상세 비교가 실제로 생겼을 때 사용한다. 이번 개명 선택을 제품 전체 결정으로 올리지 않는다. |
| Work의 현재 선택·대안·검사 | 현재 Spec·records 위치 유지 | 현재 답과 조건은 Spec, 상세 비교·실행 이력은 records가 맡는다. 같은 내용을 위한 새 support 층을 추가하지 않는다. |
| DEVELOPMENT | 현재 단일 절차 문서 유지 | 각 단계의 목적·행동·반환을 순서와 함께 읽는다. 단계마다 이유 파일을 만들지 않는다. 최종 스킬 위치·Owner는 기존대로 후속 판단이다. |

Personal의 출처 비교가 실제로 길어져야 references.md 같은 옆 문서를 추가한다. 참고 링크 몇 개는 관련 절의 끝에서 직접 설명한다. 파일을 채우려고 sources·rationale·history·log를 일괄 생성하지 않는다.014의 작성 대화는 계속 바깥014 기록이 소유한다.

### 본문 기본형은 의미별 절 안에서 기준과 이유를 연결하는 글이다

문서 첫머리는 무엇을 다루고 언제 읽으며 어떤 판단을 지향하는지 설명한다. 이후 제목은 ‘배경·목적·원칙·예외’라는 공통 항목 대신 실제로 판단할 내용을 드러낸다. 각 절에서 핵심 판단과 이유를 잇고, 선택이 갈리는 조건은 이어지는 문단·목록·표로 보여 준다. 사례가 더 필요한 독자는 그 절의 연결을 따라간다.

이름 기준의 한 절을 동일한 정보로 작성한 두 형식이다. **이 비교는 해당 절의 형식 예시이며 기존 이름 본문 전체를 대체하는 축약안이 아니다.**

#### 문장으로 연결한 형식 — 일반 본문의 추천 기본값

**역할과 완료 범위를 코드에서 먼저 드러낸다**

함수·Hook·완료 callback을 만들거나 고칠 때는 이름·타입·책임 배치·제어 흐름에서 맡은 일과 끝난 일을 읽을 수 있게 한다. 호출부를 읽는 사람이 별도 설명을 찾아야만 다음 행동을 판단한다면, 그 의미를 코드에서 더 선명하게 드러낼 여지가 있는지 본다.

설명은 코드만으로 알기 어려운 선택 이유·외부 제약·비자명한 실패 조건을 보완한다. 모든 정보를 긴 이름에 담거나 필요한 설명을 없애는 것을 목표로 삼지 않는다.

| 현재 확인한 조건 | 판단 |
| --- | --- |
| 필요한 동작은 제공하지만 역할·완료 범위를 설명에 맡기고 있다. | 개명·타입·책임 배치로 이해 부담을 줄일 수 있는지 비교한다. |
| 공개 호환성이나 실제 변경 위험이 개선 이득보다 크다. | 남는 설명 의존을 인정하고 기존 표현을 유지하는 절충을 검토한다. |
| 소비자가 필요한 결과를 구현이 제공하지 않는다. | 이름 비교에 앞서 부족한 동작·완료 계약을 고친다. |

이름 유지와 개명의 이득을 분리해 보려면 [같은 인증 코드의 표현 비교](prototypes/development-workflow/noline-demo/context/personal/development/naming-and-completion/INDEX.cases.md#같은-동작에서-이름-유지와-개명-비교)를 읽는다. 이 제안에 따라 이동한다면 연결 대상은 같은 주제의 cases.md 해당 절이 된다.

#### 항목으로 나눈 형식 — 같은 정보를 빠르게 대조할 때

| 항목 | 내용 |
| --- | --- |
| 적용 | 함수·Hook·완료 callback을 만들거나 고칠 때 |
| 기준 | 이름·타입·책임 배치·제어 흐름에서 맡은 일과 끝난 일을 읽을 수 있게 한다. |
| 이유 | 호출부를 읽을 때 별도 설명을 찾아야 하는 부담을 줄이고, 이어서 할 행동을 판단하게 한다. |
| 설명의 역할 | 선택 이유·외부 제약·비자명한 실패 조건을 보완한다. 긴 이름이나 설명 제거 자체를 목표로 삼지 않는다. |
| 선택 조건 | 필요한 동작을 제공하면서 의미가 불분명하면 표현·구성을 개선한다. 호환·변경 위험이 더 크면 기존 표현 유지의 절충을 검토한다. 필요한 결과가 없으면 동작·완료 계약부터 고친다. |
| 상세 | 이름 유지와 개명의 차이가 불분명할 때 같은 인증 코드의 표현 비교를 읽는다. |

두 형식의 정보는 같다. 일반 기준은 문장형이 이유와 조건을 이어 이해하기에 적합하다고 판단한다. 항목형은 현재 선택·미정·비용을 비교하는 Work Spec이나 결정 요약에 적합하다. 실제 독자 효과를 실험한 결론은 아니다.

문장형에서도 조건표를 쓸 수 있다. 반대로 모든 절에 표를 넣는 것이 형식 준수는 아니다. 고정할 것은 적용 범위·판단·이유·선택을 바꾸는 조건이 함께 읽힌다는 관계다.

### 상세 사례는 상황에서 선택이 달라지는 과정을 보여 준다

cases.md의 개별 사례는 다음 읽기 순서를 기본으로 삼는다. 이미 일반 본문에 있는 원칙을 다시 길게 설명하지 않고 해당 조건에서 어떻게 적용했는지 쓴다.

```text
## 같은 동작에서 이름 유지와 개명 비교

상황과 요구
  로그인 뒤 이동·닫기를 시작한다. callback에서 최신 조회 값을 읽지 않는다.
  실행 데모를 바탕으로 한 비교이며 실제 제품의 변경 전후는 아니다.

코드와 조건
  같은 동작·같은 설명을 둔 두 코드와 필요한 소비자를 보여 준다.
  내부 두 소비자·공개 호환 없음이라는 가정은 비교 전에 밝힌다.

선택을 가르는 차이
  이름에서 읽는 완료 범위, 남는 설명 의존, 변경할 참조를 대조한다.

이번 판단과 다시 볼 조건
  현재 조건에서 권하는 이유를 설명한다.
  공개 호환 요구나 최신 조회 값을 소비하는 요구가 생기면 무엇이 달라지는지 쓴다.
```

위 항목은 읽는 순서다. 짧은 사례는 문단 두세 개로 합칠 수 있다. 이 사례의 이름은 고정된 정답이 아니며, 실제 Work의 현재 선택은 Spec이 관리한다. 사례 본문의 판단은 교육용 비교로서 조건을 붙여 설명한다.

### 현재 결정과 상세 근거는 역할에 맞게 쓴다

Work Spec의 현재 선택은 ‘현재 답과 결정적 이유, 그 답을 제한하는 조건, 미정, 상세 비교 연결’을 함께 보여 주는 형식을 추천한다. 예를 들어 현재 로그인 작업은 다음처럼 읽을 수 있다.

| 구분 | 이 Work에서 읽을 내용 |
| --- | --- |
| 현재 선택과 이유 | 조회 요청과 인증 완료를 이름에서 읽도록 signInAndRequestRefresh·onSignedIn을 사용한다. 내부 두 소비자·공개 호환 없음은 개선 비용을 낮추는 조건이다. |
| 유지할 동작 | 소비자는 인증 적용 뒤 이동·닫기를 시작하며 최신 조회 값을 즉시 읽지 않는다. 현재 조회 비대기를 유지한다. |
| 다시 볼 조건 | 공개 호환성이 필요해지거나 소비자가 최신 조회 값을 사용해야 하면 표현·완료 계약을 다시 판단한다. |
| 남은 한계 | 실제 화면·네트워크·DB 동작까지 검증한 결과가 아니며 이름의 최적성을 확정하지 않았다. |
| 상세 비교 | 같은 동작·같은 주석을 둔 A/B 코드와 비교 근거는 기존 Work의 naming-alternatives 기록에서 읽는다. |

이는 [현재 Spec](prototypes/development-workflow/noline-demo/context/work/workspaces/001-login-completion-names/current/memory/spec/05-constraints-design-assumptions.md)의 선택 관련 부분을 보여 주는 형식 예시다. 기존 Spec의 제약·가정·실패 구별 등을 삭제하거나 이 표만으로 대체하려는 제안은 아니다.

깊은 대안 비교를 남길 기록에는 판단한 문제·당시 조건, 비교한 선택과 차이, 선택 이유와 남은 손해, 재검토 조건, 근거와 확인 한계를 쓴다. 이런 기록을 만들 때만 날짜와 적용 범위를 밝힌다. 모든 일반 본문에 결정 번호·승인자·상태 표를 붙이지 않는다. 새 정보로 선택이 바뀌면 현재 Spec을 고치고 과거 기록은 당시 선택으로 보존한다.

### 연결과 지위 표시는 읽는 자리에서 이해되게 한다

- 연결 문장은 자료 이름과 읽을 상황을 함께 설명한다. 예: ‘이름 유지와 개명의 이득을 분리해 보려면 같은 인증 코드의 표현 비교를 읽는다.’ ‘관련 자료 보기’만 쓰지 않는다.
- 기준 자체가 성립하는 필수 조건은 본문에 둔다. 상세 자료를 열어야 기본 규칙의 예외를 처음 알게 되는 구성은 피한다.
- 설명용 예시·현재 Work의 선택·미정인 운영 조건은 해당 주장 가까이에 적는다. 문서 전체를 한 단어로 ‘확정’ 표시하면 안쪽의 가정까지 확정된 것으로 읽힐 수 있다.
- 단순 출처는 관련 설명 가까이에 링크와 사용 범위를 둔다. 여러 원자료의 충돌이나 버전별 비교가 길어지면 상세 자료로 나누되 본문에는 현재 결론과 한계를 남긴다.
- 매 절마다 결정·근거·상태 카드를 추가하지 않는다. 코드·비교·현재 답을 가리는 반복 설명은 합친다.

### 이 구성안에서 아직 고를 것

Main의 추천은 **Personal의 주제 묶음, 일반 본문의 문장형 설명, 현재 선택의 간결한 항목형 요약, 기존 Project·Work 책임 유지**다. 사용자에게 이를 실제 문서 형태로 제시하고 논의를 이어간다. 구조의 채택과 데모 전체 이행은 아직 확정하지 않았다.

이행한다면 단순 파일 이동뿐 아니라 해당 본문·사례의 중복과 빠진 조건을 읽고 정리해야 한다. Personal 주제 경로를 바꾸면 개발 입구·관련 Work·walkthrough·viewer의 지정 경로를 함께 맞추고, 기존 코드 예시·조건·판단을 보존한다. 이번 제안에서는 이동·본문 교체·화면 재생성을 수행하지 않았다.
