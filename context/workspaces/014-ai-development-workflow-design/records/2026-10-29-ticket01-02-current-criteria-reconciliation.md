## 다음 논의가 실제로 필요한 곳

### 기존 코드 표현 기준을 어디까지 이어받을지

[78의 비교](2026-10-18-78-code-guides-comparison-and-applicability.md)는 기존 가독성·리팩터링 가이드의 고유 내용을 추상 원칙으로 대체하지 말아야 한다고 구별했다. 보존된 [Noline 코드 표현 가이드](../source/supplement/worktree-project-context/context/project/guidance/code-readability.md)에는 짧은 guard의 중괄호, 목적별 빈 줄, 전체 동작에서 helper로 읽히는 배치, 설명 주석과 탐색 주석, 실패 처리와 로그 필요성의 구별이 있다.

현재 Personal 공통은 포맷·주석·로그 세부를 Project 가이드에 맡긴다. 그런데 demo의 [code-readability](prototypes/development-workflow/noline-demo/context/project/guidance/code-readability/INDEX.md)는 인증 이름·완료에 한정된다. 기존 일반 표현 기준의 전 항목이 새 prototype에서 이어진 것은 아니다. demo가 대표 인증 사례라는 점을 고려하면 이것만으로 runtime 결함이나03 실패로 판정할 수는 없지만, 전체 품질 기준을 종합하는01-02에서는 의식적으로 범위를 선택해야 한다.

**추천:** 기존 가이드를 항목별로 대조해 개인에게 지속할 표현·판단, 프로젝트의 현재 계약·도구 규칙, 구현·검증 절차를 구별한다. 이름·실패·완료의 기존 중복을 또 복제하지 말고 중괄호·빈 줄·배치·탐색 주석·진단 로그 등 남은 의미를 연결한다. 이미 논의한 기준을 처음부터 취향 조사하지 않는다. 새 파일·새 주제 여부는 이 내용 선택 뒤 결정한다.

예를 들어 `if (...) return`에 중괄호를 쓰는 선호와, 조기 반환이 후속 처리를 생략해도 되는지의 동작 판단은 함께 보되 다른 성격이다. 로그 역시 ‘없애면 깔끔하다’가 아니라 오류 전달 이후에도 필요한 진단 정보가 무엇인지로 판단한다. 기존 가이드 전체를 Personal로 복사하는 결론은 아직 내리지 않았다.

### 계산·입력 단위와 경계값의 관점을 본문에 이어줄지

[날짜51](2026-10-16-51-date-input-and-range-contracts.md)에는 `month` 1~12와 `monthIndex` 0~11의 변환 위치, `as MonthIndex`와 실제 입력 검증의 차이, 종료일과 주 시작일이 같을 때 `>`/`>=`가 다른 결과를 만드는 사례가 있다. [구성70](2026-10-18-70-criteria-organization-proposal.md)은 단위·경계값을 동작 계약과 이름의 판단에 포함했다.

이번에 읽은 현재 Personal 공통·세 주제 본문/사례에는 이 계산 경계가 직접 구체화되어 있지 않다. 계약·이름의 일반 원칙으로 해석할 수는 있으나 독자가 해당 관점을 스스로 보충해야 한다. 오류·비동기·수명만으로 이전 탐색의 전체 폭을 대표했다고 말하지 않는다.

**추천:** 별도 날짜 체계부터 만들지 말고 계약·수명의 입력 의미에 단위·변환 경계·포함 여부를 보완하고, 기존 날짜 사례를 짧게 연결하는 안을 먼저 본다. 이름·타입 쪽에서는 그 의미를 드러내는 방법을 참조한다. 종료일 정책은 여전히 미정이며 사용자가 기억하지 못한 과거 의도를 다시 묻거나 포함/제외 하나를 정답으로 고르지 않는다. 이는 Main의 보완 제안이고 현재 본문 반영은 없다.

### 책임 배치의 기준은 있으나 지금 설명·탐색으로 충분한지

원래 논의에는 페이지에 다른 역할이 얼마나 있는지, 초대가 주된 기능인지, 내부 계산과 조율을 나눌지, 합성형 Dialog 부품을 함께 둘지의 선택이 있었다. 현재 공통 본문과 형성 자료에 그 이유가 남고, 이름·완료의 초대 예제에도 외부 기능과 내부 분해가 있다. 따라서 책임 기준이 통째로 빠졌다고 볼 수 없다.

다만 [Personal 주제 입구](prototypes/development-workflow/noline-demo/context/personal/development/README.md)의 상세 경로는 공통화·계약·이름 중심이다. ‘한 번 쓰는 큰 기능을 어느 책임으로 나눌까’라는 질문에서 이름 주제 안의 기능 예제로 내려가는 구성이 충분한지는 살펴볼 가치가 있다. 링크가 있다는 사실과 실제로 충분히 이해하는 것은 다르며, 이번에는 새 독자 수행을 시험하지 않았다.

**추천:** 기존 초대 또는 주문 사례 중 하나에서 현재 배치, 의미 있는 대안, 다음 변경을 대입했을 때 함께 고칠 위치와 새 간접 호출을 비교한다. 부족이 드러나면 본문 설명과 진입을 함께 보완한다. 곧바로 ‘책임 분리’ 폴더를 만들거나 새로운 대형 리팩터링 예제를 제작하는 일을 선행 조건으로 삼지 않는다. 사례에서 기존 본문이 충분하면 유지해도 된다.

### 설계의 충분성과 실제 효과의 관찰을 연결할지

기존 사례는 이미 유지·수정·보류와 비용을 보여 준다. 추가로 품질 점수표나 파일/줄 수 기준을 만들 필요는 없다. 다만01-02를 마감할 때는 어떤 결과를 관찰해야 기준의 도움과 과잉을 가를지 종합해야 한다.

| 기존 사례를 이용한 관찰 질문 | 좋아진 것으로 볼 근거 | 부족하거나 비용이 늘어난 근거 |
| --- | --- | --- |
| 같은 구매 규칙을 바꿀 때 | 함께 바뀌는 규칙이 모이고 화면별 차이는 직접 표현됨 | 범용 옵션·우회·추적할 파일이 늘어 변경 부담을 옮김 |
| 인증 완료를 읽고 다음 행동할 때 | 이름·타입·흐름에서 인증 적용과 조회 요청을 구별함 | 긴 이름·중복 주석만 늘고 실제 완료 경계는 다시 조사해야 함 |
| 오류 계약을 적용할 때 | 호출자가 필요한 실패 의미를 보존하며 공통 변환을 믿을 수 있음 | 타입은 같지만 HTTP 상태·실패 단계가 사라지거나 새 오류 계층 부담만 늘어남 |
| 기준을 읽고 구조를 정할 때 | 현재 조건을 근거로 유지와 개선을 모두 선택함 | 예제 모양을 따라 불필요한 Hook·파일·타입을 생성함 |

이 표는 관찰안이다. 실제 Noline의 우선 작업·판본·담당·확인 범위는 병행 반영 결과와06·07에서 연결한다. 새 사용자 연구·일률적 A/B 시험이나 같은 인증 응답 재생성을01-02 완료 조건으로 추가하지 않는다.

## 지금 필수 논의로 늘리지 않을 것

- 특정 폼 연결 API, Toast timer 이전, 과거 날짜 정책, 문자열 isError의 일괄 수정: 적용 조건을 보여 주는 사례이며 이 Ticket이 모두 결정해야 할 제품 작업이 아니다.
- 최근 추가한 원인/계약 수정과 재시도·fallback의 구별, 모순된 상태 조합과 반복 방어의 비교: 현재 일반 본문에 반영돼 있다. 실제 선택이 불명확한 사례가 생기면 보완하되 각 항목마다 새 사례를 의무화하지 않는다.
- 전체 네이밍 사전·모든 언어의 스타일 규칙, 접근성·성능·보안 등 모든 품질 영역의 신규 장: 이번 대조에서 전부 조사하거나 빠짐없이 채우기로 선택하지 않았다. 관련 제품 요구와 새로운 근거가 있으면 범위를 판단한다.
- 새 reviewer 절차, 반복 시험, 전역 설치: 각각 완료된 수행 계약과06·07의 실제 배치·관찰 책임을 사용한다.

## 이번 수행과 한계

Main이 보존 기록과 현재 문서를 직접 대조했다. 새로운 외부 조사·독립 리뷰·모델 응답 시험·제품 테스트·실제 Noline 검증을 수행하지 않았다. 루트 CODE-QUALITY는 이 저장소의 분석 작업 규칙으로 읽었으며 사용자가 제외했던01-02의 설계 비교 기준으로 다시 편입하지 않았다.

이번에는 이 분석 기록과 현재 재진입 안내를 갱신한다. source·prototype·reference-project·Noline·전역 파일의 내용은 변경하지 않는다. 다음 논의에서 새 후보의 채택 여부를 구별하고, 다른 세션의 실제 반영 내용은 확인한 근거가 생긴 뒤 상태에 반영한다.
