# 사례 개선 리뷰와 대상물 경계 정정

2026-10-19. 98에서 복원한 본문에 대한 사용자 우려를 받아 개선 리뷰를 수행했다. 아래 평가는 합의 준수 확인이 아니라 문서의 구성과 사용 가능성을 높이기 위한 검토다. 대표 재작성은 제안이며 현재 prototype 본문에 적용하지 않았다.

## 사용자 요청과 리뷰 입력

사용자는 사례를 보고 다음과 같이 요청했다.

> 일단 케이스를 봤는데 이것만 봐도 짜치는게 뭐랄까 그냥 기존에 합의랑 기록을 고대로 붙인느낌이야 이 문서에 맞게 잘 구성해야하는데 지적사항만 표면적으로 하고 제대로 못만든 것 같아 개선 리뷰어 돌려봐 제3 검증자 말고 이걸 개선시키기 위해 내 지금 우려와 결과와 필요한것만 주고 평가하게 해 끌어올리려면 어떻게 해야하는지 잘 물어봐봐

리뷰 진행 중 대상물과 설계 Workspace의 경계, 티켓 범위 안의 완성도에 관해 추가로 정정했다.

> 추가로 current 나 어디에 적절한데 메모 해놔 context/workspaces/014-ai-development-workflow-design/records/prototypes/development-workflow 이게 대상물인건 아는것 같은데 보니까 자꾸 record랑 엮는데 이 record내 워크스페이스 잖아? 그건 엮으면 안되지 자꾸 이렇게 짜치게 하는 포인트가 잇어서 이거 방지하게 결국 가능한 범위 내에서 최대한 결과물 내는건데 대충 떄우는게 아닌것 같아 범위가 티켓 범위만큼 하는건 좋은데

이전 대화를 상속하지 않은 개선 리뷰어에게 두 요청, 이전의 ‘빠진 판단 반영·동일 코드 이름 비교’ 요청, 대상물의 목적과 읽을 파일을 전달했다. Main의 기존 평가 결론이나 방어 논리는 주지 않았다. 사례 세 편을 먼저 읽고 필요한 일반 본문·진입점·대상물 내부 인증 비교를 확인하도록 했다. 실제 사실 확인이 필요할 때에만 원자료를 읽게 했으며, 리뷰어는 주문 사례를 재작성하기 위해 바깥 원기록49·52를 추가 확인했다. 파일 수정·코드 실행은 맡기지 않았다.

## 평가와 Main의 판단

리뷰어의 핵심 평가는 **판단 재료는 있지만 합의 복원과 오해 방지가 글의 구성 원리가 됐다**는 것이다. ‘누가 말했고 어디까지 동의했는가’가 ‘이 상황에서 무엇을 어떻게 판단하는가’보다 먼저 보인다. Main도 이 진단에 동의한다. 앞선 검토가 결정 과장·누락과 비교의 공정성을 확인한 것은 유효하지만, 문서가 제 역할을 하는지 평가한 것으로 대신할 수 없다.

구체적으로 공통 경계 사례는 첫 문단부터 ‘관찰, 사용자 판단과 미선택 대안을 보존’한다고 자기 역할을 정의한다. 계약·수명 사례는 동작 비교에 앞서 ‘확인한 판단의 지위’를 표로 제시한다. 각 절의 사용자 인용, Main 해석, 미선택 설명과 바깥 원기록 링크는 작성 근거 관리의 순서를 따른다. 이것이 그대로 다음 개발 판단을 돕는 사례의 순서가 되지는 않는다.

이름 사례의 내부 함수·공개 API 대비에는 ‘내부를 읽어야 구별된다’와 ‘문서에서 이미 구별된다’는 조건이 먼저 주어져 결론이 가정에 상당 부분 들어 있다. 짧은 원칙 설명으로는 쓸 수 있지만 상세 사례의 중심으로는 약하다. 반면 같은 인증 코드의 A/B 비교는 두 안이 모두 성립하는 상태에서 이름을 바꿀 이득과 비용을 볼 수 있다. 이를 맨 끝에 링크로 붙이는 데 그쳐 기존 사례의 구성을 다시 편집하지 못했다.

살릴 내용도 있다. Toast의 수명 비교 표는 같은 호출에서 시작 시점·표시 컴포넌트 부재·재표시 결과의 차이를 보여 준다. 주문의 두 사례는 다른 흐름과 같은 흐름을 비교할 재료가 있다. 인증 A/B는 동작과 설명을 같게 유지하고 개명의 차이를 비교한다. 문제를 이유로 이 재료까지 버리거나 다시 인터뷰할 필요는 없다.

결정·유보 구별은 계속 필요하다. 다만 일반 기준은 적용 조건과 판단을, 사례는 관찰·가정·대안·차이를, 실제 Project·Work는 그 제품과 작업의 선택을 맡도록 구성한다. 작성 시점의 합의 이력을 각 사례의 중심에 놓는 방식은 바꾼다. 실제로 확인하지 않은 호환 비용·오사용 빈도 등을 만들어 사례를 더 그럴듯하게 보강하지 않는다.

## 대표 재작성 시안: 같은 코드에 조건을 바꾸어 대입하기

다음은 리뷰어가 제안한 주문 사례 재작성이다. 원래 분리된 주문49와 관련 개선52의 내용을 하나의 판단 흐름으로 구성했다. 아래부터 시안 본문이며, 설명용 가정과 미정인 적용 조건을 본문 안에 밝힌다.

### 같은 주문 API를 써도 함께 묶을 동작은 달라진다

주문 성공 뒤 장바구니를 비워도 되는지는 주문 API의 이름으로 결정할 수 없다. 사용자가 장바구니를 주문한 것인지, 장바구니와 무관하게 바로 구매한 것인지에 따라 달라진다. 반대로 여러 화면이 같은 장바구니 구매를 제공한다면, 요청과 장바구니 정리를 화면마다 반복할 이유도 줄어든다.

아래는 Markdown에 있던 주문 성공 처리 예제에 두 가지 사용 조건을 대입한 비교다. 사용처와 수정 요청은 설명을 위한 가정이다.

```ts
onSuccess: response => {
  queryClient.invalidateQueries({ queryKey: ['orders'] });
  queryClient.invalidateQueries({ queryKey: ['catalog'] });
  clearCart();
  navigate(`/order-complete?orderId=${response.orderId}`);
}
```

이 네 동작이 항상 함께 필요한 한 화면을 위한 코드라면, 현재처럼 성공 처리에 모아 두는 것도 자연스럽다. 공통 Hook이나 별도 파일이 없다는 사실만으로 고칠 부분이 생기는 것은 아니다.

#### 장바구니 구매와 바로 구매가 함께 사용한다면

같은 주문 API를 두 곳에서 사용한다고 가정하자. 장바구니 구매는 주문 뒤 장바구니를 비우고 완료 화면으로 이동한다. 바로 구매는 장바구니를 건드리지 않고 모달을 닫은 뒤 자기 화면에 완료를 표시한다.

| 성공 뒤 동작 | 장바구니 구매 | 바로 구매 | 공통으로 맡길 범위 |
| --- | --- | --- | --- |
| 주문 때문에 달라진 데이터의 캐시 무효화 | 필요 | 같은 데이터가 달라진다면 필요 | 두 흐름에서 같은 데이터가 바뀐다는 근거가 있는 범위 |
| 장바구니 정리 | 필요 | 하지 않음 | 장바구니 구매 흐름 |
| 완료 표시 | 완료 화면으로 이동 | 모달 닫기와 화면 내 표시 | 실제 차이가 있으므로 각 사용처가 선택 |

여기서 전체 성공 처리를 그대로 공통화하면 바로 구매도 장바구니를 비우게 된다. 반대로 모든 처리를 사용처에 복사하면 같은 요청 계약과 캐시 규칙까지 각 화면이 관리하게 된다.

따라서 먼저 같은 API의 요청과 응답 처리를 공유하고, 같은 데이터 변경에 대응하는 캐시 처리도 함께 맡길 수 있는지 확인한다. 장바구니 정리는 장바구니 구매 흐름에 남기고, 다른 완료 표시는 각 사용처가 고르게 한다.

이 구별에서 중요한 것은 동작이 UI 가까이에 있는지 여부가 아니다. `clearCart`는 화면에서 호출되지만 장바구니 구매의 규칙일 수 있다. 그런 구매가 여러 화면에 반복된다면 공통 구매 흐름이 맡을 수 있다. 반면 `navigate`도 모든 호출이 같은 완료 화면으로 가는 전용 흐름이라면 함께 묶을 수 있다. 동작의 이름만으로 소유 위치를 고정하지 않는다.

#### 세 화면이 모두 장바구니 전체를 주문한다면

이번에는 조건을 바꾸자. PC 주문 페이지, 모바일 주문 페이지, 빠른 주문 모달이 모두 현재 장바구니 전체를 주문한다. 요청·캐시 무효화·장바구니 정리가 세 곳에 복사되어 있고, 화면 이동과 모달 완료 처리만 다르다.

이때 ‘사용한 쿠폰이 목록에 남는다’는 문제를 고치게 됐다. 원인은 세 곳 모두 쿠폰 캐시 무효화를 빠뜨린 것으로 확인됐다고 가정한다. 긴급 장애는 아니며 기존 동작을 확인할 여유가 있다.

| 수정안 | 이번에 해결하는 것 | 이후에도 남는 부담 |
| --- | --- | --- |
| 세 곳에 쿠폰 무효화만 추가 | 현재 쿠폰 누락을 작은 변경으로 고친다. | 다음 구매 규칙 변경도 세 곳에 반영해야 한다. |
| 같은 구매 흐름을 묶으며 쿠폰 무효화 추가 | 현재 누락을 고치고, 함께 바뀌어야 할 구매 규칙의 수정 위치를 모은다. | 세 화면의 연결을 바꾸고 기존 성공·실패·로딩·완료 처리를 보존해야 한다. |

이 가정에서 권할 안은 두 번째다. 요청이 같아서가 아니라 장바구니 정리까지 같은 업무 흐름이며, 이번 누락도 그 공통 규칙의 변경이기 때문이다. 화면마다 다른 완료 처리는 그대로 남긴다.

공통화를 이번에 함께 할 이유는 ‘중복을 발견했다’보다 구체적이다. 이번 수정부터 여러 곳에 같은 규칙을 맞춰야 하며, 다음 변경에서도 같은 누락이 생길 수 있는 위치가 드러났다. 그 부담을 줄이는 이득을 세 화면의 연결 변경과 보존 확인 비용에 비교할 수 있다.

작은 실험 제품이고 이후 같은 구매 규칙을 바꿀 필요가 낮다면 첫 번째 안도 타당하다. 그 경우에도 쿠폰 누락은 고친다. 달라지는 것은 정확성을 확보할지 여부가 아니라, 공통 구조에 지금 투자할 만큼의 이득이 있는지다.

#### 공통으로 옮기면서 완료 시점까지 바꾸지는 않는다

원래 예제는 캐시 무효화가 끝나기를 기다리지 않고 장바구니 정리와 화면 이동을 호출한다. 이를 공통 함수로 옮기면서 무효화 완료를 기다리도록 바꾸면, 코드 위치뿐 아니라 다음 처리의 시점도 달라진다.

따라서 이 사례의 공통화 판단만으로 대기를 추가하지 않는다. 최신 조회 결과가 준비된 뒤 이동해야 하는 요구가 있다면, 완료 시점과 로딩 동작을 별도로 정한다. 기존 동작을 유지하려는 정리와 새로운 완료 약속을 섞지 않는다.

이 비교로 정할 수 있는 것은 두 조건에서의 공유 경계와 관련 개선의 범위다. 구체적인 Hook API와 파일 배치는 아직 정하지 않았다. 실제 적용에서는 주문이 `catalog`를 바꾸는지, 일부 상품만 주문하거나 주문 중 장바구니가 바뀌어도 같은 정리 규칙이 맞는지 확인해야 한다. 이 조건이 달라지면 ‘같은 장바구니 구매’라는 판단부터 다시 볼 수 있다.

## 나머지 본문의 개선 제안

아래는 같은 양식을 강제하는 작업 목록이 아니라 각 사례에서 살릴 판단 차이다.

| 대상 | 구성할 중심 | 덜어내거나 이동할 것 |
| --- | --- | --- |
| Field·Container | Container는 목록을 남긴 채 오류를 표시할 수 있는지로 묶음의 제약을 보여 준다. Field는 배치 변경과 입력 교체를 구별하고 값·이벤트·ref·오류의 실제 연결 계약을 보여 준다. | 설계 의도 발화의 반복 해설과 ‘항상 나누기/감싸기가 아니다’의 반복. |
| fetcher | 비동기 파싱 실패의 전달, 오류 오분류, HTTP 상태와 timeout을 하나의 정비 사례로 묶고 이번 수정·유지·확장 범위를 설명한다. | 앞의 계약 관찰과 뒤의 정비 판단에 중복된 사건 설명, 판단 수용 발화. |
| Toast | ‘알림의 3초는 언제부터인가’를 중심으로 표시 컴포넌트 부재와 재표시의 차이를 보여 준다. 현재 방식이 맞는 조건도 설명한다. | 첫머리의 승인 지위와 반복되는 미선택 설명. 동작 비교 표는 유지한다. |
| 이벤트 Hook | null 입력이 준비 전인지 선택적 부재인지에 따른 실제 분기를 먼저 보여 준다. 지원하는 UI의 정확성과 지원 범위 확장을 구별한다. | 잠정 회고의 긴 해설. 관찰하지 않은 의도를 확정하지 않는다. |
| 이름·완료 | 같은 인증 코드 A/B를 중심에 놓고 사례 안에도 판단할 만큼의 코드·조건을 둔다. 전체 비교는 대상물 자체 Work 기록에서 더 확인할 수 있다. 저장 사례는 이름으로 해결되지 않는 동작 문제의 대비로 둔다. | 답이 가정에 들어 있는 내부·공개 사례의 과한 비중과 끝에 붙인 보완 절. |
| `isError`·초대·`silent` | `isError`는 당시 중요도를 낮게 본 판단만 짧게 보존한다. 초대는 외부 사용 단위와 내부 책임을 보여 준다. `silent`는 처리 순서와 옵션의 범위를 한곳에서 설명한다. | 확인하지 않은 호환 비용·오사용 빈도의 창작, 여러 주제에서 같은 사례의 반복 설명. |
| 일반 본문·읽기 입구 | 현재 제공하는 판단 범위, 필요한 조건과 읽을 경로를 안내한다. | ‘이번 요청으로 복원’, 과거 작성 순서, 미통합 진행 상황과 바깥 설계 기록 의존. |

외부 링크만 제거하면 필요한 사실도 사라질 수 있다. 확보한 자료에서 실제 판단에 필요한 코드·관찰·조건은 대상물 안에 남겨 완결한다. 반대로 작성 과정을 대상물 안의 새 provenance 문서로 옮겨 독자에게 다시 읽히는 것도 경계 정정에 맞지 않는다. 대상물의 자체 Project·Work 기록과 바깥 014 설계 기록은 구별한다.

## 이번 반영과 다음 판단

사용자가 요청한 지속 기준은 [current/memory](../current/memory.md#대상물의-경계와-범위-안의-완성도)에 남겼다. current의 진행도 개선 리뷰 회수와 대표 재작성 검토를 가리키도록 갱신했다. prototype 본문·뷰어·실행 예제는 이번 리뷰 단계에서 바꾸지 않았다. 이 기록을 대상물의 읽기 경로에 넣지 않는다.

Main의 다음 개선 방향은 항목을 더 붙이는 방식에서 문서 역할에 맞춰 기존 재료를 다시 편집하는 방식으로 바꾸는 것이다. 사례와 관련 일반 본문·진입점의 설명을 함께 보되 티켓 밖 주제를 무조건 확장하지 않는다. 리뷰어의 모든 세부 배치안이나 대표 문장을 사용자 확정으로 취급하지 않는다.

완성도를 볼 질문은 ‘바깥 014의 논의 기록을 모르는 독자가 사례에서 관찰한 동작, 선택을 가르는 조건, 자신의 Project·Work에서 확인할 점을 이해할 수 있는가’다. 합의 누락·오인용 확인도 계속 필요하지만 그것만으로 충족되지는 않는다. 이 리뷰는 문서의 역할과 편집 품질을 평가했으며 원제품의 현재 동작이나 실행 효과를 검증하지 않았다.
