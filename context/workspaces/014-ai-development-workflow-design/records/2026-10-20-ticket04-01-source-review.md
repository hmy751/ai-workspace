# 04-01 병렬 논의 시작과 보존 사례 확인

2026-10-20. **04-01의 논의는 기존 source의 평가·회고·후속 비교와 개발 대화 원문에서 시작할 수 있다.** 이번에는 자료와 이미 얻은 판단을 확인했다. 스킬 보완안의 비교·채택·구현이나 효과 검증을 마친 것은 아니다.

## 이번 요청과 작업 관계

사용자는 기존 후속이 03 이후의 04-03·워크플로 구체화였음을 짚고 다음과 같이 요청했다.

> 우리는 병렬로 04-01에 대해서 생각하자
>
> 아니다 context/workspaces/014-ai-development-workflow-design/source 여기에 이미 논의한게 잇을것같아 한 번 여기 확인해봐

01-01·04-03의 기존 후속 관계는 유지한다. 이 대화는 04-01의 근거 확인과 논의를 병렬로 맡으며, 다른 작업의 정책 보완·운영 설치를 대신 진행하지 않는다.

## 자료의 역할

[source 안내](../source/README.md)에 보존 범위와 판본 구별이 있다. `noline-evaluation/corpus/`는 당시 개발 발화, `reviews/interview-20261012.md`는 이후 사용자 회고, 후속 비교 문서는 당시 문서·도구 사건·코드를 대조한 평가다. `discussion/`에는 이 평가에서 전체 작업 체계 설계로 넘어간 대화가 있다. 개발 원문의 `source_line`은 JSONL의 물리적 줄 번호와 다르다.

[설계 논의 원문](../source/discussion/design-conversation.md#L2320)에서는 이미 기존 스킬과 실제 수행을 함께 검토할 필요를 논의했다. 그러나 당시 AI가 제안한 Main 중심 기록·조건부 reviewer·고정 흐름 전체를 현재 채택안으로 가져오지 않는다. [후속 범위 정정](../source/discussion/design-conversation.md#L2659)은 좁혀진 제안이 결론으로 남아 후속 논의를 닫는 일을 우려했다. 현재 선택은 Spec과 각 Ticket에서 확인한다.

## 04-01에 사용할 장면과 이미 확인한 것

### 제품 동작을 정한 work-discussion과 구현 결과를 다시 본 reconsider-work

DB·인증 초기화 장면에서 사용자는 `$work-discussion`을 직접 호출하고 “더 구체화할건없으면 시작하자”라고 했다. AI는 DB 준비 실패와 인증 정보 읽기 실패에 모두 안내·재시도를 권했지만, 설명과 질문 뒤 실제 선택은 갈렸다. DB 실패에는 재시도를 추가하고, 인증 정보 없음·복원 실패는 기존 로그인 화면 이동을 유지하기로 했다. 사용자는 시나리오 테스트부터 작성하도록 지시했다.

- [개발 원문](../source/noline-evaluation/corpus/01a0b2ee-2d11-7b33-ba80-2ceeb380a0ae/messages.jsonl): `source_line` 109·154·157·178·190·197·202·216·221.
- [인터뷰](../source/noline-evaluation/reviews/interview-20261012.md): 사용자는 중요한 선택과 이해 보충이었으며 나쁜 과정은 아니었다고 평가했다.

이는 질문을 줄이는 것만을 목표로 삼으면 놓치는 비교 사례다. AI 추천의 일괄 채택이나 기존 동작의 일괄 유지가 아니었다. 여기서 확인한 대화만으로 구현 완료·장기 효과·시간 절감을 주장하지 않는다.

같은 세션에서 구현 보고 뒤 사용자는 “지금 preparation 과 auth init 도 있고 뭔가 따로 구현된느낌이야 한번 봐봐”, 이어 “우리 spec의 목표도 생각해봐”라고 요청했다. AI는 reconsider-work 적용을 선언한 뒤 다음과 같이 반환했다.

> Spec 기준으로 보면, 이번 변경은 실패 동작을 구현했지만 준비 흐름을 이해하기 쉽게 정리하는 데는 부족했습니다.

AI는 완료 상태의 중복, 간접적인 재시도, 이름과 책임의 불명확함을 들고 합의한 실패 처리·시나리오 테스트는 유지하면서 상태·호출·책임 관계를 정리하자고 했다. 검토 응답에서는 추가 수정하지 않았으며 사용자의 개선 지시 뒤 후속 구현·검사 통과를 보고했다. 그러나 사용자는 다시 확장성·응집도·모듈과 앱 초기화의 의미를 고려하라고 정정했다.

- 같은 [개발 원문](../source/noline-evaluation/corpus/01a0b2ee-2d11-7b33-ba80-2ceeb380a0ae/messages.jsonl): `source_line` 411·427·432·443·450·574·583. Main은 411·427·432·443·450·583의 직접 발화·반환을 대조했다.
- [설치·사용 조사](../source/noline-evaluation/reviews/noline-context-usage.md)는 두 스킬의 적용 선언과 당시 본문 열람을 별도로 확인한 평가다.

두 스킬의 실제 연결을 비교할 수 있지만, 호출 뒤에도 추가 정정이 있었으므로 재판단이 충분히 해결됐다고 볼 수 없다. 이번에는 당시 코드나 검사 보고의 진위를 재검증하지 않았다. 제품 동작의 선택과 Spec의 구조·가독성 목표를 구현 결과에 다시 적용하는 일이 어떻게 이어졌는지 보는 사례로 사용한다.

### 질문을 변경 지시로 받은 access 장면

일정 목록 한 곳에 먼저 적용하는 중 사용자가 “근데 access 는 어디간거야?”라고 물었다. AI는 내부로 옮긴 이유를 충분히 판단하기 전에 복원을 약속했고, 사용자는 “아니 무조건 하란게 아니라 판단하라고”라고 정정했다. 이후 AI는 현재 일정 목록만 볼 때의 충분성, 폼·직접 데이터 소비자의 필요, 화면마다 규칙이 흩어질 비용을 비교하고 제한된 적용을 권했다.

- [개발 원문](../source/noline-evaluation/corpus/01a0ec21-e59e-7370-8432-8434271aa669/messages.jsonl): `source_line` 2740·2745·2757·2762·2769·2774·2781·2784.
- [평가 대화](../source/discussion/conversation.md#L1932): 사용자는 마지막 설명의 도움과 질문을 곧바로 변경으로 받아들인 문제를 함께 말했다.

최종 기술 선택이 같더라도 질문에 맞춰 즉시 복원하는 것과 소비처·비용을 판단한 권고는 다르다. 이 구간에는 reconsider-work의 명시적 호출이 보이지 않으므로 해당 스킬의 실행 실패로 확정하지 않는다. 04-02와 설명·재판단 경계를 함께 비교할 자료다.

### 기록을 읽었지만 중심을 잘못 잡은 재개

다음 세션은 구조·배경 검토와 잠정 상태가 담긴 기록을 읽고도 발견된 두 버그의 기대 동작부터 정하자고 했다. 사용자는 “지금 구조랑 배경을 더 파악해봐 마지막 문제 2가지는 아직 그렇게 중요한건 아니고”라고 정정했다.

- [재개 원문](../source/noline-evaluation/corpus/01a0f772-73ab-7823-b282-bddb19124b7e/messages.jsonl): `source_line` 69·76을 직접 확인했다.
- [기록 시점·재개 후속 비교](../source/reading/noline-evaluation/reviews/record-timing-followup.md): 핵심 원문 보존과 실제 열람, record·Ticket·state의 다른 강조, 이미 진행된 후속 작업을 반영한 보완, 성공 재개를 대조한다.

단순 기록 누락·열람 누락으로 설명할 수 없다. 배경과 선택 이유가 현재 행동에 어떻게 이어지는지 볼 근거이며, 늦은 기록 시점이 원인이었다거나 특정 스킬이 실패했다고 확정된 사례는 아니다. 과거 기록 보완도 이미 진행된 최신 작업과 맞춰야 했다.

### 동작 개선을 승인한 뒤 철회하고 일부를 다시 채택한 작업

가독성 Spec 아래에서 동작 개선의 채택·제외를 설명받은 뒤 사용자는 진행을 승인했다. 결과 설명 후에는 범위가 계속 커질 것을 우려해 되돌리도록 했다. 이후 Ticket 06은 폼 보존·대상 여행 라우팅·sync 보호를 채택했고, 복구 공개 조건은 수정했으며 알림은 제외했다.

- [개발 원문](../source/noline-evaluation/corpus/01a0ad3d-d8d0-7f33-a3fa-c9eaf01d3f30/messages.jsonl): `source_line` 351의 진행 승인과 970의 철회 발화를 직접 확인했다.
- [평가 대화](../source/discussion/conversation.md#L1891), [철회·후속 구현 비교](../source/reading/noline-evaluation/reviews/withdrawal-followup-comparison.md): 동작 개선을 알고 수용했다는 회고와 후속 채택·수정·제외를 구별한다.

가독성이라는 이름만으로 동작 개선을 무단 확대라고 판정하지 않는다. 이후 유사 기능의 채택도 당시 구현의 적절성을 증명하지 않는다. 철회의 단일 원인은 미확정이며, 이후 판단에서 무엇을 유지·수정·제외했고 왜 그랬는지를 비교할 자료다. 이번 확인에서 당시 코드를 다시 분석하거나 제품 실행을 재현하지 않았다.

## 이후 논의에 이어갈 것

보존된 work-discussion·reconsider-work 본문에는 이미 목표·선택·Spec/Ticket 연결과 변경 영향에 관한 요구가 있다. 실제 장면과 대조해 기존 기준의 수행 부족, 구체성 부족, 자료 선택·기록·책임 연결 문제를 구별해야 한다. 사례에 스킬 이름이 붙어 있다는 것, 실제 호출했다는 것, 해당 스킬 때문에 결과가 좋아졌다는 것은 각각 다른 주장이다.

우선 같은 DB·인증 작업에서 두 스킬이 이어진 장면으로 작업 정의·실제 결과·재판단의 관계를 비교할 수 있다. access 장면은 질문의 뜻과 변경 판단을, 재개와 철회 사례는 판단의 후속 반영을 살필 자료다. 이 순서는 이번 조사에서 얻은 논의 출발 후보이며 최종 설계나 고정 절차가 아니다. 현재 스킬의 Maintain 인계 계약은 06과, 설명·재판단의 경계는 04-02와 맞출 필요가 있다.

source 사본은 변경하지 않았다. 실제 Noline 저장소·외부 자료를 새로 조사하지 않았으며, 보존된 스킬 기준판을 모든 개발 장면 당시와 동일한 판본이라고 가정하지 않았다.
