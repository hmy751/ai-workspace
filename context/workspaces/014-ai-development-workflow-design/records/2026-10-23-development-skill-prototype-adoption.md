# Development 스킬·검토 상세와 진입점 이전 적용

사용자가 Personal 범위를 보완하고 Astra high 개선 리뷰를 요청한 뒤, Main이 종합한 네 보완에 “좋아 적용해줘”라고 요청했다. **[development SKILL.md](prototypes/development-workflow/skills/development/SKILL.md)와 [검토 상세](prototypes/development-workflow/skills/development/references/review.md)를 작성하고 기존 DEVELOPMENT의 현재 진입·본문을 이전했다.** 전체 workflow의 실행 세부를 모두 확정하거나 운영 환경에 설치한 작업은 아니다.

## 사용자 정정·리뷰와 적용 범위

직전 [구성 제안](2026-10-23-development-skill-structure-proposal.md)은 한 SKILL.md와 구현·검토·검증의 상세, 형성 자료를 제안했다. 사용자는 다음을 보완했다.

> 기준 personal 이나 context 층도 고려한거 근데 너말 보니까 좋은 코드기준이라고만 말해서 꼭 코드만은 아니라고 난 생각해서 그건 말해주고 싶었고

사용자의 요청에 따라 새 Astra high 개선 리뷰어에게 이 원문과 앞선 스킬·이전 구상, 현재 제안과 실제 prototype·합의·원자료 접근점을 제공했다. 읽기 전용으로 진행했고 Main의 구성안도 재판단하도록 했다. 반환의 핵심은 한 스킬로 실행을 묶는 방향을 유지하며 다음을 보완하자는 것이었다.

| 리뷰 보완과 Main의 채택 | 실제 반영 |
| --- | --- |
| Personal 전체와 지금 사용하는 개발 판단을 구별한다 | Personal 상위 README를 개인의 판단 기준·이유·조건으로 설명하고 현재 내용이 개발 중심이라는 사실을 유지했다. 새 분야나 A·B 상세 원칙을 추가한 것은 아니다. |
| SKILL.md가 Main의 전체 결과 책임을 설명한다 | 요청 파악·초기 맥락 선택뿐 아니라 작업 중 재탐색·역할 연결·종합·확인·사용자 전달·Owner별 갱신을 공통 본문에 구성했다. 고정 순서나 모든 역할 호출로 만들지 않았다. |
| 같은 상세 파일 안에서도 독자를 구별한다 | review.md에 공유 목적·범위, 검토자 수행·근거·강도·반환, Main의 선택·사용자 연결을 구별했다. |
| 일반 수행 계약과 특정 demo 적용을 나눈다 | 공통 절차는 스킬로 옮기고 로그인 계약·선택·코드·검사 결과는 기존 Project·Work·walkthrough에 남겼다. |

리뷰어는 현재 제안의 소유 표현이 이미 대화의 ‘좋은 코드 기준’보다 넓다고 보았다. 따라서 정정을 전면 구조 오류나 Personal의 새 분야 전체 작성으로 확대하지 않았다. Main은 네 보완을 모두 추천했고 사용자가 적용을 요청했다. 정확한 사용자 발췌·외부 판본·리뷰의 지위는 스킬의 [형성 근거](prototypes/development-workflow/skills/development/_background/evidence.md)에도 필요한 만큼 보존했다.

## 작성·이전한 실물

- SKILL.md는 사용 목적·범위와 Main의 공통 수행 계약을 소유한다. 기존 work-discussion·브리핑의 본문을 복제하지 않고 필요한 조건에서 연결한다.
- review.md는 확정1~5번의 독립 재판단·목표와 방법 구별·역할·강도·근거·Main 판단을 실제 지침으로 구성했다. 발견/변경 강제, 단순 기준 준수, 모든 개선의 선행 효과 검증, 모든 사용자 논의의 승인 관문화는 넣지 않았다.
- `_background`에는 맥락·최소 원문·외부 참고·독립 리뷰·전환 기록을 구별했다. 바깥014를 읽어야만 현재 수행 방법을 알 수 있게 하지 않았다.
- 구현·검증의 공통 책임은 SKILL.md에 두고 상세 파일은 아직 만들지 않았다. 남은 설계를 빈 파일로 채우지 않는다.
- 이전 DEVELOPMENT는 원문 그대로 [텍스트 보존판](prototypes/development-workflow/skills/development/_background/evidence/development-before-skill.txt)을 남기고 현재 위치에서 제거했다. 원문 SHA-256 `1a3138d4eff356d801e46da0040649d06b3460be8241e14971b2f252c4c6254f`를 대조했다. 이 판본이 모든 과거 날짜의 정확한 본문이었다는 주장은 하지 않는다.

현재 문서에서 절차를 찾는 연결은 새 스킬로, 이전 본문의 내용을 근거로 드는 날짜별 분석·기록은 보존판으로 연결했다. 링크 이전은29개 문서에서 수행했으며 과거 분석의 결론은 다시 쓰지 않았다. 원문 source와 작성 당시 snapshot의 경로 문자열은 그대로 보존한다. Source 안의 옛 링크를 현재 호출 경로로 사용하지 않는다.

demo와 Work의 AGENTS·README, context 진입과 SYSTEM-GUIDANCE, Personal 상위 설명, skills 색인·prototype README·walkthrough·viewer의 workflow 경로를 맞췄다. Work의 Spec/Ticket/current/source/output/records 구조 자체는 바꾸지 않았다. Workspace 재진입·산출물·01-01·04-03에는 적용 상태와 남은 범위를 반영했다.

## 확인한 것과 남은 한계

### 내용과 보존 대조

Main이 본문을 다음 요청에 대입해 책임을 확인했다. 실제 새 agent의 수행 시험은 아니다.

| 요청·상황 | 본문에서 확인한 행동 |
| --- | --- |
| 기존 결과의 검토만 요청함 | 요청 범위에서 시작하며 자동 수정으로 확장하지 않는다. 검토자는 공유 기준을 사용해 재판단하고 Main이 의견을 선택에 연결한다. |
| 표현을 살피다 실제 완료 계약이 쟁점이 됨 | 질문에 필요한 제품 계약·실제 호출 흐름으로 맥락을 다시 선택한다. 모든 context 재독이나 임의 목표 변경으로 확대하지 않는다. |
| 의미 있는 차이가 없는 대안 또는 결함 없는 개선 | 변경을 강제하지 않는다. 차이가 작으면 현재안을 유지하고, 결함이 없어도 근거 있는 개선은 비교한다. |
| Main이 결정할 수 있지만 사용자 이해에 중요한 대안 | 의미 있는 논의는 열어 두되 모든 변경의 사전 승인으로 만들지 않는다. |
| 검토 의견을 채택함 | 실제 수정·필요 확인을 연결하며 의견 채택·검증 완료·지속 기준 변경을 구별한다. |

이 적용을 마쳤을 당시 기존 skills·로그인 예제의 변경 전 hash와 대조해 기존 스킬 본문·배경과 예제 코드는 그대로임을 확인했다. 이 범위에서 바뀐 기존 파일은 새로운 스킬 진입을 추가한 skills/README뿐이다. 04-02의 진행 중 본문·실험·Ticket·source 변경은 이번 작업으로 수정하지 않았다.

### 정적 확인

- 스킬 기본 검사기는 Python의 PyYAML 미설치로 실행되지 않았다. 의존성을 새로 설치하지 않고 Ruby의 YAML safe_load와 별도 검사로 frontmatter 파싱, 허용 필드·name·description 제한·미완성 placeholder 부재를 확인했다. 기본 검사기 통과라고 표시하지 않는다.
- 열람 화면을 재생성했다. 문서·코드 항목149개이며 그중 예제 코드가5개다.
- 원래 viewer 검사는 변경 전 이미 표시 사본이 최신 파일 목록과 달라 실패했다. HEAD의 prototype을 임시 경로에서 재생성해 검사하자, 04-02 관련 바깥 로컬 문서 링크5개가 경계 위반으로 동일하게 실패했다.
- 변경 뒤 검사에서도 같은5개만 발견됐다. 임시 사본에서 이5개 목록과 정확히 일치함을 요구하도록 해당 assertion만 바꾼 진단 실행은 나머지 원문·SHA·경로·앵커·클라이언트 문법 검사를 통과했다. 정본 checker를 수정하거나 전체 검사를 통과했다고 처리하지 않았다. 진단기의 기존 ‘모든 로컬 링크가 안에 있음’ 출력 문구는 예외5개 때문에 전체 상태의 설명으로 사용하지 않는다.
- 새 스킬·참조 이전이 추가한 경로·앵커 문제는 발견하지 못했다. 마지막 재생성에서도 기존5개 실패만 동일했고, 변경 문서·새 본문의 로컬 파일 링크1067개는 대상이 모두 존재했다. Git whitespace 검사도 통과했다. 실제 브라우저 렌더링·에이전트 동작·운영 자동 호출 효과는 시험하지 않았다.

기존 경계 위반은 `skills/README.md`의 반영 기록·시험 입력 링크2개, `skills/_background/skills-content-policy/evidence.md`의 시험 입력 링크1개, `skills/work-artifact-briefing/_background/records/2026-10-22-code-depth-adoption.md`의 반영 기록·비교 링크2개다. 다른 세션이 담당하는04-02의 해당 내용을 이번 적용을 위해 변경하지 않았다.

## 다음 작업

원래15항목의1~5번은 설계 합의를 현재 공통·검토 본문에 적용했다. 다음은6번 구현자의 검토 전 완성 책임·인계이며, 이를 바탕으로7~12번 초기 자료·동적 맥락·권한·반환·호출·수정·재검토·종료를 구체화한다.13~15번 모델·실행 배치·기존 스킬·기록 연결도 계속 남아 있다. A·B의 정확한 Personal 본문 통합은01-02, 검증 설계는01-03의 후속이다.

다음 세션은 현재 SKILL.md·review.md를 먼저 읽고, 결정 이유가 필요하면 이 기록과 스킬의 `_background`를 선택한다. 원래15항목의 정의는 [공유 기준·독립 판단 결정](2026-10-22-shared-criteria-and-independent-review-decision.md)에 있다. 다음 논의는 다음 경계를 유지한다.

- 1~5번은 합의·prototype 반영을 마쳤다. 관련 기준을 공유하면서 독립 판단하고 Main이 종합한다는 방향을 기본으로 잇는다. 검토자는 구현 단계의 역할이며 이후 검증자와 구별한다.
- 6번의 첫 질문은 구현자가 검토 요청 전에 무엇을 완성·확인하고, 결과·선택 이유·확인 범위·미해결점을 어떻게 Main에 넘길지다. 질문의 구성 자체가 필수 보고 서식이나 새 완료 조건의 확정은 아니다.
- 7~12번에서 검토자 초기 입력, 질문에 따른 맥락 재선택, 권한·반환, 호출 시점·범위, 수정·재검토·종료와 검증 인계를 정한다. 검토자의 직접 수정 허용 여부를 현재 본문에서 추정하지 않는다.
- 13~15번은 모델·인원·이력 전달, 기존 스킬 연결, 기록·정본 갱신이다. 일반 서브는 프론티어보다 한 단계 낮은 모델·medium을 선호한다는 사용자 방향과 이번 설계 개선 리뷰의 Astra high 선택을 구별한다. 구체적 실행 설정은 아직 정하지 않았다.
- Personal은 개발 코드에 한정되지 않는 판단 기준 Owner다. A·B는 반영 방향을 채택했지만 정확한 본문 통합은01-02에서 이어간다. 검토 workflow에 개발 원칙을 복제하거나 후보 상태로 되돌리지 않는다.

## 기록 정리와 커밋 범위

사용자가 다른 세션에서도 흐름을 이어갈 수 있게 current까지 기록하고 커밋하도록 요청했다. current/index·memory·state·spec, 관련 Ticket·output과 기록 색인을 현재 적용 상태에 맞췄다. 이번 커밋 대상은 development prototype·이전 연결·형성 근거·워크스페이스 기록이다. 다른 세션이 맡은04-02의 본문·실험·source·Ticket과 공유 문서의04-02 변경은 분리한다. 열람 화면도 이번 커밋에 포함하는 원문만으로 구성한다.

전역 설치·운영 설정은 하지 않았다. 기존 합의를 실제 본문으로 옮긴 것과 전체 Ticket 완료·효과 확인을 구별하며, 커밋 상태와 해시는 Git에서 확인한다.
