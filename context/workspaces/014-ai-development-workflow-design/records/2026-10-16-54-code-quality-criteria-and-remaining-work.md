# 01-02 기준 종합과 남은 작업

2026-10-16. 사용자가 fetcher의 유지·수정·보류 판단을 수용하고 지금까지의 기준과 01-02의 남은 일을 정리하도록 요청했다. 이 문서는 현재까지의 종합 체크포인트이고, 진행·상세 기준의 현재 Owner는 current의 01-02 Ticket이다. 글로벌 코드 규칙·스킬·제품 구현을 채택한 문서는 아니다.

## 현재 도달한 지점

사용자:

> 응 이 정도 판단이면 괜찮아 보여. 그럼 지금까지 나온 기준을 모아서 01-02에서 뭘 정리했고 뭐가 아직 남았는지 보자.

컴포넌트 중심 사례에서 요청·상태·업무 흐름·이벤트·날짜 예제로 탐색을 넓혔고, 수정 비용과 제품 범위까지 판단 조건을 확인했다. fetcher 오류 계약 정비를 가정한 유지·수정·보류 판단에 대해서도 사용자 수용을 얻었다. 사용자 취향 수집만 하던 상태에서 검토 기준을 한 사례에 적용해 대조한 상태로 진행했다.

확인한 것은 판단안의 적합성이다. 실제 코드 수정·테스트·회귀·개발 효과 검증은 하지 않았다. 기록 53의 판단 수용은 세부 오류 코드·전체 구현안의 승인이나 제품 수정 지시가 아니다. 01-02는 진행 중이다.

## 검토 판단으로 연결한 결과

fetcher에서는 호출 방식·정상 반환·현재 공통 구조·화면 정책 분리를 유지하고, 오류 계약 정비 목표에 직접 관련된 파싱·HTTP 상태 보존·타이머 정리는 수정 후보로 판단했다. 다수 오류 클래스·전체 스키마 도입·자동 토스트·인증 이동 등의 확대는 보류했다. 정상·실패 장면에서 무엇을 확인할지도 제시했다. 사용자는 이 정도 판단이 괜찮다고 수용했다.

따라서 '목적에 맞으면 유지'에 더해 '맡은 책임의 빈틈은 근거를 들어 고치고, 범위 확대는 보류한다'는 적용 예를 얻었다. 이를 모든 fetcher나 모든 작업의 필수 수정 목록으로 만들지는 않는다.

## 아직 남은 일

1. **작업자가 쓸 기준으로 구성하기.** 사례에서 얻은 질문·판단 근거·예외를 구현자와 검토자가 실제 작업에서 찾고 사용할 수 있는 안내로 정리해야 한다. 공통 기준, 프로젝트의 사실·제품 규칙, 사용자 선호·사례별 선택을 구별한다. 이번 종합은 재료를 모은 것이며 전달 위치·활성 규칙을 결정한 것은 아니다. Project 맥락·스킬의 배치는 03·04와 연결한다.
2. **검토·수정·재확인 방법 구체화하기.** 무엇을 근거로 지적하고, 무엇을 보존하며, 관련 수정 범위를 어디까지 잡고, 계약·제품 정책이 바뀌는 경우 어떻게 되돌려 판단할지 정한다. 관련 공통화의 조건은 얻었지만 reviewer 권한 전체와 종료 조건은 아직 완성되지 않았다. 01-01의 역할 흐름과 01-03의 실제 검증 책임에 연결한다.
3. **실제 적용 효과 확인하기.** 한 판단안에 대한 사용자 수용은 얻었지만 실제 변경 전후 효과는 미검증이다. 설계 단계에서 적용 대상·관찰할 결과·필요 검사와 비용을 정하고, 실제 실행은 해당 작업 범위에 맞게 수행해야 한다. 지금 원본 템플릿을 고치는 것을 완료 조건으로 새로 강제하지 않는다.

세부 네이밍·가독성 선호는 일부 사례만 확인했으며 보편 코드 스타일 표준은 없다. 필요하다면 같은 동작의 대비 코드로 보완한다. 날짜 종료일 정책처럼 기억나지 않는 과거 의도는 미확정으로 남겨도 현재 기준 정리를 막지 않는다. 모든 실패 UX 정책·과제물·회사 코드·설정 전체를 인터뷰할 의무도 없다.
