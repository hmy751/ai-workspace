# 04-02 — 네 해결 과제와 첫 전달 비교 논의의 현재 위치

2026-10-26. **해결 과제는 네 개다.** 첫 전달, 선택 판단, 앞선 말 보완·정정, 부족한 조사·구현·검증을 설명으로 덮지 않는 문제다. 특정 사례의 시험 단계 네 개와 혼동하지 않는다. 현재 실행판은 `b6195d4`의 explain이며 본체 정리·기존 인증 예시 분리를 반영했다. 이후 이번 논의에서는 실행 스킬을 수정하거나 새 응답 시험을 시작하지 않았다. Ticket04-02는 진행 중이다.

## 지금까지의 흐름과 정정

1. 반복 비교 뒤 실제 코드·전체 흐름·가독성을 보완했지만 수정판의 안정된 우세는 확인하지 못했다. 사용자는 이 정도에서 다른 사례와 남은 문제를 다시 보자고 했다. [남은 문제 재점검](2026-10-25-ticket04-02-remaining-problems-review.md)은 네 문제를 구별했다.
2. 사용자 요청으로 본체를 책임별로 정리했다. 긴 인증 예시는 새로 작성하는 것이 아니라 기존 전체·후속 예시를 함께 옮기는 뜻임을 확인한 뒤 분리했다. [반영·보존 확인](2026-10-25-ticket04-02-body-organization-adoption.md)과 커밋 `b6195d4`가 근거다.
3. 남은 것을 다시 설명할 때 Main은 첫 전달·선택 판단·앞선 말 복구 세 항목만 열거하고, 네 번째를 다른 담당의 책임으로 풀어 말해 목록에서 빠진 것처럼 만들었다. explain 혼자 수행하지 않는다는 사실은 해결 대상에서 제외할 이유가 아니다.
4. 사용자가04 첫 전달부터 비교 설계를 설명하라고 하자 Main은 입력·비교 조건·확인·결과 처리의 네 단계를 제안했다. 이를 ‘재개 지점’이라고 불러04-03의 컨텍스트 작업과 혼동을 만들었고, 사용자가 원래 네 해결 과제를 다시 묻는 발화에도 시험 단계로 답했다.
5. 사용자의 최종 정정 뒤 Main은 원래 네 문제를 다시 열거했다. 이번 요청은 그 맥락·흐름과 현재 상태를 Workspace에 기록하고 커밋하는 것이다. 시험 실행 승인이 아니다.

## 특정 사례에 종속되지 않는 네 해결 과제

| 해결할 문제 | 필요한 결과와 책임 | 현재 확인 수준·남은 공백 |
| --- | --- | --- |
| 첫 결과에서 작업의 의미가 빠짐 | 별도 재설명 요청을 기다리지 않고 원래 목표·실제 변경·해결/미해결·조건을 연결한다. 설명 방법은 explain, 작업 결과와 확인의 책임은 development/Main에 있다. | 첫 결과용 본문 비교는 있었으나 현재 development 연결 이후의 전달 수행은 미확인이다. |
| 선택 질문을 동작 설명·동의·변경 약속으로 대신함 | 사용자가 이미 이해한 점을 이어받고 요구·사용처·대안·이득과 부담을 대조해 판단한다. 질문을 자동 변경 지시로 바꾸지 않는다. | 테스트 변경 질문에서 판단을 한 관찰은 있다. 애매한 선택 질문과 책임 배치의 적절성은 별도 공백이다. |
| 앞선 말을 보완·정정하며 원뜻·사실을 왜곡함 | 실제 발화에 있던 설명을 인정하고 원뜻/현재 타당성, 유지/보완/철회와 달라지는 결론을 구별한다. 새 의도를 과거에 소급하지 않는다. | 기존 recovery 비교 자료는 있으나 현재 통합판의 직접 확인은 남는다. 현재 결함 근거 없이 상세부터 다시 고칠 이유는 없다. |
| 부족한 조사·구현·검증을 설명으로 덮음 | 확인 가능한 공백을 ‘미확인’이라고 적는 데 그치지 않고 기존 범위·권한 안에서 실제 확인으로 돌아가거나 담당자에게 연결한다. 설명의 명료함을 결과 충분성과 혼동하지 않는다. | 본문에는 explain과 개발·검증 책임의 연결이 있다. 실제 수행에서 필요한 확인을 이어가는지는 별도다. 고정 완료 자료로 답만 작성하는 비교로 이 수행을 검증했다고 할 수 없다. |

이 표는 문제 지도다. 각각에 시험 하나씩을 의무 배정하거나 네 문제를 한 사례로 검증하는 계획이 아니다. 자료·책임·공백에 맞춰 확인 방법을 선택한다. 사례별 우열을 만들기 위한 문구 추가·모델 변경·응답 재생성을 기본 다음 행동으로 삼지 않는다.

## 04-02와04-03, 시험 시작 시점의 구별

014는 컨텍스트·개발·설명·검증 등을 연결하는 전체 작업 체계다.04-02는 설명의 구성과 적용을,04-03은 실제 컨텍스트의 읽기·적용·갱신·재개와 개발 흐름의 연결을 맡는다. 필요한 사실을 찾아 설명하는 과정은 접하지만 같은 Ticket이 아니다.

Main이 사용한 ‘재개 지점’은 이번 시험에서 첫 보고를 작성할 순간부터 시작하자는 뜻이었다. 컨텍스트 복구 능력을 검증한다는 뜻이 아니다. 이후에는 **‘첫 보고 작성 직전의 시험 시작 상태’**라고 표현한다. source의 사례 번호04(저장 용량)와 Ticket04-02/04-03도 구별한다.

## 첫 전달 비교의 논의안 — 미실행

사용자는 첫 전달부터 보되 입력·조건·확인 대상을 먼저 설명하라고 요청했다. 다음은 그때 Main이 제시한 계획이며 입력 패키지·조건별 문단 diff·모델 실행은 아직 만들거나 수행하지 않았다.

**확인할 주장:** 현재 개발 흐름의 첫 결과 전달 지침이 실제 explain 사용과 필요한 설명으로 이어지는가. 기존 development `c43c592`에도 조건부 explain 연결이 있었다. ‘호출 없음/있음’ 비교가 아니라 조건부 안내와 첫 결과의 명시적 책임을 비교한다. 연결 문단에는 설명 요구도 포함되므로 순수 호출 시점만의 효과로 해석하지 않는다.

**공통 입력:** source04의 선행9~1542와1549~2456 원문123발화, 당시 Ticket·관련 Spec, 수정 전 hook·테스트, 최초 실제 diff·첫 보고 직전 hook·당시 검사 원출력과 필요한 첨부. 마지막 사용자 요청은 “그래 이제 코드 변경해봐”. 구현 결과는 고정하고 첫 사용자 보고를 작성한다. 원 첫 보고2560, 이후 테스트 질문2632·추가 개선2645, 과거 시험 답·평가 기준·형성 자료는 생성 입력에서 제외한다. 과거 지시는 현재 제품 수정·커밋 권한이 아니다. 전체 원자료 폴더를 주지 않고 선택 자료·접근 범위와 읽기 누락을 확인한다.

**두 조건:** development의 나머지 현재 내용과 현재 explain 본체·상세·예시를 동일하게 두고, 결과 전달 중 설명 연결 문단만 이전/현재로 바꾸는 비교다. 현재판은 `b6195d4`, 이전 문단 출처는 `c43c592`다. 시험용 조합임을 기록하고 과거 development 전체를 복원한 실행으로 부르지 않는다. 정확한 교체 범위는 실행 준비 때 diff로 고정한다. 공통 과제에서 explain·코드·부분 실패 설명을 별도 강제하지 않는다. GPT-6-sol high, 새 컨텍스트, 조건별 최초1회가 제안됐으며 이번 요청으로 실행 승인된 것은 아니다.

**관찰:** 실제 파일 읽기·상세 선택·자료 확인과 답의 충분성을 구별한다. 답에서는 표시 조립 통합이 줄인 수정 부담, 부분 결과와 실패 중단/계속 정책의 보존, 검사 범위와 미확인, 첫 보고에 맞는 코드·조건·분량을 대조한다. 미래 테스트 질문의 완성 답을 첫 보고에 의무 삽입하지 않는다. 읽기 로그는 이해·적용 자체의 증명이 아니다.

**반환과 종료:** 실행한다면 조건을 숨긴 최초 답 전문을 먼저 제시하고, 이후 조건·읽기 경로·충분한 대목·누락·다음 행동을 공개한다. 둘 다 충분하면 현재 연결의 추가 이득 미확인으로 남기고 이 장면을 마칠 수 있다. 읽기 차이만으로 품질 개선을 판정하지 않는다. 둘 다 부족하면 자료 접근·선택·실제 설명 중 근거가 있는 지점을 먼저 좁힌다. 자료 잘림·누락 등 기술적 무효 실행만 원인을 고쳐 해당 조건을 재실행하고 그 이력도 보존한다. 답의 취향 차이나 작은 우열 때문에 재생성하지 않는다.

이 비교는 첫 전달 문제의 제한된 확인이다. 더 좋은 구현, 실제 기기 동작, 컨텍스트 복구, 사용자의 이해 자체, 네 번째 문제의 추가 조사 수행을 입증하지 않는다. [과거 저장 용량 비교](experiments/artifact-explanation-storage-placement-fullread-2026-10-22/comparison.md)도 읽기 차이와 작은 응답 차이를 이미 관찰했다. 같은 결과가 나오면 추가 이득이 없다는 제한된 결론을 받아들인다.

## 원문 발췌와 발화의 역할

사용자의 시험 설계 요청:

> 좋아 그럼 04 첫 결과 전달부터 보자. 어떤 입력이랑 조건으로 비교하고 뭘 확인할 건지 먼저 구체적으로 얘기해봐. 또 비슷한 답만 뽑고 끝나지 않게

시험 시작 상태와 Ticket 범위에 대한 질문:

> 근데 왜 1번이 재개지점이라는거지? 내가 좀 헤깔려서 왜냐면 이번 티켓이 컨텍스트랑 뭐 이런거 아니였나?

문제 목록을 복원하라는 정정:

> 그것보다 다시 아까 남은 항목을 나열해봐 우리가 해결해야할 항목 정리한게 네개였잖앙? 특정 사례 기준말고 아니야?

Main이 정정한 핵심:

> 맞아. **해결할 문제는 네 개였어.** 내가 이후 시험 순서를 설명하면서 네 번째를 다른 담당의 책임으로 넘겨 말하고, 세 항목만 남은 것처럼 정리했어. 문제 목록과 시험 계획을 섞은 거야.

기록·커밋 요청:

> 일단 기록 할거 하고 커밋하자 다른 세션이 읽어도 매갈ㅇ이나 흐름 유지하게 워크스페이스 기록도 잘 정리하고

위 발췌는 현재 대화 원문이며 과거 source에 새 해석으로 삽입하지 않는다. 시험의 모델·조건·마감 기준은 Main 제안이고, 사용자 요구는 첫 전달 비교의 사전 설명·네 해결 과제 복원·기록과 커밋이다.
