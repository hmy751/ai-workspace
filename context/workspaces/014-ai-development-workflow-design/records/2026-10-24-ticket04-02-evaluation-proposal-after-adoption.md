# 04-02 — 수정한 설명 스킬의 사례·비교 방식 제안

2026-10-24. **논의용 제안이며 시험 조건 확정·입력 패키지 생성·응답 생성은 하지 않았다.** 현재 실행판은 `7c490d2`, 이번 수정 직전 explain은 `c43c592`에서 고정할 수 있다. 사용자는06을 반복하기보다 이번 변경을 확인할 source 사례와 비교 방식부터 구체적으로 논의하도록 요청했다.

> 그럼 이제 실제로 나아졌는지 어떻게 테스트하면 좋을까? 또 06만 반복하기보다 이번에 바꾼 부분을 확인할 수 있는 source 사례랑 비교 방식부터 구체적으로 얘기해봐

## 우선 권고

첫 묶음은 **03 network 전체 흐름 질문과04 저장 용량의 ‘코드를 바꿨는데 테스트는 그대로여도 되나’라는 후속 질문**으로 권한다. 각각 직전 explain과 현재 explain을 같은 조건으로 비교하고,03에만 설명 스킬을 주지 않는 기본 응답을 추가한다. 최초 응답은 총5개다. 모델은 직전 비교에서 사용한 GPT-6-sol high로 고정하는 것을 제안하며 이번 턴에 실행하지 않는다.

이번 수정의 효과를 보려면 주 대조군은 옛 두 스킬보다 **수정 직전 explain**이어야 한다. 옛 두 스킬까지 동시에 넣으면 통합·이전 보완·이번 변경이 다시 섞인다. 기본 응답은 ‘수정 전보다 나은가’와 별도로 ‘이 스킬을 더한 가치가 있는가’를 보는 기준이다. 모든 사례를3조건으로 늘리지 않고03에서 먼저 본다.

03·04도 과거에 분석하거나 일부 시험한 source다. 완전히 처음 보는 비공개 평가 사례로 부르지 않는다. 다만 이번 실행 상세에 그 답을 예시로 넣지 않았으므로, 새 예시를 그대로 재사용하는 것 밖에서 수행이 나타나는지 볼 수 있다. 인증02·여행05·동기화06과 보고서01은 실행 상세에 직접 설명 예시가 있어 성공해도 일반화의 증거로 바로 취하지 않는다.

## 사례별로 무엇을 확인하는가

### 03 — 전체 범위를 지키면서 실제 흐름과 방어 이유를 연결하는가

질문은 [원문1209](../source/artifact-explanation-scenes/03-network-flow/input/conversation.txt)의 “이 코드 설명좀 해줘 이해가 안돼 흐름이”다. [당시 자료](../source/artifact-explanation-scenes/03-network-flow/historical-materials/README.md)에307행 관측판과 소비자·검사 발췌가 있다. 다음 날 커밋이나06의 철회 전 코드를 대신 쓰지 않는다.

입력은 기존 선행 논의9~844와895~1209를 보존한다. 과거920의 스킬 호출과963의 답도 당시 맥락으로 유지하며, 과거 지시는 현재 조건의 호출 명령이 아님을 모든 조건에 동일하게 알린다.1239 이후의 답·사용자 반응은 제외한다.1218에서 읽은 코드 관측판은 그 전 관측판과 바이트가 같음이 확인돼 있지만 원 도구 묶음에는 옛 스킬 본문도 들어 있으므로 정제된 코드·소비자만 고른다.

평가는 전체 코드의 흐름을 이해하려는 요청에 맞춰 다음을 본다. 이 판정 자료는 응답 생성자에게 주지 않는다.

- 관측 시작·일반 listener·수동 refresh·cleanup의 주요 관계가 이어지는가. 특정 session 검사 한 부분만 잘 설명하고 전체를 대체하지 않는가.
- session·현재 요청·관측 version의 비교가 서로 어떤 늦은 결과를 막는지 실제 처리와 연결하는가. 용어 설명이나 호출 순서만 늘리는 것으로 끝나지 않는가.
- 재확인 대기 종료와 연결 성공을 혼동하거나, 소스에서 재구성한 흐름을 실제 기기 관찰로 말하지 않는가.

모든 분기·문법·상세를 전수 출력할 필요는 없다. 과거 실제 답에는 이미 상세한 설명이 있었으므로 원래 응답 전체가 실패였다고 전제하지 않는다.

### 04의 후속 질문 — 선택을 판단하고 설명하되 질문을 변경 명령으로 바꾸지 않는가

[원문2632](../source/artifact-explanation-scenes/04-storage-stats-delivery/evaluation/conversation.txt):

> 근데 회귀 테스트 하고 코드르 바꾸면 테스트도 바뀌어 있어야 하는거 아닌가?

이는 첫 결과 보고 뒤의 질문이다. source의 `evaluation/`에 있다고 영구히 평가 전용인 것은 아니다. 이번 재개 시점에는2632까지의 실제 연속 대화가 공통 입력이고,2638 답과2645 추가 개선 요청은 미래 자료로 제외한다. 새 조건의 생성 답에 과거 후속 질문을 무조건 붙이지 않고, 두 조건 모두 같은 실제 과거 답과 현재 질문에서 시작한다.

첫 변경의 전후 hook·실제 diff·변경 전 테스트·당시 Ticket·검사 출력을 사용한다. `createStorageStats`와 `finally`로 표시값 조립을 모은 변경과 기존 테스트가 확인하는 외부 결과·부분 실패 조건을 대조할 수 있다. 이후 추가 개선 커밋은 사용하지 않는다. 입력 고정 시2555 자료와2632 사이에 해당 코드·테스트가 바뀌지 않았는지 남은 원기록을 대조하고, 확인하지 못하면 ‘확인된 첫 변경에 대한 판단’으로 대상 범위를 명시한다.

평가에서는 일반적인 회귀 테스트 강의만 하는지, 실제 변경과 검사 내용을 근거로 지금 테스트를 바꿔야 하는지 판단하는지를 본다. 같은 테스트가 통과했다는 이유만으로 충분성을 단정하거나 무조건 테스트를 고치겠다고 하지 않아야 한다. 요구·외부 동작이 바뀌거나 검사 공백이 있다면 판단도 달라질 수 있음을 실제 근거 범위에서 다룬다. 당시2638의 답 자체를 정답으로 고정하지 않는다.

이 장면은 여행의 예시를 외우지 않고도 **뜻·선택 판단·권한의 구별**을 수행하는지 볼 수 있다. 이미 공유한 맥락을 잇는 기존 상세의 책임이 유지되는지도 함께 본다.

### 04의 첫 보고 — development의 연결 변경은 별도로 확인한다

본문 비교와 분리한 후속 후보다. 고정된 최초 변경·확인 자료로 **2560 직전 첫 결과**를 작성하게 한다. 사용자의 추가 설명 요청2567·2632, 이후 보완2645를 미리 주지 않는다.2456의 변경 요청과 필요한 선행 맥락, 보고 전 실제 코드·diff·검사 자료를 쓰되 보고문과 결과를 요약한 갱신 Ticket을 답의 재료로 대신 주지 않는다.

현재 explain을 두 조건에 똑같이 두고 development의 결과 전달 문단만 직전판/현재판으로 달리한다. 양쪽에 ‘explain을 읽으라’고 별도 지시하지 않는다. 과거 작업의 다음 사용자 응답을 구성하라는 공통 과제에서 호출·읽기·실제 설명을 각각 기록한다. 이는 **호출 연결·첫 전달의 효과** 비교이며 단순한 읽기 시점 하나의 차이라고 부르지 않는다.

현재판이 처음부터 ‘성공·실패 경로의 조립을 한곳으로 모은 것이 어떤 중복 수정 부담을 줄였는가’, ‘부분 실패 뒤 남기는 결과는 왜 같은가’를 실제 변경과 연결하는지 본다. 입력을 작게 고쳤으므로 설명도 불필요하게 큰 전체 브리핑으로 부풀지 않는지 함께 본다. 구현 결과를 고정했기 때문에 더 좋은 구현·전체 작업 실행·실제 추가 확인 수행을 검증한 것은 아니다. 양쪽이 모두 explain을 선택했다면 ‘이번 연결 때문에 새로 호출됐다’는 차이는 성립하지 않는다.

## 공통 비교 조건

- 직전 explain은 `c43c592`, 현재판은 `7c490d2`의 본체·실행 상세와 동일한 공통 근거 기준을 사용한다. 형성 자료·검토 기록·평가표·과거 시험 답은 생성 입력으로 주지 않는다. 새 상세 안의 예시를 시험 때만 제거해 다른 후보를 만들지도 않는다.
- 본문 비교에서는 두 판을 같은 시점에 명시 적용한다. 코드·대화·도구·모델·추론 수준·출력 한도·프로젝트 공통 지침을 같게 둔다. 별도 ‘코드를 넣어라/자세히 설명하라’는 보강 prompt는 추가하지 않는다.03의 기본 응답에는 설명 스킬 묶음을 주지 않으며 같은 프로젝트 공통 지침과 자료를 사용한다.
- 각 실행은 새 컨텍스트에서 시작하고 현재 설계 대화를 상속하지 않는다. 허용 자료만 별도 실행 공간에 구성하며 폴더 구분을 접근 차단이라고 부르지 않는다. 과거 호출·커밋·작업 지시는 역사 자료이고 현재 실행 권한이 아니다.
- 원문 입력과 선택된 파일의 누락·해시·잘림·입력 변경을 확인한다. 실제 읽은 파일·상세와 생성된 답을 구별하고 읽기 목록을 억지로 동일하게 만들지 않는다. 기술적으로 무효인 실행을 부진한 답으로 세거나 답이 마음에 들지 않는다는 이유로 재생성하지 않는다.
- 원문은 길이를 맞추려고 자르거나 고치지 않는다. 사용자에게 조건을 숨긴 순서로 최초 답 전문을 먼저 제시한다.03은 세 답,04 후속은 두 답이며 사례 사이 A/B/C의 의미를 고정하지 않는다. 조건표와 모든 최초 결과는 함께 보존한다.

## 판단과 다음 행동

먼저 사용자에게 어떤 설명이 실제로 읽히고 어떤 부분이 여전히 스스로 조립해야 하는지 판단할 기회를 준다. 그 뒤 조건을 공개하고 Main이 source에 비춰 핵심 주장·누락·부담을 실제 응답 문단으로 대조한다. 답변 길이·코드 블록 수·체크리스트 충족 개수를 이해 향상의 대리 지표로 삼지 않는다. 새로운 표현도 같은 관계를 충분히 설명하면 인정한다. 사용자의 재진술·quiz나 인위적인 후속 질문을 기본으로 요구하지 않는다.
