[기준 재료54](2026-10-16-54-code-quality-criteria-and-remaining-work.md), [외부 비교61](2026-10-17-61-reference-comparison-for-format-design.md), [적용 시안68](2026-10-18-68-principle-application-and-choice-basis.md), [잔여 범위69](2026-10-18-69-ticket-boundaries-and-next-design-step.md)를 함께 대입한 구성 제안이다. **기준 안내의 공통 부분과 네 가지 판단 주제, 조건별 사례를 구별하고 현재 제품 계약·작업 결과·상세 과정에 연결한다.** 이 구분은 내용의 역할이며 파일·폴더·skill 개수를 뜻하지 않는다.

## 사용자 요청과 이번 선택의 강도

> 좋아 나도 공감돼 지금 어쨋든 가능한 부분까지는 하고 다시 03 이나 후의 티켓에서 다시 종합적으로 또 보는게 낫겠어 거기서 또 구체화 하다보면 달라질테니까
>
> 그럼 전체 기준의 구성·분류안부터 만들어서 보여줘. 지금까지 논의한 기준들을 어디에 어떤 역할로 담을지, 왜 그렇게 나누는지, 아직 정하지 않고 이후 티켓에서 구체화할 건 뭔지도 같이 설명해줘.

가능한 부분을 지금 구체화하고 후속 Ticket에서 다시 종합해 바꿀 수 있다는 진행 방향에 사용자 동의가 있다. 아래 네 주제의 이름·묶음·세부 표현은 이번에 제안한 것이며 아직 사용자 채택이 아니다. 기존 prototype의 본문·파일 배치·단계 화면은 이번 구성안으로 교체하지 않았다. 01-02는 진행 중이다.

## 무엇을 어디에 담는가

| 내용의 역할 | 현재 제안하는 위치와 담을 내용 | 구별하는 이유 |
| --- | --- | --- |
| 기준 안내의 공통 부분 | 품질 기준의 첫머리. 제품 목적·현재 범위·기준 적용 방법과 관련 개선의 판단 관점을 짧게 둔다. | 어떤 주제를 읽어도 필요한 전제다. 각 주제마다 같은 주의문을 반복하지 않으며, 공통 부분만 읽고 상세 조건 없이 결정하게 하지 않는다. |

| 이번 작업의 판단·결과 | 해당 Work의 요구·진행·기록. 적용한 조건, 유지·수정·보류 이유, 확인 결과와 미충족을 둔다. | 같은 원칙으로도 작업마다 다른 선택이 가능하다. 실행 결과를 일반 원칙 본문에 계속 쌓거나 한 번의 결과를 새 규칙으로 자동 승격하지 않는다. |
| 상세 과정과 근거 | 원문·비교·정정·대안이 보존된 기록. 기준이나 배치 자체를 재판단할 때 필요한 경로를 연결한다. | 평소 작업에서 모두 읽을 필요는 없지만, 결과만 남기면 이후 담당자가 선택 이유를 복원하지 못한다. |

지금 시안에 대응하면 공통 부분·주제별 원칙은 `quality.md`, 사례는 `cases/shared-choice.md` 또는 원칙과 구별된 사례 절, 현재 제품 계약은 `http-client.md`, 이번 판단과 결과는 Work 기록이 맡는 관계다. 이는 시안을 이해하기 위한 대응이다. 실제 Project의 다른 정보와 합쳤을 때의 최종 위치·분할은03·04-03에서 정한다. 기존 품질 안내와 제품 문서가 충분하면 새 문서를 추가할 이유부터 판단한다.

## 기준 안내의 공통 부분

처음 사용할 본문에는 다음 의미를 짧게 담는 안을 제안한다.

> 현재 제품의 목적과 지원 범위, 이번 작업의 목표와 보존할 동작을 먼저 이해한다. 기존 구조가 어떤 편의를 제공하려고 존재했는지도 살핀다. 목적을 이해한 뒤 유지·변경·제거를 판단할 수 있다.
>
> 원칙은 현재 목적·사용처·비용에 대입한다. 사례와 코드 모양이 다르다는 사실만으로 고치지 않는다. 실제 계약 문제나 읽기·변경 부담과 기대하는 개선을 근거로 판단하며, 기준을 채택한 뒤에도 이 적용 방식은 같다.
>
> 이번 작업과 직접 관련된 구조 개선은 변경 범위·동작 보존·이득과 비용으로 판단한다. 작은 제품에서 구조 투자를 줄일 수 있어도 현재 약속한 동작의 정확성은 별도로 확인한다. 무엇을 유지·수정·보류했는지와 판단을 가른 이유, 확인한 범위와 미충족을 작업 결과에 남긴다.

기존 아홉 판단축 중 **목적·제품 범위**와 **관련 구조 개선**이 이 공통 부분의 중심이다. 공통 부분은 모든 주제에 관점을 제공한다. ‘항상 이 문서 전체를 읽고 질문마다 답하라’는 실행 절차나 새 승인 단계를 정한 것은 아니다.

## 상황에 따라 찾아볼 네 가지 일반 원칙 묶음

| 제안하는 묶음 | 담을 기준과 대표 질문 | 묶는 이유·필요한 구별 |
| --- | --- | --- |
| **책임을 어디에 둘 것인가** | 책임·응집도, 기존 도구가 맡은 상태·검증·요청, 사용처가 알아야 할 일. ‘누가 이 결정을 해야 하는가? 도구가 이미 맡은 일을 다시 소유하는가? 따로 바뀔 부분과 함께 이해할 부분은 무엇인가?’ | 코드와 라이브러리 사이의 실제 역할을 함께 봐야 경계를 정할 수 있다. 책임 단위·내부 함수 분해·파일 배치는 서로 다른 결정으로 남긴다. 새 도구 도입이나 래핑·래핑 금지를 기본 답으로 두지 않는다. |
| **무엇을 함께 제공하고 무엇을 사용처에 맡길 것인가** | 공통 편의·합성 자유, 같은 업무 흐름의 공통화, 공통 정책과 화면별 후속 선택. ‘함께 관리할 것이 실제로 같은가? 사용처가 바꿔야 할 것은 무엇인가? 공유층이 줄이는 부담이 추가 계약 비용보다 큰가?’ | UI와 업무 흐름 모두 함께 제공할 편의와 독립적인 선택의 경계를 판단한다. UI의 디자인 구성과 주문의 업무 규칙은 별도 소주제로 설명하며 같은 코드·API라는 이유로 합치지 않는다. |
| **어떤 동작을 약속하고 언제 끝나는가** | 입력·반환·오류의 형태와 의미, 시간의 시작·완료·정리, 단위·경계값·지원 범위. ‘사용처가 기대하는 의미가 실패·중단에서도 유지되는가? 언제 시작하고 끝나며 자원은 언제 정리되는가?’ | 호출 형태만 같아도 의미·시간·정리가 달라질 수 있다. 수명은 타이머를 둘 위치보다 먼저 정할 동작 계약이다. 책임 위치를 바꾸는 문제는 앞의 책임 묶음과 함께 읽는다. |
| **이름과 코드에서 의미를 읽을 수 있는가** | 이름·타입·제어 흐름이 전달하는 의미, 호출부가 추가로 알아야 하는 순서·예외, 선택적 명확성 개선과 필요한 수정의 차이. ‘이 이름과 타입이 실제 역할을 예상하게 하는가? 더 명확한 표현이 이번에 고칠 만큼의 차이를 만드는가?’ | 앞선 논의에서 가독성 관점이 뒤늦게 보완됐으므로 찾아볼 자리를 명확히 둔다. 읽기 부담은 다른 세 묶음에서도 함께 본다. 이 절을 명명 규칙·접두사·formatter 표준으로 확대하지 않는다. |

이 네 가지는 Main이 현재 재료를 묶은 제안이다. 한 문제를 하나의 분류에만 가둘 필요는 없다. 예를 들어 월 인자의 단위는 이름·타입으로 뜻이 드러나는지와 계산의 입력 계약이 맞는지를 함께 본다. 의미의 상세 설명은 한곳에서 소유하고 필요한 다른 주제에서는 연결하는 방식으로 중복 작성을 줄인다.

현재 두 대표 원칙을 비교하면 ‘공통 편의·사용처 선택’은 두 번째 묶음의 중심이고, ‘공통 계약의 신뢰’는 세 번째 묶음의 중심이다. 이미 그 안에 들어간 도구 책임·이름·수명 관련 설명을 새 문서에 복제하지 않는다. 실제 본문을 보완할 때 어디에 주된 설명을 두고 어디에서 참조할지 대조한다. 모든 세부 본문을 이번에 완성한 것은 아니다.

| 일반 원칙 | 함께 제공할 형식·동작과 사용처마다 바뀔 선택을 구별하고, 줄어드는 관리 부담과 공유층의 계약 비용을 함께 판단한다. |
| 판단 질문 | 같은 도구를 호출한다는 것 외에 함께 관리할 이유가 있는가? 사용처의 차이를 공통 옵션·분기로 다시 넣게 되는가? 유지했을 때와 바꿨을 때의 부담은 무엇인가? |
| 조건별 실제 사례 | Field는 디자인 구성을 바꿀 자유 때문에 의도적으로 나눴다. Container는 당시 필요한 공통 표시 형식을 제공했다. 당시 코드와 사용자 설명을 근거로 두 선택의 조건을 대비한다. |
| 가상 적용 사례 | FIELD-01에서는 짧은 조회 반복과 별도 관리 이득 부족이라는 가정 아래 공유층을 제거하고 기존 연결을 유지했다. 반복 감소 목표 미충족도 반환했다. 실제 사용 효과나 사용자의 새 보편 선호는 아니다. |
| 현재 제품 계약 | 실제 대상 Project에서 현재 제공하는 부품·입력·표시 정책을 확인한다. 과거 Field·Container 사례나 FIELD-01 가정으로 현재 계약을 대신하지 않는다. |
| 이번 작업 결과 | 현재 사용처에서 관찰한 조건, 선택한 대안과 비용, 보존한 동작·실제 확인·미충족을 남긴다. 원칙·사례 본문에 같은 작업 결과를 중복 작성하지 않는다. |

사례의 핵심은 조건과 선택 이유를 복원하는 것이다. 원문 전체가 필요하면 연결된 과정 기록으로 내려간다. 모든 사례에 동일한 필드나 긴 전사를 요구하지 않되, 사용자 정정처럼 해석을 바꾸는 핵심 문구는 링크만 남기지 않고 필요한 만큼 보존한다.

**내용의 종류와 지위는 별도다.** 일반 원칙이어도 사용자 사례에서 도출한 후보일 수 있고, 구체 사례의 당시 의도는 직접 확인됐어도 현재 제품의 규칙은 아닐 수 있다. 날짜 정책처럼 미정인 내용은 해당 사례·제품 판단에 붙여 두며, ‘미정’이라는 별도 품질 주제로 분류하지 않는다. 지위의 종류·기계용 필드·갱신 절차를 새 체계로 확정한 것도 아니다.

## 같은 내용을 어떻게 찾아오는가

분류는 기준의 뜻을 소유하는 방식이고 읽기 안내는 작업에서 그 기준에 도달하는 방식이다. ‘책임’이라는 같은 본문을 Hook 변경·공통 컴포넌트·HTTP 경계에서 참조할 수 있다. 주제마다 다른 문서에 복제할 필요는 없다.

| 작업의 단서 | 주로 찾아갈 판단과 함께 확인할 것 |
| --- | --- |
| 기능을 Hook·모듈로 나누거나 라이브러리 연결을 옮김 | 책임 배치와 도구 책임. 함께 제공하는 범위가 바뀌면 공통화도 본다. |
| Field·목록·주문 로직의 반복을 줄임 | 공통 편의·사용처 선택. UI 구성과 업무 흐름의 조건별 사례를 고른다. |
| 오류·타이머·이벤트·날짜 입력을 바꿈 | 동작 계약·수명과 현재 기능 계약. 이름·타입이 그 의미를 숨기면 표현의 명확성도 본다. |
| 이름·타입·호출 흐름을 정리함 | 표현의 명확성. 실제 값·정책이 달라지는 부분은 동작 계약으로 돌아간다. |

이 표는 읽는 조건의 예이며 새 라우팅 파일을 만들거나 전체 기준을 매번 로드하는 명령이 아니다. 구현자와 검토자는 관련 의미의 원본을 함께 사용하되, 각각 언제 얼마나 읽는지는01-01·03·04에서 현행 스킬과 실제 작업 흐름에 대입한다.

## 왜 이 구성을 제안하는가

기존 아홉 판단축을 그대로 문서 아홉 개로 나누면 목적·변경 비용이 반복되고, 이름과 경계 계약처럼 하나의 항목 안에서도 다른 종류의 판단이 섞인다. 기술별로 React·HTTP·store 문서에 기준을 각각 나누면 책임·계약이라는 같은 의미를 여러 곳에서 다시 설명하게 된다. 따라서 현재는 판단의 종류를 본문 구성에 사용하고, 기술·작업 단서는 그 본문을 찾아오는 안내에 사용한다. 실제 제품의 기술별 계약 문서는 계속 별도 역할을 갖는다.

[외부 비교61](2026-10-17-61-reference-comparison-for-format-design.md)에서 가져오기로 제안한 요소도 여기에 대입했다. Matt의 설계·작성 자료는 뜻·조건·대비를 가까이 두고 필요한 상세로 안내하는 근거, pstack은 원칙에 상황·질문·유지 가능한 조건을 연결하는 근거, Vercel은 작업 판단·조치·근거에 연결하면서 기준의 지위를 구별하는 근거, Anthropic은 모호한 원칙과 과도한 세부 규칙 사이의 설명량을 판단하는 근거다. **위 네 묶음은 외부 자료의 합의된 분류가 아니라 우리 사례와 전체 Spec을 보고 만든 Main의 제안**이다. 외부 원문의 최신 판본이나 우리 환경의 효과를 이번에 새로 검증한 것은 아니다.

네 묶음의 비용도 있다. 실제 작업은 여러 주제에 걸치므로 읽기 안내가 필요하고, 지나치게 묶으면 특정 조건이 안 보일 수 있다. 특히 가독성은 모든 주제와 관련되므로 네 번째 절이 앞의 반복 설명으로 커질 위험이 있다. 실제 본문에서 독립적으로 필요한 판단이 적다면 짧은 공통 설명으로 합칠 수도 있다. 03에서 자료량·함께 읽는 시점·관리 책임으로 이 선택을 다시 본다.

## 다음 판단과 확인 범위

바로 다음에는 이 구성에서 빠지거나 겹친 의미, 공통 부분과 상세의 경계가 적절한지 사용자와 판단한다. 지금 가능한 범위의 구성을 정리한 뒤03·04-03의 실제 Project·기존 스킬에 대입하고, 실행·검증 조건이 필요한 부분을01-01·01-03과 이어서 구체화한다. 이 대화를 새 전체 형식 리뷰의 의무 절차로 만들지 않는다.

Main은54·61·68·69와 현재 기준 시안·Project 읽기 안내를 대조했다. 별도 읽기 담당자는31·33·35·37·45·47·48·49·50·51·52에서 묶을 때 잃기 쉬운 차이와 근거의 지위를 추출했다. 이번 산출물은 구성·분류 제안과 현재 진입 연결이며 전체 기준 본문 작성, prototype 교체, 실제 코드·테스트·스킬 변경이나 적용 효과 검증은 아니다.

같은 읽기 담당자가 원자료에서 추출한 차이와 이번 구성안을 한정 대조해 아홉 판단축의 누락, 내용 종류·읽기 상황·지위·자료 사실성의 혼동, 사례를 의무 규칙으로 올린 문장은 발견하지 못했다고 보고했다. 분류의 최적성이나 실제 사용 효과를 검증한 것은 아니다. 이 기록과 재진입 문서9개에서 로컬 링크 대상383곳의 존재와 행끝 공백을 확인했고 누락·공백 오류는 없었다. `git diff --check`가 통과했다. 내부 이동·원격 URL·브라우저·제품 동작은 이번 검사 범위가 아니다.
