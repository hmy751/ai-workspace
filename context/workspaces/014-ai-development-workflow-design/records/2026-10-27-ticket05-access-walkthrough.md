# 05 흐름 대입 — access 질문에서 검토 범위와 개선안 선택

2026-10-27. 사용자 요청에 따라 기존 실제 사례에 루프의 2~3단계를 대입했다. **현재 근거를 이용한 설계 검토이며, 당시 시점의 루프 실행을 재현하거나 개선안을 채택·적용한 결과가 아니다.** 앞선 대화에서 한 번의 전체 흐름을 제시했고, 이번에는 실제 사례에서 범위와 후보 판단을 구체화했다. 운영 기준은 아직 미정이다.

## 실제 사건과 후속 결과

[원대화](../source/noline-evaluation/corpus/01a0ec21-e59e-7370-8432-8434271aa669/messages.jsonl) source_line2757~2784:

> 사용자: 근데 access 는 어디간거야?
>
> AI: 접근 조건인 `access`와 실행 함수인 `actions`는 구분하는 편이 더 명확합니다. 아래처럼 유지하겠습니다.
>
> 사용자: 아니 무조건 하란게 아니라 판단하라고

이후 AI는 반환 여부의 이유·비용을 설명했고 사용자는 “그래”라고 했다. [후속 인터뷰](../source/noline-evaluation/reviews/interview-20261012.md)의 사용자는 “마지막에 도움은 됐던것 같아 … 내 말에 무조건 맞추지 말고 왜 그렇게 했는지 판단해서 설명해줬으면 좋겠어”라고 밝혔다. 질문을 변경 요청으로 좁힌 문제와 이후 설명의 효용을 함께 보존한다. 모든 질문마다 승인을 받으라는 의미로 일반화하지 않는다.

현재 [explain 본체](prototypes/development-workflow/skills/explain/SKILL.md)는 질문·판단·변경 권한을 구별하고, [작성 상세](prototypes/development-workflow/skills/explain/references/constructing-explanations.md)는 실제 요구에서 현재안·대안의 이득과 부담을 비교한다. 본체 전체와 관련 상세를 읽었다. 현재 본문이 과거 사건 당시에도 설치·적용됐다는 뜻은 아니다.

또한 이 사례의 [후속 시험 원응답](experiments/explain-choice-investigation-60medium-revised-2026-10-26/case02-access/output/response.md)은 구체적인 제한 이유 안내를 추천 근거로 들었지만, 공개할 필드의 축소 판단을 나중으로 미뤘다. [비교 및 배경 종합](experiments/explain-choice-investigation-60medium-revised-2026-10-26/comparison.md)은 이를 부분 개선으로 판단하고 같은 사례의 문구 보완·재생성을 멈추도록 권고했다. 코드 적절성을 이번에 새로 판정한 것은 아니다.

## 2단계 — 어디까지 읽는가

이번 선택 범위는 사건 전후 대화와 사용자 회고, 현재 설명 스킬 본체 전체와 관련 상세, 이미 수행한 개선·시험 결과, Personal 진입 본문이다. 마지막 정정 한 문장만으로 새 규칙을 만들거나 기존 처리를 중복 추천하지 않기 위한 범위다.

현재 판단 질문은 ‘협업과 설명 수행을 무엇부터 개선할까’다. 실제 API 설계를 재결정한다면 당시 지원 목표·Project 관련 본문 전체와 내용 지침, 변경 전후 코드·소비자를 추가로 대조해야 한다. 이번에는 그 제품 설계 판단까지 수행하지 않았으므로 access 공개 여부나 Project 본문 충분성을 확정하지 않는다. 전체 저장소·무관한 문서·검사 도구·외부 조사는 열지 않았다.

잠정 범위 기준은 ‘문제가 나온 곳’에만 머무르지 않고 목적·내용의 적절성을 판단할 관련 본문 단위까지 읽되, 추가 자료가 후보의 선택·반영 대상을 바꿀 수 있는지로 확장을 판단하는 것이다. 관련성·종료 기준의 일반 운영값은 열린 후보다.

## 3단계 — 후보를 어떻게 고르는가

| 후보 | 이번 추천과 이유 |
| --- | --- |
| 협업 경험을 Personal에 보존 | 추천 후보. 질문에 즉시 맞추기보다 기존 선택의 이유·대안을 판단해 주길 기대했다는 실제 경험과 이후 설명의 효용을 남긴다. 스킬과 같은 실행 규칙을 복제하거나 보편적 성향으로 확정하지 않는다. 구체 계층은 미정이다. |
| 이미 있는 기준을 다음 실제 판단에서 사용 | 추천 후보. 질문의 의미와 현재 선택을 설명하고, 선택을 가르는 대안의 차이를 판단에 사용한다. 후속 시험에서 일부 근거가 좋아진 점과 남은 비교 공백을 함께 이어간다. 운영 적용 확인은 아직이다. |
| 설명 스킬에 같은 지시 추가 | 현재 보류 권고. 관련 의미가 본체·상세에 있고 이미 보완·시험을 거쳤다. 문구 부족이 원인이라는 새 근거 없이 추가하지 않는다. 기존 구조도 면제하지 않으며 충돌·찾기 어려움·실제 적용 실패의 원인이 확인되면 다시 검토한다. |
| access 공개나 Project 가이드 변경 | 판단 유보. 이 대화의 협업 실패만으로 제품의 올바른 API 구조를 정할 수 없다. 실제 설계 결정을 맡을 때 필요한 요구·코드·본문까지 확장한다. |
| 모든 질문에서 변경 승인받기 | 추천하지 않음. 사용자 요구는 판단과 설명이며 이미 위임한 실행까지 매번 중단시키는 방향은 근거가 없다. |

추천 후보의 구체적인 경험 내용은 ‘구조가 달라진 이유를 물었을 때 복원 약속부터 하면 사용자가 판단을 다시 요구해야 했다. 기존 선택의 이유와 대안의 이득·부담을 설명한 답은 도움이 됐다. 다만 명시적인 수정 요청까지 설명 요청으로 되돌려서는 안 된다’다. 이 문안은 채택된 Personal 기준이 아니다.

이번 판단에서는 관찰이 받치는 정도, 기존 기준과의 중복, 다음 판단에 줄 이득, 유지·실행 비용을 비교했다. 이를 점수표나 모든 루프의 고정 선별 기준으로 확정하지 않는다. 반영할 내용을 사용자와 고르는 단계는 남아 있다.

## 열린 기준과 현재 한계

- 관련 본문을 고르고 범위를 넓히거나 멈추는 구체 기준.
- 경험 기록을 언제 지속 판단이나 스킬 변경으로 연결할지.
- Personal의 경험 계층, 미결 후보의 위치·상태·재검토 경로.
- 실제 사용 관찰을 어떤 계기로 누가 이어받고, 무엇을 변경 효과로 볼지.

추가 사용자 질문이나 외부 조사 없이도 이번 협업 의도는 원문·회고에서 확인된다. 해당 자료로 알 수 없는 제품 설계 결론은 별도 공백으로 남겼다. 새 시험, 제품·Personal·실행 스킬 수정, reviewer 실행은 하지 않았다. 다음에는 이 후보의 선택을 논의하거나 Project 본문 자체의 개선을 중심으로 한 다른 사례를 대조할 수 있다. 둘 중 하나를 필수 순서로 확정하지 않는다.
