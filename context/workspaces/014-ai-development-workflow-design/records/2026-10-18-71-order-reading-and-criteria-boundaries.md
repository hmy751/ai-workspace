# 주문 흐름에 대입한 기준 읽기와 공통·상세의 경계

2026-10-18. [구성안70](2026-10-18-70-criteria-organization-proposal.md)을 주문 작업에 대입해, 작업자가 무엇을 먼저 읽고 어떤 의문에서 상세 원칙·사례를 찾는지 채웠다. **현재 추천은 공통 부분을 짧은 적용 관점과 읽기 단서로 두고, 이름·가독성은 찾아갈 수 있는 짧은 독립 절을 유지하는 것**이다. 네 묶음을 매번 순서대로 모두 읽는 절차나 독립 파일 네 개를 채택한 것은 아니다.

## 요청과 산출물의 범위

직전 대화에서 사용자는 구성·분류안이 prototype에 반영된 것인지 확인했다. Main은70에 별도로 정리했고 prototype 본문·파일·화면은 유지했다고 설명했다. 이어 사용자가 다음 진행을 묻자 공통/상세 경계와 이름·가독성의 독립성을 주문 장면에서 비교하자고 제안했다.

사용자의 실행 요청:

> 그럼 주문 흐름 사례에 대입해서 보여줘. 작업자가 뭘 먼저 읽고 언제 상세 기준이나 사례를 찾아보는지, 공통 부분과 상세 기준의 경계는 어디가 좋고 이름·가독성을 별도 묶음으로 둘 필요가 있는지도 같이 봐줘.

아래는 기존 기록에 기댄 **가상 읽기·판단 장면**이다. 실제 주문 코드를 조사·수정하거나 작업자 실행·테스트 효과를 확인한 결과는 아니다. 작업 의뢰·현재 주문 설명·반환문은 이 문서 안에서 채운 예시이며 별도 제품 Workspace나 주문 문서 파일을 만들지 않았다. prototype68과 구성안70은 이전 비교 근거로 유지한다.

## 장면의 출처와 가정

[주문 기록49](2026-10-16-49-order-mutation-workflow-boundaries.md)의 원자료는 Markdown 코드 예제다. 주문 성공 뒤 orders·catalog 캐시 무효화를 호출하고, 완료를 기다리지 않고 `clearCart()`·`navigate()`를 호출한다. 그 기록의 장바구니 주문과 바로 구매 두 화면은 서로 다른 흐름을 설명하는 가상 대비였다. 같은 API를 쓰더라도 장바구니 정리까지 함께 묶는다는 결론은 아니었다.

이번 작업은 [관련 개선 기록52](2026-10-16-52-related-refactoring-and-product-scope.md)의 **PC 주문 페이지·모바일 주문 페이지·빠른 주문 모달 모두 현재 장바구니 전체를 주문하는 같은 흐름**을 사용한다. 세 화면의 주문 요청·관련 캐시 무효화·장바구니 정리가 반복되고 화면별 완료 표현만 다르며, 사용한 쿠폰이 목록에 남는 원인은 coupons 무효화 누락이라고 가정한다. 사용자는 이런 조건에서 이번 수정과 직접 관련된 공통화도 비용·동작 보존을 고려해 함께 할 수 있다고 판단했다. 실제 제품 전체에 대한 리팩터링 권한이나 특정 Hook API의 채택은 아니다.

아래를 채우기 위한 추가 가정은 세 화면의 기존 성공 처리도49처럼 캐시 무효화 완료를 기다리지 않는다는 것이다. 세 화면이 실제로 그렇게 동작한다는 새 관찰이 아니다. 실패·입력·로딩의 상세 정책은 새로 발명하지 않으며 실제 작업에서 현재 코드와 동작으로 확인해야 한다. 이번 요청만으로 새로운 대기·완료 정책을 도입하지 않는다.

## 작업자가 처음 받는 내용

Main의 가상 의뢰:

> 장바구니 전체를 주문하는 세 화면에서, 주문에 사용한 쿠폰이 목록에 계속 남는 문제를 고쳐 줘. 주문·장바구니 처리와 화면별 완료 방식은 보존해 줘. 이번 수정에 직접 관련된 반복이 있다면 함께 정리할 이득과 비용도 판단해 줘.
>
> 지정 작업의 요구와 현재 주문 동작 설명에서 시작하고, 사용하는 코드와 검사 근거를 확인해 줘. 무엇을 바꿀지와 유지할 동작, 추가 결정이 필요한 부분을 설명해 줘.

가정한 작업 요구의 발췌:

> 목표는 주문 성공 후 사용한 쿠폰의 캐시 갱신 누락을 해결하는 것이다. 대상은 PC·모바일·빠른 주문 모달의 장바구니 전체 주문이다. 다른 주문 종류나 화면 완료 정책의 변경은 포함하지 않는다. 관련 구조 개선은 현재 목적·비용·동작 보존으로 판단한다.

가정한 현재 주문 동작 설명의 발췌:

> 세 화면 모두 현재 장바구니 전체를 주문한다. 주문 성공 시 orders·catalog 무효화를 호출하고 장바구니를 정리한 뒤, 각 화면이 이동 또는 모달 완료 표시를 맡는다. 캐시 무효화의 완료를 기다려야 다음 처리를 하는 계약은 현재 두지 않았다. 쿠폰 무효화는 이번 수정에서 추가할 대상이다.

작업자는 이 요구·현재 설명과 실제 세 호출부를 대조하는 것으로 시작한다. 문서에 적힌 ‘같은 흐름’을 검증 없이 믿거나 과거52의 가정으로 실제 사용처를 대신하지 않는다. 현재 장면에서는 대조 결과도 위 가정과 같다고 놓고 다음 판단을 진행한다.

## 공통 부분에서 먼저 읽을 실제 문장

70의 공통 관점을 이 장면에 맞춰 간결하게 전달하면 다음과 같다.

> 제품 목적과 이번 목표, 보존할 동작을 먼저 확인한다. 원칙은 현재 사용처와 비용에 대입하며, 실제 문제나 읽기·변경 부담을 근거로 유지·수정·보류한다. 관련 구조 개선도 이득과 동작 보존을 함께 판단한다.
>
> 이름·타입·호출 흐름으로 책임과 결과를 예상할 수 있는지도 살핀다. 공유 범위, 책임 위치, 동작 의미·수명, 표현의 명확성 중 판단이 필요한 부분의 상세로 이어 간다. 판단을 가른 이유와 확인·미확인을 작업 결과에 남긴다.

여기서 실제 제품의 ‘무효화 완료를 기다리지 않는다’는 값은 공통 원칙에 넣지 않는다. 그 값은 현재 주문 계약이 소유한다. 공통 부분은 그 계약을 확인하고 변경을 구별하도록 돕는다. 이름·가독성도 처음부터 한 문장으로 환기하여, 별도 상세를 열지 않았다는 이유로 관점 자체가 빠지지 않게 한다. 질문마다 답안을 요구하지 않는다.

## 어떤 의문에서 상세 기준과 사례를 찾는가

아래는 이번 장면에서 실제로 열린 판단의 순서다. 모든 작업의 고정 읽기 순서가 아니다.

| 작업자가 마주친 의문 | 읽는 상세·사례와 그때의 질문 | 판단에 반영되는 것 |
| --- | --- | --- |
| 쿠폰 무효화를 세 곳에 각각 추가할지, 관련 반복을 묶을지 | **공통 편의·사용처 선택**의 업무 흐름 설명. ‘같은 API인가, 같은 업무 흐름인가? 같은 정책의 수정 위치가 줄어드는가? 화면별 차이가 공통 옵션으로 되돌아오는가?’ | 이번에는 세 화면 모두 장바구니 전체 주문이고 쿠폰 무효화 누락을 세 화면에서 함께 고쳐야 한다는 조건을 사용한다. 중복 횟수만으로 결론내리지 않는다. |
| 같은 흐름이어도 장바구니 정리까지 묶어도 되는지, 과거 바로 구매 대비와 왜 결론이 다른지 | 원칙의 구별만으로 경계가 분명하지 않아 **52의 조건별 사례**와 **49의 다른 흐름 대비**를 찾아본다. | 52는 같은 장바구니 흐름,49의 바로 구매는 장바구니를 건드리지 않는 다른 흐름이다. 현재 빠른 주문 모달을 이름만 보고 바로 구매로 분류하지 않는다. 사례는 현재 사용처 확인을 대신하지 않으며, 관련성·비용·보존 조건으로 이번 공유안을 비교한다. |
| 공통으로 옮길 때 캐시·장바구니·화면 처리를 어디까지 맡길지 | **책임 배치·기존 도구** 상세. ‘도구가 이미 맡는 상태는 무엇인가? 공통 업무 단위가 조율할 일과 각 화면의 선택은 무엇인가?’ | QueryClient가 캐시를 관리하고 기존 장바구니 동작이 상태를 바꾸게 둔다. 장바구니 주문 흐름이 요청·관련 무효화·정리를 조율하며, 목적지가 다른 화면 완료 처리는 사용처에 남기는 안을 만든다. HTTP 요청 계층에 화면 선택을 넣지 않는다. |

## 작업자가 남기는 구체적인 판단

구현 전 가상 반환문:

> 쿠폰 문제는 세 장바구니 주문 흐름의 coupons 무효화 누락으로 보고 수정할 계획이야. 세 화면이 같은 주문·정리 정책을 사용하므로 요청·관련 캐시 무효화·장바구니 정리를 함께 관리하는 안을 제안해. 세 곳에 동일 정책을 적용하는 변경 위치를 줄이는 이득이 있고, 세 화면의 연결·성공·실패·로딩을 다시 확인할 비용이 있어.
>
> 화면별 이동·모달 완료 표시는 각 사용처에 남길게. 캐시 갱신을 호출한 뒤 다음 처리로 가던 방식도 유지할 거야. 공통화하면서 캐시 갱신 완료까지 기다리도록 바꾸지는 않을게.
>
> 새 단위는 장바구니 주문을 조율한다는 범위가 이름과 짧은 설명에 드러나게 할 계획이야. 구체 Hook 이름·인자 형식은 이 판단만으로 표준화하지 않을게.
>
> 세 화면의 쿠폰 무효화 호출과 실제 쿠폰 목록 반영, 장바구니 정리, 서로 다른 완료 표시, 기존 실패·로딩 동작을 확인해야 해. 이 반환은 변경 계획이고 아직 구현·검사 결과는 아니야.

이 장면은 공유안을 선택할 조건을52에서 가져온 것이다. 제품이 작은 실험 범위이거나 같은 변경 책임이 실제로 확인되지 않는다면, 세 곳을 직접 고치는 안이 더 적절할 수도 있다. 그때도 쿠폰 문제의 해결 여부는 별도로 확인한다. 검토자는 같은 요구·관련 기준·현재 코드와 구현 결과를 대조하며 구현자가 공유했다고 해서 그 구조를 정답으로 전제하지 않는다. B의 직접 수정·재확인 상세는01-01·01-03에서 이어 정한다.

## 이름·가독성에서만 남는 판단이 있는가

아래 이름은 **이번 비교를 위한 후보**이며 기존 코드의 이름이나 채택한 API가 아니다. 같은 장바구니 주문 구현과 같은 비대기 완료 의미를 두고 표현만 비교한다.

| 비교 | 무엇을 판단하는가 |
| --- | --- |
| 공통 단위의 가칭 `useOrder`와 `useCartCheckout` | 전자는 주문 조회·생성·변경 중 무엇인지와 장바구니 정리 책임을 이름에서 알기 어렵다. 후자는 장바구니 주문 흐름이라는 단서를 준다. 모든 책임을 이름 하나에 넣지는 않으며 캐시·정리의 세부 약속은 짧은 API 설명과 타입에서 확인한다. |
| callback 가칭 `onCompleted`와 ‘주문 생성 성공 뒤 호출되며 캐시 재조회 완료는 보장하지 않는다’는 설명이 있는 `onCreated` | 이름만으로 모든 후속 완료를 약속하지 않는다. 이미 정한 호출 시점과 보장 범위를 사용처가 이해하는지 본다. 특정 callback 명칭을 의무화하지 않는다. |
| 이름은 그대로 두고 무효화 Promise를 기다리도록 구현을 바꿈 | 이름 개선이 아니라 동작 계약·수명 변경이다. 표현 절에서 답을 정하지 않고 현재 요구·완료 경계로 돌아간다. |

첫 두 비교는 책임·동작을 정한 뒤에도 남는 표현 문제다. 이름·타입·호출부에서 실제 역할을 읽을 수 있는지 확인할 자리가 필요하다는 근거가 된다. 다만 더 분명한 이름이 있다는 사실만으로 기존 전체 코드의 이름을 바꿀 필요는 없다. [isError 판단45](2026-10-16-45-naming-readability-supplement.md)는 당시 사용에서 더 명확한 boolean 표현과 필수 수정 여부를 구별했다. 이번에는 새 공통 단위를 만드는 장면이어서 적절한 이름을 선택할 비용이 다르다.

## 공통 부분과 상세 기준의 경계에 대한 추천

**공통 부분은 판단을 시작하는 관점과 필요한 상세를 알아차릴 단서까지 둔다.** 목표·현재 계약을 이해하고, 근거·비용·동작 보존으로 판단하며, 표현에서도 역할을 읽을 수 있는지 살핀다는 정도다. 지금70의 공통 부분을 주제마다 확장한 전체 요약으로 만들지 않는다.

**상세에는 그 주제에서 선택을 가르는 구체적인 구별을 둔다.** 같은 API와 같은 업무 흐름, 도구 책임과 업무 조율, 호출 순서와 완료 순서, 표현만 바꾸는 것과 계약을 바꾸는 것 등이 해당한다. 이 구별까지 모두 공통 부분에 넣으면 작은 이름 수정에도 주문·캐시·수명 설명을 먼저 읽게 된다. 반대로 ‘목적에 맞게 판단하라’만 남기면 어떤 상세가 필요한지 알아차리기 어렵다.

**사례는 원칙의 구별만으로 현재 선택이 분명하지 않을 때 읽는다.** 이 장면에서는 같은 업무 흐름인지와 관련 구조 개선을 포함할지의 차이를49·52로 비교했다. 실제 계약 확인과 필요한 상세 기준을 ‘사례는 선택적’이라는 이유로 생략하는 것은 아니다. 물리적으로 사례를 같은 문서에 둘지 분리할지는03에서 읽는 양·관리 조건으로 다시 정한다.
