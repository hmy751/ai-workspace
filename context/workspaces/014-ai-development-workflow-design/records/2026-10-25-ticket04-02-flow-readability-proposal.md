# 04-02 — 도입 흐름을 본문 가독성으로 잇는 편집안

2026-10-25. Main이 먼저 [후보](reviews/explain-flow-readability-2026-10-25/main-proposal-before-review.md)를 작성한 뒤, 새 컨텍스트의 개선 리뷰어에게 현재 본체·상세·실제 응답·사용자 원문·인증 코드를 전달했다. [리뷰 반환 전문](reviews/explain-flow-readability-2026-10-25/reviewer-response.md)을 대조해 아래처럼 범위를 좁혔다. 실행 스킬 수정·추가 시험 없음.

## 사용자 요구

> 뭐랄까 A는 구분되는 문단들이 있어서 좋았던것 같아 가독성을 지킨느낌
> 그럼 B의 처음 흐름 잡아주는 장점은 살리고 A처럼 본문도 따라가기 편하게 하려면 어떻게 보완하면 좋을까? 그냥 소제목 넣으라는 규칙 추가 말고 본체랑 상세 예시를 같이 보고 구체적으로 얘기해봐 한번 먼조 고민해보고 지금 수정한거랑 흐름 개선리뷰어한테 잘 전달해봐 해결하려면 어떻게 해야할지

이제A 선호에서 구분되는 문단·가독성의 역할은 Main 추정뿐 아니라 사용자 직접 발화로 확인됐다. A의 모든 문장·제목 형식을 정답으로 고정한 승인은 아니다.

## 대조와 채택

본체의 전체 연결·실제 코드 대응은 유지한다. 표현 절에는 이미 제목·강조·의미 단위·비중·인접 배치가 있으므로 제목 지시의 부재로 원인을 단정하지 않는다. 각 묶음이 무엇에 답하는지 읽는 중 찾아야 하는 부담을 줄이는 편집을 구체화한다. B에도 문단은 있고 A의 가운데 절도 여러 질문을 담으므로 문단 수나 A의 양식을 성능 기준으로 삼지 않는다.

리뷰 후 Main의 초기 후보에서 두 군데를 줄였다. 설명 순서 절 끝과 표현 절 양쪽의 보강은 중복될 수 있어 표현 절을 주 수정 위치로 한정한다. ‘보조 해설은 뒤로’라는 배치는 채택하지 않는다. 공유 Promise 옆의 catch처럼 오해를 막는 조건은 해당 코드 가까이에 유지해야 한다.

## 본체 교체 범위

[본체](prototypes/development-workflow/skills/explain/SKILL.md)의 ‘깊이를 유지하며 읽기 쉬운 형태로 만든다’ 첫 문단과 중심/보조·문단 분할 문단을 다음 두 문단으로 합쳐 교체하는 안이다. 표현 선택 표·의미 있는 반복·범위·권한은 유지한다.

> 여러 부분을 설명할 때는 도입에서 잡은 연결을 본문에서 함께 풀 질문들로 나눈다. 각 묶음은 지금 설명할 역할·차이와 그 답을 먼저 드러내고, 이를 이해하는 데 필요한 코드·해설·조건을 가까이 둔다. 다른 질문으로 넘어가는 경계는 문단의 첫 문장, 제목·강조, 목록이나 표 가운데 내용에 맞는 방식으로 알아볼 수 있게 한다. 함수나 도식의 항목마다 한 절을 만드는 것은 아니다.
>
> 한 묶음 안에서도 서로 다른 설명을 한 문단에 쌓지 않는다. 같은 코드에서 값을 정하는 이유와 기다린 뒤 확인하는 이유를 설명한다면, 각각의 관계를 읽을 수 있게 문단을 나누되 같은 코드 가까이에 둔다. 결론을 바꾸는 조건은 해당 주장과 함께 남기고, 다른 경로로 넘어갈 때는 무엇이 달라지는지 밝힌다. 읽기 쉽게 만들기 위해 필요한 값·실패 조건을 생략하거나 같은 결론을 매번 반복하지 않는다.

마무리의 기존 긴 문단 분할 문장을 ‘각 대목의 질문과 조건을 찾기 어려우면 묶음·배치를 고친다. 짧은 한 관계로 끝나는 답은 구분을 늘리지 않는다’는 의미로 교체한다. 새 체크리스트나 고정 소제목 개수를 추가하지 않는다.

## 상세에서 실제 바꿀 배치

[전체 인증 예시](prototypes/development-workflow/skills/explain/references/constructing-explanations.md)의 등록부와 두 갱신 경로 그림, 실제 발췌는 유지한다.

| 현재 대목 | 편집안 |
| --- | --- |
| 요청 전 코드 뒤 세션 고정·대기 후 검사·헤더 반환이 한 문단 | 같은 코드 아래 ‘요청이 속한 세션’과 ‘기다린 뒤 검사·반환’을 두 문단으로 나눈다. |
| 401 설명 말미에 성공 응답 검사 등장 | 응답 묶음의 시작에서 성공/실패 경로를 구별하고401 코드로 내려간다. 첫401과 재차401 결과도 구별해 읽게 한다. |
| 공유 Promise·각 요청 복귀·Map 정리·오류 전파가 한 문단 | 공유하는 것은 갱신 작업이라는 답, 성공 뒤 요청 전/401 각각의 다음 처리, 정리와 오류 전달의 차이를 같은 코드 가까이에서 세 문단으로 잇는다. |
| 여러 갱신 실패가 연속 산문 | 세션 불일치·자격 증명 거부·다른 오류·저장 거절을 결과와 나란히 놓는다. 실패 종류와 재인증 요구 유무를 지우지 않는다. |
| 예시 선택 이유와 실제 답이 섞임 | 원천/발췌 안내는 앞, 구성 이유는 뒤로 모은다. 의미를 바꾸는 생략 조건은 코드 가까이에 남긴다. |

공유 갱신의 실제 교체 문단과 실패 표, 요청·응답의 교체 문장은 리뷰 원문에 완성돼 있다. 단순 제목 삽입과 달리 문단이 답할 질문·내용의 위치·대비가 함께 달라진다. 요청 전과401은 호출 시점·코드·설명 목적이 달라 큰 하나로 합치지 않는다. 인증 후속 catch 예시는 전체 답과 구별해 유지한다.

## 유지와 한계

작은 bool·??= 질문, 앞선 발화 복구는 현재 경계를 유지한다. 동기화·여행·보고서에도 같은 목차를 복사하지 않는다. 실제 설명에서 관계를 유지하면서 필요한 대목을 찾을 수 있는지가 기준이며 도입 그림과 본문의 항목을1:1로 대응시키지 않는다.

이번 시험은 새 코드·짧은 구성 질문으로 실행했으며 사용자의 이번 선호 대화는 입력하지 않았다. 조건별1회와 공통 응답 스타일의 영향을 분리하지 않았으므로 특정 skill 문구가 제목을 없앴다는 인과는 미확정이다. 이 한계를 이유로 실제 편집 공백을 무시하거나 새 시험부터 반복하지 않는다.

Main은 리뷰가 짚은 문단과 실제 인증 코드를 대조했고, 위 구체 편집안을 사용자와 논의할 안으로 채택했다. 별도 리뷰는 개선 목적의1회이며 승인 확인 반복이나 전체 구조 재설계로 확대하지 않았다. 현재는 제안·리뷰 보존 단계다.
