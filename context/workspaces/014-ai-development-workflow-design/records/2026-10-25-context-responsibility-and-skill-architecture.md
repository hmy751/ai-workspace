# 04-03 — 새 작업 흐름에서 맥락 책임과 스킬 구성을 다시 비교한다

현재 추천은 후속 [Matt·Lauren 원문 조사와 종합](2026-10-25-context-reference-synthesis.md)에서 읽는다. 일상 읽기의 기본 진입을 새 context 스킬로 전제하지 않는 구성을 권고하며, 하나의 스킬 안도 비교 후보로 유지한다. 아래는 당시 비교와 형성 근거다.

당시 구체안: 사용자가 실제 책임 구분을 요청해 [문서·주체·수행별 책임과 로그인 예시](2026-10-25-context-responsibility-concrete-proposal.md)로 펼쳤다.

상태: **워크플로 안의 맥락 사용·유지를 기본으로 두고, 직접 요청도 같은 공통 절차를 쓰는 후속 추천안.** 사용자는 별도 요청도 가능하지만 주로 개발 중 담당자들이 자연스럽게 읽고 갱신하는 것이 중요하다고 명료화했다. [후속 논의](#후속--워크플로와-직접-요청이-같은-맥락-절차를-쓴다)를 현재 입력으로 읽는다. 아래 세 구성안은 그 이전 비교이며, 독립 요청 빈도를 중심으로 필요성을 판단하던 질문은 대체됐다. 정확한 스킬 구성은 미채택이고 실행 스킬·runtime은 변경하지 않았다.

## 사용자 요청과 재검토 이유

사용자는 구체 연결 전에 기존 스킬의 목적과 새 workflow의 관계를 먼저 보자고 했다. 핵심 원문은 다음과 같다.

> read 그 스킬도 해당 work에 가져오는 스킬인데 그런걸 목적으로 했지 근데 그게 아마 현실적으로 current에 필요한 부분에 한번 가져와 쓰고 하는 정도일거야 뭔가 반복적으로 보는 어찌보면 지금 새로 구축된 워크플로랑 뭔가 안맞아 보이거든? 그리고 범위도 뭔가 다르고

> update는 다시 반영인데 이건 아마 루프 작업이랑 좀 관련이 되어 있을거고 나중에 정할 어쨋든 뭔가 전반적으로 겉으로 볼때 그냥컨텍스트 읽는다 하니까 맞아보이겠지만 뉘앙스나 의도 이런게 달라서

이어 담당자에게 Main이 요약을 전달하는지 원문을 읽게 하는지, Vercel에서 참고한 질문별 선택이 맥락 읽기에도 들어갔는지 물었다. Main이 Work의 두 역할 중 하나를 새로 고르게 질문한 것은 이미 합의한 직접 읽기까지 미정인 것처럼 보이게 했다. 후속 확인에서 기존 합의를 복원했다.

> 너무 기존 스킬을 유지한다고 굳이 얽매이지 않아도 되니까 새로운 스킬 구성도 생각해봐 그러니까 또 억지로 만들란건 아니고 적합한거 지금 기존 시스템 새 워크플로 등등 그리고 우리가 추후 할 작업들 다 종합적으로 분석해서

이 요청은 새 스킬의 신설·폐기를 확정한 것이 아니다. 기존 스킬의 이름·개수·범위를 출발 조건으로 고정하지 않고, 유지·흡수·재구성·신설을 같은 기준으로 비교하라는 요청으로 해석한다.

## 확인한 현재 계약

- **원문 직접 읽기는 이미 합의됐다.** Main은 목표·범위·보존 조건·판단 권한과 관련 자료·선택 이유를 전달한다. 담당자는 필요한 실제 본문을 읽고 자기 질문에 따라 추가 탐색한다. Main의 요약으로 원문을 대신하거나 모든 Personal·Project 문서를 일괄 읽는 방식은 아니다. [7·8번 입력과 탐색 합의](2026-10-23-review-workflow-7-12-proposal.md), [현재 development](prototypes/development-workflow/skills/development/SKILL.md)에 연결돼 있다.
- **질문별 선택도 이미 있다.** 작업 주제·대상·필요한 판단에서 시작하고, 관련 원칙과 계약을 본 뒤 사례·형성 자료·실제 코드와 검증 근거를 필요에 따라 읽는다. 새 질문·충돌·변경이 생기면 다시 선택한다. Vercel 자료의 작업별 선택은 참고 근거이며, 우리 반복 수행 절차 전체가 그 자료에 그대로 있는 것은 아니다. [동적 맥락 논의](2026-10-21-dynamic-context-and-review-intent.md), [Vercel 보존 원문](<../source/lectures/vercel-product-design (1).md>).
- **기존 read도 반복 선택을 허용했다.** 단독 이해 요청과 작업 중 선택 부족 모두 발동 조건이고, 유효한 읽기는 재사용한다. Work에 본문을 한 번 복사하는 스킬로 정의돼 있지 않다. 다만 Project 중심의 실행 경계가 새 workflow의 여러 역할과 Personal·Project·Work 전체에 어떻게 대응하는지는 다시 판단해야 한다. [Reference read](../source/ai-workspace-baseline/reference-project/.agents/skills/read-project-context/SKILL.md).
- **선택·운반·이해·유지는 서로 다르다.** 과거 Recover는 선택된 Project 원문과 제한된 Work 상태를 재개 입력으로 제공했고, 읽기 스킬은 의미를 이해하고 작업에 적용했다. Work의 선택 근거와 현재 상태는 별도 책임이었다. Recover가 자료를 제공했다는 사실만으로 이해·적용이 완료되지는 않는다. [Recover 원형](../source/ai-workspace-baseline/reference-project/context/work/harness/recover/README.md).
- **기존 update에도 판단이 있다.** 지속할 사실과 의미, 근거·권위·Owner·구성·영향받는 경로를 판단한다. 완료 후 복사나 승인된 글의 기계적 저장만 맡는 절차가 아니다. 반면 원인·개입 대안·채택 후 효과까지 보는 경험 개선 전체를 소유하지는 않는다. [Reference update](../source/ai-workspace-baseline/reference-project/.agents/skills/update-project-context/SKILL.md).

## 구성 판단 기준

스킬을 나누는 근거는 별도로 요청할 수 있는 목적, 필요한 입력과 판단, 완료 결과, 여러 흐름에서 재사용할 필요다. 읽기·쓰기 같은 동작 이름, 담당자 수, 순서 번호만으로 나누지 않는다. 스킬은 같은 Main이나 담당자가 적용할 수 있는 절차이므로, 독립 스킬이라고 별도 agent·인계·보고서·전체 재독이 필요한 것은 아니다.

내용과 관리 기준의 정본은 Personal·Project·Work가 소유한다. workflow는 현재 목표를 이루기 위해 언제 어떤 책임을 수행할지 연결한다. 스킬은 필요한 실행 절차를 재사용하게 하며, Recover·Verify 같은 장치는 환경에서 입력·실행·증거를 지원한다. 한 스킬로 묶더라도 제품 결정·개인 기준·Work 상태의 권위까지 합쳐지지는 않는다.

## 세 구성안의 비교

| 구성 | 단독 맥락 이해·정비 요청 | 작업 중 새 질문·변경 | 판단 |
| --- | --- | --- | --- |
| 기존 read/update/create를 새 범위에 맞게 재구성 | 요청별 진입이 분명하고 기존 선별·권위·영향 확인 절차를 재사용한다. Project 외 범위의 연결을 정해야 한다. | 담당자가 필요한 절차만 적용할 수 있다. workflow와 동일한 선택·반영 기준을 중복 정의하지 않아야 한다. | 유효한 대안이다. 기존 형식이 익숙하다는 이유만으로 기본안으로 택하지 않는다. |
| 맥락 이해·유지·작업 인수를 한 진입으로 묶기 | 사용자는 한 진입으로 이해·복원·정비를 요청하고 필요한 상세로 내려갈 수 있다. | 목적에 맞는 상세만 적용하면 재독·별도 담당자를 강제하지 않는다. | 읽기 전용 이해, 권위가 있는 변경, 새 작업 생성의 완료와 권한이 크게 달라 본체가 넓어질 위험이 있다. 공통 진입이 실제로 유용한지 확인해야 한다. |
| 일상 수행은 workflow와 Owner 기준에 연결하고 독립 결과가 있는 과업에 스킬을 두기 | Main이 원래 요청과 Owner 지침으로 이해·정비할 수 있다. 독립 정비의 실행 절차가 반복적으로 필요하면 공통 스킬로 묶는다. | 역할별 직접 읽기·재선택과 Main의 현재 상태 반영을 수행 안에서 연결한다. | 현재 추천 후보. development 밖의 이해·정비 요청도 빠뜨리지 않아야 하며, 같은 절차가 여러 곳에 반복되면 공유 상세나 독립 스킬로 조정한다. |

세 번째를 추천하는 이유는 스킬 수를 줄이는 데 있지 않다. 현재 일을 이해하고 수행하는 책임은 그 일 안에서 이어 가고, 새로운 질문과 완료 결과를 가진 일에는 독립적인 진입을 주기 위해서다. 이는 실제 수행 효과를 확인한 결론이 아니라 현재 계약에 근거한 설계 판단이다.

## 실제 장면에서의 연결

**맥락 이해만 요청받을 때:** Main은 요청의 질문과 대상에서 관련 정본을 골라 읽고, 적용할 내용과 열린 판단을 설명한다. 개발·문서 수정·경험 개선을 시작할 필요는 없다. 기존 read 유지안도, 공통 맥락 진입안도, Owner 지침을 직접 적용하는 안도 이 결과를 낼 수 있어야 한다.

**진행 중 설명 오류를 발견할 때:** 담당자가 실제 계약·소비자·근거를 대조하고, Main은 현재 작업의 판단과 확인된 Project 설명을 필요한 범위에 맞춘다. 새로운 기준 채택이나 회고가 항상 필요한 것은 아니다. 해당 작업의 허용 범위 안에서 수행하고 미확정 제품 약속은 사실 정정과 구별한다.

**인증 완료와 조회 완료를 다시 혼동한 경험을 다룰 때:** 당장의 구현 수정·검증 결과는 Work에 남긴다. 이어 기존 기준이 부족했는지, 충분한 기준을 읽지 못했는지, 코드 표현이 혼동을 만들었는지 판단하는 것은 경험 개선 과업이다. 결과가 Personal 문장 추가일 수도 있고 코드·검사·읽기 경로 수정 또는 유지일 수도 있다. 기록, 변경 채택, 반영, 효과 확인을 같은 완료로 처리하지 않는다.

**실제 저장소 통합을 독립 목표로 시작할 때:** 새 Work는 자기 목표·완료 조건·현재 상태를 갖고 이전 예제의 관련 계약·제약·미확인만 선별 인수한다. 이전 Work 전체를 복사하지 않는다. 생성 자체로 기본 작업 선택·Maintain 연결을 자동 전환하지 않으며, 명시된 전환과 실제 환경 계약을 따른다.

- [05 경험 루프](../current/tickets/05-improvement-loop.md)는 경험 선택·해석·개입 대안·채택·반영·효과 관찰을 맡는다. update를 확대하는 것만으로 이 과업 전체가 완성되지는 않는다.
- [06 체계 전환](../current/tickets/06-framework-transition.md)은 공통과 대상별 배치, Recover·Verify 의존, 기존 자동 Maintain 대체와 실제 설치·복구를 맡는다. 저장소 사이 개선 적용의 독립 절차는 이때 기존 이식 수단과 함께 비교한다.
- [07 전체 연결](../current/tickets/07-integrated-rehearsal.md)은 단독 이해·작은 수정·의미 변경·새 Work·경험 반영 장면에서 빈 책임과 중복을 확인한다. 모든 작업마다 별도 연결 검토 스킬을 호출하는 구조는 아니다.

이 Ticket들을 순서대로 호출할 스킬 단계로 바꾸거나, 관련된 모든 설계가 끝나기 전에는 구성 논의를 할 수 없다고 보지 않는다. 현재 책임 경계를 함께 맞추고 각각의 상세와 실제 적용 근거를 이어 간다.

지금 사용자에게 확인할 유용한 사용 장면은 **개발 목표와 별개로 맥락 자체를 이해·정리·복원하는 요청이 얼마나 독립적으로 필요한가**이다. 그 요청이 중요한 기본 사용 장면이면 공통 이해·유지 스킬의 독립 진입 가치가 커진다. 사용자에게 스킬 개수를 먼저 선택하게 하거나 이미 합의된 담당자 직접 읽기를 다시 묻지 않는다.

별도 조사 두 건은 기존 스킬·현재 workflow·후속 Ticket의 경계를 대조했다. 추가 읽기 전용 리뷰에서는 독립 스킬을 별도 agent·과업 비용과 동일시하지 말고, 단독 이해 요청도 모든 대안에 공평하게 대입하라는 보완을 받아 위 비교에 반영했다. 이번 결과는 설계 분석이며 제품 실행·새 workflow 수행 시험·효과 입증·04-03 마감은 아니다.

## 후속 — 워크플로와 직접 요청이 같은 맥락 절차를 쓴다

사용자 원문:

> 그러니까 기존에 리드 해서 work current에 남기는게 워크플로 잇어도 필요하다고 말하는 것 같은데? 맞을까?
> 뭐 어쨋든 그런 요청도 할 수는 있는데 주로 개발 워크플로 안에서 자연스럽게 읽고 갱신되는 게 중요한 포인트같아 너도 워크플로 보면 작업마다 아무래도 필요하고 그럴것같잔하? 담당자들이 .
> 그럼 별도 요청도 가능하게 하는건 어떨까? 다른 층위? 뭐 어쨋든 억지로 스킬을 나누진 말고, 다시 전체가 어떻게 연결될지 생각해봐

Main은 독립 요청 빈도를 스킬 필요성의 주요 조건으로 물은 framing을 정정했다. 중심은 개발 중 필요한 맥락을 담당자가 직접 읽고 적용하며, 새 의미가 생기면 작업 상태와 해당 정본을 유지하는 것이다. 직접 요청은 같은 실행 절차에 들어오는 추가 경로로 지원할 수 있다.

### 현재 연결 추천

- **개발 workflow는 언제·누가·무엇을 위해 맥락을 다루는지 연결한다.** 시작·재개, 역할 인수, 구현·검토·검증 중 새 질문, 중요한 변경과 결과 반환에서 필요한 부분을 적용한다. 사용자가 매번 read/update를 지시해야 한다는 전제를 두지 않는다. 자동 hook을 새로 붙인다는 뜻은 아니다.
- **공통 맥락 절차는 선택·이해·적용과 변경 반영을 수행하는 방법을 재사용하게 한다.** development의 담당자와 Main이 자기 책임에 맞는 부분을 적용하며, 사용자의 직접 읽기·정리·반영 요청도 같은 절차로 처리한다. 한 번의 읽기가 매번 쓰기나 별도 보고로 이어지는 고정 순서는 아니다.
- **Personal·Project·Work는 실제 내용과 각 관리 기준을 소유한다.** 공통 절차가 이들의 정본·변경 권한을 합치거나 제품 결정을 대신하지 않는다. 자료가 충분하면 유효한 읽기를 재사용하고, 새 질문이나 근거가 생기면 관련 원문과 실제 산출물을 더 확인한다.

첫 구성 후보는 이 공통 절차를 **하나의 맥락 스킬과 필요한 상세**로 구성하는 것이다. 개발 안에서 쓸 부분과 직접 요청의 범위를 명확히 하고, 읽기·적용·Work 유지·공통 반영이라는 네 책임을 네 스킬로 바꾸지 않는다. 공통 상세 문서로 두는 형태도 가능하며 최종 파일 배치·이름·개수는 아직 확정하지 않았다. 작업 생성·경험 개선 전체까지 이 진입에 넣지는 않는다.

### Work current와 역할 연결

‘읽고 current에 남기는 연결’은 workflow가 있어도 필요하다. 정확히는 현재 작업에서 계속 의존할 **적용 조건·선택과 이유·새 사실·열린 판단**, 다시 찾아갈 **원문과 근거의 접근점**을 남긴다. 읽은 자료 전부의 요약이나 매 조회의 로그를 쌓지 않는다. 기존 read 스킬 자체는 읽기 전용이고 current 반영은 Work 책임이었으며, 여기서는 두 기능이 수행 안에서 이어지도록 재구성하는 안을 논의한다.

Main은 현재 목표와 필요한 초기 맥락을 연결한다. 각 담당자는 관련 current와 원문을 직접 읽고 자기 질문에 맞게 추가 선택·적용한다. 중요한 새 사실·선택·충돌·변경 필요를 근거와 함께 반환하면 Main이 지속 범위와 Owner를 판단하고 필요한 반영을 수행·배정한 뒤 확인한다. 그 변화가 진행 중인 담당자의 입력이나 이전 검증 근거를 바꾸면 해당 작업에도 다시 연결한다. Main의 전체 유지 책임과 담당자의 직접 읽기·판단 책임은 유지된다.

예를 들어 current에 ‘조회 실패와 인증 성공을 구별한다’는 이번 작업의 선택과 근거를 남겨도, 담당자는 정확한 실패 조건이 쟁점일 때 Project 계약과 실제 코드를 직접 읽는다. 새 사용처가 다른 대기 조건을 요구하면 기존 선택을 재판단하고 해당 Work에 남긴다. 제품 계약 자체의 변경은 Project의 권위에 따라 따로 반영한다. 한 작업의 좋은 선택을 Personal 기준으로 자동 채택하지 않는다.

직접 ‘읽어줘’라고 요청받으면 같은 선택·이해 부분을 적용하며 요청에 맞게 설명한다. 그 요청만으로 지속 문서 수정을 전제하지 않는다. ‘이번 Work에 반영해줘’나 개발 수행 안의 유지 책임이 있으면 관련 반영 부분을 수행한다. Work가 없는 단독 이해 요청 때문에 새 Work를 강제로 만들지 않는다.

05의 경험 개선은 어떤 기준·절차·도구를 바꾸는 편이 나은지 판단하는 책임으로 이어진다. 그 판단에 필요한 읽기와 채택된 맥락 변경에는 같은 공통 절차를 사용할 수 있다. 따라서 공통 맥락 절차는 개발과 경험 개선에서 재사용될 수 있으며, 경험 개선 전체를 대체하지 않는다.02는 Work에 남길 내용과 수명,06은 실제 배치·runtime 연결,07은 이 사용 경로의 연결과 부담을 구체화한다.

위 내용은 기존 합의인 담당자 직접 읽기·Main 유지·Owner 구별을 바탕으로 한 **후속 배치 추천**이다. 사용자 우선순위는 확인됐지만 하나의 맥락 스킬 채택·구현·설치는 아직 요청받거나 수행하지 않았다.
