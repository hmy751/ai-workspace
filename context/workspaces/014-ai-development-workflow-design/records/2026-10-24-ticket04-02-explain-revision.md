# 04-02 — 기존 두 스킬 재검토 후 explain 보완

**사용자 요청으로 기존 두 본문·배경을 재검토하고 explain 본체·두 상세·형성 자료를 수정했다.** 단일 진입점과 조건부 상세 구성은 유지한다. 수정 후 응답 비교·운영 설치·04-02 마감은 하지 않았다.

사용자 요청:

> 이 방향으로 수정뿐만 아니라 기존 스킬 다시 꼼꼼히봐서 더 검토해봐

앞선 [네 약화 지점·보완 후보](2026-10-24-ticket04-02-explain-contract-comparison.md)를 논의한 뒤의 요청이다. 앞선 기록의 미수정·미채택은 당시 상태이며, 이번 반영 상태와 구별한다.

## 검토와 반영

삭제 직전 브리핑·복구 본문 전체, 각각의 형성 맥락과 관련 보존 근거, 현재 explain 본체·두 상세·공통 기준을 대조했다. source 인터뷰와06 두 모델 설정의 응답·읽기 평가도 함께 확인했다. 배경을 현재의 강제 규칙으로 삼거나 다른 Desktop 저장소로 조사 범위를 넓히지 않았다. 새 독립 리뷰를 실행한 것이 아니라 Main의 재검토다.

앞선 네 지점인 전후 자료 선택, 응답 안의 구현 대응, 목표별 개선 근거, 목적별 충분성을 구체화했다. 추가로 전체 역할에서 대표 사건을 통해 부분을 선택하는 방식, 구조 변화가 실제 읽기·수정 부담에 미치는 효과와 남은 제약을 연결했다. 복구 상세는 이미 바꾼 설명과 새 질문을 잇고 현재 유효한 용어를 쓰는 부분만 보완했다.

재검토한 책임별 반영·유지 이유는 스킬 가까운 [변경 기록](prototypes/development-workflow/skills/explain/_background/records/2026-10-24-explanation-revision.md)이 소유한다. 실제 연결·현재성·미완성·추론 범위·수정 권한은 현재 본문과 공통 기준에 남아 있어 중복 추가하지 않았다. 고정 제목·Main/Maintain 배치는 되살리지 않았다. 코드 블록 개수·전수 조사·모든 답의 같은 목차·추가 승인 단계를 만들지 않았다.

현재 실행: [본체](prototypes/development-workflow/skills/explain/SKILL.md), [작성 상세](prototypes/development-workflow/skills/explain/references/constructing-explanations.md), [앞선 발화 상세](prototypes/development-workflow/skills/explain/references/prior-explanation.md). 구성과 이름이 같으므로 development·공통 기준의 호출 연결을 바꿀 필요는 없었다. 원형 스킬·source·실험 입력·최초 응답은 수정하지 않았다.

## 요청 조건별 정적 적용 점검

Main이 수정한 지침에서 다음 요청의 자료 선택과 응답 책임을 찾아 대조했다. 새 모델 응답 생성이나 블라인드 시험이 아니며, 수행 효과의 근거로 세지 않는다.

| 대표 요청 | 지침에서 확인한 선택과 설명 책임 |
| --- | --- |
| “이번 변경으로 무엇이 좋아졌나” | 본체의 비교 주장 조건에서 작성 상세의 전후 대조로 이어진다. 현재 동작 요약만으로 새 효과를 주장하지 않고, 원래 개선 목표에 필요한 부담·결과 차이를 설명한다. |
| “저장과 갱신 구조를 코드와 함께 설명해줘” | 전체 역할·대표 사건에서 실제 판단·대기·위임·결과 부분을 고른다. 기존 여행 예시의 코드와 곁 설명을 확인했다. 코드 제시가 모든 문법 강의로 확대되지 않는다. |
| “현재 이 분리는 무엇에 도움이 되나” | 현재 구조·소비자로 이득과 제약을 설명할 수 있다. 과거보다 개선됐다고 주장할 때만 비교 자료가 필요하며 불필요한 전체 이력 조사를 요구하지 않는다. |
| “그 말이 무슨 뜻이야 / 그 근거로 왜 완료야” | 실제 발화에서 뜻과 이의를 구별한다. 짧은 뜻은 대화로 풀고, 완료 주장에는 해당 목표·결과 근거를 대조한다. 원뜻을 바꾸거나 전후 코드 조사부터 일괄 시작하지 않는다. |
| “보고서에서 뭐가 남았고 이제 무엇을 해야 하나” | 원래 질문·관찰·남은 사실이 결론과 다음 판단에 주는 영향을 연결한다. 설명의 공백과 사실 부족을 구별하며 기존 권한 안의 작업 책임을 유지한다. |

## 검증과 한계

- Ruby YAML 검사로 explain의 name·description 형식을 확인했다. 기존 quick_validate의 PyYAML 의존성 부재를 설치로 해결하지 않고 대체 검사를 사용했다.
- 열람 화면을 현재 파일에서 재생성하고 viewer 검사를 통과했다. 문서160개·코드5개, 원문/해시 일치, 누락 경로·앵커0을 확인했다. 이는 다른 세션의 현재 prototype 내용도 함께 표시한 결과이며 이번에 그 본문을 수정했다는 뜻은 아니다.
- 기존 두 본문 사본의 SHA-256이 보존된 값과 일치했다. 실행 예시의 코드 내용은 변경하지 않았다.
- 변경한 Markdown의 내부 링크와 `git diff --check`를 확인했다. 브라우저 렌더링·제품 실행·새 모델 비교는 하지 않았다.

현재까지의 응답 비교는 수정 전 판본에 관한 관찰이다.6.0 medium에서 새 스킬의 핵심 이점은 미확인,6.1 high에서는 기존판의 구현·이유 연결이 우세했다. 각1회와 모델·effort 동시 변경의 한계를 유지한다. 이번 수정의 실제 설명 효과, 자율적인 적용 시점과 운영 이식은 남아 있으며 추가 생성을 자동 반복하지 않는다. 이번 변경은 커밋하지 않았다.
