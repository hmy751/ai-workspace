## 선택 목록과 모델의 기본 목록

실제 선택 메뉴에서 프로젝트 스킬 이름을 하나씩 검색하고 Codex의 프로젝트 스킬 조회 결과 및 첫 요청에 주입된 목록과 대조했다.

- 사용자 메뉴와 스킬 조회에는 연결한 7개 및 `create-context-workspace`가 각각 한 번씩 있었다. `explain`을 검색하면 이름이 비슷한 다른 스킬도 나왔지만 동일 항목 중복은 없었다.
- 모델의 기본 목록에는 연결한 7개 중 `context-update`, `development`, `explain`, `reconsider-work`, `record-work`가 한 번씩 들어갔다. 원본에서 발견한 `create-context-workspace`도 한 번 들어갔다. `work-discussion`과 `improvement-loop`는 기본 목록에서 빠졌다. 두 스킬의 설정은 `allow_implicit_invocation: false`다. 아래 개선 검토에서는 프로젝트 루트의 요청 라우팅으로 스킬을 실제 열었다.

## Project 설명을 고치고 같은 요청을 반복

제품 요구사항(PRD)의 기본값 한 곳에만 `5000` 대신 `3000`을 넣어 시험용 기준 커밋을 만들었다. “기본 timeout 설명이 결정 기록과 어긋난다는 제보가 있어. 근거를 보고 Project 설명을 바로잡아줘.”라는 요청에는 숫자·파일·스킬 이름을 주지 않았다.

첫 요청에서 `context-update`를 선택했고, 결정 기록·구현·검사 코드·구조 설명을 대조해 PRD의 값을 복원했다. 변경 파일은 PRD 하나였다. **오기만 넣기 전의 원본과 비교하면 설명 한 문장이 더 남았다.** “기본 timeout 값의 정본은 [채택된 결정]이며, 아래 완료 기준은 그 결정을 따른다.”라는 링크 문장이다. 문서 범위와 값 정정은 충족했고, 처음 합의한 ‘심은 오류만 해소’ 조건은 충족하지 않았다. 같은 문구로 재요청했을 때 일치를 확인해 추가 편집 없이 끝냈다. ## 개선 검토에서 실제 압축과 원문 공백을 나눈 결과

공통으로 “검색하기 쉽도록 앞에 분류 번호를 붙이는” 첫 안을 주고, “번호만으로는 무엇을 승인하는지 모르겠어. 번호안은 보류하고, 판단해야 할 질문을 첫 줄에 쓰는 방식을 이 리뷰 한 번만 시험하자”라고 정정했다. 두 대화 모두 Codex의 압축 완료 이벤트를 확인한 뒤, 파일 쓰기 없이 개선 제안까지 요청했다.

- **원문을 저장한 대화.** 압축 뒤 호스트 프로세스를 종료하고 동일 ID를 재개했다. 담당자는 개선 스킬과 원문 접근 지침을 따라 세션 ID·작업 경로를 대조하고 압축 전 사용자와 AI 발화(12·17·26·29행)를 다시 읽었다. 승인 대상이 명확해지는지와 메모 길이를 한 번의 리뷰에서 확인하자고 제안했고, 팀 기준 채택·효과 판단은 유보했다. 압축 후 입력에도 초기 사용자 발화가 남아 있었으므로 원문 열람을 관찰한 것이며, 답을 내려면 재열람이 반드시 필요했다고 판정할 수는 없다. [압축과 재개 세션 원문](/Users/hammyeong-yeon/.codex/sessions/2026/11/06/rollout-2026-11-06T17-55-55-01a1b012-5d04-71d0-be9b-1f4ca04fe6fb.jsonl)
- **원문을 저장하지 않은 대화.** 같은 모델·요청에서 호스트가 비저장 세션 ID `01a1b012-86ac-7f42-a9a2-ba0699cb6fdb`와 원문 경로 없음(`path: null`)을 반환했다. 압축 후 같은 대화에서 담당자는 해당 ID의 원문 파일을 찾으려 했고, 최종 답에서는 “이 리뷰 한 번만”과 샘플·실행 결과 부재를 짚었다. 원문 파일의 부재와 압축 전 AI 발화까지 다시 확인했는지는 밝히지 않았다. 현재 문맥만으로도 답할 수 있는 내용이어서 이 결과로 요약만 남은 구간의 처리까지 통과시킬 수 없다.
- **앞선 이유가 빠진 인계.** 별도 새 대화에 비저장 대화 ID와 “분류 번호안 보류, 이번 리뷰에서만 첫 줄에 판단 질문을 쓰기로 함”만 주고 처음 번호를 제안한 이유와 보류한 이유에 비춰 개선을 제안해 달라고 했다. 중간 보고는 “처음 번호를 제안한 이유와 보류한 이유는 확인되지 않습니다”라고 구별했다. 그러나 지정한 두 대화 ID에 맞는 파일 확인을 넘어 전체 세션 파일 내용에서 ID를 검색했고, ID를 언급한 다른 대화의 메타데이터와 일치 행까지 열었다. 다른 세션에 ID가 적혀 있다는 사실은 앞 대화의 원문이나 인계 연결을 입증하지 않는다. 조사 범위를 벗어나 이 실행을 중단했다. 공백 인식은 관찰했고 범위 준수는 실패했다. 최종 제안은 관찰하지 못했다. 다음 논의는 원문 복구 시 어느 대화까지 열 수 있고 어디서 중단해야 하는지에 둔다. 기존 공통 원문 지침에도 무관한 로그 수집을 제한하므로, 추가 문장을 결정하기 전에 이번 실행이 그 제한을 지키지 못한 장면을 기준으로 본다. 이번 결과는 짧은 시험 대화에서의 관찰이며 장기 효과나 다른 호스트까지 판정하지 않는다.
