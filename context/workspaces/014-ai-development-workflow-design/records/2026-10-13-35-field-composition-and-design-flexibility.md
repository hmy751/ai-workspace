# Field의 조합 구조와 디자인 변경에 대한 유연성

2026-10-13. 01-02에서 실제 Field·React Hook Form 사용 코드를 읽고, 사용자가 의도적으로 분리한 이유를 확인했다. 코드 수정이나 새 공통 API의 채택 기록은 아니다.

## 이번 논의에서 남길 코드 기준

사용자는 합성의 유연성과 라이브러리 종속성을 포함해 이번 논의에서 자신의 코드 기준으로 남길 내용을 정리해 달라고 요청했다. Field를 의도적으로 분리한 선호는 직접 확인했고, 아래의 일반화는 그 의도·질문·자료에서 Main이 정리한 기준 후보다.

1. **디자인 변경을 사용처의 합성으로 대응할 수 있게 한다.** 공통 부품을 재사용하면서 제목·입력·설명·오류의 배치, 포함 여부, 복수 입력 구성을 사용하는 곳에서 정할 수 있게 한다. Field에서 확인한 선호다. 설계할 때는 변경마다 공통 부품에 새 옵션과 분기를 추가해야 하는지도 본다.
2. **라이브러리 의존성이 필요한 위치와 범위를 살핀다.** 폼 상태·검증은 기존 도구가 맡게 하되, 범용 Input·Field와 React Hook Form을 연결하는 코드의 책임을 구별한다. 전용 연결 부품의 도입이 범용 UI의 재사용 범위를 좁히는지 평가한다. 라이브러리 종속성을 전부 없애거나 모든 래핑을 금지한다는 뜻은 아니다.
3. **유연성은 배치와 실제 부품 교체를 함께 확인한다.** JSX 순서를 바꿀 수 있다는 설명만으로 충분하지 않다. 기존 Input·다른 입력으로 바꿨을 때 값·이벤트·ref·오류를 어떤 계약으로 연결하는지, 특정 전용 부품만 써야 하는지도 확인한다. 이는 사용자의 교체 가능성 질문에서 정리한 평가 기준이다.
4. **연결 코드를 줄일 때 그 코드가 제공하던 제어를 함께 본다.** 사용처에서 폼 도구와 UI를 연결하는 코드는 두 요소를 독립적으로 선택하게 하는 역할이 있을 수 있다. 반복·줄 수만으로 제거할 대상으로 보지 않는다. 자동 연결을 검토한다면 합성과 교체 자유도를 얼마나 유지하는지 비교한다. 명시적 연결의 무조건 선호나 자동화의 거부는 확인하지 않았다.

이 기준은 코드 예시를 검토할 판단 후보이며 글로벌 의무 규칙이나 새 폼 API의 승인으로 올리지 않는다. 합성형 화면 구조와 상태 연결을 내부에서 공유하는 방법은 함께 사용할 수 있다. 어떤 연결 방식을 채택할지는 실제 사용처와 필요한 유연성을 보고 판단한다.

정리 뒤 사용자는 “좋아 이 정도 남기고, 다음은 같은 템플릿의 무한 스크롤 코드 보면서 이어가면 될까?”라고 답했다. 위 정리를 보존하고 같은 템플릿의 무한 스크롤로 논의를 이어간다. Field 논의를 보존한 것과 01-02 전체의 완료·코드 변경을 구별한다.

## 실제 코드와 대화

`/Users/hammyeong-yeon/Desktop/20_lab/template/src/component/FormSection/Field/index.tsx`와 `src/component/FormSection/index.stories.tsx`, 연결된 Input·Select 구현을 읽었다. Field는 제목·입력 배치·라벨·설명·메시지 부품을 제공하고, story의 사용처가 React Hook Form의 register·Controller와 오류 표시를 연결한다. 이름은 입력 하나, 이메일은 입력과 선택창 두 개를 Field 하나로 구성한다.

현재 코드의 연결 예:

```tsx
<Input
  {...register("name", { required: true })}
  isError={errors?.name && "필수 항목입니다."}
/>
<Field.Message>{errors.name && "필수 항목입니다."}</Field.Message>
```

Main은 이를 사용하는 곳에서 직접 연결하는 방식과, 가상의 `RHFTextField` 안에 배치·폼 연결·오류 표시를 묶는 방식을 비교했다. 사용자에게 처음 한 질문이 명확하지 않아, 오류 테두리와 문구를 매번 연결할지 공통 부품 안에서 연결할지를 묻는 뜻으로 다시 설명했다.

## 확인한 의도와 판단 범위

Field의 분리는 디자인 변경에 대응할 확장성과 조합의 유연성을 위한 의도적인 선택이다. 공통화가 덜 된 임시 상태로 읽지 않는다. 사용처의 연결 코드가 줄어드는 편의만으로 일체형 부품을 개선이라고 판단할 수 없다.

이 사례에서 얻은 기준 후보는 **추상화가 줄이는 반복과 함께, 디자인이 바뀔 때 사용처에서 바꿀 수 있는 범위와 공통 부품을 수정해야 하는 범위를 비교한다**는 것이다. 이는 Main이 사용자 의도에서 정리한 판단 후보이며, 모든 폼 래핑을 금지하거나 어떤 중복도 허용한다는 일반 규칙을 사용자가 선택한 것은 아니다. React Hook Form 자체를 감싸는 데 대한 보편적 선호도 아직 확정하지 않았다.

이후 사례를 비교할 때는 확인한 분리 의도를 전제로 한다. 예를 들어 설명·오류의 위치 변경이나 복수 입력 배치에 각 안이 어떻게 대응하는지는 구체적으로 비교할 수 있으나, 아직 해당 변경을 구현하거나 효과를 검증하지 않았다.

## 합성형 패턴의 목적 조사

사용자는 이어 “컴포넌트의 합성형 패턴을 조사해 보면 알거야 왜 그걸 사용하나”라고 요청했다. 2026-10-13에 다음 1차 자료를 확인했다. 사용자 선호와 외부 패턴의 설계 근거를 구별한다.

- [Radix Primitives의 설계 원칙](https://github.com/radix-ui/primitives/blob/main/philosophy.md): “Composition is preferred over configuration.” 공개한 부품·DOM·이벤트를 사용처에서 조합하도록 설계한다. 확인한 판본은 공개 main 문서다.
- [Kent C. Dodds의 Compound Components 설명](https://kentcdodds.com/blog/compound-components-with-react-hooks), 2019-02-18: 협력하는 컴포넌트로 표현력과 유연성을 제공하고, 내부 상태는 Context 등으로 공유할 수 있다. [Inversion of Control](https://kentcdodds.com/blog/inversion-of-control), 2019-11-18에서는 새 요구마다 공통 코드에 옵션을 추가하며 복잡해지는 문제와 사용처에 제어를 제공하는 이유를 설명한다.
- [Adobe React Aria Components 설계 RFC](https://github.com/adobe/react-spectrum/blob/main/rfcs/2023-react-aria-components.md), 2023년 제안의 공개 main 판본: 각 요소의 스타일·배치·DOM 순서를 조합할 수 있게 하면서 Context로 부품 사이의 props를 연결한다. 필요한 부분만 교체하고 다른 부품을 재사용하는 설계도 설명한다. 설계 근거로 읽었으며 설치 버전의 런타임 검증은 아니다.

이 조사로 앞선 설명을 보완한다. 합성형 API는 공통 부품과 동작을 재사용하면서 사용처에 구성·배치·부분 확장의 결정권을 제공하는 공통화 방식이다. 사용처 코드가 길어진다는 비용뿐 아니라, 다양한 요구를 공통 컴포넌트의 옵션과 분기로 누적하지 않고 표현하는 이득을 본다.

**화면의 합성 구조와 폼 상태·오류 연결을 어디에서 처리할지는 별개의 설계 축이다.** Context 등으로 필요한 연결을 공유하면서도 합성형 API를 유지할 수 있으므로, Main이 제시한 ‘사용처에서 직접 연결 / 일체형 RHFTextField’ 두 안으로 가능성을 제한하지 않는다. 현재 Field는 표시 부품을 조합하고 React Hook Form 연결은 사용처가 맡는 구현이다. 사용자가 밝힌 디자인 변경의 유연성을 이 구조의 의도로 유지하되, Context 추가나 폼 연결의 이동을 새 요구로 올리지 않는다.

## RHF 전용 연결 부품의 종속성과 교체 자유도

Main은 후속 질문에서 가상의 `RHFField`가 상위에서 폼 상태를 공유하고 `RHFField.Input`·`RHFField.Message`가 자동 연결되는 예를 제시했다. 사용자는 다음을 물었다.

> 근데 저렇게 하면 React Hook Form에 종속되는 거 아냐? 기존 Input이나 다른 입력 컴포넌트로 바꿔도 자유롭게 조합할 수 있어?

해당 제안의 `RHFField` 계층은 React Hook Form에 종속된다. 기존 공통 Input·Field까지 종속돼야 하는 것은 아니지만, 임의의 Input으로 태그만 바꾸면 자동 연결이 유지된다고 보장할 수 없다. 제안에는 다른 입력이 값·이벤트·ref·오류를 전달받는 계약이 빠져 있었다.

기존 React Hook Form의 Controller를 사용처에서 쓰면 공통 입력을 유지하며 연결을 명시할 수 있다. 네이티브 input과 같은 계약은 field props로 연결하고, `checked`나 `onValueChange` 등 다른 계약은 사용처에서 맞춘다. 이 경우 연결 책임은 사용처에 남는다. 전용 연결 부품을 만들지, Controller로 직접 연결할지는 아직 선택하지 않았다. 이 질문을 사용자가 모든 자동 연결이나 라이브러리 래핑을 거부한 것으로 기록하지 않는다.
