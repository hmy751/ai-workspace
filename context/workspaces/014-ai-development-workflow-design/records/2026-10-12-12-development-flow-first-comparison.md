# 개발 진행의 첫 비교 — 여행 조회 복구 사례

2026-10-12. Ticket 01-01의 **첫 비교 초안이며 미채택**이다. Main은 전체 영향은 먼저 조사하고 대표 흐름에서 동작·구조를 구체화한 뒤 확장하는 안을 우선 제안한다. 이 문서는 그 제안의 근거와 비용을 보존한다. Ticket 전체 설계 완료나 사용자 선택을 뜻하지 않는다.

## 이번에 구체화하는 범위

사용자는 이전 설계를 이어가되 먼저 현재 상태와 근거에 기반한 비교안을 보여 달라고 요청했다. 시작 시 Git HEAD는 `2032d6d`, 작업 트리는 clean이었다. 지정한 재진입 문서와 01-01의 연결 근거를 읽었다. 전체 자료 재수집이나 Noline 현재 코드·앱 검증은 하지 않았다.

대표 장면은 **비활성 여행의 일정을 보다가 연결이 끊기고, 다시 online이 된 경우**다. 선택 이유는 같은 사용자 가치에 대해 과거 구현과 후속 구현의 차이가 보존돼 있고, 제품 동작·코드 구조·검증·사람의 판단을 함께 논의할 수 있기 때문이다. 시작 사례 자체도 제안이며, 모든 개발을 네트워크 복구 방식으로 일반화하지 않는다.

## 직접 근거가 말하는 것

- [9/17 개발 원문](../source/noline-evaluation/corpus/01a0ad3d-d8d0-7f33-a3fa-c9eaf01d3f30/messages.jsonl)의 `source_line` 296: “아니 리뷰는 품질때문에 독립리뷰한건 맞고 니가 검증해야지 우리 합의랑 이런걸 보고”. 312에서 AI가 적용·제외를 설명했고, 339에서 사용자가 Ticket·기록 열람을 재확인했으며, 351에서 “좋아 작업 진행시켜”라고 승인했다. 리뷰 권고를 합의와 대조하는 책임을 사람이 대신 맡길 원했다는 해석은 지지하지만, 당시 AI의 대조가 정확했다는 증명은 아니다.
- 같은 원문 970: “작업의 범위가 너무 커진것 같아 다시 되돌려놓자 … 가독성 응집도 뭐 파악쉬운 등의 spec 목표정도의 코드 퀄리티 … 계속 범위가 커질 것 같아”. 범위 부담은 직접 드러난다. 승인 부재나 특정 구현 하나를 철회의 단일 원인으로 단정하지 않는다.
- [후속 비교](../source/reading/noline-evaluation/reviews/withdrawal-followup-comparison.md)는 복구 조회 성공까지 내용을 숨겼던 안과, 정책이 허용하면 기존 캐시를 즉시 보여주고 갱신 실패를 따로 알리는 후속 안을 구별한다. 폼 보존·대상 여행 분기·sync 보호는 후속에 채택됐고, 복구 성공 알림은 제외됐다. 이번에는 이 기존 비교를 근거로 사용했으며 제품 코드를 다시 검증하지 않았다.
- [인터뷰](../source/noline-evaluation/reviews/interview-20261012.md)는 사용자가 동작 개선도 의도적으로 수용했고 철회 이유의 기억은 불확실하다고 남긴다. 또 “왜 그렇게 했는지 판단해서 설명”하기를 원하며 질문마다 바꾸라는 요구가 아니었다.
- [기존 실행 기준](../source/ai-workspace-baseline/reference-project/context/work/workspaces/spec-and-tickets/EXECUTION-CRITERIA.md)은 이미 결과에 필요한 일의 발견, 조사와 변경 권한 구분, 계약 변경의 영향 설명, 결과·품질·근거를 통한 완료 판단을 요구한다. 따라서 이번 제안은 이 기준을 새로 발견한 원칙처럼 추가하기보다 실제 진행과 판단 자료로 구체화한다.

## 같은 사례에서 비교할 진행 방식

| 방식 | 실제로 어떻게 진행하나 | 이점과 비용 |
| --- | --- | --- |
| 전체 연결을 한 번에 구현 | 조회·목록·상세·폼·Router·sync의 영향을 조사하고 관련 변경을 한 묶음으로 구현·검토한다. | 연결 누락과 반복 작업을 줄일 수 있다. 반면 공개 조건·입력 보존·sync 결과 등 서로 다른 판단을 큰 변경 안에서 함께 이해해야 한다. 계약이 이미 분명하고 변경이 강하게 결합돼 있으면 적절하다. |
| 전체 영향 조사 후 대표 흐름부터 구체화 — 우선 제안 | 전체 목표와 소비처는 먼저 펼친다. 일정 화면 복구의 동작과 상태 소유를 구체적으로 비교하고, 선택된 안을 한 흐름에서 구현·검토·확인한 뒤 목록·상세 등 관련 소비처로 확장한다. | 사람이 동작과 구조의 비용을 함께 판단할 수 있다. 확장 때 예외가 발견되면 초기 안을 고치는 비용이 있다. 대표 화면 성공을 전체 완료로 오인하지 않도록 남은 소비처와 차이를 유지해야 한다. |
| 전체 설계를 먼저 상세 확정 | 모든 화면·오류·전환과 역할 관계를 구현 전에 정리해 검토한 뒤 실행한다. | 공통 계약이 여러 영역을 강하게 묶을 때 재작업을 줄일 수 있다. 실제 구현으로 확인할 문제까지 미리 추정하고 문서를 관리하는 비용이 커진다. |

여기서 작은 흐름은 단순히 한 파일을 뜻하지 않는다. 일정 화면의 요청·표시·실패 처리가 함께 성립하는 범위다. 다른 화면과 공통 상태 때문에 분리가 불가능하면 그 연결도 첫 범위에 포함한다. 반대로 전체 조사에서 발견한 별도 개선을 모두 이번 구현으로 편입하지 않는다.

## 대표 흐름을 실제로 펼치면

**시작할 때 AI가 복원할 작업:** 여행별 접근 정책과 실제 요청 조건을 일관되게 적용하고, 이해·수정하기 쉬운 구조로 정리한다는 목표를 현재 Spec·Ticket·결정과 대조한다. 제품 정책, 조회 상태의 소유, 관련 소비처, 기존 확인 경로를 선택해 읽는다. 이번 초안은 역사 사례를 설계용으로 재구성한 것이며 Noline의 새 요구나 현행 계약을 지정하지 않는다.

**구현 전에 보여줄 차이:** 이 장면에서 연결 복구 후 무엇을 보여줄지와 그 비용을 함께 제시한다.

| 선택 | 사용자에게 보이는 결과 | 개발·확인할 책임 |
| --- | --- | --- |
| 새 조회 성공 뒤 공개 | 연결이 돌아와도 로딩을 유지하고, 실패하면 기존 내용 대신 오류를 보여준다. | 기존 캐시의 공개를 막는 조건, 복구 중 여행 이동·재단절·여러 소비자의 상태 일관성을 다뤄야 한다. 별도 상태 저장이 반드시 필요하다는 뜻은 아니다. |
| 접근 정책이 허용하면 캐시 즉시 공개 | 기존 내용이 있으면 먼저 보여주고 갱신한다. 갱신 실패는 내용을 유지하며 알리고, 기존 내용이 없으면 로딩·오류를 보여준다. | 이전 내용의 허용 범위, 최초 실패와 갱신 실패의 구분, 조회 상태 재사용을 확인해야 한다. 후속 Noline 구현이 택한 방향이다. |

이 역사 사례에서는 후자를 출발안으로 제시할 근거가 있다. 다만 과거의 선택을 새 프로젝트의 일반 규칙으로 옮기지는 않는다. 최신 조회를 보장해야만 내용을 공개할 수 있는 제품 요구가 있다면 전자의 비용을 받아들일 이유가 생긴다.

**사람에게 보여줄 판단:** 캐시가 오래됐을 수 있어도 먼저 보여줄 것인지, 최신 조회가 성공할 때까지 기다릴 것인지다. AI는 동작·구조·비용에 대한 추천을 함께 제시한다. 이미 유효한 합의가 있으면 그 근거를 사용해 진행하고 같은 결정을 다시 묻지 않는다. 사람에게 hook 이름이나 파일 분리까지 일괄 선택하게 하지 않는다.

**AI가 이어서 수행할 일:** 합의한 동작 안에서 상태 소유와 소비 연결을 설계하고 구현한다. 검토에서 나온 지적은 맡은 목표·기존 결정·현재 결과와 대조해 수정·유지·추가 확인으로 판단한다. 예를 들어 검토가 복구 성공 알림을 제안하면 실제 안내 부족과 기존 제외 이유를 확인하며, 권고라는 이유만으로 구현하지 않는다. 수정한 경우 관련 동작과 영향을 다시 확인한다. 구체적인 reviewer 배치와 품질 기준은 01-02, 검증 도구는 01-03에서 비교한다.

**첫 흐름에서 확인할 장면:** 기존 내용이 있는 복구 성공·갱신 실패, 내용 없는 최초 실패, 복구 중 여행 변경, 다시 연결이 끊긴 경우를 대조한다. 단위 검사로 입증한 범위와 실제 앱에서 관찰할 범위를 나눠 보고한다. 여기서는 필요한 확인 장면만 제안했으며 테스트를 작성·실행하지 않았다.

**나머지로 확장할 때:** 목록·상세의 여러 조회, 열린 폼, sync와 겹치는 경로를 살피고 같은 계약으로 처리되는지 확인한다. 폼의 입력 수명이나 sync 완료 의미는 조회 화면 선택만으로 결정하지 않는다. 맡은 전체 결과에 필요한 연결은 계속 책임지고, 독립적인 결과는 분리할 근거와 남은 책임을 제시한다.

**첫 보고:** 바뀐 사용자 동작, 구조가 더 읽고 바꾸기 쉬워졌다고 판단하는 구체적 이유, 실제 확인한 근거와 남은 범위를 보여준다. 예를 들어 “기존 일정은 먼저 공개하고 갱신 실패를 별도 표시한다. 공개 여부와 조회 결과를 어디서 판단하는지 한 흐름으로 확인할 수 있다”는 결과 설명에 해당 구현 근거를 붙인다. 이것은 보고 예시이며 이번에 구현·확인된 사실이 아니다. 사람이 “왜 기다리지 않나”라고 물으면 선택 이유와 비용을 먼저 설명하고 재판단 요청인지 맥락으로 구별한다.

## 다른 과제에 넘길 실제 입력과 남은 비교

02에는 공개 조건의 대안·선택 이유, 조사에서 발견한 관련 범위, 폐기한 시도와 검증 결과, 현재 남은 책임이라는 기록 사례를 넘긴다. 다음 세션에 바로 필요한 내용과 나중에 비교할 근거를 모두 포함하며, 이를 current·Spec·Ticket·records 등에 어떻게 나눌지는 아직 정하지 않는다.

03에는 여행별 제품 정책, 조회·Router·sync의 책임 관계, 화면 변경 시 따라갈 가이드, 캐시 공개 선택의 이유가 작업에 쓰이는 장면을 넘긴다. Project context를 재개용 요약으로 한정하지 않는다. 04에는 기존 작업 정의·재판단·설명 스킬이 어느 장면에서 실제로 도움이 되는지 대조할 입력을 제공한다. 05·06에서는 이 사례와 적용 결과를 선별해 개선으로 돌려주는 비용을 검토할 수 있으나, 이번에 새 수집·동기화 장치를 제안한 것은 아니다.

작은 문구 수정이나 계약이 명확한 국소 결함은 이 정도의 비교 문서와 중간 판단 없이 구현·영향 확인·보고로 끝낼 수 있다. 여러 화면이 공유하는 정책·상태 소유를 바꾸는 구조 개선은 전체 결합을 먼저 더 깊게 확인해야 한다. 이 두 대비 사례는 아직 구체적으로 펼치지 않았다.

이번에 확인한 것은 보존 원문의 승인·철회 관계와 기존 비교·인터뷰·실행 기준에 대한 초안의 정합성이다. 제안한 진행 방식이 실제로 개발 품질을 높이거나 사용자 부담을 줄이는지는 미확인이다. 후속 설계에서는 코드·구조 전후, 빠뜨린 소비처, 사람이 다시 짚어준 내용의 성격, 조사·기록·재작업 비용을 함께 볼 수 있다. 질문 수 감소만으로 효과를 판단하지 않는다.
