# 작업물 이해 브리핑 — Ticket 06 앱 시작과 네트워크 연결

이 Ticket은 앱 시작 화면 하나를 정리하는 작업에서 출발했지만, 현재 맡은 결과는 **DB·인증 준비 → 여행별 Local/Remote 접근 → 네트워크 제한·복구 → sync 시작과 세션 종료**를 사용자가 겪는 한 흐름으로 연결하는 것입니다. 2026-10-04의 저장소 snapshot(`0b3b167`)과 [Ticket 06](repository/context/work/workspaces/002-code-readability-refactoring/current/memory/tickets/06-app-startup-lifecycle.md), [Workspace 현재 상태](repository/context/work/workspaces/002-code-readability-refactoring/current/state/index.md)를 기준으로 보면 상당 부분은 구현·기록됐지만 **Ticket 06과 Workspace 002는 아직 미완료**입니다. 이 snapshot에는 `.git`과 실행 환경이 없어 문서의 커밋·검증 보고를 현재 실행 결과로 재확인하지는 못했습니다.

대표 흐름은 이렇습니다. [AppInitialization](repository/apps/client/src/application/AppInitialization.tsx)이 네트워크 관측을 시작하면서 DB 준비와 인증 기록 복원을 순서대로 기다립니다. DB 실패는 재시도 화면으로 이어지고, 인증 복원 실패는 준비 완료 후 로그인 화면에서 다룹니다. 네트워크 확정이나 sync 완료는 Splash 해제 조건이 아닙니다. 준비 뒤 [Root layout](repository/apps/client/app/_layout.tsx)이 화면·인증 후 작업·SyncProvider를 연결합니다. [Network Store](repository/apps/client/src/shared/store/network.ts)는 처음 상태를 `unknown`으로 두고, 명시적인 연결 불가 신호는 `offline`, 연결과 인터넷 도달이 모두 확인된 경우만 `online`으로 바꿉니다. 10초는 `unknown` 안내 전환 시간이며 offline 판정 시한이 아닙니다.

활성 여행의 일정·경비는 Local SQLite를 계속 쓰고, 비활성 여행의 Remote 접근은 실제 online과 인증 조건을 따릅니다. [useAppPolicy](repository/apps/client/src/shared/policy/useAppPolicy.ts)가 화면에 제한 이유를 주고, [조회 조합](repository/apps/client/src/shared/services/policy-query/useTripReadAccess.ts)은 화면 표시용 상태와 실제 요청 가능 상태를 따로 확인합니다. [Query 표시 조합](repository/apps/client/src/shared/services/policy-query/usePolicyReadQuery.ts)은 제한 중 캐시를 지우지 않고 내용을 가리며, 복귀 뒤 기존 데이터를 먼저 보여 주고 조회 실패 시에도 남은 내용을 보존합니다. Debug 강제 상태는 화면 시뮬레이션용이고 실제 Remote 요청이나 새 쓰기·sync를 허용하는 근거가 아닙니다. [SyncProvider](repository/apps/client/src/shared/services/sync/provider.tsx)는 조건이 불가에서 가능으로 바뀔 때 시작을 요청하고, 실행 시점의 차단과 중복 실행은 sync lifecycle에 맡깁니다. 이는 source로 재구성한 연결이며 이번 조사에서 앱 실행을 관찰한 것은 아닙니다.

이어갈 지점은 [state](repository/context/work/workspaces/002-code-readability-refactoring/current/state/index.md)에 명시돼 있습니다. **홈·일정/경비 목록·상세·열린 폼을 한 사용자 흐름으로 묶어** 제한 안내 중복, 기존 선택과 초안 보존, online 복귀 시 내용·오류·명시적 재시도가 자연스럽게 이어지는지 대조하고, 앱이 background에서 foreground로 돌아올 때 [Network Store의 `refresh()`](repository/apps/client/src/shared/store/network.ts)를 언제 연결할지 확인하는 것입니다. 이번 snapshot의 `apps/client/src`와 `apps/client/app`에서 `AppState` 사용이나 Store `refresh()` 호출은 찾지 못했습니다. 따라서 foreground 재확인은 문서상 남은 범위와 코드 탐색이 일치합니다. 홈은 현재 [HomeScreen](repository/apps/client/src/screens/HomeScreen/index.tsx)에서 표시용 네트워크 상태로 새 여행 버튼을 안내하고 별도 pull-to-refresh를 두므로 종합 UX를 볼 때 시작점입니다. 기존 결정대로 복구 토스트 2-C는 지금 추가하지 않습니다.

[최근 기록](repository/context/work/workspaces/002-code-readability-refactoring/records/2026-10-02-03-expense-time-decisions-and-verification.md)은 경비까지 포함한 client 자동 검사 **48 suites, 523 passed, 1 skipped**와 일부 실앱·개발 DB 확인을 보고합니다. Debug 제한 중 초안 보존과 복구 후 명시적 저장은 관찰됐지만, 실제 인터넷 단절 중 Local 저장, 일정 전체 native 작성, 새 activation 전체, 최종 UX 수락은 확인되지 않았습니다. 경비 삭제 실패 이유 유실과 상세의 특정 재시도 불일치는 사용자 결정에 따라 **보류**됐으며 다음 작업의 필수 선행으로 되살리지 않습니다. 종합 UX와 foreground 연결을 확인한 뒤 남은 검증·보류 범위를 드러내고 Ticket 종료 여부를 판단하는 순서가 맞습니다. 이번 요청에서는 조사와 설명만 했습니다.
