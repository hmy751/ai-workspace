# 작업물 이해 브리핑 — 여행 생성과 목록 책임 정리

이번 작업은 **여행 한 건을 어디에 저장할지**와 **홈의 여행 목록을 어디서 최신 상태로 만들지**를 분리한 수정이야. 새 여행은 다른 여행의 활성 여부와 관계없이 서버에 생성한다. 기존 여행의 수정·삭제는 **그 여행 자체가 오프라인 사용을 위해 활성화됐는지**에 따라 로컬 또는 서버로 간다. 반면 목록 조회는 온라인일 때 서버의 전체 목록을 확인하고, 지워서는 안 되는 로컬 변경을 보존해 홈에 돌려준다. 여기서 ‘활성’은 홈에서 선택한 여행이 아니라 오프라인 사용을 준비한 여행을 뜻해.

출발점은 도쿄 테스트 여행 삭제 실패였어. 파리 여행이 활성이라는 이유로 새 도쿄 여행은 로컬 SQLite에 생성되고 서버 전송 대기열에 들어갔는데, 도쿄 자체는 비활성이어서 삭제는 서버로 갔다. 아직 서버에 도쿄가 없어 삭제할 수 없었던 거야. 생성만 서버로 옮기는 첫 수정에서는 홈 목록이 활성 여행 존재 시 로컬 DB만 읽었기 때문에, 서버 변경 직후의 로컬 사본을 생성·수정·삭제마다 따로 갱신해야 했다. 이 사본 갱신이 실패하면 새로고침으로도 회복되지 않는다는 검토를 거쳐 **목록을 맞추는 책임을 조회 경로로 옮겼어.** 이 경위는 [결정 기록](/private/tmp/0402-trip-responsibility-20261023/r26/repository/.claude/decisions/2026-10-04-inactive-trip-creation.md)에 정리돼 있어.

| 일 | 지금 코드의 담당과 결과 |
| --- | --- |
| 새 여행 생성 | `TripDateForm`이 ID와 입력값을 만들고 `useCreateTrip` → `TripRepository.create` → `routeTripCreation` → 서버 `POST /api/trips`로 이어져. 라우터가 인증·실제 연결·쓰기 제한을 확인한다. 새 여행의 로컬 CREATE 대기 작업은 만들지 않아. |
| 기존 여행 수정·삭제 | `TripRepository.update/delete`가 `routeChildMutation`에 대상 ID를 넘겨. 활성 여행이면 로컬 변경과 `sync_queue` 기록을 같은 transaction에서 수행하고, 비활성 여행이면 서버에 요청해. 수정 요청은 서버 route에 맞게 `PATCH`에서 `PUT`으로 바꿨어. |
| 홈 목록 조회 | `useGetTrips` → `TripRepository.getAllWithSource` → `routeTripQuery`로 이어져. 온라인이고 서버 세션이 있으면 서버 목록을 받은 뒤 `refreshTripListLocal`이 로컬 목록 사본을 갱신한다. 활성 여행과 미전송 변경이 있는 여행은 덮지 않고, 서버에서 사라진 비활성 사본은 숨긴다. 홈의 `TripsSection`은 이 결과를 표시해. |
| 변경 뒤 화면 갱신 | 생성·수정·삭제 훅은 저장 성공 후 공통 `cancelAndInvalidateQueries`로 진행 중인 옛 여행 목록 조회를 취소하고 새 조회를 요청해. 이 함수는 새 조회 **완료까지 기다리지는 않아.** 저장 성공과 목록 조회 성공은 별개의 결과야. |

예를 들어 파리가 활성인 상태에서 도쿄를 만들면, 도쿄 생성은 서버에서 확정된다. 이어진 온라인 목록 조회는 서버의 도쿄를 로컬 목록에도 반영하되 파리의 로컬 원본은 보존한다. 도쿄를 수정하거나 삭제할 때도 도쿄 자체가 비활성이므로 서버를 바꾸고 목록을 다시 조회한다. 서버가 삭제한 도쿄가 새 목록에 없으면 로컬 사본도 화면에서 빠진다. 서버 목록이 비었을 때는 서버가 404가 아닌 성공한 빈 배열을 반환하도록 바꿨기 때문에, 마지막 여행을 삭제한 경우도 정상적인 빈 목록으로 처리할 수 있어. 관련 구현은 [Repository](/private/tmp/0402-trip-responsibility-20261023/r26/repository/apps/client/src/entities/trip/repository/trip-repository.ts), [Router](/private/tmp/0402-trip-responsibility-20261023/r26/repository/apps/client/src/shared/services/offline-prep/router.ts), [로컬 목록 반영](/private/tmp/0402-trip-responsibility-20261023/r26/repository/apps/client/src/entities/trip/lib/trip-local.ts), [서버 route](/private/tmp/0402-trip-responsibility-20261023/r26/repository/apps/server/src/routes/trips.ts)에 있어.

로컬 변경 보존은 단순히 `isActivated`만 보는 처리가 아니야. `refreshTripListLocal`은 여행 자체의 전송 작업뿐 아니라 일정·경비 전송 작업의 **부모 여행**도 보호한다. 대기 중·전송 중·실패한 큐 항목을 포함하며, 목록 갱신은 큐를 지우지 않아. 서버 응답이 다른 계정 것이거나 조회 도중 로그인 세션이 바뀌거나 Query가 취소됐다면 로컬 반영을 오류로 끝낸다. 서버 확인을 마친 결과는 `remote` 또는 로컬 보존분이 섞인 `mixed`로 표시하고, 연결이 없거나 서버에 닿지 못해 로컬만 쓴 결과는 `local`로 표시해. [선택 훅](/private/tmp/0402-trip-responsibility-20261023/r26/repository/apps/client/src/entities/trip/data/useTripSelection.ts)은 `remote`·`mixed`의 완료된 온라인 목록에서 선택한 여행의 삭제가 확인될 때만 다른 여행으로 선택을 옮긴다. 불완전한 로컬 목록만 보고 선택을 지우지 않으려는 조건이야.

마지막 코드 점검에서 보완한 부분도 이 책임 배치에 붙어 있어. [조회 훅](/private/tmp/0402-trip-responsibility-20261023/r26/repository/apps/client/src/entities/trip/data/useGetTrips.ts)은 실제 연결과 인증 가능 여부를 Query key에 넣어 연결 단절·복구 때 알맞은 목록을 다시 조회하고 여러 화면이 같은 요청을 공유하게 한다. 온라인으로 감지돼도 API 네트워크 오류·시간 초과·서버 5xx가 나면, 같은 세션의 활성 여행이 있을 때는 로컬 목록을 보여준다. 인증 오류, 잘못된 응답, 원인 불명의 오류까지 통신 장애로 숨기지는 않는다. 이 분류를 위해 `APIError` 타입을 HTTP 클라이언트 초기화와 분리했다. 취소 신호는 로컬 목록 반영 전후를 막는 데 쓰이며, 이미 시작된 HTTP 전송 자체가 중단된다고 보장하지는 않아.

확인 범위도 구분할게. **10월 4일 당시 HEAD `ee798e7` 위의 미커밋 변경**을 기준으로 한 코드와 기록이야. 추가 점검 뒤 클라이언트 자동 검사는 **51묶음에서 578개 통과, 1개 건너뜀**이었고, 서버 빈 목록 계약 검사와 빌드는 통과했다고 기록돼 있어. 앞선 버전의 iPhone 시뮬레이터에서는 생성·수정 후 목록 반영, 삭제 후 목록 제외와 파리 여행으로 선택 복귀를 관찰했어. 하지만 마지막의 조회 취소·연결 전환·API 장애 보완 뒤에는 시뮬레이터를 다시 확인하지 않았고, 실제 통신 단절도 재현하지 않았어. 클라이언트 전체 타입 검사는 기존 오류 7건으로 통과하지 못했으며 서버 lint도 설정 오류로 실행되지 않았어. 자동 검사에 사용한 HTTP 대역과 보존된 테스트 출력은 실제 서버·기기 전 조건의 보장이 아니야.

따라서 이 변경으로 **도쿄처럼 새 비활성 여행의 생성·조회·수정·삭제가 같은 소유 기준으로 이어지는 경로**와 그 목록 갱신 책임은 코드와 제한된 검사에서 확인됐어. 서버에서 없어진 활성 여행의 처리·충돌 해결은 이번에 결정하지 않았고, 처음 문제를 꺼내게 한 **파리 여행 날짜 표시 차이도 아직 수정하지 않았어.** Ticket 06이나 전체 리팩토링의 완료·최종 수락까지 뜻하는 작업은 아니야.
