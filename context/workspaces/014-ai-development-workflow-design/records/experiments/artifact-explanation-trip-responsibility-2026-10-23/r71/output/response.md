# 작업물 이해 브리핑 — 여행 생성·목록·삭제 흐름

이번 작업은 **새 비활성 여행은 서버에 만들고, 여행 목록은 서버의 최신 정보와 기기에 남겨야 할 변경을 조합해 보여주도록 책임을 다시 나눈 것**이야. 출발점은 내가 만든 도쿄 여행이 기기에는 있는데 서버에는 아직 없어 앱의 삭제 버튼이 실패한 일이었어. 그 생성·삭제 불일치를 고친 뒤, 목록을 로컬 사본에만 의존시키는 첫 수정안의 문제까지 다시 고쳤어. 마지막 코드 점검에서는 오래된 조회, 연결 전환, 서버 접근 실패 때의 목록 처리도 보완했어. 아래는 당시 HEAD `ee798e7` 위의 **미커밋 변경**과 그때 남은 검사·관찰 기준 설명이야. 이후 코드 상태까지 확인한 설명은 아니야.

문제의 기준을 먼저 구별하면 이해하기 쉬워. **‘활성 여행’은 지금 화면에서 선택한 여행이 아니라 오프라인 사용을 위해 준비한 여행**이야. 기존 원칙에서는 활성 여행의 데이터와 변경은 기기 SQLite가 맡고 전송 대기열(`sync_queue`)을 거쳐 서버로 보내. 비활성 여행은 서버가 맡아. 그런데 옛 생성 코드는 *다른 여행을 포함해 활성 여행이 하나라도 있는지*로 저장 위치를 골랐고, 수정·삭제는 *대상 여행이 활성인지*로 골랐어. 그래서 파리가 활성인 상태에서 만든 비활성 도쿄 여행은 로컬 CREATE 대기열에 들어갔지만, 곧바로 삭제하면 서버에 없는 도쿄를 지우려 해 실패했어. 이 재현과 두 분기의 차이는 대화 기록과 [Router](/private/tmp/0402-trip-responsibility-20261023/r71/repository/apps/client/src/shared/services/offline-prep/router.ts), [Repository](/private/tmp/0402-trip-responsibility-20261023/r71/repository/apps/client/src/entities/trip/repository/trip-repository.ts)의 변경 전후에 남아 있어.

지금 코드의 대표 흐름은 다음과 같아.

| 사건 | 판단과 실행 위치 | 목록에 반영되는 방식 |
| --- | --- | --- |
| 새 여행 생성 | 새 여행에는 아직 활성 상태가 없으므로 `routeTripCreation`이 로그인·실제 온라인·debug 쓰기 제한을 확인하고 서버 `POST /api/trips`로 보냄 | 성공한 mutation hook이 진행 중인 목록 조회를 취소하고 새 조회를 요청 |
| 기존 여행 수정·삭제 | `routeChildMutation`이 **대상 여행**의 활성 상태를 확인. 활성 여행이면 SQLite 변경과 큐 기록을 같은 transaction에서 실행하고, 비활성이면 서버 `PUT`·`DELETE` 실행 | 같은 목록 재조회 경로 사용. 서버 수정 요청은 실제 서버 route에 맞춰 `PATCH`에서 `PUT`으로 변경 |
| 온라인 목록 조회 | `routeTripQuery`가 서버 목록을 읽고 `refreshTripListLocal`에 전달 | 로컬에서 보존할 여행은 유지하고 나머지 서버 사본을 갱신한 뒤 합친 목록을 반환 |
| 오프라인·재인증 상태 또는 제한된 서버 장애 | 활성 여행이 있으면 로컬 목록을 사용 | 마지막에 보관한 목록 사본과 로컬 변경을 보여 주므로 서버의 최신 상태까지 보장하지는 않음 |

핵심 책임은 [TripRepository](/private/tmp/0402-trip-responsibility-20261023/r71/repository/apps/client/src/entities/trip/repository/trip-repository.ts)에 보이게 모였어. `create`는 서버 생성만 요청하고, `update`·`delete`는 Router가 고른 대상 저장소에서 변경을 확정해. `getAllWithSource`는 온라인에서 서버 목록을 받은 뒤 로컬 목록 반영을 호출해 `{ trips, source }`를 돌려줘. **서버 변경 직후 각각 로컬 사본을 쓰던 첫 수정안은 제거**했어. 그 방식은 사본 쓰기에 실패하면 홈 새로고침도 로컬만 다시 읽어 서버 성공 결과를 회복하지 못했거든. 이제 최신 목록을 맞추는 책임은 목록 조회에 있어. [생성·수정·삭제 훅](/private/tmp/0402-trip-responsibility-20261023/r71/repository/apps/client/src/entities/trip/data/useCreateTrip.ts)은 변경 성공 후 `cancelAndInvalidateQueries`를 호출하는 역할만 해. 이 함수는 프로젝트의 기존 공통 helper로, `cancelQueries`를 기다린 다음 `invalidateQueries`를 요청해. **새 GET의 완료까지 기다리는 함수는 아니야.** 그래서 서버 변경의 성공과 화면 갱신의 성공은 서로 다른 결과야. [helper 본문](/private/tmp/0402-trip-responsibility-20261023/r71/repository/apps/client/src/shared/lib/query-refresh.ts)에 그 순서가 그대로 있어.

목록 병합에서 중요한 예외도 있어. [로컬 목록 반영 코드](/private/tmp/0402-trip-responsibility-20261023/r71/repository/apps/client/src/entities/trip/lib/trip-local.ts)의 `protectedTripScope`는 활성 여행뿐 아니라 Trip 자체의 큐 작업, 일정·경비 큐 작업의 **부모 여행**을 보호해. 큐 상태가 PENDING이든 전송 중이든 FAILED든 해당 작업이 남아 있으면 서버 목록으로 그 여행을 덮지 않아. 예컨대 도쿄를 나중에 활성화해 로컬에서 제목을 고쳤다면, 서버의 오래된 제목이 돌아와도 그 로컬 변경이 목록에서 사라지지 않도록 한 거야. 반대로 보호 대상이 아닌 비활성 여행은 서버 값으로 사본을 갱신하고, 서버 목록에서 사라졌다면 로컬 사본을 soft delete해 숨겨. 이 목록 반영 자체는 동기화 큐를 추가·삭제하지 않아. 서버에 여행이 하나도 없는 정상 상황도 [서버 GET route](/private/tmp/0402-trip-responsibility-20261023/r71/repository/apps/server/src/routes/trips.ts)가 404 대신 성공한 빈 배열로 반환하도록 바꿨어. 그래야 ‘삭제 뒤 정말 빈 목록’과 조회 실패를 구별할 수 있어.

조회 결과의 `source`는 `local`, `remote`, `mixed`로 나눠. `mixed`는 서버 조회를 마쳤지만 활성 여행이나 큐가 남은 여행도 포함한 목록이야. [여행 선택 훅](/private/tmp/0402-trip-responsibility-20261023/r71/repository/apps/client/src/entities/trip/data/useTripSelection.ts)은 단순 로컬 목록에서 여행이 보이지 않는다는 이유로 선택을 지우지 않고, 온라인에서 서버 확인을 마친 `remote` 또는 `mixed` 목록이 실제로 선택 여행의 부재를 보여줄 때 기본 여행으로 옮겨. 당시 앱 관찰에서는 테스트 여행 삭제 후 목록에서 빠지고 선택이 기존 파리 여행으로 돌아왔어.

마지막 점검에서 붙인 보완은 조회의 **시점과 접근 가능성**에 관한 거야. [목록 Query](/private/tmp/0402-trip-responsibility-20261023/r71/repository/apps/client/src/entities/trip/data/useGetTrips.ts)는 실제 연결·인증 상태를 key에 넣어 여러 화면이 같은 조회를 공유하고, 단절·복구로 조건이 바뀌면 해당 목록을 다시 읽어. 진행 중이던 옛 조회가 저장·삭제 뒤 돌아오는 문제에는 앞서 말한 취소 helper를 사용하고, [로컬 반영](/private/tmp/0402-trip-responsibility-20261023/r71/repository/apps/client/src/entities/trip/lib/trip-local.ts)은 transaction 전후에 Query 취소 신호와 현재 로그인 세션을 확인해 늦은 결과가 사본을 덮지 않게 해. 이 신호가 서버 HTTP 요청 자체를 반드시 중단한다는 뜻은 아니야. 또 기기가 online이라고 감지했어도 API가 네트워크 오류·시간 초과·5xx로 응답하지 않으면, **같은 세션에 활성 여행이 있을 때만** 로컬 목록으로 돌아가. 인증 오류, 응답 형식 오류, 원인을 알 수 없는 오류는 숨기지 않아. Router가 HTTP 클라이언트 초기화까지 불러오지 않도록 오류 타입 `APIError`도 별도 파일로 분리했어. [Router 코드](/private/tmp/0402-trip-responsibility-20261023/r71/repository/apps/client/src/shared/services/offline-prep/router.ts)와 [오류 변환](/private/tmp/0402-trip-responsibility-20261023/r71/repository/apps/client/src/shared/api/fetcher.ts)에 조건이 드러나.

확인 수준은 나눠서 봐야 해. 앞선 버전은 시뮬레이터에서 서버 생성·수정·삭제와 홈 반영을 확인했고, 목록 조회 중심으로 바꾼 버전에서는 생성·수정 뒤 재조회와 삭제 뒤 선택 복귀를 확인했다고 당시 기록돼 있어. **마지막의 취소·연결 전환·API 장애 보완 뒤에는 시뮬레이터를 다시 돌리지 않았어.** 그 보완은 당시 자동 검사로 확인됐고, 클라이언트 결과는 **51개 suite, 578개 통과·1개 건너뜀**이야. 다만 여기 제공된 일부 변경 테스트의 본문은 없어서 그 모든 assertion을 다시 대조할 수는 없어. 서버 빈 목록 route 검사와 build는 당시 통과 보고가 있지만, 서버 lint는 설정 파일을 읽지 못해 실행 자체가 실패했어. 클라이언트 전체 타입 검사도 변경과 별개로 보고된 7개 오류 때문에 통과하지 않았어. 이 결과를 실기기 전체 동작이나 최종 수락으로 넓히면 안 돼. [당시 결정·검증 기록](/private/tmp/0402-trip-responsibility-20261023/r71/repository/.claude/decisions/2026-10-04-inactive-trip-creation.md)과 [검사 출력](/private/tmp/0402-trip-responsibility-20261023/r71/observations/3853.txt)을 기준으로 한 구분이야.

남은 경계도 있어. 통신 장애 때의 로컬 목록은 최신 서버 목록이 아니고, 서버에서 없어진 **활성 여행**을 어떻게 폐기하거나 충돌 해결할지는 이번 변경에서 결정하지 않았어. 이전 구현이 이미 남긴 미전송 CREATE도 자동으로 정리하지 않았어. 생성·수정 폼의 전체 조작, 실제 통신 단절과 마지막 보완의 실앱 확인도 남아 있어. 처음 대화의 **파리 여행 날짜 차이**는 이 생성·목록 책임 수정과 별도야. 한국 시간대 신규 여행에서는 재현되지 않았지만 기존 값의 현지/UTC 해석 차이와 여행 기간의 장기 의미는 이 작업에서 고치거나 확정하지 않았어. 이 범위가 해결한 것은 비활성 여행의 저장 위치 불일치와, 그 변경을 목록·선택에서 일관되게 읽는 경로야.
