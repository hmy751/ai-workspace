## 질문과 입력

Toast를 다음 개발자가 이해하고 변경할 수 있게 설명한다. ① 호출·상태·표시·삭제 경로 ② 기본값과 사용 계약 ③ 상태와 타이머의 수명 ④ 유지·변경 판단에 필요한 조건 ⑤ 근거와 미확인 사항을 다룬다.

원본은 `/Users/hammyeong-yeon/Desktop/20_lab/template`다. 비교 입력은 store·Toast·story 3개 파일과 로컬 UI 의존 파일, package.json·tsconfig.json을 복사한 `input/` 12개 파일이다. 전체 저장소 분석이 아니다. 동일 바이트의 경로·hash는 `../../receipts/rea-toast-20261015/input-manifest.json`에 있다. 외부 라이브러리 구현은 복사하지 않는다. 직접 조사 시 호출부 발견을 위해 원본 src에서 이름 검색을 수행했다. REA도 이 실험에서 선택한 동일 소스 범위를 분석하며 전체 앱의 완전성을 주장하지 않는다.

## 방법

1. 같은 Main이 원본 코드와 호출부를 읽고 `direct-context.md`를 작성·hash 고정한다. 이 단계에서 REA 결과는 읽지 않는다.
2. 공식 npm 배포 REA를 `/tmp`에만 준비하고 CLI를 실행한다. `setup`이나 전역 MCP·스킬 등록은 하지 않는다.
3. REA 분석·조회 결과에서 확인할 수 있는 사실과 추가 원문 해석이 필요한 부분을 구별해 `rea-context.md`에 남긴다. 도구가 보고하지 않은 사실을 도구 성과로 세지 않는다.
4. 필요한 동작 검사는 양쪽 초안 작성 후 별도 수행하고, 어느 분석이 먼저 발견했는지와 실제 검증 결과를 구별한다.
5. 사실 정확성·근거 재접근·미확인 구분·개발 판단에 쓰일 내용·준비 비용을 비교한다. 도구 JSON 크기나 관계 수를 컨텍스트 품질 점수로 바꾸지 않는다.

## 실험의 한계

- 동일 세션·동일 Main의 순차 비교다. 선행 대화와 Workspace 기록에서도 Toast 구조를 이미 접했다. 독립 또는 블라인드 A/B가 아니다.
- REA는 AI와 함께 쓰는 도구다. 완전한 무도구 AI와 REA 단독 자동 보고를 비교하지 않는다. 직접 방법에도 파일 검색·공식 API 확인을 허용한다.
- 직접 분석 초안을 먼저 고정해 사후 보완을 방지하지만 두 번째 분석의 학습 효과를 제거하지 못한다. 전체 속도·토큰 우열을 일반화하지 않는다.
- 작은 React/Zustand 사례 하나의 결과다. 대규모 코드·번들·네이티브 조사까지 일반화하지 않는다.
- 원본 코드와 기존 미커밋 변경을 보존한다. 입력 사본은 원본 실행 환경 전체를 재현한 프로젝트가 아니다.
