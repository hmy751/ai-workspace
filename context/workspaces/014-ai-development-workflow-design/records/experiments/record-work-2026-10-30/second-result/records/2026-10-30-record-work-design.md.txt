# record-work의 재사용·책임 경계·구조를 선택했다

2026-10-30, 직접 판단·수정을 맡기는 기존 선택을 구체화해 같은 대화에서 기록 담당자를 재사용하고, 기본 수정 책임을 Work에 두기로 했다. 스킬 이름은 `record-work`로 정하고 프로토타입을 먼저 수정한 뒤 Reference에 적용하도록 요청했다. 이는 [첫 논의 기록](2026-10-30-recording-responsibility.md)에서 열린 상태였던 입력·재사용·운영 방식을 이어 정한 과정이다.

## 원문 탐색의 자유와 같은 담당자의 이해를 함께 유지한다

Main은 작업·논의 후 호출, 기록 반영, 결과 회수의 흐름을 설명했다(L1030). 마무리는 전체 작업 완료 외에 오늘의 작업이나 논의 한 덩어리를 정리하는 경우도 포함하되, 그때마다 의무로 호출하지 않는 방식이다. 기록 이후 원문을 기본 입력으로 삼고 필요하면 앞선 맥락을 찾아보자는 제안에 사용자는 동의했다(L1037).

> “기본적으로는 직전 기록이후의 원문이지만 필요한 앞선 대화도 보고 그래서 서브는 한 번 호출되면 바로 없애지 않으면 좋겠어”

사용자는 한 대화에서 두세 번 쓸 수 있는데 담당자를 정리하면 다시 읽혀야 한다는 비용을 이유로 들었다. 이에 Main은 같은 담당자의 이전 이해를 재사용하면서 새 대화를 읽고 현재 문서와 대조하는 구조로 정리했다(L1042). 유지와 상시 처리는 구별한다. 호출 사이에는 계속 대화를 처리하지 않고, 이전에 읽은 문서도 다른 주체가 수정했을 수 있으므로 현재판을 확인한다.

읽은 끝과 실제 반영 범위도 구별하기로 설계했다. 일부 반영이 실패했는데 읽은 구간 전체를 처리한 것으로 넘기면 다음 호출에서 빠질 수 있기 때문이다. 진행 중 새로 생긴 대화는 다음 호출로 잇고, 재사용할 수 없는 경우에는 새 담당자가 실제 문서와 마지막 반영 범위에서 이어받는 방안을 제시했다(L1030·L1159). 세션 밖 생존을 보장하는 구현은 이 대화에서 정하지 않았다.

## 컨텍스트 수정까지 묶으려던 제안을 Work 중심으로 조정했다

Main은 작업 도중 큰 방향 변경·전환에서도 자율 호출하는 방안을 추천하고, 이미 확정된 Project·Personal 내용까지 기록 담당자가 수정하면 작업 중복을 줄일 수 있다고 제안했다(L1069). 사용자는 관련 컨텍스트 부분을 development·improvement 같은 기존 워크플로와 대조하라고 요청했다(L1076).

> “2번은 development 나 improvemnt와 같은 워크플로 확인하고 생각해봐 work 중심인건 맞고 관련 컨텍스트 부분들”

Main은 확인 후 기본 수정 책임을 넓혔던 제안을 철회하고 기존 흐름의 책임을 유지하는 쪽으로 정리했다(L1109). development는 개발 결과의 컨텍스트 영향과 필요한 반영을, improvement-loop는 사용자 요청으로 선택한 경험·체계 개선의 적용을 맡으며, 해당 Personal·Project 수정은 context-update로 연결한다. 다음 수행이 바뀐 컨텍스트에 의존한다면 그 전에 반영돼야 하므로, 모두 마무리 기록으로 넘기면 중간 작업에서 낡은 기준을 사용할 위험이 있다.

사용자는 “그래 그게 맞아보여”라고 동의했다(L1116). 기록 담당자는 관련 본문을 읽고 미반영 필요를 Work의 남은 일과 Main에게 연결한다. 같은 서브에게 컨텍스트 수정을 별도로 배정할 수는 있지만, 기록 호출만으로 관련 영역의 권한까지 넘어가지는 않는다. 협업 제안을 기록하는 일도 개인 기준 채택이나 개선 루프 자동 시작과 구별한다.

## 내용 기준을 새로 만들기보다 기존 Work 지침을 연결한다

Main이 읽을 자료·기록 깊이·완료 방식을 더 구체화하자고 제안하자(L1121), 사용자는 “지침이랑 있지 않나? 참고해서 하면 좋을것 같은데”라고 짚었다(L1128). Main은 문서 목적에 맞는 분량, 이유·조건·원문 보존, 사실·보고·해석·채택 구별, 중복과 실제 반영 확인이 기존 지침에 상당 부분 있다고 보고했다(L1147).

따라서 새 스킬은 기록 기준을 길게 다시 정의하지 않고 기존 Work 지침을 적용하도록 연결한다. 바꿀 중심은 호출, 대화 접근, 담당 유지, 담당자의 직접 수정과 확인이다. 사용자는 스킬도 연결해야 한다고 응답했고(L1154), Main은 development·improvement-loop에서 필요한 Work 기록을 이 스킬로 잇되 각 흐름의 실행 조건과 컨텍스트 반영 책임을 유지하는 안을 제시했다(L1159).

기록 담당자는 자신의 수정을 확인하고 핵심 변경·미정·실패를 반환한다. Main이 매번 전체 문서를 재검토하도록 만들지 않되, 커밋·인계나 갱신된 문서에 의존하는 다음 작업 전에는 필요한 실제 반영을 확인한다. 마지막 범위를 잇는 정보는 최소한으로 관리하며 제품의 state에 호출 이력을 누적하지 않는다. Main과 기록 담당자가 같은 문서를 동시에 수정하지 않도록 배정한다.

## 실행 본문과 상세 수행을 나누고 이름을 정했다

사용자가 구체적인 스킬 구조를 묻자 Main은 다음 구성을 제안했다(L1181). 처음에는 `maintain`이라는 이름으로 설명했으나 이후 이름이 바뀌었다.

| 구성 | 맡는 설명 |
| --- | --- |
| `SKILL.md` | Main 중심의 호출·배정·재사용·입력·반영 범위·결과 회수. 서브도 핵심 공통 계약을 확인한다. |
| `references/maintainer.md` | 담당자가 원문·현재 문서를 대조하고 필요한 기록을 직접 수정·확인·반환하는 수행. 내용·분량은 기존 지침에 연결한다. |
| `references/conversation.md` | 직전 반영 이후가 기본인 입력 범위와 과거 맥락 확장. 공통 원문 접근 방법은 한곳에서 관리한다. |
| `_background/` | 기존 비용 문제, 필요시 호출, 재사용과 Work 중심 책임을 선택한 이유·기록·근거. 설계를 재검토할 때 읽는다. |

본문은 단순 파일 목록이 아니라 핵심 책임을 설명한다. 원문 접근 방법을 공통화해도 improvement-loop의 요청된 대화 전체 검토와 기록 담당자의 직전 반영 이후 입력은 각각의 스킬이 소유한다. development·improvement-loop·Work 지침·스킬 색인에 연결하고, 별도 실행기나 상태 파일 체계를 먼저 만들지는 않는다. 실제 접근·재호출을 확인한 뒤 반복 작업을 줄일 보조 도구가 필요한지 판단한다.

이름 후보는 목적과 범위의 차이로 비교했다(L1193).

| 후보 | 비교한 이유 |
| --- | --- |
| `record-work` | 작업의 판단·과정·결과를 기록하는 목적과 자연스러운 기록 요청에 맞는다. 현재 상태 갱신도 포함한다는 설명은 필요하다. |
| `work-context-update` | 수정 범위는 정확하지만 길고 내부 구조 중심이다. |
| `maintain-work` | 기존 Maintain과 연속성은 있으나 무엇을 유지하는지 추상적이다. |
| `checkpoint-work` | 중간 정리·재개를 드러내지만 나중에 돌아볼 분석과 선택 과정까지 담기에는 좁다. |

Main은 `record-work`와 “작업 기록 담당자”를 추천했고, 사용자는 이를 받아 실행 순서를 지정했다(L1200).

> “그래 이러헥 해봐 프로토타입부터 수정하고 그 다음 레퍼런스에 적용하자”

이로써 초안을 만들고 적용할 단계로 넘어갔다. 비용 개선의 실측 결과나 프로토타입·Reference 적용 완료까지 확인한 것은 아니다. 기존 문서 중복 비교안과 Work 전체 구성은 이 선택만으로 채택·재편된 것이 아니다.

## 근거와 확인 범위

[제공 원문](../../../../../../conversation.md)의 후속 L1030~L1200을 모두 읽었고, 기존 L951~L1025와 첫 기록도 다시 대조했다. L1109·L1147의 기존 워크플로·지침 확인은 Main의 보고이며, 거기에 연결된 실제 저장소 자료를 직접 열어 검증한 것은 아니다. 이번 기록은 지정된 임시 Work의 현재 문서와 제공 스킬을 대조해 수행했다. 구현 결과나 비용 측정 자료는 입력에 포함되지 않았다.
