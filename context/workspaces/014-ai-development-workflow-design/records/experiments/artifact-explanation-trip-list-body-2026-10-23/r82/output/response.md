# 작업물 이해 브리핑 — 여행 생성·목록 조회 흐름

이번 작업은 **활성 여행이 하나 있을 때 새 비활성 여행을 만들면 삭제할 수 없던 문제**에서 시작했어. 파리가 오프라인 사용을 위해 활성화된 상태에서 도쿄를 만들자, 예전 생성 코드는 “활성 여행이 하나라도 있나?”를 보고 도쿄를 기기 DB와 전송 대기열에 넣었어. 반면 삭제는 “도쿄 자체가 활성화됐나?”를 보고 서버에 요청했지. 서버에는 아직 도쿄가 없어 삭제가 실패한 거야. 여기서 *활성*은 현재 화면에서 선택한 여행이 아니라 오프라인용으로 준비한 여행을 뜻해.

최종 변경의 기준은 **새 여행은 서버에 생성하고, 기존 여행의 수정·삭제는 대상 여행의 활성 상태로 경로를 정한다**는 거야. 활성 여행의 변경은 계속 로컬 DB와 `sync_queue`에 함께 기록하고, 비활성 여행의 변경은 서버에서 확정해. 생성·수정·삭제가 끝날 때마다 각각 로컬 목록 사본을 직접 고치는 첫 수정안은 걷어냈어. 서버에는 성공했는데 사본 갱신만 실패하면, 당시의 로컬 전용 목록 새로고침으로는 회복할 길이 없었기 때문이야. 지금은 **목록 조회가 서버 목록을 받아 로컬에서 보존할 여행과 합치는 책임**을 맡아. [Repository](/private/tmp/0402-trip-briefing-20261023/r82/repository/apps/client/src/entities/trip/repository/trip-repository.ts), [라우터](/private/tmp/0402-trip-briefing-20261023/r82/repository/apps/client/src/shared/services/offline-prep/router.ts)

대표 흐름을 파리(활성)·도쿄(비활성) 사례에 대입하면 다음과 같아.

1. 생성 화면이 ID와 여행 정보를 만들어 `useCreateTrip`에 전달해. Repository는 입력을 검증하고 `routeTripCreation`에서 계정·실제 연결·화면용 네트워크 강제 설정에 따른 쓰기 제한을 확인한 뒤 서버의 `POST /api/trips`를 호출해. 파리가 활성이라는 사실은 도쿄의 생성 위치를 바꾸지 않아. [생성 폼](/private/tmp/0402-trip-briefing-20261023/r82/repository/apps/client/src/features/trip/create-trip/TripDateForm.tsx), [생성 훅](/private/tmp/0402-trip-briefing-20261023/r82/repository/apps/client/src/entities/trip/data/useCreateTrip.ts)
2. 서버 생성 성공 후 훅은 여행 목록의 진행 중 조회를 취소하고 재조회를 요청해. 온라인·로그인 상태의 `useGetTrips`는 서버 목록을 읽고, Repository가 `refreshTripListLocal`로 SQLite의 목록 사본을 갱신해. 따라서 새 도쿄는 서버가 소유하면서 홈 목록에도 나타나. 서버 조회가 완료된 결과에 보존할 로컬 여행이 섞였으면 출처를 `mixed`로 표시해. [목록 훅](/private/tmp/0402-trip-briefing-20261023/r82/repository/apps/client/src/entities/trip/data/useGetTrips.ts), [로컬 목록 반영](/private/tmp/0402-trip-briefing-20261023/r82/repository/apps/client/src/entities/trip/lib/trip-local.ts)
3. 도쿄를 수정하거나 삭제하면 `routeChildMutation`은 **도쿄의** 활성 여부를 검사해 서버의 `PUT` 또는 `DELETE`로 보내. 앞서 드러난 클라이언트 `PATCH`와 서버 `PUT`의 불일치도 맞췄어. 성공 뒤 다시 목록을 읽으며, 서버에서 사라진 비활성 사본은 로컬 목록에서 숨겨. 화면의 `TripsSection`과 여행 선택 훅은 이 재조회 결과를 사용해. 서버 확인을 마친 `mixed` 목록에서 선택한 여행이 사라졌다면 다른 여행으로 선택을 정리할 수 있어. [API](/private/tmp/0402-trip-briefing-20261023/r82/repository/apps/client/src/entities/trip/api/trips.ts), [선택 훅](/private/tmp/0402-trip-briefing-20261023/r82/repository/apps/client/src/entities/trip/data/useTripSelection.ts), [홈 소비자](/private/tmp/0402-trip-briefing-20261023/r82/repository/apps/client/src/screens/HomeScreen/TripsSection.tsx)

목록을 합칠 때 서버 응답으로 무조건 덮어쓰지는 않아. `refreshTripListLocal`은 트랜잭션 안에서 **활성 여행과 Trip·일정·경비에 전송 대기·진행·실패 작업이 남은 여행**을 보호해. 그래서 파리의 로컬 변경이나 비활성화 후 아직 전송하지 못한 변경, 미전송 로컬 삭제가 서버 목록 때문에 되돌아오지 않도록 한다. 나머지 서버 여행을 로컬 목록 사본에 반영하고, 서버에서 사라진 비보호 사본은 soft delete한다. 계정이 바뀌었거나 조회가 취소됐으면 반영을 거절하며, 이 목록 반영 자체는 새 전송 대기 작업을 만들지 않아. 서버도 마지막 여행이 삭제된 뒤 `404` 대신 성공한 빈 배열을 반환하도록 바뀌어, 빈 목록을 정상적인 목록 결과로 처리할 수 있어. [로컬 목록 반영](/private/tmp/0402-trip-briefing-20261023/r82/repository/apps/client/src/entities/trip/lib/trip-local.ts), [서버 목록](/private/tmp/0402-trip-briefing-20261023/r82/repository/apps/server/src/routes/trips.ts)

방금 물었던 `cancelAndInvalidateQueries`의 역할은 이 연결에서 분명해. 생성·수정·삭제 또는 활성 상태 전환 직전에 시작된 **이전 목록 조회를 먼저 취소**하고, 그다음 최신 조회를 요청해. `await`는 이전 조회의 취소까지이고, 새 조회가 끝날 때까지 저장 성공을 붙잡지 않아. 조회 훅은 연결·인증 상태를 Query key에 담아 단절과 복구 때 다른 목록 조회를 사용하고, 취소 신호를 로컬 반영 전후에 확인해 늦은 결과가 사본을 되돌리지 못하게 해. 이 신호가 HTTP 전송 자체까지 반드시 끊는다는 뜻은 아니야. [갱신 함수](/private/tmp/0402-trip-briefing-20261023/r82/repository/apps/client/src/shared/lib/query-refresh.ts), [조회 훅](/private/tmp/0402-trip-briefing-20261023/r82/repository/apps/client/src/entities/trip/data/useGetTrips.ts)

연결이 없거나 재로그인이 필요한 때에는 활성 여행이 있으면 로컬 목록을 사용해. 기기가 온라인으로 감지돼도 API가 네트워크 오류·시간 초과·5xx로 응답하지 않으면 같은 세션의 활성 여행이 있을 때 로컬 목록으로 돌아가도록 보완했어. 이 로컬 목록에는 이전에 받아 둔 비활성 여행의 **기본 정보 사본**도 있을 수 있지만, 그것이 그 여행의 일정·경비까지 오프라인에서 열 수 있다는 뜻은 아니야. 인증 오류, 응답 형식 오류, 알 수 없는 오류는 통신 장애로 숨기지 않고 조회 오류로 남겨. [라우터](/private/tmp/0402-trip-briefing-20261023/r82/repository/apps/client/src/shared/services/offline-prep/router.ts), [API 오류 분류](/private/tmp/0402-trip-briefing-20261023/r82/repository/apps/client/src/shared/api/fetcher.ts)

**확인 범위도 구분해야 해.** 당시 기록에는 추가 점검에서 오래된 최초 조회, 조회 도중 단절, API 장애 때의 로컬 접근 문제를 재현해 보완했다고 남아 있어. 보존된 최종 출력은 클라이언트 **51개 묶음에서 578개 통과·1개 건너뛰기**와 변경 파일 형식 검사 통과를 보여 줘. 서버의 빈 목록 계약 검사와 빌드 통과는 당시 보고로 확인되지만 해당 검사 파일 전문은 여기 제공되지 않았어. 마지막 실앱 확인에서는 생성·수정 뒤 목록 반영, 삭제 후 목록 제외와 파리 선택 복귀를 관찰했으나, **그 확인은 뒤이은 조회 취소·연결 전환·API 장애 보완 전 버전**이야. 그 보완 후에는 자동 검사가 근거이고 실앱 재검증은 하지 않았어. 전체 클라이언트 타입 검사는 여행 변경 파일 밖의 기존 오류 7건으로 통과하지 않았고, 서버 ESLint는 설정 파일 오류로 실행되지 않았어. 당시 변경은 미커밋 상태였어. [결정·검증 기록](/private/tmp/0402-trip-briefing-20261023/r82/repository/.claude/decisions/2026-10-04-inactive-trip-creation.md), [테스트 출력](/private/tmp/0402-trip-briefing-20261023/r82/observations/3853.txt)

따라서 이번 작업으로 **도쿄 같은 새 비활성 여행의 저장 위치 불일치와 목록 갱신의 책임 배치**는 코드상 정리됐어. 다만 통신 장애 때 보이는 목록은 마지막 서버 사본이라 최신성을 보장하지 않고, 서버에서 사라진 활성 여행의 정리·충돌 해결도 이번 범위에서 결정하지 않았어. 처음 대화의 **파리 여행 기간이 홈·목록에서 하루 다르게 보인 날짜 의미 문제** 역시 별도 미해결 사항이야. 이 브리핑은 2026년 10월 4일 당시 HEAD `ee798e7`과 그 위의 미커밋 변경을 복원한 자료에 한정돼. 이후 제품 코드의 현재 상태를 확인한 설명은 아니야.
