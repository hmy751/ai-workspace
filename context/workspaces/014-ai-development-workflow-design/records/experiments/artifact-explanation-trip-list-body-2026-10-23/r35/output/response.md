# 작업물 이해 브리핑 — 여행 생성·목록·수정·삭제 흐름

이번 작업은 **파리 여행이 활성화된 상태에서 새 도쿄 여행을 만들면, 도쿄는 기기에만 저장되는데 삭제는 서버로 가서 실패하던 불일치**를 고친 것이다. 저장 위치를 여행별로 맞추면서, 홈 목록이 서버의 비활성 여행과 기기의 활성 여행을 함께 보여 주도록 조회 책임도 바꿨다. 설명 기준은 2026년 10월 4일 대화 마지막의 **`ee798e7` 이후 미커밋 변경**이다. 보존된 코드와 당시 검사 기록에 대한 설명이며, 이후 제품 상태를 확인한 것은 아니다. [당시 문제·결정](repository/.claude/decisions/2026-10-04-inactive-trip-creation.md), [변경 상태](observations/git-status.txt)

핵심 구분은 **활성화**가 지금 화면에서 선택한 여행이 아니라 오프라인 사용을 위해 기기에 준비한 여행이라는 점이다. 기존 생성 분기는 *다른 여행이라도 활성 여행이 하나 있는가*를 봤다. 그래서 새 비활성 도쿄를 로컬 DB에 만들고 `sync_queue`에 서버 전송 작업을 남겼다. 반면 수정·삭제는 *대상 도쿄가 활성인가*를 봐서 서버로 보냈다. 서버 전송 전 삭제하면 서버에 도쿄가 없어 실패했다. 이 재현과 원인 범위는 [대화 원문](conversation.txt)과 [이전·변경 코드 비교](observations/changes.diff)에 남아 있다.

변경 후 대표 흐름은 다음과 같다. 사용자가 여행 생성 폼에서 날짜를 정하고 저장하면 폼이 ID를 만들어 `useCreateTrip` → `TripRepository.create`로 보낸다. Repository는 `routeTripCreation`에서 현재 계정, 실제 온라인 연결과 화면 테스트용 강제 설정에 따른 쓰기 제한을 확인한 뒤 서버에 생성한다. **새 비활성 여행은 다른 활성 여행의 존재 때문에 로컬 생성·전송 대기 경로로 들어가지 않는다.** 수정·삭제는 기존처럼 대상 여행의 활성 여부로 갈린다. 활성 여행이면 로컬 SQLite 변경과 큐 기록을 함께 수행하고, 비활성 여행이면 서버에 보낸다. 서버 수정 요청은 실제 서버 route에 맞게 `PATCH`에서 `PUT`으로 바뀌었다. [생성 폼](repository/apps/client/src/features/trip/create-trip/TripDateForm.tsx), [Repository](repository/apps/client/src/entities/trip/repository/trip-repository.ts), [Router](repository/apps/client/src/shared/services/offline-prep/router.ts), [클라이언트 API](repository/apps/client/src/entities/trip/api/trips.ts), [서버 route](repository/apps/server/src/routes/trips.ts)

저장이 끝난 뒤 홈에 새 여행이 나타나는 과정도 바뀌었다. 첫 수정안은 생성·수정·삭제가 성공할 때마다 로컬 목록 사본을 직접 고쳤지만, 사본 갱신이 실패하면 새로고침해도 서버 결과로 회복되지 않았다. 지금은 변경 훅이 **진행 중인 이전 목록 조회를 취소하고 새 조회를 요청**한다. `cancelAndInvalidateQueries`는 이 두 React Query 동작을 묶은 기존 공통 함수이며 새 조회 완료까지 기다리지는 않는다. 목록 조회는 온라인·로그인 상태에서 서버의 전체 목록을 받고, 로컬 DB의 목록 사본을 한 트랜잭션에서 갱신한다. 활성 여행과 여행·일정·경비의 미전송 작업이 남은 부모 여행은 서버 값으로 덮지 않고, 서버에서 사라진 보호 대상이 아닌 사본은 숨긴다. 서버 목록이 비어 있어도 정상적인 빈 목록으로 처리하도록 서버의 기존 404 분기도 제거했다. 이는 변경마다 목록 반영 규칙을 붙이던 부담을 목록 조회 한곳으로 옮긴 선택이다. [조회 훅](repository/apps/client/src/entities/trip/data/useGetTrips.ts), [공통 조회 갱신](repository/apps/client/src/shared/lib/query-refresh.ts), [로컬 목록 반영](repository/apps/client/src/entities/trip/lib/trip-local.ts), [서버 목록](repository/apps/server/src/routes/trips.ts)

예를 들어 파리는 활성이고 도쿄는 비활성이라면, 도쿄 생성·수정·삭제는 서버에서 확정된다. 이후 목록 재조회에서는 파리의 로컬 원본을 보존하면서 서버의 도쿄 정보를 목록 사본에 반영한다. 도쿄를 삭제한 뒤 서버에서 확인한 목록에 도쿄가 없으면 사본에서도 숨긴다. 조회 결과는 `local`·`remote`·`mixed` 출처를 함께 전달하고, 여행 선택 훅은 실제 온라인에서 조회가 끝난 `remote` 또는 `mixed` 결과일 때에만 사라진 선택을 다른 여행으로 바꾼다. 단순히 연결이 끊기거나 로컬 목록에 없다는 이유로 선택을 지우지 않는다. [목록 결과](repository/apps/client/src/entities/trip/repository/trip-repository.ts), [선택 처리](repository/apps/client/src/entities/trip/data/useTripSelection.ts), [홈 소비처](repository/apps/client/src/screens/HomeScreen/TripsSection.tsx)

추가 코드 점검에서는 목록 조회와 변경이 겹치는 경우, 조회 중 연결이 바뀌는 경우, 기기는 온라인으로 감지하지만 API 서버가 응답하지 않는 경우를 보완했다. 조회 키에 서버 접근 가능 상태를 넣어 연결 단절·복구 시 React Query가 해당 목록을 다시 읽고 여러 홈 소비자가 같은 요청을 공유한다. 서버 네트워크 오류·시간 초과·5xx라면 현재 세션에 활성 여행이 있을 때 로컬 목록으로 돌아간다. 인증 오류, 응답 형식 오류, 원인을 분류할 수 없는 오류는 이 경로에서 숨기지 않는다. 취소 신호는 로컬 목록 반영 전후에 검사해 늦은 응답의 적용을 막지만, **실제 HTTP 요청 중단까지 보장하는 코드는 아니다.** [조회 키](repository/apps/client/src/entities/trip/data/keys.ts), [목록 조회 훅](repository/apps/client/src/entities/trip/data/useGetTrips.ts), [Router의 장애 분기](repository/apps/client/src/shared/services/offline-prep/router.ts), [로컬 반영의 세션·취소 검사](repository/apps/client/src/entities/trip/lib/trip-local.ts)

확인 범위는 나눠 봐야 한다. 당시 추가 보완 전 개발 앱에서는 새 여행의 서버 생성·수정 후 목록 반영, 삭제 후 목록 제외와 파리 선택 복귀를 관찰했다고 기록돼 있다. 이후 취소·연결 전환·API 장애 보완은 자동 검사에서 확인했고 **그 최종 판본을 시뮬레이터에서 다시 확인하지는 않았다.** 보존된 마지막 클라이언트 검사 출력은 51묶음에서 **578개 통과, 1개 건너뛰기**다. 서버 빈 목록 검사와 빌드 통과는 당시 결정 기록의 보고이며, 이 자료에는 해당 테스트 본문·실행 출력 전부가 없다. 클라이언트 전체 타입 검사는 여행 변경 파일 밖의 7개 오류로 미통과했고, 서버 lint는 설정 파일 로딩 오류로 실행되지 않았다. 포맷 검사는 통과했다. 따라서 이 결과를 전체 제품 수락이나 실제 통신 단절 검증으로 확대할 수 없다. [검증 경계 기록](repository/.claude/decisions/2026-10-04-inactive-trip-creation.md), [클라이언트 검사](observations/3853.txt), [타입 오류](observations/3870.txt), [서버 lint 오류](observations/3846.txt)

이번 작업의 범위는 여행 **저장 위치와 목록 최신성**이다. 대화 초반에 확인한 파리 여행의 홈·목록 날짜 차이는 별도의 날짜 의미·기존 데이터 문제로 남아 있으며, 이 변경이 여행 기간 값을 고친 것은 아니다. 또 통신 장애 때 제공하는 로컬 목록은 마지막 서버 정보의 사본이므로 그 순간 서버 최신 목록을 보장하지 않는다. 기존에 남은 미전송 `CREATE`의 자동 폐기나 서버에서 사라진 활성 여행의 충돌 해결도 이 변경에서 결정하지 않았다.
