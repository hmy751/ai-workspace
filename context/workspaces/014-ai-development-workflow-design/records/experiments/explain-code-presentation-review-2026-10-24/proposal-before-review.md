## 추천하는 변경 단위

현재 단일 진입점과 두 상세는 유지한다. 코드 전용 스킬·상시 reviewer·hook·고정된 설명 모드나 강제 출력 양식을 추가하지 않는다. 이번에는 본체의 실제 대상 대응·표현 선택·마무리를 한 작업으로 맞추고, 작성 상세에서 기존 사례의 보여 주는 방법을 바꾼다. 앞선 발화 상세·공통 근거 기준·development의 호출 연결은 이번 부족을 고칠 직접 위치가 아니므로 유지하는 안이다.

## 본체에 넣을 구체 문구 후보

아래는 기존 대응 문단을 교체하기 위한 후보다. 기존 문장 뒤에 모두 누적하는 추가 규칙이 아니다.

### 질문 범위의 코드 요청 연결

> 코드의 역할·구조·흐름·동작을 이해하려는 요청에는 핵심 관계가 구현된 실제 코드를 설명과 함께 제시한다. 코드 제시와 문법 해설의 깊이는 따로 정한다. 문법이 질문의 대상이 아니어도 역할·분기·대기·반환을 코드에서 따라볼 수 있게 하며, ‘코드랑 같이’라는 재요청을 기다리지 않는다. 전체 요청은 주요 부분의 협력을 잇고, 특정 대목의 후속은 이미 설명한 전체를 반복하지 않고 그 대목에 필요한 코드를 고른다.

코드가 응답에 이미 있고 한 표현의 뜻만 묻는다면 그 표현을 바로 인용하는 것으로 충분하다. 원자료가 없는 경우의 사실 확인·한계 규칙은 기존 본체를 따른다. 모든 개념 설명·보고서·사소한 완료 알림까지 코드 발췌를 요구하는 문구는 아니다.

### 핵심 주장을 실제 대상으로 보여 주기

> 핵심을 이해하는 데 필요한 코드·값·관찰을 고르고, 그 자료와 설명을 가까이 둔다. 코드에서는 설명하려는 조건과 그 조건이 허용·차단하는 동작, 보관하는 값과 뒤에서 읽거나 반환하는 지점처럼 의미가 이어지는 처리 단위를 보여 준다. 함수 전체를 복사하거나 이름·비교식 몇 개를 문장에 흩어 쓰는 것으로 대신하지 않는다.
>
> 한 표현의 뜻으로 답이 끝나면 문장 안에 그 표현을 넣는다. 여러 표현의 실행 관계가 답을 만들면 해당 관계를 볼 수 있는 코드 블록을 사용한다. 발췌는 원문을 유지하고 떨어진 대목의 연결과 생략을 표시한다. 생략 때문에 실행 조건이나 반환·오류 의미가 달라 보이지 않게 필요한 주변 처리도 설명한다. 실제 자료가 부족하면 코드처럼 보이는 예시를 만들어 현재 구현인 듯 제시하지 않는다.

핵심은 단순히 긴 코드를 블록으로 바꾸는 것이 아니다. 짧은 비교식이라도 후속 행동과의 관계가 질문의 핵심이면 그 관계를 보여 주는 쪽으로 선택한다.

### 깊이를 유지하며 읽기 쉬운 형태로 만들기

> 한 부분에서 사용자가 이해할 질문을 드러내고, 그 질문에 답하는 실제 코드·근거와 해설을 붙인다. 역할 소개·코드·처리 해설·선택 이유를 각각 답 전체에 따로 모으지 않는다. 같은 관계를 도식·표·산문으로 반복하기보다 각 표현이 맡을 일을 고른다.
>
> 실행 순서가 중요하면 단계로, 나란히 비교할 조건·책임·전후 차이는 목록이나 표로, 인과와 선택 이유는 짧은 문단으로 연결한다. 하나의 문단에서 다른 질문이나 비교로 넘어가면 의미 단위를 나눈다. 제목과 강조는 독자가 찾을 핵심과 조건을 드러내는 데 쓴다. 읽기 쉽게 만들기 위해 필요한 전제·값·실패 조건을 지우지 않는다. 작은 뜻 질문에는 이런 구성을 모두 붙이지 않는다.

목차·코드 블록·표 개수나 단어 수를 강제하지 않는다. 본체에도 실제로 짧은 문단·필요한 목록을 사용해 후보 문구 자체가 긴 서술의 덩어리가 되지 않게 편집한다.

### 마무리에서 확인할 것

> 현재 질문의 범위와 핵심 이유에 답했는지 확인한다. 코드 이해 요청이라면 독자가 원래 파일에서 핵심 조건과 후속 동작을 다시 찾아 조합하지 않아도, 제시된 코드와 해설을 함께 따라갈 수 있는지 본다. 코드가 있다는 사실만으로 충분하다고 판단하지 않는다. 여러 조건·순서·비교가 긴 문단에 섞여 있으면 의미를 유지한 채 배치를 고친다. 빠진 사실은 표현으로 메우지 않고 확인으로 돌아간다.

이는 결과에서 빠진 부분을 보완하는 판단이며 별도 채점표 출력·사용자 이해 확인 시험·매 답변 재작성·추가 reviewer 호출을 요구하지 않는다.

## 상세를 어떻게 바꿀 것인가

본체는 코드 제시가 필요한 요청과 충분성 기준을 맡고, 작성 상세는 실제 처리 단위 선택과 배치 방법을 보인다. 현재 상세의 첫 두 절을 다음 내용으로 다듬고 여행의 선택 판단·보고서 근거 책임은 유지한다.

1. 전체 역할·중심 질문을 먼저 잡되, 대표 경로만으로 전체 요청을 대신하지 않는 기존 기준을 유지한다. 역할을 파일명 목록으로 소개하는 대신 해당 코드가 맡는 결정·작업을 짚고 바로 구현을 보인다.
2. 기존 동기화 예시를 활용한다. 값 저장·재사용·반환을 실제 발췌에서 찾고 첫 호출과 뒤의 호출을 구분해 설명한다. 현재의 긴 설명 문단을 첫 호출/뒤의 호출/화면 상태와 실행 공유의 역할로 배치하되 같은 해설을 표와 산문으로 중복하지 않는다. 새 예시를 계속 추가하지 않는다.
3. 발췌와 설명의 관계를 구체화한다. 조건을 보여 줬다면 그 결과 무엇을 하거나 하지 않는지도 붙인다. 요약에서 빠진 중요 조건을 문단 밖으로 밀어 과잉 일반화하지 않는다. 설명용 예시는 관찰 결과와 구별한다.
4. 한 문법 표현의 후속은 한 표현과 짧은 해설로 끝낼 수 있음을 기존 인증 사례 안에서 대비한다. 코드 동반 요구를 모든 코드 줄·모든 문법 강의로 확대하지 않는다.

03 network와04 테스트 답을 실행 상세의 새 정답 예시로 넣지는 않는 안이다. 이번 설계 논의에서는03을 실제 부족 설명에 사용하지만, 반복 시험용 답을 스킬 안에 계속 축적하는 것을 피한다.02·05·06은 이미 상세의 예시였으므로 그 사례 재시험 성공을 일반화 근거로 삼지 않는다.

## 실제 C에 적용하면 달라질 부분 — Main의 설명용 구성

새 실행 결과나 검증된 개선 효과가 아니다. 원본 C의 핵심 포착을 유지하면서 다음 발췌를 해당 해설 가까이에 둔다. 아래는 같은 함수 내부의 서로 떨어진 두 대목이며 중간 코드와 request의 다른 속성은 생략했다.

```ts
function canApplyResult() {
  return (
    currentSession === session &&
    session.refreshRequest === request &&
    session.observationVersion === startingObservationVersion
  );
}

// … 중간 코드 및 request 객체의 다른 속성 생략 …
accept: (state) => {
  if (canApplyResult()) {
    applyObservation(session, state);
  }

  finish();
},
```

| 코드에서 확인하는 것 | 그 조건이 막는 결과 |
| --- | --- |
| 현재 세션과 요청을 시작한 세션이 같은가 | cleanup 이후 옛 세션 응답이 현재 상태를 바꾸는 것 |
| 세션이 기다리는 요청이 이 요청인가 | 시간 초과된 옛 요청이 다음 재확인의 상태를 바꾸는 것 |
| 시작할 때의 관측 번호가 지금도 같은가 | 요청 이후 listener로 받은 최신 관측을 앞선 응답이 덮는 것 |

세 조건은 AND로 묶여 모두 맞아야 accept가 상태를 반영한다. 조건이 맞지 않아 상태를 바꾸지 않더라도 finish는 호출돼 해당 대기를 끝낸다. 따라서 조건의 이름과 뜻뿐 아니라 실제 적용·종료가 코드에서 어떻게 이어지는지 함께 읽을 수 있다. 이 한 구간으로 전체 network 설명을 대체하지 않는다.

실제 C의 실패/timeout 설명에서는 fail 경로의 canApplyResult 조건도 보존해야 한다. 더 읽기 좋게 배치하면서 결과를 바꾸는 조건이 없어지면 개선으로 인정할 수 없다.

## 확인 방식과 이번 경계

리뷰어는 이 목표·원문·현행 본문·실제 응답·제안 자체를 읽고 놓친 문제와 더 나은 대안을 검토한다. 제안의 프레임과 파일 유지 선택도 기각할 수 있다. ‘적당하다’는 검증보다 어떤 문구·배치를 어떻게 바꾸면 실제 실패를 줄일 수 있는지 반환하도록 요청한다.

이번에 새 응답을 생성하지 않는다. 후속 적용을 한다면 먼저 기존 지침과 교체 후보의 중복·조건·예시·마무리를 맞춘다. 그 뒤 실제 설명 요청에서 핵심 주장과 제시 코드의 대응, 읽는 순서·조건 구별, 원자료 정확성, 불필요한 확대를 본다. 이 네 가지를 점수 합산하거나 코드 블록 개수로 대신하지 않는다. 같은03의 Main 보완 예시는 작성 시연일 뿐 스킬 효과 증거가 아니다.

전역 explain-plainly의 조항 전체·새 코드 전용 스킬·출력 lint·상시 설명 agent를 추가하는 안은 이번 근거가 지지하지 않는다. 현재 역할·권한·앞선 발화 복구 책임을 보존한다. 제안과 리뷰를 마친 뒤 사용자에게 구체 변경과 이유를 반환하며 실제 본문 적용은 별도다.
