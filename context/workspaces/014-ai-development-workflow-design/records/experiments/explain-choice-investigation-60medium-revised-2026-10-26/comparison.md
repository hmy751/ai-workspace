# 두 최초 응답의 전후 대조

2026-10-26. **2번은 판단을 가르는 구체적인 사용 조건이 생겼고, 4번은 일부 검사 본문 대조를 실제로 수행했다. 다만 2번의 대안 비용 비교와 4번의 폼 검사 근거 확인은 남았다. 두 문제의 완전 해결이나 스킬의 일반 효과를 선언하지 않는다.** Main이 원응답·읽기 기록·관련 원자료를 대조한 판단이며 사용자 평가는 아직이다.

[수정 후 원응답 모음](raw-responses.md), [수정 전 평가](../explain-four-problems-60medium-2026-10-26/assessment.md), [입력·열람·해시 확인](results.json)을 함께 볼 수 있다. 원자료·prompt·필수 입력·열람 도구는 같고 실행 스킬만 교체했다. 수정 전후 각 최초1회이며 배경·평가·기대 답을 새 수행자에게 제공하지 않았다.

## 2번 — 위치 설명 뒤 구체 조건으로 추천했지만 전체 공개의 부담은 미뤘다

수정 전은 현재 access가 내부에서만 쓰인다는 사실을 정확히 설명하고도 “제가 제안했던 계약대로 […] 반환하고 […] 열어 두는 편이 일관됩니다”로 추천했다. 폼이 필요로 한다는 조건을 실제로 확인하지 않았다.

수정 후 [원응답](case02-access/output/response.md)은 다음 조건을 든다.

> 캐시가 있어 `view`가 `ready`여도 실제 조회 정책은 막혀 `actions.canRefetch`가 `false`일 수 있습니다. 지금 반환값만으로는 폼의 특정 입력 영역이 왜 조회할 수 없는지 미리 안내하기 어렵습니다. `actions.refetch()`의 차단 결과는 눌러 본 뒤에야 알 수 있습니다.

이 관계는 제공된 `read-query.ts`에서 확인된다. 표시 정책이 허용되고 query가 성공·재조회 오류 상태면 실제 조회 정책 검사보다 먼저 ready를 반환한다. 실행 가능 여부는 access.enabled로 나오며 차단 이유는 실행 결과에서 얻을 수 있다. 따라서 ‘조건과 행동의 역할이 다르다’보다 구체적인 현재 API의 정보 차이를 판단 근거로 삼았다. 실제 폼에 해당 안내가 필수라고 입증한 것은 아니며 응답도 폼까지 검증했다고 말하지 않았다.

이번에는 작성 상세와 두 폼 발췌도 읽었다. 일부 적용의 충분성을 전체 유연성 목표로 바꾸지 않았고, 최초 답과 달리 추천을 과거 제안의 일관성만으로 닫지는 않았다. 내부 위치·일정 화면의 현재 소비·한 곳만 적용한 범위는 보존했다.

**남는 부족:** access 전체를 반환하자고 권하면서 더 좁은 공개 정보로 해결하는 선택이나 내부 정책을 노출하는 부담을 실제로 비교하지 않았다. “공개할 access 필드를 줄일지는 실제 사용처를 보고 정하면 됩니다”로 핵심 비교 일부를 이후로 미뤘다. 반환 확대 결론을 오답으로 정하지 않지만 이번에 보완하려던 ‘현재안과 의미 있는 대안의 이득·부담 비교’를 충분히 수행했다고도 볼 수 없다. 현재 응답은 **구체 근거의 부분 개선**이다.

## 4번 — 검사 제목에서 일부 본문으로 내려갔지만 조사 전체의 충분성은 남았다

수정 전에는 development·review를 읽고 코드·이미지를 실제 조사했지만, 테스트는 주로 이름 검색으로 판단했다. 수정 후 [원응답](case04-investigation/output/response.md)의 실행에서는 development와 explain 본체·verification 상세를 읽었고, `expense-recovery.test.tsx`의2~4조각을 읽었다.

Main이 해당 원문을 대조한 결과 다음 assertion이 실제로 있다.

- offline→online 복귀 뒤 캐시를 표시하고 유효한 캐시에 조회를 강제하지 않는다.
- 첫 조회 실패는 빈 결과 문구가 아니라 오류·재시도를 표시한다.
- 갱신 실패에는 기존 내용을 유지하고 버튼 재시도 뒤 새 내용을 보인다.
- 다른 여행 선택 뒤 이전 여행의 늦은 응답은 표시하지 않는다.

최종 답은 해당 검사 범위를 설명하고 Repository·네트워크 상태를 대체한 검사와 새 실앱 관찰을 구별했다. `ScheduleDetailScreen.tsx`의 지도 버튼이 콘솔 기록만 남긴다는 주장도 실제 코드와 맞는다. 다만 지도 문제는 기존 대화에도 있었으므로 새 결함 발견으로 세지 않는다. 날짜 불일치를 별도④ 보고서로 구분한 것과 보류·토스트 결정 유지도 원범위를 보존한다.

**남는 부족:** 일정 생성·경비 작성의 검사 본문까지 대조한 기록은 없고 이 부분은 여전히 이름 검색과 코드·과거 기록에 기대고 있다. picker 미확인은 기존에도 알려져 있었고, 특정 mock을 못 찾았다는 이유만으로 실패로 보지는 않는다. 핵심은 중요한 폼 관련 결론의 보장 범위를 더 구체적으로 대조할 여지가 남았다는 점이다. 최종 답의 정상 경로·코드/검사·실앱 미확인·다음 확인 구조도 이전과 상당히 비슷하다. **조사 수행에는 국소적인 개선이 있으나 최종 보고가 크게 좋아졌다고 판단할 근거는 약하다.**

시험에 앱·DB·기기·설치 환경이 없었으므로 실제 조작을 하지 않은 것은 이번 실패 조건이 아니다. 이 결과로 원래 사건의 추가 실앱 검증 책임 전체를 해결·실패 처리할 수 없다.

## 입력 보존과 절차 한계

- 두 사례 모두 필수 입력의 모든 조각 열람 기록, 입력·이미지 불변, 읽기 조각 해시, 이전 원응답 불변을 Main이 재대조했다. 원응답은 반환 뒤 수정하지 않았고 [모음](raw-responses.md)에 그대로 결합했다.
- 읽기·검색 수는 결과의 설명 자료다. 파일 수 증가나 상세 열람을 판단 품질의 점수로 사용하지 않는다.
- 4번 실행자는 선택 자료156의 HTML과 Ticket 조각을 묶은 출력에서 잘림이 있었고, 그 불완전 출력은 결론 근거로 사용하지 않았다고 보고했다. 의뢰의 잘림 재독 원칙을 모든 선택 조각에서 수행한 것은 아니므로 이 절차 한계를 남긴다. 필수 입력 완독·입력 불변 통과와 출력의 완전한 전달·이해를 동일시하지 않는다. 이 문제 때문에 답을 다시 생성하지 않았다.
- 원래 quick_validate는 PyYAML 부재로 실행하지 못했고 대체 metadata 검사·문서 링크/원문 검사를 수행했다. 이는 응답 비교와 별도의 정적 확인이다.

## 현재 결론

반영·기존 의미 대조·두 최초 수행과 보존은 완료했다. 본문은 이번 반영판으로 유지하고 이 관찰만으로 자동 재수정·추가 반복 생성은 하지 않았다. 다음 판단은 두 원응답에서 추가 근거가 사용자의 선택·이해에 도움이 되는지와, 남은 대안 비용·폼 검사 근거의 부족을 어떻게 처리할지다. 1번·3번은 이번에 다시 실행하지 않았으며 구조·권한·해당 상세의 보존을 대조했다. 일반화·운영 설치·04-02 전체 완료는 아직이다.

## 배경과 함께 본 다음 행동의 권고

사용자는 “실제 응답이랑 기존 _background까지 같이 봤을 때 이제 어떻게 하는 게 좋겠어? 또 문구 추가하고 테스트만 반복하지 말고 종합적으로 판단해봐”라고 요청했다. 아래는 Main의 후속 권고이며 운영 적용·Ticket 종료에 대한 사용자 승인이나 실제 수행 기록이 아니다.

**현재판을 유지하고 같은 사례를 이용한 문구 보완·재생성 차수는 여기서 마치는 것을 권한다.** 배경에는 상세 읽기와 전후 코드 조사를 늘려도 실제 판단·설명의 뚜렷한 향상으로 이어지지 않은 반복 관찰이 있다. 이번에는 구체적인 추천 근거와 일부 검사 본문 대조가 나타났으므로 변경을 무효로 되돌릴 근거도 약하다. 남은 누락을 매번 범용 지침의 부족으로 승격할 근거는 충분하지 않다.

평가도 응답이 맡은 역할과 실제 결정에 미치는 영향으로 좁힌다. 2번은 현재 위치와 추천 이유를 설명하는 답으로는 상당히 나아졌다. 공개 API를 최종 확정하려면 전체 상태와 필요한 정보만 공개하는 선택의 부담이 남지만, 대안 항목이 없다는 사실만으로 답 전체나 스킬을 실패 처리하지 않는다. 앞서 기록한 비교의 부족은 유지하되 그 처리 위치를 실제 설계 채택 판단으로 본다.

4번의 최종 보고가 비슷하다는 사실도 수행 개선의 부재를 뜻하지 않는다. 같은 결론을 검사 본문의 실제 확인 항목으로 더 잘 뒷받침한 것은 가치가 있다. 폼 검사 근거의 부족은 남아 있으며, 실제 업무에서 그 주장으로 수정·완료를 결정하려면 담당자가 원문 확인을 보완하거나 말할 수 있는 범위를 좁혀야 한다. 다만 이번에는 앱 조작·설치·다른 담당자 호출을 제외했으므로 개발 workflow 전체의 추가 실행·수정·재검증 책임을 평가한 결과로 확대하지 않는다.

다음 적용에서는 이미 설계한 development의 Main 판단·필요한 개선 검토·검증·수정 연결을 사용한다. 별도 설명 agent나 상시 검토 단계·새 점검표를 추가하지 않는다. 2번 같은 추천이 나오면 현재 결정에 영향을 주는 대안 차이를 Main이 판단하고, 4번 같은 근거 공백은 허용된 실제 확인·담당 연결로 닫는다. 이는 기존 기준을 수행하는 개발 작업이며, 같은 최초 답을 다시 뽑는 스킬 시험과 구별한다.

04-02에는 ‘이번 보완·제한 재시험 완료, 일반 효과와 실제 수행 연결은 미확인’을 남기고 전체 완료로 올리지 않는다. 다음 실제 작업에서 서로 다른 장면에도 같은 판단 누락이 반복되거나 실행 지침 사이의 충돌이 확인되면 그때 해당 부분을 다시 연다. 단순히 답에 항목을 더 넣을 수 있다는 이유로 재개하지 않는다. 모델·추론 수준도 이번 각1회 결과만으로 원인이나 해결책으로 확정하지 않는다. 이번 권고에 따라 새 실행 지침·시험·운영 설치를 수행하지 않았다.
