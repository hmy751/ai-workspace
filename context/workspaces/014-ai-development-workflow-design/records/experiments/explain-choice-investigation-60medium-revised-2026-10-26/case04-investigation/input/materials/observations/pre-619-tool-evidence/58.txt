## Ticket 06에서 채택한 네트워크 동작

네트워크 정책을 연결하는 변경은 기존 임시 online·null의 offline 축약을 보존하지 않고 [Ticket 06의 합의](../tickets/06-app-startup-lifecycle.md)를 기준으로 확인한다. 정상 모드에서는 활성 여행이 unknown/offline에서도 Local로 읽고 쓰며, 비활성 여행은 확인된 online에서 서버를 사용한다. 탭·여행 기본 정보·활성 상태·사용자 선택은 네트워크 변화로 자동 변경하지 않는다.

예를 들어 비활성 여행의 스케줄을 보던 중 unknown이 되면 이전 서버 응답 캐시는 남겨 두고 내용 영역에 제한 안내를 보여 준다. 수정 폼에서 저장을 누르면 Router가 전송 전에 거부하고 기존 오류 흐름이 이유를 안내하며 입력은 유지한다. 같은 여행을 계속 보고 있을 때 실제 연결이 복구되어 접근이 허용되면 기존 데이터를 먼저 표시한다. 재조회 여부는 Query의 데이터 유무·유효기간·무효화 상태에 맡기며 화면 표시를 새 조회나 sync 완료까지 기다리게 하지 않는다. 조회와 sync 갱신이 겹쳐 발생하는 추가 조회는 허용하고, 실제 변경이 화면에 반영되는지는 별도로 지킨다. 저장은 자동 실행하지 않는다. 초기 unknown은 10초 후 확인 불가 안내로 바뀔 수 있지만 상태를 임의 offline으로 바꾸지 않는다.

Debug override 중에는 화면만 강제 상태를 사용하고 요청 판단은 실제 관측을 따른다. 쓰기·queue 추가·새 sync 전송은 차단한다. 이 예외를 활성 여행의 정상 Local 쓰기 정책과 혼동하지 않는다. 세부 전환·토스트·재확인 기준과 검증 사례는 Ticket 06이 소유한다.

## Ticket 06에서 채택한 앱 준비와 선택·종료 동작

DB가 준비되기 전에는 인증 복원과 앱 화면·Provider를 시작하지 않는다. DB 준비에 실패하면 실패 안내와 재시도를 제공하며, 재시도는 저장된 여행·큐·인증 정보를 삭제하지 않는다. DB 준비 성공 뒤 세션 기록 부재는 `signed-out`, 보안 저장소 읽기·해석 실패는 `restore-failed`로 복원 시도를 마치고 로그인 화면으로 간다. 복원 실패에는 안내와 명시적 재시도를 제공하고 기존 저장값·여행·큐를 보존한다. 네트워크 확정과 서버 토큰 검증은 새 진입 선행 조건이 아니다.

예를 들어 인증 정보가 저장돼 있어도 SQLite 준비에 실패하면 재시도 화면을 보여 준다. 반대로 SQLite 준비에 성공해도 인증 저장소 읽기가 실패할 수 있으며 이때는 로그인 화면을 보여 준다. 여행이 없거나 활성 여행이 없는 것과 기기 DB·스키마의 준비 여부는 별개의 조건이다.

사용자 선택은 네트워크 변화나 불완전한 Local 목록으로 바꾸지 않는다. 성공한 Remote 목록·실제 online·조회 완료에서 기존 선택의 제거를 확인하면 다른 여행을 선택하고, 목록이 비었으면 해제한다. 로그아웃/탈퇴는 새 pending cleanup을 막고 진행 중 정리의 성공·실패 종료 뒤 로컬 세션을 비운다. 이 동작을 전체 sync나 지도 정리의 취소·데이터 보존 보장으로 확대하지 않는다. 세부 계약과 자동 검사 범위는 Ticket 06이 소유한다.

새 sync는 DB 사용 가능·로그인·세션 만료가 아닌 상태·실제 online·override 해제·세션 종료 중 아님을 함께 확인한다. 로그인·인증 복구·네트워크 복구·강제 설정 해제로 조건이 충족되면 자동 요청하고, 수동 요청도 같은 경계를 사용한다. 실행 중 동시 요청은 새 작업을 예약하지 않고 보류한다. 이미 전송한 요청을 네트워크 변화만으로 취소하지 않는다.

로그아웃/탈퇴가 기존 미동기화 확인을 통과하거나 사용자가 강제 종료를 선택하면 새 sync를 막고 실행 중 sync의 성공·실패 종료를 기다린다. 그 뒤 서버 세션을 종료하고 기존 cleanup 대기 안에서 로컬 세션을 비운다. 서버 로그아웃 실패 시 로컬 종료 진행과 서버 계정 삭제 실패 시 로컬 유지의 차이를 보존한다. 강제 종료 대기 중에도 진행 표시와 종료 버튼 비활성화를 유지한다. DB reset이 실패해 준비 상태가 해제되면 인증 정보가 남아도 새 sync를 시작하지 않는다. [선택·검사 근거](../../../records/2026-09-18-03-sync-start-and-session-teardown.md)를 함께 적용한다.

# 동작을 보존하는 코드 리팩터링

기존 제품 동작을 유지하면서 이름·조건·변환·흐름·내부 책임과 여러 소비 지점의 수정 부담을 줄일 때 읽는다. 명시적인 결함 수정이나 새 기능이 주목적이면 해당 작업의 제품 기준을 먼저 정하고, 이 가이드를 버그를 그대로 고정하는 근거로 사용하지 않는다.

## 수정 목록보다 맡을 결과를 먼저 정한다

가독성 개선은 로그 삭제나 helper 추출 같은 활동이 아니라, 어떤 이해·수정 부담을 줄이고 어떤 동작을 보존할지로 정의한다. 바텀 요소부터 시작한다는 것은 이름·조건·기본값·변환처럼 가까운 코드에서 문제를 찾는 순서이지 개선 깊이의 상한이 아니다.

함수나 파일 하나로 범위를 자동 제한하지 않는다. 같은 의미를 고치려면 함께 맞춰야 하는 consumer, 실패·상태 연결, schema와 저장 경계를 따라 필요한 범위를 확인한다. 반대로 코드가 가깝다는 이유만으로 공개 동작 변경이나 별도 결함을 포함하지 않는다. 일부만 먼저 정리한다면 그 단계가 주는 결과와 남은 수정 부담, 후속 책임을 분명히 한다.

## 보존할 계약은 관찰 가능한 관계다

입력과 반환값뿐 아니라 오류 전달, 저장 결과, 화면 변화, 부분 실패 뒤 남는 값, 부작용의 횟수와 순서, 비동기 응답의 최신성, 인증·삭제 필터도 변경에 관련되면 보존 계약에 포함한다. 모든 내부 호출 순서를 테스트로 고정하지 않고 결과를 갈라놓는 조건을 고른다.

변경 전 버그나 제품 의미가 불명확한 동작은 자동으로 정답이 아니다. 먼저 현재 결과를 재현하고, 의도된 계약·알려진 결함·열린 제품 선택을 구별한다. 결함을 고치거나 방어 동작을 새로 넣었다면 동작 보존과 의도한 변경을 따로 설명하고 검증한다.

## 티켓 흐름에서 이번 작업의 위치

Ticket 06은 앱 준비·인증을 정리한 뒤 네트워크 관측, 실제 요청, 화면 제한·복구와 작성 수명을 연결하는 단계로 이어졌다. 일정 생성에 먼저 적용한 단일 초안·기능별 제한·Places 책임 분리는 `78acff5`에 있다. 사용자는 그 결과를 유지하면서 원래 경비 오류와 정책 소비 문제로 돌아가자고 정정했다. 이번 경비 작업은 그 흐름의 후속이며, 새 경비 기능 전체나 Ticket 06 전체를 완료한 일이 아니다.

## 경비 날짜와 일정 연결을 독립적으로 선택했다

기존 경비 생성은 활성 여행의 offline 상태에서 별도 수동 폼으로 바뀌어 일정 연결이 사라졌고, 생성·수정 후보는 경비와 같은 날짜의 일정으로 좁혀졌다. 서버 데이터는 Expense의 `date`와 선택적 `scheduleId`를 별도 필드로 갖고 있었다. 연결은 경비가 어느 일정과 관련되는지를 표현하며 날짜를 일치시키는 제약으로 정하지 않았다.

> “당연히 활성 여행에서는 오프라인 일정 연결 변경할 수 있어야 하고”
>
> “일정을 연결할 수 있는건 말그대로 일정에 연결을 할거냐 안할거냐로 보면 어때?”
>
> “그럼 해당 여행의 일정을 다 보여줘야 하는건가? 이렇게 정책 정하면?” → “그래 그렇게 정하자”

채택한 동작은 다음과 같다.

- 같은 여행의 모든 날짜 일정을 날짜·시각순으로 보여 주며 일정 제목과 날짜·시각으로 구별한다. 경비 날짜 그룹에 먼저 접근하기 쉽게 하되 그 날짜로 후보를 제한하지 않는다.
- 날짜가 다른 일정에도 연결할 수 있다. 경비 날짜 변경은 기존 연결을 초기화하지 않으며 명시적인 연결 해제를 제공한다.
- 활성 여행의 Local 일정은 offline/unknown에도 선택·변경·해제할 수 있다. 비활성 여행은 offline/unknown에서 후보 조회·새 선택과 서버 저장을 제한한다.
- 이미 열린 초안의 기본 입력·기존 연결 설명·해제는 유지한다. 목록·상세의 읽기 제한과 초안의 수명을 같은 전체 화면 차단으로 합치지 않는다.
- 복구 자체로 저장하지 않는다. 사용자가 다시 실행할 때 Router가 최신 조건을 확인한다. Debug override 중에는 Local/Remote mutation과 새 sync를 모두 차단하는 기존 계약도 유지한다.

사용자는 “mode 이거 맞아? full이? 좀 똑바로 정책 확인해봐 왜 expense만 다른데”라며 정책 근거를 재확인했다. Expense의 offline active `full`은 같은 여행의 Local 일정 연결까지 가능하다는 의미다. Schedule의 `manual-only`는 외부 장소 검색 제한과 관련되므로 둘의 mode가 같아야 하는 것은 아니다. mode는 폼 전체를 교체하는 근거로 쓰지 않는다.

현재 제품 기준은 [Policy Architecture](../../../../../.claude/context/policy-architecture.md), 데이터 관계는 [Product](../../../../project/common/product.md), 선택 과정은 [경비 초안·연결 결정](../../../../../.claude/decisions/2026-10-02-expense-draft-and-schedule-association.md)이 소유한다.

## 구현의 책임과 가독성 검토

경비는 생성 폼 하나를 유지하고 별도 `ManualExpenseForm`을 제거했다. 생성·수정은 [일정 선택 영역](../../../../../apps/client/src/features/expense/expense-form/ExpenseScheduleField.tsx)과 [저장 안내 영역](../../../../../apps/client/src/features/expense/expense-form/ExpenseSubmitActions.tsx)을 공유한다. 전자는 후보 조회·접근·선택 표시를, 후자는 현재 저장 제한과 마지막 실행 실패를 표현한다. 초안 값과 submit 수명은 기존 form/hook이 소유하고 Local/Remote 선택은 Repository/Router에 남는다.

제한 중에는 전체 일정 목록을 별도 복제해 공개하지 않고 이미 선택한 일정의 설명만 해당 초안에서 유지한다. 제출은 `mutateAsync`를 기다리며 성공할 때 닫고 실패하면 입력을 남긴다. 같은 tick의 연속 저장은 ref로 막고 표시용 진행 상태는 form을 사용한다. 저장 준비 중 동기 예외와 검증 실패도 잠금을 해제한다. 오류 해석은 경비 submit에 필요한 작은 함수로 두며 정책·인증·API 오류의 이유를 보존하고 내부 schema/SQLite 진단은 일반 실패 안내로 바꾼다. 삭제 오류는 이 함수 적용 범위가 아니다.

사용자는 필요 이상 복잡한 구현과 가독성을 지적했고, 독립적인 관심사를 설명할 수 있는 최소 공유 영역으로 정리했다. 전역 오류 framework나 모든 form을 감싼 범용 abstraction을 도입하지 않았다. 기준은 이름·파일 수 자체가 아니라 초안 수명, 기능별 제한, 최종 실행 검사와 오류 표시 책임을 따라가기 쉬운가였다.

## 시간 문제는 서버 직렬화의 존재만으로 해결되지 않았다

처음 경비 수정 HTTP 함수에 추가했던 날짜 변환을 사용자가 지적하며 전체 시간 시스템과 일정까지 대조하도록 요청했다. 이어 바로 수정하지 말고 별도 reviewer가 시스템과 책임 일관성, 구체적 개선 기준을 보도록 요구했다. 경비에 먼저 적용하고 확인한 뒤 다른 시간 경계로 확장하는 순서를 채택했다.

> “경비 수정 API에 추가한 날짜 변환 코드”
>
> “이미 서버 시리얼라이즈랑 뭐 다 예전에 합의를 봤던것 같은데”
>
> “서버에서 이미 한다고 했으면서 … 여기서 왜 맞춰야 하는지”
>
> “그럼 어디서 하는게 일관성과 응집성을 생각한걸까?”
>
> “한번 경비쪽에만 적용해봐”
>
> “그래 그럼 이시간관련 작업만 커밋하고 다른 곳도 일관성 있게 적용하자”

2026-09-14의 serializer 통일은 DB row에서 API 응답을 만드는 책임을 다뤘다. 이번에 드러난 구멍은 그 앞의 form/request/Local 저장 경계였다. datetime을 보내는 폼과 date-only만 받는 수정 요청 계약은 기존부터 맞지 않았고, 서버는 요청 검증에서 거절되면 serializer까지 도달하지 않는다. HTTP 함수 한 곳의 보정도 직접 REST를 사용하는 Local sync 전송을 덮지 못한다.

사용자는 `YYYY-MM-DD`, ISO string, datetime과 UTC의 관계를 이해하기 어렵다고 반복 질문했고 `ai-self-check`를 요청했다. 설명은 형식 이름 나열에서 실제 실패 지점과 필드의 의미를 연결하는 방향으로 고쳤다. `YYYY-MM-DD`도 ISO 날짜 표현이고 timezone을 포함한 ISO datetime도 반드시 `Z` 표기인 것은 아니다. 예를 들어 `2026-10-02T01:00:00+09:00`와 `2026-10-01T16:00:00Z`는 같은 시점이다. Expense `2026-10-02`는 그 자체로 달력 날짜이므로 기기 시간대 변환으로 전날에 옮기지 않는다. 이 예시는 표현과 domain 의미의 차이를 설명하며 여행 시간대 모델을 새로 채택한 것은 아니다.

최종 배치는 다음과 같다.

| 책임 | 적용 결과 |
| --- | --- |
| 공유 날짜 계약 | Expense `date`는 유효한 `YYYY-MM-DD`. legacy offset datetime 입력은 기존 serializer와 같은 UTC 날짜로 수용한다. |
| 입력 경계 | Expense Repository가 Local/Remote 분기 전에 공통 schema를 적용하고 서버 요청도 같은 규칙을 쓴다. HTTP adapter 별도 변환은 제거한다. |
| Local 반환 | 기존 datetime 행은 date-only로 읽는다. 생성·수정 결과 검사는 transaction 안에서 실행해 실패 시 행·큐를 함께 롤백한다. 잘못된 기존 행도 교정·삭제할 수 있다. |
| 일정 시점 | 현지 날짜·시각을 구성요소로 결합하고 잘못된 날짜·DST에 존재하지 않는 시각을 거절한다. 변경하지 않은 시각은 재전송하지 않아 원래 offset·초·밀리초를 보존한다. |
| 공통 시점 검증 | timezone 형식과 실제 파싱 가능성을 함께 검사한다. Schedule·Trip 요청도 Router 전 검증을 적용한다. |
| 서버 데이터 입수 | activation·pull 전체 envelope, entity와 checkpoint를 첫 Local 쓰기 전에 검사한다. `as never[]`를 제거한다. pull 전체 원자성이나 충돌 정책을 새로 보장하지 않는다. |
| 표시·날짜 범위 | 경비는 date-only를 직접 사용하고 일정은 현지 시각으로 표시한다. 두 목록의 여행 범위는 같은 UTC 일자 순회 helper를 사용한다. |

이전에는 Expense entity 자체도 datetime이었다가 이번에 처음 날짜로 바뀐 것으로 설명하면 안 된다. entity는 이미 date-only였고 입력·저장 경계가 그 계약과 어긋나 있었다. PostgreSQL timestamp 물리 저장과 응답 serializer를 유지했고, 일괄 migration이나 과거 입력자의 의도 날짜 복원은 하지 않았다. 결제일/사용일의 명칭, Trip 날짜의 장기 domain 의미와 별도 여행 timezone 모델은 이번 확정 범위가 아니다. 현재 규칙은 [날짜와 시각](../../../../project/common/date-and-time.md), 호환 선택 이유는 [경비 날짜 결정](../../../../../.claude/decisions/2026-10-02-expense-date-boundaries.md)에 있다.

사용자는 실제 앱 확인을 medium 추론으로 요청했다. 해당 worker는 iPhone 15 Pro / iOS 26.0에서 활성 여행의 경비 날짜 생성·제목만 수정·날짜 변경 후 되돌림·실제 날짜 변경을 확인했다. Local SQLite와 큐에서 제목 수정·되돌림에는 date가 빠지는 것까지 확인했지만 당시 큐는 PENDING이었고 서버 반영은 확인하지 못했다. 이 단계의 Schedule 시간 picker는 도구 클릭 오류로 미완료였다.

이후 사용자의 “그래 확인시켜봐” 요청에 Main이 실제 앱 조작을 이어 확인했다.

- 활성 여행에서 `Expense flow 1002`, EUR 19를 작성했다. 10월 1일 경비에 9월 30일 일정 A를 연결하고 Debug offline 전환 후에도 입력이 유지됐다. 일정 B로 바꾸고 경비 날짜를 10월 2일로 바꿔도 연결이 남았다.
- Debug 상태에서 저장은 기존 override 쓰기 금지로 거절됐고 초안은 남았다. override를 해제해도 자동 저장되지 않았으며 명시적 저장 후 목록·상세에 날짜와 연결이 반영됐다. 수정 화면에서 연결 해제 후 저장 성공을 확인했다.
- 비활성 여행에서 `Expense remote 1002 recovered`, EUR 7, 2026-01-06을 작성했다. Debug unknown/offline에서 후보 선택은 제한되고 입력은 편집·보존됐다. 실제 상태로 복구 뒤 명시적 저장에 성공해 목록에 표시됐다. 이 여행에 기존 연결을 만든 상태의 제한·해제까지 실앱에서 확인한 것은 아니다.
- Main이 읽기 전용 Local SQLite에서 활성 경비의 최종 날짜 `2026-10-02`, `schedule_id=null`을 확인했다. 처음에는 CREATE와 연결 해제 UPDATE 큐가 있었고, 이후 override 해제·sync가 지난 뒤 해당 큐는 비워졌다. 개발 PostgreSQL에서 두 경비의 날짜·금액·연결 해제 결과를 직접 확인했다. 서버 날짜는 각각 `2026-10-02 00:00:00+00`, `2026-01-06 00:00:00+00`였다.

실제 인터넷을 끊지 않았으므로 Debug offline/unknown UI 검증을 실제 통신 단절 중 Local 저장 증거로 확대하지 않는다. Schedule 전체 native 작성·picker·Remote 수정·새 activation 전체도 이번 실앱 검증 범위가 아니다. 선택 일정이 없는 비활성 초안으로 확인했으므로 제한 중 기존 연결 설명·해제의 실앱 관찰은 남고 자동 검사가 근거다.

조작 도구의 `noWindowsAvailable`은 앱 결함과 구별한다. 중간 재연결·세션 초기화만으로 해결되지 않았지만 Simulator의 Window → Bring All to Front 이후 클릭이 복구돼 검증을 계속했다. 최종적으로 override는 해제했고 앱·서버·Metro는 켜둔 상태였다. 테스트 경비 두 건은 삭제하지 않았으며 다음 실행의 현재 상태는 다시 확인한다.
