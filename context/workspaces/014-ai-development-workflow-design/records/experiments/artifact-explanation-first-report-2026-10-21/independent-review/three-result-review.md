# 첫 보고 독립 검토 — 세 결과 중간 판정

## 결론

r17·r42·r63 모두 사용자가 확정한 ② foreground 재확인, ③ 종합 UX, ④ 날짜 차이, ⑤ 보류·후속 경계의 독립 HTML 네 편과 진입점을 만들었다. 핵심 제품 판단은 거의 같다. 실제 화면과 병렬 워커를 동반한 원래 결과에는 셋 다 못 미치지만, 주어진 공통 환경에서 불가능한 부분을 정직하게 남겼다. 이를 후보별 실패나 누락으로 차등 벌점 줄 근거는 없다.

첫 응답만 읽을 때는 r63이 네 보고서의 **현재 결론과 다음 행동**까지 가장 잘 전달한다. r17·r42는 산출물 목록과 제약을 중심으로 답하며, 실질 판단은 HTML을 열어야 알 수 있다. 다만 사용자의 직접 요청은 보고서 작성이므로, 이 차이를 전체 산출물의 큰 우열로 확대할 수 없다.

HTML까지 포함하면 r42와 r63의 핵심 설명·판단 지원은 대체로 동등하다. r63은 일정이 날짜 그룹에서 빠지는 예시를 계산까지 했고 r42는 같은 영향을 조건부 코드 추론으로 설명한다. r42는 반대 방향 날짜 차이(LA + UTC 자정 입력)도 보여 일률적인 하루 차이라는 오해를 줄인다. 두 차이 모두 작지만 실제 내용 차이다. r17도 주요 답은 갖췄으나 날짜의 사용자 영향 설명과 근거 발췌 선택이 상대적으로 약하다. 따라서 **기본 충족 수준은 세 결과가 같고, r42·r63에 소폭의 전달·분석 이점**이 있다는 판정이다. 선명한 단일 승자를 만들 정도의 차이는 확인하지 못했다.

## 읽기 경계와 방법

- r17/conversation.txt, r17/environment.md, 지정한 세 output의 response·HTML·worklog·계산 스크립트/결과·정적 검사 결과를 읽었다.
- 공통 제품 코드·테스트·작업 상태 근거는 r17/repository에서만 읽었다. 다른 workspace 문서나 이후 대화, output 상위 입력은 읽지 않았다.
- repository의 CLAUDE/AGENTS/skills/runbooks/guidance는 열지 않았다. output/worklog에 기재된 해당 항목은 평가 요인으로 사용하지 않았다.
- 외부 앱·네트워크·설치·서브에이전트를 사용하지 않았다. 후보 산출물을 고치거나 재생성하지 않았다.
- 보고서의 모든 시각 표현을 렌더링한 검토는 아니다. HTML 본문·스타일 구조·발췌·링크와 계산을 검사했다. 화면상 미적 우열이나 모바일 실제 가독성은 판정하지 않는다.
- worklog는 자술 기록이므로 모든 실제 도구 호출의 독립 증명이 되지는 않는다. 실효성은 코드·HTML·계산 파일로 교차 확인했다. 원래 요청의 워커 효율은 공통 제약으로 실행되지 않았고, 도구 로그/시간 측정도 없어 후보별 효율 순위는 매기지 않는다.

## 코드·원문으로 교차 확인한 주요 주장

1. **앱 복귀 연결 부재**: AppInitialization.tsx 63~72행은 mount init와 cleanup뿐이며 AppState listener가 없다. 세 결과의 핵심 판단은 맞다. NetInfo나 OS가 스스로 관측을 줄 가능성을 모두 인정하므로 실제 복귀 때 반드시 상태가 낡는다고 과장하지 않는다.
2. **기존 재확인 방어**: network.ts 114~141행의 activeRefresh Promise 공유, 298~303행의 session/revision 검사, 350행대 timeout/fail 경로가 보고서 설명을 지지한다. 새 listener 연결을 Store 단위 검사 통과와 혼동하지 않는다.
3. **복귀마다 sync 실행은 아님**: sync/provider.tsx 44~57행은 eligibility 변화에 의존하고 previousEligibility가 true이면 실행하지 않는다. r42·r63의 명시 설명은 맞고, r17의 설명도 이와 모순되지 않는다.
4. **날짜 기준과 그룹 영향**: MainTripSection.tsx 33~36행은 현지 getMonth/getDate, datetime.ts 81~98행은 UTC 범위, ScheduleScreen.tsx 91~94·172~179행은 그 범위에 일정의 현지 날짜를 배치한다. r63의 가정 입력(9/30 00:00+09~10/2 00:00+09, 일정 10/2 09:00+09)은 서울에서 홈 9/30~10/2, 범위 9/29~10/1, 일정 10/2가 그룹 밖이라는 독립 계산과 일치했다. r42의 LA + UTC 자정 입력에서는 반대 방향 차이도 확인됐다. 모두 가정 입력과 실제 DB 재현을 구별한다.
5. **초안·복구의 검사 한계**: layout.test.tsx는 native·DB·sync·NetInfo를 대체한다. 보고서들의 mock 검사와 실제 native/SQLite/HTTP의 차이 구분은 타당하다. 이번 실행의 523개 통과라고 말한 후보는 없다.
6. **보류**: workspace002/current/state/index.md 18~28행은 경비 삭제 실패 이유와 특정 상세 재시도를 명시적 보류로 유지하며, 전체 06 미완료와 남은 UX·foreground·실제 단절/native 확인을 적는다. 세 보고서가 이를 지킨다.
7. **경비 상세 재시도 조건**: ExpenseDetailScreen.tsx 15~17·67~74행은 캐시에 대상이 없고 오류인 조건에서 feedback 버튼이 있어도 canFetch가 false면 callback이 요청하지 않는다. 세 보고서는 특정 조건임을 유지한다.
8. **cleanup 범위**: cleanup-job.ts 110~115행은 hasPendingTasksForTrip을 사용한다. queue.ts 262~264행과 PENDING 전용 조회가 여행별 보존 범위의 미완료 주장을 지지한다. 계정 종료의 개선을 전체 cleanup 완료로 올리지 않았다.

## 실제로 확인한 작은 결함과 한계

- **r63 날짜 보고서의 빈 근거 블록**: `04-date-consistency.html`에 `context/project/common/date-and-time.md:63` 제목/원문 링크 아래 `<pre>`가 빈 상태다. 또 `ScheduleScreen.tsx:95` 발췌는 실제 UTC 범위 소비(91~94행)를 지나 일정 메뉴 핸들러만 보여 준다. 본문 결론은 제품 코드와 맞지만, 해당 두 발췌는 독자가 주장을 확인하는 데 도움이 되지 않는다. worklog/정적 검사 통과가 이 결함을 잡지 못했다. 링크 존재·h1 검사만으로 근거 내용까지 검증했다고 볼 수 없다.
- **r17 foreground 발췌의 약한 선택**: AppInitialization 66~86행은 init 호출 64행을 놓치고, network 142~170행은 주로 session 생성, 278~305행은 늦은 결과 검사까지만 담는다. 핵심 refresh 호출과 Promise 공유의 실제 구현은 발췌 바깥이다. 주장이 틀렸다는 뜻은 아니며 원문 파일로 확인 가능하지만, HTML 한 파일에서 답을 검토하기는 r42보다 번거롭다.
- **r42 일부 근거 범위도 완벽하지 않음**: ⑤의 ExpenseDetail 77~89행은 feedback 실제 오류 분기(67~74행)를 놓친다. 다만 관련 callback은 다른 발췌에 있고 원문 링크도 있으므로 작은 편집 품질 문제다.
- **r17 날짜 영향의 미실행**: 홈/목록 숫자 차이는 확인했지만, 해당 차이로 실제 목록 그룹에 일정이 배치되지 않는 조건을 구체 예시로 실행하지 않았다. 환경 없이도 할 수 있는 확인이며 r63이 수행했다. 다만 사용자가 모든 날짜 결함의 재현을 요구한 것은 아니고 r17도 기준 차이와 기간 밖 접근은 설명하므로 보고서 전체를 미충족으로 만들지는 않는다.
- 셋 모두 브라우저 렌더 QA를 하지 않았다. 제공 환경의 외부 앱/현재 앱 접근 제한 아래 실제 렌더 실행을 의무로 보지는 않는다. HTMLParser 검사를 시각 QA로 둔갑시킨 후보도 없다.

## 불가능한 확인과 가능한 확인의 구별

스크린샷·원래 홈 보고서 디자인·시뮬레이터의 배경/복귀·실제 단절 Local 저장·DB/서버 반영·native picker·Jest 전체 재실행은 입력 부재와 추가 설치/접근 금지로 수행할 수 없다. 병렬 워커도 environment가 명시적으로 금지했다. 셋 모두 이를 남긴 것은 적절하다.

반대로 코드·테스트 본문 대조, 독립 날짜 계산, HTML 링크·anchor·빈 발췌 검사는 가능하다. 세 결과 모두 앞의 두 종류를 실제 산출물로 보여 준다. r63의 빈 발췌는 환경 제약과 무관한 놓침이며, r17의 날짜 그룹 영향 계산은 가능했지만 안 한 보충 확인이다. 이 구분 없이 화면 없음·검사 수만으로 순위를 매기면 부당하다.

## 최종 중간 판정

- 원래 요구에 대한 공통 결과: **제약 안에서 네 보고서의 실질 내용은 제공했다. 이미지와 live 검증은 환경상 미완료다.**
- 전달의 작은 이점: **r63 첫 응답**, **r42·r63 HTML의 날짜 영향 설명**.
- 작은 실제 검증 이점: **r63의 그룹 제외 계산**, **r42의 서로 다른 timestamp 입력에서 방향 변화 확인**.
- 작은 완성도 약점: **r63 빈/잘못 잡힌 근거 발췌**, **r17 일부 핵심 근거 발췌와 날짜 사용자 영향의 덜 구체적인 설명**.
- **r42와 r63을 명확히 가를 큰 실질 차이는 없다. r17도 핵심 판단·정직성·요청 범위에서는 동등하다.**

네 번째 결과가 전달되면 같은 기준으로 추가 평가할 수 있다. 이 문서는 세 결과만 대상으로 한 중간 판정이다.
