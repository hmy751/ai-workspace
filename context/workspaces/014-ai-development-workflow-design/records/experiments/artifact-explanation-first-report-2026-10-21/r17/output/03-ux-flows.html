무엇을 실제로 확인했는가

화면 조회 조합의 구현과 관련 테스트 본문을 직접 대조했습니다. useTripReadAccess는 표시 정책과 실제 관측 정책을 함께 적용하며, refetch callback은 최신 commit의 접근 조건을 다시 확인합니다. UI 제한으로 Query 캐시를 삭제하거나 별도 데이터 복제본을 만드는 구조가 아닙니다.

테스트는 네트워크·DB·Repository·native Drawer 등의 일부를 대체합니다. 실제 입력 흐름을 쓰는 검사도 iOS picker·키보드·HTTP·SQLite의 실제 작동을 모두 보장하지 않습니다.

효율적인 후속 수집 순서

  1. 비활성 여행 한 개를 online에서 열고 목록·상세를 기준 수집합니다.
  2. 같은 여행·탭에서 offline→unknown 확인 중→확인 불가→online으로 전환하며 선택·내용·안내를 수집합니다. 모든 화면에서 같은 초기 상태를 반복 준비하지 않습니다.
  3. 작성 초안 하나에 기존 일정 연결을 두고 제한·복구·명시적 저장을 수집합니다. 일정 폼은 취소·picker·키보드만 별도 보충합니다.
  4. 실제 통신 단절과 서버 실패는 Debug 전환과 나누어 실행합니다. 계정 종료·여행 해제처럼 데이터에 영향을 주는 조작은 수집을 위해 임의 수행하지 않습니다.

실행 환경이 확보되면 화면 조작은 한 수집 담당이 독점하고 관찰값·문구·캡처만 먼저 반환하는 방식이 적절합니다. 이번 환경에서는 추가 워커·시뮬레이터를 실행하지 않았습니다.

스크린샷과 다음 수집

이번 보고서에는 앱 스크린샷이 없습니다.
기존 HTML·캡처·시뮬레이터가 입력에 포함되지 않았습니다. 대화 속 관찰은 이전 보고로만 인용하며, 코드 발췌나 설명용 예제를 실제 화면으로 대체하지 않았습니다.
  1. 목록·상세 각각 정상/제한/복구 비교 캡처. 최초 조회 실패는 기존 데이터가 없는 조건과 구분.
