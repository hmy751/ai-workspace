# ③ 목록·상세·폼 종합 UX 검토

**현재 판단:** 정상 연결 상태에서 일정 목록 → 일정 상세 → 연결 경비 상세 → 경비 작성 진입은 화면으로 확인됐다. 제한·복구·조회 실패·저장 실패를 한 사용 흐름으로 이어 본 증거는 아직 부족하다. 따라서 06번의 이 항목은 **정상 경로 확인, 제한·복구의 코드·자동 검사 확인, 실제 화면 전환 미확인**으로 나누어 관리해야 한다. 이번 검토에서 제품 결함을 새로 재현한 것은 아니다.

## 코드·검사가 뒷받침하는 부분

- 일정·경비 목록은 조회 조합이 `blocked`·`loading`·`error`·`ready`를 나눠 표시한다. 첫 조회 실패는 빈 항목 안내로 바꾸지 않고 다시 불러오기 버튼을 준다. 기존 결과의 갱신 실패는 내용과 별도의 작은 안내를 함께 보여 준다. 일정·경비 상세도 같은 구분을 사용한다. 조회가 제한될 때 캐시를 삭제하는 대신 내용을 가리는 구조다. 근거: `ScheduleScreen.tsx`, `ExpensesScreen.tsx`, `ScheduleDetailScreen.tsx`, `ExpenseDetailScreen.tsx`, `usePolicyReadQuery.ts`.
- 일정 목록의 수정 Drawer는 목록 내용이 가려져도 화면에 장착된 채 남는다. 화면 검사는 미저장 제목·날짜, 제한·복귀, 조회 실패·갱신 뒤 값 유지를 다룬다. 일정 생성 화면은 현재 검색과 폼을 한 단계 상태로 교체하고, 연결 변화만으로 단계를 바꾸지 않는다. 이전 보고서의 ‘수동 폼 숨김’과 ‘일반·수동 폼 동시 표시’는 현재 코드와 회귀 검사상 수정됐다. 근거: `ScheduleScreen.tsx`, `CreateScheduleScreen.tsx`, `schedule-recovery.test.tsx`, `create-schedule-flow.test.tsx`.
- 경비 생성 검사에는 비활성 여행의 unknown에서 초안·일정 연결 유지, 저장 차단, online 복구 뒤 사용자가 다시 눌러 저장하는 경로가 있다. 활성 offline의 Local 저장과 날짜·일정 연결의 독립성도 검사한다. 기존 티켓 기록에는 Debug 전환 중 경비 초안 보존·복구 후 명시적 저장·서버 반영의 실앱 관찰이 있다. 근거: `create-expense-flow.test.tsx`, `06-app-startup-lifecycle.md`.

이 근거는 구현과 자동 검사 범위를 말한다. 이번 환경에는 DB·시뮬레이터·설치된 의존성이 없어 검사를 재실행하거나 실제 제한·복구를 새로 조작하지 못했다. 과거 기록의 `48 suites / 523 passed / 1 skipped`도 **당시 실행 결과**이지 이번 확인 결과가 아니다.

## 남은 확인과 다음 실행

1. **같은 여행을 유지한 채 제한 → 복구를 이어서 관찰한다.** 비활성 여행의 목록과 상세에서 offline·unknown 동안 이전 내용이 보이지 않고, 복구 시 이전 내용이 먼저 돌아오며 필요한 조회만 이어지는지 확인한다. 활성 여행은 Local 일정·경비가 제한 중에도 보이는지 비교한다. 탭·선택 여행·상세 이동이 바뀌는지도 함께 본다.
2. **조회 실패를 두 경우로 나눠 화면을 확인한다.** 데이터 없는 첫 조회 실패가 ‘0개/0원/찾을 수 없음’으로 보이지 않는지, 기존 내용 갱신 실패는 내용·금액·선택을 유지하면서 실패 안내와 재시도가 실제로 작동하는지 확인한다. 일정 목록·상세와 경비 목록·상세에 같은 기대를 적용하되, 모든 화면을 새로 초기화해 반복하지 말고 한 상태에서 이동하며 수집한다.
3. **열린 폼에서 제한·복구·실패를 이어 본다.** 일정 생성의 수동 입력·장소 선택·취소를 picker와 키보드까지 포함해 확인하고, 경비 생성·수정에서는 기존 일정 연결과 미저장 값을 둔 채 제한·해제한다. 저장이 막히거나 실패한 뒤에는 이유가 한 번 명확히 보이고 폼이 남으며, 복구 뒤 자동 저장 없이 사용자의 재시도에만 반응해야 한다. 10월 4일 수집은 경비 폼을 열기만 했고, 폼 내부에 Debug 진입이 없어 같은 열린 초안으로 unknown 왕복을 하지 못했다. 그 장면은 **미확인**이다.
4. **실제 통신 단절을 별도로 확인한다.** Debug override로 만든 offline과 기기의 실제 연결 단절은 다르다. 특히 활성 여행의 Local 저장, 재접속 뒤 조회·sync 결과, 새 activation을 Debug 검사로 완료 처리할 수 없다.

복구 토스트는 현재 추가하지 않기로 한 결정을 유지한다. 실제 전환에서 상태 표시와 내용 복귀가 알아차리기 어려운 장면이 나오면 그때 필요한 안내를 다시 판단하면 된다. 경비 삭제 실패 이유 유실과 경비 상세의 특정 재시도 불일치는 앞서 명시적으로 보류한 항목이다. 이번 온라인 캡처나 자동 검사 통과로 해결됐다고 표시하지 않는다.

**이 항목의 종료 기준**은 정상 화면이 존재하는지보다, 제한·실패·복구와 작성 유지가 같은 사용 경로에서 어긋나지 않는지 확인하는 것이다. 지금은 그 마지막 관찰이 없으므로 종합 UX 수락이나 Ticket 06 완료로 판정할 수 없다.
