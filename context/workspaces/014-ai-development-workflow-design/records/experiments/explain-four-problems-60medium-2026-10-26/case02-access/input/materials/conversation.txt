**`refresh`를 빼려는 이유는 원본 `refetch`와 실행 의미가 다른 두 입구를 만들 필요가 부족하기 때문입니다.**

앞선 제안의 `refresh`는 “접근 가능 여부를 확인하고 `query.refetch()`를 호출”하는 기능이었습니다. 그러면 사용자는 언제 `refresh`를 쓰고 언제 원본 `refetch`를 써야 하는지 다시 판단해야 합니다.

대신 사용자 행동의 제한은 화면이나 해당 입력 영역에 둡니다.

```tsx
const onRefresh = async () => {
  if (!access.enabled) return;
  await query.refetch();
};
```

이 정도의 행동 연결은 남습니다. 공통 훅이 줄이는 것은 **Policy 두 호출, 자동 조회 조건, 캐시 노출과 오류 표시의 우선순위를 화면마다 다시 조합하는 부담**입니다. 모든 UI 코드를 훅으로 옮기는 것은 아닙니다.

아키텍처 리뷰어는 실행 가능할 때만 원본 `refetch`를 별칭으로 제공하는 안도 제시했습니다. 하지만 두 진입점이 남는 비용을 고려해, 저는 React Query 리뷰어의 **원본 메서드 하나를 유지하는 안**을 추천합니다.

**폼과 단독 데이터 소비는 이렇게 대응합니다.**

- **목록 화면:** 조합 훅의 `view`로 내용·제한·로딩·오류를 표시합니다.
- **폼의 보조 조회:** 같은 조합 훅을 일정 선택 영역 등에 적용합니다. 폼 입력·검증·저장 조건은 폼이 소유합니다. 조회 실패가 전체 폼을 닫거나 입력값을 초기화하지 않습니다.
- **표시 정책이 필요 없는 내부 계산:** 기존 데이터 훅을 직접 사용합니다. 저장 후 경로 계산 같은 사용처에 화면 표시 모델까지 강제하지 않습니다.

다만 홈의 개수·합계처럼 **데이터를 계산해서 사용자에게 보여주는 경우**는 표시 제한이 필요한지 확인해야 합니다. “데이터만 사용한다”는 이유만으로 정책에서 제외되는 것은 아닙니다.

타입 측면에서는 **원본을 `{ query }`로 반환하면 성공 여부에 따른 타입 좁히기와 `refetch`의 옵션·반환형이 유지**됩니다. 반면 제한 시 아무것도 반환하지 않는 함수로 `refetch`를 교체하면 원래 반환 계약이 달라집니다. 전체 결과를 펼치는 방식은 타입보다 속성 추적 최적화에 비용이 있었습니다. [확인한 실험](/private/tmp/noline-query-contract-review.cjs)
