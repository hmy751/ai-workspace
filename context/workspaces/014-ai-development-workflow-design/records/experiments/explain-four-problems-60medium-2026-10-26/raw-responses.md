# GPT-6-sol medium — 네 사례의 최초 응답 원문

각 사례를 새 컨텍스트에서 한 번씩 수행했다. 아래에는 표제와 구분선만 추가했으며 응답 본문은 수정하지 않았다. 평가와 실행 한계는 별도 기록에 둔다.

## 1. 저장 용량 변경의 첫 보고

`useStorageStats`의 중복된 표시값 조립을 한곳으로 모았습니다. 이전에는 정상 종료와 바깥 `catch`에서 `dbSize`·`mapPackSize`·`totalSize`를 각각 같은 방식으로 만들었습니다. 이제 `createStorageStats(dbSizeBytes, mapSizeBytes)`가 세 값을 만들고, 조회가 끝나면 한 번만 상태에 반영합니다. 초기 `0 B` 상태도 같은 함수를 사용합니다.

```ts
} catch (error) {
  console.warn('Failed to calculate storage stats:', error);
} finally {
  setStats(createStorageStats(dbSizeBytes, mapSizeBytes));
}
```

`finally`는 정상 종료와 바깥 오류 모두에서 실행됩니다. 따라서 DB 파일 조회가 중간에 실패하면 그때까지의 DB 합계를 표시하고 Mapbox 조회는 시작하지 않습니다. `getPacks()`가 실패하면 DB 합계가 남고, 개별 팩의 `status()`가 실패하면 기존 안쪽 `catch`가 다음 팩 조회를 계속합니다. 이 실패 정책과 1,024 기준 표시 규칙은 건드리지 않았습니다. 앞으로 표시 필드를 바꿀 때 함께 고칠 조립 위치는 두 곳에서 한 곳으로 줄었고, 중단·계속 조건은 같은 hook 안에서 보입니다.

당시 검사에서 기존 hook 특성화 테스트와 설정 테스트 **2 suites, 7 tests가 통과**했습니다. Prettier 검사도 통과했습니다. 다만 client 전체 `test:typecheck`는 실패했습니다. 진단은 `mapbox.ts`의 tuple 타입 1건과 `download.ts`의 `OfflinePack.size`·`tileCount` 사용 2건으로, 이번 변경 파일에서는 나오지 않았습니다. 따라서 전체 타입 검사가 통과했다고 보지는 않습니다. 실제 Expo 파일 경로와 Mapbox native pack의 기기 동작도 이번 mock 테스트로 확인한 범위는 아닙니다.

## 2. access 선택 질문

`access`는 없어진 게 아니라 **조합 훅 내부로 들어갔고, 반환값에서는 빠졌습니다.** 제가 앞서 합의한 `{ query, access, view }`를 `{ query, actions, view }`로 설명하면서 이 변경을 짚지 않았습니다.

현재 일정 조회의 연결은 이렇습니다.

```ts
const access = useTripReadAccess(tripId, 'schedule', options);
const query = useGetSchedules(tripId ?? '', { enabled: access.enabled });
return useReadQuery(query, access);
```

`useReadQuery`는 `access`로 표시 결과를 계산하고, 재조회 직전 차단 여부를 확인합니다. 바깥에는 `actions.canRefetch`로 조회 가능 여부를, `view.kind === 'blocked'`일 때 `view.policy`로 제한 이유를 내보냅니다. 그래서 일정 화면은 지금 `access`를 직접 받지 않습니다.

하지만 **`actions`는 `access`의 대체물이 아닙니다.** `access`에는 표시 정책과 실제 네트워크 기준 정책, 조회를 잠시 꺼 둔 상태까지 들어 있습니다. 폼의 보조 조회처럼 그 구별이 필요한 사용처까지 고려한다면, 이를 숨기는 결정을 자동으로 해서는 안 됩니다. 제가 제안했던 계약대로 `{ query, access, actions, view }`를 반환하고, 정책을 고려한 실행만 `actions.refetch`로 열어 두는 편이 일관됩니다. 이번 한 곳 적용에서는 `access`가 내부에서만 쓰이고 있다는 것이 현재 구현의 정확한 상태입니다.

## 3. 인증 설명의 자기평가

맞아. 내가 “이전 설명은 메서드가 어떻게 호출되는지만 보여줬다”고 평가한 건 과장했어. 첫 설명에도 코드 주체의 역할과 책임 경계가 분명히 있었다. 처음부터 **계정 정보·서버 토큰·여행 데이터 소유권을 구분**했고, `auth.ts`는 현재 사용할 계정과 인증 범위를 판단하며, `local-access.ts`는 그 계정을 SQL의 소유자·활성 여행 조건에 넣는다고 설명했다. Store가 `local-account.ts`의 조사 결과를 받아 로그인 수락을 결정한다는 관계와, Store의 저장 순서와 `session-lifecycle.ts`가 보호하는 범위의 차이도 짚었다. 그러니 “동작만 있었다”는 내 말은 철회할게.

다만 네가 느낀 부족함도 실제로 있어. 첫 설명은 **작업의 목표와 현재 동작을 검증 가능한 근거에 붙여 브리핑하는 순서**로 전개됐다. 인증 상태 표, 앱 시작·401·재로그인 흐름을 먼저 따라가고, Store와 `local-access`의 책임은 3절에서 본격적으로 풀었다. 각 파일의 일을 정확히 설명했지만, “이 주체는 어떤 사실을 책임지고 다른 주체에게 무엇을 판단해 주는가”라는 기준이 앞의 흐름을 읽는 동안 계속 붙어 있지는 않았다. 그래서 역할에 관한 문장들이 이미 있었는데도, 독자는 여러 동작을 본 뒤에야 그 주체의 정체를 조립해야 했을 수 있어. 이것은 **내용의 부재보다 설명의 진입점과 연결 방식**의 문제에 가깝다.

`work-artifact-briefing`을 고려했을 거라는 지적도 타당한 가설이야. 첫 설명은 현재 작업 트리 기준을 밝히고, 변경 전후 상태·구현 근거·테스트와 실기기 확인의 경계를 제시하는 등 *작업물 브리핑*의 성격이 강하다. 다만 제공된 대화에는 당시 그 스킬을 실제로 읽거나 적용했다는 기록이나 스킬 본문이 없어서, **그 스킬 때문이었다고 단정할 수는 없다.** 확인되는 건 응답의 구성과 내용이지, 그것을 만든 절차는 아니야.

내 두 번째 답은 그 반작용으로 각 주체의 정의를 앞세웠지만, 첫 답의 성과를 지우고 “이제야 구조를 설명했다”는 식으로 말한 게 잘못이었어. 더 나은 설명은 둘을 결합하는 쪽이야. 예를 들어 `reauth-required`를 소개하는 바로 그 자리에서 “Auth Store는 현재 앱이 인정한 계정과 서버 사용 가능 범위를 결정한다. SecureStore는 다음 실행에 복원할 기록을 보존하고, SQLite는 여행 데이터의 소유 사실을 보관한다”를 먼저 잡고, 이어서 토큰을 지워도 A의 활성 여행을 수정할 수 있는 실제 조건과 실패 경계를 보여주는 거지. 그러면 **주체의 역할이 동작의 이유가 되고, 동작이 그 역할의 근거가 된다.** 네 지적은 역할 설명을 새 장으로 추가하자는 뜻보다, 그 관계가 흐름 설명의 중간중간 작동해야 한다는 뜻으로 이해했어.

## 코드·검사가 뒷받침하는 부분

- 일정·경비 목록은 조회 조합이 `blocked`·`loading`·`error`·`ready`를 나눠 표시한다. 첫 조회 실패는 빈 항목 안내로 바꾸지 않고 다시 불러오기 버튼을 준다. 기존 결과의 갱신 실패는 내용과 별도의 작은 안내를 함께 보여 준다. 일정·경비 상세도 같은 구분을 사용한다. 조회가 제한될 때 캐시를 삭제하는 대신 내용을 가리는 구조다. 근거: `ScheduleScreen.tsx`, `ExpensesScreen.tsx`, `ScheduleDetailScreen.tsx`, `ExpenseDetailScreen.tsx`, `usePolicyReadQuery.ts`.
- 일정 목록의 수정 Drawer는 목록 내용이 가려져도 화면에 장착된 채 남는다. 화면 검사는 미저장 제목·날짜, 제한·복귀, 조회 실패·갱신 뒤 값 유지를 다룬다. 일정 생성 화면은 현재 검색과 폼을 한 단계 상태로 교체하고, 연결 변화만으로 단계를 바꾸지 않는다. 이전 보고서의 ‘수동 폼 숨김’과 ‘일반·수동 폼 동시 표시’는 현재 코드와 회귀 검사상 수정됐다. 근거: `ScheduleScreen.tsx`, `CreateScheduleScreen.tsx`, `schedule-recovery.test.tsx`, `create-schedule-flow.test.tsx`.
- 경비 생성 검사에는 비활성 여행의 unknown에서 초안·일정 연결 유지, 저장 차단, online 복구 뒤 사용자가 다시 눌러 저장하는 경로가 있다. 활성 offline의 Local 저장과 날짜·일정 연결의 독립성도 검사한다. 기존 티켓 기록에는 Debug 전환 중 경비 초안 보존·복구 후 명시적 저장·서버 반영의 실앱 관찰이 있다. 근거: `create-expense-flow.test.tsx`, `06-app-startup-lifecycle.md`.

이 근거는 구현과 자동 검사 범위를 말한다. 이번 환경에는 DB·시뮬레이터·설치된 의존성이 없어 검사를 재실행하거나 실제 제한·복구를 새로 조작하지 못했다. 과거 기록의 `48 suites / 523 passed / 1 skipped`도 **당시 실행 결과**이지 이번 확인 결과가 아니다.

## 남은 확인과 다음 실행

1. **같은 여행을 유지한 채 제한 → 복구를 이어서 관찰한다.** 비활성 여행의 목록과 상세에서 offline·unknown 동안 이전 내용이 보이지 않고, 복구 시 이전 내용이 먼저 돌아오며 필요한 조회만 이어지는지 확인한다. 활성 여행은 Local 일정·경비가 제한 중에도 보이는지 비교한다. 탭·선택 여행·상세 이동이 바뀌는지도 함께 본다.
2. **조회 실패를 두 경우로 나눠 화면을 확인한다.** 데이터 없는 첫 조회 실패가 ‘0개/0원/찾을 수 없음’으로 보이지 않는지, 기존 내용 갱신 실패는 내용·금액·선택을 유지하면서 실패 안내와 재시도가 실제로 작동하는지 확인한다. 일정 목록·상세와 경비 목록·상세에 같은 기대를 적용하되, 모든 화면을 새로 초기화해 반복하지 말고 한 상태에서 이동하며 수집한다.
3. **열린 폼에서 제한·복구·실패를 이어 본다.** 일정 생성의 수동 입력·장소 선택·취소를 picker와 키보드까지 포함해 확인하고, 경비 생성·수정에서는 기존 일정 연결과 미저장 값을 둔 채 제한·해제한다. 저장이 막히거나 실패한 뒤에는 이유가 한 번 명확히 보이고 폼이 남으며, 복구 뒤 자동 저장 없이 사용자의 재시도에만 반응해야 한다. 10월 4일 수집은 경비 폼을 열기만 했고, 폼 내부에 Debug 진입이 없어 같은 열린 초안으로 unknown 왕복을 하지 못했다. 그 장면은 **미확인**이다.
4. **실제 통신 단절을 별도로 확인한다.** Debug override로 만든 offline과 기기의 실제 연결 단절은 다르다. 특히 활성 여행의 Local 저장, 재접속 뒤 조회·sync 결과, 새 activation을 Debug 검사로 완료 처리할 수 없다.

복구 토스트는 현재 추가하지 않기로 한 결정을 유지한다. 실제 전환에서 상태 표시와 내용 복귀가 알아차리기 어려운 장면이 나오면 그때 필요한 안내를 다시 판단하면 된다. 경비 삭제 실패 이유 유실과 경비 상세의 특정 재시도 불일치는 앞서 명시적으로 보류한 항목이다. 이번 온라인 캡처나 자동 검사 통과로 해결됐다고 표시하지 않는다.

**이 항목의 종료 기준**은 정상 화면이 존재하는지보다, 제한·실패·복구와 작성 유지가 같은 사용 경로에서 어긋나지 않는지 확인하는 것이다. 지금은 그 마지막 관찰이 없으므로 종합 UX 수락이나 Ticket 06 완료로 판정할 수 없다.
