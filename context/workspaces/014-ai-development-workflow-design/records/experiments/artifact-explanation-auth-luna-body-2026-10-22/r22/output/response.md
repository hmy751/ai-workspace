이 코드는 **일반 API와 동기화 API 요청에 로그인 토큰을 붙이고, 토큰이 만료됐을 때 갱신을 시도하는 Axios 인터셉터**예요. 크게 보면 “요청 보내기 전 확인 → 응답 확인 → 필요한 경우 한 번만 갱신 후 재요청” 순서입니다. 설명은 폴더에 제공된 2026-09-22 당시 코드 발췌를 기준으로 하며, 앱을 직접 실행한 결과는 아닙니다.

### 먼저 알아둘 값

- **access token**은 일반 API 요청에 `Authorization: Bearer ...`로 붙이는 짧은 수명의 인증표예요.
- **refresh token**은 access token이 없거나 만료됐을 때 새 토큰을 받기 위해 쓰는 값이에요.
- **sessionId**는 현재 로그인 세대를 식별하는 표식입니다. 로그인이나 로그아웃으로 세대가 바뀌면 예전 요청을 현재 로그인 요청으로 착각하지 않게 해요. 실제 세션 판단과 토큰 조회는 `auth.ts`의 store가 맡습니다.

### 요청을 보내기 전

1. 요청 설정에 `sessionId`가 아직 없으면 현재 store의 세션 ID를 넣습니다.

   ```ts
   config.sessionId ??= useAuthStore.getState().sessionId ?? undefined;
   ```

   여기서 `??=`는 왼쪽 값이 `null` 또는 `undefined`일 때만 오른쪽 값을 넣습니다. 그래서 요청에 이미 붙어 있던 세션 ID는 유지됩니다. store의 `null` 세션은 요청 설정에서 `undefined`로 바뀌고, 곧바로 아래 검사에서 유효하지 않은 세션으로 거절됩니다.

2. `assertCurrentSession`이 그 ID가 여전히 현재의 로그인 세션인지 검사합니다. 로그아웃됐거나 다른 로그인 세대로 넘어갔다면 `AuthRequiredError`를 던져 요청을 중단합니다.

3. 해당 세션에서 access token을 가져옵니다. 없으면 `renewSession(sessionId)`를 기다립니다. 갱신이 끝난 뒤에도 세션을 다시 확인하고 access token을 다시 읽습니다. 토큰을 얻지 못하면 인증 오류로 중단합니다.

4. 토큰이 있으면 `Authorization` 헤더에 넣어 실제 요청을 보냅니다.

### 토큰 갱신은 어떻게 겹침을 처리하나요?

`renewSession`은 `Map<sessionId, Promise<void>>`에 진행 중인 갱신을 보관합니다. 같은 세션에서 여러 요청이 거의 동시에 갱신을 필요로 하면 refresh API를 요청마다 여러 번 부르는 대신, 이미 진행 중인 같은 Promise를 함께 기다립니다. 세션 ID가 다르면 별개로 처리합니다. 완료되거나 실패하면 해당 항목을 Map에서 지웁니다.

갱신 작업은 현재 세션인지 먼저 확인하고 refresh token을 읽습니다. refresh token이 없으면 `rejectCredentials`로 넘어갑니다. 토큰 교환은 `auth-transport.ts`의 `refreshTokens`가 인증 인터셉터가 없는 `authAxios`로 `/api/auth/refresh`를 호출해 수행합니다. 인터셉터를 다시 타며 갱신이 반복되는 일을 피하는 구조예요.

- 서버가 refresh 요청에 **401 또는 403**을 주면 자격 증명이 거부된 것으로 보고 `requireReauthentication`을 호출한 뒤 `AuthRequiredError`를 던집니다. store는 저장을 기다리기 전에 현재 메모리 세션을 재인증 필요 상태로 바꾸므로, 저장이 실패해도 이 API 호출은 일반 오류가 아니라 인증 오류로 끝나게 합니다.
- 연결 실패나 서버의 다른 오류는 토큰이 거부됐다는 증거로 취급하지 않습니다. 이 경우 해당 오류를 그대로 던져 네트워크·서버 오류로 남깁니다.
- 갱신에 성공하면 받은 토큰을 store에 저장하고 세션에 적용합니다. 저장 과정에서 세션이 이미 바뀌어 적용되지 못하면 인증 오류가 납니다.

### 응답이 401이면

서버 응답이 성공이면, 반환하기 전에 응답에 기록된 세션 ID가 아직 현재 세션인지 확인합니다. 요청 도중 로그아웃이나 계정 전환이 일어났다면 늦게 도착한 응답도 호출자에게 성공으로 돌려주지 않습니다.

오류 응답은 다음 조건으로 갈립니다.

- 요청 정보가 없거나 상태가 401이 아니면 그대로 오류를 던집니다. 예를 들어 이 인터셉터는 5xx를 인증 갱신 사유로 보지 않습니다.
- 401이면 요청이 시작된 세션이 아직 현재인지 확인합니다.
- 그 요청이 이미 재시도된 요청(`authRetried`)이면 자격 증명을 거부 처리하고 재인증 오류를 냅니다. 두 번째 401에서 무한 재요청하지 않게 하는 장치예요.
- 첫 401이면 `authRetried = true`로 표시하고 갱신을 기다립니다. 갱신 뒤 세션을 재확인한 다음 `client(request)`로 원래 요청을 다시 보냅니다. 재전송에서도 요청 인터셉터가 토큰을 다시 붙입니다.

흐름을 한 줄로 그리면 다음과 같습니다.

```text
요청
  → 세션 확인
  → access token 확인 ─ 있음 → Authorization 헤더를 붙여 전송
                    └ 없음 → 세션당 갱신 공유 → 토큰 저장·적용 → 전송
  → 응답 ─ 성공 → 세션 재확인 후 반환
         └ 401 → 세션 확인 → 갱신 → 원 요청 한 번 재전송
                         └ 재전송도 401 → 재인증 필요 오류
```

### 일반 API와 sync API의 관계

`fetcher.ts`는 일반 `apiAxios`에 `setupAuthInterceptors`를 설정하고, `apps/client/src/shared/services/sync/api.ts`는 동기화 전용 Axios 인스턴스에 `setupSyncAuthInterceptors`를 설정합니다. 두 이름은 같은 함수를 가리키므로 세션 확인·토큰 갱신·401 처리 기준은 공유합니다. 제공된 sync 사용처에는 이 뒤에 별도의 5xx 재시도 처리도 등록돼 있지만, 그것은 인증 인터셉터의 토큰 갱신 로직과는 별도예요. 인증 인터셉터는 자체적으로 5xx를 재시도하지 않습니다.

코드상 흐름은 이렇게 연결되지만, 이번 자료에는 앱 실행 trace나 테스트 결과가 없으므로 실제 서버 응답과 런타임 순서를 관찰했다고 말할 수는 없습니다. 특히 설명한 것은 제공된 일반 API·sync 연결의 관련 경로이며 앱 전체 인증 구조를 모두 열거한 것은 아닙니다.
