이 코드는 **일반 API 요청과 동기화 요청에 인증을 붙이고, access token이 없거나 만료된 경우 갱신을 시도하는 Axios 인터셉터**예요. 핵심은 요청마다 “처음 시작한 로그인 세션이 아직 유효한가?”를 확인하고, 같은 세션의 토큰 갱신은 한 번만 진행하는 것입니다.

`sessionId`는 로그인 세션을 구분하는 값입니다. 요청이 만들어질 때 현재 세션 ID를 요청 설정에 붙여 둡니다. 이 덕분에 요청이 진행되는 사이 로그아웃하거나 다른 세션으로 바뀌었을 때, 예전 요청이 새 세션의 토큰을 잘못 쓰지 않도록 확인할 수 있어요.

### 요청이 나가기 전

```ts
config.sessionId ??= useAuthStore.getState().sessionId ?? undefined;
assertCurrentSession(config.sessionId);
```

`??=`는 왼쪽이 `null` 또는 `undefined`일 때만 현재 세션 ID를 채웁니다. 이미 요청에 세션 ID가 있으면 그대로 둡니다. 이어지는 `assertCurrentSession`은 그 ID가 지금도 로그인된 유효 세션인지 확인하고, 아니면 `AuthRequiredError`를 던져 요청을 막습니다.

그 다음 access token을 가져옵니다. 없으면 `renewSession`으로 refresh token 갱신을 기다립니다. 갱신 후 세션을 다시 확인하고 access token을 가져와 `Authorization: Bearer ...` 헤더에 넣습니다. 갱신 뒤에도 토큰을 얻지 못하면 요청을 보내지 않습니다.

### 토큰 갱신은 같은 세션에서 합쳐서 처리

`refreshes`는 세션 ID별로 진행 중인 갱신 Promise를 보관합니다. 여러 요청이 거의 동시에 토큰 갱신을 필요로 하면, 첫 요청이 갱신을 시작하고 나머지는 같은 Promise를 기다립니다. 따라서 코드상 같은 세션에서 갱신 요청이 중복되는 것을 막습니다.

갱신은 인증 인터셉터가 없는 `authAxios`로 `/api/auth/refresh`를 호출합니다. 이 분리가 없으면 갱신 요청 자체가 다시 인증 인터셉터를 타며 순환할 수 있습니다. 서버가 새 토큰을 돌려주면 store가 세션이 여전히 같은지 확인한 뒤 저장하고 적용합니다. 세션이 이미 바뀌어 적용할 수 없으면 인증 오류로 끝납니다.

### 응답이 401이면 한 번만 다시 요청

응답이 정상이어도 응답 설정에 기록된 세션이 여전히 유효한지 확인합니다. 실패 응답은 401이 아니거나 요청 정보가 없으면 그대로 오류로 전달합니다. 401이면 세션을 확인한 뒤 다음처럼 처리합니다.

- 이미 한 번 재시도한 요청이면 자격 증명이 거부된 것으로 처리하고 재로그인을 요구합니다.
- 아직 재시도하지 않았다면 `authRetried`를 표시하고 토큰 갱신을 기다립니다.
- 갱신과 세션 확인이 끝나면 같은 요청을 한 번 다시 보냅니다.

즉, **401을 무한히 재시도하지 않고 최대 한 번만 재전송**합니다. refresh 요청 자체가 401 또는 403으로 실패하면 현재 세션의 자격 증명을 거부된 것으로 보고 store를 `reauth-required` 상태로 바꾼 뒤 `AuthRequiredError`를 던집니다. 반면 네트워크 끊김이나 서버 장애는 자격 증명이 틀렸다는 증거가 아니므로, 세션을 재로그인 상태로 바꾸지 않고 해당 오류를 전달합니다.

### 이 코드가 연결된 곳과 범위

제공된 사용처 발췌에서 `fetcher.ts`는 일반 API 클라이언트에 이 인터셉터를 연결하고, `sync/api.ts`도 `setupSyncAuthInterceptors`를 통해 같은 함수를 연결합니다. 둘 다 같은 세션 확인·갱신·거부 흐름을 사용합니다. 로그인과 refresh 호출에 쓰이는 `authAxios`에는 이 인터셉터가 없습니다. 이 설명은 폴더에 보존된 코드와 사용처 발췌를 따라 재구성한 것이며, 현재 앱 실행이나 전체 저장소 연결을 확인한 결과는 아닙니다.

한 요청의 흐름을 줄이면 이렇습니다.

```text
요청에 세션 ID 지정 → 현재 세션 확인 → access token 확인
  ├─ token 있음: Authorization 헤더를 붙여 전송
  └─ token 없음: 같은 세션의 refresh 진행/대기 → 새 token 저장
               → 세션 재확인 → 헤더를 붙여 전송
응답
  ├─ 정상: 세션 재확인 후 반환
  └─ 401: 한 번 갱신 후 재전송, 재전송도 실패하면 재로그인 요구
```

이 흐름은 인증 오류를 구분하고 세션이 바뀐 뒤의 오래된 요청을 차단하도록 짜여 있습니다. 다만 여기에는 테스트나 실행 기록이 제공되지 않아, 실제 네트워크 상황에서 각 분기가 동작하는지까지 확인했다고 말할 수는 없습니다.
