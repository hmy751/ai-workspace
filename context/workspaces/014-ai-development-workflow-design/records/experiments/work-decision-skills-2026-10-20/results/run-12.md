확인한 자료 기준으로는 **2-C를 ‘연결 제한을 겪던 사용자에게 복귀를 알리는 작은 안내’로 좁히는 것**을 추천합니다. 데이터 표시와 재조회는 현재 Policy·Query의 역할을 그대로 활용하면 됩니다.

기존 정책에서 지켜야 할 것은 분명합니다. 비활성 여행의 offline·unknown 제한, 여행 선택과 입력 보존, 캐시를 오프라인 이용 권한으로 보지 않는 기준은 유지합니다. 초기 연결 확인이나 단순 재확인을 복구로 알리지 않고, 같은 장애를 반복 안내하지 않는 기준도 유효합니다.

다시 볼 부분은 **‘복구 조회가 성공한 뒤 토스트를 띄운다’는 연결 방식**입니다. 후속 정책에서는 연결이 돌아와 접근이 허용되면 기존 데이터를 바로 보여 주고, 새 조회 여부는 Query가 판단합니다. 이 흐름에서 알림을 조회 성공에 묶으면 새 조회가 없는 경우 알림을 위해 조회를 만들거나, 화면 복귀와 안내 시점이 어긋날 수 있습니다. 2-C의 의미를 연결 복귀로 정하고, 문구도 “연결이 복구되었습니다”처럼 데이터가 최신이라는 뜻을 포함하지 않는 편이 맞겠습니다.

알림 자체를 없애기에는 반대 근거가 있습니다. 최근 UX 관찰에서 헤더와 내용이 정상으로 돌아왔어도 사용자가 복귀를 놓쳐 사용을 포기하거나 재확인을 반복했습니다. 따라서 사용자에게 복귀를 알려 주는 책임은 남아 있습니다. 다만 안내 방식을 비교한 결과는 없으므로, 기존에 선택했던 토스트를 최소 후보로 삼아 실제로 인지를 돕는지 확인해야 합니다.

역할을 기준으로 구현 범위는 이렇게 잡겠습니다.

- **화면**은 현재 보고 있는 비활성 여행에서 실제 연결 제한을 겪었고, 연결 복귀로 접근이 다시 허용됐을 때 안내합니다. 이동한 사용자를 원래 여행으로 돌려보내지 않습니다.
- **Network Store**의 상태 관측·재확인 중복 처리를 활용합니다. 같은 상태를 걸러내는 것과 같은 장애를 한 번만 알리는 것은 다르므로, 화면 재진입까지 포함해 기존 흐름이 알림 중복도 막는지 확인하고 부족한 부분만 보완합니다.
- **Query·Router·인증·Sync**는 기존 조회·실행 검증·동기화 책임을 유지합니다. 알림을 위해 강제 조회, 조회 완료 대기, 별도 캐시 관리나 동기화 조율을 추가할 이유는 현재 자료에서 보이지 않습니다.

구현 전에는 실제 알림 진입점과 재사용 가능한 안내 UI부터 확인해야 합니다. 공용 토스트는 아직 확인되지 않았으므로 새 공통 체계가 필요하다고 미리 정하지 않겠습니다. 확인할 결과는 기존 데이터가 즉시 나타나는지, 초기 확인·단순 재확인·같은 장애에서 불필요한 안내가 없는지, 그리고 복귀를 놓쳤던 사용자가 안내 후 다시 사용할 수 있음을 알아차리는지입니다.

자료에 기록된 2-A·2-B 완료를 되돌릴 근거는 아직 없습니다. 제품 코드 전체를 보지 못했으므로 기존 구현의 불필요한 복잡함까지 없다고 판정한 것은 아닙니다. 기존 데이터가 있는 재조회 실패 시 내용을 유지하는 안도 아직 미채택이므로 이번 알림에 함께 끼워 넣지 않겠습니다.
