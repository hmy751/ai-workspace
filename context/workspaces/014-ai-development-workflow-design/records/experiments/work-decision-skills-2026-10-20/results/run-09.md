**지금은 복구 토스트를 바로 구현하기보다, 현재 화면만으로 연결 복귀를 충분히 알아차릴 수 있는지 먼저 확인하는 쪽을 추천합니다.** 정책이 지키려는 결과를 유지하면서, 이미 다른 부분이 맡고 있는 일을 다시 만들지 않는 방향입니다.

[기존 정책](/tmp/work-decision-trial-20261020/runs/run-09/context/work/original-policy.md)은 여행·탭·선택이 사라지지 않게 하고, 비활성 여행의 오프라인 접근을 제한하며, 같은 여행에서 복구 조회가 성공하면 한 번 알리기로 했습니다. 캐시를 따로 삭제·관리하지 않고 화면에서 제한을 선택하자는 결정도 있었습니다. 이 목적과 제약은 보존해야 합니다.

다만 [후속 정책](/tmp/work-decision-trial-20261020/runs/run-09/context/work/revised-policy.md)에서는 접근이 허용되면 기존 데이터를 바로 보여 주고, 새 조회가 필요한지는 Query가 판단하도록 바뀌었습니다. 따라서 **화면을 다시 볼 수 있게 되는 시점과 새 조회가 성공하는 시점이 더 이상 같지 않습니다.** 예전의 “조회 성공 뒤 토스트”를 그대로 구현하려고 별도 조회나 대기 상태를 만들면, 새 정책과 Query의 역할을 거슬러 복잡해집니다.

[현재 조사 기록](/tmp/work-decision-trial-20261020/runs/run-09/context/work/observations.md)에 따르면, 토스트를 추가하지 않아도 제한 해제 뒤 같은 계정·여행의 기존 내용이 나타나고 헤더에 연결 상태가 표시됩니다. 토스트를 더하면 복귀 순간을 눈에 띄게 알릴 수는 있지만, 데이터 접근이나 갱신 자체가 개선되는 것은 아닙니다. 사용자가 현재 표시만으로 복귀를 놓치는지는 아직 관찰하지 않았으므로, 토스트가 불필요하다고 확정할 근거도 없습니다. 공용 토스트 구현도 확인되지 않아 추가 비용이 작다고 단정할 수 없습니다.

역할은 다음처럼 유지하면 됩니다.

- 화면과 접근 정책은 제한·내용 표시, 선택·입력 보존을 맡습니다. 캐시가 있다는 이유로 오프라인 접근을 허용하지 않습니다.
- Query는 조회가 허용되는 동안 캐시·로딩·갱신·조회 오류를 맡습니다. 화면이나 조합 훅이 이를 별도 상태로 다시 관리할 이유는 현재 자료에서 보이지 않습니다.
- Network Store는 연결 관측과 재확인을, Router·인증은 실제 실행 시점의 연결·세션·소유권과 Local/Remote 선택을, Sync는 동기화와 변경 후 갱신을 계속 맡습니다.

다음 확인은 예정된 종합 UX 검토에서 좁게 하면 됩니다. **비활성 여행을 보다가 연결이 끊기고 다시 돌아왔을 때, 사용자가 제한 해제와 내용 복귀를 알아차리고 하던 일을 이어갈 수 있는지** 봅니다. 기존 데이터가 없는 경우에는 로딩·오류 표시가 상황을 설명하는지도 따로 봅니다. 복구 전에 다른 여행으로 이동한 경우에는 현재 선택을 유지하는지 확인합니다.

이 흐름만으로 충분하면 2-C 토스트를 추가하지 않는 쪽을 제안할 수 있습니다. 복귀를 놓쳐 사용자가 계속 기다리거나 재시도한다면 알림을 추가할 근거가 생깁니다. 그때 연결 복귀를 알릴 것인지 데이터 갱신 성공을 알릴 것인지 구별해야 합니다. 연결 복귀 안내를 데이터 최신화 완료처럼 표현하지 않고, 갱신 성공 알림을 선택하더라도 실제 조회 성공에만 붙여야 합니다. 어느 쪽이든 토스트를 위해 조회를 강제하거나 화면을 기다리게 하지 않는 기준은 유지합니다.

이번 검토로 제안하는 변경은 **2-C의 즉시 구현을 보류하고, 필요성을 가르는 UX 확인을 먼저 하는 것**입니다. 기존에 채택한 성공 토스트를 삭제하기로 확정한 것은 아닙니다. 2-A·2-B의 제한·복귀·조회 연결을 되돌릴 근거는 없고, 앱 복귀 재확인·저장 및 삭제 차단 이유 안내·최종 검증도 그대로 남습니다. 기존 데이터가 있는 상태의 재조회 실패 안내는 아직 미채택 추천이므로 이번에 확정된 정책으로 취급하지 않습니다.

제품 코드 전체나 실제 UX를 직접 검증한 결과는 아니며, 제공된 정책과 조사 기록을 비교한 판단입니다. 구현과 기존 문서는 변경하지 않았습니다.
