2-C는 **‘연결 제한이 풀려 다시 사용할 수 있음을 사용자가 알아차리게 한다’는 역할로 좁히는 게 좋겠습니다.** 기존 구성요소가 맡는 조회·캐시·동기화를 알림 때문에 다시 구현할 필요는 없습니다. 다만 최근 관찰에서 헤더와 내용이 정상으로 돌아와도 복귀를 놓치는 사용자가 있었으므로, 현재 표시만으로 충분하다고 결론 내릴 수도 없습니다.

기존 정책과 후속 정책을 비교하면, 유지할 것과 다시 정할 것이 나뉩니다.

- **유지할 것:** 여행 정보·탭·선택·입력을 보존하고, 비활성 여행의 offline/unknown 제한을 지킵니다. 캐시가 있다는 이유로 오프라인 접근을 허용하지 않고, 연결이 돌아와도 사용자를 이전 여행으로 강제 이동시키지 않습니다. 초기 연결 확인·단순 재확인은 복구 알림에서 제외하고 같은 장애를 반복 알리지 않습니다.
- **다시 정할 것:** 과거에는 ‘복구 조회 성공 후 토스트’를 선택했지만, 후속 정책에서는 접근이 허용되면 기존 내용을 먼저 보여 주고 새 조회 여부는 Query에 맡깁니다. 이제 연결 복귀와 데이터 갱신 성공은 시점도 의미도 다릅니다. 따라서 알림을 위해 조회를 강제하거나 조회 성공까지 화면을 기다리게 하는 설계는 현재 정책과 맞지 않습니다.

역할을 따라 구현을 줄이면, Network Store는 연결 관측과 재확인 요청 정리, Policy와 조회 조합은 내용 표시·조회 허용, Query는 캐시·로딩·갱신·조회 오류, Sync는 동기화와 변경 후 갱신을 계속 맡으면 됩니다. 화면 쪽에 남는 일은 **이 화면에서 제한을 겪던 사용자가 실제로 다시 사용할 수 있게 됐는지 보고, 그 사실을 적절하게 안내하는 것**입니다. 조회 조합 훅에 별도 캐시 상태나 복구 전용 조회 흐름을 더할 이유는 현재 자료에서 찾지 못했습니다. Router·인증 계층의 실행 시점 연결·세션·소유권 확인도 그대로 필요합니다.

안내의 의미는 우선 ‘연결 제한이 해제되어 다시 이용할 수 있음’으로 잡는 것을 추천합니다. ‘최신 데이터로 갱신됐음’까지 뜻하게 해서는 안 됩니다. 다만 **토스트가 적절한지는 아직 확인되지 않았습니다.** 화면을 잠시 보지 않던 사용자가 놓친 장면이므로 짧게 사라지는 토스트도 놓칠 수 있습니다. 해당 복귀 장면에서 일회성 토스트와 화면에 남는 짧은 안내를 비교해, 사용자가 재확인 버튼을 반복해서 누르지 않고 사용을 재개하는지 먼저 확인하는 편이 좋겠습니다. 이 확인을 뒤의 종합 UX 검토로 전부 미루지는 않는 것을 추천합니다.

중복 방지도 역할을 구분해야 합니다. Network Store가 같은 연결 관측을 걸러낸다는 사실만으로 ‘이 사용자가 이 여행에서 겪은 장애를 한 번만 안내한다’까지 보장되지는 않습니다. 실제 제한 경험, 현재 계정·여행, 이미 안내했는지를 기존 상태로 판단할 수 있는지 확인하고, 부족한 기억만 최소한으로 두면 됩니다. 전체 코드와 공용 토스트 구현이 제공되지 않아 어느 코드까지 재사용하거나 제거할 수 있는지는 아직 확정할 수 없습니다.

기존 2-A·2-B의 제한·복귀와 Query 연결은 조사 자료상 완료된 결과로 유지할 수 있습니다. 다만 그 완료가 ‘사용자가 복귀를 알아차린다’는 목표까지 충족한 것은 아닙니다. 다음 작업은 2-C에 안내의 의미·대상·중복 기준과 위 UX 확인을 반영하는 것으로 좁히고, 앱 복귀 재확인·저장 및 삭제 차단 이유 안내·최종 검증은 남은 일로 유지하면 됩니다. 기존 내용을 유지하면서 background 조회 실패를 안내하자는 제안도 아직 채택 전이므로 이번 결정에 섞지 않아야 합니다.

현재 답은 검토와 변경 제안입니다. 채택한다면 공통 정책의 알림 의미는 [후속 정책](/tmp/work-decision-trial-20261020/runs/run-08/context/work/revised-policy.md)에, 2-C의 구체적인 범위와 확인 결과는 [현재 Ticket](/tmp/work-decision-trial-20261020/runs/run-08/context/work/ticket.md)에 반영하면 됩니다. 이번에는 제품 구현과 기존 문서를 수정하지 않았습니다.
