**2-C 복구 알림을 바로 구현하는 순서를 재검토하고, 기존 화면 표시로 복귀를 충분히 알 수 있는지 먼저 확인하는 쪽을 추천합니다.** 현재 자료에서는 알림을 추가해야 할 사용자 문제가 아직 확인되지 않았습니다. 다만 이전에 채택한 토스트를 없애기로 결정할 근거도 아직 없습니다.

[기존 정책](/tmp/work-decision-trial-20261020/runs/run-16/context/work/original-policy.md)의 목적은 연결이 끊겨도 여행이 사라진 것처럼 보이지 않고, 탭과 선택을 유지하는 것이었습니다. 비활성 여행에는 제한을 보여 주고, 같은 여행에 머물러 있다면 복구 후 다시 조회하며, 조회 성공을 토스트 한 번으로 알리기로 했습니다. 캐시를 별도로 관리하지 않고 제한 안내를 선택한 것도 복잡함을 줄이려는 결정이었습니다.

[후속 정책](/tmp/work-decision-trial-20261020/runs/run-16/context/work/revised-policy.md)에서는 제한이 풀리면 기존 데이터를 바로 보여 주고, 새 조회의 필요성은 Query가 판단하도록 바뀌었습니다. 따라서 **연결 복귀, 내용 표시 재개, 새 데이터 조회 성공이 같은 시점에 일어난다는 전제로 알림을 붙일 수는 없습니다.** 이전 토스트 결정은 확인해야 할 정책이지만, 당시의 조회 흐름까지 그대로 유지할 이유는 약해졌습니다.

제공된 [현재 조사 기록](/tmp/work-decision-trial-20261020/runs/run-16/context/work/observations.md)을 보면 역할도 이미 나뉘어 있습니다.

- 헤더는 연결 상태를 표시하고, 화면과 접근 정책은 제한·내용 표시 및 선택 보존을 맡습니다.
- Query는 캐시와 조회·갱신·오류 상태를, Sync는 동기화와 실제 변경 뒤 갱신을 맡습니다.
- Network Store는 반복 상태 관측과 재확인 요청을 정리합니다.

이 역할을 활용하면 알림을 위해 별도 조회를 강제하거나, 캐시·조회 상태를 다시 관리하거나, Sync 종료까지 화면을 기다리게 할 필요가 없습니다. 다만 Network Store가 반복 관측을 거른다는 사실만으로 ‘같은 장애에 토스트 한 번’까지 보장된다고 볼 수는 없습니다. 토스트를 선택하면 그 알림 책임은 추가로 필요합니다.

그래서 다음 작업은 이렇게 좁히는 것이 좋겠습니다.

1. 예정된 종합 UX 검토에서 복귀 장면을 먼저 봅니다. 같은 비활성 여행을 보던 중 연결이 돌아올 때 헤더 변화와 제한 해제만으로 복귀를 알아차리는지, 기존 데이터가 없는 경우에도 상태가 이해되는지 확인합니다. 초기 unknown 해소·단순 재확인·다른 여행으로 이동한 경우도 구별합니다.
2. 기존 표시로 충분하면 별도 복구 토스트를 생략하는 정책 변경안을 제시합니다. 충분하지 않으면 부족한 안내만 추가합니다. 연결 복귀를 알릴지 데이터 갱신 성공을 알릴지 먼저 정하고, 그 의미에 맞는 기존 상태를 사용합니다. 토스트를 띄우려고 GET을 만들지는 않습니다.

2-A·2-B의 제한과 즉시 내용 복귀는 이 판단과 양립하므로 되돌릴 이유가 보이지 않습니다. 다시 볼 대상은 **2-C를 반드시 추가 구현해야 한다는 계획과, 과거의 조회 성공 알림을 새 흐름에 그대로 적용할 수 있다는 가정**입니다. 기존 데이터가 있는 재조회 실패 때 내용을 유지하고 재시도를 안내하는 방안도 아직 추천 단계이므로 확정 정책에 섞지 않아야 합니다.

이번 검토는 제공된 정책과 조사 기록에 근거하며, 제품 코드나 실제 UX를 직접 확인한 결과는 아닙니다. Ticket에는 이 확인을 2-C 구현보다 앞에 두는 변경을 제안합니다. 알림을 생략하거나 의미를 바꾸는 정책은 사용자 판단을 거쳐 확정할 부분이고, 이번에는 구현이나 기존 문서를 변경하지 않았습니다.
