# 작업물 이해 브리핑 — 인증 인터셉터

이 코드는 **일반 API와 동기화 요청에 현재 로그인 세션의 access token을 붙이는 공통 관문**이에요. 토큰이 없거나 서버가 `401`(인증 실패)을 돌려주면 refresh token으로 새 토큰을 받아 요청을 이어갑니다. 갱신이 불가능하다고 확인되면 다시 로그인이 필요한 상태로 바꿉니다. 아래 설명은 질문에 담긴 2026-09-22 코드와 함께 제공된 관련 파일을 읽어 재구성한 흐름이며, 앱 실행을 관찰한 결과는 아닙니다.

예를 들어 여행 목록을 요청할 때는 다음 순서로 움직입니다.

1. **요청 직전:** `config.sessionId ??= ...`가 요청에 세션 표식이 없을 때 현재 store의 `sessionId`를 붙입니다. 앞서 물으신 `??=`가 바로 여기 쓰였어요. `sessionId`는 토큰 자체가 아니라 *이 요청이 어느 로그인 세션에서 시작됐는지* 식별하는 `symbol`입니다. `assertCurrentSession`은 이 표식이 지금도 유효한 로그인 세션인지 확인합니다.
2. **토큰 준비:** 현재 세션의 access token이 있으면 `Authorization: Bearer ...` 헤더에 넣어 보냅니다. 없으면 `renewSession`이 refresh token으로 `/api/auth/refresh`를 호출하고, 새 토큰을 저장한 뒤 헤더에 넣습니다. 갱신 요청은 인증 인터셉터가 없는 `authAxios`를 사용하므로 자기 자신을 다시 호출하지 않습니다.
3. **응답 확인:** 성공 응답도 `assertCurrentSession`을 거칩니다. 요청하는 동안 로그아웃하거나 다른 세션으로 바뀌었다면 오래된 요청의 응답을 정상 결과로 넘기지 않고 `AuthRequiredError`를 던집니다.
4. **서버가 `401`을 준 경우:** 원래 요청에 `authRetried = true`를 표시하고 토큰을 갱신한 뒤 `client(request)`로 **한 번 다시 보냅니다**. 그 재시도도 `401`이면 `rejectCredentials`가 재인증 필요 상태로 바꾸고 `AuthRequiredError`를 던집니다. `401`이 아닌 오류는 이 인증 재시도 경로에 들어가지 않습니다.

`renewSession`의 `refreshes` Map은 같은 `sessionId`로 동시에 여러 요청이 갱신을 요구할 때 **하나의 갱신 Promise를 공유**하게 합니다. 요청마다 refresh API를 중복 호출하지 않도록 하는 장치예요. 작업이 끝나면 Map에서 제거합니다.

갱신 자체의 실패도 구분합니다. refresh token이 없거나 refresh API가 `401`/`403`을 반환하면 자격 증명이 거부된 것으로 보고 재인증을 요구합니다. 연결 실패나 서버 장애 등 다른 오류는 로그인 실패로 확정하지 않고 원래 오류를 전달합니다. Store의 `requireReauthentication`은 먼저 메모리의 토큰을 비우고 상태를 `reauth-required`로 바꾼 다음 기기에 저장합니다. 저장이 실패해도 호출자에게는 `AuthRequiredError`가 전달됩니다. 새 토큰을 저장하는 중 세션이 바뀌면 Store가 적용을 거부하고, 이 코드도 인증 오류로 처리합니다.

핵심은 **오래된 요청을 새 로그인 세션의 토큰으로 계속 진행시키지 않는 것**입니다. 요청, 갱신, 응답, 재시도 사이에 `sessionId`를 다시 확인하는 이유가 여기에 있습니다. `setupSyncAuthInterceptors`는 같은 함수를 가리키므로 동기화 API에도 이 인증 기준이 적용됩니다. 제공된 사용처에서는 일반 API의 `fetcher.ts`와 동기화 API의 `sync/api.ts`가 각각 설치합니다. 이 설명은 제공된 코드의 연결과 조건에 한정되며, 실제 서버 응답이나 실행 결과까지 확인한 것은 아닙니다.
