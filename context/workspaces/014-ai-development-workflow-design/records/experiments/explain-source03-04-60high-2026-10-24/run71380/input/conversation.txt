- **검색·길찾기·지도:** 강제 online 표시가 실제 offline 요청을 열지 않도록 했습니다. 이것도 기존 debug 합의에 포함됩니다.

반면 transaction 원자성, sync engine의 결과·재시도, cleanup, DB/auth 실패 화면과 인증 guard 전체 재설계는 진행하지 않았습니다. 별도 draft·자동 저장·캐시 관리 시스템도 추가하지 않았습니다.

1. **네트워크 상태를 관측하는 책임과 사용하는 책임을 구별했습니다.**

   Network Store는 인터넷 연결 신호를 받아 `online`, `offline`, `unknown`으로 표현합니다. `unknown`은 초기 확인 전뿐 아니라 사용 중 관측이 다시 불확실해진 경우에도 사용합니다.

   판정은 기존에 합의한 그대로입니다. 두 신호 중 하나라도 명시적으로 false이면 offline, 둘 다 true이면 online, 나머지는 unknown입니다. 10초가 지나도 unknown을 offline으로 바꾸지 않습니다. “확인 중” 안내를 “확인하지 못했음”으로 바꾸는 시간일 뿐입니다.

   이번 품질 개선에서는 이 Store를 더 분할하지 않았습니다. 구독·타이머·재확인 요청을 같은 파일의 private action factory가 소유하는 기존 구조를 유지했습니다.

   소비자는 목적에 맞는 값을 읽습니다.

   - 실제 요청과 sync는 실제 관측값을 읽습니다.
   - 화면 표시와 제한 시뮬레이션은 debug 강제 설정을 반영한 값을 읽습니다.
   - 재확인 안내는 연결 상태와 별도의 확인 진행 상태를 읽습니다.

   이 차이는 [Store의 실제·표시 API](/Users/hammyeong-yeon/Desktop/10_work/noline/apps/client/src/shared/store/network.ts:257)에 드러납니다. 예를 들어 debug에서 online으로 표시해도 실제 상태가 unknown이면 서버 요청을 허용하지 않습니다.

   품질 측면에서는 “이 online이 실제 관측인지 화면용 강제 값인지”를 호출하는 곳마다 추측하는 부담을 줄였습니다.

2. **앱 진입 준비와 sync 실행 준비를 구별했습니다.**

   앱을 켰을 때 네트워크 확인과 DB·인증 준비는 독립적으로 시작합니다. 네트워크 결과가 늦다고 DB 초기화나 인증 복원을 기다리게 하지 않습니다.

   Root에는 의미가 다른 두 값이 있습니다.

   - `isAppReady`: 준비 시도가 끝났으므로 Splash를 해제할 수 있는가.
   - `isDatabaseReady`: DB 초기화가 실제로 성공했는가.

   이 구분이 필요한 이유는 준비 시도가 실패해도 종료될 수 있기 때문입니다. “준비가 끝났다”는 값 하나를 DB 사용 가능의 증거로 사용하면 실패한 DB를 대상으로 sync를 시작할 수 있습니다. 현재 Root는 실제 DB 성공을 Provider에 전달합니다. [Root의 준비 처리와 Provider 연결](/Users/hammyeong-yeon/Desktop/10_work/noline/apps/client/app/_layout.tsx:173)

3. **데이터를 어느 여행 기준으로 처리하는지 호출부에서 명확하게 전달했습니다.**

   Activation Router는 여행 데이터의 Local/Remote 분기를 맡습니다. 활성 여행은 Local SQLite, 비활성 여행은 실제 online에서 Server API를 사용합니다.

   이전에는 Trip 수정·삭제가 “앱에 활성 여행이 하나라도 있는가”에 영향을 받았습니다. 활성 여행 A가 있다는 이유로 비활성 여행 B의 수정이 Local로 갈 수 있는 구조였습니다. 지금은 **수정하려는 B의 tripId**로 B의 활성 여부를 판단합니다.

   Schedule·Expense 수정과 삭제에도 문제가 있었습니다. 소속 여행을 알아내려고 데이터를 먼저 Local에서 찾았습니다. 하지만 비활성 여행의 데이터는 서버에만 있을 수 있습니다. 그러면 서버 작업을 해야 하는데 Local 선조회에서 먼저 실패합니다.

   지금은 화면이 이미 알고 있는 tripId를 mutation hook과 repository에 전달합니다. 예를 들어 경비 수정은 `update(id, tripId, data)`이고 일정별 경비 조회도 `getByScheduleId(scheduleId, tripId)`입니다. [Expense repository의 명시적 여행 입력](/Users/hammyeong-yeon/Desktop/10_work/noline/apps/client/src/entities/expense/repository/expense-repository.ts:36)

   Router는 대상 여행의 활성 여부를 조회한 뒤 최신 네트워크와 override를 확인합니다. 활성 여행은 unknown/offline에서도 기존 Local 저장·queue 경로를 사용합니다. 비활성 여행은 실제 online에서만 서버 작업을 시작합니다. override 중에는 두 쓰기 경로 모두 거부합니다. [대상 여행 mutation 분기](/Users/hammyeong-yeon/Desktop/10_work/noline/apps/client/src/shared/services/offline-prep/router.ts:76)

   여기에는 두 가지 구별도 남겼습니다. 전체 여행 목록은 기존 “활성 여행이 있으면 Local 목록” 계약을 유지했습니다. 새 여행은 아직 활성화된 대상이 없으므로 실제 online에서 Remote로 생성합니다.

   품질 개선의 핵심은 소속 여행을 내부에서 다시 찾아 추론하던 전제를 없애고, 분기에 필요한 입력을 함수 인자에 드러낸 것입니다.

4. **서버 캐시가 남아 있는 것과 지금 내용을 볼 수 있는 것을 구별했습니다.**

   React Query는 이전 서버 응답을 앱 메모리에 보관합니다. 서버 요청을 차단해도 그 응답은 남아 있습니다. 따라서 `data`가 있다는 이유만으로 일정·경비를 렌더하면 비활성 여행의 내용이 offline에서도 계속 보일 수 있습니다.

   합의한 방식은 캐시를 삭제하지 않고 화면에서 접근 정책을 적용하는 것입니다. 이를 위해 역할을 세 부분으로 나눴습니다.

   `useAppPolicy`는 현재 여행의 활성 여부와 화면 네트워크 상태를 해석해 내용 접근 권한·제한 이유를 제공합니다. 활성 여부를 아직 읽는 중인 상태도 inactive로 단정하지 않고 로딩으로 구별합니다. [내용 접근 정책](/Users/hammyeong-yeon/Desktop/10_work/noline/apps/client/src/shared/policy/useAppPolicy.ts:85)

   `useTripContentAccess`는 조회 상태와 복구 과정을 다룹니다. 같은 비활성 여행에서 실제 연결이 회복되면 다시 조회하고 성공 뒤 내용을 엽니다. 실패하면 일반 오류와 재시도 상태를 보여 줍니다. [내용 복구 처리](/Users/hammyeong-yeon/Desktop/10_work/noline/apps/client/src/shared/policy/useTripContentAccess.ts:30)

   `TripContentStatus`는 그 결과를 기존 정책 안내와 버튼으로 표시합니다. 일정·경비 화면은 본문을 내용 또는 제한 안내 중 하나로 선택하고 여행 선택 UI와 수정 Drawer는 밖에 유지합니다. [일정 화면의 실제 본문 연결](/Users/hammyeong-yeon/Desktop/10_work/noline/apps/client/src/screens/ScheduleScreen.tsx:228)

   설명용으로 비활성 여행 B의 경비를 보고 있다고 가정하면, 현재 코드는 다음 흐름을 만듭니다.

   1. 실제 offline이 되면 B의 선택과 캐시는 유지하고 경비 내용 대신 제한 안내를 보여 줍니다.
   2. 실제 online으로 돌아오면 B의 경비를 다시 조회하며, 성공 전에는 이전 내용을 공개하지 않습니다.
   3. 성공하면 최신 내용을 열고 복구 안내를 표시합니다. 실패하면 재시도를 제공합니다.
   4. 사용자가 그 사이 다른 여행으로 이동했다면 B의 늦은 완료가 현재 화면의 복구 상태나 안내를 바꾸지 않습니다.

   초기 unknown이 처음 online으로 확인되는 경우에는 장애 복구 안내를 붙이지 않습니다. 실제 offline을 겪은 뒤 조회가 성공한 경우를 구별합니다.

   상세 화면에도 이 연결이 필요한 이유가 있습니다. 목록에서 내용을 가려도 이미 열려 있는 상세가 캐시를 그대로 보여 주면 같은 정책을 우회합니다. 일정 상세는 일정과 연결 경비의 조회가 모두 성공해야 복구 내용을 엽니다. [상세 화면의 두 조회 연결](/Users/hammyeong-yeon/Desktop/10_work/noline/apps/client/src/screens/ScheduleDetailScreen.tsx:24)

   목록과 상세가 같은 query를 동시에 관찰할 수도 있습니다. 복구 조회에는 `cancelRefetch: false`를 사용해 이미 진행 중인 요청을 취소하고 새 요청을 만드는 대신 완료를 공유합니다. 이 부분은 실제 React Query를 사용하는 [다중 소비자 회귀 검사](/Users/hammyeong-yeon/Desktop/10_work/noline/apps/client/tests/shared/policy/content-query-concurrency.test.tsx:51)로 확인했습니다.

5. **저장 차단과 입력 보존을 서로 다른 책임으로 유지했습니다.**

   화면의 정책 안내는 현재 제한을 설명합니다. 실제 저장·삭제 차단은 Router가 실행 순간에 합니다. 버튼마다 unknown 조건을 복제하지 않았습니다.

   예를 들어 비활성 여행의 경비를 입력하다가 unknown이 되어 저장을 누르면, Router가 서버 전송 전에 거부합니다. 폼은 그대로 있고 기존 오류 처리에서 “연결을 아직 확인하지 못했다”는 이유를 보여 줍니다. 연결이 회복돼도 자동 저장하지 않으며 사용자가 다시 누릅니다.
