# Case A — 로그인 작업 설명 요청의 수행 관찰

대상: `read/noline-demo`. 요청: “현재 로그인 작업의 선택 이유와 어디까지 확인했는지 설명해줘.”

## 실제 답변

현재 선택은 **인증이 끝난 시점과 조회가 끝난 시점을 이름과 안내에서 구별하는 것**입니다. 그래서 `signInAndRequestRefresh`는 인증 적용 뒤 조회를 요청한다는 일을, `onSignedIn`은 인증 적용이 끝났다는 시점을 드러냅니다. 기존 `loginAndRefresh`·`onCompleted`도 주석을 읽으면 사용할 수 있지만, 같은 동작과 같은 주석을 둔 비교에서는 현재 이름이 완료 범위를 코드 자체에서 더 잘 드러낸다고 판단했습니다. 내부 소비자 두 곳만 사용하는 조건은 바꿀 비용을 낮춥니다. 이 이름이 모든 Noline 코드의 규칙으로 정해진 것은 아닙니다.

조회를 기다리지 않는 이유는 지금의 Login·Reauth가 최신 조회값을 즉시 사용하지 않기 때문입니다. 인증 저장과 공개 상태 반영이 끝나면 Login은 “로그인 완료”를 안내하고 이동 함수를 부르며, Reauth는 “인증을 복구했어요”를 안내하고 닫기 함수를 부릅니다. 조회 실패가 인증을 되돌리지 않는다는 계약은 이 대기 선택과 별개입니다. 조회 결과가 필요한 새 소비자가 생기면 조회를 기다리면서도 인증 성공과 조회 실패를 구별할 수 있습니다. 초기 입력의 “로그인과 화면 갱신 완료”라는 안내는 실제 보장보다 넓어서 현재 안내로 맞췄습니다.

확인 범위는 **메모리 기반 예제의 저장·공개 상태·후속 조회·완료 전달과 두 소비자의 함수 호출까지**입니다. 2026-10-19 실행 기록에는 검사 7개가 모두 통과했고 정상·조회 실패 예제를 실행했다고 남아 있습니다. 검사 내용은 저장 전 새 상태를 공개하지 않는지, 저장 실패 때 기존 상태와 여행이 남는지, 조회가 대기 중이어도 인증 완료를 전달하는지, 조회의 동기·비동기 오류를 따로 전달하는지, 인증 실패·귀속 불명 데이터가 후속 저장으로 진행하지 않는지, 두 소비자가 알맞은 안내와 이동·닫기를 요청하는지입니다. 이번에는 해당 코드와 검사 본문을 읽어 기록의 주장 범위와 대조했으며, 새로 실행한 결과로 보고하지 않습니다.

실제 UI 전환, 서버·기기 저장소·Query 라이브러리 연결, DB·queue 조율, 동시 로그인·로그아웃, 부분 저장 실패와 재시작 복구, callback 자체의 예외는 확인하지 않았습니다. 저장 실패 시 이전 저장값을 보존하는 어댑터와 정상 반환하는 callback을 전제합니다. 이 작업은 초기 가정에서 만든 실행 예제이며 실제 Noline 제품의 개명·통합이나 사용자 수락까지 마친 상태는 아닙니다. 선택의 직접 근거는 `records/2026-10-19-06-naming-alternatives.md`, 확인 범위는 `records/2026-10-19-03-execution.md`와 현재 `state`에서 찾을 수 있습니다.

## 진입점과 선택한 근거

- 실제 복사본의 root `AGENTS.md`, `README.md`, `context/README.md`, `context/USAGE.md`, `context/work/AGENTS.md`, Work·Workspace 목록을 읽었다. 한정 설명 요청이므로 개발 전체 재개나 새 Work 생성을 수행하지 않았다.
- `../skills/README.md`, `../skills/explain/SKILL.md`, 설명 작성 상세와 공통 설명·근거 기준을 적용했다. 설명 요청이 지속 파일의 쓰기 권한을 만들지 않는다는 경계를 따랐다.
- Work 001의 README, memory 색인, state, output, Personal·Project 선택, Spec의 목표·현재 가정, 입력 선택·동일 코드 명명 비교·실행 기록을 읽었다. 직접 근거가 없는 “실제 이해 속도 개선”이나 “실제 제품 개명 이력”을 답에 넣지 않았다.
- Personal의 개발 공통과 이름·완료 본문, Project의 읽기 기준·인증 계약·현재 인증 흐름을 읽었다. 비대기와 실패 분리의 선택이 별개라는 계약을 적용했다.
- `examples/authentication/src/{authentication,device-session,consumers}.mjs`와 `tests/authentication.test.mjs`를 직접 읽었다. 저장 await 뒤 공개 상태 반영, 조회 Promise 비대기, 두 소비자의 안내·행동과 검사 assertion을 확인했다.

## 실제 변경과 직접 확인

대상 복사본 내부 변경 없음. 이 관찰 파일만 요청된 복사본 바깥 위치에 작성했다. 코드·검사 열람은 수행했지만 테스트와 데모는 A에서 재실행하지 않았다. “7개 통과”와 정상·실패 데모 결과는 명시한 기존 실행 기록의 사실이다.

첫 파일 탐색 뒤 선택 기록 이름을 `2026-10-19-01-context-selection.md`로 한 번 추정해 열려 했지만 파일이 없었다. 이후 memory에 연결된 실제 `2026-10-19-01-input-selection.md`를 읽었다. 없는 파일을 근거로 사용하지 않았다.

## 미확인·남은 일

요청된 설명은 완료했다. 실제품 통합·추가 소비자 요구·저장소 실패 복구·callback 예외는 기존 예제의 범위 밖이며 이번 읽기 요청으로 수행하지 않았다. 새 소비자가 조회 결과를 즉시 써야 하면 대기와 실패 계약을 재판단해야 한다. 코드·문서 수정이나 Work 상태 변경은 시작하지 않았다.

원본 ai-workspace, 다른 Desktop 저장소, 다른 담당자의 복사본, 외부 서비스에 접근하지 않았다. 패키지 설치·커밋·child agent 생성은 하지 않았다.
