# 맥락 연결 프로토타입의 제한 수행 확인

2026-10-26. 실제 prototype을 임시 폴더의 read·update·create 세 복사본으로 나누고 새로운 수행자에게 그 대상과 요청만 제공했다. 원본 저장소·다른 Desktop 조사, 제품 코드 변경·설치·외부 서비스·커밋은 범위에서 제외했다. 필요한 읽기·문서 반영은 실제 복사본의 root·context·스킬을 따라 수행했다. 원본 prototype에 새 Work나 시험용 오류를 만들지 않았다.

읽기와 갱신은 한 수행자가 별개 복사본에서 순서대로 수행했다. B는 현재 파일이 같다고 가정하지 않고 직접 읽었다. 생성과 전환은 다른 새 수행자가 같은 복사본에서 이어 수행했다. 각 요청1회이며 독립 반복 비교·성능 실험이 아니다. Main은 기대 결론·수정할 위치를 수행자에게 주지 않았다.

갱신 복사본에만 Project current의 ‘실제 환경까지 확인한 상태가 아니다’를 ‘실제 환경에서 확인했다’로 바꿨다. 나머지 계약·코드·Work 기록은 실제 메모리 한계를 유지했다. 이 오류는 실제 prototype의 결함으로 발견한 것이 아니라 정정 흐름을 확인할 입력이다. 수행자는 코드·검사·기존 기록과 대조하고, 같은 수행에서 기존7개 검사와 정상/조회 실패 데모를 실행했다고 반환했다. Main은 해당 실행을 중복 실행하지 않고 실제 파일 diff와 보존 경계를 확인했다.

## Main이 직접 확인한 것과 한계

- [입력·전후 해시와 파일 변화](../../receipts/context-prototype-integration-2026-10-26/file-deltas.json)를 대조했다. 읽기 변경0, 갱신 수정1, 생성 추가16·목록 수정1, 전환 추가1·기존6개 수정이며 삭제는 없다. 원래001·코드·스킬의 변경은 없다.
- 새 current의 목표·보존 조건·완료 기준·첫 Ticket을 직접 읽었다. 실제 저장소 입력이 없는 상태와 생성/전환의 완료를 구별하며, 기존 메모리 검사의 성공을 실제품 성공으로 이어 쓰지 않았다. Main의 직접 읽기이며 별도 새 세션의 독립 인수 시험은 아니다.
- 시험 입력의 Markdown/mjs196개는 [manifest](../../receipts/context-prototype-integration-2026-10-26/input-manifest.json)로 고정했다. 이후 원본 prototype에서 달라진 입력은 독립 리뷰를 반영한 walkthrough 한 곳이다. [시험 당시 본문](walkthrough-input.md)을 보존했다. 실행 스킬·관리 계약은 같은 판본이며 새 소비자의 Project 선별 예시는 별도 문서 검토로 확인했다.
- 생성 수행자는 표시 사본 재생성을 한 번 시도했으나 복사본의 marked 모듈 부재로 실패했다. 새 Work 문서 생성·인수와 분리했으며 전환 요청에서는 선택적 표시 작업을 반복하지 않았다. 원본 prototype의 표시 사본은 Main이 기존 제공 의존성으로 별도 재생성·검사했다.
- 자동 발견·host activation·병렬 담당자의 늦은 결과·실제 중단 복구·전체 개발 수행·장기 비용은 시험하지 않았다. 도구 출력 전체를 보존한 녹취는 아니며, 수행자의 관찰 보고와 Main의 파일·본문 대조 근거를 구별한다.

이 결과는 [적용 기록](../../2026-10-26-context-prototype-adoption.md)의 제한 확인 근거다. 복사본의 문안과 새002 Work를 원본 제품에 이식하지 않는다.
