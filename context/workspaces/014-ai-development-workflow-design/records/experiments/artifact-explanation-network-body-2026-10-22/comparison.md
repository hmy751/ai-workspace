# network.ts 기존판·수정판 — 최초 응답 대조

**이번 한 쌍도 수정판의 실질적인 우세를 확인하지 못했다.** 두 판 모두 역할을 먼저 설명하고 상태·호출 흐름·늦은 응답·표시와 실제 값의 경계를 구체화했다. 수정판의 수치 예시와 감시 유지 문장은 더 명시적이지만, 기존판에도 같은 책임과 사례가 있다. 인증 결과와 합쳐도 이번 두 코드 설명 장면에서 본문 교체의 추가 효과가 분명하지 않다는 관찰까지다. 시점 문제나 문서 결과 설명의 개선 필요까지 부정하지 않는다.

## 실행과 입력

- 사용자의 “지금이랑 유사한 사례로 한번더 테스트” 요청으로03 network.ts를 추가했다. 기존 설계의 저장 용량 비교를 자동 실행하지 않았다.

## 원 코드와 사실 대조

Main이 `input/code/network.ts` 전체와 소비자·테스트 발췌를 읽어 확인했다. 테스트를 실행한 것은 아니다.

- **상태 판정:** 하나라도 false이면 offline, 모두 true이면 online, 나머지는 unknown이다. 두 응답 모두 일치한다.
- **초기화와 정리:** currentSession으로 중복 등록을 막고, cleanup은 먼저 null로 무효화한다. override는 초기화하지 않는다. 두 응답 모두 일치한다.
- **관측 반영:** 같은 상태면 돌아간다. online/offline 확정 시 idle로 바꾸고, 새 unknown이면 안내 타이머를 시작한다. 두 응답 모두 일치한다.
- **재확인 순서:** init 확보, 진행 중 Promise 공유, unknown 안내 재시작, 구독 확보, 요청 생성, NetInfo.refresh 호출이다. 기존 session이 있으면 init은 새로 만들지 않는다. 두 응답의 순서와 설명이 코드에 맞는다.
- **결과 적용 조건:** session 동일성, request 동일성, listener 관측 횟수 동일성을 모두 검사한다. listener는 상태 변화 여부와 무관하게 횟수를 늘린다. 두 응답 모두 맞다.
- **대기 종료:** 앱의 대기를 resolve하며 NetInfo 요청 취소는 없다. 정상 완료와 연결 성공을 같게 보지 않는 설명도 맞다.
- **소비 경계:** Root의 init/cleanup, header의 display 훅, Dashboard의 각 상태 구독이 발췌와 맞는다. getter 직접 읽기와 React 구독, 실제 값과 override의 차이도 맞다.

설명용 값을 관찰된 실행값으로 제시하지 않았고, 실기기 실행을 확인했다거나 보존 테스트를 이번에 통과했다고 주장하지 않았다. 질문의 답을 바꾸는 사실 오류는 이 대조에서 찾지 못했다.

## 이후 실제 대화가 보여 주는 범위

평가용 원문1246에서 사용자는 “물론 리프레시나 앱이 꺼지면 보통 끝날거고 새로고침같이”라고 이해를 확인했다.1251은 “refresh()는 session을 끝내거나 새로 만들지 않습니다”라고 바로잡았다. 당시 첫 답1239에도 session의 필드·init·refresh·cleanup 설명이 있었다. 따라서 구성요소를 설명했다는 사실만으로 수명 관계까지 이해됐다고 판정할 수 없다.

이번 수정판은 “감시를 유지하면서”라고 직접 말하고, 기존판도 init의 중복 방지와 별도 요청을 설명한다. 다만 둘 다1251과 동일하게 “refresh는 session을 끝내거나 새로 만들지 않는다”는 대조를 직접 문장화하지는 않았다. 이 문장 하나의 유무를 필수 정답으로 삼지 않으며, 실제 독자가 그 관계를 복원하는지는 아직 시험하지 않았다. 재질문 예방·사용자 이해 개선은 미확정이다.
