# 자료를 이해할 수 있는 설명으로 만들기

여러 부분의 관계·동작, 선택 이유 또는 관찰에서 나온 결론을 실제 자료와 연결할 때 읽는다. 목적·공통 수행·권한·마무리는 [본체](../SKILL.md)가 맡는다. 여기서는 설명할 범위를 잡고, 실제로 부족했던 문단을 보완하며, 질문에 맞는 근거를 선택하는 방법을 구체화한다. 필요한 절을 선택하며 사례 이름이나 아래 구성을 사용자 답의 필수 항목으로 삼지 않는다.

## 여러 부분을 하나의 설명으로 구성한다

여러 부분을 설명할 때는 이름별 해설을 모으기 전에 어떤 사건이 어느 부분을 호출하고, 무엇을 주고받으며, 어디서 결과가 되는지를 잇는다. 그 관계가 실제 설명 순서와 코드 선택을 정해야 한다. 역할을 소개하는 문단만 앞에 붙이는 것으로 대신하지 않는다. 대표 사건을 따라 필요한 구현을 보여 주되, 별도로 시작하거나 겹치는 경로를 한 번의 실행 순서처럼 잇지 않는다. 아래 인증은 등록·실행·공유가 있는 예시이며 모든 대상이 이런 구조인 것은 아니다.

### 인증 코드 전체: 등록된 처리와 공유 갱신을 함께 읽는다

과거 대화에서 사용자는 `??=`의 문법을 물은 뒤 인증 요청·응답 처리 코드 전체가 어렵다고 했다. 이때는 ‘요청에 토큰을 붙이고401이면 갱신한다’는 요약이나 갱신 실패 한 대목만으로 끝내지 않는다. 다음은 당시 관측 코드로 구성한 전체 설명 예시다. 코드 블록들은 서로 다른 위치의 발췌이며, 등록부를 제외하면 각 블록 내부의 실행문은 연속된 원문이다. 설명용 사건은 실제 관측 결과가 아니다.

이 코드는 **요청이 속한 로그인 세션을 유지하면서, 필요한 토큰 갱신을 같은 세션의 요청들이 공유하고,401 뒤에는 한 번 재시도하도록** 일반 API와 sync의 인증 처리를 연결한다. 먼저 `setupAuthInterceptors`를 호출하는 순간과 나중에 API 요청이 실행되는 순간을 구별한다.

```ts
export function setupAuthInterceptors(client: AxiosInstance): void {
  client.interceptors.request.use(async (config: AuthRequest) => {
    // … 아래에서 설명할 요청 전 처리 …
  });

  client.interceptors.response.use(
    (response) => {
      // … 성공 응답의 세션 검사와 반환 …
    },
    async (error: AxiosError) => {
      // … 아래에서 설명할 실패 응답 처리 …
    },
  );
}
```

위 블록은 원문 등록부에서 callback 내부를 생략해 위치를 표시한 것으로, 실행 가능한 대체 구현이 아니다. 이 함수를 호출하면 Axios가 나중에 사용할 처리를 등록한다. 이 자리에서 요청·응답·갱신이 모두 한 번 실행되는 것은 아니다. API 요청 때는 요청 전 callback을 거치고, 응답이 오면 성공 또는 실패 callback을 거친다. 두 경로가 필요에 따라 같은 `renewSession`을 호출한다.

```text
요청 전 처리 ── 토큰이 없을 때 ──┐
                                ├─ renewSession: 같은 세션의 갱신 작업 공유
401 응답 처리 ── 첫 재시도 때 ───┘
```

이 그림은 두 호출 경로가 하나의 갱신 기능을 사용한다는 관계만 나타낸다. 요청 전 처리에서 반드시 갱신하는 것도, 모든 응답이401인 것도 아니다. 이제 그 연결을 실제 코드에서 읽는다.

**요청 전에는 이 요청의 세션을 잡고, 그 세션의 토큰을 붙인다.** 다음은 request callback의 본문이다.

```ts
config.sessionId ??= useAuthStore.getState().sessionId ?? undefined;
assertCurrentSession(config.sessionId);

if (!useAuthStore.getAccessToken(config.sessionId)) {
  await renewSession(config.sessionId);
}

assertCurrentSession(config.sessionId);

const accessToken = useAuthStore.getAccessToken(config.sessionId);
if (!accessToken) {
  throw new AuthRequiredError();
}

config.headers.Authorization = `Bearer ${accessToken}`;
return config;
```

`??=`는 이 요청에 세션이 아직 없을 때만 현재 세션을 넣는다. 재시도로 같은 요청이 다시 들어오면 원래 세션을 유지한다. 토큰이 없을 때만 갱신을 기다리고, 그동안 로그인이 바뀔 수 있으므로 기다린 뒤 다시 세션을 검사한다. 통과하면 토큰을 헤더에 붙인 요청 설정을 반환한다. 이 반환 뒤 Axios가 요청을 계속 보낸다.

**응답이401이면 갱신 뒤 원 요청을 한 번 다시 보낸다.** 실패 callback에서 요청 설정이 없거나 상태가401이 아니면 원래 오류를 던진다. 다음은 그 조건을 통과한 뒤의 연속된 코드다.

```ts
assertCurrentSession(request.sessionId);

if (request.authRetried) {
  return rejectCredentials(request.sessionId);
}

request.authRetried = true;

await renewSession(request.sessionId);

assertCurrentSession(request.sessionId);

return client(request);
```

`authRetried`는 이 요청이 이미 인증 재시도를 했는지 표시한다. 첫401이면 표시를 남기고 갱신을 기다린 다음, 세션이 여전히 같은지 확인해 `client(request)`로 원 요청을 다시 보낸다. 이 요청도 위의 요청 전 처리를 거쳐 새 토큰을 붙인다. 다시401이면 재시도를 반복하지 않고 `rejectCredentials`로 재인증 요구를 처리한다. 성공 응답 callback도 응답에 저장된 요청의 세션을 검사한 뒤 응답을 반환하므로, 이전 로그인에서 시작한 성공 응답까지 현재 세션의 결과로 받아들이지 않는다.

**두 경로의 `renewSession`은 같은 세션에서 진행 중인 갱신을 공유한다.** 함수의 시작과 끝을 따로 발췌한다.

```ts
const existing = refreshes.get(sessionId);
if (existing) {
  return existing;
}
```

이미 해당 세션의 갱신 Promise가 있으면 그것을 반환한다. 없다면 그 사이 코드에서 `renewal`이라는 갱신 작업을 만든다. 이 작업은 현재 세션 확인, refresh token 확보, 서버 갱신, 받은 토큰 저장을 수행한다. 다음은 작업을 만든 뒤의 보관·정리·반환이다.

```ts
refreshes.set(sessionId, renewal);
renewal.finally(() => refreshes.delete(sessionId)).catch(() => undefined);
return renewal;
```

예를 들어 같은 세션의 두 요청이 거의 함께 갱신을 요구하면, 앞선 요청이 보관한 Promise를 뒤 요청도 반환받아 기다린다. 두 요청이 끝까지 하나로 합쳐지는 것은 아니다. 갱신만 공유하고 각 요청은 자신의 처리로 돌아간다. 갱신이 끝나면 Map에서 항목을 지워 이후 필요한 갱신이 새로 시작될 수 있게 한다. 정리용 Promise의 `catch`와 달리 호출자에게 반환되는 것은 원래 `renewal`이므로, 갱신 실패가 호출자에게 성공으로 바뀌지는 않는다.

갱신의 실패 처리는 서버가 자격 증명을 거부한 경우와 연결·서버 장애를 구별한다. refresh token이 없거나 현재 세션의 갱신이401·403으로 거부되면 `rejectCredentials`를 통해 재인증을 요구하고 인증 오류로 끝낸다. 다른 갱신 오류는 전달한다. 갱신 후 토큰 저장이 수용되지 않은 경우에도 인증 오류로 끝나며 재시도까지 진행하지 않는다. 이 차이를 더 묻는다면 아래의 실제 실패 처리로 내려간다.

이 예시는 등록부에서 실행 시점을 잡고, 두 호출 경로에서 공유 작업으로 합류한 뒤 각 요청으로 돌아오는 연결을 코드와 대응시켰다. 함수 선언 순서를 그대로 따르거나 각 함수의 역할 표만 제시한 구성과 구별한다. 모든 답에 이 목차·도식·발췌 수를 요구하지 않으며, 이미 공유한 전체를 후속 질문마다 반복하지 않는다.

### 같은 코드의 후속: 갱신 실패 때 어느 세션을 바꾸는가

그 뒤 실제로 코드와 순서를 자세히 설명한 응답이 있었지만, 사용자는 갱신 실패 처리의 특정 대목을 다시 물었다. 그때 다음처럼 이름과 순서만 반복하면 관계가 남는다.

> `catch`에서 현재 세션을 확인하고, 상태가401 또는403이면 자격 증명을 거부합니다.

이는 보완 방법을 보여 주기 위한 요약이다. 보완할 핵심은 **작업이 보관한 세션 값과 현재 저장소의 세션 값이 다를 수 있음**이다. 다음은 원자료의 동작에서 구성한 가능한 상황이며 당시 사용자의 내적 혼동을 확정한 진단은 아니다.

이 관계가 구현된 부분을 먼저 보여 준다. 다음은 당시 `renewSession`의 서버 갱신과 실패 처리 발췌다.

```ts
try {
  tokens = await refreshTokens(refreshToken);
} catch (error) {
  assertCurrentSession(sessionId);

  const status = (error as AxiosError).response?.status;
  if (status === 401 || status === 403) {
    return rejectCredentials(sessionId);
  }

  // 연결 실패·서버 장애는 자격 증명이 거부됐다는 증거가 아니다.
  throw error;
}
```

이 실패 처리는 **현재 세션의 자격 증명이 거부된 경우와 다른 오류를 구별하는 일**을 맡는다. 그런데 다른 로그인으로 바뀐 뒤 옛 요청이 실패했다면, 지금 세션을 재인증 상태로 바꾸면 안 된다. 그래서 오류 종류를 판단하기 전에 `assertCurrentSession(sessionId)`가 작업의 세션이 아직 현재인지 확인한다.

| 기다리는 동안의 값 | 설명용 상황에서의 의미 |
| --- | --- |
| 이 작업이 보관한 `sessionId` | 갱신을 시작한 A이며, 로그인 상태가 바뀌어도 이 값 자체가 B로 바뀌지는 않는다. |
| 현재 Store의 세션 | 기다리는 사이 다른 로그인으로 B가 될 수 있다. |
| `assertCurrentSession(A)` | 현재 B와 다르면 예외를 던져 아래 상태 판정과 `rejectCredentials`로 진행하지 못하게 한다. |

A가 여전히 현재라면 그다음 분기로 간다.401·403이면 자격 증명 거부 처리를 반환하고, 그 밖의 오류는 원래 오류를 던진다. 따라서 코드와 함께 **어느 값이 유지되고 무엇과 비교되며 어떤 후속 처리가 막히는지**를 읽을 수 있다. 이 상황이 실제로 관찰됐다고 말하려면 별도의 실행 근거가 필요하다.

반면 `??=` 자체의 뜻만 묻는다면 `config.sessionId ??= 값`은 왼쪽이 `null` 또는 `undefined`일 때만 오른쪽 값을 대입한다는 짧은 설명과 필요한 대비로 끝날 수 있다. 코드 제시가 필요하다는 사실과 전체 인증 흐름·모든 문법을 다시 설명해야 한다는 판단은 다르다.

## 그럴듯한 요약에서 빠진 처리를 채운다

완성된 문장을 보고도 독자가 ‘그 값이 어떻게 그 결과를 만들지?’를 직접 보충해야 한다면 그 중간 처리를 고른다. 코드를 이미 읽었거나 정확한 용어를 썼다는 사실만으로 이 연결이 응답에 생기지는 않는다.

### 동기화 변경: 공유한다고 말하는 것과 공유되는 지점을 설명하는 것

과거 첫 결과 전달 비교에서 실제로 나온 문장이다.

> 실행 중 Promise를 화면용 `isSyncing`보다 먼저 보관하므로 같은 순간의 자동·수동 호출은 한 실행의 완료를 함께 기다립니다.

틀린 문장으로 보지는 않는다. 다만 변경의 의미를 이해하려면 화면 상태가 왜 충분하지 않았는지, 뒤의 호출이 어떤 값을 돌려주는지를 독자가 채워야 한다. 변경 전 코드에서는 `isSyncing`이면 즉시 반환했고, 실행을 시작할 때 `setIsSyncing(true)`를 호출했다. 이 상태 변경 요청은 이미 만들어진 호출 함수의 값을 즉시 바꾸지 않는다. 화면 반영 전에 들어오는 호출에는 여전히 이전 값이 보일 수 있다.

변경 후 코드에서 이 차이를 만드는 부분은 다음이다. 같은 함수의 두 대목을 발췌했고 가운데 시작 가능 조건과 Promise 생성 등은 생략했다.

```tsx
if (inFlightRef.current) {
  return inFlightRef.current;
}

// … 시작 조건 확인 및 run 생성 …
inFlightRef.current = run;
previouslyEligibleRef.current = true;
setIsSyncing(true);
```

이 부분은 **화면의 진행 표시와 실제 실행 공유를 구별한다**는 변화를 보여 준다. 코드 가까이에서 두 호출을 같은 기준으로 비교한다.

| 호출 | 읽거나 보관하는 값과 결과 |
| --- | --- |
| 첫 호출 | 시작 조건을 통과해 만든 `run` Promise를 `inFlightRef.current`에 바로 넣고 화면 상태를 바꾼다. |
| 뒤의 호출 | ref에 이미 있는 Promise를 위 조건에서 반환하므로 새 실행을 만들지 않고 먼저 시작한 실행의 결과를 기다린다. |

ref는 화면이 다시 그려졌는지와 관계없이 같은 값을 바로 읽을 수 있다. 그래서 화면의 진행 표시는 `isSyncing`이, 진행 중 실행의 공유는 `inFlightRef`가 맡는다. 발췌에서 생략한 시작 조건을 만족하지 못한 호출까지 실행을 시작한다고 해석하지 않는다.

핵심 차이는 코드 블록의 수가 아니라 상태 반영 시점·즉시 보관하는 값·후속 호출의 반환을 이은 것이다. 이 한 문단으로 전체 변경 보고를 대신하지 않는다. 또한 반환 결과의 `completed`는 engine이 반환됐다는 뜻이며 큐의 모든 항목이 서버에 반영됐다는 보장은 별도 계약에서 확인해야 한다. 실제 응답에서는 현재 질문의 의미를 바꾸는 이런 경계도 가까이 설명한다.

이 예시는 작성 중 빠진 연결을 찾는 방법이다. 매번 부족한 초안과 수정본을 함께 출력하거나 모든 설명에 전후 코드를 요구하는 양식이 아니다. 뜻 하나를 묻는 질문에는 짧은 정의와 필요한 조건이면 충분할 수 있다. 예를 들어 `value ??= fallback`에는 `null`·`undefined`일 때 대입하고 `0`·`false`는 유지한다는 대비로 답할 수 있다.

## 선택의 적절성과 변경의 이득을 판단한다

구조의 역할과 협력 관계를 설명하는 데 필요한 근거와, 그 배치가 적절한지 판단하는 데 필요한 근거는 다르다. 적절성을 묻는다면 현재 요구·사용처·실패나 변경 상황에서 의미 있는 대안의 이득과 부담을 비교한다. 복잡한 처리가 남았다면 어떤 조건 때문에 필요한지도 설명한다. 당시 선택 의도는 결정 기록에서, 현재 효과의 추론은 실제 구조에서 확인한 범위로 구별한다.

### 여행 목록: 역할 이름으로 복구 가능성 판단을 대신하지 않는다

과거 여행 앱에서 생성·수정·삭제 후 로컬 목록 사본을 갱신하고 있었다. 사용자가 책임 분리가 적절한지 다시 검토해 달라고 하자, 당시 검토는 활성 여행이 있을 때 목록 조회가 로컬만 읽어 사본 갱신 실패를 새로고침으로 복구하지 못한다는 문제를 짚었다. 다음은 그 판단을 설명하기 위한 상황이며 현재 제품의 실행 결과가 아니다.

> 서버에서 여행을 만드는 데 성공했지만 로컬 목록 반영은 실패했다고 하겠습니다. 생성 코드만 사본을 고치고 목록 조회는 로컬만 읽는다면, 새로고침해도 빠진 여행을 다시 가져오지 못합니다. 목록 조회가 서버 결과를 받아 사본을 맞추게 하면 생성 직후 갱신이 실패해도 이후 조회에서 다시 시도할 수 있습니다. 이 상황에서 책임을 옮길 이유는 복구 경로를 만드는 데 있습니다.

보존된 후속 코드의 목록 조회에는 다음 서버 경로가 있다.

```ts
const response = await TripApi.fetchAllTrips();
const result = await TripLocal.refreshTripListLocal(response.data, sessionId, signal);
return { trips: result.trips, source: result.hasLocalTrips ? 'mixed' : 'remote' };
```

이 코드는 서버 응답을 로컬 목록에 반영한 결과로 조회 응답을 만든다. 생성 훅은 저장 성공 뒤 목록 갱신을 요청한다. 따라서 저장과 조회의 연결, 이후 조회가 다시 사본을 맞출 수 있는 이유를 설명할 수 있다. 단, 갱신 요청 자체가 조회 성공을 보장하지 않으며 서버 값으로 로컬의 미전송 변경을 덮지 않는 보호도 필요하다. 이 발췌 하나가 그 보호나 모든 복구 조건을 증명하지는 않는다. 이런 조건을 함께 봐야 책임을 옮기는 선택의 이득과 남는 부담을 판단할 수 있다.

반면 ‘Repository와 Router가 무슨 역할이냐’에는 같은 앱의 다음 코드가 더 직접적이다.

```ts
return await routeChildMutation(id, {
  local: () => TripLocal.updateTripLocal(id, input),
  remote: () => TripApi.fetchUpdateTrip(id, input),
});
```

이 부분에서는 **실제 변경을 제공하는 책임과 실행 경로를 고르는 책임**을 코드에서 함께 볼 수 있다.

- **Repository:** `local`과 `remote`에 함수를 넣어 로컬·서버에서 실제로 할 일을 제공한다. `() => ...`로 넘겼으므로 이 객체를 만드는 순간 두 변경을 모두 실행하는 것은 아니다.
- **Router:** `routeChildMutation`이 대상 여행의 상태·연결 조건에 따라 제공된 실행 경로를 고른다. 호출부는 그 결과를 기다려 반환한다.

이 발췌만으로 선택 조건의 정확한 내용을 알 수는 없으므로 그 조건이 질문에 중요하면 Router 구현을 확인한다. 이 역할 설명이 앞의 목록 복구 문제에 답하는 것은 아니다. 반대로 책임 배치 검토가 요청됐다면 역할 소개에 그치지 않고 맡은 검토를 수행해야 한다.

### 전후 비교와 선택 질문에 적용한다

‘더 좋아졌다’고 말할 때는 비교할 기준을 고정하고 diff에서 찾은 차이를 해석하는 데 필요한 전후 구현·사용처·관찰을 대조한다. 같은 입력이나 수정 과제에서 무엇이 달라졌는지 본다. 읽기·수정 부담이 목표라면 전후에 함께 추적하거나 고쳐야 하는 책임·사용처를 비교한다. 이름·함수 수의 변화만으로 품질 개선을 인정하지 않으며, 구조에서 예상한 이득과 실제 사용에서 확인한 효과를 구별한다.

현재 구조의 이점을 묻는 질문에는 현재 요구와 사용처로 답할 수 있다. 전후 자료가 없으면 과거 차이를 만들어내지 않는다. ‘어디 갔나’, ‘왜 없나’도 바로 복원 명령으로 바꾸지 않는다. 예를 들어 반환 항목이 사라진 이유를 물었다면 소비자가 여전히 그 값을 필요로 하는지, 대체 경로의 이득과 부담이 무엇인지 보고 의견을 낸다. 구현 변경은 본체의 권한 경계를 따른다.

## 작업 결과는 원래 질문에 연결한다

보고서나 첫 결과를 설명할 때는 원래 목표를 판단할 관찰을 골라 결론으로 잇는다. ‘연결이 제한됐다 돌아와도 보던 목록이 유지되는가’에는 정상 화면 한 장보다 같은 대상의 제한 상태와 복귀 뒤 관찰이 필요하다. 과거 보고서 사건의 관계를 추리면 다음처럼 답할 수 있다.

> 같은 비활성 여행에서 제한을 해제한 뒤 경비 합계와 기존 카드가 돌아오는 것을 확인했습니다. 이 관찰은 목록이 복귀하는지에 답하므로 그 흐름을 추가 수정 대상으로 남길 이유는 없어졌습니다. 다만 앱으로 돌아오는 순간 네트워크를 재확인하는 연결은 별도 문제이며, 이 목록 관찰로 해결됐다고 말할 수 없습니다.

이는 원문 그대로의 최종 보고서나 현재 제품 확인이 아니다. 문장을 쓰기 전에 해당 조건의 실제 관찰이 있어야 한다. 이전 문제의 후속이라면 그 뒤 변경과 이번 확인이 어떻게 이어지는지도 설명한다. 관찰이 없다면 필요한 확인으로 돌아가거나 접근 한계가 결론을 어떻게 제한하는지 밝힌다. 남은 확인을 고지하는 것과 맡은 확인을 수행하는 것은 다르다.

예시의 출처·판본·발췌 범위는 [형성 근거](../_background/evidence.md#실행-상세-예시의-출처와-한계)에 있다. 실행 중 모든 형성 자료를 읽을 필요는 없다. 실제 답에서는 역할·처리·이유를 별도 긴 해설로 쌓지 않고 현재 질문을 푸는 관계로 이어 쓴 뒤 [본체의 마무리](../SKILL.md#답의-범위와-마무리를-지킨다)를 따른다.
