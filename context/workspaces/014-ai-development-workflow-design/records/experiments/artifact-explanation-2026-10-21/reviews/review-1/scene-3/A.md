**`access`는 그대로 필요한데, 제가 `refetch`를 분리하는 설명에서 빠뜨렸습니다.** 사용자가 요청한 것은 정책을 고려해야 하는 메서드를 `query` 밖으로 옮기는 것이었고, 접근 조건 자체를 없애자는 것은 아니었습니다.

앞서 논의한 역할을 유지하면 반환 형태는 다음과 같아야 합니다. 아래는 설계 정리이며, 실제 구현을 확인한 코드는 아닙니다.

```tsx
const { query, access, actions, view } = useSchedulesRead(tripId);
```

- **`query`**: 데이터·오류·조회 상태. `refetch`는 제외하되 성공 상태에 따른 데이터 타입 관계는 유지합니다.
- **`access`**: 현재 표시·조회가 가능한 조건. 화면이나 폼이 버튼과 안내를 구성할 때 참조합니다.
- **`actions`**: 정책을 확인하고 실행하는 행동. `actions.refetch()`가 재조회 실행을 맡고, 차단됐다면 그 결과를 반환합니다.
- **`view`**: 접근 조건과 조회 상태를 종합한 표시 결과. 목록 전체나 폼의 보조 조회 영역에서 필요한 경우 사용합니다.

예를 들어 **재조회 버튼을 비활성화할지 판단하는 데는 `access`를 쓰고, 버튼을 눌렀을 때의 실행은 `actions.refetch()`가 맡습니다.** 화면에서 버튼을 막는 것과 실행 시 정책을 확인하는 것은 역할이 다르므로, `actions`가 생겼다고 `access`가 불필요해지지는 않습니다.

대화에서 확인되는 것은 제가 반환 구조를 `query / actions / view`로 설명하며 `access`를 누락했다는 점입니다. 실제 코드에서도 빠졌는지는 제공된 자료로 확인할 수 없습니다. **일정 목록 한 곳만 적용한다는 범위와 별개로, `access`를 제거할 근거는 앞선 논의에 없었습니다.**
