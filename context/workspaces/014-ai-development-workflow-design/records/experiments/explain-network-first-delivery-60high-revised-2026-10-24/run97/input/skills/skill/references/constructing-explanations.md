# 자료에서 설명할 부분을 고르고 연결하기

여러 부분의 관계·동작, 선택 이유 또는 관찰에서 나온 결론을 실제 자료와 연결해야 할 때 사용한다. 설명 전체의 목적·범위·마무리는 [본체](../SKILL.md)가 맡는다. 여기서는 무엇을 골라 어떻게 한 대목의 설명으로 만드는지 다룬다. 아래 절은 한 답에서 함께 사용할 수 있고, 예시의 작성 과정을 사용자 답의 목차로 복사할 필요는 없다.

## 관계가 드러나는 부분을 고른다

현재 질문을 푸는 관계가 어디에서 드러나는지 찾는다. 코드에서는 판단하는 조건, 위임하는 호출, 값이 바뀌거나 반환되는 부분이 될 수 있다. 문서에서는 주장과 이를 지지하거나 제한하는 관찰이 될 수 있다. 정의나 이름만으로 충분한지, 실제 연결을 보여야 뜻이 드러나는지는 질문으로 판단한다.

전체 구조를 설명할 때는 대표 입력·사건 하나가 어디서 시작해 어떤 판단·위임을 거쳐 결과나 외부 효과로 이어지는지 잡고, 그 흐름을 설명할 부분을 고른다. 각 파일의 설명을 따로 쓴 뒤 나열하기보다 같은 사건에서 책임이 어떻게 이어지는지 연결한다. 이때 대표 경로 밖의 조건이 현재 답을 바꾸면 함께 드러내되 모든 경로를 펼치지는 않는다.

선택한 코드에서는 역할뿐 아니라 그 역할을 만드는 실제 처리를 짚는다. 반환값이 다음 처리의 입력이라면 그 값과 소비를 잇고, 대기 여부가 중요하면 무엇의 완료를 기다리는지 대응시킨다. 코드 제시와 모든 문법을 해설하는 깊이는 별개다. 문법 질문에 이어 코드가 어렵다고 한 경우에는 필요한 표현의 뜻을 해당 처리의 값·결과와 연결한다. 사용자가 다시 ‘코드와 함께’라고 말할 때까지 기다리지 않는다.

고른 부분만으로 주장이 성립하는지 대조한다. 호출은 보이지만 대상의 동작이 중요하면 그 구현을 확인하고, type이나 interface만 있다면 실제 provider·사용처·설정이 연결됐는지 필요한 범위를 확인한다. 실행 여부가 질문의 핵심이면 허용된 관찰 근거를 찾는다. 읽은 파일의 수나 선언의 존재로 실제 수행을 인정하지 않는다.

### 작성 과정 예시 — 저장과 목록 갱신

다음은 과거 여행 앱 코드의 보존 발췌를 사용한 설명 예시다. 현재 제품의 실행 결과나 새 시험이 아니다. [형성 근거](../_background/evidence.md)에 출처 식별자와 예시의 확인 범위가 있다.

설명할 것은 **여행 저장이 끝난 것과 화면 목록이 최신 상태가 된 것은 다른 결과**라는 관계다. `TripRepository.create`만 고르면 저장은 설명되지만 그 뒤의 목록 갱신은 설명되지 않는다. 그래서 생성 훅에서 저장과 갱신 요청이 나뉘는 부분, 갱신 helper의 대기 경계, 목록 조회의 반영 부분을 고른다. 아래는 각 원문에서 필요한 부분만 발췌했으며 서로 붙어 있는 하나의 함수가 아니다.

생성 훅 `useCreateTrip`:

```ts
mutationFn: (data: CreateTripRequest) => TripRepository.create(data),
onSuccess: () => cancelAndInvalidateQueries(queryClient, { queryKey: tripQueryKeys.all() }),
```

갱신 helper `cancelAndInvalidateQueries`:

```ts
await client.cancelQueries(filters);
client.invalidateQueries(filters).catch((error) => console.error('[Query] cache refresh failed', error));
```

목록 조회 `getAllWithSource`의 서버 경로:

```ts
const response = await TripApi.fetchAllTrips();
const result = await TripLocal.refreshTripListLocal(response.data, sessionId, signal);
return { trips: result.trips, source: result.hasLocalTrips ? 'mixed' : 'remote' };
```

이 발췌에 붙일 설명은 다음처럼 만들 수 있다.

> 생성 훅은 `create`로 여행 저장을 요청하고, 성공하면 목록을 다시 읽도록 요청합니다. 갱신 helper는 이전 조회의 취소를 기다리지만 새 조회의 완료는 기다리지 않습니다. 실제로 서버 목록을 읽고 기기에 남길 데이터와 조합하는 일은 세 번째 코드의 조회 경로가 맡습니다. 따라서 저장에 성공했어도 그 뒤 조회가 실패하면 화면 목록이 최신 상태가 됐다고 말할 수 없습니다.

핵심은 세 코드 블록의 개수가 아니다. 저장 요청만으로 설명되지 않는 갱신을 어디서 맡는지 보여 주고, 대기 여부의 주장은 실제 helper로 확인해 설명한 것이다. 실제 응답에서는 이 문장들을 해당 코드 가까이에 배치한다. 사용자가 역할 관계만 물었으면 필요한 범위를 고르고, 구체 문법을 묻는다면 그 표현을 더 펼친다. 생략한 전체 함수나 별도의 로컬 보호 조건까지 이 발췌가 모두 증명하지는 않는다.

## 변경 전후를 비교해 이번 변화의 의미를 만든다

변경을 설명할 때는 사용자가 정한 비교 기준을 따른다. 기준이 없으면 관련 이력·작업 상태에서 이번 변경의 시작점을 확인해 밝힌다. diff로 달라진 부분을 찾고, 그 차이를 해석하는 데 필요한 전후 구현과 변경 후 사용처를 함께 읽는다. 동작을 비교하는 근거가 관찰·보고서라면 서로의 조건과 시점이 비교 가능한지도 확인한다. 모든 과거 파일이나 이력을 읽는 것이 목적은 아니다.

같은 입력·사건을 전후에 놓고 어느 처리·책임·결과가 달라졌는지 설명한다. 기존에도 있던 기반, 이번에 바꾼 부분, 그로 인해 생기는 차이를 구별한다. 변경 후 구조를 정확히 설명했어도 그것만으로 이번에 새로 생긴 효과라고 말할 수는 없다. 전후 코드가 길면 차이를 만드는 부분을 발췌하고, 나머지 맥락은 짧게 잇는다.

‘개선됐다’는 주장은 원래 개선하려던 부담이나 결과로 돌아가 확인한다. 읽기·변경 부담이 목표라면 대표적인 읽기나 수정 작업에서 전후에 무엇을 함께 추적하거나 고쳐야 하는지 비교한다. 역할 이름·함수 수가 달라졌다는 사실에 그치지 않고, 실제 책임과 사용처가 나뉘어 줄어든 부담과 여전히 남은 결합을 설명한다. 구조로부터 예상한 이득과 실제 작업·실행에서 확인한 효과는 구별한다.

현재 구조의 이점만 물었다면 그 구조와 관련 사용처로 답할 수 있다. 과거와 비교해 더 좋아졌다고 말할 때 비교 근거를 추가한다. 전후 자료가 없으면 현재 효과를 설명하되 확인하지 못한 과거 차이를 만들어내지 않는다.

## 조건을 바꿔 차이가 생기는 곳을 보여 준다

같은 입력·사건에서 중요한 조건만 바꿔 결과 차이를 설명한다. 모든 분기를 열거하기보다 현재 질문에서 혼동할 수 있는 두 결과를 비교한다. ‘저장 성공·조회 실패’처럼 가능한 경우를 설명했다면 실제 관찰인지 소스로 재구성한 가능성인지 밝힌다. 가상의 값으로 설명할 때 실제 로그인 것처럼 제시하지 않는다.

간단한 개념에도 같은 방법을 쓸 수 있다. `value ??= fallback`을 설명한다면 `value`가 `null`이나 `undefined`인 경우와 `0`·`false`인 경우를 비교하면 대입 조건이 드러난다. 필요한 조건만으로 뜻이 풀리면 큰 구조도나 프로젝트 조사는 필요하지 않다.

관계를 그림으로 보일 때는 실행 순서·데이터 이동·소유 중 무엇을 보여 주는지 분명하게 한다. 분기나 묶음도 근거가 필요한 주장이다. 대표 경로를 전체 구조처럼 그리거나 source에서 재구성한 흐름을 실제 trace처럼 설명하지 않는다. 전후 차이나 정확한 대응은 표가, 이유와 인과는 짧은 문단이 더 명확할 수도 있다.

## 선택 이유와 관찰의 의미를 설명한다

‘왜 이렇게 했나’에는 당시 의도와 지금의 적절성 판단이 함께 들어 있을 수 있다. 당시 이유는 대화·결정 기록에서 확인한 범위로 복원하고, 현재 구조가 만드는 효과에서 추론한 이유와 구별한다. 지금도 적절한지 묻는다면 현재 요구와 소비자, 의미 있는 대안의 효과·비용을 비교해 의견을 낸다. 설명할 수 있는 구조라는 이유만으로 좋은 선택이라고 정당화하지 않는다.

‘어디 갔나’, ‘왜 없나’ 같은 질문을 곧바로 복원·수정 명령으로 바꾸지 않는다. 예를 들어 반환값에서 어떤 항목이 사라진 이유를 묻는다면, 실제 소비자에게 필요한 값과 변경 이유를 대조해 유지·변경 의견을 설명한다. 구현을 바꾸는 권한은 별도 요청과 기존 위임을 따른다.

보고서에서는 원래 질문·맡은 결과를 판단할 기준과 이번 관찰을 연결해 무엇을 해결했는지 설명한다. 예를 들어 검사 통과가 동작 보존을 뒷받침하더라도, 코드를 이해·수정하기 쉬워졌다는 목표에는 실제 책임·사용처의 변화가 별도로 필요하다. 남은 부분이 있으면 단순히 ‘미확인’으로 나열하기보다 이번 결론이나 다음 판단을 어떻게 제한하는지 잇는다.

이전 문제의 후속 자료라면 그 뒤 변경과 이번 확인의 관계도 답에 필요한 만큼 잇는다. 관찰이 답을 만들기에 부족하면 부족한 사실이 무엇인지와 추가 확인 가능성을 판단한다. 설명 순서를 바꾸는 일과 실제로 더 확인해야 하는 일을 섞지 않는다.

### 작성 과정 예시 — 관찰에서 결론으로

다음은 실제 보고서 사건에서 핵심 관계만 추린 작성 예시다. 원문 그대로의 최종 보고서가 아니며 현재 제품 확인도 아니다.

원래 질문은 ‘연결이 제한됐다 돌아와도 보던 목록이 유지되는가’였다. 정상 상태 화면만 골라서는 이 질문에 답할 수 없다. 따라서 같은 여행의 제한 상태와 복귀 뒤 목록을 대조한 관찰을 고른다. 앱 복귀 시 네트워크 재확인 연결이 있는지는 다른 관찰이 필요하므로 한 결론에 섞지 않는다.

> 같은 비활성 여행에서 제한을 해제한 뒤 경비 합계와 기존 카드가 돌아오는 것을 확인했습니다. 이 관찰은 목록이 복귀하는지에 답하므로, 그 흐름을 추가 수정 대상으로 남길 이유는 없어졌습니다. 다만 앱으로 돌아오는 순간 네트워크를 재확인하는 연결은 별도 문제이며, 이 목록 관찰로 해결됐다고 말할 수 없습니다.

관찰을 ‘확인했다’고 쓰려면 실제 그 조건의 근거가 있어야 한다. 위 문장을 얻기 위해 필요한 관찰이 없다면 문장만 복사할 수 없다. 현재 답을 바꿀 사실을 더 확인하거나, 확인하지 못한 이유와 결론의 한계를 설명한다. 그 판단과 실행은 현재 작업 담당자의 권한 안에서 한다.

## 한 답으로 연결하고 필요한 상세만 펼친다

역할·동작·이유를 각각 독립된 긴 해설로 만든 뒤 붙이기보다, 같은 대상이 무엇을 맡고 어떤 조건에서 어떤 결과를 만드는지 이어 쓴다. 각 설명에서 근거가 필요한 문장과 선택한 자료가 대응하는지, 관계의 핵심을 링크 뒤로 미루지 않았는지 확인한다. 이는 작성 중의 대조이며 사용자에게 점검표를 출력하라는 요구가 아니다.

핵심 관계를 이해하는 데 필요한 조건은 가까이에 두고, 그 관계를 바꾸지 않는 보강 자료는 별도 문단이나 링크로 내려 둔다. 더 많은 코드·표·예시가 있다는 사실을 설명의 완성으로 취급하지 않는다. 현재 질문에 필요한 답과 관계가 이어졌으면 [본체의 마무리](../SKILL.md#답의-범위와-마무리를-지킨다)로 돌아간다.
