## Main의 리뷰 전 권고안

**Project의 사실 설명은 원칙적으로 그 사실을 바꾸는 작업에 포함하고, Main은 Work와 전체 반영의 연결을 책임진다. 루프는 경험에서 무엇을 바꿀지 판단하며, 결정 뒤 반영은 같은 방법을 사용한다.** 별도 context 작성자를 기본 역할로 추가하지 않는다.

앞선 “그 단계를 맡은 주체가 상황에 맞춰 정한다”보다 실제 배정의 기본값을 드러내려는 안이다. 모든 읽는 사람에게 쓰기 권한을 주거나, 모든 사실 정정을 Main에게 모으거나, 루프 때까지 보류하는 안은 권고하지 않는다.

### 개발 중

Main은 결과를 맡길 때 관련 Project 사실 설명도 결과의 범위에 포함한다. 기존 관리 계약과 허용된 내용 범위 안에서 담당자가 실제 구현·설정·연결과 직접 관련된 설명을 함께 맞추는 것을 기본으로 제안한다. 파일 목록은 접근점이며, 이미 맡긴 의미 범위의 설명을 다른 문서에서 발견해도 파일이 처음 목록에 없다는 이유만으로 빠뜨리지 않는다. 다른 Owner·새 결정·허용 범위 밖 변경은 Main에게 연결한다. 검토·검증만 맡은 역할이 발견을 이유로 자동 편집하는 뜻은 아니다.

Main이 이미 근거를 아는 작은 정정, 여러 담당자의 결과를 모아야 하는 본문, 공유 편집의 충돌이 있으면 Main이 직접 하거나 한 담당자에게 모아 배정한다. 구현자가 항상 작성해야 하는 규칙은 아니다. 변경이 현재 설명을 바꾸지 않으면 문서를 형식적으로 수정하지 않는다.

### 완료 정리와 뒤늦게 발견한 차이

Main은 실제 코드·본문·확인 결과에서 이번 작업 때문에 설명이 어긋났거나 누락된 중요한 부분을 확인하고 갱신을 마무리한다. 담당자의 반영을 전부 다시 조사하는 별도 문서 심사로 만들지 않는다. 관련 사실을 현재 설명에 맞추는 일을 일반적으로 다음 루프까지 미루지 않는다.

완료 후 또는 루프에서 차이를 처음 발견했다면 그때 바로 정리할 수 있다. 사실과 근거가 분명하고 허용된 범위면 해당 주체가 직접 반영하며, 여러 결과의 종합이나 다른 권한이 필요하면 Main과 연결해 담당을 정한다. ‘루프에서 발견했다’는 이유로 반드시 새 기준 채택 절차를 거치지는 않는다. 제품 약속과 실제 동작이 다른 경우에는 설명 오류인지 제품 결함인지 먼저 구별하고 약속을 구현에 맞춰 낮추지 않는다.

### 경험에서 새 기준·약속을 채택할 때

05 루프는 기존 기준을 유지할지, 제품·개발 방식·도구·문서·스킬 등을 바꿀지 판단하는 책임을 맡는다. 역할의 수·호출 시점·매회 사용자 승인 여부는 지금 정하지 않는다. 실제 채택 권한과 독립 판단의 필요는 기존 계약과 후속 설계를 따른다. 이미 채택한 변경은 같은 주체가 실제 반영할 수도 있고 필요한 전문성·범위에 맞게 위임할 수도 있다. 반영 담당이라는 이유로 새 기준의 채택권이 생기지는 않는다.

## 리뷰를 반영한 최종 권고

**변경을 맡은 사람이 그 변경에 필요한 Project 본문까지 완성하고, Main이 Work와 전체 반영의 연결을 책임진다. 루프에서 채택한 작은 본문 변경은 그 논의를 종합한 Main이 직접 이어 처리한다.** 특별한 이유가 없을 때 쓸 배정 기본값이며 변경 불가능한 역할표가 아니다.

| 실제 장면 | 기본 수행과 끝나는 결과 |
| --- | --- |
| 기능·설정·연결을 변경한다. | Main이 허용된 변경과 직접 관련된 Project 본문 반영을 같은 작업에 포함한다. 구현자는 현재 사실과 이미 채택된 약속·규약을 반영하고 자기 확인과 함께 반환한다. 관련 본문이 계속 정확하면 형식적으로 수정하지 않는다. |
| 여러 담당자의 결과를 종합하거나 작은 누락을 정리한다. | Main이 직접 맞춘다. 큰 재구성·별도 전문성·병행 편집 때문에 분리하는 편이 낫다면 한 담당자에게 모아 맡긴다. Main은 Work 상태·남은 일·진행 중 담당자와 이전 근거에 미친 영향을 연결한다. |
| 완료 후 루프에서 현재 설명의 오류를 발견한다. | 새로운 학습 채택과 구별해 해당 반영을 맡은 수행자가 근거와 범위 안에서 정정한다. Main이 근거를 확인한 작은 정정은 직접 처리한다. 읽기 전용 조사자·검토자는 발견과 근거를 반환한다. |
| 루프에서 앞으로 쓸 기준이나 제품 약속을 채택한다. | 기존 결정 권한을 따라 채택한 뒤, 종합한 Main이 작은 본문 변경을 직접 이어 반영한다. 코드·도구 변경이나 큰 재구성은 필요한 과업으로 맡긴다. 실제 변경·확인과 이후 효과 관찰은 구별한다. |

Main이 직접 구현하거나 문서 반영만 요청받은 경우에도 같은 관계를 적용한다. 별도 요청을 위해 구현자·루프·새 Work·새 작성자를 반드시 만들지 않는다. 제품 약속과 코드가 다를 때는 결함인지 설명 오류인지 먼저 구별하며, 현재 코드에 맞춰 약속을 자동으로 낮추지 않는다.

예를 들어 새 화면의 대기 동작을 이미 결정했다면 Main은 구현과 관련 Project 설명을 함께 맡긴다. 구현자는 관련 코드를 바꾸고 실제 지원 상태와 이미 결정된 계약 설명을 맞춘다. Main은 반환을 실제 변경·확인과 대조하고 Work와 다음 수행을 잇는다. 나중에 루프에서 해당 설명의 작은 누락을 발견하면 Main이 근거를 확인해 직접 정리할 수 있다. 경험에서 새 공통 기준을 채택했다면 그 본문 반영도 Main이 이어 할 수 있고, 별도 코드 변경이 필요하면 해당 구현을 배정한다. 이 사례는 수행 예시이며 실제 제품 변경·효과 관찰이 아니다.

## 기존 합의와 새로 권고한 부분

이미 합의된 것은 담당자의 직접 원문 읽기, Personal·Project·Work의 내용과 관리 권한, Main의 Work·전체 영향 연결, 일상 유지와 경험 개선의 구별이다. 본문 편집만으로 새 기준의 선택 권한이 생기지 않고 이미 권한 있게 정한 수정에 반복 승인을 요구하지 않는 것도 유지한다.

**이번 새 권고는 실제 작성의 기본값 두 가지다.** 2번의 구현자 동시 반영을 조건부 가능성에서 통상적인 초기 배정으로 삼고, 루프에서 작은 채택 내용을 반영할 때 종합한 Main이 직접 이어 수행한다. 개발 중 반영에 이미 채택된 약속을 포함하는 것은 새 내용 권한을 만드는 일이 아니라 기존 반영 범위의 누락을 막는 보완이다.

개발·완료의 배정과 연결은 development, 실제 쓰기 범위·판본·병행 작업은 execution이 맡는다. 영역 관리 계약은 내용·정본·결정 권한을, 공통 읽기·반영 방법은 실제 수행 방법을 소유한다. 공통 반영 스킬에 담당자 선정 규칙을 다시 정의하지 않는다. 읽기·반영 수단이 바뀌어도 내용 Owner와 Main의 책임은 남는다. USAGE/context-update의 정확한 형태·사용감 유보도 유지한다.

채택 후에는 development의 Main 직접 갱신 문장, Work AGENTS·README, 2번·3번·통합안의 조건부 배정을 함께 맞춰야 한다. Main의 전체 책임과 실제 작성의 위임을 구별하기 위한 변경이다. 이번에는 해당 실행 본문을 수정하지 않았고 05의 발동 시점·검토 인원·채택 권한·효과 관찰 구조도 확정하지 않았다.

## 확인 범위

Main은 두 핵심 개선을 현재 관리 본문·3번 안·development의 실제 문장과 대조했다. 이 기록의 로컬 링크 16개에서 누락이 없었고 변경 공백 검사도 통과했다. 이는 설계 정합성과 기록 연결의 확인이며, 실제 담당자 수행·재조사 비용 감소·문서 누락 감소를 입증하는 시험은 아니다.

## 후속 질문 — 구현자가 전체 맥락을 모르면 잘못 반영할 수 있지 않은가

사용자:

> 그럼 구현 담당자가 틀릴일은 없을까? 구현자가 보긴하는데 전체 맥락을 모르니까? 아닌가?

Main은 기존 development·execution·review·verification의 실제 책임을 다시 읽고 같은 reviewer에게 이 우려를 좁게 재판단하도록 요청했다. 이는 새 독립 전체 리뷰가 아니라 기존 리뷰어의 후속 검토다. 구현 내용을 아는 것과 Project에서 그 내용을 어떤 범위의 주장으로 설명할지 판단하는 것은 다르며, 앞선 추천이 작성 담당에 비해 그 주장 범위의 확인을 충분히 설명하지 못했다는 판단을 채택했다.

**구현자의 관련 본문 동시 작성 기본값은 유지하되, 수정된 Project 본문도 코드와 함께 검토할 변경 결과에 포함한다.** 구현자에게는 자기 변경으로 직접 확인할 수 있는 사실과 이미 정해진 계약의 한정 반영을 맡긴다. 여러 기능의 종합, 제품 공통 약속의 해석, 적용 범위를 넓히는 판단은 Main이 종합하며 필요한 기존 검토에 질문으로 포함한다. 구현자 역할이나 관련 원문을 읽었다는 사실만으로 전체 Project의 의미를 결정할 권한은 생기지 않는다.

[개선 검토](prototypes/development-workflow/skills/development/references/review.md)는 원요구·주변 사용처·기준의 적용을 별도로 재판단하고, [검증](prototypes/development-workflow/skills/development/references/verification/INDEX.md)은 유효한 요구·계약에서 기대 결과를 도출해 실제 충족을 확인한다. Main은 실제 변경된 본문과 판단 근거가 되는 기존 유효한 약속·권한 있는 결정·적용 조건을 함께 연결한다. **구현자가 고친 문서를 검증의 기준으로만 사용하면 코드와 문서가 같은 잘못된 가정을 공유할 수 있다.** 작성자의 새로운 설명은 원요구와 결정 근거로 대조할 주장이다. 기존 판본 전체를 항상 복제하거나 새로운 필수 문서 심사를 추가하는 방식은 아니다.

예를 들어 새 화면만 후속 조회를 기다리게 했는데 ‘로그인 성공은 후속 조회 완료까지 포함한다’고 공통 설명을 바꾸면 다른 기존 소비자까지 잘못 일반화한다. 관련 문서는 새 화면의 대기와 기존 소비자의 보존 동작을 구별해야 한다. Main·개선 검토는 그 범위와 근거를 대조하고, 검증은 요구된 실제 동작을 확인한다. 가상 예시이며 실제 demo 변경은 없다.

Main도 전체 맥락을 완벽히 안다는 전제는 두지 않는다. Main의 책임은 국소 결과의 조합에 필요한 원문·근거를 찾아 판단하고 부족한 범위를 연결하는 것이다. 루프에서 Main이 직접 쓰는 작은 본문 변경도 같은 원칙을 따른다. 문장 수가 작아도 계약·범위가 달라지면 그 의미에 맞는 판단·확인이 필요하다.

이번 후속은 작성과 확인의 연결을 명료화한 권고 보완이다. 실행 지침·2번 본문 전체·새 스킬·05의 전체 운영 설계는 적용하지 않았다. 기존 별도 검토·요구 검증의 조건과 Main의 전체 책임을 바꾸지 않는다.

## 후속 논의 — 구현자는 반영을 제안하고 담당자가 검토 후 반영한다

사용자는 현재 합의가 Main의 직접 갱신이며 별도 맥락 담당이나05 루프의 구체 담당은 아직 정하지 않았다는 설명을 들은 뒤 다음 안을 제시했다.

> 그럼 어때? 구현자가 제안하고  메인이든 추후 합의될 담당자든 검토 한번하고 반영하는거지 그럼 구현자가 이미 아는정보로 바로 제안하는거니까 조사할 필요도 없고 그리고 나중에 루프 단계에서 반영할때도 안헤깔리고 물론 이때도 구현자 음 아니다 이미 구현자가 계속 제안을 해왔으니 추가로 구현자한테 물어볼 필요 없고

Main은 이 방향을 앞선 직접 수정 기본값보다 적합하다고 권고한다. 구현자는 자기 작업에서 이미 확인한 변화·이유·적용 범위·근거를 기존 결과 반환에 연결해 Project 반영을 제안한다. 자기 코드 작업에 원래 포함된 주석·호출부 등의 완성 책임까지 제안으로 대체하는 것은 아니다. 지속 맥락의 실제 반영은 현재 합의상 Main이 원요구·유효한 계약·다른 사용처와 대조해 채택·조정·보류한 뒤 수행한다. 추후 다른 반영 담당을 합의하더라도 제안과 근거를 받아 판단하는 관계는 유지할 수 있다. 미래 담당자를 현재 존재하는 역할로 기록하지 않는다.

제안은 별도 제안서·필수 양식을 만들지 않고 기존 결과 반환에 필요한 만큼 담는다. ‘어떤 지속 내용이 왜 달라져야 하는지, 어디까지 확인했는지, 무엇을 근거로 판단했는지’가 이해되면 된다. 구체 문안이 도움이 되면 함께 줄 수 있으나 모든 제안에 완성 문안을 요구하지 않는다. 구현자에게 관련 Project의 직접 편집권을 기본 추가하지 않으면서 해당 작업에서 확보한 지식을 재사용하는 안이다.

Main은 받아들여 반영한 것과 아직 검토·반영하지 않은 중요한 제안을 기존 Work 기록·상태에서 구별해 남긴다. 이후 루프에서는 그 제안과 판단·반영 경과를 입력으로 사용할 수 있어, 담당자가 이미 아는 내용을 다시 설명받기 위한 재호출을 기본으로 삼지 않는다. 다만 제안의 근거가 빠졌거나 충돌·후속 변경으로 유효성이 달라지면 해당 부분만 추가 확인한다. 제안을 받았다는 사실로 검토·사실 확인이 자동 완료되거나 추가 조사가 절대 필요 없다고 보장하지 않는다.

개발 중 필요한 사실·이미 결정된 의미의 반영은 그때 검토해 처리하고, 모두05까지 보류하지 않는다.05는 축적된 제안과 결과를 바탕으로 경험에서 새 기준을 채택할지 판단할 수 있으며, 채택된 내용을 실제 반영하는 방법은 같은 것을 사용한다. 루프에 제안이 입력됐다는 사실과 새 지속 기준의 채택을 구별한다.

이번에는 사용자 제안과 Main의 추천 변경을 기록했다. 앞선 reviewer는 직접 수정안의 검토 연결을 판단했으며 **이번 제안 우선안까지 새로 리뷰한 것은 아니다.** 실행 지침·스킬·2번과3번의 본문 전체·05의 구체 운영은 아직 변경하지 않았다.
