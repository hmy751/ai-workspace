# AI 개발 작업 체계의 개선 설계 — Spec 초안

이 Spec은 **014에서 설계하는 AI 개발 작업 체계의 목표·범위와 현재 전체 구상**을 소유한다. 목표와 주의할 점만 남기는 문서가 아니라, 다음 세션에서도 무엇을 만들려 하며 어떤 선택이 남았는지 복원할 기준이다. 현재 전체 잠정안과 Ticket을 연결하는 방법은 3절, 선택과 미정은 5절에서 확인한다.

현재는 상위 Ticket 01~07과 개발 방식·스킬의 하위 Ticket으로 설계를 구체화하는 단계다. **검토자가 필요한 품질 수정까지 수행하는 B 방향**은 선택했지만, 아래 전체 잠정안이나 상세 운영을 모두 채택한 것은 아니다. 실제 스킬·하네스·제품 변경은 시작하지 않았다. [B의 선택 범위와 원문](../records/2026-10-12-15-reviewer-editing-choice-and-start.md)

사용자가 우려한 것은 좁혀진 AI 제안이 다음 세션에서 결론처럼 읽혀 이후 논의의 범위를 닫는 일이다. 각 부분을 구체화할 때에는 앞선 제안을 미채택으로 표시하는 데 더해, 원자료에 따라 필요한 다른 범위와 대안도 열어 둔다.

[배경과 평가](memory.md)는 왜 이 작업에 이르렀는지, [Ticket 색인](tickets/index.md)은 부분별로 만들 결과, [state](state.md)는 전체 진행을 설명한다. 원래 연구와 사용자 정정의 상세는 [기록](../records/README.md), 직접 근거는 [source](../source/README.md)에 있다.

## 1. 문제·목표·범위

Noline에 이식한 Project·Work context와 스킬은 재설명을 줄이고 작업을 이어가는 데 도움이 됐다. 동시에 기록을 읽고도 작업 중심을 다시 잡아줘야 하거나, 결과·설명을 한 번 더 요청해야 나아지는 장면이 남았다. 모든 질문이 실패는 아니며, 필요한 이해와 중요한 제품 선택도 있었다. 기존 평가로 특정 스킬이나 코드 품질 하나를 모든 마찰의 원인으로 확정하지 않았다.

개발 자체의 질과 사용자 스타일·배경지식에 맞는 개발은 사용자가 실제 다음 개선 과제로 강하게 보고 있는 방향이다. 과거 마찰의 인과를 입증하지 못했다는 이유로 이 과제를 계속 보류하지 않으며, 더 큰 작업 체계 안에서 구체화한다.

전체적으로 발전시키려는 것은 **사람과 AI가 개발하고, 이해·판단하고, 기록을 남기고, 경험을 다음 작업 방식에 반영하는 체계**다. ai-workspace의 기본 틀, 대상 프로젝트의 맥락, 실제 스킬과 개발 방법·도구를 함께 다룬다. 판단 연속성이나 코드 리팩터링 한 과제로 범위를 닫지 않는다.

현재 단계에서는 각 부분을 실제 사례로 비교할 수 있는 설계안으로 구체화하고, 서로 연결했을 때의 의미와 필요한 변경을 설명한다. 강연·Vercel 자료와 기존 구성에서 새로운 방법의 후보를 만들고, 과거 사례는 그 후보의 적합성과 약점을 검토하는 데 쓴다. 과거에 기록된 문제의 개선만으로 후보 범위를 제한하지 않는다. 사람이 선택할 차이와 미정인 이유를 드러내며, 이후 적용할 범위와 확인 방법을 정할 수 있는 상태를 만든다. 설계 논의를 거쳐 실행·적용·효과 확인으로 이어갈 수 있으나, 이번 분해 요청이 그 실행 전체에 대한 승인은 아니다.

검토할 범위에는 다음이 포함된다. 논의 중 필요가 드러나면 근거를 따라 보완한다.

- Work의 기록과 Workspace 구성: 무엇을 남기고 어떻게 다시 사용하는가. current·memory·state·Spec·Ticket·records·source·output의 역할과 관계, 진입·갱신·보존 방식을 어떻게 더 낫게 구성할 수 있는가.
- Project context: 제품·구조·가이드·선택 이유와 작업 주체가 소비할 맥락을 어떻게 구성하는가.
- 개발 방법: 요구 해석·조사·설계·구현·검토·검증·보고를 어떤 근거와 책임으로 이어 가는가.
- 기존 스킬: 작업 논의·재판단·설명·복구·Project 읽기와 갱신 등이 어떤 조건에서 무엇을 맡는가.
- 기록 운영과 경험 반영: 어느 시점에 누가 갱신하고, 어떤 경험을 개선 후보와 다음 확인으로 이어 가는가.
- 기반과 적용: 공통 기준과 프로젝트 적응, 기존 Maintainer 장치 제거 이후의 책임과 읽기·검증 경로를 어떻게 잇는가. 프로젝트 경험을 ai-workspace 개선에 쓰고 다시 반영하는 과정도 비용을 줄일 여지가 있는지 비교하며, 새 장치 도입을 전제하지 않는다.

## 2. 지켜야 할 의미와 대표 사례

아래는 사용자가 밝힌 방향을 설계에 대입할 대표 장면이다. 구현할 기능 목록이나 모든 평가 사례의 고정 집합은 아니다.

| 장면 | 설계가 설명해야 할 차이 |
| --- | --- |
| 기록을 읽고 재개했는데 두 버그부터 제안하고, 사용자는 구조·배경 검토를 원한다 | 원문 보존·열람과 현재 작업에 적용하는 판단을 구별한다. 현재 중심·잠정 선택·후속 작업의 관계를 복원할 수 있어야 한다. |
| 지금 할 일에는 직접 쓰이지 않지만 나중에 다시 볼 분석·시행착오·검증이 있다 | 후일 보존 목적도 판단한다. current에 모두 넣거나, 다음 행동에 필요 없다는 이유로 모두 버리는 양쪽을 피한다. |
| 개발자와 reviewer가 Project 문서를 읽는다 | 제품 의미, 현재 구조, 변경 가이드, 선택 이유 등 맡은 작업에 필요한 내용을 찾고 사용할 수 있게 한다. 다음 판단을 위한 요약만으로 한정하지 않는다. |
| 사용자가 “왜 이렇게 했나”를 묻는다 | 이해 요청·선택 재검토·변경 요청을 맥락으로 구별한다. AI가 기존 선택의 이유와 적절성을 판단해 설명할 수 있어야 한다. |
| 결과를 다시 써 달라고 해야 설명이 조금 나아진다 | 첫 보고의 충분함과 별도 브리핑·설명 복구의 역할을 구체화한다. 재질문이나 침묵만으로 성공·실패를 확정하지 않는다. |
| 구현과 검사가 끝났지만 실제 사용 흐름·구조의 질이 의문이다 | 요구 충족, 코드 구조·변경 부담, 실제 동작 근거를 각각 살핀다. 코드·도구·검사·문서·리뷰에 무엇을 맡길지 비교한다. |
| 반복 교정 또는 잘된 장면에서 개선 후보가 보인다 | 기록 유지와 작업 방식 개선의 판단을 구별한다. 구체 사례를 바탕으로 후보·사람의 선택·반영·효과 확인을 이어 갈 수 있어야 한다. |

이 사례는 [평가·인터뷰](../records/2026-10-12-01-background-and-evaluation.md), [강연과 기준 구현](../records/2026-10-12-02-framework-and-lecture-reading.md), [사용자 정정](../records/2026-10-12-03-proposals-and-corrections.md)에 근거한다. 사례에서 확인되지 않은 결과는 가정 또는 이후 확인으로 남긴다.

## 3. 함께 사용할 개념과 결과의 관계

### 지금 쓰는 Spec·Ticket과 설계 대상의 구별

| 구분 | 이번에 다루는 의미 |
| --- | --- |
| **014의 Spec·Ticket** | 이 설계 작업을 진행하는 문서다. Spec에 현재 전체안과 중요한 미결정을 모으고, Ticket에서 필요한 부분을 조사·비교·구체화한다. 아래 문서 운영 설명은 우선 이 층에 적용한다. |
| **개선할 시스템의 Spec·Ticket** | 향후 개발 작업에서 무엇을 정의하고 구현자·검토자에게 어떻게 전달하며 진행 중 어떻게 고칠지를 설계할 대상이다. Project context와 다른 Work 기록의 관계, 문서 구성·작성 주체·갱신 시점도 아직 검토 대상이다. 014에서 쓰는 형식을 그대로 표준으로 채택한 것은 아니다. |

예를 들어 014의 01-02는 ‘어떤 설계·테스트 방법을 어떤 조건에서 쓸지’를 비교한다. 개선할 시스템에서 기능 개발 Ticket에 어떤 요구·제약·검증 근거를 적게 할지는 별도로 정해야 한다. 014에서 얻은 운영 경험도 그 판단의 근거가 될 수 있으나 자동으로 공통 규칙이 되지는 않는다.

### 현재 구상하는 체계 — 논의용 잠정안

설계하려는 것은 **Project의 지속적인 개발 환경과 그 위에서 작업·판단·기록·개선을 이어가는 체계**다. 아래는 흩어진 논의를 한 전체안에서 검토하기 위한 현재 구상이다. 각 행을 별도 폴더·스킬·agent로 만든다는 뜻은 아니며, 전체 구성이 채택된 것도 아니다.

| 구성 | 현재 구상과 다른 구성과의 연결 |
| --- | --- |
| Project에서 계속 갖추는 개발 환경 | 제품 의미와 선택 이유, 코드 패턴·개발 기준, 검사와 실행·관찰 수단, 필요한 내용을 찾는 경로를 갖춘다. 한 작업의 설계·구현·검토가 이 공통 환경을 사용한다. 문서뿐 아니라 코드·검사·도구에 무엇을 맡길지도 설계한다. |
| 한 작업의 정의와 실행 | Main이 사용자와 결과·범위를 구체화하고 필요한 공통 맥락과 작업 상태를 구현·검토에 연결한다. 선택한 B 방향에서는 검토자가 직접 품질을 개선한다. 검토자가 최종 실제 확인까지 이어가는 안도 제안했으나, 선행 설계·인수 내용·수정 범위·검증 책임은 현재 원자료의 실제 방식과 대조해 재검토한다. |
| 작업 중·이후의 기록 | 현재 선택·미완료·근거를 Work에서 이어가고, 후일 재검토할 분석·대안·시도·결과도 목적에 맞게 보존한다. 여러 작업에 필요한 제품·구조의 사실과 선택은 Project 공통 맥락에 반영하거나 연결한다. 파일 구성과 갱신 책임은 여기서 확정하지 않는다. |
| 경험에 따른 개선 | 잘된 결과와 반복 마찰에서 개선 후보를 찾고 코드·검사·도구·기준·스킬 중 어디에 반영할지 판단한다. 프로젝트 경험을 ai-workspace 개선으로 가져오고 다시 적용하는 비용도 비교한다. 기록 갱신과 새 기준 채택은 구별한다. |

이 구상은 [자료와 기존 구성을 읽고 만든 전체안 제안](../records/2026-10-13-20-overall-design-and-ticket-direction.md)을 모은 것이다. Matt의 설계·테스트·검토 방법, Lauren의 코드·검사·실행 환경, Vercel의 근거·사례·필요한 자료로의 안내는 후보를 구체화하는 데 쓴다. 서로 바로 결합할 수 있다고 전제하지 않으며, 사용자 기준과 Noline 경험을 통해 적합성과 비용을 판단한다. Feature Map과 라우팅의 대체 관계도 아직 확인하지 않았다.

**전체 형태를 바꿀 주요 미결정**은 다음과 같다. 모두 동시에 상세화하라는 순서가 아니라 다음 논의를 선택할 질문이다.

- 구현자·검토자가 판단해야 할 것은 무엇이며, 무엇을 코드 구조·자동 검사·실행 도구·지침으로 받쳐 줄 것인가. 이 선택에 따라 개발 방식과 필요한 Project 환경이 함께 달라진다.
- 공통 제품·개발 맥락과 한 작업의 정의·진행을 어디에서 소유하고 어떻게 찾아 사용할 것인가. 여기에는 개선할 시스템의 Spec·Ticket과 다른 기록의 구성도 포함한다.
- 실행 중 바뀐 판단과 결과를 누가 언제 기록하고, 어떤 경험을 프로젝트 또는 공통 방식의 개선으로 올릴 것인가. 기록 유지 비용과 실제 개선의 이득을 함께 본다.

### 현재 초점과 전체 체계에 돌려줄 내용

**먼저 구체화할 것은 작업 단계의 시스템이다.** 사용자는 Main과 Spec·Ticket 등을 논의·결정하는 단계와 실제 작업·구현 단계를 구별했다. 전자는 기존에도 어느 정도 잘 작동했고, 강연에서 특히 와닿은 것은 좋은 구현을 받치는 컨텍스트·코드 기준·워크플로·작업 절차·도구였다. 요구·설계 절차도 필요한 보완을 연결하지만 선행 설계 도입을 출발점으로 고정하지 않는다. 구현 중 모듈·인터페이스·테스트 경계를 설계하는 일은 이 작업 단계에 포함된다. ### 근거와 논의 방식

외부 자료의 권고, 사용자 선호, 현재 코드의 사실, Main의 예시·추천을 구별한다. Matt·Lauren·Vercel의 실제 계약과 판본 차이는 [원자료 조사 27](../records/2026-10-13-27-source-investigation-and-proposal-reset.md)에서 선택해 읽는다. Noline 경험은 후보의 적합성을 검토하는 데 쓰며 새로운 대안의 범위를 과거 실패로 제한하지 않는다. Feature Map·Vercel 라우팅·깊은 모듈·합성형 UI의 대체나 충돌 관계를 아직 단정하지 않는다.

[기준 배치 비교 22](../records/2026-10-13-22-first-decision-and-system-effects.md)와 [알림 설정 인수 예시 23](../records/2026-10-13-23-notification-settings-handoff-example.md)는 조사 전 Main의 가설이다. 두 번째 안을 예시에 가정한 것을 ‘세부 기준을 검토자에게 집중한다’는 일반 선택으로 올리지 않는다. B의 검토자 직접 수정 선택과도 별개다.

현재 실제 사례는 더 풍부한 `20_lab/template`이며 앞의 `30_study/code-template` 메모와 다르다. [조사 기록 32](../records/2026-10-13-32-template-code-and-usage-discovery.md)에서 내용·사용 예시·한계를 확인한다. 과제물·회사 자료는 지정됐으나 추가 조사는 보류했고, 실제 대상 저장소·사용자 작성자 범위는 미확인이다. 템플릿을 읽었다는 사실은 그 자료에서 얻을 선호를 다 논의했다는 뜻이 아니다.

AI는 실제 도구와 주변 역할, 구체 코드·변경 상황을 제시한 뒤 사용자에게 필요한 의도를 묻는다. 추상 기준 전체를 먼저 정의해 달라고 돌리거나, 예시를 보자마자 결론·기준 확정·구현으로 서두르지 않는다. 한 컴포넌트의 API 문제를 끝없이 설계하기보다 그 사례가 드러낸 판단과 열린 조건을 전체안에 돌려놓는다.

### 부분 논의를 전체안에 반영하는 방법

이번 설계에서 Project context는 여러 작업이 사용하는 프로젝트 공통 맥락이고, Work context는 한 작업의 목표·현재 상태·산출물·과정을 맡는다. 코드·검사·도구·스킬도 실제 행동과 품질에 영향을 준다. 이들 사이의 구체적인 내용·관리 책임·소비 경로는 설계할 대상이며 현재 폴더 이름만으로 확정하지 않는다.

**기록 관리**는 필요한 내용을 보존·갱신하고 다시 사용할 수 있게 하는 일이다. **산출물 검토**는 맡은 결과와 품질이 성립하는지 판단하는 일이다. **경험 반영**은 반복 경험에서 작업 방식이나 기준의 개선을 도출하는 일이다. 같은 대화에서 함께 할 수 있지만 하나를 수행했다고 나머지도 완료된 것은 아니다.

014의 Ticket은 전체안에서 아직 풀지 못한 질문을 맡아 결과·필요한 입력·진행·근거를 구체화한다. 선택이나 가정 변경이 생기면 Main은 전체안에서 달라지는 관계와 남은 영향을 이 Spec에 반영한다. 세부 대안·분석은 Ticket과 records에 두고, state는 지금 이어갈 위치를 가리킨다. 중요한 잠정안도 그 지위를 밝혀 Spec에 남기므로 채택 전이라는 이유로 대화 속에만 두지 않는다.

한 Ticket은 여러 세션에 걸칠 수 있다. 번호는 식별자이며 별도 agent, 고정 순서, 단독 실행을 뜻하지 않는다. 전체안에 영향을 주는 논의가 생기면 07의 연결 검토를 그때 수행하며, 모든 Ticket을 완료한 뒤에만 통합하지 않는다. 현재 번호·분할은 유지하되, 같은 결정을 여러 Ticket이 중복 소유하는 문제가 확인되면 그 범위를 조정한다.

설계안이 갖춰진 것, 사용자가 선택한 것, 실제로 변경한 것, 사용 효과를 확인한 것을 구별한다. 예를 들어 비교안을 맡은 Ticket은 충분한 비교안을 만들면 완료될 수 있으나, 운영 방식의 결정을 맡았다면 그 선택이 남아 있는 동안 완료로 닫지 않는다. 지금 Ticket들은 우선 **검토 가능한 설계안을 만드는 범위**로 제안한다.

## 4. 품질·완료 판단

각 설계안은 기존 구성을 실제로 읽고, 유지할 효용과 개선할 기회를 근거로 설명해야 한다. 과거 실패가 확인된 부분만 고치는 것으로 한정하지 않는다. 문제가 보고되지 않은 구성도 더 나은 대안과 비용을 비교할 수 있으며, 예상 이득과 확인된 효과는 구별한다. 기존 기준이 이미 요구하는 내용, 구체성이 부족한 내용, 실행·도구·책임 배치의 문제를 사례별로 구별한다. 자료 전체를 다시 수집하거나 모든 문제를 같은 원인으로 환원하지 않는다.

Ticket의 설계 결과에는 그 범위에 필요한 다음 관계가 드러나야 한다.

- 무엇을 가능하게 하는 안인지와 현재 방식에서 달라지는 점.
- 실제 사용 장면에 대입한 내용·동작 예시와 선택 이유. 파일 목록이나 추상 원칙만으로 대신하지 않는다.
- 의미 있게 다른 대안, 받아들이는 비용, 관련 Ticket·기존 구성에 미치는 영향. 형식적인 대안 개수를 채우지는 않는다.
- 직접 확인한 사실, 해석, 제안, 사용자 선택, 남은 판단과 그 영향.
- 설계 단계에서 확인할 수 있는 것과 적용 이후 관찰해야 할 효과.

전체 설계의 충분성은 Ticket 수나 문서 완성 여부로 판단하지 않는다. 개발 시작·진행·사람의 질문·결과 검토·기록·다음 세션 재개·경험 반영이 연결되는 대표 사례에서 책임이 비거나 같은 판단이 충돌하지 않는지 확인한다. 필요한 세부 설계가 아직 부족하면 해당 부분을 구체화하며, 큰 범위의 완료로 덮지 않는다.

현재 초안을 만든 사실은 위 설계 작업을 수행했다는 뜻이 아니다. 실제 적용 효과는 아직 미확인이고, 강연이나 제공 스킬의 존재만으로 우리 환경에서의 효과를 입증하지 않는다.

## 5. 제약·현재 구성 선택·열린 판단

**사용자가 분명히 한 방향:** Maintain의 보존 대상을 다음 작업 정보로 한정하지 않는다. Project context의 역할도 다음 판단에 한정하지 않는다. 개발 에이전트를 역할 파일만으로 다루지 않는다. 자동 Maintainer는 재개하지 않으며, 장치를 걷어내되 기록 원칙을 보존하는 방향을 설계한다. 반복 질문에는 필요한 인간 참여가 포함되고, 침묵은 만족의 증거가 아니다.

적절한 범위에서 기록과 경험 반영을 계속 이어 가는 루프를 만들고 싶다는 방향도 분명하다. 이후 설계할 것은 그 구체적인 시점·주체·단계이며, 매 응답 자동 실행이나 매번 전체 회고로 확정한 것은 아니다.

**이번 문서 구성에서 선택한 것:** 루트 Workspace의 수동 운영에 Spec 한 편과 Ticket 본문·색인을 더했다. 기존의 다섯 Spec 관점은 이 문서의 다섯 절로 다룬다. memory는 배경·평가를, design-map은 열린 영역과 Ticket의 관계를, state는 전체 진행을 맡는다. Reference의 자동 Maintain·Recover·JSON 상태 계약을 이 Workspace에 설치하지 않았다. 이 선택은 014의 논의 운영이며 향후 공통 템플릿의 최종 구조가 아니다.

**선택한 개발 방향:** 실행할 Ticket이 구체화된 뒤 구현·검사를 거쳐 별도 검토자가 품질 검토와 필요한 수정을 맡는 B 방향으로 설계한다. Main은 작업 정의·전체 결과 통합을 맡고, 결과·계약의 변경은 재판단한다. 구현 세부를 모두 미리 고정하거나 실제 스킬·하네스를 변경한 것은 아니다.

**미정:** 구체적인 기록 시점·작성 주체, reviewer의 상세 수정 범위와 인계·최종 확인, 첫 보고의 기준, 개발 도구, 스킬의 최종 구성, 공통 기준과 프로젝트 적응의 경계, Recover·Verify의 유지·단순화 범위, 실제 적용 범위와 순서. Main 기록·조건부 reviewer 등 앞선 제안은 검토 후보로 남는다.

**설계 대안을 판단할 때 확인할 목적:** 사용자는 Dialog 논의에서, Confirm의 확인 역할과 주변 관계를 검토하지 않은 채 즉시 닫는 용도로 축소하고 비동기 처리를 사용처로 우회시킨 대안을 지적했다. 대상의 존재 이유와 맡은 역할을 이해한 뒤 유지·변경·통합·제거를 판단한다. 목적을 검토한 뒤 추상화를 없애거나 사용처에 제어를 두는 선택은 가능하며, 기존 구조 보존 의무로 해석하지 않는다. **자료 사용의 주의점:** 사용자가 제외한 코드 퀄리티 문서를 이번 설계 비교의 기준으로 다시 가져오지 않는다. 사용자 자신의 코드 기준을 모두 파악했다고 보지 않으며, 강연·스킬·Vercel의 권고도 구체 사례에서 논의할 후보로 사용한다.

현재 작업의 Main이 사용자 선택과 확인된 근거를 반영해 이 Spec·Ticket·state를 관리한다. 이번 권한은 분해와 설계 논의용 문서 작성·보완이다. 제품 코드·글로벌 스킬·실행 하네스의 실제 변경은 해당 범위를 구체화해 이어서 다룬다.

분해 근거와 원문: [최초 초안 구성](../records/2026-10-12-05-spec-ticket-draft.md), [상위·하위 Ticket 분할 기록](../records/2026-10-12-09-ticket-split.md). 참고한 작성 관점: [기준판 Spec](../source/ai-workspace-baseline/reference-project/context/work/workspaces/spec-and-tickets/SPEC.md), [기준판 Ticket](../source/ai-workspace-baseline/reference-project/context/work/workspaces/spec-and-tickets/TICKET.md). 해당 자료의 개발 중심 예시는 이 작업의 설계 결과에 맞춰 해석하며, 자동 Maintain 책임 배치를 가져오지 않는다.
