## 맡은 결과와 범위

2026-10-18 시안 연결: 구현자와 B 검토자의 전달·반환을 정할 때 [보완66](../../../records/2026-10-18-66-principles-cases-and-refinement-prototype.md)과 [구체 장면](../../../records/prototypes/applied-criteria-2026-10-17/field-walkthrough.md)을 읽는다. 요청·현재 조건·판단 근거를 전달하고 검토자가 원요구와 직접 대조하는 장면을 사용한다. 이 사례의 상세 권한·인수 방식이 전체 운영으로 채택된 것은 아니다.

목표·Spec·Ticket에서 조사·설계·구현·검토·수정·첫 보고까지 이어지는 **대표 작업의 진행안과 판단 책임의 선택 근거**를 만든다. AI가 필요한 일을 찾아 수행하는 부분과 사람의 제품 선택·이해·재판단이 필요한 지점을 구체화한다. Main·worker·reviewer의 수나 고정 호출 순서는 아직 정하지 않는다.

이 Ticket은 전체 진행과 책임의 연결을 맡는다. 코드·설계 품질의 실제 기준과 검토·수정 방법은 [01-02](01-02-code-design-quality.md), 동작 검증과 도구는 [01-03](01-03-behavior-verification.md)가 구체화한다. 두 결과를 받아 진행안을 보완하되, 먼저 연결 초안을 만들어 기록·Project 논의를 시작할 수 있다.

## 현재 비교와 근거

강연·Vercel 자료와 현행 구성에서 구현·품질 검토·실제 검증의 연결 후보를 만들고, 과거 Noline 사례로 그 안의 약점을 대조한다. 과거에 확인된 문제만 해결하는 것으로 범위를 제한하지 않는다. 01-02·01-03의 상세 결과를 기다린 뒤 연결하는 것이 아니라, 그 선택이 진행안을 바꾸는 부분부터 함께 설계한다.

- [워크플로 세 안 비교](../../../records/2026-10-12-13-implementation-review-verification-workflows.md): 한 담당자 완결, 별도 품질 검토자의 직접 수정, 구현자 수정·검토자 재검토. 별도 실행 검증자 배치는 따로 비교한다. 자료 간 차이와 기존 구성, 가상 작업 예시·과거 사례 대조를 포함한다.
- [PR 병목 강연](../../../source/lectures/01_PR_병목_강연_전체번역.md), [Agent 신뢰 강연](../../../source/lectures/03_Agent_신뢰_강연_전체번역.md), [Vercel 자료](<../../../source/lectures/vercel-product-design (1).md>): 구현·검토의 부담 배치, 실제 실행 근거, 제품 판단·상태·기준의 연결.
- [현행 실행 기준](../../../../../../reference-project/context/work/workspaces/spec-and-tickets/EXECUTION-CRITERIA.md): 필요한 일의 발견과 실행자·Main의 결과 책임. 기존 책임을 새 원칙으로 재정의하지 않는다.
- [철회와 후속 구현 비교](../../../source/reading/noline-evaluation/reviews/withdrawal-followup-comparison.md), [평가·인터뷰](../../../records/2026-10-12-01-background-and-evaluation.md): 후보가 합의·범위·사람의 질문을 어떻게 처리하는지 대조하는 근거.

## 다른 Ticket과 주고받을 것

실제 인수·반환과 Main의 판단 범위를 정할 때 [01-02 후속 연결 65](../../../records/2026-10-18-65-criteria-status-and-cross-ticket-refinement.md)의 과정 근거를 확인한다. 앞선 HTTP-07 가상 사례는 Main이 기준을 지정하고 구현자가 검증 공백까지 알려 준 장면이다. 이후 Field 장면은 작업 단서로 기준을 찾는 모습을 보충했다. 담당자가 스스로 찾을 범위와 Main이 전달할 맥락을 새 조건에서 다시 판단하고, 달라지면 작업 요청·읽기 조건·반환 요구를 함께 고친다. B의 직접 품질 수정 선택과 이 가상 장면의 세부 운영을 구별한다.

[02](../02-work-records.md)에는 실제로 생기는 기록과 다시 사용할 장면을, [03](../03-project-context.md)에는 작업 주체가 소비할 맥락을 제시한다. [04-01](../04-skill-improvements/04-01-work-decision-skills.md)은 작업 정의·재판단을 실제 스킬로 연결하고, [04-02](../04-skill-improvements/04-02-artifact-explanation.md)은 첫 보고와 별도 브리핑·설명 복구를 구별해 보완한다.

01-01은 검토 지적의 판단·수정·재확인이 작업 흐름 어디에 놓이는지 맡고, 01-02·01-03는 그 판단에 필요한 품질 기준과 증거를 구체화한다. 미정인 부분을 확정된 역할 배치로 채우지 않는다.

## 완료 조건과 확인 방법

- 대표 작업에서 목표를 결과로 나누고 필요한 조사·개발·검토를 찾는 방법이 구체적이다. 초안 파일 목록을 처리한 것으로 목표 달성을 대신하지 않는다.
- AI가 더 확인할 때, 판단 가능한 결과를 제시할 때, 사람의 선택이나 추가 관찰이 필요한 때를 사례로 비교한다. 중요한 사람 참여를 모두 줄이는 목표로 만들지 않는다.
- 검토 지적의 판단·수정·재확인·종료, 첫 보고와 기록의 책임이 연결된다. 01-02·01-03의 선택과 충돌하거나 빠진 부분을 드러낸다.
- 작은 변경과 큰 구조 개선에서 적용할 방법과 생략할 방법, 역할·자료·도구 비용, 이후 관찰할 품질·사용자 부담을 설명한다.
- 결과는 검토 가능한 진행안이다. 초기 연결 초안과 관련 결과를 반영한 설계 완료를 구별하며, 설계의 채택·구현·효과 확인을 완료로 앞당기지 않는다.

## 선택한 방향과 다음 판단

사용자는 **검토자가 지적 리포트만 넘기지 않고 필요한 품질 수정까지 수행하는 B 방향**으로 설계를 이어가도록 선택했다. [선택 원문과 시작점 설명](../../../records/2026-10-12-15-reviewer-editing-choice-and-start.md)에 근거와 선택 범위를 남겼다. C 일반 기본 추천과 기본 미정 상태는 앞선 비교의 이력이며 현재 선택이 아니다.

Main은 사용자 요구·제품 맥락에서 Spec과 실행할 Ticket을 구체화하고 전체 결과를 통합한다. B 흐름은 해당 Ticket의 결과·범위·보존 계약·완료 근거가 충분해져 구현 담당자가 인수하는 시점부터 적용하는 것으로 구체화한다. 필요한 맥락 확인·세부 설계, 구현·검사, 검토자의 직접 수정, 수정 후 실제 확인을 연결한다. 내부 설계는 실행 중 발전시키고, 결과·계약·공통 전제가 달라지면 Main으로 돌아가 재판단한다.

[B의 실행·수정·검증 상세 초안](../../../records/2026-10-12-16-b-execution-review-verification-contract.md)에서 구현 인수 내용, 검토 기준과 직접 수정 범위, 최종 실제 검증·실패 반환·종료를 구체화했다. 이후에는 **검토자가 최종 실제 확인까지 이어가고 Main이 완료를 판단하는 안**을 제안했다. [당시 근거와 관련 Ticket 연결](../../../records/2026-10-12-17-workflow-basis-and-connected-design.md)은 분석 이력이다. 최종 실제 확인의 주체와 독립성은 원자료 조사 및 현재 작업 단계 논의에서 다시 판단하며, 전체 흐름과 컨텍스트의 충분함·실제 효과는 아직 확인하지 않았다.

사용자는 [01-02](01-02-code-design-quality.md)의 자료를 먼저 구체화해 논의하도록 선택했고, 이후에는 [Spec](../../spec.md)의 전체안과 중요한 결정을 출발점으로 보완했다. [당시 선택 기록](../../../records/2026-10-12-18-quality-materials-next-step.md). 현재 [기준 배치와 전체 영향의 비교](../../../records/2026-10-13-22-first-decision-and-system-effects.md)에서 구현 인수 때 갖출 내용과 검토에서 집중할 판단을 두 안으로 제시했다. 이 Ticket의 역할 흐름은 잠정안으로 유지하고 품질 기준과 기준 배치의 선택에 따라 보완한다. 모든 관련 Ticket을 동시에 구체화하는 것을 다음 작업으로 삼지 않는다. 실제 스킬·하네스·제품 구현과 효과 확인은 수행하지 않았으며 Ticket은 진행 중이다.

사용자가 두 번째 안을 가정해 보자고 요청해 [알림 설정 인수 예시](../../../records/2026-10-13-23-notification-settings-handoff-example.md)를 작성했다. 같은 개발 Spec·Ticket과 Project 맥락을 사용하면서 구현자는 초기 코드·검사·확인 근거를, 검토자는 직접 개선한 결과와 최종 실제 확인을 반환한다. Main으로 돌아갈 제품 선택과 내부 구조 수정의 예를 구별했다. 실제 역할 실행이나 일반 운영 방식의 최종 채택은 아니다.
