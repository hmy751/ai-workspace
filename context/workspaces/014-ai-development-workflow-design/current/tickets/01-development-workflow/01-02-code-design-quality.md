## 유지할 판단의 뉘앙스

- **책임 분리를 선호하지만 모양을 고정하지 않는다.** 의미 있는 재사용 단위를 고려하되 재사용 횟수를 문턱으로 정하지 않았다. 외부 기능 단위·내부 함수·파일 배치는 관련되지만 다른 선택이다. 이름·길이만으로 답하는 질문보다 실제 주변 코드와 역할이 필요하다.
- **기존 도구를 고려한다는 것과 도입·래핑 의무는 다르다.** 공통 Dialog는 사용처에 프로젝트의 부품을 제공하려는 의도가 있다. Radix를 쓴 직접 이유는 개발 리소스 절감이고, 직접 구현이 낫다면 그렇게 할 수 있다. 교체 용이성을 검증했다는 뜻도 아니다.
- **Confirm의 목적 정정과 이후 제거 선택을 함께 읽는다.** 비동기 문제를 피하려고 즉시 닫기용으로 축소한 제안이 문제였다. 목적을 이해하고 완료·닫기의 책임을 옮기며 제거하는 선택은 가능하다. 결과값·재전파·어댑터 제안은 채택되지 않았다.
- **사용처 부담은 아직 평가 질문이다.** 결과 반환이나 오류 전파 자체가 나쁘다고 정하지 않았다. 어떤 역할을 자연스럽게 맡는지와 자동화의 편의를 얻기 위한 계약 비용을 같이 본다.
- **자료 읽기와 선호 탐색 완료를 구별한다.** 사용자 코드·강연·토스·Airbnb 등 떠올린 자료를 정답이나 전부 조사할 지시로 취급하지 않는다. 코드 스타일·네이밍은 이후 논의할 것으로 남겼다. 제외한 코드 퀄리티 문서를 비교 기준으로 복원하지 않는다.
- **기준 후보를 보존하는 것과 채택·구현을 구별한다.** 추상 질문을 연속해서 던지거나 예시를 곧바로 결론으로 올리지 않는다. 실제 코드와 도구, 필요한 상황 차이를 보여 주며 의도를 확인한다. 라이브러리 사용법 논의가 독립 목표가 되면 얻은 판단과 열린 조건을 다시 정리한다.

## 맡은 결과와 범위

실제 코드·구조의 전후 또는 대비안을 바탕으로 **좋은 설계를 판단하는 방법과 검토 지적을 수정으로 잇는 안**을 만든다. 책임·중복·응집도·인터페이스·변경 부담과 코드가 후속 개발의 패턴이 되는 역할을 다룬다. 요구 충족과 구조 품질을 각각 판단한다.

개발 자체의 질과 사용자 스타일·배경지식에 맞는 개발을 실제 개선 방향으로 구체화한다. 과거 설명 혼란의 원인이 전부 코드 품질이었다고 입증할 필요는 없다. 사용자가 추상적 품질 기준을 먼저 완성하도록 요구하지 않고, AI가 근거 있는 대비안을 제시한다.

## 완료 조건과 확인 방법

- 실제 대비안에서 호출자가 알아야 할 지식·순서·오류 부담과 변경의 분산 정도, 유지할 동작·제품 계약이 드러난다. 줄 수나 파일 수만으로 품질을 판정하지 않는다.
- 현행 기준의 부족, 이미 있는 기준의 수행 문제, 코드·도구·검사 보완의 필요를 근거에 따라 구별한다.
- 표준 준수와 요구 충족의 차이, 근거가 충분한 지적과 판단이 필요한 후보, 유지·수정·보류 이유를 보여 준다.
- 검토 결과의 판단·수정·재확인 방법과 종료 조건, 다른 책임에 미치는 영향이 01-01·01-03과 연결된다. 선택한 B의 직접 수정 책임을 구체화하되, 실제 권한 범위와 역할 수를 근거에 따라 정한다.
- 대안의 적용 조건·비용·사용자에게 필요한 선택과 실제 적용 뒤 관찰할 효과가 있다. 코드 예시만으로 제품 개선 효과를 인정하지 않는다.

검토·수정 책임의 연결은 초안으로 비교했고 B의 직접 수정 방향을 선택했다. 실제 템플릿과 API의 책임 대비, 사용자 기준 후보 탐색까지 진행했지만 실행된 리팩터링 전후 비교·세부 기준의 의무화·제품 코드 수정은 아직 없다.

[자료 기반 워크플로 비교](../../../records/2026-10-12-13-implementation-review-verification-workflows.md)에서 이 과제의 책임이 전체 진행을 바꾸는 부분을 함께 다뤘다. 미채택 초안이며 위 완료 조건의 실제 대비·실행 근거를 아직 갖추지 않았다. 구체화 결과에 따라 01-01의 진행안도 함께 보완한다.

## B의 수정 범위 구체화

[상세 초안](../../../records/2026-10-12-16-b-execution-review-verification-contract.md)은 요구·제품 동작, 구조·인터페이스, 검사 품질, 실제 결과 근거로 검토하고 맡은 결과에 필요한 관련 코드를 직접 수정하도록 제안한다. 여러 파일의 구조 개선도 가능하며, 결과·공개 계약·제외 범위·다른 Ticket 책임이 바뀌면 Main으로 돌아간다. 이는 가상 사례의 기준이며 실제 구조 전후와 비용은 더 확인해야 한다.

## 자료 논의를 위한 구체 비교

[설계·테스트 방법과 기존 기준 비교](../../../records/2026-10-12-19-design-and-testing-methods.md)에 가상 설정 저장 사례로 호출자 부담·깊은 모듈, 인터페이스를 통한 동작 검사, 외부 의존성 대체와 순수 계산, 구조 후보 탐색·Spec/Standards 검토를 설명했다. 당시 CODE-QUALITY 대조는 분석 이력으로 보존하며, 이후 사용자 요청에 따라 설계 비교 기준에서 제외했다. 자료를 실제 스킬로 호출하거나 기준을 채택하지 않았다.

[전체안에서 먼저 볼 결정의 비교](../../../records/2026-10-13-22-first-decision-and-system-effects.md)는 상세 설계·테스트 기준을 구현자와 검토자가 함께 쓰는 안과 검토자에게 집중하는 안을 같은 가상 저장 작업에 대입했다. 당시 Main은 후자를 추천했으나 현재 기본안으로 삼지 않는다. 기준의 실제 내용·적용 조건·작업 단계에서의 지원 방법을 먼저 논의하고, 그 이해를 01-01의 인수·수정 범위와 Spec의 전체안에 연결한다. 당시 예시는 가상이었고 이후 실제 템플릿을 비교했으나, 변경 후 효과 확인은 아직 수행하지 않았다.
