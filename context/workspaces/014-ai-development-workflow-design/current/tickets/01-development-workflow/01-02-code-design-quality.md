# 01-02 — 코드·설계 품질과 검토·수정 방법을 구체화한다

상위 과제: [01 개발 작업 방식](README.md). 전체 목표·현재 구상은 [Spec 3절](../../spec.md), 다음 세션의 재개 위치는 [state](../../state.md)가 소유한다.

상태: **판단 기준을 사례별 조건과 함께 정리했고, fetcher의 유지·수정·보류 적용안에 사용자 수용을 얻었다. 작업용 기준과 검토·수정·재확인 방법을 구체화할 단계이며 01-02는 진행 중이다.** 컴포넌트에서 요청·상태·업무 흐름·이벤트·날짜 예제로 탐색을 넓혔지만 전체 코드 품질을 검증한 것은 아니다.

최신 종합은 [54](../../../records/2026-10-16-54-code-quality-criteria-and-remaining-work.md)가 소유한다. 세부 근거는 [네이밍 보완 45](../../../records/2026-10-16-45-naming-readability-supplement.md), [fetcher 비교 47](../../../records/2026-10-16-47-fetcher-error-contract-comparison.md), [Toast 48](../../../records/2026-10-16-48-toast-state-and-timer-responsibilities.md), [주문 49](../../../records/2026-10-16-49-order-mutation-workflow-boundaries.md), [이벤트 Hook 50](../../../records/2026-10-16-50-event-hook-usage-and-boundaries.md), [날짜 51](../../../records/2026-10-16-51-date-input-and-range-contracts.md), [관련 개선 조건 52](../../../records/2026-10-16-52-related-refactoring-and-product-scope.md), [검토 적용 53](../../../records/2026-10-16-53-fetcher-review-decision-rehearsal.md)에 있다. 판단안 수용과 실제 코드 수정·실행 검증은 구별하며 제품·지침·스킬 구현은 하지 않았다.

## 유지할 판단의 뉘앙스

- **책임 분리를 선호하지만 모양을 고정하지 않는다.** 의미 있는 재사용 단위를 고려하되 재사용 횟수를 문턱으로 정하지 않았다. 외부 기능 단위·내부 함수·파일 배치는 관련되지만 다른 선택이다. 이름·길이만으로 답하는 질문보다 실제 주변 코드와 역할이 필요하다.
- **기존 도구를 고려한다는 것과 도입·래핑 의무는 다르다.** 공통 Dialog는 사용처에 프로젝트의 부품을 제공하려는 의도가 있다. Radix를 쓴 직접 이유는 개발 리소스 절감이고, 직접 구현이 낫다면 그렇게 할 수 있다. 교체 용이성을 검증했다는 뜻도 아니다.
- **Confirm의 목적 정정과 이후 제거 선택을 함께 읽는다.** 비동기 문제를 피하려고 즉시 닫기용으로 축소한 제안이 문제였다. 목적을 이해하고 완료·닫기의 책임을 옮기며 제거하는 선택은 가능하다. 결과값·재전파·어댑터 제안은 채택되지 않았다.
- **사용처 부담은 아직 평가 질문이다.** 결과 반환이나 오류 전파 자체가 나쁘다고 정하지 않았다. 어떤 역할을 자연스럽게 맡는지와 자동화의 편의를 얻기 위한 계약 비용을 같이 본다.
- **Field에서 확인한 합성 의도와 후속 기준 후보를 구별한다.** 디자인 변경의 자유도를 위한 분리는 직접 확인했다. 라이브러리 의존성의 범위, 배치뿐 아니라 입력의 실제 교체 가능성, 연결 코드를 줄일 때 유지할 제어는 후속 질문에서 정리한 평가 기준이다. 네 가지 정리와 한계는 [기록 35](../../../records/2026-10-13-35-field-composition-and-design-flexibility.md)가 소유한다. 특정 폼 연결 API는 채택하지 않았다.
- **자료 읽기와 선호 탐색 완료를 구별한다.** 사용자 코드·강연·토스·Airbnb 등 떠올린 자료를 정답이나 전부 조사할 지시로 취급하지 않는다. 코드 스타일·네이밍을 뒤에 논의하기로 남겼다가 계획 42에서 각 코드와 함께 살펴보도록 제안했다. 사용자 지적에 따라 [보완 검토 45](../../../records/2026-10-16-45-naming-readability-supplement.md)에서 앞선 실제 코드도 같은 관점으로 확인했다. 스타일 규칙은 아직 미확정이다. 제외한 코드 퀄리티 문서를 비교 기준으로 복원하지 않는다.
- **기준 후보를 보존하는 것과 채택·구현을 구별한다.** 추상 질문을 연속해서 던지거나 예시를 곧바로 결론으로 올리지 않는다. 실제 코드와 도구, 필요한 상황 차이를 보여 주며 의도를 확인한다. 라이브러리 사용법 논의가 독립 목표가 되면 얻은 판단과 열린 조건을 다시 정리한다.

| 책임·응집도 | 누가 무엇을 알고 결정해야 하는지 본다. 파일·함수 수나 길이로 분리하지 않는다. |

사용자 동의·회고·AI의 적용점은 최신 종합 54와 원 사례에서 구별한다. 이 표를 고정 스타일이나 모든 파일의 의무 체크리스트로 만들지 않는다.

fetcher에서는 기존 호출·정상 반환·현재 구조를 유지하고, 오류 계약 정비와 직접 관련된 파싱·HTTP 상태 보존·타이머 정리는 수정 후보로, 오류 서비스의 범용 확대는 보류로 판단했다. 사용자는 이 판단 수준을 수용했다. 관련 확인 장면을 제시했지만 실제 테스트·수정은 수행하지 않았다.

남은 일은 다음과 같다.

1. 사례·조건을 구현자와 검토자가 사용할 안내로 구성한다. 공통 기준·프로젝트의 제품 규칙·사용자 선호를 구별하고 전달·배치 방법을 03·04와 연결한다.
2. 근거 있는 지적, 수정 범위, 보존 계약, 재확인과 종료 조건을 구체화한다. reviewer의 상세 실행 흐름은 01-01, 실제 동작 확인은 01-03과 연결한다.
3. 적용 뒤 무엇을 관찰할지 정하고 실제 실행 근거로 효과를 확인한다. 사용자에게 판단안이 수용된 것과 제품 효과가 입증된 것을 구별한다. 지금 템플릿 수정을 새 필수 작업으로 만들지 않는다.

세부 가독성·네이밍 선호는 일부 확인에 그쳤고 범용 스타일 표준은 없다. 추가 대비가 실제 판단을 바꿀 때 보완한다. 날짜의 과거 정책 회고나 전체 파일 인터뷰를 반복할 필요는 없다. 과제물·회사 자료 조사는 보류이며, 추가로 지정된 inter-persona는 오류 처리 범위만 비교했다.

계획 42의 다섯 영역에서 서로 다른 계약과 사용자 판단을 확인한 근거로 다음은 작업용 기준 초안과 검토 방법 구체화를 추천한다. 영역을 순회했다는 이유로 01-02 완료나 탐색 충분성을 선언하지 않으며 실제 적용 중 새 판단 차이가 드러나면 해당 사례를 보완한다. 기록 40의 당시 성급한 순서 판단과 기록 41의 보정은 역사적 근거로 유지한다.

## 맡은 결과와 범위

실제 코드·구조의 전후 또는 대비안을 바탕으로 **좋은 설계를 판단하는 방법과 검토 지적을 수정으로 잇는 안**을 만든다. 책임·중복·응집도·인터페이스·변경 부담과 코드가 후속 개발의 패턴이 되는 역할을 다룬다. 요구 충족과 구조 품질을 각각 판단한다.

개발 자체의 질과 사용자 스타일·배경지식에 맞는 개발을 실제 개선 방향으로 구체화한다. 과거 설명 혼란의 원인이 전부 코드 품질이었다고 입증할 필요는 없다. 사용자가 추상적 품질 기준을 먼저 완성하도록 요구하지 않고, AI가 근거 있는 대비안을 제시한다.

## 처음 만들 결과와 근거

사용자는 01-02부터 보되 **먼저 자료를 더 구체화하고 함께 논의하자**고 요청했고, 자료 설명 이후에는 전체안과 중요한 결정에서 출발하도록 방향을 보완했다. 품질 기준과 구현자·검토자 사이의 기준 배치는 선택할 후보이며, 바로 채택하거나 제품 코드를 고치지 않는다. [당시 정정과 선택 원문](../../../records/2026-10-12-18-quality-materials-next-step.md), [현재 전체안](../../spec.md)

변경이 흩어지거나 호출자가 순서·설정·오류 처리를 많이 알아야 하는 좁은 구조 사례를 골라 현재 방식과 개선 후보를 비교한다. 같은 동작을 보존하는 개선과 제품 동작을 바꾸는 선택은 구별한다. 대상 코드는 착수 시 보존 근거와 필요한 현행 상태를 확인해 고른다.

- [codebase-design](../../../source/lectures/codebase-design.ko.md): module·locality·seam, 호출자 부담과 테스트 경계.
- [PR 병목 강연](../../../source/lectures/01_PR_병목_강연_전체번역.md), [code-review](../../../source/lectures/code-review.ko.md): 표준·명세 검토, reviewer 수정 제안과 제공 스킬의 보고 종료 사이의 차이.
- [Agent 신뢰 강연](../../../source/lectures/03_Agent_신뢰_강연_전체번역.md): 코드 패턴·기계적 검사·규칙과 사람 판단.
- [Vercel 자료](<../../../source/lectures/vercel-product-design (1).md>): 결정·이유·예외·사례로 기준을 구체화하고 기계적 검사와 맥락 판단을 나누는 방법.
- [기존 실행 기준](../../../source/ai-workspace-baseline/reference-project/context/work/workspaces/spec-and-tickets/EXECUTION-CRITERIA.md): 이미 요구하는 구조 개선과 필요한 구체화의 구별.

## 다른 Ticket과 주고받을 것

[01-01](01-01-development-flow.md)은 전체 진행·책임 연결, 이 Ticket은 설계 품질의 판단·검토·수정 방법, [01-03](01-03-behavior-verification.md)는 테스트와 실제 동작 근거를 맡는다. 검토의 기준 diff·미커밋 변경 범위, 지적을 누가 판단·수정하고 언제 다시 확인하는지를 01-01과 맞춘다.

선택한 내용 중 코드·검사·개발 가이드·스킬에 둘 것을 비교하고 [03](../03-project-context.md)·[04-01](../04-skill-improvements/04-01-work-decision-skills.md)·[06](../06-framework-transition.md)에 영향을 전달한다. reviewer에게 세부 기준을 집중한다는 강연의 제안을 구현자에게 필요한 제품·구조 맥락까지 생략하는 규칙으로 확대하지 않는다.

## 완료 조건과 확인 방법

- 실제 대비안에서 호출자가 알아야 할 지식·순서·오류 부담과 변경의 분산 정도, 유지할 동작·제품 계약이 드러난다. 줄 수나 파일 수만으로 품질을 판정하지 않는다.
- 현행 기준의 부족, 이미 있는 기준의 수행 문제, 코드·도구·검사 보완의 필요를 근거에 따라 구별한다.
- 표준 준수와 요구 충족의 차이, 근거가 충분한 지적과 판단이 필요한 후보, 유지·수정·보류 이유를 보여 준다.
- 검토 결과의 판단·수정·재확인 방법과 종료 조건, 다른 책임에 미치는 영향이 01-01·01-03과 연결된다. 선택한 B의 직접 수정 책임을 구체화하되, 실제 권한 범위와 역할 수를 근거에 따라 정한다.
- 대안의 적용 조건·비용·사용자에게 필요한 선택과 실제 적용 뒤 관찰할 효과가 있다. 코드 예시만으로 제품 개선 효과를 인정하지 않는다.

검토·수정 책임의 연결은 초안으로 비교했고 B의 직접 수정 방향을 선택했다. 실제 템플릿과 API의 책임 대비, 사용자 기준 후보 탐색까지 진행했지만 실행된 리팩터링 전후 비교·세부 기준의 의무화·제품 코드 수정은 아직 없다.

## 진행안과 연결한 첫 비교

[자료 기반 워크플로 비교](../../../records/2026-10-12-13-implementation-review-verification-workflows.md)에서 이 과제의 책임이 전체 진행을 바꾸는 부분을 함께 다뤘다. 미채택 초안이며 위 완료 조건의 실제 대비·실행 근거를 아직 갖추지 않았다. 구체화 결과에 따라 01-01의 진행안도 함께 보완한다.

## B의 수정 범위 구체화

[상세 초안](../../../records/2026-10-12-16-b-execution-review-verification-contract.md)은 요구·제품 동작, 구조·인터페이스, 검사 품질, 실제 결과 근거로 검토하고 맡은 결과에 필요한 관련 코드를 직접 수정하도록 제안한다. 여러 파일의 구조 개선도 가능하며, 결과·공개 계약·제외 범위·다른 Ticket 책임이 바뀌면 Main으로 돌아간다. 이는 가상 사례의 기준이며 실제 구조 전후와 비용은 더 확인해야 한다.

## 자료 논의를 위한 구체 비교

[설계·테스트 방법과 기존 기준 비교](../../../records/2026-10-12-19-design-and-testing-methods.md)에 가상 설정 저장 사례로 호출자 부담·깊은 모듈, 인터페이스를 통한 동작 검사, 외부 의존성 대체와 순수 계산, 구조 후보 탐색·Spec/Standards 검토를 설명했다. 당시 CODE-QUALITY 대조는 분석 이력으로 보존하며, 이후 사용자 요청에 따라 설계 비교 기준에서 제외했다. 자료를 실제 스킬로 호출하거나 기준을 채택하지 않았다.

[전체안에서 먼저 볼 결정의 비교](../../../records/2026-10-13-22-first-decision-and-system-effects.md)는 상세 설계·테스트 기준을 구현자와 검토자가 함께 쓰는 안과 검토자에게 집중하는 안을 같은 가상 저장 작업에 대입했다. 당시 Main은 후자를 추천했으나 현재 기본안으로 삼지 않는다. 기준의 실제 내용·적용 조건·작업 단계에서의 지원 방법을 먼저 논의하고, 그 이해를 01-01의 인수·수정 범위와 Spec의 전체안에 연결한다. 당시 예시는 가상이었고 이후 실제 템플릿을 비교했으나, 변경 후 효과 확인은 아직 수행하지 않았다.
