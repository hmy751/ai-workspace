# 01-03 — 실제 동작 검증과 도구 선택을 구체화한다

상위 과제: [01 개발 작업 방식](README.md)

상태: **검증자1~12 설계 합의·실행 본문 통합·대표 장면 대조 완료**. [검증 상세](../../../records/prototypes/development-workflow/skills/development/references/verification.md)와 [통합·확인 기록](../../../records/2026-10-24-verifier-runtime-integration.md)에 실제 결과를 연결했다. 기계 검사를 구현 중부터 활용하고 검증자는 유효성·적절성·추가 실행을 구별한다. 수정 담당의 자기 확인과 같은 재현·영향 경계의 재검증, Main의 완료 판단까지 본문에 반영했다. 인증 예제7개 검사와 두 실행을 직접 확인했으며 실제 기기·DB·UI·역할 전체의 수행 효과 검증은 아니다. 이 Ticket의 완료 조건별 최종 대조는 아직 별도로 정리하지 않았다.

## 맡은 결과와 범위

2026-10-18 시안 연결: 기준·질문이 선택에 쓰였는지 확인할 장면을 정할 때 [보완66](../../../records/2026-10-18-66-principles-cases-and-refinement-prototype.md)과 [구체 장면](../../../records/prototypes/applied-criteria-2026-10-17/field-walkthrough.md)을 읽는다. 원칙을 읽었다는 서술, 현재 조건에 따른 선택, 제품 검사 결과를 구별한다. 이 문서의 관찰·수정·검사는 가정이므로 실제 효과의 증거로 사용하지 않는다.

대표 사용자 장면에서 **어떤 근거로 동작을 확인하고 어떤 검사·앱 관찰·도구를 사용할지 비교한 안**을 만든다. 자동 테스트의 충분성, 실제 앱 제어와 관찰, 기능과 접근 경로를 설명하는 Feature Map, 기존 실행 도구와 Verify receipt의 역할을 구별한다.

기능 발견·접근·조작·결과 확인이 어떻게 이어지는지 살피고, 관찰할 수 없는 부분과 도구 자체의 정확성·유지 비용을 드러낸다. 새 CLI 구축이나 모든 변경의 전체 앱 검사를 미리 결정하지 않는다.

## 처음 만들 결과와 근거

사용자 흐름 하나에서 원하는 동작과 실패를 먼저 정의하고, 기존 테스트·앱 실행·직접 관찰로 확인할 수 있는 것과 부족한 것을 나란히 제시한다. 구현을 반복하는 테스트, 구조에 민감한 테스트, 과도한 mock이 실제 실패를 숨기는 경우도 대조한다.

- [PR 병목 강연](../../../source/lectures/01_PR_병목_강연_전체번역.md): 자동 검사의 거짓 확신과 인터페이스를 통한 확인.
- [Agent 신뢰 강연](../../../source/lectures/03_Agent_신뢰_강연_전체번역.md): CLI·Feature Map·경험적 근거의 관계.
- [기반 동작 분석](../../../records/2026-10-12-02-framework-and-lecture-reading.md): Verify의 고정 명령·근거 보존과 실제 앱 검증의 차이.
- [Noline 스킬 색인](../../../source/noline-baseline/.claude/skills/README.md): 기존 앱 실행 등 이용 가능한 경로. 보존판에 실제 본문이나 실행 근거가 없으면 해당 범위만 추가 확인한다.

## 다른 Ticket과 주고받을 것

확인 방법을 정할 때 [01-02의 과정과 후속 재검토 65](../../../records/2026-10-18-65-criteria-status-and-cross-ticket-refinement.md)에서 판단안 수용, 가상 검사 결과, 질문의 역할을 실제로 확인하지 못한 한계를 구별한다. 반복 가능한 검사로 옮길 수 있는 판단과 맥락 해석이 필요한 판단을 나누고, 결과가 달라지면 01-02 질문의 범위·검토 입력과 Project의 계약·검사 안내도 함께 보완한다.

[01-01](01-01-development-flow.md)에 진행·검토·첫 보고에서 사용할 증거와 그 한계를 제공하고, [01-02](01-02-code-design-quality.md)의 설계 변경에서 유지할 동작과 실패 조건을 받는다. [02](../02-work-records.md)에는 후일 보존할 실행 근거, [03](../03-project-context.md)에는 기능·조작·검증 맥락의 필요를 전달한다.

실제 도구 배치·기존 장치와의 결합은 [06](../06-framework-transition.md), 전체 적용·효과 관찰은 [07](../07-integrated-rehearsal.md)과 연결한다. 보존한 실행 기록과 이번 설계에서 직접 실행한 결과를 구별한다.

## 완료 조건과 확인 방법

- 대표 사용자 장면의 요구·실패 조건과 필요한 증거가 연결된다. 검사 통과·reviewer 보고·Verify receipt·사람의 수락이 각각 증명하는 범위를 설명한다.
- 기존 검사와 직접 관찰로 충분한 경우, 테스트나 도구 보완이 필요한 경우를 비교한다. 실제 오류를 숨기는 테스트의 한계를 보여 준다.
- 기능에 접근해 조작하고 결과·trace를 확인할 경로 또는 그 경로의 미확인·공백이 구체적이다.
- 도구의 정확성·설정·유지 비용, 작은 작업에서의 확인 범위와 재검증 조건을 비교한다. 확인할 수 없는 것을 완료로 보고하지 않는다.
- 선택 가능한 도구·방법의 장단점과 후속 구현·실제 환경 확인 범위를 제시한다. 설계 예시와 실제 실행 증거를 구별한다.

현재는 별도 검증의 수행·도구 선택·수정·종료·배치를 실행 본문에 반영하고 대표 장면에 대조했다. 과거 설계 리뷰, 이번 Main의 의미 대조, 직접 실행한 메모리 예제 근거를 구별한다. 실제 앱·대상별 도구의 확인과 역할 전체의 수행 효과는 남아 있다.

## 진행안과 연결한 첫 비교

[자료 기반 워크플로 비교](../../../records/2026-10-12-13-implementation-review-verification-workflows.md)에서 이 과제의 책임이 전체 진행을 바꾸는 부분을 함께 다뤘다. 미채택 초안이며 위 완료 조건의 실제 대비·실행 근거를 아직 갖추지 않았다. 구체화 결과에 따라 01-01의 진행안도 함께 보완한다.

## 과거 B의 최종 실제 검증 제안

[상세 초안](../../../records/2026-10-12-16-b-execution-review-verification-contract.md)의 원 구현자 최종 검증은 이전 제안이다. 이후에는 검토자가 수정·검사·최종 실제 확인을 이어가고 Main이 완료를 판단하는 안을 제안했다. [당시 변경 근거](../../../records/2026-10-12-17-workflow-basis-and-connected-design.md)는 분석 이력으로 남긴다. 원자료 조사에서 실제 검증과 코드 작성에 참여하지 않은 주체의 검증이 다른 계약으로 나타났으므로, 주체는 후속 합의의 별도 검증자와 Main으로 이어졌고, 구체 독립 확인·수정·종료 조건을 현재 설계에서 채운다. 대상 앱의 실행 경로·데이터·도구는 아직 확인하지 않았다.
