# 02 — 기록 운영과 Workspace 구성을 구체화한다

상태: **분해 정리 완료 · 설계 작업 미착수**. 보존 자료가 준비된 것과 이 Ticket의 기록 운영안을 만든 것은 다르다. 전체 기준은 [Spec](../spec.md)에 있다.

## 맡은 결과와 범위

Work에서 생기는 목표·선택·분석·중간 결과·검증·시행착오를 무엇 때문에 보존하고, 어디에 얼마나 남기며, 언제 누가 갱신하고 다시 읽는지 **구체적인 기록 예시와 운영안**으로 만든다. 바로 다음 행동을 돕는 기록과 후일 재검토할 기록을 함께 다루되, 모든 대화를 보존하는 안을 기본값으로 두지 않는다.

기록을 담는 **Workspace 구성 자체**도 설계 대상이다. `current` 안의 memory·state·Spec·Ticket, records·source·output의 역할과 관계, 진입점과 읽는 순서, 생성·갱신·완료 후 보존 방식을 함께 비교한다. 지금의 폴더와 파일 구성을 고정한 채 내용을 보강하는 데 한정하지 않는다. 과거에 문제가 관찰되지 않았더라도 더 나은 탐색·이해·작성·유지 방식이 있는지 제안하고 판단할 수 있다.

재개할 때 읽기만 하고 작업 중심을 놓친 사례를 포함한다. Spec·Ticket·state의 현재 의미와 records·output·원문 보존의 관계를 함께 보고, 기록 시점과 내용 기준, 읽고 적용하는 행동을 구별한다. 세션 종료 외에도 작업 도중 의미가 바뀌는 경계나 부분 완료에서 어떻게 대응할지 비교한다.

이 Ticket의 결과는 자동 Maintainer를 재개하지 않는 조건에서 가능한 기록 운영안이다. 실제 장치의 코드·설정 제거와 의존 관계 정리는 06이 맡고, 경험에서 새 기준을 채택하는 루프는 05가 맡는다. 문서를 갱신할 때 곧바로 운영 기준도 바뀌는 것으로 만들지 않는다.

## 실행 맥락과 접근

기존 기록·재개 실패와 성공 비교를 함께 사용한다. 핵심 발췌가 보존되고 열람됐어도 우선순위가 어긋난 사실, 긴 작업 뒤 수동 기록에서도 재개가 성공한 사실을 대조한다. 기록을 더 자주 하거나 더 많이 쓰면 해결된다고 미리 정하지 않는다.

구조 대안은 현재 구성을 유지하며 역할을 명료하게 하는 안, 겹치는 내용을 합치거나 진입 경로를 줄이는 안, 작업 크기·단계에 따라 필요한 구성을 달리하는 안 등에서 의미 있는 차이가 있을 때 비교한다. 이는 후보 예시이며 고정 선택지가 아니다. 짧은 작업, 여러 세션의 장기 작업, 작업 중 방향 변경, 완료 뒤 재검토에 대입해 무엇을 읽고 어디를 고쳐야 하는지 보여 준다. 파일 수나 읽는 양만 줄이지 않고, 누락·중복·낡은 상태·작성 부담과 이후 다시 찾을 수 있는지를 함께 판단한다.

실제 장면 일부를 골라 지금 기록의 의미, 보완한 기록 예시, 그것을 읽고 할 다음 행동을 나란히 제시한다. 후일 돌아볼 분석이나 버린 대안처럼 당장 작업 중심이 아닌 자료도 포함한다. 갱신 주체와 호출 방식은 이런 결과를 충분히 남길 수 있는지를 보고 비교한다.

- [기록 시점과 재개 비교](../../source/reading/noline-evaluation/reviews/record-timing-followup.md): 보존·열람·적용을 구별할 직접 사례.
- [추가 원문 도구 사건](../../source/supplement/README.md): 기록 내용과 읽은 사실을 다시 확인할 때.
- [Workspace 문서 기준](../../source/ai-workspace-baseline/reference-project/context/work/workspaces/DOCUMENT-WRITING.md): 이미 요구하는 의미와 부족한 구체성을 구별할 기반.
- [사용자의 범위 정정](../../source/discussion/design-conversation.md#L2659): 기록을 다음 작업용으로 한정하지 말라는 요청.

프로젝트 경험을 공통 기반 개선으로 전달할 때 필요한 근거의 보존 형태는 여기서 다루고, 어떤 경험을 개선으로 채택할지는 05, 저장소 사이의 전달·재적용 방식은 06과 맞춘다. [범위 보완 요청과 초기 후보](../../records/2026-10-12-10-workspace-and-feedback-scope.md)를 참고한다.

03의 Project 공통 내용, 01-01의 실제 개발·보고 흐름, 04-01~04-03의 스킬 기록 연결과 맞춘다. 특정 Main·skill 배치를 먼저 확정해 나머지를 맞추지 않는다.

## 완료 조건과 확인 방법

- Workspace의 구성과 진입·갱신·보존 경로를 비교하고 유지·변경할 이유를 제시한다. 과거 실패의 재발 방지만이 아니라 작업 규모·수명에 맞는 사용성도 검토한다. 선택한 안에서 각 내용의 정본과 관리 책임을 찾을 수 있다.
- 대표 사례에서 남길 내용·위치·분량과 원문 필요 여부를 판단한 이유가 구체적으로 보인다. 바로 재개할 정보와 후일 보존할 자료가 모두 검토된다.
- 보완한 기록을 읽었을 때 현재 중심, 잠정 선택, 완료·미완료와 근거로 내려가는 경로를 복원할 수 있다. 필요한 경우 제한된 새 독자 검토로 확인하며 자동 보장으로 말하지 않는다.
- 기록 시점·작성 책임·갱신과 다시 읽는 경로의 후보가 실제 대화 장면에 적용된다. 작성 부담, 놓칠 가능성, 다른 문서와의 중복 및 재검토 조건을 설명한다.
- 유지할 기록 원칙과 이후 06에서 바꿔야 할 장치·연결이 구분된다. 운영 선택이 미정이면 대안과 영향이 남는다.

위 조건을 만족하는 **운영안 제시**가 현재 맡은 결과다. 선택·실제 적용·재개 효과 확인은 그 상태를 별도로 남긴다.

## 현재 상태와 실제 결과

평가·인터뷰·성공/실패 비교가 보존돼 있다. 기록 예시의 재작성, 후보 비교, 갱신 시점과 책임의 설계는 아직 수행하지 않았다. 01-01의 진행 초안과 대조하며 구체화할 과제다.
