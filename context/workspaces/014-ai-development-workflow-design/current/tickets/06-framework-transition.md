## 04-02에서 이어받은 배치 입력

2026-10-26 [04-02 설계 마감](../../records/2026-10-26-ticket04-02-closeout-and-followups.md)의 현재 explain·development·관련 상세·공통 근거를 전환 계획의 입력으로 받는다. 기존 두 설명 스킬은 prototype에서 통합됐지만 실제 운영 대상의 설치·호출·참조가 바뀐 것은 아니다.

대상을 선택하면 현재 설치판과 새 묶음의 차이, development→explain 호출, 상세·공통 근거의 접근, 기존 스킬 참조의 교체·공존 필요, 적용 순서와 되돌릴 판본을 확인한다. 계획에는 변경 담당·허용 범위·직접 확인 경로와07에 넘길 적용 조건을 포함한다. 역할·실행 지침은04-02 결과를 재사용하고 배치 때문에 의미를 바꿔야 할 때만 해당 책임에 돌려준다. 실제 제거·설치·배포는 별도 실행 범위이며 이 입력 연결로 완료되지 않는다.

## 맡은 결과와 범위

앞선 설계를 실제로 어디에 반영해야 하는지, 공통 기반과 대상 프로젝트에서 무엇을 다르게 소유해야 하는지 **변경 배치와 전환 계획**으로 만든다. 문서·스킬·설정·코드·검증이 해당 책임을 중심으로 이어지게 하고, root·reference-project·Noline의 운영 차이를 반영한다.

일회성 이식 이후의 **프로젝트 경험 → ai-workspace 개선 → 대상 프로젝트 반영**도 검토한다. Noline의 기록을 매번 크게 옮겨야 하는지, 공통 개선과 프로젝트별 수정을 어떻게 구별하고 필요한 변경만 전달할지 비교한다. 더 효율적인 방법이 없다면 현재 수동 방식을 유지하는 결론도 가능하다. 자동 동기화·새 도구·배포 체계 구축을 요구하는 과제로 바꾸지 않는다.

기존 자동 Maintainer를 재개하지 않으며 장치를 걷어내고 기록 원칙을 남기려는 사용자 방향을 다룬다. 남길 원칙, 사라질 동작, 대신 수행할 책임, 스킬의 기록 인계, Recover·Verify·공통 CLI의 결합을 대조한다. 폴더 삭제 목록이나 Main이 다 맡는다는 선언만으로 전환이 성립한다고 보지 않는다.

개발 방식·기록·Project·스킬·경험 반영의 내용이 정리될 때까지 현재 의존 관계 확인을 미룰 필요는 없다. 다만 최종 변경 배치는 관련 설계 결과를 바탕으로 보완한다. 실제 자동 장치 제거·스킬 개편·Noline 이식·공개 배포는 여기서 설계할 후속 실행이며 지금 수행하지 않는다.

## 실행 맥락과 접근

저장소 루트는 수동 기록을 쓰고, Reference에는 Recover·Maintain·Verify의 기준 구현이 있으며, Noline은 별도로 이식·변경됐다. 이 세 상태를 같은 것으로 취급하지 않는다. 기존 012 publication과 013 Maintain 효율 검토는 별도 목적을 가진 작업으로 남는다.

설계 선택별로 공통 기준에서 바꿀 의미, 대상 프로젝트에서 채울 실제 내용, 실행 장치와 호출·검증의 연결을 대응시킨다. Spec·Ticket 작성/실행 기준과 Project 구성 기준, 작업 스킬도 포함한다. 모든 결과를 글로벌 지침으로 올리거나 Reference를 통째로 복사하는 방식으로 고정하지 않는다.

- [기반의 실제 구성·동작 분석](../../records/2026-10-12-02-framework-and-lecture-reading.md): root와 Reference, 장치의 책임 및 확인 한계.
- [ai-workspace 기준판](../../source/ai-workspace-baseline/README.md), [Reference 기준판](../../source/ai-workspace-baseline/reference-project/README.md): 소스·문서·테스트를 좁게 확인할 경로.
- [Noline 설치·설계 근거](../../source/reading/noline-evaluation/reviews/noline-design-basis.md): 공통 기반과 실제 적용의 차이.
- [이식 스킬 기준판](../../source/ai-workspace-baseline/.agents/skills/apply-context-harness/SKILL.md): 기존 정본·대상 내용과 적용 경계.

기존 이식 절차의 source commit, 책임별 적용·적응·제외 매핑, 기존 정본·사용자 변경 보호를 출발점으로 삼는다. 개선 사례에 필요한 발췌·산출물·적용 버전을 선별해 보존하고, 채택한 공통 변경을 이전 적용 기준·새 기준·대상 현행 상태와 대조해 좁게 반영하는 방식은 초기 비교 후보다. 이런 반복 갱신 흐름이 이미 구현됐다고 간주하지 않는다. 원문을 다시 볼 수 없는 경로 링크만 남기거나 프로젝트 고유 맥락을 공통 템플릿에 복제하는 방식은 피한다.

한 가지 개선을 왕복시키는 예시로 전달·재조사·충돌 확인·적용 후 확인의 부담을 비교한다. 어떤 자료가 실제로 더 필요한지, 버전과 적용 차이를 유지하는 비용이 반복 수집을 줄이는 이득보다 큰지도 본다. 초기 후보와 확인한 기존 기반은 [범위 보완 기록](../../records/2026-10-12-10-workspace-and-feedback-scope.md)에 있다.

특히 02의 기록 책임, 03의 Project 내용·관리, 01-01의 진행·판단, 01-02·01-03의 품질·검증, 04-01~04-03의 스킬 연결, 05의 개선 후보 반영 위치를 서로 대조한다. 최종 owner나 권한을 이름만으로 정하지 말고 실제 산출물과 호출 경로에서 빈 책임을 찾는다.

## 완료 조건과 확인 방법

- 각 제안이 어떤 기준·파일·스킬·장치와 대상 프로젝트의 내용에 영향을 주는지 추적할 수 있다. 공통 정의와 개별 내용의 중복 정본을 검토한다.
- Maintainer 장치를 제거한 뒤에도 보존하려는 기록 원칙과 필요한 작업이 누가 무엇을 통해 수행되는지 연결된다. 제거 범위·남길 결합·필요한 수정·확인 방법이 구체적이다.
- Recover·Verify 등을 유지·단순화할 선택은 이유와 의존 관계로 판단하고, 자동 Maintainer를 재개하지 않는 사용자 방향을 충족한다.
- 적용 단위, 선행 조건, 기존 자료 보존과 실패 시 되돌릴 범위, 실제 환경에서 확인할 사항을 설명한다. 코드 실행을 하지 않은 부분은 계획으로 표시한다.
- 공통 기준 개편·대상 프로젝트 반영·별도 진행 작업의 관계 및 남은 선택이 분명하다.
- 프로젝트 경험을 공통 개선으로 검토하고 다시 반영하는 대표 예시에서 근거의 보존 위치·전달 범위, 공통/개별 변경의 구별, 적용 기준과 대상의 차이 확인, 적용 후 확인 경로가 드러난다. 기존 수동 방식 대비 이득·추가 관리 비용을 설명하고, 더 나은 대안이 없으면 유지할 이유를 남긴다. 시간·토큰 절감은 관찰 없이 단정하지 않는다.

현재 맡은 결과는 변경·전환의 설계안이다. 검토 가능한 안의 완료와 실제 제거·설치·적용 성공을 구별한다.
