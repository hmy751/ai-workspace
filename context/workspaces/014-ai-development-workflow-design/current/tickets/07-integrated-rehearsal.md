# 07 — 부분 설계를 실제 장면으로 연결하고 후속 적용을 계획한다

2026-10-26 [04-03 프로토타입 적용과 확인](../../records/2026-10-26-context-prototype-adoption.md)을 부분 연결 근거로 받는다. 직접 요청의 읽기·반영·생성/전환과 문서상 역할 연결을 실제 여러 역할의 개발 수행·host 재개/전환·자동 발견·반복 사용감의 증거로 확대하지 않는다. USAGE와 context-update가 이어지는 사용감, 중단 뒤 실제 복구, 구현자의 제안과 Main 반영을 전체 적용 계획에서 선택해 관찰한다. 확인한 장면을 이유 없이 다시 반복하지 않는다.

상태: **개발 흐름의 부분 연결 근거 확보 · 전체 체계 연결과 적용·관찰 계획은 미완료**. [01-01·01-03 마감](../../records/2026-10-24-ticket01-01-03-closeout-and-next-scope.md)의 대표 장면 대조를 재사용한다. 전체 기준은 [Spec](../spec.md)에 있다.

2026-10-20 후속 입력: [03 마감119](../../records/2026-10-20-119-ticket03-closeout.md)의 본문 구성 결과를 전체 연결 검토의 입력으로 사용한다. 제한된 변경 실험·새 독자 관찰·정적 링크 검사와 실제 운영 사용·장기 유지 효과를 구별한다. 후속의 새 소비·변경에서 관리 단위나 자료 충분성 문제가 드러나면03 결과와 해당 정책까지 다시 대조한다. 이번 마감에서 전체 적용 실험을 수행한 것은 아니다.

## 04-02에서 이어받은 적용·관찰 항목

2026-10-26 [04-02 설계 마감](../../records/2026-10-26-ticket04-02-closeout-and-followups.md)을 입력으로 받는다. [두 최초 응답과 한계](../../records/experiments/explain-choice-investigation-60medium-revised-2026-10-26/comparison.md)는 제한 수행의 근거이며 전체 개발 workflow나 일반 효과의 검증이 아니다. 같은 사례의 문구 보강·재생성을 기본 계획으로 잡지 않는다.

| 관찰할 것 | 실제 작업에 연결할 수행과 근거 |
| --- | --- |
| 선택 판단이 역할 설명·과거 제안의 반복으로 끝나는가 | 적용 대상의 Main이 명시 목표·실제 소비를 기준으로 현재안과 의미 있는 대안의 결과·부담을 비교하고 선택 이유를 설명한다. access 사례에서는 전체 공개와 필요한 정보만 공개하는 대안 비교가 남았다. 이 사례의 특정 반환 형태를 정답으로 고정하지 않는다. |
| 미확인 표기가 가능한 조사를 대신하는가 | 조사 담당이 중요한 주장의 검사 본문·입력·assertion·대체 경계와 기존 실행의 유효성을 대조한다. 가능한 추가 확인은 수행하고 막힌 실행은 Main이 준비·담당을 연결한다. 폼 근거 부족과 실제 기기 실행 미확인을 구별하고, 파일 읽기를 실앱 실행으로 세지 않는다. |
| 첫 결과·앞선 말의 의미가 유지되는가 | 원래 목표·변경·확인 연결과 원뜻/현재 타당성 구별을 실제 적합한 작업에서 관찰한다. 이미 주요 미충족을 찾지 못한1번·3번을 자동 재시험할 필요는 없다. |

이 티켓의 적용 계획에는 대상 작업·시점·Main과 수행 담당·접근 및 실행 조건·비교할 결과·남길 최소 근거를 구체화한다.06의 배치 계획을 입력으로 받아 가능한 범위부터 연결하되, 계획을 실제 적용 성공으로 표시하지 않는다. 현재는 대상 작업을 새로 실행하거나 Noline의 제품 변경을 맡긴 상태가 아니다.

관찰은 원요청·자료·실제 행동·결과·사용자 반응과 미확인을 구별한다. 읽기 수·문장 수·재질문 유무를 성능 점수로 쓰지 않으며 필요한 학습·설계 질문은 실패로 세지 않는다. 중요한 누락이 반복되거나 지침 충돌·요구 누락이 드러나면05의 개선 판단과 해당04-02 본문으로 반환한다. 제품·검사·환경 문제는 실제 개발 작업의 기존 담당에게 연결한다.

## 맡은 결과와 범위

2026-10-18 시안 연결: 부분 설계의 재판단이 다른 책임에 미치는 영향을 볼 때 [보완66](../../records/2026-10-18-66-principles-cases-and-refinement-prototype.md)과 [구체 장면](../../records/prototypes/applied-criteria-2026-10-17/refinement-walkthrough.md)을 읽는다. 후속03이 파일 배치를 바꾸면 기준 본문·안내·역할·기록 연결 중 무엇을 함께 바꾸는지 대조한다. 전체 Ticket 완료 뒤에만 하는 작업으로 미루지 않는다.

각 설계가 한 작업에서 함께 쓰일 때 모순·빠진 책임·과한 비용이 없는지 확인하고, 무엇부터 실제 적용해 확인할지 **연결 검토 결과와 후속 적용·관찰 계획**으로 만든다. 개별 Ticket에서 이미 확인해야 할 사례와 품질을 이 Ticket의 마지막 검토로 미루지 않는다.

개발 시작부터 조사·사람의 선택·결과 확인·보고·기록·재개까지 이어지는 장면을 선택하고, 장면별로 어느 맥락·스킬·도구·사람 판단이 필요한지 따라가 본다. 후일 기록을 다시 검토하는 경우와 경험에서 개선 후보를 만드는 경우도 관련성에 따라 연결한다. 한 실제 세션에서 모두 발생했다고 꾸미지 않는다.

과거 장면에 새 설계를 대입하는 확인은 설계의 충분성을 검토하는 재현 예시다. 실제 제품에서 효과가 개선됐다는 증거는 아니다. 이후 실제 작업에서 확인할 결과·부담·관찰 범위를 별도로 정한다.

## 실행 맥락과 접근

부분 설계가 다른 조건과 만나는 때 [01-02 후속 조언 65](../../records/2026-10-18-65-criteria-status-and-cross-ticket-refinement.md)의 재검토 경로를 사용한다. 결과물뿐 아니라 성립 조건·대안·사용자 정정을 필요한 만큼 읽고, 읽기·역할·검사·기록의 새 선택이 기존 기준과 배치를 바꾸는지 살핀다. 달라진 현재 정본·Ticket을 고치고 전체 관계 변화는 Spec에, 변경 이유는 기록에 남긴다. 설계 중 재구체화를 실제 사용 뒤 경험 반영까지 미루지 않으며, 이 연결 문장만으로 전체 리허설이나 효과 확인을 완료했다고 보지 않는다.

대표 사례는 [Spec의 장면](../spec.md)과 기존 평가에서 고른다. 필요한 학습 질문이나 중요한 제품 선택을 포함해, 모든 사람 개입이 줄어야 성공이라는 기준으로 흐르지 않게 한다. 한 번의 성공과 반복 사용의 효과도 구별한다.

각 안을 함께 적용했을 때 작업 중심과 입력이 전달되는지, 지적·수정·선택·기록의 책임이 비거나 겹치는지, 다음 주체가 충분히 이해할 수 있는지 본다. 맞지 않으면 관련 Ticket과 Spec을 보완하고 의미 있는 검토 이유를 records에 남긴다.

- [평가·인터뷰 해석](../../records/2026-10-12-01-background-and-evaluation.md): 필요한 참여, 반복 교정, 만족도 미확인을 구별하는 사례.
- [장면 색인](../../source/reading/noline-evaluation/scene-index.md): 다시 볼 직접 장면을 좁게 선택할 경로.
- [설계 정정 원문](../../source/discussion/design-conversation.md#L2659): 전체 통합에서 기록과 Project의 범위를 다시 좁히지 않을 기준.
- [Vercel 제품 설계 자료](<../../source/lectures/vercel-product-design (1).md>): 기준 없는 실행과의 비교, 사람 선택, 관찰할 효과의 참고. 제공된 eval 범위를 일반 효과 증명으로 확대하지 않는다.

다른 Ticket의 결과가 모두 최종 채택돼야 사례 선택이나 부분 연결을 시작할 수 있는 것은 아니다. 다만 전체 안을 충분하다고 보고할 때에는 아직 검토하지 않은 영역과 그 영향을 함께 밝힌다.

## 완료 조건과 확인 방법

- 대표 장면에서 부분 설계의 내용·행동·근거·결과가 이어지는 것을 설명하고, 충돌이나 빠진 책임을 관련 문서로 되돌려 반영한다.
- 배경 없는 독자가 목표·선택 이유·현재 상태·미정과 다음 행동을 복원할 수 있는지 필요한 범위에서 확인한다. 링크 존재 검사와 의미 복원을 구별한다.
- 남은 설계 문제와 후속 적용에서만 확인할 것을 분리하고, 전체 완료 주장의 범위가 그 결과와 맞는다.
- 우선 적용 후보와 선택 이유, 실제 변경 단위, 필요한 전제, 관찰할 효과와 부작용, 부족할 때 보완할 경로가 있는 계획을 제시한다. 측정하지 않은 토큰·시간 절감을 단정하지 않는다.

현재 맡은 결과는 연결 검토와 **적용 계획의 제시**다. 실제 적용 범위의 선택과 실행, 장기 효과 확인은 이후 상태로 남긴다.

## 현재 상태와 실제 결과

014의 기록 Workspace 자체는 새 독자의 재진입을 확인했다. 이는 앞으로 만들 전체 작업 방식의 검증이 아니다. 개발 내부의 구현·개선 검토·검증·수정·Main 기록 연결은01-01·01-03에서 대조했다. 이 Ticket은 그 근거를 재사용하며 기록 재개·경험 반영·새 독자의 복원과 우선 적용·관찰 계획을 전체 체계에서 종합해야 한다.
