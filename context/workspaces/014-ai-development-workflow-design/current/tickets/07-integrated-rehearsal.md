## Noline에서 대상과 실행 범위를 정한다

첫 대상은 **기존 작업 하나와 그 판단을 복원할 관련 기록**에서 고른다. 해결하거나 재검토할 실제 질문이 있고 원요청·선택 이유·현재 결과를 확인할 수 있는 작업을 우선한다. 완료된 작업의 회고인지, 진행 중인 작업의 재개·변경인지 구별한다. 지금 특정 Ticket·기록·원문 범위나 실행 시점을 선택한 것은 아니다.

Noline에서 실행을 맡는 Main은 해당 작업의 기존 담당·관리 규칙과 아래 내용을 확인해 실행 범위를 정한다. 같은 내용을 새 양식이나 별도 Workspace로 복제할 필요는 없다.

1. **현행과 질문:** 실제 설치본·제품 고유 기준·사용자 변경, 지금 답할 질문과 결과를 사용할 곳을 확인한다.06의 반영 기준은 Noline `41170efd`이며 이후 변경은 현행과 대조한다. 실행에는 Noline 설치본을 사용하고 prototype은 판단 이유를 다시 볼 때 참조한다.
2. **근거 범위:** 관련 작업·결정·검증 기록과 필요한 대화 원문을 고른다. 과거 선택과 현재 유효한 판단을 구별한다. 요청된 전체 대화에 접근할 수 없으면 확보 범위·공백을 드러내고 전체 검토 완료로 올리지 않는다.
3. **실행과 관찰:** 질문에 필요한 개선 루프·개발·설명·맥락 읽기/갱신을 선택하고, 아래 항목 중 이번 장면에서 실제로 확인할 것과 미확인으로 남길 것을 정한다. 기존 검사·관찰 근거는 판본과 적용 범위가 맞으면 재사용한다.
4. **반영과 종료:** 추천·사용자 선택·실제 변경·직접 확인을 구별해 실제 Owner에 반영한다. 한정 시도를 선택했다면 재개 위치와 종료 조건을 연결하고 종료 때 임시 지시를 정리한다. 다음 관련 요청이 있을 때 기존 경험·미결·기반영 항목을 다시 본다.

Maintain·Work 구성/기록 계약 변경과 host 통합 테스트는 계속02에서 진행한다. Noline의 기존 계약으로 가능한 작업·기록 검토는 그와 구별하며,02 미정에 의존하는 부분은 의존 이유와 남은 확인으로 둔다.07 계획으로 장치 전환이나 통합 테스트를 앞당겨 실행하지 않는다.

## 맡은 결과와 범위

2026-10-18 시안 연결: 부분 설계의 재판단이 다른 책임에 미치는 영향을 볼 때 [보완66](../../records/2026-10-18-66-principles-cases-and-refinement-prototype.md)과 [구체 장면](../../records/prototypes/applied-criteria-2026-10-17/refinement-walkthrough.md)을 읽는다. 후속03이 파일 배치를 바꾸면 기준 본문·안내·역할·기록 연결 중 무엇을 함께 바꾸는지 대조한다. 전체 Ticket 완료 뒤에만 하는 작업으로 미루지 않는다.

개발 시작부터 조사·사람의 선택·결과 확인·보고·기록·재개까지 이어지는 장면을 선택하고, 장면별로 어느 맥락·스킬·도구·사람 판단이 필요한지 따라가 본다. 후일 기록을 다시 검토하는 경우와 경험에서 개선 후보를 만드는 경우도 관련성에 따라 연결한다. 한 실제 세션에서 모두 발생했다고 꾸미지 않는다.

과거 장면에 새 설계를 대입하는 확인은 설계의 충분성을 검토하는 재현 예시다. 실제 제품에서 효과가 개선됐다는 증거는 아니다. 이후 실제 작업에서 확인할 결과·부담·관찰 범위를 별도로 정한다.

## 실행 맥락과 접근

부분 설계가 다른 조건과 만나는 때 [01-02 후속 조언 65](../../records/2026-10-18-65-criteria-status-and-cross-ticket-refinement.md)의 재검토 경로를 사용한다. 결과물뿐 아니라 성립 조건·대안·사용자 정정을 필요한 만큼 읽고, 읽기·역할·검사·기록의 새 선택이 기존 기준과 배치를 바꾸는지 살핀다. 달라진 현재 정본·Ticket을 고치고 전체 관계 변화는 Spec에, 변경 이유는 기록에 남긴다. 설계 중 재구체화를 실제 사용 뒤 경험 반영까지 미루지 않으며, 이 연결 문장만으로 전체 리허설이나 효과 확인을 완료했다고 보지 않는다.

대표 사례는 Noline에서 기존 작업·기록의 실제 질문을 기준으로 고르고 [Spec의 장면](../spec.md)과 기존 평가는 관련 판단을 보강할 때 사용한다. 필요한 학습 질문이나 중요한 제품 선택을 포함해, 모든 사람 개입이 줄어야 성공이라는 기준으로 흐르지 않게 한다. 한 번의 성공과 반복 사용의 효과도 구별한다.

각 안을 함께 적용했을 때 작업 중심과 입력이 전달되는지, 지적·수정·선택·기록의 책임이 비거나 겹치는지, 다음 주체가 충분히 이해할 수 있는지 본다. 맞지 않으면 관련 Ticket과 Spec을 보완하고 의미 있는 검토 이유를 records에 남긴다.

- [평가·인터뷰 해석](../../records/2026-10-12-01-background-and-evaluation.md): 필요한 참여, 반복 교정, 만족도 미확인을 구별하는 사례.
- [장면 색인](../../source/reading/noline-evaluation/scene-index.md): 다시 볼 직접 장면을 좁게 선택할 경로.
- [설계 정정 원문](../../source/discussion/design-conversation.md#L2659): 전체 통합에서 기록과 Project의 범위를 다시 좁히지 않을 기준.
- [Vercel 제품 설계 자료](<../../source/lectures/vercel-product-design (1).md>): 기준 없는 실행과의 비교, 사람 선택, 관찰할 효과의 참고. 제공된 eval 범위를 일반 효과 증명으로 확대하지 않는다.

다른 Ticket의 결과가 모두 최종 채택돼야 사례 선택이나 부분 연결을 시작할 수 있는 것은 아니다. 다만 전체 안을 충분하다고 보고할 때에는 아직 검토하지 않은 영역과 그 영향을 함께 밝힌다.

## 완료 조건과 확인 방법

- 대표 장면에서 부분 설계의 내용·행동·근거·결과가 이어지는 것을 설명하고, 충돌이나 빠진 책임을 관련 문서로 되돌려 반영한다.
- 배경 없는 독자가 목표·선택 이유·현재 상태·미정과 다음 행동을 복원할 수 있는지 필요한 범위에서 확인한다. 링크 존재 검사와 의미 복원을 구별한다.
- 남은 설계 문제와 후속 적용에서만 확인할 것을 분리하고, 전체 완료 주장의 범위가 그 결과와 맞는다.
- 우선 적용 후보와 선택 이유, 실제 변경 단위, 필요한 전제, 관찰할 효과와 부작용, 부족할 때 보완할 경로가 있는 계획을 제시한다. 측정하지 않은 토큰·시간 절감을 단정하지 않는다.

현재 맡은 결과는 연결 검토와 **적용 계획의 제시**다. 실제 적용 범위의 선택과 실행, 장기 효과 확인은 이후 상태로 남긴다.

## 현재 상태와 실제 결과

014의 기록 Workspace 자체는 새 독자의 재진입을 확인했다. 이는 앞으로 만들 전체 작업 방식의 검증이 아니다. 개발 내부의 구현·개선 검토·검증·수정·Main 기록 연결은01-01·01-03에서 대조했다. 이 Ticket은 그 근거를 재사용하며 기록 재개·경험 반영·새 독자의 복원과 우선 적용·관찰 계획을 전체 체계에서 종합해야 한다.

## 05에서 이어받은 루프 적용 관찰 입력

[05 설계 마감](../../records/2026-10-29-ticket05-closeout.md)의 완료 경계와 열린 기준을 입력으로 받는다. prototype 설계 완료를 실제 운영 확인으로 바꾸지 않는다.

[루프 실행안](../../records/prototypes/development-workflow/skills/improvement-loop/SKILL.md)과 [Main 점검의 상한](../../records/2026-10-28-ticket05-execution-prototype.md)을 입력으로 받는다. 실제 사용자 요청의 대화 전체 확인·관련 본문 검토·추천/선택·즉시 반영과, 다음 관련 루프의 Personal 경험/미결/기반영 항목 재조회·갱신을 확인할 장면을 정한다. 읽음·실제 적용·도움·부담·미확인을 구별하고 새 근거 없는 보류안 반복 제안·미채택 후보의 지침화가 없는지 본다. 입력 누락은 전체 검토 미완료로 남긴다. 동일 긴 대화 재실행·정기 평가·별도 Work 등록을 의무로 만들지 않는다. 실제 사용 효과를 prototype 파일·링크 검사로 대신하지 않는다.

05의 두 실행 보완은 [반영·완료 조건 대조](../../records/2026-10-29-improvement-loop-means-comparison-adoption.md)에서 이어받는다. 후속 적용을 맡는 Main은 사용자가 요청한 첫 실제 루프에서 원문 접근·범위 공백과 기존 경험 재조회를, 한정 시도를 실제로 선택한 경우 해당 작업의 재개·종료 정리를 관찰할 장면으로 잡는다. 다음 요청된 관련 루프에서는 실제 사용·도움·부담·미확인을 대조한다. 후보를 실행 지시로 오독하거나 종료된 시도가 계속 적용되면 해당 읽기·종료 연결을 수정하고, 적용했으나 이득이 불분명하면 조건 축소·유지·철회를 비교한다. 자료 접근 문제는06의 실제 host 확인과 잇는다. 이는 후속 관찰 입력이며 지금 새 시험·정기 평가를 실행하거나 도구 시도를 선택한 것이 아니다.
