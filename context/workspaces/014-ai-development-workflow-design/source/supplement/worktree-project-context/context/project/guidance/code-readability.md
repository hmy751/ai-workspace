# 코드 표현과 책임을 읽는 기준

Noline의 새 코드와 기존 코드를 수정할 때 적용하는 표현 기준이다. 목적은 값·조건·실패·완료와 책임을 가까운 코드에서 이해하게 하는 것이다. 이 기준의 채택은 기존 코드 전체를 일괄 정리하거나 lint 설정을 바꾸는 작업을 뜻하지 않는다. 동작을 유지하며 구조를 고치는 작업은 [리팩터링 가이드](behavior-preserving-refactoring.md)를 함께 읽는다.

## 흐름과 함께 읽을 단위를 드러낸다

- **중괄호는 항상 쓴다.** 짧은 guard에도 적용한다. 조기 반환을 추가할 때는 뒤에서 실행하지 않게 되는 일을 확인한다. 조회 오류 뒤 캐시로 선택을 유지하던 코드의 `return`은 표현 정리를 넘어 동작을 바꿀 수 있다.
- **빈 줄은 처리 목적이 바뀌는 곳에 둔다.** 같은 조건을 준비하거나 한 결과를 구성하는 코드는 붙이고, 준비·거절·외부 작업·결과 적용은 필요에 따라 나눈다. 모든 `await`·guard·`return` 앞뒤에 일괄 적용하지 않는다.
- **전체 동작에서 세부 구현으로 읽히게 배치한다.** 공개 동작과 helper 사이를 여러 번 오가야 하면 조정한다. 고정 public/private 순서나 배치를 위한 새 함수·파일 분리는 요구하지 않는다.

들여쓰기·따옴표 등 기계적인 형식은 기존 formatter를 따른다.

## 이름은 실제 책임과 완료 범위를 표현한다

상태나 함수의 이름이 실제 보장보다 큰 뜻을 갖지 않게 한다. 네트워크의 실제 관측과 Debug 표시 상태, 일부 저장 action과 로그인 전체 절차, 조회 갱신 요청과 조회 완료는 서로 다른 책임이다.

- 실제 네트워크를 사용하는지 화면 override가 포함되는지 이름과 소비 API에서 드러낸다.
- 인증 정보를 저장·적용하는 action은 계정 전환의 전체 중단·검사·정리 절차를 완료한 것처럼 이름 붙이지 않는다.
- 캐시 무효화를 요청했으면 화면 데이터 갱신이 끝났다고 표현하지 않는다. 지도 metadata row를 삭제했으면 native 지도 pack까지 삭제했다고 표현하지 않는다.
- 현재 값이 같아도 변경 이유가 다른 상수는 나눌 수 있다. unknown 안내 시간과 refresh 대기 종료 시간은 독립적으로 바뀔 이유가 있다.

helper나 파일은 함께 바뀌는 조건과 책임으로 나눈다. nullable 반환과 예외 발생이라는 형식 차이만으로 같은 상태 판단을 여러 Owner에 흩뜨리지 않는다. 반대로 SQL 조건·DB 사실 확인과 인증 상태 판단은 각각의 변경 이유가 있으므로 구별한다. 이 기준은 특정 class·factory·facade 형식의 금지나 의무가 아니다.

## 주석에는 코드 밖의 이유를 남긴다

| 주석이 하는 일 | 판단 |
| --- | --- |
| 인접 코드를 그대로 읽어 줌 | 줄인다. |
| 코드만으로 알기 어려운 이유·계약·예외 설명 | 남긴다. 예: 인증 거부를 느린 저장보다 먼저 메모리에 적용하는 이유. |
| 역할·처리 구간을 찾는 짧은 설명 | 탐색에 필요하면 둔다. |

긴 장식 구분선은 간소화하되 요약·예시·단계 번호라는 형식만으로 금지하지 않는다. “항상 최신”, “모두 완료”처럼 실제보다 강한 보장도 함께 고친다.

## 오류 처리와 로그의 목적을 따로 판단한다

실패 처리부터 정하고 로그의 필요를 판단한다.

1. 실패를 복구할지, 호출자에게 전파할지, 사용자에게 안내할지 정한다.
2. 그 처리만으로 남지 않는 진단·운영 정보가 필요한지 확인한다.
3. 불필요한 정상 진행 출력·같은 오류의 중복 출력을 줄인다. 남기는 로그는 실제 사건·값·실패 단계·완료 범위를 표현한다.

`catch`가 있거나 오류를 다시 던지지 않는다는 사실만으로 로그가 필수인 것은 아니다. Console 전면 금지나 새 logger 도입도 이 기준에 포함하지 않는다. 중복을 합칠 때 필요한 작업 식별·실패 맥락은 보존한다.

**`catch`의 범위는 분류할 실패에 맞춘다.** 단순 기록·재전파와 복구·분류·후처리를 구별한다. 네트워크 실패만 분류하려는 `catch`가 후속 상태 적용까지 감싸면 적용 오류를 통신 오류로 오인할 수 있다. 사용자 안내에는 토큰·민감한 원문을 노출하지 않는 [오류 처리 기준](../../../.claude/context/error-handling.md)도 적용한다.

## 비동기 표현은 순서와 실패 책임을 따른다

`void`를 붙이거나 제거하는 통일 규칙은 두지 않는다. `void`는 결과를 사용하지 않겠다는 표현이며, Promise의 실패를 처리하거나 작업 완료를 기다려 주지 않는다.

`await`는 뒤 작업의 선행 조건인지를 보고 사용한다. 보기 좋게 순서를 맞추려고 추가하면 동시 실행과 완료 시점이 달라질 수 있다. 기다리지 않는 작업에도 누가 실패를 처리하는지, 호출자의 완료가 어디까지인지는 분명해야 한다. 인증 완료 뒤 캐시 갱신 실패를 인증 저장 실패로 되돌리지 않는 것처럼 서로 다른 완료 경계는 이름·반환·`catch` 범위에서도 유지한다.
