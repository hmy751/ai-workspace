# 로컬 변경의 전송과 데이터 보존

기기에 저장한 변경이 어떤 상태로 남고, 언제 정리할 수 있으며, 저장·전송·정리 완료가 무엇을 뜻하는지 판단할 때 읽는다. 이 본문은 Local 데이터와 queue의 보존 의미를 소유한다. 구현·변경·검증 계약은 [데이터 저장과 동기화 가이드](../guidance/local-data-and-sync.md), 실제 실행과 남은 차이는 [동기화와 정리 현황](../current/sync-and-cleanup.md)에 있다.

## 기기 저장과 서버 반영은 서로 다른 결과다

**활성 여행의 Entity 변경과 `sync_queue` 기록은 같은 SQLite transaction에서 함께 저장한다.** 한쪽이 실패하면 둘 다 rollback한다. Queue 추가는 서버 전송이 아니며, Entity만 저장하고 나중에 보상 삭제하는 방식으로 대체하지 않는다.

| 결과 | 말할 수 있는 것 |
| --- | --- |
| Local 저장 성공 | Entity와 전송할 변경이 기기에 저장됐다. |
| 서버 반영 확인 | 해당 변경이 서버에 적용됐음을 확인했다. |
| 연결·인증 때문에 전송 실패 | 이미 저장한 변경은 기기에 남아야 한다. |

저장 안내와 sync 안내는 이 결과를 구별한다. 기존 queue가 있다는 사실만으로 새 저장 호출의 성공을 입증하지 않는다.

Entity ID는 클라이언트가 만들고 서버가 수용한다. 시간·version·soft-delete 정보도 변경 의미에 맞게 보존한다. Router는 읽고 쓸 출처를, sync는 이미 저장한 변경의 서버 반영을 맡는다. 지도·검색·길찾기는 이 queue에 넣는 사용자 소유 Entity가 아니다.

## 미전송은 서버 반영을 확인하지 못한 변경이다

| Queue 상태 | 의미 | 파괴적 정리 전 보존·손실 확인 |
| --- | --- | --- |
| `PENDING` | 전송 대기 | 포함 |
| `IN_PROGRESS` | 전송 작업 진행 | 포함 |
| `FAILED` | 작업 실패 | 포함 |

실패해도 사용자 입력과 소유권은 남는다. PENDING만 세면 실패하거나 중단된 변경을 놓친다. 또한 미전송은 **서버에 아무 변경도 없다는 뜻이 아니다.** 서버가 처리한 뒤 응답만 잃을 수 있고, 클라이언트 ID 유지 자체는 서버 중복 처리를 보장하지 않는다.

계정 종료는 세 상태를 손실 안내와 보류에 포함한다. 여행 비활성화·지연 cleanup에는 PENDING 중심 판정이 남아 있다. 이는 새 정책을 기다리는 문제가 아니라 채택한 보존 기준의 구현 간격이다. 실제 차이는 [정리 현황](../current/sync-and-cleanup.md)에서 확인한다.

## queue의 계정과 참조 원본도 함께 보존한다

Local 변경은 소유 계정으로만 전송해야 한다. 현재 queue의 귀속은 참조하는 원본 row의 userId와 payload의 계정 정보를 대조해 확인한다. 원본이 없거나 payload를 해석할 수 없어 귀속을 알 수 없다면 다른 계정 데이터라고 단정해 전송하거나 자동 폐기하지 않는다. 로그인·복원에서도 이 불명확성을 보존하며, SQLite 소유자 정보만으로 새 기기 세션을 만들지 않는다.

이 관계 때문에 오래된 soft-delete 일정·경비라도 queue가 원본을 참조하는 동안은 vacuum으로 지우지 않는다. 원본은 사용자 데이터일 뿐 아니라 남은 변경이 누구의 것인지 확인하는 근거다. 원본만 지우고 queue를 남기면 같은 계정으로도 복원·재로그인할 때 귀속을 확인하지 못할 수 있다. 현재 보호는 queue 상태와 관계없이 참조가 있는 원본에 적용하며, 참조가 제거되면 기존 기간 조건으로 물리 삭제할 수 있다.

앞으로 queue에 명시적 소유자 정보를 추가할지는 별도 설계 판단이다. 현재 원본 의존 구조를 유일한 영구 방식으로 고정하지 않는다. 방식을 바꿀 때도 이전 형식의 queue와 원본을 포함해 소유자를 확인할 수 없는 변경을 보존해야 한다.

## HTTP 호출과 저장된 변경의 수명을 구별한다

일반 Remote 요청은 자동 인증 갱신을 기다렸다 재전송할 수 있지만, 갱신을 완료하지 못하면 호출이 오류로 끝난다. 사람의 재로그인까지 HTTP 요청을 보관하지 않는다. 반면 queue는 이미 Local에 저장한 변경의 기록이므로 인증 중단 후에도 남아 이후 새 HTTP 요청을 만들 수 있다. 일반 호출의 종료와 Local 변경 폐기는 같은 사건이 아니다.

인증 갱신 후 원래 요청의 재전송, sync HTTP client의 서버 오류 재시도, Query의 조회 재시도, 다음 sync에서 저장된 실패 작업을 다시 선택하는 것은 서로 다른 책임이다. 한 계층의 횟수나 시간 간격을 전체 재시도 정책으로 쓰지 않는다. 현재 값과 실패 분류는 [API 계약 가이드](../guidance/api-contracts.md)와 [데이터·sync 가이드](../guidance/local-data-and-sync.md)가 설명한다.

재로그인이 성공했다고 모든 FAILED가 무조건 전송되는 것은 아니다. 재시도 한도에 도달한 작업과 남은 IN_PROGRESS를 건너뛰거나 재개할지에는 순서·중복 반영·사용자 복구 행동이 함께 걸린다. 현재 전송 선택과 별개로, 앱 재시작 뒤 IN_PROGRESS의 명시적 복구와 한도 도달 작업의 사용자 회복 방식은 열린 판단이다.

## sync를 실행할 조건과 완료 결과

새 sync는 DB 사용 가능·보호 요청 가능한 인증·실제 online·Debug override 해제·세션 종료 중 아님을 함께 확인한다. 로그인·인증/연결 복구·override 해제로 실행 가능해지면 자동 요청한다. 일반 rerender나 앞 작업 완료 자체로 다시 실행하지 않는다. 실행 중 동시 요청은 추가 실행을 예약하지 않고 보류한다.

Push는 현재 계정의 queue를, pull은 현재 계정의 활성 여행을 대상으로 한다. 활성 여행이 없으면 pull은 생략한다. 응답 검증·충돌·cursor의 실제 보장과 간격은 [동기화 현황](../current/sync-and-cleanup.md)이 소유한다.

| 결과 | 의미와 안내 범위 |
| --- | --- |
| `skipped` | engine을 시작하지 않았다. 성공 시각을 갱신하지 않는다. |
| 실패 | 인증 중단·요청 실패 또는 남은 FAILED/IN_PROGRESS가 있다. 성공으로 안내하지 않는다. |
| 현재 `completed` | 해당 push·pull 경로가 오류 없이 끝났다. 실행 중 새 PENDING이 생길 수 있어 queue가 비었다는 뜻은 아니다. |

활성 여행이 없어 pull을 생략해도 앞선 push 실패를 성공으로 바꾸지 않는다. Cleanup 부분 실패·캐시 재조회·native 지도 정리까지 완료했다고 확대하지 않는다. 부분 성공을 더 세밀하게 전달하는 결과 계약은 후속 구현이 남아 있다.

## 비활성화·삭제·공간 회수의 순서

비활성화는 해당 여행을 Local 이용 대상으로 삼는 상태를 내리는 일이다. 그 순간 데이터를 모두 물리 삭제하는 것과 다르다. 미전송 변경이 있으면 로컬 정리를 지연하고 `cleanupPending`으로 남겨 이후 정리를 다시 시도한다. 사용자 입력 보존을 위해 비활성화를 sync 완료까지 기다리게 하거나 곧바로 hard delete하는 방식 대신 상태 변경과 정리를 나누었다.

soft delete는 `deletedAt`으로 논리적 삭제를 기록하고, vacuum은 정해진 보존 기간이 지난 row를 물리 삭제한다. 기간이 지났다는 사실만으로 미전송·queue 참조 보호를 생략할 수 없다. 현재 여행별 predicate의 간격 때문에 “비활성화·지연 정리의 모든 미전송 데이터가 이미 안전하다”고 설명하지 않는다.

정리를 시도한 여행 수와 실제 정리를 수행한 여행 수도 다르다. 미전송 때문에 건너뛴 작업을 정리 완료로 표시하면 안 된다. DB metadata 정리와 native 지도 pack 삭제는 각각 별도 결과이며, metadata만 삭제한 경로를 기기의 지도 파일까지 회수한 것으로 표현하지 않는다. 현재 집계와 지도 부분 실패의 결과 전달에는 남은 차이가 있다. 지도 공간 회수 자체의 상세 계약은 [오프라인 지도](../../../.claude/context/offline-map.md)에 남으며, 필요한 요구를 단순히 현재 구현에서 역으로 확정하지 않는다.

## 명시적 기기 정리와 원자성의 범위

사용자가 손실을 확인하고 명시적으로 종료·폐기한 경우에는 미전송 변경도 정리할 수 있다. 일반 종료에서 최초 미전송 확인 이후 새 Local 저장을 받아 놓고 삭제하지 않도록, 이미 접수된 저장까지 마친 뒤 최종 미전송 판단을 해야 한다. 진행 중 sync·cleanup 대기와 실패·보류 뒤 해제는 [기기 세션](device-session.md)의 종료 계약을 따른다.

SQLite reset은 DB·queue 삭제와 스키마 재생성을 같은 transaction으로 처리해 재생성 실패 시 기존 데이터를 함께 rollback한다. 이 범위와 서버 로그아웃·SecureStore 삭제까지 한 번에 rollback하는 전체 계정 종료는 다르다. DB를 비운 뒤 인증 기록 삭제가 실패할 수 있으며, 이를 정상 종료나 DB 복원으로 표현하지 않는다. 앱 강제 종료 뒤 journal로 정리를 재개하는 기능도 채택하지 않았다.

DB 저장, 캐시 무효화 요청, 실제 재조회, 화면 이동, 지도 준비는 서로 다른 완료다. 후속 실패가 선행 저장을 취소하는지 여부를 각 작업의 계약에 따라 설명해야 한다. 모든 후속 작업을 무조건 await하거나 모든 오류를 무시하는 규칙으로 바꾸지 않는다.

## 근거와 갱신

2026-09-25에 기존 transaction·정리 기준과 [DB·Promise 의미 확인](../../work/workspaces/002-code-readability-refactoring/records/2026-09-21-01-auth-policy-split-review-and-commits.md), [원본 보존·종료·실패 전달의 보완](../../work/workspaces/002-code-readability-refactoring/records/2026-09-21-04-auth-responsibilities-and-regression-fixes.md)을 통합했다. 단계별 삭제를 선택한 이유는 [기존 비활성화·정리 결정](../../../.claude/decisions/2025-11-20-deactivation-sync-queue-safety.md)에 보존돼 있다. 그 기록의 PENDING 중심 예시와 당시 완료 설명은 현재 모든 경로의 보장으로 사용하지 않는다.

queue 상태·소유자 판별·전송 결과·삭제 범위가 바뀌면 해당 책임자가 이 본문과 데이터·sync 가이드·정리 현황을 함께 갱신한다. 실제 Drizzle SQL을 사용하는 Node SQLite 검사와 기기 SQLite·SecureStore·실제 서버 검증은 구별하며, 현재 증거의 범위는 현황에서 확인한다.
