# 0003. 인증 만료 뒤 로컬 이용을 이어가고 계정 변경은 명시적 종료로 구분한다

- 상태: 채택. 2026-09-18 최초 기기 세션 결정의 자동 계정 전환을 후속 합의로 대체한다.
- 결정 시점: 2026-09-18~21. Project 편입: 2026-09-25.
- 현재 의미: [기기 세션과 로컬 이용](../common/device-session.md), [로컬 데이터 보존](../common/local-data-preservation.md)
- 변경 기준·구현 연결: [인증 가이드](../guidance/authentication-and-session.md), [현재 세션과 데이터](../current/session-and-local-data.md)

## 만료 뒤에도 Local CRUD를 허용하는 이유

서버 인증이 거부된 뒤 읽기만 허용하거나 로컬 전체를 차단하는 안을 검토했다. 여행 중 잠깐 연결돼 만료를 확인했다는 이유로 준비한 여행의 조회·기록이 끊기는 비용이 크다. 읽기 전용으로 바꿔도 타인의 열람이나 미전송 데이터의 계정 귀속·보존·재로그인 문제는 해결되지 않는다. 전체 차단도 이 책임을 없애지는 않는다.

따라서 재인증이 필요해지면 보호된 원격 요청과 새 sync를 막고, **기존 계정의 활성 여행 Local CRUD는 계속한다.** 비활성 여행의 Remote 작업이나 새 여행·새 활성화까지 허용하는 선택은 아니다. 사용자의 “로컬 이용기간은 그냥 제한하지 말자”에 따라 인증 만료 후 별도 유예 기간은 두지 않는다. 기존 여행 활성화·정리 기준까지 없애거나, 일정한 날 여행이 반드시 삭제된다고 가정한 결정은 아니다.

## 저장 사실에서 상태를 구분한다

단순한 로그인 boolean과 만료 flag 조합으로는 토큰 부재, 기록 없음, 저장소 실패의 차이가 가려졌다. 사용자도 “프로그래밍적으로 좀 명확하게 생각하면 좋겟어”라며 무엇을 읽고 실패 뒤 무엇이 남는지 설명하도록 정정했다.

서버 로그인으로 생성한 기기 세션 기록은 계정과 nullable 인증 수단을 함께 보관한다. SQLite에서 발견한 userId만으로 세션을 만들지 않는다. 기록이 없음을 성공적으로 확인한 상태는 `signed-out`, 읽기·해석·귀속 확인에 실패한 상태는 `restore-failed`다. `signed-in`은 요청에 사용할 인증 수단을 복원했다는 의미이며 서버가 방금 유효성을 검증했다는 뜻이 아니다. 인증 수단을 잃어도 유효한 기기 계정은 `reauth-required`에서 유지할 수 있다. 초기 복원의 수명은 [앱 준비 결정](0004-startup-failure-and-retry.md)과 연결된다.

## 같은 계정 복구와 다른 계정 변경

초기에는 다른 계정 로그인 성공 뒤 이전 데이터를 자동 폐기하는 안을 채택했다. 후속 논의에서 재로그인의 책임을 좁혔다. 같은 계정의 서버 인증과 기기 저장이 성공하면 기존 DB·큐를 유지하며 정상 흐름으로 돌아간다. 서버 인증이나 기기 저장이 실패하면 기존 상태와 Local 이용을 유지하고 다시 시도한다. 저장 실패 전용 인증 상태는 추가하지 않는다.

다른 계정 재로그인은 거절하고 기존 데이터를 보존한다. 계정 변경은 사용자가 명시적으로 로그아웃한 뒤 로그인한다. 종료에서 폐기한 미전송 변경은 같은 계정으로 다시 로그인해도 복구되지 않는다. 여러 계정 보관함·데이터 이전 기능은 추가하지 않았다.

복원 실패나 기록 부재인데 데이터가 남은 경우에도 계정 검사는 필요하다. 귀속 불명을 다른 계정이라고 단정해 자동 삭제하지 않는다. 정상 프로필 화면에 못 들어가는 사용자에게는 복원 재시도와 명시적 로컬 정리 진입이 필요하다.

## 인증 완료와 요청의 수명

일반 API와 sync는 첫 401 뒤 공통 자동 갱신을 사용한다. 통신 실패·5xx·기기 저장 실패를 인증 거부로 단정하지 않는다. 재로그인이 필요하면 그 HTTP 호출은 오류로 끝난다. 이후 사람이 로그인할 때까지 과거 요청을 붙잡아 두거나 모두 자동 재전송하지 않는다. 로컬에 이미 저장된 변경의 queue는 별도 수명으로 남는다.

요청 당시 세션이 바뀌면 늦은 응답을 적용하지 않는다. 같은 계정 재로그인도 새 세션이므로 userId 비교만으로 충분하지 않다. 토큰을 공개 Store snapshot에서 분리한 목적은 raw token과 일부 상태 변경만으로 인증 절차를 우회하는 사용을 줄이는 것이다. OS 보안이나 임의 코드 실행 방어까지 강화됐다는 뜻은 아니다. 별도 facade/session-store 시도의 철회는 모든 Store 분리나 facade를 금지하는 일반 규칙으로 확대하지 않는다.

[기존 Axios factory 결정](../../../.claude/decisions/2025-12-23-auth-axios-factory.md)의 인스턴스 분리·순환 참조 회피 이유는 유지한다. sync의 첫 401에서 갱신 없이 만료시키는 과거 설명만 공통 인증 처리로 대체한다.

## 종료를 기다리는 비용과 제외한 기능

진행 중 sync나 cleanup이 DB reset 뒤 다시 쓰는 충돌을 피하려고, 종료 확정 뒤 새 작업을 막고 이미 진행 중인 작업의 성공·실패 종료를 기다린다. 사용자는 이 대기 비용을 수용했다. 강제 종료도 이 조율을 건너뛰지 않는다. 새 timeout이나 일반 작업 취소 체계는 도입하지 않았다. 현재 실행 순서는 [인증 가이드](../guidance/authentication-and-session.md)가 소유한다.

서버 로그아웃 실패에도 로컬 종료를 진행하고, 서버 계정 삭제 실패에는 로컬 세션을 유지하는 기존 차이는 보존한다. 이는 리팩터링에서 유지한 계약이며 최초 제품 선택 이유까지 새로 확인한 것은 아니다. 저장소 일부 정리 실패를 정상 종료 완료로 표현하지 않는다.

원격 기기별 접근 회수는 “다른기기에서 이기기.. 이건 지금 고려할건 아니라고봐”로 제외했다. 종료 도중 앱 강제 종료 뒤 정리를 재개하는 durable journal도 “로그아웃중 앱종료 냅둬”로 제외했다. 정상 실행의 대기·오류 처리까지 없애는 결정은 아니다.
