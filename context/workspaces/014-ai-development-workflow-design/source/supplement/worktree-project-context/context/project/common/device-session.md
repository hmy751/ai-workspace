# 기기 세션과 로컬 이용

앱 시작·인증 실패·재로그인·계정 종료에서 이 기기의 여행을 누구의 데이터로 이용하고 무엇을 보존할지 판단할 때 읽는다. 이 본문은 기기 세션과 계정 복구·종료의 제품 기준을 소유한다. 상태·저장·요청을 변경하는 계약은 [인증과 세션 가이드](../guidance/authentication-and-session.md), 실제 보호가 연결된 범위는 [세션과 로컬 데이터 현황](../current/session-and-local-data.md)에 있다.

## 앱 준비와 계정 복원은 무엇을 확인하는가

앱 진입에는 **DB 준비 성공과 기기 세션 복원 시도의 종료**가 필요하다. 여행이나 활성 여행이 없어도 SQLite 연결·스키마를 준비한다. SecureStore 인증 기록과 여행 DB는 별개이므로 한쪽을 읽었다고 다른 쪽도 준비됐다고 볼 수 없다.

| 준비 결과 | 다음 행동 |
| --- | --- |
| DB 준비 실패 | 화면·데이터 Provider 진입을 막고 실패 안내와 재시도를 제공한다. 재시도는 삭제 없는 재준비다. |
| DB 준비 성공·인증 복원 시도 종료 | 복원 결과에 맞는 화면으로 진입한다. 로그인·네트워크 확정·서버 검증·지도·sync 완료는 기다리지 않는다. |

기기 세션은 서버 로그인으로 만든 계정과 인증 수단의 기록이다. 토큰이 없어져도 어떤 계정의 기록인지 남길 수 있다. **SQLite의 userId만으로 세션을 만들지 않는다.** DB 소유자 검사는 복원·로그인할 계정과 남아 있는 여행·queue의 계정이 같은지 확인하는 역할이다. 준비 순서와 재시도의 실행 수명은 [앱 준비 가이드](../guidance/app-startup.md)가 맡는다.

## 인증 상태는 계정·인증 수단·확인 실패를 구별한다

같은 로그인 화면으로 이어져도, 다시 읽을지·Local을 허용할지·데이터를 보존할지 판단이 다르므로 다섯 상태를 구별한다.

| 상태 | 확인한 사실 | 이용·복구 방향 |
| --- | --- | --- |
| `initializing` | 최초 복원 또는 명시적 복원 재시도 중 | 결과를 기다린다. |
| `signed-out` | 세션 기록 부재를 확인했거나 명시적 삭제에 성공 | 새 로그인. DB가 비었다는 뜻은 아니다. |
| `signed-in` | 계정과 사용할 인증 수단을 복원·저장 | 보호 요청·자동 갱신을 시도할 수 있다. |
| `reauth-required` | Local 계정은 유지되지만 서버 인증 복구가 필요 | 활성 여행 Local 이용과 같은 계정 재로그인. |
| `restore-failed` | 기록 읽기·해석 또는 Local 계정 일치를 확인하지 못함 | 데이터를 보존하고 복원 재시도·명시적 정리를 제공한다. Local 접근은 막는다. |

`signed-in`은 최근 서버 검증 성공이 아니다. access token이 없으면 refresh token으로 갱신할 수 있고, refresh token이 없어도 사용할 access token을 즉시 무효로 보지 않는다. 앱 시작에 온라인 검증을 필수로 추가하지 않는다.

최초 복원은 프로세스 시작과 `restore-failed`의 명시적 재시도에서 수행한다. 진행 중 복원과 완료 결과를 재사용하되 명시적 실패 재시도는 새로 읽는다. 화면 이동·foreground·재렌더·네트워크 변화·refresh·재로그인마다 `initializing`으로 돌아가 여행 작업을 막지 않는다.

## 서버 인증을 잃어도 준비한 여행의 기록을 이어간다

보호된 요청의 첫 401 응답에는 자동 갱신 기회를 준다. 갱신이 필요한 시점에 갱신 수단이 없거나 갱신의 401/403, 갱신 후 재전송의 인증 거부를 확인하면 재인증이 필요하다. 통신 실패·timeout·서버 5xx·기기 저장 실패는 각각 해당 작업의 실패이며, 그것만으로 서버가 인증을 거절했다고 판단하지 않는다.

재인증이 필요하면 보호된 Remote 요청과 새 sync를 멈추고 같은 계정 활성 여행의 조회·생성·수정·삭제를 계속 허용한다. 잠깐 연결돼 토큰 만료를 확인했다는 이유로 여행 중 기록이 끊기는 비용을 피하기 위한 선택이다. 별도 로컬 이용 기한은 두지 않는다. 활성 여행이 없으면 이어갈 Local 여행도 없으며, 비활성 여행 서버 이용이나 새 여행의 오프라인 생성까지 열지는 않는다. 기존 활성화·데이터 정리 조건도 계속 적용한다.

인증 실패를 네트워크 offline으로 바꾸지 않는다. 지도·검색·길찾기는 실제 연결 상태와 각 서비스의 인증 요구를 따르며, 공개 서비스 요청에 보호된 여행 API의 인증 조건을 일괄 적용하지 않는다. 접근·제한 화면의 관계는 [여행 이용](travel-access.md)에서 설명한다.

재로그인이 늦어질수록 변경이 기기에만 남을 수 있으므로 기기 저장과 서버 반영 완료를 구별해 안내해야 한다. 재인증 안내 자체가 각 저장 성공이나 sync 성공을 증명하지는 않는다.

## 재로그인은 같은 계정의 인증을 복구한다

| 재로그인 결과 | 유지·적용할 상태 |
| --- | --- |
| 같은 계정으로 인증하고 기기 저장·세션 적용까지 성공 | 기존 DB·미전송 queue를 유지하고 보호 요청을 다시 허용한다. 나머지 조건도 맞으면 sync를 재개한다. |
| 다른 계정 선택 | 불일치를 알리고 기존 계정·데이터를 보존한다. 계정 변경은 명시적 로그아웃 뒤 진행한다. |
| 취소·서버 인증 실패·기기 저장 실패 | 기존 `reauth-required`와 Local 이용을 유지하고 재시도할 수 있게 한다. |
| 기기 저장·세션 적용 뒤 캐시 갱신 실패 | 이미 완료된 인증 저장을 실패로 되돌려 표현하지 않는다. |

서버 로그인 성공만으로 재로그인이 완료되지는 않는다. 기기 저장 성공이 필요하며, 저장 실패 전용 전역 인증 상태는 두지 않는다. 같은 계정 복구가 DB 교체나 기존 데이터 폐기를 함께 수행하지 않도록 책임을 한정한다.

## 소유자를 확인하지 못한 데이터는 보존한다

기기 세션을 복원하거나 새 로그인 정보를 적용하기 전에 남아 있는 데이터의 계정을 확인한다. 다른 소유자가 있다는 결과와 소유자를 알 수 없다는 결과는 다르다. malformed payload나 원본 row가 없는 queue 때문에 귀속이 불명확하면, 다른 계정 데이터라고 단정해 자동 폐기하지 않는다. 일부 row에서 다른 소유자를 먼저 발견했더라도 불명확한 queue의 존재를 무시하지 않는다.

복원에서는 이 불일치·불명확성을 `restore-failed`로 드러내고 세션 공개를 보류한다. 로그인 저장도 소유 계정을 확인할 수 없으면 기존 데이터를 보존한 채 실패한다. `signed-out`이더라도 SQLite에 잔존 데이터가 있을 수 있으므로, 그 상태 이름만으로 DB가 비었다고 가정하지 않는다.

계정 복원이 실패해 프로필에 들어가지 못하는 사용자도 복원 재시도와 명시적 기기 정리에 접근할 수 있어야 한다. 로그인 화면에서 데이터 손실을 확인한 뒤 정리를 선택할 수 있게 한다. 자동 손상 복구나 계정별 보관함을 만든다는 뜻은 아니다. queue 귀속과 원본 보존의 관계는 [로컬 데이터 보존](local-data-preservation.md)이 소유한다.

## 명시적 종료는 로컬 준비와 미전송 변경을 지운다

**정상 로그아웃은 Local DB·queue·기기 인증·선택·조회 캐시를 비운다.** 서버에 반영된 데이터는 남지만 기기에만 남은 변경과 오프라인 준비는 같은 계정 재로그인으로 복구되지 않는다. 다음 로그인이 실패하면 이전 Local 여행으로 바로 돌아갈 수 없다.

일반 로그아웃·계정 삭제는 `PENDING`·`IN_PROGRESS`·`FAILED`가 있으면 손실을 안내하고 종료를 보류한다. 사용자가 폐기를 명시적으로 확인한 force 종료는 이 보류를 넘는다. force는 앱 프로세스 강제 종료와 다르며, 진행 중 작업을 기다리는 순서는 유지한다.

1. 새 sync·pending cleanup을 막고 이미 실행 중인 작업의 성공·실패 종료를 기다린다.
2. 새 Local transaction을 막고 접수된 저장을 끝낸다.
3. 그 결과까지 포함해 미전송 여부를 판단한 뒤 정리한다. 보류·실패하면 일시 중단을 해제한다.

최초 수량만 보고 삭제하면 대기 중 저장된 변경을 놓칠 수 있어 이 순서를 지킨다. 대기 비용은 수용했으며 별도 취소·timeout은 채택하지 않았다.

| 실패 지점 | 종료의 의미 |
| --- | --- |
| 서버 로그아웃 실패 | Local 종료는 계속한다. |
| 서버 계정 삭제 실패 | Local 세션을 유지한다. |
| SQLite reset 실패 | DB transaction의 삭제를 rollback한다. 전체 종료 완료로 표시하지 않는다. |
| DB를 비운 뒤 기기 인증 삭제 실패 | DB는 이미 비어 있다. 이전 보호 요청을 막고 선택·캐시도 정리한다. 오류를 알리고 종료를 재시도할 수 있게 해야 한다. |

SQLite rollback이 서버·SecureStore를 포함한 전체 종료의 원자성을 뜻하지 않는다. 실패 뒤 실제 재시도 연결은 [세션 현황](../current/session-and-local-data.md)에서 확인한다. 종료 도중 앱이 강제 종료됐을 때 journal로 재개하는 장치는 채택하지 않았다.

## 요청은 시작한 세션에 속한다

계정 소유자와 요청 세션의 동일성은 다른 조건이다. A 계정의 요청이 진행 중일 때 로그아웃하고 B로 로그인하거나, 같은 A로 다시 로그인해도 이전 세션의 늦은 응답은 현재 저장소·인증 상태에 적용하지 않는다. userId가 같다는 이유만으로 이전 토큰이나 응답을 받아들이면 안 된다. 확정된 인증 거부도 느린 저장 완료 때문에 다시 보호 요청을 열어서는 안 된다.

일반 API와 sync는 같은 세션의 자동 갱신을 공유하고, 성공하면 각 원래 요청을 새 토큰으로 한 번 재전송한다. 갱신을 완료하지 못하면 그 호출은 오류로 끝난다. 사람의 재로그인을 기다리며 일반 HTTP 요청을 보관하지 않는다. 로그인 후 필요한 조회는 새 요청이며, 저장된 Local 변경을 queue에서 다시 전송하는 것은 별도 수명이다.

이 기기에서 다른 계정의 데이터가 보이거나 전송되지 않도록 하는 경계는 필요하다. 원격 로그아웃·다른 기기의 접근 회수·계정별 보관함까지 같은 계약에 포함하지 않는다. 일반적인 토큰 무효 응답만으로 계정 삭제나 원격 기기 회수 사실을 추정하지 않는다.
