# 여행 이용과 연결 상태

연결 상태가 바뀔 때 어떤 여행을 계속 이용하고, 선택·입력·조회 결과를 어떻게 보존할지 판단할 때 읽는다. 이 본문은 여행 접근과 제한·복구 경험의 제품 기준을 소유한다. 상태 관측·Policy·화면을 수정하는 방법은 [연결 관측과 화면 접근 가이드](../guidance/network-and-policy.md), 실제 연결 범위는 [네트워크와 화면 접근 현황](../current/network-and-screen-access.md)에 있다.

## 활성화와 선택은 서로 다른 일이다

| 구분 | 정하는 것 | 접근 기준 |
| --- | --- | --- |
| 여행 활성화 | 기기에 준비하고 Local 저장·동기화를 책임질 여행 | 사용자당 하나. 저장된 activation metadata로 판단한다. |
| 여행 선택 | 지금 화면에서 보고 작업할 여행 | 활성 여행과 달라도 된다. 연결 변화만으로 바꾸지 않는다. |

활성 여행은 Local SQLite를 기준으로 읽고 쓰고, 비활성 여행은 Server API를 사용한다. 온라인에서는 비활성 여행도 조회·수정·삭제할 수 있다. 다른 여행이 활성화돼 있다는 이유로 대상 비활성 여행의 작업을 Local로 보내지 않는다.

지도·경로 다운로드 진행이나 현재 선택으로 활성 여부를 대신 판단하지 않는다. 대상별 라우팅과 Trip 목록·생성의 차이는 [데이터 가이드](../guidance/local-data-and-sync.md)가 맡는다. 이 지원 계약과 모든 endpoint의 구현·검증 완료는 구별한다.

## 보던 여행에서 연결을 잃었을 때

| 상황 | 유지할 것 | 사용자에게 제공할 행동 |
| --- | --- | --- |
| 비활성 여행을 보다가 연결을 잃음 | 알고 있는 기본 정보·탭·선택 | 일정·경비 내용에 제한 안내. 준비된 활성 여행으로 돌아갈 행동을 제공한다. |
| 이미 offline인데 새 비활성 여행을 선택함 | 기존 선택 | 연결 후 선택하도록 안내한다. |
| 실제 online에서 끝난 성공한 Remote 목록에 선택한 여행이 없음 | 삭제된 선택을 유지하지 않음 | 다른 기본 여행을 고르고, 남은 여행이 없으면 선택을 해제한다. |

활성 여행이 없으면 이 기기에서 이용할 여행이 없다고 안내한다. 한 번도 서버에서 받지 못한 목록까지 오프라인에서 얻는 보장은 없다. 접근 제한을 빈 목록이나 삭제 완료로 표현하지 않는다.

**Query 캐시 보유는 오프라인 이용 권한이 아니다.** 캐시는 앞서 받은 응답이며, 활성 여행의 SQLite와 준비·보존 책임이 다르다. 캐시를 지워 제한을 만들지 말고 화면이 현재 정책에 따라 내용과 안내를 선택한다. 별도 캐시 복제·관리 체계는 두지 않는다.

선택한 여행의 제거를 판단할 때는 조회가 성공·종료됐는지, 실제 출처가 Remote인지, 실제 online인지를 함께 확인한다. 불완전한 Local 목록·조회 실패·진행 중 결과·남은 캐시로 제거를 판정하지 않는다. 조회 출처도 현재 네트워크나 Debug override에서 추정하지 않는다.

## 연결을 확인하지 못한 상태도 그대로 표현한다

연결은 `online`, `offline`, `unknown`을 구별한다. unknown은 시작과 사용 중 모두 생길 수 있는 **미확정 상태**다. 임시 online이나 offline으로 치환하지 않는다. 관측 신호의 조합은 [Network 가이드](../guidance/network-and-policy.md)가 소유한다.

- **앱·Local 이용:** unknown이어도 앱 전체 준비 화면을 연장하지 않고 준비된 활성 여행은 계속 이용한다.
- **Remote·온라인 서비스·새 sync:** 실제 online을 확인한 뒤 실행한다. Policy가 offline 권한 모드를 재사용해도 관측과 안내 이유는 unknown으로 유지한다.
- **확인 중 안내:** 10초 동안 확정되지 않으면 확인 불가와 재확인 행동으로 바꾼다. offline 판정 시간이나 HTTP timeout이 아니다. 같은 미확정 관측의 반복으로 시간을 계속 초기화하지 않는다.
- **재확인:** 새 관측을 요청한다. 클릭만으로 확정된 online/offline을 unknown으로 바꾸지 않는다. refresh 반환 뒤에도 확정 관측이 도착할 수 있다. 늦은 결과의 적용 순서는 Network 가이드에서 다룬다.

online은 인터넷 연결·도달성의 관측이며 Noline 서버의 정상 응답을 보장하지 않는다. 요청 timeout·서버 오류·인증 실패는 각각의 실패로 처리하고 전역 offline 판정으로 바꾸지 않는다.

## 제한 중 작성한 입력과 기존 정보를 보존한다

오프라인 활성 여행은 제목·날짜·금액 같은 핵심 입력을 계속 저장한다. 외부 검색·정보 보강을 못 쓰면 수동 입력을 제공하되 같은 Entity 저장 경로를 사용한다. 비활성 여행의 오프라인 편집과 오프라인 여행 생성은 지원하지 않는다.

| 제한이 생긴 편집 | 보존할 결과 |
| --- | --- |
| 일정에서 새 장소를 검색·선택하지 못함 | 기존 장소·주소·좌표를 유지한다. |
| 경비에서 새 일정을 연결하지 못함 | 기존 `scheduleId`와 연결 표시를 유지한다. |
| 비활성 여행의 저장이 연결·인증 조건에 막힘 | 열린 폼과 입력을 유지하고 제한 이유를 알린다. 사용자가 다시 저장한다. |

신규 입력의 null/default를 기존 데이터 수정에 그대로 적용하지 않는다. **경비 날짜 변경으로 기존 일정 연결이 유효하지 않게 될 때의 유지·해제·재선택 UX는 미정**이다.

입력 보존은 열려 있는 편집의 수명에 대한 계약이다. 별도 draft, 앱 종료 뒤 복구, 쓰기 예약·복구 뒤 자동 저장은 포함하지 않는다.

Router는 전송 전 실행 조건과 거절 이유를 확인하고 화면은 이를 안내한다. 이미 전송한 요청은 일반 성공·실패 흐름을 따른다. 연결 변화만으로 취소·자동 재전송·별도 결과 대조를 시작하지 않는다. 서버 반영 뒤 응답만 잃을 가능성은 남으며, 클라이언트 ID 유지 자체가 서버 중복 처리를 보장하지는 않는다.

## 복구는 현재 여행의 조회 성공까지 확인한다

같은 비활성 여행을 계속 보고 있을 때 online으로 복구되면 다시 조회하고, 조회가 성공한 뒤 내용을 복구한다. 사용자가 이미 다른 여행으로 이동했다면 원래 여행으로 돌려보내지 않는다. 실패는 일반 조회 오류로 안내한다.

같은 장애의 복구 성공 안내는 한 번이면 충분하다. 초기 unknown이 해소된 경우나 재확인 요청이 끝난 것만으로 장애 복구 토스트를 표시하지 않는다. 연결 신호의 복구와 실제 여행 조회 성공을 구별해야 한다.

복구 재조회·한 번의 성공 안내·foreground 재확인·unknown 안내 끝단은 합의된 경험이다. 각 화면의 연결은 [현재 지원 범위](../current/network-and-screen-access.md)와 대조해야 하며, 관측 Store나 일부 제한 화면이 구현됐다는 이유로 전부 지원된 것으로 간주하지 않는다.

## 화면 판단과 실제 실행 조건을 연결한다

Policy는 Schedule·Expense의 생성·조회·수정·삭제와 지도·검색 같은 Service의 허용 여부·모드·이유를 표현한다. Router는 Entity를 어디서 읽고 쓸지 정하고 실행 순간의 조건을 확인한다. UI는 제한과 대안을 사용자 경험으로 옮기며 Service는 실제 외부 호출을 수행한다. 폼 검증이나 동기화 실행을 Policy 표에 선언했다는 사실만으로 보장할 수는 없다.

인증 만료는 offline으로 표현하지 않는다. 같은 계정 활성 여행의 Local 이용과 보호된 Remote 요청은 [기기 세션 기준](device-session.md)을 따르고, 지도·검색·길찾기는 해당 서비스의 실제 연결·인증 요구를 따른다. 공개 요청과 보호 요청은 서버가 실제 요구하는 조건에 맞춰야 한다.

Debug override는 화면과 제한 안내를 실험하기 위한 강제 상태다. 실제 요청 가능 여부는 실제 네트워크 관측을 사용한다. override 중에는 Trip·Schedule·Expense mutation, Local 변경과 queue 추가, 새 sync 전송을 막는다. Local queue도 이후 서버 쓰기로 이어지기 때문이다. 해제 뒤 실제 조건에 따른 정상 동작으로 돌아가며, 이미 전송된 요청의 원복을 보장하지 않는다. 개발 메뉴 표시 조건만으로 데이터 환경 격리를 입증하지 않는다. 실제 쓰기를 포함하는 실험은 환경 격리를 확인한 뒤 별도로 재검토한다.
