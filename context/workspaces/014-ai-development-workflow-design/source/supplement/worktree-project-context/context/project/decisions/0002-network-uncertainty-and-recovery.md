## 연결 관측과 서버 요청을 구별한 이유

Noline은 준비한 활성 여행의 기록을 연결 없이 이어가는 앱이다. 네트워크 신호가 미확정이라는 이유로 앱 전체 진입이나 Local 이용을 막지 않는다. 반대로 인터넷 신호만으로 Noline 서버의 응답 성공을 보장할 수도 없다.

연결 관측은 `online/offline/unknown`으로 표현한다. NetInfo의 연결·인터넷 도달 가능성 신호 중 명시적 false가 있으면 offline, 둘 다 true이면 online, 나머지는 unknown이다. 최초 실행뿐 아니라 사용 중 미확정 관측도 보존한다. 당시 라이브러리 소스와 대역 검사에서는 정상 online의 주기 검사 중 기존 true가 유지됐고, 일부 복구 과정에서 null을 거쳤다. 이는 실제 기기의 변동 빈도나 오판율을 측정한 결과는 아니다.

별도 weak/degraded 상태나 선제 debounce는 추가하지 않았다. 우선 관측과 개별 요청 오류를 처리하고, 자동 여행 전환·중복 sync·반복 토스트·불필요한 화면 재생성을 막기로 했다. **실기기에서 반복 부작용이 관찰되면** 전환 지연이나 NetInfo 설정을 다시 검토한다.

## 10초 안내와 재확인

사용자는 unknown 안내 시간에 “그래 10초 하자”라고 결정했다. 10초 뒤에는 확인 불가와 재확인 행동을 안내한다. offline으로 판정하거나 HTTP 요청을 종료하는 시간이 아니다. 같은 null 관측으로 안내 시간을 계속 초기화하지 않는다.

재확인은 기존 listener를 유지한 채 관측을 갱신한다. 버튼 클릭만으로 확정 상태를 unknown으로 되돌리지 않는다. refresh 반환이 후속 인터넷 probe 완료까지 보장하지 않으므로, 앱의 대기를 마친 뒤에도 늦은 확정 관측은 받아야 한다. Foreground 재확인을 unknown에만 제한하는 안은 채택하지 않았다. 이전 확정값도 오래됐을 수 있기 때문이다.

## 여행이 없어졌다는 인상을 만들지 않는다

연결이 끊겨 탭이 닫히거나 선택이 바뀌면 사용자는 여행 데이터가 사라졌다고 이해할 수 있다. 보던 비활성 여행의 기본 정보·탭·선택을 유지하고 일정·경비 내용에 제한을 표시한다. 이미 offline일 때 새 비활성 여행을 선택하려는 행동은 기존 선택을 유지하며 안내한다. 준비한 활성 여행으로 돌아갈지는 사용자가 고른다.

Query 캐시 삭제·별도 캐시 관리도 검토했지만 사용자는 “복잡도가 너무 높아질것 같아 … 그냥 자연스레 제한을보여주는걸로 하자”라고 선택했다. 캐시는 남겨 두고 화면 정책이 접근을 결정한다. 캐시가 있다는 사실은 오프라인 이용 권한이 아니다.

복구 때 같은 비활성 여행을 계속 보고 있는 경우만 재조회하고, 성공 뒤 한 번 알린다. 사용자가 다른 여행으로 이동했으면 되돌리지 않는다. 초기 unknown 해소나 단순 재확인 완료는 장애 복구 알림 대상이 아니다. 성공한 실제 Remote 목록에서 여행 제거가 확인되어 선택을 바꾸는 별도 규칙은 [여행 이용](../common/travel-access.md)에 있다.

## 쓰기 거절과 입력 보존

사용자의 “버튼 말고 라우터에서 일괄 처리하게 할수는 없을까?”라는 제안에 따라 Router가 실행 순간의 Remote 가능 여부를 검사하고 오류로 이유를 전달한다. 화면은 기존 오류 흐름에서 안내하며 폼을 닫거나 초기화하지 않는다. 연결 복구 후 사용자가 다시 저장한다. 버튼별 조건 복제, Router 내부 Alert·toast, 자동 draft·지연 실행 관리자는 이 선택에 포함하지 않았다.

이미 전송한 Remote 요청의 응답 유실은 일반 요청 실패 범위로 다룬다. 사용자는 이를 “일반 앱 동작과 같은 상황”으로 정정했다. 네트워크 변화만으로 취소·자동 재전송하거나 별도 결과 대조 시스템을 필수로 만들지 않는다. 서버 반영 여부를 모를 가능성은 남으며 client ID만으로 서버 중복 처리가 보장되지는 않는다.

## Debug 표시와 쓰기의 구별

사용자는 “화면만 일단 debug로 덮을까? 쓰기는 안되고 추후 분리 설정 확인하고 하게”라고 선택했다. 화면 override는 실제 연결 관측과 구별한다. Local 변경과 queue도 나중에 서버에 반영되므로 override 동안 쓰기와 새 sync를 막는다. 이미 전송한 작업의 원복은 보장하지 않는다. 실제 쓰기를 포함하는 실험은 실행 환경과 데이터 격리를 확인한 뒤 재검토한다.

## 근거와 후속 관계

선택의 원문 발췌·라이브러리 조사 범위는 [네트워크 정책 합의 기록](../../work/workspaces/002-code-readability-refactoring/records/2026-09-16-01-network-policy-and-implementation-boundaries.md)에 있다. 당시 library 버전·검사 설정은 그 기록의 시점 근거이며 영구 정책값이 아니다. 9/17 소비 확대 시도는 철회되었으므로 당시 검사 통과를 현재 구현의 증거로 쓰지 않는다. 현재 연결과 남은 구현은 [현황](../current/network-and-screen-access.md)에서 확인한다.
