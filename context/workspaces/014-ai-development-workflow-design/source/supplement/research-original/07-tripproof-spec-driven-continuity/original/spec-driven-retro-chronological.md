# TripProof spec-driven 회고: 작업의 연속성과 판단의 연속성

> 현재까지의 논의를 문제 체감에서 원인, 방향, 지속 컨텍스트 설계 질문으로 이어지는 순서로 정리한 작업 문서다. 해결책을 확정한 문서는 아니다. 같은 내용을 관점별로 배치한 버전은 `spec-driven-retro-conceptual.md`에 있다.

## 1. 실제로 불편했던 것은 무엇이었나

> 근본 문제는 아직 안 풀렸는데, 그 주변을 설명하고 측정하고 부분적으로 보완한 코드와 spec만 계속 늘어났다.

구현량과 테스트 수는 늘었지만, 두 가지 믿음은 생기지 않았다.

- 이 제품이 이제 정말 사용자의 문제를 해결한다는 믿음
- 이 코드베이스를 앞으로도 계속 키워나갈 수 있다는 믿음

당시 느꼈던 “프로덕션 수준이 아닌 것 같다”는 감각은 배포 준비나 운영 환경이 부족하다는 뜻이 아니었다. 더 정확히는 다음에 가까웠다.

> 기능은 늘어나는데, 코드베이스가 다음 기능을 더 잘 받아들일 수 있는 구조로 성숙하고 있다는 확신이 없다.

작은 완료를 많이 만드는 것만으로는 충분하지 않았다.

> 작은 완료를 많이 만든 것이 아니라, 모든 작은 완료가 하나의 실제 제품과 유지 가능한 코드로 수렴하게 했어야 했다.

하지만 실제로는 새로운 문제가 나타날 때마다 “현재 모델이 잘못된 것은 아닐까?”를 다시 묻기보다, 기존 구조에 조건·계층·연결 코드를 더해 해당 문제를 해결했다. 하나하나의 구현은 틀리지 않았을 수 있지만, 전체적으로는 문제를 해결해 붙여 나가는 느낌이 쌓였다.

## 2. 어떻게 이런 상태가 되었나

두 가지 믿음이 생기지 않은 이유는 완료를 개별 동작의 통과로 판단했을 뿐, 각 변경이 제품과 코드 구조에 남기는 누적 효과까지 충분히 판단하지 않았기 때문이다.

성공을 측정하는 기준은 주로 다음 질문에 집중돼 있었다.

> 명시된 동작이 구현됐는가?

반면 다음 질문들은 상대적으로 판단되지 않았다.

- 같은 제품 개념이 여러 곳으로 흩어지지는 않았는가
- 새 기능 때문에 기존 구조가 더 복잡해지지는 않았는가
- 다음 변경도 또 예외를 붙여야 하는가
- 현재 코드는 제품의 핵심 개념을 분명하게 표현하는가
- 이제는 기존 설계를 다시 열어야 할 시점이 아닌가

spec-driven 방식은 작업을 이어가는 데 강했다. 해야 할 일과 AC, 구현 순서를 남겼고, 다음 작업이 어디에서 시작되어야 하는지를 분명하게 했다.

그러나 spec을 수정하거나 폐기해야 하는 판단, 전체 제품을 다시 보는 판단, 코드 구조의 질적 성장을 자동으로 이어주지는 못했다. 오히려 spec이 많이 쌓일수록 그 내용과 기존 구조는 이미 확정된 현실처럼 작용했다.

따라서 문제는 spec의 존재 자체가 아니라, 이전 판단을 다시 열 장치 없이 spec이 다음 작업의 전제로 계속 승계된 데 있었다.

여기에는 완료 신호의 비대칭도 있었다. 기능 spec과 AC는 무엇을 끝내야 하는지 명시적이었고, 구현 여부와 테스트 통과를 바로 확인할 수 있었다. 반면 제품이 하나의 문제 해결로 수렴하고 있는지, 코드베이스가 다음 기능을 더 잘 받아들이는 구조로 성숙하고 있는지는 전체를 비교해야 했고 판단 결과도 늦게 드러났다.

작업이 길어질수록 이 차이는 커졌다. 지금 닫을 수 있는 항목은 분명하지만, 이미 구현한 전제를 다시 열거나 구조를 교체하는 행동은 진척으로 잘 계산되지 않았다. 그 결과 전체적으로 더 중요한 판단보다 측정하기 쉬운 국소 완료가 작업을 지배하기 쉬웠다.

> 기능 완료는 명시적이고 즉시 검증할 수 있었지만, 제품의 수렴과 코드 구조의 성숙은 모호하고 늦게 드러났다. 그래서 긴 작업일수록 전체적으로 더 중요한 것보다, 지금 닫을 수 있는 다음 항목이 작업을 지배했다.

> 국소 완료는 계속 보상됐지만, 기존 판단을 폐기하거나 이미 구현한 구조를 다시 여는 행동은 진척으로 잘 계산되지 않았다.

그렇다고 모든 원인이 spec-driven에 있었던 것은 아니다. 당시 모델의 한계, 빠른 작업 속도, 제품 자체의 복잡성, 설계 경험을 쌓아가던 과정도 함께 작용했을 것이다. 다만 작업 방식 차원에서 가장 선명한 문제는 다음 문장으로 정리된다.

> 스펙은 작업의 연속성은 보존했지만, 판단의 연속성은 보존하지 못했다.

여기서 판단의 연속성은 이전 결론을 계속 따르는 것을 뜻하지 않는다. 오히려 이전 결론도 다시 열 수 있도록 판단의 맥락을 이어가는 것이다.

> 판단의 연속성은 이전 결론을 보존하는 것이 아니다. 왜 그런 결론을 내렸는지, 무엇이 불확실했는지, 어떤 신호가 나타나면 다시 열어야 하는지를 다음 작업까지 이어가는 것이다.

따라서 지속되어야 하는 것은 결론만이 아니다. 결론의 근거, 당시 열려 있던 의문, 판단이 더 이상 유효하지 않게 되는 조건, 필요하면 기존 결론과 산출물을 교체할 수 있는 권한도 함께 이어져야 한다.

이 문제는 “spec을 더 잘 쓰면 된다”만으로 해결되지 않는다. 여러 spec이 쌓인 뒤에는 다음 spec을 여는 것보다 먼저, 지금 구조를 앞으로도 계속 전제로 삼아도 되는지 다시 판단하는 순간이 필요하다.

## 3. 무엇을 완료로 봐야 하나

완료의 기준은 두 가지여야 한다.

- 요구한 동작이 실제로 되었는가
- 그 동작을 받아들인 뒤 코드베이스가 더 잘 설명되고 계속 키우기 쉬워졌는가

여기서 코드 품질은 막연한 ‘깔끔한 코드’를 뜻하지 않는다. 계속 키울 수 있는 수준은 좀 더 구체적으로 다음과 같다.

- 하나의 제품 개념이 코드에서 한 군데의 분명한 주인을 가진다.
- 새 경우가 생겨도 여러 층에 조건문과 예외가 퍼지지 않는다.
- 변경할 위치와 영향 범위를 예측할 수 있다.
- 과거 가정이 틀리면 그 위에 덧대지 않고 교체할 수 있다.
- 기능이 늘수록 제품 구조가 더 잘 드러나지, 더 가려지지 않는다.

이를 판단하려면 두 가지 비교가 함께 필요하다.

첫째, 제품 원자료와 실제 동작을 비교해야 한다.

- 제품의 의도가 결과에 살아 있는가
- 사용자 흐름이 실제로 이어지는가
- 각 기능이 부분들의 집합이 아니라 하나의 제품으로 느껴지는가

둘째, 변경 전 코드와 변경 후 코드를 비교해야 한다.

- 기능은 생겼지만 제품 개념이 여러 곳으로 흩어지지는 않았는가
- 의존성·예외·중복이 증가하지 않았는가
- 다음 비슷한 변경이 더 명확한 위치에서 이루어질 수 있는가

따라서 앞으로의 질문도 달라져야 한다.

- “이 요구를 어디에 추가하지?”보다 **“이 요구가 자꾸 생긴다면 현재 모델에서 무엇을 잘못 잡은 걸까?”**
- “남은 AC가 무엇이지?”보다 **“지금 만들고 있는 제품 전체가 무엇을 향해 수렴하고 있지?”**
- “구현됐나?”보다 **“다음 비슷한 변경이 왔을 때 고칠 자리가 더 명확해졌나?”**
- “기존 구조를 최대한 유지하자”보다 **“기존 구조가 틀렸다면 지금 다시 열어도 되는가?”**
- “스펙을 계속 보존하자”보다 **“오래 남겨야 할 판단과 수명이 끝난 작업 지시를 구분하자”**

## 4. spec의 역할은 어떻게 달라져야 하나

큰 방향은 spec을 작업의 지휘자로 두는 방식에서 벗어나, 제품과 코드 구조를 계속 판단 대상으로 두고 spec은 그때의 실행 도구로만 사용하는 것이다.

spec은 권위 있는 누적 기록이 아니라 수정되거나 폐기될 수 있는 실행 도구여야 한다. 그렇다고 제품의 결과나 의미까지 불분명하게 두자는 뜻은 아니다.

미리 분명히 해도 되는 것은 다음과 같다.

- 사용자가 무엇을 할 수 있어야 하는가
- 제품에서 어떤 의미가 보존되어야 하는가
- 이번 작업의 범위와 하지 않을 것
- 실제로 확인해야 할 대표 사용 흐름

반면 실제 코드와 구현 과정에서 판단할 수 있도록 열어두는 편이 좋은 것은 다음과 같다.

- 어느 class나 module에 넣을지
- 내부 데이터 구조를 어떻게 바꿀지
- 기존 추상화를 유지할지 교체할지
- task를 어떤 순서와 크기로 나눌지
- 기존 코드 중 무엇을 제거하거나 합칠지

> 이것은 spec을 불완전하게 쓰자는 뜻이 아니다. 제품에서 필요한 결과는 분명히 하되, 실제 코드를 보고 판단해야 하는 것까지 미리 확정하지 말자는 뜻이다.

그래야 구현 중에 “이 기능을 추가하는 것보다 기존 모델을 고치는 게 맞다”는 판단이 가능해진다.

매 작업에서 변경이 제품과 구조에 미치는 영향은 살펴보되, 매번 거대한 아키텍처 리뷰를 열 필요는 없다. 깊은 재검토는 구조가 저항하는 구체적인 신호가 나타났을 때 발동하면 된다.

## 5. 언제 기존 spec이나 구조를 다시 의심해야 하나

“가끔 전체를 다시 보자”는 약속만으로는 실제 재판단이 일어나기 어렵다. 구조가 저항하고 있다는 관찰 가능한 신호가 필요하다.

- 같은 제품 규칙을 여러 위치에서 다시 표현해야 한다.
- 간단해 보인 변경이 예상 밖으로 많은 module이나 layer를 건드린다.
- 기존 구조에 맞추기 위해 flag나 예외 조건을 하나 더 만들어야 한다.
- 이 동작을 책임져야 할 분명한 위치가 없다.
- 기능을 추가하기 전에 관련 없는 코드를 먼저 정리해야 한다.
- 기능은 통과했지만 전체 흐름이 파편적으로 느껴진다고 평가된다.
- 새 spec이 상위 제품 목적이나 기존 도메인 의미와 충돌한다.

이런 신호가 나오면 곧바로 다음 AC로 진행하거나 무조건 리팩터링을 시작하는 것이 아니라, 다음 중 무엇이 필요한지 다시 판단해야 한다.

- 기능의 형태나 범위를 바꾼다.
- 기존 코드 구조를 먼저 다시 만든다.
- 상위 제품 판단이 바뀌었으므로 지속 컨텍스트를 수정한다.

핵심은 다음과 같다.

> 구조가 저항하는 신호가 생겼을 때 feature 완료보다 재판단을 우선한다.

## 6. 판단의 연속성을 위해 무엇을 지속해야 하나

spec의 권위를 낮추는 것만으로 판단의 연속성이 생기지는 않는다. 오래 남겨야 할 판단에는 별도의 저장 위치와 수명, 읽히는 조건이 필요하다.

기존 spec에서 계속 유효한 내용을 상위 컨텍스트로 올리는 방향은 필요하다. 다만 spec 문장을 그대로 승격하면 일시적인 설계 결정까지 영구 규칙이 될 수 있다.

판단할 때는 다음 질문이 필요하다.

> 이 내용은 앞으로 어떤 기능을 만들더라도 지켜야 하는 제품의 진실인가, 여러 작업에서 반복해서 필요한 기술적 판단인가, 아니면 당시 기능을 구현하기 위해 선택한 방법인가?

지속할 정보에는 제품 정보만 있는 것이 아니다.

- 제품의 목적과 핵심 도메인 개념
- 반드시 지켜야 하는 제품 의미와 품질 기준
- 백엔드와 프런트엔드의 책임 구조
- 테스트와 설계에 관한 기술적 판단 기준
- 무엇을 좋은 결과로 보는지에 관한 평가 감각
- 작업 종류별로 어떤 자료와 검토가 필요한지에 관한 workflow
- 현재 구조의 위험과 아직 열려 있는 판단

다만 이 정보들을 모두 같은 방식으로 다루면 안 된다. 보존 기간, 이번 작업에서 읽히는 조건, 현재 갖는 권위는 서로 다른 문제다.

### 보존 기간

오래 유지할 정보:

- 제품의 목적과 핵심 도메인 의미
- 반드시 지켜야 하는 제약
- 제품 품질에 관한 판단
- 여러 작업에서 반복해서 필요한 기술적 판단 기준

현재 상태로 유지할 정보:

- 현재 코드 구조와 책임 경계
- 알려진 구조적 문제와 위험
- 아직 해결하지 못한 질문
- 최근 선택한 설계 방향
- 임시 호환 계층과 아직 제거하지 못한 기술 부채

이 정보는 과거 상태를 계속 쌓기보다 현재 상태로 교체되어야 한다.

작업이 끝나면 지속적인 역할이 끝나는 정보:

- 기능 spec과 AC
- 구현 plan과 세부 task
- 조사 메모
- 이번 작업의 구체적인 테스트 케이스

이 자료들을 반드시 삭제해야 한다는 뜻은 아니다. 다만 다음 작업을 지휘하는 지속 컨텍스트와 실행 권한은 잃어야 한다.

### 읽히는 조건

장기적으로 보존할 정보와 매 작업마다 자동으로 넣을 정보는 같지 않다.

항상 짧게 읽힐 수 있는 것은 제품 목적, 핵심 도메인 의미, 중요한 기술적 제약, 필요한 자료의 위치 정도다.

반면 다음 내용은 관련 작업에서만 읽히면 된다.

- 메타모픽 테스트 방법
- API 설계 가이드
- 데이터 마이그레이션 원칙
- UI 검증 방법
- 특정 종류의 품질 평가 기준
- 관련 작업 workflow

예를 들어 메타모픽 테스트 원칙은 여러 spec을 넘어 보존할 수 있지만, 판정 로직이나 입력 조합이 복잡한 작업에서만 불러오면 된다.

### 현재 갖는 권위

지속된 정보라고 해서 모두 영구 규칙은 아니다.

- 제품과 도메인의 불변 조건일 수 있다.
- 특정 상황에 적용하는 기술적 판단 기준일 수 있다.
- 언제든 갱신할 수 있는 현재 구조 설명일 수 있다.
- 한 작업에서만 유효한 실행 지시일 수 있다.

따라서 모든 정보에는 다음 세 가지를 물어야 한다.

- 다음 작업까지 보존해야 하는가
- 어떤 종류의 작업에서 읽어야 하는가
- 확정된 원칙인가, 현재 상태인가, 수정 가능한 판단 방법인가

## 7. 새 세션은 무엇을 알아야 하나

새로운 세션에 지속 정보를 전부 넣으면 컨텍스트는 다시 비대해진다. 목표는 모든 것을 처음부터 아는 세션을 만드는 것이 아니다.

> 새로운 세션이 모든 것을 처음부터 아는 것이 아니라, 현재 작업에 필요한 지식을 어디서 찾아야 하는지 아는 상태를 만든다.

그러므로 필요한 것은 거대한 공통 문서 하나가 아니다.

- 짧은 프로젝트 진입점
- 책임이 분리된 몇 개의 지속 컨텍스트
- 작업에 따라 필요한 자료를 선택해 읽는 routing
- 실제 코드와 결과물을 그때 직접 확인하는 방법

평가 감각도 별도의 지속 대상이 될 수 있다. 외부 평가 주체가 제품 원자료와 실제 결과, 변경 전후 코드를 비교할 때 관련 평가 기준과 판단 사례를 불러오게 할 수 있다.

다만 기능 완성 외의 전체 품질을 정확히 누가 판단할지, 언제 평가를 발동할지, 평가자가 작업 진행을 멈출 권한을 어디까지 가질지는 아직 정해지지 않았다.

> 지속되어야 할 지식은 늘어날 수 있지만, 매 세션의 컨텍스트와 영구적인 권위까지 함께 늘어나서는 안 된다.

## 8. 이 장치가 다시 문서와 절차를 쌓지 않게 하려면

각 문서와 규칙에는 수명이 있어야 한다.

- 상위 제품 컨텍스트는 한곳에서 현재 내용으로 갱신한다.
- 현재 구조와 위험도 한곳에서 교체한다.
- feature spec과 plan은 작업 완료 후 지속 컨텍스트로 사용하지 않는다.
- 작업에서 발견한 내용 중 장기적으로 의미 있는 판단만 추려 올린다.
- 특정 실패 때문에 추가한 절차는 그 실패가 더 이상 재현되지 않으면 제거할 수 있어야 한다.

작업 하나가 끝날 때마다 문서가 하나씩 더 남는 구조가 아니라 다음과 같은 흐름이어야 한다.

> 임시 spec으로 작업한다 → 장기적으로 의미 있는 판단만 추린다 → 지속 컨텍스트를 갱신한다 → 임시 spec은 실행 권한을 잃는다.

기술 개발 정보를 지속할 때도 마찬가지다. 여러 기능에서 반복해서 필요하고, 지키지 않았을 때 코드베이스 전체의 품질이 나빠지며, 적용되는 상황과 적용되지 않는 상황을 설명할 수 있어야 한다. 단순한 도구 취향이 아니라 실제로 피하려는 실패가 있어야 하고, 미래의 모델이나 구조가 달라지면 수정하거나 제거할 수도 있어야 한다.

> 제품의 의미와 함께, 여러 작업에서 반복해서 필요한 기술적 판단 기준도 남겨야 한다. 다만 구체적인 해결책보다 판단 기준을 남기고, 세부 내용은 관련 작업에서만 불러온다.

## 9. 이 회고의 근거와 현재 지위

이 문서는 당시의 체감만을 뒤늦게 해석한 메모가 아니다. 남아 있는 원자료와 기존 분석을 비교하고, 당시 작업을 직접 수행한 사용자와의 대화를 통해 문제의 양상과 원인을 더 명확히 한 회고 분석이다. 따라서 아래 중심 진단은 현재 TripProof 개발 경험을 설명하는 근거 기반 결론으로 사용한다.

원자료와 회고 대화에서 함께 확인된 문제:

- 구현량과 spec, 테스트는 계속 늘었다.
- 개별 기능은 구현됐지만 제품 전체에 대한 만족감은 충분하지 않았다.
- 코드베이스를 계속 키워도 되는지에 대한 우려가 있었다.
- 구현들이 근본 모델을 다듬기보다 문제를 하나씩 해결해 붙이는 것처럼 느껴졌다.

원자료 비교와 회고 대화를 통해 구체화된 중심 진단:

- 명시적이고 측정하기 쉬운 국소 완료가 제품과 구조에 대한 전체 판단보다 우선됐다.
- 이전 spec과 코드 구조가 재검토 대상보다 다음 작업의 전제로 승계됐다.
- 작업의 연속성에 비해 판단의 근거와 재검토 조건은 충분히 지속되지 않았다.

주장 단위의 추적성을 더 촘촘히 남길 수 있는 것:

- 실제 spec들이 이전 판단과 구조를 어떤 방식으로 전제했는가
- 조건, 예외, 책임 분산이 코드 변화에서 실제로 어떻게 누적됐는가
- 제품 원자료와 구현 결과 사이에서 어떤 간극이 반복됐는가
- 전체 판단을 다시 열려 했거나 열지 못했던 구체적인 작업 장면은 무엇이었는가

> 남은 일은 중심 진단의 타당성을 처음부터 다시 검증하는 것이 아니라, 특정 구현 시점과 인과를 서술할 때 제시할 세부 근거 연결을 보강하는 것이다. 이 분석에서 도출한 해결 장치의 효과는 실제 적용 결과로 별도 검증해야 한다.

## 10. 현재까지 남은 설계 질문

처음의 다섯 질문은 지속과 실제 주입을 구분하면서 여섯 질문으로 다듬어졌다.

- 무엇을 여러 작업과 세션에 걸쳐 보존할 것인가
- 보존된 것 중 무엇을 이번 작업에 읽힐 것인가
- 무엇을 미리 결정하지 않고 구현 중의 판단으로 열어둘 것인가
- 기존 spec이나 구조를 언제 다시 의심할 것인가
- 기능 완성 외에 제품 전체와 코드 구조의 품질을 누가 어떻게 판단할 것인가
- 이 판단 장치 자체가 다시 문서와 절차를 누적시키지 않게 하려면 어떻게 해야 하는가

핵심은 spec을 없애는 것이 아니다. spec이 작업을 이어주는 장점은 살리되, 그것이 제품과 코드 구조를 다시 판단할 권한까지 대신하지 않게 하는 것이다.

> 작업의 연속성 위에 판단의 연속성이 함께 남아야 한다.
