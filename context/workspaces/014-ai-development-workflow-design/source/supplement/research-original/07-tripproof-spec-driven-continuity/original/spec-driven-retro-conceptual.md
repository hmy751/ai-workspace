# TripProof spec-driven 회고: 관점별 정리

> 현재까지의 논의를 시간 흐름이 아니라 하나의 중심 문제를 둘러싼 제품, 코드, spec, 평가, 컨텍스트 관점으로 배치한 작업 문서다. 해결책을 확정한 문서는 아니다. 같은 내용을 순차적으로 정리한 버전은 `spec-driven-retro-chronological.md`에 있다.

## 중심 문제

> 근본 문제는 아직 안 풀렸는데, 그 주변을 설명하고 측정하고 부분적으로 보완한 코드와 spec만 계속 늘어났다.

구현량과 테스트 수는 늘었지만 두 가지 믿음은 생기지 않았다.

- 이 제품이 이제 정말 사용자의 문제를 해결한다는 믿음
- 이 코드베이스를 앞으로도 계속 키워나갈 수 있다는 믿음

> 기능은 늘어나는데, 코드베이스가 다음 기능을 더 잘 받아들일 수 있는 구조로 성숙하고 있다는 확신이 없다.

문제는 작은 완료가 부족했던 것이 아니다.

> 작은 완료를 많이 만든 것이 아니라, 모든 작은 완료가 하나의 실제 제품과 유지 가능한 코드로 수렴하게 했어야 했다.

| 관점 | 드러난 문제 | 원했던 상태 |
|---|---|---|
| 제품 | 기능은 늘지만 근본적인 사용자 문제 해결로 수렴하지 않음 | 작은 완료들이 하나의 실제 제품으로 수렴 |
| 코드 | 문제마다 조건·계층·연결 코드를 붙여 해결함 | 기능이 늘수록 책임과 제품 구조가 더 분명해짐 |
| spec | 작업은 이어졌지만 이전 판단과 구조가 확정된 전제로 굳음 | spec을 실행 도구로 쓰면서 기존 판단을 다시 열 수 있음 |
| 평가 | 명시된 동작과 AC 통과를 주로 확인함 | 제품 전체와 변경 전후 코드 구조를 함께 판단 |
| 컨텍스트 | 보존할 정보를 모두 읽히거나 영구 규칙으로 만들기 쉬움 | 보존, 선택적 읽기, 현재 권위를 구분 |

## 왜 긴 작업에서 국소 완료가 전체 판단을 밀어냈나

spec과 AC가 나빴기 때문이라고만 설명하면 충분하지 않다. 기능 완료는 명시적이고 즉시 검증할 수 있었던 반면, 제품의 수렴과 코드 구조의 성숙은 모호하고 늦게 드러났다는 차이가 있었다.

- 다음 AC의 구현 여부는 바로 확인할 수 있었다.
- 테스트 통과는 성공과 실패를 비교적 분명하게 알려줬다.
- 이미 구현한 구조를 유지하면 다음 작업을 곧바로 시작할 수 있었다.
- 제품 전체가 더 설득력 있어졌는지는 여러 기능과 실제 사용자 흐름을 함께 봐야 했다.
- 코드베이스가 성장 가능한 방향으로 바뀌었는지는 변경 전후와 이후 작업까지 비교해야 했다.

작업이 길어질수록 측정하기 쉽고 바로 닫을 수 있는 항목이 작업의 진척을 대표하기 쉬웠다. 반대로 기존 판단을 폐기하거나 이미 구현한 구조를 다시 여는 행동은 작업량이 늘고 완료를 뒤로 미루는 것처럼 보일 수 있었다.

> 기능 완료는 명시적이고 즉시 검증할 수 있었지만, 제품의 수렴과 코드 구조의 성숙은 모호하고 늦게 드러났다. 그래서 긴 작업일수록 전체적으로 더 중요한 것보다, 지금 닫을 수 있는 다음 항목이 작업을 지배했다.

> 국소 완료는 계속 보상됐지만, 기존 판단을 폐기하거나 이미 구현한 구조를 다시 여는 행동은 진척으로 잘 계산되지 않았다.

이 비대칭이 해결되지 않으면 초기에는 제품과 구조를 충분히 대화하더라도, spec과 구현이 쌓인 뒤에는 다시 국소 완료 중심으로 돌아갈 수 있다.

## 제품 관점: 기능 추가와 제품의 수렴

### 드러난 문제

각 기능과 AC는 완료됐지만, 그것들이 사용자의 근본 문제를 해결하는 하나의 제품으로 모이고 있는지는 충분히 판단되지 않았다.

성공의 기준이 주로 다음에 머물렀다.

> 명시된 동작이 구현됐는가?

하지만 기능 하나가 동작한다는 사실과 제품 전체가 설득력 있게 작동한다는 사실은 다르다. 구현과 테스트가 늘어도 사용자의 실제 흐름이 매끄럽지 않거나, 각 기능이 서로 분리된 조각처럼 느껴질 수 있다.

### 원했던 상태

- 각 기능이 제품의 핵심 목적을 더 분명하게 만든다.
- 부분적인 기능들이 실제 사용자 흐름으로 연결된다.
- 기능 수가 아니라 근본 문제를 해결하는 정도로 진척을 판단한다.
- 다음 기능을 추가하기 전에 제품 전체가 무엇을 향해 가고 있는지 다시 볼 수 있다.

### 필요한 판단

- 이 기능이 제품의 어떤 핵심 문제를 더 깊게 해결하는가
- 기능들이 하나의 사용자 경험으로 연결되는가
- 근본 문제는 남아 있는데 주변 기능만 정교해지고 있지는 않은가
- 지금 만드는 제품 전체가 무엇을 향해 수렴하고 있는가

## 코드 관점: 동작하는 코드와 성장 가능한 구조

### 드러난 문제

새로운 문제가 나타날 때마다 “현재 모델이 잘못된 것은 아닐까?”를 다시 묻기보다, 기존 구조 안에 조건·계층·연결 코드를 추가해 해결했다.

각 구현은 틀리지 않았을 수 있다. 하지만 이런 해결이 반복되면서 전체적으로는 하나하나 문제를 해결해 붙여 나가는 느낌이 쌓였다.

### 성장 가능한 코드의 의미

여기서 말하는 코드 품질은 막연한 ‘깔끔한 코드’가 아니다.

- 하나의 제품 개념이 코드에서 한 군데의 분명한 주인을 가진다.
- 새 경우가 생겨도 여러 층에 조건문과 예외가 퍼지지 않는다.
- 변경할 위치와 영향 범위를 예측할 수 있다.
- 과거 가정이 틀리면 그 위에 덧대지 않고 교체할 수 있다.
- 기능이 늘수록 제품 구조가 더 잘 드러나지, 더 가려지지 않는다.

### 구조가 저항하고 있다는 신호

- 같은 제품 규칙을 여러 위치에서 다시 표현해야 한다.
- 간단해 보인 변경이 예상 밖으로 많은 module이나 layer를 건드린다.
- 기존 구조에 맞추기 위해 flag나 예외 조건을 하나 더 만들어야 한다.
- 이 동작을 책임져야 할 분명한 위치가 없다.
- 기능을 추가하기 전에 관련 없는 코드를 먼저 정리해야 한다.
- 기능은 통과했지만 전체 흐름이 파편적으로 느껴진다.
- 새 spec이 상위 제품 목적이나 기존 도메인 의미와 충돌한다.

이런 신호가 나오면 바로 다음 AC로 진행하거나 무조건 리팩터링을 시작하는 것이 아니라 다음 선택을 다시 판단해야 한다.

- 기능의 형태나 범위를 바꾼다.
- 기존 코드 구조를 먼저 다시 만든다.
- 상위 제품 판단이 바뀌었으므로 지속 컨텍스트를 수정한다.

> 구조가 저항하는 신호가 생겼을 때 feature 완료보다 재판단을 우선한다.

## spec 관점: 작업의 연속성과 판단의 연속성

### spec이 잘한 것

spec-driven 방식은 작업을 이어가는 데 강했다.

- 해야 할 일을 남겼다.
- AC와 구현 범위를 명확하게 했다.
- 다음 작업이 어디에서 시작되어야 하는지 알려줬다.
- 긴 작업에서도 기능 구현을 계속 진행할 수 있게 했다.

### spec이 이어주지 못한 것

- 현재 구조를 계속 전제로 삼아도 되는가
- 기존 모델이 잘못 잡힌 것은 아닌가
- 이제 spec 자체를 수정하거나 폐기해야 하는가
- 각 변경이 제품 전체와 코드 구조에 어떤 누적 효과를 남겼는가

> 스펙은 작업의 연속성은 보존했지만, 판단의 연속성은 보존하지 못했다.

여기서 판단의 연속성은 이전 결론을 다음 작업에 그대로 물려주는 것이 아니다.

> 판단의 연속성은 이전 결론을 보존하는 것이 아니다. 왜 그런 결론을 내렸는지, 무엇이 불확실했는지, 어떤 신호가 나타나면 다시 열어야 하는지를 다음 작업까지 이어가는 것이다.

따라서 지속되어야 할 것은 결론만이 아니라 다음 내용이다.

- 그 결론을 내린 이유와 확인한 근거
- 결론을 내릴 당시 남아 있던 불확실성
- 판단이 더 이상 유효하지 않다고 볼 수 있는 신호
- 기존 결론과 이미 만들어진 산출물을 교체할 수 있는 권한

판단을 지속한다는 것은 과거 선택에 영구적인 권위를 주는 일이 아니라, 다음 작업에서도 그 선택을 다시 판단할 수 있게 하는 일이다.

spec이 많이 쌓일수록 당시의 선택과 기존 구조는 확정된 현실처럼 작용했다. 다음 작업은 그 판단을 다시 검토하기보다 이미 정해진 전제로 승계했다.

### spec의 역할

spec을 없애는 것이 목표는 아니다. spec이 작업을 이어주는 장점은 유지하되, 제품과 코드 구조를 판단할 권한까지 대신하지 않게 해야 한다.

spec은 권위 있는 누적 기록이 아니라 수정되거나 폐기될 수 있는 실행 도구여야 한다.

분명히 정할 것:

- 사용자가 무엇을 할 수 있어야 하는가
- 제품에서 어떤 의미가 보존되어야 하는가
- 이번 작업의 범위와 하지 않을 것
- 실제로 확인해야 할 대표 사용 흐름

구현 과정에 열어둘 것:

- 어느 class나 module에 넣을지
- 내부 데이터 구조를 어떻게 바꿀지
- 기존 추상화를 유지할지 교체할지
- task를 어떤 순서와 크기로 나눌지
- 기존 코드 중 무엇을 제거하거나 합칠지

> 제품에서 필요한 결과는 분명히 하되, 실제 코드를 보고 판단해야 하는 것까지 미리 확정하지 않는다.

## 평가 관점: 기능 통과와 전체 품질

### 완료의 두 기준

- 요구한 동작이 실제로 되었는가
- 그 동작을 받아들인 뒤 코드베이스가 더 잘 설명되고 계속 키우기 쉬워졌는가

첫 번째 기준만으로는 제품과 코드의 수렴을 확인할 수 없다. 두 번째 기준도 함께 판단해야 한다.

### 필요한 두 가지 비교

제품 원자료와 실제 동작의 비교:

- 제품의 의도가 결과에 살아 있는가
- 사용자 흐름이 실제로 이어지는가
- 각 기능이 부분들의 집합이 아니라 하나의 제품으로 느껴지는가

변경 전 코드와 변경 후 코드의 비교:

- 제품 개념이 여러 곳으로 흩어지지는 않았는가
- 의존성·예외·중복이 증가하지 않았는가
- 다음 비슷한 변경의 위치가 더 명확해졌는가
- 기존 가정을 교체한 것인가, 그 위에 다시 덧댄 것인가

### 평가 감각의 지속

평가 감각도 새로운 세션이 이어받아야 할 정보다.

- 무엇을 좋은 제품 결과로 보는가
- 기능은 통과했지만 왜 피상적이라고 판단했는가
- 어떤 코드 변경을 성장 가능한 방향으로 보는가
- 평가 판단의 근거가 된 원자료와 외부 레퍼런스는 무엇인가

현재 후보는 외부 평가 주체가 제품 원자료와 결과물, 변경 전후 코드를 직접 비교하게 하는 것이다.

다만 다음은 아직 결정되지 않았다.

- 누가 평가를 발동하는가
- 어떤 작업에 어떤 평가 기준을 불러오는가
- 평가자가 기존 spec 자체도 문제 삼을 수 있는가
- 평가 결과가 작업을 멈추거나 구조를 다시 여는 데 어느 정도 권한을 갖는가

## 컨텍스트 관점: 보존, 선택적 읽기, 권위

### 제품 정보만 지속되는 것은 아니다

여러 작업과 세션에 걸쳐 남겨야 할 정보에는 다음이 포함될 수 있다.

- 제품의 목적과 핵심 도메인 개념
- 반드시 지켜야 하는 제품 의미와 품질 기준
- 백엔드와 프런트엔드의 책임 구조
- 테스트와 설계에 관한 기술적 판단 기준
- 무엇을 좋은 결과로 보는지에 관한 평가 감각
- 작업 종류별 workflow
- 현재 구조의 위험과 아직 열려 있는 판단

그러나 지속된다는 이유로 모두 매번 읽히거나 영구 규칙이 되어서는 안 된다.

### 보존 기간

오래 유지할 정보:

- 제품의 목적과 핵심 도메인 의미
- 반드시 지켜야 하는 제약
- 제품 품질에 관한 판단
- 여러 작업에서 반복해서 필요한 기술적 판단 기준

현재 상태로 유지할 정보:

- 현재 코드 구조와 책임 경계
- 알려진 구조적 위험
- 아직 해결하지 못한 질문
- 최근 선택한 설계 방향
- 임시 호환 계층과 기술 부채

이 내용은 과거 상태를 계속 쌓기보다 현재 상태로 교체한다.

작업이 끝나면 지속적인 역할이 끝나는 정보:

- 기능 spec과 AC
- 구현 plan과 세부 task
- 조사 메모
- 이번 작업의 구체적인 테스트 케이스

파일을 반드시 삭제한다는 뜻은 아니다. 다음 작업을 지휘하는 지속 컨텍스트와 실행 권한을 잃는다는 뜻이다.

### 읽히는 조건

> 장기적으로 보존할 정보와 매 작업마다 자동으로 넣을 정보는 같지 않다.

항상 짧게 읽힐 수 있는 것:

- 제품 목적과 핵심 도메인 의미
- 중요한 기술적 제약
- 현재 작업에 필요한 자료를 찾는 경로

관련 작업에서만 읽힐 것:

- 메타모픽 테스트 방법
- API 설계 가이드
- 데이터 마이그레이션 원칙
- UI 검증 방법
- 관련 평가 기준과 workflow

### 현재 권위

지속된 정보는 서로 다른 성격을 가진다.

- 반드시 지켜야 할 제품·도메인 불변 조건
- 특정 상황에 적용하는 기술적 판단 기준
- 계속 수정할 수 있는 현재 구조 설명
- 한 작업에만 유효한 실행 지시

모든 정보에는 세 가지를 따로 물어야 한다.

- 다음 작업까지 보존해야 하는가
- 어떤 종류의 작업에서 읽어야 하는가
- 확정된 원칙인가, 현재 상태인가, 수정 가능한 판단 방법인가

> 지속되어야 할 지식은 늘어날 수 있지만, 매 세션의 컨텍스트와 영구적인 권위까지 함께 늘어나서는 안 된다.

새로운 세션이 모든 것을 처음부터 알 필요는 없다.

> 새로운 세션이 모든 것을 처음부터 아는 것이 아니라, 현재 작업에 필요한 지식을 어디서 찾아야 하는지 아는 상태를 만든다.

따라서 필요한 것은 거대한 공통 문서 하나가 아니라 다음에 가깝다.

- 짧은 프로젝트 진입점
- 책임이 분리된 지속 컨텍스트
- 작업에 따라 필요한 자료를 선택해 읽는 routing
- 실제 코드와 결과물을 그때 직접 확인하는 방식

## 이 관점들을 관통하는 핵심 구분

- 작업을 계속 이어가는 것과 이전 판단을 계속 이어가는 것은 다르다.
- 기능이 동작하는 것과 코드베이스가 그 기능을 건강하게 흡수하는 것은 다르다.
- 제품 결과를 명확히 하는 것과 내부 구현을 미리 확정하는 것은 다르다.
- 정보를 장기 보존하는 것과 모든 세션에 자동으로 읽히는 것은 다르다.
- 현재 구조를 기록하는 것과 그 구조에 영구적인 권위를 주는 것은 다르다.
- 완료된 spec을 보관하는 것과 다음 작업을 계속 지휘하게 하는 것은 다르다.
- 매 작업에서 구조적 영향을 살펴보는 것과 매번 거대한 아키텍처 리뷰를 여는 것은 다르다.
- 구조 저항 신호를 발견하는 것과 곧바로 리팩터링을 확정하는 것은 다르다.

## 이 정리가 주장하지 않는 것

- spec-driven이 모든 문제의 유일한 원인이라는 뜻은 아니다. 모델의 한계, 작업 속도, 제품의 복잡성, 설계 경험도 함께 작용했을 수 있다.
- spec을 없애자는 뜻은 아니다.
- 모든 작업마다 전체 아키텍처를 처음부터 다시 검토하자는 뜻은 아니다.
- 지속 컨텍스트를 모두 하나의 거대한 문서에 넣자는 뜻은 아니다.
- 지속되는 정보를 모든 세션에 항상 주입하자는 뜻은 아니다.
- 작업이 끝난 spec 파일을 반드시 삭제하자는 뜻은 아니다.
- 현재 아키텍처를 영구 원칙으로 고정하자는 뜻은 아니다.

## 이 회고의 근거와 현재 지위

이 문서는 당시의 체감만을 뒤늦게 해석한 메모가 아니다. 남아 있는 원자료와 기존 분석을 비교하고, 당시 작업을 직접 수행한 사용자와의 대화를 통해 문제의 양상과 원인을 더 명확히 한 회고 분석이다. 따라서 아래 중심 진단은 현재 TripProof 개발 경험을 설명하는 근거 기반 결론으로 사용한다.

원자료와 회고 대화에서 함께 확인된 문제:

- 구현량과 spec, 테스트는 계속 늘었다.
- 개별 기능은 구현됐지만 제품 전체에 대한 만족감은 충분하지 않았다.
- 코드베이스를 계속 키워도 되는지에 대한 우려가 있었다.
- 구현들이 근본 모델을 다듬기보다 문제를 하나씩 해결해 붙이는 것처럼 느껴졌다.

원자료 비교와 회고 대화를 통해 구체화된 중심 진단:

- 측정하기 쉬운 국소 완료가 제품과 구조에 대한 전체 판단보다 우선됐다.
- 이전 spec과 코드 구조가 재검토 대상보다 다음 작업의 전제로 승계됐다.
- 작업의 연속성에 비해 판단의 근거와 재검토 조건은 충분히 지속되지 않았다.

주장 단위의 추적성을 더 촘촘히 남길 수 있는 것:

- 실제 spec들이 이전 판단과 구조를 어떤 방식으로 전제했는가
- 조건, 예외, 책임 분산이 코드 변화에서 실제로 어떻게 누적됐는가
- 제품 원자료와 구현 결과 사이에서 어떤 간극이 반복됐는가
- 전체 판단을 다시 열려 했거나 열지 못했던 구체적인 작업 장면은 무엇이었는가

> 남은 일은 중심 진단의 타당성을 처음부터 다시 검증하는 것이 아니라, 특정 구현 시점과 인과를 서술할 때 제시할 세부 근거 연결을 보강하는 것이다. 이 분석에서 도출한 해결 장치의 효과는 실제 적용 결과로 별도 검증해야 한다.

## 아직 남은 설계 질문

- 무엇을 여러 작업과 세션에 걸쳐 보존할 것인가
- 보존된 것 중 무엇을 이번 작업에 읽힐 것인가
- 무엇을 미리 결정하지 않고 구현 중의 판단으로 열어둘 것인가
- 기존 spec이나 구조를 언제 다시 의심할 것인가
- 제품 전체와 코드 구조의 품질을 누가 어떻게 판단할 것인가
- 그 평가가 재판단을 발동할 권한을 어떻게 가질 것인가
- 이 장치 자체가 다시 문서와 절차를 누적시키지 않게 하려면 어떻게 해야 하는가

전체를 관통하는 목표는 하나다.

> spec이 제공한 작업의 연속성은 살리되, 그 위에 제품과 코드 구조를 다시 판단할 수 있는 연속성도 함께 남긴다.
