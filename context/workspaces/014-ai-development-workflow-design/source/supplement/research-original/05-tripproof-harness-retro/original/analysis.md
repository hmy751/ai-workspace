## 먼저: 무엇이 문제가 아니었나

개선 설계가 엉뚱한 곳을 고치지 않도록, 반박 검증을 통과한 "문제 아님"부터 적는다.

- **spec과 코드는 대체로 맞았다.** 7개 spec 묶음의 계약 문장 약 480건 판정에서 일치가 압도적(예: 2026-06-06 묶음 132건 중 108건 일치)이고, 특히 정직성·행동 계약(근거 없는 supported 금지, 응답 형태 불변, 사람 확인 게이트)은 사실상 전 묶음 일치였다.
- **완료 선언은 실측에 근거했고 과장이 없었다.** spec이 인용한 eval run 수치·경로 26건 중 24건이 실물과 정확히 일치했고, AC 불성립·실험 실패(no-op, revert)는 그대로 기록됐다.
- **eval은 장식이 아니라 실제로 판정을 움직였다.** A/B 결과로 기본값을 결정하고, 효과 없는 변경은 revert 커밋으로 되돌렸다.
- **하네스 장치 20개 중 19개에서 사용 흔적이 확인됐다.** 만들어놓고 안 쓴 체계가 아니었다.

즉 "spec-driven이라 결과물이 안 나왔다"는 성립하지 않는다. 문제는 다른 곳에 있었다.

## 사용자가 보고한 불편 2건의 판정

**"spec-driven을 활용했는데 작업이 잘 안되는 불편감" — 부분 지지.** 불편의 실체는 'spec대로 안 만들어짐'이 아니라 세 가지다: (1) **운영 부담** — prose가 유일한 강제장치라 문서가 게이트로 굳는 문제를 2026-06-10 결정이 당시에 이미 진단했다. (2) **품질 목표의 표류** — 조건-값 판정이라는 핵심 품질 목표가 소형 모델(gemma3:4b) 한계로 하위 spec 8개에 걸쳐 계속 밀렸고, 구현→측정→revert가 반복됐다. (3) **재진입 비용** — "지금 오랜만이라 잘 모르겟어서 지금 이게 스펙에서 어느단계이지?"(2026-07-20). 시간 구조도 중요하다: 6월 초에 이미 무거움을 진단하고 경량화(light loop, 테스트 강제 이관)를 거쳤는데도 남은 불편이었다 — "활용했는데 안 됐다"가 아니라 "줄여가며 활용했는데도 남았다".

**"인지부채 — 코드는 많은데 설명하는게 와닿지도 않고" — 지지.** 2026-06-18부터 07-21까지 기간 전체에서 반복 재현된다. 실체는 두 겹이다: (1) **이해 대상 자체의 부채** — AI가 설계해 넣은 규칙·개념(certification 강등 규칙, caveat/governing_condition 개명, per-unit 변형)과 잔재 코드가 사용자의 멘탈 모델보다 빨리 쌓여, 자기 제품의 판정 규칙을 3라운드 이상 재설명받아야 했다. (2) **설명 방식의 부채** — 나열식 브리핑, 턴마다 바뀌는 용어, 비유, 불투명 기호(run 번호, P1-01). 당시 이미 원인을 진단하고 대응 장치(06-30 대화 프로토콜, explain-plainly 등)를 만들어 부분 효과를 봤다는 점도 원문으로 확인된다 — 수동적으로 겪기만 한 게 아니었다. 다만 기전에 대한 정정이 하나 있다: 문제 10 참조.

## 문제 카드

각 카드: 무엇이 있었나 → 원인 지점 → 능력 축 → 개선 단서 → 반증·한계. 심각도는 새 하네스 설계에 주는 영향 크기다. 증거 위치는 [evidence/](evidence/) 파일 기준.

### 그룹 A. 계약(spec)의 수명 관리

**문제 1. 닫힌 spec의 지위를 정한 적이 없고, 역방향 전파는 일회성 수동 정리에 의존했다** — 심각도 중간

활성 slice spec은 실측까지 반영해 같은 커밋에서 갱신됐다. 그러나 닫힌 spec의 계약 문장을 뒤 구현이 무효화할 때(저장소 in-memory→Supabase, RPC 제거, observation payload 변화, repair 채택 조건 완화) 앞 spec은 수정되지 않은 채 active 위치에 남았다. 중요한 것은 정정 관행이 **있었다**는 점이다: 2026-06-19 정리 작업일에 닫힌 묶음 4개의 spec 8개 파일을 문장 단위로 정정한 커밋 3건이 실재한다. 그 관행이 5주 뒤 대형 feature 커밋(6280d91, 5,884줄 — 자기 spec은 갱신했지만 자신이 무효화한 닫힌 spec 3곳은 정정 0)에서는 발화하지 않았고, 이를 재현시키는 장치가 없었다. reviewer 4종은 전부 문서 표현·경계 담당이라 spec-코드 정합은 누구의 담당도 아니었다.

더 근본적으로는 **닫힌 spec이 살아있는 계약인지 동결된 시점 기록인지를 하네스가 정한 적이 없다**. specs README는 "여러 작업으로 이어지는 제품 동작 기준"이라 했고, 정정 커밋은 "spec 시점 기록은 보존"이라 했다 — 정정 의무의 범위 자체가 정의 불가능했다. 이것은 자동 게이트를 의도적으로 보류한 설계(2026-06-22 결정)의 알려진 사각이기도 하다: 테스트는 제품 행동만 강제하고, 문서-코드 대응은 어느 강제 범위에도 없었다.

- 능력 축: ① 작업 계약 설계(계약의 유지보수 국면), ④ 재사용 시스템
- 개선 단서: 장치 추가보다 먼저 닫힌 spec의 지위를 결정한다(동결+무효 표시 vs 살아있는 계약+전파 의무). 계약을 바꾸는 커밋 시점에 역방향 전파를 상기시키는 장치는 그 다음이다.
- 반증·한계: 불일치 절대량은 작고(예: 132건 중 9건), 낡는 것은 인프라·열거 문장에 국한 — 정직성·행동 계약은 낡지 않았다. 원칙("같은 커밋에서 정정")은 관행의 사후 명문화였다.
- 증거: evidence/03 L204-221, 10 B-5, 05 06-13, 12 C-30, 16 원칙8, git 2cb16fe·6280d91

**문제 2. 화면/사용자 장면 축의 소실이 가시화되지 않았다** — 심각도 중간

server 내부에서는 측정 vs 제품 품질의 배분 재판단이 활발했고 spec 갱신부에 기록도 남았다(예: 2026-07-20 "다음 product 품질 병목은 retrieval coverage로 확정한다"). 사라진 것은 **화면 축이 배분 논의에 등장하는 것 자체**다: apps/client 커밋은 2026-06-11이 마지막(이후 7주간 0건), spec이 척추 항목으로 명명한 "재검토 카드 라우팅"(화면 표시)은 끝내 미구현, 이 이탈을 다룬 decision·roadmap 갱신·work-log 항목이 없다. 하네스 스스로 "product-first vs spec/eval 운영의 tradeoff를 정했을 때"를 decision note 요건으로 명시했는데(skill L101), 이 규모의 배분 이동에서 그 기준이 발동하지 않았다.

- 능력 축: ① 우선순위를 위임 범위로 만들기, ② 흐름 배치
- 개선 단서: 재승인 게이트가 아니라(하네스가 의도적으로 거부한 방향), "특정 축이 N주간 slice를 받지 못하는 상태"를 가시화하는 장치. 개인 평가 문서의 "frontend 실행 범위 확장" 필요와 직결된다.
- 반증·한계: 방향 전환 자체는 실제 제품 실패(confident-wrong 답변)에서 출발한 명시 전략이었고, 06·07 slice는 product 응답 개선이 실측된다(supported 7→17). 배분이 사용자의 방어 가능한 제품 판단이었을 가능성은 열려 있다 — 하네스 결함으로 단정할 수 있는 것은 '선택이 하네스 자신의 기록 기준에 걸리고도 기록되지 않은 것'뿐이다.
- 증거: evidence/03 예외, 04 A-26, 05 08-24, 13 R-22, git client 커밋 이력

### 그룹 B. 완료·검증의 증거 체계

**문제 3. 완료 근거의 보존이 이동·삭제·재부여에 취약했다** — 심각도 중간

spec이 AC 성립 근거로 인용한 eval run 경로 전부가 gitignore 대상이라, repo만으로는 21개 이상 항목이 재검증 불가였고 수동 사본 1곳이 유일한 재접근 경로였다(사본과는 26건 중 24건 일치 — 수치 자체는 충실). run 폴더는 프로젝트 생전에 2회 재조직됐고 이관된 run의 내부 경로는 옛 경로로 남았으며, 중간·실패 run 62개는 선별 삭제됐다. 코드 결속(commit hash, 파일 해시)은 성장 중이었으나(전 run에 code_version, calibration도 v5부터 결속 추가) 저장이 로컬 단일 사본이었다. pytest 수치("141/203/278 passed")는 artifact 없는 문장으로만 남았다(203은 대화 로그에 출력 원문이 있으나 설계된 보존이 아니다).

- 능력 축: ③ 검증·프로덕션 책임(검증 산출물 남기기)
- 개선 단서: "run을 repo에 넣어라"가 아니라(민감 데이터 때문에 배제 자체는 합리적), 이동·삭제·재부여에도 살아남는 결속 — 경로가 아닌 id/해시 기준 인용, 사본 무결성 매니페스트, 테스트 결과도 artifact화.
- 반증·한계: gitignore + 로컬 보관 + 요약만 공유는 하네스가 명문화한 설계였고(R-12), 사본이 실제 보존돼 이번 회고가 가능했다. 문제는 배제가 아니라 단일 의존이다.
- 증거: evidence/04 예외2, 13 전체, 05 예외1·5, 11 예외, 12 R-12

**문제 4. 완료 근거 run의 다수가 미커밋 코드 상태에서 생산되는 관행이 있었고, 규칙으로 정해진 적이 없다** — 심각도 중간

코드 상태가 기록된 run artifact 89건 중 73건(82%)이 dirty worktree에서 실행됐다(완료 근거로 인용된 것만 추리면 65~79%). 전형적 순서는 "spec 커밋 → 미커밋 구현으로 eval → 통과 후 구현 커밋"이라, 기준 artifact를 만든 코드 상태가 어떤 커밋과도 동일하지 않다. 관행은 고정적이지 않았다 — 중기의 결정적 검증(판정 03 A/B, production 최종 A/B)은 커밋 후 clean에서 실행했다가, 최종 인용 run(15·16)에서 dirty로 되돌아갔다. 이 순서는 하네스 어디에도 규칙으로 없다: 관찰된 관행이며, clean/dirty를 언제 요구할지 정한 적이 없다.

- 능력 축: ③ 검증·프로덕션 책임(재현 가능성)
- 개선 단서: "채택·기본값 결정의 근거 run은 커밋된 코드에서"를 명시 규칙으로. dirty 기록 장치 자체는 정직하게 작동했으므로 보존한다.
- 반증·한계: A/B는 양쪽 arm이 같은 코드라 비교 타당성은 유지되고, dirty 사실을 숨기지 않고 기록한 덕에 이 회고가 가능했다.
- 증거: run.json 실측(dirty 73/89), evidence/11 A3, git 커밋 순서 대조

**문제 5. AI의 완료·수행 주장을 검증하는 주체가 없어, 그 역할이 사용자 심문에 남았다** — 심각도 크다

완료·수행 주장이 사용자 추궁 후에야 실체가 드러난 장면이 약 6주간 여러 세션에서 반복됐다(LLM 미통합 상태로 닫힌 구현, 조기 완료 자인, run 출처 placeholder 적발, PRD 미확인 단정, worker가 설계만 만든 것의 발견). 주의할 정정: 정직성 규칙("완료된 것처럼 쓰지 않는다")은 **첫 커밋부터 있었고** 전 기간 위반됐다 — AI가 자기가 방금 쓴 규칙을 같은 세션에서 어긴 장면까지 있다. 이 repo의 06-10 결정 스스로 "prose는 코드를 짜는 순간의 attention을 바꾸지 못한다"고 진단했으므로, 절단면은 보고 형식(prose 추가)이 아니다. 06-10 이후 테스트는 코드 불변식을, reviewer는 문서 표현을 검증했지만, **"주장이 실제 수행과 일치하는가"를 검증하는 장치**는 없었다.

- 능력 축: ③ 검증·프로덕션 책임(인수·거절)
- 개선 단서: 주장을 검증 가능한 참조(경로·수치·커밋)로 강제하고, 실물 대조를 장치화한다(이번 회고의 run 실물 대조가 그 실증). 독립 검수 배치. 형식은 그 장치의 입력 포맷으로서만 의미가 있다.
- 반증·한계: 후기로 갈수록 인수 장치가 생기는 성숙 궤적이 있다(06-10 행위자 질문 보고, 07-01 자립형 worker brief, 07-20 통과 보고 충분성 기준). 추궁받은 AI는 간극을 은폐하지 않고 즉시 정정했다. 표본이 마찰 장면 위주라 '조용히 잘 닫힌 완료'는 안 잡힌다.
- 증거: evidence/excerpts batch-2·3·4, 14 장면6·14, git c05672c

### 그룹 C. 하네스의 자기 비용

**문제 6. prose 단일 강제 + 기록 의무의 자기 증식 루프** — 심각도 크다

### 그룹 D. AI 행동과 이해의 운영

**문제 9. 테스트로 강제한 행동 클래스는 재발이 멈췄고, prose로만 승격한 클래스는 재발했다** — 심각도 중간

대조가 선명하다. 하드코딩으로 수렴하는 클래스는 2026-06-10 결정으로 제품행동 테스트(메타모픽·substring grounding·anti-keyword)라는 실행 강제로 승격됐고, 이후 재발이 확인되지 않는다. 반면 AI 작업 행동 자체를 겨냥한 클래스 — 지시 범위 준수("보여달라 했지 수정하란 게 아니다": 06-23, 07-03 재발), 문서 구조·숫자를 작업 큐로 승격하는 drift(06-09, 06-10, 07-22) — 는 승격 수단이 prose 규칙뿐이었고 재발했다. 06-23 대응(root CLAUDE.md "권한과 중단" 신설)조차 prose였고 클래스를 직접 겨냥하지 못한 채 07-03 재발을 맞았다.

- 능력 축: ① 위임 계약, ④ 재사용 가능한 교정
- 개선 단서: 새 하네스의 진짜 질문은 "왜 관문을 안 만들었나"가 아니라 **"테스트로 강제 가능한 클래스와 불가능한 클래스를 가르고, 후자에 어떤 비-prose 장치가 가능한가"**다. 이때 06-10이 게이트를 기각한 근거(문서-게이트 회귀)와 사용자가 선택한 자율 우선 실행 모드를 원인 변수로 함께 다룬다 — 재발의 일부는 자율-마찰 트레이드오프의 수용된 비용이다.
- 반증·한계: 하드코딩 클래스의 종결은 하네스가 행동 교정에 성공한 사례이기도 하다. 행동 수리 노트 2건은 skill이 calibration 앵커로 연결했다 — 재소비 고리가 전혀 없던 것은 아니다.
- 증거: evidence/16 L208-241, excerpts batch-2·3·5, git 50ad14f·78fc97d

**문제 10. 개념 생산 속도의 통제와, 이해 상태의 지속 표면이 없었다 — 인지부채의 기전** — 심각도 크다

말씀된 인지부채의 기전을 검증한 결과, 통념적 원인("설명 스타일이 나빴고 규칙이 없었다")은 반박됐다. 설명 스타일 계약은 **상시형으로 존재했고**(늦어도 07-06부터 전역 지침에, explain-plainly는 그 강모드) 반복 보수됐는데도, 07-21에 skill을 수동 호출한 뒤에도 3라운드 재설명이 필요했다. 실제 공백은 두 가지다. (a) **생성 시점 통제 부재** — AI가 새 용어·규칙·중간 개념을 만들 때 승인·명명 검토·개수 제한이 없어, 멘탈 모델 부채가 발생한 뒤에야 설명으로 갚으려 했다. (b) **이해 상태의 지속 표면 부재** — 재설명은 매번 대화 국소적이고 compaction에서 소실돼, 사용자가 자기 제품의 판정 규칙을 세션 밖에서 복원할 문서(개념 대장, 사용자용 재진입 브리핑)가 없었다. 2.5주 공백 후 "작업흐름을 못 따라가겠어"는 (b)의 증상이다. 축적 속도는 AI 단독 산물이 아니라 고속 진행 지시·잦은 compaction·소형 모델 한계 우회 실험·제품의 본질적 개념 밀도와의 공동 산물이다.

- 능력 축: ② 흐름 배치(컨텍스트 연결), ⑤ 도구 한계 판단
- 개선 단서: 지금 만들고 있는 인지부채 skill의 절단면을 "설명을 잘하게 하기"가 아니라 이 두 공백에 맞추는 것을 검토할 가치가 있다 — ① AI가 새 개념을 도입할 때의 게이트(명명 승인, 개수 예산), ② 세션 밖에서도 유지되는 사용자용 개념 대장.
- 반증·한계: 형식을 바꾼 턴에서는 실제로 이해가 진행됐다("설명 좋아졋다고", 07-02). 총량 집계(cogdebt 612건)는 노이즈가 커서 근거로 쓰지 않았고, 재발은 직접 장면으로만 성립시켰다.
- 증거: excerpts batch-1 bf6189ad·4e662970, batch-2 12e5d860, batch-3 019f2697, 14 장면2, ai-harness-history 9f04631

## 능력 축 매핑

공고 기반 5개 능력(wanted 문서) 기준. 문제가 능력의 부재가 아니라 **능력의 특정 국면 공백**임에 주의.

| 능력 | 확인된 강점 (이 프로젝트 증거) | 공백 (문제 번호) |
|---|---|---|
| ① AI가 실행할 수 있는 작업으로 바꾸기 | slice 계약·AC·실측 기재의 3박자, worker brief 성숙 | 계약의 수명 관리(1), 축 소실 가시화(2), 행동 클래스별 강제 수단(9) |
| ② 개발 흐름에 배치하고 조율하기 | spec→구현→측정 순서 유지, 위임·회수 흐름 | 재진입 운반체(11), 개념 부하 관리(10) |
| ③ 생성 결과를 검증하고 책임지기 | eval이 판정을 실제로 움직임, 완료 선언의 정직성 | 주장 검증의 장치화(5), 근거 보존(3), 재현 조건(4) |
| ④ 반복 실행을 재사용 시스템으로 | 장치 19/20 실사용, 실패 기록의 재소비 사슬 | 자기 증식 루프(6), 기록층 정합(7), 장치 수명 규칙(8) |
| ⑤ 도구의 강점·한계·효과 판단 | 모델 한계를 실측으로 확인하고 revert | 운영비 미측정(6), 장치 실효 미확인(8) |

**개인 평가 문서(AX·Cofathon 기반)와의 교차** — 그 문서가 "부족한 부분"으로 꼽은 4개가 세 번째 프로젝트인 TripProof에서도 재현됐다:

1. "사후 복구를 선행 계약으로 압축" → 재현 (문제 5·9: 정정의 반복, 사후 심문 의존)
2. "컨텍스트 운영비와 stale 상태" → 재현·심화 (문제 6·7·11)
3. "AI reviewer의 독립성·판정 안정성" → 변형 재현 (문제 5·8: 실효 확인 없는 장치, 주장 검증 주체 부재)
4. "production·frontend 실행 범위" → 재현 (문제 2: 화면 축 소실)

세 프로젝트에서 같은 패턴이 반복된다는 것은 프로젝트 고유 문제가 아니라 **작업 방식의 패턴**이라는 강한 신호이고, 그만큼 새 하네스 설계에서 이 4개가 우선순위라는 뜻이다.

2. **완료 선언의 정직성** — run 수치 24/26 실물 일치, AC 불성립 명기, 실패의 implementation-note 보존
3. **3단 완료선 계약** (배관=단위 테스트 / 행동 변경=질문셋 1회 / 채택=repeat A/B) — 문서에만 있지 않고 지켜졌다
4. **행동 계약의 테스트 승격** (06-10) — 하드코딩 클래스 종결의 실증
5. **기록 위생** — 대체 배너, MANIFEST 리셋 절차, run 출처 인용 규칙(R-12)
6. **product/eval 경계의 코드 강제** — 문서 규칙이 아니라 import 0건·allowlist·테스트로
7. **자립형 worker brief** (07-01 형태) — 검증된 사실·AC·금지 조항·열린 결정 포함
8. **fail-closed eval 규율** — malformed judge 출력을 pass로 계산하지 않음, calibration 게이트

## 관찰 (문제로 확정하지 않은 것)

- **닫을 수 없는 AC 유형**: "사람이 읽을 수 있다" 같은 해석 규범 AC와 skill의 AC 1-3 상한 초과가 반복됐다. 다만 README가 항목을 "판단 질문"으로 규정한 철학의 산물이라 결함 단정을 보류하고 관찰로 남긴다.
- **다중 에이전트 취합 부담**: 병렬 리뷰 산출의 취합·어휘 번역이 사용자에게 되돌아온 장면 2개 세션 — 표본이 작아 확정하지 않는다.
- **Claude/Codex pair 대칭**: 정의 차이 4건이 잔존했으나, 실질 제약은 기계 강제(sandbox)로 등가였고 auditor 계약 범위 문제로 분리된다.
