## 이 문서의 역할

이 문서는 TripProof 제품의 성공·실패를 평가하거나 과거 하네스의 결함만 나열하기 위한 문서가 아니다.

목적은 TripProof를 AI와 함께 개발한 실제 기록을 이용해 다음을 밝히는 것이다.

1. 이 프로젝트에서 사용자가 직접 소유한 판단과 행동은 무엇이었는가.
2. 그 행동은 어떤 AI-native 역량을 증명하는가.
3. 이미 있는 역량이 어느 국면에서 끊겼는가.
4. 현재 이력서와 포트폴리오에서 어디까지 주장할 수 있는가.
5. 다음에는 무엇을 바꾸고 어떤 결과를 측정해야 더 강한 역량 증거가 되는가.

기존 [analysis.md](analysis.md)는 사실 대조와 반박 검증을 거친 문제 판정서로서 유지한다. 이 문서는 그 판단을 사용자의 역량, 이력서 증거, 다음 개선으로 연결해 이해하기 위한 해석본이다.

## 먼저 알아둘 말

- **spec**: 제품 동작, 작업 범위, 예외, 완료 조건을 사람과 AI가 함께 판정할 수 있게 적은 작업 계약이다.
- **AC**: Acceptance Criteria. 작업이 완료됐다고 받을 수 있는 구체적인 조건이다.
- **eval run**: 구현 결과가 질문셋이나 판정 기준에서 실제로 어떻게 동작했는지 측정한 한 번의 실행과 그 산출물이다.
- **하네스**: AI가 이 프로젝트에서 어떻게 읽고, 구현하고, 검증하고, 보고할지를 정한 root 지침, skill, reviewer, 테스트, 기록 체계의 묶음이다.
- **dirty worktree**: 아직 커밋하지 않은 코드 변경이 남아 있는 Git 상태다. 이 상태에서 만든 eval 결과는 나중에 정확히 같은 코드를 다시 꺼내기 어렵다.
- **재진입**: 며칠 또는 몇 주 뒤 새 세션에서 프로젝트의 목적, 현재 단계, 다음 행동을 다시 복원하는 일이다.

## 결론

TripProof는 AI-native 역량이 없어서 실패한 사례가 아니다.

이 프로젝트에서는 다음 역량이 실제 기록으로 확인된다.

- 제품 동작을 slice, spec, AC로 나눠 AI가 실행 가능한 작업으로 만드는 능력
- 구현과 측정을 연결하고 A/B 결과로 변경을 채택하거나 되돌리는 능력
- 실패, no-op, AC 미성립을 성공으로 포장하지 않는 검증 책임
- 반복되는 작업 규칙을 테스트, skill, reviewer, 기록 체계로 만드는 능력
- 모델과 도구의 한계를 실측하고 다음 선택을 바꾸는 능력

그러나 이 역량을 여러 주와 여러 세션에 걸쳐 운영하는 과정에서는 다음 공백이 반복됐다.

- 현재 spec은 잘 관리했지만 닫힌 spec의 이후 지위와 변경 전파는 관리하지 못했다.
- eval은 실제 판단에 사용했지만 근거의 장기 보존과 동일 코드 재현은 약했다.
- AI의 작업 중 완료 주장을 검수하는 일이 별도 절차가 아니라 사용자의 추궁에 남았다.
- 하네스 장치는 대부분 사용됐지만 운영비, 소비 시점, 폐기 기준을 관리하지 못했다.
- AI가 만든 개념과 사용자의 현재 이해를 다음 세션에서도 복원할 지속 상태가 없었다.
- 내부 서버·eval 품질에 집중하는 동안 화면과 실제 사용자 장면이 장기간 작업 배분에서 사라졌다.

따라서 현재 가장 정확한 평가는 다음과 같다.

> 사용자는 TripProof에서 AI가 결과를 만들 수 있는 작업 계약과 측정 체계를 설계하고, 그 결과를 채택·거절하며, 반복 방식을 하네스로 만드는 역량을 보여 줬다. 다음 숙련 과제는 그 체계를 장기간 운영하면서 AI의 주장, 증거의 재현성, 오래된 계약, 현재 작업 상태, 사용자의 이해, 장치의 운영비를 함께 관리하는 것이다.

이번 회고는 이 공백을 증거로 구체화하고 개선안을 파일 초안으로 만든 단계다. 개선안을 실제 TripProof에 적용해 효과를 측정한 단계는 아니다.

## 이 분석이 나오기 전의 맥락

### 1. 채용 시장에서 정의한 다섯 AI-native 역량

선행 분석은 2026-07-26에 수집한 원티드 Product Engineer 공고 54개를 바탕으로 AI-native 역량을 다음 다섯 가지로 정리했다.

1. **AI가 실행할 수 있는 작업으로 바꾸기**

   모호한 요청을 목표, 범위, 제약, 인터페이스, 예외, 완료 조건으로 바꾸고 사람이 판단할 일과 AI에 맡길 일을 나눈다.

2. **AI를 개발 흐름에 배치하고 조율하기**

   AI를 단발성 코드 생성기로 쓰지 않고 조사, 설계, 구현, 테스트, 문서화, 배포, 운영 중 필요한 위치에 배치하고 단계 사이의 결과와 맥락을 연결한다.

3. **AI 생성 결과를 검증하고 최종 결과를 책임지기**

   AI의 완료 보고를 신뢰 전제로 받지 않고 코드, 테스트, 보안, 성능, 상태 경계, 변경 영향, 운영 가능성을 기준으로 승인·수정·거절한다.

4. **반복 실행을 재사용 가능한 워크플로우로 만들기**

   같은 교정을 대화마다 반복하지 않고 컨텍스트, 스크립트, 하네스, 자동 평가, 개발 환경으로 바꿔 다음 실행에서도 사용할 수 있게 한다.

5. **도구의 강점·한계·효과를 판단하기**

   도구명이나 사용량이 아니라 어떤 작업에서 무엇이 잘됐고 실패했는지, 품질·속도·반복 횟수·운영 부담이 실제로 어떻게 달라졌는지를 보고 다음 방식을 바꾼다.

일반적인 문제 정의, 제품 우선순위, 아키텍처 판단을 모두 AI-native라고 부르지는 않는다. 그 판단이 AI에게 줄 작업, 컨텍스트, 승인 기준, 위임 경계를 실제로 바꾼 지점부터 AI-native 역량의 증거로 본다.

### 2. AX·Cofathon에서 먼저 확인된 개인 역량

시장 분류를 개인 사례에 바로 끼워 맞추기 전에 AX와 Cofathon의 실제 대화, commit, diff, test, runtime을 먼저 묶었다. 여기서는 다음 네 행동이 반복된다고 판정했다.

- AI가 아직 열린 판단을 너무 빨리 확정하면 다시 연다.
- AI가 일할 실행 구조와 역할을 만들고 실제 실패에 맞춰 고친다.
- AI의 완료 보고를 그대로 받지 않고 전체 완료선을 기준으로 인수·거절한다.
- AI가 많이 만든 결과보다 실제 제품 가치를 우선해 보존·폐기 범위를 정한다.

동시에 다음 네 가지 실제 역량 공백도 발견했다.

1. 사후 복구를 더 작은 선행 계약으로 압축해야 한다.
2. 컨텍스트 운영비를 줄이고 stale 상태를 관리해야 한다.
3. AI reviewer의 독립성과 판정 안정성을 높여야 한다.
4. production과 frontend 실행 범위를 확장해야 한다.

그리고 역량과 별개로 이력서 증거의 공백도 있었다.

- 최종 코드만 보면 사용자가 정한 문제·범위·완료 기준과 AI 산출물이 분리돼 보이지 않는다.
- 코드를 왜 그렇게 설계했고 어떤 실패 입력 때문에 어떤 테스트가 필요한지 사용자가 직접 설명하는 공개 증거가 약하다.
- 하네스를 재사용했다는 계보는 있지만 시간, 교정 횟수, 결함, 운영비가 실제로 좋아졌다는 비교값이 없다.
- 실제 사용자, production 배포·운영, 동료 채택과 handoff는 문서 표현으로 채울 수 없는 외부 결과다.

### 3. TripProof 분석의 위치

TripProof는 위 강점과 공백을 세 번째 프로젝트에서 다시 확인하는 사례다.

이 회고가 답해야 했던 질문은 다음과 같다.

- AX·Cofathon에서 확인된 작업 방식이 TripProof에서도 반복되는가.
- 반복된다면 추상적인 인상 대신 어떤 spec, commit, run, 대화 장면으로 확인되는가.
- 기존 강점은 더 강한 증거를 얻었는가.
- 기존 공백은 다시 나타났는가. 나타났다면 어떤 작동 구조 때문에 생겼는가.
- 어느 사건을 짧은 이력서·포트폴리오 사례로 만들 수 있는가.
- 다음 프로젝트에서는 무엇을 새로 실행하고 측정해야 하는가.

따라서 TripProof 회고의 11개 문제는 프로젝트 결함 목록으로 끝나는 것이 아니라, **개인 역량의 확인된 범위와 다음 성숙 구간을 구체화하는 재료**다.

## TripProof에서 실제로 운영한 AI-assisted 개발 방식

TripProof의 제품 목적은 여행 자료를 넣으면 원문 근거가 붙은 답을 받고, 확인한 값만 카드로 남기는 것이다. 근거가 없으면 값을 만들어 답하지 않는 것이 중요한 제품 계약이었다.

이 프로젝트에서 AI는 단순 코드 생성기로만 사용되지 않았다.

- 제품 행동을 여러 spec 묶음과 slice로 나눴다.
- 각 slice에 계약 문장, AC, 구현 범위, 측정 결과를 남겼다.
- 구현 뒤 질문셋과 eval run으로 행동 변화를 측정했다.
- A/B 결과로 기본값을 정하고 효과 없는 변경은 revert했다.
- worker와 reviewer를 나눠 구현과 검토를 수행했다.
- 반복 실패를 제품행동 테스트와 하네스 규칙으로 옮겼다.
- decision, work-log, implementation note, spec 갱신부를 이용해 판단을 다음 실행에 남기려 했다.

사용자가 소유한 부분은 AI가 생성한 코드의 모든 문자를 직접 썼다는 뜻이 아니다. 현재 근거가 보여 주는 사용자 책임은 다음에 가깝다.

- 해결해야 할 제품 문제와 지켜야 할 계약을 정했다.
- AI에게 맡길 작업 범위와 완료 조건을 만들거나 교정했다.
- 결과를 채택·거절할 eval과 테스트 기준을 정했다.
- no-op, 실패, 불성립을 성공으로 바꾸지 않았다.
- 제품 가치와 맞지 않는 방향, 범위 이탈, 불충분한 완료를 다시 열었다.
- 반복 문제를 다음 실행에서도 사용할 체계로 바꾸려 했다.

## 먼저 확인된 강점

개선 문제를 읽기 전에 다음 사실을 먼저 고정해야 한다.

### spec-driven이라 결과가 나오지 않은 것은 아니다

- 7개 spec 묶음의 계약 문장 약 480건을 코드와 대조했을 때 일치가 압도적이었다.
- 정직성·행동 계약은 사실상 전 묶음에서 유지됐다.
- 불일치는 주로 저장소 방식, RPC, payload, 열거 문장처럼 뒤 구현에서 낡은 인프라 서술에 집중됐다.

이것은 사용자가 제품 동작을 AI가 실행하고 사람이 판정할 수 있는 계약으로 바꾸는 능력이 실제 구현에 연결됐음을 보여 준다.

### eval은 장식이 아니라 실제 의사결정 장치였다

- spec이 인용한 eval 수치와 경로 26건 중 24건이 보존 사본의 실물과 일치했다.
- A/B 결과가 기본값 선택에 사용됐다.
- 효과 없는 변경은 no-op으로 기록하고 revert했다.
- AC가 성립하지 않거나 실험이 실패한 경우도 그대로 남겼다.

이것은 AI가 만든 결과를 수용하기 전에 측정하고, 근거가 없으면 채택하지 않는 검증 행동을 보여 준다.

### 반복 방식을 실제 하네스로 만들었다

- 하네스 장치 20개 중 19개에서 사용 흔적이 확인됐다.
- 3단 완료선, product/eval 코드 경계, fail-closed eval, worker brief는 문서에만 있지 않고 실제로 사용됐다.
- 하드코딩으로 수렴하는 행동 문제를 제품행동 테스트로 옮긴 뒤에는 검토한 이력에서 같은 오류 유형의 재발이 확인되지 않았다.

따라서 “하네스를 만들기만 하고 쓰지 않았다”는 해석도 맞지 않는다.

| AI가 실행할 작업 만들기 | slice 계약, AC, 실측을 연결하고 활성 spec을 구현과 함께 갱신했다 | 닫힌 spec이 역사 기록인지 살아 있는 계약인지 정하지 않았고, 화면 축의 장기 미배정이 보이지 않았다 | 현재 작업의 계약 설계는 강함. 계약의 장기 수명과 우선순위 상태 운영은 보완 필요 |
| AI를 개발 흐름에 배치하기 | spec → 구현 → 측정, worker → review 흐름을 운영했다 | 세션 재진입 운반체가 없고, 사용자 이해와 현재 개념이 다음 세션에 전달되지 않았다 | 한 slice와 한 세션 안의 조율은 강함. 여러 세션과 시간축을 잇는 조율은 보완 필요 |
| AI 결과 검증·인수하기 | A/B, no-op 기록, revert, fail-closed eval이 실제 판정을 움직였다 | 완료 근거가 로컬 단일 사본에 의존했고, 다수 run이 dirty였으며, 대화 중 완료 주장은 사용자 추궁이 검사했다 | 로컬 계약·eval 기준의 인수·거절은 강함. 재현 가능한 증거와 production 책임은 미완성 |
| 반복 방식을 시스템화하기 | skill, reviewer, 테스트, 기록 체계를 만들고 대부분 실제 사용했다 | 문서와 장치가 계속 늘었고, 소비 시점·운영비·폐기 기준을 관리하지 못했다 | 시스템을 만들고 사용한 증거는 강함. 시스템의 비용·수명·효과 관리가 다음 단계 |
| 도구 효과 판단하기 | 모델 한계와 무효 변경을 실측하고 선택을 바꾸거나 되돌렸다 | 하네스 자체의 속도·품질·교정 감소 효과와 reviewer 독립성을 측정하지 않았다 | 개별 모델·변경 효과는 실측 확인. 하네스 자체의 정량 효과와 외부 판정 안정성은 미확인 |

## 11개 문제를 역량 관점으로 다시 읽기

원 [analysis.md](analysis.md)의 `수정` 판정은 문제가 해결됐다는 뜻이 아니다. 최초 문제 주장이 반박 검토에서 과장·사실 오류·원인 귀속을 지적받아 수정됐고, 아래 카드는 그 수정 내용을 반영한 판정이라는 뜻이다. 카드의 `심각도`도 개인 역량의 결함 정도나 이력서 위험도가 아니라 새 하네스 설계에 주는 영향 크기다.

### 1. 계약의 수명과 제품 축의 가시성 — 문제 1·2

#### 실제로 있었던 일

활성 slice spec은 구현과 실측에 맞춰 같은 커밋에서 갱신됐다. 그러나 뒤 구현이 과거의 닫힌 spec을 무효화해도 과거 spec은 active 위치에 남았다. 과거 정리 작업에서 닫힌 spec을 실제로 정정한 관행은 있었지만, 이를 다음 계약 변경에서도 재현시키는 담당과 장치가 없었다.

더 근본적으로 닫힌 spec이 다음 중 무엇인지 결정하지 않았다.

- 당시 상태를 보존하는 동결 기록
- 이후 코드와 계속 일치해야 하는 살아 있는 계약

화면과 사용자 장면에서도 비슷한 일이 있었다. 서버 내부의 품질·측정 우선순위는 계속 재판단했지만, client 작업은 7주간 진행되지 않았고 spec이 명명한 화면 흐름도 구현되지 않았다. 이 축이 장기간 작업을 받지 못했다는 사실은 decision, roadmap, work-log에서 현재 상태로 드러나지 않았다.

#### 역량 해석

이것은 spec을 못 썼거나 우선순위 판단이 틀렸다는 뜻이 아니다.

- 현재 작업을 계약하고 구현·측정하는 능력은 확인됐다.
- 실제 제품 실패를 보고 서버 품질을 우선한 판단도 방어 가능하다.
- 공백은 그 판단으로 인해 무엇이 낡았고 어떤 제품 축이 오래 멈췄는지를 지속해서 보이게 하는 데 있었다.

따라서 다음 숙련 과제는 계약을 더 자세히 쓰는 것이 아니라:

- 닫힌 계약의 지위를 정하고
- 계약 변경이 이전 계약에 미치는 영향을 같은 작업에서 확인하며
- 장기간 slice를 받지 못한 사용자·화면 축을 현재 상태에 표시하는 것

이다.

#### 제안된 개선

- `docs/now.md` 한 곳에 목적, 현재 단계, 마지막 실측, 다음 행동, 화면 마지막 작업 시점을 둔다.
- slice를 열거나 닫거나 방향을 바꾸는 커밋에서 같은 커밋으로 갱신한다.
- 계약을 바꾸는 변경은 일반 구현과 분리하고, 이전 계약에 미치는 영향을 확인한다.
- 닫힌 spec은 `동결 + 무효 표시` 또는 `살아 있는 계약 + 전파 의무` 중 한 정책을 선택한다.

현재 [proposed-harness/](proposed-harness/)에는 `now.md` 초안은 있지만 spec의 수명 정책 자체는 적용 범위 밖이다. 따라서 문제 1은 아직 해결된 것으로 말할 수 없다.

### 2. 완료 근거와 인수 책임 — 문제 3·4·5

#### 공식 완료 기록과 작업 중 AI 주장을 구분해야 한다

기존 문서는 다음 두 사실을 가까이 두지 않아 모순처럼 보인다.

1. 공식 spec과 eval에 보존된 완료 근거는 대체로 정확했다. 26건 중 24건이 실물과 일치했다.
2. 작업 중 대화에서 AI가 한 수행·완료 주장은 별도 검수 장치가 없어 사용자가 되물은 뒤에야 간극이 드러난 장면이 반복됐다.

첫 번째는 보존된 최종 기록의 정직성이다. 두 번째는 작업 중 AI의 주장을 인수하는 절차다. 평가 대상이 다르다.

#### 재현성 공백

- spec이 AC 근거로 인용한 run은 gitignore 영역에 있었고 수동 사본 한 곳이 유일한 재접근 경로였다.
- 코드 상태가 남은 run artifact 89건 중 73건, 약 82%가 dirty worktree에서 실행됐다.
- 전형적인 순서는 `spec 커밋 → 미커밋 구현으로 eval → 통과 후 구현 커밋`이었다.

A/B 양쪽이 같은 코드에서 실행됐다면 비교 자체의 타당성은 유지될 수 있다. 문제는 판정을 만든 정확한 코드 상태를 나중에 동일하게 꺼낼 수 없다는 것이다.

#### 역량 해석

- 결과를 측정하고 채택·거절하는 능력은 강하게 확인됐다.
- 실패와 dirty 상태를 숨기지 않고 남긴 기록 태도도 강점이다.
- 다음 단계는 실험 결과, commit, 테스트 출력을 결속해 다른 사람이 다시 확인할 수 있게 만드는 것이다.
- AI의 완료 주장을 사용자가 매번 심문하는 대신, 주장과 실물을 대조하는 반복 가능한 인수 절차가 필요하다.

#### 제안된 개선

- 완료 보고에 실행 명령, 출력 수치 원문, run 또는 commit 근거, 테스트 변경, 하지 않은 범위를 함께 적는다.
- `claim-verifier`가 완료 주장과 run·commit·test 실물을 대조한다.
- 채택·기본값 변경에 쓰는 eval은 committed clean 상태에서만 실행한다.
- run 경로뿐 아니라 `code_version.commit_hash`를 함께 인용한다.
- 테스트 출력도 나중에 다시 읽을 수 있는 artifact로 남긴다.

이 개선은 파일 초안까지 만들어졌지만 TripProof에 적용·운영되지 않았다. 따라서 재현성이나 검증 부담이 실제로 개선됐다고 말할 수는 없다.

### 3. 하네스 자체의 운영비와 장치 수명 — 문제 6·7·8

#### 실제로 있었던 일

- 9.5주 동안 기록·하네스 파일을 건드린 커밋이 전체의 약 41%였다.
- 이 비율은 작업량이 41%였다는 뜻이 아니다. 제품 코드 산출 라인은 기록보다 훨씬 많았다. 이 수치는 작업의 주의가 하네스 쪽으로 자주 전환됐음을 보여 준다.
- 무거움을 줄이려는 결정이 다섯 차례 있었지만 문제를 발견할 때마다 문서를 더하는 기본 구조는 바뀌지 않았다.
- work-log와 flat decision의 역할이 root spec 갱신부로 사실상 이동했지만, 이관 사실과 새 소비 규칙은 정해지지 않았다.
- reviewer 하나는 수집된 로그에서 실행 흔적이 확인되지 않았지만 2개월간 정의가 유지·수정됐다. 다만 로그 채널의 사각 때문에 실행 0회를 절대 사실로 단정할 수는 없다.

#### 역량 해석

장치 대부분에 사용 흔적이 있었으므로 재사용 시스템을 만들고 실제 작업에 붙이는 능력은 확인된다. 메타 결정 문서도 후속 판단과 포트폴리오 재료로 재사용됐다.

다음 공백은 장치 생성 이후의 운영이다.

- 이 장치가 실제 시간을 줄였는가.
- 같은 사용자 교정을 줄였는가.
- 누가 언제 이 문서를 읽는가.
- 실제 사용되지 않는 agent를 언제 폐기하는가.
- 하네스를 유지하는 비용이 제품 개발보다 커지고 있는가.

즉 “하네스를 만들 수 있는가”에서 “하네스의 효과·비용·수명을 관리할 수 있는가”로 숙련 질문이 이동했다.

#### 제안된 개선

- 실행 게이트를 소수로 제한하고 추가하려면 기존 하나를 폐기하거나 승인받는다.
- 자동 로드 문서와 전체 줄 수에 상한을 둔다.
- 새 문서에는 읽는 사람과 읽는 시점을 함께 적는다.
- agent·skill 신설 때 첫 실행 확인 시점과 일정 기간 실행 0건일 때의 폐기 기준을 함께 둔다.
- 실행되지는 않지만 본문 원칙이 소비되는 agent는 실행형 정의를 제거하고 기준 문서로 옮긴다.
- 하네스의 시간·교정·운영비는 상시 기록을 늘리기보다 한 번의 표적 샘플링으로 측정한다.

### 4. AI 행동, 사용자 이해, 세션 연속성 — 문제 9·10·11

#### 테스트로 옮긴 행동과 문장으로만 남긴 행동의 차이

하드코딩으로 수렴하는 제품 행동 문제는 메타모픽, substring grounding, anti-keyword 테스트로 옮긴 뒤 검토한 이력에서 재발이 확인되지 않았다.

반면 다음 AI 작업 행동은 prose 규칙을 추가해도 반복됐다.

- 보여 달라고 했는데 수정까지 진행함
- 문서의 숫자와 구조를 작업 큐로 오해함
- 완료하지 않은 일을 완료로 요약함

차이는 문서냐 코드냐가 아니다. 테스트는 위반이 일어나는 실행 순간에 작동했다. 일반 규칙 문장은 해당 행동 순간에 반드시 읽히거나 검사된다는 보장이 없었다.

#### 인지부채의 정확한 원인

설명을 잘하지 못한 것만이 원인은 아니다. 설명 형식을 바꾼 뒤 사용자가 실제로 이해가 좋아졌다고 확인한 장면도 있다.

남은 공백은 두 가지였다.

1. AI가 새 용어, 범주, 판정 규칙을 만들 때 승인·명명 검토·개수 제한이 없었다.
2. 사용자가 이해한 현재 개념과 제품 흐름을 다음 세션에서도 복원할 지속 표면이 없었다.

그래서 개념이 사용자의 멘탈 모델보다 빠르게 쌓인 뒤 설명으로 갚았고, 며칠 또는 몇 주 뒤에는 같은 내용을 다시 복원해야 했다.

#### 재진입 공백

2.5주 공백 뒤 사용자는 현재 spec 단계와 diff의 정체를 다시 물어야 했다. 별도 세션에서는 프로젝트를 만든 원래 목적을 이전 대화에서 다시 찾아야 했다. compaction 요약과 전사 복붙이 세션 사이 맥락 전달을 대신했다. decisions와 work-log는 존재했지만 다음 세션이 자동으로 읽는 재진입 운반체로 설계되지 않았다.

Git 이력 재작성으로 대화와 리뷰가 인용한 commit hash 최소 9개가 어느 ref에서도 도달할 수 없게 된 문제도 있었다. 이 문제는 현재 새 하네스 초안에 직접적인 해결책이 없다.

#### 역량 해석

- 반복 오류를 적절한 실행 검사로 바꾸는 능력은 일부 성공했다.
- 후기 worker brief는 이전 대화 없이도 착수할 수 있도록 검증된 사실, AC, 금지 조항을 담는 형태로 성숙했다.
- 다음 단계는 실패 유형에 따라 테스트, 실행 게이트, 사람 승인 중 적절한 수단을 고르는 것이다.
- 사람과 AI가 모두 현재 목적, 단계, 개념, 열린 결정을 세션 밖에서 복원할 수 있어야 한다.

#### 제안된 개선

- 세션 시작에 `docs/now.md`를 자동 로드한다.
- 같은 파일 안에 현재 목적, 단계, 다음 행동, 열린 결정, 개념 대장을 둔다.
- 새 이름은 기존 이름으로 설명할 수 없는 이유를 먼저 밝히고 승인 후 사용한다.
- 위임은 이전 전사 전체가 아니라 검증된 코드 사실, 배제한 대안, AC, 금지 범위를 담은 brief로 전달한다.
- 재진입 카드와 개념 대장을 별도 문서층으로 늘리지 않고 하나의 현재 상태 표면에 둔다.

## 11개 문제를 관통하는 두 축

[insight-memo.md](insight-memo.md)는 문제 11개에서 반복된 구조를 다음 두 축으로 압축한다. 이 두 축은 여러 문제를 설명하는 설계 판단이지 하네스가 모든 사건의 단독 원인이라는 인과 확정이 아니다.

### 1. 규칙과 검사가 필요한 순간에 작동하지 않았다

성공한 장치와 실패한 장치를 가른 것은 문서냐 코드냐가 아니었다.

- 테스트와 import 경계는 위반 순간 자동으로 작동했다.
- 3단 완료선과 worker brief는 문장이지만 작업을 닫거나 위임하는 순간에 반드시 읽히는 위치에 있었다.
- 완료 주장은 완료를 말하는 순간 검사되지 않았다.
- 닫힌 spec은 뒤 구현이 계약을 바꾸는 순간 확인되지 않았다.
- 새 개념은 처음 도입할 때 검토되지 않고 이해가 어려워진 뒤 설명했다.

따라서 개선은 문서를 모두 코드로 바꾸는 것이 아니다. **규칙이나 검사가 실제 행동이 발생하는 시점에 읽히거나 실행되게 하는 것**이다.

### 2. 시간이 지나며 낡는 상태를 관리하지 않았다

구 하네스는 현재 산출물이 통과인지 판단하는 장치는 많았지만 다음 상태를 여러 주 동안 유효하게 관리하는 장치는 없었다.

- 닫힌 spec의 현재 유효성
- 화면·사용자 장면이 마지막으로 작업을 받은 시점
- eval 근거의 보존·재현 상태
- 실제로 사용되는 기록층과 장치
- 사용자의 현재 이해와 개념
- 다음 세션이 읽을 프로젝트 목적과 단계

이 상태에는 명시적인 소유자, 하나의 현재 표면, 갱신 시점이 필요하다.

## AX·Cofathon에서 찾은 기존 공백은 TripProof에서도 반복됐는가

### 1. 사후 복구를 선행 계약으로 압축하기 — 반복 확인

AI의 범위 이탈과 과장된 완료 주장을 사용자가 발견하고 복구한 장면은 다시 확인됐다. 테스트로 승격한 제품 행동은 재발이 멈췄지만 AI 작업 행동은 문장 규칙만으로 반복됐다. 다만 재발 일부는 `멈춰 묻기보다 진행`하는 자율 우선 실행 모드에서 사용자가 받아들인 비용이므로, 전부를 계약 공백의 결과로 귀속할 수는 없다.

따라서 사용자의 복구 능력은 강점으로 다시 확인됐지만, 같은 교정을 작업 시작·완료·eval 실행 순간의 작은 계약과 검사로 바꾸는 과제도 남았다.

### 2. 컨텍스트 운영비와 stale 상태 — 반복·심화 확인

문서와 장치는 실제 사용됐지만 기록 역할이 소리 없이 옮겨가고, 닫힌 spec과 현재 상태가 낡으며, 재진입 때 사용자가 목적과 단계를 다시 공급했다. 하네스를 줄이려는 결정도 여러 번 반복됐다.

이것은 특정 프로젝트의 우연보다 작업 방식에서 반복되는 공백이라는 강한 신호다.

### 3. reviewer 독립성과 판정 안정성 — 변형되어 반복 확인

문서 표현 reviewer는 있었지만 완료 주장과 기존 계약 정합처럼 더 중요한 층은 담당이 없었다. 실행형으로 정의한 장치의 실제 실행·효과를 점검하는 수명 규칙도 없었다.

또한 이번 회고의 판단과 반박 검증도 같은 Claude 계보에서 수행돼 완전한 독립 검증이라고 할 수 없다.

### 4. production과 frontend 실행 범위 — 반복 확인

서버와 eval 품질은 개선됐지만 client 작업은 장기간 멈췄다. 실제 사용자, 배포, 관측성, 롤백, frontend acceptance는 이번 회고로 새로 생기지 않았다.

따라서 TripProof는 기존 네 가지 개선 이슈가 세 번째 프로젝트에서도 나타났다는 근거를 추가했다.

## 현재 이력서와 포트폴리오에서 말할 수 있는 것

### 이미 방어 가능한 주장

- TripProof에서 spec–implementation–eval 흐름을 운영했다.
- 제품 동작을 slice, 계약, AC로 나눠 AI가 구현 가능한 작업으로 만들었다.
- A/B 결과로 변경을 채택하고 효과 없는 변경은 revert했다.
- 실패와 AC 미성립을 성공으로 바꾸지 않았다.
- 반복 오류 중 테스트로 표현 가능한 제품 행동을 실행 검사로 승격했다.
- worker brief, reviewer, 기록, eval을 실제 사용되는 하네스로 운영했다.
- 장기간의 spec, commit, run, 대화 기록을 다시 대조해 작업 체계의 병목을 구체화했다.

### 분석과 설계까지 완료한 주장

- 완료 주장과 실물 근거가 분리되는 문제를 발견했다.
- dirty eval, stale spec, 세션 재진입, 개념 축적, reviewer 수명 문제를 구체적인 증거로 확인했다.
- 문제를 `필요한 순간의 검사`와 `시간축 상태 관리`라는 두 원리로 압축했다.
- 재진입 카드, 개념 대장, claim-verifier, clean-run 검사, 위임 상한을 실제 파일 초안으로 설계했다.

이 부분은 “구현해 효과를 냈다”가 아니라 “증거를 바탕으로 문제를 진단하고 적용 가능한 초안을 설계했다”고 표현해야 한다.

### 아직 말하면 안 되는 주장

- 새 하네스로 재진입 시간이 줄었다.
- 사용자 교정 횟수가 감소했다.
- 완료 오판을 제거했다.
- dirty 채택 run이 없어졌다.
- 하네스 운영비나 토큰 비용이 감소했다.
- 인지부채를 해결했다.
- frontend와 production 역량을 강화했다.
- 다른 사람이나 팀이 이 하네스를 채택했다.

새 하네스는 [proposed-harness/README.md](proposed-harness/README.md)에 파일 초안으로 존재하지만 TripProof repo에는 적용되지 않았다.

## 이력서 사례로 만드는 방법

최종 코드만 보여 주면 사용자가 무엇을 판단했고 AI가 무엇을 생성했는지 구분하기 어렵다. 전체 대화는 너무 길다. 각 사례는 다음 다섯 조각으로 줄인다.

1. AI가 처음 만든 상태
2. 사용자가 발견한 문제
3. 사용자가 바꾼 작업 범위 또는 승인 기준
4. 그 뒤 실제로 달라진 commit, test, runtime, 제품 방향
5. 아직 검증하지 못한 것

### 사례 후보 1. 문장 규칙을 제품행동 테스트로 바꾼 사건

- **처음 상태**: 근거 계약을 문서로 정했지만 구현이 하드코딩으로 수렴하는 문제가 반복됐다.
- **사용자가 발견한 문제**: 문장 규칙은 코드 작성 순간의 행동을 바꾸지 못했다.
- **바꾼 기준**: 자료가 바뀌면 답도 바뀌는지, 근거가 원문의 실제 부분 문자열인지, 특정 키워드에만 반응하지 않는지를 제품행동 테스트로 만들었다.
- **실제 변화**: 검토한 이후 이력에서 같은 오류 유형의 재발이 확인되지 않았다.
- **남은 한계**: 이번 회고에서는 서버와 LLM을 다시 실행하지 않았으므로 현재 runtime 보장과 production 효과는 주장할 수 없다.

이 사례는 작업 계약 설계, AI 결과 검증, 반복 교정의 시스템화, 도구 한계 판단을 함께 보여 준다.

### 사례 후보 2. eval로 채택·revert하고 나중에 증거 체계를 감사한 사건

- **처음 상태**: 여러 구현 후보와 모델·설정 변경이 있었다.
- **사용자 판단**: 설명이나 구현량이 아니라 A/B와 repeat 결과로 채택 여부를 정했다.
- **실제 변화**: no-op과 실패를 남기고 효과 없는 변경은 revert했다. 보존된 완료 근거 26건 중 24건은 실물과 일치했다.
- **회고에서 발견한 문제**: run 89건 중 73건이 dirty 상태였고, 근거 보존이 로컬 사본 하나에 의존했다.
- **남은 한계**: clean-run과 claim-verifier는 아직 적용 전 초안이다.

이 사례는 강한 검증 행동과 그 검증 체계의 재현성 공백을 함께 정직하게 보여 준다.

### 사례 후보 3. 성장한 하네스를 근거로 감사하고 재설계한 사건

- **처음 상태**: 하네스 장치 대부분이 실제 사용됐지만 문제마다 문서를 추가하는 방식으로 운영 부담이 커졌다.
- **회고에서 확인한 문제**: 하네스 축소 결정을 여러 번 했는데도 장치의 수, 소비 시점, 폐기 기준을 관리하지 못했다.
- **회고에서 종합한 판단**: 하네스의 크기가 아니라 필요한 순간에 실제로 읽히거나 검사되는지와 시간이 지나며 낡는 상태를 관리하는지를 중심 기준으로 바꿨다.
- **실제 산출물**: 재진입 카드, 개념 대장, claim-verifier, clean-run, 위임 상한을 포함한 적용 가능한 파일 초안을 만들었다.
- **남은 한계**: 적용 후 시간·교정·오류 감소 효과는 아직 없다.

이 사례는 재사용 시스템을 만든 경험과 그 시스템의 한계를 증거로 감사한 기록을 함께 보여 준다. 다만 두 축과 새 하네스 구조는 AI 회고가 종합한 판단이므로, 사용자가 이를 검토·채택해 실제 작업 방식을 바꾸기 전에는 사용자의 단독 판단 경험으로 표현하지 않는다. 현재는 개선 성과가 아니라 AI-assisted 진단과 설계 사례다.

## 현재 근거로 가능한 이력서 서술 초안

아래 문장은 완성된 이력서 문구가 아니라 현재 근거가 방어하는 범위를 확인하기 위한 초안이다.

> AI-assisted 여행 검증 제품 TripProof에서 제품 동작을 7개 spec 묶음의 slice·계약·AC로 구조화하고, 구현 뒤 질문셋 A/B 결과로 변경을 채택하거나 revert하는 개발 흐름을 운영했다. 이후 spec·commit·eval artifact·대화 로그를 정적 감사해 완료 인수, dirty run 재현성, 세션 재진입, stale 상태, 하네스 운영비가 다음 병목임을 구체화했다.

> 반복 문제를 문서 규칙으로 추가하는 대신 필요한 행동 순간에 검사가 작동하도록 재진입 카드, claim-verifier, 채택급 clean-run 검사, 위임 상한을 적용 가능한 파일 트리로 설계했다. 이 개선안은 아직 적용 전이므로 생산성·오류 감소 효과는 별도 검증 과제로 남겼다.

이 서술에서 사용자가 소유한 것은 문제, 범위, 승인 기준, 제품 방향, 최종 채택·폐기 결정이다. 구현 코드를 모두 손으로 작성했다거나 production 운영까지 완료했다고 표현하면 현재 근거를 넘어선다.

## 다음 개선에서 새로 만들어야 할 증거

새 하네스의 파일 존재는 개선 효과의 증거가 아니다. 실제로 적용한 뒤 같은 단위로 전후를 비교해야 한다.

| 개선 후보 | 해결하려는 공백 | 적용 뒤 확인할 것 |
| --- | --- | --- |
| `docs/now.md` 재진입 카드 | 목적·현재 단계·다음 행동이 세션 밖에 없음 | 새 세션 첫 답이 현재 단계와 다음 행동을 맞히는지, 사용자가 다시 설명한 횟수 |
| 개념 대장과 새 이름 절차 | 개념이 사용자 이해보다 빠르게 늘어남 | 새 이름 수, 같은 개념의 재설명 라운드, 옛 이름 혼용 재발 |
| 완료 보고 + `claim-verifier` | AI 완료 주장을 사용자가 직접 심문함 | 근거 없는 완료 주장 수, 실물 불일치 수, 확인 불가 수 |
| 채택급 `--require-clean` | dirty run이 최종 채택 근거가 됨 | 채택 근거 run의 dirty 수가 0인지, commit hash로 재접근 가능한지 |
| 위임 상한과 재시도 상한 | 대형 변경과 반복 실험 안에 계약 변화가 묻힘 | 상한 초과 전 분할 횟수, 같은 AC의 재검토 없는 반복 여부 |
| 장치 수명 규칙 | 사용되지 않는 agent·skill이 계속 유지됨 | 첫 실행 확인 여부, 일정 기간 실행 0건 장치의 폐기·강등 결과 |
| 하네스 비용 표적 샘플링 | 시스템이 실제 시간을 줄였는지 모름 | 재진입 시간, 사용자 교정 횟수, 검증 왕복 시간, 하네스 유지 변경 빈도 |
| 화면 축 현재 상태 표시 | 사용자·frontend 작업이 장기간 배분에서 사라짐 | 화면 마지막 작업 시점과 다음 사용자-facing slice 결정 |

이 결과가 생겨야 다음에는 “정교한 하네스를 만들었다”가 아니라 “AI-assisted 개발 운영을 바꿔 재진입 오류와 검증 불확실성을 실제로 줄였다”고 말할 수 있다.

## 이번 회고가 증명하는 범위와 증명하지 않는 범위

### 증명하는 범위

- archived spec과 코드의 정적 대조
- 보존된 run artifact와 spec 인용 수치의 대조
- Git commit 이력과 일부 대화 원문을 결합한 작업 방식 분석
- 문제 후보를 분리하고 반대 증거를 반영해 수정한 문제 카드
- 외부 기준과 대조한 두 가지 설계 원리
- 실제 파일 형태로 만든 새 하네스 초안

### 증명하지 않는 범위

- 테스트, 서버, LLM을 다시 실행한 현재 runtime 정확성
- pytest 수치 전체의 재실행 확인
- 대화 로그 전체에서 AI 행동이 발생한 정확한 비율
- 마찰 없이 잘 끝난 작업까지 균형 있게 포함한 성공률
- 서로 다른 AI 계보나 외부 사람에 의한 완전 독립 검증
- 실제 사용자 문제 검증과 반복 사용
- production 배포, 관측성, 롤백, 보안, 성능 결과
- frontend 구현과 UI acceptance
- 새 하네스 적용 후 생산성, 이해도, 검증 시간, 재현성 개선
- 다른 사람이나 팀의 채택과 handoff 효과

로그 수치에는 중복 record, subagent가 상속한 전사, 부분 문자열 매치 같은 노이즈가 있다. 따라서 단순 키워드 발생 횟수는 인지부채나 마찰의 발생률로 사용하지 않고 직접 확인한 장면을 주장 근거로 사용한다.

판정과 반박 검증은 모두 같은 Claude 계보에서 수행됐다. fresh context와 역할 분리는 내부 교차검사의 질을 높이지만 외부 사람이나 고정된 ground truth와 같은 독립성은 제공하지 않는다.

## 최종 판정

TripProof가 보여 준 핵심은 AI를 많이 사용했다는 사실이 아니다.

사용자는 제품 문제와 책임 기준을 AI에게 넘기지 않고, 그 기준을 AI가 실행할 spec·AC·테스트·eval로 바꿨다. 결과가 기준에 맞지 않으면 no-op과 실패를 남기고 변경을 되돌렸으며, 반복되는 협업 방식을 하네스로 만들었다. 이것은 AI-native Product Engineer 역량의 실질적인 증거다.

동시에 TripProof는 그 역량의 다음 성숙 구간도 보여 줬다. 현재 작업을 잘 닫는 것과 여러 주 뒤에도 계약·증거·현재 상태·사용자 이해가 유효한 것은 다른 문제다. 하네스를 만드는 것과 그 하네스의 비용·수명·효과를 관리하는 것도 다른 문제다. 로컬 eval로 결과를 판정하는 것과 다른 사람이 같은 코드와 근거로 다시 인수할 수 있게 하는 것도 다른 문제다.

따라서 이 프로젝트의 현재 의미는 다음과 같다.

> AI-assisted 개발 작업을 계약·측정·거절·재사용 체계로 운영한 역량은 확인됐다. 그 체계를 장기간 지속 가능하고, 사람이 이해할 수 있으며, 다른 사람이 재검증할 수 있고, 실제 사용자와 production 결과로 이어지게 만드는 것이 다음 개선 과제다.
