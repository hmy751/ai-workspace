# 지속 컨텍스트의 경계와 소유에 대한 전역 기준

## 지속 단위의 경계를 언제 정의하나

이 문서는 하나의 지속 단위로 취급되는 컨텍스트의 정체성·범위·내부 관계와 관리 책임이 어디에 귀속되어야 하는지 판단할 때 참고하는 전역 공유 reference다.

여러 작업이나 세션에서 하나의 의미 있는 지속 단위로 의존하는 경계에 적용한다. 모든 폴더나 문서 묶음에 별도의 경계 정의를 만들거나 특정 파일명·폴더 구조·관리 workflow를 따르라는 기준은 아니다.

## 이 기준이 막으려는 상태

하위 문서들은 각각 잘 나뉘고 설명되어 있지만, 이들을 왜 하나의 지속 컨텍스트로 묶어 사용하는지, 전체 범위가 어디까지인지, 하위 영역이 서로 어떤 관계인지는 어느 한 곳에서도 정의되지 않을 수 있다.

이 경우 새 사람이나 AI는 여러 문서와 도구 지침을 읽고 전체 구조를 다시 추론해야 한다. 내용은 정리되어 있어도, 그 내용을 묶는 단위에는 경계 정의의 정본이 없는 상태다.

## 진입점에서 경계와 관리 책임을 찾을 수 있게 한다

지속 컨텍스트가 하나의 단위로 취급된다면, 그 단위가 무엇이며 어디까지를 포함하고 바로 아래 구성요소들이 어떤 관계인지 설명하는 **경계 정의의 정본(canonical)**을 일반적인 진입점에서 찾을 수 있어야 한다.

여기서 canonical은 자료가 충돌할 때 무엇을 기준으로 삼는지를 나타내는 권위 속성이다. 정본은 그 기준이 되는 문서나 정보원이며, 별도 구성요소를 뜻하지 않는다.

여기서 일반적인 진입점은 사람이나 AI가 해당 단위를 이해하기 위해 통상 먼저 읽도록 지정된 위치를 뜻한다. 사람과 AI의 시작점이 다르더라도 같은 경계 정의로 이어져야 한다.

하나의 지속 컨텍스트 경계에서는 다음 관계가 함께 식별되어야 한다.

- **경계 정의**: 이 단위의 정체성, 범위, 바로 아래 구성요소의 관계
- **실제 내용**: 이 경계 안에서 지속해서 유효하게 유지하려는 정보
- **관리 규칙**: 어떤 조건에서 내용을 유효하다고 보고 언제·어떤 기준으로 변경하는지 정하는 기준
- **책임 Owner**: 경계와 내용, 관리 규칙의 유효성에 책임이 귀속되는 사람이나 역할

각 역할은 서로 다른 위치에 있을 수 있다. 일반적인 진입점에서 그 관계와 각 정의의 정본, 책임자를 찾을 수 있어야 한다. 경계 정의, 실제 내용, 관리 규칙이 서로 다른 정본을 가질 수 있으며, 최근에 수정됐거나 `current`, `latest`, `final`이라는 이름을 가졌다는 이유만으로 정본이 되지는 않는다.

상위 경계는 자신의 정체성·범위와 바로 아래 구성요소들의 관계를 정의하고, 하위 경계는 자기 내부의 상세 의미와 구성을 정의한다. 상위가 모든 하위 정의를 복제하거나 하위가 상위 전체를 다시 정의하지 않는다. 같은 책임을 여러 곳에 중복해서 정의해 무엇이 기준인지 모호하게 만들지 않는다.

책임자가 상위 경계에서 명확하게 이어진다면 하위마다 반복하지 않고 책임이 달라지는 지점만 드러낸다.

실제 읽기·갱신·검증을 수행하는 AI, skill, hook, script는 관리 장치다. 갱신을 수행한다는 사실만으로 정의와 내용의 유효성에 책임지는 주체가 되지는 않는다.

## 실제 파일 형태를 사용한 구조 예시

아래 `README.md`, `current/index.md`, `memory/`, `state/`는 원칙을 설명하기 위한 한 가지 구현 예시다. 이 이름이나 배치를 전역 표준으로 요구하지 않는다.

경계 정의가 있는 구조:

```text
workspace/
├─ README.md
├─ current/
│  ├─ index.md
│  ├─ memory/
│  │  ├─ index.md
│  │  └─ ...
│  └─ state/
│     ├─ index.md
│     └─ ...
└─ records/
   ├─ index.md
   └─ ...
```

이 구조에서 경계 정의의 정본은 다음 범위로 나뉜다.

- `workspace/README.md`: Workspace가 무엇인지와 바로 아래 `current`·`records`의 관계를 정의한다.
- `current/index.md`: `current`가 무엇인지와 바로 아래 `memory`·`state`의 관계를 정의한다.
- `memory/index.md`: `memory`에 어떤 내용을 두고 내부 내용을 어떻게 해석하는지 정의한다.
- `state/index.md`: `state`에 어떤 내용을 두고 내부 내용을 어떻게 해석하는지 정의한다.
- `records/index.md`: `records`에 어떤 내용을 두고 내부 내용을 어떻게 해석하는지 정의한다.

`current/index.md`는 `memory`와 `state`의 상세 정의를 복제하지 않는다. 두 하위 영역이 `current` 안에서 맡는 역할과 관계만 정의하고, 상세 내용은 각 하위 index로 연결한다.

예를 들어 `current/index.md`의 실제 내용은 다음 정도일 수 있다.

```markdown
# Current

이 디렉터리는 다음 작업이 이어받을 현재 유효 컨텍스트를 묶는다.

- `memory/`: 작업 위치가 달라져도 계속 유효한 판단
- `state/`: 지금 이어갈 작업의 현재 상태

각 영역의 상세 의미는 해당 `index.md`에서 정의한다.
실행 기록은 이 경계에 포함하지 않으며, `current`와 `records`의 관계는 Workspace 진입 문서에서 정의한다.
이 경계의 유지 규칙과 책임 Owner는 [Workspace context contract](../README.md#context-contract)에서 찾는다.
```

이 예시에서 중요한 것은 파일 이름이 아니라 상위가 하위의 역할과 연결을 설명하고, 상세 정의는 하위가 소유한다는 점이다. 다른 위치의 문서가 같은 경계 정의의 정본이고 일반적인 진입점에서 바로 찾을 수 있다면 다른 형태도 가능하다.

경계 정의가 불명확한 구조:

```text
workspace/
├─ current/
│  ├─ memory/
│  │  └─ index.md   # memory 자체만 설명
│  └─ state/
│     └─ index.md   # state 자체만 설명
└─ records/
```

`memory`와 `state`는 각각 설명되어 있지만, `current` 자체의 정체성·범위·두 하위 영역의 관계가 상위 지침, AI prompt, 관리 도구에 나뉘어 있다면 새 독자는 여러 자료를 읽고 전체 구조를 다시 조립해야 한다.

## 처음 보는 사람으로 확인하기

해당 단위의 일반적인 진입점에서 시작한 사람이 다음 질문에 답할 수 있어야 한다.

- 이 단위는 무엇을 위해 존재하는가?
- 무엇을 포함하고 무엇을 포함하지 않는가?
- 바로 아래 구성요소들은 어떤 역할과 관계를 가지는가?
- 각 책임의 canonical과 책임 Owner는 어디에서 찾는가?

답하려면 관리 도구 내부나 관련 없는 여러 상위 지침을 찾아야 한다면 경계 정의와 책임 관계가 충분히 드러난 것이 아니다.
