# v0 검토와 확인 범위

2026-09-08 [논의 결정](01-discussion-decisions.md)을 반영한 [v0 준비본](v0/README.md)을 작성하고 확인했다. 아래 실제 변경·형식 검사·의미 검토는 최초 작성의 기록이며, 이후 정의·Ticket 구성 합의의 반영과 검사는 [후속 갱신](#후속-합의의-v0-반영)에 구별해 남겼다. 준비본 작성은 완료했으며 실제 적용 프로젝트 선택·설치·공동 사용은 남아 있다.

## 실제 변경

기존 08 단일 문서를 `01-discussion-decisions.md`로 옮겼다. 상대 링크를 새 위치에 맞추고, 논의 당시의 미수정 상태와 이후 v0 작성 요청을 구별하는 안내를 더했다. 주변 연구·Workspace 안내와 산출물 지도도 새 위치에 연결했다. Workspace current의 문서 이동에 따른 링크도 바로잡았으며, 진행 판단의 자동 갱신은 기존 Maintain 운영에 맡겼다.

기존 [06 공동 준비본](../06-judgment-and-understanding-application/v0/README.md)을 복사해 네 `SKILL.md`에 합의한 연결을 반영했다. 네 호출 설정과 공통 기준·색인은 그대로 보존했다. Spec·Ticket 양식이나 Harness 코드, 기존 준비본, 전역 스킬·상위 지침은 변경하지 않았다. 별도 AI-native moment는 저장하지 않았다.

## 파일과 형식 검사

- `skill-creator/scripts/quick_validate.py`를 네 스킬 각각에 실행했고 모두 `Skill is valid!`로 통과했다. 기본 Python에 PyYAML이 없어 `/private/tmp/skills-spec-ticket-validation-20260908`의 격리 환경에 PyYAML 6.0.3을 설치해 실행했다. 프로젝트·전역 Python 환경은 변경하지 않았다.
- [manifest](v0/manifest.json)의 일반 파일 열 개를 실제 payload와 대조했다. 네 스킬 본문이 변경됐고 나머지 일반 파일 여섯 개는 입력과 같으며, 각 입력은 `08fd27146b540a0b2ab73ce0d661b64a997355be`의 내용과 일치한다.
- 네 스킬의 frontmatter와 `agents/openai.yaml`은 기존 준비본과 동일하다. Claude·Codex의 상대 symlink 여덟 개가 동일 `.agents` 원본으로 해석되고, 공통 기준 링크와 소비자 관계를 유지한다.
- 이동한 논의 문서·새 묶음·갱신한 안내의 로컬 링크, 파일 끝·공백, `git diff --check`를 확인했다. 삭제한 기존 08 단일 파일 경로를 남은 안내가 참조하지 않도록 수정했다.

형식·해시·링크 검사는 패키지의 구성과 참조를 확인한다. 스킬의 판단 품질이나 실제 host 호출·문서 반영을 검증하는 테스트로 해석하지 않는다.

## 의미 검토

Main이 네 스킬의 원본 대비 차이를 읽고 논의 결정과 대조했다. 두 설명 스킬의 편집은 별도 실행자가 맡았고 Main이 결과를 확인해 채택했다. 이와 독립된 읽기 전용 검토에서는 사용자 작성 요청, 논의 결정과 정정 발췌, 기존·수정 payload, 공통 기준·호출 설정, Reference의 Spec·Ticket·Maintain·lifecycle 원문을 제공했다. Main의 결론이나 예상 결함은 주지 않았다.

독립 검토는 “실질적인 수정 필요 발견은 없다”고 보고했다. 적극적인 Spec 구체화, 구현 누락과 가정 실패의 구별, 필요한 범위의 설명, Main 최종 응답과 Maintain 입력·실제 문서 준비의 구별이 연결돼 있다고 판단했다. Main은 직접 확인한 diff와 상위 원문 범위에서 이 결론을 채택했다.

검토자는 다음 요청을 읽은 지침에 따라 짧게 추론했다. 실제 스킬을 host에서 호출하거나 Workspace를 갱신한 실행은 아니다.

- `$work-discussion … 대표 사례와 완료 기준을 같이 정리해줘`: 필요한 사례·기준을 구체화하고 실행을 봐야 아는 점은 가정으로 남긴다. 같은 대화의 Ticket 분해와 실제 파일 반영 완료를 구별한다.
- `Ticket은 완료라는데 원래 목표였던 실제 모델 판단이 없잖아. 다시 판단해줘`: Spec·담당 Ticket·실제 결과를 대조해 구현 누락이면 목표를 유지하고 맡을 일을 보완한다. 검토만 요청받았다면 반영안까지 반환한다.
- `아까 완료됐다는 게 무슨 뜻이야?`: 앞선 발화와 필요한 완료 범위에서 시작하고, 과장된 말이면 정정한다. 설명을 전체 재계획이나 파일 수정으로 확대하지 않는다.

책임 배치와 제거 가능성도 검토했다. 스킬은 판단과 전달 관계를 안내하고, 지속 작업 정의·운영 계약과 Maintain의 허용 경로는 기존 소유 위치에 남는다. 스킬을 제거해도 Spec·Ticket과 상위 운영 계약이 사라지지 않는다. 묶음 README에서 논의·실제 파일·검사 근거와 다음 적용 판단을 찾을 수 있다. 새 실행 장치·독점 작성 권한·판단 장부는 추가하지 않았다.

## 후속 합의의 v0 반영

최초 v0 뒤에 [Spec·Ticket 정의와 범위](03-spec-ticket-definition-and-scope.md), [Ticket 네 구성과 이유](04-ticket-components-and-rationale.md)를 채택했다. 사용자는 갱신 결과를 비교할 수 있도록 순서를 명시했다.

> 잠깐 커밋부터하고 갱신해 갱신 결과 좀 보게

이에 합의 문서와 최초 v0, 관련 연구·Workspace 안내를 `7fa7bde`에 먼저 커밋했다. 다음 변경은 그 뒤 작업 트리에 작성했다. 이 비교 기준은 최초 입력인 06 준비본의 `08fd271`과 구별한다.

- `work-discussion`: Work당 Spec 하나와 기능·코드 개선을 포괄하는 정의를 반영했다. Ticket의 결과·확인 가능성·핵심 수행의 지연 여부로 범위를 판단하고, 네 기본 구성에 실행 맥락·설계 이유·완료 조건·실제 결과를 구체화하도록 안내했다. 정확한 제목·순서·필드를 강제하지 않고, 유용한 내용을 적극적으로 다루는 기존 기준을 유지했다.
- `reconsider-work`: Ticket 안에서 입력을 잠정적으로 신뢰하며 설계를 발전시키는 관계를 명시했다. 모든 하위 작업이나 Ticket 완료를 자동 재판단 계기로 삼지 않는다. 기존의 “요구·설계·가정의 변화는 Spec에”라는 문구를 공통 판단은 Spec에, 이번 실행 안의 설계·선택 이유·결과는 Ticket에 연결하도록 고쳤다.
- `work-artifact-briefing`: Ticket의 확인 계획과 실제 결과를 구별하고, 코드 개선의 동작 보존과 구조 개선의 근거를 각각 설명하도록 보완했다.
- `explanation-recovery`: 과거 발화 우선, 현재 문서와 원래 뜻의 구별, 실제 완료 범위의 확인이 이미 있어 본문을 유지했다. 네 스킬의 frontmatter·호출 설정, 공통 기준과 상대 symlink도 유지했다.

묶음·v0 안내와 두 합의 문서에서 당시 미반영 상태와 이후 갱신을 구별했다. manifest에는 두 후속 합의 문서와 비교 기준 커밋을 연결하고 결과 해시를 갱신했다. Context Harness의 상위 운영 계약은 수정하지 않았다. 적용 시 Maintain도 같은 정의·구성을 이어받도록 대상 상위 기준을 맞춰야 한다는 전제를 v0 안내에 남겼다.

Main은 바뀐 세 스킬의 diff를 두 합의 문서와 대조했다. API 자체가 전달 결과인 경우, 코드 개선의 동작 보존과 구조 개선, Ticket 내부의 설계 선택과 공통 전제 변경을 지침이 구별하는지 확인했다. 새 독립 리뷰나 실제 host 호출을 수행한 결과는 아니며, 앞선 독립 검토를 이번 갱신의 실행 검증으로 확대하지 않는다.

갱신 후 네 스킬 모두 `quick_validate.py`를 통과했다. manifest의 일반 파일 열 개·원본 커밋·해시, frontmatter와 호출 설정, 상대 symlink 여덟 개를 다시 확인했다. 06 입력 대비 변경 본문은 여전히 네 개이며, 이번 비교 기준 `7fa7bde` 대비 변경 본문은 세 개다. 로컬 링크와 공백, `git diff --check`도 확인했다. 이 검사는 실제 스킬 사용이나 Maintain의 문서 갱신 품질을 입증하지 않는다.

## 남은 확인

실제 적용 대상의 root 지침과 경로, 기존 동명 스킬·공통 기준과의 병합, Maintain의 입력·갱신 계약 호환은 설치 대상이 정해진 뒤 확인한다. 실제 host의 스킬 발견·호출, 서브 결과가 Main의 응답을 통해 전달되는 흐름, 비동기 문서 갱신과 문서 의존 실행, 작업 결과·사용자 이해의 개선은 아직 관찰하지 않았다.

Spec·Ticket과 Maintain 계약의 대조 기준은 context-harness 구현 `dcd3c6fa957102894bc6e4629923bc90fca5aefc`와 확인 checkout `9505bf31521ec40e09a9608c815566f2d89e3dc1`이다. 원자료 접근점은 [v0 운영 전제](v0/README.md#운영-전제와-적용-지점)에 있다. 이번에 제품·Harness 테스트를 실행하지 않았으며, 기존 Reference 검증 기록의 Verify timeout 실패를 해결된 것으로 바꾸지 않는다.
