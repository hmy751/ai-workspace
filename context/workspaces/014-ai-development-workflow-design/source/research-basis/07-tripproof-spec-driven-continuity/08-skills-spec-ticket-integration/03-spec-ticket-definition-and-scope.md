# Spec·Ticket 정의와 범위 확정

2026-09-08, [Workspace 012](../../../../workspaces/012-skills-spec-ticket-integration/README.md)에서 Spec·Ticket의 정의와 범위에 관한 후속 논의를 마무리했다. [앞선 스킬 연결 합의](01-discussion-decisions.md)를 유지하면서, 기능 구현과 코드 개선 등 작업 성격이 달라도 사용할 수 있도록 두 개념의 역할과 Ticket 범위 판단을 구체화했다.

**기존 Spec 다섯 구성요소와 Spec·Ticket 구조를 유지한다. Spec은 Work의 결과와 공통 판단 기준을 정의하고, Ticket은 그 기준 아래에서 확인 가능한 결과를 만드는 실행 단위를 맡는다.** 크기나 사용자 행동 여부만으로 둘을 구별하지 않는다.

후속 논의에서 사용자는 **Work당 Spec 하나**라는 기존 선택을 재확인했다. 이어 제3 리뷰를 거쳐 [Ticket 구성요소와 구성 이유](04-ticket-components-and-rationale.md)를 채택했다. 이 문서는 정의와 범위를, 후속 문서는 Ticket의 네 기본 구성과 그 근거를 소유한다.

이 문서는 이번에 채택한 의미와 이유를 보존하는 연구 산출물이다. 실제 운영 계약은 Context Harness의 [Spec·Ticket 기준](../../../../../context-harness/reference-project/context/work/workspaces/SPEC-AND-TICKETS.md)이 소유한다. 합의 기록 당시에는 상위 계약이나 v0 본문을 수정하지 않았다. 이후 사용자 요청으로 합의 문서와 최초 v0를 `7fa7bde`에 보존하고 [v0](v0/README.md)에 필요한 스킬 안내를 반영했다. 상위 계약 수정과 설치는 아직이다.

## Spec의 정의와 범위

> 하나의 Work에서 해결할 문제와 이루려는 결과, 그 결과를 판단할 기준을 정의한다. 실행들이 함께 지켜야 할 의미·계약·제약과 현재 설계·가정을 담는다.

기능 구현 Work에서는 요구 동작과 사용자에게 전달할 결과를 다룬다. 코드 개선 Work에서는 현재 구조의 문제, 보존할 동작, 개선하려는 책임 배치와 품질 기준을 다룬다. 내부의 세부 구현까지 전부 미리 결정할 필요는 없으며, 실행 중 판단할 부분과 이미 함께 지켜야 할 선택을 구별한다.

[기존 Spec 구성요소와 이유](../../../../../context-harness/context/workspaces/010-spec-ticket-workspace-design/output/spec-components-and-rationale.md)의 다섯 구성을 유지한다. 각 항목을 작업 이해와 정의를 깊게 하는 관점으로 적극적으로 구체화하되, 무관한 내용이나 근거 없는 결정을 억지로 채우지 않는 앞선 합의도 유지한다.

## Ticket의 정의와 범위

> Spec의 목표와 기준 안에서, 확인 가능한 결과를 만들도록 범위를 묶은 실행 단위다. 맡은 범위와 완료 조건, 필요한 입력·의존 관계, 진행과 실제 결과를 함께 남긴다.

Ticket은 기능 구현뿐 아니라 코드 개선이나 결함 수정도 맡을 수 있다. 결과의 의미는 해당 작업의 성격에 맞게 정한다. 다음은 범위를 설명하는 예시이며 실제 작업을 생성하거나 특정 분해를 승인한 것은 아니다.

- 기능 구현: 대표 조건 하나를 실제로 판정하고 그 결과를 보여 주는 동작을 만든다.
- 코드 개선: 흩어진 판정 규칙을 한 책임으로 모으고, 기존 동작의 보존과 변경 부담의 감소를 확인한다.
- 결함 수정: 특정 실패 원인을 해결하고, 해당 상황에서 정상 동작함을 확인한다.

Ticket 안에서는 필요한 여러 세부 작업을 이어서 수행할 수 있다. 이를 위해 API task 같은 별도의 관리 계층을 추가하지 않는다. 모든 구현 순서나 파일 변경을 각각 Ticket으로 만들지도 않는다.

### 범위를 나눌 때의 판단

1. **무엇을 끝내서 넘기는지 분명한가?** 관련 코드를 작업한다는 활동만 적기보다, 이번 실행으로 달라질 동작이나 구조를 드러낸다.
2. **그 범위의 결과를 확인할 수 있는가?** 전체 Work를 완성하기 전에도 이번 Ticket이 어디까지 이뤘는지 근거로 판단할 수 있어야 한다. 필요한 선행 작업과 의존 관계는 함께 남긴다.
3. **나누는 방식 때문에 핵심 수행이 계속 뒤로 밀리지 않는가?** 기능 작업에서는 필요한 계층을 연결하는 좁은 동작을 우선한다. 구조 개선에서는 변경 후에도 동작을 보존하며 개선 효과를 확인할 수 있는 범위를 잡는다.

이 기준은 모든 Ticket의 크기나 모양을 같게 만드는 규칙이 아니다. API 자체가 전달할 결과라면 그 계약과 완료 근거로 범위를 판단할 수 있다. 기반 작업을 따로 맡긴 경우에는 그 완료가 의미하는 범위와 실제 수행을 이어 갈 후속 작업을 드러낸다. 기반 완료를 전체 기능의 완료로 확대하지 않는다.

## 실행과 설계 개선의 관계

Ticket 내부에서는 정한 입력을 잠정적으로 신뢰하며 구현과 세부 설계를 계속 발전시킨다. 하위 작업을 할 때마다 상위 판단을 처음부터 다시 여는 절차를 두지 않는다.

실행 중 공통 요구·계약이나 현재 설계의 전제를 흔드는 근거가 나오면 관련 Spec과 그 판단에 의존하는 작업·결과를 다시 본다. 구현이 요구를 따르지 않은 문제와, 요구대로 구현해도 의도한 결과를 얻지 못하는 문제를 구별한다. Ticket 완료를 자동 재판단 발동점으로 정하지 않는다.

Spec은 코드 개선의 목표와 기준을 담고, Ticket은 그 범위의 개선을 실제로 수행하고 결과를 남길 수 있다. 문서를 만들거나 기능 사례를 통과한 사실만으로 구조적 품질까지 입증되지는 않는다. 실제 작업에서는 구현 중 설계를 다듬는 책임과 결과를 받을 때 요구 충족·구조의 적절성을 확인하는 책임이 이어져야 한다. 구체적인 실행자와 검토 배치는 해당 작업에서 정한다.

## 기존 Spec을 유지하는 이유와 Matt 비교의 의미

사용자가 제시한 [구성 이유](../../../../../context-harness/context/workspaces/010-spec-ticket-workspace-design/output/spec-components-and-rationale.md)와 [여행 상품 답변 예시](../../../../../context-harness/context/workspaces/010-spec-ticket-workspace-design/output/spec-example-travel-answer.md)를 Matt의 같은 고정 판본과 비교했다. Matt의 Spec도 문제·해결·범위, 사용자 요구, 구현 결정과 테스트 결정을 담는다. 우리 Spec의 대표 사례와 코드 품질 기준을 Matt 양식에 담거나, Matt의 모듈·테스트 설계를 우리 구성에 담을 수 있다. 두 양식이 다룰 수 있는 작업 종류가 본질적으로 갈린다고 보지 않는다.

우리 구성은 기존 연구에서 겪었던 문제를 더 명시한다. 기반 구현을 전체 완료로 받아들이지 않기, 현재 설계를 고정 제약으로 착각하지 않기, 기능이 동작해도 책임·중복·다음 변경의 부담을 확인하기가 그 내용이다. 이를 다음 실행자가 찾을 수 있게 두는 데 이유가 있으므로 현재 구성을 유지한다. Matt와 차별화하기 위해 새로 설계하거나 문서만으로 어느 쪽의 운영 효과가 우월하다고 결론내리지 않는다.

Matt의 구현 Ticket은 필요한 계층을 통과하는 좁은 완성 동작을 기본으로 삼는다. 그 분해 감각은 핵심 수행이 계속 미뤄지는 문제를 줄이는 데 참고하되, 이번 Ticket의 보편 정의를 사용자 기능 하나로 한정하지 않는다. Spec 양식의 유사성만으로 Ticket의 크기와 분해 방식이 결정되는 것도 아니다.

## 채택 근거와 이번 마무리 범위

사용자는 비교 설명 뒤 다음과 같이 판단의 어려움을 말했다.

> 내가 느끼기엔 얼추 비슷해서 뭐 딱잘라서 판단을 못하겠네 넌 어때?

Main은 두 구성이 본질적으로 비슷하며 현재 Spec을 유지해도 충분하다고 판단했다. 기능 구현과 코드 개선을 모두 담을 수 있고, Ticket도 그 목표 아래에서 확인 가능한 결과를 만드는 실행 단위로 둘 수 있다고 설명했다. 이어 사용자가 다음과 같이 논의 종료를 결정했다.

> 그래 이정도로 결정하자 아까 spec, ticket 정의처럼 해서 논의를 마무리 하자

따라서 앞서 제안한 두 정의와 범위 판단, 현재 Spec 구성의 유지로 이번 논의를 마무리한다. [기존 스킬 연결 결정](01-discussion-decisions.md)의 Main·Maintain 역할과 결과 전달 관계는 이어진다.

스킬 준비본의 후속 반영은 [검토 기록](02-review-and-validation.md#후속-합의의-v0-반영)에 남겼다. 상위 계약 반영, 실제 적용 프로젝트·설치, 작업별 Ticket 분해·실행·검토 배치는 남아 있다. Ticket의 기본 구성은 후속 문서에서 채택했으며, 기계적으로 고정한 세부 필드·상태 체계나 모든 Ticket의 서브 위임·새 세션 실행을 정한 것은 아니다. Work당 Spec 하나라는 선택을 별도의 미정 항목으로 다시 열지 않는다. 준비본의 실제 공동 사용, Ticket 관리의 실익과 설계 품질 개선 효과도 아직 확인하지 않았다.
