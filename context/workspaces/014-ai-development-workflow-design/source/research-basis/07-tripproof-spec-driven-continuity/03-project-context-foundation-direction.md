# Project context foundation 방향

## 문서의 지위

이 문서는 [`01-problem-analysis.md`](01-problem-analysis.md)가 남긴 Project context의 보존 기간·읽히는 조건·현재 권위 문제와, [`02-workspace-based-continuity-direction.md`](02-workspace-based-continuity-direction.md)가 Project context로 넘긴 후속 책임을 구체화한다.

여기서 정하는 것은 다음 두 가지다.

- 여러 Workspace가 함께 참조할 Project context의 최소 책임 구조
- Workspace에서 발견된 Project-wide 변화를 기존 Project 정본 위치에 반영하는 project-local skill의 책임 경계

이 문서는 실제 디렉터리와 skill 구현을 완료한 결과가 아니다. 이후 구현에서 지켜야 할 채택 방향과 판별 기준이며, 실제 파일 배치·Recover 연결·skill 설치와 대표 사례 검토는 후속 작업으로 남아 있다.

## 이번 설계가 이어받는 문제

07의 중심 문제는 정보를 많이 보존하지 못한 것이 아니다. 장기간 이어진 spec이 작업 목표와 구현 순서는 잘 넘겼지만, 당시 판단의 이유와 불확실성, 다시 열어야 할 신호까지 다음 작업에 전달하지 못한 것이다. 이전 결론과 기존 구조는 재검토할 선택보다 이미 확정된 전제로 작용했다.

따라서 지속 컨텍스트는 모든 정보를 한곳에 모으거나 모든 새 session에 넣는 방식으로 만들 수 없다. 각 정보에서 다음 세 판단을 분리해야 한다.

1. **보존 기간**: 얼마나 오래 유지하는가
2. **읽히는 조건**: 어떤 작업에서 현재 입력으로 선택하는가
3. **현재 권위**: 지금 무엇을 판단하거나 지시할 수 있는가

오래 보존되는 정보가 항상 읽혀야 하는 것은 아니다. Project context 안에 있다는 사실도 그 내용을 자동으로 채택된 제품 규칙으로 만들지 않는다. 오래 유지할 판단, 현재값으로 교체할 상태, 한 작업 안에서만 실행을 지휘하는 내용은 서로 다른 방식으로 관리되어야 한다.

[`02-workspace-based-continuity-direction.md`](02-workspace-based-continuity-direction.md)는 이 가운데 현재 작업의 재진입과 실행 맥락을 Workspace가 맡도록 정했다. 이번 문서는 Workspace를 다시 설계하지 않고, 여러 Workspace에 걸쳐 지속되는 Project context가 무엇을 맡아야 하는지를 다룬다.

## Context Harness 원형과 이번 분석의 관계

`~/Desktop/context-harness`의 원형은 Project context와 Workspace의 큰 경계를 제공한다.

- Project context는 여러 Workspace가 함께 사용하는 공통 맥락이다.
- Workspace는 현재 작업 하나를 복구하고 이어가기 위한 제한된 실행 경계다.
- Recover는 Project 문서 전체가 아니라 현재 Workspace가 선택한 문서만 읽는다.
- 관리 장치는 Project 의미와 사람의 acceptance를 소유하지 않는다.

이번 분석은 이 큰 경계를 대체하지 않는다. Project context 안에서 실제 정보의 수명과 읽기 조건, 권위가 다시 한 층으로 섞이지 않도록 더 세밀한 책임 profile을 추가한다.

`~/Desktop/10_work/tripproof/context/project/`의 현재 구성과 기존 자료는 이 책임 profile이 실제 제품·architecture·작업 기준을 구분할 수 있는지 확인하는 사례로 사용했다. 현재 TripProof의 Project 문서가 완성되었거나 실제 운영 효과가 증명됐다는 전제는 두지 않는다.

## 중심 판단: 세 축은 층이 아니고, 책임 profile을 도출하는 기준이다

보존 기간·읽히는 조건·현재 권위는 디렉터리 이름이나 최종 층 개수가 아니다. 모든 지속 정보에 적용하는 판단축이다.

TripProof의 실제 정보 종류를 이 세 축으로 대조하면 Project 안에서 반복되는 세 책임 profile이 보인다.

1. Project 공통 맥락
2. Project 현재 상태
3. Project 조건부 지침

Workspace의 실행 맥락은 이 세 책임과 나란히 Project 안에 넣는 제4층이 아니다. 이미 별도로 채택된 현재 작업 경계다. 이번 설계가 추가하는 것은 **Project 내부의 세 책임 구분**이다.

이 책임들은 실제 내용을 분류하고 읽기·갱신 규칙을 정하기 위한 개념이다. 그대로 세 디렉터리로 만들 필요는 없다. 한 문서 안의 서로 다른 section이나 주장에 다른 책임 profile이 적용될 수도 있다.

## Project context의 정체성과 최소 경계

Project context는 여러 Workspace에서 계속 유효한 현재 Project 맥락과 그 맥락을 찾고 관리하는 관계를 제공한다. 다음 관련 작업은 제품 목적과 사용자 문제, 핵심 domain 의미, 현재 상태와 관련된 반복 판단 기준을 다시 추측하지 않고 현재 답과 판단 근거의 위치를 복원할 수 있어야 한다. 여기서 복원 가능하다는 것은 필요한 경로와 권위가 드러난다는 뜻이지, 모든 Project 문서를 매 작업에 자동으로 읽거나 주입한다는 뜻이 아니다.

Project context의 일반 진입점에서는 최소한 다음을 찾을 수 있어야 한다.

- 이 경계가 무엇을 위해 존재하는가
- 무엇을 직접 소유하고 무엇을 기존 상세 정본으로 연결하는가
- 바로 아래 Project 책임들이 어떤 관계를 가지는가
- 각 내용의 정본 위치와 유효성 책임 주체는 어디인가
- 어떤 작업에서 어떤 문서를 선택해 읽는가
- 내용을 변경할 때 적용할 관리 규칙은 어디에 있는가
- project-local skill이 맡는 실행과 맡지 않는 판단은 무엇인가
- 다음 관련 작업이 제품 의미와 판단 근거를 다시 추측하지 않으려면 어떤 현재 내용과 열린 지점을 어디서 찾아야 하는가

일반 진입점은 전체 Project 내용을 다시 적는 통합 문서가 아니다. 경계와 관계를 설명하고 실제 내용과 상세 근거로 연결한다. 하위 내용을 복제하지 않으며, 현재값이나 상세 사실을 여러 곳에서 독립된 기준처럼 유지하지 않는다.

## 세 Project 책임

### Project 공통 맥락

Project 공통 맥락은 제품과 domain에 관해 여러 Workspace가 공유해야 하는 의미를 맡는다.

대표 내용은 다음과 같다.

- 제품이 해결하려는 문제와 목적
- 핵심 domain 개념과 관계
- 여러 작업에서 지켜야 하는 제품 제약
- 공통 제품 요구와 품질 판단의 상위 기준

이 책임의 중심 질문은 다음과 같다.

> 여러 Workspace가 달라도 제품과 domain에 관해 계속 참이어야 하는가?

공통 맥락은 비교적 오래 유지되지만 불변이라는 뜻은 아니다. 제품 판단이 바뀌면 현재 내용으로 수정할 수 있다. 또한 공통 맥락에 속한다고 모든 상세 문서를 매 session에 넣지 않는다. 짧은 overview는 기본 접근점이 될 수 있고, 상세 PRD나 domain model은 관련 작업에서만 선택할 수 있다.

문서가 Project context 아래에 있다는 사실만으로 내용이 채택된 요구가 되지는 않는다. 논의용 초안이라면 그 권위가 드러나야 하며, 제품 목적·domain 의미·중요한 제약의 새로운 결정, 현재 의미의 변경, 서로 충돌하는 근거 사이의 선택은 사람의 판단 없이 관리 장치가 확정하지 않는다.

반대로 현재 권위가 확인되었거나 사용자가 명시적으로 허용한 기존 의미를 출처에 추적 가능하게 옮기고, 새 의미를 더하지 않으며, 해결하지 않은 충돌도 없는 재구성은 새로운 제품 결정을 내리는 일이 아니다. 선택한 책임 범위에서 다음 판단에 필요한 근거가 있는데도 불확실하다는 이유만으로 조용히 빼서는 안 된다. 현재 답, 역사 근거, 열린 판단 중 어느 역할인지 권위와 수명에 맞게 드러낸다. 관련 없는 역사를 생략하거나 상세 정본을 링크로 연결하는 것은 누락이 아니다.

현재 TripProof 사례에서는 `overview.md`, `domain-model.md`, `prd.md`의 일부 내용이 이 책임에 해당할 수 있다. 각 파일 전체가 같은 권위나 같은 수명을 가진다는 뜻은 아니다.

### Project 현재 상태

Project 현재 상태는 지금 구현과 구조가 어떤 상태인지, 다음 작업이 어떤 현실에서 시작해야 하는지를 맡는다.

대표 내용은 다음과 같다.

- 현재 architecture와 책임 경계
- 현재 알려진 구조적 문제와 위험
- 열린 질문과 최근 설계 방향
- 임시 호환 구조와 기술 부채
- 현재 제품 축별 진행 상태

이 책임의 중심 질문은 다음과 같다.

> 장기 원칙이 아니라, 다음 관련 작업이 알아야 할 현재 Project 상태인가?

현재 상태는 변경 이력을 계속 덧붙이는 방식보다 현재값으로 교체한다. 과거 판단 이유가 중요하면 현재 상태 본문에 모두 누적하지 않고 필요한 근거 위치로 연결한다.

현재 상태 문서는 상세 구현의 복제본이 아니다. architecture 요약과 실제 코드·테스트가 충돌하면 상세 사실을 소유하는 위치를 먼저 확인한다. 충돌을 발견한 관리 장치는 오래된 요약을 조용히 계속 제공해서는 안 되며, 근거가 명확하면 요약을 갱신하고 모호하거나 영향이 크면 사람의 판단을 요청해야 한다.

현재 TripProof의 `architecture.md`는 이 책임의 출발점이 될 수 있다. 코드와 테스트가 소유하는 상세 사실까지 `architecture.md`에 복제하라는 뜻은 아니다.

### Project 조건부 지침

Project 조건부 지침은 특정 종류의 작업에서 반복해서 사용하는 판단·검증·진행 기준을 맡는다.

대표 내용은 다음과 같다.

- engineering 판단 기준
- testing 전략과 적용 조건
- product behavior 평가 기준
- 반복 가능한 review나 workflow의 운용 감각
- 특정 실패를 막기 위해 채택한 Project-wide 작업 규칙

이 책임의 중심 질문은 다음과 같다.

> 여러 작업에서 재사용할 기준이지만, 관련 작업에서만 읽고 적용해야 하는가?

조건부 지침은 오래 유지될 수 있지만 항상 주입되는 공통 규칙이 아니다. 각 지침에서는 최소한 다음을 알 수 있어야 한다.

- 어떤 작업과 신호에서 읽는가
- 어떤 상황에서는 적용하지 않는가
- 어떤 실패를 막기 위해 존재하는가
- 어떤 전제가 사라지면 완화하거나 제거할 수 있는가
- 현재 제품·architecture의 다른 정본과 어떤 관계인가

한 작업에서 사용한 방법이 유용해 보인다는 이유만으로 곧바로 Project 지침이 되지는 않는다. 여러 작업에 적용할 의미와 필요성이 확인되고, 필요한 권위로 채택된 경우에만 이 책임에 둔다.

현재 TripProof에는 이 책임을 전담하는 정본 위치와 유효성 책임 주체가 아직 명확하지 않다. 미래 workflow taxonomy나 빈 디렉터리를 미리 만들지 않고, 실제로 채택할 지침이 생길 때 기존 책임 관계를 확인한 뒤 필요한 최소 경계를 만든다.

## 책임 profile과 실제 파일 구조의 관계

세 책임은 파일 형식이나 디렉터리 taxonomy가 아니다.

- 하나의 PRD에는 장기 제품 요구와 아직 합의되지 않은 열린 항목이 함께 있을 수 있다.
- 하나의 architecture 문서에는 현재 구현 상태와 특정 변경에서 지켜야 할 해석 기준이 함께 있을 수 있다.
- 하나의 Project 변화가 현재 architecture 갱신과 조건부 지침 보강을 함께 요구할 수 있다.

따라서 파일 이름만으로 분류하지 않고, 실제 주장과 section이 어떤 역할을 하는지 판별한다. 하나의 변화가 여러 책임에 영향을 주면 하나의 분류값으로 억지로 줄이지 않고, 영향받는 주장을 나누어 각각의 실제 정본 위치를 찾는다.

현재 Context Harness와 TripProof의 `context/project/` 구성을 출발점으로 사용할 수 있지만, 이 분석만으로 `common/`, `current/`, `guidance/` 디렉터리를 새로 만들지는 않는다.

초기 구조에서는 다음 정도로 충분하다.

```text
context/project/
├── README.md
├── 기존 제품·domain·architecture 문서
└── decisions/
```

`README.md`는 세 책임의 관계와 각 내용의 정본 위치·유효성 책임 주체를 routing한다. 기존 문서는 자기 계약에 따라 내용을 소유한다. 조건부 지침은 실제로 지속할 내용이 생길 때만 필요한 정본과 책임 경계를 만든다.

## 정본, 책임 주체와 관리 장치

글로벌 `ai-system_context-ownership-boundary.md`는 canonical을 별도 구성요소가 아니라, 자료가 충돌할 때 무엇을 기준으로 판단할지를 나타내는 권위 속성으로 정의한다. 또한 실제 내용과 관리 규칙, 책임 주체, 관리 장치는 서로 다른 역할일 수 있다고 구분한다.

이번 문서에서는 혼동을 줄이기 위해 다음 표현을 구분한다.

- **정본 위치**: 특정 정의나 사실이 충돌할 때 기준으로 삼는 문서·코드·정보원
- **책임 주체**: 그 정의와 내용이 계속 유효하도록 판단하고 유지할 사람이나 역할
- **관리 장치**: 정해진 계약에 따라 읽기·후보 식별·갱신·검토를 보조하는 skill이나 도구

Project context의 일반 진입점은 정본 위치와 책임 주체, 관리 규칙으로 이어지는 경로를 제공한다. 같은 의미의 두 번째 정본을 만들지 않는다.

Project-local skill이 문서를 실제로 수정하더라도 그것만으로 정본이나 책임 주체가 되지 않는다. 이 구분은 skill의 책임이 Project context보다 커지는 것을 막는 핵심 기준이다.

## Decision의 위치와 역할

Decision은 Project 내부 `decisions/`에 둘 수 있다. 그러나 세 Project 책임에 추가되는 별도 층으로 보지 않고, 현재 답의 정본으로도 기본 설정하지 않는다.

현재 유효한 답은 해당 내용을 직접 소유하는 제품·domain·architecture·지침 문서에 둔다. Decision은 중요한 선택의 맥락을 보존한다.

Decision이 맡는 내용은 다음과 같다.

- 당시 무엇을 선택했는가
- 왜 그 선택을 했는가
- 어떤 대안을 검토했는가
- 무엇이 불확실했는가
- 어떤 신호가 나타나면 다시 검토해야 하는가
- 현재 답을 확인할 Project 정본 위치는 어디인가
- 이전 판단을 대체했다면 어떤 관계인가

Decision은 현재 답을 독립적으로 복제하거나 실제 내용의 정본과 경쟁하지 않는다. 현재 답이 바뀌면 해당 내용의 정본이 먼저 현재 상태를 표현하고, 관련 decision에는 필요할 때 대체 관계나 재검토 결과를 남긴다.

모든 변경에 decision을 만들지 않는다. 다음 중 하나 이상이 성립할 때만 별도 기록을 검토한다.

- 의미 있는 대안 사이의 선택이었다.
- 이유를 잃으면 다음 작업이 같은 논쟁을 반복할 가능성이 크다.
- 여러 Project 책임이나 후속 작업에 영향을 준다.
- 특정 신호가 나타나면 다시 판단해야 한다.
- 현재 결과만 보고는 선택 근거를 복원하기 어렵다.

Context Harness Reference의 timeout decision은 decision 자체를 canonical 상위 맥락으로 사용하는 사례다. 이번 foundation은 그 배치를 Project 전체의 기본 규칙으로 일반화하지 않는다. 현재 답과 이유 보존의 책임을 단순하게 유지하기 위해, 현재 답은 실제 내용 문서가, 선택 이유와 재검토 맥락은 decision이 맡는 방향을 채택한다.

## Workspace와의 관계

Workspace는 현재 목표를 위해 무엇을 해야 하고 무엇을 완료로 볼지를 맡는다. Project context는 여러 Workspace에 걸쳐 유효한 의미·현재 상태·조건부 기준을 맡는다.

Workspace에서 만들어진 spec, AC, plan, 조사 메모나 작업별 테스트는 해당 작업 안에서 강한 실행 권위를 가질 수 있다. 그러나 작업이 바뀐 뒤에도 자동으로 Project를 지휘하지 않는다. 그 안에서 발견한 내용 중 여러 Workspace에 계속 유효한 현재 판단만 적절한 Project 정본 위치에 반영할 후보가 된다.

Project context 반영은 Workspace 종료 때의 일괄 승격 단계가 아니다. 작업 중 변화가 명확해진 자연스러운 경계에서 수행할 수 있다. 종료는 누락 가능성을 확인하는 한 시점일 뿐이다.

Project context가 바뀌어도 다른 Workspace를 역으로 갱신하지 않는다. 현재 Workspace가 새 Project 문서를 계속 필요로 할 때만 자기 bounded Recover 선택을 바꾼다.

## Bounded Recover와 읽기 조건

Recover의 목표는 모든 Project 지식을 넣는 것이 아니라, 현재 작업이 필요한 지식과 그 밖의 지식으로 내려갈 접근점을 제공하는 것이다.

기본 방향은 다음과 같다.

- Project의 일반 진입점과 최소 공통 맥락만 기본 후보로 둔다.
- 각 Workspace가 필요한 Project 문서를 이유와 함께 명시적으로 선택한다.
- 제품 요구 작업은 관련 공통 맥락을 선택한다.
- architecture 작업은 현재 상태를 선택한다.
- 특정 testing·evaluation 작업은 적용 조건에 맞는 지침만 선택한다.
- 선택하지 않은 자료도 Project 진입점에서 정본 위치와 유효성 책임 주체를 찾을 수 있어야 한다.

공통 맥락에 속한다는 사실과 기본 주입 대상이라는 판단을 동일시하지 않는다. 조건부 지침이 많아져도 모든 Workspace의 기본 입력으로 누적하지 않는다.

## Project-local skill의 축소된 책임

### 중심 원칙

Project-local skill은 Project context를 설계하고 정책을 소유하는 상위 주체가 아니다.

> Project context 계약이 무엇을 지속할지, 어떤 책임으로 해석할지, 누가 현재 답을 소유하는지, 언제 사람 판단이 필요한지를 정한다. Skill은 이 계약을 읽고 현재 작업의 근거에 적용하여 제한된 반영을 보조한다.

이 관계가 뒤집히면 Project context의 의미가 skill prompt 안에만 존재하게 된다. 다른 사람이나 AI는 skill을 읽어야 Project 구조를 이해하게 되고, skill을 교체하거나 제거하면 지속 책임도 함께 사라진다. 글로벌 `ai-system_harness-rippability.md`가 막으려는 상태다.

### Project context 계약이 소유할 것

Project의 일반 진입점에서 이어지는 계약이 다음 기준을 소유한다.

- Project context의 정체성과 범위
- 공통 맥락·현재 상태·조건부 지침의 의미
- 정보의 보존 기간·읽기 조건·현재 권위를 판별하는 질문
- 각 내용의 실제 정본 위치와 책임 주체를 찾는 방법
- 상세 source와 Project 요약이 충돌할 때의 우선순위
- 초안과 채택된 판단을 구분하는 권위 규칙
- 사람의 결정을 받아야 하는 고권위 변경 경계
- 다음 관련 작업이 제품 의미와 판단 근거를 재추론하지 않게 하는 내용 충분성·누락 표시 기준
- 별도 decision을 남길 조건
- Recover에서 Project 문서를 선택하는 원칙

이 기준은 skill 안에만 정의하지 않는다. Skill 문서는 같은 의미를 다시 소유하지 않고 Project 계약을 참조한다.

### Skill이 소유할 것

Skill은 교체 가능한 실행 인터페이스와 절차만 맡는다.

- 언제 명시적으로 호출할 수 있는지
- 현재 Workspace와 관련 근거를 어떻게 제한해서 읽는지
- Project 계약의 판별 질문을 어떤 순서로 적용하는지
- 후보 변화와 근거, 예상 반영 위치·책임 주체를 사람에게 어떻게 보여 주는지
- 계약상 명확하고 허용된 변경을 어떻게 반영하는지
- 명시된 재구성 범위에서 근거가 있는 의미의 누락과 열린 판단을 어떻게 드러내는지
- 모호하거나 권위가 큰 변경을 어떻게 중단하고 사용자 판단으로 올리는지
- 무엇을 읽고 무엇을 바꿨는지 어떻게 보고하는지

Skill은 Project 계약을 해석해 사례에 적용할 수 있지만, 실행 중 새 Project 분류나 권위 정책을 발명하지 않는다.

### Skill이 맡지 않을 것

- 제품 목적이나 domain 의미를 독자적으로 확정하는 일
- Project context의 제품 의미 충분성이나 실제 acceptance를 최종 판정하는 일
- Project responsibility taxonomy를 새로 만들거나 바꾸는 일
- 기존 정본이 있는데 새로운 통합 정본을 만드는 일
- 초안을 채택된 Project 규칙으로 승격하는 일
- 근거가 모호한 고권위 변경을 추정으로 쓰는 일
- 한 번 사용한 작업 방식을 영구 지침으로 만드는 일
- 미래 workflow와 빈 디렉터리를 미리 만드는 일
- Project 전체의 제품·코드 평가 workflow를 수행하는 일
- 다른 Workspace의 내용을 기본 탐색하거나 갱신하는 일

### 판단·권한·실행 배치

글로벌 `ai-system_behavior-responsibility-allocation.md`의 관점에서 책임을 다음처럼 배치한다.

| 책임 | 배치 |
| --- | --- |
| Project의 의미·분류·권위·책임 관계 | Project context 계약과 실제 내용의 정본·책임 주체 |
| 현재 근거의 해석과 반영 후보 구성 | skill을 실행하는 모델 |
| 경로 제한, 허용된 쓰기 범위 같은 명확한 보장 | skill 계약과 필요한 규칙 기반 장치 |
| 새로운 제품 목적·domain 의미·중요 제약, 현재 의미 변경, 모호한 충돌의 결정 | 사용자 |
| 허용된 문서 변경과 결과 보고 | skill |
| 내용 복원 가능성의 계약과 coverage 기준 | Project context 계약 |
| 제품 의미의 실제 충분성과 acceptance | 사용자와 별도 검토 책임 |

Skill이 후보를 고른다는 이유로 최종 판단권까지 갖지 않는다. 반대로 모든 사례를 고정 규칙으로 만들지 않는다. 의미 해석은 모델이 하되, Project 계약이 허용 범위와 사람에게 돌려보낼 경계를 정한다.

### Skill의 최소 동작

Project 계약이 이미 존재한다는 전제에서 skill의 최소 동작은 다음과 같다. 호출 대상은 현재 작업에서 발견한 Project-wide 변화뿐 아니라, 사용자가 명시적으로 요청한 기존 Project context의 누락·손실 재구성일 수 있다.

1. 요청이 Project-wide 변화 반영인지, 명시적으로 허용된 기존 맥락 재구성인지와 선택한 책임 범위를 식별한다.
2. Project 계약을 읽고 주장별 보존 기간·읽기 조건·현재 권위와 이후 작업에 미치는 영향을 확인한다.
3. 근거가 현재 권위를 가진 내용인지, 변경 후보인지, 역사 증거인지 구분한다.
4. 각 주장에 대응하는 기존 정본 위치와 책임 주체를 찾는다.
5. 재구성은 출처 추적 가능성, 비창작, 미해결 충돌 없음이 모두 확인된 범위에서만 수행한다. 새로운 의미·현재 의미 변경·충돌 선택은 사용자 판단으로 올린다.
6. 계약상 명확하고 허용된 범위만 기존 정본 위치에 반영한다.
7. 선택한 범위에서 근거가 있지만 반영하지 못한 판단 내용과 열린 지점을 보고한다.
8. 중요한 선택 이유를 별도로 남길 조건이 성립하는지 확인한다.
9. 현재 Workspace가 새 Project 문서를 계속 필요로 할 때만 선택 목록 변경을 제안한다.
10. 읽은 근거, 적용한 Project 규칙, 변경 또는 무변경 이유를 보고한다.

이 순서는 skill이 자체 판단 체계를 소유한다는 뜻이 아니다. Project 계약을 실제 사례에 적용하는 실행 흐름이다.

## 대표 적용 장면

### 제품·domain 의미가 바뀌는 후보

한 Workspace에서 기존 domain 개념의 의미가 잘못됐다는 정황을 발견했다.

- 여러 후속 작업에 영향을 주므로 Project-wide 후보는 맞다.
- 그러나 제품 의미와 권위가 크고 근거가 모호하다면 skill이 domain model을 직접 바꾸지 않는다.
- 기존 제품 원자료와 domain 정본·책임 주체를 찾고, 충돌과 선택지를 사용자에게 보여 준다.
- 사용자가 판단한 뒤 실제 공통 맥락의 정본을 갱신한다.
- 의미 있는 대안과 재검토 조건이 있었다면 decision을 남길 수 있다.

### 현재 architecture가 명확히 바뀐 경우

구현과 테스트에서 기존 architecture 요약이 더 이상 맞지 않는 것이 명확하다.

- 상세 사실을 소유하는 코드·테스트를 근거로 확인한다.
- Project 현재 상태의 정본 위치를 찾는다.
- 계약상 허용된 범위라면 현재 요약을 교체한다.
- 단순 현황 갱신이면 별도 decision을 만들지 않는다.
- 선택의 이유와 대안이 후속 구조 판단에 중요하다면 decision을 검토한다.

### 반복해서 쓸 작업 기준이 보인 경우

한 Workspace에서 사용한 testing 방식이 유용했다.

- 한 번 성공했다는 사실만으로 Project 조건부 지침으로 만들지 않는다.
- 어떤 종류의 작업에 적용되고 무엇을 막는지, 비적용 조건과 제거 조건이 설명되는지 본다.
- Project-wide 기준으로 채택할 권위가 없다면 후보만 제시하고 쓰지 않는다.
- 채택됐지만 기존 정본·책임 경계가 없다면 사람 판단 없이 새 taxonomy를 만들지 않는다.

## 글로벌 AI-system 기준과의 정합성

이번 방향은 다음 글로벌 reference를 적용한다.

- `ai-system_context-ownership-boundary.md`: Project context의 일반 진입점에서 경계 정의, 실제 내용, 관리 규칙, 정본 위치와 책임 주체의 관계를 찾을 수 있게 한다.
- `ai-system_responsibility-cohesion.md`: 책임 profile을 곧 파일·디렉터리 수로 번역하지 않고, 실제로 독립된 목적과 규칙이 생길 때만 구조 경계를 만든다.
- `ai-system_behavior-responsibility-allocation.md`: 의미 해석, 명시적 보장, 사람의 결정 권한과 실제 쓰기 실행을 구분한다.
- `ai-system_human-readable-structure.md`: 사람이 skill 내부 구현을 읽지 않고 현재 Project 구조, 판단 지점과 실제 근거 위치를 찾을 수 있게 한다.
- `ai-system_harness-rippability.md`: skill을 제거해도 Project context의 의미와 관리 책임이 남도록 한다.

이 기준들이 공통으로 요구하는 것은 문서나 장치를 늘리는 일이 아니다. 지속 의미와 관리 책임은 Project 경계에 두고, skill은 그 의미를 참조하는 교체 가능한 보조 장치로 제한하는 것이다.

## 외부 reference에서 채택한 원칙

이번 논의에서는 유사한 정보 구조와 AI context 운용 사례를 보조 근거로 검토했다. 특정 framework 전체를 이식하지 않고 다음 원칙만 채택한다.

- [arc42](https://arc42.org/method/): 제품 목표·제약, 현재 구조, 여러 영역을 가로지르는 개념, 결정, 위험을 서로 다른 책임으로 다루되 결과는 갱신 가능한 상태로 유지한다.
- [Codex AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)와 [Skills](https://learn.chatgpt.com/docs/build-skills): 상위 진입 지침은 routing과 범위를 제공하고, 상세 skill과 reference는 관련 작업에서만 읽는 progressive disclosure를 사용한다.
- [Kubernetes KEP](https://github.com/kubernetes/enhancements/blob/master/keps/sig-architecture/0000-kep-process/README.md)와 [Rust RFC](https://github.com/rust-lang/rfcs#the-rfc-life-cycle): 문서가 보존된다는 사실과 현재 실행 권위가 있다는 사실을 분리한다.
- [MADR](https://adr.github.io/madr/): 중요한 선택의 이유, 상태와 대체 관계를 남긴다.
- [Backstage Catalog](https://backstage.io/docs/features/software-catalog/life-of-an-entity/): 실제 정본은 자연스러운 책임 위치 가까이에 두고, 공통 진입점은 위치와 관계를 안내한다.
- [Anthropic context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents): 기본 입력은 작고 신호 밀도가 높게 유지하고, 필요한 상세 맥락을 작업 중 선택해서 읽는다.

외부 reference의 section 구조, lifecycle 상태 집합이나 catalog 시스템은 채택하지 않는다. 이번 Project에 필요한 최소 책임과 읽기·권위 계약만 가져온다. 위 링크는 `2026-08-28`에 검토한 재접근 경로다.

## 독립 검토에서 확인한 교정

세 Project 책임과 Workspace 실행 경계를 구분하는 큰 구조는 유지할 수 있다는 독립 검토를 받았다. 다만 초기 skill 후보였던 `common / current / guidance / decision / no-op`는 서로 다른 차원을 하나의 배타적 분류로 섞는 문제가 확인됐다.

- `common / current / guidance`는 변화가 어떤 Project 책임에 관한 것인지 묻는다.
- decision은 선택 이유를 별도로 남길 필요가 있는지 묻는다.
- 변경하지 않음은 반영 가능한 변화가 있는지에 대한 실행 결과다.

따라서 skill은 이들을 하나의 enum처럼 선택하지 않는다. 먼저 Project-wide 변화인지와 영향받는 실제 책임을 확인하고, 정본 위치와 승인 경계를 찾은 뒤, 별도 decision 필요성과 실제 쓰기 여부를 각각 판단한다.

독립 검토는 decision 자체가 현재 답의 canonical일 수 있는 기존 Reference 사례도 지적했다. 후속 논의에서 복잡성을 줄이고 실제 내용의 정본을 분명히 하기 위해, 이번 foundation은 decision을 현재 답의 기본 정본으로 삼지 않는 방향으로 좁혔다.

## 채택하지 않은 접근

다음 접근은 이번 foundation에 채택하지 않는다.

- 보존 기간·읽기 조건·현재 권위라는 세 축을 세 디렉터리로 만드는 방식
- Project 공통 맥락·현재 상태·조건부 지침을 지금 바로 세 디렉터리로 고정하는 방식
- decision을 세 Project 책임과 나란한 제4 책임층으로 두는 방식
- decision을 모든 현재 Project 판단의 기본 정본으로 두는 방식
- Project context가 기존 source·domain·코드 사실을 복제하는 통합 저장소가 되는 방식
- Project 자료 전체를 모든 Workspace에 자동 주입하는 방식
- 한 작업에서 유용했던 workflow를 바로 Project 지침으로 올리는 방식
- Project 의미·분류·권위 규칙을 skill prompt 안에서만 정의하는 방식
- skill이 새 정본·책임 경계와 미래 taxonomy를 스스로 만드는 방식
- Workspace 종료를 Project context 반영의 유일한 시점으로 삼는 방식

## 구현 전 acceptance criteria

### Project 경계와 책임

- 일반 진입점에서 Project context의 목적, 범위와 세 책임의 관계를 설명할 수 있다.
- 다음 관련 작업이 제품 목적·사용자 문제·핵심 domain 의미·현재 상태·관련 반복 판단 기준의 현재 Owner와 경로를 다시 추측하지 않고 찾을 수 있다.
- 구조와 링크가 유효하더라도 선택한 책임 범위의 판단 내용이 비어 있거나 근거 있는 핵심 의미가 누락되면 완성으로 판정하지 않는다.
- 각 대표 내용에서 실제 정본 위치와 책임 주체를 찾을 수 있다.
- 공통 맥락·현재 상태·조건부 지침을 파일 이름이 아니라 주장 역할로 판별할 수 있다.
- Project 문서의 위치만으로 초안이 채택된 규칙으로 승격되지 않는다.

### 읽기와 수명

- 제품 요구 작업, architecture 작업과 관련 없는 작업에서 서로 다른 Project 문서 선택이 가능하다.
- 내용 복원 가능성은 Project context 전체 자동 주입이 아니라 작업별 문서 선택과 권위가 드러난 경로로 보장된다.
- 선택하지 않은 Project 문서도 일반 진입점에서 찾을 수 있다.
- 현재 상태가 상세 사실과 충돌할 때 오래된 내용을 계속 제공하지 않는다.
- 조건부 지침마다 적용·비적용·재검토·제거 조건을 찾을 수 있다.

### Decision

- 현재 답은 실제 내용의 정본에서 찾을 수 있다.
- 중요한 선택은 이유, 대안, 불확실성과 다시 열 신호를 잃지 않는다.
- 단순한 현재값 갱신에 decision을 강제하지 않는다.
- decision의 설명이 현재 답을 별도 정본처럼 중복하지 않는다.

### Skill

- Skill을 읽지 않아도 Project context의 의미와 관리 규칙을 이해할 수 있다.
- Skill은 Project 계약을 참조하며 같은 분류·권위 규칙을 독립적으로 다시 정의하지 않는다.
- 명확한 현재 상태 갱신과 고권위 제품 의미 변경에서 서로 다른 쓰기·승인 경계를 적용한다.
- 명시적으로 허용된 비창작·무충돌 재구성과 새로운 의미 결정·현재 의미 변경·충돌 선택을 구분한다.
- 선택한 재구성 범위에서 근거 있는 의미를 반영하지 못하면 누락과 열린 판단을 숨기지 않고 보고한다.
- 기존 정본과 책임 주체를 찾지 못하거나 근거가 충돌하면 새 정본을 만들지 않고 사용자 판단을 요청한다.
- 한 변화가 여러 Project 책임에 영향을 줄 때 하나의 분류로 정보를 잃지 않는다.
- Skill을 제거해도 사람이 같은 Project 계약과 정본·책임 관계를 따라 수동으로 관리할 수 있다.

## 후속 구현에서 정할 것

이 방향을 바탕으로 다음 항목을 실제 Project 구조와 skill 계약으로 구체화해야 한다.

1. Project context의 일반 진입점과 경계 계약을 둘 실제 위치
2. 현재 Project 문서별로 직접 소유하는 내용과 연결만 하는 상세 정본
3. Project 현재 상태의 stale 신호와 갱신 규칙
4. 실제 조건부 지침이 생길 때 정본 위치와 책임 주체를 정하는 기준
5. Decision의 최소 형식과 생성 기준
6. Project-local skill의 발동 인터페이스, 읽기 범위와 변경 보고 형식
7. 제품 의미·중요 제약·모호한 충돌의 사용자 승인 경계
8. Recover가 새 Project 진입점과 선택 가능한 문서를 허용하는 방식
9. 대표 Project-wide 변화 하나를 사용한 end-to-end 경계 검토

실제 디렉터리명, 조건부 지침 파일 구조, 자동 trigger와 hook, 제품·코드 평가 workflow는 위 책임과 대표 사례가 확인되기 전에 미리 확정하지 않는다.

## 현재 결론

Project context foundation의 최소 구조는 새로운 통합 정본이나 많은 문서가 아니다.

- Project의 일반 진입점이 경계와 세 책임, 실제 정본·책임 주체와 읽기 규칙을 연결한다.
- 다음 관련 작업이 제품 의미와 판단 근거를 다시 추측하지 않도록 현재 내용과 열린 지점의 복원 경로를 제공한다.
- Project 공통 맥락은 제품·domain에서 여러 Workspace가 공유할 의미를 맡는다.
- Project 현재 상태는 다음 관련 작업이 알아야 할 현재 현실을 교체형으로 유지한다.
- Project 조건부 지침은 관련 작업에서만 읽히는 반복 판단 기준을 맡는다.
- Decision은 현재 답을 대신하지 않고 중요한 선택의 이유와 재검토 맥락을 선택적으로 보존한다.
- Workspace는 현재 작업의 실행 맥락을 맡고, 그 안의 내용이 자동으로 Project 권위를 얻지 않는다.
- Project-local skill은 이 구조나 내용 충분성을 소유하지 않고, Project 계약을 읽어 기존 정본의 변경 또는 명시적으로 허용된 재구성을 보조하는 교체 가능한 관리 장치다.

이 결론을 기준으로 다음 단계에서는 Project 경계 문서와 기존 정본·책임 주체 지도를 먼저 만들고, 그 계약을 따르는 얇은 skill을 구체화한다.
