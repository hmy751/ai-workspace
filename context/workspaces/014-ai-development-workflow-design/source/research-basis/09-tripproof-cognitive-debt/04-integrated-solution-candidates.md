# 전체 문제에서 도출한 해결 후보 비교

## 이 문서의 지위

이 문서는 [`전체 인과 지도와 해결 책임`](03-integrated-causal-map-and-solution-obligations.md)을 실제 책임 배치가 다른 후보들로 구체화한다. 작업 전·어려운 응답·코드와 작업물 이해라는 세 장면을 각각 해결안으로 만들지 않는다.

현재 설계를 다시 판단할 때 읽는 후보 비교 근거다. 아래의 `아직 정하지 않는다`, `다음 설계 전에`와 미룬 항목은 비교 당시의 범위이며, 현재 미결정 목록이 아니다. 이후 선택한 세 skill의 구성·호출·공통 기준과 현재 남은 한계는 [현재 설계](05-current-solution-design.md)가 소유한다. 후보의 장단점과 비채택 이유는 보존하되, 이 문서의 입력·수행 순서를 현재 skill의 실행 절차로 중복 적용하지 않는다.

첫 비교에서는 `사용자 호출만`, `모든 응답의 고정 형식`, `별도 이해 ledger`라는 단일 수단 세 개와 그 장점을 모두 결합한 적응형 후보를 나란히 두었다. 당연히 결합 후보가 이기는 불공정한 비교였다. 더 중요한 문제는 같은 AI가 중요 경계와 국소 대리물 승격을 스스로 정확히 감지한다고 전제해, TripProof에서 실패한 바로 그 판단을 다시 같은 주체의 추상 판단에 맡긴 것이었다.

따라서 비교를 두 질문으로 다시 나눈다.

1. 005가 실제로 호출됐을 때 무엇을 책임지는가.
2. 사용자가 아직 문제를 발견하지 못했을 때 그 책임이나 별도 판단을 누가, 어느 순간에 호출하는가.

Skill·공통 rule·hook·reviewer 같은 구현 형태와 test는 아직 정하지 않는다.

## 먼저 고정되는 005의 실행 책임

호출 주체가 달라도 005가 수행할 핵심은 같다. 아래 A·B·C는 005를 시작하는 서로 다른 activation 경로이고, D는 숨은 semantic 불일치를 새로 만드는 별도 finding 책임이다. D는 A·B·C 가운데 하나와 결합될 수 있으므로 네 항목이 모두 상호 배타적인 대안은 아니다.

### 입력

- 이해하려는 응답·계획·code·작업물·finding 가운데 정확한 대상
- 즉시 선택을 내리려는지, 현재 구조를 파악하려는지 같은 사용 목적
- 현재 답의 canonical과 기준 code state·runtime·artifact
- 이미 존재하는 product·code·review finding과 그 근거
- 알려진 미확정, 사람에게 남은 판단과 다음 소비자

기준 상태는 필요한 경우 branch·commit·working tree·runtime configuration·artifact 시점을 포함한다. 현재성을 확인할 수 없으면 그 사실도 입력 상태다.

### 수행

1. 현재 이해 대상과 사용 목적을 분명히 한다.
2. 질문별 canonical, 역사적 이유 근거, 현재 구현 사실과 실행 observation을 구분해 조사한다.
3. 전체에서의 역할·관계·흐름을 사람이 잡을 수 있게 설명하고 필요한 exact source로 내려간다.
4. 확인 사실, 실행 observation, 기계적 보장, AI 해석, 미확정과 사람 판단을 구분한다.
5. 이미 주어진 finding이 있으면 그것의 의미·근거 상한·영향을 설명한다.
6. 현재 설명의 효력 범위, 다시 확인해야 할 변화와 가능한 다음 인수처를 밝힌다.

005는 이해 질문에 답하는 데 필요한 current fact를 조사할 수 있다. 예를 들어 현재 runtime에서 실제 provider가 연결됐는지는 source·configuration에서 확인할 수 있다. 그러나 “현재 구조가 원래 제품 목표에 충분한가”를 open-ended하게 감사하거나 새로운 제품·코드 적합성 finding을 만드는 것은 별도 review·판단 책임이다.

### 출력

고정 template이 아니라 다음 상태를 만드는 데 필요한 설명이다.

- 대상이 전체에서 무엇을 하고 왜 현재 질문에 중요한지 알 수 있다.
- 무엇을 어떤 기준 상태에서 확인했는지와 근거 상한을 알 수 있다.
- 수행한 것, 수행하지 않은 것, AI 해석과 사람 판단을 구분할 수 있다.
- 즉시 결정이 목적이 아니어도 현재 구조를 바탕으로 다음 질문을 만들 수 있다.
- 추가 조사·review·사용자 판단·durable 반영이 필요하면 가능한 수신처와 아직 인수되지 않았다는 상태가 보인다.

005는 사용자의 내적 이해를 판정하거나 `이해 완료`를 기록하지 않는다. 별도 current ledger도 만들지 않는다.

## 공통 실행 책임만으로 없앨 수 있는 두 방식

### 모든 주요 응답에 같은 긴 설명 형식을 붙이는 방식

목적·근거·미확정·영향·다음 결정을 항상 모두 출력하면 사용자가 먼저 혼란을 알리지 않아도 정보는 노출될 수 있다. 그러나 작은 사실과 중요한 acceptance가 같은 비용을 내고, 반복되는 항목은 읽히지 않을 가능성이 크다. 무엇보다 AI가 잘못 잡은 목표를 목적 칸에 쓰고 국소 test를 evidence 칸에 넣어도 형식은 완성된다.

필요한 책임을 상황에 맞게 표현하는 것은 유지하되, 고정된 긴 응답 schema 자체는 해결 후보에서 제외한다.

### 사람의 이해 상태를 별도 문서나 ledger로 누적하는 방식

이 방식은 장기 재진입을 돕는 것처럼 보이지만 `저장됨 ≠ 사용됨 ≠ 현재도 맞음 ≠ 사람이 이해함`을 다시 하나의 상태로 합친다. Workspace current, Project context, decision·record와도 경쟁하며 새 update·invalidation·consumer 부채를 만든다.

Durable 결정과 현재 상태는 기존 Owner 규칙을 따르고, 사용자의 이해 자체를 정본으로 저장하는 후보는 제외한다.

두 기각은 아래 activation 후보들의 공통 경계다. 어느 후보도 긴 고정 형식이나 새 이해 ledger를 기본으로 사용하지 않는다.

## 후보 A — 사용자가 필요할 때 직접 호출한다

### 책임 배치와 작동 시점

사용자가 작업 논의에서 이 구체화·이해 지원을 명시적으로 요청하거나, AI 응답에서 이해를 잃었다고 알리거나, code·작업물의 구조와 현재 상태를 알고 싶다고 말했을 때 005 실행 책임이 시작된다. 일반 작업 논의를 시작한 것만으로 자동 발동하지 않는다. 명시 호출은 사용자의 의도와 기대되는 작동 경계를 관찰 가능하게 하고, 누락됐을 때 일반 prose rule보다 실패를 지적하기 쉽게 한다. Skill이 실제로 load되고 모든 책임이 수행됐다는 것까지 호출 자체가 보장하지는 않는다.

평소 AI가 자기 판단으로 깊은 설명을 자동 시작하지 않는다. AI의 일반적인 사실성·권한·증명 상한 계약은 계속 지켜야 하지만, 그것이 005의 효과나 silent failure 예방으로 계산되지는 않는다.

### 정보 흐름과 결과

```text
사용자의 이해 요청
→ 005가 대상·사용 목적과 기준 상태를 확인
→ 현재 source와 필요한 과거 이유 조사
→ 의미·근거·미확정·판단 경계 설명
→ 사용자가 다음 질문·판단·보류를 선택
→ durable 변화가 있으면 별도 Owner 인수 요청
```

실제 인수자가 없으면 finding은 `아직 인수되지 않음`으로 남고, 현재 판단을 막는지 현재 설명 범위만 제한하는지 사용자에게 알린다.

### 강점

- 사용자가 필요성을 느낀 순간과 기대 동작을 명시해 실패 경계를 볼 수 있다.
- 작업 전 인터뷰·구체화의 기존 방식을 자동 절차로 덮지 않는다.
- 깊이와 비용에 대한 최종 통제권이 사용자에게 있다.
- 현재 구체화한 005 단독 책임 범위에서 성립하며 07이나 상시 reviewer가 있다고 가정하지 않는다.

### 한계

- 사용자가 간극을 감지하지 못하면 호출되지 않는다.
- 설명 전에 이미 잘못 닫힌 completion claim이나 제품·코드 불일치를 자동 발견하지 않는다.
- TripProof의 silent judgment failure 전체를 해결하지 않고, 사용자가 이해를 요구한 뒤의 재구성 부담을 줄이도록 설계하는 데 한정된다.

### 증명 상한

이 후보가 약속할 수 있는 것은 **호출된 대상에 대해 판단에 사용할 수 있는 설명 기반을 만드는 것**이다. 사용자가 먼저 발견하지 않아도 모든 간극이 노출된다고 말할 수 없다.

## 후보 B — 응답을 만든 같은 AI가 필요성을 스스로 판단해 호출한다

### 책임 배치와 작동 시점

응답 AI가 새 plan·scope·completion·acceptance처럼 중요하다고 판단한 순간 또는 자기 claim보다 evidence가 좁다고 판단한 순간 005 실행 책임을 함께 수행한다. 별도 주체나 workflow가 필요하지 않다.

### 정보 흐름과 결과

```text
AI가 응답 작성
→ 같은 AI가 중요도·불확실성·근거 범위를 판별
→ 필요하다고 보면 005 설명 수행
→ 사람에게 claim·evidence·판단 경계 제시
```

### 강점

- 사용자가 혼란을 먼저 표현하지 않아도 개입할 수 있다.
- 별도 runtime이나 reviewer 없이 일반 대화 안에서 작동할 수 있다.
- AI가 이미 알고 있는 evidence 상한과 미확정을 더 일찍 드러낼 수 있다.

### 한계

TripProof에서는 같은 AI가 상위 판단을 알고도 완료 순간에 소비하지 못했다. 이 후보는 그 AI에게 다시 `중요한 순간`, `핵심 책임`, `충분한 근거`를 올바르게 판별하라고 맡긴다. 일반 instruction이 실제 행동 순간에 소비된다는 보장도 없다.

자기 claim이 인용한 evidence보다 문언상 넓다는 것은 발견할 수 있어도, AI가 놓친 제품·코드 불일치를 독립적으로 찾는 장치는 아니다. 작동하지 않은 경우가 사용자에게 보이지 않는다는 점도 크다.

### 증명 상한

보조 경로로는 유용할 수 있지만 단독 예방 장치로 채택할 근거는 부족하다. 특히 “사용자가 먼저 발견하지 않아도 대리 승격을 막는다”고 약속할 수 없다.

## 후보 C — 미리 정한 작업 경계가 005를 호출한다

### 책임 배치와 작동 시점

응답 AI의 자기 판단이 아니라 workflow·host·작업 계약이 completion claim, scope 변경, handoff, acceptance 요청 같은 명시적 event에서 005를 호출한다. 호출에는 현재 claim, 기준 목표·범위, 사용한 evidence와 기준 상태가 입력돼야 한다.

### 정보 흐름과 결과

```text
명시 event 발생
→ workflow가 005 호출과 필수 입력을 요구
→ 005가 주어진 claim·evidence의 의미와 상한 설명
→ 사용자 또는 다음 책임자가 판단
→ 인수 여부가 별도로 결정됨
```

### 강점

- `필요한 행동 순간에 규칙이 실제로 소비돼야 한다`는 05 회고의 인과에 직접 대응한다.
- 같은 AI가 호출 여부를 전부 결정하지 않는다.
- Completion과 handoff처럼 이름 붙일 수 있는 경계에서는 누락 여부가 보인다.

### 한계

- 어느 event가 충분히 중요한지와 필요한 입력을 누가 정할지 별도 설계가 필요하다.
- Event 호출은 시점을 보장할 뿐, 상위 목적과 현재 artifact의 숨은 불일치를 새로 발견하지 않는다.
- 모든 completion에 무거운 설명을 강제하면 후보에서 제외한 전면 고정 방식으로 돌아갈 수 있다.
- 현재 005 Workspace에는 이 호출 workflow와 실제 consumer acceptance가 구현돼 있지 않다.

### 증명 상한

이 후보는 설명 책임의 **호출 시점**을 더 강하게 만들 수 있지만 semantic review를 대신하지 않는다. 어떤 경계에 어떤 깊이로 적용할지는 아직 열린 설계다.

## 후보 D — 독립적인 finding 생성과 005 설명을 분리한다

### 책임 배치와 작동 시점

별도 reviewer 또는 07 판단 연속성 책임이 상위 목적·현재 판단과 plan·code·result를 대조해 새로운 충분성·불일치 finding을 만든다. 005는 그 finding, 근거와 증명 상한을 사람이 이해하고 판단할 수 있게 설명한다. 사용자의 직접 호출도 별도 입구로 유지한다.

### 정보 흐름과 결과

```text
별도 review·판단 대조
→ bounded finding + 근거 + 미확정
→ 005가 현재 사람의 질문과 의미 구조에 맞게 설명
→ 사용자의 채택·보류·추가 근거 요구
→ 실제 실행·완료·과거 결과 재판정 책임이 별도 인수
```

005는 finding을 쉽게 만드는 과정에서 범위를 넓히거나 최종 verdict로 바꾸지 않는다. Reviewer도 사람의 acceptance를 대신하지 않는다.

### 강점

- 응답을 만든 같은 AI의 blind spot과 설명 책임을 분리한다.
- 사용자가 먼저 code와 목표를 대조하지 않아도 불일치가 제기될 수 있다.
- 005는 고유 책임인 의미·근거·판단 연결에 집중한다.

### 한계

- 독립 reviewer와 07 판단 연속성은 현재 005의 기존 인수 Owner가 아니다. 특히 07은 아직 연구 중인 방향이다.
- Finding을 누가 언제 요청하고, 어떤 baseline을 고정하며, 누가 실제로 수락하는지가 없으면 read-only 보고서로 끝난다.
- Review 비용과 오탐, finding 없는 일반 이해 요청은 별도로 다뤄야 한다.

### 증명 상한

TripProof의 silent semantic failure까지 다루려면 가장 직접적인 책임 분리지만, 지금 존재하는 005 단독 해결안으로 말할 수 없다. 07 또는 별도 review 설계와 명시적으로 결합해야 하는 시스템 후보다.

앞의 네 배치는 같은 005 실행 책임과 저장 경계를 사용한다. A·B·C는 누가 필요한 순간을 만드는지, D는 누가 새로운 finding을 생성하는지를 비교한다.

## 현재 수렴한 것과 아직 수렴하지 않은 것

### 수렴한 실행 핵심

어느 activation을 택하더라도 005는 다음 책임으로 수렴한다.

> 현재 판단이나 orientation에 필요한 의미를 정확한 source와 evidence 범위에 연결하고, 확인 사실·AI 해석·미확정·사람 판단을 구분해 다음 질문이나 판단이 가능한 설명 기반을 만든다.

이 책임은 새 정본, review verdict, 판단 연속성, 후속 실행을 소유하지 않는다. 긴 고정 template과 별도 이해 ledger도 사용하지 않는다.

### 지금 단독으로 성립하는 방향

후보 A는 사용자가 직접 호출한 순간에 한정하면 필요한 행동 시점과 005의 경계가 모두 분명하다. 따라서 **005 자체의 첫 설계 방향**으로는 가장 근거가 강하다. 이것은 사용자가 먼저 알지 못한 모든 부채를 예방한다는 뜻이 아니다.

후보 B는 일반 응답의 보조적 성실성으로 남길 수 있지만 효과를 약속하는 trigger로 볼 수 없다. 기존 사실성·권한 계약을 005의 새 성과로 중복 소유해서도 안 된다.

### TripProof 전체 원인까지 다루려면 필요한 결합

판단을 알고도 작업·완료에서 소비하지 못한 TripProof의 전체 원인을 바꾸려면 D의 별도 semantic finding 책임과 실제 consumer acceptance가 필요하다. A·B·C는 D나 005를 시작하는 activation 경로로 결합할 수 있고, 특히 C는 completion·scope·handoff 같은 명시 event에서 review 또는 설명을 호출하는 방식이다. C만으로는 숨은 불일치를 찾지 못한다.

그러나 C의 workflow, D의 finder와 후속 인수 책임은 아직 채택·구현되지 않았다. 따라서 이 문서에서는 `005와 연결할 시스템 구성요소`로 남기며, 존재하는 해결책처럼 표현하지 않는다.

## 다음 설계 전에 필요한 사용자 판단

이 비교는 기술 구현 선택보다 먼저 범위 선택을 요구한다.

- 이번 005에서는 후보 A의 사용자 호출형 이해 책임을 완결하고, C·D는 07·review와의 명시적 후속 결합으로 남길 수 있다.
- 또는 이번 해결 도출의 범위를 넓혀, 005 구현은 분리하되 D의 finding 책임, A·B·C 중 필요한 activation과 consumer acceptance까지 시스템 조합으로 함께 설계할 수 있다.

두 번째를 택해도 005가 finding 생성·완료 보류·판단 전파를 소유하지는 않는다. 차이는 이번 단계에서 인접 책임과의 인수 계약까지 구체화할지 여부다.

## 이 비교가 의도적으로 미룬 것

- 세 장면을 한 skill의 여러 입구로 둘지 일부를 별도 skill로 나눌지
- 정확한 호출 이름과 사용자 명령
- 화면에 보일 응답 형식
- 후보 C의 event·host·workflow
- 후보 D의 reviewer·07 실제 Owner와 acceptance 계약
- 실제 사례 test, pilot, 평가 지표와 acceptance

이 항목들은 사용자에게 필요한 범위 판단을 받은 뒤에야 정한다. 구현하기 쉬운 형식이나 test가 전체 문제의 충분성을 대신하게 하지 않는다.
