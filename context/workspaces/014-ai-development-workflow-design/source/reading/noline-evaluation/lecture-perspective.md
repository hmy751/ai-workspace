이 파일은 [보존 원본](<../../noline-evaluation/lecture-perspective.md>)의 Markdown 링크를 보존된 내부 사본으로 연결한 파생본이다. 본문 주장은 당시 평가이며 현재 설계의 확정안이 아니다. 사본이 없는 링크는 원래 외부 경로로 남겼다.

# 강연과 관련 스킬이 제시하는 개발 평가 관점

**이 자료들이 강조하는 것은 좋은 결과를 만들고, 사람이 필요한 판단을 하기 쉽게 하며, 반복되는 문제를 줄이는 개발 환경이다.** 사람의 개입이 있었다는 사실만으로 성공이나 실패를 판정할 수 없다. 동시에 사람이 계속 감시하고 같은 오류를 고쳐주는 상태를 당연하게 받아들이지도 않는다.

두 강연과 관련 스킬, 별도의 Vercel 글을 독립적으로 읽은 분석이다. Noline의 성과 판정은 아직 포함하지 않는다. 먼저 아래 요약을 읽고, 원문 확인이 필요할 때 뒤의 근거로 내려가면 된다.

## 먼저 읽을 요약

- **결과의 질을 여러 면에서 본다.** 요구를 충족했는지, 실제로 동작하는지, 구조가 이해·변경하기 좋은지를 따로 확인한다. 테스트 통과나 명세 준수 하나로 전체 품질을 대신하지 않는다.
- **사람의 판단에 도달하기 전 작업의 질을 본다.** AI와 검사 도구가 확인할 수 있는 것을 확인했는지, 사람이 선택할 때 변경 이유·대안·영향·불확실성을 알 수 있는지가 중요하다.
- **반복 개입이 이후 작업을 바꿨는지 본다.** 피드백이 다음에 활용되는 코드 구조·검사·지침·사례로 반영됐는지 살핀다. 문서나 규칙의 증가 자체는 성과가 아니다.
- **판단을 맡기는 위치와 비용을 본다.** 기계적으로 판별할 규칙, 맥락을 해석할 AI, 새 기준이나 미해결 선택을 결정할 사람을 구분한다. 복잡한 절차·방대한 지침·추측성 추상화도 검토 대상이다.

따라서 이 자료에서 도출할 평가 질문은 **“사람의 개입이 어떤 역할을 했고, 그 전후로 결과·판단 가능성·반복 작업·비용이 어떻게 달라졌는가?”**다. 이는 아래 자료를 종합한 분석자의 질문이며, 발표자가 제시한 단일 평가표는 아니다.

## 자료마다 강조하는 문제가 다르다

| 자료 | 주로 해결하려는 문제 | 판단에 주는 관점 |
| --- | --- | --- |
| PR 병목 강연 | 코드 생성 속도를 사람이 검토하는 속도가 따라가지 못함 | 자동 검사·AI 리뷰를 거친 변경을 사람이 위험에 맞게 검토할 수 있는가 |
| Agent 신뢰 강연 | AI 작업마다 사람이 감시·교정·수동 검증해야 함 | 실제 실행 도구와 코드 구조가 좋은 결과를 만들고 잘못을 막아주는가 |
| 관련 스킬 다섯 개 | 명세·표준 검토, 설계 탐색, 변경 설명, 회고를 실제 절차로 만드는 일 | 언제 무엇을 읽고 검사하며, 어떤 결과를 사람에게 넘기는가 |
| Vercel 제품 설계 글 | 구현된 모양만으로는 제품 결정의 이유를 알 수 없음 | 근거 있는 판단을 재사용하되 새 기준은 사람이 검토하며, 지침의 효과를 별도로 확인하는가 |

Vercel 글은 두 강연과 별도 자료다. 스킬 번역본들도 강연 당시 소개한 버전과 동일하다고 확인되지 않는다. 따라서 하나의 완성된 운영 체계로 합쳐서 읽지 않는다.

## 실제 원문과 스킬에서 확인되는 근거

**사람의 개입은 역할에 따라 의미가 다르다.** PR 병목 강연은 검사·AI 리뷰 다음에 Human Review를 두고, 되돌리기 어려운 변경과 영향 범위에 따라 리뷰 강도를 달리한다. 아키텍처 개선 스킬은 후보의 문제·이점·전후 구조·추천 강도를 먼저 보여준 뒤 “아직 인터페이스를 제안하지 않습니다”라고 제한하고 사람이 후보를 고르게 한다. 이때의 선택과 후속 논의는 절차에 포함된 일이다. 반면 Agent 신뢰 강연은 매 대화마다 사람이 방향을 바로잡아야 하는 상태를 개선 대상으로 삼는다. [PR 강연](<../../lectures/01_PR_병목_강연_전체번역.md:25>) · [위험별 리뷰](<../../lectures/01_PR_병목_강연_전체번역.md:89>) · [후보 선택](<../../lectures/improve-codebase-architecture.ko.md:39>) · [반복 감시 문제](<../../lectures/03_Agent_신뢰_강연_전체번역.md:33>)

**좋은 결과에는 서로 다른 확인이 필요하다.** `code-review`는 “모든 표준을 따르지만 잘못된 기능을 구현한 코드”와 요구는 충족하지만 관례를 어긴 코드를 구분한다. 강연은 실제 화면 대신 소스의 문자열 순서를 검사하거나 과도한 가짜 구현으로 실패를 감추는 테스트를 비판한다. `codebase-design`은 호출자가 알아야 하는 복잡성과 변경이 흩어지는 정도를 다룬다. 이들을 종합하면 명세 충족·관찰 가능한 동작·구조의 질은 별도 근거로 판단해야 한다. [독립된 검토 축](<../../lectures/code-review.ko.md:83>) · [테스트의 한계](<../../lectures/01_PR_병목_강연_전체번역.md:35>) · [설계 원칙](<../../lectures/codebase-design.ko.md:14>)

**보고의 가치는 판단에 필요한 정보를 주는 데 있다.** PR 강연은 “목표는 Why를 이해하는 시간을 가능한 한 줄이는 것입니다”라고 말한다. `pr` 스킬은 변경에 맞는 설명·그림과 구체적인 전후 근거, 되돌릴 수 있는지와 영향 범위를 요구한다. 그림이나 보고서가 존재한다는 사실만으로 사람이 이해하고 판단할 수 있었다고 볼 수는 없다. [강연의 설명 목적](<../../lectures/01_PR_병목_강연_전체번역.md:99>) · [전후 근거와 위험](<../../lectures/pr.ko.md:158>)

**피드백을 남기는 것과 재발을 줄이는 것은 다르다.** PR 강연의 강한 원칙은 “같은 Comment를 두 번 작성해서는 안 됩니다”다. `retro`는 기존 검사가 실제로 연결되어 있는지, 기계적으로 판별할 규칙을 문서에만 두었는지, 지침이 행동을 바꾸는지와 도구 비용을 살핀다. 아키텍처 개선 스킬은 거절 이유도 미래의 같은 제안을 막는 데 실제로 유용할 때만 ADR이라는 결정 기록으로 남기도록 제안한다. 일시적으로 할 가치가 없다는 이유는 제외한다. [반복 피드백](<../../lectures/01_PR_병목_강연_전체번역.md:107>) · [회고 대상](<../../lectures/retro.ko.md:15>) · [기록할 거절 이유](<../../lectures/improve-codebase-architecture.ko.md:66>)

**Vercel 글은 판단을 재사용하면서 새 기준을 만드는 권한을 구분한다.** 글 속 간략화된 스킬은 사용자 목표·검증된 사실·프로젝트 지침·수용된 결정 등의 우선순위를 제시한다. 글은 “Keep new standards, policy choices, and unresolved product decisions with people”라고 명시한다. 하나의 화면이나 리뷰 의견을 보편 규칙으로 올리지 않으며, 수집된 후보는 사람 검토 전까지 후보로 남긴다. 이는 사람에게 모든 구현 선택을 물으라는 뜻이 아니다. [판단 근거의 순서](<../../lectures/vercel-product-design (1).md:128>) · [규칙 갱신 제한](<../../lectures/vercel-product-design (1).md:210>) · [사람에게 남기는 판단](<../../lectures/vercel-product-design (1).md:437>)

**스킬의 효과는 사용 여부와 별도로 평가한다.** Vercel 글은 예상 수정이 노출되지 않은 사례, 스킬을 쓰지 않은 비교 실행, 규칙 준수와 기존 출시 결과의 유사성에 대한 분리 평가를 설명한다. 기존 출시 코드에도 결함이 있을 수 있기 때문이다. 또한 스킬을 불러왔는지와 규칙을 적용했는지를 따로 시험하라고 한다. 이로부터 문서 작성·스킬 호출·결과 개선을 같은 성과로 취급하면 안 된다는 평가 원칙을 얻을 수 있다. [효과 평가](<../../lectures/vercel-product-design (1).md:325>) · [읽기와 적용의 구별](<../../lectures/vercel-product-design (1).md:441>)

**코드와 판단 기록은 제공하는 정보가 다르다.** Agent 신뢰 강연은 AI가 기존 패턴을 확장하기 때문에 코드 자체를 중요한 기억으로 본다. Vercel 글은 출시된 코드를 보는 것만으로 그 결정을 택한 이유를 알 수 없다고 지적한다. 두 관점을 함께 읽으면 좋은 구현 패턴과 결정의 이유·예외를 남기는 기록에 각각 역할이 있다. 기록이 필요한지는 코드의 존재만으로, 코드 품질은 기록의 충실함만으로 판정할 수 없다. [기존 코드의 역할](<../../lectures/03_Agent_신뢰_강연_전체번역.md:67>) · [결정 이유의 맥락](<../../lectures/vercel-product-design (1).md:5>)

## 이 관점으로도 성급하게 단정할 수 없는 것

강연은 높은 처리량과 감시 감소를 지향하지만, 그 목표를 모든 개발 작업의 성공 기준으로 가져올 수는 없다. 학습·제품 탐색·새 요구 결정에서는 대화가 결과의 일부가 될 수 있다. 반대로 사람의 최종 책임이 있다는 이유로 AI가 할 수 있었던 검증 누락이나 반복 교정을 정당화해서도 안 된다.

“같은 지적을 두 번 하지 않는다”는 방향은 유용하지만 반복 횟수만으로 실패를 판정하기에는 강하다. 앞선 결정이 현재 조건에도 유효했는지, 사용할 수 있는 형태로 전달됐는지, 새 정보가 생겼는지 확인해야 한다. 이는 원문을 실제 사례 평가에 적용하기 위한 분석자의 제한이다.

자료 사이의 차이도 남겨야 한다. PR 강연은 확실한 문제를 리뷰어가 직접 수정·커밋하도록 권하지만, 이 폴더의 `code-review` 본문은 두 검토 결과를 보고하는 절차다. `retro`가 코딩 표준의 책임을 리뷰 단계에 두는 것과 Vercel이 구현 전 제품 판단을 요구하는 것은 대상과 책임이 다르므로 바로 모순이라고 볼 수 없다.

이 자료만으로 특정 스킬의 효과나 Noline에 대한 적합성이 증명되지는 않는다. 두 강연의 전체 번역과 상세정리, 관련 스킬 다섯 개, Vercel 글을 2026-10-11에 읽었다. 상세정리의 React·Next 예시와 실무 보완은 발표자 주장과 구분했다. 번역 정확성·최신 버전·실행 효과는 별도 확인 대상이며, 스킬이 참조하는 외부 파일의 내용까지 확보한 것은 아니다.

## 다음 Noline 평가와의 관계

별도로 작성한 [Noline 자체 평가](<noline-assessment.md>)는 **실제 결과, 사용자의 이해와 결정, 불필요하게 반복한 일과 비용**을 중심으로 본다. 07·09 연구는 설계 배경과 검토할 가설로 사용한다. 판단 연속성 하나로 전체 성패를 결정하지 않는다. Maintainer 하네스는 평가·개선 범위에서 제외하고, Work 기록의 실제 활용은 포함한다.

2026-10-12 인터뷰와 후속 비교를 반영한 [강연 대조와 개선 방향](<improvement-directions.md>)에서 추가로 보이는 성과·한계와 다음 과제를 정리했다. 이 문서의 독립 분석은 그대로 유지한다. 앞서 수집한 [장면 후보](<assessment-entry.md>)는 근거의 진입점이며, 최종 평가 기준이나 실패 목록이 아니다.
