# Noline에서 시도한 구성의 성과와 한계

**티켓·Work 기록은 이전 방식보다 다시 설명할 일을 줄이고 작업을 이어가기 편하게 했다는 사용자 경험이 확인됐다. 실제 코드 개선과 유용한 설명·선택 과정도 남았다. 다만 첫 결과와 보고부터 충분히 검토하고 이해할 수 있게 만드는 수준은 일정하지 않았고, 사용자가 한 번 더 짚어야 나아지는 문제는 남아 있다.** 기록의 효용과 초기 개발·검토·설명 품질의 한계를 함께 평가한다.

평가 범위는 최초 이식부터 Ticket 06 종료까지다. 07·09 연구는 설계 배경으로 사용하고, 요구 결과·코드 품질·사람의 이해와 선택·작업 부담을 함께 봤다. 2026-10-11~12의 [장면별 인터뷰](<reviews/interview-20261012.md>)와 보류했던 원자료 비교를 반영했다. 강연 대조와 개선 방향은 [후속 판단](<improvement-directions.md>)에 분리했다. Maintainer 하네스는 평가·개선에서 제외하고 Work 기록은 포함한다.

## 무엇이 실제로 잘됐나

**실제 코드 개선이 남았다.** Ticket 03은 표시 객체의 중복 정리에서 출발해, 겹친 조회의 오래된 응답이나 화면 해제 후 응답이 상태를 덮지 않도록 처리하는 수준까지 발전했다. 사용자는 결과가 기대에 “훨씬 가까워졌어”라고 평가했다. Ticket 05에서는 날짜를 응답 값으로 바꾸는 처리와 응답 계약 검증을 구분하고, 수정·삭제와 하위 조회의 소유권 조건을 보강했다. 온라인 복구 작업에서는 캐시 표시와 조회 정책을 조합하고 이후 여러 화면에 적용했다. 이 변화는 코드로 확인되며, 모든 성과를 스킬 단독 효과로 돌릴 수는 없다. [전후 코드와 원문](<reviews/noline-change-evidence.md>)

**사람의 참여가 유효한 선택으로 이어진 장면이 있다.** DB 작업 순서 설명에서는 사용자가 이해된 부분과 남은 부분을 구별해 질문했고, 실패 전파를 자기 말로 설명한 뒤 이름 수정과 커밋을 선택했다. 조회용 중간 구조는 사용처 하나일 때 제거했다가 여러 화면에서 공통 책임이 생기자 다시 검토했다. 인터뷰에서 사용자는 두 갈래 Promise 설명이 도움됐지만 혼동을 더 빨리 짚을 여지도 있었다고 했다. DB·인증 실패 처리의 선택 질문은 중요한 동작을 이해하기 위한 자연스러운 과정으로 받아들였다. 학습·제품 선택을 같은 오류의 반복으로 세지 않는다. [DB 설명](<scene-evidence.md#b05-s11>) · [조회 구조 재판단](<scene-evidence.md#b07-s07>)

**반복된 약점은 결과의 충분성을 확인하는 데 있었다.** Ticket 03에서는 좁은 요청 목록을 고친 것으로 충분한 개선을 설명했고, Project 재시험에서는 파일 구성이 정리됐다는 보고 뒤 본문의 중복·의미 누락·진입 경로를 다시 검토해야 했다. 후반 보고서는 사용자가 형식을 재사용하도록 선택했지만, 무엇이 해결됐고 왜 검사했으며 다음에 무엇을 할지 다시 물어야 했다. 인터뷰에서는 재작성도 조금 나아진 정도였고 기준이 불명확해 넘어갔다고 했다. 후속 이의가 없었다는 사실을 만족으로 읽지 않는다. 서로 같은 버그는 아니지만, 산출물을 만들었다는 사실과 사람이 필요한 결과를 받았는지를 구별하는 기준이 반복해서 사용자 교정으로 보완됐다. [Ticket](<scene-evidence.md#b01-s07>) · [Project 재시험](<scene-evidence.md#b03-s05>) · [보고서](<scene-evidence.md#b09-s02>)

## 구성별 판정

| 구성 | 확인된 도움 | 남은 한계와 판정 |
| --- | --- | --- |
| **Spec·Ticket** | 작업 범위·검증·현재 결과를 연결할 문서가 생겼고, 부족한 Ticket 기준을 실제로 수정했다. Ticket 06 종료 때도 보류·후속·미검증을 구분했다. | 초기에는 좁은 문안이 충분성 판단을 대신했다. **작업 경계를 공유하는 효용은 있으나 적정 개선 깊이와 완료 판단은 일정하지 않았다.** 가독성 Spec 아래에서도 사용자 동의로 동작 개선을 진행했으므로, 동작 변경 자체를 범위 위반으로 평가하지 않는다. |
| **Work와 기록** | 다음 세션이 미해결 문제를 이어받고, 제안된 순서를 확정된 결정과 구별하고, 원래 선택창 문제로 돌아오는 데 쓰였다. | 자료를 읽어도 중심 과제를 좁혀 잡아 사용자가 다시 설명한 경우가 있다. **재사용과 사용자의 재설명 감소 체감이 함께 확인된다.** 어긋난 재개는 답답했지만 보통 한두 번 정정하는 정도로, 사용자에게 큰 부담은 아니었다. 다음 판단의 우선순위 전달은 보완할 부분이다. |
| **Project 컨텍스트와 읽기·갱신 스킬** | 공통 계약·현재 상태·작업 기준을 나눠 주제별로 읽을 수 있게 했고 실제 읽기 명령도 확인된다. 10월 1일 별도 워크트리의 본문 보완에서는 글로벌 작성 스킬·기준의 실제 사용 뒤 사용자가 “훨씬 나아졌네”라고 평가했다. | 이관·재시험에서 기록을 기준 본문처럼 쓰거나 기존 의미·연결을 빠뜨렸고, 이를 바로잡는 별도 작업이 필요했다. **선택적 참조와 한 차례 문서 개선은 확인된다.** 초기 이관과 후속 워크트리 개선을 구별해야 하며, 글로벌 스킬만의 효과와 관리 비용 절감은 미확정이다. 필요한 사례·상세의 양은 문서 역할에 따라 판단한다. |
| **work-discussion** | 직접 호출 후 DB·인증 초기화의 미정인 실패 동작을 구분해 사람의 선택으로 제시했다. | **남은 결정을 드러내는 작동과, 나쁘지 않은 선택 과정이었다는 사용자 경험이 확인된다.** 설명을 더 요청한 것을 실패로 세거나 시간 절감으로 일반화하지 않는다. |
| **reconsider-work** | 실제 호출·열람 뒤 기존 목표, 코드와 후속 적용 이유를 다시 검토했다. 변경된 사용처와 비용을 보고 선택을 조정하는 과정이 있었다. | **재판단 절차는 작동했다.** access 질문 뒤 최종 설명은 도움됐지만, 질문만으로 즉시 바꾸려 한 대응은 사용자도 문제로 평가했다. 기존 선택의 이유와 재검토가 필요하다. |
| **작업물 브리핑·설명 복구** | 코드 역할·동작·전제를 설명하고 사용자 재진술과 다음 선택으로 이어진 사례가 있다. | 역할과 동작의 연결, 읽을 수 있는 구성, 기존 문제와 현재 결과의 연결을 반복 보완했다. **일부 설명의 도움은 사용자도 확인했다.** 보고서 재작성은 부분 개선에 그쳤다. 코드 자체의 품질과 사용자의 배경지식·스타일 적합성도 이해 부담에 영향을 줄 수 있어 설명 스킬 문제로만 좁히지 않는다. |

판정은 [설계·설치 근거](<reviews/noline-design-basis.md>), [실제 호출·열람·후속 행동](<reviews/noline-context-usage.md>), [코드 변경 대조](<reviews/noline-change-evidence.md>)에 연결된다. 설치 전의 초기 논의를 나중에 설치된 스킬의 성과로 계산하지 않았다.

## 개입을 어떻게 해석했나

| 개입 장면 | 개입의 역할에 대한 판정 |
| --- | --- |
| 작은 수정 뒤 관련 흐름과 충분한 개선을 다시 요구 | 개선 깊이를 다시 요구한 사실은 있으나, 추가 질문의 원인 전체를 하나로 묶지 않는다. 이미 구현한 결과를 이해하려는 질문도 있었다는 회고를 반영한다. |
| Project 재시험의 본문·의미·연결을 다시 검토시킴 | **반복 교정 작업은 관찰됨.** 사용자가 이를 부담으로 여겼는지, 나중으로 미뤘는지는 기억 불확실하다. 관찰된 작업량을 주관적 비용으로 대체하지 않는다. |
| DB·Promise를 여러 번 질문하고 이해된 부분을 확인 | 이해된 부분과 남은 부분을 구별하며 진행한 **학습·검토 참여**. 같은 내용을 다시 묻기도 했지만, 질문 횟수를 동일 실패의 반복 횟수로 환산하지 않는다. |
| 사용처가 늘자 공통 조회 구조를 다시 선택 | 조건 변화에 따른 **정상적인 설계 재판단**. 다만 사라진 access에 대한 질문을 즉시 복원 명령으로 읽은 부분은 별도 교정이다. |
| 구현을 본 뒤 확대 범위를 철회 | **승인 후 재검토하고 철회한 사실은 확인됨.** 후속에 유사 기능을 다른 구조·정책으로 채택했다. 일시 범위 조절인지 당시 복잡성·구현 문제가 컸는지라는 사용자 동기는 불확실하다. |

이 구분은 [독립 의미 검토](<reviews/noline-semantic-review.md>)에서도 원문을 먼저 읽고 대조했다. 같은 판단 기준을 다시 요구한 경우, 새 조건으로 판단을 바꾼 경우, 필요한 이해를 쌓은 경우를 분리했다.

## 비용과 남은 불확실성

사용자가 Project 구성 재시험, 긴 설명의 재편집, 기록의 읽기 범위, 필요 이상의 절차 추가를 직접 조정한 비용은 관찰된다. DB 설명처럼 그 노력이 이해와 선택으로 이어진 경우도 있다. **사용자는 전반적인 재설명 감소와 이전보다 편해졌다는 체감을 명시했다. 총시간·토큰 절감이나 전체 개발 부담의 크기는 측정하지 않았다.** 기존 하네스가 있었고 작업·지침도 계속 바뀌어 단순 전후 비교가 되지 않는다.

코드 대조는 대표 세 흐름을 확인한 범위다. 장면의 전수 채점이나 성공률 계산, 앱 전체 품질·장기 유지보수 용이성의 검증은 하지 않았다. Ticket 06 종료는 남은 범주를 설명한 뒤 기록·커밋으로 마무리한 사실로 판단한다. 사용자가 세션을 넘기려 했는지, 충분하다고 여겨 다른 작업으로 가려 했는지는 기억 불확실하다. 모든 오류의 해결이나 앱 전체의 준비 완료로 확대하지 않는다. [종료 원문](<scene-evidence.md#b09-s10>)

## 보류했던 비교에서 확인한 것

- **철회안과 후속 구현은 기능이 일부 겹쳐도 같은 구현이 아니었다.** 후속에는 캐시 공개 조건과 복구 상태 관리 등을 바꿨다. 사전 승인·철회·후속 채택을 함께 보고, 가독성만의 범위로 소급하지 않는다. [코드와 정책 비교](<reviews/withdrawal-followup-comparison.md>)
- **글로벌 작성 기준의 적용과 문서 개선이 이어진 사례가 있다.** 9월 30일 도입 뒤 10월 1일 명시 호출·자료 열람·본문 수정·긍정 평가가 연결된다. 초기 이관 개선이나 main에 반영된 결과와 혼동하지 않는다. [도입과 본문 비교](<reviews/document-guidance-followup.md>)
- **재개 오류는 원문 부재만으로 설명되지 않는다.** 배경과 잠정 상태는 기록돼 있었고, 다음 행동을 묶어 전달하고 읽는 과정에서 두 버그가 앞섰다. 긴 대화 뒤 기록한 것이 원인이라는 가설은 미확정이다. [시점과 재개 비교](<reviews/record-timing-followup.md>)

개선은 기록을 없애거나 사람의 참여를 모두 줄이는 방향이 아니다. 유지할 효용은 보존하면서 코드·검토·설명 결과의 질과 다음 판단의 전달을 보완한다. 구체적인 우선순위와 사람·AI·자동 검사의 역할은 [강연 대조와 개선 방향](<improvement-directions.md>)에 있다.
