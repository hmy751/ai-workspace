## 해결책의 초점이 바뀐 근거

사용자는 Spec 이름, Ticket 크기, Spec·Ticket 구별을 원인 후보로 질문했다. 그러나 변경 전 Spec에도 읽기·수정 부담, 공통점과 필요한 차이, 함께 수정할 위치, 대표 사례만으로 전체 완료하지 않는 기준이 이미 있었다. 그래서 이름에 품질 단어를 더하거나 모든 Ticket을 크게 만드는 방식 대신 다음 관계를 명시하는 쪽을 선택했다.

- 결과 달성을 맡긴 요청에는 그 결과에 필요한 일을 발견할 책임도 따른다.
- 분석 예시와 Ticket 초안의 수정 목록은 실행의 출발점이지 검토 범위와 품질의 상한이 아니다.
- Ticket은 수정 방법보다 맡은 결과, 필요한 범위, 완료 근거를 먼저 정한다.
- 조사할 필요와 실제 변경 권한은 구별하며, 명시적 제약과 보존할 계약은 유지한다.
- 테스트 통과나 목록 이행이 실제 맡은 결과를 입증하는지 대조한다.

이 선택은 “적힌 그대로 완료해도 핵심 문제가 남는가”라는 이전 질문도 새 Main의 `핵심 문제` 정의에 의존한다는 reviewer 지적을 반영했다. 좁게 정의하면 얕은 수정이 통과하고, 크게 정의하면 작은 문제를 놓칠 수 있으므로 특정 문제를 추측하게 하기보다 맡은 결과와 검토 책임의 관계를 기준으로 삼았다.

사용자는 다음 조건도 명시했다.

## 일반화 후보 자체를 확인한 결과

최종 일반화 후보와 요청·가상 코드만 받은 새 Main들이 세 요청 유형, 다섯 사례의 계획을 작성했고 reviewer가 원자료에 대조했다는 보고를 확인했다.

- 주문 계산 전반 개선은 변수명 변경을 넘어 두 계산 사용처의 관계를 다뤘고, 저장된 금액을 표시하는 영수증은 다른 책임으로 구별했다.
- CSV 미리보기 전반 개선은 로그·주석 외에 중첩 흐름, 변수 의미, 중복과 집계 상태를 다뤘다.
- 다운로드 기능 완성은 버튼과 로그에서 멈추지 않고 실제 다운로드 연결을 계획했으며, 제공되지 않은 화면 연결은 미확인으로 남겼다.
- 오탈자 수정은 지정된 문자열 변경 범위에 머물렀다.
- API 납품은 함수 계약과 사용 예제를 결과로 삼고 제외된 UI·다운로드를 추가하지 않았다.

Reviewer가 적절하다고 본 관점은 목표 해석, 필요한 작업 발견, 작은 요청과 API 납품의 범위 준수, 완료 근거와 미확인의 구별이다. 추가 문구 수정을 요구할 문제는 보고되지 않았다.

다만 다섯 사례의 전체 입력·계획과 reviewer 원문은 해당 Noline 기록에도 포함되지 않았고 Main의 보고로만 남았다. 이 결과는 작은 사례의 계획 수립 근거이며 실제 구현, 검증 수행, 완료 보류 행동, 복잡한 작업의 반복 신뢰성을 입증하지 않는다.
