# AI Workspace

AI 에이전트와 실제 소프트웨어를 개발하면서 쓰는 작업 방식과 도구를 쌓아 가는 개인 저장소다. 에이전트와 사람이 맥락을 어떻게 나눠 갖고, 세션이 바뀔 때 무엇을 이어 주고, 무엇을 확인된 사실로 취급할지를 다룬다. 적용하고 실패하고 고친 기록을 근거로 함께 두고, 쓸모가 확인된 것만 남기기 때문에 내용은 계속 늘어난다.

## 배경

AI 에이전트와 개발하면 작업 자체는 꽤 잘 이어진다. 목표와 범위와 완료 조건은 문서에 남고, 다음 세션도 그걸 읽고 이어서 한다. 잘 이어지지 않는 건 그 일을 왜 그렇게 했는지에 대한 판단이다. 왜 이 구조를 골랐는지, 어떤 근거가 약했는지, 어떤 신호가 나오면 그 선택을 다시 열어야 하는지는 거의 남지 않는다.

그래서 다음 작업은 이전 선택을 검토 대상이 아니라 이미 정해진 전제로 받게 된다. 새 문제가 들어와도 이 구조가 아직 맞는지보다 이 구조 안에 어떻게 넣을지를 먼저 묻는다.

여기에 측정하기 쉬운 쪽이 먼저 정리되는 문제가 겹친다. 테스트 통과나 완료 체크는 즉시 보이는데, 제품이 한 방향으로 모이고 있는지나 코드가 다음 변경을 받을 만해졌는지는 느리고 애매하다. 국소적인 완료가 쌓이는 동안 전체에 대한 판단은 계속 뒤로 밀린다.

그러다 보면 구현만 된 것과 기계가 확인한 것과 사람이 받아들인 것이 한 덩어리로 섞이고, 다음 세션은 낡은 상태나 근거 없는 완료에서 출발하게 된다. 세션마다 처음부터 다시 설명하거나 문서를 통째로 읽히는 것도 같은 문제의 다른 면이다. 다음 세션에 필요한 건 전부를 아는 상태가 아니라, 지금 작업에 필요한 걸 어디서 찾을지 아는 상태다.

문서를 꼼꼼히 쓰는 습관만으로는 잘 안 됐다. 그래서 무엇을 어디가 소유하는지를 먼저 정하고, 그 경계 위에서 읽기와 반영과 검증을 다룬다.

## Project context와 Work context

맥락을 두 종류로 나눈다. 여러 작업에 공통으로 적용되는 Project context와, 지금 진행 중인 작업 하나의 Work context다. 어느 쪽이든 문서와 디렉터리는 자기가 무엇을 책임지고 무엇은 책임지지 않는지 밝힌다. 같은 사실을 여러 곳에 복사하지 않고, 실제 주인이 다른 곳에 있으면 가리킨다.

### Project context

한 덩어리로 두지 않고 정보의 수명에 따라 나눈다.

- 오래 지속되는 제품과 도메인의 의미, 프로젝트 전체 제약
- 자주 교체되는 현재 구현, 지원 범위와 아직 보장하지 않는 것
- 관련 작업이 지켜야 할 계약과 판단 기준
- 중요한 선택의 이유와 다시 볼 신호

현재 구현은 자주 바뀌고 제품의 의미는 오래 간다. 둘을 같은 문서에 두면 무엇을 고쳐야 하는지 매번 다시 판단해야 한다. 이번 작업의 spec이나 조사 메모처럼 일이 끝나면 다음 작업을 지휘할 권한을 잃어야 하는 것도 여기에 섞지 않는다.

### Work context

작업마다 Workspace를 하나 두고 그 안을 네 가지로 나눈다.

- `current/`: 다음 세션이 바로 행동하기 위해 읽는 현재 상태
- `source/`: 그 작업이 선택한 원자료와 출처
- `output/`: 목표를 위해 선택된 현재 산출물. 실제 파일이 프로젝트의 다른 곳에 있으면 복제하지 않고 가리킨다
- `records/`: 후보, 비교, 탈락 이유, 시도, 검증처럼 결과가 만들어진 과정

`current/` 안에는 Spec과 Ticket을 둔다. Spec은 그 작업에서 풀 문제와 이루려는 결과, 그리고 그 결과를 판단할 기준이다. Ticket은 Spec의 기준 안에서 확인 가능한 결과를 만드는 실행 단위다. 둘은 크기가 아니라 맡은 책임으로 나눈다.

Spec은 사용자가 무엇을 할 수 있어야 하는지와 이번 작업에서 하지 않을 것까지 정하지만, 어느 모듈에 넣을지나 기존 추상화를 유지할지 바꿀지는 실제 코드를 보며 정할 몫으로 열어 둔다. 작업을 이어 가는 도구가 구조를 다시 판단할 권한까지 가져가지 않게 하려는 구분이다.

한 작업의 결과가 다른 작업이나 프로젝트 전체의 기준으로 저절로 올라가지도 않는다. 필요한 건 그때 판단해서 가져온다.

## 세션 경계

세션이 바뀌면 그 전까지의 맥락은 자동으로 따라오지 않는다. 그래서 무엇이 어느 방향으로 넘어가는지를 세 동작으로 나눠 두었다. 셋이 함께 막으려는 건 하나다. 다음 세션이 낡은 상태나 근거 없는 완료에서 출발하는 것이다.

**Recover**는 새 세션의 진입이다. 지정한 Workspace의 현재 상태와, 그 작업에 필요하다고 미리 골라 둔 Project 문서만 모아 읽기 전용 묶음으로 만든다. 원자료 전체와 산출물 본문은 기본 입력에 넣지 않는다. 전부를 아는 상태가 아니라 어디서 찾을지 아는 상태로 만드는 게 목적이고, 무엇을 왜 골랐는지는 그 Workspace가 소유한다.

**Maintain**은 반대 방향이다. 작업하면서 달라진 목표, 판단, 진행 상태를 원래 그 내용을 소유한 문서로 되돌린다. 새 세션은 기본적으로 연결되지 않고 사용자가 지정한 Workspace만 연결된다. 의미 판단은 에이전트가 하지만 실제 쓰기는 허용된 문서인지와 그 사이에 파일이 바뀌지 않았는지 검사한 뒤에만 일어나고, 원자료나 제품 코드나 검증 결과는 이 경로로 고칠 수 없다. 뜻이 애매하면 추측해서 쓰지 않고 사람에게 되묻는다.

**Verify**는 증거를 남긴다. 무엇을 주장하는지와 어떤 파일이 그 근거인지 먼저 고정한 뒤, 정해진 명령을 제한된 조건에서 실행하고 결과를 receipt로 남긴다. 실패도 성공과 같은 형식으로 남는다. 검증이 통과했다는 건 기계가 확인한 사실이지 사람의 수락이나 작업 완료를 뜻하지 않는다. 에이전트는 판단하고 반영하되, 무엇을 받아들일지와 언제 끝났는지는 사람이 정한다.

세 동작의 실행 도구는 Python 스크립트지만 그 스크립트가 맥락의 의미를 소유하지는 않는다. 지우거나 다른 것으로 바꿔도 각 문서의 기준과 기록은 그대로 읽힌다. 어떤 실패 때문에 더한 절차는 그 실패가 더는 나지 않으면 걷어낼 수 있어야 한다는 기준을 장치 자체에도 적용한다.

## Skill

읽고 고치는 일 중 반복되는 것은 에이전트가 호출하는 skill로 두었다. 지금은 일곱 가지이고 세 묶음으로 나뉜다. 각자의 호출 조건은 [Reference skill 색인](./reference-project/.agents/skills/README.md)에 있다.

**맥락**

- `read-project-context`: 지금 작업 주제에 필요한 Project 문서만 골라 읽고, 거기 있는 계약과 예외와 현재 차이를 작업에 적용한다. 읽기 전용이다.
- `update-project-context`: 작업 중 확인된 것 가운데 여러 작업에 계속 유효할 의미를 그 내용을 소유한 Project 문서에 반영한다.
- `create-context-workspace`: 새 작업의 Workspace를 만들고, 그것만 읽고 재진입할 수 있는지 검토한다.

**판단**

- `work-discussion`: 구현 전에 이번 작업으로 무엇이 달라져야 하고 무엇을 잃지 않아야 하는지 사용자와 맞춰 Spec과 Ticket으로 구체화한다. 사용자가 직접 부를 때만 동작한다.
- `reconsider-work`: 결과나 조건이 달라졌을 때 현재 방법이 원래 목표를 이루는지 다시 본다. 작업은 끝났는데 원래 하려던 일이 남아 있는지, 기능은 동작하는데 처음 생각도 맞았는지, 기능을 더한 뒤 다음 변경을 더 잘 받을 수 있는지를 함께 본다. 배경에서 말한 판단이 끊기는 자리가 실제로 걸리는 지점이다.

**설명**

- `work-artifact-briefing`: 이미 있는 코드나 변경, 문서, 분석이 전체에서 무슨 역할이고 실제로 어떻게 연결되며 무엇까지 확인됐는지 원자료를 조사해 설명한다.
- `explanation-recovery`: 앞선 설명에서 놓친 뜻이나 지시 대상, 빠진 전제를 찾아 원래 뜻까지 다시 이어 준다.

모든 작업에서 순서대로 실행하는 고정 절차는 두지 않고, 같은 절차가 실제로 반복되는 게 확인되면 그때 새로 더한다.

## 시작

자기 프로젝트에 쓰려면 에이전트에게 대상 경로와 함께 이식을 요청한다. 루트의 `apply-context-harness` skill이 받는다. 필요한 건 세 가지다.

- 대상 프로젝트의 경로
- 허용할 변경 범위
- 첫 Workspace가 다룰 실제 작업 하나

그러면 이 순서로 진행된다.

1. 대상의 기존 지침, 문서, Git 상태를 읽는다.
2. 새로 만들 파일과 건드리지 않을 파일을 manifest로 보여 주고 승인을 기다린다.
3. Project context를 그 프로젝트의 실제 사실로 채우고, 첫 Workspace를 실제 작업으로 만든다.
4. 세 동작의 실행 도구와 일곱 skill을 설치한다. 대상에 이미 같은 역할이 있으면 덮어쓰지 않고 제외 이유를 남긴다.
5. 무엇을 설치했고 무엇을 아직 확인하지 못했는지 보고한다.

예시 프로젝트의 내용은 복사하지 않는다. 자동 Maintain 연결은 설치까지만 하고 어느 세션에 붙일지는 사용자가 따로 켠다. 커밋과 수락은 사람이 한다.

## 구성

- [`reference-project/`](./reference-project/): 위 구조가 실제로 돌아가는 예시 프로젝트다. 작은 샘플 제품과 그 작업 Workspace 하나를 두고, 세 동작과 일곱 skill이 함께 동작하는 모습을 보여 준다. 구조를 따라 읽거나 직접 실행해 보려면 [Reference Project README](./reference-project/README.md)에서 시작한다.
- [`.agents/skills/`](./.agents/skills/): 위 구조를 다른 프로젝트에 이식하는 `apply-context-harness`가 있다.
- [`context/`](./context/): 이 방식을 이 저장소에 스스로 적용한 기록이다. 작업 열두 개가 있고 끝난 것, 보류한 것, 중단한 것이 함께 있다. 접은 작업도 왜 접었는지와 함께 남아 있고, 그 판단이 다음 작업의 출발점이 됐다. 위의 구조는 설계로 먼저 정한 게 아니라 실제 제품 개발을 회고하고 여기서 다시 걸린 문제에서 나왔다.

## 지금 보장하는 범위

결정적으로 확인한 건 고른 맥락만 복구하는 재진입, 허용 조건을 검사한 뒤의 문서 반영, 검증 전 근거 고정과 실패·성공 receipt 생성이다.

아직 확인하지 못한 것도 있다. 에이전트가 실제 변화에서 어떤 의미를 남겨야 하는지, 자동 연결이 실제 도구 환경에서 끝까지 동작하는지, 이 방식이 긴 기간의 맥락 유지에 실제로 효과가 있는지는 증명하지 않았다. 각 항목의 정확한 경계는 [Reference Project README의 증명 범위](./reference-project/README.md#증명-범위)에 있다.

계속 쓰면서 고쳐 나가는 저장소이므로 구조와 skill 목록은 바뀐다. 재사용 허용 범위를 정하는 라이선스는 아직 선택하지 않았다.
