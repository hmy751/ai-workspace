# batch-06 장면 색인

11개 part(인벤토리 207,324자)를 순서대로 읽었다. part-01은 첫 출력이 잘려 140~355행을 재조회해 누락 구간을 메웠고, 나머지 큰 part는 줄 범위로 나누어 읽었다. 별도 corpus 인접 발화는 열지 않았다. 인용은 packet 본문의 정확한 부분문자열로 검증했다.

현재 JSON에서 생성한 색인이다. 독립 검토가 적용된 장면은 승인 경위·보고 주체·미확정을 보강했다. 원문 인용과 대안은 상세 링크에서 함께 읽는다.

## B06-S01 · 토큰 비공개 분리의 범위가 전체 인증 경로와 실패 처리로 넓어짐

사용자는 공개 AuthState의 토큰 보안성을 묻고 기존 정책 보존 가능성을 재차 요구했다. assistant는 처음 위치 이동을 제안했지만 전체 코드·합의 기록 재검토에서 SecureStore 직접 읽기 경로와 저장 실패 후 차단 불일치를 보고했다. 구현 후 262개 테스트 통과를 보고했으나 사용자의 품질 재질문 뒤 로그아웃 삭제 실패 시 공개 상태와 내부 차단 상태가 어긋나는 실패 경로를 발견해 보완하고, 사용자가 요청한 인증 작업 전체 브리핑으로 범위를 넓혔다.

[원문·해석·대안·미확정](../scene-evidence.md#b06-s01)

## B06-S02 · 인증 소비 계약 재검토와 medium 구현의 철회

복원 경로 설명에서 사용자는 저장 정보가 아니라 signed-in 등 상태 소비 기준의 파편화를 지적했다. assistant는 오류 타입·공개 부분 명령·화면 read 정책의 불일치를 제시했다. 사용자의 medium 지시는 서브에이전트 배치였는데 처음 직접 진행으로 오해해 정정했다. 290개 테스트 통과와 새 구조 보고 뒤 사용자는 적절성을 의심하고 마지막 기록 이후 대화를 남기며 직전 변경만 원복하라고 지시했다. assistant는 이전 토큰 분리 작업을 보존하고 266개 테스트 상태로 돌아왔다고 보고했다.

[원문·해석·대안·미확정](../scene-evidence.md#b06-s02)

## B06-S03 · 기록을 통한 다음 세션의 3번 작업 범위 복원

이전 세션 말미 사용자는 과거 대화 원문으로 다섯 단계 중 인증이 3번임을 다음 세션에 전달하도록 했다. assistant는 인계문에 커밋·원복·미확정 범위를 구분했다고 보고했다. 다음 세션 사용자는 Ticket 06과 기록을 확인하게 하고, 다섯 단계 원문을 다시 붙여 현재 코드의 3번 범위를 재확인시켰다. assistant는 HEAD와 미커밋 3·4·5번 혼합 상태를 구별해 설명했다.

[원문·해석·대안·미확정](../scene-evidence.md#b06-s03)

## B06-S04 · 읽기 쉬운 인증 구조 제안에서 실행 순서의 여섯 결함으로 판단 변경

다음 세션에서 assistant는 읽기 기준·복원 검증·명명 변경을 제안하고 270개 테스트 통과를 보고했다. 사용자는 selectLocalUserId와 local-access의 위치를 거듭 물으며 정책은 이해해도 코드에 확신이 없다고 말했다. 전체 재점검에서 assistant는 동시 로그인, 세션 삭제와 저장 경합, 인증 차단 지연, 로그아웃 중 로컬 저장 삭제, 큐 원본 정리, sync 완료 오표시 등 여섯 실패 시나리오를 추가 검사로 재현했다고 보고했다. 이후 파일 위치보다 전체 동작 보장 주체를 기준으로 삼겠다고 정리했다.

[원문·해석·대안·미확정](../scene-evidence.md#b06-s04)

## B06-S05 · 3번 검토 중 4·5번까지 커밋한 범위 이탈과 이후 단계별 승인

사용자가 확정한 책임 기준으로 구현하라고 한 뒤 assistant는 인증·동기화·화면 정책을 세 커밋으로 모두 저장했다고 보고했다. 사용자는 기존의 순차 검토·승인 방식과 현재 3번 범위를 상기시키며 커밋 해제를 요구했다. assistant는 세 커밋만 풀고 작업물은 남겼다고 보고했다. 다음 날 사용자가 인증 범위 커밋을 명시적으로 요청했고, 메인 워크트리 staging 사실을 확인한 뒤 진행을 승인했다. 이후 3·4·5번 커밋은 각각 후속 사용자 지시에 따라 이루어졌다.

[원문·해석·대안·미확정](../scene-evidence.md#b06-s05)

## B06-S06 · Ticket 06 잔여 작업을 사람의 검토 단위로 나누고 1-A·B·C를 진행

다섯 단계 커밋 뒤 Ticket 06 잔여 작업을 1~4로 확인했고, 사용자가 이해 가능한 검토 단위를 요청하자 1번 unknown 안내를 1-A 활성 상태 판정, 1-B 네트워크 이유 표시, 1-C 재확인 행동으로 나눴다. assistant가 처음 이를 커밋 단위와 곧바로 결부하자 사용자는 커밋 보류를 지시했고, assistant는 검토 단위와 커밋 단위를 구별했다. 1-A 설명 후 사용자는 네트워크 깜빡임과 pending 관계를 물었다. 1-C에서는 packages/ui 사용처 점검으로 헤더 내부 중첩 버튼과 테스트 mock 누락을 찾고, 사용자의 내부 recoveryButton 구조 지적까지 반영한 뒤 커밋했다.

## B06-S07 · 온라인 복구 2-A의 구현 복잡도를 사용자·독립 리뷰가 다시 정의

2-A 일정 화면 복구는 재조회 성공 전 캐시 숨김과 여행 전환 방어로 구현됐다고 보고됐다. 사용자는 새 ScheduleScreen 하위 폴더의 위치를 문제 삼아 기능 책임에 맞게 옮기게 했다. React 관점 재검토에서는 기존 13개 테스트가 놓친 중복 조회와 오류 화면 고착을 추가 시나리오로 재현했고 후속 수정했다고 assistant가 보고했다. 사용자는 코드 성숙도와 FSD를 포함한 독립 리뷰를 요구했고, 첫 리뷰가 결함 판정에 치우치자 개선 목표와 새 평가 관점까지 요청했다. 이후 표시 계약과 지도 선택 유지의 개선을 assistant가 보고했지만, 복구 훅 내부의 Promise·캐시 이벤트 추적은 여전히 복잡하다는 질문으로 이어졌다.

[원문·해석·대안·미확정](../scene-evidence.md#b06-s07)

## B06-S08 · 원래 온라인 복구 정책과 후속 구현 선택을 분리해 미확정으로 기록

복구 훅 단순화 논의 중 assistant는 진행 중 GET을 공유하는 방향으로 바로 수정하려 했으나, 사용자가 수정 전 설명과 기존 Ticket·합의 기록 대조를 요구했다. 대조 결과 원래 정책에는 재조회 성공 뒤 표시와 중복 방지가 있지만, 단절 전 요청을 기다린 뒤 새 요청을 보낸다는 문장은 후속 구현 기록이라고 구별했다. React Query, Router, sync의 책임을 다시 검토하면서 구체적인 단순화 후보와 기존 동작 차이를 설명했다. 사용자는 확정하지 않고 Work 기록에 미확정 판단을 남기라고 했다.
