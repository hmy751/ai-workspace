# batch-07 장면 색인

inventory에 지정된 part-01~part-15를 순서대로 모두 읽음. part-01은 초기 출력이 잘려 150~500행을 별도로 다시 읽었고 다른 part는 행 범위로 나눠 출력 누락 없이 읽음. 공개 발화 패킷 범위이며 도구 원출력·코드·커밋은 장면별 명시한 경우 외에는 직접 검증하지 않음. part 경계는 연속된 후속 part의 공개 발화로 이어 확인함.

현재 JSON에서 생성한 색인이다. 독립 검토가 적용된 장면은 승인 경위·보고 주체·미확정을 보강했다. 원문 인용과 대안은 상세 링크에서 함께 읽는다.

## B07-S01 · 후보 수집의 분류축을 사용자 정정으로 변경

사용자는 Project 갱신 이후 Ticket 06의 넓은 후보 수집을 제안하며 카테고리별 서브에이전트를 생각했다. assistant는 처음 제품 주제별 분담을 권했으나, 사용자가 코드 스타일과 common/guidance의 서로 다른 용도를 지적하자 폴더 관점별 동일 자료 조사로 바꿨다. assistant는 4개 보고서 240후보를 수집했다고 보고하고 본문 반영은 아직 하지 않았다고 구분했다.

## B07-S02 · 스타일 기준을 예시와 질문으로 좁히고 Project 소유를 결정

assistant는 수집 후보를 공통 스타일로 올릴 범위와 문서 소유를 물었다. 사용자는 기준별 적용 조건을 먼저 구체화하고, 합의한 주제는 Project에 취합하자고 정했다. void의 뜻을 재질문하며 실행 차이를 이해한 뒤 일괄 규칙을 제외했고, 콘솔 예시의 필요성을 다시 물었다. assistant는 오류 진단 로그 유지 제안을 철회하고 catch의 실제 처리와 기록 목적을 먼저 판단하는 기준으로 고쳤다. 이후 구성안을 작성했다고 보고했다.

[원문·해석·대안·미확정](../scene-evidence.md#b07-s02)

## B07-S03 · 문서가 읽히는 방식과 코드 중복의 유지비용을 재검토

Project 본문 반영 뒤 사용자는 서술이 많아 눈에 들어오지 않는다고 지적하고 독립 리뷰를 요청했다. assistant는 원래 목적과 산출물을 준 리뷰의 한계를 밝히고 인증 가이드를 표·도식 중심으로 편집했다. 사용자가 코드와 중복된 문서의 노후화를 우려하자, assistant는 유지할 판단과 코드에서 바로 복원할 세부를 분리해 같은 문서를 축약했다. 별도 워크트리에서 다른 Project 문서 11편, 이어 작성 당시 근거를 읽고 기존 8편을 개선했다고 보고했다. 사용자는 더 나아졌다고 반응했다.

## B07-S04 · 기록 정리 요청의 실제 목적은 과잉 열람 방지

사용자는 records 분류를 물었고 assistant는 주제별 색인, 이후 하위 폴더 가능성까지 제안했다. 사용자가 진짜 걱정은 작업마다 모든 records를 읽게 되는 것이라고 밝히자 assistant는 구조 재편안을 거두고, Ticket·Spec·Project·코드에서 시작하며 구체적인 판단 공백이 있을 때만 기록을 읽는 기준을 제시했다. 파일 수정은 하지 않았다고 보고했다.

[원문·해석·대안·미확정](../scene-evidence.md#b07-s04)

## B07-S05 · 기존 복구 정책과 미커밋 구현의 차이에서 sync 충돌까지 발견

새 세션은 Ticket 06 기록에서 일정 온라인 복구의 미커밋 상태를 복원했다. assistant는 이전 요청을 새 복구에서 제외하는 조건이 합의보다 강하다고 보고, 사용자 요청에 따라 기존 정책·인증·sync와 대조했다. 임시 검사에서 push 이후 오래된 GET 결과가 남을 수 있다고 보고했다. 이후 사용자 질문으로 기존 커밋에도 오프라인 제한과 온라인 복귀 시 캐시 표시가 이미 있었고, 미커밋 작업은 새 조회 성공까지 숨기는 조건을 추가했음을 분명히 했다. sync와 Query의 현재 동작을 섞어 설명한 점도 정정했다.

[원문·해석·대안·미확정](../scene-evidence.md#b07-s05)

## B07-S06 · 복구를 새 성공 상태로 관리할 필요를 재판단

사용자는 비활성 여행의 캐시가 단절만으로 오래되지는 않는다는 점과 적절한 복잡도를 강조했다. assistant는 기존 제한 화면과 캐시 재표시를 유지하고, 조회 성공을 화면 복귀 조건으로 삼지 않는 방향을 제안했다. 사용자의 질문으로 reconnect 재조회가 이미 꺼져 있고 sync 뒤 무효화와 겹칠 수 있음을 확인했다. 개선 리뷰 뒤 두 조회를 무조건 하나로 합치지 않고, 실제 데이터 변경 후 갱신은 보장하자는 방향을 사용자가 채택했다. 결정은 Workspace에 기록하고 assistant는 2-A 구현과 354개 테스트 통과를 보고했다.

## B07-S07 · 조회 조합의 책임과 배치가 사용처 증가에 따라 다시 바뀜

사용자는 새 useScheduleContent가 Policy·Query와 겹쳐 보인다고 질문했고, 독립 리뷰 후 assistant는 단일 일정 화면에서는 중간 훅을 제거했다. 이후 일정·경비 세 화면에 같은 표시 조합이 반복되자 공통화를 재검토했다. 한 화면 시험 적용에서 사용자가 Query 원본 타입과 정책을 고려하는 refetch를 분리하자고 제안했고, assistant는 query/access/actions/view 구조를 일정 목록 한 곳에 먼저 적용했다고 보고했다. 이름·디렉터리·FSD 의존 관계는 사용자 정정과 리뷰를 거쳐 다시 바뀌었다. 최종 해당 범위의 세 화면 교체와 커밋 b4db89d를 보고하면서 미전환 소비자를 구별했고, 사용자는 현재 Project보다 Workspace 기록을 택했다.
