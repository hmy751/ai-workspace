# batch-03 장면 색인

15개 part의 공개 발화를 순서대로 읽었다. part-01·03·04·10·14의 최초 도구 출력이 잘려 해당 구간을 행 단위로 다시 읽었다. 공개 발화 이외의 도구 출력과 코드·커밋은 독립 검증하지 않았으므로 실행·테스트·문서 상태는 원칙적으로 당시 assistant의 보고로 적었다. part-15 끝은 넓은 코드 재조사 보고에서 끝나며 이후 사용자 반응은 이 batch에 없다.

현재 JSON에서 생성한 색인이다. 독립 검토가 적용된 장면은 승인 경위·보고 주체·미확정을 보강했다. 원문 인용과 대안은 상세 링크에서 함께 읽는다.

## B03-S01 · 첫 사용 버그 조사의 완료 기준을 기능 전체로 다시 잡음

사용자는 로그인 재시도 배너를 예로 들며 개발자의 첫 사용 시나리오 전반을 조사하라고 했다. assistant는 인증과 몇몇 결함을 상세 보고했으나 사용자는 활성화 등 주요 카테고리 전체를 충실히 조사했는지 재차 물었다. assistant는 누락을 인정했지만 곧 티켓 구성으로 넘어가려 했고, 사용자가 조사 선행을 다시 지정했다. 이후 assistant는 39개 관찰 항목과 미확인 iOS 범위를 분리한 확대 조사 결과를 보고했다.

## B03-S03 · 002 완료 범위와 옛 .claude 자료를 합칠 때 기준 본문 소유권을 정함

## B03-S04 · Project의 common·current·guidance와 읽기 경로를 사용자와 구체화

사용자는 새 current 파일이 지엽적으로 늘어나는 점을 문제 삼고 API 공통 계약 안에 Schedule 적용을 충분히 담는 형태를 제안했다. 초기 설계 문서를 추가로 읽힌 뒤, common/current/guidance 폴더는 의도된 구분이며 guidance는 판단과 적용을 포함한 구체적 작업 가이드라고 정정했다. assistant가 API 문서의 실물형 예시를 보여주자 사용자는 긍정했다. current의 존재 이유와 유지비용은 논의했지만 폐기하지 않고 이후 재구성 시험에서 판단하기로 했다. 읽기 스킬과 reference를 새로 구성하고 합의를 records에 남기자는 요청이 뒤따랐다. 사용자는 외부 자료에서 반영할 기준과 current 재시험 방향을 앞선 기록과 별도 record에 남기라고 요청했다. assistant는 Maintain 자동 반영 실패 때문에 record·색인을 직접 작성했다고 보고했다. 실제 저장 및 자동화 상태는 별도 확인 대상이다.
