# batch-05 장면 색인

읽은 범위: `packets/batch-05/part-01.md`부터 `part-10.md`까지 10개 part 전체(두 세션). part-01의 잘린 출력 구간은 다시 읽었다. 도구 출력·실제 커밋 diff는 확인하지 않았으므로 테스트와 구현 결과는 당시 assistant의 보고로 구분한다.

1. **B05-S01 · 앱 준비와 여행 데이터의 구분** — 사용자는 선택 여행 삭제 시 다른 여행으로 전환하도록 정했고, 초기화 변경 브리핑 뒤 “여행이 없으면 DB가 없는가”를 확인했다. assistant는 DB 준비와 여행 row 존재를 구분했다. 질문 자체를 이해 실패로 보지 않는다. (`01a0b2ee-2d11-7b33-ba80-2ceeb380a0ae:906–1112`)

2. **B05-S02 · 코드 스타일 불안을 검토 기준과 적용으로 전환** — 사용자가 변경 파일만 독립 리뷰어에게 주고 기준을 묻게 했다. assistant는 개행보다 실제 보장을 과장한 주석·로그·이름과 테스트 대기 방식 등을 보고했고, 요청에 따라 기준을 적용한 뒤 154개 테스트 통과, 기록 갱신과 커밋을 보고했다. 실제 리뷰 범위와 diff는 확인이 필요하다. (`01a0b2ee-2d11-7b33-ba80-2ceeb380a0ae:1119–1472`)

3. **B05-S03 · sync와 로그아웃의 겹침을 한 계약으로 결정** — “더 물어볼 것”에 assistant가 진행 중 sync의 종료 대기를 제시했고 사용자가 채택했다. assistant는 실패 시나리오 재현, 실행 조건·잠금·종료 순서 구현, 185개 테스트와 커밋을 보고했다. (`01a0b2ee-2d11-7b33-ba80-2ceeb380a0ae:1490–1915`)

4. **B05-S04 · 인증 논의에서 예시가 논점으로 바뀐 뒤 철회** — 재로그인 라우트 충돌은 로컬 이용 정책 논의로 커졌다. 사용자는 unknown이 예시일 뿐이라며 인증의 역할과 부작용을 보라고 정정했고 `ai-self-check`를 요청했다. assistant는 읽기 전용 추천을 철회하고 계정 경계·서버 인증·기록 보존을 다시 나눴다. (`01a0b2ee-2d11-7b33-ba80-2ceeb380a0ae:1933–2228`)

5. **B05-S05 · 상태 이름에서 저장·복원 계약으로 이동** — 토큰 누락, 복원 오류, 로그아웃을 세 상태나 플래그로 설명하는 동안 반례가 이어졌다. 사용자는 프로그램의 실제 값과 전이를 요구했고, 최종적으로 SecureStore 세션 기록, `restore-failed`, `initializing`, 계정별 로컬 이용 조건을 정리했다. 사용자는 이용 기한 없음·다른 계정 전환 시 폐기·로그아웃 중 앱 종료 복구 제외를 선택하고, 과정은 `records`, 현재 기준은 `current`에 남기게 했다. assistant는 정책 문서 커밋과 235개 테스트를 보고했다. (`01a0b2ee-2d11-7b33-ba80-2ceeb380a0ae:2235–3399`)

6. **B05-S06 · unbound 세션을 수동 소급 수집** — 사용자가 evidence-collector 수집 여부를 물었고 assistant는 자동 수집 근거가 없다고 답했다. 수동 수집 지시 뒤 assistant는 원문 교환 75개를 보존했다고 보고했고, 사용자는 수행 주체를 재확인했다. 저장 레코드 검증은 남는다. (`01a0b2ee-2d11-7b33-ba80-2ceeb380a0ae:3413–3653`)

7. **B05-S07 · 구현 후 관리 부담과 기존 테스트의 한계 재검토** — 다음 세션에서 사용자는 235개 테스트가 통과한 구현을 보고도 관리 복잡도를 우려했다. assistant는 Policy·API·세션 저장·DB·sync를 넓게 검토해 연결 결함을 보고했다. 논의 끝에 로컬 기록은 유지하고 재로그인은 같은 계정 인증 복구로 좁혔다. 다른 계정 이용은 명시적 로그아웃 뒤로 옮겼다. 임시 재현과 실제 관리 부담 감소는 추가 검증이 필요하다. (`01a0b4fc-3afa-7462-ae9e-6052b5a9e3c0:9–747`)

8. **B05-S08 · 최신 결정의 문서화와 연결 수정** — 사용자는 구현 전에 대화 전체를 Workspace에 남기게 했다. assistant는 문서 18개를 커밋하고 API 응답, 인증 저장 실패, 계정 전환, Policy·Router·DB·sync 경계를 수정한 뒤 249개 테스트 통과를 보고했다. 실기기와 실제 OAuth 서버 검증은 남았다. (`01a0b4fc-3afa-7462-ae9e-6052b5a9e3c0:755–1771`)

9. **B05-S09 · Policy 축소의 반작용을 사용자 질문으로 수정** — Schedule·Expense 정책에 create/read만 남긴 이유를 묻는 질문에서, 핵심 편집 대상의 CRUD 전체와 실제 수정·삭제 UI 연결이 필요하다는 방향이 나왔다. 사용자는 변수명도 재검토시켰고 assistant는 첫 이름 변경안 일부를 철회했다. 최종 구현과 249개 테스트 통과는 assistant 보고다. (`01a0b4fc-3afa-7462-ae9e-6052b5a9e3c0:1778–2130`)

10. **B05-S10 · 부분 커밋 브리핑에서 빠진 Repository 검사를 발견** — 사용자는 동작 단위로 확인·커밋하려 했다. 첫 라우팅 브리핑은 Router 테스트와 Repository 연결 테스트의 차이를 드러냈다. 커밋 요청 직후 assistant는 1번 범위를 인증으로 잘못 회수했다가 바로 라우팅으로 정정했고, Repository 회귀 검사 5개와 staged diff 독립 검증 뒤 `f0f680e`를 보고했다. (`01a0b4fc-3afa-7462-ae9e-6052b5a9e3c0:2149–3286`)

11. **B05-S11 · DB 직렬화 이해가 재진술과 두 번째 커밋으로 연결** — 사용자는 transaction, SQL의 `COMMIT`·`ROLLBACK`, `pendingWrites`의 Promise P1/P2 분기를 차례로 물었다. 설명을 거쳐 `catch`가 다음 Promise로 오류를 전파하지 않는다는 점을 자기 말로 정리했고, 정확한 변수명 수정과 DB 전용 테스트 분리 후 커밋을 지시했다. assistant는 254개 테스트와 `9936662`를 보고했다. (`01a0b4fc-3afa-7462-ae9e-6052b5a9e3c0:3292–3727`)

평범한 표본 구간은 JSON의 `ordinary_spans`에 세 곳 남겼다. 커밋 마감, 문서 커밋, 파일 목록·도식 요청은 그 자체로 편안함이나 문제의 대리지표가 아니다.

가장 큰 미확정은 **assistant가 보고한 테스트·커밋과 실제 코드·실행 결과의 대응**, 그리고 이식된 Workspace 기록이 뒤 작업에서 어느 정도 판단을 실제로 도왔는지다.
