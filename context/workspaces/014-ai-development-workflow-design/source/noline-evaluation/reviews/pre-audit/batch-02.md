# batch-02 장면 색인

읽은 범위: `packets/batch-02/part-01.md`부터 `part-14.md`까지 14개 part 전체. 출력이 잘린 part-01·09·13은 해당 구간을 다시 읽었다. 이미지, 도구 실행 결과, 실제 커밋 diff는 이 검토에서 확인하지 않았으므로 관련 결과는 당시 assistant의 보고로 구분했다.

1. **B02-S01 · 테스트 기반 결과를 기록하고 다음 작업의 경계를 세움** — 사용자가 설정 결과를 records에 남기고 커밋하도록 한 뒤 다음 작업을 물었다. assistant는 특성화 테스트를 먼저 제시하고 제품 코드 변경 전 완료했다고 보고했다. 기록이 실제 후속 세션에서 읽혔는지는 미확인이다. (`01a08ff3-0e91-7921-afe4-69f0968638ef:1454–1668`)

2. **B02-S02 · CLI 통과 주장과 에디터 오류 사이의 기준을 재설정** — 사용자가 에디터의 오류를 반복 지적했는데 assistant는 별도 CLI 통과와 기존 source 오류를 먼저 설명했다. 테스트 설정 배치를 되돌리고 Cursor TypeScript로 재현했다고 보고한 뒤, 설치 문제를 Jest 오류의 원인처럼 묶은 설명도 정정했다. 스크린샷 내용과 실제 진단 로그는 추가 확인이 필요하다. (`01a08ff3-0e91-7921-afe4-69f0968638ef:1675–2418`)

3. **B02-S03 · 작은 리팩터링을 React 생명주기까지 재정의** — 사용자의 “코드 개찔끔”, React 관점, production 수준 요구에 따라 assistant는 중간 구조를 폐기하고 요청 겹침·unmount 처리까지 넣었다고 보고했다. 다음날 사용자는 request ID 설명을 듣고 “중복 방지”와 “최신 결과만 반영”을 구분해 재진술했다. 실제 코드 품질은 diff 검토가 필요하다. (`01a08ff3-0e91-7921-afe4-69f0968638ef:2632–3021`, `01a09311-8d84-7081-9654-f000305f880e:9–105`)

4. **B02-S04 · 병행 작업 중 Ticket 04의 로그 계약과 커밋 소유 범위** — assistant는 재전파 catch를 없애도 예외 전달은 같지만 조회 오류 로그는 사라진다고 사용자의 질문에 답했다. Ticket 03과 변경이 섞인 작업 트리에서는 Ticket 04의 output hunk만 stage하고 구현·기록 커밋을 분리했다고 보고했다. 실제 포함 범위는 커밋 검증이 필요하다. (`01a08ff3-754d-73a3-9c15-7c2e66d6367b:80–627`)

5. **B02-S05 · Ticket 05의 성급한 검사안에서 Context와 코드의 실제 문제로 회귀** — assistant가 새로운 테스트 방식을 Ticket에 고정한 뒤 사용자는 기존 규칙을 바꿨는지 물었다. 이후 Ticket 설명보다 기존 Context와 실제 코드의 관계, 그리고 각각 무엇이 문제인지 요구했다. assistant가 반복, 검증 누락, 소유권 조건, 문서 차이, 테스트 부재를 분리한 후 사용자는 설명이 나아졌다고 하고 판단을 유보했다. (`01a08ff3-bde0-7bd3-bd92-0dde7abc883d:107–797`)

6. **B02-S06 · 테스트 도구 대안 비교가 채택·기록·첫 실행으로 이어짐** — 사용자는 Vitest·Supertest 추천의 대안과 비용을 비교하고 두 도구의 역할을 더 자세히 물었다. 그 과정에서 assistant는 Node 20의 module mock 가능 조건을 정정했다. 사용자는 조합을 채택하고 트레이드오프를 records에 남기게 한 뒤 테스트 기반부터 실행하도록 했다. assistant는 Node 20에서 첫 route 테스트가 통과했다고 보고했다. (`01a08ff3-bde0-7bd3-bd92-0dde7abc883d:874–1970`)

7. **B02-S07 · 일곱 응답의 특성화와 serializer·Zod 책임 경계** — 일곱 Schedule 응답을 먼저 테스트한 뒤 공통 변환을 적용했다고 assistant가 보고했다. 사용자는 serializer의 위치와 Zod와의 중복을 검토했고, 값 변환과 최종 계약 검증의 분리를 자신의 말로 확인했다. 이후 삭제·activation 응답 검증과 Trip·Expense 직렬화 조각까지 순서대로 구현·기록했다고 보고됐다. (`01a08ff3-bde0-7bd3-bd92-0dde7abc883d:2131–3260`)

8. **B02-S08 · 소유권 결함을 mock과 일회성 PostgreSQL로 나눠 검증** — 사용자 질문으로 부모 Trip, 자식 Schedule, soft-delete의 차이를 설명한 후 Ticket 05의 3번으로 구현했다. assistant는 기존 코드의 실패를 route 테스트로 재현하고, fixture 오류를 고친 뒤 실제 PostgreSQL 통합 검사 네 건이 통과했다고 보고했다. 실제 SQL·DB 격리와 JWT 검사는 별도 근거가 필요하다. (`01a08ff3-bde0-7bd3-bd92-0dde7abc883d:842–3870`)

9. **B02-S09 · 미완료 티켓을 사전 문서화한 뒤 앱 사용 흐름으로 재배치** — 남은 Spec의 티켓 구성에서 05가 빠져 보이자 사용자가 지적했고, 06–17을 구현 전에 만들어야 한다고 다시 확인했다. assistant는 문서 12개를 작성했다고 보고한 뒤, 후속 세션에서 05 완료와 Workspace 003의 담당 관계를 반영해 앱 진입 티켓을 더하고 06–18을 재배치·커밋했다고 보고했다. 이 문서들이 실제 다음 작업에서 얼마나 쓰였는지는 아직 알 수 없다. (`01a09437-64d8-73d2-a37d-d73df45986f7:9–1568`)

평범한 구간도 JSON의 `ordinary_spans`에 세 곳 남겼다. 한국어 테스트 설명 변경, `tsx` 용어 설명, 별도 세션의 Maintain 해제는 그 자체로 만족이나 문제의 증거로 취급하지 않는다.

가장 큰 후속 확인은 **assistant가 보고한 테스트·커밋·Maintain 상태와 실제 실행 근거의 대응**이다. 이 대응이 확인돼야 대화에서 관찰한 판단 변화와 제품·문서 결과를 같은 주장으로 묶을 수 있다.
