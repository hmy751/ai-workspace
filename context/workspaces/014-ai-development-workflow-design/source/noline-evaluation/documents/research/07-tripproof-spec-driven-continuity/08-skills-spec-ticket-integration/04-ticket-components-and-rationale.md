# Ticket 구성요소와 구성 이유

2026-09-08, [Workspace 012](../../../../workspaces/012-skills-spec-ticket-integration/README.md)에서 Matt의 Ticket 양식·근거와 우리 운영의 차이를 제3 리뷰한 뒤, 아래 네 부분을 Ticket의 기본 구성으로 합의했다. [Spec·Ticket 정의와 범위](03-spec-ticket-definition-and-scope.md)를 이어받으며 **Work당 Spec 하나**라는 결정을 유지한다.

**Ticket은 제목 아래 맡은 결과와 범위, 실행 맥락과 접근, 완료 조건과 확인 방법, 현재 상태와 실제 결과를 한 문서에 둔다.** 각 부분의 정확한 제목·순서·세부 필드를 기계적으로 강제하지는 않지만, 필요한 내용을 매번 처음부터 정하지 않도록 기본 구성으로 사용한다. 유용한 내용은 적극적으로 구체화하고, 무관한 내용이나 근거 없는 결정을 억지로 만들지 않는다.

이 문서는 채택한 구성과 이유를 보존하는 연구 산출물이다. 합의 기록 당시에는 Context Harness의 상위 운영 계약이나 v0를 수정하지 않았다. 이후 사용자 요청으로 합의 문서와 최초 v0를 `7fa7bde`에 보존하고, 네 구성을 논의·재판단·설명에 사용하는 안내를 [v0 준비본](v0/README.md)에 반영했다. 상위 계약 수정과 설치는 아직이다.

## 1. 맡은 결과와 범위

이 Ticket을 마치면 무엇이 달라지고, 어디까지 끝내서 넘기는지 적는다. 관련 Spec의 요구를 연결하고, 결과를 오해할 여지가 있으면 제외 범위와 후속 작업의 경계를 구체화한다.

기능 구현이면 실제로 가능해질 동작을 설명한다. 코드 개선이면 바꾸려는 책임·구조와 보존할 동작을 설명한다. 활동이나 파일 변경 목록만으로 맡은 결과를 대신하지 않는다.

이 부분을 단순히 목표라고 부를 수도 있지만, Work 전체의 목표를 다시 작성하는 것으로 읽히지 않도록 이번 Ticket이 맡은 결과를 앞세웠다. Spec의 공통 목표를 복제하지 않고 이번 실행의 책임을 구체화하는 자리다.

## 2. 실행 맥락과 접근

실행에 필요한 Spec 부분, 원자료·코드·앞선 결과, 선행 작업과 막힘을 연결한다. 이번 Ticket에 필요한 현재 설계와 선택 이유, 확인할 가정, 실행하면서 정할 부분도 담는다.

구현을 시작할 수 있을 만큼 구체화하되, 아직 결정하지 않은 구조나 파일별 할 일을 억지로 채우지 않는다. 링크만으로 의미를 이어받기 어렵다면 필요한 핵심 내용도 함께 적는다.

Main의 처음 제안은 실행 입력·의존 관계였다. 제3 리뷰는 그 제목만으로 운영하면 Ticket 안에서 발전시키기로 한 세부 설계와 이유가 들어갈 자리가 불분명해질 수 있다고 지적했다. 이를 모든 경우 Spec이나 별도 문서로 옮기기보다, 실행 맥락과 접근 안에서 함께 다룬다.

## 3. 완료 조건과 확인 방법

무엇이 관찰되면 맡은 결과를 이뤘다고 판단할지, 어떤 자료·실제 동작·테스트·코드 비교로 확인할지 적는다. Spec의 공통 품질 기준을 이번 Ticket의 범위에 구체화한다.

코드 개선에서는 기존 동작의 보존과 구조를 개선한 효과를 각각 확인할 수 있어야 한다. 기존 사례가 통과한다는 사실만으로 책임·중복·변경 부담이 개선됐다고 판단하지 않는다. 반대로 동작 보존 조건이 변경 전에도 통과했다는 이유만으로 무의미한 조건으로 취급하지 않는다.

이 부분은 확인할 기준과 방법을 담는다. 실제 수행 여부와 확인한 결과는 다음 부분에 남긴다. 테스트 목록만으로 완료 조건을 대신하거나 다른 Ticket의 담당 결과까지 이번 Ticket의 완료 조건으로 삼지 않는다.

## 4. 현재 상태와 실제 결과

현재 진행 상태, 실제로 만든 것과 확인한 근거, 막힘·남은 일·미확인을 남긴다. 다른 실행자가 보고한 내용과 직접 확인한 사실이 다르면 그 차이도 드러낸다.

실행 전에는 현재 상태를 짧게 표시하고, 실행하면서 결과를 채운다. 이 Ticket이 어디까지 끝났고 무엇을 근거로 그렇게 판단하는지 다음 주체가 이어받을 수 있게 한다. 매번 긴 작업 일지를 쓰라는 요구는 아니다. 필요한 상세 과정과 변경 이력은 기존 records에 연결한다.

Ticket의 정의와 진행·실제 결과를 같은 본문에 유지하고 Maintain이 갱신하기로 한 [기존 운영 합의](01-discussion-decisions.md)를 구체화한 부분이다. 상태 이름의 고정 목록이나 새로운 갱신 주기를 추가로 정한 것은 아니다.

## Matt의 근거와 우리에게 맞춘 차이

비교 기준은 Matt Pocock의 AI 개발용 스킬 저장소 `068b6e0c62393147daf03530149cdce209c93da8` 판본이다. [to-tickets 실제 지침](https://github.com/mattpocock/skills/blob/068b6e0c62393147daf03530149cdce209c93da8/skills/engineering/to-tickets/SKILL.md)과 [운영 설명](https://github.com/mattpocock/skills/blob/068b6e0c62393147daf03530149cdce209c93da8/docs/engineering/to-tickets.md)을 구별해서 읽었다.

Matt의 핵심 근거는 각 Ticket이 자기 범위의 결과를 확인할 수 있어야 한다는 점과, 실제 착수를 막는 선행 관계를 명시해야 한다는 점이다. 필요한 계층을 연결하는 좁은 동작을 기본으로 삼아, 통합을 끝까지 미루거나 자기 완료 조건이 다른 Ticket의 담당 작업에 기대는 문제를 줄이려 한다. 이 근거는 우리의 맡은 결과·완료 조건·선행 관계를 구체화할 때 이어받는다.

Matt의 로컬 양식은 제목, 만들 동작, 선행 Ticket, 상태, 완료 조건 체크리스트를 담는다. tracker 양식은 해당할 때 상위 이슈 참조를 더한다. 로컬에서는 한 Ticket을 한 파일에 두며, 별도 진행·실제 결과 본문은 없다. `ready-for-agent` 표시는 선행 작업이 없는 상태와 같지 않으며, 실제 착수 가능 여부는 선행 Ticket의 완료로 판단한다.

우리 구성에 그대로 옮기지 않은 차이는 다음과 같다.

- **진행·결과 유지:** Matt의 운영 설명은 분해 이후 실행·배정을 사용자가 맡고, 구현 스킬이 완료 상태를 안정적으로 갱신하지 않아 상태도 운영자가 관리한다고 설명한다. [실제 implement 지침](https://github.com/mattpocock/skills/blob/068b6e0c62393147daf03530149cdce209c93da8/skills/engineering/implement/SKILL.md)에도 Ticket 결과 기록이나 상태 갱신 단계가 없다. 우리는 정의와 진행·결과를 같은 본문에서 이어받기로 했으므로 네 번째 부분을 명시한다.
- **자료 경로:** Matt는 낡기 쉬운 구체적 파일 경로·코드 조각을 피하도록 한다. 우리는 원자료와 실제 결과에 재접근해야 하므로 필요한 입력·근거의 경로를 연결한다. 이미 알고 있는 구현 파일 목록을 미래의 필수 변경 계획으로 불필요하게 고정하는 일을 경계한다.
- **완료 조건:** Matt의 운영 설명은 작업 전부터 통과하는 무의미한 조건을 경계하고 시작 시점의 실패를 확인하도록 권고한다. 우리 코드 개선 작업에서는 새로 이룰 변화와 보존할 동작을 구별한다. 동작 보존 조건은 변경 전부터 통과할 수 있으며, 구조 개선의 근거를 함께 확인해야 한다.

Matt 역시 [code-review](https://github.com/mattpocock/skills/blob/068b6e0c62393147daf03530149cdce209c93da8/skills/engineering/code-review/SKILL.md)에서 요구 충족과 코드 품질을 따로 검토한다. 결과·품질을 중요하게 본다는 이유만으로 우리 구성의 우월성을 주장하지 않는다. 우리 구성은 이미 채택한 문서 운영에 맞춰 실행 판단의 입력과 실제 결과를 Ticket에 이어받도록 명시한 것이다.

## Spec·Ticket·state·records의 관계

Spec은 Work 전체의 결과·공통 계약·판단 기준을 맡는다. Ticket은 관련 Spec을 연결하면서 이번 실행에 필요한 구체적인 설계·범위와 결과를 맡는다. Workspace state는 전체 상황과 다음 행동을, records는 필요한 상세 이력을 맡는다.

Ticket 안의 모든 설계 선택을 Spec으로 올릴 필요는 없다. 여러 실행이 함께 지켜야 할 계약·설계나 Work의 판단 기준을 바꾸는 발견이라면 관련 Spec과 그 판단에 의존한 작업·결과에 반영한다. Ticket 내부에서는 정한 입력을 잠정적으로 신뢰하며 구현과 세부 설계를 이어가는 기존 합의를 유지한다.

문서 갱신과 실행 결과 전달은 기존 Main·Maintain 관계를 따른다. 구성요소를 정한 사실로 새로운 작성 권한, 고정 검토 배치, Ticket별 새 세션 절차가 생기지는 않는다.
