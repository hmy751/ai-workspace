# 07 TripProof spec-driven continuity 분석

## 이 문서의 지위

이 문서는 TripProof의 해결책을 정하는 문서가 아니라, 해결책을 찾기 전에 문제를 정확히 붙잡기 위한 분석 자료다.

주 근거는 `07-tripproof-spec-driven-continuity`의 두 문서다.

- [`spec-driven-retro-conceptual.md`](../../source/07-tripproof-spec-driven-continuity/original/spec-driven-retro-conceptual.md): 문제를 제품, 코드, spec, 평가, context 관점으로 재구성한 주 문서
- [`spec-driven-retro-chronological.md`](../../source/07-tripproof-spec-driven-continuity/original/spec-driven-retro-chronological.md): 같은 문제의 논의가 어떤 순서로 전개됐는지 보조하는 문서

보조 근거는 `05-tripproof-harness-retro`의 [`analysis-2.md`](../../source/05-tripproof-harness-retro/original/analysis-2.md)와 [`source.md`](../../source/05-tripproof-harness-retro/source.md)다. 이 문서는 사용자의 요청에 따라 다른 source와 기존 교차 분석 문서를 근거로 삼지 않는다.

`07` 자체도 아직 실제 TripProof spec, 코드 변화, 제품 원자료, 작업 장면과 주장 단위로 촘촘하게 대조된 문서는 아니다. 따라서 여기의 진단은 후속 논의를 위한 중심 가설이자 현재 근거로 방어 가능한 문제 정리로 다룬다. 해결책의 효과는 별도 적용과 검증이 필요하다.

## 한 문장 진단

TripProof의 핵심 문제는 작업이 끊긴 것이 아니라, 작업을 이어 가는 동안 제품과 코드 구조를 다시 판단하는 감각이 같이 이어지지 않았다는 데 있다.

개별 spec, AC, 테스트, eval은 많은 일을 끝내게 했다. 그러나 그 완료들이 하나의 제품으로 모이고 있는지, 코드베이스가 다음 기능을 받을 만큼 더 설명 가능하고 바꾸기 쉬워지고 있는지, 이전 판단을 언제 다시 열어야 하는지는 같은 강도로 관리되지 않았다.

## 07이 말하는 문제

### 1. 제품 문제: 기능은 닫혔지만 제품 전체의 신뢰는 닫히지 않았다

`07`의 출발점은 “근본 문제는 아직 안 풀렸는데 주변의 spec과 구현은 계속 자랐다”는 불편감이다.

TripProof는 여행 자료를 바탕으로 근거 있는 답을 만들고, 확인한 값만 카드로 남기는 제품이다. 여기서 중요한 것은 개별 기능이 AC를 통과했는지가 아니라 사용자가 실제 여행 검토 상황에서 “이 제품을 믿고 쓸 수 있다”고 느끼는가다.

그런데 spec-driven 흐름에서는 다음이 더 쉽게 완료로 잡혔다.

- 이 slice의 동작이 구현됐는가
- 이 AC가 통과했는가
- 이번 eval 수치가 나왔는가
- 다음 작업으로 넘길 문서가 정리됐는가

반대로 다음 질문은 상대적으로 늦게, 약하게, 또는 별도 회고에서야 열렸다.

- 이 기능들이 사용자의 근본 문제를 같은 방향으로 풀고 있는가
- 개별 예외 처리가 늘면서 제품 의미가 흐려지지 않았는가
- 사용자가 실제로 겪는 흐름이 제품 안에서 대표 흐름으로 구현됐는가
- 화면과 사용자 장면이 장기간 작업 배분에서 사라지지 않았는가

따라서 문제는 “기능을 덜 만들었다”가 아니다. 기능 단위의 완료가 제품 단위의 만족과 같은 말처럼 취급되기 쉬웠다는 점이다.

### 2. 코드 문제: 새 요구를 받았지만 구조가 성숙했다는 판단은 약했다

`07`은 코드베이스가 자랐지만 “계속 키워도 되겠다”는 신뢰가 생기지 않았다고 본다.

당시의 “프로덕션 수준이 아닌 것 같다”는 감각도 배포 준비나 운영 환경이 부족하다는 뜻이라기보다, 기능이 늘어날수록 코드베이스가 다음 기능을 더 잘 받아들일 수 있는 구조로 성숙하고 있는지 확신하기 어렵다는 뜻에 가까웠다.

코드가 성장한다는 것은 파일 수나 조건문이 늘어나는 것이 아니다. 제품 개념의 주인이 분명하고, 예외가 흩어지지 않으며, 같은 종류의 변경을 예측 가능하게 넣을 수 있고, 잘못된 가정을 발견했을 때 일부 구조를 교체할 수 있어야 한다.

TripProof에서는 새 문제가 나타날 때마다 기존 모델이 틀렸는지 묻기보다, 기존 구조 위에 조건, 레이어, 호환 코드, 추가 규칙을 붙여 해결하는 쪽으로 흐르기 쉬웠다. 그런 방식은 당장의 AC에는 유리하지만, 다음과 같은 신호가 반복되면 구조 판단을 다시 열어야 한다.

- 비슷한 예외가 여러 위치에 흩어진다.
- 한 기능 변경이 여러 책임 영역을 동시에 건드린다.
- 새 spec을 이해하려면 이전 임시 결정을 계속 알아야 한다.
- 테스트는 통과하지만 왜 그렇게 동작하는지 설명하기 어려워진다.
- 기존 구조를 유지하기 위한 보조 코드가 제품 로직보다 눈에 띄게 많아진다.

이때 필요한 질문은 “어디에 더 추가할까”가 아니라 “현재 모델이 이 제품 문제를 아직 잘 설명하는가”다.

### 3. Spec 문제: 작업 연속성은 줬지만 판단 연속성은 부족했다

`07`의 가장 중요한 구분은 작업의 연속성과 판단의 연속성이다.

spec은 다음을 잘 보존했다.

- 이번 작업의 목표
- scope와 AC
- 구현해야 할 항목
- 다음 세션이 어디서 시작할지
- 완료로 볼 수 있는 조건

하지만 다음은 같은 방식으로 보존되지 않았다.

- 왜 이 구조와 제품 해석을 택했는가
- 어떤 근거가 약했는가
- 어떤 신호가 나오면 이전 판단을 다시 열어야 하는가
- 닫힌 spec은 동결 기록인가, 살아 있는 계약인가
- 후속 구현이 이전 spec을 무효화하면 누가 어디에 표시해야 하는가
- spec이 코드 구조까지 지휘해도 되는가, 어디부터 구현 판단으로 열어야 하는가

결과적으로 spec은 다음 작업을 시작하게 해 줬지만, 이전 판단을 재검토해야 할 순간에는 오히려 이전 spec과 코드 구조가 전제처럼 승계될 수 있었다.

해결책을 찾을 때 핵심은 spec을 없애는 것이 아니다. spec은 실행 도구로 남겨야 한다. 다만 spec이 누적될수록 제품과 코드 구조를 다시 판단할 권한까지 대신하지 않도록 해야 한다.

`07`이 특히 구분하는 것은 제품 결과를 명확히 하는 것과 내부 구현을 미리 확정하는 것이다. spec은 사용자가 무엇을 할 수 있어야 하는지, 제품에서 어떤 의미가 보존되어야 하는지, 이번 작업의 범위와 하지 않을 것, 실제로 확인해야 할 대표 사용 흐름은 분명히 할 수 있다. 반면 어느 class나 module에 넣을지, 내부 데이터 구조를 어떻게 바꿀지, 기존 추상화를 유지할지 교체할지, task를 어떤 순서와 크기로 나눌지, 기존 코드 중 무엇을 제거하거나 합칠지는 실제 코드를 보며 판단해야 할 수 있다.

### 4. 평가 문제: 완료 판정이 기능 동작에 좁게 머물렀다

`07`은 완료 기준을 둘로 나눈다.

- 제품 행동이 구현됐는가
- 그 구현 뒤 코드베이스가 더 설명 가능하고 확장하기 쉬워졌는가

TripProof의 eval은 첫 번째 질문에는 꽤 강했다. 입력과 출력, A/B, no-op, revert, AC 미성립을 실제 판단에 사용했다. 그러나 두 번째 질문은 자동으로 따라오지 않았다.

필요한 평가는 단순한 테스트 통과가 아니라 다음 두 비교를 포함해야 한다.

- 제품 원자료와 실제 행동의 비교: 구현이 사용자의 원래 문제를 제대로 대표하는가
- 변경 전후 코드의 비교: 이번 변경 뒤 같은 종류의 다음 변경이 더 쉬워졌는가, 더 어려워졌는가

외부 평가 주체나 reviewer를 둘 수도 있지만, 아직 정해야 할 것이 남아 있다. 누가 평가를 발동하는지, 어떤 기준을 고르는지, 평가자가 spec을 반박할 수 있는지, 작업을 멈추거나 다시 열 권한을 어디까지 갖는지가 아직 열린 문제다.

### 5. Context 문제: 많이 보존하는 것과 적절히 읽히는 것은 다르다

`07`은 지속 정보의 문제를 세 갈래로 나눈다.

- 얼마나 오래 보존할 것인가
- 어떤 작업에서 읽힐 것인가
- 현재 어떤 권위를 갖는가

제품 목적, 핵심 도메인 의미, 중요한 제약, 제품 품질 판단, 백엔드와 프런트엔드의 책임 구조, 반복되는 기술 판단 기준, 작업 종류별 workflow는 오래 보존될 수 있다. 현재 코드 구조, 알려진 위험, 임시 호환 계층, 열린 질문은 현재 상태로 갱신되어야 한다. 반면 기능 spec, AC, 구현 plan, 조사 메모, 이번 작업의 테스트 케이스는 작업이 끝나면 다음 작업을 지휘하는 권한을 잃어야 한다.

문제는 모든 것을 큰 context에 계속 넣는 것이 아니다. 새 세션이 모든 것을 아는 상태가 아니라, 이번 작업에 필요한 것을 어디서 찾아야 하는지 아는 상태가 되어야 한다.

## 왜 이 문제가 누적됐나

### 측정하기 쉬운 국소 완료가 전체 판단보다 강했다

AC 통과, 테스트 성공, eval 수치, 체크리스트 완료는 즉시 보인다. 반면 제품이 하나로 수렴하는지, 코드 구조가 다음 기능을 잘 받을 수 있는지는 느리고 애매하며 다시 논쟁해야 한다.

그래서 작업 중에는 국소 완료가 자연스럽게 우선됐다. 이 선택이 매번 틀렸다는 뜻은 아니다. 문제는 국소 완료가 쌓였을 때 전체 제품과 구조를 다시 보는 별도 계기가 충분하지 않았다는 것이다.

`07`은 이 원인을 spec-driven 방식 하나로만 돌리지 않는다. 당시 모델의 한계, 빠른 작업 속도, 제품 자체의 복잡성, 설계 경험을 쌓아 가던 과정도 함께 작용했을 수 있다. 다만 작업 방식 차원에서 가장 선명하게 보이는 비대칭이 국소 완료와 전체 판단의 비대칭이었다.

### 이전 spec과 코드 구조가 재검토 대상이 아니라 전제가 됐다

새 spec은 보통 이전 spec과 기존 코드 구조를 바탕으로 다음 작업을 열었다. 이 방식은 속도를 준다. 하지만 이전 판단의 근거, 불확실성, 무효화 조건이 함께 이어지지 않으면 기존 구조는 “검토해야 할 선택”이 아니라 “이미 정해진 현실”이 된다.

그 결과 새 문제가 생겨도 “이 구조가 아직 맞나”보다 “이 구조 안에 어떻게 넣나”가 기본 질문이 되기 쉽다.

### 재검토 비용이 작업 비용으로 보이지 않았다

spec을 다시 열고, 제품 의미를 다시 묻고, 코드 구조를 바꾸는 일은 당장 느리다. 반면 조건을 하나 더하거나 adapter를 붙이는 일은 빠르다.

하지만 빠른 해결이 반복되면 나중의 변경 비용은 커진다. 이 비용은 한 작업의 완료 기록에는 잘 드러나지 않는다. 그래서 후속 논의에서는 “지금 다시 열어야 할 만큼 위험한가”를 판단하는 신호가 무엇인지 확인해야 한다.

### 문서와 장치의 수명이 관리되지 않았다

작업이 끝난 spec, plan, 조사 메모가 모두 같은 권위로 남으면 다음 작업은 과거의 실행 문서까지 계속 짊어지게 된다. 반대로 필요한 판단 기준이 어디에 있는지 모르면 새 세션은 다시 대화와 임시 요약에 의존한다.

따라서 지속 컨텍스트는 더 많이 쌓는 방식이 아니라 수명, 읽히는 조건, 권위를 분리하는 방식이어야 한다.

## 05가 보조 근거로 보강하는 것

`05`는 `07`의 진단을 “spec과 하네스가 실패했다”는 식으로 단순화하지 않게 해 준다. 오히려 TripProof 안에는 강하게 작동한 부분이 있었다.

첫째, spec-driven 흐름은 실제 결과를 만들었다. `05`는 7개 spec 묶음의 계약 문장 약 480건을 코드와 대조했을 때 대체로 일치했고, 정직성·행동 계약은 거의 유지됐다고 정리한다. 즉 문제는 “spec이 있으니 구현이 안 됐다”가 아니다.

둘째, eval은 장식이 아니었다. spec이 인용한 eval 수치와 경로 26건 중 24건이 보존 사본과 일치했고, A/B 결과는 기본값 선택과 revert 판단에 사용됐다. 실패와 AC 미성립도 성공으로 포장하지 않았다.

셋째, 하네스도 실제로 사용됐다. 하네스 장치 20개 중 19개에서 사용 흔적이 확인됐고, 제품 행동 문제 일부는 테스트로 옮긴 뒤 검토한 이력에서 같은 오류 유형의 재발이 확인되지 않았다.

그런데 `05`가 보여 주는 공백은 장기 운영 쪽이다.

- 활성 spec은 갱신됐지만 닫힌 spec의 이후 지위는 정해지지 않았다.
- 서버와 eval 품질에 집중하는 동안 client와 사용자 장면이 7주간 작업을 받지 못했고, 이 사실이 현재 상태로 잘 보이지 않았다.
- 공식 완료 기록은 대체로 정직했지만, 작업 중 AI의 완료 주장은 사용자의 되물음 뒤에야 간극이 드러난 장면이 있었다.
- spec이 인용한 run은 gitignore 영역에 있었고, 코드 상태가 남은 run artifact 89건 중 73건, 약 82%가 dirty worktree에서 실행됐다.
- 9.5주 동안 기록·하네스 파일을 건드린 커밋이 전체의 약 41%였고, 하네스를 줄이려는 결정이 반복됐지만 장치 수명과 폐기 기준은 충분히 관리되지 않았다.
- AI가 만든 새 용어, 범주, 판정 규칙이 사용자의 현재 이해보다 빠르게 쌓였고, 그 이해를 다음 세션에서 복원할 지속 표면이 부족했다.
- 2.5주 공백 뒤 현재 spec 단계와 diff의 정체를 다시 물어야 했고, 다른 세션에서는 프로젝트의 원래 목적을 이전 대화에서 다시 찾아야 했다.

이 보조 근거를 통해 `07`의 문제는 더 선명해진다. TripProof는 한 작업 안의 계약, 측정, 완료 기록은 강했지만, 여러 주 뒤에도 유효해야 하는 계약 지위, 증거 재현성, 현재 상태, 사용자 이해, 장치 수명은 충분히 이어지지 않았다.

## 해결책을 찾기 전에 확인할 질문

아래 항목은 해결책 요구사항을 확정한 목록이 아니다. `07`이 남긴 설계 질문을 `05`의 운영 공백과 함께 다시 묶은 것이다. 각 항목은 “이렇게 해야 한다”보다 “이 문제가 후속 설계에서 빠지면 같은 현상이 반복될 수 있다”는 확인 지점으로 읽는다.

### 1. 완료 판정은 무엇을 함께 봐야 하는가

`07`은 완료 판정이 요구 동작의 구현 여부에 좁게 머물렀다고 본다. 후속 설계에서는 적어도 두 층이 어떻게 구분되는지 확인해야 한다.

- 제품 행동: 사용자의 원래 문제를 실제 흐름에서 더 잘 풀고 있는가
- 코드 상태: 같은 종류의 다음 변경을 더 설명 가능하고 덜 위험하게 받게 되었는가

이것은 모든 작업에서 큰 리뷰를 하자는 뜻이 아니다. 기능 통과가 제품과 코드 구조의 수렴을 자동으로 보장하지 않는다는 점을 완료 판정 안에서 어떻게 다룰지 묻는 것이다.

### 2. 이전 판단을 언제 다시 열어야 하는가

`07`은 “가끔 전체를 다시 보자”는 말만으로는 재판단이 일어나기 어렵다고 본다. 그래서 구조가 저항하고 있다는 관찰 가능한 신호가 필요하다고 정리한다.

- 같은 제품 규칙을 여러 위치에서 다시 표현해야 한다.
- 간단해 보인 변경이 예상 밖으로 많은 module이나 layer를 건드린다.
- 기존 구조에 맞추기 위해 flag나 예외 조건을 하나 더 만들어야 한다.
- 이 동작을 책임져야 할 분명한 위치가 없다.
- 기능을 추가하기 전에 관련 없는 코드를 먼저 정리해야 한다.
- 기능은 통과했지만 전체 흐름이 파편적으로 느껴진다.
- 새 spec이 상위 제품 목적이나 기존 도메인 의미와 충돌한다.

이 신호가 곧바로 리팩터링을 확정한다는 뜻은 아니다. 기능의 형태나 범위를 바꿀지, 기존 코드 구조를 먼저 다시 볼지, 상위 제품 판단을 수정할지 고르는 판단 지점으로 보는 편이 `07`에 가깝다.

### 3. Spec은 무엇을 정하고 무엇을 열어둬야 하는가

`07`은 spec을 더 약하게 쓰자는 주장이 아니라, spec이 정해야 할 것과 구현 중 판단해야 할 것을 나누자는 주장에 가깝다.

spec이 분명히 해도 되는 것:

- 사용자가 무엇을 할 수 있어야 하는가
- 제품에서 어떤 의미가 보존되어야 하는가
- 이번 작업의 범위와 하지 않을 것
- 실제로 확인해야 할 대표 사용 흐름

실제 코드와 구현 과정에서 열어둘 수 있는 것:

- 어느 class나 module에 넣을지
- 내부 데이터 구조를 어떻게 바꿀지
- 기존 추상화를 유지할지 교체할지
- task를 어떤 순서와 크기로 나눌지
- 기존 코드 중 무엇을 제거하거나 합칠지

핵심 질문은 spec이 부족했는가가 아니라, spec이 실행 도구의 범위를 넘어 제품 판단과 코드 구조 판단까지 고정해 버린 순간이 있었는가다.

### 4. 닫힌 spec은 지금 어떤 지위를 갖는가

`05`는 활성 spec은 구현과 실측에 맞춰 갱신됐지만, 뒤 구현이 닫힌 spec을 무효화했을 때 그 spec의 지위가 분명하지 않았다고 정리한다. `07`도 완료된 spec을 보관하는 것과 다음 작업을 계속 지휘하게 하는 것은 다르다고 본다.

아직 정책을 정한 것은 아니지만, 해결책을 찾기 전에는 닫힌 spec이 다음 중 어디에 가까운지 확인해야 한다.

- 당시 판단을 보존하는 기록인가
- 현재 구현과 계속 맞아야 하는 계약인가
- 후속 변경으로 일부 무효화됐음을 표시해야 하는 자료인가
- 장기 컨텍스트로 승격할 판단을 포함한 자료인가

이 질문이 빠지면 과거의 실행 문서가 현재 판단을 계속 지휘하거나, 반대로 중요한 판단이 어디에도 남지 않을 수 있다.

### 5. 어떤 정보가 지속되고, 언제 읽히며, 어떤 권위를 갖는가

`07`은 보존 기간, 읽히는 조건, 현재 권위를 분리한다. 장기 보존할 정보와 매 작업마다 자동으로 넣을 정보는 같지 않고, 오래 남은 정보가 모두 영구 규칙인 것도 아니다.

검토해야 할 구분은 다음이다.

- 오래 유지할 정보: 제품 목적, 핵심 도메인 의미, 반드시 지켜야 하는 제약, 제품 품질 판단, 반복되는 기술 판단 기준
- 현재 상태로 교체할 정보: 현재 코드 구조와 책임 경계, 알려진 구조적 문제와 위험, 열린 질문, 최근 설계 방향, 임시 호환 계층과 기술 부채
- 작업 뒤 실행 권한을 잃을 정보: 기능 spec과 AC, 구현 plan, 조사 메모, 이번 작업의 구체적인 테스트 케이스

새 세션의 목표도 “모든 것을 처음부터 아는 상태”가 아니라 “현재 작업에 필요한 지식을 어디서 찾아야 하는지 아는 상태”에 가깝다.

### 6. 평가 감각은 어떻게 이어져야 하는가

`07`은 평가 감각도 지속 대상이 될 수 있다고 본다. 여기서 말하는 평가는 단순 테스트 통과가 아니라 제품 원자료와 실제 결과, 변경 전후 코드를 함께 비교하는 판단이다.

아직 정해지지 않은 질문은 다음이다.

- 누가 평가를 발동하는가
- 어떤 작업에 어떤 평가 기준을 불러오는가
- 평가자가 기존 spec 자체도 문제 삼을 수 있는가
- 평가 결과가 작업을 멈추거나 구조를 다시 여는 데 어느 정도 권한을 갖는가

이 문서는 평가자를 두자는 결론을 내리지 않는다. 다만 기능 완성 외의 전체 품질을 어떤 근거와 권한으로 판단할지 정하지 않으면, 제품·코드 구조의 판단이 다시 뒤로 밀릴 수 있다는 문제를 남긴다.

### 7. 문서와 규칙의 수명은 어떻게 다룰 것인가

`07`은 판단을 지속하더라도 문서와 절차가 계속 쌓이는 방식이 되면 안 된다고 본다. 여기서 핵심은 문서를 더 만들지 말자는 것이 아니라, 각 문서와 규칙의 역할이 언제 끝나는지 구분하는 것이다.

후속 설계에서 확인할 질문은 다음이다.

- 상위 제품 컨텍스트는 현재 내용으로 갱신되는가
- 현재 구조와 위험도 과거 기록을 계속 쌓기보다 현재 상태로 교체되는가
- feature spec과 plan은 작업 완료 뒤 다음 작업을 지휘하는 권한을 잃는가
- 작업에서 발견한 내용 중 장기적으로 의미 있는 판단만 별도 지속 컨텍스트로 올라가는가
- 특정 실패 때문에 추가한 절차는 그 실패가 더 이상 재현되지 않을 때 제거하거나 낮출 수 있는가
- 기술 판단 기준은 여러 기능에서 반복해서 필요하고, 지키지 않으면 코드베이스 전체 품질이 나빠지며, 적용되는 상황과 적용되지 않는 상황을 설명할 수 있는가

이 질문은 `05`의 하네스 운영비 문제와도 이어진다. 하네스 장치가 실제로 사용됐더라도, 사용 시점과 폐기 기준이 없으면 문제를 발견할 때마다 문서와 규칙을 더하는 흐름으로 돌아갈 수 있다.

### 8. 05가 보조로 추가하는 운영 질문은 무엇인가

`05`는 `07`의 중심 진단을 보조하되, 해결책을 이미 증명하지는 않는다. `05`에서 추가로 조심해야 할 운영 질문은 다음이다.

- eval 근거가 나중에 같은 코드 상태로 재접근 가능한가
- dirty worktree에서 나온 run을 어떤 범위의 판단 근거로 삼을 수 있는가
- 최종 spec·eval 기록의 정직성과 작업 중 AI 완료 주장 인수 절차를 어떻게 구분할 것인가
- 새 규칙, 문서, reviewer, skill은 언제 읽히거나 실행되고 언제 폐기되는가
- 새 용어와 판정 규칙이 사용자의 현재 이해보다 빠르게 쌓일 때 어디에 현재 상태로 남길 것인가
- client와 사용자 장면처럼 오래 작업을 받지 못한 제품 축을 어떻게 현재 상태에서 보이게 할 것인가

이 항목들은 `05`의 제안 하네스를 채택하자는 뜻이 아니다. `05`의 새 하네스 초안은 적용 효과가 아직 검증되지 않았다.

## 이 정리가 주장하지 않는 것

`07`은 자기 주장의 경계도 분명히 둔다. 이 문서도 그 경계를 따른다.

- spec-driven이 모든 문제의 유일한 원인이라는 뜻은 아니다. 모델의 한계, 작업 속도, 제품의 복잡성, 설계 경험도 함께 작용했을 수 있다.
- spec을 없애자는 뜻은 아니다.
- 모든 작업마다 전체 아키텍처를 처음부터 다시 검토하자는 뜻은 아니다.
- 지속 컨텍스트를 모두 하나의 거대한 문서에 넣자는 뜻은 아니다.
- 지속되는 정보를 모든 세션에 항상 주입하자는 뜻은 아니다.
- 작업이 끝난 spec 파일을 반드시 삭제하자는 뜻은 아니다.
- 현재 아키텍처를 영구 원칙으로 고정하자는 뜻은 아니다.
- 구조 저항 신호를 발견했다고 곧바로 리팩터링을 확정하자는 뜻은 아니다.

`05`까지 함께 볼 때도 조심할 점이 있다. TripProof의 spec, eval, 하네스가 작동하지 않았다는 결론은 맞지 않는다. 한 slice와 한 세션 안에서는 계약, 측정, 완료 기록이 실제로 작동했다. `05`가 보강하는 것은 그 체계가 여러 주 뒤의 계약 지위, 증거 재현성, 현재 상태, 사용자 이해, 장치 수명까지 충분히 관리했는가라는 질문이다.

## 다음 검토에서 확인해야 할 것

이 문서는 문제를 해결 가능한 형태로 정리하지만, 아직 실제 해결책을 채택하지 않는다. 다음 단계에서는 `07`이 남긴 중심 질문을 실제 TripProof 자료에 더 촘촘히 연결해야 한다.

- 실제 spec들이 이전 판단과 구조를 어떤 방식으로 전제했는가
- 조건, 예외, 책임 분산이 코드 변화에서 실제로 어떻게 누적됐는가
- 제품 원자료와 구현 결과 사이에서 어떤 간극이 반복됐는가
- 전체 판단을 다시 열려 했거나 열지 못했던 구체적인 작업 장면은 무엇이었는가
- 어떤 정보는 오래 보존해야 하고, 어떤 정보는 현재 상태로 교체해야 하며, 어떤 작업 문서는 완료 뒤 실행 권한을 잃어야 하는가
- 기능 완성 외에 제품 전체와 코드 구조의 품질을 누가 어떤 근거로 판단할 것인가
- 그 판단이 기존 spec과 구조를 다시 여는 데 어느 정도 권한을 가질 것인가
- 이 판단 장치 자체가 다시 문서와 절차를 누적시키지 않게 하려면 어떤 수명 기준이 필요한가

핵심은 TripProof에 더 정교한 spec을 쓰는 것이 아니다. spec이 주는 작업 연속성은 유지하되, 제품과 코드 구조를 다시 판단하는 연속성을 함께 남기는 것이다.
