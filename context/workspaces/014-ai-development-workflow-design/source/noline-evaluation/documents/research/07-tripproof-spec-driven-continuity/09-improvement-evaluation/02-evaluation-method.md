# 스킬·레퍼런스 개선안을 평가하는 방법

2026-09-09. 문제 분석을 바탕으로 개선한 스킬·레퍼런스·작업 구성을 실제 개발 작업에서 어떻게 평가할지 설명하는 현재 방법 문서다. 기존 11의 상세 방법과 13의 설계 이유·대안·비용 분석을 읽고 사용할 위치에 재구성했다. 새 실험·수치 합격선을 정하거나 개발 효과를 확인한 결과는 아니다.

[전체 구조](01-evaluation-structure.md)는 평가 대상·세 기준·성과 항목·판정·근거·해석 관점의 관계를 보여 준다. 이 문서는 그 구조 안에서 **무엇을 읽고 관찰하며, 어떤 구분으로 판단하고, 결과를 어떻게 비교·기록할지**를 다룬다. 실제 원자료로 끝까지 채운 평가와 일반 개발 사례는 [평가 기록과 적용 예](04-worked-evaluations.md), 외부 방법의 상세 비교와 선택 이유는 [외부 자료 분석](03-external-reference-analysis.md), 원래 문제와 개입 판본·검사 범위는 [문제·개입 근거](05-problem-and-intervention-basis.md)에 있다.

## 평가 대상과 방법의 범위

평가 대상은 **05·07 문제 분석을 바탕으로 사용자가 개선한 스킬·레퍼런스·Spec·Ticket·맥락과 판단 전달의 구성**이다. 목표는 그 개선안이 문제에 맞게 만들어졌는지, 실제로 의도한 판단과 행동을 만드는지, 개발 결과에도 도움이 되는지를 여러 작업에서 평가하고 설명하는 것이다. 여기서 범용성은 이 개선안을 기능 개발·리팩토링·버그 수정 등 서로 다른 작업과 프로젝트에서 평가할 수 있다는 뜻이다. TripProof는 문제의 출발 근거이며 TripProof와 Noline은 활용 사례 후보다.

일반적인 개발 품질 기준은 이 개선안의 효과를 판단하는 데 사용한다. 스킬·레퍼런스가 원래 문제와 어떻게 연결되며 실제로 작동하는지의 검토도 함께 필요하다.

개발 결과를 볼 때는 기존 세 기준을 유지한다. **요구한 개발 결과가 충분한가**, **코드 품질과 후속 변경 용이성이 나아졌는가**, **사람이 이해·판단하며 결과까지 가는 부담은 어떻게 달라졌는가**다. 여기에 각 방향의 관찰 질문과 판정 근거를 붙인다. 종합 점수와 공통 수치 합격선은 채택하지 않았다. 개선안의 구성 검토·행동 확인과 이 세 결과 방향은 서로 다른 질문에 답한다.

코드·실행 결과는 개발 결과의 변화를 뒷받침한다. 중요한 판단이 해석·수정·구현·검증에 이어진 기록은 AI 작업 방식의 기여를 설명한다. 정성 분석, 실행 확인, 직접 측정, 사용자 경험은 각각 확인할 수 있는 내용에 맞춰 함께 쓴다. 회사 글이나 논문이라는 출처 종류 자체에 우선권을 고정하지 않는다.

## 기존 분석에서 유지할 판단

[01](../01-problem-analysis.md)은 개별 완료와 제품 목표의 충분성, 구조의 성장과 변경 가능성, 작업 재개와 판단의 재검토를 구별했다. [04](../04-conversation-scene-analysis.md)는 필요한 정보와 사용자 정정이 있었어도 실제 구현·완료에 이어지지 않은 장면을 보존했다. 따라서 완료 티켓·테스트·문서의 개수만으로 이 문제의 개선을 판정할 수 없다.

[05 최종 분석](../../../source/05-tripproof-harness-retro/original/analysis-2.md)과 [문제·개입 근거](05-problem-and-intervention-basis.md)에 기록된 기존 체계의 강점도 보존한다. 명시한 범위, 검사와 계약, 근거 추적이 실제로 도움이 된 부분을 없애는 것을 개선으로 가정하지 않는다. 상황이 달라져 판단을 바꾼 것과 이전 판단을 잊어버린 것도 구분한다.

이 분석은 평가 질문의 도출 근거다. 여러 개발 환경에서 해당 문제가 얼마나 자주 발생하는지에 대한 통계는 아니다.

## 개선한 내용과 평가할 변화의 대응

평가할 판본은 실제 적용 시 명시한다. 아래는 [2026-09-09 당시 확인한 구성](05-problem-and-intervention-basis.md)과 08 준비본의 네 스킬·공통 설명 기준을 대조한 평가 대상 지도다. 형제 Reference 전체를 적용하면 추가 Decision 기준 등 포함된 변경도 기록한다. 전체 기반과 특정 스킬 추가분의 효과는 실제 적용 범위에 맞춰 설명한다.

| 개선한 부분 | 원래 문제에서 기대하는 변화 | 여러 작업에서 공통으로 관찰할 것 |
| --- | --- | --- |
| `work-discussion`과 Spec·Ticket 구성 | 원하는 결과와 실행 조각의 관계를 분명히 해, 겉보기 완료로 핵심 수행을 대신하지 않는다. | 결과를 바꾸는 선택·보존 조건·미확정이 구분되는가. 나눈 작업을 합치면 필요한 결과를 맡는 책임이 있는가. 문서와 후속 구현이 그 뜻을 유지하는가. |
| `reconsider-work` | 새 결과·조건·변경 부담에서 현재 계획과 가정을 다시 판단한다. | 구현이 빠진 경우와 원래 가정이 부족한 경우를 구별하는가. 유지할 근거가 있으면 유지하고, 바꾸면 관련 기존 결과까지 확인하는가. 제안이 채택된 뒤 실제 행동이 달라지는가. |
| `explanation-recovery` | 뜻이 끊긴 설명을 복구하면서 오류·조건·한계를 숨기지 않는다. | 원래 뜻과 지금 정정한 부분이 구분되는가. 실제 질문에 답하고 사람이 판단할 차이를 드러내는가. 재설명 과정에서 새로운 오해나 불필요한 전체 재논의를 만드는가. |
| `work-artifact-briefing`과 공통 설명·근거 기준 | 작업물의 역할·실제 연결·확인 범위를 이해할 수 있게 한다. | 파일·검사 개수보다 실제 책임과 흐름을 설명하는가. 설계·소스·실행·미확인의 근거 범위를 지키는가. 다음 판단에 필요한 이해를 사람이 얻었는지는 별도로 확인한다. |
| Workspace·Project context·Main과 Maintain의 전달 | 회복한 판단이 문서와 다음 실행에서 다시 빠지지 않게 한다. | 채택한 의미가 담당 문서에 실제 반영되고 다음 실행에 이어지는가. 현재 답과 과거 판단, 접수와 반영 완료를 구분하는가. 관련 없는 문서 갱신이나 재조사가 늘어나는가. |

기대 행동의 내용은 각 스킬의 문장을 그대로 채점 정답으로 삼아 도출하지 않는다. 원래 목표·사용자 선택·코드와 실제 결과를 먼저 대조해 해당 판단이 적절했는지 평가한다. 스킬 문구를 충실히 따랐어도 문제를 놓치거나 불필요한 개입을 만들면 개선안을 재검토할 근거다.

## 설계 이유·대안·비용을 함께 검토한다

### 작업을 나누더라도 전체 결과를 맡는 책임을 남긴다

원래 문제는 작업을 작게 나누거나 검사하는 행위 자체가 아니었다. [05 최종 분석의 강점](../../../source/05-tripproof-harness-retro/original/analysis-2.md#먼저-확인된-강점)은 계약과 코드의 대조, 실험에 따른 채택·되돌림, 반복 행동의 테스트화를 확인했다. [07 회고 원문](../../../source/07-tripproof-spec-driven-continuity/original/spec-driven-retro-conceptual.md#왜-긴-작업에서-국소-완료가-전체-판단을-밀어냈나)은 그 강점과 별개로, 즉시 확인할 수 있는 부분 결과가 원래 제품·코드 목표의 충분성을 대신했다고 분석했다.

실제 서버 리팩터링 대화에서도 사용자는 서버 흐름과 이름을 이해하기 어렵다고 설명했고, AI는 “판단 흐름을 사람이 읽을 수 있는 실행 구조”를 목표로 다시 잡았다. 사용자는 원래 목표에 부합할 때까지 계속하라고 했다. 그러나 AI는 route 분리와 이름 정리 뒤 테스트 통과를 보고하며 종료했고, 사용자의 재질문 뒤에야 같은 목표에 속한 잔여 문제를 다시 열었다. [실제 평가 기록](04-worked-evaluations.md)에 발화와 코드 근거를 보존했다.

현재 구성은 **Work 전체의 문제·결과·공통 판단을 Spec에, 이번 실행의 결과·접근·확인·실제 상태를 Ticket에 연결**한다. Spec은 작업 전체를 정의하는 문서이고 Ticket은 그 안에서 확인 가능한 결과를 만드는 실행 단위다. Ticket을 완료해도 다른 Ticket이나 전체 목표의 완료까지 대신 판정하지 않는다. 기반만 맡은 Ticket이라면 실제 수행을 맡을 후속 작업과 연결을 드러낸다. 이 관계는 [작업 논의 스킬의 Spec·Ticket 본문](../08-skills-spec-ticket-integration/v0/payload/.agents/skills/work-discussion/SKILL.md#work의-정의를-spec으로-구체화한다)과 [현재 구성 현황](05-problem-and-intervention-basis.md)에서 확인된다.

이 선택의 이유는 작업을 더 자세히 적기 위해서가 아니다. “자료 업로드 route를 분리했다”는 실행 결과가 “서버의 판단 흐름을 읽고 변경할 수 있게 됐다”는 목표를 어느 범위까지 뒷받침하는지 다시 볼 위치를 남기는 데 있다. 현재 코드가 답할 세부 설계는 구현자가 정하며, 작업 전체의 완료 범위를 줄이는 선택은 별도로 드러나야 한다.

비용도 있다. Spec과 Ticket이 같은 내용을 복제하거나 실제 결과보다 늦게 갱신되면 두 문서를 맞추는 부담이 생긴다. 작은 실행의 내부 설계를 모두 공통 계약으로 올리면 다음 수정도 어려워진다. 따라서 평가에서는 문서가 존재하는지만 보지 않고, 실제로 빠진 책임을 찾는 데 사용됐는지, 복제·갱신 비용이 어떤 판단에 쓰였는지 본다. `work-discussion`은 사용자가 직접 호출할 때의 예방적 논의 보강이다. 일반 작업에서 호출되지 않았다는 사실은 이 스킬의 판단 실패가 아니다.

### 결과가 부족한 이유에 따라 고칠 위치를 고른다

이미 합의한 판단을 다시 적는 것만으로는 충분하지 않았다. 위 리팩터링에서 넓은 목표는 대화에 존재했고, spec-driven 스킬도 금지돼 있었다. 따라서 “spec 문구가 부족했기 때문”이나 “사용자가 더 명확히 말했어야 했다”만으로 이 장면을 설명하기 어렵다. 다만 원래 목표가 넓었던 만큼, 어디까지 개선하면 충분한지 작업 중 구체화할 여지는 있었다.

현재 [`reconsider-work`](../08-skills-spec-ticket-integration/v0/payload/.agents/skills/reconsider-work/SKILL.md)는 기대와 결과의 간극, 새 조건, 누적된 변경 부담에서 원래 목표·선택 이유·실제 결과·관련 작업을 대조한다. 이미 정한 수행이 빠졌다면 목표를 유지하며 빠진 일을 채울 수 있다. 정한 설계를 충실히 따라도 원하는 결과가 어렵다면 그 가정과 의존한 기존 결과를 다시 볼 수 있다. 어느 쪽이든 새 구조를 만드는 것이 자동 정답은 아니다.

예를 들어 “업로드 실패 유형을 추가할 때마다 업무 처리와 기록 모듈의 문자열을 함께 수정해야 한다”는 관찰이 나오면, 실패 분류가 실제로 같은 규칙인지부터 확인한다. 같은 의미가 중복된 것이라면 책임을 모을 이유가 있지만, 외부 기록 형식과 내부 처리 의미가 달라 번역이 필요한 것이라면 두 책임을 유지할 수 있다. 새로운 예외가 생겼다는 사실과 기존 설계를 바꿔야 한다는 결론 사이에 이 판단이 필요하다.

재판단 결과는 제안이며, Main이 채택한 판단과 같지 않다. 채택 뒤에는 해당 Spec·Ticket·현재 상태에 필요한 의미가 반영돼야 하고, 문서를 읽는 다음 실행자의 행동까지 이어지는지 확인해야 한다. **스킬이 적절한 답을 냈는데 Main이 채택하지 않은 경우, 문서 반영이 빠진 경우, 다음 구현이 따르지 않은 경우는 수정할 위치가 다르다.** 현재 준비본의 [반영 관계](../08-skills-spec-ticket-integration/v0/payload/.agents/skills/reconsider-work/SKILL.md#필요한-맥락을-가져와-무엇을-유지하고-바꿀지-정하라)는 이를 구분한다.

비용은 불필요하게 작업을 다시 여는 데서도 발생한다. 국소 버그가 원래 계약 안에서 해결되는데 상위 목표와 모든 문서를 다시 검토한다면, 판단은 길어지고 사용자는 같은 선택을 반복한다. 기대할 변화는 재판단 횟수의 증가가 아니라, 실제 근거에 맞는 유지·수정·범위 변경과 그 실행이다.

### 사람이 이해할 설명과 실제 수용을 구분한다

완료 보고가 파일·커밋·검사 목록에 머물면 사람은 무엇이 달라졌고 무엇을 더 판단해야 하는지 다시 추론해야 한다. 그렇다고 설명을 짧게 만들기만 하면 이미 남아 있는 실패·호환·미확인 조건이 가려질 수 있다.

현재 [`work-artifact-briefing`](../08-skills-spec-ticket-integration/v0/payload/.agents/skills/work-artifact-briefing/SKILL.md)은 작업물의 역할, 대표 흐름, 실제 연결과 근거 범위를 조사해 설명한다. [`explanation-recovery`](../08-skills-spec-ticket-integration/v0/payload/.agents/skills/explanation-recovery/SKILL.md)는 앞선 응답에서 뜻이 끊겼는지, 주장 자체가 잘못됐는지 구분해 복구한다. [공통 설명·근거 기준](../08-skills-spec-ticket-integration/v0/payload/context/project/guidance/explanation-and-evidence-criteria.md)은 과거 의도, 소스상 구조, 실제 실행, 검사가 확인한 조건, AI 해석과 사람 판단을 구별한다.

이 구성은 설명을 읽은 사람이 다음 선택을 할 수 있게 하려는 설계다. 설명을 제공했다는 사실이나 사용자의 짧은 동의를 이해 개선의 결과로 저장하지 않는다. 사람의 실제 질문·검토·수정과 경험은 별도 자료다. 설명할 때마다 모든 코드를 재조사하거나 전체 구조를 펼치는 비용, 잘못된 완료를 더 설득력 있게 포장하는 위험도 평가해야 한다.

### 더 단순한 대안으로도 같은 결과를 만들 수 있는가

과거 대화에서 실제로 확인되는 대응은 목표를 다시 설명하고, 첫 구조화 범위를 정하고, 테스트를 유지하며, 조기 종료 뒤 사용자가 추가 진행과 별도 목표 리뷰어를 요청한 것이다. 이번 네 스킬과 같은 대안을 당시 전부 비교했다는 근거는 없다. 다음은 **기존 평가안 구체화 과정에서 비교한 대안**이다.

| 대안 | 충분할 수 있는 조건 | 이번 구성과 비교할 남은 차이·비용 |
| --- | --- | --- |
| 기존 지침에 “전체 목표까지 확인하라”를 강화한다 | 문제가 단순 누락이고 완료 시점에 해당 기준이 실제로 읽히며 결과와 대조된다 | 당시에도 목표가 다시 설명된 뒤 종료가 좁아졌다. 문장 강화만으로 판단·반영·다음 실행이 이어지는지는 미확인이다. 별도 스킬보다 운영은 가볍다. |
| 빠진 결과를 테스트로 추가한다 | 크기 제한, 상태 전환, 입력별 출력처럼 요구를 관찰 가능한 검사로 표현할 수 있다 | 동작 누락에는 직접적인 방법이다. 어떤 구조가 다음 변경을 어렵게 하는지, 사용자가 잘못된 완료를 이해했는지까지 같은 테스트가 답하지는 않는다. 검사 자체의 유지비도 생긴다. |
| 완료 보고와 설명만 개선한다 | 구현은 충분하고 사람이 결과·한계를 찾는 데만 어려움이 있다 | 사람의 검토를 도울 수 있다. 구현 누락이나 잘못된 책임 배치를 설명만으로 고치지는 못한다. |
| 사람이 매번 전체 결과를 재검토하거나 별도 리뷰어를 둔다 | 검토자가 원자료와 코드에 접근하고 실제로 부족한 결과를 다시 열 수 있다 | 과거에는 사용자의 재질문이 이 역할을 했다. 검토 대기·반복 설명·잘못된 지적의 비용이 있으며, 리뷰 제안의 반영까지 저절로 이어지지는 않는다. |

현재 스킬·문서 구성이 **유일하게 가능한 해법이라는 근거는 없다.** 더 단순한 방법이 같은 판단과 결과를 더 적은 부담으로 만든다면 그 방법을 유지하거나 구성 일부를 줄일 이유가 된다. 지금 지지할 수 있는 것은 원래 문제의 판단 지점과 현재 설계의 책임이 대응한다는 점이다. 어느 방법이 실제로 더 도움이 되는지는 이 문서의 구성·행동 검토와 세 평가 기준으로 확인한다.

## 설계와 실제 판단·작동을 확인하는 방법

**먼저 구성과 설계 이유를 검토한다.** 원래 문제마다 누가 어떤 판단을 맡고 어디에 반영하는지, 실제 스킬·참조·상위 계약에 그 관계가 있는지 대조한다. 호출 조건·읽을 자료·역할 경계가 맞물리는지, 이전 지침과 충돌하거나 책임이 비는지, 불필요한 개입·문서·이해 부담을 만드는지 살펴본다. 형식·링크·설정 검사와 의미 검토를 함께 사용한다. 이미 수행한 검사는 [개입 판본·검사 범위](05-problem-and-intervention-basis.md)에 있으며, 기록된 검사 범위를 넘어 효과를 확인했다고 주장하지 않는다.

**실제 판단과 행동은 다른 내용의 작업 상황에서 확인한다.** 원래 문제가 드러낸 중요한 구분은 유지하고 프로젝트·기술·표현을 바꿔, 특정 예시의 답을 반복하는지와 현재 근거로 판단하는지를 확인한다. 과거 장면의 재검사와 새 상황의 적용은 구별한다.

다음은 프로젝트에 묶이지 않는 시험 상황 후보다. 전체를 매번 실행하는 고정 시험 묶음은 아니다.

| 바꿔 제시할 상황 | 확인하려는 판단 | 함께 보존할 대비 |
| --- | --- | --- |
| 일부 구현·검사는 완료됐지만 목표의 핵심 수행이 남은 작업 | 실제 책임과 후속 작업을 확인해 누락 여부와 다음 행동을 판단하는가 | 준비 작업만 맡고 후속 책임도 분명한 경우에는 정당한 부분 완료를 인정해야 한다. |
| 결과가 부족한 작업에서 구현 누락 또는 설계 가정의 오류를 제시 | 증거에 따라 수정할 위치와 판단 범위를 구분하는가 | 국소 수정으로 충분한 경우를 전체 재설계로 키우지 않아야 한다. |
| 유사한 변경이 누적되면서 책임·예외가 흩어지는 작업 | 결과의 동작과 구조의 변경 부담을 각각 평가하는가 | 필요한 책임 분리·호환 제약을 단순 중복으로 없애지 않아야 한다. |
| 사용자가 설명의 연결을 이해하지 못하거나 실제 오류를 지적한 상황 | 뜻의 복구와 주장 정정을 구분하고 필요한 답을 제공하는가 | 짧은 동의나 침묵을 이해 완료로 처리하지 않아야 한다. |
| 중요한 선택이 바뀐 뒤 문서 갱신과 다음 실행이 이어지는 작업 | 채택·실제 반영·후속 행동을 구분해 의미가 이어지는가 | 다음 작업에 필요하지 않은 모든 갱신을 기다리거나 매번 재승인을 요구하지 않아야 한다. |

검토용 시험에는 판단을 가르는 원자료와 조건을 제공하고, 기대 결과는 정확한 문구보다 선택의 적절성·누락·근거·실제 반영으로 본다. 구현·문서 반영이 없는 읽기 전용 시험은 판단 제안까지만 확인한 것으로 남긴다. 실제 사람의 이해나 개발 결과는 뒤의 실제 작업 관찰로 확인한다.

**실제 작업에서는 아래 세 결과 방향과 비용을 본다.** 구성 검사와 첫 응답 시험이 통과해도 효과를 대신 입증하지 않는다. 반대로 한 번 좋은 코드가 나왔다는 사실만으로 개선안 전체의 기여를 확정하지 않는다. 여러 작업에서 어떤 구성과 판단이 도움이 됐고 어느 부분이 작동하지 않았는지를 누적한다.

## 실제 개발 결과에 사용할 세 평가 기준

### 1. 요구한 개발 결과가 충분한가

작업의 목표와 실제 산출물을 대조한다. 작업이 더 큰 제품의 일부라면 이번 범위에서 맡은 결과와 아직 남은 제품 문제를 구분한다. 작업 도중 목표가 바뀌면 바뀐 이유와 범위를 함께 남긴다.

관찰 질문은 다음과 같다.

- 핵심 동작이나 해결하려던 문제가 실제 결과에서 확인되는가? 중요한 예외·실패 조건도 다뤘는가?
- 이번 범위의 완료와 상위 목표의 달성을 구분했는가? 남은 문제를 알고도 전체 완료로 보고하지 않았는가?
- 확인 방법이 해당 문제를 실제로 드러낼 수 있는가? 검사의 개수보다 검사가 확인하는 동작과 빠진 범위를 설명할 수 있는가?

**충분하다고 판단할 근거:** 요구와 결과가 대응하고, 중요한 미충족 사항을 확인할 수 있는 코드·실행·검토 자료가 있다. 의도적으로 미룬 부분은 이유와 영향이 드러난다. 목표상 필수인 부분을 미룬 경우에는 해당 목표가 미충족임을 함께 판단한다.

**개선이라고 판단할 근거:** 기존에 누락·오류·오해가 있던 부분이 구체적으로 해결됐거나, 처음 완료 보고 이후 필요한 교정이 달라졌음을 비교할 자료가 있다. 기능이 동작해도 실제 사용자의 가치가 검증된 것인지는 별도로 밝힌다.

사용할 수 있는 자료는 요구·범위와 그 변경 기록, 실행 결과와 검사의 의미, 중요한 실패 재현, 첫 완료 당시 산출물과 최종 결과다. 자동화가 부적합한 부분은 직접 실행·검토로 확인할 수 있다.

**판단을 바꾸는 관찰과 정당한 부분 완료:** 화면과 파서·저장 인터페이스가 있어도 이번 목표가 실제 저장까지였다면, 저장이 호출되지 않는 결과는 전체 요청의 충족을 뒷받침하지 않는다. 반대로 원래 범위가 다른 팀에 넘길 파서 라이브러리였고 입출력 계약·소비자·후속 저장 책임이 분명하다면 저장을 직접 하지 않았다는 이유로 미완료로 판정하지 않는다. 준비와 실제 수행의 차이는 원래 맡은 책임에 따라 해석한다.

**판정을 유보할 조건:** mock을 사용한 검사만 있으면 그 검사에서 확인한 계약과 실제 환경의 완료를 구분한다. 결과를 본 뒤 새로 정한 정책은 처음부터 있었던 요구의 누락으로 계산하지 않는다. 당시 그 정책을 미정으로 둔 채 완료한 것이 적절했는지는 당시 범위와 불확실성 처리로 판단한다. 현재 동작을 확인했어도 이전 상태의 자료가 없으면 충족과 개선 여부를 따로 남긴다.

### 2. 코드 품질과 후속 변경 용이성이 나아졌는가

코드를 읽고 수정하는 사람이 무엇을 알아야 하는지와, 그 지식이 코드·설계에 어떻게 드러나는지 본다. 현재 필요한 책임의 분리, 값과 상태의 의미, 예외와 의존 관계, 표현의 명료함을 함께 검토한다.

관찰 질문은 다음과 같다.

- 중요한 규칙을 어디서 판단하는지, 값과 상태가 어떻게 변하는지, 실패를 누가 처리하는지 코드에서 설명할 수 있는가?
- 같은 이유로 함께 바뀌어야 할 규칙이 흩어져 있거나, 한 곳의 변경이 무관한 책임까지 흔드는가? 공통점과 의도적인 차이를 구분했는가?
- 추상화·예외·타입 단언·호환 처리에 현재 근거가 있는가? 이름·주석·설정이 실제 동작과 맞는가?
- 다음 수정의 위치와 영향을 예상할 수 있는가? 실제 변경을 수행했다면 예상과 결과는 어땠는가?

**품질 판단의 근거:** 문제인 코드 표현·호출 관계를 특정하고, 왜 이해나 변경을 어렵게 하는지 설명한다. 변경 후 그 어려움이 어떻게 줄었는지 보여주며, 기존 동작의 보존과 새 구조의 비용을 함께 검토한다. 단순한 스타일 선호와 기술적 이유를 구분한다.

**변경 용이성 주장에 더할 근거:** 실제 후속 요구의 탐색·수정·검증 결과, 예상 밖의 영향, 발생한 회귀와 추가 도움이다. 코드 검토만 했다면 구조에 관한 판단으로 보고한다. 실제 후속 변경을 수행하기 전부터 변경 시간 절감을 주장하지 않는다.

파일·함수 길이, 결합도·복잡도, 중복 수치는 관련 문제가 있을 때 보조로 쓸 수 있다. 작은 수정이라도 필요한 검증을 생략했거나 의미가 흐려졌으면 개선으로 인정하지 않는다. 단순해진 코드에서 필요한 동작이 빠진 경우도 함께 판정한다.

**판단을 바꾸는 관찰과 유지할 차이:** 파일은 작아졌지만 여러 진입점이 여전히 같은 정책을 다르게 판단하거나, 새 공통 함수의 flag 안에 기존 중복 분기를 옮겼을 뿐이라면 책임이 명확해졌다는 주장은 지지되지 않는다. 반대로 관리자 요청과 일괄 처리의 재시도·저장 단위처럼 실제 실행 제약이 다르면 그 차이를 유지해야 할 수 있다. 코드량 감소를 위해 필요한 호환·실행 차이를 없애 기존 동작을 깨뜨렸다면 개선으로 보지 않는다.

**판정을 유보할 조건:** 코드 검토는 규칙의 위치·의존·표현에 대한 판단을 뒷받침한다. 실제 후속 변경의 시간·실수 감소는 변경 기록이 있어야 한다. 한 파일만 고친다는 조건도 보편 합격선은 아니다. 필요한 테스트·타입·호환 처리를 함께 고치는 것은 규칙의 책임이 불필요하게 흩어진 것과 다르다.

### 3. 사람이 이해·판단하며 결과까지 가는 부담은 어떻게 달라졌는가

사람이 요구와 설계를 판단하는 일, 결과를 검토하는 일, AI의 누락을 교정하는 일, 도구·문서를 관리하는 일을 실제 내용에 따라 살펴본다. 필요한 참여를 모두 줄여야 한다고 가정하지 않는다.

관찰 질문은 다음과 같다.

- 사람은 현재 문제·선택 이유·완료 범위·다음 판단을 이해할 수 있는가? 설명에 만족한 것과 실제로 경로·원인·변경 영향을 설명하거나 수정한 결과는 어떤 관계인가?
- 중요한 정정이나 재판단이 실제 작업에 이어졌는가? 같은 이유를 반복해서 설명하거나 이미 해결한 문제를 다시 조사해야 했는가?
- 결과를 수용할 때까지 어떤 검토·교정·대기·도구 관리가 필요했는가? 품질이 좋아지는 대신 추가된 부담은 무엇인가?

**개선이라고 판단할 근거:** 특정한 이해·교정·재작업의 어려움이 어떻게 달라졌는지 작업 기록과 사람의 설명을 연결할 수 있다. 시간이나 비용을 비교했다면 포함 구간과 측정 방법이 같다거나, 달라진 조건을 해석할 수 있어야 한다.

체감 부담은 그 사람의 경험에 대한 유효한 자료다. 이를 시간 절감의 실측이나 다른 사람의 경험으로 바꾸지 않는다. 직접 작업 시간·대기·총 경과 시간은 가능한 경우 분리한다. 기록이 없으면 사후 추정이라고 표시하며, 평균을 보고할 정도의 자료가 있다면 지연된 사례와 분포도 함께 본다.

**판단을 바꾸는 관찰과 필요한 참여:** 설명이 짧고 만족스럽더라도 사람이 실패 뒤 남는 상태를 잘못 이해했다면 만족과 필요한 이해가 어긋난 것이다. 원래 선택하지 않은 전체 취소·부분 저장 중 하나를 고르는 일은 필요한 설계 참여다. 이미 전체 취소로 정했는데 구현이 부분 저장한 것을 사람이 다시 지적하는 일은 누락 교정이다. 두 일을 같은 재개입 횟수로 합치지 않는다. 코드가 답할 사실을 사람이 찾아 가르쳐 준 경우에는 별도 탐색 부담이 있다.

**판정을 유보할 조건:** 설명문만으로는 필요한 차이를 설명했는지 검토할 수 있지만 사람의 이해 개선은 확인할 수 없다. 사람의 실제 다음 질문·선택·수정·수행과 경험이 있으면 연결한다. 자연스럽게 발생한 자료를 활용하며 매 작업 뒤 이해 시험이나 재진술을 요구하지 않는다. 대화 왕복 수를 측정되지 않은 시간 절감으로 환산하지 않는다.

설명을 보완한 뒤 선택은 정확해졌지만 검토 시간이 늘었다면 이해 개선과 비용 증가를 함께 보고한다. 이 세 기준의 결과는 합산 점수로 덮지 않는다. 요구 결과가 충분해도 다음 변경이 어려울 수 있고, 코드를 이해하기 쉬워졌어도 필수 동작이 빠질 수 있다. 각 기준의 관찰이 판단을 바꾸는 전체 예는 [평가 기록과 적용 예](04-worked-evaluations.md)에 있다.

## 각 기준에 대해 어떻게 결론을 내릴 것인가

현재 결과가 충분한지와 이전보다 나아졌는지는 따로 판단한다. **개선했지만 아직 미충족인 결과**, **충분하지만 전후 개선은 비교할 수 없는 결과**도 가능하다. 근거가 부족하다는 것을 실패나 효과 없음으로 바꾸지 않는다.

판정 표현의 제안은 다음과 같다. 숫자 점수로 합산하지 않는다.

| 판단하는 것 | 사용할 표현 | 함께 필요한 설명 |
| --- | --- | --- |
| 현재 결과와 목표의 관계 | 충족 / 일부 충족 / 미충족 / 미확인 | 어떤 목표·조건을 어느 범위까지 확인했는가 |
| 이전 상태와의 차이 | 개선 / 확인한 변화 없음 / 악화 / 비교 불가 | 비교할 자료와 조건, 남은 문제·추가 비용은 무엇인가 |
| 결론을 지지하는 근거 | 코드·설계 검토 / 실행 확인 / 실제 작업 관찰 / 직접 측정 / 체감·추정 | 누가 무엇을 언제 확인했는가. 근거 종류를 우열 점수로 쓰지 않는다. |

‘코드가 더 명료하다’는 판단에는 해당 코드·흐름과 판단 이유를 붙인다. ‘누락을 고쳤다’에는 원래 요구와 수정·확인 결과를 붙인다. ‘시간을 줄였다’에는 대응되는 시간 기록을 붙인다. 자료끼리 모순되면 어느 자료가 어떤 결론을 지지하거나 제한하는지 설명한다.

다른 개발자가 원래 요구·전후 코드·확인 결과를 보고 같은 질문을 검토할 수 있도록 자료를 연결한다. 검토자가 있다면 동의 여부뿐 아니라 이견의 근거를 남긴다. 여러 AI가 같은 의견을 냈다는 사실만으로 실행 확인이나 사람의 검토가 완료됐다고 보지 않는다. 별도의 검토자나 정보를 가린 평가는 필요에 따라 추가할 수 있다.

## AI 작업 방식의 기여를 연결하는 방법

결과의 개선과 함께, 그 결과를 만드는 중요한 선택을 살펴본다. 다음 정보를 이미 있는 대화·작업 문서·diff·검사 기록에서 연결한다.

- 어떤 문제나 불확실성이 나타났고, 당시 선택은 무엇이었는가.
- 사람이 한 판단, AI가 제안한 판단, 스킬·컨텍스트·검사가 제공한 정보는 각각 무엇이었는가.
- 어떤 이유로 선택을 유지하거나 바꿨으며, 실제 구현·설명·검증의 어디에 반영됐는가.
- 그 선택의 결과와 남은 문제는 무엇인가. 추가 비용이나 도움이 되지 않은 적용은 있었는가.

모든 메시지를 별도 보고서로 다시 작성할 필요는 없다. 중요한 선택의 원문·코드 상태를 나중에도 확인할 수 있게 보존한다. 단순한 스킬 호출 기록보다 선택의 내용과 실제 결과의 연결을 설명한다.

전체 작업 방식의 기여는 여러 조건이 함께 바뀐 실제 작업에서도 관찰할 수 있다. 특정 스킬 하나의 독립 효과나 평균 향상률을 주장하려면 그 주장에 맞는 추가 비교가 필요하다. 과거 AI 작성이라는 사실만으로 기존 코드 문제의 원인을 확정하지 않는다.

## 자료가 부족할 때 다음 확인을 고른다

먼저 무엇을 모르는지 한 문장으로 좁힌다. 결과가 부족하다는 사실과 그 이유는 다르다. 당시 목표·적용 판본·사용 가능했던 자료를 잡고, 결론을 바꿀 수 있는 가장 가까운 위치를 확인한다. 기존 대화·diff·실행 기록으로 답할 수 있으면 새 보고서를 만들 필요가 없다.

호출 여부, 제안 내용, Main의 채택, 문서의 실제 반영, 다음 구현은 각각 다른 사실이다. 호출 흔적이 없다는 사실만으로 사용하지 않았다고 단정하지 않으며 기록의 사각도 남긴다. 문서에 반영했다는 말만 있고 파일의 의미가 다르면 전달 완료로 판단하지 않는다.

- 판단 자체가 없거나 잘못됐다면 당시 요청이 해당 역할의 적용 조건에 속했는지, 필요한 목표·코드·관련 작업에 접근하고 읽었는지 확인한다. 정상적인 비적용, 자료 접근 문제, 읽고도 놓친 판단을 구분한다.
- 적절한 제안이 나왔는데 결과가 같다면 Main이 무엇을 어떤 이유로 채택·기각했는지, 허용한 후속 작업과 실제 diff가 무엇인지 확인한다. 근거 있는 기각일 수도 있으므로 실행 부재를 곧 제안의 판단 실패로 보지 않는다.
- 채택한 의미와 다음 실행이 어긋나면 전달 내용, 해당 시점의 담당 문서, 반영 상태, 다음 실행자가 읽은 판본과 구현을 대조한다. 곧바로 더 많은 컨텍스트나 새 스킬을 추가하는 대신 확인된 위치에서 다음 판단을 정한다.

확인 범위는 하려는 주장에 맞춘다. 누락을 적절히 지적하는지는 읽기 전용 판단 시험으로 볼 수 있다. 실제로 고치는지는 제안·채택·구현·실행 자료가 필요하다. 사람이 더 잘 판단하는지는 사람의 행동이나 경험이 필요하다. 자료가 없는 주장만 유보하고 이미 답할 수 있는 구조·판단 결과는 남긴다.

도움이 된 장면뿐 아니라 차이가 없거나 비용이 늘어난 장면도 같은 질문으로 본다. 재검토가 실제 일을 가로막았다면 이미 정한 선택의 반복 질문, 관련 없는 읽기·갱신, 사용하지 않은 결과를 살펴 적용 범위나 종료 조건을 줄일 근거로 삼을 수 있다. 중요한 결손을 발견한 추가 비용과 아무 판단도 바꾸지 않은 비용을 함께 비교한다.

구체적인 관찰마다 다음 자료 위치와 가능한 판정을 연결한 표, 중복 정책 변경을 예로 든 적용 설명은 [평가 기록과 다음 확인](04-worked-evaluations.md)에 있다. 이 자료를 모든 작업에서 전부 기록해야 하는 고정 절차로 사용하지 않는다.

## 확보할 수 있는 자료에 맞춰 비교하기

공통 질문은 유지하면서 아래 방법을 선택하거나 결합한다. 동일 과제 재실행이 어려워도 전후 코드·관찰 기록을 활용할 수 있다.

| 확보 가능한 자료 | 할 수 있는 비교 | 결론을 제한하는 조건 |
| --- | --- | --- |
| 기존 코드·분석과 변경 후 코드·확인 결과 | 구조·동작·검증 범위가 어떻게 달라졌는지 비교 | 당시 개발 과정을 재현한 것은 아니다. 코드 전후만으로 전체 생산성 향상률은 계산하지 않는다. |
| 첫 완료 보고와 수용까지의 기록 | 남은 요구, 발견 시점, 필요한 교정과 재작업을 비교 | 명시적인 새 요구와 원래 요구의 누락을 구분한다. 완료 보고를 늦춘 비용도 살펴본다. |
| 서로 다른 여러 실제 작업의 기록 | 어떤 조건에서 비슷한 도움·실패·부담이 반복되는지 비교 | 작업 종류·규모·모델·개발자의 익숙함을 해석한다. 서로 다른 작업의 시간을 그대로 평균내어 방식의 향상률로 쓰지 않는다. |
| 같은 출발 조건에서 두 방식의 실행 | 같은 요구의 결과·비용을 더 직접 비교 | 실행 간 학습·해답 노출·조건 차이를 기록한다. 이 방식만을 전체 평가의 의무로 두지 않는다. |

각 작업에서는 적용한 방법·판본, 관찰 범위와 시작 상태를 남긴다. 이미 알려진 실패와 새로 발견한 문제를 구별하고, 성공한 사례뿐 아니라 차이가 없거나 더 어려워진 사례도 포함한다. 비교 질문이나 범위가 바뀌면 변경 이유를 남긴다. 사전에 모든 중요한 문제를 알 수 있다고 가정하지 않는다.

### 시간과 작업 상태를 비교할 때 남길 내용

시간이나 작업 부담의 변화를 주장할 때는 무엇을 시작과 끝으로 잡았는지 함께 남긴다. 시작 상태를 설명하는 자료에는 시작 commit과 미커밋 diff, 시작 요청, 모델·추론 설정, 사용할 수 있었던 도구·권한, 시간·비용 한도가 있다. 선택한 비교에서 결과에 영향을 줄 조건을 기록하며, 모든 작업에 동일한 실행 환경이나 기록 항목을 강제하지 않는다. 같은 과제를 두 번 수행했다면 앞 실행에서 얻은 해답과 검토 경험이 뒤 실행에 영향을 줬는지도 설명한다.

첫 완료 보고 시점에는 **코드·diff·응답·검사 결과**를 함께 보존한다. 이후 원래 요구의 누락을 고쳤는지, 새로운 요구가 추가됐는지 구분할 수 있어야 한다. 최종 종료점은 AI가 완료했다고 말한 시각만으로 정하지 않고, 해당 작업에서 정한 필수 동작과 코드 수용 조건을 확인한 시점으로 잡는다. 처음부터 필요한 리뷰, 피할 수 있었던 오류 수정, 검토 대기를 구분하고, 총 경과 시간을 제시한다면 대기 시간의 포함 여부도 밝힌다.

대응되는 작업끼리 시간을 비교할 수 있을 때 개선율은 `(Before 시간 - After 시간) / Before 시간`으로 계산하고 원시 시간도 함께 제시한다. 작업이 끝나지 않았다면 비교에서 삭제하지 않고 **미완료 상태와 관찰 종료까지의 시간**을 남긴다. 서로 다른 작업의 시간을 모아 같은 과제의 향상률처럼 제시하지 않는다. 표본이 작으면 개별 결과·범위·실패를 보여 주고, 평균과 중앙값을 쓴다면 무엇을 집계했으며 오래 지연된 작업이 결과에 어떤 영향을 줬는지 설명한다.

초기 하네스 구축 비용과 매 작업에서 읽기·갱신·검토에 쓴 비용도 구분한다. 기존 연구·제작에 쓴 시간을 제외한 비교라면 ‘도입 후 운영 비교’라는 범위를 밝힌다. 사람이 절약한 시간이 초기 구축과 후속 유지에 든 시간을 회수했는지는 이런 자료가 누적됐을 때 확인할 수 있다. 이 내용은 [외부 사례의 시간·비용 해석](03-external-reference-analysis.md)을 비교 기록에 반영한 것이며, 시간 측정이 없는 코드 품질 평가에도 수치를 요구하는 것은 아니다.

## 실제로 남길 평가 기록의 형태

아래는 다른 사람이 판단을 따라가기 위해 필요한 정보다. 기존 문서와 diff가 정보를 담고 있으면 연결하며, 중복 서류를 늘리기 위한 고정 양식으로 쓰지 않는다.

```text
평가할 작업과 관찰 범위:
평가할 개선안의 구성·판본 / 원래 문제 / 기대한 판단·행동:
해결하려던 문제 / 보존할 품질 / 변경된 목표와 이유:
적용한 AI 작업 방식과 비교할 이전 상태:

개선안의 구성·판단·실제 반영에서 확인한 것:
- 설계·구현 검토, 판단 제안 시험, 후속 반영 중 어디까지 확인했는가

개발 결과의 충분성:
- 판정, 근거, 남은 문제
코드 품질과 후속 변경 용이성:
- 판정, 전후 코드의 이유, 확인한 동작·변경 범위
사람의 이해·판단·작업 부담:
- 실제 장면과 사람의 설명, 측정했다면 시간·비용의 정의

중요한 판단과 AI 작업 방식의 기여:
- 당시 정보·선택 이유·실제 반영 위치·확인 결과
다른 해석과 추가 비용:
지금 주장할 수 있는 결과 / 추가 확인이 필요한 부분:
원자료·코드 상태·실행 결과의 접근점:
```

처음에는 해당하지 않는 항목과 아직 확인하지 못한 항목을 구분한다. 실제 적용에서 기록 비용만 늘리고 판단에 쓰이지 않는 부분이 발견되면 줄인다. 공개 문서를 만들 때는 독자가 볼 수 있는 코드·재현 방법·필요한 발췌로 정리해야 하며, 현재 연구의 로컬 접근점 자체를 공개 증거로 간주하지 않는다.

## 작업 종류와 조건에 맞춰 해석한다

아래는 특정 프로젝트를 선택하지 않고 질문의 적용 가능성을 검토한 것이다. 실제 작업 실험이나 사용성 검증 결과는 아니다.

| 작업 종류 | 같은 질문에 답할 수 있는 근거 | 이 작업에 맞는 해석 |
| --- | --- | --- |
| 기능 개발 | 요구·대표 동작·예외, 코드 구조, 검토와 수정 기록 | 사용자에게 필요한 결과와 구현 완료의 범위를 대조한다. |
| 리팩토링 | 기존 동작, 전후 책임·표현·의존 관계, 변경 영향 | 새 기능 수가 늘지 않아도 구조와 이해의 개선을 판단한다. |
| 버그 수정 | 실패 조건·원인·수정 결과, 재발 확인, 진단 과정 | 원인 범위와 수정 범위가 맞는지, 관련 동작에 영향이 없는지 본다. 작은 수정에 전체 구조 개편을 요구하지 않는다. |
| 여러 세션에 걸친 작업 | 판단·조건 변경과 후속 반영, 재조사·재설명, 누적 결과 | 기억을 복원한 설명과 실제 다음 작업의 정확성을 구분한다. |

실제 적용에서는 방법 자체도 검토한다. 공통 질문이 필요한 차이를 드러냈는지, 중요한 정성적 근거가 형식 때문에 빠지지 않았는지, 다른 검토자가 결론의 자료를 찾을 수 있는지, 수집 비용이 판단에 비해 과하지 않았는지를 본다. 다른 프로젝트에서도 반복되는 도움과 한계를 근거로 적용 방법을 다듬는다.

## 현재 방법의 지위와 이어갈 구체화

이 문서는 기존에 마련한 방법을 현재 사용할 본문으로 정리한 것이다. [전체 구조](01-evaluation-structure.md)의 성과 항목을 구체화할 때, 위 관찰 질문·판정 근거·반례·비교 방법을 해당 작업과 주장에 맞춰 연결한다. 모든 항목을 매번 같은 비중으로 실행하거나 공통 점수·고정 A/B·수치 문턱을 새로 요구하지 않는다.

이미 작성한 [과거 리팩터링 평가와 일반 개발 예](04-worked-evaluations.md)는 실제 관찰·가정·미확인을 나눠 이 방법을 사용하는 모습을 보여 준다. 그 사례가 곧 새 구성의 적용 효과이거나 앞으로 사용할 유일한 과제는 아니다. [외부 자료 분석](03-external-reference-analysis.md)은 방법 선택과 한계를 설명하는 근거이며, 이 개선안의 효과를 대신 증명하지 않는다.

각 성과 항목에서 어떤 자료의 어떤 차이로 충분성·개선을 판단할지 채우고, 업무적 의미와 실제 판단·기여를 연결한 후속 결과는 [06 확인할 성과와 평가안](06-outcomes-and-evaluation-plan.md)에 있다. 이 문서는 그 제안에서 사용하는 상세 방법과 판단 근거를 계속 소유한다. 실제 적용 시에는 작업의 목표·보존할 품질·시작 상태·적용 판본·확보 가능한 근거를 정한다. 프로젝트 선정, 설치, 코드 수정, 효과 측정이나 새로운 실험은 수행하지 않았다.

이 문서의 기반은 [정리 전 11 평가안](archive/2026-09-09-before-organization/11-general-ai-development-evaluation.md)과 [13 구체화 초안](archive/2026-09-09-before-organization/13-evaluation-concretization-draft.md)이다. 작성·검토의 대화 경위, 당시 완료 보고와 판본별 보존 상태는 기록에 두며, 현재 사용할 평가 방법은 위 본문에서 읽는다.
