# 실제 평가 기록과 개발 작업별 사용 예

평가 방법을 작업 자료에 적용할 때 참고할 상세 본문이다. 먼저 과거 리팩터링의 원문·고정 코드·판정을 제시하고, 이어서 다른 개발 장면의 가정 사례와 다음 확인 방법을 설명한다. 일반 원리와 판정·기록 방법은 [평가 방법](02-evaluation-method.md), 외부 방법의 근거는 [외부 자료 분석](03-external-reference-analysis.md)에 있다.

아래 실제 평가는 **2026-09-09 기존 12·13 작성 때 확인한 과거 사건**이다. 코드와 원문 발췌, 대조 명령, 다른 해석과 판정 범위를 현재 작업에서 읽고 사용할 수 있게 유지했다. 이번 문서 구성으로 과거 코드 실행이나 새 스킬의 효과를 재검증한 것은 아니다. CSV·공통 정책·이해·알림 사례는 방법을 설명하기 위한 가정이며 실제 성과와 구별한다. 작성·리뷰 과정과 당시 완료 보고는 [12 리뷰 기록](archive/2026-09-09-before-organization/12-evaluation-refinement-review.md)과 [13 당시 기록](archive/2026-09-09-before-organization/13-evaluation-concretization-draft.md)에 보존했다.

## 과거 원자료로 채운 평가 기록

### 작업·범위·비교 상태

대상은 TripProof 서버의 readable-flow 리팩터링이다. TripProof는 여행 자료의 근거로 답을 만드는 개발 프로젝트이며, 여기서는 그 제품의 전체 성과가 아니라 **서버 흐름과 이름을 읽고 판단하기 쉽게 만들라는 작업이 처음 완료로 보고된 경계**를 평가한다. 원대화의 첫 문제 제기부터 첫 완료, 사용자 재질문과 재개 지시까지 읽었다. 이후 모든 리팩터링이나 현재 제품 상태를 평가하지 않는다.

당시 방식은 사용자와 AI의 논의, 내부 리뷰 의견, PR 단위의 리팩터링과 테스트였다. 사용자는 spec-driven 스킬을 금지했다. 현재 네 스킬·Spec·Ticket·맥락 전달 구성은 이 과거 작업에 적용한 것이 아니다.

코드 비교는 첫 보고의 커밋 묶음 이전 `c8ad7c60c3eb5fa2d747a2e4cb4c4bda8d071d4c`와 보고된 마지막 커밋 `d8b968e4d0068ba463996c777337132c7369d0b8` 사이에서 업로드 route와 검색 자료 타입을 대조했다. 마지막 커밋의 업로드 use case도 직접 읽었다. 이 문서에서 말하는 **과거 변경 전·후**는 이 두 코드 상태다. 새 개선안 적용 뒤의 After 자료는 없다. 전체 working tree와 당시 실행 환경을 복원한 비교도 아니다.

### 코드에서 직접 확인한 변화와 남은 질문

**업로드 처리의 책임은 실제로 옮겨졌다.** 과거 변경 전 `apps/server/api/routes/materials.py`에는 파일 크기·형식 확인, PDF 파싱, 저장, 실패·성공 관찰 기록이 HTTP 처리와 함께 있었다. `d8b968e`에서는 route의 `upload_material`이 입력을 `UploadMaterialCommand`로 구성해 `UploadMaterialUseCase.run`을 호출하고, 크기 초과 오류를 HTTP 413으로 변환한다. 크기·형식·파싱·저장과 관찰 처리는 `apps/server/use_cases/materials.py`의 `run`에 있다. 단순히 새 파일이 생겼다는 사실보다, HTTP 표현과 업로드 수행의 경계가 호출 관계로 드러난 것이 제한적인 구조 개선 근거다.

**내부 관찰 단계의 표현은 업로드 수행 코드에 남았다.** `d8b968e`의 use case 85·97·123행에는 각각 다음 호출이 있다.

```python
observation.fail("upload_snapshot", "size_limit_exceeded")
observation.fail("upload_snapshot", "unsupported_file")
observation.fail("pdf_parse", "parse_failed")
```

원문 117행의 “관찰 단계 문자열이 use case에 남았다”는 내용은 이 범위에서 소스와 부합한다. 코드의 실제 클래스명은 `UploadMaterialUseCase`이며, 당시 AI 답변의 `MaterialUploadUseCase` 표현은 이름이 뒤집힌 보고였다.

이 잔여 표현의 존재만으로 별도 reporter 클래스가 필수라고 결론 내리지는 않는다. 업무상 실패 의미와 기록 단계의 관계를 자주 바꿔야 한다면 바꿀 위치가 늘어날 수 있다. 반대로 이 표현이 작고 안정적이며 호출부에 있는 편이 의미를 더 잘 드러낸다면 감싸는 비용이 더 클 수 있다. 실제로 어떤 변경이 어려웠는지, 기록 소비자가 무엇을 요구하는지를 확인해야 다음 구조 선택이 정해진다.

**타입명은 바뀌었고 기존 이름도 남았다.** `apps/server/retrieval/models.py` 23·33행에는 `RetrievedSource`와 `AnswerContext`가 있고, 39·40행에는 다음 alias가 있다.

```python
RetrievalCandidate = RetrievedSource
ContextPack = AnswerContext
```

이 파일의 diff에서는 두 데이터 구조의 필드 구성이 유지됐다. 검색 결과와 답변 입력 묶음에 새 이름을 준 것은 확인되지만, 데이터의 책임이나 처리 동작 자체가 바뀌었다는 증거는 아니다. 원문 108행은 내부 호환을 위해 alias를 남겼다고 보고한다. 이 설명과 코드 존재는 확인했으며, 당시 모든 소비자를 조사해 alias의 필수성과 제거 시점을 판정하지는 않았다.

동작 보존은 이번 정적 검토만으로 확정하지 않았다. 예컨대 지원하지 않는 파일·파싱 실패의 분기에서 실패 기록과 `store.add_failed`의 호출 순서도 전후가 완전히 같지는 않다. 이것을 실행 결함으로 판정한 것은 아니지만, “코드를 옮겼으므로 동작은 당연히 같다”는 설명으로 끝내지 않고 관련 실패·관찰 조건을 확인해야 할 이유다.

### 세 방향의 현재 판정

**개발 결과의 충분성 — 부분 결과는 확인되지만 전체 목표 충족은 지지되지 않는다.** HTTP 처리에서 업로드 수행을 분리한 변화는 실제로 있다. 그러나 첫 완료 보고는 이 변화가 서버 흐름·명명·AI 판단 경계라는 원래 목표를 어디까지 충족했는지, 남은 영역은 왜 종료해도 되는지 설명하지 않았다. 바로 뒤의 재질문에 AI가 같은 목표에 속한 잔여 영역을 제시했고 사용자가 계속하라고 했다. 따라서 그 시점의 “전체 완료”를 수용할 근거는 부족하다고 판단한다. 모든 코드가 나빴거나 작업 결과가 무가치했다는 판정은 아니다.

**코드 품질과 후속 변경 — 업로드 경계에 대한 부분 구조 개선, 전체 품질과 변경 비용은 유보다.** 과거 전후 코드에서 HTTP 표현과 업로드 수행을 별도 책임으로 읽을 수 있게 된 점은 지지한다. 타입명 변경은 의미 전달을 위한 선택으로 확인하며, 필드·책임 변화와 구분한다. 관찰 문자열이 남은 점은 추가 구조 검토의 구체적인 출발점이다. 나머지 잔여 모듈은 이번에 코드로 재검증하지 않았고, 후속 수정도 실행하지 않았다. 서버 전체가 충분히 읽기 쉬워졌거나 다음 변경 시간이 줄었다는 결론은 내릴 수 없다.

**사람의 이해·판단·부담 — 완료의 재개방에 사람이 개입한 사실은 확인된다.** 109행의 재질문과 118행의 목표 재지시는 원래 목표의 충분성을 다시 검토하게 했다. 새 제품 기능을 더 요청한 장면으로만 처리하기 어렵다. 앞서 맡긴 목표가 유지되고 AI도 조기 종료를 정정했기 때문이다. 반면 처음 구조와 보존 범위를 논의한 참여는 필요한 설계 판단이며 같은 교정 부담으로 합치지 않는다. 이 자료에는 사람의 직접 작업시간, 새 코드 이해를 확인한 수행, 최종 수용까지의 전체 비용이 없다. 반복 정정이 줄었거나 이해가 향상됐다고는 말할 수 없다.

`56 passed`는 당시 AI가 보고한 테스트 통과 수다. 여기서는 테스트를 재실행하거나 당시 테스트 stdout 원본을 별도로 감사하지 않았다. 보고된 세 커밋의 존재와 선택한 코드 내용은 현재 저장소의 Git 객체에서 확인했다. 커밋 수·테스트 수를 전체 목표의 충족도나 사람의 시간으로 환산하지 않았다.

### 중요한 판단과 다른 설명

사용자가 직접 한 판단은 흐름·이름의 이해 어려움을 문제로 정하고, 구조·AI 엔지니어 관점을 요청하고, PR 단위 작업을 허용하면서 원래 목표의 책임은 유지하고, 조기 완료 뒤 다시 연 것이다. AI는 목표와 일부 보존 경계를 설명하고 구현 대상을 골랐으며, 이후 자기 완료 판단을 정정했다. 이 장면은 새 스킬의 기여를 보여 주지 않지만, 새 구성에서 어떤 선택을 관찰해야 하는지는 구체적으로 보여 준다.

가능한 다른 설명도 남긴다. “완료했습니다”가 그날의 첫 리팩터링 묶음만 가리켰을 가능성은 있다. 다만 68행의 계속 진행 요청, 첫 보고에 남은 전체 목표가 드러나지 않은 점, 117행의 조기 종료 정정은 전체 완료와 부분 완료가 구별되지 않았다는 해석을 지지한다. 별도의 범위 축소 합의나 완료를 보류한 기록이 확인된다면 이 판정은 바뀔 수 있다.

목표가 넓어서 충분성을 판단하기 어려웠다는 설명도 가능하다. 이 때문에 끝없는 리팩터링을 요구해서는 안 된다. 그러나 AI가 이미 주요 잔여 영역을 구체적으로 열 수 있었고, 첫 완료에서 그 영역의 중요도·보류 이유를 다루지 않은 점은 여전히 남는다. “어느 잔여 문제를 이번 목표상 해결해야 했는가”에 이견이 있다면, 각 코드 문제와 보존 조건을 대조해 범위를 다시 판단하면 된다. 모든 잔여 후보를 그대로 구현해야 했다는 주장은 이 기록의 결론이 아니다.

당시 모델, 작업 속도, 도구와 사용자의 선택도 결과에 영향을 줬을 수 있다. 이 한 장면으로 스킬 부재를 유일한 원인으로 정하지 않는다. 또 AI가 117행에서 제시한 구조 후보가 모두 적절했는지도 확정하지 않는다.

## 세 결과 방향에서 어떤 관찰이 판단을 바꾸는가

아래는 평가자가 어떤 자료의 어떤 차이를 읽어야 하는지 보여 주는 **설명용 가정**이다. 특정 프로젝트에서 실행한 결과나 새 구성의 성공 사례가 아니다. 기술과 작업 유형은 달라도 목표·수행·구조·사람의 행동을 대조하는 질문은 유지한다.

### 결과의 충분성: 고객 명단 가져오기에서 준비와 수행을 구분한다

요청을 “CSV를 올리면 고객 명단이 저장되고, 중복 이메일이 있으면 정한 처리 결과를 알려준다”로 놓자. 이번 책임은 파일 파싱뿐 아니라 저장과 중복 처리 결과까지 만드는 것이다. 작업 전 자료에는 중복 처리 정책과 필수 입력 예가 있고, 첫 완료 산출물에는 업로드 화면·파서·저장 인터페이스·단위 테스트가 있다.

**충분성을 지지하는 관찰:** 정상 파일을 처리한 뒤 실제 저장소에서 명단을 확인할 수 있고, 중복 파일에서는 정한 정책대로 저장 상태와 사용자 결과가 일치한다. 빈 파일·잘못된 이메일 등 이번 요구에 중요한 조건도 실제 결과나 적절한 검사로 확인한다. 구현 경로와 관찰 결과를 함께 보면 “저장할 자리가 있다”와 “저장했다”를 가를 수 있다.

**판단을 바꾸는 관찰:** 화면은 성공이라고 표시하지만 실제 저장은 호출되지 않거나, 중복 이메일을 조용히 덮어써 원래 보존 조건을 어긴다. 이 경우 파서와 UI가 유효해도 전체 요청은 일부 충족이다. 반대로 원래 요청이 “다른 팀에 넘길 파서 라이브러리”였고 입출력 계약·실제 소비자·후속 저장 책임이 분명했다면, 저장을 하지 않았다는 이유로 이번 작업을 미완료로 판정하면 안 된다. “나중에 저장한다”는 말만 있고 담당 결과가 어느 작업에도 없으면 정당한 분리의 근거는 부족하다.

**유보할 부분:** mock 저장소 테스트만 있으면 테스트된 입출력 계약은 평가할 수 있지만 실제 저장 환경에서의 완료는 미확인이다. 중복 처리 정책이 원래 없었고 결과를 보고 새로 정했다면, 처음부터 있었던 요구의 누락으로 계산하지 않는다. 그 정책을 정하지 않고 완료한 것이 적절했는지는 당시 범위와 불확실성 처리로 따로 판단한다.

새 구성의 기여를 주장하려면, Spec·Ticket 또는 재판단에서 저장 책임의 누락을 알아보고 실제 담당 작업·코드·확인까지 바꾼 기록을 연결한다. 구현이 우연히 충분했던 결과만으로 스킬의 기여를 확정하지 않는다. 충분성을 확인했어도 이전 상태와 비교할 자료가 없으면 “충족, 개선 여부는 비교 불가”로 남길 수 있다.

### 코드 품질: 파일이 나뉜 것과 규칙을 바꿀 책임이 분명해진 것을 구분한다

관리자 화면과 일괄 처리 작업이 같은 고객 명단 가져오기 기능을 호출한다고 하자. 둘은 동일한 중복 이메일 정책을 지켜야 한다. 기존에는 HTTP route와 일괄 처리 함수가 각각 중복 판단·저장 분기를 갖고 있다. 바꾼 코드에서는 두 진입점이 공통 가져오기 기능을 호출하고, 입력 변환과 각 채널의 결과 표현은 바깥에 둔다.

**구조 개선을 지지하는 관찰:** 실제 호출 위치를 읽었을 때 두 경로가 같은 정책 구현을 사용하며, 그 정책과 저장 조건의 관계가 한 흐름에서 드러난다. “기존 고객을 유지하되 새 전화번호만 반영”하는 후속 요구가 생겼을 때 어디를 바꾸고 무엇을 검증해야 하는지 설명할 수 있다. 실제 수정까지 관찰했다면, 예상한 책임에서 정책을 바꾸고 두 채널의 결과를 확인했는지, 예상 밖의 수정·회귀·도움이 있었는지도 더한다.

**판단을 바꾸는 관찰:** 파일은 작아졌지만 route가 여전히 중복 여부를 판단하고 공통 기능도 다른 조건으로 다시 판단한다. 또는 새 추상화가 채널마다 flag를 요구해 기존 두 분기를 한 큰 함수 안으로 옮겼을 뿐이다. 이 경우 파일 분리나 이름 변경은 확인돼도 정책 책임이 명확해졌다는 주장은 지지되지 않는다. 다음 수정에서 한 채널만 달라지는 오류가 생기면 해당 구조 평가를 다시 열 근거다.

**유지할 차이:** 관리자 요청은 즉시 결과를 주고 일괄 처리는 중단 지점부터 재개해야 한다면 저장 단위·재시도 책임이 다를 수 있다. 구버전 클라이언트의 필드명 변환도 당장 필요할 수 있다. 이런 차이를 공통화나 코드량 감소를 위해 없애서 기존 동작을 깨뜨렸다면 개선으로 보지 않는다. 동일한 정책과 서로 다른 실행 제약을 구별해야 한다.

**유보할 부분:** 코드 검토만으로는 규칙의 위치·의존·표현에 대한 판단을 할 수 있다. 실제 후속 변경의 소요 시간이나 실수를 줄였다는 결론은 변경 기록이 있어야 한다. “한 파일만 고친다”도 보편적 합격선이 아니다. 필요한 테스트·타입·호환 처리의 수정이 함께 생기는 것은 책임 분산과 다르다.

새 구성에는 `reconsider-work`가 같은 종류의 최근 변경과 실제 사용처를 비교하게 하는 이유가 있다. 평가할 때는 이 지침을 읽었는지에서 멈추지 않고, 공통화가 필요 없는 곳을 유지했는지와 필요한 책임 수정이 실제 코드로 이어졌는지 본다. 기술적 이유와 취향을 구분하는 데는 Google의 [코드 리뷰 검토 내용](https://google.github.io/eng-practices/review/reviewer/looking-for.html)의 복잡성·검사·명명 관점을 참고했다.

### 사람의 이해와 부담: 짧은 설명보다 다음 선택과 교정의 내용을 본다

같은 기능을 검토하는 사람이 “일부 행이 틀려도 나머지는 저장되는가, 다시 올리면 어떤 행이 바뀌는가”를 알고 싶다고 하자. “검증과 저장을 분리했고 테스트가 통과했다”는 짧은 보고만으로는 답하기 어렵다. 필요한 설명은 실제 저장 경계, 중복 정책, 실패 뒤 남는 상태와 아직 정하지 않은 선택이다.

**도움을 지지하는 관찰:** 설명을 받은 사람이 업무상 허용할 처리 방식을 선택하거나, 원하지 않는 부분 저장을 지적하거나, 재시도 영향에 맞춰 다음 수정 범위를 정한다. 실제 후속 작업에서 올바른 담당 코드와 확인 조건을 이용했다면 수행 근거도 된다. 체감상 이해하기 쉬웠다는 답은 그 사람의 경험으로 함께 보존한다.

**판단을 바꾸는 관찰:** 짧고 만족스러운 설명 뒤 사람이 “실패한 행은 저장되지 않는다”고 이해했는데 실제로는 일부 변경이 남는다. 이 경우 설명 만족도와 필요한 이해가 어긋났다. AI가 앞서 놓친 실패 조건을 사용자가 반복해서 찾아내거나, 같은 질문을 다시 해야 했다면 교정 부담이다. 설명을 길게 보완한 뒤 선택은 정확해졌지만 검토에 더 많은 시간이 들었다면 이해 개선과 비용 증가를 함께 보고한다.

**필요한 참여:** 원래 선택하지 않은 “전체 취소와 부분 저장 중 어느 것이 업무에 맞는가”를 사람이 결정하는 일은 요구·설계 참여다. 이미 “전체 취소”로 정했는데 구현이 부분 저장한 것을 다시 지적하는 일은 AI 누락의 교정이다. 둘을 같은 재개입 횟수로 더하면 사람의 가치 있는 판단까지 실패로 계산한다. 저장 함수 위치처럼 코드가 답할 사실을 사람이 찾아 가르쳐 줬다면 그것도 별도 탐색 부담이다.

**유보할 부분:** 설명문만 있고 사람의 후속 발화·검토·수행이 없다면 설명이 필요한 차이를 담는지는 검토할 수 있지만 이해 개선은 미확인이다. 자연스럽게 발생한 다음 행동이 있으면 사용하며, 매 작업 뒤 이해 시험이나 재진술을 요구하지 않는다. 시간이 없으면 대화의 왕복을 시간 절감으로 환산하지 않는다.

이 세 방향의 결과는 합산 점수로 덮지 않는다. 고객 명단이 정확히 저장돼도 후속 정책 변경은 어려울 수 있고, 코드를 이해하기 쉬워졌어도 요구한 저장 동작이 빠질 수 있다. 무엇을 얻고 무엇이 남았는지를 함께 판단한다.

## 다른 유형의 작업에서는 무엇을 바꿔 채우는가

리팩터링 기록의 질문을 **구독 알림 중복 발송 버그**에 적용해 보자. 다음 기록은 설명용 가정이며 실제 프로젝트를 선정하거나 버그를 재현한 결과가 아니다.

해결할 문제는 “예약 작업이 재시도되면 같은 알림이 두 번 발송된다”이고, 보존할 조건은 “다음 날의 정상 알림은 계속 발송된다”다. 비교할 상태는 수정 전 재시도 기록과 코드, 수정 뒤 같은 알림의 재시도·다음 날짜의 발송 결과다. 과거 리팩터링의 ‘전체 서버 가독성’ 대신 이 실패 조건과 보존 조건이 범위를 정한다.

가령 확보한 자료에 같은 구독·같은 예정 시각의 발송 요청이 두 번 처리된 기록이 있고, 수정 코드가 요청 처리 함수의 맨 앞에 중복 방지 키를 넣었다고 하자. 이는 수정 위치의 근거가 되지만 동시 처리와 발송 실패 뒤 재시도를 해결했는지는 아직 답하지 않는다. 실제 결과가 중복 발송은 막으면서 다음 날 알림도 막았다면, 증상 일부는 개선했지만 요청 결과는 미충족이다. 반대로 재시도·다음 날 발송이 확인됐다면 관찰한 범위의 동작은 충족으로 볼 수 있다.

코드 품질에서는 중복 키의 의미와 발송 성공·실패 상태를 누가 바꾸는지 본다. 같은 키를 API와 예약 실행기가 서로 다르게 만들거나, 실패해도 영구적으로 발송 완료로 남긴다면 그 차이를 고칠 근거가 된다. 기존 계약은 맞고 한 경로만 어겼다면 국소 수정이 적절할 수 있다. 키를 추가했다는 이유로 모든 알림 아키텍처를 다시 설계할 필요는 없다.

사람의 부담은 설명 길이보다 원인·남는 위험·다음 확인을 알 수 있었는지 본다. 사용자가 이미 요구한 다음 날 발송을 다시 지적해야 했다면 누락 교정이다. 공급자가 성공 여부를 알려 주지 않는 상황에서 어떤 재시도 위험을 수용할지 고르는 일은 필요한 설계 참여다. 후속 작업자가 이 차이를 문서와 코드에서 복원해 필요한 검사를 고를 수 있었는지가 맥락 전달의 관찰이다.

이때의 평가 기록 결론은 자료에 따라 다음처럼 달라진다. **코드와 과거 로그만 있으면 “원인·수정 접근은 검토 가능, 수정 후 동작은 미확인”이다.** 재시도와 다음 날 발송까지 실행했다면 그 조건의 충족을 말할 수 있다. 사람이 덜 개입했거나 수정 시간이 줄었다는 자료가 없으면 비용 개선은 비교 불가다. 적용한 `reconsider-work`가 기존 계약 안의 국소 수정을 추천하고 그대로 실행됐는지, 또는 적절한 이유 없이 범위를 확대했는지를 별도로 연결한다.

유지되는 것은 요구·실제 결과·보존 조건·다른 설명·다음 확인을 잇는 평가 방식이다. 바뀌는 것은 구체 입력, 실패 상태, 중요한 코드 책임, 필요한 실행과 사람의 선택이다. 특정 제품에서 쓰던 클래스명이나 테스트 수를 옮기지 않는다. Noline은 다른 작업의 미확정 후보로 남아 있으며, 이 문서에서는 분석이나 적용 결과로 사용하지 않았다.

## 자료가 부족하거나 기대와 다를 때 다음 확인을 고르는 방법

먼저 “무엇을 모르는가”를 한 문장으로 좁힌다. 결과가 부족하다는 사실과 그 이유는 다르다. 작업 당시 목표·적용 판본·사용 가능했던 자료를 잡고, **결론을 바꿀 수 있는 가장 가까운 위치**를 확인한다. 기존 대화·diff·실행 기록이 답하면 새 보고서를 만들 필요가 없다.

호출 여부, 제안 내용, Main의 채택, 문서의 실제 반영, 다음 구현은 각각 다른 사실이다. 호출 흔적이 없다는 것만으로 사용하지 않았다고 단정하지 않으며 기록 사각도 남긴다. 반영됐다는 말만 있고 파일이 다르면 전달 완료로 올리지 않는다. 다음 표는 확인이 필요한 경우의 선택지이며 모든 작업에 전 과정을 의무 기록하는 절차가 아니다.

| 현재 막힌 질문·관찰 | 다음에 볼 위치와 구체 질문 | 그 확인 뒤 가능한 판단 |
| --- | --- | --- |
| 준비 산출물만 있고 핵심 동작이 없다 | 당시 요청·Spec과 관련 Ticket에서 “이번 수행을 누가 맡았고 실제 후속 작업도 맡는가?”를 본다 | 후속 책임이 있으면 정당한 부분 완료를 유지할 수 있다. 어느 작업도 맡지 않으면 누락이며, 못 읽었으면 전체 완료를 유보한다. |
| 논의 보강이 있었는지 알 수 없다 | 사용자의 직접 호출과 읽은 본문을 확인한다. `work-discussion`이 호출 대상이었는가? | 직접 호출이 없으면 이 스킬의 응답 품질은 평가하지 않는다. 필요할 때 사용자가 발견·선택하기 어려웠다는 자료가 있다면 별도 사용성 문제다. |
| 재판단이 없거나 잘못됐다 | 당시 결과·변경 부담이 재판단 조건에 해당했는지, 모델이 필요한 목표·코드·관련 작업을 실제 읽었는지 본다 | 자료 접근·routing 문제, 읽고도 놓친 판단 문제, 해당하지 않는 정상 비적용을 구분한다. 결과만 보고 원인을 하나로 묶지 않는다. |
| 재판단 제안은 적절한데 결과가 그대로다 | 제안 뒤 Main 응답에서 무엇을 어떤 이유로 채택·기각했는지, 허용 범위와 실제 후속 diff가 무엇인지 확인한다 | 근거 있는 기각일 수 있다. 채택되지 않은 제안의 실행 부재를 곧 스킬의 판단 실패로 보지 않는다. 전체 방식의 결과·비용 평가는 그대로 남는다. |
| Main은 채택했는데 다음 작업이 옛 판단을 따른다 | 최종 전달 내용, 필요한 문서의 해당 시점 내용, Maintain 처리 결과, 다음 실행자가 읽은 판본을 순서대로 대조한다 | 전달 누락, 문서 갱신 실패·지연, 낡은 판본 읽기, 읽고도 구현에서 놓침 중 확인된 위치를 고른다. 접수와 실제 반영을 구분한다. |
| 파일을 나눴는데 변경은 여전히 어렵다 | 전후 소스·실제 호출자·같은 종류의 최근 변경에서 “같은 규칙이 어디에 있고 왜 함께 바뀌는가?”를 본다 | 실제 중복 책임인지 필요한 호환·실행 제약인지 판정한다. 변경의 시간·실수 감소는 후속 수정 자료가 있을 때만 말한다. |
| 코드·테스트는 있는데 핵심 결과가 확인되지 않는다 | 실제 사용 설정·연결·관련 출력에서 “관찰한 실행이 어떤 수행과 조건을 통과했는가?”를 본다 | 소스상 가능성과 실행 결과를 구별한다. 당시 실행을 복원할 수 없으면 구조 검토만 남긴다. |
| 설명은 좋아 보이지만 사람의 도움이 늘었다 | 사람의 다음 질문·선택·수정과 경험을 읽고 “새로운 선택인가, 앞선 누락의 반복 교정인가?”를 본다 | 필요한 설계 참여, 설명의 오해, AI 사실 탐색 부담을 구분한다. 대화만으로 시간 감소나 내부 이해를 추정하지 않는다. |
| 재검토·설명이 실제 일을 가로막는다 | 이미 정한 선택의 반복 질문, 관련 없는 읽기·문서 갱신, 사용하지 않은 결과를 본다 | 적용 범위나 종료 조건을 줄일 근거가 된다. 중요한 결손을 실제로 발견한 추가 비용과 아무 판단도 바꾸지 않은 비용을 함께 비교한다. |

예를 들어 문서에 새 중복 정책은 들어갔는데 일괄 처리 구현만 옛 정책이면, 먼저 그 작업이 읽은 문서와 실제 호출 경로를 본다. 곧바로 더 많은 컨텍스트를 넣거나 재판단 스킬을 늘리지 않는다. 반대로 문서가 옛 정책이고 Main의 채택까지는 확인된다면 문서 전달과 반영 위치가 우선이다.

다음 확인의 범위는 하려는 주장에 맞춘다. “누락을 적절히 지적하는가”는 읽기 전용 판단 시험으로 볼 수 있다. “실제로 고치는가”는 제안·채택·구현과 실행 자료가 필요하다. “사람이 더 잘 판단하는가”는 사람의 행동이나 경험이 필요하다. 자료가 없으면 해당 주장을 유보하고 이미 답할 수 있는 구조·판단 결과는 남긴다.

여러 작업의 결과를 모을 때에는 도움이 된 장면뿐 아니라 차이가 없거나 비용이 늘어난 장면도 같은 질문으로 본다. 동작이 좋아졌지만 리뷰·문서 관리가 늘었다면 두 결과를 함께 적는다. 한 방식의 운영 부담을 줄였다는 주장은 읽기·갱신·검토·재작업을 어디까지 포함했는지 밝혀야 한다. 직접 잰 시간이 있으면 쓰고, 사후 체감이나 추정뿐이면 그 종류로 남긴다. 사례 수·종합 점수·같은 조건 A/B는 현재 방법의 의무가 아니다.

## 외부 개발자가 주장을 검토할 수 있게 연결하기

외부 독자는 스킬 이름보다 문제의 영향, 개발자가 고른 방법, 실제로 바뀐 것과 확인 범위를 알아야 한다. 현재 이 연구의 로컬 대화·저장소에 접근할 수 있다고 가정하지 않는다. 이 문서는 내부 검토 초안이며, 아래는 공개용 자료를 준비할 때 무엇을 연결할지 판단한 결과다. 실제 공개나 성과 문구의 확정은 하지 않았다.

현재 설명 가능한 흐름은 다음과 같다. **서버 리팩터링에서 부분 변경과 테스트 보고로 전체 목표가 닫힌 장면을 원래 요청과 코드에 대조했다. 이 문제를 바탕으로 전체 목표와 실행 단위를 연결하고, 결과에 따라 재판단하며, 채택된 의미를 문서와 후속 실행으로 잇는 구성을 마련했다. 설계와 준비본은 검토할 수 있으나 실제 사용 효과는 별도 자료가 필요하다.**

| 외부 독자의 질문 | 지금 연결할 근거와 가능한 설명 | 아직 없거나 공개 전 더 필요한 자료 |
| --- | --- | --- |
| 무엇을 직접 판단하고 바꿨는가? | 위 실제 기록의 사용자 발화는 흐름·명명 문제 정의, 목표 유지, 완료 재개방을 보여 준다. 현재 스킬·Spec·Ticket 관계는 그 문제에 대한 설계 선택이다 | 설계 개정에서 사용자가 선택·수용한 대화와 해당 diff를 연결해야 한다. 과거 사용자 판단, AI 제안, 새 구성의 작성·검토 역할을 한 사람이 모두 직접 구현한 것처럼 합치지 않는다. |
| 왜 이 방법을 선택했는가? | 본문의 문제·책임·대안·비용 분석과 실제 준비본을 함께 보여 준다. 목표 재설명만으로 해결되지 않았던 장면, 테스트가 다룬 동작과 남긴 판단의 차이를 설명할 수 있다 | 공개 가능한 최소 원문 발췌와 설계 diff·적용 조건이 필요하다. 당시 실제 대안과 이번에 새로 비교한 대안의 시점을 유지한다. |
| 결과가 나아졌다고 볼 근거는 무엇인가? | 과거 코드에서 HTTP와 업로드 수행의 분리는 확인했다. 현재 개선안은 [09 현황의 구현·검사 기록](05-problem-and-intervention-basis.md#이미-있는-검사와-아직-없는-효과-증거)과 본문 판본으로 준비 상태를 설명할 수 있다 | 이 과거 코드 변경을 새 구성의 효과로 사용할 수 없다. 새 적용의 결과·첫 완료·수용 범위·중요 판단의 반영·추가 부담이 필요하다. 독립적인 스킬 효과나 시간 감소는 그 주장에 맞는 비교가 없으면 미확인이다. |
| 다른 작업에서도 통할 조건은 무엇인가? | CSV 기능·중복 알림 버그 예는 요구와 실행 책임, 보존할 동작, 후속 변경, 사람의 판단을 다른 기술로 해석하는 방법을 보여 준다 | 현재는 적용 설명이다. 실제 여러 작업에서 무엇이 도움이 됐고 실패했는지, 작업·도구·개발자 경험이 달라진 조건을 담은 기록이 필요하다. Noline 선정이나 외부 팀 채택의 증거는 없다. |

공개할 때 최소한의 한 묶음은 **원래 요청과 첫 완료·정정의 필요한 발췌, 같은 시점의 코드 또는 접근 가능한 diff, 확인 방법과 실제 결과, 작성자의 해석과 미확인**으로 구성할 수 있다. 코드의 특정 변경이 논점이면 해당 코드와 소비 관계가 필요하고, 시간·사용자 경험 주장이 없으면 억지로 수치를 만들지 않는다. 원본 전체를 공개할 필요는 없지만 핵심 발췌의 순서·범위·편집 여부는 남겨야 한다.

이번 기록을 공유 가능한 예로 만들 경우에는 JSONL의 개인 경로 대신 접근 가능한 발췌를 놓고, 과거 commit을 열 수 있는 코드 자료를 연결해야 한다. `56 passed`를 결과 증거로 더 강하게 쓰려면 당시 출력·실행 조건과 검사의 의미를 추가한다. 확보하지 못하면 “당시 보고” 표현을 유지한다. 실제 원문을 공개할 수 없어 설명용으로 재구성한다면 재구성 사실을 표시하며, 그 재구성 자체를 과거 관찰 증거로 쓰지 않는다.

외부 출처는 이런 설명 방식을 돕는 근거다. 회사나 논문이 현재 개선안의 효과를 대신 증명하지는 않는다. 독자가 이견을 낼 때에는 “부분 완료 해석이 다른가”, “업로드 책임 분리를 개선으로 보는 기술적 이유가 부족한가”, “스킬 제안이 실제 반영됐다는 근거가 없는가”처럼 논점을 특정할 수 있어야 한다.
