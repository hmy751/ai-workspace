# 외부 자료에서 가져온 평가 방법과 근거

이 문서는 회사의 개발 사례, 코드 검토 지침, 소프트웨어공학 연구에서 무엇을 비교했고 어떤 근거로 판단했는지 보존한다. 현재 평가 방법을 사용할 때 필요한 출처별 내용·공개 수치의 의미·적용 조건·한계를 본문에서 읽을 수 있게 구성했다. 자료의 주소와 접근 상태에 관한 원천은 [외부 출처 기록](../../../source/09-ai-native-engineering-evaluation/source.md)이다.

2026-09-09에 작성한 기존 분석과 확인 기록을 내용별로 재구성했다. 이번 문서 정리에서 웹페이지를 새로 확인하거나 회사의 원시 측정 자료를 확보한 것은 아니다. 본문의 접근 상태와 수치는 당시 확인 범위에 귀속한다.

[전체 평가 구조](01-evaluation-structure.md)에서 이 자료는 평가 기준·성과 항목을 구체화하고 판단과 근거를 연결하는 데 사용한다. 여러 개발 작업에서 사용할 공통 질문과 비교 원리는 [평가 방법](02-evaluation-method.md), 원자료를 실제 판단에 연결한 예는 [평가 예와 근거](04-worked-evaluations.md)가 소유한다. 이 문서는 그 방법을 참고한 외부 자료의 상세 내용과 선택 이유를 소유한다.

## 외부 자료를 사용하는 이유와 범위

이번 평가의 출발점은 사용자가 실제 문제를 분석해 개선한 스킬·레퍼런스·작업 구성이다. 외부 자료는 그 문제를 대신 정의하거나 기존 세 평가 기준의 정답을 정하는 역할을 맡지 않는다. 무엇이 좋아졌다고 판단할지, 어떤 자료를 비교할지, 다른 사람이 결론을 검토하려면 무엇이 필요한지를 구체화하는 데 사용한다.

회사 기술블로그는 개발자가 어떤 문제를 발견하고 방법을 고른 뒤 어떤 결과를 확인했는지 보여 준다. 코드 리뷰 지침은 코드 품질을 살필 기술적 내용을, 유지보수성 보고서는 변경 상황에 맞춘 관찰 방법을, 사례연구 지침은 여러 근거에서 결론까지 이어지는 설명 방법을 제공한다. 자료 종류나 회사 이름에 고정 우선순위를 두지 않고 현재 판단하려는 질문에 맞는 부분을 선택한다.

여기서 AI-native 개발은 AI가 코드 작성뿐 아니라 요구 해석·작업 분해·구현·검증·설명에 관여하고, 사람이 결과와 다음 선택을 판단하는 개발 방식을 가리킨다. 따라서 코드 생성 속도만으로는 합의·검토·수정으로 옮겨간 비용을 놓칠 수 있다는 것이 기존 분석의 판단이다. 외부 사례의 향상률을 우리 목표값으로 가져오지 않고, 수용 가능한 결과까지의 과정과 실제 산출물을 연결하는 방식을 참고한다.

## 개발 결과의 충족과 완료 이후 남은 문제

### 당근: 기대 동작과 개발자의 코드 수용을 함께 확인

지역생활 플랫폼 당근의 Elon park가 작성한 [Cursor와 TDD로 만드는 Swift Macro](https://medium.com/daangn/cursor%EC%99%80-tdd%EB%A1%9C-%EB%A7%8C%EB%93%9C%EB%8A%94-swift-macro-0e4a245caee2)는 2025-04-17에 공개된 개발 사례다. AI 코드 편집기 Cursor로 Swift 매크로를 구현하면서 테스트 주도 개발(TDD)을 사용하는 절차를 설명한다. 매크로는 입력 코드를 받아 정해진 코드를 생성하므로, 기대 입력과 출력의 관계를 구체적으로 정할 수 있는 작업이다.

사람이 매크로 입력과 생성되어야 할 코드를 먼저 정하고 실패하는 테스트를 작성한다. 이후 Cursor가 작성한 구현을 사람이 리뷰하고, Xcode에서 컴파일·테스트하며 결과를 확인한다. 기대 출력은 인덴트까지 일치해야 한다. 후속 리팩터링도 테스트로 검증하면서 사람이 커밋할 만한 코드 품질인지 판단한다. 즉 동작 통과와 엔지니어의 코드·기술 검토가 함께 있다.

글은 시간 절약을 정성적으로 설명하지만 정량적인 작업시간 전후 비교는 확인되지 않았다. 엔지니어의 기술 이해와 코드 리뷰가 필요하다는 설명도 남아 있다. 이 사례를 시간 개선율의 근거로 쓰거나, AI 구현을 테스트 통과만으로 수용했다는 사례로 해석하지 않는다.

이번 평가에서 가져온 것은 구현 전에 기대 동작을 명확하게 하고 실제 동작과 코드 수용을 함께 확인하는 방법이다. 모든 작업에 TDD나 출력 문자열 완전 일치를 요구하는 것은 아니다. 자연어 결과를 내는 기능처럼 출력이 여러 형태로 타당할 수 있는 작업에서는 요구 충족·근거·나오면 안 되는 결과를 판단할 기준이 더 적합할 수 있다.

당시 최초 읽기에서는 검색에 노출된 일부만 확인됐고, 재조사에서 일반 브라우저로 Red·Green·Refactor와 장단점·나가며까지 본문을 확인했다. 일반 읽기 도구의 403과 실제 브라우저의 접근 성공은 구별해 기록돼 있다.

### 우아한형제들: AI 검사 완료 뒤에도 남은 결함을 같은 코드에서 확인

배달의민족 운영사 우아한형제들의 박재용이 작성한 [사람도 AI도 놓친 번역 누락, ESLint 플러그인을 만들어 해결하기](https://techblog.woowahan.com/26388/)는 2026-06-23에 공개됐다. AI 작성 규칙과 리뷰를 거친 코드에도 번역 누락 등이 남아, ESLint가 규칙 위반을 탐지하고 AI가 교정하며 사람이 모호한 사례를 판단하도록 바꾼 사례다. ESLint는 코드에서 정해진 규칙 위반을 검사하는 도구다.

이 사례에서 특히 중요한 비교 단위는 검사 시점의 코드다. **AI 검사 완료 후, 린트 교정 전의 코드 형상으로 돌아가** 새 검사를 실행했다. 이미 완료로 여긴 같은 산출물에서 추가로 무엇을 발견했는지 확인할 수 있는 방식이다. 글은 번역 누락 182개, 기수·서수 오역 5개, 불필요한 복잡 코드 22개를 검출하고 배포 전에 교정했다고 보고한다.

이 숫자는 검출한 위반의 종류별 개수다. 전체 결함의 분모, 미탐률, 시간 절감량은 공개되지 않았으므로 전체 결함 탐지율이나 생산성 향상률을 계산할 근거로 삼지 않는다. 작성자는 기대를 넘는 성과로 평가하지만 사전에 정한 수치 합격선은 제시하지 않는다. 회사의 평가 시점 코드 사본과 검사 원자료도 이번 조사에서 확보하지 않았다.

이번 평가에서는 최초 완료 상태와 이후 교정 상태를 따로 보는 방법에 사용했다. 핵심 요구를 놓친 채 완료한 작업을 평가할 때, 최종 결과만 보면 누락과 재작업이 사라져 보일 수 있다. 처음 완료했다고 한 산출물을 원래 요구와 대조하고 무엇을 추가 발견해 실제로 고쳤는지 남기는 것이다. 잘못된 지적과 처리 비용도 함께 볼 수 있다.

또한 규칙으로 검사할 수 있는 누락과 제품·설계 판단이 필요한 누락을 구분한다. 이 사례는 모든 중요한 판단을 자동 린트로 바꿀 수 있다는 근거가 아니다. 기존 규칙의 한계, 직접 도구를 만든 이유와 복잡도 비용을 함께 검토했다는 점도 개선안의 선택 이유를 설명하는 데 참고했다.

## 코드 품질과 후속 변경을 판단하는 방법

### Google: 기술적 검토 내용과 개인적 취향을 구분

Google Engineering Practices의 [What to look for in a code review](https://google.github.io/eng-practices/review/reviewer/looking-for.html)와 [The Standard of Code Review](https://google.github.io/eng-practices/review/reviewer/standard.html)는 개발자가 코드 변경을 검토할 때 사용할 운영 지침이다. AI 작업 방식의 효과 실험이나 보편적인 코드 품질 점수를 제공하는 자료는 아니다.

기존 분석에서 읽고 사용한 범위는 설계, 동작, 복잡성, 테스트, 이름, 주석과 리뷰 기준이다. 코드 독자가 이해하고 수정할 때 어떤 어려움이 생기는지, 검사가 실제 결함을 발견하는지, 필요한 수준보다 과하게 일반화한 코드는 아닌지를 검토하는 데 참고했다. 기술적인 이유가 있는 지적과 개인적인 스타일 선호를 구별하는 기준도 중요하다.

이번 평가에서는 파일을 나누거나 이름을 바꾼 사실만으로 코드 품질 개선을 인정하지 않고, 그 변화가 책임과 동작을 이해하고 수정하는 데 어떤 도움을 주는지 설명하는 데 사용한다. 반대로 전체 문제가 남아 있다는 이유로 기술적 근거가 있는 부분 개선까지 지우지 않는다. 어떤 변경을 개선으로 인정했고 어떤 문제는 남았는지 구체적으로 검토한다.

Google의 모든 운영 규칙이나 조직별 승인 절차를 현재 작업에 이식하지 않는다. 이 지침에서 선택한 검토 내용을 사용하더라도 현재 개선안의 실제 효과는 해당 코드와 작업 기록으로 따로 확인해야 한다.

### SEI: 어떤 변경을 어떤 조건에서 수행하는지 구체화

카네기멜런대학교 소프트웨어공학연구소(SEI)의 Rick Kazman 외가 작성한 [Maintainability](https://www.sei.cmu.edu/documents/1288/2020_005_001_650490.pdf)는 2020-12 보고서 CMU/SEI-2020-TR-006이다. 소프트웨어 구조의 유지보수성을 분석하는 자료이며, 이번 분석에서는 추상적인 ‘수정하기 좋은 구조’를 실제 변경 상황과 연결하는 데 사용했다.

확인한 주요 내용은 §§3–4의 변경 상황·응답·관찰 기준, §4의 상황·대상·환경·응답 관계, §7의 실제 구조 위치·설계 근거·다른 품질에 미치는 영향·비용 검토다. 인쇄쪽 2와 41에서 문서 기반 검토와 실제 구현·실행에 따른 확신의 차이도 확인했다. 74쪽 PDF의 웹 텍스트를 읽은 범위이며 전체 그림과 참고문헌을 검증한 것은 아니다.

이번 평가에서 ‘후속 변경이 쉬워졌는가’는 어떤 요구를 바꾸는지, 어느 구조에 영향을 주는지, 어떤 결과를 보존해야 하는지를 구체적으로 적어야 판단할 수 있다. 설계 문서나 코드만 보고 예상하는 변경 용이성과 실제 수정·검증을 수행해 확인한 결과는 구분해 남긴다. 실제 수행에서 예상 밖 수정이나 다른 품질의 손상이 발견되면 그 결과도 판정에 포함한다.

원문에는 측정값과 문턱을 포함한 시나리오 방식이 있다. 기존 분석에서는 상황과 관찰을 구체화하는 부분을 선택했으며 특정 시스템·계약자·기간·비용 기준이나 공통 수치 문턱을 채택하지 않았다. 모든 프로젝트에 똑같은 수정 과제와 합격선을 부과하는 근거로 사용하지 않는다.

## 결과까지의 시간과 비용을 비교하는 방법

### 무신사: 개발부터 배포까지의 구간과 사람의 체감을 함께 관찰

패션 커머스 기업 무신사의 김도영이 작성한 [무신사 X GitHub Copilot은 정말로 우리의 생산성을 높였을까?](https://techblog.musinsa.com/무신사-x-github-copilot은-정말로-우리의-생산성을-높였을까-de149ad7b7f6)는 2025-02-11에 공개됐다. 2024년 11~12월 약 30명의 GitHub Copilot 도입을 조사한 글이다. Copilot은 코드 작성 등을 지원하는 AI 개발 도구다.

GitHub·Jira 작업 기록을 Grafana로 분석하고 도입 초기와 도구에 익숙해진 시점에 설문을 시행했다. 코드 작성부터 PR 생성, 리뷰 시작 대기, PR 생성부터 리뷰 완료, 개발 시작부터 배포까지의 시간을 구별해 추적했다. PR은 코드 변경을 검토하고 병합하기 위한 요청이다. 만족·피로·학습·품질 체감도 별도로 수집했다.

보고된 평균 감소는 전체 개발·배포 주기 약 50%, PR 생성부터 리뷰 완료까지 약 40%다. 하지만 원문은 일부 오래 지연되던 작업이 줄어 평균이 내려갔으며, 중앙값으로 보면 대부분 작업은 원래도 빠르게 처리됐다고 설명한다. 따라서 일부 오래 걸리던 작업의 개선과 모든 작업의 전반적 개선을 구별해야 한다. 약 40%를 코딩·대기·리뷰 각각의 독립 개선율로 나누거나 더하지 않는다.

무작위 통제군, 상세 원시 분포, 미리 고정한 채택 임계치는 확인되지 않았다. 대형 이벤트와 설문 수집의 어려움도 글에 기록돼 있다. 최신 스킬·하네스 묶음의 독립 효과를 실험한 자료는 아니지만, 현업 개발 성과를 구간과 분포, 사람의 경험으로 함께 비교한 방법의 근거다.

이번 평가에서는 작성·대기·검토 구간의 시작과 끝을 명확히 하고 겹치는 시간을 중복 합산하지 않는 데 사용한다. 평균·중앙값과 오래 지연된 개별 작업을 함께 보면 반복 정정이 특히 심한 작업에서 얻은 효과를 모든 작업의 향상으로 과장하지 않을 수 있다. 실제 작업 기록에서 확인한 시간과 만족·피로에 관한 응답도 서로 다른 근거로 해석한다.

당시 재조사에서 일반 브라우저로 정량적 지표 설계, 실제 효과, 주요 개선점, 설문과 마지막 한계 설명을 확인했다. 후속 웹 읽기 도구의 오류는 그 브라우저 확인을 취소하거나 페이지가 없다는 근거로 사용하지 않았다.

### LINE Plus: 완료 정의와 산식에 따라 생산성 결론이 달라짐

메신저·인터넷 서비스 기업 LINE 계열의 백엔드팀이 공개한 [Can AI tools really deliver 10× productivity? A backend team’s 10-month record](https://speakerdeck.com/lycorptech_jp/can-ai-tools-really-deliver-10x-productivity-a-backend-teams-10-month-record-9x-plus-productivity-built-by-redefining-environment-star-verification-star-work-definition)는 2026-06-29 공식 발표다. 약 10개월의 Jira 티켓 384개와 병합 PR 460개 등을 바탕으로 수작업, 프롬프트, 컨텍스트 구성, 자율 에이전트, 하네스 도입 단계를 비교했다.

이 발표에서 완료는 작업 시작부터 병합까지이며 QA와 출시는 제외된다. 팀 규모도 3명에서 7명으로 변했다. 무엇을 완료로 보았는지와 어느 조직 조건에서 관찰했는지를 함께 읽어야 한다.

발표의 생산성 9.24배는 작업량 보정과 처리속도를 결합한 값이다. 보정 작업량 WWP의 산식은 다음과 같다.

```text
WWP = SP × (0.35·구조 영향 + 0.20·유효 코드량
            + 0.25·명세 깊이 + 0.20·검증) ÷ AI 반복 차감
```

SP는 팀이 추정한 작업 크기다. 같은 자료도 완료 티켓을 단순 집계하면 2.82배, SP만 사용하면 5.1배가 된다. 발표자는 9.24배를 정의에 의존하는 상한으로 명시한다. [37쪽 산식과 민감도](https://files.speakerdeck.com/presentations/8b57640892f6487a8080ed8ffe57c8fd/slide_36.jpg)는 계산법의 선택이 결과 해석에 미치는 영향을 보여 준다.

같은 3SP 티켓의 평균 처리시간은 Agentic 단계 1.5일에서 Harness 단계 3.8일로 늘었다. 단계마다 작업 성격·모델·인원이 달라 하네스의 독립 효과를 분리한 실험은 아니다. 사전에 정한 성공 임계치도 확인되지 않는다. [36쪽 단계별 비교](https://files.speakerdeck.com/presentations/8b57640892f6487a8080ed8ffe57c8fd/slide_35.jpg)와 종합 생산성 수치는 함께 해석해야 한다.

이번 평가에서 가져온 것은 완료의 끝을 명시하고 원시 시간·완료 수·품질을 먼저 제시하는 방식이다. 합성 점수를 사용한다면 계산법을 바꿨을 때 결론이 어떻게 달라지는지도 보여야 한다. 현재처럼 표본과 조건이 제한된 작업에서는 임의의 종합 생산성 점수보다 실제 작업별 결과·범위·남은 문제를 보여 주는 편이 적절하다는 판단을 유지한다.

### METR: 실제 시간과 체감, 선택 조건과 병렬 실행을 구별

AI 평가 연구기관 METR의 [2025년 실험 논문](https://metr.org/Early_2025_AI_Experienced_OS_Devs_Study-paper.pdf)은 숙련 오픈소스 개발자 16명의 실제 작업 246개를 미리 정한 뒤 AI 사용 가능 여부를 무작위 배정하고 완료 시간을 측정했다. 당시 AI 사용 조건은 19% 더 오래 걸렸지만 개발자의 체감은 달랐다.

이 결과는 당시 도구와 참가자·과제 조건에서 측정한 것이다. 현재 모델의 성능이나 이번 하네스 개선의 결과로 일반화하지 않는다. 기존 분석에서 가져온 방법은 결과를 보기 전에 과제를 정하고 실제 완료 시간을 재며, 체감과 측정을 별도로 보는 것이다. 모든 실제 프로젝트에 무작위 AI 사용·비사용 실험을 요구하는 것은 아니다.

METR의 [2026-02-24 후속 설명](https://metr.org/blog/2026-02-24-uplift-update/)은 AI를 못 쓰는 조건을 피하는 참가자·과제 선택과 병렬 작업 때문에 측정이 어려워졌다고 설명한다. 여기서는 경과 시간, 사람이 직접 일한 시간, 동시에 끝낸 작업 수를 분리해야 한다는 점을 참고했다. 병렬 실행이 포함되면 한 작업의 대기 시간이 길었다는 사실과 사람의 직접 작업이 늘었다는 사실이 같지 않을 수 있다.

이번 평가의 기본 관심은 AI 사용 유무보다 기존 AI 개발 방식과 사용자가 개선한 방식의 차이다. 무엇을 비교했는지 먼저 구분해야 하며, 작업·모델·사람의 경험·실행 조건이 바뀐 경우에는 그 변화도 함께 남긴다. 실제로 잰 시간과 과거 방식이라면 걸렸을 것으로 추정한 시간은 같은 수치로 취급하지 않는다.

## 사람의 이해와 재사용, 하네스 운영 부담

### LINEヤフー: 문서가 있어도 남을 수 있는 인지부채

LINEヤフー의 Masami Yamate가 2026-07-14에 발표하고 07-15에 게시한 [AI가 구현을 자율 수행하는 시대의 인지부채와의 싸움](https://speakerdeck.com/lycorptech_jp/20260715b)은 AI가 구현을 진행하는 동안 코드 이해와 리뷰가 따라가지 못한 경험을 설명한다. 설계 이유를 문서와 PR에 연결하는 방식으로 대응했지만, 이후에도 의도 합의의 부담이 앞단에 남았다고 보고한다.

이 자료는 문제와 대응을 설명하는 정성 사례다. 이해도와 재작업 감소를 수치로 검증한 연구는 아니며 코드·업무 측정 원자료를 확보한 것도 아니다. 설명 문서가 존재한다는 사실만으로 사람의 이해가 회복됐다고 판단하지 않아야 한다는 관찰을 뒷받침한다.

이번 평가에서는 설계 이유를 검토 자료에 연결하는 구성과, 사람이 다음 변경을 올바르게 판단하고 수행하는 능력을 함께 살핀다. 설명 만족도, 실제 이해, 의도 합의에 들어간 부담이 서로 어떻게 달라졌는지 구별하는 데 참고한다.

### Anthropic: 설명 만족도와 실제 이해·수행을 구별

AI 개발사 Anthropic의 [How AI assistance impacts the formation of coding skills](https://www.anthropic.com/research/AI-assistance-coding-skills)는 2026-01-29에 공개된 연구 설명이다. 개발자 52명에게 익숙하지 않은 라이브러리 과제를 주고 AI 사용 여부를 무작위 배정한 뒤 코드 읽기·디버깅·개념 이해 등을 평가했다.

보고된 AI 조건 점수는 50%, 비사용 조건은 67%였고, 작업시간 차이는 통계적으로 유의하지 않았다. 이 수치는 단기 학습 실험의 이해도 평가 결과이며 현업 하네스의 효과나 장기 유지보수성을 측정한 것은 아니다.

이번 평가에서는 설명 만족도와 별도로 코드 경로를 설명할 수 있는지, 결함 원인을 판단할 수 있는지, 필요한 후속 수정을 실제로 수행할 수 있는지를 확인하는 방법에 참고했다. 모든 작업에서 고정된 이해도 시험을 실시하거나 사람의 모든 구현 세부 이해를 요구하는 것으로 확장하지 않는다. 주장하려는 이해와 판단 능력에 맞는 관찰을 선택한다.

### 우아한형제들: 입력량과 호출 수는 운영 비용의 관찰

우아한형제들의 이재홍이 작성한 [하네스 엔지니어링으로 팀 맞춤형 AI 환경 구축하기](https://techblog.woowahan.com/26177/)는 2026-04-17 공식 글이다. 5개 도메인에서 AI 자율 탐색과 스크립트 요약을 비교해 입력 데이터량 평균 96.5% 감소, 호출 4회에서 1회 감소를 보고한다. 약 6,800토큰 절감은 bytes에서 환산한 추정이다.

이 비교에서 개발 완료 시간과 결함률까지 정량 입증한 것은 아니다. 입력 데이터량, 실제 사용 토큰, 환산한 토큰 추정, 호출 횟수는 서로 다른 측정 내용이다. 그 감소 자체를 개발 품질 개선이나 수용까지의 시간 절감으로 바로 바꾸어 말하지 않는다.

이번 평가에서는 이런 내용을 하네스 운영 비용으로 기록할 수 있다. 그 절감으로 중요한 맥락이 빠지지 않았는지는 실제 요구에 대한 결과 품질과 함께 확인해야 한다. 구성의 제작·유지·검토 비용도 이득을 해석할 때 포함하거나, 운영 중의 효과만 비교했다면 그 범위를 밝혀야 한다.

### 무신사: AI 코드 리뷰 운영을 공통화한 사례의 역할

무신사 김의중 Uyjoong의 [무신사의 AI 코드 리뷰 프로세스 구축기](https://techblog.musinsa.com/무신사의-ai-코드-리뷰-프로세스-구축기-3ddb3c674e56)는 2026-02-10 공식 글이다. 공통 실행을 Composite Action으로 제공하고, 사람의 답변·해결 기록을 보존하면서 방치된 봇 코멘트를 정리하는 운영 방식을 설명한다. Composite Action은 여러 실행 단계를 묶어 재사용하는 GitHub Actions 구성이다.

당시 브라우저에서 도입·전사 공통화·팀 확장·최적화·마무리까지 확인했다. 다만 코드 리뷰 시간이나 결함률의 전후 실측은 확인되지 않았다. 따라서 앞의 Copilot 도입 글에서 보고한 개선율을 이 별도 사례에 붙이지 않는다.

이 자료는 공통 실행 구성과 사람의 검토 기록, 방치된 자동화 산출물의 정리라는 운영 선택을 이해하는 참고다. 재사용 가능한 구성을 만들었다는 사실과 그 구성으로 실제 개발 품질·부담이 개선됐다는 결과는 각각의 근거로 확인해야 한다.

## 정성·정량 근거와 결론을 연결하는 방법

### Runeson·Höst: 자료에서 결론까지 따라갈 수 있는 사례 설명

룬드대학교 연구자 Per Runeson과 Martin Höst의 [Guidelines for conducting and reporting case study research in software engineering](https://link.springer.com/article/10.1007/s10664-008-9102-8)은 실제 소프트웨어 개발 현장을 연구하고 보고하는 지침이다. 온라인 공개는 2008-12-19, 학술지 게재는 2009년 14권 131–164쪽이다. 기존 조사에서는 [대학 서지](https://www.lu.se/publikation/216a6bb2-bb55-4f2a-a9a1-a4079268ae80)와 출판사 본문을 확인했다.

확인한 §§2.2·5.2·6.1은 정성·정량 자료의 결합, 결론에서 원자료까지 추적 가능한 설명, 다른 설명과 반대 사례의 검토, 상황을 포함한 결과 해석에 사용했다. 독자가 수집 자료에서 결과와 결론을 도출한 과정을 따라갈 수 있어야 한다는 설명이 핵심이다.

이번 평가에서는 코드, 원래 요구, 완료 보고, 이후 정정과 실제 변경을 서로 대조한다. 관찰한 사실과 그에 대한 해석을 구분하고, 동일한 자료에 가능한 다른 설명도 함께 검토한다. 예를 들어 일부 구조 개선은 코드에서 확인되더라도 전체 요구의 완료나 새 스킬의 효과는 별도 근거가 필요할 수 있다. 판단에 필요한 원문 발췌와 코드 요약을 현재 평가 기록에 함께 두는 이유다.

모든 작업을 학술 연구의 수집·분석 절차로 운영할 필요는 없다. 정성 분석을 수치로 대체해야 한다는 근거도 아니다. 몇 건의 사례로 모든 개발 작업의 평균 효과를 추정하지 않고, 확인한 상황과 자료 안에서 결론을 설명하는 방법으로 사용한다.

### SPACE: 빠진 관점을 확인하는 보충 자료

Nicole Forsgren 외의 [The SPACE of Developer Productivity](https://www.microsoft.com/en-us/research/publication/the-space-of-developer-productivity-theres-more-to-it-than-you-think/)는 개발 생산성을 여러 측면에서 보는 연구 글이다. 2021-02 ACM Queue 19(1)에 실렸으며 [Queue 본문](https://queue.acm.org/detail.cfm?id=3454124)과 Microsoft 공식 서지·초록이 확인 기록에 있다.

이번 분석에서 참고한 것은 커밋·코드량 같은 하나의 활동량으로 생산성을 대표하지 않고, 결과·작업 흐름·사람의 경험을 함께 살펴야 한다는 관점이다. 개발 결과만 보다가 이해와 부담을 빠뜨리거나, 활동량이 늘었다는 이유로 전체 성과가 좋아졌다고 판단하지 않는 데 보완적으로 사용한다.

SPACE는 기존 세 평가 기준의 원천이나 그 기준이 옳다는 검증 근거가 아니다. 이번 평가 전체를 SPACE 분류에 맞추거나 그 틀로 다른 분석을 대체하지 않는다.

### DORA: 서비스 전달 흐름을 실제로 관찰할 때 참고

DORA의 [소프트웨어 전달 성과 지표](https://dora.dev/guides/dora-metrics/)는 애플리케이션·서비스의 소프트웨어 전달 성과를 맥락과 함께 해석하는 자료다. 기존 조사에서는 공식 웹 본문을 확인했다.

이번 평가에서는 서비스 안의 전달 흐름을 관찰할 조건이 맞는 경우에 선택적으로 참고한다. 배포까지 관찰하지 않은 개발 작업에 배포 성과를 붙이지 않으며, 서로 다른 작업·프로젝트를 맥락 없이 순위화하는 공통 점수로 사용하지 않는다. LINE 발표에서 병합을 완료로 정의한 것처럼, 실제 관찰의 끝이 어디인지 먼저 확인하는 데 연결된다.

## 접근이 제한된 두 세션에서 보존할 내용

아래 두 자료는 사용자가 보존을 요청한 참고 자료다. 2026-09-09 당시 실제 브라우저에서는 404였고, 검색·읽기 도구에는 과거 수집 텍스트가 남아 있었다. 삭제하지 않으며, 현행 원문을 직접 확인한 회사 사례와도 구분한다. 두 결과는 수집 시점을 ‘Crawled: last week’로 표시했지만 정확한 수집 날짜는 제공하지 않았다.

### 무신사 재고 플랫폼: 구현 밖의 문서·합의·검증 비용

무신사 김지환·김도영의 [AI-native 하게 재고 플랫폼 구축하기](https://pattern.musinsa.com/sessions/collection-ciap-staff-engineer/)는 검색 추출문상 2026-09-18 예정 행사 세션이다. 추출문은 재고 플랫폼팀이 요구사항·구조·코드·테스트·검증 증거를 연결하는 하네스를 소개한다고 설명한다.

전체 10개월 과정에서 구현에는 2개월이면 충분했고, 나머지는 문서 이해·합의·검증 등 구현 바깥의 병목을 해결하는 시간이었다는 내용이 남아 있다. **이는 10개월에서 2개월로 개발 기간을 단축했다는 전후 비교가 아니다.** 시간 산정 방식도 확인되지 않았다. 비교 일치율 99.99%라는 표현은 있으나 비교 대상·분모·측정기간·남은 불일치의 중요도·합격 문턱은 추출문에서 확인되지 않는다.

출처 기록에 보존된 최소 발췌는 다음과 같다. 현재 웹페이지에서 직접 읽은 인용이 아니라 당시 검색 도구가 원 URL에 연결해 반환한 텍스트다.

> AI로 구현이 빨라지자 병목은 사라지지 않고 문서, 합의, 검증으로 옮겨갔습니다.

이 내용에서 도출했던 평가상의 관심은 코딩과 구현 바깥의 시간을 구분하되 최종 성과를 전체 비용으로 보고, 요구 변경 뒤 문서·코드·검증이 같은 조건을 가리키는지 실제 결과에서 확인하는 것이다. 이 제안의 유용성과 회사 수치의 검증 상태는 구별한다. 이 자료의 미확인 수치로 현재 판정 기준이나 목표값을 정하지 않는다.

### 29CM: 스킬과 규칙의 재사용 효과를 자기 보고로 추정

무신사 계열 패션 플랫폼 29CM의 김지혜·김태호가 발표하는 [개인의 숙련도는 조직의 자산이 아니다](https://pattern.musinsa.com/sessions/collection-product/)도 검색 추출문상 2026-09-18 예정 세션이다. 추출문에 따르면 6개월간 258세션을 기록하고, 절감 1,443시간 중 52%를 스킬·규칙·검수 게이트의 자산화 효과로 분류했다고 소개한다.

절감 시간은 **자기 보고 추정**이라고 명시돼 있다. 상세 산식·중복 산정 방식·통제군·원시 세션 기록은 확인되지 않았다. 당시 웹 읽기 도구가 반환한 지난주 수집 텍스트 53줄을 현행 원문 접속 성공으로 해석하지 않는다. 출처 기록의 최소 발췌는 다음과 같다.

> 절감 시간이 자기 보고 추정이라는 한계까지 그대로 공개합니다.

이 자료에서 가져온 관찰은 실제 잰 시간과 예전 방식이라면 걸렸을 것이라는 추정을 별도로 남기는 것이다. 재사용 가능한 파일을 만들었다면 다음 세션이나 다른 주체가 정확한 결과를 더 적은 도움으로 만드는지까지 관찰할 수 있다. 스킬 파일 수나 도입 신청 수가 곧 개발 품질 개선을 뜻하지는 않는다.

두 세션의 제목·연사·핵심 수치·다른 도메인 재게시 여부를 조사했지만 당시 새 공식 주소는 확보하지 못했다. 행사 목록도 404였고 메인에는 행사 제목·문의·푸터만 표시됐다. 행사 안내에서 일정과 도메인은 교차 확인됐지만 두 세션의 본문과 수치를 검증하는 대체 자료는 아니었다. 사이트 변경이나 게시 상태 전환 가능성은 있어도 404의 원인은 확인되지 않았다. 상세 접근 추적과 insane-search 실패 기록은 [출처 기록](../../../source/09-ai-native-engineering-evaluation/source.md)에 남아 있다.

## 현재 평가 방법에 연결한 선택

위 자료의 역할을 함께 보면 다음과 같다. 이는 기존 분석에서 선택한 방법과 범위이며 어느 출처도 평가안 전체나 현재 개선안의 효과를 검증해 주지는 않는다.

| 평가에서 필요한 내용 | 선택한 외부 방법 | 적용하면서 보존할 구분 |
| --- | --- | --- |
| 요구한 결과의 충족과 완료 판단 | 당근의 기대 동작·코드 수용, 우아한형제들의 AI 검사 후 코드 재검사 | 동작 통과와 개발자 수용을 함께 보고, 최초 완료 상태와 교정 후 상태를 구분한다. 고정 출력 방식이나 자동 린트를 일괄 의무화하지 않는다. |
| 코드 품질과 후속 변경 | Google의 기술적 리뷰 내용, SEI의 변경 상황과 관찰 | 취향과 기술적 이유, 구조 검토의 예상과 실제 변경 결과를 구분한다. 특정 조직의 규칙이나 수치 문턱을 가져오지 않는다. |
| 이해·판단과 사람의 부담 | LINE 인지부채 사례, Anthropic의 실제 이해·수행 관찰 | 문서 존재·설명 만족도·실제 이해와 수행을 구분한다. 단기 학습 실험이나 정성 경험을 장기 효과로 확장하지 않는다. |
| 결과까지의 시간과 비용 | 무신사의 구간·분포·설문 비교, METR의 측정과 병렬 작업 한계 | 경과 시간·직접 작업·대기·병렬 완료량·체감·추정을 구분한다. 품질·재작업·운영 비용을 함께 해석한다. |
| 완료 정의와 수치 해석 | LINE 생산성 발표, 조건이 맞을 때 DORA | 병합·수용·배포 중 실제 끝점을 밝힌다. 산식에 의존한 종합 점수와 원시 관찰을 구분한다. 프로젝트 간 순위로 고정하지 않는다. |
| 판단 근거의 설득력 | Runeson·Höst의 사례연구 지침 | 요구·관찰·해석·다른 설명을 연결하고 필요한 원문과 코드 근거를 남긴다. 정성 분석을 버리거나 모든 작업을 학술 실험으로 만들지 않는다. |
| 빠진 관점의 점검 | SPACE | 활동량 하나로 전체 성과를 대표하지 않는다. 기존 세 기준을 대체하는 틀로 고정하지 않는다. |
| 재사용과 운영 구성의 비용 | 우아한형제들 하네스, 무신사 AI 리뷰 운영 | 입력량·토큰 추정·호출 수·공통 구성의 존재와 실제 개발 효과를 구분한다. |

자료를 실제로 적용할 때는 평가하려는 질문과 확보할 수 있는 근거에 맞춰 선택한다. 동일 조건의 비교가 가능하다면 비교의 강점이 있지만, 서로 다른 실제 작업을 수행한다는 이유로 정성적 분석과 원자료 비교를 버리지는 않는다. 작업별 범위·조건·실패·다른 설명을 함께 제시하고 확인한 수준 안에서 판단한다. 구체적인 비교 선택과 판정 기록은 [평가 방법](02-evaluation-method.md)에 이어진다.

## 당시 제안으로 남긴 내용과 현재 본문의 경계

기존 외부 사례 분석의 후반에는 고정 조건 A/B 실행, 핵심 미충족·회귀 0건이라는 초안 문턱, 주지표 하나 선정, 특정 과제·이해 질문·후속 수정 시험 목록이 제안돼 있었다. 이것들은 여러 방법 중 당시 마련한 실험안이며 범용 평가의 필수 절차로 채택되지 않았다. 현재 본문에서는 외부 자료가 실제로 보여 준 방법과 유효한 적용 조건을 보존하고, 그 미채택 실험안은 [정리 전 분석 기록](archive/2026-09-09-before-organization/10-ai-native-engineering-evaluation-references.md)에 둔다.

평가 내용의 구체성과 사전 판단 이유를 남기는 필요는 유지한다. 다만 모든 작업을 같은 조건에서 재실행하거나 고정 시험을 통과하도록 만드는 것과 구별한다. 실제로 사용할 비교 단위·근거·판정 조건은 [평가 방법](02-evaluation-method.md)과 해당 작업의 평가 기록에서 정한다.
