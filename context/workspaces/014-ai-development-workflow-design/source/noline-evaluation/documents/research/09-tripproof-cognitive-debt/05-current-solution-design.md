# TripProof 이해 지원의 현재 설계

## 목표와 이 문서의 역할

목표는 **AI와 함께 작업하면서 사람이 필요한 이해와 판단을 유지하고, 나중에 다시 복구해야 할 인지부채를 줄이는 것**이다. 인지피로는 개입의 비용과 제약으로 본다. 필요한 전제·위험·미확정을 없애거나 AI가 판단을 대신해 응답을 짧게 만든 것을 성공으로 삼지 않는다. 필요한 이해를 확보하면서 반복 설명, 용어 해독, 재탐색과 맥락 재구성 부담을 줄이려 한다.

현재 선택은 세 개의 project-local skill과 하나의 비호출 공통 guidance다. 이 문서는 그 선택, 선택 이유, 결과에 남겨야 할 의미, 적용 경계와 아직 확인하지 않은 것을 소유한다. 실행 절차와 호출 metadata의 원천은 [v0 검토 산출물](v0/README.md)의 실제 파일이며, 완성 응답과 호출 경계 예시는 [출력 preview](v0/OUTPUT-PREVIEW.md)가 소유한다. 현재 package는 연구 repository 안의 미설치 후보다.

현재 설계를 이해할 때는 이 문서에서 시작하고, 선택을 재검토할 때 해당 분석과 원자료로 내려간다. 과거 판단이 보존할 가치가 있다는 사실만으로 별도 현재 문서나 기본 읽기 입력이 되어야 하는 것은 아니다. 외부 근거, 대안 비교와 변경 당시의 검토 기록은 각 역할에 따라 연결하며, 현재도 중요한 선택 이유는 아래 본문에 남긴다.

## 세 사용 장면과 선택한 구성

세 장면은 사용자가 이해하려는 대상과 필요한 조사·대화 수명이 다르다.

- **작업을 시작하기 전:** `work-discussion`은 앞으로 만들 결과와 지킬 경계를 함께 맞추고 `작업 이해안`을 만든다. 사용자가 `/` UI에서 `$work-discussion`을 직접 선택할 때만 적용한다. 여러 질문 round가 필요할 수 있으며 결과는 우선 현재 대화의 작업 출발점이다.
- **앞선 AI 응답에서 이해가 끊긴 때:** `explanation-recovery`는 그 응답의 실제 뜻과 빠진 연결을 복구한다. 직접 호출하거나 사용자가 특정한 앞선 설명의 뜻·지시 대상·중간 논리를 놓쳤음을 드러낸 요청에서 선택한다. 대화만으로 해결되면 자료 조사 없이 작은 응답으로 끝날 수 있다.
- **이미 존재하는 작업물을 이해할 때:** `work-artifact-briefing`은 code·변경·문서·분석·검토 결과의 역할, 실제 연결과 근거 범위를 조사해 설명한다. 직접 호출하거나 해당 작업물의 이해가 목적인 요청에서 선택한다. 현재 구조뿐 아니라 특정 변경과 과거 시점의 작업물도 직접 다룬다.

세 skill을 유지한 이유는 사용자가 하나로 묶지 않기로 선택했고, 위 입력·조사 범위·대화 수명·기대 결과의 차이가 실제로 존재하기 때문이다. 외부 자료가 세 skill이라는 완성 구성을 직접 제시한 것은 아니다. 이름만 다른 공통 template이나 별도 상위 skill로 합치지 않고 반복되는 근거·권한 기준만 공유한다.

`work-discussion`은 기존에 사용자가 하던 인터뷰와 구체화를 보강하는 **예방적·선택적 개입**이다. 작업 전 논의가 TripProof에서 반복 실패의 중심이었다고 전제하지 않으므로 일반 작업 대화에 자동으로 질문 절차를 붙이지 않는다. 작업물 브리핑은 실제 판단 주체, 국소 test와 전체 목표, 내부 데이터와 사용자 답변의 차이를 설명하므로 확인된 TripProof 문제와 가장 직접적으로 연결된다. 세 장면을 같은 근거 강도의 해결책으로 취급하지 않는다.

나머지 둘의 implicit invocation은 사용자가 드러낸 이해 목적을 해당 skill로 연결하는 것이다. 키워드만으로 발동하거나 사용자가 아직 발견하지 못한 문제를 AI가 먼저 찾아 개입한다는 뜻이 아니다. 단순 요약·재작성·값이나 위치 조회·진행 보고·구현·수정·진단·review·acceptance 판정이 주목적인 요청에는 자동 적용하지 않는다. 호출 허용과 실제 host가 정확히 skill을 선택해 수행했다는 사실도 구분한다.

세 장면은 한 대화에서 이어질 수 있으나 고정 pipeline은 아니다. 작업 논의에 현재 구조 이해가 필요하면 브리핑의 설명을 필요한 만큼 사용하고 돌아올 수 있고, 그 설명이 끊기면 설명 복구가 필요할 수 있다. 복구 중 목표나 선택이 쟁점으로 드러나면 논의를 다시 열 수 있지만, 그 사실만으로 직접 호출 전용인 `work-discussion`이 발동하지는 않는다. 사실이 부족한 문제는 설명을 매끄럽게 만드는 대신 해당 source나 실행 근거에서 확인한다.

## 각 결과가 남겨야 하는 이해

### 작업 이해안

작업 이해안은 이번에 실제로 달라질 결과, AI가 확인한 현재 사실, 지킬 의미·제약, 사람이 정한 선택, 구현하면서 열어 둘 부분과 바로 이어갈 행동을 관계 있게 보여 준다. Spec이나 내부 module·task의 전체 목록을 미리 확정하는 결과가 아니다. Code·문서·환경에서 답할 사실은 AI가 조사하고, 범위·우선순위·허용할 축소처럼 결과를 바꾸는 선택은 사람이 판단하도록 한다.

원하는 결과나 완료 경계가 여러 뜻으로 읽힐 때는 같은 대표 입력·사용 장면에서 **원하는 결과와 겉보기에는 비슷하지만 부족한 결과**를 대비한다. 예를 들어 내부 후보 `facts[]`가 화면에 도착하는 것과, 후보를 supported·missing 상태와 근거가 포함된 `ChatAnswer`로 바꿔 사용자가 질문의 답을 받는 것은 다른 결과다. 특정 구현 이름을 충분·부족의 기준으로 삼지 않고 사용자가 받을 결과에서 무엇이 빠지는지 설명한다. 이미 정한 차이는 이해안에 남기며 재질문하지 않는다.

결과를 바꾸는 선택이 남았다면 그 선택을 먼저 다루고, 선택 후에 최종 이해안을 만든다. 이미 충분하면 의례적인 질문 round를 만들지 않는다. 작은 질문 round는 선행 결정을 보고 다음 질문을 할 수 있게 하려는 방식이며, 피로를 이유로 중요한 예외와 선택을 삭제하는 장치가 아니다. 모든 작업에 대표 사례나 별도 acceptance 문서를 요구하지 않는다.

### 설명 복구본

설명 복구는 사용자가 가리킨 **실제 앞선 응답의 뜻**에서 시작한다. 같은 단어의 일반 정의나 codebase에 있는 동명 symbol로 대상을 바꾸지 않는다. 직접 답과 가장 가까운 누락을 먼저 연결하고, 그것으로 부족할 때 마지막으로 의미가 공유됐던 지점과 필요한 전제까지 돌아간다. 원뜻의 조건·한계를 유지하고, 새 라벨이나 비유를 늘려 막힘을 덮지 않는다.

예를 들어 앞선 말의 `verdict`를 묻는다면 “판단”이라는 동의어만 주는 데서 끝내지 않고, 그 문장에서 근거를 본 뒤 결과를 받아들일지 보류할지 정하는 결론을 뜻했는지 설명한다. 앞선 문장을 확인하지 못했고 가능한 뜻에 따라 답이 달라지면 대상을 확인하거나 현재 해석이 추정임을 밝힌다.

**원뜻 복구와 원래 주장의 타당성 인정은 다르다.** 뜻 질문과 이의 제기가 함께 있으면 둘 다 답한다. 대화나 읽은 근거에서 실제 오류·모순·잘못된 추론을 확인했다면 문제가 된 연결과 무엇을 유지·정정·철회하거나 아직 판단하지 못하는지 보여 준다. 재설명 중 결론이나 제안이 달라졌다면 달라진 뜻을 원래부터 했던 말처럼 쓰지 않는다. 반대로 사용자가 혼란을 알렸다는 이유만으로 원래 주장을 오류로 단정하지 않는다.

대화만으로 복구할 수 있으면 repository와 공통 guidance를 먼저 읽지 않는다. 사실 부족이나 의심되는 사실 오류가 현재 답을 바꾸고 대화로 확인할 수 없는 부분에 한해 source를 조사한다. 정정은 확인한 발화·사실·추론에서 설명하며 AI의 숨은 의도를 만들어내지 않는다. 설명 안의 정정이 과거 전체 감사, 구현·문서 수정이나 작업 범위 재합의를 자동으로 시작하게 하지는 않는다.

### 작업물 이해 브리핑

브리핑은 대상의 전체 역할과 대표 흐름에서 시작해 현재 질문에 필요한 component 책임·경계, 실제 연결, source·사용 위치와 실행 근거로 내려가게 한다. File 이름이나 호출 순서를 나열하는 것만으로 사용자가 자기 일과 연결할 수 있다고 가정하지 않는다. 중요한 이름은 처음 등장할 때 그것이 가리키는 데이터나 책임, 사용자가 하려는 일에서의 역할과 함께 설명한다.

추상적인 역할 설명만으로 동작이나 근거 한계가 잘 드러나지 않을 때는 대표 장면의 입력·중간값·결과 가운데 필요한 값을 연결한다. 실제 확인한 값과 설명용 값을 구분하고, 중요한 조건에 따라 결과가 달라지면 그 차이를 함께 보여 준다. Source로 재구성한 동작, 관찰한 실행과 아직 제안한 동작의 지위를 유지한다. 핵심 주장 가까이에 무엇을 확인한 source인지 두어 사용자가 설명과 원자료 사이를 이동할 수 있게 한다.

다음 변경이나 선택을 위한 브리핑에서는 중요한 구조가 무엇을 쉽게 만들고 어떤 제약을 남기는지 필요한 부분에서 설명한다. **당시 선택 이유는 당시 자료에서 확인한 경우에만 말하고, 현재 구조에서 도출한 이득·제약과 구별한다.** 모든 구조의 장단점이나 선택 이력을 조사하는 고정 의무는 없으며, 이 조건이 일반 동작 설명을 architecture review로 바꾸지는 않는다.

조사 범위는 질문을 따른다. 변경은 base·target의 diff에 더해 변경 후 source와 consumer·호출 경로를, 현재 구조는 entry point에서 결과·외부 effect까지의 실제 연결을, 과거 작업물은 당시 commit·기록·artifact를 근거로 한다. 문서·검토 결과는 작성 당시의 질문·기준·대상과 근거 범위를 읽는다. 기존 map과 요약은 보조 자료이고 다른 skill이 만든 요약은 필수 선행 단계가 아니다.

관계·분기·상태 변화를 문장으로만 재조립하기 어렵고 그 관계를 놓치면 답의 의미가 달라질 때는 작은 부분 구조를 사용할 수 있다. 구조 표현의 행동 Owner는 이 skill 하나다. 화살표·묶음도 근거가 필요한 관계 주장으로 다루고, AI의 설명용 묶음, 경로의 기본·opt-in·disabled·stub 상태와 미확인을 확인된 전체 구조로 합치지 않는다. Source·configuration으로 재구성한 흐름은 그 범위와 live trace가 아니라는 점을 밝힌다. 근거가 섞인 구간과 생략 범위도 결론에 필요한 수준에서 드러낸다. 정적인 구조도가 영상의 interactive 탐색과 같은 이해 효과를 낸다는 근거는 없으며, 이 선택의 도출과 한계는 [구조 시각화 분석](06-work-artifact-briefing-visual-structure-analysis.md)에 남아 있다.

## 공통 guidance를 분리한 이유와 수명

세 skill이 공유하는 것은 **답을 바꾸는 현재성, 근거별 증명 상한, 사람 판단과 부작용 경계**다. 상황별 호출·조사·대화·출력·종료 방법은 각 `SKILL.md`가 소유한다. 공통 guidance를 상위 workflow로 두거나 일반 대화마다 먼저 읽히지 않는다. 특히 작은 설명 복구에 전체 Project 조사와 긴 근거 분류를 먼저 요구하지 않는 것이 이 분리의 실제 의미다.

현재 [공통 guidance 후보](v0/payload/context/project/guidance/explanation-and-evidence-criteria.md)의 설치 목표 canonical은 TripProof의 `context/project/guidance/explanation-and-evidence-criteria.md`다. 세 skill 본문의 canonical 목표는 `.agents/skills/<skill-name>/SKILL.md`이며, `.claude/skills/`와 `.codex/skills/`는 그 본문을 가리키는 symlink다. 연구 분석과 preview는 설치 뒤 runtime 의존성이 되지 않는다. 설치 구조와 target 기준 상태는 [v0 manifest](v0/README.md)가 소유한다.

공통 기준은 여러 skill이 조건부로 소비하는 Project-wide 설명 판단이어서 Project guidance에 둔다. 제품 목적, 현재 code, test 결과와 사람의 결정을 복제하는 새 정본이나 `common/`·`current/`와 경쟁하는 새 context 단위를 만들지 않는다. 같은 기준의 반복은 한 곳에서 유지하고, 상황마다 다른 실행 방법은 가까운 skill에서 바꿀 수 있게 한다.

Live 채택 뒤 관련 Project-wide 설명 계약을 바꾸는 주체는 기존 [Project guidance 계약](v0/payload/context/project/guidance/README.md)의 관리 경로를 통해 본문·guidance index·consumer link를 함께 유지한다. Source·authority 계약이나 세 skill의 역할이 바뀌거나, 실제 사용에서 중요한 차이를 반복해서 놓치거나 불필요한 부담을 만들면 다시 판단한다. 세 consumer가 모두 없어지거나 같은 책임을 더 가까운 현재 정본이 소유하면 제거하거나 그 Owner로 합친다. 새 제품 의미·중요 제약·최종 acceptance를 이 문서의 갱신만으로 정하지 않는다.

## 근거가 말할 수 있는 범위

설명에 필요한 권위는 질문마다 다르다. 근거를 찾았다는 사실만으로 현재 질문에 사용할 수 있는 결론까지 확보한 것은 아니며, 다음 차이가 결론을 바꿀 때 응답에 드러낸다.

- **과거 decision·design**은 당시 의도·선택 이유·명시된 제약을 보여 준다. 그 의도가 현재 구현됐거나 지금도 유효함을 증명하지 않는다.
- **현재 source·configuration·사용 위치**는 현재 구조, 가능한 동작과 연결된 component를 보여 준다. Code에 있는 경로가 이번 실행에서도 실제 수행됐음을 증명하지 않는다.
- **Trace·log·runtime observation**은 관찰한 조건과 실행에서 실제로 지난 경로와 결과를 보여 준다. 관찰하지 않은 입력과 모든 실행을 보장하지 않는다.
- **Test·compiler·rule**은 표현되고 검사·실행된 조건의 통과나 type·정적 규칙 준수를 보여 준다. 다루지 않은 위험, 제품 목표의 타당성과 전체 완료를 판정하지 않는다.
- **AI 해석**은 위 자료의 관계와 현재 질문에서의 의미를 도출한다. 유용한 판단 재료지만 source나 관찰 사실 자체가 아니며, 직접 근거가 허용하는 범위를 넘겨 단정하지 않는다.
- **외부 답변과 사람 판단**은 서로 다른 책임이다. 판매자·운영자 등 외부 책임자만 아는 사실은 확인한 답변 범위에 한정한다. 제품 가치, 중요한 범위 축소, 위험 수용과 최종 acceptance는 실제 책임자가 판단한다. AI의 추천은 채택된 결정이 아니다.

현재 code·실행·과거 사례를 혼동할 수 있으면 관련 branch·commit·working tree, runtime configuration, artifact 생성 시점이나 당시 결정의 범위를 확인한다. 모든 답에 hash를 붙이는 의례는 없으며, 답의 의미를 바꾸는 기준과 재확인 조건만 남긴다. Current summary와 source가 충돌하면 summary를 사실로 반복하지 않고 차이와 설명 범위를 밝힌다. 현재성을 확인하지 못했다면 확인하지 못한 상태로 말한다.

### TripProof에서 놓치면 안 되는 차이

다음은 [실제 장면과 원인 분석](03-integrated-causal-map-and-solution-obligations.md)에 근거한 역사적 대비다. 현재 TripProof working tree의 상태나 이번 skill 실행 결과를 주장하는 예시는 아니다.

- **Interface와 실제 판단:** 당시 proposer interface·validator는 유용한 기반이었지만 실제 proposer가 local regex였으므로 LLM provider가 의미를 판단하는 단계까지 수행한 것은 아니었다. Interface 존재와 test 통과로 실제 provider 연결을 대신 증명할 수 없다.
- **국소 개선과 전체 구조:** 세 refactor의 변경 내용은 그 부분의 구조 개선을, 서버 test 56개 통과 보고는 작성된 조건의 통과를 보여 준다. 이 두 근거만으로 서버 전체 readable-flow 목표가 충분히 달성됐다고 판정할 수 없다. 개별 test와 실행 조건을 읽지 않았다면 통과 보고보다 구체적인 보장도 단정하지 않는다.
- **데이터 전달과 사용자 답변:** 당시 raw `facts[]` 연결안은 실제 구현되지 않은 계획이었다. 계획대로 내부 후보를 화면에 전달해도 `FactCandidate[]`를 supported·missing 상태와 근거가 담긴 `ChatAnswer`로 변환하는 책임은 남는다.

이 대비는 interface, refactor나 작은 end-to-end 작업의 가치를 부정하지 않는다. 수행한 국소 가치와 아직 수행하지 않은 상위 책임을 같은 완료로 합치지 않기 위한 기준이다. 보존된 보고가 exact file·symbol을 담고 있지 않으면 현재 위치를 만들어 붙이지 않고, 현재 구조를 묻는 다음 질문에서 live source를 확인해야 한다.

## 설명 깊이와 현재 응답의 종료

깊이는 현재 질문에서 무엇을 생략하면 뜻이 달라지는지로 조절한다. 전제·현재성·실제 연결이 빠지거나, 근거 종류가 섞여 더 강한 보장처럼 보이거나, 수행한 것과 stub·미구현을 혼동하거나, 사용자가 이유·영향·전체 흐름을 요청했다면 필요한 만큼 더 설명한다. 작은 diff나 가역적 작업이라는 이유만으로 중요한 조건을 줄이지 않는다.

이미 공유한 의미 구조 안의 짧고 명확한 질문이라면 직접 답과 한계를 말하고 필요한 source 위치를 남기는 것으로 충분할 수 있다. 전체 history·모든 파일·모든 실패 경로를 펼치거나 매번 같은 목차를 채우지 않는다. 선택적 설명은 다음 판단에 필요한 정보를 제거하는 요약과 구별된다.

현재 응답은 요청한 질문에 답하고, 결론을 바꾸는 미확정·미수행·근거 한계와 사람에게 남은 판단이 보이면 끝낼 수 있다. 즉시 결정이 목적이면 선택과 필요한 추가 근거를 연결하고, 우선 현재 구조를 이해하려는 목적이면 전체 관계와 더 확인할 위치 자체를 충분한 결과로 인정한다. 억지로 다음 작업이나 승인 질문을 만들지 않는다.

약속하는 산출물은 **사용자가 이해하고 자기 판단에 사용할 수 있도록 필요한 의미와 근거를 준비한 설명**이다. 사용자의 내적 이해 완료를 판정하는 것은 아니다. 침묵·짧은 동의·다음 주제로 이동한 사실을 이해의 증거로 저장하지 않으며 quiz·재진술·형식적 승인을 기본 종료 조건으로 요구하지 않는다. 이해, 주장에 대한 사실 확인과 동의도 서로 다른 상태다.

## 설명·판정·실행·지속 인수의 경계

설명에 필요한 현재 사실은 허용된 범위에서 조사할 수 있다. 직접 확인한 차이뿐 아니라 그 차이에서 **근거 있게 도출되는 동작·사용상 영향**도 설명하고, 추론한 부분과 근거 범위를 밝힌다. 영향을 말하면 모두 review라는 경계 때문에 필요한 설명을 막지 않는다. 다만 요구 위반 여부, 위험 수용, 작업 중단과 최종 acceptance를 설명 요청만으로 확정하지 않으며, 별도 판정이 요청됐으면 그 범위와 실제 책임을 따른다.

이미 있는 검토 결과는 대조한 기준, 대상과 시점, 발견한 차이, 직접 근거, 영향 범위와 미확정을 읽어 설명한다. 그 결과를 이해하기 쉽게 표현한다는 이유로 finding 범위를 넓히거나 새 최종 판정으로 바꾸지 않는다. 사용자는 설명을 토대로 반대·보류·추가 근거 요구를 할 수 있어야 한다.

Code·test·eval·runtime의 상세 사실은 가까운 Owner가, 여러 작업을 구속할 제품 의미와 조건부 지침은 Project context가, 현재 작업의 목표·제약·열린 판단과 상세 근거로 가는 경로는 Workspace current가 맡는다. Verify는 고정 claim·basis·evidence의 실행 확인을 맡으며 의미의 충분성이나 사람의 acceptance를 대신하지 않는다. 이해 지원은 이 책임들을 현재 사용자가 따라갈 수 있는 설명 관계로 연결하며, 기존 사실성·권한·저장 계약을 새 성과로 소유하지 않는다.

작업 이해안은 대화 산출물이므로 작성됐거나 사용자가 선택지를 골랐다는 사실만으로 spec·ticket·Workspace current·장기 실행 정본이 되지 않는다. **같은 대화에서 사용자가 `이대로 진행해`라고 명시하면 현재 작업 지시로 사용할 수 있다.** 이미 구현까지 요청했다면 이해안을 반환한 뒤 열린 선택을 확인하고 그 지시를 따른다. 다른 session·후속 작업을 계속 구속하려면 Work·spec·Workspace current 등 실제 작업을 소유하는 기존 산출물이 선택과 미확정·완료 경계를 명시적으로 인수해야 한다.

설명 요청만으로 code·문서·test·review 결과를 수정하거나 durable context 갱신·후속 실행을 시작하지 않는다. 지속 학습, 새 적합성 review, 판단을 이후 구현과 완료에 반영하는 일도 별도 책임이다. 후보 수신처를 제안한 것과 실제 인수가 끝난 것을 구분한다. 인수가 없으면 미확정이 지금 답을 막는지, 답의 적용 범위만 제한하는지, 이번 범위 밖의 별도 선택인지가 보이면 된다.

## 선택 근거와 채택하지 않은 방식

현재 구성은 외부 reference의 직접 제안 하나를 채택한 결과가 아니라 [자료별 재추출](01-external-reference-insight-extraction.md)과 [세 장면별 합성](02-three-scenes-reference-synthesis.md)을 실제 TripProof의 [문제·해결 의무](03-integrated-causal-map-and-solution-obligations.md)에 대조한 설계다.

`grill-with-docs`는 작업 전 질문을 돕는 외부 skill로, codebase가 답할 질문을 AI가 조사하게 하는 재료를 제공했다. 질문 round를 선행 결정에 맞춰 작게 나누는 재료와 합쳐 사실 조사·사람 선택을 구분한 것은 현재 합성이다. `Wait What`은 AI 설명을 놓친 지점으로 돌아가 빠진 맥락과 공유 어휘를 쓰게 하는 외부 skill이며, 현재 설명 복구의 직접 재료다. 근거·정정·사람 판단의 전체 계약까지 이 자료가 제공한 것은 아니다.

Source 02의 AI code 작업 발표는 큰 의미 구조에서 필요한 부분을 펼쳐 정확한 source line으로 내려가는 탐색을 보여 준다. 역할·대표 흐름·상태 변화·실행 근거·미완성을 한 브리핑에 연결한 전체 순서는 현재 설계의 합성이다. Source 06의 인지부채 자료는 근거와 사람 판정, 실행 위임과 판단 포기를 구별하는 재료다. 제품 개발 방법인 Shape Up은 전체 문제와 구현 중 열어 둘 부분, 작은 실제 결과와 불완전한 주변부의 구분을 보조한다. 어느 자료도 이 세 skill의 조합이나 정적인 응답 형상의 이해 효과를 직접 검증하지 않았다.

[후보 비교](04-integrated-solution-candidates.md)에 보존된 다른 방식은 다음 이유로 현재 기본 설계에 넣지 않았다.

- **모든 응답의 긴 고정 형식:** 불필요한 읽기 비용을 만들고, 잘못 잡은 목표와 좁은 test 근거를 칸에 넣어도 형식만 완성될 수 있다. 필요한 책임은 유지하되 응답량·목차를 고정하지 않는다.
- **별도 이해 ledger:** 저장, 실제 사용, 현재성, 사람의 이해를 같은 상태로 오인하게 하고 기존 Workspace·Project context와 별도의 갱신·무효화·소비 책임을 만든다. Durable 결정은 기존 Owner가 인수한다.
- **상시 이해 확인:** Quiz나 재진술은 사람을 시험하는 새 부담을 만들며 매번 필요한 설명의 종료를 보장하는 근거도 없다. 사용자의 혼란이 드러나면 다시 설명하되 내적 이해를 형식적 확인으로 대체하지 않는다.
- **같은 AI의 자기 호출, 작업 경계의 강제 호출, 독립 finding 생성:** 서로 배타적인 완성 대안은 아니며 결합할 수 있다. 그러나 같은 AI가 놓친 의미 차이를 다시 스스로 감지하리라는 가정만으로 예방을 보장할 수 없다. 작업 경계 호출과 독립 review에는 호출 event·입력·대조 기준·finding 범위·실제 소비자를 별도로 설계해야 하므로 세 설명 skill의 암묵적 책임으로 넣지 않는다.

세 skill 분리와 호출·응답량 조정의 사용자 선택은 [최초 품질 검토와 수정 기록](../../../workspaces/005-tripproof-cognitive-debt-skill/records/2026-09-06-01-package-quality-review-and-revision-history.md)에, 원뜻·정정과 조건부 대표 장면·값 연결의 근거는 [첫 보강 기록](../../../workspaces/008-tripproof-cognitive-debt-package-adoption/records/2026-09-05-05-quality-review-revision.md)에, 근거 있는 영향과 구조 선택의 이득·제약 보강은 [두 번째 보강 기록](../../../workspaces/008-tripproof-cognitive-debt-package-adoption/records/2026-09-06-03-quality-review-revision.md)에 남아 있다. 이 기록들은 결정 당시의 이유·승인·확인 범위를 다시 보는 경로이며 runtime 필수 입력이 아니다.

## 아직 확인하지 않은 것과 다시 판단할 때

현재 package는 문서·예시와 정적 계약을 검토하고 보강한 결과다. 실제 설치, host의 자연어 routing, 실제 skill 출력, 반복 질문·교정 비용·이해 시간과 장기 인지부채 감소 효과는 이 검토로 증명되지 않았다. 사용자가 결과의 이름·응답량·형상을 실제 사용에서 받아들이는지도 별도 확인이 필요하다. 역사적 TripProof 사례를 설명할 수 있다는 사실은 그 사례에 skill을 실행해 효과를 측정했다는 뜻이 아니다.

이 설계는 사용자가 아직 발견하지 못한 모든 이해 누락, 제품·code 불일치와 판단 소비 실패를 자동으로 찾지 않는다. 사람의 판단이 후속 선택·구현·완료와 의존 결과까지 유지되는 문제는 [판단 연속성 연구](../07-tripproof-spec-driven-continuity/README.md)의 책임과 연결해야 하며, 이 문서나 설명 결과의 존재를 그 인수의 완료로 취급하지 않는다. Workspace·Project context가 존재한다고 자동 현재성이나 모든 stale 발견을 보장하지도 않는다.

실제 사용에서 중요한 전제가 반복해서 빠지거나 설명·질문·routing 비용이 커지면 세 skill의 역할과 공통 기준을 다시 판단한다. 새 reference가 현재 세 장면 밖의 중요한 문제를 보여 주면 억지로 끼워 넣지 않고 실제 TripProof 장면에서 반복되는지 확인한 뒤 범위 변경을 검토한다. 현재 선택을 재검토할 때는 이해·판단 이득, 새 용어·질문·문서·조사 비용, 근거 강도와 다른 책임으로 넘어갈 조건을 함께 본다.
