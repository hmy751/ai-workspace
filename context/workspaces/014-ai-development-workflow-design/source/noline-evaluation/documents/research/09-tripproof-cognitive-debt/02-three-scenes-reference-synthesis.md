# 외부 reference를 세 사용 장면에 다시 배열한 결과

## 이 문서의 역할

[`자료별 재정독`](01-external-reference-insight-extraction.md)에서 뽑은 내용을 다음 세 장면에 맞춰 다시 배열한다.

1. 작업을 시작하기 전에 함께 논의할 때: 앞으로 무슨 작업을 할 것인가?
2. AI의 응답이 어려워 이해가 끊겼을 때: AI가 한 말은 무슨 뜻인가?
3. 코드나 작업물의 구조·동작·현재 상황을 이해하려 할 때: 현재 존재하는 code와 작업물은 어떻게 되어 있는가?

이 문서는 자료별 직접 근거와 이미 도출한 적용을 함께 사용할 때의 동작 순서·종료·전환·비적용 조건을 장면별로 결합한 지원 분석이다. [`01`](01-external-reference-insight-extraction.md)도 이해 복구 순서, 책임자 확인 강도와 사용자 흐름 설명을 이미 합성하고 있으므로, 여기서 모든 새 판단이 시작됐다는 뜻은 아니다. TripProof의 실제 문제 근거와 해결 책임은 [`03`](03-integrated-causal-map-and-solution-obligations.md)에서 다룬다.

아래의 후보 동작과 종료 관찰은 현재 실행 계약이 아니다. 현재 채택한 호출·출력·설명 종료 경계는 [`05 현재 설계`](05-current-solution-design.md), 구체적 실행 지시는 [`v0`](v0/README.md)가 소유한다. 특히 사용자 내적 이해를 AI가 판정하거나 침묵을 이해의 증거로 삼지 않는 현재 경계와, 이 문서가 검토한 이해 관찰 후보를 구분한다. 세 장면 자체는 순서대로 실행할 pipeline이 아니다.

## 장면 1 — 작업을 시작하기 전에 함께 논의할 때

### 이 장면이 보강하려는 작업 전 논의

장면 1은 TripProof에서 심각한 인지부채 문제가 반복되어 새로 만든 교정 장면이 아니다. 사용자는 TripProof 밖의 작업에서도 이미 작업 전에 인터뷰와 구체화를 거쳐 왔고, 이 장면은 외부 reference에서 그 과정을 보강할 만한 원리를 발견해 세 장면에 추가한 것이다. 따라서 질문과 설명을 줄이는 것보다 작업 의도·제약·선택을 정확하고 충분하게 맞추는 일을 우선한다. 인지피로는 그 정확성을 해치지 않는 범위에서, codebase가 답할 사실의 전가·질문 선후관계의 혼선·불필요한 history 복구 같은 부담만 줄이는 방향으로 다룬다.

사용자는 원하는 결과와 중요한 판단을 말해야 하지만 codebase가 답할 사실, 내부 구현 task와 질문 전체의 선후관계까지 동시에 들고 있을 필요는 없다. 반대로 AI가 질문 없이 바로 계획하거나, 모든 미결정을 한꺼번에 묻거나, 자세한 spec과 task list로 너무 일찍 닫으면 사용자가 원한 결과와 구현이 갈라질 수 있다.

외부 reference를 함께 보면 이 장면의 목적은 **모든 것을 확정하는 것**이 아니라 **전체 문제와 중요한 경계를 함께 이해하고, 실제 작업자가 판단할 여지를 남긴 채 시작할 수 있게 하는 것**에 가깝다.

`Grill with Docs` 원문은 사용자가 직접 호출하고 한 session 안에서 정할 수 있는 change를 전제한다. 이 문서는 그 원리를 더 넓은 작업 전 논의에 적용해 보는 현재 합성이며, 장면 1도 사용자 발동을 기본으로 둔다. [`원래 호출과 규모`](../../source/04-matt-pocock-skills/original/grill-with-docs.md#L7)

### 후보 동작 순서

1. **현재 살아 있는 문제와 원하는 결과를 먼저 잡는다.**

   여러 후보 중 작업을 고르는 상황이라면 왜 이 문제가 지금 다시 중요해졌는지, 최근 어떤 근거나 필요가 있는지부터 확인한다. 오래된 목록에 있다는 사실만으로 모든 후보를 다시 불러오지 않는다. 이는 Shape Up Chapter 7의 현재 맥락을 가진 재주장 원리에서 가져온다. [`현재 맥락을 가진 후보`](../../source/08-shape-up-chapters-ko/chapter-07-bets-not-backlogs/translation.ko.md#L96)

   이미 작업 하나가 선택됐다면 후보 선정을 다시 열지 않는다. 그때는 사용자가 기대하는 결과, 그 결과가 필요한 이유와 이번 작업의 범위로 바로 들어간다.

2. **작업을 task 목록이 아니라 온전한 문제로 유지한다.**

   사용자가 보게 될 결과, 중요한 제약과 하지 않을 것을 먼저 맞춘다. 내부 module·class·세부 task는 실제 code를 보며 발견할 여지를 남긴다. Shape Up Chapter 10은 project를 미리 task로 분쇄하면 실행자가 전체 관계와 판단 책임을 잃을 수 있다고 말한다. [`전체 project와 경계`](../../source/08-shape-up-chapters-ko/chapter-10-hand-over-responsibility/translation.ko.md#L8), [`미리 정할 것과 열어 둘 것`](../../source/08-shape-up-chapters-ko/chapter-10-hand-over-responsibility/translation.ko.md#L40)

3. **과거 정보는 현재 논의에 필요한 것이 빠졌을 때만 가져온다.**

   이전 대화가 길다면 현재 질문을 구속하는 확정 결정과 아직 유효한 제약만 복구한다. 폐기된 대안과 전체 history는 현재 선택 이유를 이해하는 데 필요할 때만 연다. 이 우선순위는 Source 01이 검증한 ranking 공식이 아니라 현재 목표에 맞춘 도출이다. 원문이 직접 제공하는 근거는 관련 없는 memory가 비용과 오판을 만들 수 있고, 정확한 정보를 주는 것만으로 실제 사용이 보장되지 않았다는 점이다. [`나쁜 memory의 비용`](../../source/01-yUjTWl7tOYc/translation.ko.md#L251), [`정확한 memory도 사용되지 않을 수 있음`](../../source/01-yUjTWl7tOYc/translation.ko.md#L217)

4. **Code·문서·환경이 답할 사실은 AI가 먼저 확인한다.**

   현재 구현, 이미 정해진 contract, 사용 중인 API처럼 repository에서 답을 찾을 수 있는 질문을 사용자에게 되묻지 않는다. `Grill with Docs` 원문이 이 역할 분리를 직접 둔다. [`codebase가 답할 사실`](../../source/04-matt-pocock-skills/original/grill-with-docs.md#L72)

   조사 중인 상태를 확정된 설명처럼 포장하지 않는다. Shape Up Chapter 10은 기존 system을 이해하고 시작점을 찾는 orientation을 실제 작업으로 본다. [`방향을 잡는 시간`](../../source/08-shape-up-chapters-ko/chapter-10-hand-over-responsibility/translation.ko.md#L90)

5. **판단 책임자만 정할 선택을 선행관계에 맞춰 작은 묶음으로 묻는다.**

   범위, 우선순위, 허용 가능한 축소, 제품상 trade-off처럼 답에 따라 실제 결과가 달라지는 판단만 그 판단의 책임자에게 올린다. 대화 중인 사용자가 책임자일 때 사용자에게 묻고, team·기관·다른 담당자가 책임자라면 필요한 전달·확인을 드러낸다. 현재 답할 수 있는 여러 질문은 함께 묻고, 다음 질문을 바꾸는 핵심 선행 결정은 먼저 하나만 물을 수 있다. [`질문 dependency와 round`](../../source/03-sZrFaPMau6A/translation.ko.md#L291), [`책임 주체의 범위`](../../source/06-wHePopfD6js/translation.ko.md#L663)

   추천안과 번호는 scanning과 답변 비용을 줄이는 보조 수단일 뿐 AI 추천을 책임자의 판단으로 바꾸는 장치가 아니다. 사람의 판단은 모든 세부가 아니라 가치·위험·품질을 실제로 갈라놓는 시점에 두는 편이 06의 근거와 맞는다. 다만 06이 직접 대비한 것은 작업 전·중·후가 아니라 30초 interaction과 한 시간·하루 workstream이다. 이 장면에 checkpoint를 놓는 것은 현재 합성이며, 확인 강도는 작업 지속시간·위임 깊이·병렬성에 따라 달라져야 한다. [`사람의 판단이 필요한 checkpoint`](../../source/06-wHePopfD6js/translation.ko.md#L113), [`짧은 interaction과 긴 workstream`](../../source/06-wHePopfD6js/translation.ko.md#L517)

6. **오래 유지할 경계와 구현 중 발견할 내용을 구분한다.**

   여러 작업을 계속 구속할 architecture나 반드시 지킬 invariant가 있다면 작고 안정적인 형태로 명시한다. 특정 tool 사용법이나 아직 보지 않은 내부 구조를 미리 고정하지 않는다. [`작고 오래 유지할 architecture`](../../source/02-bKT2wOec_rg/translation.ko.md#L77)

7. **첫 실제 결과를 골라야 할 때만 핵심 불확실성을 시험할 작은 동작을 정한다.**

   작업 논의가 바로 구현의 첫 목표까지 정해야 한다면, project의 핵심이고 짧은 시간 안에 실제로 동작하며 아직 검증하지 않은 부분을 우선할 수 있다. [`첫 결과를 고르는 세 조건`](../../source/08-shape-up-chapters-ko/chapter-11-get-one-piece-done/translation.ko.md#L281) 모든 작업 전에 이 선택을 강제하지 않는다.

8. **정확한 구체화를 거쳐 다음 행동을 책임 있게 시작할 수 있을 때 멈춘다.**

   전체 문제와 결과, 중요한 경계, 결과를 바꿀 질문과 현재 남은 사용자 결정이 충분히 드러났고 바로 다음 행동이 분명하면 대화를 끝낼 수 있다. 이는 대화를 짧게 끝낸다는 뜻이 아니다. 정확성에 필요한 질문을 생략하지 않되, 모든 task와 아직 보지 않은 내부 구조를 대화에서 만들어낼 때까지 묻지는 않는다. Shape Up의 kickoff도 중요한 질문 뒤 project에 대한 대략적인 이해가 생기면 시작한다. [`kickoff의 종료`](../../source/08-shape-up-chapters-ko/chapter-10-hand-over-responsibility/translation.ko.md#L76)

   Spec은 필요할 때 만드는 후속 산출물이지 이 장면의 고정 입력이나 완료 조건이 아니다. [`grill 뒤의 여러 이동`](../../source/04-matt-pocock-skills/original/grill-with-docs.md#L66)

### 응답에 남길 수 있는 핵심 내용

아래는 source가 직접 제시한 template이 아니라 위 내용을 실제 대화에 옮긴 후보다. 항목 수를 줄이는 것보다 현재 작업의 정확성에 필요한 내용을 빠뜨리지 않는 일을 우선한다.

- 내가 이해한 이번 작업의 목적과 사용자가 보게 될 결과
- code·자료에서 확인한 현재 사실
- 사용자가 정해야 해서 아직 열린 선택과 선택별 실제 차이
- 이번에 지킬 경계와 하지 않을 것
- 구현하면서 열어 둘 부분
- 바로 이어갈 다음 행동

### 사용하지 않거나 다른 책임으로 보낼 때

- 이미 결과와 경계가 명확하고 가역적인 작은 작업에는 질문 절차를 추가하지 않는다.
- 사용자가 선호를 정할 수 없는 이유가 domain 지식 부족이라면 선택을 재촉하지 않고 필요한 설명이나 학습으로 먼저 보낸다. `teach`는 일회성 설명과 지속 학습이 다르다는 경계만 제공한다. [`설명과 학습의 구분`](../../source/04-matt-pocock-skills/original/teach.md#L13)
- 실제 현재 구조를 알아야 선택할 수 있으면 장면 3으로 필요한 부분만 조사·설명한 뒤 돌아온다.
- 질문을 추천안 승인 절차로 만들지 않는다. 추천은 anchoring을 만들 수 있다.
- 합의 내용을 자동으로 glossary·ADR·spec에 모두 쓰지 않는다. 이후 독자가 있고 재유도 비용이 큰 내용만 기존 Owner에 넘긴다.

## 장면 2 — AI의 응답이 어려워 이해가 끊겼을 때

### 이 장면에서 줄이려는 부담

사용자가 “중요한 말인 것 같지만 무슨 뜻인지 모르겠다”고 느낀 뒤에도 대화를 계속하면 이해하지 못한 설명이 다음 판단의 전제가 된다. 이때 답을 짧게 자르거나 쉬운 동의어로 바꾸는 것만으로는 빠진 전제, 새로 생긴 용어와 논리의 도약이 복구되지 않을 수 있다.

이 장면의 중심 근거는 03·04의 `Wait What`이다. 01은 필요한 과거 context 선택을, 06은 명료한 AI 결론과 사용자의 별도 판단을 구분하는 데 보조적으로 쓰인다. 02와 08은 어려운 응답을 다시 설명하는 직접 방법을 제공하지 않는다.

아래 순서 전체는 여러 source를 합친 **내부 진단과 설명 후보**다. `Wait What` 원문은 오히려 장황한 설명 규칙이 문제를 재생산하지 않도록 핵심 지시를 세 줄로 유지한다. [`의도적으로 짧은 지시`](../../source/04-matt-pocock-skills/original/wait-what.md#L3) 따라서 매번 여덟 단계를 사용자에게 목차처럼 노출하지 않고 실제 막힘에 필요한 부분만 사용한다.

### 후보 동작 순서

1. **진행과 다음 결정을 잠시 멈춘다.**

   `Wait What`은 사용자가 output 길이가 아니라 자신의 listener state, 즉 “당신이 나를 놓쳤다”는 상태를 알리는 호출이다. [`listener 상태를 알리는 이유`](../../source/04-matt-pocock-skills/original/wait-what.md#L13) 사용자가 이해를 요청했는데 바로 승인·선택·다음 작업을 재촉하지 않는다.

2. **마지막 message 한 문단이 아니라 이해가 실제로 공유됐던 지점까지 돌아간다.**

   AI는 무엇이 사용자를 놓치게 했는지 보고 필요한 만큼 rewind한다. [`되돌아갈 범위`](../../source/04-matt-pocock-skills/original/wait-what.md#L19) 새 용어·기호, 가리키는 대상이 불분명한 말, 빠진 전제, 생략된 중간 논리, 너무 많은 압축 가운데 무엇이 막힘을 만들었는지 좁힌다. 이 원인 목록은 source의 사례를 현재 장면에 맞춰 구체화한 것이다.

3. **사용자가 이미 이해한 context와 표현에서 다시 출발한다.**

   Project 대화라면 새 이름을 더 만들지 않고 앞서 사용자와 함께 사용한 명사를 쓴다. 일반 대화처럼 합의된 project language가 없으면 현재 대화에서 이미 이해된 표현으로 돌아가고, 그것도 없으면 plain language와 빠진 premise 복구에 집중한다. 원문도 `CONTEXT.md`가 없어도 작동하되 domain vocabulary의 이점만 줄어든다고 말한다. [`빠진 context와 project vocabulary`](../../source/04-matt-pocock-skills/original/wait-what.md#L1), [`project context가 없을 때`](../../source/04-matt-pocock-skills/original/wait-what.md#L21)

4. **원래 뜻을 보존하면서 전제와 결론의 연결을 복구한다.**

   먼저 AI가 방금 말하려던 핵심을 한 문장으로 둔다. 그다음 그 말에 필요한 전제, 전제에서 결론으로 가는 이유, 현재 대화나 작업에서 그 말이 뜻하는 바를 연결한다. `짧게` 만드는 것이 목적이 아니므로 필요한 전제를 삭제하지 않는다.

5. **사실, AI의 해석, 미확정을 섞어서 더 매끄러운 하나의 결론으로 만들지 않는다.**

   이해를 막은 것이 문장 난이도보다 주장의 상태라면 확인된 사실, 그 사실에서 AI가 도출한 해석과 아직 모르는 부분을 구분한다. 이 세 부분은 06의 고정 response 형식이 아니라 evidence와 사람의 최종 판단을 나눈 데서 만든 현재 합성이다. 06은 이해하기 전에 AI 답을 자기 답으로 받아들일 수 있다고 경고한다. [`delegation과 cognitive surrender`](../../source/06-wHePopfD6js/translation.ko.md#L541)

6. **과거 context는 막힌 설명에 필요한 최소 전제만 가져온다.**

   방금 응답과 필요한 전제가 현재 대화에 있으면 별도 history를 불러오지 않는다. 빠졌다면 그 문장을 실제로 구속하는 사용자 의미나 결정만 가져오고, 전체 대화를 다시 요약하지 않는다. 이는 01의 recall 실험을 현재 설명에 옮긴 도출이다. [`불필요한 memory의 비용`](../../source/01-yUjTWl7tOYc/translation.ko.md#L251)

7. **설명 방식이 아니라 실제 사실이나 학습이 부족한 문제인지 구분한다.**

   현재 code 상태가 없어서 뜻을 설명할 수 없다면 표현을 다시 바꾸지 말고 장면 3의 source·trace 조사로 이동한다. 반복 재설명이 실패하고 실제 domain 학습이 필요하다면 `teach` 같은 별도 학습 책임을 고려할 수 있다. `Teach` 원문도 방금 message 이해 복구와 장기 학습을 구분한다. [`일회성 설명과 지속 학습`](../../source/04-matt-pocock-skills/original/teach.md#L13)

8. **최소한의 확인 뒤 멈춘다.**

   이 합성에서는 사용자가 핵심 뜻과 이유를 따라가거나 남은 모르는 지점을 구체적으로 말하는 모습을 종료 관찰 후보로 보았다. 이는 `Wait What` 원문이 제공하지 않은 설계 보완이며 부담과 효과도 검증하지 않았다. 현재 설계는 AI가 사용자의 내적 이해를 판정하는 대신, 현재 요청에서 이해하고 판단하는 데 필요한 설명을 준비했는지를 종료 범위로 삼는다. 사용자가 자발적으로 드러낸 이해나 혼란은 후속 설명의 근거가 될 수 있지만, quiz·“자기 말로 다시 말해 보라”는 요구·형식적 승인을 기본 종료 조건으로 두지 않는다. [`현재 설명 종료 경계`](05-current-solution-design.md)

### 응답에 남길 수 있는 최소 내용

아래 역시 여러 source를 조합한 후보이며, 이해를 복구하는 데 필요한 항목만 노출한다.

- 내가 방금 말하려던 핵심
- 이해가 끊긴 용어나 문장이 여기서 가리키는 실제 대상
- 빠져 있던 전제
- 그 전제가 핵심 결론으로 이어지는 이유
- 확인된 사실과 AI가 더한 해석, 아직 확인하지 않은 부분
- 이 설명이 현재 논의나 작업에서 의미하는 것

### 사용하지 않거나 다른 책임으로 보낼 때

- 사용자가 단순히 더 짧은 요약을 요청한 경우에는 이해 실패를 추정해 전체 설명을 재구성하지 않는다.
- 익숙한 project term이 오래됐거나 현재 의미와 충돌하면 그대로 재사용하지 않고 먼저 용어 합의를 다시 연다.
- 친숙하고 명료한 설명은 사실성 증명이 아니다. 실제 주장이 틀렸는지 의심되면 source나 실행 근거를 확인한다.
- 한 번의 이해 복구를 지속 학습 workspace, glossary와 quiz로 확대하지 않는다.
- Actual comprehension failure는 listener만 확실히 알 수 있으므로 사용자 호출을 기본으로 보는 것이 근거에 맞다. AI는 명시적 혼란 신호가 있을 때만 제한적으로 제안할 수 있다.

## 장면 3 — 코드나 작업물의 구조·동작·현재 상황을 이해하려 할 때

### 이 장면에서 줄이려는 부담

파일 목록, diff 요약과 test pass만으로는 사용자가 system에서 무엇이 실제로 달라졌고 어느 부분을 믿거나 다시 물어야 하는지 알기 어렵다. 반대로 모든 line을 같은 깊이로 읽으면 중요한 구조, 상태 변화와 실패 지점에 쓸 주의가 소진된다.

이 장면의 중심 재료는 02의 semantic structure·source·trace, Shape Up Chapter 11의 실제로 동작하는 작은 결과, 06의 근거와 설명 책임 구분이다. 03·04는 현재 사실을 조사하는 책임과 어려운 설명을 복구하는 인접 경계만 준다.

### 먼저 질문의 종류를 가른다

같은 “설명해 줘”라도 필요한 근거가 다르다.

- 현재 구조와 책임을 묻는가
- 특정 입력이나 event가 어떻게 실행되는지 묻는가
- 방금 변경에서 무엇이 달라졌는지 묻는가
- 왜 이 구조와 선택이 생겼는지 묻는가
- 요구나 repository 기준에 맞는지 review를 요청하는가

이해 설명과 적합성 review는 기본적으로 분리한다. `code-review`는 fixed point 이후 diff의 repository 기준과 spec 충족을 판정하는 도구이지, 구조와 흐름을 가르치는 도구가 아니다. [`code review의 두 판정축`](../../source/04-matt-pocock-skills/original/code-review.SKILL.md#L74)

### 후보 설명 순서

1. **이 작업물이 사용자나 제품 흐름에서 맡는 역할을 먼저 둔다.**

   File이나 class 이름에서 시작하지 않고, 사용자가 무엇을 하거나 system이 어떤 결과를 만들기 위해 이 작업물이 존재하는지 말한다. Shape Up Chapter 11은 수평 layer의 진척보다 직접 써 볼 수 있는 작은 end-to-end 결과가 실제 판단을 가능하게 한다고 보여 준다. [`작은 통합 결과`](../../source/08-shape-up-chapters-ko/chapter-11-get-one-piece-done/translation.ko.md#L20)

   이 내용을 code 설명의 첫 순서로 삼는 것은 source의 구현 원리를 설명에 옮긴 도출이다.

2. **시작점부터 결과까지 한 흐름을 따라간다.**

   대표 입력·사용자 행동·event 하나를 골라 어떤 component를 거쳐 결과가 나오는지 보여 준다. 먼저 온전한 흐름을 유지하면 각 file이 왜 등장하는지 연결할 수 있다. 모든 가능한 경로를 한꺼번에 펼치지 않는다.

3. **흐름 안에서 component의 책임과 경계를 설명한다.**

   02의 demo는 초기화, agent loop와 component 관계 같은 큰 semantic structure를 먼저 보고 필요한 부분만 확장한다. [`큰 구조에서 선택적 확장`](../../source/02-bKT2wOec_rg/translation.ko.md#L391) 각 component에 대해 현재 질문에 필요한 입력·출력, 상태 변경, 외부 effect, 오류와 invariant를 설명한다.

   이 세부 항목은 원문이 그대로 열거한 template이 아니다. Package·component·function 경계를 사람이 판단할 수 있는 system 의미로 옮긴 현재 도출이다.

4. **필요한 곳에서 실제 source와 사용 위치로 내려간다.**

   Component 설명을 실제 file·symbol·call site와 연결한다. 02의 semantic query는 function 설명, source와 모든 사용 위치를 한 번에 보는 예를 제공한다. [`설명·source·사용 위치`](../../source/02-bKT2wOec_rg/translation.ko.md#L479) “무엇이 바뀌었는가”가 질문이면 비교할 commit·branch·working tree 범위도 먼저 고정한다.

5. **실제 동작은 trace·test·log로 별도 확인한다.**

   Source에서 가능한 동작을 읽은 것과 특정 실행에서 관찰한 일을 나눈다. Trace는 지나간 경로를, test는 작성된 조건의 결과를, compiler나 rule check는 표현된 조건의 보장을 보여 준다. 어느 하나가 나머지 질문까지 대신하지 않는다. [`execution trace`](../../source/02-bKT2wOec_rg/translation.ko.md#L425), [`판단 근거의 여러 형태`](../../source/06-wHePopfD6js/translation.ko.md#L817)

6. **실제로 동작하는 범위와 임시·미구현 범위를 분리한다.**

   End-to-end로 연결된 작은 결과가 전체 feature 완료를 뜻하지 않을 수 있다. Shape Up 사례의 toggle은 상태를 저장했지만 실제 콘텐츠 공개 여부까지 바꾸지는 않았다. [`부분적으로 동작한 toggle`](../../source/08-shape-up-chapters-ko/chapter-11-get-one-piece-done/translation.ko.md#L95) Stub, mock, hard-coded 값, 아직 연결되지 않은 effect와 확인하지 않은 위험을 숨기지 않는다.

7. **표면 결과에 들어간 제품·구조 결정을 연결한다.**

   화면의 field와 option처럼 단순해 보이는 형태에도 가격·권한·workflow 결정이 들어 있을 수 있다. [`표면 형태가 반영한 결정`](../../source/08-shape-up-chapters-ko/chapter-11-get-one-piece-done/translation.ko.md#L173) 설계 문서는 그 이유를 찾는 근거로 쓰되 현재 구현은 source와 실행에서 다시 확인한다.

8. **사용자의 다음 판단과 위험에 맞춰 깊이를 조절한다.**

   모든 line을 설명하지 않는다. 되돌리기 어려운 경계, 외부 effect, 실패 영향과 사용자가 다음에 바꾸려는 부분을 더 깊게 보고 안정적인 내부 세부는 source 경로만 남긴다는 것은 **현재 합성의 깊이 조절 후보**다. 06의 `Explain it or don't ship it`은 모든 line을 읽으라는 뜻이 아니라 변경을 방어하고 설명할 만큼 이해해야 한다고 말하지만, 무엇이 충분한 깊이인지는 정하지 않는다. [`설명할 수 있는 충분한 이해`](../../source/06-wHePopfD6js/translation.ko.md#L873), [`충분한 이해의 빈칸`](../06-wHePopfD6js.md#L170)

### 이 설명 순서의 근거 강도

02가 하나의 visualization demo에서 직접 연결해 보여 주는 이동은 다음까지다.

```text
큰 semantic structure
→ 필요한 부분 확장
→ 실제 source line
```

설명·source·사용 위치를 묶는 query, trace와 function 독립 실행은 각각 별도의 demo다. 08은 수평 layer보다 실제로 동작하는 한 조각을 먼저 보게 하고, 06은 근거와 사람의 판단을 분리한다. 따라서 아래 순서는 02의 여러 demo와 08·06을 합친 도출이다.

```text
사용자·제품에서의 역할
→ 대표 end-to-end 흐름
→ component 책임과 경계
→ 실제 source와 diff
→ trace·test·보장 범위
→ stub·미확정·선택 이유
```

즉 “설명 순서가 source에 있었다”는 말은 일부만 맞다. **넓은 의미 구조에서 필요한 source line으로 내려가는 이동은 직접 근거가 있고, 여기에 사용 위치·실행 근거를 붙이며 사용자 흐름과 책임·상태 변화를 앞세운 완성된 답변 목차는 현재 합성에서 만든 것이다.** 보존 번역에는 demo의 실제 화면·code·결과 일부가 빠져 있어 그 표현 충실도도 독립 검증하지 못했다. [`02의 보존 한계`](../02-bKT2wOec_rg.md#L148)

### 근거마다 답할 수 있는 질문

설명의 순서를 정한 뒤 근거의 차이를 정리하면 다음과 같다.

| 궁금한 것 | 먼저 볼 근거 | 이 근거만으로는 알 수 없는 것 |
| --- | --- | --- |
| 왜 이런 방향을 골랐는가 | 당시 design·결정 자료 | 현재 code가 그대로 구현됐는지 |
| 지금 어떤 구조와 책임인가 | 현재 source와 사용 위치 | 특정 실행에서 실제로 지난 경로 |
| 이번 실행에서 무슨 일이 있었나 | trace·log·test | 실행하지 않은 모든 경로의 안전성 |
| 어떤 조건이 기계적으로 보장되나 | compiler·type·rule check | 요구 자체의 타당성과 외부 system 전체 |
| 변경이 무엇을 건드렸나 | 고정한 기준점의 diff | 변경 이유와 실제 runtime 결과 |
| 결과를 받아들일 수 있는가 | 위 근거와 남은 위험 | 사람의 최종 판단 자체 |

### 사용하지 않거나 다른 책임으로 보낼 때

- 단일 symbol의 위치나 짧은 사실만 물었다면 전체 workflow 설명을 만들지 않는다.
- 실제 code 구조가 흐리면 설명에서 새로운 의미 경계를 지어내지 않는다. 확인된 구조와 추정한 grouping을 구분한다.
- Trace 한 번을 모든 입력의 보장으로, test pass를 전체 요구 충족으로, compiler 통과를 제품 정확성으로 확대하지 않는다.
- 사용자가 설명 문장 자체를 이해하지 못하면 장면 2로 이동한다.
- “좋은 구조인가”, “요구를 충족했는가”까지 묻지 않았다면 review와 수정 제안을 자동으로 포함하지 않는다.
- 한 번의 orientation을 장기 학습 project로 확대하지 않는다. 사용자가 codebase를 여러 session에 걸쳐 익히고 싶다고 할 때만 `teach`의 지속 학습 구조를 별도로 검토한다.

## 세 장면을 함께 사용할 때의 공통 경계

- 세 장면은 순서대로 모두 실행하는 pipeline이 아니다. 현재 이해와 판단에 필요한 장면 하나에서 시작한다.
- 장면 1 중 현재 구조가 필요하면 장면 3으로 잠시 이동하고, 설명이 어렵다면 장면 2로 복구한 뒤 원래 논의로 돌아올 수 있다.
- 장면 2의 반복 설명으로 풀리지 않고 작업 목표나 선택을 다시 정해야 한다면 장면 1을 다시 연다. 실제 상태가 쟁점이라면 장면 3이나 사실 조사로 이동한다.
- 자료나 code에서 확인해야 할 사실을 더 유창한 설명으로 메우지 않는다.
- 필요한 이해를 보존한 뒤에만 반복 설명, 전체 history 탐색, 불필요한 질문·문서·모든 line 읽기를 줄인다.
- 이해를 돕는 설명, 사실 검증, 적합성 review와 사용자의 최종 판단을 하나의 완료 표시로 합치지 않는다.
- 사람의 채택·최종 판단은 세 장면에 공통인 권한 경계이며 별도의 기본 장면을 하나 더 만드는 근거로 삼지 않는다.
- 자료 전체를 채택하거나 모든 자료에서 세 장면을 모두 채우지 않는다. 틀 밖의 중요한 문제는 별도 근거로 보존하고, 장면을 늘리거나 목표를 좁히기 전에 실제 TripProof에서 반복되는지 확인한다.
- 외부 reference의 특정 skill과 파일 구성을 그대로 복제하지 않는다. 실제 skill·공통 reference의 배치 판단은 현재 설계로 이어졌으며, 이 분석의 후보를 추가 실행 규칙으로 중복 적용하지 않는다.

## 현재 설계로 이어진 판단과 남은 확인

자료 재독 뒤 검토한 질문은 입력, 항상 필요한 책임과 상황별 동작, 종료 관찰, 다른 장면·조사·학습·review로 전환할 조건이었다. 당시에는 skill 개수·이름·호출·출력·설치 위치도 열려 있었지만, 현재 채택 내용은 [`05 현재 설계`](05-current-solution-design.md)와 [`v0`](v0/README.md)에 인수됐다. 이 문서는 그 결정을 다시 미정으로 돌리지 않고 장면별 결합의 근거와 비용을 재검토할 때 사용한다. 장면 1에서 기존 인터뷰와 구체화를 보강한다는 선정 이유는 그대로 유지한다.

실제 적용에서 필요한 이해를 보존하면서 질문·설명·재탐색 비용을 얼마나 줄이는지는 검증되지 않았다. 후보 응답을 실제 대화에 대입해 보자는 당시 계획은 완료된 효과 검증이 아니다. 8월 재구성 작업은 문제를 이해하는 과거 근거로 사용할 수 있지만 향후 첫 적용 장면으로 자동 선택하지 않는다. 현재의 미확정과 적용 범위는 현재 설계에서 확인한다.
