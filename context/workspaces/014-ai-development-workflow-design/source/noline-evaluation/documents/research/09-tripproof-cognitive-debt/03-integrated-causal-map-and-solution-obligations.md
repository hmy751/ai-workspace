# 전체 인과 지도와 해결 의무

## 이 문서의 지위

이 문서는 TripProof 인지부채의 문제 정의, 전체 인과, 해결 책임과 기존 Owner 경계를 소유한다. 세 장면으로 나누기 전에 무엇이 실제로 손실됐는지 전체 시간 흐름으로 묶고, 어떤 형태의 해결 후보라도 수행해야 할 책임을 도출한다. 목표는 AI와 함께 작업하면서 사람이 필요한 이해와 판단을 유지하고, 나중에 다시 복구해야 할 인지부채를 줄이는 방법을 찾는 것이다.

문제 근거와 설계 재료의 역할은 구분한다.

- [`05 TripProof harness 회고`](../05-tripproof-harness-retro.md)와 [`07 문제 분석`](../07-tripproof-spec-driven-continuity/01-problem-analysis.md), [`07 대화 장면 분석`](../07-tripproof-spec-driven-continuity/04-conversation-scene-analysis.md)은 TripProof에서 실제로 확인된 강점·손실·운영 공백의 근거다.
- [`외부 reference 재추출`](01-external-reference-insight-extraction.md)은 다른 자료에서 얻은 정보 선택·의미 설명·근거 구분·사람 판단 원리의 재료다.
- [`세 장면 합성`](02-three-scenes-reference-synthesis.md)은 나중에 채택 후보의 coverage를 확인할 관찰 자료다. 해결안을 세 조각으로 나누는 출발점으로 사용하지 않는다.

이 문서는 개별 skill의 호출·출력·실행 절차를 추가로 정하지 않는다. 여기서 도출한 책임의 후보 비교는 [`04`](04-integrated-solution-candidates.md), 현재 채택한 설계는 [`05`](05-current-solution-design.md), 구체적 실행 계약은 [`v0`](v0/README.md)에 있다. 아래의 충분성 질문은 현재 설계도 재검토할 수 있는 기준이며, 과거에 열려 있던 형상 결정을 계속 미정으로 두는 목록은 아니다.

## 중심 결론

TripProof에서 강하게 확인되는 문제는 사용자의 목적을 처음부터 전혀 이해하지 못한 것이 아니다. 사용자와 AI가 제품 목적과 기술적 기대를 함께 확인한 뒤에도 그 판단이 `작업 선택 → 미룰 범위 → 구현 → 근거 해석 → 완료 설명 → 다음 행동`으로 이동할 때 더 쉽게 만들고 측정할 수 있는 국소 산출물로 대체됐다.

실제 LLM 판단은 proposer interface로, 서버 전체의 readable flow는 세 번의 유효한 refactor와 56개 test 통과로 약해졌다. 사람이 읽을 답변을 만드는 제품 책임 대신 raw `facts[]`를 화면에 연결하자는 안은 구현된 실패가 아니라 계획 단계에서 같은 약화가 일어날 수 있음을 보여 준 사례다. 이 산출물들은 각각 가치가 있었지만 원래 목표와 같은 것은 아니었다. 사용자가 결과를 보고 다시 물었을 때 AI가 빠진 문제를 곧바로 다시 찾은 사례는 정보가 전혀 없었다기보다 **그 판단이 필요한 순간에 소비되지 않았음**을 보여 준다. 자세한 흐름은 [`07 대화 장면 분석`](../07-tripproof-spec-driven-continuity/04-conversation-scene-analysis.md)의 `세 장면에서 반복된 흐름`과 `구체화된 중심 진단`에 있다.

따라서 여기서 줄이려는 인지부채는 단순한 정보량이나 어려운 문장의 양이 아니다.

> AI의 응답·계획·작업물·근거가 다음 판단이나 행동의 안정된 전제가 되는데, 그 전제의 목적·의미·근거 범위·영향·미확정·현재 권위를 사람이 충분히 파악하지 못한 상태에서 나중의 재질문·재조사·재판정·재작업 비용이 생기는 것

모든 세부를 사람이 완전히 이해하거나 기억해야 한다는 뜻은 아니다. 직접 이해할 범위와 의식적으로 위임할 범위는 그 결과로 내릴 다음 판단, 잘못됐을 때의 영향과 되돌리기 가능성에 따라 달라진다. 위험별로 무엇이 충분한 이해인지 검증된 기준은 아직 없다.

정확하고 쉬운 설명은 사람이 반대하거나 추가 근거를 요구하고 판단을 보류하기 위한 중요한 개입이다. 그러나 설명만으로 원래 전제와 source의 정확성, evidence의 입증 범위, artifact의 현재성, 사람 자신의 판단과 다시 열 조건까지 보장되지는 않는다. 인지부채의 전체 해답을 설명 문제로 좁히지 않는다.

인지피로 감소는 별도의 최상위 목표가 아니라 개입의 비용과 제약이다. 먼저 다음 판단에 필요한 의미·전제·위험·미확정을 보존하고, 그 이해에 기여하지 않는 반복 설명·용어 번역·재탐색·맥락 재구성 부담을 줄인다. 짧은 설명이나 AI가 대신 내린 판단을 성공으로 취급하지 않는다.

## 전체 흐름에서 부채가 생기는 위치

인지부채는 하나의 설명 순간에만 생기지 않는다. 목적이 결과로 바뀌고 그 결과가 다시 다음 행동의 전제가 되는 전체 흐름에서 생긴다.

```text
사용자의 목적·판단
→ AI가 구성한 현재 이해
→ 작업 선택·범위·미룰 것
→ 구현·문서·분석 결과
→ source·test·trace·eval 같은 근거
→ AI의 해석과 설명
→ 사람의 이해·채택·보류·재질문
→ 다음 작업과 완료 판정
→ 시간이 지난 뒤의 재진입·재판정
```

각 연결에서는 앞 단계의 모든 정보를 그대로 복사할 필요가 없다. 대신 다음 소비자가 자기 역할을 수행하는 데 필요한 의미가 보존돼야 한다. TripProof에서는 다음 세 종류의 손실이 반복되거나 장기 공백으로 확인됐다.

### 의미가 더 쉬운 대리물로 바뀌었다

핵심 제품 책임, 구조 판단과 전체 목표가 interface, file, test, commit, UI 연결처럼 구현·측정하기 쉬운 대상으로 바뀌었다. 이 대리물 자체가 잘못된 것은 아니다. 문제는 그것이 무엇을 수행했고 무엇을 아직 수행하지 않았는지 구분하지 않은 채 상위 목표의 충분성까지 대신한 것이다.

### 근거와 결론의 범위가 섞였다

설계 의도, 현재 source, 한 번의 실행, test가 확인한 조건, compiler가 보장한 조건, AI의 해석과 사람의 최종 판단은 서로 다른 질문에 답한다. 그런데 국소 evidence가 더 넓은 완료 설명으로 승격되거나, 나중에 정직해진 final record가 당시 live claim의 신뢰성까지 대신할 수 있었다. [`05 회고의 final record와 live claim 구분`](../05-tripproof-harness-retro.md#2-final-record의-정직성과-작업-중-completion-claim의-신뢰성은-다른-문제였다)은 두 사실을 별도로 유지한다.

### 저장된 판단이 필요한 순간에 작동하지 않았다

Spec·decision·work-log가 존재해도 다음 선택과 완료 판정에서 반드시 읽히고 적용되지는 않았다. 시간이 지나면 closed spec의 권위, exact code state와 과거 판단의 유효성도 달라졌다. 2.5주 공백 뒤에는 current stage와 diff의 정체를 다시 물어야 했다. 저장, 현재 제시, 실제 사용, 사람의 이해와 판단은 서로 다른 상태다.

이 세 손실은 서로 이어진다. 의미가 대리물로 바뀌면 맞지 않는 근거가 충분해 보이고, 그 설명을 사람이 채택하면 다음 작업이 그 약해진 의미를 다시 입력으로 받는다. 시간이 지나 권위까지 흐려지면 나중에는 무엇이 원래 판단이었는지부터 복구해야 한다.

## 서로 대신할 수 없는 상태

후보를 판단할 때는 다음 관계를 계속 분리해야 한다. 오른쪽 단계가 더 좋아 보인다는 뜻도 아니고, 모든 단계를 항상 노출해야 한다는 뜻도 아니다. 앞 단계의 존재만으로 뒤 단계가 자동 성립하지 않는다는 뜻이다.

```text
저장됨 ≠ 현재 질문에 선택됨 ≠ 실제 응답에 사용됨 ≠ 사람이 이해함 ≠ 사람이 판단함

설계 의도 ≠ 현재 source ≠ 관찰된 실행 ≠ 기계적 보장 ≠ 요구 충족 ≠ 최종 acceptance

문서 생성 ≠ 다음 소비자가 읽음 ≠ 후속 산출물에 의미가 보존됨

쉬운 설명 ≠ 사실 확인
추천안 ≠ 책임자의 선택
작은 end-to-end 결과 ≠ 전체 완료
한 번 이해함 ≠ 시간이 지난 뒤에도 현재 판단으로 사용할 수 있음
```

외부 reference가 공통으로 보강하는 것도 이 구분이다. Source 01은 memory가 존재하는 것과 실제로 선택·사용되는 것을, Source 02는 의미 구조·source·실행·mechanical guarantee를, Source 03·04는 codebase가 답할 사실과 사람이 정할 선택 및 listener의 이해 복구를, Source 06은 evidence와 사람의 책임을, Source 08은 전체 문제와 작은 구현 조각을 구분한다. 직접 근거와 현재 도출의 차이는 [`외부 reference 재추출`](01-external-reference-insight-extraction.md)에 보존돼 있다.

## 과잉 교정으로 없애면 안 되는 것

문제가 있었다고 해서 기존 작업 방식을 전부 교체하면 원인을 잘못 잡는다.

- 이번 논의에서 사용자가 확인한 바에 따르면 이미 작업 전에 인터뷰와 구체화를 사용해 왔다. 이 시점의 일반적 실패가 TripProof 인지부채의 강한 근거는 아니다. 작업 전 장면은 좋은 reference가 기존 방식을 보강할 수 있어 추가한 것이다.
- Spec은 한 slice의 목표·범위·AC와 다음 시작점을 강하게 보존했다. 문제는 spec 자체보다 여러 결과가 쌓인 뒤의 전체 판단, 수명과 재개방이었다.
- 7개 spec bundle 약 480개 contract sentence는 code와 대체로 맞았고, 보존된 eval 근거 26건 중 24건은 실물과 일치했다.
- 실패·no-op·AC 미성립은 최종 기록에서 성공으로 포장되지 않았고, A/B는 실제 default 선택과 revert에 사용됐다.
- 반복 가능한 violation을 실행 순간의 behavior test로 옮긴 뒤에는 검토 범위에서 같은 hardcoding 유형의 재발이 확인되지 않았다.
- Route/use-case 분리, 명명 개선, RAG·context pack과 validator 같은 국소 산출물에도 실제 가치가 있었다.
- 사용자의 재질문과 재개방 권한은 잘못 승격된 완료를 복구했다. 없앨 것은 이 권한이 아니라 사용자가 매번 먼저 간극을 발견해야 했던 부담이다.

이 강점과 수치의 해석 한계는 [`05 회고`](../05-tripproof-harness-retro.md)의 `먼저 고정해야 할 세 가지 강점`, `이 회고가 허용하는 주장`에 있다. Record·harness file을 건드린 commit 약 41%는 노동 시간 비율이 아니라 attention 전환 신호이고, 자료는 인지피로를 수치로 측정하지 않았다.

이 진단은 spec-driven을 유일한 원인으로 확정하거나 모든 작업에 전체 architecture 검토를 요구하지 않는다. 구조를 바꾸기 어렵다는 관찰도 자동 refactor 명령이 아니다. 실제 막힘이 제품 수렴, 코드 모델의 유효성이나 과거 판단의 재개방에 있다면 설명만 보강하지 않고 해당 책임과 연결해야 한다.

## 해결 책임을 근거와 Owner에 따라 나누면

설명 전략과 해결 책임을 모두 같은 강도의 `필수 의무`로 두면 외부 reference에서 가져온 유력한 방법까지 정답으로 승격되고, 그 방법을 모두 담은 후보가 비교 전에 이기게 된다. 따라서 문제에서 직접 요구되는 005의 책임, 그 책임을 수행할 현재 전략, 그리고 다른 Owner가 맡아야 할 전체 시스템 책임을 구분한다. 여기서 005는 이 인지부채 연구 Workspace를 가리킨다.

### 005가 직접 맡아야 할 책임

#### 설명 대상과 사용 목적을 분명히 한다

사용자가 지금 이해하려는 대상이 무엇인지, 즉시 결정을 내리려는지 또는 현재 구조를 파악해 이후 질문 가능한 상태가 되려는지 구분한다. 작업 전 논의에서는 이미 있는 답을 다시 인터뷰하지 않고, 정확한 구체화에 필요한 내용을 축약하지 않는다.

#### 현재 답을 지지하는 권위와 기준 상태를 밝힌다

현재 code가 답할 사실, 과거 결정의 이유, 특정 실행과 사람만 정할 선택은 서로 다른 source를 가진다. 어떤 branch·commit·working tree·runtime·artifact를 설명 기준으로 삼았는지 현재 판단에 필요한 수준으로 밝히고, 재사용할 때 바뀌면 다시 확인해야 할 조건을 남긴다.

#### 의미와 실제 근거를 연결한다

File 목록이나 유창한 결론만 주지 않고, 사용자가 잡을 수 있는 역할·관계·흐름과 필요한 exact source·diff·trace·test를 연결한다. 이미 주어진 review·판단 finding이 있다면 그 finding이 무엇을 뜻하고 어디까지 영향을 주는지 설명한다.

#### Claim과 evidence의 범위를 넘지 않는다

현재 source에서 확인한 것, 특정 실행에서 관찰한 것, test·compiler·rule이 보장한 조건, AI가 도출한 해석과 아직 확인하지 않은 것을 섞지 않는다. 국소 근거로 더 넓은 완료를 주장하지 않는다. 005가 별도 제품·코드 충분성 review를 하지 않았다면 상위 목표 충족은 확인하지 않은 상태로 남긴다.

#### 사실·외부 답변·사람 판단을 구분한다

Repository·문서·환경이 답할 사실은 AI가 조사하고, 외부 담당자만 아는 사실은 그 담당자에게 보낸다. 제품 가치, 위험 수용, 핵심 책임 포기와 최종 acceptance는 실제 판단 책임자에게 남긴다. 추천안은 그 판단을 대신하지 않는다.

#### 현재 설명의 한계와 다음 인수 후보를 보여 준다

좋은 설명으로 끝내거나 후속 일을 자동 소유하지 않는다. 무엇이 확인됐고 무엇이 아직 열려 있는지, 현재 판단을 막는지 아니면 범위만 제한하는지, 추가 조사·review·사용자 판단·durable 반영 중 어느 책임이 필요할지 보여 준다. 실제 Owner가 없거나 인수하지 않았다면 `전달 완료`로 말하지 않는다.

### 외부 reference에서 얻은 현재 유력 전략

아래는 위 책임을 수행할 유력한 방법이지만 모든 해결안이 반드시 같은 형식으로 사용해야 한다는 직접 근거는 없다.

- 현재 질문을 구속하는 결정·제약·전환점만 선택하고 전체 history를 기본으로 불러오지 않는다.
- 이해가 끊겼다면 마지막 공유 지점으로 돌아가 빠진 전제와 논리를 복구한다.
- Code·작업물은 넓은 semantic structure에서 필요한 부분을 확장해 exact source로 내려간다.
- 영향, 되돌리기 가능성, 불확실성과 후속 의존 범위에 따라 설명 깊이를 조절한다.
- 질문 dependency와 실제 답변 책임자에 따라 조사와 사람 질문의 순서를 조절한다.

Source 02가 직접 보여 준 것은 `큰 semantic structure → 필요한 부분 확장 → 정확한 source line`이다. 사용자 흐름·상태 변화·근거까지 잇는 완성된 설명 순서, 위험별 깊이 조절 기준과 통합 routing은 현재 합성이다. 후보는 이 전략을 채택하거나 다른 방식으로 위 직접 책임을 만족시킬 수 있다.

정확성을 지킨 뒤에만 질문 묶음, 요약과 익숙한 표현으로 피로를 줄인다. 중요한 전제·희귀 위험·사용자 선택을 지운다면 비용 절감 전략을 사용하지 않는다.

### 005 밖에서 별도로 닫아야 할 전체 시스템 책임

TripProof의 주된 판단 소비 실패를 실제로 막으려면 다음 책임도 필요하다. 그러나 이를 005의 설명 책임으로 흡수하면 review·판단 연속성을 우회한다.

- 상위 목적·판단과 현재 plan·code·결과를 대조해 새로운 제품·코드 충분성 finding을 만드는 책임
- Completion·scope·handoff처럼 필요한 행동 순간에 그 대조와 설명이 실제로 호출되게 하는 책임
- 사용자가 내린 판단을 이후 작업 선택·구현·완료와 의존한 과거 결과에 전파하는 책임
- Durable 결정과 현재 상태를 실제 canonical Owner가 수락·갱신하고, 낡으면 다시 여는 책임

005는 자기 설명의 claim 범위를 제한하고, 이해 질문에 답하기 위해 필요한 현재 사실을 조사하며, 이미 주어진 finding을 이해 가능하게 만들 수 있다. 그러나 open-ended review로 새로운 구조·제품 문제를 찾거나, 그 finding으로 완료를 보류하고 scope를 변경하거나, 이후 실행에서 판단이 유지되게 하는 일은 별도 책임이다.

## 기존 책임과의 경계

이 Workspace가 해결하려는 부분은 **AI의 응답·작업물·근거가 사람이나 다음 행동의 판단 기반으로 넘어갈 때, 필요한 의미와 근거 범위를 이해 가능한 상태로 전달하는 책임**이다. 전체 흐름을 보되 모든 인접 문제를 흡수하지 않는다.

Workspace와 Project context는 이미 적용된 저장·재진입·권위 기반이다. 기반의 존재를 사람의 이해·acceptance, 제품·코드 수렴이나 장기 운영 효과의 증거로 보지 않는다. 새 개입은 이를 복제하는 저장 체계나 모든 context를 자동 주입하는 범용 router가 되지 않고, 현재 질문에 필요한 근거와 Owner를 찾아 사용한다.

- [`Workspace current 기반`](../07-tripproof-spec-driven-continuity/02-workspace-based-continuity-direction.md)은 현재 작업의 목표·제약·열린 판단·next action과, 현재 판단에 영향을 주는 사실의 보고·Owner pointer를 맡는다. 현재 답과 역사·선택 이유를 같은 권위로 두지 않으며, 실제 code·runtime·test 사실의 상세 정본도 아니다. 이 분석은 새 reentry store를 만들지 않는다.
- [`Project context 기반`](../07-tripproof-spec-driven-continuity/03-project-context-foundation-direction.md)은 여러 Workspace에 걸쳐 유효한 제품 의미·사람용 현재 요약·조건부 판단 기준과 실제 상세 Owner 경로를 맡는다. 필요한 context를 이유와 함께 선택하며, 현재 구조의 상세 정본은 code·test·설정이다. 관리 skill은 Project 의미·권위·사람의 acceptance를 소유하지 않는다.
- Source·code·test·eval·runtime은 각 질문의 사실과 evidence를 소유한다. 이해하기 좋은 설명은 이들을 대신하지 않는다.
- 별도로 호출된 review는 고정된 diff나 산출물이 요구·repository 기준에 맞는지 판정할 수 있다. 현재 항상 작동하는 인수 Owner라고 전제하지 않으며, 구조 설명이나 사람의 acceptance를 대신하지 않는다.
- Verify는 정해진 claim과 evidence의 기계적 검사를 맡지만 제품 의미 충분성, 사람의 이해와 acceptance를 증명하지 않는다.
- [`07 판단 연속성 방향`](../07-tripproof-spec-driven-continuity/05-judgment-continuity-solution-direction/archive/2026-09-06-before-reassessment/01-current-direction.md)은 현재 제품·코드 판단이 작업 선택·구현·근거 해석·완료 판정과 의존 결과 재평가까지 계속 작동하는 문제를 연구한다. 아직 채택·구현된 인수 Owner는 아니다.

005와 07의 경계는 다음처럼 구분할 수 있다.

```text
005: 지금 이 결과를 무엇으로, 어떤 근거 범위까지 이해하고
     사용자가 어떤 판단을 할 수 있는 상태로 넘길 것인가

07: 그렇게 형성·수정된 판단이 이후 작업 선택·구현·완료와
    그 판단에 의존한 과거 결과까지 실제로 계속 지휘하는가
```

두 책임은 이어지지만 같지 않다. 005만으로는 새로운 제품·코드 불일치를 독립적으로 발견하거나 올바른 판단이 이후 구현에서 유지됨을 보장하지 못한다. 반대로 07이 나중에 finding과 판단 전파를 맡더라도, 사람이 불투명한 AI 설명을 근거로 판단하는 문제는 별도 이해 연결이 필요하다. 아직 07 인수 책임이 구현되지 않았으므로 두 책임을 연결했다고만 써서 TripProof 전체 문제가 닫혔다고 말할 수 없다.

## 해결 후보와 현재 설계의 충분성 점검

해결 후보를 도출할 때 사용한 다음 질문은 현재 설계를 재검토할 때도 유지한다. 답의 현재 상태는 [`05 현재 설계`](05-current-solution-design.md)에서 확인한다.

1. 어느 순간에 작동하며, 사용자가 먼저 문제를 알아차려야만 하는가.
2. 무엇을 입력으로 삼고 어떤 source의 현재성을 어떻게 구분하는가.
3. 현재 목적·finding·artifact의 의미를 설명에서 왜곡하지 않고, 새 적합성 finding이 필요할 때 005의 조사와 별도 review 경계를 어떻게 가르는가.
4. 설명과 사실 확인, evidence와 AI 해석, 사람 판단을 어떻게 분리하는가.
5. 사람이 다음 지시·보류·추가 조사 중 하나를 책임 있게 고를 수 있도록 무엇을 돌려주는가.
6. 그 결과 중 무엇을 현재 대화에만 두고 무엇을 실제 존재하는 Owner의 인수 후보로 제시하며, 인수가 없을 때 상태를 어떻게 표시하는가.
7. 틀렸거나 낡았거나 source가 부족할 때 어떻게 드러내고 어디로 보내는가.
8. 모든 작업을 긴 절차로 만들지 않으면서도 정확성과 중요한 전제를 어떻게 지키는가.
9. 사용자가 이해했다고 말하는 형식적인 승인 없이도, 어떤 상태까지를 이 책임의 종료로 보는가.
10. 기존의 잘 작동한 인터뷰·spec·eval·Workspace를 어떻게 보존하고, 별도 review와 아직 미채택인 07 책임을 어떻게 침범하지 않는가.

세 장면은 위 질문을 모두 통과한 후보가 필요한 사용 상황을 다루는지 확인하는 데 사용한다. 한 장면에서 보기 좋은 답이 나온 것이 전체 해결의 충분성을 대신하지 않는다.

## 이 문서가 아직 주장하지 않는 것

- 위 의무가 실제로 인지부채나 인지피로를 줄였다는 효과는 아직 없다.
- 세 사례가 TripProof 전체 작업의 실패 빈도를 대표한다는 뜻이 아니다.
- 모든 stub, deterministic code, 작은 slice나 국소 refactor가 잘못이라는 뜻이 아니다.
- 인지피로의 크기와 reference별 효과를 수치로 측정하지 않았다.
- 외부 reference는 이 의무들을 하나의 완성된 방법으로 제공하지 않았다. 직접 근거를 현재 문제에 맞춰 결합한 도출이다.
- Test·pilot·고정 schema의 존재로 부족한 판단이나 실제 효과 검증을 대신하지 않는다.
