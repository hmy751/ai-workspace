# 코드베이스 아키텍처 개선

얕은 모듈을 깊은 모듈로 바꾸는 리팩터링, 즉 **깊이 강화 기회**를 찾아 아키텍처의 마찰을 드러냅니다. 목표는 테스트 용이성과 AI가 코드를 탐색하기 쉬운 구조입니다.

이 명령은 프로젝트의 도메인 모델과 공통 설계 어휘를 바탕으로 합니다.

- Skill 도구에서 `codebase-design`을 호출해 아키텍처 어휘(**module**, **interface**, **depth**, **seam**, **adapter**, **leverage**, **locality**)와 원칙(삭제 테스트, “인터페이스가 테스트 표면이다”, “어댑터 하나면 가상의 seam, 둘이면 실제 seam”)을 확인합니다. 모든 제안에서 이 용어를 정확히 사용하고 “component”, “service”, “API”, “boundary”로 바꿔 부르지 않습니다.
- 도메인 용어집 `GLOSSARY.md`는 좋은 seam에 이름을 붙이고, `docs/adr/`의 ADR은 다시 논의하지 말아야 할 결정을 기록합니다.

## 진행 절차

### 1. 탐색

**살펴보기 전에 범위를 정합니다: YAGNI.** 모듈을 깊게 만들면 앞으로 그 모듈을 바꾸기 쉬워지므로 최근 변경된 코드에 더 무게를 둡니다. 살펴보기 전에 어디를 볼지 결정합니다.

- 사용자가 방향(모듈, 하위 시스템, 불편한 지점)을 지정했다면 그 범위를 따르고 아래 추론은 건너뜁니다.
- 그렇지 않으면 커밋 이력(`git log --oneline`)을 충분히 거슬러 올라가 반복해서 변경된 코드베이스의 핵심 지점, 파일과 영역을 찾고 먼저 살펴봅니다. 변경이 흩어져 있어 핵심 지점이 분명하지 않으면 범위를 넓힙니다.

먼저 프로젝트의 도메인 용어집(`GLOSSARY.md`)과 다루려는 영역의 ADR을 읽습니다.

그다음 하위 에이전트를 실행해 코드베이스를 살펴보게 합니다. 경직된 기준을 따르기보다 자연스럽게 탐색하면서 어디에서 이해가 막히는지 기록합니다.

- 한 개념을 이해하려면 작고 많은 모듈 사이를 오가야 하나요?
- 인터페이스가 구현만큼 복잡한 **얕은** 모듈이 있나요?
- 테스트 편의를 위해 순수 함수를 분리했지만, 실제 버그는 그 함수를 호출하는 방식에 숨어 있나요(**locality 부족**)?
- 강하게 결합된 모듈이 서로의 seam을 넘어 내부를 노출하나요?
- 테스트되지 않았거나 현재 인터페이스로 테스트하기 어려운 영역은 어디인가요?

얕다고 의심되는 대상에는 **삭제 테스트**를 적용합니다. 이 모듈을 삭제하면 복잡성이 한곳에 모이나요, 아니면 다른 곳으로 옮겨갈 뿐인가요? 복잡성이 한곳에 모인다면 개선 후보입니다.

### 2. 후보를 HTML 보고서로 제시

저장소에 임시 파일이 남지 않도록 OS 임시 디렉터리에 자체 완결형 HTML 파일을 작성합니다. `$TMPDIR`에서 임시 디렉터리를 확인하고, 없으면 `/tmp`(Windows에서는 `%TEMP%`)를 사용합니다. 매 실행마다 새 파일이 되도록 `<tmpdir>/architecture-review-<timestamp>.html` 경로를 씁니다. 사용자에게 파일을 열어주고(`xdg-open <path>`는 Linux, `open <path>`는 macOS, `start <path>`는 Windows) 절대 경로를 알려줍니다.

보고서는 레이아웃과 스타일에 Tailwind CDN을, 그래프 형태의 구조를 안정적으로 전달하는 다이어그램에는 Mermaid CDN을 사용합니다. Mermaid와 직접 만든 CSS/SVG 시각화를 함께 활용합니다. 호출 그래프, 의존성, 순서처럼 관계가 그래프 형태면 Mermaid를 사용하고, 전체 규모 그림·단면·접기 애니메이션처럼 편집적인 표현에는 직접 만든 div/SVG를 사용합니다. 각 후보에는 변경 전과 후의 시각 자료를 넣습니다. 시각적으로 구성합니다.

각 후보를 카드로 표시하며 다음 내용을 포함합니다.

- **파일**: 관련 파일/모듈
- **문제**: 현재 아키텍처가 마찰을 일으키는 이유
- **해결책**: 무엇이 바뀌는지 쉬운 말로 설명
- **이점**: locality와 leverage, 테스트 개선 측면에서 설명
- **변경 전/후 다이어그램**: 얕은 구조와 깊어진 구조를 나란히 직접 그려 보여줌
- **추천 강도**: `Strong`, `Worth exploring`, `Speculative` 중 하나를 배지로 표시

보고서 마지막에는 **최우선 추천** 섹션을 두고 어떤 후보를 먼저 다룰지와 이유를 씁니다.

도메인에는 `GLOSSARY.md` 어휘를, 아키텍처에는 `/codebase-design` 어휘를 사용합니다. 예를 들어 `GLOSSARY.md`에 “Order”가 정의되어 있다면 “FooBarHandler”나 “Order service” 대신 “Order intake module”이라고 합니다.

**ADR 충돌**: 후보가 기존 ADR과 충돌한다면, 그 ADR을 다시 검토할 만큼 실제 마찰이 큰 경우에만 제시합니다. 그 경우 카드에 경고를 분명히 표시합니다(예: _“ADR-0007과 충돌하지만, … 때문에 재검토할 가치가 있음”_). ADR이 금지하는 모든 이론적 리팩터링을 나열하지 않습니다.

전체 HTML 뼈대, 다이어그램 패턴, 스타일 지침은 [HTML-REPORT.md](HTML-REPORT.md)를 참고합니다.

아직 인터페이스를 제안하지 않습니다. 파일을 작성한 뒤 사용자에게 “어떤 후보를 더 살펴볼까요?”라고 묻습니다.

### 3. 함께 구체화하기

사용자가 후보를 고르면 Skill 도구에서 `grilling`을 호출해 제약, 의존성, 깊어진 모듈의 형태, seam 뒤에 둘 것, 유지할 테스트를 사용자와 함께 검토합니다.

결정이 구체화되면서 부수 효과가 생기면 그 자리에서 처리합니다. 진행 중 도메인 모델을 최신 상태로 유지하도록 `domain-modeling` Skill을 호출합니다.

- 깊게 만들 모듈에 `GLOSSARY.md`에 없는 개념 이름을 붙이나요? `GLOSSARY.md`에 용어를 추가합니다. 파일이 없으면 필요할 때 생성합니다.
- 대화 중 모호한 용어를 명확히 했나요? 그 자리에서 `GLOSSARY.md`를 갱신합니다.
- 사용자가 중요한 이유를 들어 후보를 거절했나요? “앞으로 아키텍처 검토에서 같은 제안을 반복하지 않도록 ADR로 기록할까요?”라고 제안합니다. 미래 탐색자가 같은 제안을 피하는 데 실제로 필요한 이유일 때만 제안합니다. “지금은 할 가치가 없다” 같은 일시적 이유나 자명한 이유는 제외합니다.
- 깊어진 모듈의 대안 인터페이스도 살펴보고 싶나요? `codebase-design`을 호출하고, 병렬 하위 에이전트가 서로 크게 다른 인터페이스를 설계한 뒤 depth, locality, seam 배치 기준으로 비교하는 패턴을 사용합니다.
