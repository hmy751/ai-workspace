# Fixing the PR Bottleneck — 챕터별 상세 정리

> 첫 번째 강연의 내용을 중심으로 정리했습니다. **강연의 주장**과 **실무 적용 예시**를 구분합니다.

## 0. 강연의 핵심 문제와 해결 흐름

AI Agent가 코드와 PR을 만들어내는 속도는 빨라졌지만, 사람이 PR을 읽고 승인하는 능력은 같은 비율로 증가하지 않았다. 발표자가 해결하려는 것은 코드 생성 속도가 아니라 **PR 처리 파이프라인 전체의 병목**이다. 코드 품질이 떨어지면 Agent가 그 코드를 다시 참고하며 품질 저하가 확대될 수 있다. 따라서 Software Factory는 가속 장치와 함께 품질을 보호하는 Brake가 필요하다.

전체 흐름은 다음과 같다.

```text
Human / Event / Agent가 작업 시작
    ↓
Implementation Agent가 코드 작성
    ↓
Layer 1: Automated Checks (Lint, Type, Test, CI)
    ↓
Layer 2: Automated Review (Coding Standards, 구조 검토, Auto-fix)
    ↓
Layer 3: Human Review (의도, 위험, 승인)
    ↓
Merge / Deploy
    ↓
Retro: 반복 피드백을 규칙·테스트·Skill·환경에 반영
```

## 1. Software Factory Challenge (00:00~02:18)

### 기존 PR 병목
- AI 이전부터 리뷰받지 못한 PR이 누적되는 문제는 존재했다.
- Agent로 구현 속도가 빨라지면서 리뷰가 새로운 주요 병목으로 드러난다.
- **생성된 PR 수 증가와 전체 생산성 향상은 동의어가 아니다.** 검증되지 않은 변경은 오히려 유지보수 비용과 장애 위험을 키운다.

### Software Factory의 정의
- 사람만이 작업을 시작하지 않는 시스템이다. 자동 이벤트나 Agent도 작업을 시작할 수 있다.
- 예시: PlanetScale Slow Query Report → 조건 확인 → Classifier가 Reproduction/Fix 분류 → 자동 작업 요청.
- 발표자가 말한 Trigger는 Deterministic Code에 의해 시작될 수 있다. Agent의 추론까지 결정적이라는 뜻은 아니다.

### Slop Cannon
- 가속만 있고 제동이 없으면 부실한 PR이 빠르게 증가한다.
- 나쁜 Codebase는 다음 Agent 작업의 Environment가 되어, 불량 패턴을 반복 생산할 수 있다.
- 따라서 '더 많은 코드'가 아니라 '검증되고 이해 가능한 변경'을 목표로 해야 한다.

## 2. Three-Layer Review Model (02:18~04:39)

### Layer 1: Automated Checks
- Linting, Testing, Type Checking, Code Quality Metrics 같은 결정적인 검증.
- 상대적으로 저렴해 반복 실행하기 좋고, 사람이 동일한 문제를 다시 확인할 필요를 줄인다.
- 실패한 테스트를 Agent가 수정할 때 Token을 사용하더라도 의미 있는 비용이라고 설명한다.

### Layer 2: Automated Review
- Agent가 Diff와 주변 코드를 읽어 Automated Checks가 잡지 못한 문제, 특히 구조와 Coding Standards 위반을 확인한다.
- 결정적인 Check를 대신하는 것이 아니라 그 위에 추가된다.

### Layer 3: Human Review
- 사람이 PR의 변경 의도와 영향, 위험을 확인한다.
- 앞의 두 계층을 강화해 사람이 반복적으로 처리해야 할 사소한 오류를 줄이는 것이 목표.

| 단계 | 강점 | 한계 |
|---|---|---|
| Automated Checks | 반복 가능, 빠른 오류 검출 | 검사 조건 자체가 부실할 수 있음 |
| Automated Review | 구조와 맥락을 해석 | False Positive, 잘못된 수정 가능 |
| Human Review | 목적·위험·사업적 판단 | 비싸고 처리량이 제한됨 |

## 3. Why Automated Checks Lie (04:39~08:15)

### 문제 A: Tautological Test

구현에 `X_POST_CHARACTER_LIMIT = 280`이 있으니 테스트에서도 그 값이 `280`인지 확인하는 패턴이다. 값의 선언을 재확인할 뿐 **사용자가 실제로 281자를 게시하지 못하는지** 검증하지 않는다. 내부 구조에 민감한 테스트가 되기 쉽다.

**적용 예시:**

```ts
expect(validatePost('a'.repeat(280))).toBe(true);
expect(validatePost('a'.repeat(281))).toBe(false);
```

내부 Constant가 아니라 외부에서 관찰되는 Behavior를 검증한다. 단, 공개 API 계약인 Constant는 직접 검사하는 테스트가 필요할 수 있다.

### 문제 B: Structure-sensitive Test

UI에서 Content Plan 뒤에 Video Section이 보이는지 검사해야 하는데, Source File의 문자열 위치만 읽어서 확인한 사례. 실제 화면을 Render하지 않으므로 Source 구조를 바꾸면 불필요하게 실패할 수 있고, 실제 UI가 잘못돼도 통과할 수 있다.

**적용 예시:** React Testing Library로 Render된 DOM 순서를 확인하거나, 시각적 순서가 중요하면 Browser E2E/Visual Test를 활용한다.

### 문제 C: Tests That Cannot Fail

AudioContext를 사용하는 Hook의 Browser API를 지나치게 단순한 Stub으로 바꾸면 실제 브라우저에서 발생하는 복잡한 Error Mode가 테스트에 나타나지 않는다. Agent가 선의로 만든 테스트라도 Production 문제를 숨길 수 있다.

**적용 예시:** 성공 Mock뿐 아니라 `resume()` 실패, 권한/상태 제약을 재현하고 필요한 경우 실제 Browser에서 Integration/E2E Test를 수행한다.

### 공통 원리
- Green CI는 Merge 안전성을 증명하지 않는다.
- '테스트의 수'보다 '테스트가 무엇을 관찰하는가'가 중요하다.
- Agent가 Implementation Detail 대신 Observable Behavior를 검사하도록 유도해야 한다.

## 4. Designing Better Codebases (08:15~11:20)

### Deep Module

John Ousterhout의 『A Philosophy of Software Design』에 나오는 개념. 복잡한 Implementation을 작고 단순한 Interface 뒤에 감춘다. 반대는 Interface가 크지만 각 Method가 거의 일을 하지 않는 Shallow Module이다.

예시:

```ts
// Caller가 내부 구현 순서를 모두 알아야 하는 방식
validateCart(); calculateDiscount(); calculateTax(); processPayment();

// 복잡성을 내부로 감춘 인터페이스
await checkout({ cartId, couponCode, paymentMethod });
```

아래 코드는 강연의 아이디어를 설명하는 별도 예시다. Deep Module은 큰 함수 하나에 코드를 몰아넣으라는 의미가 아니라 **호출자가 알아야 하는 복잡성을 줄이는 설계**다.

### 좋은 설계가 Test에 미치는 영향
- Public Interface에서 테스트할 수 있어 구현의 작은 변경이 테스트를 무너뜨릴 가능성이 낮아진다.
- Agent가 내부 데이터 구조나 문자열에 직접 의존하는 테스트를 덜 작성하게 유도할 수 있다.

### 발표자의 설계 언어
- **Locality:** 관련 변경이 작은 영역에 국한되는 정도.
- **Leverage:** 작은 Interface를 호출해서 얻는 기능적 가치.
- **Seam:** 모듈 사이의 경계/연결 지점.

### Codebase Design Skill
- 중복 제거와 Module Deepening 기회를 찾아 Before/After를 HTML로 보여준다.
- Team이 코드 구조에 대해 일관된 언어로 소통하도록 돕는다.

## 5. Implementing Review Agents (11:20~16:17)

### 핵심 주장: Implement Agent에 모든 Standards를 넣지 마라

Implementation Agent는 이미 Code Exploration, 실제 Implementation, Debugging, Verification을 하나의 Context Window 안에서 처리해야 한다. 여기에 방대한 Coding Standards까지 더하면 Overloaded될 수 있다.

반면 Review Agent는 Diff가 있으므로 변경 위치를 알고 있으며 비교적 좁은 탐색만 필요하다. 발표자는 Reviewer를 별도 Sub-agent Context에서 수행해 자세한 Standards를 적용한다.

```text
Implementation Agent: Explore → Implement → Tests
    ↓ Diff
Review Sub-agent: Read coding-standards.md → Inspect → Fix → Verify
```

### Make it work → Make it good
- Implement 단계에서는 기능이 동작하도록 만들고,
- Review 단계에서는 구조와 Coding Standards를 적용해 개선한다.
- 발표자는 이를 TDD의 Red-Green-Refactor와 유사한 두 Context의 분리로 설명한다.

### Coding Standards 파일
- 발표자는 Global 지침이나 `AGENTS.md`에 세부 Standards를 가득 넣는 대신 `coding-standards.md`로 분리해 Reviewer가 읽게 하라고 권한다.
- 프로젝트 탐색이나 보안처럼 구현 전 반드시 알아야 할 필수 제약까지 없애라는 뜻은 아니다.

### 범용 리뷰 도구의 한계
- 너무 일반적인 리뷰는 False Positive가 많고,
- 너무 구체적인 리뷰는 특정 언어나 프로젝트에서만 동작한다.
- Cursor Bugbot, CodeRabbit 등이 등장하지만 발표자의 주장은 팀 고유의 Standards를 스스로 축적하고 적용하라는 것이다.

### Reviewer Should Commit
- 리뷰 결과를 Comment로만 남기면 사람이 처리해야 할 일이 늘어난다.
- Reviewer Agent가 안전하게 고칠 수 있는 문제는 직접 Fix/Commit하고, 불확실한 판단만 Comment로 남기라고 권한다.
- **실무 보완:** 수정 후 테스트를 재실행하고, 자동 수정 가능한 범위와 권한을 제한할 필요가 있다.

## 6. Maximizing PR Review Quality (16:17~20:22)

### Human-friendly PR
- 모든 PR을 같은 강도로 Review하지 않는다.
- PR Body에 Change Summary, Pseudocode, Diagram, Risk Summary를 담아 Reviewer가 '무엇이 왜 바뀌는지' 빨리 이해하도록 한다.
- Dex Holley의 Show Me Skill처럼 시각 자료를 적극 활용한다.

### One-way Door vs Two-way Door

| 분류 | 의미 | 예시 |
|---|---|---|
| Two-way Door | 쉽게 되돌릴 수 있는 변경 | 일반적인 국소적 UI 변경 |
| One-way Door | 외부 영향이나 영구 변경으로 되돌리기 어려움 | 6만 명 이메일 전송, 데이터 삭제, 고비용 Migration |

### Blast Radius
- 문제 발생 시 영향이 미치는 범위와 심각성을 평가한다.
- Git Revert가 가능해도 고객에게 발송된 메일이나 삭제된 데이터는 되돌릴 수 없다는 점이 중요하다.
- 발표자는 PR 하단의 `Merge Danger`에 Door Type과 Blast Radius를 표시한다.

### PR Body 예시 (실무 적용)

```md
## Summary
쿠폰 검증을 Checkout 흐름에 추가
## Why
사용자가 결제 전에 쿠폰을 적용할 수 있어야 함
## Behavior / Diagram
주문 생성 → 쿠폰 검증 → 할인 계산 → 결제
## Verification
Unit / Integration / E2E 결과
## Merge Danger
Door Type: Two-way Door
Blast Radius: Checkout Flow
## Rollback
Feature Flag Off / Revert
```

### 코드를 만드는 System도 리뷰한다
- 같은 문제를 두 PR에서 반복 지적하지 않도록 프로세스를 개선해야 한다.
- PR Review는 단순히 코드의 품질 평가가 아니라 앞으로 Agent가 좋은 코드를 생성할 조건을 개선하는 활동이 된다.

## 7. Continuous System Refinement (20:22~22:24)

### Retro Skill

하나의 Session, PR+Session, 최근 일주일의 모든 PR과 Review를 분석해 다음을 제안한다.

1. **Automated Checks:** 반복 오류를 Test나 Lint로 막는 방법.
2. **Coding Standards:** `coding-standards.md`에 추가/수정할 규칙.
3. **Navigation Pointers:** Agent가 정보를 못 찾은 경우 `AGENTS.md`에 경로 안내.
4. **Tool Economy:** 불필요한 탐색/Tool Call과 Token 낭비 개선.
5. **Bloat:** 너무 길어진 Steering File과 Skills 정리.

### Compounding Effect

한 번의 Human Review가 해당 PR만 개선하고 끝나지 않는다. 배운 내용을 검사, 규칙, 도구, 구조에 누적하면 앞으로 작성하는 PR의 품질과 리뷰 경험까지 개선된다. '같은 Comment를 두 번 쓰지 않는다'는 것이 발표자의 원칙이다.

## 8. React / TypeScript / Next.js 적용 로드맵 (정리자가 추가한 예시)

### 1단계: 기계적 검증 확보

```json
{
  "scripts": {
    "lint": "eslint .",
    "typecheck": "tsc --noEmit",
    "test": "vitest run",
    "test:e2e": "playwright test"
  }
}
```

### 2단계: Behavior-based Tests 정리
- UI Source 문자열을 읽는 테스트 대신 Rendering/사용자 행동을 확인한다.
- 과도한 Mocking을 찾아 실패 시나리오와 실제 Browser Integration을 보완한다.

### 3단계: Coding Standards와 Agent 역할 분리
- `AGENTS.md`: 프로젝트 탐색 및 작업 경로.
- `coding-standards.md`: Review 시 적용할 구체적 설계·테스트 기준.
- Implementation Agent: 구현과 기본 검증.
- Review Agent: Diff 기반 구조 검토, 안전한 수정, 테스트 재실행.

### 4단계: 위험 기반 PR Body
- Summary, Why, Pseudocode/Diagram, Verification, Door Type, Blast Radius, Rollback.
- 비가역적 변경은 명시적 사람 승인.

### 5단계: 주간 Retro
- 반복 Comment를 수집해 Lint/Test/Architecture/Skills 개선으로 전환.

## 9. 현실적인 한계

- Green CI는 충분한 근거가 아니지만, Agent 리뷰도 정확성을 증명하지 못한다.
- Auto-fix가 안전하려면 테스트와 권한 경계가 필요하다.
- One-way / Two-way 분류는 위험 관리 보조 수단이며 보안·규정·Branch Protection을 대체하지 않는다.
- PR의 **생성량**보다 Review Time, Regression, Incident, Rollback 등 실제 품질 지표가 중요하다.
