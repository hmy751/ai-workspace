# Fixing the PR Bottleneck — 전체 한국어 번역

> 원문 순서와 챕터 구성을 유지한 번역본입니다. PR, CI, Agent, Skill, Diff, Context Window 등의 개발 용어와 고유명사는 가급적 원문대로 유지했습니다. 제공된 스크립트에서 1:15~1:48 구간은 누락되어 있습니다.

## 챕터 1. The software factory challenge (00:00~02:18)

저는 오늘 PR 병목을 해결하는 방법에 대해 이야기하려고 합니다. 이건 꽤 거창한 제목이지만, 사실 AI 이전부터 대부분의 조직이 오랫동안 어려움을 겪어온 문제를 해결해보려는 겁니다. 우리는 항상 리뷰하지 않은 PR이 엄청나게 많이 쌓여 있는 상황을 겪었습니다. 이제 AI가 만들어내는 새로운 부담과 이상한 제약들 때문에 그 문제가 훨씬 심해졌습니다.

이 문제를 이야기하기 위해 제 Skills를 틀로 사용하겠습니다. 아마 들어보셨거나 사용해보셨을 겁니다. 그리고 PR을 작성하는 방식, 리뷰하는 방식, 특히 리뷰 속도를 개선할 수 있기를 바라는 몇 가지 새 Skill도 발표하겠습니다.

속도입니다. 우리는 사실상 더 적은 자원으로 더 많은 PR, 더 많은 작업, 더 많은 것을 해내라는 압박을 받고 있습니다. AI의 핵심 약속이 바로 Agent를 활용해서 우리 자신의 작업 능력을 확장하는 것이죠. 그래서 오늘날 가장 큰 유행어 중 하나가 Software Factory가 되었습니다. 제가 만나는 거의 모든 사람이 이 이야기를 합니다.

제가 생각하는 Software Factory는 인간이 모든 작업의 시작을 담당하지 않는 시스템입니다. 작업을 시작하는 역할의 일부를 Agent에게 넘깁니다.

[원본 스크립트 01:15~01:48 구간 누락]

예를 들어 Jev 같은 Classifier가 들어와서 이것을 Fix로 만들지, Reproduction으로 만들지 판단할 수 있습니다. 또는 바로 담당자에게 Ping을 보낼 수도 있습니다. PlanetScale을 연결해 Database의 Slow Query Report를 받을 수도 있죠. 이것이 다시 Software Factory의 다른 작업을 Trigger할 수 있습니다. 이 모든 것을 인간이 직접 시작하지 않습니다. Deterministic Code가 Trigger합니다. 이 과정이 Software Factory를 가속하고, 더 많은 코드가 통과하도록 합니다. 하지만 Brake가 필요합니다.

## 챕터 2. The three-layer review model (02:18~04:39)

Factory에 계속 가속만 있다면 결국 Slop Cannon이 됩니다. 형편없는 PR이 잔뜩 쏟아져 나와서 손댈 수도, 리뷰할 수도, 심지어 쳐다볼 수도 없을 겁니다. 따라서 속도를 늦추고 품질을 높이며 Codebase가 Software Entropy의 악몽으로 변하지 않게 하는 Brake가 필요합니다. 코드는 Agent가 작업하는 Environment이기 때문입니다. Codebase에 나쁜 코드가 있으면 더 많은 나쁜 코드를 낳게 됩니다.

오늘은 이 세 가지 Brake를 이야기하고, 이것들을 통해 어떻게 역설적으로 더 빨라질 수 있는지 설명하겠습니다.

먼저 Automated Checks입니다. Repository에 있는 Deterministic Check들이죠. 아주 오래전부터 사용해온 Linting, Tests, Type Checking, Code Quality Metrics 같은 것들입니다. 모두 매번 같은 방식으로 동작합니다.

그 위에 Automated Review가 있습니다. Agent가 코드를 살펴보며 Test가 잡지 못한 문제를 찾거나 Codebase 전체의 구조를 확인합니다. 그리고 세 번째이자 마지막 층은 Human Review입니다. 사람이 PR을 보는 것이죠. 세 층이 케이크처럼 쌓여 최종 Human Review에 도달합니다.

속도가 높아진다는 것은 PR이 많아진다는 뜻입니다. 따라서 앞의 두 단계를 활용해 Human Review를 더 빠르게 하는 것이 목표입니다. 우선 Slop을 막아야 합니다. Shipping하는 코드 품질을 높이면 Human Review에서 개입해야 할 일이 줄어듭니다. 처음부터 더 좋은 결과물이기 때문입니다.

Automated Checks는 저렴합니다. Automated Review처럼 Token이 들지 않고, Human Effort도 요구하지 않습니다. CPU Cycle을 사용하죠. 예를 들어 코드가 바뀔 때마다 Test를 실행합니다. Agent가 Bug를 만들어 Test에 걸리면 수정하는 데 Token이 조금 쓰이겠지만, 제 생각에는 아주 잘 쓰인 Token입니다. Check가 저렴하기 때문에 Repository에 아주 많이 쌓을 수 있습니다.

## 챕터 3. Why automated checks lie (04:39~08:15)

아마 여러분은 Check를 충분히 사용하지 않거나 창의적으로 활용하지 않고 있을 겁니다. 하지만 Check는 거짓말을 할 수 있습니다.

CI가 Green이라고 해서 Merge할 준비가 된 것일까요? 아닙니다. 그래서 Shipping 전에 코드에 치명적인 문제가 없는지 알아내는 추가 계층이 늘 필요했습니다. Automated Review와 Human Review는 Automated Checks의 거짓말을 찾아내는 Lie Detector인 셈입니다.

첫 번째 거짓말은 Tautological Test입니다. Implementation을 그대로 다시 주장하는 Test죠. Opus 5는 이런 테스트에 중독돼 있었습니다. 왜 그랬는지는 모르겠습니다. 예를 들어 X Post Character Limit이 280이라는 Constant가 있다면 Agent는 그것이 280이어야 한다고 Expect하는 Test를 작성합니다. Implementation에 있는 내용을 그대로 반복하는 것이죠.

이런 Test는 구조에 지나치게 민감합니다. Constant를 변경하면 실패하고, 이름만 바꿔도 실패할 수 있습니다. System의 내부 구조에 너무 밀접하게 결합된 겁니다.

더 터무니없는 사례도 있었습니다. UI에서 Content Plan 다음에 Video Section이 나타나는지 테스트하는 코드입니다. 그런데 Screen에 Render하지 않습니다. 그냥 Module의 Source File을 Memory로 읽고 Content Plan과 Videos라는 문자열의 위치를 찾은 다음 Videos가 뒤에 있는지를 확인합니다. Source의 모양만 바꿔도 실패합니다. Codebase의 구조에 너무 민감한 테스트입니다.

그리고 문자 그대로 실패할 수 없는 Test도 있습니다. Mocking을 과용해본 사람에게는 익숙할 겁니다. 예를 들어 DOM의 AudioContext API를 사용하는 useAudioBoost Function이 있습니다. Test에서 그 API의 Method들을 가짜로 Stub 처리해버립니다. 하지만 실제 AudioContext에는 복잡한 Error Mode가 있고 특수한 조건에서는 실패합니다. 단순한 Stub만 사용하면 이런 실패를 Test가 잡지 못합니다. 결국 Production에서 이상한 Error를 만나게 됩니다.

Agent가 일부러 나쁜 Test를 작성하는 것은 아닙니다. 선의로 Instruction을 따르는 과정에서 실제 코드를 실행해 확인하기보다 구조에 지나치게 연결된 Test를 작성하는 것입니다. 그렇다면 Automated Checks를 속이기 어렵게 만들려면 어떻게 해야 할까요?

## 챕터 4. Designing better codebases (08:15~11:20)

그렇게 할 수 있다면 Check의 품질과 Quality Bar가 높아집니다. 제가 좋아하는 첫 번째 방법은 Codebase Design입니다. 설계를 통해 나쁜 Check에서 벗어날 수 있습니다.

좋은 Codebase Design은 어떤 것일까요? 이전 AI Engineer 강연에서도 이야기했던 Deep Module입니다. John Ousterhout의 『A Philosophy of Software Design』에서 나온 생각으로, 복잡한 Behavior를 간단한 Interface 뒤에 숨기는 Module입니다.

Module A는 작은 Interface 뒤에 큰 Implementation을 숨깁니다. Module B는 Interface가 크고 호출할 Function이 많지만 각각의 Function은 하는 일이 적습니다. Deep Module을 사용하면 Implementation의 더 많은 부분을 Interface 뒤에 숨기므로 Structure-sensitive Test가 줄어듭니다. Test가 그 작은 Interface를 사용하도록 Agent에게 강제하는 것이 여러분의 일입니다. 내부 Implementation Detail에 들어가 이상한 Test를 작성하지 않도록 해야 합니다.

그래서 제가 만든 Skill이 있습니다. 정말 이상하게 Vibe-coded된 Codebase, 아무리 형편없는 Codebase라도 이 Skill을 실행하면 개선할 기회를 찾아줍니다. Deep Module로 바꿀 수 있는 곳을 찾고, 중복을 줄이고, Before와 After를 비교하는 HTML Document를 제공합니다. 그다음 제안된 변경을 실제로 Implement하면 됩니다.

또 Module을 설명하기 위한 일관된 Language도 만들었습니다. Codebase를 어떻게 구조화할지 읽어보면 스무 가지의 서로 다른 접근을 발견할 텐데, 모두 DDD라고 부를 겁니다. 팀에서 일관된 언어로 소통할 수 있어야 합니다. 제 Codebase Design Skill은 Locality, Leverage, Seam을 정의합니다. 저는 Seam이 유행하기 전부터 사용했죠.

Locality는 관련 코드가 얼마나 잘 한곳에 모여 있는지, 작은 변경이 얼마나 넓게 퍼지는지에 관한 것입니다. Leverage는 Deep Module을 사용할 때, Caller가 단순한 Function 호출 한 번으로 큰 가치를 얻는 것입니다. 두 특성 모두 Codebase와 Agent에게 좋습니다.

그런데 이런 고상한 Coding Standards를 Agent가 실제로 잘 지키도록 만들려면 어떻게 해야 할까요?

## 챕터 5. Implementing review agents (11:20~16:17)

Agent가 Deep Module과 좋은 Test를 만들고, 형편없는 Tautological Test나 Structure-sensitive Test를 피하게 하려면 어떻게 할까요? 제 생각에는 대부분 이 부분을 잘못하고 있습니다.

첫 번째 조언은 **Coding Standards를 Implement Agent에 넣지 말라**는 것입니다. 설명하겠습니다. Implement Agent는 하나의 Context Window 안에서 변경할 코드를 탐색하고, 실제 파일을 수정하고, Automated Checks를 실행하고, Debugging까지 해야 합니다. 이미 할 일이 많습니다. 여기에 Coding Standards까지 강요하면 성능이 떨어집니다. 제가 드리고 싶은 Mental Model은 Implementation이 Overloaded되어 있다는 것입니다.

그러면 다른 방식으로 Standards를 적용할 수 있을까요? 제 Code Review Skill은 Diff를 받고 Repository 안의 Coding Standards File을 읽어 코드가 Standards를 따르는지 확인합니다. 중요한 점은 Reviewer Agent를 Sub-agent에서 실행한다는 것입니다. 고유한 Context Window와 Budget이 있습니다.

Reviewer는 Diff를 알고 있으니 약간의 Exploration으로 넓은 Context를 파악하면 됩니다. 구현이나 디버깅을 처음부터 할 필요는 없습니다. Implementation은 Overloaded되어 있지만 Review는 상대적으로 Underloaded입니다. 그래서 Reviewer에 많은 Coding Standards를 넣어도 Implementer에 넣을 때보다 더 잘 처리할 수 있습니다.

이건 좋은 코드를 작성하는 두 단계 Process입니다. 처음부터 좋은 코드를 얻고 싶은 마음과는 다를 수 있지만, 먼저 Implement로 작동하게 만들고, Code Review로 좋은 코드로 만듭니다. Coding Standards를 적용하는 것이죠. 오래된 개발자들에게는 Red-Green-Refactor 접근과 비슷합니다. 하나의 Context Window에서 Red와 Green을 하고, 다른 Context Window에서 Refactor하는 겁니다. 제 경험에는 매우 성공적이었습니다.

따라서 Coding Standards를 Global Scope나 AGENTS.md에 잔뜩 넣지 않습니다. 그러면 Implementer의 Context를 압도할 수 있습니다. 대신 coding-standards.md에 넣어 Code Review Agent만 읽도록 합니다.

오늘 사람들과 이야기해보니 Automated Review에는 Cursor Bugbot이나 CodeRabbit 같은 Third-party Service를 쓰는 경우가 많더군요. 저도 모든 Bug를 찾고 Security Review도 해주는 Generic Code Review Skill을 만들려고 노력했는데, 정말 어렵습니다. 너무 일반적으로 만들면 관련 없는 False Positive가 많아지고, 너무 구체적으로 만들면 TypeScript용 Rule을 Rust 사용자에게 적용할 수 없습니다.

그래서 Automated Review를 전적으로 Outsource하지 말라고 말씀드리고 싶습니다. 자신의 팀에 맞는 것을 구축하고 Coding Standards를 시간에 따라 축적해 팀과 공유하세요. 아무도 읽지 않는 Documentation이 있다면 그것을 활용할 곳이기도 합니다.

그리고 많은 사람이 Code Review Agent가 PR에 Comment를 달도록 만듭니다. 하지만 그러면 Human Reviewer에게 일이 더 생깁니다. 장황한 Comment를 전부 읽고 무엇을 수정할지 판단해야 하니까요. **Reviewer는 Commit해야 합니다.** 문제를 찾았다면 실제로 변경을 적용해야 합니다. 그래야 사람이 나중에 훨씬 좋은 Artifact를 리뷰하게 됩니다. 확신이 없는 부분은 물론 Comment를 달 수 있지만 Default는 Commit이어야 합니다.

처음부터 완벽한 코드를 One-shot으로 만들려고 하지 마세요. Implementer Agent 하나에 모든 것을 강제하려 하지 마세요. 생각의 방향을 바꾸면 정말 훌륭합니다. 이제 Automated Checks를 거쳤고, Automated Review로 그 Checks가 거짓말하는지도 확인했습니다.

## 챕터 6. Maximizing PR review quality (16:17~20:22)

그렇다면 Human Review가 가장 효율적으로 동작하려면 어떻게 해야 할까요? Human-friendly PR이 필요합니다. 이것이 새로 만들고 있는 PR Skill입니다. 오랫동안 고민했고 아직 State-of-the-art가 정확히 무엇인지 몰랐습니다. 그러다 다른 사람들의 좋은 아이디어를 전부 가져오는 것이 가장 좋은 방법이라는 것을 깨달았죠.

좋은 PR Body는 어떤 모습일까요? 첫 번째 원칙은 어떤 Review는 다른 Review보다 중요하다는 것입니다. 모든 Review가 필수적인 것은 아닙니다. 그렇다면 가장 중요한 Review에 에너지를 집중할 수 있습니다.

PR이 AWS 용어로 One-way Door인지 Two-way Door인지 생각해야 합니다. 대부분의 PR은 Merge한 다음 쉽게 Revert할 수 있는 Two-way Door입니다. 이건 토목 엔지니어와 비교했을 때 소프트웨어 엔지니어의 멋진 장점입니다. 다리는 잘못 만들면 무너지니까 보통 One-way Door죠.

다만 간단한 변경도 실수로 60,000명에게 Email을 보내버린다면 One-way Door입니다. 비싼 Migration이나 Data Loss를 수반한다면 One-way Door입니다. 이런 PR은 아주 철저하게 Review해야 합니다.

여기에 Blast Radius도 고려해야 합니다. 무엇이 잘못될 수 있는지, 잘못되면 얼마나 나쁜지 말입니다. 제 PR 하단에는 Merge Danger라는 작은 Summary가 있습니다. 이 PR이 Two-way Door이고 Blast Radius가 Localized라면, 상대적으로 가볍게 살펴봐도 된다고 판단할 수 있습니다.

그다음은 PR이 실제로 무엇을 하는지 이해하는 것입니다. 제가 찾은 가장 좋은 방법은 Pseudocode입니다. HumanLayer Skills Repository의 Dex Holley가 만든 Show Me Skill에 감사드립니다. 대부분의 Text 대신 Image와 Diagram으로 보여주는 정말 뛰어난 Skill입니다. 무엇이 왜 변경되는지 쉽게 이해할 수 있습니다.

Mermaid나 UML로 실행 순서를 보여줄 수도 있고, CLI에 새로운 Command나 Flag가 추가됐다는 것을 단순한 그림으로 보여줄 수도 있습니다. 이런 작은 Summary가 엄청난 차이를 만듭니다. 목표는 Why를 이해하는 시간을 가능한 한 줄이는 것입니다.

세 번째 원칙은 Human Review에서 늘 생각해야 합니다. 이제 우리는 같은 Skill File과 Steering File을 중심으로 협업하며 Agent가 일할 공통 Environment를 만들고 있습니다. 따라서 코드를 만들어내는 Process 역시 코드만큼 중요합니다. Human Review를 할 때는 코드뿐 아니라 **그 코드를 만들어낸 System을 리뷰하는 것**입니다.

## 챕터 7. Continuous system refinement (20:22~22:24)

같은 Comment를 두 번 작성해서는 안 됩니다. 서로 다른 PR에서 Agent가 같은 실수를 반복하는 것을 사람이 두 번 잡아내서는 안 됩니다. Human Review가 다음 작업에도 영향을 주도록 만드는 Mechanism은 무엇일까요?

새로운 Skill인 Retro, 즉 Retrospective입니다. 하나의 Agent Session, PR과 그 Session, 또는 지난 일주일 동안의 PR과 Review 전부를 가져와 회고할 수 있습니다. 그러면 다음 작업을 더 좋게 만들 Automated Checks와 Coding Standards를 제안합니다.

이것이 Compounding Effect입니다. Human Review를 수행함으로써 다음 Human Review의 품질을 높이고, 다음에 사람이 해야 할 일을 줄여갑니다.

Retro는 Automated Checks와 coding-standards.md 업데이트를 제안합니다. Navigation Pointer도 살펴봅니다. Agent가 정보를 얼마나 쉽게 찾았는지, 다음에는 AGENTS.md에 Pointer를 추가하면 도움이 될지 확인합니다.

Tool Economy도 봅니다. Session에서 사용한 Tool을 Token 측면에서 더 효율적으로 만들 수 있는지 살펴봅니다. 외부에서 디버깅하기 힘든 비효율이 의외로 많이 발견됩니다. Bloat도 확인합니다. 너무 커진 Steering File이나 Skill이 결과를 악화시키고 있지 않은지, 더 체계적으로 정리할 수 있는지 검토합니다.

최종 목표는 Human Review를 더 빠르게 만드는 것입니다. Automated Checks를 쌓고, Automated Review를 쌓고, Human Review를 가능한 한 고통 없고 단순하게, 필요에 따라 선택적으로 만듭니다. 모든 Two-way Door를 전부 리뷰할 필요는 없습니다. One-way Door는 모두 리뷰해야 합니다.
