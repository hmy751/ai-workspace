# 코드베이스 설계

작은 인터페이스 뒤에 많은 동작을 두고, 명확한 seam에 배치하며, 그 인터페이스를 통해 테스트할 수 있는 **깊은 모듈**을 설계합니다. 코드 설계나 구조 변경에는 이 용어와 원칙을 일관되게 사용합니다. 목표는 호출자를 위한 leverage, 유지보수자를 위한 locality, 모두를 위한 테스트 용이성입니다.

## 용어집

이 용어를 정확히 사용합니다. “component”, “service”, “API”, “boundary”로 바꾸지 않습니다. 일관된 언어가 핵심입니다.

**Module(모듈)**: 인터페이스와 구현을 가진 모든 것. 함수, 클래스, 패키지, 여러 계층에 걸친 기능 단위 등 규모와 무관합니다. 피할 표현: unit, component, service.

**Interface(인터페이스)**: 호출자가 모듈을 올바르게 사용하기 위해 알아야 하는 모든 것. 타입 시그니처뿐 아니라 불변 조건, 순서 제약, 오류 방식, 필수 설정, 성능 특성도 포함합니다. 피할 표현: API, signature(타입 표면만 가리켜 범위가 좁음).

**Implementation(구현)**: 모듈의 내부, 즉 코드 본문입니다. **Adapter(어댑터)**와 구별합니다. 작은 어댑터가 큰 구현을 가질 수도 있고(Postgres 저장소), 큰 어댑터가 작은 구현을 가질 수도 있습니다(메모리 내 가짜 구현). seam이 주제일 때는 “adapter”, 그 외에는 “implementation”을 사용합니다.

**Depth(깊이)**: 인터페이스가 제공하는 leverage입니다. 호출자(또는 테스트)가 익혀야 하는 인터페이스 단위당 사용할 수 있는 동작의 양입니다. 적은 인터페이스 뒤에 많은 동작이 있으면 깊은 모듈이고, 인터페이스가 구현만큼 복잡하면 얕은 모듈입니다.

**Seam** _(Michael Feathers)_: 그 지점을 수정하지 않고도 동작을 바꿀 수 있는 자리, 즉 모듈 인터페이스가 놓이는 위치입니다. seam을 어디에 둘지는 그 뒤에 무엇을 둘지와 별개의 설계 결정입니다. DDD의 bounded context와 혼동될 수 있으므로 “boundary”라고 하지 않습니다.

**Adapter(어댑터)**: seam에서 인터페이스를 충족하는 구체적인 대상입니다. 내부 내용이 아니라 어떤 자리를 채우는지, 즉 역할을 설명합니다.

**Leverage**: 깊이에서 나오는 호출자의 이점입니다. 익혀야 하는 인터페이스 단위당 더 많은 기능을 얻습니다. 한 번 구현한 것이 N개의 호출 지점과 M개의 테스트에서 이점을 냅니다.

**Locality**: 깊이에서 나오는 유지보수자의 이점입니다. 변경, 버그, 지식, 검증이 호출 지점 여기저기로 퍼지지 않고 한곳에 모입니다. 한 번 고치면 모든 곳에서 고쳐집니다.

## 깊은 모듈과 얕은 모듈

**깊은 모듈** = 작은 인터페이스 + 많은 구현

```text
┌─────────────────────┐
│   작은 인터페이스    │  ← 메서드가 적고 매개변수가 단순함
├─────────────────────┤
│                     │
│   깊은 구현          │  ← 복잡한 로직을 내부에 감춤
│                     │
└─────────────────────┘
```

**얕은 모듈** = 큰 인터페이스 + 적은 구현(피할 것)

```text
┌─────────────────────────────────┐
│       큰 인터페이스              │  ← 메서드가 많고 매개변수가 복잡함
├─────────────────────────────────┤
│  얇은 구현                       │  ← 전달만 함
└─────────────────────────────────┘
```

인터페이스를 설계할 때 질문합니다.

- 메서드 수를 줄일 수 있나요?
- 매개변수를 단순하게 만들 수 있나요?
- 더 많은 복잡성을 내부에 숨길 수 있나요?

## 원칙

- **깊이는 구현이 아니라 인터페이스의 속성입니다.** 깊은 모듈도 내부적으로 작고 mock 가능하며 교체 가능한 부분으로 구성될 수 있습니다. 다만 그 부분은 인터페이스의 일부가 아닙니다. 모듈에는 구현 자체의 테스트에서 사용하는 **내부 seam**과 인터페이스에 놓인 **외부 seam**이 있을 수 있습니다.
- **삭제 테스트.** 모듈을 삭제한다고 상상해 봅니다. 복잡성이 사라지면 단순 전달자였던 것입니다. 복잡성이 N개의 호출자에 다시 나타나면 모듈은 제 역할을 한 것입니다.
- **인터페이스가 테스트 표면입니다.** 호출자와 테스트는 같은 seam을 통과합니다. 인터페이스를 넘어가서 테스트해야 한다면 모듈의 형태가 잘못됐을 가능성이 큽니다.
- **어댑터 하나면 가상의 seam, 둘이면 실제 seam입니다.** seam을 사이에 둔 실제 변이가 없으면 seam을 만들지 않습니다.

## 테스트하기 쉬운 설계

좋은 인터페이스는 자연스러운 테스트를 가능하게 합니다.

1. **의존성을 직접 만들지 말고 전달받습니다.**

   ```typescript
   // 테스트하기 쉬움
   function processOrder(order, paymentGateway) {}

   // 테스트하기 어려움
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **부수 효과를 발생시키지 말고 결과를 반환합니다.**

   ```typescript
   // 테스트하기 쉬움
   function calculateDiscount(cart): Discount {}

   // 테스트하기 어려움
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **표면적을 작게 유지합니다.** 메서드가 적으면 필요한 테스트도 줄어듭니다. 매개변수가 적으면 테스트 준비가 단순해집니다.

## 관계

- **Module**에는 정확히 하나의 **Interface**가 있습니다(호출자와 테스트에 제공하는 표면).
- **Depth**는 **Module**의 속성이며, 그 **Interface**를 기준으로 측정합니다.
- **Seam**은 **Module**의 **Interface**가 놓이는 자리입니다.
- **Adapter**는 **Seam**에 놓여 **Interface**를 충족합니다.
- **Depth**는 호출자에게 **Leverage**를, 유지보수자에게 **Locality**를 제공합니다.

## 사용하지 않는 관점

- **구현 줄 수 대 인터페이스 줄 수의 비율로 깊이를 정의**(Ousterhout): 구현을 불필요하게 부풀릴 유인이 됩니다. 여기서는 깊이를 leverage로 봅니다.
- **“Interface”를 TypeScript의 `interface` 키워드나 클래스의 public 메서드로 한정**: 범위가 너무 좁습니다. 여기서 인터페이스는 호출자가 알아야 하는 모든 정보를 뜻합니다.
- **“Boundary”**: DDD의 bounded context와 의미가 겹칩니다. **seam** 또는 **interface**라고 합니다.
