---

사용자가 제공한 기준점과 `HEAD` 사이의 diff를 두 축으로 검토합니다.

- **Standards(표준)**: 코드가 저장소에 문서화된 코딩 표준을 따르나요?
- **Spec(명세)**: 코드가 시작점이 된 이슈/명세를 충실히 구현했나요?

두 축은 서로의 문맥을 섞지 않도록 **병렬 하위 에이전트**에서 검토한 뒤 결과를 모아 보고합니다.

이슈 트래커 정보가 제공되어 있어야 합니다. 없다면 사용자에게 `/setup-matt-pocock-skills`를 실행하라고 안내합니다.

## 절차

### 1. 기준점을 고정합니다

사용자가 말한 기준점(커밋 SHA, 브랜치 이름, 태그, `main`, `HEAD~5` 등)을 사용합니다. 기준점을 지정하지 않았다면 사용자에게 묻습니다.

diff 명령을 한 번 정해 둡니다: `git diff <fixed-point>...HEAD`(3점 표기이므로 merge-base를 기준으로 비교). 커밋 목록도 `git log <fixed-point>..HEAD --oneline`으로 기록합니다.

진행하기 전에 기준점이 유효한지(`git rev-parse <fixed-point>`) 확인하고 diff가 비어 있지 않은지 확인합니다. 잘못된 참조이거나 diff가 비었다면 여기서 종료합니다. 하위 에이전트 안에서야 발견하게 두지 않습니다.

### 2. 명세의 출처를 찾습니다

다음 순서로 시작점이 된 명세를 찾습니다.

1. 커밋 메시지의 이슈 참조(`#123`, `Closes #45`, GitLab `!67` 등)를 찾고 트래커 문서의 절차에 따라 가져옵니다.
2. 사용자가 인자로 전달한 경로를 확인합니다.
3. 브랜치명 또는 기능과 일치하는 `docs/`, `specs/`, `.scratch/` 내 명세 파일을 찾습니다.
4. 찾지 못하면 사용자에게 명세 위치를 묻습니다. 사용자가 명세가 없다고 하면 **Spec** 하위 에이전트는 검토를 건너뛰고 “사용 가능한 명세 없음”이라고 보고합니다.

### 3. 표준의 출처를 찾습니다

저장소에서 코드를 어떻게 작성해야 하는지 설명하는 모든 파일을 찾습니다. `CODING_STANDARDS.md` 또는 `CONTRIBUTING.md`가 있으면 반드시 목록에 넣습니다.

저장소 문서에 더해 Standards 축에는 아래의 고정된 Fowler 코드 스멜 기준(`_Refactoring_`, 3장)을 항상 포함합니다. 적용 규칙은 두 가지입니다.

- **저장소 규칙이 우선합니다.** 문서화된 저장소 표준이 스멜 기준과 충돌하면, 저장소가 허용하는 패턴을 스멜로 지적하지 않습니다.
- **언제나 판단이 필요한 지적입니다.** 각 스멜은 “Feature Envy 가능성” 같은 휴리스틱으로 표시하며 절대적인 위반으로 처리하지 않습니다. 다른 표준과 마찬가지로 도구가 이미 강제하는 항목은 건너뜁니다.

각 스멜은 ‘무엇인지 → 어떻게 고칠지’ 순서입니다. diff에서 해당 형태를 찾습니다.

- **이해하기 어려운 이름(Mysterious Name)**: 함수, 변수, 타입의 이름만으로 역할이나 값이 드러나지 않음. → 이름을 바꿉니다. 적절한 이름을 붙일 수 없다면 설계가 불분명한 것입니다.
- **중복 코드(Duplicated Code)**: 변경된 여러 hunk 또는 파일에 같은 로직 형태가 반복됨. → 공통 형태를 추출해 두 곳에서 호출합니다.
- **기능 선망(Feature Envy)**: 메서드가 자기 객체보다 다른 객체의 데이터에 더 많이 접근함. → 메서드를 그 데이터가 속한 객체로 옮깁니다.
- **데이터 뭉치(Data Clumps)**: 같은 필드나 매개변수 몇 개가 계속 함께 이동함(새 타입으로 묶을 신호). → 하나의 타입으로 묶어 전달합니다.
- **원시 타입 집착(Primitive Obsession)**: 별도 타입으로 표현할 만한 도메인 개념을 원시 값이나 문자열로 표현함. → 그 개념을 나타내는 작은 타입을 만듭니다.
- **반복되는 분기(Repeated Switches)**: 변경된 곳 여러 군데에서 같은 타입을 대상으로 한 `switch` 또는 `if` 연쇄가 반복됨. → 다형성으로 바꾸거나 두 위치가 공유하는 맵 하나를 사용합니다.
- **산탄총 수술(Shotgun Surgery)**: 하나의 논리적 변경 때문에 diff의 여러 파일을 흩어져 수정해야 함. → 함께 바뀌는 것을 하나의 모듈로 모읍니다.
- **서로 다른 변경 이유(Divergent Change)**: 파일 또는 모듈 하나가 서로 무관한 여러 이유로 수정됨. → 모듈마다 한 가지 이유로 바뀌도록 나눕니다.
- **추측성 일반화(Speculative Generality)**: 명세가 요구하지 않는 추상화, 매개변수, 확장 지점을 추가함. → 삭제합니다. 실제 필요가 생길 때까지 인라인 형태로 되돌립니다.
- **메시지 체인(Message Chains)**: 호출자가 의존하지 않아야 할 긴 `a.b().c().d()` 탐색이 있음. → 첫 번째 객체의 메서드 하나 뒤에 탐색을 숨깁니다.
- **중개자(Middle Man)**: 클래스나 함수가 대부분 다른 곳으로 전달만 함. → 제거하고 실제 대상을 직접 호출합니다.
- **상속 거부(Refused Bequest)**: 하위 클래스나 구현체가 상속받은 기능 대부분을 무시하거나 재정의함. → 상속을 제거하고 조합을 사용합니다.

### 4. 두 하위 에이전트를 병렬 실행합니다

두 하위 에이전트를 병렬로 호출하고, 포그라운드에서 결과가 돌아오면 보고를 취합합니다.

**Standards 하위 에이전트 프롬프트**에 포함할 내용:

- 전체 diff 명령과 커밋 목록
- 3단계에서 찾은 표준 문서 목록 **및 3단계의 스멜 기준 전체**(하위 에이전트가 해당 기준을 따로 볼 수 없으므로 그대로 붙여넣음)
- 다음 요청: “파일/hunk별로 관련된 경우 (a) diff에서 문서화된 표준을 위반하는 모든 지점을 찾고 표준(파일 + 규칙)을 인용하세요. (b) 기준 코드 스멜이 있으면 이름을 붙이고 해당 hunk를 인용하세요. 명확한 위반과 판단이 필요한 지적을 구분하세요. 문서화된 표준 위반은 명확한 위반일 수 있지만 기준 스멜은 언제나 판단이 필요하며, 문서화된 저장소 표준이 스멜 기준보다 우선합니다. 도구가 이미 검사하는 항목은 생략하세요. 400단어 미만으로 작성하세요.”

**Spec 하위 에이전트 프롬프트**에 포함할 내용:

- diff 명령과 커밋 목록
- 명세 경로 또는 가져온 명세 본문
- 다음 요청: “(a) 명세의 요구 중 누락되거나 일부만 구현된 항목, (b) 요청하지 않은 diff의 동작(범위 확장), (c) 구현된 것처럼 보이나 잘못 구현된 요구를 보고하세요. 각 지적의 명세 문장을 인용하세요. 400단어 미만으로 작성하세요.”

명세가 없다면 Spec 하위 에이전트를 실행하지 않고 최종 보고서에 그 사실을 씁니다.

### 5. 결과를 취합합니다

두 보고서를 `## Standards`, `## Spec` 제목 아래에 원문 그대로 또는 가볍게 다듬어 제시합니다. 두 축은 의도적으로 분리되어 있으므로 지적을 합치거나 순위를 다시 매기지 않습니다.

마지막에는 축별 전체 지적 수와 각 축에서 가장 심각한 문제(있는 경우)를 한 줄로 요약합니다. 두 축을 가로질러 하나를 최우선으로 뽑지 않습니다. 축을 분리한 취지를 훼손하기 때문입니다.

## 두 축을 나누는 이유

한 축은 통과하고 다른 축은 실패할 수 있습니다.

- 모든 표준을 따르지만 잘못된 기능을 구현한 코드 → **Standards 통과, Spec 실패**
- 이슈가 요청한 일은 정확히 했지만 프로젝트 관례를 어긴 코드 → **Spec 통과, Standards 실패**

두 결과를 따로 보고하면 한 축의 평가가 다른 축의 문제를 가리지 않습니다.
