**이번 작업은 이미 만든 네트워크 상태를 실제 데이터 요청·화면·동기화가 일관되게 사용하도록 연결한 것입니다.** 코드의 책임을 정리하는 개선과, 합의한 동작을 막던 결함 수정이 함께 들어갔습니다.

1. **네트워크 상태를 관측하는 책임과 사용하는 책임을 구별했습니다.**

   Network Store는 인터넷 연결 신호를 받아 `online`, `offline`, `unknown`으로 표현합니다. `unknown`은 초기 확인 전뿐 아니라 사용 중 관측이 다시 불확실해진 경우에도 사용합니다.

   판정은 기존에 합의한 그대로입니다. 두 신호 중 하나라도 명시적으로 false이면 offline, 둘 다 true이면 online, 나머지는 unknown입니다. 10초가 지나도 unknown을 offline으로 바꾸지 않습니다. “확인 중” 안내를 “확인하지 못했음”으로 바꾸는 시간일 뿐입니다.

   이번 품질 개선에서는 이 Store를 더 분할하지 않았습니다. 구독·타이머·재확인 요청을 같은 파일의 private action factory가 소유하는 기존 구조를 유지했습니다.

   소비자는 목적에 맞는 값을 읽습니다.

   - 실제 요청과 sync는 실제 관측값을 읽습니다.
   - 화면 표시와 제한 시뮬레이션은 debug 강제 설정을 반영한 값을 읽습니다.
   - 재확인 안내는 연결 상태와 별도의 확인 진행 상태를 읽습니다.

   이 차이는 [Store의 실제·표시 API](/Users/hammyeong-yeon/Desktop/10_work/noline/apps/client/src/shared/store/network.ts:257)에 드러납니다. 예를 들어 debug에서 online으로 표시해도 실제 상태가 unknown이면 서버 요청을 허용하지 않습니다.

   품질 측면에서는 “이 online이 실제 관측인지 화면용 강제 값인지”를 호출하는 곳마다 추측하는 부담을 줄였습니다.

2. **앱 진입 준비와 sync 실행 준비를 구별했습니다.**

   앱을 켰을 때 네트워크 확인과 DB·인증 준비는 독립적으로 시작합니다. 네트워크 결과가 늦다고 DB 초기화나 인증 복원을 기다리게 하지 않습니다.

   실제 debug 버튼도 engine을 직접 호출하지 않고 이 Provider를 사용합니다. 그래서 Provider에 보호 조건이 있어도 버튼이 우회하던 문제를 해결했습니다. 버튼은 실행 거부·실행 실패·engine 반환을 구별해 안내합니다. [수동 sync 버튼 연결](/Users/hammyeong-yeon/Desktop/10_work/noline/apps/client/src/features/debug/ui/DebugScreen.tsx:126)

3. **데이터를 어느 여행 기준으로 처리하는지 호출부에서 명확하게 전달했습니다.**

4. **서버 캐시가 남아 있는 것과 지금 내용을 볼 수 있는 것을 구별했습니다.**

   React Query는 이전 서버 응답을 앱 메모리에 보관합니다. 서버 요청을 차단해도 그 응답은 남아 있습니다. 따라서 `data`가 있다는 이유만으로 일정·경비를 렌더하면 비활성 여행의 내용이 offline에서도 계속 보일 수 있습니다.

   `useAppPolicy`는 현재 여행의 활성 여부와 화면 네트워크 상태를 해석해 내용 접근 권한·제한 이유를 제공합니다. 활성 여부를 아직 읽는 중인 상태도 inactive로 단정하지 않고 로딩으로 구별합니다. [내용 접근 정책](/Users/hammyeong-yeon/Desktop/10_work/noline/apps/client/src/shared/policy/useAppPolicy.ts:85)

   `TripContentStatus`는 그 결과를 기존 정책 안내와 버튼으로 표시합니다. 일정·경비 화면은 본문을 내용 또는 제한 안내 중 하나로 선택하고 여행 선택 UI와 수정 Drawer는 밖에 유지합니다. [일정 화면의 실제 본문 연결](/Users/hammyeong-yeon/Desktop/10_work/noline/apps/client/src/screens/ScheduleScreen.tsx:228)

   설명용으로 비활성 여행 B의 경비를 보고 있다고 가정하면, 현재 코드는 다음 흐름을 만듭니다.

   1. 실제 offline이 되면 B의 선택과 캐시는 유지하고 경비 내용 대신 제한 안내를 보여 줍니다.
   2. 실제 online으로 돌아오면 B의 경비를 다시 조회하며, 성공 전에는 이전 내용을 공개하지 않습니다.
