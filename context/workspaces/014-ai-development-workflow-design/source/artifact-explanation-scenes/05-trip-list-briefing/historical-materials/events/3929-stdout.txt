# 문제·목표·범위

현재 제품은 일반적인 화면·feature·data·repository 역할 분리와 재사용 기반을 갖추고 있다. 한편 작은 처리 주변에 반복 주석·로그·catch가 붙고, 비슷한 처리 방식이 다르거나 이름·설정·주석과 실행 의미가 어긋나 독자가 값·조건·타입과 설계 이유를 다시 추적해야 하는 부분이 있다. 폼과 저장 후 처리에도 비슷한 책임이 서로 다른 위치에 놓여 있다.

목표는 기존 기능과 유효한 역할 분리를 유지하면서 코드를 이해하고 수정하는 부담을 줄이는 것이다. 비슷한 처리는 공통된 방식으로 이해할 수 있게 하고 필요한 차이는 이유가 드러나게 한다. 이름·주석·타입·설정은 실제 동작과 책임을 설명해야 한다. 표면 표현만 정리하는 데 그치지 않고, 컴포넌트 안의 복잡한 흐름과 여러 메서드·소비 지점에 걸쳐 같은 책임을 추적하고 수정해야 하는 부담도 실제 관련 범위에서 해소한다.

사용자가 선택한 방향은 **리팩토링 우선, 큰 구조보다 바텀 요소부터**다. 바텀은 이름·조건식·기본값·값 변환·작은 함수·타입 등 가까운 코드 요소를 먼저 본다는 뜻이며 개선 깊이의 상한이 아니다. 이 방향은 눈에 띄는 몇몇 대표 지점만 고치고 전체 개선을 끝내는 것을 막고, 분석과 현재 코드에서 근거가 확인된 고칠 수 있는 부분을 가능한 한 폭넓게 살피기 위해 선택했다. 작은 요소를 하나씩 해결하면서 반복 패턴을 확인하고, 근거가 있을 때 컴포넌트 내부 책임과 여러 경로에 걸친 연결 부담의 정리로 이어간다. 특정 디렉터리의 전수 개편, 전면 통일이나 큰 구조 개편을 목표로 추가하지 않는다.

사용자가 인터뷰에서 밝힌 기대에 따르면 콘솔·불필요한 주석 정리는 기본이고, 분석에서 드러난 컴포넌트 내부의 복잡한 흐름도 전반적으로 다뤄져야 한다. Schedule 응답처럼 같은 책임이 여러 경로에 분산되어 생기는 연결 부담도 이 Spec을 수행한 결과로 해결돼 있어야 한다. 이는 모든 Ticket이나 변경을 크게 만들거나 모든 후보를 무조건 수정한다는 뜻이 아니라, 몇 개의 특징적인 수정만으로 끝내지 않고 작은 범위와 연결된 핵심 부담을 하나씩 검토해 해소하거나 남기는 이유를 설명한다는 완료 기대다.

포함 범위는 client·server·schema·UI의 코드 표현, 함수 내부 흐름, 기존 계약을 유지하는 타입·검증 정리, 의미가 같은 중복, 폼·컴포넌트·hook의 내부 책임이다. [전체 후보](../analysis-items.md)에 기존 분석과 추가 관찰을 유지한다. 후보는 채택 시 원자료와 현재 코드를 대조하며 무조건 변경할 목록이 아니다.

README 개선, 신규 기능 전반, 폴더·계층 재편 자체, 버그 전체 수정과 하네스 개편은 이 Work의 목표에 포함하지 않는다. 공개 동작·오류 계약을 바꾸어야 하는 후보는 기대 동작과 수정 범위를 명시한다. Schedule 주변에서 확인한 서버 오류 처리의 전면 공통화는 server error envelope뿐 아니라 client API의 오류 변환과 UI 표시까지 함께 재검토해야 하므로 이번 단계에서 제외한다. 알려진 결함은 잘못된 동작을 영구 보존할 근거가 아니라 직접 관련된 범위의 선행 조건 또는 제외 경계다.

2026-09-15~16에 사용자는 [Ticket 06](../tickets/06-app-startup-lifecycle.md)의 네트워크 관측·정책·실제 소비 연결을 먼저 수행하고, 직접 필요한 수정은 003으로 분리하지 않고 여기서 함께 하기로 선택했다. 이 범위에서는 unknown 상태, 비활성 여행 제한·복구 UX, Router 중앙 차단과 기존 오류 안내, 화면용 debug override 분리를 구현한다. 기존 온라인 비활성 여행의 Remote 경로를 막는 대상 분기·Local 선조회 결함도 함께 정상화한다. 이 선택은 모든 버그나 sync·cleanup 내부 문제를 흡수하는 허용이 아니며, 상세 경계와 완료 조건은 Ticket 06이 소유한다. [합의 기록](../../../records/2026-09-16-01-network-policy-and-implementation-boundaries.md)에 선택 이유가 있다.

Ticket 06의 앱 준비에서는 사용자가 DB 실패 진입 차단·데이터 삭제 없는 재시도, 인증 복원 실패의 로그인 진입, 정상 서버 목록에서 선택한 여행이 제거된 경우 다른 여행 전환, 진행 중 pending cleanup을 기다리는 로그아웃/탈퇴를 채택했다. 후속 논의에서 진행 중 sync도 종료를 기다린 뒤 서버 세션과 DB를 비우도록 사용자가 추가로 선택했다. 이 공개 동작의 변화와 앱 전체 준비를 `application`으로 분리하는 책임 정리, sync 시작 조건·Debug 우회 제거는 이번 범위에 포함한다. 전면 계층 재편·sync 전체 취소·SQL migration·cleanup 내부 보존 계약까지 확장하는 허용은 아니다. [현재 계약](../tickets/06-app-startup-lifecycle.md)과 [선택 근거](../../../records/2026-09-18-02-app-initialization-and-style.md)를 함께 적용한다.

Ticket 06의 인증 범위에는 SecureStore 세션 기록, 명시적인 인증 상태와 초기 복원 수명, 같은 계정 활성 여행의 Local CRUD 지속, 모든 로그인 진입의 계정 경계와 이전 세션의 늦은 응답 방어를 포함한다. 재로그인은 같은 계정의 인증만 복구하며 다른 계정 전환은 명시적 로그아웃으로 로컬 데이터·큐·인증을 정리한 뒤 진행한다. 인증 만료에 별도 로컬 이용 기한을 두지 않는다. 기존 인증 구현을 기반으로 실제 apiClient의 갱신·재시도·응답·오류 전달과 저장 실패의 상태 정합성을 보완한다. 핵심 정책과 직접 연결 결함의 보완 구현은 반영됐고, Ticket 06의 나머지 네트워크 화면 연결과 실제 기기 검증·사용자 수락은 남아 있다. 다중 기기 제어·원격 세션 회수와 로그아웃 중 앱 강제 종료 뒤 정리를 재개하는 장치는 제외한다. [인증 결정 과정](../../../records/2026-09-18-04-auth-session-policy-and-decisions.md)과 Ticket의 후속 실행 정의를 함께 적용한다.

현재 진행과 다음 행동은 [state](../../state/index.md), 실행 범위와 개별 결과의 진입점은 [Ticket 색인](../tickets/index.md)이 소유한다. 최초 방향의 원문은 [사용자 발췌](../../../source/user-direction.md), 목표 보강에 사용한 분석은 [보존본](../../../source/codebase-analysis/README.md)에 있다. 사용자는 source를 읽어 배경을 보강하되 무조건 따르지는 말라고 했고, 보강된 목표를 수용했다. 현재 목표와 변경 판단은 이 Spec을 기준으로 한다.
# 품질·완료 판단

각 실행 범위의 완료에는 동작 보존 근거와 실제 코드 개선 근거가 모두 필요하다. 테스트 통과는 개선 효과의 증거를 대신하지 않는다. 줄 수·함수 분리 개수·테스트 개수·coverage 숫자만으로 가독성 개선을 판정하지 않는다.

## 동작 보존 확인

리팩토링 전 코드에서 기존 테스트를 활용하고 필요한 테스트를 추가·실행하여 기준 결과를 확인한다. 수정 후에는 같은 테스트와 관찰 조건으로 비교한다. 테스트는 확인된 계약과 결과에 기대값을 두며 구현을 복제하지 않는다. 보존 계약을 깨뜨리는 변경에는 실패하면서 내부 함수 분리나 이름 변경만으로 불필요하게 깨지지 않도록 구성한다.

실패하면 구현과 테스트 중 원인을 확인하고 통과를 위해 기대값부터 바꾸지 않는다. 변경 전 버그나 불명확한 동작을 정답으로 고정하지 않으며 [보존 계약](03-concepts-and-contracts.md)의 경계에 따라 처리한다.

검증 범위는 변경의 영향에 맞게 고른다.

- 단순 이름·주석·저위험 표현은 전후 diff·사용처·관련 타입/린트로 확인할 수 있다. 구현을 따라 쓰는 새 테스트를 만들지 않는다.
- 조건·변환·검증·계산은 결과를 갈라놓는 관련 입력과 경계값으로 확인한다.
- 폼·비동기·저장 후 처리는 관련 상태 변화와 연결된 부작용까지 확인한다.
- 저장·동기화·정리는 관련 데이터와 부작용을 확인할 통합 검증을 선택하고, 중간 실패나 미전송 데이터가 관련되면 그 조건을 포함한다.

mock이나 함수 반환값 확인만으로 실제 연결이나 데이터 보존을 증명했다고 말하지 않는다. 자동화하기 어려운 부분은 재현 조건과 관찰 결과를 남기는 수동 검증을 사용하고 미확인을 밝힌다. 구체적인 사례·도구·실행 방법은 Ticket 또는 실행 범위에서 정한다.

## 개선 효과 확인

수정 전에 무엇을 해석하거나 추적해야 했으며 무엇이 명확해져야 하는지 정하고, 수정 후 그 기준으로 코드를 비교한다. 사후 소감만으로 개선을 주장하지 않는다.

- 값·조건·함수의 실제 의미와 책임을 이름·타입·가까운 코드로 이해할 수 있다.
- 반복 해석·불필요한 우회·함께 맞춰 수정할 위치가 줄어든다.
- 유사 처리의 공통점과 필요한 차이가 읽히고 차이의 이유가 숨겨지지 않는다.
- 간접 호출이나 범용 옵션을 늘려 읽기·수정 부담을 다른 위치로 옮긴 결과를 자동으로 개선으로 보지 않는다.

예를 들어 같은 통화 강조 조건을 두 곳에서 해석해야 했다면, 변경 후 조건의 의미가 정확한 이름으로 드러나고 두 사용처가 그 판단을 함께 쓰는지 확인한다. 이름만 추가하고 더 많은 함수를 따라가게 됐다면 개선 여부를 다시 판단한다.

## 결과와 전체 완료

각 범위에는 실제 실행 조건과 결과, 동작 보존 및 개선 효과의 근거, 기존 실패와 새 회귀의 구분, 남은 문제와 미확인을 남긴다. 부족하면 보완한다.

사용자가 채택한 진행 방식에 따라 개별 Ticket의 결과와 전체 분석 관점의 검토 범위를 함께 관리한다. [기존 후보](../analysis-items.md)와 [추가 조사·후속 범위](../additional-research.md)를 [Ticket](../tickets/index.md)과 연결해 각 관점·후보에서 확인한 코드 범위와 남은 범위를 찾을 수 있게 한다. 한 Ticket의 이름·조건 개선을 해당 관점 전체의 검토 완료로 보지 않는다. 다룬 범위에는 개선 내용과 이유, 변경 없이 유지한 이유, 버그 수정으로 분리한 부분, 보류·미확인을 남긴다. 실행하며 이 연결을 보완하되 전체 후보의 Ticket 배치를 먼저 끝내야 실행할 수 있다는 일괄 선행 조건으로 두지 않는다.

전체 완료를 보고할 때에는 어떤 사소한 문제를 끝냈고 어떤 개선 주제를 찾아 살폈는지, 무엇이 남았는지를 함께 제시한다. 단순한 항목 나열에 그치지 않고 이미 구체화한 동작 보존·개선 효과·범위 기준에 비추어 결과가 왜 충분한지 설명해야 한다. 사용자는 이 정도의 보고 방향을 기대한다고 밝혔지만 정확한 검증 방법과 충분성 판정 방식은 아직 확정하지 않았다.

이번 인터뷰와 재조사에서 확인된 Ticket 03의 최초 적용은 표시값 중복을 한 곳으로 모아 Ticket의 좁은 맡은 결과를 충족했지만, 저장 용량 처리의 내부 책임과 React 연결 부담을 그대로 남겼다. 실행 단위의 문구를 충족했다는 보고만으로 Spec의 개선 깊이나 전체 완료를 입증하지 않는다.

이번 문서 반영으로 Verify receipt나 machine status를 변경하지 않는다. 가독성 판단·다음 행동·사람의 수락은 machine status와 분리한다.

Ticket 06의 네트워크 범위는 합의된 동작 변경과 기존 정상 동작 보존을 함께 검사한다. 변환·Router 단위 검사 외에 캐시가 남은 제한 화면, 폼 입력 유지, 실제/강제 네트워크 상태의 요청 분리와 중복 sync 방지까지 소비 연결을 확인한다. 기존 버그가 통과하던 baseline만으로 새 정책을 입증하지 않는다. 세부 사례는 Ticket 06에 두며 그 검사로 실제 SQLite 원자성·sync 내부 재시도·실기기 네트워크 빈도까지 검증했다고 하지 않는다.

인증 보완에서는 인증 interceptor만 붙인 client와 실제 apiClient의 응답 가공까지 연결한 검사를 구분한다. 자동 갱신 후 원래 요청의 반환 shape·오류 의미, 동시 갱신 공유, 저장 실패 뒤 재시도와 이전 세션 응답 차단을 함께 확인한다. [추가 검사](../../../records/2026-09-19-02-auth-review-checks.md)에서 기존 235개 검사 통과와 연결 결함 5개를 함께 관찰했고, 보완 뒤 전체 client Jest 25개 suite·249개 test가 통과했다. 이 결과에는 실제 apiClient 응답·오류, 저장 실패 재시도, 계정 불일치 보존, 독립 DB write, FAILED 재시도가 포함된다. ### 홈 요약: 표시 소유권과 기존 정책·조회 결과 재사용

홈의 일정·경비 숫자 칸에 완성된 오류 UI를 각각 주입하던 구조를 카드 내부 TripSummary가 상태별 배치·문구·버튼을 소유하도록 바꿨다. 제품 코드와 테스트는 `e54fe42`에 저장했다. MainTripSection은 기존 일정·경비 조회 훅의 ReadQueryView를 그대로 사용하고 성공한 데이터만 집계하며 실행 callback을 연결한다. 별도 상태 체계·변환 훅·복구 추적은 없다. 기존 useAppPolicy·조회 조합·Router의 판단과 실행 경계를 유지한다.

### 네트워크 안내 후속 작업 1-A — 활성 여부 최초 확인
