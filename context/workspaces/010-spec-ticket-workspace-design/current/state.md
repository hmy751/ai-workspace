# Spec·Ticket 설계 state

마지막 갱신: 2026-09-07

## 현재 상태

사용자는 Spec·Ticket을 사용하는 방향으로 설계를 구체화하고 있으며, 아직 Spec 구성요소와 적용 방식은 정하지 않았다. 이 대화 처음부터의 논의와 작업을 009에서 독립된 010으로 분리하도록 요청했다. 현재는 그 종합 기록과 연구 Workspace를 구성한 단계다.

## 확인한 조사와 판단

- 공개 자료를 비교해 Spec의 범위·수명·문서 구성과 Ticket의 분해 규율이 도구마다 다름을 확인했다.
- Reference의 goal/current와 Spec이 겹치는 내용, Recover·Maintain·Verify·생성·이식의 실제 접점을 조사했다. 초기 상세 근거는 009의 09·10 기록에 그대로 있다.
- 초기 임시 fixture에서 goal 미등록 변경은 receipt freshness에 반영되지 않고, 링크만 있는 Spec 본문은 Recover 입력에 포함되지 않으며, basis로 등록한 Spec의 변경은 stale이 됨을 확인했다. 당시 관련 회귀 검사 5개가 통과했다. 이번 기록 작성에서 제품 테스트를 재실행한 결과는 아니다.
- 기존 memory/state 선택 이유를 기록·Git 이력으로 조사하고 별도 리뷰를 받았다. 지속 맥락의 책임이 빠져 있던 memory 제거 제안은 보류했다.
- 공유 Spec 제안은 사용자 조건에 따라 제외했다. Ticket을 진행 상태가 있다는 이유만으로 state에 배치하던 판단도 수정했다.
- 개념 트레이드오프에 대한 새 맥락의 제3 리뷰를 받았다. Spec·Ticket 사용의 합당한 이유는 있지만, Project·Work의 추가 관리 비용이 충분히 관리되는 Spec-driven 운영보다 유리하다는 실제 비교 근거는 없다는 판단을 얻었다.
- 전체 목표를 이어갈 책임과 별도의 Work 단위를 둘 필요는 구분해야 한다. 이 조건부 평가가 현재 판단이며 도입 반대나 전체 설계 승인으로 쓰지 않는다.

## 다음 논의

다음에는 Spec에 담을 구성요소와 그 역할을 정한다. goal·scope·requirements·constraints·acceptance·design은 이미 나온 후보지만, 그 이름을 곧바로 필수 파일 목록으로 확정하지 않는다.

구성요소를 정할 때 함께 결정할 것은 다음과 같다.

1. Spec이 어떤 작업 범위를 정의하며, Workspace 전체 목표와 같은 범위인지 일부인지.
2. 기존 goal·constraints의 어느 의미를 Spec이 소유하고 어떤 지속 맥락은 밖에 남기는지.
3. Ticket의 입력·실행 범위·완료 조건·의존 관계와 진행 정보의 책임.
4. 새 세션과 개별 실행자가 무엇을 읽고, 실행 결과로 기준이 바뀌면 누가 무엇을 갱신하고 재판정하는지.

독립 스냅샷 조건은 유지한다. Spec-driven 대비 별도 Project·Work의 이득·비용을 설명하는 질문도 설계 기준으로 이어간다. 추가 비교 실험이나 새 검토 절차를 필수 gate로 합의한 것은 아니다.

## 기록과 구현의 구분

[세션 종합 기록](../records/2026-09-07-01-session-synthesis.md)은 처음부터의 조사·제안·정정·리뷰를 보존한다. 현재 단계에서 최종 Spec, 실제 Ticket, Reference 구조·코드·schema 변경은 없다. 010 생성과 active 진입점 전환은 연구 기록 분리이며 runtime activation이나 설계의 사람 acceptance가 아니다.
