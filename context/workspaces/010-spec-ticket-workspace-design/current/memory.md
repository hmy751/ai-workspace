# Spec·Ticket 설계 memory

마지막 갱신: 2026-09-07

## 목표

스킬 작성·작업 분해·인계에서 Spec과 Ticket을 실제 개념과 용어로 사용할 수 있도록, Workspace/current와의 관계 및 관리 책임을 사용자와 정한다. 동시에 충분히 관리되는 Spec-driven 운영과 비교해 Project·Work를 별도로 두는 선택의 이득과 비용을 설명한다.

정의와 운영 책임이 정리되고 사용자가 선택해야 할 중요한 지점이 구체화되는 것이 현재 설계 작업의 목적이다. Spec 구성요소와 Reference 구현은 아직 확정되지 않았다.

## 사용자에게서 이어받는 조건

- 외부 개발 스킬·자료의 Spec·Ticket을 매번 자체 표현으로 번역하는 부담을 줄이려는 목적이 있다. 특정 spec-driven 체계 전체를 그대로 도입하거나 개념을 잘게 나눠 새로운 이름의 대체물을 만드는 방향은 아니다.
- 기존 구조는 필요하면 수정할 수 있다. 과거 Work-first 선택이나 외부 분석 문서를 Spec 도입을 막는 규칙으로 사용하지 않는다.
- 다른 Workspace에서 Spec을 새로 작성하거나 가져와도 Workspace별 독립 스냅샷 경계를 유지한다. 공유 Spec의 Workspace 간 자동 전파·상호 갱신은 채택하지 않는다.
- 개별 Ticket·테스트·작업의 완료가 전체 목표 달성을 대신하지 않아야 한다. 과거 Spec과 구현을 재검토 불가능한 현재 전제로 취급하지 않는다.
- Spec-driven 대비 Project·Work 선택의 타당성은 개념과 운영의 이득·비용으로 비교한다. 우리 구현의 수정 난이도가 그 질문을 대신하지 않는다.
- 사용자가 010으로 분리하라고 한 범위는 이 대화 처음부터의 논의·조사·작업 전체다. 최근 제3 리뷰만 보존하는 것이 아니다.

## 현재의 설계 후보와 미결정 경계

- 현재 goal·범위·완료 기준·constraints는 이미 Spec 역할 일부를 수행한다. Spec을 도입할 때 같은 요구를 두 곳에서 독립적으로 관리하지 않도록 책임을 정해야 한다.
- 기존 memory는 작업 단계가 바뀌어도 유효한 목표·기준·판단·제약·계속 영향을 주는 결과를, state는 현재 진행·막힘·근거 해석·다음 행동을 맡는다. memory의 역할에는 Spec에 자연스럽게 들어가지 않는 지속 맥락도 있다.
- memory를 유지하며 그 아래 spec/과 tickets/를 두는 것이 현재 논의 후보다. Spec 구성요소를 하위 파일로 나눌 수 있지만 파일 목록과 필수 여부는 결정하지 않았다.
- Spec과 Ticket의 현재 적용되는 정의를 memory에, 진행과 결과의 현재 해석을 state에 두는 후보를 논의했다. Ticket 상태를 반드시 별도 파일에 두어야 한다는 보편 규칙은 아니다.
- 현재와 과거는 기존 current/records 책임으로 구분한다. Ticket 완료만으로 자동 이동시키지 않고 현재 후속 판단에 필요한 의미를 판단한다.
- Workspace와 Spec의 범위·개수, 전체 목표의 정의 위치, 소비자별 읽기, 변경 시 갱신·전달·기존 결과 재판정은 미결정이다. Workspace 내부의 매 수정까지 불변 스냅샷으로 보존할지도 아직 정하지 않았다.

## 비교에서 유지할 판단

Spec은 요구하는 결과를 명시하고, Ticket은 실행할 일을 식별·배분·추적한다. 이 연구의 Project는 여러 작업이 공유하는 맥락의 범위이고 Work는 한 목표를 추구하면서 판단과 진행을 이어가는 범위다. 네 개념은 완전히 같은 자리를 놓고 경쟁하는 대안이 아니다.

Spec의 불변성, Ticket의 한 세션 크기·완전한 구현 조각은 특정 운영 방식의 선택이다. 판단 변화 관리가 Work라는 이름만의 기능인 것도 아니다. Spec-driven 운영에도 공통 맥락·변경 이유·상위 목표 판단이 있을 수 있으므로 그런 기능이 없는 상대와 비교하지 않는다.

Spec·Ticket 사용에는 요구 명시·실행 인계와 공통 용어 사용의 이득이 있다. 별도 Project·Work 관리의 조건부 이유는 설명되지만, 추가 관리 비용보다 실제 효과가 크다는 비교 증거는 아직 없다. 지속 판단이 필요하다는 사실과 별도 Work 단위가 필요하다는 주장을 구분한다.

## 근거와 작업 경계

[세션 종합 기록](../records/2026-09-07-01-session-synthesis.md)이 사용자 핵심 발췌, 제안·정정 과정, 조사 및 리뷰 근거를 연결한다. 초기 코드 조사는 Reference revision 5e45310 기준이다. 그때의 테스트 결과를 새 설계나 현재 제품 전체의 검증으로 사용하지 않는다.

외부 연구는 사용자가 지정한 memory-harness-research의 관련 분석만 선택해서 읽는다. 다른 Desktop 저장소로 조사 범위를 넓히지 않는다. 이번 문서 작성은 Reference·외부 연구 저장소·자동 Maintain 설정의 변경을 포함하지 않는다.
