# Spec·Ticket 설계 memory

마지막 갱신: 2026-09-08

## 목표

스킬 작성·작업 분해·인계에서 Spec과 Ticket을 실제 개념과 용어로 사용할 수 있도록, Workspace/current와의 관계 및 관리 책임을 사용자와 정한다. 동시에 충분히 관리되는 Spec-driven 운영과 비교해 Project·Work를 별도로 두는 선택의 이득과 비용을 설명한다.

정의와 운영 책임이 정리되고 사용자가 선택해야 할 중요한 지점이 구체화되는 것이 현재 설계 작업의 목적이다. Spec 구성요소·구성 이유·예시는 2026-09-08 채택했으며, Workspace/current와의 통합 및 Reference 구현은 아직 남아 있다.

## 사용자에게서 이어받는 조건

- 외부 개발 스킬·자료의 Spec·Ticket을 매번 자체 표현으로 번역하는 부담을 줄이려는 목적이 있다. 특정 spec-driven 체계 전체를 그대로 도입하거나 개념을 잘게 나눠 새로운 이름의 대체물을 만드는 방향은 아니다.
- 기존 구조는 필요하면 수정할 수 있다. 과거 Work-first 선택이나 외부 분석 문서를 Spec 도입을 막는 규칙으로 사용하지 않는다.
- 다른 Workspace에서 Spec을 새로 작성하거나 가져와도 Workspace별 독립 스냅샷 경계를 유지한다. 공유 Spec의 Workspace 간 자동 전파·상호 갱신은 채택하지 않는다.
- 개별 Ticket·테스트·작업의 완료가 전체 목표 달성을 대신하지 않아야 한다. 과거 Spec과 구현을 재검토 불가능한 현재 전제로 취급하지 않는다.
- Spec-driven 대비 Project·Work 선택의 타당성은 개념과 운영의 이득·비용으로 비교한다. 우리 구현의 수정 난이도가 그 질문을 대신하지 않는다.
- 사용자가 010으로 분리하라고 한 범위는 이 대화 처음부터의 논의·조사·작업 전체다. 최근 제3 리뷰만 보존하는 것이 아니다.

## 채택한 Spec 구성과 설명 방식

1. **문제·목표·범위**: 사용자가 얻을 결과와 이번 Spec이 맡는 범위.
2. **요구 동작과 대표 사례**: 제품에서 보존해야 할 의미와 그 차이를 드러내는 사례.
3. **핵심 개념·입출력 계약**: 작업을 나누고 전달해도 같은 뜻으로 다룰 대상·정보·결과.
4. **품질·완료 판단**: 제품 원자료와 실제 동작, 변경 전후 코드의 비교 및 확인한 근거에 맞는 완료 판단.
5. **제약·현재 설계·가정**: 지킬 조건과 현재 선택한 방법, 그 이유·불확실성을 구별해 판단의 연속성을 유지.

[구성요소와 구성 이유](../output/spec-components-and-rationale.md), [여행 상품 답변 예시 Spec](../output/spec-example-travel-answer.md)을 독립 문서로 유지한다. 후속 설계에서 Spec의 다섯 구성요소는 `memory/spec/` 아래 각각의 Markdown 파일로 두기로 했다. 각 파일의 분량은 작업에 맞게 작성한다. 예시의 부분 답변·전체 오류 거절·필드·revision·30초·20개는 해당 예시의 동작 또는 제안으로서, 모든 Spec의 필수 요구나 실제 제품 계약으로 승격하지 않는다.

구체적인 요구·입출력·평가는 실행에 필요한 의미를 분명하게 한다. 그 구체성을 무조건 줄이지 않으며, 임시 선택이 확정 제약으로 굳지 않도록 이유와 적용 범위를 남긴다. 실제 모델 인터페이스나 테스트가 있다는 것만으로 핵심 수행을 완료로 보지 않는다. 구현 누락과 Spec 가정의 부족을 구별하며, 결과가 부족하다는 이유만으로 전체 목표부터 변경하지 않는다.

리뷰를 설명할 때는 기존 문서에서 쓰던 ‘제품에서 보존해야 할 의미’, ‘판단의 연속성’, ‘제품 원자료와 실제 동작의 비교’, ‘변경 전후 코드의 비교’를 초안의 구체 항목·수정 이유와 연결한다. 사용자의 이해 요청을 추상적 요약이나 상세 분량 증가로 대신하지 않는다. 실행용 예시 본문과 구성 설명을 한 문서에 주석처럼 섞지 않는다.

## 후속 설계에서 두는 가정

일단 Spec 하나가 생긴다는 전제로 논의를 이어간다. Workspace의 goal·제약 등을 Spec이 맡는 방향을 구체화하기 위한 가정이다. Workspace마다 반드시 하나만 허용하거나 별도 Spec마다 새 Workspace를 강제하는 운영 규칙은 정하지 않는다. 사용자는 별도 Spec이 필요하면 다른 Workspace에서 구성하며 진행할 수 있다고 보았지만, 이를 너무 타이트하게 정하지 말라고 명시했다.

관련 발화와 정정은 [Spec 하나를 전제로 이어가는 논의](../records/2026-09-08-02-workspace-spec-scope.md)에 있다.

## Spec의 위치와 유지 방식

memory 유지·제거와 records/current 경계를 재검토한 뒤 사용자는 **memory를 유지하고 Ticket의 정의·진행을 함께 적는 방향**을 선택했다. [최신 결정](../records/2026-09-08-07-memory-ticket-placement-decision.md)에 사용자 원문과 선택 범위가 있다. Spec 구성·기존 goal/constraints 대체·project-context 유지·독립 스냅샷 조건은 그대로 이어간다.

Spec은 memory에 둔다. 필요하면 수정·갱신할 수 있지만, 진행 상황을 계속 반영하는 state와는 달리 해당 Workspace의 작업 기준으로 유지하는 문서로 본다. Workspace와 함께 스냅샷처럼 남으며, 후속 작업과 Project의 변화에 맞춰 장기적으로 계속 최신화해야 하는 문서로 보지 않는다.

이는 Spec을 수정 불가능하게 만든다는 뜻이 아니다. 필요한 수정은 가능하고, Workspace별 독립 스냅샷 경계는 유지한다. 사용자가 이 위치와 이유를 선택한 발화는 [후속 논의 기록](../records/2026-09-08-02-workspace-spec-scope.md)에 있다.

## 기존 memory와의 관계

- 기존 `01-goal.md`의 목표·완료 기준과 `02-constraints.md`의 작업별 제약·결정은 Spec이 대체한다. 같은 정의를 별도 goal·constraints 파일에서 다시 관리하지 않는다.
- 02에 있던 source·records·output 등의 공통 관리 규칙은 Workspace 운영 지침과 원래 책임 문서가 맡는다. 그 규칙을 Spec에 옮겨 반복하거나 02를 유지할 이유로 삼지 않는다.
- 기존 `03-project-context.md`는 Spec의 책임이 아니므로 memory에서 유지한다.
- Spec의 다섯 구성요소는 각각 Markdown 파일로 둔다. 이 결정은 설계에 반영했으며 Reference의 실제 파일은 아직 변경하지 않았다.

## Ticket·state·records의 관계

- Ticket은 `current/memory/tickets/`에 둔다. 작업 정의와 진행·막힘·결과 등 해당 작업을 함께 이해할 내용을 같은 Ticket에 적고 필요한 때 갱신한다.
- 구성은 Matt의 `to-tickets`를 기본으로 삼되 열어 둔다. 제목·만들 동작·완료 조건·선행 Ticket·상태 등을 참고하고, 작업에 필요한 내용으로 조정한다. Main이 제안한 네 부분이나 Matt의 항목·상태 이름을 고정 필수 schema로 삼지 않는다. [후속 사용자 선택](../records/2026-09-08-07-memory-ticket-placement-decision.md)에 근거를 남겼다.
- memory를 변경이 적은 문장만 담는 곳으로 해석해 Ticket의 현재 상태를 억지로 떼어내지 않는다. 이는 기존 memory/state 내용 구분을 일부 조정한 선택이다.
- state는 Workspace 전체의 현재 상황·판단·다음 행동을 맡는다. 필요한 Ticket 상황을 종합해서 설명할 수 있으며, Ticket별 상태를 별도 정본으로 다시 관리할 필요는 없다.
- Ticket은 자연스럽게 유지하고, 상세 이력·변경 이유·보존할 내용은 필요에 따라 records에 둔다. 완료나 현재 영향 유무만으로 자동 이동·삭제하는 규칙은 정하지 않는다. 직전 예시의 `records/tickets/` 폴더와 구체적인 이동 방식도 필수로 정한 것이 아니다.
- records에서 지금 적용할 의미를 골라 현재 문서에 유지하는 역할은 이어간다. 필요한 의미를 records 링크만으로 대신하거나 모든 상세 과정을 current에 누적하지 않는다. 이 구별을 이유로 함께 읽어야 할 Ticket 내용을 기계적으로 분리하지 않는다.
- [제3 리뷰](../records/2026-09-08-05-memory-ticket-independent-review.md)의 약한 제거 선호는 당시 판단 자료로 남긴다. 사용자는 이후 memory 유지와 Ticket 정의·진행 통합을 선택했으며, 실제 운영 효과까지 검증된 것은 아니다.

## 문서 유지와 작업 조율

사용자는 [작성 책임 독립 리뷰 뒤의 확인](../records/2026-09-08-10-spec-ticket-authorship-independent-review.md)에서 기존처럼 Maintain은 기록을 맡고 조율은 Main이 자연스럽게 한다고 정리했다. 기존 역할을 유지하면서 기록 대상에 Spec·Ticket을 포함하는 방향이며 새 책임 배분 체계를 만드는 것이 아니다.

- Maintain은 대화와 결과를 이해해 Spec·Ticket·state에 필요한 내용을 기록하고 갱신한다. 무엇을 남기고 어떻게 반영할지 판단하는 기존 동작을 이어간다.
- Main은 필요한 설계·작업 분해와 위임, 실행 결과의 회수, 다음 행동으로 이어가는 작업 조율을 맡는다. 이 조율을 Maintain에 넘기지 않는다.
- 이 구분은 Main만 Spec·Ticket 파일을 작성할 수 있다는 규칙이나 새 승인·조율 절차가 아니다. 개별 실행자의 구체적인 읽기·쓰기 범위는 실제 작업에 맞게 열어 둔다.

## Workspace 진입과 실행자 범위

사용자는 전체 Spec·Workspace를 맡는 주체가 Ticket을 읽고, 개별 Ticket 실행은 독립 에이전트나 세션이 맡을 것으로 구상했다. [읽기·결과 전달 구상](../records/2026-09-08-08-workspace-ticket-execution-direction.md)을 기준으로 전체 담당과 개별 실행자의 필요한 맥락을 구별해 논의를 이어간다. 이는 모든 Ticket 위임이나 매번 새 세션을 강제하는 규칙이 아니며 쓰기 권한·자동화 방식은 아직 정하지 않았다.

후속 확인에서는 기존 Workspace 진입이 memory와 state의 현재 맥락을 함께 읽는다는 점을 기준으로, goal·constraints를 대체하는 Spec 전체도 기본 진입에 포함하는 방향으로 정리했다. 다만 사용자는 Ticket 실행자의 범위는 열어 두라고 했다. 앞선 실행자별 읽기·실행 설명은 구상이며, Spec 전체 또는 일부를 반드시 읽힌다는 정책이나 고정 실행 단위를 정하지 않는다. 실제 위임에 맞게 입력과 범위를 정할 수 있다. 현재 Recover는 하위 폴더를 자동으로 읽지 않으므로 Spec 폴더 지원은 실제 적용 단계의 변경이다.

Ticket 구성은 Matt를 참고해 실제 작업에 맞춰 조정하며, 항목을 모두 확정하는 절차를 먼저 요구하지 않는다. 개수 제한이나 새 Workspace 생성 조건을 먼저 규칙으로 만들지 않는다. 모든 수정에 별도 불변 사본을 남기는 의무도 두지 않는다. 실제 적용의 남은 일은 [state](state.md)에서 이어간다.

## 비교에서 유지할 판단

Spec은 요구하는 결과를 명시하고, Ticket은 실행할 일을 식별·배분·추적한다. 이 연구의 Project는 여러 작업이 공유하는 맥락의 범위이고 Work는 한 목표를 추구하면서 판단과 진행을 이어가는 범위다. 네 개념은 완전히 같은 자리를 놓고 경쟁하는 대안이 아니다.

Spec의 불변성, Ticket의 한 세션 크기·완전한 구현 조각은 특정 운영 방식의 선택이다. 판단 변화 관리가 Work라는 이름만의 기능인 것도 아니다. Spec-driven 운영에도 공통 맥락·변경 이유·상위 목표 판단이 있을 수 있으므로 그런 기능이 없는 상대와 비교하지 않는다.

Spec·Ticket 사용에는 요구 명시·실행 인계와 공통 용어 사용의 이득이 있다. 별도 Project·Work 관리의 조건부 이유는 설명되지만, 추가 관리 비용보다 실제 효과가 크다는 비교 증거는 아직 없다. 지속 판단이 필요하다는 사실과 별도 Work 단위가 필요하다는 주장을 구분한다.
