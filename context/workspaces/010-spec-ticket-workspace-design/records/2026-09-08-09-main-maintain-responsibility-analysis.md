# Main과 Maintain의 판단 책임 재검토

날짜: 2026-09-08

상태: **사용자 문제 제기에 따른 분석·제안. 역할 재배치의 채택이나 Reference 변경은 아니다.**

## 논의가 생긴 이유

Main은 동작 설계의 다음 쟁점으로 Spec 변경 판단, Ticket 결과의 전체 Workspace 반영, 기준 변경에 따른 기존 결과 재검토를 제시했다. 이어 목표·요구를 바꾸는 판단은 전체 작업 대화와 Main 쪽에, 지속할 내용의 반영은 Maintain 쪽에 두는 방향을 제안했다. 이는 직전 답변의 요지이며, 확정된 역할 계약이 아니다.

사용자는 다음과 같이 문제를 제기했다.

> 근데 그렇게 되면 다른것도 대부분 main이 맡아야 할것 같은데? 그럼 메인이 맡아야 하는가? 이런것도 분석해야겟네

핵심은 Spec 파일의 수정자를 정하는 데 그치지 않는다. 판단이 필요하다는 이유로 Main에 책임을 몰면 기존 Maintain의 의미 판단까지 Main으로 옮기는지, 전체 작업을 맡는 책임과 개별 판단·실행을 같은 주체에 둘 이유가 있는지를 확인해야 한다.

## 실제 구조와 이전 선택에서 확인한 것

[현재 Maintain 계약](../../../../reference-project/context/work/harness/maintain/README.md)과 [semantic agent 지침](../../../../reference-project/context/work/harness/maintain/workspace-context-maintainer.toml)을 읽었다. Maintain은 처음 Workspace를 이해하고 같은 세션의 사용자 발화·Main 응답을 이어 받으며, 지속할 변화·기존 문서의 책임·모호함·보고 중요도를 판단한다. 명확한 변화는 guarded apply를 통해 별도 Main 승인 절차 없이 반영할 수 있다. 단순한 받아쓰기나 파일 저장 장치가 아니다.

현재 계약은 사용자 대신 목표·설계 기준·acceptance·완료를 결정하지 않고 제품 검증을 직접 수행하지 않도록 한다. 이것이 모든 관련 분석과 실행을 Main 혼자 해야 한다는 뜻은 아니다. 현재 입력·권한으로 Maintain이 책임지는 범위를 정한 것이다.

[007의 동작 근거](../../007-maintain-clean-room-reimplementation/records/2026-08-18-01-clean-room-source-and-behavior-contract.md)는 Maintainer가 세션을 이해하는 에이전트이고 Main을 기다리게 하지 않으며, 명확한 변화는 반영하고 중요한 것은 보고하는 경험을 보존한다. [목적 재기준화](../../007-maintain-clean-room-reimplementation/records/2026-08-19-06-purpose-rebaseline-and-remaining-scope.md)에는 사용자가 diff·test 등을 모두 전달하는 것이 Maintain에 너무 많은 책임을 싣는지 물었던 근거가 있다. 이에 기본 입력을 Workspace Context·사용자 발화·Main 응답으로 두고 제품 검증을 기본 업무에서 뺐다. 따라서 현재 입력의 제한은 우연한 구현 제약만이 아니라 목적과 비용을 비교한 선택이다. 새 필요가 생기면 재검토할 수 있다.

이 연구 저장소에서 Main이 직접 문서를 유지하는 것은 outer root 자동 Maintain이 비활성인 동안의 운영이다. 이를 새 Reference에서도 Main이 모든 갱신을 맡아야 한다는 근거로 삼지 않는다.

## 상황별로 나누면 달라지는 책임

**사용자가 목표나 요구를 분명히 바꾼 경우:** 변경 결정은 이미 사용자에게서 나왔다. Maintain이 의미를 해석해 Spec의 관련 부분과 현재 상태를 갱신하는 데 Main의 별도 재승인을 필수로 둘 이유는 없다. 다만 새 폴더를 지원하는 실제 읽기·쓰기 계약 변경은 필요하다.

**Ticket 실행과 확인 결과가 나온 경우:** 구현·검증은 실제 작업을 맡은 주체가 수행한다. Maintain은 제공받은 결과를 바탕으로 Ticket과 Workspace 상태에 필요한 의미를 반영할 수 있다. Main의 보고만 받았다면 보고된 상태로 남기며 직접 검증한 사실처럼 쓰지 않는다. 정확한 실행자 입력과 직접 쓰기 방식은 아직 정하지 않는다.

**Ticket은 완료됐는데 전체 목표에 필요한 확인이 빠진 경우:** 입력만으로 드러나는 불일치나 미확인은 Maintain도 식별하고 현재 상태에 남길 수 있다. 전체 완료로 기록하지 않는 데 모든 문제를 Main이 먼저 문장으로 정리해야 할 이유는 없다. 그러나 실제 구현·제품을 더 확인해야 해결되는 판단은 그 확인을 수행할 수 있는 작업 주체가 맡아야 한다. 그 주체가 반드시 Main일 필요는 없다.

**실행 결과 때문에 현재 설계나 가정을 바꿔야 할 가능성이 생긴 경우:** 근거를 해석하고 대안을 비교하는 작업과, 채택한 결론을 Spec에 반영하는 작업은 구분할 수 있다. 실제 작업 담당이나 필요한 검토 주체가 판단을 만들 수 있고, Maintain은 확인된 변경과 남은 불확실성을 관련 문서에 반영할 수 있다. 기존 목표 안의 구현 선택까지 매번 사용자 결정으로 올릴 필요는 없지만, 구현 부족을 이유로 사용자 목표나 완료 기준을 조용히 낮추는 일은 어느 AI에게도 자동으로 맡길 수 없다.

이 구분은 새 역할이나 단계의 필수 추가가 아니다. 같은 Main이 둘 다 수행할 수도 있고 다른 실행 주체가 맡을 수도 있다. 문서 이름이나 중요도만으로 수행 주체를 고정하지 않기 위한 비교다.

## 배치의 트레이드오프와 현재 제안

Main이 모든 의미 판단과 갱신 지시를 만들면 작업 맥락을 한 곳에서 대조하기 쉽다. 대신 Main의 응답·컨텍스트 부담이 커지고, 작업 중 놓친 의미를 Maintain이 보완할 여지가 줄어든다. Main을 방해하지 않으면서 맥락을 유지하려던 기존 목적과도 맞지 않을 수 있다.

Maintain이 다음 작업·설계 변경·실제 완료 판정까지 맡으면 Main 부담을 줄일 수 있다. 대신 지금보다 많은 실행 근거와 권한이 필요하고, Main이나 실행자와 별도로 작업 방향을 판단하는 주체가 생긴다. 최신 결정의 전달, 판단 충돌과 반영 시점을 다루는 비용도 생긴다. 현재 response-end 입력만 유지한 채 권한만 넓히는 것으로 해결되지 않는다.

**현재 제안은 Maintain의 기존 의미 판단과 자율 반영을 유지하면서, 실제 작업을 더 수행해야 얻을 판단은 해당 작업을 맡은 주체에 두는 것이다.** 전체 Workspace를 함께 보고 빠진 판단을 연결할 책임은 필요하지만, 그 담당이 모든 분석·실행·갱신을 직접 해야 한다고 정하지 않는다. 중요한지보다 필요한 맥락·근거가 무엇이고 누가 그것을 갖고 있으며 어떤 결정을 맡았는지로 배치한다.

직접 읽은 공유 기준 `ai-system_behavior-responsibility-allocation.md`도 해석·선택, 보장·거부, 권한·승인, 실행·기록을 한 주체에 통째로 몰지 않고 판단 성격과 맥락으로 배치하도록 한다. `ai-system_responsibility-cohesion.md`에 따라 이 비교를 새 에이전트·파일·단계의 의무로 확대하지 않는다. 두 기준의 위치는 `~/.claude/references/`이며 프로젝트 동작의 새 canonical로 복제하지 않는다.

## 다음에 구체화할 것

우선 Spec·Ticket·state 각각을 Main 또는 Maintain 전용으로 배정하기보다, 실제 갱신 장면에서 **입력만으로 현재 의미를 유지할 수 있는지, 추가 작업 판단이 필요한지**를 대조한다. 특히 실행자의 결과가 Maintain에 어떻게 전달되는지, 별도 실행자가 직접 Ticket을 수정하는 경우의 반영 방식은 아직 남아 있다. 이번 분석으로 실행자 읽기·쓰기 범위나 별도 승인 절차를 확정하지 않는다.

이번에는 현재 계약과 007의 선택 근거를 읽고 010의 분석·현재 논의 지점만 기록했다. Reference 코드·prompt·권한·hook과 외부 연구 자료는 변경하지 않았다. 이 역할 배치의 실제 운영 효과를 실험한 결과는 아니다.
