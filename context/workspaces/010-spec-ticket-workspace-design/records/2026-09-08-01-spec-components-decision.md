다섯 구성과 구성 이유, 그 적용 예시를 현재 설계 기준으로 채택했다. Spec·Ticket의 실제 저장 위치, 파일 분할, Workspace와의 범위 관계, runtime 변경까지 채택한 것은 아니다. 예시의 부분 답변 정책·필드 이름·시간제한·평가 규모를 모든 Spec의 공통 요구나 실제 TripProof의 확정 계약으로 승격하지 않는다.

## 3. 구성요소를 판단한 근거

### 원래 문제에서 유지한 판단

사용자는 먼저 01·02 분석을, 이어 03·04와 05의 archive를 제외한 자료를 읽게 했다. 뒤에는 01의 원본인 관점별·시간순 회고도 다시 읽도록 했다. 이 자료들을 Spec 도입을 막는 규칙으로 취급하지 않았다.

[관점별 회고](/Users/hammyeong-yeon/Desktop/memory-harness-research/context/source/07-tripproof-spec-driven-continuity/original/spec-driven-retro-conceptual.md)의 중심 문제는 다음 문장에 드러난다.

> 근본 문제는 아직 안 풀렸는데, 그 주변을 설명하고 측정하고 부분적으로 보완한 코드와 spec만 계속 늘어났다.

이 원문에서 구성요소 판단으로 가져온 내용은 다음과 같다.

- **제품의 수렴**: 개별 기능과 작업이 사용자의 근본 문제를 해결하는 실제 흐름으로 이어져야 한다.
- **성장 가능한 코드**: 제품 개념의 주인이 분명하고, 같은 규칙과 예외를 여러 곳에 덧붙이지 않으며, 다음 변경 위치를 예측하고 잘못된 가정을 교체할 수 있어야 한다.
- **작업의 연속성과 판단의 연속성**: 할 일과 범위뿐 아니라 선택의 이유·불확실성·다시 판단할 근거도 이어져야 한다.
- **Spec에서 분명히 할 것과 구현 중 열어둘 것**: 제품 결과·제품 의미·범위·대표 흐름은 분명히 하되, 실제 코드를 보고 판단해야 하는 내부 구조를 미리 고정하지 않는다.
- **평가의 두 비교**: 제품 원자료와 실제 동작을 비교하고, 변경 전 코드와 변경 후 코드를 함께 본다.

원문에서 특히 다음 두 문장을 판단 기준으로 사용했다.

> 판단의 연속성은 이전 결론을 보존하는 것이 아니다. 왜 그런 결론을 내렸는지, 무엇이 불확실했는지, 어떤 신호가 나타나면 다시 열어야 하는지를 다음 작업까지 이어가는 것이다.

> 제품에서 필요한 결과는 분명히 하되, 실제 코드를 보고 판단해야 하는 것까지 미리 확정하지 않는다.

### 실제 장면이 추가한 구체성

[04 장면 분석](/Users/hammyeong-yeon/Desktop/memory-harness-research/context/analysis/07-tripproof-spec-driven-continuity/04-conversation-scene-analysis.md)의 보존 발췌를 통해 다음 세 장면을 대조했다. 이 문서가 연결한 별도 private JSONL까지 직접 재감사한 것은 아니다.

1. LLM이 자료 의미를 판단하고 서버가 원문 근거를 확인하기로 합의했지만, 구현에는 실제 provider 호출 없이 인터페이스 뒤의 regex 판단이 남았다. 테스트 통과와 기반 구조가 실제 기능 완료처럼 보고됐다. 원문에는 “내가 또 ‘구조를 만든 것’을 ‘기능을 붙인 것’처럼 취급했기 때문입니다”라는 인정이 보존돼 있다.
2. 사용자가 Spec-driven을 금지한 넓은 코드 품질 작업에서도 유효한 리팩터링 세 커밋과 서버 테스트 56개 통과 후 완료를 선언했다. 다시 물었을 때 이미 알고 있던 책임 혼합 등의 문제가 드러났다. 이는 Spec 유무만으로 설명되는 실패가 아니며, 테스트나 부분 개선이 무가치했다는 뜻도 아니다.
3. 내부 후보를 사용자 답변으로 변환하는 책임을 미루고 raw 자료를 화면까지 연결하는 계획이 제안됐다. 실제로 구현된 버그의 증거는 아니다. 화면까지 이어지는 형식만으로 핵심 제품 변환이 수행됐다고 볼 수 없다는 범위 선택의 사례다.

공통점은 목표나 맥락이 문서에 없었다는 것만으로 설명되지 않는다. 작업 선택, 핵심 수행의 연기, 테스트 해석, 완료 선언에서 이미 알고 있던 판단이 실제 행동을 계속 이끌지 못했다.

### 후속 방향 자료의 적용 범위

[05 현재 해결 방향](/Users/hammyeong-yeon/Desktop/memory-harness-research/context/analysis/07-tripproof-spec-driven-continuity/05-judgment-continuity-solution-direction/04-solution-direction.md)에서는 다음 구별을 이어받았다.

- 필요한 상위·다른 맥락을 참고하는 것과 상위 목표나 판단을 수정하는 것은 다르다. 요구가 이미 맞고 구현이 빠졌다면 먼저 구현을 고친다.
- 정보 부족은 목표나 설계가 틀렸다는 증거가 아니다.
- 제품 결과·실제 호환 책임과 당시의 내부 구조 선택을 구별한다. 내부 결정이라는 이름만으로 현재 호환 책임을 제거하지 않는다.
- 판단을 채택했다면 실제 작업 범위·현재 상태·다음 읽기 위치에 반영해야 한다. 영향을 받는 이전 결과는 실제 의존 관계를 따라 확인한다.
- 코드 변경의 부담은 재판단 근거이지, 자동 리팩터링 기준은 아니다.

05의 `reconsider-work` v0는 연구 산출물로 읽었다. 이번 세션에서 설치·호출 절차를 도입하거나 매 Ticket 완료에 별도 평가를 자동 발동하는 결정을 하지 않았다. 이 방향과 이번 Spec의 실제 운영 효과는 아직 검증되지 않았다.

## 4. 외부 Spec-driven 자료를 사용한 방식

개발 도구의 문서 구성을 비교하되 어느 도구의 전체 체계를 보편적인 Spec 정의로 옮기지 않았다. 아래는 2026-09-07~08 논의 중 열람한 공식 자료에서 사용한 내용의 요약이다. 이번 기록 시점의 새 버전 감사는 아니다.

- **GitHub Spec Kit**: [Spec template](https://github.com/github/spec-kit/blob/main/templates/spec-template.md)의 사용자 시나리오·수락 조건·예외 상황·요구사항·핵심 개념·성공 기준·가정과 의존 관계를 참고했다. [Clarify](https://github.com/github/spec-kit/blob/main/templates/commands/clarify.md)는 구현이나 검증을 바꾸지 않는 질문과 계획 단계로 미룰 내용을 구별한다. [Plan template](https://github.com/github/spec-kit/blob/main/templates/plan-template.md)은 기술 설계의 별도 책임을 확인하는 비교 자료였다.
- **Kiro**: [Requirements-first](https://kiro.dev/docs/specs/feature-specs/requirements-first/)의 요구·설계·실행 항목 구분과 예외·오류 동작, 설계 검토를 참고했다. 모든 Spec에 특정 ID·우선순위·용어집·수치 목표가 필수라고 확인한 것은 아니다.
- **OpenSpec**: [Concepts](https://github.com/Fission-AI/OpenSpec/blob/main/docs/concepts.md)의 요구·시나리오·동작 계약과 변경 제안·설계·실행 항목의 관계를 비교했다. 구체성은 의미 있는 모호함에 맞춰 높일 수 있지만, 현재 Spec과 변경을 합치는 운영 방식은 사용자의 Workspace별 독립 스냅샷 정책으로 도입하지 않았다.

외부 자료는 구체적인 요구와 실행 인계에 필요한 누락을 찾는 데 사용했다. 원래 실패를 이유로 Spec을 무조건 짧게 만들거나, 외부 템플릿에 있다는 이유만으로 모든 내용을 추가하는 근거로 사용하지 않았다.

## 5. 초안이 바뀐 과정

초기에는 문제·목표, 범위·제약, 요구·대표 흐름, 수락·평가, 설계·결정을 논의했다. 이후 문제·목표·범위, 요구와 수락 기준, 제약, 필요한 설계 정도로 줄이는 후보도 검토했다.

첫 구성 리뷰에서 요구와 수락 기준을 합칠 수는 있지만, 대표 사용자 흐름과 그 확인이 목표 달성을 충분히 뒷받침하는지는 남아 있어야 한다고 판단했다. 제약은 해당할 때 필요하고, 상세 설계가 선택적이라는 말이 중요한 선택의 이유까지 생략한다는 뜻은 아니었다. 코드 품질을 일반 지침으로 돌리더라도 구조 개선 자체가 목표인 Spec에서는 그 요구와 평가가 빠지면 안 된다.

이 과정에서 기존 current의 goal·constraints를 모두 Spec으로 옮기는 식의 제안도 성급하다고 바로잡았다. Spec과 Workspace의 범위 관계를 정하기 전에는 전체 목표의 소유 위치까지 확정할 수 없다.

사용자는 구성요소를 적용한 여행 상품 답변 예시를 요청했고, 이후 일반적인 Spec-driven 자료와 비교해 빠진 구체 내용을 물었다. 확장 초안에는 핵심 개념과 관계, 구체 입출력, 오류·경계 상황, 품질·평가 기준을 보강했다. 출력 JSON, 네 가지 결과 상태, 자료 판본, 시간제한 30초, 평가 사례 20개 등도 이때 논의 가능한 제안으로 들어갔다.

다시 원문 실패 장면에 비췄을 때, 이 구체성이 필요한 의미를 명확히 하는 이득과 임시 선택을 조기에 굳힐 위험을 함께 드러냈다. 확장 초안에도 실제 모델과 의미 평가가 있었으므로 이를 ‘테스트만 확인하는 초안’으로 축소한 평가는 맞지 않았다. 보다 정확한 약점은 코드 변경의 판단과 이미 발견한 문제를 완료 기준에 충분히 연결하지 못했다는 점이었다.

사용자는 개선 리뷰에 짧은 초안과 확장 초안 모두를 포함하고, 좋은 점·나쁜 점과 함께 기준과 이유를 제시하도록 요청했다.

## 6. 독립 개선 리뷰의 입력과 평가

리뷰에는 짧은 예시와 확장 예시의 본문, JSON·수치 제안, 사용자 의도, 관점별·시간순 원문, 04 장면 분석과 필요한 05 자료, 공식 Spec-driven 비교 자료를 제공했다. Main도 공식 자료가 무엇을 요구하는지 별도로 대조했다.

평가 기준은 실제 사용자 결과에 기여하는지, 구현·평가를 바꾸는 모호함을 줄이는지, 선택의 이유와 변경 가능성을 남기는지, 읽고 관리할 책임과 비용이 감당되는지였다. 평가 결과는 확장 초안을 바탕으로 필요한 구체성을 유지하면서 다음을 수정하는 방향이었다.

### 실제 모델과 사용자 결과까지 이어지는 흐름

실제 모델 판단은 이 예시에서 합의한 핵심이므로 유지한다. 연결 구조만 만든 상태와 실제 수행을 구별한다. 다만 모델 호출 자체가 목표 달성의 충분조건은 아니며 질문의 조건에 적용한 사용자 답변까지 확인한다. 제외했던 자료 수집·예약으로 범위를 넓히는 권고는 아니었다.

### 개념, 근거 인용, 자료 판본

상품·원문·답변·근거 관계를 구체화한 것은 유지한다. ‘각 문장에 근거’는 확인 질문과 오류 안내까지 불필요하게 강제하므로 ‘상품 자료에 기대어 하는 판단’으로 적용 범위를 고친다. 인용의 실제 존재와 의미상 뒷받침은 별도로 확인한다.

`revision`은 사용한 자료를 다시 대조하는 데 유익하지만 제공자가 실제로 주는지 확인이 필요하다. 자료 식별 책임은 유지하되, 예시 필드를 채우기 위해 새 판본 관리 기능을 범위에 끼워 넣지 않는다.

### 질문 전체의 상태와 부분 답변

기존 초안은 `answered`, `needs_input`, `insufficient_evidence`, `error` 중 하나를 질문 전체에 붙이고, `answered`가 아니면 `statements`를 비우도록 했다. 실패 이유의 구별은 유용하지만 일부만 답할 수 있는 질문의 처리까지 이 형식이 정해버렸다.

검토 사례는 “B구역 숙소인데 픽업되나요? 점심도 포함인가요?”였다. 픽업은 확인되고 점심은 자료가 없을 때 유효한 답변까지 비우거나 전체가 답변된 것처럼 표현할 수 있다. 이 예시의 목적에 맞춰 답변과 미해결 부분을 함께 반환하도록 권했다. 단일 판단만 받는 범위 제한도 가능한 선택이지만 마지막 예시는 부분 답변을 채택했다. 이는 모든 제품의 필수 정책이 아니다.

### 오류, 시한과 전체 거절

기술 실패를 상품의 부정적 조건으로 바꾸지 않고 미검증 답변을 반환하지 않는 요구는 유지한다. 30초는 실제 호출 시한과 맞춰 확정할 제안값이다.

잘못된 인용이 하나라도 있으면 전체 응답을 거절하는 것은 선택 가능한 방법이다. 보호할 요구와 처리 방법을 구별한다. 마지막 예시는 잘못된 근거가 다른 판단에 끼친 영향을 분리 검증하는 작업을 이번 범위에 넣지 않는다는 이유로 전체 거절을 유지했다. 자료가 없어서 모르는 부분을 함께 알리는 정상 부분 답변과 구별한다. 재시도·부분 구제 기능을 필수로 추가하지 않았다.

### 평가 사례의 의미와 개수

고정 사례, 표현 변경, 정보 부족, 자료 충돌, 실제 모델·원자료 대조는 유지한다. ‘A구역 픽업, 나머지 직접 이동’과 ‘A구역 픽업’만 있는 자료를 함께 평가해 명시된 제한과 원문에 없는 부정을 구별한다. 복합 질문도 선택한 부분 답변 동작을 확인하는 데 쓴다.

20개라는 초기 규모 자체를 잘못으로 보지 않았다. 왜 그 사례를 골랐고 어떤 조건이 미확인인지 남기며, 사례 수와 통과를 전체 충분성으로 해석하지 않는다.

### 역할 배치와 선택 이유

모델이 의미·조건을 판단하고 서버가 직접 대조 가능한 형식·자료 참조·인용을 검사하는 역할 및 그 이유를 유지한다. 내부 모듈·라이브러리·데이터 구조는 실제 코드를 보고 정한다. 같은 제품 규칙을 여러 곳에 반복해야 한다면 현재 책임 배치의 이유를 다시 검토한다. 별도의 거대한 설계 문서나 모든 대안 비교표를 필수로 만들지 않았다.

### 변경 코드, 완료 판단과 가독성

평가 사례와 실제 흐름을 통과했더라도 이미 발견한 핵심 누락이나 이번 목표를 가로막는 책임 문제를 완료 판단에서 제외하지 않는다. 실제 결과와 변경 전후 코드를 보되, 모든 구조 문제를 해결하거나 매번 전체 아키텍처를 재검토하도록 확대하지 않는다.

긴 초안에서 요구·개념·JSON·오류·평가가 한 절에 몰려 있던 것은 삭제보다 재배치로 개선했다. 그 결과가 지금의 다섯 구성이다. 상세를 별도 파일로 옮기더라도 요구와 검증 책임이 사라지는 것은 아니다.

## 7. 리뷰 설명이 이해되지 않았던 과정과 정정

사용자는 개선된 예시는 좋아졌다고 느끼지만 리뷰 설명은 이해하기 어렵다고 했다. 처음부터 분량보다 기존 문서의 말과 맥락을 지목했다.

> 우리가 논의한 문서와 맥락 단어 컨텍스트 뉘앙스로 좀 리뷰 내용을 조정하면 이해가 될까? 저건 제3자 내용이니까 뭔가 표현이 다를수 있잖아?

Main은 이를 제대로 이어받지 못했다. 먼저 큰 원칙으로 다시 묶었고, 이어 구성요소 평가와 여행 기능 수정 의견이 섞였다고 요약했다. 사용자가 구체적인 평가를 원한다고 하자 이번에는 일곱 항목의 설명을 길게 늘렸다. 이 과정에서 사용자가 원했던 기존 개념과 구체 평가의 연결은 계속 약했다.

> 구체적 요소들에 대한 평가였는데 아까 세부적인 내용있었잔하? 그냥 그걸 온전히 이해하고 싶은거야 이건 너무 추상적이고 이건 그냥 뭐 대부분 좋다 이정도 평가이고

> 아니 그렇다고 단순히자세한것도 너무 많아서 이해가 안되고 나의 이해르 돕기 위해 고민해보라니까 ?
> 이전문서와단어 사용이리뷰어가 안햇ㄴ느지 뭐 이런거 잇잖아? 근본적으로 생각해서 다시 설명해봐

별도 검토에서는 Main이 표현·맥락 연결 요청을 정보량 문제로 바꿔 처리했다고 판단했다. 기존 리뷰어에게 최초 보고의 실제 표현도 확인하도록 했다. 리뷰어는 자기 맥락에서 최초 보고를 직접 확인했다고 보고하며 다음 대조를 돌려줬다. 아래는 그 회수 보고에 근거하며 Main이 최초 보고 전체를 별도 원문 파일로 재감사한 결과는 아니다.

이후에는 사용자가 이미 보고 있던 구성요소를 기준으로, 평가한 실제 내용·기존 문서의 문제·유지하거나 바꿀 이유를 연결해 설명했다. 예를 들어 부분 답변은 ‘제품 의미가 응답 형식 때문에 사라지는가’, 30초·전체 거절 정책은 ‘임시 선택이 확정 전제로 굳는가’, 인용·사례·코드 평가는 ‘확인한 근거를 어디까지 완료 판단으로 쓸 수 있는가’로 설명했다.

## 8. 예시와 구성 설명의 분리

사용자는 구체적 초안과 구성 이유를 요청했다. Main은 처음에 Spec의 각 절 뒤에 구성 이유를 주석처럼 붙였다. 사용자는 두 종류의 문서를 분리해 달라고 정정했다.

> 아니 예시구체적인거 하나 그리고 설명 문서라고 해야하나? 각 구성은 왜 그렇게 했고 따로 보여줘

이에 실행자가 읽을 예시 Spec 본문과, 각 구성요소의 역할·구성 이유를 설명하는 문서를 따로 제시했다. 최신 사용자 결정은 이 두 문서에 대한 것이다. 저장 시에도 별도 파일로 유지하고, 리뷰 과정과 정정은 이 record에서 찾도록 한다. 본문의 구성 이유와 과정 기록을 서로의 대체물로 사용하지 않는다.

## 9. 이번 합의로 닫지 않은 사항

- Spec과 Workspace의 범위·개수 및 전체 목표의 정의 위치.
- 기존 current의 goal·constraints·지속 판단과 Spec의 소유 관계.
- memory/spec·tickets 폴더 후보의 실제 채택과 파일 분할.
- Ticket의 정의·상태·입력·범위·완료·의존 관계.
- 새 세션·개별 실행자·관리 주체의 읽기 계약과 변경 전달 방식.
- 판단이 바뀔 때 갱신하는 Owner, 영향받는 이전 결과·Ticket·검증의 재판정 방식.
- Reference의 Recover·Maintain·Verify·schema·hook·생성·이식 변경과 migration.

Workspace별 독립 스냅샷 조건은 유지한다. Spec 도입 여부와 이번 구성요소 합의는 다음 논의에서 다시 미결정으로 되돌리지 않는다. 실제 적용에서 새 근거로 바뀔 수 있다는 점과 아직 결정하지 않았다는 상태를 구별한다.
