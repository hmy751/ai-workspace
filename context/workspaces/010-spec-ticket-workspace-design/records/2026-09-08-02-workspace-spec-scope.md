# Spec 하나를 전제로 이어가는 논의

날짜: 2026-09-08

Spec 구성요소·이유·예시와 종합 기록은 사용자 요청에 따라 commit `6982fbe`로 남겼다. 이후 기존 Workspace/current와의 관계를 논의했다.

## 사용자 발화와 정정

> 일단 spec을 하나로 한다고 가정할까? 일종의 workspace의 goal 이나 제약등을 spec으로 대신하는거지 개념을 그러면 여러개는 무넺이지 않을까? 하는데?

> 그래 spec이 여러개가 생길경우는 뭐 다른데서 워크스페이스 파고 또 하나 구성해서 진행하는 식으로 자연스레 진해오디지 않을까 싶어

Main은 이를 Workspace마다 Spec 하나가 목표·범위·제약·완료 기준을 소유하고, 별도 Spec은 새 Workspace에서 진행하는 관계로 상세하게 기록했다. 사용자는 그 정도로 타이트하게 정하지 말라고 정정했다.

> 너무 타이트하게 하진말고 어쨋든 그냥 하나 spec이 생긴다는 전제로 가자 일단

## 현재 이어갈 의미

**일단 Spec 하나가 생긴다는 전제로 설계를 이어간다.** Workspace의 goal·제약 등을 Spec이 맡는 방향을 구체화하는 데 이 가정을 쓴다. Workspace마다 반드시 하나만 허용하거나, 별도 Spec마다 새 Workspace를 생성해야 한다는 규칙으로 굳히지 않는다.

별도 Spec이 필요하면 다른 Workspace에서 구성하며 진행할 수 있다는 사용자 생각은 가능한 진행 방식으로 남긴다. 개수 제한·예외·작업 전환 조건을 지금 모두 설계할 필요는 없다. 기존의 Workspace별 독립 스냅샷 조건은 유지한다.

다음에는 이 가정 아래 기존 current의 goal·constraints와 Spec 구성을 대조하고, Spec이 맡을 내용과 밖에 남길 지속 맥락·진행 정보를 구체화한다. 실제 저장 구조, Ticket 계약, 읽기·갱신 책임과 Reference 구현은 후속으로 남아 있다.

이 변경은 010의 설계 기록과 현재 상태 갱신이다. Reference를 변경하거나 새 Workspace를 생성하지 않았다.

## 후속 선택: Spec은 memory에 두고 Workspace와 함께 유지

사용자는 앞서 memory 아래 spec·tickets를 두는 방향까지 논의했음을 확인한 뒤, Spec의 위치와 유지 방식을 다음과 같이 선택했다.

> 그래 memory로 하자 일단 state보다 어쨋든 spec은 수정이 가능하고 갱신은 가능하지만 계속 해서 현재로 남기고 하는것보다 그냥 유지된다 정도로 보자
> 어차피 워크스페이스랑 같이 스냅샷 처럼 남을거고 장기적으로 갱신해야 하는것도 아니니까

Spec은 memory에 둔다. 수정·갱신은 가능하되 해당 Workspace의 작업 기준으로 유지하며, Workspace와 함께 스냅샷처럼 남는다. 진행 상황을 계속 반영하는 state와 구별하고, Project의 변화에 맞춰 장기적으로 계속 최신화해야 하는 문서로 보지 않는다.

Main이 앞서 쓴 ‘현재 적용되는 정의’라는 표현도 이 수명 안에서 이해한다. 그 표현을 영구적인 최신성 유지 의무로 확대하지 않는다. 독립 스냅샷이라는 기존 조건을 Spec 수정 금지나 매 수정의 별도 revision 발행 규칙으로 바꾸지도 않는다.

Spec의 memory 배치는 선택했으며, 구체적인 하위 파일 분할과 Ticket의 세부 배치·상태·읽기·갱신 계약은 후속 논의로 남아 있다.

## 후속 결정: goal·constraints 대체, project-context 유지, 다섯 Markdown 파일

Main은 Reference 예제 Workspace의 실제 current를 읽고 `01-goal.md`의 목표·완료 기준과 `02-constraints.md`의 작업 제약이 Spec과 겹침을 확인했다. 02에 있던 source·records·output 관리 문장은 상위 [Workspace 운영 문서](../../../../reference-project/context/work/workspaces/README.md)와 운영 지침에도 정의돼 있었다. 이 공통 규칙이 02를 유지해야 할 이유는 아니라고 설명했다.

사용자는 다음과 같이 결정했다.

> 그래 이걸 02가 맡는건 아닌것 같아 아마 그냥 예시로 적혀있던것 같은데 workspace 관리규칙 지침이나 맡는곳에서 해야지
> 그럼 대체이고
>
> project-context는 spec이 맡을건 아니니 유지해야 될것 같아
>
> 그럼 spec 아래 구성요소는 파일을 아까 5개를 각 md 파일로 두는걸로 하자

설계에 반영할 관계는 다음과 같다.

- 기존 `01-goal.md`와 `02-constraints.md`의 작업 목표·완료 기준·제약·결정은 Spec이 대체한다. 동일 내용을 별도 goal·constraints 파일에서 독립 관리하지 않는다.
- Workspace 공통 관리 규칙은 원래 운영 지침·책임 문서가 맡는다. Spec에 복사하거나 그 규칙 때문에 02를 남기지 않는다. 예시에 들어간 작성 경위 자체를 새로 입증한 것은 아니다.
- 기존 `03-project-context.md`는 Spec의 책임이 아니므로 memory에서 유지한다.
- `memory/spec/` 아래 합의한 다섯 구성요소를 각각 Markdown 파일로 둔다. 구성은 문제·목표·범위, 요구 동작과 대표 사례, 핵심 개념·입출력 계약, 품질·완료 판단, 제약·현재 설계·가정이다.

Spec의 내용·위치·기존 파일 대체와 하위 파일 분할은 이제 결정됐다. Ticket의 구성과 state의 관계, 소비자별 읽기·갱신·판단 변화 반영, 실제 Reference 변경과 검증이 남아 있다. 이번에는 설계 문서를 갱신했으며 Reference의 파일을 실제로 생성·삭제·이동하지 않았다.
