# Ticket의 기록 보존과 구체적인 배치 후보

날짜: 2026-09-08

## 사용자 발화

제3 리뷰 이후 사용자는 현재 행동에 영향을 주지 않는 Ticket도 기록처럼 남기고 싶을 수 있다고 말했다. 다음 발화에서 확정한 뜻은 아니라고 직접 유보했다.

> 근데 영향은 주지 않지만 ticket이 기록처럼 남는게 낫긴할것 같아 지워지고갱신되더라도 아니다 이것도 뭐 확정은 아니지만 어렵네

Main은 보존할 가치와 현재 읽을 필요를 구별하고, Ticket에 실행 중 문서와 실행 후 기록의 역할이 모두 있을 수 있다고 설명했다. 사용자는 추상적인 설명 뒤 실제 배치를 물었다.

## Main이 설명할 구체안 — 채택 전

기존 current/records 구분에 맞추면, 현재 작업에 필요한 Ticket은 current에서 관리하고 현재 필요가 사라져 기록으로만 남길 Ticket은 records에 보존하는 안이 가능하다.

memory 유지안을 예로 들면 `current/memory/tickets/`에 진행 중이거나 후속 판단에 필요한 Ticket을, `records/tickets/`에 현재 작업에서는 더 이상 사용하지 않는 Ticket을 둔다. memory 제거안을 선택하면 앞의 위치가 `current/tickets/`가 된다. 이는 memory 유지·제거나 records 하위 파일 규칙을 확정한 것이 아닌 배치 예시다.

- 실행 중에는 Ticket의 정의·진행을 함께 갱신한다.
- 완료 뒤에도 다른 Ticket의 선행 조건이나 현재 결과 판단에 필요하면 current에 남긴다.
- 현재에 필요하지 않아 정리할 때에는 Ticket 내용·최종 상태·결과를 records에서 찾을 수 있게 보존하고 current에서 뺀다. 완료 표시만으로 자동 이동시키는 규칙은 아니다.
- Ticket의 범위·완료 조건 등을 바꿀 때 재검토에 필요한 이전 기준과 변경 이유는 기록으로 남길 수 있다. 매 수정마다 새 사본을 의무화하거나 구체적 이력 수단까지 확정하지 않는다.

이 안은 기록으로 남기는 Ticket을 현재 문서로 계속 유지할 필요 없이 보존한다. 대신 현재 필요가 없어졌는지 판단하고, 위치를 옮기면 관련 참조를 정리하는 비용이 있다. Ticket을 처음부터 끝까지 같은 경로에 두는 방식과 동일한 안은 아니다.

## 현재 지위

Ticket의 기록 보존 필요성, 구체적인 이동·이력 방식, memory 배치는 아직 사용자 선택 전이다. 이 설명을 새 archive 체계나 자동 정리 구현 승인으로 읽지 않는다. 연구 Workspace의 기록만 추가했으며 실제 Reference 파일 배치는 변경하지 않았다.
