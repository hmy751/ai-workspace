# 예시 Spec — 여행 상품 자료에 근거한 질문 답변

2026-09-08 [Spec 구성요소와 구성 이유](spec-components-and-rationale.md)와 함께 채택한 설계 설명용 예시다. 실제 TripProof의 구현 계약이나 모든 Spec의 공통 요구가 아니다. API 필드와 수치는 실제 호출 환경을 확인해 확정한다.

## 1. 문제·목표·범위

사용자는 상품 설명에 적힌 조건을 자신의 상황에 적용해서 알고 싶다. 관련 원문을 보여주는 것만으로는 사용자가 필요한 판단까지 얻지 못할 수 있다.

이 기능의 목표는 **실제 모델이 상품 자료와 사용자 질문을 해석해서, 답할 수 있는 내용과 아직 판단할 수 없는 내용을 구별해 반환하는 것**이다.

이번 범위에 포함하는 것은 다음과 같다.

- 선택된 상품의 자료와 사용자 질문을 입력받는다.
- 실제 모델이 질문의 의미와 조건을 해석한다.
- 답변에 사용한 자료 참조와 인용을 확인한다.
- 확인한 답변과 미해결 내용을 함께 반환한다.

상품 선택과 자료 확보 기능은 이미 제공된다고 가정한다. 자료 수집 구현, 상품 간 비교, 예약·결제, 새로운 화면 설계는 이번 범위에서 제외한다.

모델 연결 인터페이스와 검증기만 만든 상태는 기반 작업의 진척이다. 이 Spec의 완료에는 실제 모델의 판단이 사용자 답변으로 이어지는 동작이 필요하다.

## 2. 요구 동작과 대표 사례

답변은 자료의 대상·지역·시간·예외 조건을 사용자 상황에 맞게 적용해야 한다. 같은 뜻의 질문은 표현이 달라도 일관된 판단을 해야 한다.

자료에 명시된 제한과 자료에 설명이 없는 상황을 구별한다. 특정 지역이 언급되지 않았다는 이유만으로 그 지역의 이용 불가를 확정하지 않는다.

질문의 일부만 답할 수 있다면 확인한 답변을 제공하고, 나머지는 판단하지 못한 이유를 함께 알린다. 사용자 정보 부족, 상품 자료 부족, 자료 간 충돌을 구별한다.

상품 자료에 근거한 각 판단에는 해당 자료와 인용을 연결한다. 확인 질문이나 처리 실패 안내에는 상품 인용을 요구하지 않는다.

대표 사례는 다음과 같다.

| 자료와 질문 | 기대하는 동작 |
|---|---|
| “A구역은 픽업, 나머지 구역은 직접 이동.” B구역 픽업 여부를 질문 | B구역은 직접 이동해야 한다고 답하고 근거를 연결한다. |
| “A구역은 픽업.” B구역 픽업 여부를 질문 | 제공된 자료만으로는 B구역 픽업 여부를 확인할 수 없다고 답한다. |
| 지역별 픽업 조건은 있지만 사용자의 숙소 구역을 모름 | 숙소 구역을 묻는다. |
| B구역 이동 방식은 확인되지만 점심 안내는 없음. 두 가지를 함께 질문 | 이동 방식은 답하고, 점심 포함 여부는 확인할 수 없다고 알린다. |
| 같은 조건에 대한 자료가 충돌하고 우선할 자료를 정할 근거가 없음 | 임의로 하나를 선택하지 않고 충돌을 알린다. |
| 모델 호출에 실패함 | 처리 실패를 알린다. 상품의 이용 불가로 답하지 않는다. |

첫 번째와 두 번째 사례는 함께 확인한다. 자료에 적힌 조건의 차이가 답변의 결론에 반영돼야 한다.

## 3. 핵심 개념·입출력 계약

이 기능에서 다루는 개념은 다음과 같다.

- **상품**: 이번 질문의 대상이다.
- **자료**: 해당 상품에 관해 제공된 원문이다.
- **답변 항목**: 질문 중 판단할 수 있는 부분과 그 결론이다.
- **미해결 항목**: 아직 판단할 수 없는 부분과 그 이유다.
- **근거**: 답변의 판단을 뒷받침하는 자료 참조와 인용문이다.

입력에는 다음 정보가 있어야 한다.

- `product_id`: 대상 상품의 식별자.
- `question`: 비어 있지 않은 사용자 질문.
- `sources`: 자료 목록. 각 자료에는 요청 안에서 구별되는 `source_id`, 대상 상품, 원문이 있어야 한다.

자료 제공자가 판본을 제공한다면 `revision`도 함께 사용한다.

출력은 답변과 미해결 내용을 동시에 포함할 수 있다. 예를 들어 “B구역 숙소인데 픽업되나요? 점심도 포함인가요?”에 대해 다음처럼 반환한다.

```json
{
  "status": "result",
  "answers": [
    {
      "topic": "호텔 픽업",
      "text": "B구역 숙소는 지정 집결지로 직접 이동해야 합니다.",
      "evidence": [
        {
          "source_id": "guide-001#pickup",
          "quote": "A구역 호텔은 픽업을 제공합니다. 그 외 지역은 지정 집결지로 직접 이동해야 합니다."
        }
      ]
    }
  ],
  "unresolved": [
    {
      "topic": "점심 포함 여부",
      "reasons": ["missing_evidence"],
      "message": "제공된 자료에서는 점심 포함 여부를 확인할 수 없습니다."
    }
  ],
  "error": null
}
```

`status: result`는 판단 결과를 반환했다는 뜻이며, 질문 전체가 해결됐다는 뜻은 아니다.

미해결 이유는 다음과 같이 구별한다. 필요한 경우 여러 이유를 함께 표시한다.

- `needs_input`: 사용자 정보가 더 필요하다.
- `missing_evidence`: 판단할 상품 자료가 부족하다.
- `conflicting_evidence`: 자료가 충돌한다.

빈 자료 목록은 자료 부족으로 처리한다. 잘못된 입력이나 상품이 맞지 않는 자료는 입력 오류로 처리한다.

모델 호출 실패·잘못된 응답 형식·시간 초과는 처리 오류로 구별한다. 처리 오류에서는 `status: error`와 오류 정보를 반환하고, 생성 중이던 미검증 답변은 포함하지 않는다.

필드 이름과 구체 형식은 현재 제안이며 실제 호출자와 자료 제공자의 계약을 확인해 확정한다.

## 4. 품질·완료 판단

평가는 다음 두 비교를 포함한다.

### 제품 원자료와 실제 동작의 비교

실제 모델이 연결된 흐름에서 자료 입력, 조건 해석, 답변·미해결 내용 구성, 인용 확인, 결과 반환까지 확인한다.

답변을 원자료와 직접 대조해서 다음을 판단한다.

- 질문의 대상과 조건을 올바르게 적용했는가.
- 자료에 없는 긍정·부정의 결론을 만들지 않았는가.
- 확인한 내용과 판단하지 못한 내용을 올바르게 구별했는가.
- 인용한 원문이 답변의 결론을 뒷받침하는가.

인용문이 원문에 존재한다는 검사와, 그 인용문이 답변을 뒷받침한다는 평가는 구별한다.

대표 사례는 이후 변경에서도 반복 확인할 수 있도록 고정한다. 초기 평가 규모로 20개를 제안하되, 사례를 고른 이유와 아직 확인하지 못한 조건을 남긴다. 사례 개수 자체를 평가의 충분성으로 사용하지 않는다.

### 변경 전 코드와 변경 후 코드의 비교

이번 기능과 관련된 코드에서 다음을 확인한다.

- 의미 판단, 인용 확인, 결과 구성의 책임이 분명한가.
- 같은 상품 규칙을 여러 위치에서 따로 유지하게 됐는가.
- 다음에 비슷한 조건을 바꿀 위치를 설명할 수 있는가.
- 잘못된 가정을 교체했는가, 기존 구조 위에 예외를 더 붙였는가.

### 완료 판단

대표 사례와 실제 흐름을 확인하고, 그 과정에서 발견한 문제가 이번 목표를 가로막는지 함께 판단한다.

핵심 판단을 후속 작업으로 미뤘거나 이번 목표와 관련된 책임 문제가 남아 있다면, 사례 통과만으로 완료하지 않는다.

구현이 요구를 따르지 않았다면 구현을 수정한다. 요구대로 구현했는데도 의도한 결과를 얻지 못했다면 Spec의 요구나 설계를 다시 판단한다.

Ticket 완료와 평가 통과는 완료 판단의 근거다. 이 Spec의 완료가 더 넓은 Workspace나 제품 목표의 달성을 자동으로 뜻하지는 않는다.

## 5. 제약·현재 설계·가정

### 지켜야 할 제약

선택된 상품에 대해 제공된 자료를 사용한다. 자료의 대상·지역·시간·예외 조건을 보존한다.

검증되지 않은 주장을 검증된 답변으로 반환하지 않는다. 처리 실패를 상품에 대한 부정적인 판단으로 바꾸지 않는다.

기존 호출자가 의존하는 입력과 출력의 의미를 확인하고, 그 의미를 임의로 바꾸지 않는다.

### 현재 설계와 선택 이유

모델은 질문의 의미와 조건 관계를 판단하고 답변·미해결 내용·인용 후보를 구성한다. 서버는 입력, 응답 형식, 시간제한, 자료 참조와 인용 일치를 검사한다.

표현과 조건의 해석은 모델에 맡기고, 직접 대조할 수 있는 사항은 서버에서 확인하려는 배치다. 서버 검사 통과만으로 답변의 의미가 적절하다고 판단하지 않는다.

잘못된 인용이나 자료 참조가 발견되면 현재 설계에서는 전체 응답을 거절한다. 잘못된 근거가 다른 판단에 끼친 영향까지 분리해 검증하는 작업은 이번 범위에 포함하지 않기 때문이다.

시간제한은 현재 30초를 제안한다. 실제 호출자가 기다리는 시간과 실행 환경을 확인해 확정한다.

내부 모듈, 라이브러리, 데이터 구조는 실제 코드를 보고 정한다. 현재 구조를 유지하려고 같은 상품 규칙을 여러 곳에 반복해야 한다면 그 구조를 유지할 이유부터 다시 검토한다.

### 남아 있는 가정

상품 선택과 자료 확보 기능이 준비돼 있다고 가정한다. 실제로 필요한 자료를 제공하지 못한다면 선행 조건과 이번 범위를 다시 판단한다.

자료 판본은 제공자가 제공하는 경우에 사용한다. `revision` 필드를 채우기 위해 새로운 버전 관리 기능이 필요하다고 전제하지 않는다.
