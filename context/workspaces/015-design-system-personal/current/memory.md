# 목표와 기준

마지막 갱신: `2026-11-06`

## 목표

UI를 층으로 쌓을 때 사용자가 실제로 어떻게 판단해 왔는지 근거에서 찾아, 다음 작업의 사람과 AI가 쓸 수 있는 `design-system` Personal로 정리한다.

사용자가 정한 문제는 UI를 구조를 보지 않고 덧대는 방식이다. absolute는 그 한 증상이며, 증상의 비율을 판정하는 일은 목표가 아니다. Personal은 금지 목록이 아니라 토큰, 배치, 부품, 조합, 화면을 어떻게 쌓는지에 대한 판단을 준다. 중심 질문은 "이 UI 결정은 어느 층에 있어야 하는가"다.

## 성공 기준

- 수집 결과가 주제별로 "근거 있음, 찾았지만 없음, 확인 못 함"을 구별한다. 확인하지 않은 주제가 없는 것처럼 보이지 않는다.
- 각 관찰이 출처, 근거 종류, 시기, 확신도를 갖는다.
- 말한 것과 만든 것이 어긋나는 지점, 시기별 판단 변화, 근거가 부족한 주제가 드러난다.
- Personal 후보마다 넣거나 빼는 이유가 있고, 최종 선택은 사용자가 한다.

## 유지할 결정

- **독자와 범위:** AI를 우선하고 사람도 읽는다. 결과물은 여러 Project에 가져갈 Personal이며 특정 Project 전용 문서가 아니다.
- **반영 위치:** Personal 본문은 `reference-project`에 먼저 적용한다. 그래야 기준 Project에서 유지되고 다른 Project로 이어질 수 있다.
- **template 활용:** template은 근거이고 Personal은 판단 문서다. 구조와 판단 기준을 가져오고 예시 코드를 적절히 사례로 쓴다. template 자체는 고치지 않는다.
- **경험이 적은 주제:** 접근성은 목표로 표시하고 부품별 실제 범위를 적는다. Storybook은 경험을 표시하고 역할은 미정으로 둔다. 배치 책임을 단위로 빼는 것은 기준, 구체적 프리미티브 세트는 미정으로 둔다.

- **본문 구성:** 분야가 넓으므로 한 주제 안에서 시작 본문을 입구로 두고 영역별 본문으로 나눈다. 분량을 미리 제한하지 않고 채우려고 늘리지도 않는다. 재측정에서 도달에 문제가 드러나면 다시 판단한다.
- **형성 자료:** 본문과 함께 `_background`를 쓴다. 채택 때로 미루지 않는다.
- **문서의 성격:** 정답의 원천이 아니라 사용자의 생각과 지식을 최대한 담은 것이다. 답을 고정하기보다 볼 것과 트레이드오프를 적고, 애매하면 레퍼런스를 본 뒤 사용자에게 묻는다.
- **지켜지게 하는 방식:** 문서만으로 보장하지 않는다. 기계가 판정할 수 있는 것은 검사로, 판단이 필요한 것은 스킬의 작성 전 확인과 완료 보고로 드러낸다. 아직 시험하지 않았다.
- **사용자 판단을 묻는 방식:** 선택지보다 Main이 자료로 판단을 재구성해 제시하고 사용자가 고치게 한다. 사용자가 모른다고 한 것은 미정으로 둔다.
- **이름:** 주제 이름은 `design-system`이다. 레이아웃 구성(layout composition)은 그 안의 한 층이다. 일반적인 디자인 시스템이 포함하는 브랜드·Figma 자산·운영 전반이 아니라 프론트 구현에서 쌓는 판단을 다룬다는 범위를 본문 첫머리에 밝힌다.
- **근거 비중:** 프로젝트를 건너 계속 가져간 구조를 가장 강한 근거로 본다. 단일 버그 수정이나 사소한 구현 정정을 핵심 근거로 올리지 않는다.
- **근거 구분:** 말한 것(이력서·인터뷰), 만든 것(코드), 고친 것(리팩터링·피드백·정정)을 구별한다. 이력서는 지원용으로 다듬은 글이므로 사실 근거로 쓰지 않는다. 내 이름의 커밋도 AI가 쓴 코드일 수 있으므로 Noline에서는 고친 흔적과 작업 기록을 더 중요하게 본다.
- **코드 읽기:** 수치는 단서로만 쓰고 실제 쓰임을 읽는다. 커밋 수가 아니라 직접 만들었거나 오래 다듬은 파일을 중심으로 본다.
- **누락 방지:** 주제 목록으로 찾기, 자료에서 거꾸로 찾기, 자료 간 재대조를 함께 한다. 목록에 없는 주제가 나오면 추가한다.
- **조사 주제:** 기반값, 레이아웃, 컴포넌트 구조, 컴포넌트 API(Headless·Composition 포함), 상태와 접근성, 스타일 기술, 개발과 검증(Storybook 포함), 운영과 변화, AI 협업.
- **대상별 확정 사실:** 본인 계정, 제외할 저장소, 핵심 사례와 조사하지 않을 구조는 사용자가 확정했다. 내용은 공개하지 않으므로 [로컬 수집 기록](../records/collection/README.md#대상별-확정-사실)에서 읽는다.

## 제약

- **공개 저장소:** `hmy751/ai-workspace`는 공개 저장소이므로 커밋 후 push하면 내용이 공개된다. 회사 재직 계정, 로컬 경로, 회사 코드 관찰, 이력서·인터뷰·피드백 내용은 Git에서 제외된 [`records/collection/`](../records/collection/README.md)에만 둔다. Personal 본문을 포함한 다른 문서에는 공개해도 되는 판단만 옮긴다.
- **회사 코드:** oround와 POD-SHOP은 `records/collection/` 안에서도 코드 원문을 옮기지 않는다. 경로와 직접 정리한 내용만 남긴다.
- **로컬 기록 보존:** `records/collection/`은 Git 기록이 없어 지우면 복구할 수 없고 다른 clone이나 worktree에 나타나지 않는다. 이 저장소의 원래 위치에서 작업한다.
- **읽기 전용:** 조사 대상 저장소를 수정하지 않는다. `.env` 파일과 인증 정보는 읽지 않는다.
- **조사 범위:** 사용자가 지정한 자료 밖으로 넓히지 않는다.
