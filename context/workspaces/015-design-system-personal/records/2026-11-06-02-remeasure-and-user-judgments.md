# 재측정 대조와 사용자 판단

작성일: `2026-11-06`

재측정 결과를 기준선과 대조한 결론과, 측정으로 알 수 없는 판단을 사용자와 정한 경위를 남긴다. 코드 비교, 답 원문 전체, 초안은 Git에서 제외된 [`로컬 수집 기록`](collection/README.md)에 있다. 이 기록은 공개를 전제로 쓴다.

## 초안의 효과는 작업마다 달랐다

같은 앱의 목록, 폼, 메뉴 작업을 초안 없이 한 번, 초안을 더해 한 번 수행했다. 결과는 대체로 나아졌지만 초안의 효과로 볼 수 있는 것은 일부다. 작업당 한 번이라 원인을 확정하지 않는다.

| 작업 | 초안 도달 | 판단 |
| --- | --- | --- |
| 목록 | 읽지 않음 | 초안의 효과가 아니다. 두 세션 모두 같은 Project 문서를 읽었다. 작성 전에 기존 코드를 더 읽은 세션 차이로 보인다. |
| 폼 | 영역 본문 일부 | 입력 부품에서 단서가 있다. 읽은 기존 폼과 안내 예시가 모두 raw 입력인데 초안을 읽은 세션만 공통 입력을 썼다. |
| 메뉴 | 시작 본문과 영역 본문 | 결과 차이가 문서 차이를 따르지만, 초안 사례가 같은 앱의 코드를 담아 다른 앱의 효과로 읽을 수 없다. |

세션 로그로 두 측정의 모델과 추론 수준이 같고, 시작 지침도 날짜와 권한 항목, 플러그인 목록 외에 같으며, 세션이 보고한 읽은 문서가 실제 읽기와 일치함을 확인했다.

## 문서가 읽혀도 지켜진다는 보장이 없다

목록의 두 세션은 같은 조합 부품 지침을 읽고도 한쪽만 그 부품을 썼다. 메뉴 세션은 "벗어나면 이유를 남긴다"를 읽고도 남기지 않았다. 세션 차이도 커서 한 번씩의 측정으로 문장별 효과를 판정할 수 없다.

Main은 내용의 성격에 따라 나누자고 제안했고 사용자가 동의했다. 아직 시험하지 않았다.

> 나도 니 추천이 제일 나은 것 같긴하고 뭐 스킬도 같이 보완해야 될것 같단 생각은 드네

- 기계가 판정할 수 있는 값과 금지 부품은 lint나 검사로 다룬다.
- 판단이 필요한 것은 스킬의 작성 전 확인과 완료 보고 항목으로 드러낸다.
- Personal 본문은 시점과 행동이 붙은 문장으로 판단의 이유와 기준을 담는다.

## 사용자 판단을 물어 본문을 고쳤다

처음에는 선택지로 물었으나 사용자가 맞지 않다고 했다.

> 이건 하냐 안하냐 보다 트레이드오프를 비교해서 결저애햐하는거 아닌가?

이후 Main이 수집 자료에서 판단을 재구성해 제시하고 사용자가 고치는 방식으로 바꿨다. 아래 표의 항목 다수는 Main의 정리에 사용자가 동의한 것이며, 사용자가 처음부터 말한 원칙은 아니다.

| 주제 | 본문에 넣은 판단 | 사용자가 직접 정한 부분 |
| --- | --- | --- |
| 공통 부품 변경 | 공통에 둘 이유를 실제 코드로 말할 수 있을 때 고친다. 호출부 수가 아니라 이득과 사람이 다시 봐야 할 양을 견준다. | 답을 고정하지 않는다. 고칠 곳이 많다는 것 자체는 AI에게 안 바꿀 이유가 아니지만, 사소한데 확인할 곳이 많으면 다르게 판단할 수 있다. 이유 없는 공통화가 문제다. |
| 옆 화면과 공통 부품 | 코드가 많은 쪽이 아니라 같은 모양과 책임인지 본다. 옆 화면을 선례로 단정하지 않는다. | 공통과 같은 모양의 raw 입력은 "그냥 놓친거지 개발하다가". |
| 간격과 자리 | 자리는 관련 요소를 모두 아는 쪽이 나눈다. 숫자나 absolute 자체가 아니라 그 값을 누가 아는지 본다. | 부모가 간격을 맡는 것이 "맞아 레이아웃 관리 관점으로". |
| 배치 단위 | 빠지면 동작이 달라지는 보장을 담은 단위는 쓴다. 방향과 간격을 줄여 쓰는 단위의 필수 여부는 미정이다. | 모바일 경험이 적어 정하지 않았다. |
| 값과 열림 상태 | 알아야 하는 쪽이 가진다. 대화창 같은 범용 부품은 제어와 비제어를 둘 다 지원할 수 있다. | 둘 다 지원한 것은 상황마다 달라 레퍼런스를 보고 고른 판단이다. 비제어와 `Controller`는 상황에 따른 트레이드오프다. |
| 애매할 때 | 먼저 잘 만든 라이브러리를 보고, 그래도 갈리면 사용자에게 묻는다. | "애매할때는 라이브러리 레퍼런스를 보거든". |

Main이 표에서 틀렸던 것도 남긴다. 공통 변경에서 "기존 동작을 유지하는 수정만"을 권했으나 사용자의 이력과 맞지 않았다. 대화창이 둘 다 지원하는 것을 관성으로 볼 수 있다고 했으나 판단이었다. 측정에서 배치 단위를 쓰지 않은 것을 규칙 위반으로 봤으나 필수가 아닐 수 있다.

## 문서의 성격

> 그래 결국 이것도 정답 원천은 아니니까 다 대응되진 않고 최대한 내 생각과 지식을 담는거라 완벽할수 없어 그래서 전반적으로 다 확인하더라도 애매한 상황이거나 하면 뭐 물어볼수 잇는거고

이 말을 시작 본문에 넣었다. 답을 고정하기보다 볼 것과 트레이드오프를 적고, 애매하면 묻는 문서로 쓴다.

## 남은 일

값과 토큰, 떠 있는 표면, 상태 표현, 검증, 플랫폼, 사례 본문은 아직 사용자와 함께 보지 않았다. 사용자가 입구와 스킬 문구보다 이 확인을 먼저 하기로 했다. 고친 초안은 측정하지 않았고 채택하지 않았다.
