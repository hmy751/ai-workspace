# 2차 측정과 측정 없는 채택 결정

작성일: `2026-11-06`

입구 문구를 넣어 2차 측정한 결과, 스킬 문구를 고친 경위, 고친 문구를 다시 측정하지 않고 채택하기로 한 결정을 남긴다. 상세 비교는 Git에서 제외된 [`로컬 수집 기록`](collection/README.md)에 있다. 이 기록은 공개를 전제로 쓴다.

## 2차 측정에서 본 것

사용자 답을 반영한 초안과 `development` 스킬 구현 상세의 두 문장을 새 사본에 넣어, 같은 지시문으로 목록 두 번, 폼 두 번, 메뉴 한 번을 수행했다. 세션 로그로 읽은 순서와 설정을 대조했다.

- **입구는 위치가 문제였다.** 5개 세션 모두 구현 상세를 읽었지만 두 세션은 묶음 출력의 중간이 잘려 첫 문장이 보이지 않았다. 문장이 보인 3개는 모두 코드를 쓰기 전에 초안을 읽었고, 보이지 않은 2개는 읽지 않았다. 우연히 생긴 비교이며 표본이 작다.
- **보고 문장은 효과가 없었다.** 5개 세션 모두 받았지만 벗어난 곳, 이유, 달라지는 사용처를 적은 보고가 없었다.
- **초안의 효과는 일부만 보인다.** 초안을 읽지 않은 세션도 토큰과 공통 입력을 잘 썼다. 앞서 초안의 단서로 본 공통 입력 사용은 약해졌다. 첫 기준선이 나쁜 쪽 표본이었을 수 있다.
- **읽고도 지켜지지 않은 것이 있다.** 미리보기 사정으로 공통 헤더에 옵션을 더한 세션과, 공통 메뉴의 결함을 화면 안 모달로 우회하고 언급하지 않은 세션이 있었다. 둘 다 개선 검토를 호출하지 않았다.

## 입구 문장의 자리

세 측정의 Main 세션 11개에서 코드를 쓰기 전에 출력에 보인 자리를 셌다. `SKILL.md`의 앞부분과 "맥락의 소유와 현재 적용을 구별한다" 절은 11개 모두에 보였고, 구현 상세 첫 절은 9개, `SKILL.md` 중간의 구현자 절은 7개에 보였다. 문장을 맥락 절로 옮긴다. Codex의 출력 한도에서 나온 값이며 다른 도구에서는 달라질 수 있다.

## 검증 담당에 항목을 더하지 않은 이유

Main은 공통 변경을 검증 담당이 확인하도록 항목을 더하자고 제안했다. 사용자가 다음과 같이 지적했다.

> 근데 애매한게 이렇게 적용 안됐다고 검증담당도 보게하는것보다 애초에 personal을 검증담당자가 보는게 지금 현재 아닌가?

대조해 보니 기준의 적용을 다시 판단하는 책임은 이미 개선 검토에 있고, Main이 관련 Personal의 접근점을 넘기게 되어 있다. 문제는 규칙이 없는 것이 아니라 개선 검토가 호출되지 않았거나 초안이 넘어가지 않은 것이었다. 그래서 새 책임을 만들지 않고, 공통 부품을 바꾸거나 우회했으면 개선 검토를 맡기고 이 본문을 넘긴다는 문장만 두기로 했다. 효과가 없었던 보고 문장은 뺐다.

**남는 한계:** Main이 공통을 우회했다고 스스로 알아차려야 검토를 부른다.

## 측정 없이 채택한다

사용자가 고친 문구를 다시 측정하지 않고 채택하기로 했다.

> 측정 없이 채택

이 문서의 목적은 사용자의 판단을 담는 것이고, 측정으로 효과를 입증할 필요는 없다. 측정에서 초안 때문에 나빠진 징후는 찾지 못했다. 고친 문단의 효과는 시험하지 않았으므로 실제 사용에서 어긋나면 고친다.

## 반영 범위

- `reference-project`의 Personal 개발 판단에 본문과 형성 자료를 더하고, 선택 표에 입구를 더한다.
- 기계 검사와 Noline의 안내 수정은 이번 범위가 아니다.

## 반영하며 바꾼 것

위 문단을 `development` 스킬에 넣어 봤다. 맥락 절의 문단은 사용자가 "뜬금없어보인다"고 했고, Personal 행의 문장은 "본문스타일상 뭔가 안 어울려"라고 했다. 대조해 보니 이 스킬은 개발 판단의 특정 주제를 이름으로 가리키지 않는다. 그래서 UI 읽을 곳은 스킬에서 뺐다. 공통 변경 문장만 UI에 한정할 이유가 없어 개선 검토의 호출 판단에 남겼다.

사용자는 입구에 대해 다음과 같이 판단했다.

> 애초에 personal 쪽에 리드미에 진입점 쪽에 있어서 괜찮을 것 같으데

측정에서 Personal 선택 표의 입구만으로 닿지 않은 세션이 있었다. 사용자의 판단을 따르며 실제 사용에서 어긋나면 다시 본다.

## Noline에 옮김

사용자가 남은 작업을 하자고 해 Noline 원본에 옮겼다. 다른 작업의 미커밋 변경이 있는 파일은 건드리지 않았고, 사용자 요청에 따라 경로를 지정해 Noline `main`의 `4bc8d4cd`로 커밋했다. push하지 않았다.

- Personal에 주제와 입구를 더했고, `development` 스킬에 개선 검토 문장과 형성 기록을 더했다.
- 앱 가이드의 `UI composition` 행에 본문 링크를 더했다. 측정에서 11개 세션 모두에 보인 자리다.
- 폼 안내 예시의 `TextInput`을 공통 `Input`으로 바꿨다.

바뀐 파일의 링크 222개는 깨지지 않았다. Noline `harness:check`는 이전부터 실패하며(64건, 옛 `.claude` 링크 등), 옮기기 전후 출력이 같다. 실제 작업에서 본문에 닿는지는 시험하지 않았다.

Noline 코드에 남은 raw `TextInput`과 직접 쓴 색은 고치지 않았다. Noline 외 Project로의 이식은 사용자 판단을 기다린다.

## Noline에 lint 경고를 더함

사용자가 "그래 경고로 추가하자"고 했다. 오류로 두면 기존 코드 때문에 바로 실패하므로 경고로 넣었다(Noline `13d573c7`, push하지 않음). 앱 설정에만 넣었고 공통 `Input`을 구현하는 `packages/ui`와 테스트, 디버그 화면은 제외했다. 판단이 필요한 공통 변경과 자리는 lint로 잡지 않고 문서가 맡는다.

- **잡는 것:** 코드에 직접 쓴 hex·`rgb`·`hsl` 색, 테마를 거치지 않은 Tailwind 색, `react-native`의 `TextInput` 가져오기.
- **먼저 고친 것:** `pnpm client lint`는 이전부터 Prettier 플러그인에서 멈춰 규칙이 돌지 않았다. 선언된 5.x 대신 다른 패키지가 끌고 온 4.2.5가 불렸다. 의존성을 바꾸지 않고 client lint 명령에 플러그인 위치만 지정했다. 그 결과 플러그인 버전이 달라져 `no-explicit-any`가 경고에서 오류가 되는 등 기존 규칙의 결과도 달라졌다.
- **결과:** 경고 219건이 새로 나온다(색 215건, `TextInput` 4개 파일). 기존 오류 14건은 그대로이며 이번에 고치지 않았다.
- **남은 것:** 루트 `pnpm lint`는 여전히 멈춘다. CI와 커밋 훅을 찾지 못했으므로 누군가 명령을 돌려야 경고가 보인다. AI 세션이 경고를 보고 행동이 달라지는지는 시험하지 않았다.
- **본문 정정:** `INDEX.tokens.md`의 lint 미정 문장이 Noline 도입 뒤 사실과 달라져 Reference와 Noline 양쪽을 고쳤고, 형성 기록에 결정을 더했다. 다른 Project의 도입 여부는 정하지 않았다.
