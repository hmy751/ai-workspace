# AI Workspace

한국어 | [English](./README.en.md)

AI 에이전트와 실제 소프트웨어를 개발하면서 쓰는 작업 방식을 문서와 스킬로 정리한 개인 저장소다. 에이전트가 무엇을 읽고 일을 시작하는지, 개발을 어떤 역할로 나눠 진행하는지, 끝난 뒤 무엇을 남기는지를 다룬다.

라이브러리나 CLI가 아니다. 내용의 대부분은 Markdown 문서와 스킬 정의이고, 실행되는 코드는 방식을 보여 주기 위한 작은 샘플 제품 하나다. Claude Code와 Codex에서 쓴다.

- [`reference-project/`](./reference-project/): 이 방식을 샘플 제품에 그대로 적용해 둔 기준 프로젝트. 방식을 보려면 여기서 시작한다.
- [`.agents/skills/apply-context-harness/`](./.agents/skills/apply-context-harness/): 기준 프로젝트의 구성을 다른 프로젝트로 옮기는 스킬.
- [`context/`](./context/): 이 방식을 설계하고 고쳐 온 작업 기록. 저장소 파일의 대부분을 차지하지만 방식을 이해하려고 읽을 필요는 없다.

## 풀려는 문제

실제로 있었던 장면이다. 이전 세션의 기록을 읽고 작업을 재개한 에이전트가 버그 두 개를 먼저 고치자고 제안했다. 그 시점에 사람이 원한 것은 구조와 배경을 다시 검토하는 일이었다. 기록은 남아 있었고 에이전트도 그것을 읽었다. 이어지지 않은 것은 지금 무엇이 중심인지에 대한 판단이었다.

AI 에이전트와 개발하면 작업 자체는 꽤 잘 이어진다. 목표와 범위와 완료 조건은 문서에 남고, 다음 세션도 그걸 읽고 이어서 한다. 잘 이어지지 않는 건 왜 그렇게 했는지다. 왜 이 구조를 골랐는지, 어떤 근거가 약했는지, 어떤 신호가 나오면 그 선택을 다시 열어야 하는지는 거의 남지 않는다. 그래서 다음 작업은 이전 선택을 검토 대상이 아니라 이미 정해진 전제로 받는다.

여기에 측정하기 쉬운 쪽이 먼저 정리되는 문제가 겹친다. 테스트 통과나 완료 체크는 즉시 보이는데, 코드가 다음 변경을 받을 만해졌는지는 느리고 애매하다. 그러다 보면 구현만 된 것, 검사가 통과한 것, 사람이 받아들인 것이 한 덩어리로 섞이고, 다음 세션은 근거 없는 완료에서 출발한다.

문서를 꼼꼼히 쓰는 습관만으로는 잘 안 됐다. 그래서 어떤 내용을 어느 문서가 책임지는지를 먼저 정하고, 그 위에서 읽기와 개발과 기록을 다룬다.

## 맥락을 세 층으로 나눈다

| 층 | 담는 것 | 바뀌는 때 |
| --- | --- | --- |
| Personal | 여러 프로젝트에 가져가는 개인의 판단 기준과 협업 경험 | 사람이 기준을 새로 채택하거나 고칠 때 |
| Project | 한 제품에서 여러 작업에 걸쳐 유지되는 의미, 현재 구조, 계약, 선택 이유 | 제품이나 구현이 바뀔 때 |
| Work | 작업 하나의 목표, 현재 상태, 원자료, 과정 기록 | 그 작업이 진행되는 동안 계속 |

세 층에 공통으로 적용하는 규칙은 두 가지다.

- 같은 사실을 여러 곳에 복사하지 않는다. 실제로 책임지는 문서가 다른 곳에 있으면 그 문서를 가리킨다.
- 아래 층의 결과가 위 층으로 저절로 올라가지 않는다. 한 작업에서 내린 선택이 제품 전체의 기준이 되거나 개인 기준이 되려면 따로 판단해서 옮긴다.

**Personal**에는 지금 개발 판단 다섯 주제가 있다. 무엇을 공통화할지, 계약과 수명, 이름과 완료 시점, 코드 표현과 진단, 디자인 시스템이다. 주제마다 일반 기준을 두고 필요한 곳에는 코드 사례를 붙였다. 사람과 AI가 함께 일하며 얻은 경험과 아직 채택하지 않은 개선 후보도 이 층에 모은다. 기준을 채택할 권한은 사람에게 있다.

**Project**는 정보의 수명에 따라 다시 나눈다. 오래 가는 제품의 의미와 제약(`common`), 자주 바뀌는 현재 구현과 지원 범위(`current`), 작업이 지킬 계약과 기준(`guidance`), 중요한 선택의 이유와 다시 볼 신호(`decisions`)다. 현재 구현과 제품의 의미를 같은 문서에 두면 무엇을 고쳐야 하는지 매번 다시 판단해야 한다.

**Work**는 작업마다 Workspace를 하나 둔다.

```text
reference-project/
├── AGENTS.md                 에이전트가 처음 읽는 진입 지침 (CLAUDE.md는 이 파일의 symlink)
├── .agents/skills/           스킬 원본 (.claude/skills, .codex/skills가 여기를 가리킨다)
├── src/, tests/              샘플 제품과 검사
└── context/
    ├── personal/             개인 기준과 경험
    ├── project/              제품의 의미, 현재 구조, 계약, 결정
    └── work/workspaces/
        └── 001-default-timeout/
            ├── recover.md    재개할 때 무엇을 왜 읽을지 안내
            ├── current/      지금 유효한 목표, Spec, Ticket, 상태
            ├── source/       이 작업이 고른 원자료와 출처
            ├── output/       결과물이 실제로 있는 위치
            └── records/      후보, 비교, 시도, 검증 같은 과정
```

`current/`에는 Spec과 Ticket을 둔다. Spec은 이 작업에서 풀 문제와 이루려는 결과, 그 결과를 판단할 기준이다. Ticket은 Spec의 기준 안에서 확인 가능한 결과를 만드는 실행 단위다. 둘은 크기가 아니라 맡은 책임으로 나눈다. Spec은 사용자가 무엇을 할 수 있어야 하는지와 이번에 하지 않을 것까지 정하지만, 어느 모듈에 넣을지나 기존 추상화를 유지할지는 실제 코드를 보며 정하도록 열어 둔다.

## 작업 한 번의 흐름

고정된 단계가 아니라 필요할 때 쓰는 네 가지 연결이다.

**1. 재개.** 새 세션은 Workspace의 `recover.md`부터 읽는다. 이 파일은 내용을 요약하지 않고 읽을 자료와 이유를 안내한다. 빠지면 목표나 다음 행동을 잘못 이해할 자료는 기본 읽기로, 특정 판단에서만 필요한 자료는 조건과 함께 적는다. 샘플 Workspace의 [`recover.md`](./reference-project/context/work/workspaces/001-default-timeout/recover.md)에서 세 줄을 줄여 옮겼다.

| 요청·판단 | 읽을 자료 |
| --- | --- |
| 기본값·거부 입력·반환값을 설명하거나 수정한다 | Project 맥락 선택 문서, 요구 동작, 입출력 계약을 실제 코드와 대조한다 |
| 왜 `5000`인지, 현재 구현 방식을 유지할지 판단한다 | default-timeout 결정 문서와 제약·설계·가정 |
| 앞선 검증을 다시 근거로 사용한다 | 기록 색인에서 해당 실행을 고르고 당시 조건과 지금의 코드를 대조한다 |

Workspace 전체를 매번 읽히지 않는 것이 목적이다. 안내는 출발점이고, 읽다가 공백이 보이면 에이전트가 범위를 넓힌다.

**2. 개발.** [`development`](./reference-project/.agents/skills/development/SKILL.md) 스킬이 구현부터 검증까지를 잇는다. 역할은 넷이다.

- 전체 담당: 사용자와 대화하는 에이전트. 목표와 맥락을 연결하고, 검토 의견의 채택과 전체 완료를 판단한다.
- 구현자: 맡은 사용 경로를 자기 확인까지 끝낸다. 알고 있는 누락을 검토자에게 넘기지 않는다.
- 개선 검토자: 현재 선택과 의미 있는 대안을 비교한다.
- 검증자: 구현과 수정에 참여하지 않은 채로 요구가 충족됐는지 확인한다.

동작이나 계약이 바뀌는 변경에는 별도 검증자 한 명을 기본으로 두고, 오탈자 같은 변경은 전체 담당의 확인으로 줄인다. 매번 같은 수의 에이전트를 부르는 절차는 아니다.

**3. 기록.** [`record-work`](./reference-project/.agents/skills/record-work/SKILL.md)를 호출하면 기록 담당 에이전트가 대화 원문과 실제 결과를 보고 Work 문서를 직접 고친다. 작업을 정리할 때나 방향이 바뀐 경계에서 부르고, 같은 대화에서는 같은 담당자를 다시 쓴다. 읽을 자료나 이유가 달라졌으면 `recover.md`도 함께 고친다.

**4. 개선.** 사용자가 대화를 돌아보자고 하면 [`improvement-loop`](./reference-project/.agents/skills/improvement-loop/SKILL.md)가 그 대화와 관련 문서에서 개선할 것을 찾아 추천한다. 함께 고른 것은 바로 반영하고, 채택하지 않은 경험과 후보는 Personal에 남겨 다음에 다시 본다. 작업이 끝났다고 자동으로 돌지 않는다.

이 흐름 전체에서 검사 통과, 사람의 수락, 작업 완료를 서로 다른 상태로 다룬다.

## 스킬

기준 프로젝트에 여덟 개가 있다. 원본은 [`reference-project/.agents/skills/`](./reference-project/.agents/skills/README.md)에 있다.

| 스킬 | 쓰는 때 | 하는 일 |
| --- | --- | --- |
| `development` | 기능 구현, 버그 수정, 리팩터링, 결과 검토 | 요구와 맥락을 연결해 구현, 개선 검토, 검증을 조율한다 |
| `record-work` | 기록 요청, 작업 정리 | 대화 원문과 결과를 보고 Work 문서를 갱신한다 |
| `improvement-loop` | 사용자가 대화를 돌아보자고 할 때 | 개선을 찾아 함께 고르고 반영하며 경험을 남긴다 |
| `explain` | 개념, 코드, 결과, 앞선 말의 뜻을 물을 때 | 실제 대상을 근거로 관계와 선택 이유를 설명한다 |
| `work-discussion` | 사용자가 직접 호출할 때만 | 구현 전에 원하는 결과와 경계를 맞춰 Spec으로 구체화한다 |
| `reconsider-work` | 결과, 새 조건, 막힘 때문에 방법이 의심될 때 | 현재 방법이 원래 목표를 이루는지 다시 판단한다 |
| `context-update` | Personal·Project에 지속할 변화가 확인됐을 때 | 허용된 범위에서 해당 본문과 읽기 경로를 고친다 |
| `create-context-workspace` | 새 독립 작업을 시작할 때 | Workspace와 재개 안내를 만든다 |

모든 작업에서 순서대로 실행하는 공통 절차는 두지 않는다. 같은 절차가 실제로 반복되는 게 확인되면 그때 스킬로 더한다. 스킬을 지우거나 바꿔도 각 문서의 내용과 책임은 그대로 남게 했다.

1. [기준 프로젝트 README](./reference-project/README.md): 세 층과 시작점
2. 샘플 Workspace의 [`recover.md`](./reference-project/context/work/workspaces/001-default-timeout/recover.md): 재개 안내가 실제로 어떻게 생겼는지
3. [`development` 스킬](./reference-project/.agents/skills/development/SKILL.md): 역할과 흐름
4. [Personal 개발 판단](./reference-project/context/personal/development/INDEX.md): 개인 기준이 어떤 글인지

샘플 제품은 요청 정책 설정을 읽는 작은 Python 모듈이다. 검사는 이렇게 실행한다.

```bash
cd reference-project && python3 -B -m unittest tests.test_config_loader -v
```

자기 프로젝트에 옮겨 보려면 이 저장소를 연 에이전트에게 대상 경로와 함께 요청한다. 루트의 `apply-context-harness` 스킬이 받는다.

```text
reference-project의 구성을 ~/code/my-app 에 이식해 줘.
context/ 와 .agents/ 아래만 새로 만들고 기존 문서는 건드리지 마.
첫 Workspace는 지금 하고 있는 결제 모듈 분리 작업으로 해 줘.
```

에이전트는 대상의 기존 지침, 문서, Git 상태를 먼저 읽고, 새로 만들 파일과 건드리지 않을 파일의 목록을 보여 준 뒤 승인을 기다린다. 샘플 제품의 내용은 복사하지 않고 Project context를 대상 프로젝트의 실제 사실로 채운다. 대상 프로젝트의 커밋은 따로 승인받기 전에는 하지 않는다.

## 바꿔 온 것

지금 구성은 처음과 많이 다르다.

처음에는 Python 실행기 세 개가 중심이었다. Recover는 새 세션이 읽을 문서 묶음을 만들었고, Maintain은 응답이 끝날 때마다 달라진 내용을 문서에 자동으로 반영했고, Verify는 근거 파일을 고정한 뒤 검사를 실행해 결과를 JSON으로 남겼다.

이 구성을 실제 개발 중인 제품에 이식해 쓴 뒤 사용 경험을 평가했다. 다시 설명하는 일은 줄었다. 하지만 위의 장면처럼 기록을 읽고도 작업의 중심을 다시 잡아 줘야 하거나, 결과 설명을 한 번 더 요청해야 나아지는 일이 남았다. 그래서 범위를 맥락 문서의 구조에서 개발 방법, 설명, 경험 반영으로 넓혔다. `development`, `improvement-loop`와 Personal 층이 그때 생겼고, 설명을 맡던 스킬 두 개는 `explain` 하나로 합쳤다.

세 실행기는 내렸다.

- **Maintain은 `record-work`로 바꿨다.** 매 응답마다 자동으로 도는 비용이 크다고 판단했다. 수치로 측정한 결과는 아니다. 이제 필요할 때 기록 담당자를 부른다.
- **Recover는 `recover.md`로 바꿨다.** 정해진 문서 묶음을 넘기는 대신 읽을 자료와 이유와 조건을 적어 두고 읽는 쪽이 판단하게 했다.
- **Verify는 보관했다.** 제품 검사를 실행하는 데는 필요하지 않았고, 검증 판단은 `development`가 이미 맡고 있었다.

바꾸면서 잃은 것도 있다. 실행 전 입력의 자동 스냅샷, 결과 파일의 자동 저장, 이전 증거가 낡았는지의 자동 비교, 검사 프로세스와 자식 프로세스의 강제 종료는 지금 구성이 제공하지 않는다. 검사 도구와 Git으로 같은 일을 할 수는 있지만 저절로 묶여 실행되지는 않는다.

## 확인한 것과 아직 아닌 것

| 확인한 것 | 아직 확인하지 못한 것 |
| --- | --- |
| 샘플 제품의 검사 7개가 통과한다 | 긴 기간에 걸쳐 맥락이 실제로 유지되는지 |
| 기준 프로젝트의 문서 링크와 스킬 연결이 맞는다 | 에이전트 도구가 스킬을 항상 발견하고 호출하는지 |
| 실제 제품 하나에 이식해 사용했고 재설명이 줄었다 | 기록 담당자가 원문에서 남길 것을 고르는 판단의 품질 |
| 새 세션에서의 재개를 제한된 범위로 시험했다 | 다른 프로젝트와 다른 사람에게도 같은 효과가 나는지 |

Personal을 여러 저장소 사이에서 배포하거나 동기화하는 기능은 없다. 지금은 프로젝트 안의 폴더로 둔다.

## 저장소 지도

- [`reference-project/`](./reference-project/): 기준 프로젝트. 문서, 스킬, 샘플 제품.
- [`.agents/skills/`](./.agents/skills/): 이식 스킬 `apply-context-harness`.
- [`context/workspaces/`](./context/workspaces/): 이 방식을 만든 작업 열다섯 개의 현재 상태와 기록. 끝난 것, 보류한 것, 중단한 것이 함께 있고 접은 이유도 남겼다. 실험 입력과 비교 자료가 포함되어 분량이 많다.
- [`context/source/`](./context/source/): 여러 작업이 참고한 원자료.
- [`AGENTS.md`](./AGENTS.md), [`CODE-QUALITY.md`](./CODE-QUALITY.md): 이 저장소에서 에이전트가 따르는 지침과 코드 작업 기준.

계속 쓰면서 고쳐 나가는 저장소라 구조와 스킬 목록은 바뀐다. 라이선스는 아직 선택하지 않았다.
