# Project context 관리 계약

이 문서는 Project context를 작성·복원·재구성·갱신할 때의 시점, 변경 권한과 영향 범위, 반영 완료 기준을 소유한다. 구조·층별 책임·권위는 [Project README](README.md), 내용 선별·주제 구성·분리는 [구성 기준](REFERENCE/composition.md)이 소유한다. 관리 작업을 수행하는 주체는 이 문서와 구성 기준을 직접 읽고 적용한다.


본문과 형성 자료의 구성·보존은 [공통 관리 원칙](../CONTENT-POLICY.md)을 따른다. 유효한 기존 진입과 상세 기준을 유지하며 형식을 맞추기 위한 분할·빈 형성 자료를 만들지 않는다. 개인 판단 기준은 Personal이 소유하므로 제품 계약에 자동 승격하지 않는다.

## 언제 무엇을 반영하나

여러 작업의 이해·판단·행동에 계속 영향을 줄 변화가 명확해지거나, 사용자가 기존 Project 맥락의 복원·재구성·승인된 Owner 이동을 요청하면 [context-update](../../.agents/skills/context-update/SKILL.md)를 사용한다. 명확해진 경계에서 수행하며 Workspace 종료를 기다리지 않는다. 작업 완료 자체는 새 Project 문서를 만들 근거가 아니다.

현재 Workspace와 요청에 필요한 source·record·output, 관련 제품 문서와 코드·테스트만 대조한다. 일시적인 방법·후보 전체·실행 이력은 Work에 남기고, 계속 필요한 의미는 기존 주제의 본문에 통합한다. 코드에 있다는 이유로 의미를 제외하거나 모든 구현 사실을 문서에 복제하지 않는 판단은 구성 기준을 따른다.

과거 자료는 현재 뜻과 대체 관계를 확인하는 근거다. 조사 범위에서 허용한 자료만 읽고, archive·source·날짜별 record의 원문을 현재 답으로 덮어쓰지 않는다. 중요한 선택 이유를 별도로 남길지는 [decisions 기준](decisions/README.md)에 따른다.

## 근거와 결정 권한

현재 권위가 확인되었거나 사용자가 재구성을 허용한 기존 의미는 근거를 추적할 수 있게 복원한다. 확인된 사실의 재서술, 유효한 의미의 통합과 미정·미확인·충돌의 보존은 새 제품 결정을 내리는 것과 다르다. 초안·과거 계획·현재 구현만으로 제품 요구나 Project-wide 계약이 채택되지는 않는다.

새로운 제품 목적·핵심 domain 의미·중요 제약이나 상충하는 근거 사이의 선택은 사용자 또는 명시된 책임자가 결정한다. 이미 승인된 범위의 반영을 같은 결정 요청으로 되돌리지 않는다. 충돌 때문에 확정할 수 없는 부분만 구체적으로 남기고, 근거가 지지하는 나머지는 충분히 서술한다.

문서와 코드가 다르면 문서의 권위, 채택한 결정과 실제 구현을 함께 대조한다. 구현 사실의 요약 오류는 직접 근거에 맞추되, 구현과 제품 기준의 차이를 제품 정책 변경으로 조용히 해소하지 않는다.

하나의 사실 문장이 입력·저장·runtime·응답처럼 여러 경계를 함께 설명하면 포함된 실제 경계를 각각 대조한다. 일부 경로만 확인했다면 Project 전체의 공통 동작처럼 넓히지 않고 확인한 경로로 표현을 좁힌다. 경계마다 구현이 다르면 사실의 차이와 어떤 표현을 채택할지는 구별한다.

## 바뀐 의미와 실제 영향을 따라 갱신한다

변경된 의미를 소유한 기준 본문부터 맞춘다. 새 내용을 끝에 누적하기보다 기존 구성에 통합하고, 대체된 설명·조건·현재 상태는 함께 정리한다. 분리·통합할 필요는 구성 기준으로 판단하며 책임 층이나 원자료 수를 파일 수로 바꾸지 않는다.

이어 그 변화 때문에 설명·적용·판단·읽기 경로가 실제로 달라지는 문서를 맞춘다. 다른 본문의 짧은 전제 재서술도 영향을 받으면 갱신 대상이다. 단순히 링크로 연결됐다는 이유만으로 전부 수정하지 않는다.

문서의 읽을 조건도 내용의 일부로 관리한다. 주제 범위·이름·경로가 달라지면 Project README와 해당 층의 색인뿐 아니라 같은 작업을 시작시키는 active runbook·workspace guide·호환 문서·skill에서 실제 Owner까지 이어지는지 대조한다. 문서가 없는 상태나 Project README 한 경로만 성공한 상태를 완성된 소비 경로처럼 보이지 않게 한다.

## 승인된 주제별 Owner 이동

기존 상세 Owner의 현재 의미를 Project로 옮기는 승인은 주제·책임 범위로 한정할 수 있다. 승인된 범위는 의미와 권위를 함께 전환하되 관련 없는 문서 전체 개편으로 넓히지 않는다.

1. 이동할 의미와 반복해서 읽을 작업, 기존 기준 본문과 현재 소비자를 확인한다. 초안을 쓰기 전에 기존 Owner에서 보존할 의미, 직접 근거로 다시 확인할 사실, 새 결정 없이는 닫을 수 없는 선택, Owner 변경으로 영향받는 진입 경로를 구분한다. 이 구분은 영구 표 양식을 요구하지 않지만 초안 뒤 누락과 권한 확대를 대조할 기준으로 유지한다.
2. 구성 기준으로 온전한 주제 본문을 구성하고 주 책임에 맞는 층에 둔다. 모든 주제에 세 층의 문서를 만들거나 분류를 위해 의미를 흩뜨리지 않는다.
3. 기존 자료의 유효한 뜻을 새 Owner에 통합한다. 제품 선택이 필요한 충돌은 구체적으로 열어 두고 나머지를 먼저 반영한다. 초안 뒤에는 1단계에서 잡은 의미가 보존·갱신·의도적 제외 중 어디에 놓였는지 다시 대조한다.
4. 이전 문서는 실제 남은 역할에 따라 구현 상세·근거·역사·호환 routing으로 좁히거나 현재 문서 규칙에 따라 이동·제거한다. 같은 현재 답을 독립적으로 소유하는 경쟁 canonical을 남기지 않는다.
5. 주제별 진입점과 영향받는 live Workspace의 선택·사람용 current·output을 [Workspace collection의 reconciliation 계약](../work/workspaces/README.md)에 따라 맞춘다. 과거 Workspace 전체를 역동기화하지 않는다.

새 파일이 존재한다는 사실만으로 이동이 끝나지 않는다. 선택된 본문에서 해당 의미와 적용·열린 판단을 이해할 수 있고, 이전 문서와 현재 권위 관계가 하나로 이어져야 한다.

## 반영 완료 확인

새로 구성하거나 크게 재구성했다면 [읽기 기준](REFERENCE/reading.md)으로 다음 독자가 맡을 대표 관련 작업을 정하고, Project README에서 필요한 본문을 찾아 적용해 본다. 작성 중 읽은 원자료나 대화의 기억으로 본문의 빈칸을 대신하지 않는다. 모든 문서에 같은 항목이나 목차를 채우지는 않는다.

핵심 뜻을 상세 Owner에서 다시 조립해야 하거나 경로와 방어적 한계만 남았다면 미완성이다. 본문에서 의미를 이해한 뒤 실제 코드·자료와 대조하여 사실·권위·검증 범위가 맞는지 확인한다. 필요한 내용은 충분히 유지하면서 무관한 읽기를 늘리지 않았는지도 본다.

Owner 이동이나 큰 재구성은 다음 관계를 따로 확인한다.

- 기존 Owner의 유효한 의미가 새 기준 본문에 보존됐는지 의미 단위로 대조한다.
- 여러 구현 경계를 설명하는 사실은 직접 확인한 경로 범위와 문장의 범위가 맞는지 대조한다.
- Project README와 기존 작업 진입점에서 시작한 대표 작업이 같은 현재 Owner와 필요한 적용 본문에 도달하는지 따라가 본다.

이 대조는 고정된 체크리스트 파일이나 독립 검토를 매번 만들라는 요구가 아니다. 다만 link·diff·문서 수와 작성자의 기억만으로 세 관계를 확인했다고 간주하지 않는다.

일반 갱신에서는 바뀐 기준과 그 기준을 소비하는 설명이 함께 맞는지 확인한다. `current`는 관련 가이드와 코드를 읽은 뒤에도 그 본문이 추가로 가능하게 하는 판단, 그 판단을 다시 확인할 신호와 갱신 비용으로 평가한다. 구체적인 실행 수치나 당시 환경 오류가 이 관계를 설명하지 못하면 Work의 기록으로 연결한다.

Local link·diff·설치 검사는 경로와 형식을 확인할 뿐 의미 충분성이나 실제 읽기 효과를 증명하지 않는다. 작성자의 대조, 다른 독자의 적용, 실제 제품 실행으로 확인한 결과를 구별하며 독립 검토를 매번 필수 절차로 추가하지 않는다. 문서 갱신을 제품 검증·acceptance·Workspace 완료로 확대하지 않는다.

## 실행 장치와 보고 경계

[context-update](../../.agents/skills/context-update/SKILL.md)는 이 계약을 실행하는 절차다. Workspace Maintain의 쓰기 범위를 Project 문서로 넓히지 않는다. 현재 Workspace의 Project 선택을 바꿀 필요가 있으면 기존 Work Owner에 연결하고, path·책임·authority 변경이 live consumer에 영향을 주면 reconciliation 계약을 따른다.

반영한 현재 내용과 근거, 아직 남은 판단, 근거가 있어도 반영하지 못한 내용과 이유를 보고한다. Skill을 교체하거나 제거해도 사람이 이 문서와 각 내용 Owner를 따라 같은 갱신 책임을 수행할 수 있어야 한다.
